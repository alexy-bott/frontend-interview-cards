## Вопрос

<br>

 💬 **Зачем нужен `package.json`? Чем отличаются `dependencies`, `devDependencies` и `peerDependencies`?**

<h2></h2>

<br>
<dl>
<dd>

`package.json` является манифестом Node.js-проекта: он описывает пакет, команды, зависимости, поддерживаемое окружение и настройки инструментов. По этому файлу разработчик и CI понимают, как установить, запустить, проверить и собрать проект.

Для frontend-приложения особенно важны следующие поля:

| Поле | Назначение |
| --- | --- |
| `scripts` | Команды разработки, проверки и сборки |
| `dependencies` | Библиотеки, необходимые приложению или потребителю публикуемого пакета |
| `devDependencies` | Инструменты разработки, тестирования и сборки |
| `peerDependencies` | Совместимые host-зависимости, общие для библиотеки и проекта-потребителя |
| `engines` | Поддерживаемые версии Node.js и иногда менеджера пакетов |
| `packageManager` | Ожидаемый менеджер пакетов и его конкретная версия |
| `type` | Интерпретация `.js` как ESM или CommonJS в Node.js |
| `browserslist` | Целевые браузеры для инструментов, поддерживающих Browserslist |
| `private` | Запрет случайной публикации пакета |

`scripts` задаёт единый интерфейс команд. Например, `npm run build` запускает значение `scripts.build`. Во время запуска менеджер пакетов добавляет локальные исполняемые файлы из `node_modules/.bin` в `PATH`, поэтому используется установленная в проекте версия Vite, Jest или ESLint, а не неизвестная глобальная версия.

```json
{
  "private": true,
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "test": "jest",
    "lint": "eslint ."
  },
  "dependencies": {
    "react": "^19.0.0"
  },
  "devDependencies": {
    "typescript": "^5.8.0",
    "vite": "^8.0.0"
  }
}
```

`dependencies` обычно содержат React, маршрутизатор, менеджер состояния и другие библиотеки, необходимые коду приложения. В публикуемом пакете эти зависимости устанавливаются потребителю вместе с пакетом.

`devDependencies` содержат TypeScript, сборщик, test runner, линтеры и плагины. Они нужны для разработки, проверки и формирования готового артефакта, но не должны устанавливаться потребителю библиотеки как её runtime-зависимости.

Для frontend-приложения обе группы обычно нужны на стадии сборки. После сборки статического SPA хостинг раздаёт готовые HTML, CSS и JavaScript и не запускает Vite или TypeScript. При production-only установке менеджер пакетов также может исключить `devDependencies`.

Группа в `package.json` сама по себе не решает, попадёт ли модуль в браузерный бандл. Это определяют граф импортов, настройки сборщика и tree shaking.

Если код из `devDependencies` импортирован приложением, сборщик способен включить его в результат или завершить сборку ошибкой. И наоборот, пакет из `dependencies`, который не используется клиентским графом импортов, не попадает в JavaScript только из-за записи в манифесте.

`peerDependencies` особенно важны для библиотек и плагинов. Они описывают совместимость с host-пакетом, экземпляр которого должен быть общим с приложением-потребителем.

Например, компонентная библиотека указывает React как peer dependency:

```json
{
  "peerDependencies": {
    "react": "^18.0.0 || ^19.0.0",
    "react-dom": "^18.0.0 || ^19.0.0"
  }
}
```

Так библиотека сообщает, с какими версиями React совместима, и использует React из общего dependency graph приложения, а не полагается на отдельную независимую копию.

Современный менеджер пакетов может автоматически установить отсутствующую peer dependency, но итоговый граф всё равно должен содержать совместимую версию. При конфликте менеджер выводит предупреждение или завершает установку ошибкой в зависимости от инструмента и настроек.

В самой библиотеке React часто дополнительно находится в `devDependencies`:

```json
{
  "peerDependencies": {
    "react": "^18.0.0 || ^19.0.0"
  },
  "devDependencies": {
    "react": "^19.0.0"
  }
}
```

Здесь:

- `peerDependencies` описывает требование к потребителю;
- `devDependencies` предоставляет React для локальной разработки, сборки и тестов библиотеки.

Необязательную peer dependency можно описать через `peerDependenciesMeta`:

```json
{
  "peerDependencies": {
    "some-plugin": "^2.0.0"
  },
  "peerDependenciesMeta": {
    "some-plugin": {
      "optional": true
    }
  }
}
```

`package.json` задаёт диапазоны версий, но не фиксирует точное установленное дерево зависимостей. Эту задачу выполняет lock-файл.

Поля `packageManager` и `engines` тоже решают разные задачи:

```json
{
  "packageManager": "pnpm@11.0.0",
  "engines": {
    "node": ">=22"
  }
}
```

`packageManager` указывает ожидаемый менеджер и обычно его конкретную версию. Это поле могут использовать Corepack и другие инструменты.

`engines` описывает поддерживаемое окружение. Строгость проверки зависит от менеджера пакетов и его конфигурации: например, npm без `engine-strict` обычно воспринимает несовпадение как предупреждение.

Современные менеджеры также могут поддерживать `devEngines.packageManager`:

```json
{
  "devEngines": {
    "packageManager": {
      "name": "pnpm",
      "version": ">=11 <12",
      "onFail": "error"
    }
  }
}
```

Поддержка, допустимый формат версии и реакция на несовпадение зависят от конкретного менеджера. Поэтому CI всё равно должен явно выбирать нужные версии Node.js и package manager.

Для публикуемого пакета дополнительно важны:

- `exports`;
- `types`;
- `files`;
- `main`;
- иногда `module`;
- используемое сборщиками поле `sideEffects`.

Они определяют публичные точки импорта, декларации TypeScript, содержимое npm-архива и возможность удалить неиспользуемый код при сборке.

В обычном закрытом SPA многие из этих полей не нужны.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему scripts запускают через менеджер пакетов, а не глобальную команду?</strong></summary>

<dl>
<dd>
<h2></h2>

Менеджер пакетов добавляет локальные исполняемые файлы из `node_modules/.bin` в `PATH` процесса script:

```json
{
  "scripts": {
    "build": "vite build"
  }
}
```

Команда использует установленную в проекте версию Vite, связанную с `package.json` и lock-файлом.

Глобальная установка может отличаться у разработчиков и в CI, из-за чего одинаковая команда даст разный результат.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли пакет из <code>devDependencies</code> попасть в production-бандл?</strong></summary>

<dl>
<dd>
<h2></h2>

Да, если клиентский код его импортирует.

Раздел `devDependencies` описывает назначение пакета при установке и публикации, а не правило включения в бандл.

Например, случайный импорт тестовой утилиты из production-модуля способен:

- включить её код в бандл;
- увеличить его размер;
- привести к ошибке сборки;
- добавить несовместимый с браузером код.

Состав бандла определяют граф импортов и сборщик.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему Vite обычно находится в <code>devDependencies</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Vite нужен для:

- сервера разработки;
- преобразования модулей;
- формирования production-файлов.

Но он не выполняется в браузере как часть собранного приложения.

После сборки статического SPA хостинг раздаёт готовые:

- HTML;
- CSS;
- JavaScript;
- статические ресурсы.

Для приложения с серверным рендерингом отдельно определяют, какие зависимости нужны серверному процессу во время выполнения, а какие используются только при сборке.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>peerDependencies</code> отличаются от <code>dependencies</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`dependencies` включаются в обычный dependency graph пакета и устанавливаются потребителю вместе с ним.

`peerDependencies` описывают совместимость с host-библиотекой или инструментом, которые должны использоваться совместно с потребителем:

```text
React-компонентная библиотека
→ React приложения

ESLint plugin
→ ESLint проекта

Webpack plugin
→ Webpack проекта
```

Современный менеджер пакетов может автоматически установить отсутствующий peer, но должен подобрать совместимую версию в общем dependency graph.

Библиотека часто указывает одну зависимость одновременно:

- в `peerDependencies` — как требование к потребителю;
- в `devDependencies` — для собственной разработки и тестов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает поле <code>type</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

В Node.js:

```json
{
  "type": "module"
}
```

интерпретирует `.js` как ESM.

```json
{
  "type": "commonjs"
}
```

явно интерпретирует `.js` как CommonJS.

Расширения задают формат независимо от поля:

```text
.mjs
→ ESM

.cjs
→ CommonJS
```

Без `type` файл `.js` становится неоднозначным. Современный Node.js может применять определение синтаксиса, но авторам пакетов рекомендуется указывать формат явно, чтобы поведение не зависело от версии runtime и анализа содержимого файла.

Поле влияет прежде всего на Node.js-скрипты, серверный код и конфигурационные файлы. Сборщик frontend-приложения может использовать собственные правила преобразования модулей.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем одновременно нужны <code>packageManager</code> и <code>engines</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`packageManager` указывает ожидаемый инструмент и обычно его конкретную версию:

```json
{
  "packageManager": "pnpm@11.0.0"
}
```

`engines.node` описывает допустимый диапазон Node.js:

```json
{
  "engines": {
    "node": ">=22"
  }
}
```

`packageManager` могут использовать Corepack и другие инструменты выбора package manager.

Строгость `engines` зависит от менеджера и настроек. Например, npm без `engine-strict` обычно выводит предупреждение.

`devEngines.packageManager` может дополнительно проверять окружение разработчиков и в некоторых менеджерах поддерживать диапазон версий:

```json
{
  "devEngines": {
    "packageManager": {
      "name": "pnpm",
      "version": ">=11 <12",
      "onFail": "error"
    }
  }
}
```

CI всё равно должен явно устанавливать требуемые версии инструментов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем ставить <code>private: true</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Поле:

```json
{
  "private": true
}
```

заставляет npm отказаться от публикации пакета и защищает закрытое приложение от случайного:

```bash
npm publish
```

Для корня monorepo оно также часто показывает, что корневой пакет используется для организации workspace, а не предназначен для отдельной публикации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужны <code>overrides</code> или <code>resolutions</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Они принудительно выбирают версию транзитивной зависимости, которую нельзя обновить обычным изменением прямой зависимости.

Это бывает нужно для:

- временного исправления уязвимости;
- устранения конфликта;
- замены пакета исправленным fork;
- унификации версии во всём дереве.

Название и место настройки зависят от менеджера пакетов:

- npm использует `overrides`;
- Yarn использует `resolutions`;
- pnpm предоставляет собственный механизм overrides в соответствии со своей конфигурацией и версией.

В npm учитывается `overrides` только из корневого `package.json`.

Принудительная версия может нарушить ожидания родительского пакета. Поэтому причину фиксируют в PR, проверяют тестами, а временное правило удаляют после обычного обновления зависимости.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Задача | Поле или команда |
| --- | --- |
| Запустить одинаковую сборку локально и в CI | `scripts.build` |
| Зафиксировать менеджер пакетов | `packageManager` |
| Проверить инструменты разработчиков | `devEngines` при поддержке менеджером |
| Ограничить версию Node.js | `engines` и настройка CI |
| Не опубликовать приложение случайно | `private: true` |
| Подключить React как требование библиотеки | `peerDependencies` |
| Использовать React при разработке библиотеки | `devDependencies` |
| Защититься от проблемной вложенной версии | `overrides`, `resolutions` или аналог менеджера |
