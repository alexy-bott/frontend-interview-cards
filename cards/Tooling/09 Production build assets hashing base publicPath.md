## Вопрос

Что нужно проверить в production-сборке: хеширование файлов, заголовки кеширования, `base`/`publicPath`, fallback для SPA и согласованность развёртывания?

<details>
<summary><strong>Показать ответ</strong></summary>

Production-сборка, то есть сборка для рабочей среды, должна сформировать согласованный набор оптимизированных HTML, JavaScript, CSS, изображений, шрифтов и карт исходного кода. Работа сервера разработки не доказывает корректность этого набора: во время разработки иначе преобразуются модули, строятся URL и подставляются переменные окружения.

Content hash, или хеш содержимого, зависит от байтов файла и добавляется в его имя, например `app.a81f2c.js`. Такой неизменяемый ресурс можно кешировать надолго:

```http
Cache-Control: public, max-age=31536000, immutable
```

При изменении файла меняется хеш и, следовательно, его URL. Браузер запрашивает новый ресурс, не используя старую копию из кеша. HTML обычно не получает директиву `immutable`, потому что в нём находятся ссылки на ресурсы текущей версии. Для HTML применяют `no-cache` с повторной проверкой актуальности на сервере либо небольшой `max-age`.

`base` в Vite и `output.publicPath` в Webpack задают основу публичных URL для ресурсов и динамически загружаемых чанков. Чанк является отдельной частью бандла, которую браузер может запросить позже. Эти настройки описывают URL, а не физический каталог на диске. Если приложение размещено по пути `/app/` или файлы находятся на CDN, сборщик должен добавить правильный префикс. Иначе HTML откроется, а CSS или динамический `import()` вернёт 404.

В SPA переходы между страницами обрабатывает клиентский маршрутизатор. Но при прямом запросе `/profile/settings` веб-сервер сначала ищет физический файл и без специального правила возвращает 404. Нужен fallback, то есть возврат `index.html` для клиентских маршрутов. Запросы к `/api`, существующим ресурсам и действительно отсутствующим файлам нельзя безусловно превращать в HTML с кодом 200.

Развёртывание должно быть атомарным: пользователь должен получать файлы одной версии. Проблема возникает, если новый HTML уже опубликован, а новые чанки ещё не загружены, либо старые чанки удалены, пока открытая вкладка продолжает использовать старый код сборщика. В результате браузер получает `ChunkLoadError`, и приложение может показать белый экран.

Практические меры:

1. Создавать один версионированный артефакт сборки и разворачивать его целиком.
2. Загружать новые ресурсы с хешами до переключения HTML.
3. Не удалять старые чанки сразу, если открытые вкладки ещё могут их запросить.
4. Задавать разные заголовки кеширования для HTML и неизменяемых ресурсов.
5. После переключения выполнять smoke-тесты, то есть короткие проверки ключевых сценариев.
6. Поддерживать откат на предыдущий согласованный артефакт.

Обработчик ошибки загрузки чанка может один раз предложить перезагрузить страницу, но не должен запускать бесконечный цикл перезагрузок. Сначала нужно устранить причину: неверный путь, слишком раннее удаление старых файлов, устаревший service worker или несогласованный кеш CDN.

Перед развёртыванием в CI запускают проверку типов, тесты и production-сборку. Затем проверяют отчёт сборщика, лимит размера бандла, загрузку карт исходного кода, конфигурацию окружения и известные маршруты. Локальный `vite preview` или статический сервер подходит для первичной проверки, но реальные заголовки, CDN и fallback нужно проверять в окружении, близком к рабочему.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Зачем нужен <code>contenthash</code>?</summary>

Он создаёт новый URL только при изменении содержимого файла. Браузер и CDN могут долго хранить неизменившийся ресурс, а новая версия получит другое имя и не потребует ручной очистки старого URL. Хеш стоит добавлять в имена всех ресурсов и чанков, для которых используется длительное кеширование.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему HTML не кэшируют как hashed JavaScript?</summary>

URL HTML часто остаётся тем же, но внутри находится список чанков текущего релиза. Долгое кеширование с `immutable` сохранит старую точку входа, которая будет ссылаться на устаревшие файлы. Поэтому браузер должен повторно проверять актуальность HTML, тогда как файлы с хешем можно считать неизменяемыми.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему обновление страницы на <code>/dashboard</code> возвращает 404?</summary>

При переходе внутри приложения маршрут обработал клиентский JavaScript-маршрутизатор. При обновлении страницы запрос сначала получает веб-сервер, который не находит физический файл `/dashboard`. Для клиентских маршрутов SPA настраивают возврат `index.html`, сохраняя отдельные правила для API и статических ресурсов.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем <code>base</code> отличается от <code>publicPath</code>?</summary>

Они решают близкую задачу в разных инструментах: задают основу URL, по которой HTML и код сборщика находят ресурсы. `base` является общей настройкой Vite, а `output.publicPath` принадлежит Webpack. Точное поведение HTML и динамических `import()` нужно проверять в используемом сборщике.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему после развёртывания возникает <code>ChunkLoadError</code>?</summary>

Открытая вкладка или устаревший HTML запрашивает чанк, которого уже нет, либо код сборщика формирует неверный URL. Причиной также бывает service worker или CDN с файлами разных релизов. На вкладке Network проверяют фактический URL и HTTP-статус, затем политику кеширования и атомарность развёртывания.

</details>

<details>
<summary><strong>Вопрос:</strong> Что означает атомарное развёртывание?</summary>

Все файлы релиза публикуются как единая версия, а трафик переключается только после их готовности. Пользователь не должен получить HTML новой версии со старыми чанками. Каталоги с номером версии и неизменяемые артефакты упрощают переключение и откат.

</details>

<details>
<summary><strong>Вопрос:</strong> Нужно ли удалять старые ресурсы с хешами?</summary>

Да, но не сразу после каждой выкладки. Открытая вкладка со старой версией приложения может запросить лениво загружаемый чанк позже. Срок хранения выбирают с учётом длительности пользовательских сессий и стоимости хранилища, а очистка не должна затрагивать активные релизы.

</details>

<details>
<summary><strong>Вопрос:</strong> Что обязательно проверить перед развёртыванием в рабочей среде?</summary>

Нужны чистая установка зависимостей и успешная сборка, правильный адрес API, URL ресурсов, прямое открытие вложенных маршрутов, заголовки кеширования, динамические импорты, загрузка карт исходного кода и ключевой smoke-сценарий. Проверять нужно собранный артефакт, а не только приложение на сервере разработки.

</details>

## Где это встречается во frontend

| Симптом | Что проверить |
| --- | --- |
| Ресурсы возвращают 404 | `base`, `publicPath`, адрес CDN |
| Вложенный URL возвращает 404 | SPA fallback |
| Пользователь видит старую версию | Кеш HTML и service worker |
| `ChunkLoadError` после релиза | Старые чанки и атомарность развёртывания |
| Кеш не используется | Хеш содержимого и заголовки кеширования |
| Не удалось восстановить место ошибки | Карта исходного кода и идентификатор релиза |
