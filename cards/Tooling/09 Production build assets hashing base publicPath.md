## Вопрос

<br>

 💬 **Что нужно проверить в production-сборке: хеширование файлов, заголовки кеширования, `base`/`publicPath`, fallback для SPA и согласованность развёртывания?**

<h2></h2>

<br>
<dl>
<dd>

Production-сборка, то есть сборка для рабочей среды, должна сформировать согласованный набор оптимизированных HTML, JavaScript, CSS, изображений, шрифтов и других ресурсов. Карты исходного кода также могут создаваться во время сборки, но обычно их отдельно загружают в систему мониторинга и не публикуют вместе с приложением.

Работа сервера разработки не доказывает корректность production-сборки. Во время разработки иначе преобразуются модули, строятся URL ресурсов, обрабатываются динамические импорты и подставляются переменные окружения. Поэтому перед релизом нужно проверять именно собранный артефакт.

Content hash, или хеш содержимого, зависит от содержимого файла и добавляется в его имя, например `app.a81f2c.js`. Если содержимое изменится, изменятся хеш и URL файла. Неизменяемые ресурсы с такими именами можно кешировать надолго:

```http
Cache-Control: public, max-age=31536000, immutable
```

Браузер может использовать старый файл по прежнему URL, потому что его содержимое уже никогда не должно изменяться. После новой сборки HTML будет ссылаться на новый URL с другим хешем, и браузер загрузит новый ресурс.

HTML обычно не получает длительное кеширование с `immutable`, потому что его URL часто остаётся прежним, а внутри находятся ссылки на ресурсы текущего релиза. Для HTML часто используют:

```http
Cache-Control: no-cache
```

`no-cache` не запрещает хранить HTML в кеше. Директива требует проверить его актуальность на сервере перед повторным использованием. Если файл не изменился, сервер может ответить `304 Not Modified`; если изменился — вернуть новую версию. Другой вариант — небольшой `max-age`, если продукт допускает короткий период использования старого HTML.

`base` в Vite и `output.publicPath` в Webpack связаны с публичными URL ресурсов, но принадлежат разным инструментам и имеют собственные правила.

`base` в Vite задаёт базовый публичный путь приложения и используется при формировании URL для JavaScript, CSS, изображений и динамических импортов. `output.publicPath` в Webpack задаёт URL-префикс, откуда служебный код Webpack загружает созданные ресурсы и асинхронные чанки.

Эти настройки описывают URL в браузере, а не физический каталог на диске. Если приложение размещено по пути `/app/` или ресурсы загружаются с CDN, сборщик должен сформировать соответствующие адреса. Иначе HTML может открыться, но CSS, изображение или динамический `import()` вернёт 404.

В SPA переходы между страницами обрабатывает клиентский маршрутизатор. При переходе внутри приложения сервер обычно не получает отдельный запрос HTML для каждого маршрута.

Но при прямом открытии или обновлении `/profile/settings` запрос сначала приходит на веб-сервер. Если физического файла с таким путём нет, сервер без дополнительной настройки вернёт 404. Для клиентских маршрутов нужен fallback — возврат `index.html`, после чего нужный экран определит frontend-маршрутизатор.

Fallback нельзя безусловно применять ко всем запросам. Запросы к `/api`, существующим статическим ресурсам и действительно отсутствующим файлам должны сохранять свои обычные ответы и статусы. Иначе запрос отсутствующего JavaScript может получить HTML с кодом 200, что усложнит диагностику.

Развёртывание должно сохранять согласованность HTML и ресурсов. Новый HTML должен публиковаться только после того, как все JavaScript, CSS и другие файлы, на которые он ссылается, уже доступны.

Проблема возникает в двух основных случаях:

1. Новый HTML уже опубликован, а часть новых ресурсов ещё отсутствует.
2. Старые ресурсы удалены, хотя открытая вкладка со старой версией приложения всё ещё может запросить лениво загружаемый чанк.

В обоих случаях динамический импорт может завершиться ошибкой `ChunkLoadError`, а приложение — показать сломанный экран.

Практические меры:

1. Создавать один версионированный артефакт сборки и не пересобирать его между проверкой и публикацией.
2. Загружать новые ресурсы с хешами до переключения HTML или атомарно переключать весь каталог релиза.
3. Не перезаписывать содержимое файлов, URL которых содержит старый хеш.
4. Не удалять старые чанки сразу, если открытые вкладки ещё могут их запросить.
5. Задавать разные заголовки кеширования для HTML и неизменяемых ресурсов.
6. После переключения выполнять smoke-тесты, то есть короткие проверки ключевых сценариев.
7. Поддерживать откат на предыдущий согласованный артефакт.

`ChunkLoadError` не всегда означает ошибку развёртывания. Его также может вызвать временная проблема сети, неверный `base` или `publicPath`, устаревший кеш CDN либо service worker, который смешал HTML и ресурсы разных версий.

Обработчик ошибки загрузки чанка может предложить пользователю обновить страницу. Автоматическую перезагрузку допустимо выполнять не более одного раза и только после проверки, что ошибка может быть связана с появлением новой версии. Иначе временная сетевая ошибка способна запустить бесконечный цикл перезагрузок.

Перед развёртыванием в CI запускают чистую установку зависимостей, проверку типов, тесты и production-сборку. Затем проверяют:

- состав и размер бандла;
- правильность переменных окружения;
- URL начальных и динамических ресурсов;
- загрузку карт исходного кода в систему мониторинга;
- прямое открытие клиентских маршрутов;
- основные пользовательские сценарии.

Локальный `vite preview` или другой статический сервер подходит для первичной проверки файлов сборки. Но он не воспроизводит автоматически реальные заголовки кеширования, CDN, reverse proxy, SPA fallback и поведение service worker. Эти части нужно дополнительно проверять в staging или другом окружении, близком к рабочему.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Зачем нужен <code>contenthash</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`contenthash` добавляет в имя файла значение, зависящее от его содержимого. Если содержимое файла меняется, новая сборка создаёт другой URL.

Это позволяет разделить ресурсы на две группы:

- старый URL всегда обозначает прежнее неизменяемое содержимое;
- новый URL обозначает новую версию ресурса.

Браузер и CDN могут долго кешировать файлы с хешами без ручной очистки кеша. Хеш стоит добавлять в имена JavaScript, CSS и других ресурсов, для которых применяется длительное кеширование.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему HTML не кэшируют как hashed JavaScript?</strong></summary>

<dl>
<dd>
<h2></h2>

URL HTML часто остаётся прежним, но содержимое меняется при каждом релизе: в нём появляются ссылки на новые JavaScript и CSS с другими хешами.

Если сохранить HTML надолго с директивой `immutable`, браузер продолжит открывать старую точку входа и обращаться к ресурсам предыдущего релиза.

Поэтому HTML обычно заставляют повторно проверять на сервере с помощью `Cache-Control: no-cache` либо задают ему небольшой срок кеширования. Ресурсы с хешами при этом можно хранить долго как неизменяемые.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>no-cache</code> не означает полный запрет кеширования?</strong></summary>

<dl>
<dd>
<h2></h2>

Директива `no-cache` разрешает браузеру сохранить ответ, но запрещает повторно использовать его без проверки актуальности на сервере.

При следующем запросе браузер может отправить условный запрос с `ETag` или `Last-Modified`. Если файл не изменился, сервер ответит `304 Not Modified`, и браузер использует сохранённую копию без повторной передачи всего HTML.

Полный запрет хранения задаёт директива `no-store`. Для обычного публичного HTML она требуется не всегда, потому что повторная проверка через `no-cache` позволяет экономить трафик и одновременно получать актуальную версию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему обновление страницы на <code>/dashboard</code> возвращает 404?</strong></summary>

<dl>
<dd>
<h2></h2>

При переходе внутри приложения маршрут обработал клиентский JavaScript-маршрутизатор. При обновлении страницы браузер отправляет прямой запрос `/dashboard` на веб-сервер.

Сервер пытается найти физический файл или серверный маршрут с таким адресом. Если его нет, возвращается 404.

Для клиентских маршрутов SPA настраивают возврат `index.html`. При этом отдельные правила для API, статических ресурсов и отсутствующих файлов должны продолжать возвращать корректные ответы, а не HTML для любого URL.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>base</code> отличается от <code>publicPath</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Обе настройки участвуют в формировании публичных URL ресурсов, но относятся к разным сборщикам.

`base` — общая настройка Vite для базового публичного пути приложения. Vite учитывает её при формировании URL в HTML, JavaScript, CSS и динамических импортах.

`output.publicPath` — настройка Webpack, которая сообщает служебному коду сборщика, откуда загружать созданные файлы и асинхронные чанки.

Они решают близкую задачу, но не являются одной и той же настройкой. Точное поведение нужно проверять в используемом сборщике и в реальном окружении размещения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему после развёртывания возникает <code>ChunkLoadError</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Частые причины:

- открытая вкладка со старым кодом запрашивает уже удалённый чанк;
- новый HTML опубликован раньше новых ресурсов;
- `base` или `publicPath` формирует неправильный URL;
- CDN отдаёт файлы разных релизов;
- service worker возвращает устаревший HTML или runtime;
- запрос завершился временной сетевой ошибкой.

На вкладке Network сначала проверяют фактический URL, HTTP-статус и тип ответа. Затем проверяют заголовки кеширования, активный service worker, содержимое CDN и порядок развёртывания.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означает атомарное развёртывание?</strong></summary>

<dl>
<dd>
<h2></h2>

Атомарное развёртывание означает, что пользователь не видит промежуточное состояние релиза.

Сначала все файлы новой версии полностью загружаются и проверяются. Только после этого сервер, CDN, ссылка или каталог переключается на новый HTML.

Пользователь не должен получить HTML, который ссылается на ещё не опубликованные ресурсы. Версионированные каталоги и неизменяемые артефакты упрощают переключение между релизами и откат.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли удалять старые ресурсы с хешами?</strong></summary>

<dl>
<dd>
<h2></h2>

Да, но не сразу после каждой выкладки. Открытая вкладка может продолжать выполнять JavaScript предыдущего релиза и запросить старый лениво загружаемый чанк через несколько минут или часов.

Срок хранения выбирают с учётом продолжительности пользовательских сессий, частоты релизов и стоимости хранилища. Очистка не должна затрагивать текущий релиз, предыдущие активные релизы и версии, на которые ещё могут ссылаться сохранённые HTML или service worker.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что обязательно проверить перед развёртыванием в рабочей среде?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно проверить:

1. Чистую установку зависимостей и успешную production-сборку.
2. Правильные значения публичной конфигурации и адрес API.
3. Загрузку начальных файлов и динамических чанков.
4. Правильность `base` или `publicPath`.
5. Прямое открытие вложенных маршрутов SPA.
6. Заголовки кеширования HTML и ресурсов с хешами.
7. Загрузку карт исходного кода в систему мониторинга.
8. Ключевой smoke-сценарий после развёртывания.
9. Возможность отката на предыдущий артефакт.

Проверять нужно тот же собранный артефакт, который будет развёрнут, а не только приложение на сервере разработки.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Симптом | Что проверить |
| --- | --- |
| Ресурсы возвращают 404 | `base`, `publicPath`, адрес CDN |
| Вложенный URL возвращает 404 | SPA fallback |
| Пользователь видит старую версию | Кеш HTML и service worker |
| `ChunkLoadError` после релиза | Наличие старых чанков, URL ресурсов и согласованность развёртывания |
| Кеш не используется | Хеш содержимого и заголовки кеширования |
| Не удалось восстановить место ошибки | Карта исходного кода и соответствие артефакту релиза |
