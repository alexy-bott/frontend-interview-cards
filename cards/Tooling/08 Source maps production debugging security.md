## Вопрос

<br>

 💬 **Что такое source map, или карта исходного кода? Как использовать такие карты в рабочей среде и не публиковать исходный код без необходимости?**

<h2></h2>

<br>
<dl>
<dd>

Source map, или карта исходного кода, связывает позицию в сгенерированном JavaScript или CSS с исходным файлом, строкой и столбцом. Она нужна, потому что компиляция TypeScript и JSX, преобразование SCSS, сборка модулей и минификация меняют структуру кода.

Без карты стек вызовов из рабочей версии приложения указывает на минифицированный файл и позицию вроде `app.a81f.js:1:92841`. С картой инструмент отладки может сопоставить эту позицию с исходным компонентом, функцией и строкой TypeScript или JavaScript.

Source map является вспомогательным файлом и не участвует в выполнении приложения. Браузер выполняет собранный JavaScript, а карту используют DevTools и системы отслеживания ошибок только для восстановления исходных позиций.

Карта обычно является JSON-файлом с полями `sources`, `names`, `mappings` и иногда `sourcesContent`. Поле `mappings` хранит закодированное соответствие между сгенерированными и исходными позициями. `sourcesContent` может содержать полный текст исходных файлов.

При локальной разработке карты позволяют отлаживать TypeScript и JSX так, будто браузер выполняет исходные файлы. Здесь приходится выбирать между точностью карты и скоростью первой и повторной сборки.

В рабочей среде карты нужны Sentry, Datadog или другой системе мониторинга, чтобы превратить минифицированный стек вызовов в понятные имена файлов, функций и номера строк. Такое восстановление называют symbolication.

Основные способы создания и публикации карт различаются:

| Вариант | Поведение |
| --- | --- |
| Обычная внешняя карта | Создаётся отдельный `.map`, а бандл содержит `sourceMappingURL`, по которому инструменты могут найти карту |
| Встроенная карта | Карта находится внутри бандла и увеличивает размер загружаемого файла |
| Hidden source map | `.map` создаётся отдельно, но бандл не содержит ссылки на неё |
| No-sources source map | Карта сохраняет сопоставление позиций, но не включает полный исходный текст в `sourcesContent` |
| Без карты | Исходные позиции в стеке вызовов автоматически не восстанавливаются |

Наличие `sourceMappingURL` не означает, что обычный пользователь обязательно скачает карту вместе с приложением. Для выполнения JavaScript она не нужна. Однако DevTools или другой инструмент могут обнаружить карту по этой ссылке и запросить её.

Hidden source map не становится закрытой автоматически. Она лишь не упоминается в собранном JavaScript. Если `.map` всё равно опубликован на CDN или сервере по доступному адресу, его можно скачать напрямую.

Надёжная production-схема выглядит так:

1. Одна сборка создаёт JavaScript и соответствующие ему source maps.
2. CI связывает файлы и карты способом, который поддерживает система мониторинга.
3. Карты загружаются напрямую в систему мониторинга.
4. CI проверяет, что загрузка завершилась успешно.
5. В рабочую среду разворачивается тот же JavaScript-артефакт, но `.map` не попадают в публичный каталог.

Для сопоставления система мониторинга может использовать внедрённый в JavaScript и карту Debug ID. Другой вариант — сопоставление по идентификатору релиза, версии, пути файла и дополнительным параметрам системы. Важно не название механизма, а точное соответствие карты конкретному собранному JavaScript.

Карта должна соответствовать JavaScript конкретной сборки. Даже повторная сборка одного и того же коммита может изменить расположение кода, хеши файлов или служебные данные. Поэтому нельзя загрузить карты, а затем отдельно пересобрать приложение перед развёртыванием.

No-sources source map уменьшает объём раскрываемого исходного текста, потому что не содержит `sourcesContent`. При этом карта всё ещё может раскрывать пути файлов, имена функций и структуру модулей. Она позволяет сопоставлять позиции стека, но система мониторинга не сможет показать полный фрагмент исходного кода, если не получила его другим способом.

Source maps не являются границей безопасности. Даже без них пользователь получает клиентский JavaScript и может изучать его после форматирования и анализа. Минификация только усложняет чтение, но не делает код закрытым.

Секретные значения вообще не должны попадать в клиентский исходный код, бандл или source map. Отсутствие карт не защищает пароль, приватный ключ или закрытый API-токен, если он уже отправлен в браузер.

После загрузки карт их исключают из публичного артефакта или удаляют из каталога, который будет опубликован. Нельзя удалять карты до подтверждения успешной загрузки. Если восстановление production-ошибок обязательно для проекта, неудачная загрузка карт должна остановить выпуск версии.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что делает hidden source map?</strong></summary>

<dl>
<dd>
<h2></h2>

Сборщик создаёт отдельный `.map`, но не добавляет в JavaScript комментарий `sourceMappingURL`. Поэтому браузер и DevTools не могут автоматически обнаружить карту через собранный файл.

Это не ограничивает сетевой доступ к самому `.map`. Если файл скопирован в публичный каталог, его всё равно можно скачать по прямому адресу. Hidden-карты обычно загружают напрямую в систему отслеживания ошибок и исключают из публичного развёртывания.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем no-sources source map отличается от hidden?</strong></summary>

<dl>
<dd>
<h2></h2>

Hidden определяет способ обнаружения карты: в собранном файле отсутствует ссылка `sourceMappingURL`.

No-sources определяет содержимое карты: в ней нет полного текста исходных файлов в `sourcesContent`, но остаётся информация для сопоставления позиций.

No-sources-карта может быть публично связана с бандлом, а hidden-карта может содержать полный исходный код. Эти свойства решают разные задачи и могут сочетаться, если сборщик поддерживает такую конфигурацию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое Debug ID и зачем он нужен?</strong></summary>

<dl>
<dd>
<h2></h2>

Debug ID — это уникальный идентификатор, который добавляется в конкретный собранный JavaScript-файл и соответствующую ему source map.

Система мониторинга получает ошибку из этого JavaScript, читает его Debug ID и находит загруженную карту с тем же идентификатором. Это уменьшает зависимость от совпадения URL, имён файлов и ручной настройки release.

Debug ID нужно внедрять и загружать в рамках той же сборки. Если после этого пересобрать JavaScript, новая версия уже не будет соответствовать ранее загруженной карте.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему карты загружены, а стек вызовов остался минифицированным?</strong></summary>

<dl>
<dd>
<h2></h2>

Частые причины:

- JavaScript и карта созданы разными сборками;
- Debug ID в событии не совпадает с Debug ID загруженной карты;
- при сопоставлении по release указан другой идентификатор версии;
- URL или путь рабочего JavaScript не совпадает с путём загруженного артефакта;
- CDN отдаёт старую версию JavaScript;
- часть карт не была загружена;
- ошибка произошла в файле, для которого карта не создавалась.

Нужно определить точный JavaScript-файл из события и проверить соответствующую ему карту, идентификатор сопоставления и версию развёрнутого артефакта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Могут ли карты исходного кода раскрыть секреты?</strong></summary>

<dl>
<dd>
<h2></h2>

Карты могут упростить чтение исходного кода, комментариев, путей файлов и строковых констант, особенно если заполнено поле `sourcesContent`.

Но наличие секрета в клиентском коде уже является архитектурной ошибкой. Всё отправленное в браузер следует считать доступным пользователю независимо от наличия карты, минификации или обфускации.

Секрет должен оставаться на сервере и не попадать ни в клиентский бандл, ни в source map.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему в Webpack есть много значений <code>devtool</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Разные значения задают компромисс между:

- скоростью первой сборки;
- скоростью повторной сборки;
- точностью строк и столбцов;
- способом хранения карты;
- наличием исходного текста;
- присутствием ссылки на карту в бандле.

При разработке обычно важны быстрые пересборки и удобная отладка. В рабочей среде нужны точные стеки вызовов и контроль над тем, где хранятся `.map`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Увеличивает ли отдельная <code>.map</code> загрузку приложения?</strong></summary>

<dl>
<dd>
<h2></h2>

Для выполнения приложения внешняя карта не нужна, поэтому браузер обычно не загружает её вместе с JavaScript. Она может быть запрошена DevTools или другим инструментом, если тот попытается восстановить исходный код.

Отдельный `.map` увеличивает размер артефактов сборки и хранилища, но не начальную загрузку приложения, если карта не запрашивается браузером.

Встроенная карта находится непосредственно внутри JavaScript и всегда увеличивает размер загружаемого бандла, поэтому обычно не подходит для рабочей сборки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>В каком порядке загружать карты и разворачивать приложение?</strong></summary>

<dl>
<dd>
<h2></h2>

Одна сборка должна создать JavaScript и точно соответствующие ему карты. Затем CI внедряет необходимые идентификаторы, загружает карты в систему мониторинга и проверяет успешность загрузки.

После этого разворачивается JavaScript из той же сборки. Его нельзя пересобирать после загрузки карт.

Файлы `.map` не копируют в публичный каталог или удаляют из публикуемой части артефакта только после подтверждения загрузки.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Подход |
| --- | --- |
| Локальная отладка | Быстрые source maps с исходниками |
| Отслеживание ошибок в рабочей среде | Создать карты, закрыто загрузить их в систему мониторинга и не публиковать `.map` |
| Строгая политика исходного кода | Не публиковать `.map` и проверить наличие `sourcesContent` |
| Ошибка у пользователя | Найти карту по Debug ID или идентификатору релиза |
| Несовпадение строк | Проверить, что JavaScript и карта получены из одной сборки, а CDN отдаёт нужную версию |
