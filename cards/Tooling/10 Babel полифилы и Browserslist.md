## Вопрос

<br>

 💬 **Зачем нужен Babel? Чем транспиляция отличается от полифила и как Browserslist влияет на результат сборки?**

<h2></h2>

<br>
<dl>
<dd>

Babel преобразует JavaScript, JSX и TypeScript в другой JavaScript. Он разбирает исходный код в AST, то есть абстрактное синтаксическое дерево, применяет настроенные плагины и создаёт новый код.

Главное различие инструментов:

- Babel преобразует синтаксис;
- полифил добавляет отсутствующий API времени выполнения;
- Browserslist описывает браузеры и другие окружения, которые проект должен поддерживать.

Преобразование исходного кода до его запуска называют транспиляцией. Например, Babel может переписать optional chaining `user?.name` в более старый синтаксис с обычными проверками.

Но транспиляция не может автоматически добавить API, которого вообще нет в браузере. Если среда не поддерживает `Promise`, `Array.prototype.at`, `fetch` или нужный `Intl` API, одного преобразования синтаксиса недостаточно.

Полифил — это реализация отсутствующего API. Например, полифил может добавить `Promise` в глобальное окружение браузера.

Ponyfill решает похожую задачу, но не изменяет глобальные объекты. Его импортируют и используют как обычную функцию или модуль. Такой подход уменьшает риск конфликтов с окружением, но требует явно использовать импортированную реализацию.

Полифилы увеличивают объём JavaScript и могут влиять на глобальное окружение. Поэтому их подключают только для API и браузеров, которые проект действительно должен поддерживать.

`@babel/preset-env` выбирает преобразования синтаксиса в зависимости от целевых браузеров. Если современный синтаксис уже поддерживается всеми указанными окружениями, соответствующее преобразование можно не добавлять.

Подключение полифилов настраивается отдельно и зависит от версии Babel. В Babel 7 `@babel/preset-env` мог добавлять полифилы `core-js` через `useBuiltIns: "usage"` или `"entry"`. В Babel 8 параметры `useBuiltIns` и `corejs` удалены из preset, а полифилы подключаются через отдельные плагины-провайдеры, например `babel-plugin-polyfill-corejs3`.

`core-js` покрывает многие встроенные возможности ECMAScript, например методы массивов, объектов и коллекций. Но он не реализует все браузерные Web API. Например, для отсутствующего `fetch` нужен отдельный полифил, собственная обёртка или отказ от поддержки такого браузера.

Browserslist хранит запрос, описывающий целевые браузеры и другие окружения. Его можно задать в `package.json` или `.browserslistrc`.

Browserslist сам не преобразует JavaScript, не добавляет CSS-префиксы и не подключает полифилы. Он возвращает список целевых браузеров, который затем используют совместимые инструменты:

- Babel выбирает нужные преобразования JavaScript;
- Autoprefixer добавляет необходимые CSS-префиксы;
- другие инструменты могут проверять поддержку используемых API.

Чем старше целевые браузеры, тем больше может потребоваться преобразований, CSS-префиксов и полифилов. В результате увеличиваются размер бандла, время сборки и количество окружений, которые нужно тестировать.

Само наличие конфигурации Browserslist не гарантирует, что каждый инструмент её использует. Нужно проверить документацию и настройки конкретного сборщика, компилятора или PostCSS-плагина.

Babel умеет удалить TypeScript-синтаксис с помощью `@babel/preset-typescript`, но не выполняет проверку типов. Он может успешно создать JavaScript из кода, в котором TypeScript обнаружил бы ошибку.

Поэтому транспиляцию и type checking запускают как отдельные проверки. Например, Babel или другой компилятор создаёт JavaScript, а `tsc --noEmit` проверяет типы без генерации файлов.

Babel нужен не каждому современному проекту. Многие инструменты уже используют собственные компиляторы: Vite 8 использует Oxc и Rolldown, а Next.js имеет встроенную цепочку преобразований.

Babel добавляют, когда проекту нужен конкретный Babel-плагин, нестандартное преобразование или интеграция, которой нет в основной цепочке инструмента. Подключать его только потому, что проект использует React или TypeScript, обычно не требуется.

Поддержка старых браузеров является продуктовым решением. Она влияет на размер бандла, доступные API, количество полифилов и стоимость тестирования. Поэтому список целей выбирают по требованиям бизнеса и статистике браузеров реальных пользователей.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>В чём разница между транспиляцией и полифилом?</strong></summary>

<dl>
<dd>
<h2></h2>

Транспиляция переписывает исходный код в другой синтаксис до запуска программы. Например, optional chaining можно заменить обычными проверками на `null` и `undefined`.

Полифил добавляет реализацию API, которого нет в среде выполнения. Например, если браузер не поддерживает `Promise`, синтаксическое преобразование не поможет — нужна реализация самого `Promise`.

Кратко: транспиляция меняет запись кода, а полифил добавляет отсутствующую возможность среды.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает <code>@babel/preset-env</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`@babel/preset-env` сопоставляет целевые браузеры с данными об их поддержке JavaScript и включает необходимые плагины преобразования синтаксиса.

Например, если все целевые браузеры поддерживают стрелочные функции, преобразование стрелочных функций не требуется. Если часть браузеров их не поддерживает, preset подключит соответствующий transform.

Целевые окружения можно передать напрямую через `targets` или получить из конфигурации Browserslist.

Полифилы не являются обязательной частью работы `preset-env`. В Babel 7 ими можно было управлять через `useBuiltIns` и `corejs`, а в Babel 8 для этого используются отдельные плагины-провайдеры.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>useBuiltIns: "usage"</code> отличается от <code>"entry"</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Эти настройки относятся к Babel 7.

В режиме `usage` Babel анализирует исходные файлы и добавляет импорты полифилов для обнаруженных возможностей, которые отсутствуют в целевых браузерах.

В режиме `entry` разработчик добавляет общий импорт `core-js`, а Babel заменяет его набором необходимых полифилов для выбранных целей.

Оба режима требуют указать совместимую версию `corejs` и не покрывают автоматически все браузерные Web API.

В Babel 8 параметры `useBuiltIns` и `corejs` удалены из `@babel/preset-env`. Для аналогичной задачи используют отдельный плагин-провайдер полифилов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что изменилось в подключении полифилов в Babel 8?</strong></summary>

<dl>
<dd>
<h2></h2>

В Babel 7 `@babel/preset-env` одновременно мог выбирать синтаксические преобразования и управлять подключением `core-js` через параметры `useBuiltIns` и `corejs`.

В Babel 8 эти параметры удалены из preset. Выбор синтаксических преобразований остаётся задачей `@babel/preset-env`, а полифилы подключаются отдельным плагином, например `babel-plugin-polyfill-corejs3`.

Так конфигурация явно разделяет две разные задачи: преобразование синтаксиса и добавление API времени выполнения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Сам ли Browserslist преобразует код и добавляет полифилы?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Browserslist только превращает запрос вроде `last 2 versions` или `> 0.5%` в конкретный список браузеров и их версий.

Дальше этот список используют другие инструменты. Babel выбирает преобразования JavaScript, Autoprefixer добавляет CSS-префиксы, а отдельные плагины могут определять необходимые полифилы.

Поэтому изменение Browserslist повлияет на сборку только через инструменты, которые действительно читают эту конфигурацию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему Babel не проверяет TypeScript-типы?</strong></summary>

<dl>
<dd>
<h2></h2>

Babel воспринимает аннотации TypeScript как синтаксис, который нужно удалить перед генерацией JavaScript. Он не строит полную модель типов и не проверяет, совместимы ли значения между собой.

Поэтому код с ошибкой типов может успешно пройти через Babel и превратиться в JavaScript.

Проверку типов выполняют отдельно через `tsc --noEmit` или другой инструмент, использующий TypeScript type checker.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем плагин Babel отличается от preset?</strong></summary>

<dl>
<dd>
<h2></h2>

Плагин обычно выполняет одно конкретное преобразование или анализ AST. Например, он может обработать определённую синтаксическую конструкцию.

Preset — это готовый набор плагинов и связанных настроек для общей задачи. Например, `@babel/preset-env` подбирает преобразования современного JavaScript, а `@babel/preset-typescript` удаляет TypeScript-синтаксис.

Порядок и параметры имеют значение, потому что разные преобразования могут влиять друг на друга.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужен ли Babel в Vite или Next.js?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычно не нужен для базовой работы с JavaScript, React или TypeScript. У Vite и Next.js есть собственные быстрые цепочки преобразований.

Babel подключают, если проекту нужен конкретный Babel-плагин, особая настройка преобразования или совместимость с существующей инфраструктурой.

Перед добавлением нужно проверить, как Babel встраивается в выбранный инструмент. Пользовательская Babel-конфигурация может изменить стандартную цепочку сборки, повлиять на скорость и отключить часть встроенных оптимизаций.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему изменение Browserslist увеличило бандл?</strong></summary>

<dl>
<dd>
<h2></h2>

После добавления старых браузеров совместимые инструменты могли включить дополнительные преобразования синтаксиса, полифилы и CSS-префиксы.

Особенно заметно растёт JavaScript, если для всех пользователей приходится загружать полифилы ради небольшого процента старых браузеров.

Нужно сравнить список целей, отчёт сборки и статистику реальной аудитории. Поддержка редкого браузера должна быть осознанным продуктовым требованием.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Полностью ли <code>core-js</code> решает совместимость браузера?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. `core-js` реализует многие встроенные возможности ECMAScript, но не все DOM, CSS и Web API браузера.

Поддержку `fetch`, Canvas, WebSocket, отдельных возможностей `Intl` и CSS нужно проверять отдельно. Для некоторых API существуют отдельные полифилы, а некоторые возможности невозможно полноценно воспроизвести без поддержки платформы.

Также полифил не исправляет особенности поведения и ошибки конкретного браузера, если для них не предусмотрена отдельная реализация или трансформация.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что проверить |
| --- | --- |
| Старый браузер не понимает синтаксис | Целевые браузеры и транспиляция |
| `Promise is not defined` | Полифил для API времени выполнения |
| `fetch is not defined` | Отдельный полифил или изменение списка поддерживаемых браузеров |
| Сборка прошла при ошибке типов TypeScript | Запускается ли `tsc --noEmit` |
| После изменения Browserslist вырос бандл | Целевые браузеры, преобразования и полифилы |
| Babel замедляет сборку | Нужны ли конкретные плагины и не заменяет ли он встроенный компилятор |
