#### Вопрос

Что входит во frontend-бандл? Как контролировать его размер с помощью code splitting, tree shaking и лимитов размера?

#### Ответ

Бандл является набором файлов, которые сборщик сформировал из графа импортов приложения. Обычно в него входят начальные JavaScript и CSS, асинхронные чанки, служебный код сборщика, общие vendor-чанки со сторонними библиотеками, изображения, шрифты и другие ресурсы. Запись пакета в `package.json` сама по себе не включает его в бандл: код должен быть достижим из точки входа.

Размер JavaScript важен не только из-за скачивания. Браузер должен распаковать, разобрать, скомпилировать и выполнить код. Поэтому нужно смотреть несколько метрик:

- исходный размер файла показывает объём JavaScript для разбора и компиляции;
- gzip/Brotli показывает сетевую передачу при настроенном сжатии;
- начальный JavaScript нужен до работы первого экрана;
- асинхронный chunk загружается при открытии соответствующей функции;
- время выполнения показывает фактическую нагрузку на главный поток.

Code splitting, или разделение кода, делит граф модулей на чанки. Динамический `import()` создаёт асинхронную границу, поэтому сборщик может вынести модуль в отдельный файл:

```ts
const editorModule = await import("./Editor");
```

В React маршрут или тяжёлый компонент обычно загружают через API маршрутизатора, `React.lazy` и Suspense. Это уменьшает начальный бандл, но переносит загрузку на момент перехода. Если тот же модуль где-то импортирован статически, он снова окажется в начальном графе, и асинхронная граница не даст ожидаемого эффекта.

Tree shaking удаляет из production-бандла неиспользуемые экспорты и модули. Он лучше работает с ESM, потому что импорты и экспорты известны до выполнения программы. Сборщик отмечает используемые экспорты, учитывает поле `sideEffects`, а минификатор удаляет недостижимый код. Tree shaking и минификация являются разными процессами: первый определяет ненужные части графа, а вторая сокращает оставшийся код.

Поле `sideEffects: false` сообщает, что простой импорт модуля не выполняет наблюдаемых побочных действий. Неверное значение способно удалить нужный импорт CSS, регистрацию полифила или инициализацию SDK. Пакет с побочными эффектами должен перечислить исключения, например `"sideEffects": ["**/*.css"]`.

Size budget, или лимит размера, является автоматической проверкой объёма бандла. Полезно ограничивать не весь каталог `dist`, а значимые показатели: начальные JS и CSS, чанк отдельного маршрута, общий vendor-код, размер после сжатия и рост относительно базовой ветки. Проверка в CI останавливает PR, если он неожиданно добавил тяжёлый редактор, вторую версию библиотеки или большой полифил.

Слишком мелкое разделение тоже ухудшает работу: появляется много запросов, инструкций предварительной загрузки модулей и последовательных цепочек скачивания. Границы выбирают по пользовательским сценариям, вероятности открытия функции, размеру модуля и возможности загрузить его заранее.

Работу начинают с измерения. Отчёт сборки и bundle analyzer показывают состав чанков, вкладка Coverage в DevTools находит загруженный, но не выполненный код, Network показывает порядок запросов и сжатие, а Performance измеряет разбор и выполнение JavaScript. После этого исправляют конкретную причину: ненужный импорт, тяжёлую зависимость, дубликат пакета, лишние локали, полный набор иконок, полифил или неудачную стратегию чанков.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Как динамический импорт создаёт отдельный чанк?
>
> **Ответ:** `import("./module")` возвращает Promise и создаёт асинхронную связь в графе. Сборщик может вынести модуль и его уникальные зависимости в отдельный чанк, а служебный код загрузит этот файл перед выполнением продолжения промиса. Точная граница зависит от общего кода и настроек разделения.

> [!followup]
> **Вопрос:** Почему динамический импорт иногда не уменьшает начальный бандл?
>
> **Ответ:** Модуль может одновременно импортироваться статически из другой начальной точки входа либо его зависимость уже находится в общем чанке. Анализатор покажет фактическое размещение. Небольшая обёртка, загружаемая лениво, тоже не поможет, если тяжёлая библиотека импортирована выше асинхронной границы.

> [!followup]
> **Вопрос:** Почему ESM важен для tree shaking?
>
> **Ответ:** Статические импорты и экспорты ESM можно определить без выполнения модуля. CommonJS допускает вычисляемые `require` и изменение `module.exports` во время работы, поэтому сборщику труднее доказать, что часть кода не нужна.

> [!followup]
> **Вопрос:** Что означает `sideEffects` в `package.json`?
>
> **Ответ:** Поле сообщает сборщику, можно ли удалить модуль, если его экспорты не используются. `false` разрешает агрессивное удаление, а массив отмечает файлы с побочными эффектами. Ошибочное значение может сломать приложение, поэтому это контракт автора пакета, а не универсальный флаг ускорения.

> [!followup]
> **Вопрос:** Что искать в анализаторе бандла?
>
> **Ответ:** Большие библиотеки, несколько версий одного пакета, лишние локали, полные наборы иконок, полифилы, код только для разработки и модуль, который без причины оказался в начальном чанке. Затем нужно выяснить, через какой импорт он достижим, а не просто переместить его в другой чанк.

> [!followup]
> **Вопрос:** Почему нельзя сравнивать только размер после gzip?
>
> **Ответ:** Сжатие уменьшает передачу по сети, но браузер всё равно распаковывает и обрабатывает исходный JavaScript. Два файла одинакового размера после gzip могут требовать разного времени на разбор и выполнение. Поэтому сравнивают сетевой и исходный размер, а также профиль загрузки процессора на слабом устройстве.

> [!followup]
> **Вопрос:** Почему в бандле появляются две версии одной библиотеки?
>
> **Ответ:** Разные зависимости могут требовать несовместимые диапазоны, либо менеджер пакетов не смог поднять и объединить одну версию. Это увеличивает размер и опасно для singleton-библиотек, которые должны существовать в одном экземпляре, например React. Проверяют дерево lock-файла, peer dependencies, псевдонимы и возможность согласовать диапазоны.

> [!followup]
> **Вопрос:** Как выбрать лимит размера бандла?
>
> **Ответ:** Сначала измеряют текущую production-сборку и целевые показатели производительности продукта. Затем задают лимит на начальные ресурсы и допустимый рост в PR. Лимит должен учитывать размер после gzip или Brotli и исходный JavaScript, различаться по маршрутам и регулярно пересматриваться, а не быть случайным числом.

#### Где это встречается во frontend

| Проблема | Проверка или решение |
| --- | --- |
| Большой начальный JavaScript | Разделение кода по маршрутам или компонентам |
| Тяжёлая библиотека графиков | Ленивый импорт и предварительная загрузка перед открытием |
| Tree shaking не работает | ESM, `sideEffects`, фактическая точка входа пакета |
| Дубликаты зависимостей | Дерево lock-файла и анализатор бандла |
| PR увеличил начальный чанк | Лимит размера в CI |
| Много мелких запросов | Укрупнить границы и проверить цепочки загрузки |
