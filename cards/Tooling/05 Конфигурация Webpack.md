## Вопрос

<br>

 💬 **Как устроена конфигурация Webpack? Чем отличаются `entry`, loaders, plugins, `output` и `optimization`?**

<h2></h2>

<br>
<dl>
<dd>

Webpack — это сборщик модулей (module bundler). Он начинает с одной или нескольких точек входа `entry`, проходит по импортам и строит граф всех зависимых модулей приложения.

Во время обработки графа loaders преобразуют отдельные импортированные файлы, а plugins могут вмешиваться в разные этапы всей сборки. После этого Webpack объединяет модули во внутренние группы — chunks, выполняет настроенные оптимизации и записывает итоговые JavaScript, CSS и другие файлы в `output`.

Основные части конфигурации решают разные задачи:

| Раздел | Назначение |
| --- | --- |
| `entry` | Модули, с которых Webpack начинает строить граф зависимостей |
| `module.rules` | Правила выбора и преобразования импортированных файлов через loaders |
| `plugins` | Расширение и изменение разных этапов процесса сборки |
| `output` | Каталог, имена файлов и публичные URL результатов |
| `resolve` | Правила поиска модулей, расширений и псевдонимов путей |
| `optimization` | Разделение чанков, runtime, минификация и стабильность идентификаторов |
| `devServer` | Локальный сервер, HMR, проксирование и fallback для SPA |

Упрощённая production-конфигурация выглядит так:

```js
const path = require("node:path");
const HtmlWebpackPlugin = require("html-webpack-plugin");

module.exports = {
  mode: "production",
  entry: "./src/index.tsx",
  output: {
    path: path.resolve(__dirname, "dist"),
    filename: "assets/[name].[contenthash].js",
    chunkFilename: "assets/[name].[contenthash].js",
    publicPath: "/",
    clean: true,
  },
  module: {
    rules: [
      {
        test: /\.tsx?$/,
        exclude: /node_modules/,
        use: "babel-loader",
      },
      {
        test: /\.scss$/,
        use: ["style-loader", "css-loader", "sass-loader"],
      },
    ],
  },
  resolve: {
    extensions: [".tsx", ".ts", ".js"],
  },
  plugins: [new HtmlWebpackPlugin({ template: "./public/index.html" })],
  optimization: {
    splitChunks: { chunks: "all" },
    runtimeChunk: "single",
  },
};
```

Пример предполагает, что для `babel-loader` отдельно настроены Babel-пресеты для TypeScript, JSX и нужных браузеров. В production-сборке CSS обычно не вставляют через `style-loader`, а извлекают в отдельные файлы с помощью соответствующего плагина.

`entry` указывает, с каких модулей начинать сборку. Для обычного SPA это часто один файл вроде `src/index.tsx`. В многостраничном приложении или при создании нескольких независимых сборок точек входа может быть несколько.

Loader преобразует конкретный импортированный модуль. Например, TypeScript можно преобразовать в JavaScript, SCSS — в CSS, а CSS — в JavaScript-модуль, который Webpack сможет добавить в граф.

В обычной цепочке `use` loaders выполняются справа налево:

1. `sass-loader` преобразует SCSS в CSS.
2. `css-loader` обрабатывает CSS-импорты и `url()`.
3. `style-loader` добавляет полученные стили в документ через JavaScript.

Каждый loader передаёт результат следующему, а итог цепочки должен быть представлен в форме, которую Webpack может включить в граф модулей.

Plugin подключается к hooks — этапам жизненного цикла компиляции Webpack — и обычно работает шире одного файла. Плагин может создать HTML, извлечь CSS, определить константы времени сборки, скопировать ресурсы или сформировать отчёт о размере бандла.

Таким образом, loader отвечает прежде всего за преобразование конкретных модулей, а plugin — за управление или расширение процесса сборки в целом.

Раздел `resolve` определяет, как Webpack находит модуль по пути из `import` или `require`. Например, `resolve.extensions` разрешает опускать указанные расширения в импортах, а `resolve.alias` позволяет заменить длинные относительные пути короткими псевдонимами.

Раздел `output` определяет, куда и под какими именами Webpack запишет результат:

- `path` задаёт физический каталог на диске;
- `filename` задаёт имена файлов начальных чанков;
- `chunkFilename` задаёт имена дополнительных чанков, например созданных динамическим `import()`;
- `publicPath` задаёт базовый URL, по которому браузер будет загружать ресурсы;
- `clean` очищает каталог сборки перед записью новых файлов.

Неверный `publicPath` часто проявляется только после развёртывания: основной файл приложения загружается, но динамический импорт запрашивает дополнительный чанк по неправильному адресу и получает 404.

`mode: "development"` и `mode: "production"` включают разные встроенные настройки. Режим `production` активирует минификацию и другие оптимизации, а также подставляет значение `"production"` вместо `process.env.NODE_ENV` в собираемом коде.

При этом `mode` не устанавливает переменную `process.env.NODE_ENV` внутри самого `webpack.config.js`. Он также не заменяет явную настройку путей, source maps, кеширования и стратегии разделения кода.

Раздел `optimization` управляет тем, как Webpack формирует и оптимизирует чанки.

`optimization.splitChunks` может выносить общий код в отдельные чанки, чтобы уменьшить дублирование. По умолчанию Webpack в первую очередь применяет эту оптимизацию к асинхронно загружаемым чанкам. Настройка `chunks: "all"` разрешает анализировать также код начальных точек входа.

`runtimeChunk` выносит Webpack runtime — служебный код запуска приложения, регистрации модулей и загрузки дополнительных чанков — в отдельный файл. Это может улучшить долгосрочное кеширование, особенно при нескольких точках входа.

`[contenthash]` формирует имя файла на основе его содержимого. Вместе с предсказуемым разделением чанков и стабильными идентификаторами модулей это помогает сохранять URL файлов, содержимое которых не изменилось.

Tree shaking помогает удалить неиспользуемый код из production-бандла. Наиболее предсказуемо он работает со статическими ESM-импортами и экспортами.

В этом процессе участвуют несколько механизмов:

- `optimization.usedExports` определяет, какие экспорты действительно используются;
- поле `sideEffects` сообщает, какие файлы можно полностью удалить, если их результат нигде не используется;
- минификатор удаляет оставшиеся выражения, которые были определены как мёртвый код.

CommonJS, динамический выбор свойств и неверное поле `sideEffects` могут ограничить tree shaking. Особенно опасно без проверки указывать `sideEffects: false`: вместе с неиспользуемым модулем Webpack может удалить импорт CSS, полифилл или другой код с необходимым побочным эффектом.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Может ли Webpack иметь несколько <code>entry</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Да. Несколько именованных точек входа используют, например, для многостраничного приложения или независимых частей системы:

```js
entry: {
  main: "./src/main.js",
  admin: "./src/admin.js",
}
```

Webpack строит граф от каждой точки входа и создаёт соответствующие начальные чанки. Общие зависимости между ними можно вынести через `splitChunks`.

Не следует создавать отдельный `entry` только ради ручного выделения vendor-кода: для этой задачи обычно используют `optimization.splitChunks`. Если несколько точек входа загружаются на одной странице, также нужно проверить стратегию Webpack runtime, чтобы не создавать несколько независимых runtime без необходимости.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем loader отличается от plugin?</strong></summary>

<dl>
<dd>
<h2></h2>

Loader преобразует конкретный модуль, который попал в граф через `import` или `require`. Например, цепочка loaders может преобразовать SCSS в CSS, обработать CSS-импорты и подготовить результат для добавления в приложение.

Plugin подключается к этапам жизненного цикла всей сборки. Он может анализировать граф, изменять чанки, создавать итоговые файлы или добавлять данные времени компиляции.

Кратко: loader преобразует модуль, а plugin расширяет процесс сборки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>В каком порядке выполняются loaders?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычная цепочка `use` выполняется справа налево. Для `use: ["style-loader", "css-loader", "sass-loader"]` первым работает `sass-loader`, затем `css-loader`, а последним — `style-loader`.

У loaders также существует отдельная фаза `pitch`, которая выполняется в обратном направлении — слева направо. При настройке типовой цепочки обычно достаточно помнить порядок основной фазы: справа налево.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое <code>publicPath</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`publicPath` — это базовый URL, который служебный код Webpack использует при формировании адресов ресурсов и лениво загружаемых чанков.

Например, физически файл может находиться в каталоге `dist/assets`, но загружаться браузером по адресу `/app/assets/` или с отдельного CDN.

`output.path` отвечает за расположение файла на диске во время сборки, а `publicPath` — за URL, по которому браузер будет искать его после развёртывания. Неверное значение часто приводит к 404 при динамическом импорте, даже если сам файл присутствует на сервере.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что изменили Asset Modules в Webpack 5?</strong></summary>

<dl>
<dd>
<h2></h2>

Asset Modules добавили встроенную обработку изображений, шрифтов, текстовых и других ресурсов без обязательного использования `file-loader`, `url-loader` и `raw-loader`.

Основные типы:

- `asset/resource` создаёт отдельный файл и возвращает его URL;
- `asset/inline` встраивает ресурс как data URL;
- `asset/source` возвращает содержимое ресурса как строку;
- `asset/bytes` возвращает содержимое как `Uint8Array`;
- `asset` автоматически выбирает между отдельным файлом и встраиванием по размеру.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает <code>splitChunks</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`splitChunks` анализирует модули, попавшие в разные чанки, и при выполнении заданных условий может вынести общий код в отдельный переиспользуемый чанк.

По умолчанию оптимизация ориентирована на асинхронные чанки. Значение `chunks: "all"` позволяет учитывать также начальные чанки.

Решение о разделении зависит не только от повторного использования, но и от ограничений размера, количества запросов и настроек `cacheGroups`. Поэтому включение `splitChunks` не означает, что каждая общая зависимость обязательно получит отдельный файл.

Правильное разделение уменьшает дублирование и помогает кешированию. Однако один слишком большой общий vendor-чанк может заставить пользователя загрузить код экранов, которые он ещё не открывал.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем выносить <code>runtimeChunk</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Webpack runtime содержит служебную логику запуска модулей и загрузки дополнительных чанков. Если runtime находится внутри основного или vendor-чанка, изменение структуры сборки может изменить хеш этого файла, даже когда большая часть его бизнес-кода осталась прежней.

Вынос runtime в отдельный файл может сделать хеши остальных чанков стабильнее и улучшить долгосрочное кеширование. Особенно это полезно, когда на одной странице используется несколько точек входа.

Польза зависит от структуры приложения, количества entry и настроенных HTTP-заголовков кеширования.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Работает ли <code>devServer.proxy</code> в production?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Webpack Dev Server запускается только для локальной разработки. Его proxy позволяет браузеру отправлять запросы на origin dev server, после чего сервер разработки пересылает их на backend.

После развёртывания Webpack Dev Server отсутствует. Проксирование, раздачу статических файлов, заголовки кеширования и fallback для SPA настраивают в Nginx, ingress, CDN, на платформе хостинга или на backend-сервере.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему import одной функции иногда включает почти всю библиотеку?</strong></summary>

<dl>
<dd>
<h2></h2>

Причиной может быть CommonJS-точка входа, динамическая структура экспортов, импорт всего пространства имён, barrel-файл с побочными эффектами или некорректно заполненное поле `sideEffects`.

Сначала нужно проверить, какой файл Webpack выбирает через `package.json` пакета и поле `exports`, а затем изучить итоговый бандл в анализаторе.

Замена синтаксиса импорта помогает только тогда, когда библиотека действительно предоставляет отдельные ESM-модули или поддерживает импорт отдельных путей. Запись `import { method } from "library"` сама по себе не гарантирует, что в бандл попадёт только одна функция.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Симптом | Что проверить |
| --- | --- |
| SCSS не импортируется | `module.rules`, совпадение `test` и порядок loaders |
| Lazy chunk даёт 404 | `output.publicPath` и путь размещения приложения |
| Общий код дублируется | `optimization.splitChunks` и `cacheGroups` |
| Хеш меняется у неизменного vendor-чанка | Размещение runtime и стабильность идентификаторов |
| Большой начальный бандл | `entry`, синхронные импорты, `splitChunks` и анализ состава чанков |
| Медленная повторная сборка | Постоянный кеш, дорогие loaders и настройки source maps |
