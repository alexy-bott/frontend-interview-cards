## Вопрос

<br>

 💬 **Чем отличаются npm, Yarn и pnpm? Как менеджер пакетов и workspaces связаны со структурой monorepo?**

<h2></h2>

<br>
<dl>
<dd>

npm, Yarn и pnpm являются менеджерами пакетов. Они выбирают версии зависимостей, скачивают пакеты, создают lock-файл, формируют структуру установленных модулей, запускают scripts и поддерживают работу с несколькими локальными пакетами через workspaces.

Для команды важно использовать один менеджер пакетов, одну согласованную версию и один lock-файл во всём репозитории и CI. Иначе разные алгоритмы разрешения, связывания и размещения зависимостей могут создать разные деревья установки.

Нужно разделять три понятия:

- менеджер пакетов устанавливает зависимости и запускает команды;
- workspaces позволяют ему управлять несколькими локальными пакетами как одним проектом;
- monorepo описывает организацию нескольких приложений и библиотек в одном Git-репозитории.

npm обычно устанавливается вместе с Node.js и использует `package-lock.json`. Yarn существует в заметно различающихся поколениях: Yarn Classic в основном использует обычный `node_modules`, а современный Yarn поддерживает несколько моделей установки. pnpm использует `pnpm-lock.yaml`, общее адресуемое по содержимому хранилище и систему ссылок, чтобы не копировать одни и те же файлы пакетов в каждый проект.

Основное различие видно в способе установки зависимостей:

| Менеджер | Типичная модель |
| --- | --- |
| npm | Обычный `node_modules` с hoisting и `package-lock.json` |
| Yarn | PnP по умолчанию в современном Yarn либо настраиваемые `node_modules` и pnpm-подобная структура |
| pnpm | Общее хранилище файлов, жёсткие ссылки и связанное символическими ссылками дерево `node_modules` |

Hoisting, или поднятие зависимостей, размещает часть пакетов выше по дереву `node_modules`. Это уменьшает вложенность и позволяет переиспользовать одну подходящую версию пакета в нескольких частях дерева.

Из-за hoisting может появиться phantom dependency, или неявная зависимость: код импортирует пакет, которого нет в его собственном `package.json`, но который случайно доступен на верхнем уровне `node_modules`. Такой импорт может работать до изменения дерева зависимостей, перехода на другой менеджер или публикации пакета.

Важно: физическая доступность пакета в `node_modules` не означает, что зависимость объявлена правильно. Каждый пакет должен явно перечислять используемые зависимости в своём `package.json`.

pnpm хранит содержимое пакетов в общем хранилище. При установке файлы связываются с проектом жёсткими ссылками, поэтому одинаковая версия пакета не копируется полностью для каждого проекта.

Затем pnpm формирует структуру зависимостей через каталог `.pnpm` и символические ссылки. Благодаря этому пакет по умолчанию получает доступ только к тем зависимостям, которые объявлены в его `package.json`. Такая структура экономит место и помогает раньше обнаруживать неявные зависимости.

При этом pnpm поддерживает разные настройки hoisting и режим `nodeLinker: hoisted` для совместимости с инструментами, которые плохо работают с символическими ссылками. Поэтому утверждение «pnpm вообще ничего не поднимает» неверно.

Современный Yarn по умолчанию может использовать Plug'n'Play. В этом режиме обычный `node_modules` не создаётся: Yarn записывает информацию о расположении и связях пакетов в `.pnp.cjs`, а специальный механизм разрешает импорты на основе этой карты.

PnP разрешает пакету обращаться только к объявленным зависимостям и поэтому хорошо обнаруживает phantom dependencies. Однако IDE, плагины, сборщики и другие инструменты должны поддерживать PnP или запускаться через интеграцию Yarn.

Современный Yarn также может использовать обычный `node_modules` или pnpm-подобную структуру через настройку `nodeLinker`. Поэтому при обсуждении Yarn важно уточнять не только его версию, но и выбранный режим установки.

Workspaces — это механизм управления несколькими локальными пакетами в рамках одного проекта. Каждый workspace обычно имеет собственный `package.json`, `name`, зависимости, scripts и границы ответственности.

В npm и Yarn каталоги workspaces обычно перечисляют в корневом `package.json`:

```json
{
  "private": true,
  "workspaces": ["apps/*", "packages/*"]
}
```

В pnpm состав workspace объявляют в корневом файле `pnpm-workspace.yaml`, а не через поле `workspaces` в `package.json`.

Менеджер пакетов находит локальные пакеты, устанавливает их зависимости, связывает их между собой и позволяет запускать команды для одного или нескольких workspaces.

Monorepo, или монорепозиторий, хранит несколько приложений и библиотек в одном Git-репозитории. Например, в нём могут находиться frontend-приложение, административная панель, UI-библиотека и общие утилиты.

Workspaces решают прежде всего следующие задачи:

- общая установка зависимостей;
- один lock-файл;
- связывание локальных пакетов;
- запуск scripts по выбранным пакетам;
- согласованное управление зависимостями.

Но workspaces сами по себе не дают полный процесс управления monorepo: распределённый кеш задач, анализ изменений Git, сложные графы выполнения, отчёты CI и управление релизами. Для этого дополнительно используют Turborepo, Nx, Changesets, Rush или собственную логику CI.

Зависимость от локального workspace нужно объявлять явно. Yarn и pnpm поддерживают протокол `workspace:`, который требует использовать пакет из текущего workspace и не позволяет случайно скачать из registry опубликованный пакет с тем же именем.

Например, `workspace:*` означает использование доступной локальной версии. Формы `workspace:^` и `workspace:~` дополнительно задают политику semver для публикации. При упаковке или публикации менеджер заменяет `workspace:` на обычную версию или диапазон, который сможет использовать потребитель пакета.

Поле `packageManager`, например `"packageManager": "pnpm@11.0.0"`, объявляет выбранный менеджер и ожидаемую версию. Само поле является метаданными и не гарантирует, что разработчик действительно запустит именно эту версию.

Версию должен применять или проверять Corepack, CI, контейнер, Volta, mise или другой менеджер инструментов. Corepack поставлялся вместе с Node.js до версии 25, но для Node.js 25 и новее его при необходимости устанавливают отдельно. Поэтому CI должен явно подготавливать нужную версию менеджера, а не полагаться только на её наличие в системе.

В репозитории должен оставаться lock-файл выбранного менеджера: `package-lock.json`, `yarn.lock` или `pnpm-lock.yaml`. Lock-файлы других менеджеров нужно удалить, чтобы не создавать несколько конкурирующих источников истины.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Почему нельзя использовать npm локально, если в проекте лежит <code>pnpm-lock.yaml</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

npm не использует `pnpm-lock.yaml` и построит собственное дерево зависимостей по правилам npm. При этом может появиться новый `package-lock.json`, а структура `node_modules` будет отличаться от установки pnpm.

В результате ошибка может воспроизводиться только у части команды или только в CI. Нужно использовать менеджер из поля `packageManager`, а при установке в CI запрещать изменение lock-файла.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>За счёт чего pnpm экономит место?</strong></summary>

<dl>
<dd>
<h2></h2>

Файлы каждого пакета хранятся в общем адресуемом по содержимому хранилище. Если одна версия зависимости нужна нескольким проектам, её содержимое не скачивается и не копируется полностью для каждого из них.

Жёсткие ссылки связывают файлы общего хранилища с каталогом установки проекта, а символические ссылки формируют структуру зависимостей, которую видят пакеты.

Поэтому одинаковая версия пакета занимает на диске значительно меньше дополнительного места при установке в нескольких проектах.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое phantom dependency, или неявная зависимость?</strong></summary>

<dl>
<dd>
<h2></h2>

Это пакет, который код импортирует, но не объявляет в собственном `package.json`.

Импорт может случайно работать, если другой пакет установил эту зависимость, а менеджер поднял её на доступный уровень `node_modules`. После изменения дерева, перехода на pnpm или PnP либо публикации библиотеки такой импорт может сломаться.

Исправление состоит не в дополнительном hoisting, а в явном объявлении зависимости в нужном пакете.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое Yarn Plug'n'Play?</strong></summary>

<dl>
<dd>
<h2></h2>

Plug'n'Play, или PnP, — это режим установки Yarn без обычного дерева `node_modules`.

Yarn создаёт файл `.pnp.cjs` с картой пакетов и их зависимостей. Специальный механизм использует эту карту, чтобы определить, где находится импортируемый пакет и имеет ли текущий пакет право обращаться к нему.

PnP помогает обнаруживать неявные зависимости и ускоряет установку, но используемые IDE и инструменты должны поддерживать PnP или работать через интеграцию Yarn.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем workspace отличается от monorepo?</strong></summary>

<dl>
<dd>
<h2></h2>

Monorepo — это способ организации нескольких проектов в одном Git-репозитории.

Workspace — это отдельный локальный пакет, которым менеджер пакетов управляет в составе общего проекта. Набор таких пакетов также называют workspaces.

Monorepo может существовать без npm, Yarn или pnpm workspaces. И наоборот, наличие workspaces не добавляет автоматически кеш задач, анализ изменений Git, управление релизами и остальные возможности полноценных monorepo-инструментов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужен протокол <code>workspace:*</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Протокол `workspace:` явно требует использовать пакет из текущего workspace, а не совпадающую опубликованную версию из registry.

`workspace:*` принимает текущую локальную версию пакета. Формы `workspace:^` и `workspace:~` также задают диапазон, который будет сформирован при публикации.

Это защищает от случайного использования старой версии из registry и явно показывает связь между внутренними пакетами monorepo.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как зафиксировать менеджер пакетов и его версию?</strong></summary>

<dl>
<dd>
<h2></h2>

В корневом `package.json` указывают поле `packageManager`, например `"packageManager": "pnpm@11.0.0"`.

Затем CI или инструмент управления версиями должен установить и запустить именно эту версию. Для этого можно использовать Corepack, официальный action выбранного менеджера, контейнер или другой менеджер инструментов.

Одного поля `packageManager` недостаточно: без проверки разработчик всё ещё может запустить другую глобально установленную версию.

Также в репозитории должен находиться только lock-файл выбранного менеджера, а строгая установка в CI не должна разрешать его изменение.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему в monorepo появляются несколько версий React?</strong></summary>

<dl>
<dd>
<h2></h2>

Разные пакеты могут объявить несовместимые диапазоны React. Другой частой причиной является библиотека, которая ошибочно поместила React в `dependencies` вместо `peerDependencies`.

Менеджер пакетов в таком случае может сохранить несколько экземпляров, а сборщик — включить их в приложение. Это увеличивает бандл и может нарушить работу React hooks.

Нужно согласовать диапазоны, исправить `peerDependencies`, проверить lock-файл и убедиться, что приложение разрешает React в один ожидаемый экземпляр.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как запускать проверки только для затронутых пакетов?</strong></summary>

<dl>
<dd>
<h2></h2>

npm, Yarn и pnpm позволяют запускать scripts для выбранных workspaces. Yarn и pnpm также поддерживают фильтрацию по зависимостям, зависимым пакетам и изменённым частям репозитория.

Для более сложного анализа обычно используют Nx, Turborepo или собственную логику CI. Инструмент определяет изменённые пакеты и проекты, которые от них зависят, а затем запускает линтер, тесты и сборку только для нужной части графа.

Такие инструменты также могут кешировать результаты задач, чего обычного связывания workspaces само по себе не даёт.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что проверить |
| --- | --- |
| Разные деревья у команды | Менеджер, его версия и lock-файл |
| Импорт работает только в одном проекте | Неявная зависимость и hoisting |
| Много места занимает `node_modules` | Общее хранилище pnpm и ссылки |
| Несколько приложений и UI-библиотека | Workspaces и monorepo |
| Локальный пакет скачался из реестра | `workspace:*` |
| CI собирает всё слишком долго | Граф затронутых проектов и кеш задач |
