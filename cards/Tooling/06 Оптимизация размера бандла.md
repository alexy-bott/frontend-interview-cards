## Вопрос

<br>

 💬 **Что входит во frontend-бандл? Как контролировать его размер с помощью code splitting, tree shaking и лимитов размера?**

<h2></h2>

<br>
<dl>
<dd>

Frontend-бандл — это набор итоговых файлов, которые сборщик создаёт из графа импортов приложения. Обычно в него входят начальные JavaScript и CSS, асинхронные чанки, служебный код сборщика, общие чанки со сторонними библиотеками, изображения, шрифты и другие ресурсы.

Запись пакета в `package.json` сама по себе не включает его код в бандл. Модуль должен быть достижим из точки входа приложения через статические или динамические импорты. При этом конкретный ресурс может быть создан отдельным файлом, встроен внутрь другого файла или оставлен внешним — это зависит от настроек сборщика.

Размер JavaScript важен не только из-за времени скачивания. После получения файла браузер должен его распаковать, разобрать, скомпилировать и выполнить. Поэтому нужно смотреть несколько разных показателей:

- исходный размер показывает объём несжатого кода и косвенно указывает на стоимость его обработки;
- размер после gzip или Brotli показывает объём передачи по сети при настроенном сжатии;
- начальный JavaScript загружается до работы первого экрана;
- асинхронный чанк может быть загружен позже при переходе к соответствующей функции или маршруту;
- время разбора и выполнения показывает фактическую нагрузку на главный поток.

Code splitting, или разделение кода, делит граф модулей на несколько чанков. Он не обязательно уменьшает общий объём кода приложения, а позволяет не загружать часть кода до того момента, когда она действительно понадобится.

Динамический `import()` создаёт асинхронную границу в графе, поэтому сборщик получает возможность вынести модуль и его зависимости в отдельный чанк:

```ts
const editorModule = await import("./Editor");
```

В React маршрут или тяжёлый компонент обычно загружают через API маршрутизатора либо через `React.lazy` и `Suspense`. Это уменьшает начальный бандл, но переносит загрузку на момент перехода или отображения компонента.

Если тот же тяжёлый модуль остаётся достижимым через статический импорт из начальной точки входа, он всё равно попадёт в начальный граф. В таком случае динамический импорт в другом месте не даст ожидаемого уменьшения начальной загрузки.

Tree shaking удаляет из production-бандла код, который сборщик смог определить как неиспользуемый. В отличие от code splitting, он не переносит код в другой чанк, а полностью исключает доказанно ненужные части из результата.

Tree shaking лучше работает с ESM, потому что статические импорты и экспорты можно проанализировать до выполнения программы. Сборщик отмечает используемые экспорты, учитывает побочные эффекты модулей, а минификатор удаляет оставшийся мёртвый код.

Tree shaking и минификация — разные процессы. Tree shaking определяет, какие модули и экспорты не нужны, а минификация сокращает оставшийся код: переименовывает локальные идентификаторы, удаляет пробелы и упрощает выражения.

Поле `sideEffects: false` сообщает сборщику, что импорт модулей пакета сам по себе не выполняет наблюдаемых побочных действий. Благодаря этому неиспользуемый модуль можно удалить целиком.

Неверное значение способно удалить нужный импорт CSS, регистрацию полифила, глобальную настройку или инициализацию SDK. Если побочные эффекты есть только у отдельных файлов, их перечисляют явно, например `"sideEffects": ["**/*.css"]`.

Size budget, или лимит размера, — это автоматическая проверка объёма ресурсов приложения. Она помогает обнаружить рост бандла до того, как изменение попадёт в production.

Полезно ограничивать не только весь каталог `dist`, а конкретные показатели:

- начальные JavaScript и CSS;
- начальный чанк отдельной точки входа;
- чанк важного маршрута;
- общий код сторонних библиотек;
- исходный и сжатый размер;
- допустимый рост относительно основной ветки.

Проверка в CI может остановить PR, если он неожиданно добавил тяжёлый редактор, вторую версию библиотеки, большой полифил или полный набор ресурсов.

Слишком мелкое разделение тоже может ухудшить загрузку. Появляется больше файлов, сетевых запросов, служебного кода и последовательных цепочек загрузки. Даже при HTTP/2 и HTTP/3 большое количество зависимых чанков может задерживать отображение нужного интерфейса.

Границы разделения выбирают по пользовательским сценариям, вероятности открытия функции, размеру модуля и возможности загрузить его заранее. Код критичного первого экрана обычно не следует откладывать, а тяжёлую редко используемую функцию выгодно загружать отдельно.

Оптимизацию начинают с измерения. Отчёт сборки и bundle analyzer показывают состав чанков, вкладка Coverage в DevTools находит загруженный, но не использованный во время записи код, Network показывает порядок запросов и сетевое сжатие, а Performance измеряет разбор и выполнение JavaScript.

После этого исправляют конкретную причину: ненужный импорт, тяжёлую зависимость, дубликат пакета, лишние локали, полный набор иконок, полифил или неудачную стратегию разделения чанков.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Как динамический импорт создаёт отдельный чанк?</strong></summary>

<dl>
<dd>
<h2></h2>

`import("./module")` возвращает Promise и создаёт асинхронную связь в графе модулей. Благодаря этой границе сборщик может вынести модуль и его уникальные зависимости в отдельный чанк.

Когда выполнение дойдёт до динамического импорта, служебный код сборщика загрузит нужный файл и только после этого продолжит выполнение Promise.

Динамический импорт не гарантирует, что весь модуль окажется в полностью независимом файле. Общие зависимости могут быть вынесены в другой общий чанк, а точное разделение зависит от настроек и структуры графа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Уменьшает ли code splitting общий размер приложения?</strong></summary>

<dl>
<dd>
<h2></h2>

Не обязательно. Code splitting в первую очередь меняет момент загрузки кода: часть JavaScript не попадает в начальную загрузку, а запрашивается позже.

Общий размер всех чанков может остаться примерно тем же или немного увеличиться из-за служебного кода и повторяющихся частей. Уменьшение общего объёма достигается через удаление ненужного кода, tree shaking, замену тяжёлых зависимостей и исключение дубликатов.

Поэтому после разделения нужно проверять и размер начального JavaScript, и общий объём загружаемого кода для конкретного пользовательского сценария.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему динамический импорт иногда не уменьшает начальный бандл?</strong></summary>

<dl>
<dd>
<h2></h2>

Модуль может одновременно импортироваться статически из начальной точки входа. В этом случае он уже входит в начальный граф и не может быть полностью отложен динамическим импортом из другого места.

Также тяжёлая зависимость может находиться выше асинхронной границы или быть вынесена в общий чанк, который всё равно загружается сразу.

Анализатор бандла показывает фактическое размещение модулей и помогает найти статический импорт, из-за которого код остался в начальной загрузке.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему ESM важен для tree shaking?</strong></summary>

<dl>
<dd>
<h2></h2>

Статические импорты и экспорты ESM можно определить без выполнения модуля. Сборщик заранее видит, какие значения экспортируются и какие из них используются приложением.

CommonJS допускает вычисляемые вызовы `require`, условные импорты и изменение `module.exports` во время выполнения. Поэтому сборщику сложнее доказать, что конкретная часть такого модуля не нужна и может быть безопасно удалена.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означает <code>sideEffects</code> в <code>package.json</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Поле сообщает сборщику, можно ли полностью удалить модуль, если его экспорты нигде не используются.

Значение `false` означает, что модули пакета не выполняют необходимых действий только за счёт импорта. Массив позволяет перечислить файлы, которые всё же имеют побочные эффекты, например CSS или модуль глобальной инициализации.

Ошибочное значение может сломать приложение, поэтому `sideEffects` — это описание поведения пакета, а не универсальный флаг для уменьшения бандла.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что искать в анализаторе бандла?</strong></summary>

<dl>
<dd>
<h2></h2>

В анализаторе ищут:

- большие сторонние библиотеки;
- несколько версий одного пакета;
- лишние локали;
- полные наборы иконок;
- ненужные полифилы;
- код только для разработки;
- модуль, который без причины оказался в начальном чанке;
- общий чанк, содержащий код множества редко открываемых экранов.

После обнаружения большого модуля нужно определить, через какой импорт он попал в граф. Простое перемещение кода в другой чанк не всегда уменьшает объём, который пользователь загружает в своём сценарии.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему нельзя сравнивать только размер после gzip?</strong></summary>

<dl>
<dd>
<h2></h2>

Gzip или Brotli уменьшают объём передачи по сети, но перед выполнением браузер распаковывает файл и обрабатывает исходный JavaScript.

Два файла одинакового размера после сжатия могут содержать разное количество и разную сложность кода, поэтому отличаться по времени разбора, компиляции и выполнения.

Нужно сравнивать сетевой размер, несжатый размер и фактическое время обработки JavaScript, желательно на устройстве, близком к слабому устройству целевой аудитории.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему в бандле появляются две версии одной библиотеки?</strong></summary>

<dl>
<dd>
<h2></h2>

Разные зависимости могут требовать несовместимые диапазоны версий, из-за чего менеджер пакетов не может использовать один общий экземпляр. Дубликат также может появиться из-за разных точек входа пакета, символических ссылок или различающихся настроек разрешения модулей.

Это увеличивает размер бандла и может быть особенно опасно для библиотек, которые должны существовать в одном экземпляре, например React.

Проверяют дерево lock-файла, peer dependencies, правила `resolve`, псевдонимы и возможность согласовать диапазоны зависимостей.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выбрать лимит размера бандла?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала измеряют текущую production-сборку и определяют, какие ресурсы влияют на ключевые пользовательские сценарии. Затем задают лимиты на начальные JavaScript и CSS, отдельные маршруты и допустимый рост в PR.

Полезно одновременно контролировать исходный и сжатый размер. Лимит должен опираться на цели производительности продукта, а не на случайное универсальное число.

Порог нужно регулярно пересматривать, но его не следует автоматически повышать после каждого превышения. Сначала нужно выяснить причину роста и оценить, оправдана ли она новой функциональностью.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Проблема | Проверка или решение |
| --- | --- |
| Большой начальный JavaScript | Разделение кода по маршрутам или компонентам |
| Тяжёлая библиотека графиков | Ленивый импорт и предварительная загрузка перед открытием |
| Tree shaking не работает | ESM, `sideEffects`, фактическая точка входа пакета |
| Дубликаты зависимостей | Дерево lock-файла и анализатор бандла |
| PR увеличил начальный чанк | Лимит размера в CI |
| Много мелких запросов | Укрупнить границы и проверить цепочки загрузки |
