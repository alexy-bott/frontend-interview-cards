## Вопрос

<br>

 💬 **Как переменные окружения попадают во frontend? Чем конфигурация времени сборки отличается от runtime config и почему в браузере нельзя хранить секреты?**

<h2></h2>

<br>
<dl>
<dd>

Браузер не имеет прямого доступа к переменным окружения операционной системы или контейнера. Значение может попасть во frontend двумя основными способами: быть встроено в клиентский код во время сборки или загружено приложением во время выполнения.

Build-time config, или конфигурация времени сборки, встраивается в итоговые файлы заранее:

```ts
const apiUrl = import.meta.env.VITE_API_URL;
```

При production-сборке Vite заменяет обращение к `VITE_API_URL` конкретным значением. Webpack обычно выполняет похожую подстановку через `DefinePlugin`, а Next.js встраивает клиентские переменные с префиксом `NEXT_PUBLIC_*`.

После сборки такое значение становится частью JavaScript-бандла. Изменение переменной окружения на сервере или в контейнере не изменит уже собранный SPA: потребуется новая сборка.

Префиксы `VITE_` и `NEXT_PUBLIC_` не скрывают и не защищают значение. Наоборот, они явно разрешают передать его в клиентский код.

Runtime config, или конфигурация времени выполнения, не встраивается в бандл заранее. Приложение получает её после сборки — например, из `config.js`, `config.json` или отдельного API.

Для статического SPA контейнер может при запуске создать файл конфигурации, который браузер загрузит до основного приложения:

```html
<script src="/config.js"></script>
```

```js
window.__APP_CONFIG__ = {
  API_URL: "https://api.example.com",
};
```

Так один и тот же Docker-образ можно разворачивать в тестовом и рабочем окружениях с разными адресами API без повторной сборки.

Runtime config в браузере всё равно является публичным. Пользователь может загрузить `config.js`, посмотреть ответ API или прочитать значение в памяти приложения. Его преимущество состоит не в защите данных, а в возможности изменить публичную конфигурацию без пересборки frontend-артефакта.

Конфигурацию времени выполнения нужно загрузить до кода, который её использует, и проверить при старте приложения. Если обязательное поле отсутствует или имеет неправильный формат, приложение должно показать понятную ошибку, а не продолжать работу с цепочкой значений `undefined`.

Для `config.js` или `config.json` отдельно настраивают кеширование. Старый файл конфигурации вместе с новым бандлом может направить приложение к неверному API или передать несовместимые параметры. Обычно такой файл не кешируют надолго либо используют контролируемую версию конфигурации.

В серверном приложении, например Next.js, существует ещё один вариант: server-only переменные могут читаться во время выполнения непосредственно серверным кодом. Они не попадают в браузер, пока разработчик явно не включит их в HTML, props, JSON-ответ или клиентский JavaScript.

Никакая конфигурация, доступная браузеру, не подходит для хранения секрета. Пользователь может прочитать JavaScript, DOM, загруженные файлы и запросы на вкладке Network.

Во frontend допустимо хранить публичный адрес API, идентификатор релиза, публичный Sentry DSN и настройки интерфейса. Недопустимо передавать пароль базы данных, ключ подписи, закрытый API-ключ или учётные данные внешнего сервиса.

Если операция требует секрета, её выполняют на сервере. Клиент отправляет разрешённые данные на backend, BFF, Server Action или Route Handler. Сервер проверяет пользователя, выполняет необходимую авторизацию и только затем обращается к внешнему сервису с закрытыми учётными данными.

BFF (Backend for Frontend) — это серверный слой, созданный специально под потребности конкретного frontend-приложения. Он может объединять внешние API, преобразовывать ответы и скрывать серверные ключи от браузера.

`.env` — это способ загрузить значения в процесс разработки или сборки, а не средство защиты. `.env.local` с локальными секретами не коммитят, но любое значение, которое затем попало в клиентский код или публичный runtime config, становится доступно пользователю независимо от исходного файла.

Пользовательские значения из env обычно приходят строками. Например, непустая строка `"false"` является truthy, то есть считается истинным значением в условии, а `Number(undefined)` возвращает `NaN`.

Поэтому конфигурацию нужно явно преобразовать и проверить при старте. Проверка по схеме или отдельная функция валидации позволяют остановить сборку либо запуск с понятным сообщением о неверном значении.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем конфигурация времени сборки отличается от конфигурации времени запуска?</strong></summary>

<dl>
<dd>
<h2></h2>

Значение времени сборки записывается в итоговые файлы заранее. Чтобы изменить его в статическом SPA, нужно создать новый frontend-артефакт.

Конфигурация времени запуска читается уже после сборки: сервером во время запроса либо браузером из отдельного файла или API. Благодаря этому один артефакт может работать в разных окружениях.

Runtime config сложнее: нужно отдельно организовать его загрузку, проверку, обработку ошибок и кеширование. Если конфигурация передаётся браузеру, она остаётся публичной.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему нельзя хранить секрет в <code>VITE_*</code> или <code>NEXT_PUBLIC_*</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Эти префиксы специально разрешают включить значение в клиентский JavaScript. Любой пользователь может скачать бандл и найти встроенную строку.

Ограничение доступа в интерфейсе, минификация, обфускация и отсутствие карты исходного кода не превращают опубликованное значение обратно в секрет.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>process.env</code> в браузере не является настоящим окружением Node.js?</strong></summary>

<dl>
<dd>
<h2></h2>

У браузера нет Node.js-объекта `process` с доступом к переменным операционной системы. Сборщик может заранее заменить конкретное выражение вроде `process.env.API_URL` значением или добавить ограниченную совместимую заглушку.

После публикации готового SPA изменение env контейнера не может изменить строку, которая уже записана в JavaScript-бандле.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли коммитить <code>.env</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычно коммитят `.env.example` со списком необходимых ключей и безопасными примерами значений. Он показывает разработчику, какую конфигурацию нужно предоставить, но не содержит настоящих секретов.

Файлы с локальными и рабочими секретами передают через защищённое хранилище или настройки окружения и исключают из Git. Публичные клиентские значения технически можно хранить в репозитории, но их публичность должна быть осознанной.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означает принцип «один раз собрать, многократно развернуть»?</strong></summary>

<dl>
<dd>
<h2></h2>

Один проверенный артефакт последовательно разворачивают в разных окружениях, меняя только конфигурацию времени выполнения.

Для статического SPA это обычно требует отдельного `config.js`, `config.json` или API конфигурации. Если значения `VITE_*` или `NEXT_PUBLIC_*` встроены при сборке, для их изменения потребуется новый артефакт.

Серверное приложение также может читать server-only переменные во время выполнения, если соответствующий код действительно выполняется на сервере при запуске или обработке запроса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как Next.js получает переменные окружения во время выполнения?</strong></summary>

<dl>
<dd>
<h2></h2>

Переменные с префиксом `NEXT_PUBLIC_*` встраиваются в клиентский код во время `next build` и после сборки уже не меняются.

Обычные переменные без этого префикса доступны только серверному коду. При динамическом серверном выполнении Next.js может прочитать их из окружения текущего процесса во время запроса.

Важно не передать секрет дальше в Client Component, HTML, props или JSON-ответ. Само чтение на сервере безопасно, но любое явно возвращённое клиенту значение становится публичным.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему env-флаг <code>"false"</code> может включить функцию?</strong></summary>

<dl>
<dd>
<h2></h2>

Пользовательские env-значения обычно являются строками. Непустая строка в JavaScript считается истинной, поэтому проверка `if (import.meta.env.VITE_FLAG)` воспримет строку `"false"` как `true`.

Значение нужно сравнить с ожидаемой строкой, например `value === "true"`, либо преобразовать и проверить через общую схему конфигурации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли использовать клиентский feature flag для защиты доступа?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Клиентский feature flag управляет отображением или поведением интерфейса, но пользователь может изменить JavaScript, состояние приложения или отправить запрос напрямую.

Backend должен самостоятельно проверять права пользователя для каждой защищённой операции. Скрытая кнопка и выключенный клиентский флаг не являются авторизацией.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Безопасно ли поместить секрет в <code>next.config.js -&gt; env</code> без <code>NEXT_PUBLIC_</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Значения из поля `env` в `next.config.js` подставляются в JavaScript во время сборки независимо от наличия префикса `NEXT_PUBLIC_`.

Для серверного секрета используют обычную переменную окружения и читают её только в коде, который гарантированно выполняется на сервере и не передаёт значение клиенту.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что нужно учесть у <code>config.js</code> в SPA?</strong></summary>

<dl>
<dd>
<h2></h2>

Файл нужно загрузить до инициализации приложения, проверить наличие обязательных полей и убедиться, что версия конфигурации совместима с frontend-артефактом.

`config.js` не должен содержать секреты, потому что браузер загружает его как обычный публичный ресурс.

Политика кеширования должна позволять быстро получить актуальное значение после развёртывания. Иначе старый `config.js` может пережить обновление приложения и направить новый frontend к неверному API.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Значение | Где хранить |
| --- | --- |
| Публичный адрес API | Конфигурация времени сборки или запуска |
| Feature flag интерфейса | Публичная конфигурация или сервис управления функциями |
| Идентификатор релиза | Публичные метаданные сборки |
| Пароль базы данных | Только серверное хранилище секретов |
| Один образ для разных окружений | Конфигурация времени запуска |
| Логическое или числовое значение из env | Явное преобразование и проверка по схеме |
