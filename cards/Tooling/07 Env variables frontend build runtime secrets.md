#### Вопрос

Как переменные окружения попадают во frontend? Чем конфигурация времени сборки отличается от runtime config и почему в браузере нельзя хранить секреты?

#### Ответ

Браузер не читает переменные окружения операционной системы. В обычном SPA сборщик заменяет разрешённые выражения конкретными значениями во время сборки. После этого значение становится частью JavaScript-бандла и не меняется без новой сборки.

Build-time config, или конфигурация времени сборки, работает так:

```ts
const apiUrl = import.meta.env.VITE_API_URL;
```

Vite подставляет значение `VITE_API_URL` в production-JavaScript. Webpack обычно использует `DefinePlugin`, а Next.js встраивает переменные `NEXT_PUBLIC_*`. Префикс не скрывает значение, а явно разрешает его публикацию в клиентском коде.

Runtime config, или конфигурация времени запуска, загружается после сборки. Для SPA контейнер может при старте создать `config.js` или `config.json`, а приложение прочитает его до инициализации. Тогда один образ Docker можно последовательно разворачивать в тестовом и рабочем окружениях без пересборки:

```html
<script src="/config.js"></script>
```

```js
window.__APP_CONFIG__ = {
  API_URL: "https://api.example.com",
};
```

Конфигурацию времени запуска нужно проверять, версионировать и загружать до кода, который её использует. Для неё отдельно настраивают заголовки кеширования: старый `config.js` вместе с новым бандлом приложения способен сломать запуск. Ошибка загрузки должна приводить к понятному сообщению, а не к цепочке значений `undefined`.

Никакая клиентская конфигурация не подходит для секрета. Пользователь может прочитать JavaScript, карты исходного кода, DOM и запросы на вкладке Network. Допустимы публичный адрес API, идентификатор релиза, публичный Sentry DSN и feature flag, то есть переключатель функции интерфейса. Недопустимы закрытый API-ключ, пароль базы данных, ключ подписи и учётные данные сервиса.

Если операция требует секрета, её выполняют на backend, в BFF (Backend for Frontend), Server Action или Route Handler. BFF является серверным слоем, созданным под потребности конкретного frontend-приложения. Клиент отправляет разрешённые данные на сервер, сервер проверяет пользователя и добавляет закрытые учётные данные при обращении к внешнему сервису.

`.env` является способом загрузить значения, а не средством защиты. `.env.local` с секретами не коммитят, но любое значение, которое сборщик включил в клиентский код, становится публичным независимо от исходного файла.

Все значения из env обычно приходят строками. Непустая строка `"false"` является truthy, то есть считается истинным значением в условии, а `Number(undefined)` даёт `NaN`. Поэтому конфигурацию нужно явно преобразовать и проверить при старте. Проверка по схеме позволяет остановить сборку или запуск с понятной ошибкой.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Чем конфигурация времени сборки отличается от конфигурации времени запуска?
>
> **Ответ:** Значение времени сборки записывается в файлы заранее и требует нового артефакта для изменения. Конфигурация времени запуска читается при старте сервера или контейнера либо при загрузке приложения, поэтому один артефакт может работать в разных окружениях. Второй подход сложнее из-за отдельной загрузки, проверки и кеширования конфигурации.

> [!followup]
> **Вопрос:** Почему нельзя хранить секрет в `VITE_*` или `NEXT_PUBLIC_*`?
>
> **Ответ:** Эти префиксы специально разрешают включить значение в клиентский JavaScript. Любой пользователь может скачать файл и найти строку. Ограничение доступа в интерфейсе, минификация и отсутствие карты исходного кода не превращают значение обратно в секрет.

> [!followup]
> **Вопрос:** Почему `process.env` в браузере не является настоящим окружением Node.js?
>
> **Ответ:** У браузера нет Node.js-объекта `process` с переменными окружения. Сборщик статически заменяет известное выражение или добавляет совместимую заглушку. Изменение env контейнера после публикации готового SPA не способно изменить строку, уже записанную в JavaScript.

> [!followup]
> **Вопрос:** Нужно ли коммитить `.env`?
>
> **Ответ:** Обычно коммитят `.env.example` со списком ключей и безопасными примерами. Реальные локальные и рабочие секреты передают через защищённое хранилище и исключают из Git. Публичные клиентские значения можно хранить в репозитории, но команда должна понимать, что пользователь сможет их прочитать.

> [!followup]
> **Вопрос:** Что означает принцип «один раз собрать, многократно развернуть»?
>
> **Ответ:** Один проверенный артефакт разворачивают во всех окружениях, меняя конфигурацию при запуске. Для статического frontend это требует runtime config или вставки значений на сервере. Если `VITE_*` или `NEXT_PUBLIC_*` записаны при сборке, для разных значений нужны разные артефакты.

> [!followup]
> **Вопрос:** Почему env-флаг `"false"` может включить функцию?
>
> **Ответ:** Непустая строка в JavaScript считается истинной. Проверка `if (import.meta.env.VITE_FLAG)` воспримет `"false"` как `true`. Значение нужно сравнить с ожидаемой строкой или преобразовать по схеме в `boolean`.

> [!followup]
> **Вопрос:** Безопасно ли поместить секрет в `next.config.js -> env` без `NEXT_PUBLIC_`?
>
> **Ответ:** Нет. Значения поля `env` из `next.config.js` всегда подставляются в JavaScript-бандл. Для серверного секрета используют обычную переменную окружения и читают её только в коде, который гарантированно выполняется на сервере.

> [!followup]
> **Вопрос:** Что нужно учесть у `config.js` в SPA?
>
> **Ответ:** Его нужно загрузить до приложения, проверить обязательные поля и согласовать версии конфигурации и frontend-артефакта. Файл не должен содержать секреты. Политика кеширования должна позволять быстро получать новое значение, иначе старый `config.js` переживёт развёртывание и направит новое приложение к неверному API.

#### Где это встречается во frontend

| Значение | Где хранить |
| --- | --- |
| Публичный адрес API | Конфигурация времени сборки или запуска |
| Feature flag интерфейса | Публичная конфигурация или сервис управления функциями |
| Идентификатор релиза | Публичные метаданные сборки |
| Пароль базы данных | Только серверное хранилище секретов |
| Один образ для разных окружений | Конфигурация времени запуска |
| Логическое или числовое значение из env | Явное преобразование и проверка по схеме |
