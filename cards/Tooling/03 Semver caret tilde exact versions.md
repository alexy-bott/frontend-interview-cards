## Вопрос

<br>

 💬 **Как работает semantic versioning? Что означают `^`, `~`, точная версия и prerelease?**

<h2></h2>

<br>
<dl>
<dd>

Semantic Versioning, или семантическое версионирование, использует формат `major.minor.patch`, например `3.2.1`. Его части сообщают ожидаемый характер изменений:

- `major`, или мажорная часть, меняется при несовместимом изменении публичного API;
- `minor`, или минорная часть, добавляет обратно совместимую возможность;
- `patch`, или патч-часть, содержит обратно совместимое исправление.

Это договорённость автора пакета, а не техническая гарантия. Ошибка или нарушение semver может сломать приложение даже после патч-обновления, поэтому lock-файл и проверки остаются обязательными.

В `package.json` обычно указывают диапазон:

| Запись | Допустимый диапазон |
| --- | --- |
| `1.2.3` | Только `1.2.3` |
| `~1.2.3` | `>=1.2.3 <1.3.0` |
| `^1.2.3` | `>=1.2.3 <2.0.0` |
| `>=1.2 <2` | Явный составной диапазон |
| `*` | Любая версия, обычно слишком широкий выбор |

Caret `^` разрешает изменения, которые не меняют крайнюю левую ненулевую часть. Поэтому для стабильной версии он обычно допускает минорные и патч-обновления, но у `0.x` ведёт себя строже:

- `^0.2.3` означает `>=0.2.3 <0.3.0`;
- `^0.0.3` означает `>=0.0.3 <0.0.4`.

Версии `0.y.z` относятся к начальной разработке, где публичный API ещё не считается стабильным. Минорное изменение такого пакета может быть несовместимым, поэтому поведение caret ограничено.

Prerelease, то есть предварительная версия, имеет суффикс `-alpha.1`, `-beta.2` или `-rc.1`. Она сортируется ниже соответствующего стабильного релиза и обычно не попадает в обычный диапазон без явного разрешения. npm dist-tag, например `latest`, `next` или `beta`, является именованным указателем реестра пакетов (registry) на опубликованную версию и не входит в сам алгоритм semver.

Lock-файл фиксирует конкретную версию, выбранную из диапазона. Пока он не меняется, два проекта с `^1.2.3` устанавливают одну зафиксированную версию. После удаления или обновления lock-файла resolver, то есть алгоритм разрешения зависимостей, может выбрать более новый допустимый релиз. То же относится к transitive dependencies, то есть зависимостям зависимостей.

Точная версия уменьшает неявные обновления при новом разрешении, но не заменяет lock-файл: дерево содержит множество вложенных диапазонов. Полная воспроизводимость достигается lock-файлом и строгой установкой, а точная запись лишь определяет политику конкретной прямой зависимости.

При обновлении важно отдельно учитывать peer dependencies. Например, плагин может поддерживать React `^18 || ^19`, но менеджер пакетов только проверяет заявленный диапазон. Фактическое поведение подтверждают описание релиза, проверка типов, тесты и production-сборка.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем <code>^1.2.3</code> отличается от <code>~1.2.3</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Caret разрешает минорные и патч-обновления в пределах мажорной версии, то есть версии до `2.0.0`. Tilde сохраняет минорную часть и разрешает только патч-обновления до `1.3.0`. В обоих случаях нижняя граница начинается с указанной версии.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>^0.2.3</code> не разрешает <code>0.3.0</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

До `1.0.0` semver не считает публичный API стабильным. Caret сохраняет крайнюю левую ненулевую часть, поэтому для `0.2.3` совместимым диапазоном считается только `0.2.x`. Для `0.0.3` фиксируется даже патч-часть.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое prerelease и попадёт ли beta в обычное обновление?</strong></summary>

<dl>
<dd>
<h2></h2>

Prerelease является предварительным релизом с суффиксом вроде `2.0.0-beta.1`. Обычный диапазон, который не включает prerelease явно, обычно его не выбирает. Для тестирования используют конкретную версию, подходящий диапазон или npm tag `next`/`beta`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем npm tag <code>latest</code> отличается от версии?</strong></summary>

<dl>
<dd>
<h2></h2>

Версия является неизменяемым semver-идентификатором опубликованного пакета. Dist-tag является изменяемым именем, которое registry связывает с версией. Команда установки без версии обычно использует `latest`, а автор пакета может направить `next` на предварительный релиз.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда оправдана точная версия?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда зависимость нестабильна, критично влияет на сборку или команда хочет подтверждать каждое обновление вручную. Для форматтера точная версия также предотвращает шумные изменения форматирования. Но точная запись не отменяет регулярные обновления безопасности и проверку lock-файла.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему проект сломался, хотя прямые зависимости не менялись?</strong></summary>

<dl>
<dd>
<h2></h2>

Мог измениться lock-файл и выбрать новую транзитивную зависимость, peer dependency или платформенный пакет. Нужно сравнить изменения lock-файла и итоговое дерево командами менеджера пакетов. Одинаковый `package.json` без одинакового lock-файла не означает одинаковую установку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать, если patch-релиз нарушил совместимость?</strong></summary>

<dl>
<dd>
<h2></h2>

Можно временно вернуть предыдущий lock-файл или применить документированное принудительное правило версии, изучить обсуждение ошибки и описание релиза, затем добавить регрессионный тест. Semver описывает намерение автора, но не защищает от ошибки в реализации или публикации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как обновлять major-версию?</strong></summary>

<dl>
<dd>
<h2></h2>

Обновление выносят в отдельный PR, читают руководство по миграции, проверяют peer dependencies и меняют код поэтапно. Затем запускают проверку типов, модульные и интеграционные тесты, production-сборку и ключевые пользовательские сценарии. Для крупных миграций полезно сначала установить промежуточные версии и убрать устаревшие API.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что проверить |
| --- | --- |
| Минорная версия обновилась без изменения `package.json` | Диапазон и изменения lock-файла |
| Два React в бандле | Peer dependencies и дерево пакетов |
| Нужна beta-версия библиотеки | Конкретная предварительная версия или dist-tag |
| Инструмент сборки сломался после обновления | Описание релиза и временная фиксация точной версии |
| Автоматические PR Renovate | Группировка, CI и политика мажорных обновлений |
