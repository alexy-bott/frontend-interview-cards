## Вопрос

<br>

 💬 **Что такое CSR, SSR, SSG и hydration? Почему возникает hydration mismatch?**

<h2></h2>

<br>
<dl>
<dd>

CSR, SSR и SSG описывают, где и когда создаётся первоначальный HTML страницы. Hydration, или гидратация, является отдельным клиентским этапом: React связывает уже полученный серверный HTML со своим деревом, добавляет обработчики событий и делает интерфейс интерактивным.

| Подход | Когда создаётся HTML | Типичный сценарий |
| --- | --- | --- |
| CSR, клиентский рендеринг | В браузере после загрузки JavaScript | Внутреннее приложение без требования к первоначальному HTML |
| SSR, серверный рендеринг | На сервере для запроса или серверного обновления | Персональная или часто меняющаяся страница |
| SSG, статическая генерация | Заранее во время сборки | Документация, блог, стабильный каталог |

SSR может раньше показать содержимое и дать поисковому роботу готовый HTML, но не делает приложение интерактивным без клиентского JavaScript. Он также добавляет серверную нагрузку, время ответа и требование выполнять код рендера в двух средах. SSG быстро отдаётся с CDN, но устаревает до следующей сборки или ревалидации, то есть фонового обновления статического результата. Фреймворк может кешировать SSR-результат или частично обновлять статическую страницу, поэтому реальные стратегии образуют спектр, а не три жёстких режима.

Для создания HTML сервер использует API серверного рендеринга React, а браузер вызывает `hydrateRoot(container, <App />)`. Первый клиентский рендер должен создать то же содержимое, что сервер. React сопоставляет дерево с существующим DOM и подключает поведение вместо безусловного создания всех узлов заново.

Hydration mismatch, или несовпадение при гидратации, означает, что первоначальный клиентский вывод отличается от серверного HTML. Частые причины:

- `Date.now()`, `Math.random()` или генерация нового идентификатора во время рендера;
- разные локаль, часовой пояс или форматирование даты;
- чтение `window`, `localStorage` или размера экрана только на клиенте;
- изменившиеся данные без передачи клиенту того же снимка;
- условие `typeof window !== "undefined"` с разным JSX;
- невалидная HTML-вложенность, которую браузер исправил до React;
- расширение браузера или сторонний скрипт, изменивший DOM.

Несовпадение является ошибкой, а не нормальным способом показать разные интерфейсы. React может отказаться от гидратации проблемного поддерева и создать его заново на клиенте, потеряв преимущество SSR и потенциально вызвав скачок интерфейса. `suppressHydrationWarning` скрывает предупреждение только на один уровень и подходит для неизбежного отличия вроде метки времени, но не исправляет структуру.

Для значения, доступного только в браузере, можно сначала вернуть одинаковый HTML, а после монтирования обновить его в `useEffect`. Это создаёт дополнительный рендер и может визуально переключить содержимое, поэтому для крупных браузерных виджетов фреймворк часто предоставляет отдельную клиентскую границу или отключение SSR. Стабильные идентификаторы разметки получают через `useId`, а не случайное значение.

React 18 добавил конкурентный потоковый SSR: сервер может отправить каркас страницы до готовности всех границ Suspense, а браузер выборочно гидрировать доступные части. React 19 улучшил сообщение о несовпадении единым сравнением разметки. React 19.2 добавил низкоуровневые React DOM API для частичного предварительного рендеринга (Partial Pre-rendering) и последующего продолжения (resume), а также изменил группировку раскрытия Suspense при SSR. В приложениях эти API обычно предоставляет фреймворк.

SSR и React Server Components не являются одним механизмом. SSR создаёт HTML для загрузки страницы. RSC создаёт сериализованное описание React-дерева, часть которого никогда не попадает в клиентский бандл; первоначальный RSC-результат фреймворк может дополнительно преобразовать в HTML через SSR.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Hydration заново создаёт весь DOM?</strong></summary>

<dl>
<dd>
<h2></h2>

При совпадающей разметке React переиспользует существующие DOM-узлы и подключает к ним обработчики и состояние. Он всё равно выполняет клиентский рендер для сопоставления дерева. При несовпадении React может пересоздать проблемное поддерево или весь корневой узел, поэтому совпадение является обязательным контрактом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем SSR отличается от CSR?</strong></summary>

<dl>
<dd>
<h2></h2>

При CSR первоначальный интерфейс строит браузер после загрузки и выполнения JavaScript. При SSR сервер заранее отправляет HTML, а браузер позднее гидрирует его. SSR улучшает наличие первоначального контента, но приложение может какое-то время выглядеть готовым и ещё не реагировать на ввод, если JavaScript загружается медленно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем SSR отличается от SSG?</strong></summary>

<dl>
<dd>
<h2></h2>

SSR вычисляет результат на сервере во время запроса или динамического обновления. SSG создаёт файл заранее и позволяет отдавать его напрямую с CDN. SSG дешевле на запрос, но требует стратегии обновления данных; фреймворк может добавлять ревалидацию и получать промежуточную модель.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что даёт потоковый SSR?</strong></summary>

<dl>
<dd>
<h2></h2>

Сервер начинает отправлять готовый HTML, не ожидая медленных частей страницы. Границы Suspense отмечают места, которые можно раскрыть позже. Это сокращает ожидание каркаса страницы, но не отменяет загрузку JavaScript и гидратацию интерактивных Client Components.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как безопасно использовать <code>window</code> или <code>localStorage</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Серверный рендер не должен обращаться к браузерным API. Для некритичного клиентского значения сначала рендерят одинаковый запасной результат, затем читают API в эффекте. Если весь компонент зависит от браузера, используют клиентский механизм фреймворка. Простая проверка `typeof window` внутри JSX часто создаёт несовпадение.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>useId</code> подходит для SSR, а <code>Math.random()</code> нет?</strong></summary>

<dl>
<dd>
<h2></h2>

React координирует `useId` так, чтобы сервер и клиент получили совместимые идентификаторы при одинаковом дереве. `Math.random()` создаёт независимые значения в двух средах. `useId` предназначен для связей доступности, например между полем и подписью, а не для `key` элементов списка.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как это проявляется в Next.js 14 App Router?</strong></summary>

<dl>
<dd>
<h2></h2>

Фреймворк сочетает Server Components, SSR или статическую генерацию, потоковую передачу через Suspense и гидратацию Client Components. Конкретный маршрут может иметь статические и динамические части. Директива `"use client"` не означает полный CSR страницы: сервер всё ещё может сформировать её начальный HTML.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что проверить |
| --- | --- |
| `Hydration failed` | Первый серверный и клиентский вывод, HTML-вложенность и снимок данных |
| Дата отличается после загрузки | Часовой пояс, локаль и место форматирования |
| Компонент использует браузерный API | Клиентская граница или чтение после монтирования |
| Страница долго остаётся неинтерактивной | Размер клиентского бандла и стоимость гидратации |
| Медленный ответ сервера | Границы потоковой передачи и серверные запросы |
| Статическая страница устаревает | Ревалидация или переход к динамической стратегии |
