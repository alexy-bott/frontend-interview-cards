## Вопрос

<br>

 💬 **Что такое CSR, SSR, SSG и hydration? Почему возникает hydration mismatch?**

<h2></h2>

<br>
<dl>
<dd>

CSR, SSR и SSG описывают, где и когда создаётся первоначальная разметка страницы. Hydration, или гидратация, является отдельным клиентским этапом: React присоединяет логику компонентов к уже полученному серверному HTML, подключает обработчики событий и берёт существующий DOM под управление.

| Подход | Когда создаётся HTML | Типичный сценарий |
| --- | --- | --- |
| CSR, клиентский рендеринг | В браузере после загрузки и выполнения JavaScript | Внутреннее приложение без требования к первоначальному HTML |
| SSR, серверный рендеринг | На сервере при запросе | Персональная или часто меняющаяся страница |
| SSG, статическая генерация | Заранее во время сборки | Документация, блог, стабильный каталог |

SSR может раньше показать содержимое и дать поисковому роботу готовый HTML, но не делает приложение интерактивным без клиентского JavaScript. Он также добавляет серверную нагрузку, время ответа и требование выполнять код рендера в двух средах.

SSG быстро отдаётся с CDN, но созданный результат остаётся прежним до следующей сборки. Фреймворк может дополнительно поддерживать ревалидацию или ISR, то есть пересоздание статического результата без полной сборки приложения.

SSR-результат также может кешироваться. Поэтому реальные стратегии образуют спектр, а не три жёстко изолированных режима.

Для создания HTML сервер использует API серверного рендеринга React, а браузер вызывает:

```ts
hydrateRoot(container, <App />);
```

Первый клиентский рендер должен создать то же содержимое, что сервер. React сопоставляет дерево компонентов с существующим DOM и по возможности переиспользует его вместо безусловного создания всех узлов заново.

Hydration mismatch, или несовпадение при гидратации, означает, что первоначальный клиентский вывод отличается от серверного HTML.

Частые причины:

- `Date.now()`, `Math.random()` или генерация нового идентификатора во время рендера;
- разные локаль, часовой пояс или форматирование даты;
- чтение `window`, `localStorage` или размера экрана только на клиенте;
- изменившиеся данные без передачи клиенту того же снимка;
- условие `typeof window !== "undefined"` с разным JSX;
- невалидная HTML-вложенность, которую браузер исправил до React;
- расширение браузера или сторонний скрипт, изменивший DOM.

React 19 лучше учитывает некоторые элементы, добавленные сторонними скриптами и расширениями, особенно внутри `<head>` и `<body>`, но произвольное изменение DOM до hydration всё ещё может привести к несовпадению.

Hydration mismatch является ошибкой, а не нормальным способом показать разные интерфейсы.

React может восстановиться после некоторых hydration errors. Если совпадение восстановить нельзя, соответствующее React-дерево создаётся заново на клиенте. Это приводит к дополнительной работе, может вызвать скачок интерфейса и лишает страницу части преимуществ SSR. В худшем случае обработчики событий могут быть связаны с неправильными элементами.

`suppressHydrationWarning` скрывает предупреждение только на один уровень и подходит для редкого неизбежного отличия, например метки времени:

```tsx
<time suppressHydrationWarning>
  {new Date().toLocaleString()}
</time>
```

Он не исправляет несовпадение структуры. React также не пытается исправить несовпадающий текст элемента, для которого установлен `suppressHydrationWarning`.

Для значения, доступного только в браузере, можно сначала вернуть одинаковый серверный и первоначальный клиентский HTML, а после монтирования обновить его в `useEffect`:

```tsx
function ClientValue() {
  const [value, setValue] = useState<string | null>(null);

  useEffect(() => {
    setValue(localStorage.getItem("value"));
  }, []);

  return <span>{value ?? "Загрузка..."}</span>;
}
```

Такой подход избегает mismatch, потому что первый клиентский рендер совпадает с серверным. Но сразу после hydration выполняется дополнительный рендер, который может замедлить загрузку и визуально переключить содержимое.

Для крупных браузерных виджетов фреймворк часто предоставляет отдельную клиентскую границу или возможность отключить SSR.

Стабильные идентификаторы разметки получают через `useId`, а не через случайное значение:

```tsx
function Field() {
  const descriptionId = useId();

  return (
    <>
      <input aria-describedby={descriptionId} />
      <p id={descriptionId}>Описание поля</p>
    </>
  );
}
```

`useId` требует одинакового дерева компонентов на сервере и клиенте. Он предназначен прежде всего для связей доступности, а не для `key` элементов списка.

React 18 добавил streaming SSR через Suspense и selective hydration. Сервер может отправить каркас страницы до готовности всех Suspense boundaries, а браузер может гидратировать доступные интерактивные части, не ожидая завершения всей страницы.

React 19 улучшил сообщения о hydration mismatch: вместо нескольких разрозненных ошибок React показывает одно сообщение с diff серверного и клиентского результата.

React 19.2 добавил низкоуровневые React DOM API для Partial Pre-rendering: статическую часть приложения можно подготовить заранее, сохранить отложенное состояние, а затем продолжить рендеринг через `resume`.

React 19.2 также изменил раскрытие серверных Suspense boundaries: близкие по времени результаты кратковременно группируются, чтобы несколько частей интерфейса могли появиться вместе. В приложениях Partial Pre-rendering и resume API обычно интегрирует фреймворк.

SSR и React Server Components не являются одним механизмом.

SSR создаёт HTML для первоначальной загрузки страницы.

RSC создаёт сериализованное описание React-дерева. Код Server Components не попадает в клиентский бандл, а их результат фреймворк может дополнительно преобразовать в HTML через SSR.

В браузере гидратируются интерактивные Client Components. Сами Server Components в браузере не выполняются и не гидратируются.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Hydration заново создаёт весь DOM?</strong></summary>

<dl>
<dd>
<h2></h2>

При совпадающей разметке React переиспользует существующие DOM-узлы, присоединяет к ним логику компонентов и берёт DOM под управление. Он всё равно выполняет первоначальный клиентский рендер, чтобы сопоставить React-дерево с серверным HTML.

Если разметка не совпадает, React может восстановиться после части ошибок. При существенном несовпадении соответствующее дерево или вся граница создаётся заново на клиенте.

Поэтому совпадение серверного и первоначального клиентского результата является обязательным контрактом, а не только оптимизацией.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем SSR отличается от CSR?</strong></summary>

<dl>
<dd>
<h2></h2>

При CSR первоначальный интерфейс строит браузер после загрузки и выполнения JavaScript.

При SSR сервер заранее отправляет HTML, а браузер позднее гидрирует интерактивную часть приложения.

SSR улучшает наличие первоначального контента, но приложение может какое-то время выглядеть готовым и ещё не реагировать на ввод, если клиентский JavaScript загружается или выполняется медленно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем SSR отличается от SSG?</strong></summary>

<dl>
<dd>
<h2></h2>

SSR вычисляет результат на сервере при запросе.

SSG создаёт HTML заранее во время сборки и позволяет отдавать его напрямую с CDN или статического хостинга.

SSG дешевле на запрос, но без дополнительного механизма обновляется только при новой сборке. Фреймворк может добавить ревалидацию или ISR и получить промежуточную модель между статической генерацией и динамическим серверным рендерингом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что даёт потоковый SSR?</strong></summary>

<dl>
<dd>
<h2></h2>

Сервер начинает отправлять готовый HTML, не ожидая медленных частей страницы.

Suspense boundaries отмечают области, для которых сначала можно отправить fallback, а готовое содержимое передать позднее тем же потоком.

Это сокращает ожидание каркаса страницы, но не отменяет загрузку JavaScript и hydration интерактивных Client Components.

Selective hydration позволяет React в первую очередь гидратировать доступные или более приоритетные части интерфейса, не ожидая готовности всего дерева.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как безопасно использовать <code>window</code> или <code>localStorage</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Серверный рендер не должен обращаться к браузерным API, потому что на сервере отсутствуют:

```ts
window
document
localStorage
matchMedia
```

Для некритичного клиентского значения сначала рендерят одинаковый запасной результат, а затем читают API в `useEffect`.

`useEffect` не выполняется на сервере, поэтому первоначальный серверный и клиентский вывод остаётся одинаковым.

Если весь компонент зависит от браузера, используют клиентский механизм фреймворка или отключают для него SSR.

Простая проверка:

```tsx
typeof window !== "undefined"
  ? <ClientContent />
  : <ServerContent />
```

внутри JSX часто создаёт mismatch, потому что сервер и первый клиентский рендер возвращают разную разметку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>useId</code> подходит для SSR, а <code>Math.random()</code> нет?</strong></summary>

<dl>
<dd>
<h2></h2>

React координирует `useId`, чтобы сервер и клиент получили совместимые идентификаторы при одинаковом дереве компонентов.

`Math.random()` создаёт независимые значения в двух средах:

```text
server → 0.351
client → 0.847
```

Из-за этого атрибуты `id`, `htmlFor` или `aria-describedby` могут не совпасть при hydration.

`useId` предназначен для связей доступности, например между полем, подписью и описанием:

```tsx
const hintId = useId();

<input aria-describedby={hintId} />
<p id={hintId}>Подсказка</p>
```

Он не предназначен для `key` элементов списка. `key` должен создаваться из данных.

`useId` также требует одинакового дерева компонентов на сервере и клиенте. Если структура отличается, сгенерированные идентификаторы тоже могут разойтись.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как это проявляется в Next.js 14 App Router?</strong></summary>

<dl>
<dd>
<h2></h2>

Next.js App Router сочетает:

- Server Components;
- SSR или статическую генерацию;
- RSC Payload;
- streaming через Suspense;
- hydration Client Components.

Конкретный маршрут может одновременно содержать статические, динамические, серверные и интерактивные клиентские части.

Директива:

```tsx
"use client";
```

не означает полный CSR страницы.

При первоначальной загрузке Next.js всё ещё может сформировать HTML Client Component на сервере. После загрузки JavaScript этот компонент гидратируется в браузере.

Server Components формируют результат на сервере, но их код не отправляется клиенту и не гидратируется.

Поэтому в одной странице могут одновременно использоваться:

```text
Server Component
→ выполняется только на сервере

Client Component
→ участвует в первоначальном HTML
→ затем гидратируется в браузере
```

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что проверить |
| --- | --- |
| `Hydration failed` | Первый серверный и клиентский вывод, HTML-вложенность и снимок данных |
| Дата отличается после загрузки | Часовой пояс, локаль и место форматирования |
| Компонент использует браузерный API | Клиентская граница или чтение после монтирования |
| Страница долго остаётся неинтерактивной | Размер клиентского бандла и стоимость hydration |
| Медленный ответ сервера | Suspense boundaries, streaming и серверные запросы |
| Статическая страница устаревает | Новая сборка, ревалидация или переход к динамической стратегии |
