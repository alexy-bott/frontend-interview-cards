## Вопрос

<br>

 💬 **Какие правила действуют для хуков React? Для чего создают пользовательские хуки?**

<h2></h2>

<br>
<dl>
<dd>

Hooks, или хуки, — функции React, которые позволяют функциональному компоненту использовать:

- состояние;
- Context;
- `ref`;
- эффекты;
- другие возможности React.

Для обычных Hooks действуют два основных правила.

Первое правило — вызывать Hooks только на верхнем уровне функционального компонента или custom hook и в одинаковом порядке при каждом рендере.

Обычные Hooks нельзя вызывать:

- внутри условия;
- внутри цикла;
- во вложенной функции;
- в обработчике события;
- в `async`-функции;
- в `try`, `catch` или `finally`;
- после условного `return`;
- на уровне модуля.

Неправильно:

```tsx
function Chat({
  isConnected,
}: {
  isConnected: boolean;
}) {
  if (isConnected) {
    useEffect(() => {
      return subscribe();
    }, []);
  }

  return <ChatContent />;
}
```

Правильно вызвать Hook безусловно, а проверку перенести внутрь:

```tsx
function Chat({
  isConnected,
}: {
  isConnected: boolean;
}) {
  useEffect(() => {
    if (!isConnected) {
      return;
    }

    return subscribe();
  }, [isConnected]);

  return <ChatContent />;
}
```

Другой вариант — выделить отдельный компонент:

```tsx
function Chat({
  isConnected,
}: {
  isConnected: boolean;
}) {
  return isConnected
    ? <ConnectedChat />
    : <DisconnectedChat />;
}
```

React связывает состояние обычных Hooks с последовательностью их вызовов в конкретной позиции компонента в React-дереве.

Например, при первом рендере порядок выглядит так:

```text
1. useState
2. useEffect
3. useRef
```

Если при следующем рендере условие пропустит первый Hook, React получит другую последовательность:

```text
1. useEffect
2. useRef
```

React больше не сможет правильно сопоставить внутреннее состояние с вызовами Hooks.

Поэтому обычные Hooks должны вызываться в одинаковом порядке при каждом рендере.

Второе правило — вызывать Hooks только во время рендера React-компонента или другого custom hook.

Правильно:

```tsx
function Profile() {
  const [
    user,
    setUser,
  ] = useState<User | null>(
    null,
  );

  return <ProfileView user={user} />;
}
```

Правильно внутри custom hook:

```tsx
function useOnlineStatus() {
  const [
    isOnline,
    setIsOnline,
  ] = useState(
    navigator.onLine,
  );

  // ...
}
```

Неправильно вызывать Hook в обычной вспомогательной функции:

```tsx
function calculateValue() {
  const [
    value,
    setValue,
  ] = useState(0);

  return value;
}
```

Нельзя также вызывать компонент как обычную функцию:

```tsx
const content = Profile();
```

Компонент должен передаваться React через JSX:

```tsx
const content = <Profile />;
```

Тогда React управляет его рендером и корректно связывает вызовы Hooks с позицией компонента в дереве.

Custom hook, или пользовательский хук, — функция, которая переиспользует связанную React-логику.

Его имя начинается с:

```text
use
```

после которого обычно идёт заглавная буква:

```text
useOnlineStatus
useMediaQuery
useDebouncedValue
```

Так линтер и разработчики понимают, что функция:

- может вызывать другие Hooks;
- должна соблюсти Rules of Hooks;
- может содержать локальное состояние и эффекты.

Обычную функцию, которая не вызывает Hooks и не является custom hook, не следует называть с префиксом `use`.

Custom hook переиспользует логику состояния и синхронизации, но обычно не определяет JSX.

Например, `useOnlineStatus` может скрывать:

- чтение начального сетевого состояния;
- подписку на события `online` и `offline`;
- очистку подписки;
- предоставление текущего результата компоненту.

Компонент использует готовый контракт:

```tsx
function Status() {
  const isOnline =
    useOnlineStatus();

  return (
    <p>
      {isOnline
        ? "В сети"
        : "Нет подключения"}
    </p>
  );
}
```

Custom hook переиспользует код, но не делит локальное состояние между вызовами автоматически.

Например:

```tsx
const first =
  useOnlineStatus();

const second =
  useOnlineStatus();
```

Каждый вызов создаёт собственную цепочку внутренних Hooks.

Общее состояние появляется только тогда, когда оба вызова используют один реактивный внешний источник:

- Context;
- внешний store с подпиской;
- кеш библиотеки запросов;
- другой источник, интегрированный с React.

Один изменяемый объект на уровне модуля сам по себе не является полноценным React-состоянием:

```ts
const sharedState = {
  value: 0,
};
```

Изменение такого объекта не уведомит React и не запустит рендер без отдельного механизма подписки.

Хороший custom hook выражает понятный сценарий:

```text
useOnlineStatus
useResizeObserver
useProductSearch
useProfileEditor
```

Он скрывает детали:

- состояния;
- подписок;
- очистки;
- работы со сторонним API;
- координации нескольких Hooks.

Механическая оболочка над одним `useState` обычно не добавляет пользы:

```tsx
function useCounter() {
  return useState(0);
}
```

Она становится оправданной, если формирует предметный контракт и скрывает реальные правила:

```tsx
function useCartQuantity(
  initialQuantity: number,
) {
  const [
    quantity,
    setQuantity,
  ] = useState(
    initialQuantity,
  );

  function increment() {
    setQuantity(
      (value) => value + 1,
    );
  }

  function decrement() {
    setQuantity(
      (value) =>
        Math.max(1, value - 1),
    );
  }

  return {
    quantity,
    increment,
    decrement,
  };
}
```

Входные параметры и возвращаемые значения custom hook являются его публичным контрактом.

Например, hook может вернуть:

- данные;
- состояние операции;
- функции действий;
- `ref`;
- props для передачи элементу.

Новая функция или объект обычно создаются заново при каждом рендере:

```tsx
return {
  value,
  reset: () => {
    setValue(initialValue);
  },
};
```

Это важно, если потребитель использует возвращённое значение:

- в зависимостях Effect;
- как prop мемоизированного компонента;
- как ключ кеша или подписки.

Но оборачивать все функции и объекты в `useCallback` и `useMemo` автоматически не нужно.

Стабильную identity предоставляют осознанно, когда:

- она является частью контракта hook;
- потребитель действительно от неё зависит;
- измерения показывают проблему производительности.

API `use`, доступный в React 19, является специальным исключением из обычного правила верхнего уровня.

Через него можно прочитать Promise или Context:

```tsx
const data = use(dataPromise);
```

```tsx
const theme = use(ThemeContext);
```

В отличие от обычных Hooks, `use` можно вызывать внутри условий и циклов:

```tsx
function Message({
  shouldReadTheme,
}: {
  shouldReadTheme: boolean;
}) {
  if (shouldReadTheme) {
    const theme =
      use(ThemeContext);

    return (
      <p className={theme}>
        Сообщение
      </p>
    );
  }

  return <p>Сообщение</p>;
}
```

При этом `use`:

- разрешён только внутри компонента или custom hook;
- нельзя вызывать внутри `try/catch`;
- не отменяет правила для `useState`, `useEffect` и остальных Hooks.

Ошибки Promise, переданного в `use`, обрабатывают через Error Boundary, а состояние ожидания — через Suspense.

`eslint-plugin-react-hooks` статически проверяет код, потому что многие нарушения проявляются только при определённой последовательности рендеров.

Основные правила:

- `rules-of-hooks` проверяет место и порядок вызовов;
- `exhaustive-deps` проверяет реактивные зависимости Hooks вроде `useEffect`.

Актуальный плагин также содержит дополнительные проверки правил React и диагностику, связанную с React Compiler.

Если Compiler находит неподдерживаемый паттерн, он может пропустить оптимизацию конкретного компонента или custom hook, сохранив работу остальной части приложения.

Отключать `exhaustive-deps` вместо исправления кода опасно:

```tsx
// eslint-disable-next-line react-hooks/exhaustive-deps
```

Так в Effect может остаться stale closure, или устаревшее замыкание, которое проявится только после определённой последовательности обновлений.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Почему <code>useEffect</code> нельзя вызвать внутри <code>if</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Условие может изменить число и порядок обычных Hooks между рендерами.

Например:

```tsx
if (isEnabled) {
  useEffect(() => {
    // ...
  }, []);
}

const [
  value,
  setValue,
] = useState("");
```

Если `isEnabled` изменится с `true` на `false`, первым вызовом Hook станет уже `useState`.

React сопоставляет внутренние данные Hooks по последовательности вызовов, поэтому состояние может быть связано с неправильной позицией.

Нужно вызвать Hook безусловно:

```tsx
useEffect(() => {
  if (!isEnabled) {
    return;
  }

  return subscribe();
}, [isEnabled]);
```

Либо вынести условную часть в отдельный компонент.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>use</code> можно вызывать условно?</strong></summary>

<dl>
<dd>
<h2></h2>

`use` является специальным React API с отдельными публичными правилами вызова.

React разрешает использовать его:

- в условиях;
- в циклах;
- после условного `return`, если вызов всё равно происходит внутри компонента или custom hook.

Например:

```tsx
if (shouldLoad) {
  const data =
    use(dataPromise);

  return <Content data={data} />;
}
```

Это исключение не распространяется на:

- `useState`;
- `useEffect`;
- `useMemo`;
- `useContext`;
- другие обычные Hooks.

`use` также нельзя:

- вызывать вне компонента или custom hook;
- помещать внутрь `try/catch`.

Ошибку Promise следует обрабатывать через Error Boundary.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Делят ли два компонента состояние одного пользовательского хука?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Custom hook переиспользует реализацию, но каждый вызов создаёт собственное локальное состояние.

Например:

```tsx
function FirstComponent() {
  const state =
    useDisclosure();

  // Собственный state.
}

function SecondComponent() {
  const state =
    useDisclosure();

  // Другой state.
}
```

Общее состояние появляется, если custom hook обращается к одному внешнему реактивному источнику:

- Context;
- Redux store;
- Zustand store;
- кеш RTK Query;
- внешний store с подпиской.

Обычного изменяемого объекта уровня модуля недостаточно: React должен получить уведомление об изменении и запланировать новый рендер.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли пользовательский хук возвращать JSX?</strong></summary>

<dl>
<dd>
<h2></h2>

Технически функция может вернуть React element или другое значение.

Но custom hook предназначен прежде всего для переиспользования логики, а компонент — для описания интерфейса.

Если основным результатом функции является JSX:

```tsx
function useDialog() {
  return <Dialog />;
}
```

яснее создать компонент:

```tsx
function Dialog() {
  return <div>...</div>;
}
```

Custom hook обычно возвращает:

- состояние;
- данные;
- действия;
- `ref`;
- props для элемента.

Например:

```tsx
const {
  isOpen,
  open,
  close,
} = useDisclosure();
```

После этого компонент самостоятельно определяет разметку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужен <code>eslint-plugin-react-hooks</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Ошибки Hooks могут проявляться только при определённой последовательности рендеров.

Например:

- условие изменило порядок Hooks;
- Effect продолжает видеть старое значение;
- функция нарушает требования чистоты;
- код несовместим с оптимизациями React Compiler.

Статический анализ находит такие проблемы до выполнения приложения.

Основные проверки:

```text
rules-of-hooks
→ место и порядок вызовов

exhaustive-deps
→ зависимости Effects и других реактивных Hooks
```

Актуальный плагин также включает дополнительные правила React и диагностику React Compiler.

Линтер не заменяет тестирование, но предотвращает класс ошибок, которые трудно стабильно воспроизвести вручную.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли повторяющуюся логику нужно выносить в пользовательский хук?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Два похожих фрагмента могут:

- относиться к разным сценариям;
- иметь разные причины изменения;
- разойтись после следующих требований.

Custom hook оправдан, когда существует единая абстракция с понятными:

- названием;
- входными данными;
- результатом;
- жизненным циклом;
- правилами синхронизации.

Признаки неудачного hook:

- слишком общее имя вроде `useSomething`;
- большое количество флагов;
- несвязанные обязанности;
- разные потребители используют несовместимые части результата;
- hook только перемещает код, но не создаёт понятный контракт.

Небольшое повторение иногда проще преждевременной общей абстракции.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Возможный пользовательский хук |
| --- | --- |
| Подписка на состояние сети | `useOnlineStatus` |
| Наблюдение за CSS-медиазапросом | `useMediaQuery` |
| Задержка поискового значения | `useDebouncedValue` |
| Интеграция `ResizeObserver` | `useResizeObserver` |
| Общий сценарий запроса | Hook поверх RTK Query с предметными аргументами |
| Компонент без собственной разметки | Hook возвращает состояние, props и обработчики |
| Общий внешний источник | Hook использует Context, кеш или store с подпиской |
