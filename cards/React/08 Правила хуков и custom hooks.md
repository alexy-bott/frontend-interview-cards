#### Вопрос

Какие правила действуют для хуков React? Для чего создают пользовательские хуки?

#### Ответ

Хуки (hooks) являются функциями React, которые подключают компонент к состоянию, Context, `ref`, эффектам и другим возможностям. Обычные хуки нужно вызывать только на верхнем уровне функционального компонента или пользовательского хука, в одинаковом порядке при каждом рендере. Их нельзя помещать в условие, цикл, вложенную функцию, обработчик события, `try/catch` или код после условного `return`.

React связывает состояние хука с позицией его вызова в конкретном компоненте. Если сейчас первым вызван `useState`, а в следующем рендере условие пропустило его, второй хук займёт прежнюю позицию и получит чужое состояние. Поэтому условие помещают внутрь хука или разбивают интерфейс на отдельные компоненты:

```tsx
useEffect(() => {
  if (!isConnected) return;
  return subscribe();
}, [isConnected]);
```

Второе правило: хуки вызывают только во время рендера React-компонента или другого пользовательского хука. Обычная вспомогательная функция может быть вызвана вне React и не имеет жизненного цикла хука. Имя пользовательского хука начинается с `use`, чтобы линтер и разработчик распознавали функцию, которая подчиняется этим правилам.

API `use` из React 19 является специальным исключением: `use(promise)` и `use(context)` можно вызывать в условиях и циклах. При этом `use` всё равно разрешён только внутри компонента или пользовательского хука, и его нельзя оборачивать в `try/catch`. Остальные хуки, включая `useState` и `useEffect`, сохраняют обычное требование неизменного порядка.

Пользовательский хук переиспользует логику состояния и эффектов, но не JSX. Например, `useOnlineStatus` скрывает детали подписки на состояние сети, а `useDebouncedValue` связывает состояние и таймер. Каждый вызов пользовательского хука получает собственные состояние и эффекты. Общее состояние появится только тогда, когда реализация подписывается на общий Context, внешнее хранилище или кеш.

Хороший пользовательский хук выражает понятный сценарий и скрывает детали его синхронизации. Он не должен быть механической оболочкой над одним `useState` без добавленного смысла. Его входы и возвращаемые значения являются публичным контрактом: новые ссылки на функции или объекты могут заставить потребителя лишний раз запускать эффекты, поэтому стабильность ссылок выбирают осознанно.

`eslint-plugin-react-hooks` проверяет порядок вызовов, зависимости эффектов и дополнительные правила React. В актуальных версиях он также содержит диагностику, связанную с React Compiler. Отключать правило `exhaustive-deps` вместо исправления эффекта опасно: в коде может остаться устаревшее замыкание, которое трудно заметить при обычном тестировании.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Почему `useEffect` нельзя вызвать внутри `if`?
>
> **Ответ:** Условие меняет число и порядок обычных хуков между рендерами. React сопоставляет их состояние по позиции вызова, поэтому следующий хук может получить данные предыдущего. Нужно вызвать хук безусловно, а проверку поместить внутрь его функции.

> [!followup]
> **Вопрос:** Почему `use` можно вызывать условно?
>
> **Ответ:** `use` в React 19 имеет отдельную реализацию и не хранит локальное состояние по обычной позиции вызова хука. Поэтому его разрешено использовать в условиях и циклах. Это исключение не распространяется на `useState`, `useEffect` и другие хуки; `use` также нельзя вызывать вне компонента или оборачивать в `try/catch`.

> [!followup]
> **Вопрос:** Делят ли два компонента состояние одного пользовательского хука?
>
> **Ответ:** Нет. Пользовательский хук переиспользует код, а каждый вызов создаёт собственную цепочку хуков в компоненте. Для общего состояния хук должен обратиться к общему источнику: Context, внешнему хранилищу, намеренно общему объекту модуля или кешу запросов.

> [!followup]
> **Вопрос:** Может ли пользовательский хук возвращать JSX?
>
> **Ответ:** Технически функция способна вернуть любое значение, но хук предназначен для переиспользования логики, а компонент для описания интерфейса. Если основным результатом является JSX, яснее создать компонент. Хук может вернуть состояние, данные, функции и `props`, необходимые компоненту без собственной разметки.

> [!followup]
> **Вопрос:** Зачем нужен `eslint-plugin-react-hooks`?
>
> **Ответ:** Нарушение порядка и пропущенная зависимость могут проявиться только в определённой последовательности рендеров. Статический анализ находит эти ошибки раньше. Актуальная версия плагина также проверяет дополнительные правила чистоты и совместимость кода с React Compiler.

> [!followup]
> **Вопрос:** Всегда ли повторяющуюся логику нужно выносить в пользовательский хук?
>
> **Ответ:** Нет. Два похожих фрагмента могут иметь разные причины изменения и разойтись в будущем. Хук оправдан, когда существует единая абстракция с понятным названием, жизненным циклом и контрактом. Слишком общий `useSomething` с множеством флагов лишь прячет сложность.

#### Где это встречается во frontend

| Ситуация | Возможный пользовательский хук |
| --- | --- |
| Подписка на состояние сети | `useOnlineStatus` |
| Наблюдение за CSS-медиазапросом | `useMediaQuery` |
| Задержка поискового значения | `useDebouncedValue` |
| Интеграция `ResizeObserver` | `useResizeObserver` |
| Общий сценарий запроса | Хук поверх RTK Query с предметными аргументами |
| Компонент без собственной разметки | Хук возвращает состояние, `props` и обработчики |
