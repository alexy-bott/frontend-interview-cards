## Вопрос

<br>

 💬 **Что такое `Suspense`, `lazy` и разделение кода? Как они связаны и чего `Suspense` не делает?**

<h2></h2>

<br>
<dl>
<dd>

Code splitting, или разделение кода, разбивает JavaScript-бандл на части, или chunks, которые загружаются по требованию.

`lazy` связывает загрузку модуля с React-компонентом, а `Suspense` показывает запасной интерфейс из prop `fallback`, пока ближайшее дочернее поддерево не готово продолжить render.

Эти механизмы часто работают вместе, но выполняют разные задачи:

```text
динамический import()
→ начинает загрузку модуля

сборщик
→ обычно создаёт отдельный chunk

lazy
→ создаёт React-компонент для загружаемого модуля

Suspense
→ показывает fallback, пока render приостановлен
```

Пример:

```tsx
const SettingsPage =
  lazy(() =>
    import("./SettingsPage"),
  );

function App() {
  return (
    <Suspense
      fallback={
        <PageSkeleton />
      }
    >
      <SettingsPage />
    </Suspense>
  );
}
```

Динамический импорт:

```tsx
import("./SettingsPage")
```

возвращает Promise модуля.

Сборщик или фреймворк видит динамическую границу импорта и обычно создаёт отдельный chunk, который браузер загружает при выполнении `import()`.

`lazy(load)` создаёт тип React-компонента.

React вызывает `load` только при первой попытке отрендерить этот компонент:

```tsx
const SettingsPage =
  lazy(() =>
    import("./SettingsPage"),
  );
```

React кеширует:

- возвращённый Promise;
- результат его выполнения.

Поэтому для одного lazy-типа функция `load` не вызывается повторно.

Promise должен успешно вернуть объект, у которого поле:

```ts
default
```

является допустимым React-компонентом.

Например, модуль должен иметь default export:

```tsx
export default function SettingsPage() {
  return (
    <h1>Настройки</h1>
  );
}
```

Объявление `lazy` размещают на уровне модуля:

```tsx
const SettingsPage =
  lazy(() =>
    import("./SettingsPage"),
  );
```

а не внутри компонента:

```tsx
function App() {
  const SettingsPage =
    lazy(() =>
      import(
        "./SettingsPage"
      ),
    );

  // ...
}
```

Во втором случае каждый render создаёт новый тип компонента.

React перестаёт считать его прежним компонентом, поэтому локальное состояние поддерева может сбрасываться.

Если код lazy-компонента ещё не загружен, попытка его отрендерить приостанавливает render.

React находит ближайшую границу:

```tsx
<Suspense
  fallback={
    <PageSkeleton />
  }
>
```

и показывает `fallback`.

После выполнения Promise React повторно рендерит приостановленное поддерево.

Если render завершается успешно, fallback заменяется готовым содержимым.

Если поддерево приостановилось до первого успешного монтирования, React не сохраняет состояние этой незавершённой попытки.

После готовности ресурса React начинает render поддерева заново.

`Suspense` сам по себе:

- не выполняет `fetch`;
- не создаёт chunks;
- не начинает динамический импорт;
- не хранит кеш данных;
- не устраняет одинаковые запросы;
- не обрабатывает ошибки;
- не реагирует на произвольный boolean `isLoading`.

Он только управляет запасным интерфейсом, когда поддерживаемый источник приостанавливает render дочернего дерева.

Границу могут активировать, например:

- lazy-компонент;
- Promise, прочитанный через `use`;
- источник данных фреймворка с поддержкой Suspense;
- поддерживаемые React ресурсы;
- ещё не полученный HTML во время streaming SSR.

Обычный запрос внутри Effect не активирует Suspense:

```tsx
useEffect(() => {
  fetchData().then(
    setData,
  );
}, []);
```

Не активирует его автоматически и запрос из обработчика события:

```tsx
async function handleClick() {
  const data =
    await fetchData();

  setData(data);
}
```

В этих случаях loading-состоянием управляет сам компонент или библиотека работы с данными.

В React 19 Promise можно прочитать через:

```tsx
use(promise)
```

Например:

```tsx
function User({
  userPromise,
}: {
  userPromise:
    Promise<UserData>;
}) {
  const user =
    use(userPromise);

  return (
    <p>{user.name}</p>
  );
}
```

Если Promise ещё ожидается, ближайший Suspense показывает `fallback`.

Если Promise отклонён, ошибка передаётся ближайшему Error Boundary.

В Client Components должна повторно использоваться одна и та же закешированная Promise:

```tsx
const cache =
  new Map<
    string,
    Promise<UserData>
  >();

function getUser(
  userId: string,
) {
  let promise =
    cache.get(userId);

  if (!promise) {
    promise =
      fetchUser(userId);

    cache.set(
      userId,
      promise,
    );
  }

  return promise;
}
```

Компонент получает стабильную Promise:

```tsx
const user =
  use(
    getUser(userId),
  );
```

Создавать новую Promise непосредственно при каждом render не следует:

```tsx
const user =
  use(
    fetchUser(userId),
  );
```

если `fetchUser` каждый раз возвращает новый Promise без кеширования.

Это может повторно активировать `fallback`, создавать лишние запросы и нарушать ожидаемую модель Suspense.

Кеширование, дедупликацию запросов, обработку ошибок и повтор обычно предоставляет:

- React-фреймворк;
- маршрутизатор;
- библиотека загрузки данных;
- отдельный слой кеша приложения.

Suspense не является Error Boundary.

Пока ресурс ожидается:

```text
pending
→ Suspense fallback
```

Если загрузка завершилась ошибкой:

```text
rejected
→ Error Boundary fallback
```

Например:

```tsx
<ErrorBoundary>
  <Suspense
    fallback={
      <PageSkeleton />
    }
  >
    <SettingsPage />
  </Suspense>
</ErrorBoundary>
```

Пока JavaScript-модуль загружается, работает Suspense.

Если Promise динамического импорта отклонится, `lazy` бросит причину ошибки, и её должен перехватить Error Boundary.

Граница Suspense определяет, какая часть интерфейса заменяется во время ожидания.

Одна глобальная граница:

```tsx
<Suspense
  fallback={
    <FullPageLoader />
  }
>
  <App />
</Suspense>
```

может скрывать слишком большую часть уже понятного пользователю интерфейса.

Несколько смысловых границ позволяют раскрывать части независимо:

```tsx
<PageLayout>
  <Profile />

  <Suspense
    fallback={
      <ChartSkeleton />
    }
  >
    <Chart />
  </Suspense>
</PageLayout>
```

В этом случае каркас страницы и профиль остаются видимыми, пока загружается график.

Но границу не нужно создавать вокруг каждого маленького компонента.

Слишком большое число мелких границ может привести к:

- частому переключению fallback;
- визуальному мерцанию;
- фрагментарному появлению страницы;
- усложнению пользовательского сценария;
- большому числу сетевых запросов.

Границы выбирают по смысловым этапам загрузки интерфейса.

Fallback должен быть:

- лёгким;
- стабильным;
- похожим по размеру на итоговый блок;
- не создающим сильный layout shift.

Если уже показанное содержимое снова приостанавливает render, React по умолчанию может скрыть его и снова показать fallback.

Например:

```text
старые данные показаны
→ изменился запрос
→ новые данные ещё не готовы
→ fallback
```

Чтобы сохранить уже показанное содержимое во время несрочного обновления, используют:

- `startTransition`;
- `useTransition`;
- `useDeferredValue`.

При этом React может продолжать показывать прежний интерфейс, пока новый не будет готов.

Если React всё же скрывает ранее показанное Suspense-поддерево, он выполняет cleanup его layout effects.

Когда содержимое снова становится видимым, layout effects запускаются заново.

Это необходимо, потому что layout effect не должен измерять DOM, который сейчас скрыт.

Suspense интегрирован со streaming SSR.

Сервер может сначала отправить shell страницы с fallback:

```text
готовый каркас
+
fallback Suspense
```

а затем передать HTML готовой границы отдельной частью потока.

Браузер заменяет fallback поступившим содержимым без ожидания завершения всей страницы.

Suspense также участвует в Selective Hydration: React может раньше гидратировать часть интерфейса, с которой пользователь начал взаимодействовать.

При серверной ошибке streaming renderer может отправить fallback ближайшей Suspense-границы и повторить проблемный render на клиенте.

Если на клиенте ошибка повторится, её сможет обработать ближайший Error Boundary.

Code splitting выбирают по реальной стоимости и вероятности использования компонента.

Хорошими границами часто являются:

- маршруты;
- тяжёлые редакторы;
- карты;
- графики;
- отчёты;
- редкие административные сценарии;
- крупные модальные инструменты.

Нежелательно создавать отдельный chunk для каждого маленького компонента.

Каждая дополнительная часть может добавить:

- сетевой запрос;
- задержку;
- работу на разбор и выполнение JavaScript;
- новый fallback;
- зависимость от следующего chunk.

Слишком мелкое разделение может создать waterfall:

```text
загрузился маршрут
→ обнаружился lazy-компонент
→ загрузился компонент
→ обнаружился запрос данных
→ загрузились данные
```

Задержку уменьшают, если:

- начинают загрузку маршрута заранее;
- используют prefetch или preload;
- загружают код и данные параллельно;
- не прячут первый запрос глубоко внутри lazy-компонента;
- выбирают крупные смысловые границы;
- используют возможности маршрутизатора или фреймворка.

Конкретный API предварительной загрузки зависит от:

- сборщика;
- маршрутизатора;
- React-фреймворка;
- инфраструктуры приложения.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Что делает <code>import("./Chart")</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Это динамический импорт, который возвращает Promise модуля:

```tsx
const modulePromise =
  import("./Chart");
```

Сборщик обычно выносит модуль и его уникальные зависимости в отдельный chunk.

Браузер начинает загрузку при выполнении `import()`.

После выполнения Promise становятся доступны экспорты модуля:

```tsx
const module =
  await import("./Chart");

const Chart =
  module.default;
```

Сам `import()` не показывает loading-интерфейс и не является React API.

Его связывают с React через `lazy`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что именно делает <code>lazy</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`lazy` создаёт тип React-компонента, код которого загружается при первой попытке render.

```tsx
const Chart =
  lazy(() =>
    import("./Chart"),
  );
```

При первом render React:

1. Вызывает функцию `load`.
2. Получает Promise модуля.
3. Кеширует Promise.
4. Приостанавливает render до загрузки.
5. После выполнения Promise рендерит `module.default`.

React кеширует и Promise, и его результат.

Если Promise отклонён, React бросает причину ошибки ближайшему Error Boundary.

Для того же lazy-типа функция `load` повторно не вызывается.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем несколько границ Suspense?</strong></summary>

<dl>
<dd>
<h2></h2>

Несколько границ позволяют независимо показывать смысловые части страницы.

Например:

```tsx
<Page>
  <Header />

  <Suspense
    fallback={
      <ProfileSkeleton />
    }
  >
    <Profile />
  </Suspense>

  <Suspense
    fallback={
      <ChartSkeleton />
    }
  >
    <Chart />
  </Suspense>
</Page>
```

Если график загружается дольше, профиль может появиться раньше.

Количество границ выбирают по пользовательскому сценарию, а не по числу компонентов.

Не нужно оборачивать каждый маленький элемент в собственный Suspense.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что произойдёт, если часть бандла для <code>lazy</code> не загрузилась?</strong></summary>

<dl>
<dd>
<h2></h2>

Promise динамического импорта будет отклонён.

`lazy` передаст причину ошибки ближайшему Error Boundary:

```text
chunk не загрузился
→ Promise rejected
→ Error Boundary
```

Suspense не продолжает показывать loading-fallback как обычное ожидание, потому что загрузка уже завершилась ошибкой.

Важно учитывать, что `lazy` кеширует Promise и результат его выполнения, включая отклонение.

Поэтому простой сброс Error Boundary не заставляет тот же lazy-тип повторно вызвать функцию `load`.

У React нет универсального встроенного API повторной загрузки отклонённого lazy-компонента.

Стратегия восстановления зависит от приложения:

- обновить страницу;
- загрузить новую версию ресурса с другим URL;
- использовать retry-механизм маршрутизатора или фреймворка;
- предложить пользователю обновиться после deployment новой версии.

Особенно часто chunk может не загрузиться, если пользователь открыл старую версию приложения, а после deployment соответствующий файл был удалён с CDN.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли обернуть обычный <code>fetch</code> в <code>Suspense</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Одной JSX-обёртки недостаточно:

```tsx
<Suspense
  fallback={<Loader />}
>
  <ComponentWithEffectFetch />
</Suspense>
```

Запрос из `useEffect` не приостанавливает render, поэтому Suspense его loading-состояние не увидит.

Источник данных должен быть интегрирован с Suspense.

В React 19 поддерживаемую закешированную Promise можно прочитать через:

```tsx
const data =
  use(dataPromise);
```

На практике интеграцию обычно предоставляет:

- React-фреймворк;
- маршрутизатор;
- библиотека загрузки данных;
- общий кеш приложения.

Произвольное создание новой Promise во время каждого клиентского render не является надёжной реализацией Suspense-загрузки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему не следует делать <code>lazy</code> для каждого компонента?</strong></summary>

<dl>
<dd>
<h2></h2>

Каждое разделение создаёт новую границу загрузки.

Множество мелких chunks может увеличить:

- число запросов;
- сетевые накладные расходы;
- количество fallback;
- время последовательной загрузки;
- сложность кеширования;
- риск waterfall.

Небольшой часто используемый компонент выгоднее оставить в основном chunk.

Разделять обычно имеет смысл код, который:

- имеет заметный размер;
- используется редко;
- не нужен для первоначального экрана;
- соответствует отдельному пользовательскому сценарию.

Решение проверяют по production-сборке и профилю загрузки, а не только по размеру исходного файла.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как уменьшить каскадную загрузку кода и данных?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно начинать загрузку раньше и выполнять независимую работу параллельно.

Возможные меры:

- prefetch маршрута до перехода;
- preload важного chunk;
- одновременная загрузка кода и данных;
- запуск загрузки при наведении или появлении ссылки в viewport;
- получение данных на уровне маршрута;
- отказ от слишком мелких последовательных lazy-границ;
- использование возможностей фреймворка.

Нежелательный waterfall:

```text
переход
→ загрузка компонента
→ mount компонента
→ Effect
→ запрос данных
```

Более быстрый вариант:

```text
переход
→ параллельно код + данные
→ render готового интерфейса
```

Конкретный API зависит от фреймворка, маршрутизатора и сборщика.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```tsx
function App() {
  const SettingsPage = lazy(() => import("./SettingsPage"));

  return (
    <Suspense fallback={<PageSkeleton />}>
      <SettingsPage />
    </Suspense>
  );
}
```

<details>
<summary><strong>Почему объявление <code>lazy</code> внутри <code>App</code> является ошибкой?</strong></summary>

<dl>
<dd>
<h2></h2>

Каждый render создаёт новый тип компонента:

```tsx
const SettingsPage =
  lazy(() =>
    import("./SettingsPage"),
  );
```

React перестаёт считать новый `SettingsPage` тем же компонентом.

Из-за этого поддерево может:

- размонтироваться;
- смонтироваться заново;
- потерять локальное состояние;
- повторно запустить effects.

Объявление нужно вынести на уровень модуля:

```tsx
const SettingsPage =
  lazy(() =>
    import("./SettingsPage"),
  );

function App() {
  return (
    <Suspense
      fallback={
        <PageSkeleton />
      }
    >
      <SettingsPage />
    </Suspense>
  );
}
```

Так тип компонента остаётся стабильным между рендерами.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Подход |
| --- | --- |
| Крупный маршрут | Отдельный chunk и Suspense на уровне страницы |
| Редкий редактор или карта | `lazy` по фактическому открытию |
| Ошибка загрузки chunk | Error Boundary и стратегия восстановления приложения |
| Данные через Suspense-интеграцию | Закешированная Promise и `use` либо API фреймворка |
| Потоковый SSR | Граница определяет независимо передаваемые части HTML |
