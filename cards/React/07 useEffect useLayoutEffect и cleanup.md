## Вопрос

<br>

 💬 **Для чего нужен `useEffect`? Чем он отличается от `useLayoutEffect` и как работает очистка?**

<h2></h2>

<br>
<dl>
<dd>

`useEffect` синхронизирует React-компонент с внешней системой после commit. Внешней системой может быть WebSocket, таймер, DOM API, браузерное событие, сторонний виджет или сетевой запрос. Если внешней системы нет и значение можно вычислить из `props` и `state` во время рендера, эффект обычно не нужен.

Эффект состоит из функции запуска (setup), массива зависимостей и необязательной функции очистки (cleanup):

```tsx
useEffect(() => {
  const connection = createConnection(roomId);
  connection.connect();

  return () => connection.disconnect();
}, [roomId]);
```

После commit React запускает функцию эффекта. Когда зависимость изменилась, React сначала выполняет очистку с данными прежнего рендера, а затем запускает эффект с актуальными данными. При окончательном размонтировании очистка выполняется в последний раз. Поэтому эффект нужно проектировать как отдельный цикл «начать синхронизацию → остановить её», а не как набор событий жизненного цикла компонента.

Массив зависимостей содержит все реактивные значения, которые эффект читает из компонента. Реактивными здесь называются `props`, `state`, функции и переменные из тела компонента, способные отличаться между рендерами. React сравнивает каждую зависимость через `Object.is`. Зависимости не выбирают вручную ради желаемой частоты запуска. Если значение не должно запускать повторную синхронизацию, меняют структуру кода: переносят действие в обработчик, создают объект внутри эффекта, используют функцию обновления состояния или, в подходящем сценарии React 19.2, `useEffectEvent`.

Без массива зависимостей эффект запускается после каждого commit. Пустой массив означает, что эффект не читает изменяемые значения компонента. В production-сборке такой эффект запускается после монтирования, а очистка выполняется при размонтировании. В режиме разработки Strict Mode добавляет проверочный цикл «запуск → очистка → запуск», чтобы проверить симметричность очистки. Исправлять нужно саму очистку, а не скрывать второй запуск флагом.

`useLayoutEffect` имеет тот же жизненный цикл, но React запускает его после изменения DOM и до следующей отрисовки браузером. Он нужен, если требуется измерить расположение элемента и синхронно скорректировать его позицию до того, как пользователь увидит кадр, например для всплывающей подсказки. Код и обновления состояния внутри `useLayoutEffect` задерживают отрисовку, поэтому обычная синхронизация должна оставаться в `useEffect`.

Обычный `useEffect` выполняется после commit. React часто позволяет браузеру сначала обновить экран, но не гарантирует это для каждого взаимодействия. Если эффект выполняет визуальную работу и мерцание недопустимо, проверяют необходимость `useLayoutEffect`. Эффекты не выполняются при серверном рендеринге, потому что на сервере DOM-компонент не монтируется.

Функцию, переданную в `useEffect`, нельзя объявить `async`: асинхронная функция возвращает Promise, а React ожидает только функцию очистки или `undefined`. Асинхронную функцию объявляют и запускают внутри эффекта. Очистка отменяет запрос через `AbortController` либо помечает прежний результат неактуальным, чтобы поздний ответ не перезаписал данные нового запроса.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Как формируется массив зависимостей эффекта?</strong></summary>

<dl>
<dd>
<h2></h2>

В него входят все реактивные значения, прочитанные эффектом: `props`, `state`, функции и переменные из тела компонента. Линтер `exhaustive-deps` проверяет соответствие. Значение можно удалить из массива только после изменения кода, которое действительно устранило зависимость, например после переноса создания объекта внутрь эффекта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему побочный эффект нельзя выполнить в теле компонента?</strong></summary>

<dl>
<dd>
<h2></h2>

Рендер должен быть чистым и может быть повторён или отброшен до commit. Подписка или запрос внутри компонента тогда выполнится лишний раз и не получит надёжного момента очистки. Эффект запускается после успешного commit и задаёт парную функцию очистки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему функцию <code>useEffect</code> не делают <code>async</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Асинхронная функция всегда возвращает Promise, а React интерпретирует возвращаемое значение эффекта как функцию очистки. Нужно объявить асинхронную функцию внутри эффекта, вызвать её и отдельно вернуть синхронную функцию очистки, которая отменяет запрос или делает его результат неактуальным.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое stale closure в эффекте?</strong></summary>

<dl>
<dd>
<h2></h2>

Stale closure, или устаревшее замыкание, возникает, когда функция продолжает видеть `props` и `state` того рендера, в котором была создана. Если зависимость пропущена, таймер или подписка будет работать со старым значением. Решение зависит от задачи: полный массив зависимостей, функция обновления состояния, перенос действия в обработчик, `ref` для значения вне интерфейса или `useEffectEvent` для нереактивной логики внутри эффекта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему эффект запускается дополнительный раз в Strict Mode?</strong></summary>

<dl>
<dd>
<h2></h2>

В режиме разработки React после первого запуска сразу выполняет очистку и запускает эффект повторно. Так обнаруживаются соединения, таймеры и подписки, которые не очищаются. В production-сборке этого проверочного цикла нет, но корректный эффект должен одинаково работать после любой последовательности запуска и очистки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли загружать данные через <code>fetch</code> в эффекте?</strong></summary>

<dl>
<dd>
<h2></h2>

Можно, но нужно самостоятельно обработать состояние загрузки, ошибки, отмену или игнорирование устаревшего ответа, кеш, повторяющиеся запросы и отсутствие эффекта при SSR. API фреймворка для загрузки данных, RTK Query или TanStack Query обычно решают эти задачи системно. Ручной эффект оправдан для простого клиентского запроса или API без подходящей интеграции.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем обработчик события отличается от эффекта?</strong></summary>

<dl>
<dd>
<h2></h2>

Обработчик выполняется из-за конкретного действия пользователя, например нажатия «Оплатить». Эффект выполняется потому, что компонент оказался на экране или изменились прочитанные им реактивные значения. Запрос оплаты относится к обработчику, а подключение к комнате `roomId` относится к эффекту.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```tsx
useEffect(() => {
  const id = setInterval(() => {
    setSeconds(seconds + 1);
  }, 1000);

  return () => clearInterval(id);
}, []);
```

<details>
<summary><strong>Почему счётчик перестанет расти после первого обновления?</strong></summary>

<dl>
<dd>
<h2></h2>

Функция интервала замкнула `seconds` из первого рендера, а пустой массив не создаёт новый интервал с актуальным значением. Нужно вычислять состояние из предыдущего элемента очереди: `setSeconds((value) => value + 1)`. Тогда эффект не читает `seconds`, и пустой массив соответствует коду.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Решение |
| --- | --- |
| `window.addEventListener` | Создание подписки и симметричная очистка |
| WebSocket для выбранной комнаты | Эффект зависит от `roomId` и закрывает прежнее соединение |
| Позиционирование всплывающей подсказки | Точечный `useLayoutEffect` для измерения |
| Запрос без библиотеки для данных | Отмена или игнорирование устаревшего результата |
| Вычисляемый список | Вычисление во время рендера, эффект не нужен |
| Отправка формы | Обработчик события, а не эффект по флагу |
