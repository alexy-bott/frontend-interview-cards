# Повторный рендер и batching

## Вопрос

<br>

 💬 **Почему React-компонент рендерится повторно? Что такое batching?**

<h2></h2>

<br>
<dl>
<dd>

Повторный рендер означает, что React снова вызывает компонент, чтобы вычислить следующее описание интерфейса.

Основные причины рендера:

- первоначальное добавление компонента в React-дерево;
- обновление его собственного `state`;
- рендер родительского компонента;
- изменение значения Context, которое компонент читает;
- изменение внешнего хранилища, на которое компонент подписан.

Например, внешнее хранилище может уведомить React через подписку, созданную с помощью:

```ts
useSyncExternalStore
```

Повторный вызов компонента не означает, что React обязательно изменит DOM.

После render phase React сопоставит новое дерево с предыдущим. Если фактический интерфейс не изменился, commit может не содержать DOM-изменений.

`Props` сами по себе не являются отдельным событием, запускающим рендер.

Новые `props` появляются потому, что родитель уже начал рендер и создал дочерний React-элемент с очередными значениями:

```tsx
<Profile user={user} />
```

По умолчанию при рендере родителя React продолжает вычисление его дочернего дерева.

Однако React может пропустить часть работы, например если:

- компонент обёрнут в `memo`;
- React может повторно использовать уже созданный JSX;
- внутренние механизмы React выполняют bailout.

`memo` позволяет обычно пропустить рендер ребёнка, если каждый новый prop равен предыдущему по `Object.is`:

```tsx
const UserRow = memo(
  function UserRow({
    user,
  }: {
    user: User;
  }) {
    return <div>{user.name}</div>;
  },
);
```

Это сравнение часто называют поверхностным: React не обходит объект в глубину, а сравнивает каждое значение prop.

Новый объект считается другим prop:

```tsx
<UserRow
  user={{
    id: user.id,
    name: user.name,
  }}
/>
```

даже если его поля содержат те же значения.

`memo` является оптимизацией, а не гарантией полного отсутствия повторных вызовов.

Мемоизированный компонент всё равно рендерится, если:

- обновилось его собственное состояние;
- изменился Context, который он читает;
- переданные props перестали быть равны;
- React по внутренним причинам решил повторно выполнить render.

При обновлении состояния React сравнивает новое значение с предыдущим через:

```ts
Object.is
```

Например:

```tsx
setCount(1);
```

обычно не запустит новое отображаемое обновление, если текущее состояние уже равно `1`.

Для объектов и массивов сравниваются ссылки:

```tsx
user.name = "Анна";

setUser(user);
```

Здесь ссылка осталась прежней, поэтому React может пропустить обновление.

Кроме того, мутация меняет старый снимок состояния задним числом и нарушает предсказуемость render.

Нужно создать новое значение:

```tsx
setUser({
  ...user,
  name: "Анна",
});
```

Если новое состояние равно текущему по `Object.is`, React пропускает рендер компонента и его дочернего дерева.

В отдельных случаях React может всё же вызвать функцию компонента, прежде чем окончательно отказаться от дальнейшей работы. Код компонента не должен зависеть от того, произойдёт такой вызов или нет.

Batching, или пакетная обработка, означает, что React собирает несколько обновлений состояния и обрабатывает их вместе перед следующим применением интерфейса.

Например:

```tsx
function handleClick() {
  setCount((count) => count + 1);
  setIsOpen(false);
  setSelectedId(null);
}
```

React сначала выполняет обработчик и ставит обновления в очередь.

После завершения обработчика он вычисляет итоговое состояние и применяет согласованный результат без отображения промежуточных состояний:

```text
старое состояние
→ очередь обновлений
→ новый render
→ commit итогового результата
```

Batching:

- уменьшает число промежуточных рендеров;
- объединяет обновления разных state variables;
- может объединять обновления из нескольких компонентов;
- не позволяет пользователю увидеть наполовину обновлённое состояние.

Это не означает строгую гарантию, что каждая функция компонента будет вызвана ровно один раз. Например, development Strict Mode может выполнять дополнительные вызовы для проверки чистоты кода.

React не объединяет независимые намеренные пользовательские события.

Два отдельных клика обрабатываются отдельно:

```text
первый клик
→ обработка и обновление интерфейса

второй клик
→ новая отдельная обработка
```

Это важно, например, когда первый клик блокирует кнопку и второй уже не должен повторно отправить форму.

Начиная с React 18 при использовании:

```tsx
createRoot(container)
```

автоматический batching распространяется не только на обработчики событий React, но и на обновления из:

- Promise;
- `setTimeout`;
- нативных обработчиков событий;
- других асинхронных callback-функций.

Например:

```tsx
setTimeout(() => {
  setCount(
    (count) => count + 1,
  );

  setIsReady(true);
}, 1000);
```

В современном root эти обновления обычно обрабатываются одним batch.

До React 18 автоматический batching по умолчанию в основном ограничивался обработчиками событий React.

При использовании старого:

```ts
ReactDOM.render
```

поведение автоматического batching из React 18 не включалось полностью.

Асинхронная граница вроде:

```ts
await
```

разделяет выполнение функции на части.

Не следует рассчитывать, что обновления до и после `await` обязательно попадут в один общий batch:

```tsx
async function handleSave() {
  setIsSaving(true);

  await save();

  setIsSaving(false);
  setIsSuccess(true);
}
```

Обновления после `await` могут быть объединены друг с другом, но React не обещает единый batch со всеми обновлениями, выполненными до `await`.

Состояние внутри текущего рендера является неизменяемым снимком.

Например:

```tsx
function increment() {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
}
```

Если `count` равен `0`, все три вызова вычисляют:

```ts
setCount(1);
```

Поэтому итоговое значение обычно будет равно `1`, а не `3`.

Когда следующее состояние зависит от предыдущего состояния в очереди, используют updater-функцию:

```tsx
setCount(
  (previous) => previous + 1,
);
```

Три updater-функции будут применены последовательно:

```tsx
setCount(
  (value) => value + 1,
);

setCount(
  (value) => value + 1,
);

setCount(
  (value) => value + 1,
);
```

Очередь обрабатывается так:

```text
0
→ 1
→ 2
→ 3
```

Updater получает pending state — результат предыдущих обновлений в очереди.

В одной очереди можно сочетать прямые значения и updater-функции:

```tsx
setCount(5);
setCount(
  (count) => count + 1,
);
```

Сначала состояние заменяется на `5`, затем updater получает `5` и возвращает `6`.

`flushSync` позволяет принудительно обработать обновление и синхронно применить его к DOM:

```tsx
import {
  flushSync,
} from "react-dom";

flushSync(() => {
  setIsOpen(true);
});

// DOM уже обновлён.
dialogRef.current?.focus();
```

Это может понадобиться при интеграции со сторонним или браузерным API, которому обновлённый DOM нужен до выполнения следующей строки.

`flushSync` используют редко, потому что он:

- нарушает обычную пакетную обработку;
- может ухудшить производительность;
- способен обработать другую ожидающую работу;
- может запустить ожидающие Effects;
- способен снова показать fallback границы Suspense.

В обычном React-коде без специальной интеграции `flushSync` обычно не нужен.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Если родитель рендерится, ребёнок всегда вызывается повторно?</strong></summary>

<dl>
<dd>
<h2></h2>

По умолчанию React продолжает вычисление дочернего дерева после рендера родителя.

Например:

```tsx
function Parent() {
  return <Child />;
}
```

При повторном рендере `Parent` функция `Child` обычно также будет вызвана.

DOM при этом может не измениться.

Работу можно пропустить, например через:

```tsx
memo(Child)
```

если props ребёнка равны предыдущим.

Однако `memo` не блокирует обновления, вызванные:

- собственным состоянием ребёнка;
- изменившимся Context;
- изменившимися props.

Кроме того, `memo` является оптимизацией, а не частью логической корректности компонента.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему три <code>setCount(count + 1)</code> обычно увеличивают значение только на один?</strong></summary>

<dl>
<dd>
<h2></h2>

Все три выражения читают `count` из одного снимка состояния.

При:

```ts
count === 0
```

в очередь фактически попадает:

```tsx
setCount(1);
setCount(1);
setCount(1);
```

Итоговое значение равно `1`.

Updater-функция получает pending state после предыдущего обновления очереди:

```tsx
setCount(
  (value) => value + 1,
);

setCount(
  (value) => value + 1,
);

setCount(
  (value) => value + 1,
);
```

React обработает очередь:

```text
0 → 1 → 2 → 3
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что изменилось в batching в React 18?</strong></summary>

<dl>
<dd>
<h2></h2>

До React 18 batching по умолчанию в основном применялся внутри обработчиков событий React:

```tsx
function handleClick() {
  setCount(
    (count) => count + 1,
  );

  setIsOpen(false);
}
```

При использовании `createRoot` в React 18 автоматический batching стал распространяться также на обновления внутри:

- Promise;
- `setTimeout`;
- нативных обработчиков;
- других callback-функций.

Например:

```tsx
fetchData().then(() => {
  setIsLoading(false);
  setIsReady(true);
});
```

Оба обновления обычно обрабатываются вместе.

При использовании legacy API:

```ts
ReactDOM.render
```

новое поведение полностью не включалось.

Для принудительного синхронного применения обновления существует `flushSync`, но он нужен только в редких интеграционных сценариях.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему мутация состояния может не вызвать рендер?</strong></summary>

<dl>
<dd>
<h2></h2>

React сравнивает новое состояние с предыдущим через:

```ts
Object.is
```

После мутации объекта его ссылка остаётся прежней:

```tsx
user.name = "Анна";

setUser(user);
```

Для React передано то же значение, поэтому обновление может быть пропущено.

Мутация также изменяет данные старых снимков состояния, что может привести к ошибкам при:

- повторных рендерах;
- мемоизации;
- конкурентном рендеринге;
- сравнении предыдущих и новых данных.

Нужно создать новый объект или массив на изменившемся пути:

```tsx
setUser({
  ...user,
  name: "Анна",
});
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли повторный рендер является проблемой производительности?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Большинство рендеров компонентов выполняются быстро, а reconciliation может не привести ни к одному изменению DOM.

Оптимизация оправдана, когда измерения показывают реальную проблему:

- задержку реакции на действие;
- долгий commit;
- дорогое вычисление;
- слишком широкое обновление дерева;
- большое число тяжёлых дочерних компонентов.

Для анализа используют:

- React Profiler;
- React DevTools;
- Performance panel браузера.

Один `console.log` не даёт полной картины.

В development Strict Mode React может намеренно повторно вызвать компонент, поэтому количество логов не всегда соответствует числу production-render или DOM-изменений.

Не нужно механически добавлять:

- `memo`;
- `useMemo`;
- `useCallback`.

Сначала определяют источник дорогого обновления, а затем применяют точечную оптимизацию.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  function increment() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
  }

  return <button onClick={increment}>{count}</button>;
}
```

<details>
<summary><strong>Что покажет кнопка после одного клика и как получить прибавление на три?</strong></summary>

<dl>
<dd>
<h2></h2>

При начальном:

```ts
count = 0
```

все три вызова ставят в очередь значение `1`:

```tsx
setCount(1);
setCount(1);
setCount(1);
```

После одного клика кнопка покажет:

```text
1
```

Для прибавления на три нужно трижды передать updater-функцию:

```tsx
function increment() {
  setCount(
    (value) => value + 1,
  );

  setCount(
    (value) => value + 1,
  );

  setCount(
    (value) => value + 1,
  );
}
```

React последовательно применит функции:

```text
0 → 1 → 2 → 3
```

</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что проверить |
| --- | --- |
| Рендерится большая таблица | Какое обновление запускает родителя и можно ли сузить область состояния |
| Context обновляет потребителей | Стабильность `value`, сравнение через `Object.is` и границы Provider |
| Несколько setter-функций подряд | Batching и зависимость от предыдущего pending state |
| Объект состояния изменили на месте | Новая ссылка и иммутабельное обновление |
| Обновления находятся по разные стороны `await` | Не рассчитывать на один общий batch |
| Подозрение на лишние рендеры | React Profiler, а не только `console.log` |
| Стороннему API немедленно нужен новый DOM | Точечное использование `flushSync` как последнего средства |
