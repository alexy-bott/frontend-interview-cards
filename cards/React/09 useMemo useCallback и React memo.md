## Вопрос

<br>

 💬 **Чем отличаются `useMemo`, `useCallback` и `memo`? Когда мемоизация в React действительно полезна?**

<h2></h2>

<br>
<dl>
<dd>

Все три API являются оптимизациями, но сохраняют разные вещи. `useMemo` кеширует результат вычисления внутри компонента, `useCallback` кеширует ссылку на функцию, а `memo` позволяет пропустить рендер дочернего компонента, если его `props` не изменились. Они не должны быть нужны для правильности программы.

| API | Что сохраняет | Типичный сценарий |
| --- | --- | --- |
| `useMemo(calculate, deps)` | Результат `calculate()` | Дорогое вычисление или стабильный объект для другой оптимизации |
| `useCallback(fn, deps)` | Ссылку на `fn` | Функция для мемоизированного ребёнка или API, зависящего от ссылки |
| `memo(Component)` | Возможность пропустить вызов компонента | Измеримо дорогой ребёнок с редко меняющимися `props` |

`useMemo` выполняет функцию во время рендера и возвращает сохранённое значение, пока зависимости не изменились. Поэтому вычисляющая функция должна быть чистой. React вправе удалить кеш по внутренней причине, например во время разработки после изменения файла или при определённых сценариях Suspense. Если объект нужен для правильности программы, его следует хранить в состоянии или `ref`, а не полагаться на `useMemo`.

`useCallback(fn, deps)` эквивалентен `useMemo(() => fn, deps)` по назначению. Он не делает выполнение функции быстрее и не запрещает JavaScript создать очередную функцию во время рендера. React просто возвращает прежнюю кешированную ссылку, пока зависимости равны. Новая функция является проблемой только тогда, когда её ссылка ломает конкретную оптимизацию или повторно запускает подписку.

`memo` сравнивает каждый prop с предыдущим через `Object.is`. Примитивы с тем же значением считаются равными, а новый объект, массив или функция имеют другую ссылку. При равных `props` React обычно пропускает рендер, но собственное состояние и прочитанный Context всё равно обновляют компонент. `memo` является подсказкой производительности, а не гарантией никогда не вызывать компонент повторно.

Пользовательская функция сравнения во втором аргументе `memo` иногда полезна, но сама может оказаться дороже рендера. Она обязана сравнивать каждый prop, включая функции. Если вернуть `true` для изменившейся функции, ребёнок сохранит замыкание со старыми `props` или состоянием родителя. Глубокое сравнение структуры неизвестной глубины особенно опасно.

До добавления мемоизации сначала проверяют структуру состояния и измеряют проблему в React Profiler. Часто эффективнее держать состояние ближе к месту использования, передавать JSX как `children`, не поднимать краткоживущее состояние интерфейса без причины и убрать эффект, который запускает цепочку обновлений. Мемоизация полезна, когда дорогой участок действительно повторяется с теми же входными данными.

React Compiler 1.0 стабильно доступен с октября 2025 года и автоматически мемоизирует компоненты и вычисления при сборке. Он совместим с React 17+ при подходящей настройке служебной среды выполнения. В проекте с Compiler потребность в ручных `memo`, `useMemo` и `useCallback` заметно ниже, но миграция требует соблюдения правил React и измерения результата. Ручную мемоизацию сохраняют там, где она нужна внешнему контракту или Compiler не оптимизировал конкретный участок.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему два объекта <code>{}</code> не равны для <code>memo</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Каждый литерал создаёт новую ссылку, а `Object.is({}, {})` возвращает `false`. Если родитель передаёт `options={{ sort: "name" }}` при каждом рендере, `memo` видит новый prop. Решение выбирают по контексту: передать примитивы, создать объект внутри ребёнка или мемоизировать его, если это поддерживает измеримую оптимизацию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что произойдёт при пропущенной зависимости в <code>useMemo</code> или <code>useCallback</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Кешированное вычисление или функция продолжит использовать значения старого рендера. Возникнет устаревшее замыкание: ссылка выглядит стабильной, но поведение уже не соответствует актуальным `props` и состоянию. Массив зависимостей должен содержать все реактивные значения, прочитанные внутри функции.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда <code>useCallback</code> является лишним?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда функция используется только в текущем компоненте, не входит в зависимости другого хука и не передаётся в мемоизированный компонент или внешний API со сравнением ссылок. В таком случае кеш, массив зависимостей и усложнение чтения могут стоить больше, чем создание функции.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>memo</code> не спасает от обновления Context?</strong></summary>

<dl>
<dd>
<h2></h2>

`memo` сравнивает только `props` от родителя. Если компонент прочитал Context и значение ближайшего провайдера изменилось, React должен передать ему новое значение независимо от равенства `props`. Чтобы сузить обновления, разделяют Context или выносят чтение в небольшой внешний компонент.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем опасна пользовательская функция сравнения для <code>memo</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Сравнение выполняется при каждом обновлении родителя и может быть дороже самого рендера. Если функция сравнения ошибочно считает разные функции равными, компонент продолжит вызывать старое замыкание. Такой вариант используют только для структуры с ограниченной глубиной и после профилирования.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Отменяет ли React Compiler ручную мемоизацию полностью?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Compiler автоматически покрывает многие обычные случаи, поэтому ручного кода становится меньше. Но проект может внедрять его постепенно, часть файлов может не компилироваться, а внешняя библиотека иногда требует стабильную ссылку. Сначала проверяют результат Compiler в профилировщике, затем оставляют только обоснованные ручные оптимизации.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Возможное решение |
| --- | --- |
| Дорогая фильтрация большого списка | `useMemo` после измерения |
| Новая функция ломает `memo` тяжёлой строки | `useCallback` с полным массивом зависимостей |
| Большой ребёнок редко меняет `props` | `memo` |
| Новый объект создаётся только для эффекта | Создать объект внутри эффекта вместо мемоизации |
| Context обновляет потребителя | Изменить границы Context, а не добавлять `memo` |
| Проект использует React Compiler | Сначала полагаться на Compiler и измерения |
