## Вопрос

Что такое Portal в React? Как он влияет на Context, события, CSS и доступность всплывающих компонентов?

<details>
<summary><strong>Показать ответ</strong></summary>

Portal позволяет отрендерить DOM-узлы дочернего компонента в другой DOM-контейнер, сохранив компонент на прежнем месте React-дерева. Его создают через `createPortal(children, domNode)`. Portal меняет физическое размещение DOM, но не создаёт отдельное React-приложение.

```tsx
function Modal({ children }) {
  return createPortal(children, document.getElementById("modal-root")!);
}
```

Portal используют для модальных окон, всплывающих подсказок (tooltip), popover, выпадающих меню и уведомлений. Такой интерфейс часто должен выйти из контейнера с `overflow: hidden` или из локального контекста наложения (stacking context), который управляет слоями `z-index`. Перенос ближе к `document.body` упрощает расположение поверх страницы, хотя сам по себе не гарантирует верхний слой. Нужно учитывать CSS других контейнеров и нативный верхний слой браузера (top layer), в который могут попадать `<dialog>` и элементы Popover API.

У Portal одновременно существуют две иерархии:

| Иерархия | Что определяет |
| --- | --- |
| React-дерево | `Props`, состояние, Context, Error Boundary и всплытие событий React |
| DOM-дерево | Наследование CSS, селекторы, расположение элементов, `contains()`, фокус и нативные события |

Context продолжает работать по React-дереву. Если `Modal` создан внутри `ThemeContext`, его дочерние компоненты прочитают тему независимо от размещения DOM. `Props` и функции обратного вызова работают так же, как у обычного ребёнка.

События React из Portal всплывают по React-дереву. Клик по кнопке, физически находящейся под `document.body`, может дойти до `onClick` React-родителя внутри другого DOM-контейнера. Это поведение связано с тем, как React сопоставляет DOM-узел своему дереву. `SyntheticEvent` является унифицированным объектом события, а не отдельной причиной такого всплытия.

CSS, напротив, следует DOM-дереву. Portal может потерять стили вида `.card .tooltip`, потому что `.tooltip` больше не находится внутри `.card`. Наследуемые свойства и пользовательские CSS-переменные также берутся от реальных DOM-предков контейнера. Дизайн-система должна размещать глобальные токены на общем предке либо передавать необходимые значения явно.

`domNode` должен существовать к моменту вызова `createPortal`. Передача другого контейнера на следующем рендере пересоздаёт содержимое Portal, поэтому контейнер делают стабильным. На сервере нет `document`, следовательно браузерный контейнер нельзя читать во время SSR. Приложение использует предусмотренный фреймворком механизм или создаёт Portal только после монтирования на клиенте, контролируя возможное изменение первоначальной разметки.

Portal решает только размещение DOM. Полноценное модальное окно дополнительно требует:

- доступного имени через заголовок или `aria-label`;
- семантики `role="dialog"` и `aria-modal="true"` либо нативного `<dialog>`;
- переноса начального фокуса внутрь и возврата на элемент, открывший окно, после закрытия;
- удержания Tab внутри модального интерфейса;
- закрытия по `Escape` с учётом вложенных всплывающих элементов;
- блокировки взаимодействия и прокрутки фона;
- корректной обработки клика по фону за окном.

Эти правила сложнее самого Portal, поэтому в production-сборке обычно используют проверенные примитивы Radix UI, React Aria или аналогичной библиотеки.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Как всплывают события из Portal?</summary>

Нативное событие возникает на реальном DOM-узле, после чего React находит соответствующий компонент. Обработчики React вызываются вдоль React-родителей Portal. Поэтому `onClick` родителя может получить клик из модального окна, хотя в DOM родитель и кнопка находятся в разных контейнерах. Обработчики размещают по смыслу, а `stopPropagation()` используют только при осознанной границе поведения.

</details>

<details>
<summary><strong>Вопрос:</strong> Причём здесь <code>SyntheticEvent</code>?</summary>

Это объект React, который предоставляет единый интерфейс события, например `target`, `currentTarget`, `preventDefault()` и `stopPropagation()`. Исходное браузерное событие доступно как `nativeEvent`. Всплытие из Portal определяется React-деревом, а обработчики задаются обычными JSX-свойствами.

</details>

<details>
<summary><strong>Вопрос:</strong> Работает ли Context внутри Portal?</summary>

Да. Context ищется по React-родителям. Portal внутри `ThemeContext` или `AuthContext` видит те же значения, даже если его DOM находится под `body`. Portal меняет DOM-контейнер, а не логического родителя компонента.

</details>

<details>
<summary><strong>Вопрос:</strong> Что произойдёт при смене контейнера Portal?</summary>

React пересоздаст содержимое в новом DOM-узле, поэтому локальное состояние и DOM-состояние поддерева могут быть потеряны. Контейнер `#modal-root` или элемент слоя обычно создают один раз и сохраняют стабильным на весь жизненный цикл Portal.

</details>

<details>
<summary><strong>Вопрос:</strong> Как Portal влияет на CSS?</summary>

Селекторы и наследование используют физическое DOM-дерево. Стиль, зависящий от предка компонента, после переноса может перестать применяться; CSS-переменные также должны быть доступны на новом DOM-пути. Portal помогает обойти `overflow` и локальный контекст наложения, но позиционирование, токены и `z-index` всё равно проектируют отдельно.

</details>

<details>
<summary><strong>Вопрос:</strong> Как определить клик вне выпадающего меню, отрендеренного через Portal?</summary>

Проверяют DOM-принадлежность относительно `ref` открывающего элемента и содержимого: находится ли `event.target` внутри одного из них. Для составных DOM-деревьев полезен `event.composedPath()`. Слушатель часто ставят на `pointerdown` в фазе перехвата, но нужно учитывать полосу прокрутки, вложенные всплывающие элементы и то, что нажатие внутри содержимого не должно считаться внешним кликом.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему <code>createPortal</code> недостаточно для модального окна?</summary>

Portal только выбирает DOM-контейнер. Он не назначает доступное имя, не управляет Tab и начальным фокусом, не возвращает фокус на открывший элемент, не делает фон неактивным через `inert` и не обрабатывает `Escape`. Эти обязанности реализует готовый примитив диалога или сам компонент поверх Portal.

</details>

<details>
<summary><strong>Вопрос:</strong> Как Portal работает с SSR?</summary>

На сервере нет DOM-узла и `document`. Нельзя безусловно искать `modal-root` во время серверного рендера. Фреймворк может иметь собственную поддержку, либо компонент откладывает создание Portal до монтирования в браузере. При этом нужно избежать несовпадения при гидратации и не делать критичный первоначальный контент доступным только после эффекта.

</details>

## Мини-задача

```tsx
function Page() {
  return (
    <div onClick={() => console.log("page click")}>
      <Modal />
    </div>
  );
}

function Modal() {
  return createPortal(
    <button onClick={() => console.log("modal button")}>Save</button>,
    document.body
  );
}
```

<details>
<summary><strong>Вопрос:</strong> Какие сообщения появятся после клика по кнопке?</summary>

Сначала `modal button`, затем `page click`, если обработчик кнопки не остановил всплытие. Кнопка находится под `body` в DOM, но компонент `Modal` остаётся ребёнком `Page` в React-дереве.

</details>

## Где это встречается во frontend

| UI | Что даёт Portal |
| --- | --- |
| Модальное окно | Отдельный DOM-слой поверх основной раскладки |
| Всплывающая подсказка | Выход из `overflow: hidden` и независимое позиционирование |
| Выпадающее меню или popover | Размещение содержимого вне локального контекста наложения |
| Уведомления | Общий контейнер уведомлений |
| Дизайн-система | Единый слой всплывающих элементов с согласованными `z-index` и правилами фокуса |
| Клик снаружи | Необходимость проверять реальное DOM-дерево |
