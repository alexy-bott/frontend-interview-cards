# Reconciliation и key в списках

## Вопрос

<br>

 💬 **Что такое reconciliation в React? Зачем нужен `key` в списках?**

<h2></h2>

<br>
<dl>
<dd>

Reconciliation, или согласование деревьев, — процесс сопоставления нового описания интерфейса с предыдущим.

React определяет:

- какие компоненты и DOM-узлы можно сохранить;
- какие нужно обновить;
- какие нужно удалить;
- какие нужно создать заново.

Подготовленный результат применяется к DOM позднее, во время commit phase.

Состояние компонента связано с его позицией в React-дереве.

При сопоставлении React учитывает:

- положение элемента внутри родителя;
- тип элемента;
- `key`.

Если на прежней позиции остаётся тот же тип с тем же `key`, React обычно сохраняет состояние соответствующего поддерева.

Если тип изменился:

```tsx
<Profile />
```

заменился на:

```tsx
<Settings />
```

React считает это другим поддеревом. Старый компонент размонтируется, его состояние удалится, а новый компонент смонтируется с начальным состоянием.

Для массива дочерних элементов одной позиции недостаточно, потому что элементы могут:

- вставляться;
- удаляться;
- фильтроваться;
- сортироваться;
- менять порядок.

`key` сообщает React устойчивую идентичность элемента среди соседей.

Например:

```tsx
{orders.map((order) => (
  <OrderRow
    key={order.id}
    order={order}
  />
))}
```

После сортировки заказ с:

```tsx
key={order.id}
```

остаётся тем же заказом, хотя его индекс в массиве изменился.

Хороший `key` обладает двумя свойствами:

1. Уникален среди соседних элементов одного списка.
2. Стабилен для одной сущности между рендерами.

Обычно используют идентификатор из данных:

```tsx
key={user.id}
```

`key` не обязан быть уникальным во всём приложении. Одинаковые значения можно использовать в разных независимых списках.

`key` нужно ставить на JSX-элемент, непосредственно возвращаемый из массива:

```tsx
{users.map((user) => (
  <UserRow
    key={user.id}
    user={user}
  />
))}
```

Если разметка вынесена в компонент, `key` всё равно остаётся в месте построения списка:

```tsx
function UserRow({
  user,
}: {
  user: User;
}) {
  return <li>{user.name}</li>;
}

function UserList({
  users,
}: {
  users: User[];
}) {
  return (
    <ul>
      {users.map((user) => (
        <UserRow
          key={user.id}
          user={user}
        />
      ))}
    </ul>
  );
}
```

Если один элемент массива должен вернуть несколько соседних узлов без дополнительного DOM-контейнера, используют `Fragment` с `key`:

```tsx
import {
  Fragment,
} from "react";

{users.map((user) => (
  <Fragment key={user.id}>
    <h2>{user.name}</h2>
    <p>{user.description}</p>
  </Fragment>
))}
```

Короткая запись:

```tsx
<>
  ...
</>
```

не позволяет передать `key`.

`key` является специальным полем React и не передаётся компоненту как обычный prop.

Если компоненту нужен тот же идентификатор, его передают отдельно:

```tsx
<Row
  key={item.id}
  itemId={item.id}
/>
```

Индекс массива является слабым `key`, если список может изменяться:

```tsx
{users.map((user, index) => (
  <UserRow
    key={index}
    user={user}
  />
))}
```

Индекс описывает позицию, а не сущность.

После перестановки на прежней позиции окажутся другие данные, но React сопоставит их с прежним `key`. В результате локальное состояние поддерева может перейти к другой сущности.

Проблема особенно заметна, если элементы содержат:

- локальный `state`;
- неконтролируемые поля ввода;
- focus;
- refs;
- анимации;
- effects, связанные с конкретной сущностью.

Если явный `key` отсутствует, React фактически использует позицию элемента, что создаёт похожие риски.

Индекс допустим для действительно статичного списка без устойчивых идентификаторов, если:

- элементы не сортируются;
- элементы не фильтруются;
- элементы не вставляются и не удаляются;
- порядок никогда не изменяется.

Случайное значение ещё хуже:

```tsx
key={Math.random()}
```

При каждом render создаётся новая идентичность.

React считает прежние элементы удалёнными, а новые — только что добавленными. В результате:

- компоненты размонтируются и монтируются заново;
- DOM-узлы пересоздаются;
- локальное состояние теряется;
- пользовательский ввод может пропасть;
- focus сбрасывается;
- effects запускаются заново.

Если идентификатор создаётся локально, его генерируют один раз при создании самой сущности, а не во время render.

Например:

```ts
const item = {
  id: crypto.randomUUID(),
  title,
};
```

Намеренная смена стабильного `key` полезна, когда поддерево действительно нужно сбросить:

```tsx
<ProfileForm
  key={userId}
  userId={userId}
/>
```

После изменения `userId` React создаст новую идентичность формы и инициализирует её состояние заново.

При этом будут также пересозданы:

- дочерние компоненты;
- DOM-узлы;
- refs;
- effects.

Поэтому смену `key` используют как явный механизм сброса конкретного поддерева, а не как универсальный способ исправлять ошибки синхронизации.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что произойдёт при смене типа элемента на том же месте?</strong></summary>

<dl>
<dd>
<h2></h2>

Если вместо:

```tsx
<Profile />
```

на той же позиции появляется:

```tsx
<Settings />
```

React считает их разными поддеревьями.

`Profile` размонтируется:

- его локальное состояние удалится;
- cleanup его effects выполнится;
- refs очистятся;
- дочернее дерево будет удалено.

Затем `Settings` смонтируется с начальным состоянием.

Одинаковый `key` не превращает разные типы в один компонент:

```tsx
<Profile key="page" />
<Settings key="page" />
```

Тип элемента остаётся частью его идентичности.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему индекс массива часто является плохим <code>key</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Индекс описывает позицию, а не сущность.

Например, первоначальный список:

```text
index 0 → Alice
index 1 → Bob
```

После вставки нового пользователя в начало:

```text
index 0 → Carol
index 1 → Alice
index 2 → Bob
```

React видит прежние ключи `0` и `1`, но теперь им соответствуют другие пользователи.

В результате состояние компонента, ранее находившегося на позиции `0`, может быть сохранено уже для `Carol`.

Ошибка особенно заметна у строк с:

- локальным состоянием;
- полем ввода;
- focus;
- раскрытым меню;
- анимацией.

Если сущность имеет устойчивый идентификатор, нужно использовать его:

```tsx
key={user.id}
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли использовать случайный <code>key</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Нельзя генерировать новый случайный `key` во время каждого render:

```tsx
key={Math.random()}
```

Значение не совпадёт с предыдущим render, поэтому React посчитает элемент новым.

Это приводит к:

- повторному mounting;
- пересозданию DOM;
- потере локального состояния;
- потере пользовательского ввода;
- сбросу focus;
- повторному запуску effects.

Случайный идентификатор допустимо создать один раз при создании самих данных:

```ts
const newTodo = {
  id: crypto.randomUUID(),
  text,
};
```

После этого сохранённый `id` используется как стабильный `key`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Доступен ли <code>key</code> внутри props компонента?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

`key` и `ref` являются специальными полями React и не входят в обычные props компонента.

Нельзя прочитать:

```tsx
function UserRow(props) {
  console.log(props.key);
}
```

Если дочернему компоненту нужен идентификатор, его передают отдельно:

```tsx
<UserRow
  key={user.id}
  userId={user.id}
/>
```

`key` используется React для reconciliation, а `userId` относится к логике приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем намеренно менять <code>key</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Новый `key` создаёт другую идентичность элемента внутри родителя.

Например:

```tsx
<Chat
  key={recipient.id}
  recipient={recipient}
/>
```

При смене получателя React не сохраняет черновик состояния прежнего `Chat`, а создаёт новое поддерево.

Это полезно для:

- сброса формы при смене сущности;
- очистки черновика;
- перезапуска локального состояния;
- повторной инициализации стороннего компонента.

Но смена `key` также:

- размонтирует всё поддерево;
- сбросит focus;
- очистит refs;
- выполнит cleanup effects;
- создаст DOM заново.

Поэтому её не используют как универсальное исправление любой проблемы синхронизации.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```tsx
{users.map((user, index) => (
  <UserRow key={index} user={user} />
))}
```

<details>
<summary><strong>Чем опасен код, если список можно сортировать?</strong></summary>

<dl>
<dd>
<h2></h2>

После сортировки индекс продолжит обозначать позицию, но на ней окажется другой пользователь.

React может сохранить состояние прежнего `UserRow` на этой позиции и связать его уже с новыми данными.

Например, к другому пользователю могут перейти:

- введённый текст;
- раскрытое меню;
- локальный флаг выбора;
- focus;
- состояние анимации.

Если у пользователя есть устойчивый идентификатор, нужен:

```tsx
{users.map((user) => (
  <UserRow
    key={user.id}
    user={user}
  />
))}
```

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что обеспечивает `key` |
| --- | --- |
| Таблица после сортировки | Сохраняет идентичность строк |
| Drag and drop | Сопоставляет элементы после смены порядка |
| Поля ввода внутри списка | Не переносит состояние и ввод к другой сущности |
| Enter/exit-анимация | Помогает отличить добавление, удаление и обновление |
| Несколько узлов на элемент списка | `<Fragment key={id}>` задаёт идентичность группы |
| Смена редактируемой сущности | Новый `key` намеренно сбрасывает форму |
