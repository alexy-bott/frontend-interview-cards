## Вопрос

<br>

 💬 **Чем отличаются `useMemo`, `useCallback` и `memo`? Когда мемоизация в React действительно полезна?**

<h2></h2>

<br>
<dl>
<dd>

`useMemo`, `useCallback` и `memo` являются оптимизациями, но сохраняют разные вещи.

Они не должны быть необходимы для правильности программы.

| API | Что сохраняет | Типичный сценарий |
| --- | --- | --- |
| `useMemo(calculate, deps)` | Результат вычисления | Дорогое чистое вычисление или стабильное значение для другой оптимизации |
| `useCallback(fn, deps)` | Ссылку на функцию | Функция для мемоизированного ребёнка или API, зависящего от identity |
| `memo(Component)` | Возможность пропустить рендер компонента | Измеримо дорогой ребёнок с редко меняющимися `props` |

Эти API не образуют обязательную цепочку.

Компонент не нужно автоматически оборачивать в `memo`, каждую функцию — в `useCallback`, а каждый объект — в `useMemo`.

`useMemo` кеширует результат чистого вычисления внутри конкретного экземпляра компонента:

```tsx
const visibleItems =
  useMemo(
    () =>
      filterItems(
        items,
        query,
      ),
    [items, query],
  );
```

При первоначальном рендере React вызывает функцию вычисления и сохраняет её результат.

Во время следующих рендеров React сравнивает зависимости через:

```ts
Object.is
```

Если зависимости не изменились, React возвращает сохранённое значение.

Если хотя бы одна зависимость изменилась, вычисление выполняется заново.

Функция внутри `useMemo` выполняется во время render, поэтому она должна быть чистой.

Нельзя выполнять внутри неё:

- запросы;
- изменение DOM;
- запись в storage;
- отправку аналитики;
- мутацию внешних данных.

В development Strict Mode React может вызвать функцию вычисления дважды, чтобы обнаружить нечистый код. Один из результатов будет проигнорирован.

`useMemo` полезен, когда:

- чистое вычисление действительно дорогое;
- оно часто повторяется с теми же входными данными;
- сохранённая ссылка поддерживает другую измеримую оптимизацию;
- значение используется как зависимость API, которому важна identity.

Например:

```tsx
const options =
  useMemo(
    () => ({
      sort,
      direction,
    }),
    [sort, direction],
  );
```

может быть полезен, если `options` передаётся мемоизированному компоненту.

Но если объект нужен только внутри Effect, часто проще создать его непосредственно там:

```tsx
useEffect(() => {
  const options = {
    serverUrl,
    roomId,
  };

  const connection =
    createConnection(options);

  return () => {
    connection.disconnect();
  };
}, [serverUrl, roomId]);
```

Это лучше, чем добавлять мемоизацию только ради исправления зависимости:

```tsx
const options =
  useMemo(
    () => ({
      serverUrl,
      roomId,
    }),
    [serverUrl, roomId],
  );

useEffect(() => {
  const connection =
    createConnection(options);

  return () => {
    connection.disconnect();
  };
}, [options]);
```

Кеш `useMemo` является оптимизацией, а не семантической гарантией.

React может удалить его по внутренней причине, например:

- после изменения файла в development;
- если компонент приостановился во время первоначального монтирования;
- в будущих сценариях управления виртуализированным содержимым.

Если значение требуется сохранить для правильности программы, используют:

- `state`;
- `ref`;
- подходящий внешний store.

`useMemo` не предназначен для хранения предметного состояния.

Каждый экземпляр компонента также имеет собственный кеш:

```tsx
<ProductList />
<ProductList />
```

Эти два компонента не делят результат одного `useMemo`.

`useCallback` кеширует ссылку на функцию:

```tsx
const handleSubmit =
  useCallback(
    (
      order: Order,
    ) => {
      submitOrder(
        productId,
        order,
      );
    },
    [productId],
  );
```

При неизменных зависимостях React возвращает ту же ссылку, что и во время предыдущего рендера.

По назначению:

```tsx
useCallback(fn, deps)
```

близок к:

```tsx
useMemo(
  () => fn,
  deps,
)
```

`useCallback`:

- не выполняет переданную функцию;
- не делает её внутренний код быстрее;
- не предотвращает создание функции JavaScript во время текущего render;
- не гарантирует вечное сохранение ссылки.

JavaScript всё равно вычисляет выражение функции:

```tsx
() => {
  submitOrder(productId);
}
```

React либо возвращает сохранённую предыдущую ссылку, либо сохраняет новую, если зависимости изменились.

Новая функция сама по себе обычно не является проблемой.

Она становится важной, если ссылка:

- передаётся в компонент с `memo`;
- входит в зависимости другого Hook;
- используется API подписки;
- служит ключом кеша;
- передаётся сторонней библиотеке, сравнивающей функции по ссылке.

Например:

```tsx
const ProductForm =
  memo(function ProductForm({
    onSubmit,
  }: {
    onSubmit: (
      order: Order,
    ) => void;
  }) {
    // Дорогой render.
  });
```

Родитель может сохранить callback:

```tsx
const handleSubmit =
  useCallback(
    (
      order: Order,
    ) => {
      submitOrder(
        productId,
        order,
      );
    },
    [productId],
  );

return (
  <ProductForm
    onSubmit={handleSubmit}
  />
);
```

Без `memo` ребёнок по умолчанию всё равно рендерится вместе с родителем, поэтому стабильная ссылка на callback сама по себе обычно не даст выигрыша.

`memo` принимает компонент и возвращает его мемоизированную версию:

```tsx
const UserRow =
  memo(function UserRow({
    user,
  }: {
    user: User;
  }) {
    return (
      <div>{user.name}</div>
    );
  });
```

Когда родитель рендерится, React сравнивает каждый новый prop с предыдущим через:

```ts
Object.is
```

Примитивы с одинаковым значением равны:

```ts
Object.is(10, 10);
// true
```

Новые объекты, массивы и функции имеют другие ссылки:

```ts
Object.is({}, {});
// false
```

```ts
Object.is(
  () => {},
  () => {},
);
// false
```

Поэтому такой prop меняется при каждом рендере:

```tsx
<UserRow
  options={{
    compact: true,
  }}
/>
```

даже если содержимое объекта выглядит одинаково.

`memo` обычно пропускает рендер при равных `props`, но не блокирует обновления, вызванные:

- собственным `state`;
- прочитанным Context;
- внешним хранилищем;
- внутренними решениями React.

`memo` является подсказкой производительности, а не гарантией того, что функция компонента никогда не будет вызвана повторно.

Для хорошей работы `memo` сначала полезно уменьшить контракт компонента.

Вместо большого объекта:

```tsx
<Profile person={person} />
```

можно передать минимальные значения:

```tsx
<Profile
  name={person.name}
  imageUrl={person.imageUrl}
/>
```

Так меньше вероятность, что изменение ненужного поля сломает мемоизацию.

Нужно учитывать и `children`.

Например:

```tsx
<Card>
  <Content />
</Card>
```

создаёт React-элемент `Content` во время render родителя.

Если `Card` обёрнут в `memo`, новый `children` может считаться изменившимся prop.

Это не означает, что любой JSX нужно мемоизировать. Сначала проверяют, является ли render `Card` измеримо дорогим.

Массив зависимостей `useMemo` и `useCallback` должен содержать все реактивные значения, прочитанные внутри функции:

```tsx
const handleSave =
  useCallback(() => {
    saveUser(
      userId,
      formValues,
    );
  }, [
    userId,
    formValues,
  ]);
```

Список зависимостей:

- записывается inline;
- имеет постоянное число элементов;
- сравнивается через `Object.is`.

Пропущенная зависимость создаёт не просто менее эффективный кеш, а ошибку корректности:

```tsx
const handleSave =
  useCallback(() => {
    saveUser(userId);
  }, []);
```

Функция продолжит использовать `userId` того рендера, в котором была сохранена.

Это stale closure, или устаревшее замыкание.

Пользовательскую функцию сравнения можно передать вторым аргументом `memo`:

```tsx
const Chart =
  memo(
    ChartComponent,
    arePropsEqual,
  );
```

Она получает предыдущие и новые props:

```tsx
function arePropsEqual(
  previousProps: ChartProps,
  nextProps: ChartProps,
) {
  return (
    previousProps.points
      === nextProps.points
  );
}
```

Функция должна вернуть:

```text
true
→ новые props дадут тот же результат и поведение

false
→ компонент нужно отрендерить заново
```

Нужно сравнить все props, включая функции.

Например, опасно игнорировать callback:

```tsx
function arePropsEqual(
  previousProps: Props,
  nextProps: Props,
) {
  return (
    previousProps.value
      === nextProps.value
  );
}
```

если одновременно изменился:

```tsx
onClick
```

Компонент может сохранить старую функцию, замкнувшую устаревшие `props` или `state` родителя.

Пользовательское сравнение выполняется при каждом обновлении родителя.

Оно может оказаться дороже обычного рендера.

Глубокое сравнение структуры неизвестной глубины особенно опасно:

```tsx
JSON.stringify(
  previousProps,
) ===
  JSON.stringify(
    nextProps,
  )
```

Такой код:

- выполняет дополнительную работу;
- не поддерживает все JavaScript-значения;
- может блокировать главный поток на больших данных;
- скрывает проблему нестабильного контракта.

Custom comparator применяют редко, для структуры с ограниченной и понятной глубиной и только после измерения в production-сборке.

Перед ручной мемоизацией сначала проверяют архитектуру обновлений.

Часто эффективнее:

- держать состояние ближе к месту использования;
- не поднимать временное UI-состояние без причины;
- передавать минимальные `props`;
- передавать оболочке готовый JSX через композицию;
- разделять слишком широкий Context;
- удалять Effects, создающие цепочки обновлений;
- не пересоздавать состояние из Effects;
- виртуализировать действительно большие списки.

После этого измеряют:

- React Profiler;
- Performance panel браузера;
- длительность пользовательского взаимодействия.

Ручная мемоизация полезна, когда одновременно выполняются условия:

```text
участок измеримо дорогой
+
часто получает те же входы
+
стоимость сравнения и кеша ниже повторной работы
```

React Compiler автоматически применяет мемоизацию к успешно компилируемым компонентам и значениям.

Стабильный релиз React Compiler 1.0 вышел 7 октября 2025 года.

Compiler работает во время сборки и анализирует:

- компоненты;
- custom hooks;
- поток данных;
- изменяемость значений.

Он может автоматически:

- переиспользовать JSX;
- кешировать вычисления;
- стабилизировать значения;
- пропускать лишние рендеры дочерних компонентов.

Поэтому в проекте с React Compiler потребность в ручных:

- `memo`;
- `useMemo`;
- `useCallback`;

становится значительно ниже.

Охват Compiler зависит от конфигурации.

По умолчанию он определяет компоненты и hooks по соглашениям React, но может:

- внедряться постепенно;
- компилировать только отмеченные функции;
- пропускать функцию с неподдерживаемым кодом;
- быть временно отключён для конкретного участка.

React Compiler совместим с React 17 и новее.

Для React 17 и React 18 требуется:

- указать подходящий `target`;
- подключить `react-compiler-runtime`.

В проекте с Compiler ручную мемоизацию не добавляют автоматически.

Её сохраняют или добавляют, если:

- конкретный участок пока не компилируется;
- оптимизация подтверждена измерениями;
- внешнему API нужна стабильная identity;
- библиотечный контракт явно требует сохранения ссылки;
- проводится постепенная миграция.

Даже с Compiler нельзя полагаться на мемоизацию для правильности программы.

Будущая версия Compiler может изменить степень и гранулярность оптимизации.

Если изменение количества мемоизации ломает Effect или бизнес-логику, значит код ошибочно использует identity кешированного значения как семантическую гарантию.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Почему два объекта <code>{}</code> не равны для <code>memo</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Каждый объектный литерал создаёт новую ссылку:

```ts
Object.is({}, {});
// false
```

Например:

```tsx
<UsersList
  options={{
    sort: "name",
  }}
/>
```

при каждом render передаёт новый объект.

Даже если его поля содержат те же значения, `memo` видит изменившийся prop.

Вариант решения зависит от контекста.

Можно передать примитивы:

```tsx
<UsersList
  sort="name"
/>
```

Можно создать объект внутри ребёнка:

```tsx
function UsersList({
  sort,
}: {
  sort: Sort;
}) {
  const options = {
    sort,
  };

  // ...
}
```

Либо сохранить ссылку через `useMemo`, если это поддерживает подтверждённую оптимизацию:

```tsx
const options =
  useMemo(
    () => ({
      sort: "name",
    }),
    [],
  );
```

Не нужно мемоизировать объект только потому, что он является объектом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что произойдёт при пропущенной зависимости в <code>useMemo</code> или <code>useCallback</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Кешированное вычисление или функция продолжат использовать значения старого рендера.

Например:

```tsx
const handleSubmit =
  useCallback(() => {
    submitOrder(
      productId,
    );
  }, []);
```

Если `productId` изменится, React продолжит возвращать функцию, которая замкнула прежнее значение.

Возникает stale closure:

```text
ссылка стабильна
→ поведение устарело
```

Массив зависимостей должен содержать все реактивные значения, прочитанные внутри функции:

```tsx
const handleSubmit =
  useCallback(() => {
    submitOrder(
      productId,
    );
  }, [productId]);
```

Пропуск зависимости является ошибкой корректности, а не способом усилить мемоизацию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда <code>useCallback</code> является лишним?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда функция:

- используется только в текущем компоненте;
- не передаётся мемоизированному ребёнку;
- не входит в зависимости другого Hook;
- не используется API, сравнивающим ссылки;
- не является частью публичного контракта custom hook.

Например:

```tsx
function Form() {
  function handleSubmit() {
    saveForm();
  }

  return (
    <form
      onSubmit={handleSubmit}
    />
  );
}
```

Здесь `useCallback` обычно ничего не улучшает.

Он добавит:

- массив зависимостей;
- кеш;
- дополнительный уровень чтения;
- риск stale closure при ошибочных зависимостях.

Создание небольшой функции во время render обычно дешевле обслуживания ненужной мемоизации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>memo</code> не спасает от обновления Context?</strong></summary>

<dl>
<dd>
<h2></h2>

`memo` сравнивает только `props`, полученные от родителя.

Если компонент читает Context:

```tsx
const theme =
  useContext(ThemeContext);
```

и значение ближайшего Provider изменилось, React должен передать потребителю новое значение независимо от равенства props.

Например:

```tsx
const Button =
  memo(function Button() {
    const theme =
      useContext(
        ThemeContext,
      );

    return (
      <button
        className={theme}
      />
    );
  });
```

Изменение `theme` запустит render `Button`.

Чтобы сузить обновления, можно:

- разделить слишком широкий Context;
- передавать более узкие значения;
- вынести чтение Context во внешний компонент;
- передать мемоизированному ребёнку минимальный prop;
- использовать внешний store с selectors, если это соответствует задаче.

Простое добавление `memo` Context-обновление не блокирует.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем опасна пользовательская функция сравнения для <code>memo</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Custom comparator выполняется при каждом обновлении родителя.

Он может оказаться дороже самого render.

Кроме того, функция должна сравнивать каждый prop, включая callbacks.

Если изменившуюся функцию ошибочно считать равной:

```tsx
previousProps.onClick
nextProps.onClick
```

ребёнок продолжит использовать старое замыкание с предыдущими значениями родителя.

Опасно также применять глубокое сравнение к данным неизвестной глубины.

Оно может надолго заблокировать главный поток после роста структуры.

Custom comparator используют только когда:

- структура данных имеет ограниченную глубину;
- обычные props нельзя сделать стабильнее;
- render компонента измеримо дорогой;
- production-профилирование подтвердило выигрыш.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Отменяет ли React Compiler ручную мемоизацию полностью?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

React Compiler автоматически покрывает многие обычные случаи, поэтому ручного кода становится значительно меньше.

Но проект может:

- внедрять Compiler постепенно;
- компилировать только часть каталогов;
- использовать annotation mode;
- содержать функции, которые Compiler пропустил;
- интегрироваться с API, которому явно нужна стабильная identity.

При использовании Compiler сначала проверяют:

- какие компоненты действительно скомпилированы;
- изменилось ли время взаимодействия;
- исчезли ли дорогие повторные рендеры;
- не используется ли мемоизация как условие правильности.

Ручную мемоизацию оставляют там, где она имеет подтверждённую пользу или является частью внешнего контракта.

Удалять существующие `useMemo`, `useCallback` и `memo` только ради чистоты кода без проверки поведения и профилирования не обязательно.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Возможное решение |
| --- | --- |
| Дорогая фильтрация большого списка | `useMemo` после измерения |
| Новая функция ломает `memo` тяжёлой строки | `useCallback` с полным массивом зависимостей |
| Большой ребёнок редко меняет `props` | `memo` |
| Новый объект создаётся только для Effect | Создать объект внутри Effect вместо мемоизации |
| Context обновляет потребителя | Изменить границы Context, а не добавлять `memo` |
| Custom comparator дороже render | Удалить comparator или упростить props |
| Проект использует React Compiler | Сначала полагаться на Compiler, правила React и измерения |
