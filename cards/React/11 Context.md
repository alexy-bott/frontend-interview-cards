## Вопрос

<br>

 💬 **Для чего нужен React Context? Как он распространяет обновления и какие у него ограничения?**

<h2></h2>

<br>
<dl>
<dd>

Context передаёт значение всем заинтересованным компонентам ниже провайдера без ручной передачи `props` через каждый промежуточный уровень. Он подходит для данных, которые относятся ко всему поддереву: тема, локаль, текущая сессия, флаги возможностей (feature flags), настройки дизайн-системы или зависимость окружения.

`createContext(defaultValue)` создаёт объект Context. Компонент читает значение ближайшего провайдера выше себя через `useContext`. Если провайдера нет, возвращается статический `defaultValue`; он не меняется со временем и может служить осмысленным запасным или тестовым значением.

```tsx
const ThemeContext = createContext<"light" | "dark">("light");

function App() {
  return (
    <ThemeContext value="dark">
      <Toolbar />
    </ThemeContext>
  );
}

function Button() {
  const theme = useContext(ThemeContext);
  return <button className={theme}>Save</button>;
}
```

Синтаксис `<ThemeContext value={...}>` появился в React 19. В React 18 и совместимых библиотеках используют `<ThemeContext.Provider value={...}>`.

Когда `value` ближайшего провайдера меняется по `Object.is`, React обновляет всех потребителей этого Context ниже него. `memo` не блокирует такое обновление, потому что сравнивает `props`, а не Context. Новый объект `value={{ user, logout }}` создаётся при каждом рендере провайдера и считается изменившимся даже при тех же полях. Мемоизация `value` может помочь, но сначала нужно убедиться, что обновление действительно лишнее и ссылки на передаваемые функции также стабильны.

Context передаёт значение, но не предоставляет селектор, то есть функцию для подписки на отдельную часть значения. Если один большой Context содержит часто меняющиеся несвязанные данные, каждый потребитель будет получать обновление. Обычно Context разделяют по причинам изменения, например на `CurrentUserContext` и `ThemeContext`, либо используют внешнее хранилище с селекторами для частых точечных обновлений. Иногда отдельно передают состояние и `dispatch`, чтобы компонентам, которые только отправляют действия, не требовалось читать меняющееся состояние.

Провайдер влияет только на потомков. `useContext` в том же компоненте, который возвращает провайдер, прочитает провайдер выше, а не только что созданный ниже. Кроме того, провайдер и потребитель должны использовать один и тот же объект Context. Если сборка создала две копии модуля, визуально одинаковые объекты Context не будут связаны.

Context не заменяет любое управление состоянием. Один-два уровня явных `props` часто проще. Данные API обычно принадлежат кешу запросов, а не Context. Сложное клиентское состояние с селекторами, DevTools и middleware для промежуточной обработки действий удобнее держать в Redux Toolkit или другом внешнем хранилище. Значение авторизации в Context управляет интерфейсом, но не защищает данные: права всегда проверяет сервер.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что такое prop drilling и всегда ли он плох?</strong></summary>

<dl>
<dd>
<h2></h2>

Prop drilling, или сквозная передача `props`, означает передачу значения через промежуточные компоненты, которым оно самим не нужно. Это становится шумом на большой глубине. Однако один-два явных уровня `props` часто лучше Context: зависимости компонента видны прямо в его интерфейсе, а сам компонент проще переиспользовать.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>value={{ user, logout }}</code> обновляет потребителей?</strong></summary>

<dl>
<dd>
<h2></h2>

Литерал создаёт новый объект при каждом рендере, а Context сравнивает `value` через `Object.is`. Новая ссылка означает изменение. Можно мемоизировать объект и функцию, но важнее понять, должны ли `user` и команды находиться в одном Context и насколько часто провайдер рендерится.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Спасает ли <code>memo</code> потребителя от обновления Context?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. `memo` может пропустить рендер из-за равных `props`, но изменение прочитанного Context является отдельной причиной обновления. Можно вынести `useContext` в небольшой компонент и передавать нужный фрагмент мемоизированному ребёнку либо использовать внешнее хранилище с селектором.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли заменить Redux одним Context?</strong></summary>

<dl>
<dd>
<h2></h2>

Для небольшого редко меняющегося состояния иногда можно. Context сам по себе не даёт подписки через селекторы, DevTools, middleware, нормализованную модель и готовую организацию сложных обновлений. Часто обновляемый большой объект Context приводит к более широкой работе, чем точечная подписка через селектор Redux.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Для чего нужен <code>defaultValue</code> в <code>createContext</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Он используется только тогда, когда выше нет соответствующего провайдера. Это статическое запасное значение, а не начальное состояние провайдера. Если отсутствие провайдера является ошибкой, часто передают `null` и создают пользовательский хук, который выбрасывает понятное исключение при `null`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему потребитель иногда не видит провайдер?</strong></summary>

<dl>
<dd>
<h2></h2>

Провайдер может находиться не выше потребителя, либо потребитель читает другой экземпляр Context из дублированного модуля. Значение также не действует на сам компонент, который только возвращает провайдер: его `useContext` ищет провайдер среди родителей.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Подход |
| --- | --- |
| Тема и дизайн-токены | Context для поддерева приложения |
| Локаль | Context с редко меняющимся значением |
| Текущий пользователь | Context для UI, серверная проверка прав отдельно |
| Часто меняющееся значение каждого поля | Локальное состояние формы, не общий Context |
| Данные API | RTK Query, TanStack Query или кеш фреймворка |
| Частые точечные обновления общего состояния | Внешнее хранилище с селекторами |
