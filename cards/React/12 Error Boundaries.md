## Вопрос

Что такое Error Boundary в React? Какие ошибки он перехватывает и какие не перехватывает?

<details>
<summary><strong>Показать ответ</strong></summary>

Error Boundary, или граница обработки ошибок, является компонентом, который перехватывает ошибку в дочернем React-дереве и вместо сломанной области показывает запасной интерфейс (fallback UI). Граница не предотвращает ошибку, а ограничивает область отказа, сохраняет остальную часть приложения доступной и даёт место для логирования.

Классическая граница реализуется классовым компонентом с двумя методами жизненного цикла:

```tsx
class ErrorBoundary extends React.Component<
  React.PropsWithChildren,
  { hasError: boolean }
> {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    reportError(error, info.componentStack);
  }

  render() {
    if (this.state.hasError) {
      return <p>Не удалось показать этот блок.</p>;
    }

    return this.props.children;
  }
}
```

`getDerivedStateFromError` обновляет состояние для показа запасного интерфейса. `componentDidCatch` получает ошибку и стек компонентов, то есть путь по React-дереву до места сбоя, и подходит для отправки в Sentry или другую систему мониторинга. Логировать только текст недостаточно: полезны URL, версия приложения, пользовательский сценарий и идентификатор события, но без чувствительных данных.

Граница перехватывает ошибки, которые React обнаруживает во время рендера и методов жизненного цикла дочерних компонентов, включая конструкторы классовых компонентов. Она не перехватывает:

- ошибку внутри самой границы или её запасного интерфейса, её должна поймать граница выше;
- ошибку обычного обработчика события, потому что уже показанный интерфейс не требуется заменять;
- отклонение Promise, `setTimeout` или другую асинхронную функцию вне рендера React;
- ошибку серверного рендеринга этим клиентским экземпляром границы;
- ошибку, которую код уже поймал и не бросил во время рендера.

Если ошибка возникла в обработчике события, её обрабатывают рядом с действием через `try/catch`, состояние операции и уведомление пользователя. Если библиотека загрузки данных сохраняет асинхронную ошибку, а затем бросает её во время рендера, граница сможет её перехватить. Поэтому фраза «Error Boundary не ловит асинхронные ошибки» слишком груба: важен момент, в который ошибка была брошена в React.

Error Boundary размещают вокруг областей, которые могут отказать независимо: страницы, виджета панели данных, редактора, микрофронтенда или стороннего компонента. Одна граница у корня защищает от пустого экрана, но ошибка маленького блока заменит всё приложение. Слишком мелкая граница вокруг каждой кнопки также создаёт шум и запасные интерфейсы без полезного контекста.

Повтор требует сбросить состояние границы и устранить причину. Готовая библиотека, например `react-error-boundary`, предоставляет API сброса. В простом случае компонент можно перемонтировать новым `key`. Бесконечно повторять тот же рендер без изменения данных нельзя: граница немедленно поймает ту же ошибку.

В React 19 API `createRoot` и гидратации получили функции `onCaughtError`, `onUncaughtError` и `onRecoverableError` для общей отчётности об ошибках. Они дополняют границы интерфейса, но не заменяют локальный запасной интерфейс и решение о том, какую часть приложения сохранить.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Что такое fallback UI у Error Boundary?</summary>

Это запасной интерфейс вместо упавшего поддерева: понятное сообщение, безопасное действие «повторить», ссылка назад или сохранённая часть данных. Он должен соответствовать размеру области и не ломать раскладку страницы. Для динамического сообщения полезно `role="alert"`, но фокус не следует перемещать без необходимости.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему boundary не ловит ошибку в <code>onClick</code>?</summary>

Обработчик выполняется после commit, когда интерфейс уже показан, и ошибка не оставляет React в незавершённом рендере. Её перехватывают в асинхронном процессе операции, показывают пользователю и при необходимости логируют. Если требуется заменить интерфейс, обработчик может записать ошибку в состояние, а компонент затем бросит её во время рендера или покажет собственное состояние ошибки.

</details>

<details>
<summary><strong>Вопрос:</strong> Перехватит ли Error Boundary отклонённый Promise?</summary>

Само необработанное отклонение Promise граница не перехватит. Но фреймворк или библиотека загрузки данных может сохранить ошибку запроса и бросить её при следующем рендере, тогда Error Boundary сработает. Ошибка импорта `lazy` также проявляется через рендер и должна обрабатываться Error Boundary рядом с `Suspense`.

</details>

<details>
<summary><strong>Вопрос:</strong> Можно ли реализовать Error Boundary обычным функциональным компонентом?</summary>

В стабильном публичном React API собственный Error Boundary по-прежнему реализуется классовым компонентом. Приложения часто используют `react-error-boundary` и получают удобный интерфейс для функциональных компонентов, но механизм перехвата внутри опирается на классовую границу.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем Error Boundary отличается от <code>Suspense</code>?</summary>

`Suspense` показывает запасной интерфейс, пока дочерний код или поддерживаемый ресурс загружается. Error Boundary показывает запасной интерфейс после ошибки. Для `lazy` обычно нужны обе границы: `Suspense` на время загрузки части JavaScript-бандла, а Error Boundary на случай, если загрузка завершилась ошибкой.

</details>

<details>
<summary><strong>Вопрос:</strong> Как выбрать уровень Error Boundary?</summary>

Нужно определить область, которая может отказать независимо и имеет осмысленный запасной интерфейс. Для приложения это часто маршрут, крупный виджет, редактор или внешняя интеграция. Граница не должна молча скрывать системную проблему: ошибка логируется, а пользователь получает понятный следующий шаг.

</details>

<details>
<summary><strong>Вопрос:</strong> Как реализовать повтор после ошибки?</summary>

Нужно сбросить состояние границы и операции, при необходимости пометить ошибочные кешированные данные устаревшими или повторно загрузить часть бандла. Если причина связана с прежними `props`, помогает новый `key`. Кнопка повтора не должна запускать бесконечный цикл одинакового падения.

</details>

## Где это встречается во frontend

| Область | Польза Error Boundary |
| --- | --- |
| Маршрут | Ошибка страницы не удаляет общий каркас приложения |
| Виджет панели данных | Остальные виджеты продолжают работать |
| Часть бандла из `lazy` | Ошибка загрузки получает отдельный интерфейс и повтор |
| Сторонний редактор или график | Нестабильная интеграция изолирована |
| Микрофронтенд | Отказ одного блока не размонтирует соседние |
| Корень приложения | Последняя защита от полностью пустого экрана |
