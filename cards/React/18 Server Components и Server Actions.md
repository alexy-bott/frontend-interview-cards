#### Вопрос

Что такое React Server Components и Server Functions? Чем они отличаются от SSR и Client Components?

#### Ответ

React Server Components, или RSC, являются компонентами, которые выполняются в серверной среде или во время сборки и не отправляют собственный JavaScript в клиентский бандл. Они могут напрямую читать серверные данные и формировать сериализованное описание React-дерева. Фреймворк объединяет этот результат с интерактивными Client Components.

Server Component может быть асинхронным, обращаться к базе или внутреннему API и импортировать серверную библиотеку. Он не может использовать `useState`, `useEffect`, DOM, `window` и JSX-обработчики событий, потому что его код не выполняется как компонент в браузере.

Client Component нужен для интерактивности: состояния, эффектов, обработчиков событий и браузерных API. В Next.js файл помечается директивой `"use client"`, которая создаёт границу графа клиентских модулей. Экспортируемый компонент и импортируемые им модули становятся частью клиентского кода. Директиву не требуется повторять в каждом дочернем файле.

RSC и SSR отвечают на разные вопросы:

| Механизм | Результат | Задача |
| --- | --- | --- |
| RSC | Сериализованные данные React Server Components | Разделить серверный и клиентский код в дереве |
| SSR | HTML | Дать браузеру первоначальную разметку |
| Гидратация | Связь Client Components с существующим DOM | Добавить интерактивность в браузере |

При первом открытии фреймворк может выполнить Server Components, получить сериализованные RSC-данные, затем использовать их для создания HTML через SSR. При клиентской навигации он может запросить новые RSC-данные без полной HTML-страницы. Поэтому фраза «компонент выполнился на сервере» ещё не объясняет, идёт ли речь о RSC или SSR.

Server Component может импортировать и рендерить Client Component. `Props` через эту границу должны поддерживать сериализацию React: строки, числа, обычные структуры, React-элементы и специальные поддерживаемые ссылки. Нельзя передать произвольную функцию или экземпляр класса. Исключение составляют ссылки на Server Functions, которые React и фреймворк кодируют особым образом.

Client Component не может импортировать Server Component как обычный модуль, иначе серверный код попал бы в граф клиентских модулей. Однако Server Component может заранее создать серверное содержимое и передать его Client Component через `children` или другой prop:

```tsx
// Server Component
export default function Page() {
  return (
    <ClientModal>
      <ServerCart />
    </ClientModal>
  );
}
```

Server Functions являются асинхронными функциями, выполняемыми на сервере и доступными клиенту через интеграцию фреймворка. Директива `"use server"` помечает такую функцию или модуль. Она не нужна для обозначения Server Component: отдельной директивы `"use server component"` нет. Название Server Actions часто используют для Server Functions, переданных в `action` формы или transition.

Вызов Server Function является сетевым запросом, а не прямым вызовом доверенного серверного кода из браузера. Любой аргумент считается пользовательским вводом. Функция заново проверяет аутентификацию, право на объект, схему данных и принятую во фреймворке защиту от CSRF. Скрытое поле формы, недоступная кнопка и факт импорта функции не являются авторизацией.

React 19 стабилизировал публичную поверхность Server Components, чтобы фреймворк мог использовать React 19 как зависимость. Низкоуровневые API, через которые сборщик или фреймворк реализует RSC, могут меняться между минорными версиями React 19.x. Поэтому приложение использует поддерживаемую версию Next.js или другого фреймворка, а не собирает собственный RSC-протокол без отдельной необходимости.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Server Component является просто SSR-компонентом?
>
> **Ответ:** Нет. SSR создаёт HTML и может выполнять как серверные, так и клиентские компоненты для первоначальной разметки. RSC определяет, код каких компонентов остаётся на сервере, и передаёт сериализованные данные React вместо их JavaScript. Механизмы часто работают вместе, но их результаты и границы различаются.

> [!followup]
> **Вопрос:** Что делает `"use client"`?
>
> **Ответ:** Директива объявляет точку входа в граф клиентских модулей. Экспортированные компоненты могут использовать хуки и браузерные API, а их код и клиентские зависимости войдут в бандл. Это не означает, что весь маршрут становится CSR.

> [!followup]
> **Вопрос:** Делает ли `"use server"` компонент серверным?
>
> **Ответ:** Нет. Директива создаёт Server Function, которую фреймворк может вызвать с клиента. Server Components определяются серверной частью графа модулей без такой директивы. Функция и компонент имеют разные правила вызова и сериализации.

> [!followup]
> **Вопрос:** Можно ли передать функцию из Server Component в Client Component?
>
> **Ответ:** Обычную функцию-замыкание нельзя сериализовать. Можно создать функцию обратного вызова уже внутри Client Component либо передать специальную ссылку на Server Function. Даже Server Function остаётся сетевой операцией с серверной валидацией, а не обычным синхронным вызовом.

> [!followup]
> **Вопрос:** Может ли Client Component показать Server Component внутри себя?
>
> **Ответ:** Да, если Server Component был создан выше на сервере и передан как `children` или React-элемент. Client Component не импортирует его реализацию и только размещает уже описанное серверное содержимое. Прямой импорт серверного модуля из графа клиентских модулей запрещён.

> [!followup]
> **Вопрос:** Уменьшают ли Server Components клиентский бандл автоматически?
>
> **Ответ:** Серверный компонент и его чисто серверные зависимости не отправляются в браузер. Но импорт тяжёлой библиотеки через Client Component всё равно увеличит бандл. Слишком высокая граница `"use client"` затягивает в клиентский граф больше модулей, поэтому интерактивные области стараются держать узкими.

> [!followup]
> **Вопрос:** Можно ли доверять данным Server Function?
>
> **Ответ:** Нет. Аргументы пришли по сети и могут быть подделаны. На каждом вызове проверяются сессия, право на конкретный ресурс, схема данных и допустимость перехода состояния. После изменения данных фреймворк также должен обновить или пометить устаревшим соответствующий кеш.

> [!followup]
> **Вопрос:** Что может вызвать каскадную загрузку в Server Components?
>
> **Ответ:** Последовательные `await`, когда дочерний запрос начинается только после завершения родительского. Независимые данные запускают параллельно, а границы Suspense позволяют потоково раскрывать части. Кеширование и устранение одинаковых запросов зависят от фреймворка и не должны предполагаться без проверки его версии.

#### Где это встречается во frontend

| Ситуация | Выбор |
| --- | --- |
| Чтение данных без интерактивности | Server Component |
| `useState`, обработчик клика или браузерный API | Client Component |
| Первоначальный HTML | SSR поверх результата дерева |
| Изменение данных из формы | Server Function с полной проверкой входа |
| Тяжёлая серверная зависимость | Не пересекать границу `"use client"` |
| Интерактивная оболочка с серверным содержимым | Передать RSC через `children` |
