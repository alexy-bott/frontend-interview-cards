## Вопрос

<br>

 💬 **Что такое React? Почему его используют во frontend-разработке?**

<h2></h2>

<br>
<dl>
<dd>

React — библиотека для построения пользовательских интерфейсов из компонентов.

Разработчик декларативно описывает, каким должен быть интерфейс при текущих входных данных и состоянии. Когда данные меняются, React повторно вычисляет описание интерфейса, сопоставляет его с предыдущим результатом и синхронизирует необходимые изменения с целевой средой, например DOM браузера.

Современный React-компонент обычно является JavaScript-функцией:

```tsx
type GreetingProps = {
  name: string;
};

function Greeting({
  name,
}: GreetingProps) {
  return <h1>Привет, {name}</h1>;
}
```

Компонент получает входные данные и возвращает React node — значение, которое React умеет отобразить.

Это может быть:

- React element;
- строка;
- число;
- массив элементов;
- Fragment;
- `null`.

Классовые компоненты также поддерживаются, но для нового React-кода обычно используют функциональные компоненты и hooks.

React element — неизменяемый объект с описанием одного узла будущего интерфейса.

Он содержит:

- `type`;
- `props`;
- `key`;
- служебные данные React.

Обычно React elements создаются через JSX:

```tsx
<Button label="Сохранить" />
```

JSX похож на HTML, но является расширением синтаксиса JavaScript. Компилятор или инструмент сборки преобразует его в создание React elements.

JSX сам по себе:

- не создаёт DOM;
- не изменяет страницу;
- не рисует пиксели;
- не является HTML-строкой.

Основные части модели React:

| Понятие | Смысл |
| --- | --- |
| Компонент | Функция, описывающая часть интерфейса через React nodes |
| `props` | Входные данные компонента, которые он должен рассматривать как доступные только для чтения |
| `state` | Состояние, которое React связывает с позицией компонента в дереве и сохраняет между рендерами |
| Render | Вычисление следующего описания интерфейса |
| Reconciliation | Сопоставление нового дерева с предыдущим |
| Commit | Применение подготовленных изменений к DOM или другой целевой среде |

Декларативный подход означает, что компонент описывает конечный результат для текущего состояния:

```tsx
<button disabled={isSaving}>
  {isSaving
    ? "Сохранение..."
    : "Сохранить"}
</button>
```

Разработчику не нужно вручную выполнять последовательность команд:

```text
найти DOM-узел
→ изменить disabled
→ заменить текст
→ вернуть прежнее состояние
```

Когда `isSaving` изменяется, React планирует новый render, повторно вызывает необходимые компоненты и получает новое описание интерфейса.

Во время render React не должен выполнять непосредственное изменение DOM.

React вычисляет следующее дерево и во время reconciliation сопоставляет его с предыдущим результатом, учитывая:

- тип элемента;
- положение в дереве;
- `key`.

После этого во время commit React применяет необходимые изменения:

- создаёт, обновляет или удаляет DOM-узлы;
- обновляет refs;
- запускает связанные с commit layout effects.

Обычные effects выполняются отдельно после обновления интерфейса.

За связь React с браузерным DOM отвечает renderer:

```text
React DOM
```

Другие renderers могут применять ту же компонентную модель к другим платформам, например React Native.

React используют во frontend-разработке, потому что он предоставляет:

- декларативное описание интерфейса;
- компонентную модель;
- композицию небольших частей;
- локальное состояние;
- однонаправленный поток данных;
- предсказуемое обновление интерфейса;
- возможность переиспользовать и тестировать компоненты;
- большую экосистему инструментов.

Компонентная модель помогает разделить крупный интерфейс на части с понятными:

- входными данными;
- состояниями;
- действиями;
- ответственностями.

Компоненты можно:

- комбинировать;
- переиспользовать;
- типизировать;
- тестировать;
- собирать в дизайн-систему.

При этом React не определяет всю архитектуру приложения.

Сам React не предоставляет готовую полную модель для:

- маршрутизации;
- сборки проекта;
- серверного рендеринга приложения;
- получения и кэширования серверных данных;
- организации каталогов;
- deployment.

Эти задачи решают дополнительные инструменты.

Например:

| Задача | Инструмент |
| --- | --- |
| Полноценный React-фреймворк, SSR и маршрутизация | Next.js |
| Клиентская маршрутизация | React Router |
| Получение и кэширование серверных данных | RTK Query |
| Разработка и сборка приложения | Vite |

React не гарантирует, что при каждом вызове компонента изменится DOM.

Компонент может быть вызван повторно, но reconciliation покажет, что фактических изменений не требуется.

Поэтому нужно различать:

```text
Render React
→ вычисление нового описания

Commit React DOM
→ изменение DOM при необходимости

Render браузера
→ layout, paint и отображение пикселей
```

Это разные этапы.

При серверном рендеринге React может сформировать начальный HTML на сервере, а затем связать его с клиентским приложением через hydration.

При этом не каждый компонент обязательно выполняется и на сервере, и в браузере: конкретные границы зависят от используемого React-фреймворка и его модели Server и Client Components.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что означает декларативный интерфейс?</strong></summary>

<dl>
<dd>
<h2></h2>

Декларативный код описывает конечный вид интерфейса для текущих данных, а не последовательность команд изменения DOM.

Например:

```tsx
<button disabled={isSaving}>
  Сохранить
</button>
```

Компонент сообщает:

```text
если isSaving равен true
→ кнопка должна быть disabled
```

Когда значение меняется, React повторно вычисляет JSX и сам приводит DOM к нужному состоянию.

При императивном подходе разработчик вручную искал бы DOM-узел и изменял его свойства в нужный момент.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>JSX является HTML внутри JavaScript?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

JSX — расширение синтаксиса JavaScript, предназначенное для описания React-дерева.

Например:

```tsx
<button className="button">
  Сохранить
</button>
```

преобразуется в создание React element.

JSX подчиняется правилам JavaScript и React:

- пользовательские компоненты начинаются с заглавной буквы;
- JavaScript-выражения помещаются в `{}`;
- CSS-класс записывается как `className`;
- обработчик события передаётся как функция в `onClick`;
- несколько соседних элементов должны иметь общего родителя или Fragment.

JSX создаёт описание интерфейса, а не настоящий DOM-узел.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем компонент отличается от React element?</strong></summary>

<dl>
<dd>
<h2></h2>

Компонент — функция или поддерживаемый классовый компонент, который описывает часть интерфейса.

Например:

```tsx
function Button({
  label,
}: {
  label: string;
}) {
  return <button>{label}</button>;
}
```

React element — объект, описывающий конкретное использование компонента или встроенного элемента:

```tsx
<Button label="Сохранить" />
```

В этом случае element содержит примерно следующую информацию:

```text
type
→ Button

props
→ { label: "Сохранить" }
```

Позднее React использует `type`, чтобы вызвать компонент `Button` и получить описание его дочернего дерева.

React element:

- не является DOM-узлом;
- не является экземпляром компонента;
- не содержит отрисованные пиксели;
- рассматривается как неизменяемое описание.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему React называют библиотекой, а не фреймворком?</strong></summary>

<dl>
<dd>
<h2></h2>

React в основном предоставляет:

- компонентную модель;
- state;
- hooks;
- reconciliation;
- механизм рендеринга интерфейса.

Он не задаёт обязательную полную структуру приложения и не включает единое встроенное решение для:

- маршрутизации;
- backend;
- deployment;
- загрузки данных;
- сборки;
- организации каталогов.

Разработчик может подобрать дополнительные инструменты под требования проекта.

React-фреймворк вроде Next.js строит вокруг React более полную модель приложения и добавляет:

- файловую маршрутизацию;
- серверный рендеринг;
- Server Components;
- загрузку данных;
- оптимизацию;
- production-сборку.

Граница между библиотекой и фреймворком не является строгой технической классификацией, но такое разделение помогает описать область ответственности React.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что обычно называют Virtual DOM?</strong></summary>

<dl>
<dd>
<h2></h2>

Virtual DOM — распространённый упрощённый термин для хранимого в памяти описания интерфейса, которое React сопоставляет между обновлениями.

React elements являются лёгкими объектами с описанием узлов, а React на их основе строит и обновляет внутреннее Fiber-дерево.

Это не полная копия настоящего DOM.

React использует новое и предыдущее описание, чтобы определить:

- какие узлы сохранить;
- какие свойства обновить;
- какие элементы создать;
- какие элементы удалить.

Сам термин Virtual DOM не объясняет:

- приоритеты обновлений;
- возможность прерывания render;
- хранение состояния;
- планирование работы.

За эти внутренние механизмы отвечает архитектура Fiber.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Как помогает React |
| --- | --- |
| Повторяющиеся элементы интерфейса | Компоненты переиспользуются и комбинируются |
| Интерфейс зависит от данных | JSX декларативно описывает результат для текущих `props` и `state` |
| Дизайн-система | Компоненты задают единый программный и визуальный контракт |
| Веб-приложение с SSR | React-дерево может получить начальный HTML на сервере и продолжить работу в браузере |
| Несколько платформ | Renderer связывает React с DOM или другой целевой средой |
