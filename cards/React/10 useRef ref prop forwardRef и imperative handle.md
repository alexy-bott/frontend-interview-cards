#### Вопрос

Для чего нужен `useRef`? Как связаны DOM-ссылка, `forwardRef`, передача `ref` как prop и `useImperativeHandle`?

#### Ответ

`useRef` возвращает один и тот же изменяемый объект `{ current }` между рендерами. Запись в `ref.current` не запускает рендер, поэтому `ref` подходит для данных, которые нужны обработчикам или интеграции с внешним API, но не определяют отображаемый интерфейс. Значение, от которого зависит JSX, должно находиться в состоянии.

Основные сценарии:

1. Получить DOM-узел, чтобы сфокусировать поле, прокрутить контейнер или измерить его размеры и положение.
2. Сохранить идентификатор таймера, экземпляр сторонней библиотеки или другое значение конкретного экземпляра компонента.
3. Предоставить родителю небольшой императивный API дочернего компонента.

```tsx
function Search() {
  const inputRef = useRef<HTMLInputElement>(null);

  return (
    <>
      <input ref={inputRef} />
      <button onClick={() => inputRef.current?.focus()}>Focus</button>
    </>
  );
}
```

React устанавливает DOM-узел в `current` во время commit и очищает `ref` при удалении узла. Во время первого рендера `current` обычно равен `null`. Читать или записывать обычный `ref` во время рендера не следует: это нарушает чистоту компонента. Допустима предсказуемая одноразовая инициализация, когда результат всегда одинаков и запись выполняется только при `current === null`.

В React 18 функциональный компонент не получает `ref` как обычный prop. Для передачи `ref` через компонент используют `forwardRef`. В React 19 функциональный компонент может принимать `ref` как prop, поэтому для нового кода `forwardRef` больше не обязателен. Он остаётся необходимым в библиотеках и приложениях, поддерживающих React 18. Официальный API помечен как предназначенный для будущего устаревания, но не удалён из React 19.

```tsx
function MyInput({ ref, ...props }: React.ComponentProps<"input">) {
  return <input ref={ref} {...props} />;
}
```

Пробрасывать наружу весь DOM-узел не всегда правильно. `useImperativeHandle(ref, createHandle, dependencies)` позволяет вернуть ограниченный набор методов, например только `focus()` и `clear()`. Это сохраняет свободу изменить внутреннюю разметку. Императивный API остаётся средством для особых случаев: обычное поведение лучше выражать через `props`, состояние и функции обратного вызова.

Callback ref, то есть `ref` в виде функции, получает DOM-узел при присоединении. Начиная с React 19 эта функция может вернуть функцию очистки, которую React вызовет при отсоединении. Краткая стрелочная функция не должна случайно возвращать результат присваивания: TypeScript для React 19 ожидает `void` или функцию очистки.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Почему изменение `ref.current` не вызывает рендер?
>
> **Ответ:** `Ref` является обычным изменяемым контейнером, запись в который React не отслеживает как обновление интерфейса. Это позволяет хранить таймер или DOM-узел без лишнего рендера. Если пользователь должен увидеть новое значение, нужно состояние.

> [!followup]
> **Вопрос:** Чем `useRef` отличается от переменной на уровне модуля?
>
> **Ответ:** Каждый экземпляр компонента получает собственный `ref` при монтировании. Модульная переменная общая для всех экземпляров в одной среде выполнения JavaScript и может смешать таймеры или DOM-узлы разных компонентов. На уровне модуля хранят только намеренно общую инфраструктуру или константы.

> [!followup]
> **Вопрос:** Можно ли читать `ref.current` во время рендера?
>
> **Ответ:** Обычно нет. Рендер должен зависеть от `props`, состояния и Context, а `ref` меняется без уведомления React, поэтому результат станет непредсказуемым. Исключением является одноразовая детерминированная инициализация объекта под условием `ref.current === null`.

> [!followup]
> **Вопрос:** `forwardRef` больше не нужен в React 19?
>
> **Ответ:** Новые функциональные компоненты React 19 могут принимать `ref` как prop. Но `forwardRef` остаётся рабочим и необходим для React 18, библиотек с широким диапазоном поддерживаемых версий React и существующего кода. Его нельзя удалить из библиотеки без изменения минимальной поддерживаемой версии и типов.

> [!followup]
> **Вопрос:** Для чего нужен `useImperativeHandle`?
>
> **Ответ:** Он заменяет значение, которое родитель получит через `ref`, на небольшой объект методов. Например, компонент дизайн-системы может раскрыть `focus()` и `select()`, но скрыть внутренний `<input>`. Массив зависимостей должен включать все реактивные значения, использованные при создании этого объекта.

> [!followup]
> **Вопрос:** Что изменилось у callback refs в React 19?
>
> **Ответ:** `Ref` в виде функции может вернуть функцию очистки. React вызовет её, когда узел отсоединится или сама callback-функция изменится. Раньше очистку обычно получали повторным вызовом callback с `null`; в React 19 можно явно вернуть функцию очистки.

#### Где это встречается во frontend

| Ситуация | Решение |
| --- | --- |
| Фокус после открытия диалога | DOM-ссылка с управлением фокусом |
| Измерение элемента | Ref и точечный `useLayoutEffect` |
| Идентификатор таймера | `useRef`, если он не влияет на JSX |
| Экземпляр карты или редактора | `Ref` плюс запуск и очистка интеграции |
| Поле ввода дизайн-системы | `Ref` как prop в React 19 или `forwardRef` для React 18 |
| Ограниченный императивный API | `useImperativeHandle` |
