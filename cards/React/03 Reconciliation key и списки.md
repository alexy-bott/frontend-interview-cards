## Вопрос

Что такое reconciliation в React? Зачем нужен `key` в списках?

<details>
<summary><strong>Показать ответ</strong></summary>

Reconciliation, или согласование деревьев, является процессом сопоставления нового описания интерфейса с предыдущим. React определяет, какие компоненты и DOM-узлы можно сохранить, какие нужно обновить, а какие удалить или создать. Результат сравнения применяется к DOM во время фазы commit.

Состояние компонента связано с его положением в React-дереве. При сопоставлении React учитывает позицию, тип элемента и `key`. Если на прежнем месте остаётся тот же тип, React обычно сохраняет экземпляр компонента и его состояние. Если тип изменился, прежнее поддерево размонтируется, а новое создаётся с начальным состоянием.

Для массива дочерних элементов одной позиции недостаточно, потому что строки могут вставляться, удаляться и менять порядок. `key` сообщает React устойчивую идентичность элемента среди соседей. Например, заказ с `key={order.id}` остаётся тем же заказом после сортировки, хотя его индекс в массиве изменился.

Хороший `key` обладает двумя свойствами:

1. Уникален среди соседних элементов одного списка.
2. Стабилен для одной сущности между рендерами.

Обычно используют идентификатор из данных. `key` не обязан быть уникальным во всём приложении. React использует его только при сопоставлении соседей в конкретном месте дерева и не передаёт компоненту как обычный prop. Если компоненту нужен тот же идентификатор, его передают отдельно: `<Row key={item.id} id={item.id} />`.

Индекс массива является слабым `key`, если список сортируется, фильтруется или получает элементы в середину. После перестановки прежний индекс начнёт обозначать другую сущность, и React может сохранить за ней локальное состояние, значение неконтролируемого поля, фокус или состояние анимации. Индекс допустим для действительно статичного списка без устойчивых идентификаторов, если порядок и состав никогда не меняются.

Случайное значение вроде `key={Math.random()}` ещё хуже: каждый рендер создаёт новую идентичность. React размонтирует старые компоненты и смонтирует новые, потеряет состояние и выполнит лишнюю работу. Напротив, намеренная смена стабильного `key` полезна, когда компонент нужно явно сбросить, например начать форму заново при смене `userId`.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Что произойдёт при смене типа элемента на том же месте?</summary>

Если вместо `<Profile />` на той же позиции появляется `<Settings />`, React считает их разными поддеревьями. `Profile` размонтируется вместе с дочерним состоянием и эффектами, затем `Settings` смонтируется с нуля. Одинаковый `key` не делает разные типы одним компонентом.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему индекс массива часто является плохим <code>key</code>?</summary>

Индекс описывает позицию, а не сущность. После вставки в начало прежняя строка с индексом `0` получит индекс `1`, а её старый компонент может быть переиспользован для новых данных. Ошибка особенно заметна у строк с локальным состоянием, полем ввода, фокусом или анимацией.

</details>

<details>
<summary><strong>Вопрос:</strong> Можно ли использовать случайный <code>key</code>?</summary>

Нет, если требуется сохранить компонент. Новое случайное значение на каждом рендере заставляет React считать все элементы новыми: DOM и компоненты пересоздаются, локальное состояние и фокус теряются, а эффекты запускаются заново. `key` должен происходить из устойчивой идентичности данных.

</details>

<details>
<summary><strong>Вопрос:</strong> Доступен ли <code>key</code> внутри props компонента?</summary>

Нет. `key` и `ref` являются специальными полями React и не входят в обычные props. Если дочернему компоненту нужен идентификатор, его передают отдельным prop, например `itemId={item.id}`.

</details>

<details>
<summary><strong>Вопрос:</strong> Зачем намеренно менять <code>key</code>?</summary>

Новая пара «тип плюс key» создаёт новую идентичность, поэтому React сбрасывает локальное состояние и заново монтирует поддерево. Это удобно для формы редактирования разных сущностей. Использовать смену `key` как универсальный способ исправлять синхронизацию не стоит, потому что она также сбрасывает фокус и заново запускает весь жизненный цикл компонента.

</details>

## Мини-задача

```tsx
{users.map((user, index) => (
  <UserRow key={index} user={user} />
))}
```

<details>
<summary><strong>Вопрос:</strong> Чем опасен код, если список можно сортировать?</summary>

После сортировки индекс продолжит обозначать позицию, но на ней окажется другой пользователь. React может перенести локальное состояние `UserRow` к чужим данным. Если у пользователя есть устойчивый идентификатор, нужен `key={user.id}`.

</details>

## Где это встречается во frontend

| Ситуация | Что обеспечивает `key` |
| --- | --- |
| Таблица после сортировки | Сохраняет идентичность строк |
| Drag and drop | Сопоставляет элементы после смены порядка |
| Поля ввода внутри списка | Не переносит значение и фокус к другой сущности |
| Enter/exit-анимация | Позволяет отличить добавление от обновления |
| Смена редактируемой сущности | Новый `key` намеренно сбрасывает форму |
