## Вопрос

<br>

 💬 **Как диагностировать и исправлять проблемы производительности React-приложения?**

<h2></h2>

<br>
<dl>
<dd>

Оптимизацию начинают с наблюдаемого симптома и измерения, а не с добавления `useMemo`. Медленной может быть сеть, загрузка и выполнение бандла, рендер React, применение изменений к DOM, расчёт расположения и отрисовка браузером, длинная задача JavaScript, серверный ответ или работа с памятью. Инструмент и исправление зависят от слоя проблемы.

Практический порядок:

1. Воспроизвести проблему в production-сборке на реалистичном устройстве и объёме данных.
2. Определить пользовательский симптом: медленная загрузка, задержка ввода, рывок скролла или долгая навигация.
3. Посмотреть вкладку Network и Core Web Vitals: LCP для крупного контента, INP для реакции на взаимодействие, CLS для сдвигов раскладки.
4. Записать профиль во вкладке Performance браузера и найти длинные задачи, выполнение JavaScript, пересчёт стилей и раскладки, отрисовку или загрузку.
5. Если время находится в React, записать React DevTools Profiler и изучить commit-фазы, длительность рендера компонентов и причины обновления.
6. Изменить одну причину, повторить тот же сценарий и сравнить результат.

React Profiler показывает commit-фазы, участвовавшие в рендере компоненты, длительность их работы и причины обновлений при включённой диагностике. Он не показывает всю стоимость браузера: быстрый commit React способен вызвать дорогой пересчёт раскладки из-за большого DOM. Поэтому flamegraph, то есть диаграмму длительности компонентов, сопоставляют с временной шкалой Chrome Performance.

React 19.2 добавил React Performance Tracks в Chrome DevTools. Дорожка Scheduler показывает приоритеты блокирующей работы и transitions, а также момент постановки и выполнения обновления. Дорожка Components показывает монтирование, рендер, эффекты и блокировки по компонентам. Эти дорожки помогают связать работу React с остальной временной шкалой браузера.

Типовые причины и решения:

| Причина | Возможное решение |
| --- | --- |
| Состояние расположено слишком высоко | Перенести состояние ближе к потребителю, разделить компоненты |
| Провайдер получает новый большой `value` | Разделить Context или использовать селекторы внешнего хранилища |
| Дорогое вычисление повторяется с теми же входами | React Compiler или точечный `useMemo` |
| Тяжёлый ребёнок получает стабильные данные | Compiler или `memo` после профилирования |
| Тысячи DOM-строк | Виртуализация, постраничная загрузка и уменьшение DOM |
| Ввод конкурирует с рендером списка | `useDeferredValue` или transition |
| Длинная непрерывная задача на CPU | Другой алгоритм, дробление или Web Worker |
| Большой первоначальный JavaScript | Разделение по маршрутам, `lazy`, tree shaking и анализ бандла |
| Последовательные запросы | Параллельная загрузка, кеш, preload и устранение каскадной загрузки |

Виртуализация рендерит видимую часть списка и небольшой запас элементов за краями экрана вместо тысяч строк. Она уменьшает работу React, изменения DOM, пересчёт раскладки и память, но добавляет требования к размеру элементов, клавиатурной навигации, фокусу и доступности. Мемоизация строк не заменяет виртуализацию, если DOM всё равно огромен.

Transitions меняют приоритет рендера, но не сокращают сетевые запросы и не ускоряют новый тяжёлый алгоритм. React Compiler уменьшает повторные вычисления, но не уменьшает первоначальный бандл, объём DOM и стоимость браузерной раскладки. Каждое средство привязано к своей причине.

Частые цепочки «эффект → обновление состояния → рендер» особенно дороги и часто указывают на вычисляемые данные, которые ошибочно синхронизируются через эффект. Также проверяют очистку таймеров, Observer API, WebSocket и отсоединённых DOM-узлов: утечка памяти постепенно ухудшает приложение даже при быстром отдельном рендере.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что показывает React DevTools Profiler?</strong></summary>

<dl>
<dd>
<h2></h2>

Он группирует работу рендера по commit-фазам, показывает длительность компонентов и помогает увидеть, какие `props`, состояние или хуки вызвали обновление. Он измеряет React-часть, а не полную загрузку, сеть или отрисовку браузером. Профиль режима разработки может искажаться Strict Mode, поэтому итоговый вывод проверяют в production-сборке с профилированием.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем длительность рендера отличается от длительности commit?</strong></summary>

<dl>
<dd>
<h2></h2>

Длительность рендера относится к вычислению следующего дерева компонентов. Commit применяет DOM-изменения, `ref` и layout-эффекты. После commit браузер отдельно пересчитывает стили и расположение элементов, а затем рисует их. Оптимизация рендера не поможет, если основное время уходит на принудительный пересчёт большого DOM.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>useMemo</code> не уменьшает размер бандла?</strong></summary>

<dl>
<dd>
<h2></h2>

Он кеширует вычисление во время выполнения уже загруженного компонента. Объём JavaScript для скачивания, разбора и компиляции не меняется. Для уменьшения бандла нужны анализ импортов, tree shaking, разделение кода и удаление тяжёлой зависимости.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое виртуализация списка?</strong></summary>

<dl>
<dd>
<h2></h2>

В DOM находятся только видимые строки и небольшой запас вокруг области просмотра, а прокрутка имитирует полный размер списка. Это радикально уменьшает число компонентов и DOM-узлов. Реализацию обычно доверяют библиотеке, потому что переменная высота, фокус и прокрутка имеют много пограничных случаев.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему Context может создавать широкие обновления?</strong></summary>

<dl>
<dd>
<h2></h2>

Каждый потребитель обновляется при изменении `value` своего Context. Большой объект с часто меняющимися полями затрагивает даже компоненты, которым изменившееся поле не нужно. Context разделяют по причинам изменения или используют внешнее хранилище с подписками через селекторы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое длинная задача и почему она мешает React?</strong></summary>

<dl>
<dd>
<h2></h2>

Это непрерывная задача на главном потоке, которая длится более 50 мс. Пока она выполняется, браузер не может обработать ввод и отрисовать следующий кадр. Задачу делят на части, устраняют лишнюю работу или переносят расчёт в Web Worker. `useTransition` не может прервать произвольную синхронную функцию внутри такой задачи.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить, что оптимизация помогла?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно повторить тот же сценарий на том же устройстве, с теми же данными и production-сборкой, затем сравнить выбранную метрику до и после. Важно проверить не только среднее время, но и худшие взаимодействия, память и отсутствие регрессии поведения. Уменьшение числа сообщений о рендере в консоли само по себе не является продуктовой метрикой.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```tsx
function Page({ items }) {
  const [query, setQuery] = useState("");
  const visibleItems = items.filter((item) => item.name.includes(query));

  return (
    <>
      <input value={query} onChange={(event) => setQuery(event.target.value)} />
      <BigList items={visibleItems} />
    </>
  );
}
```

<details>
<summary><strong>Что нужно измерить и какие решения возможны?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала нужно измерить размер `items`, стоимость `filter`, рендер `BigList`, число DOM-строк и задержку поля ввода. Если фильтрация дорога при тех же входных данных, поможет Compiler или `useMemo`; если дорог каждый новый результат, нужен более быстрый поиск; если проблема в DOM, виртуализация; если ввод ждёт рендер React, отложенный `query`. Для серверного поиска отдельно нужны debounce, отмена и кеш.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Симптом | Первый инструмент |
| --- | --- |
| Медленная первоначальная загрузка | Network, анализатор бандла, Lighthouse |
| Задержка после клика | Профиль Performance и INP |
| Частые обновления React | React Profiler и Performance Tracks |
| Рывки большой таблицы | Число DOM-узлов, раскладка и виртуализация |
| Постепенно растёт память | Снимки памяти и проверка очистки |
| Медленная серверная навигация | Серверные тайминги, запросы и границы потоковой передачи |
