## Вопрос

<br>

 💬 **Как React обновляет интерфейс? Что такое фаза рендера, фаза применения изменений и Fiber?**

<h2></h2>

<br>
<dl>
<dd>

Обновление интерфейса в React DOM можно условно разделить на четыре этапа:

```text
trigger
→ render
→ commit
→ browser paint
```

Первоначальный рендер запускается, когда дерево передают созданному React root:

```tsx
const root = createRoot(
  document.getElementById("root")!,
);

root.render(<App />);
```

Сам вызов `createRoot()` только создаёт корневой объект. Компоненты начинают рендериться после `root.render()`.

Если начальный HTML уже сформирован на сервере, вместо `createRoot` обычно используют:

```tsx
hydrateRoot(
  document.getElementById("root")!,
  <App />,
);
```

Последующие обновления могут запускаться при:

- обновлении `state`;
- изменении используемого `context`;
- изменении внешнего хранилища, на которое компонент подписан;
- рендере родительского компонента.

Новые `props` не появляются сами по себе. Сначала рендерится родитель и передаёт дочернему компоненту очередные значения.

React по умолчанию продолжает render по дочернему дереву обновлённого компонента. Часть работы может быть пропущена благодаря мемоизации и другим оптимизациям.

Во время render phase React вычисляет следующую версию интерфейса.

Он:

- вызывает функции компонентов;
- читает текущие `props`, `state` и `context`;
- получает React elements;
- выполняет reconciliation;
- подготавливает work-in-progress tree;
- определяет необходимые изменения.

Render является вычислением, а не изменением DOM или рисованием пикселей.

Код компонента должен быть чистым и идемпотентным:

```text
одинаковые props, state и context
→ одинаковый результат render
```

Во время render нельзя:

- изменять DOM;
- мутировать `props` и `state`;
- записывать во внешнее хранилище;
- отправлять аналитику;
- выполнять сетевой запрос как побочный эффект;
- изменять глобальные переменные.

Локальная мутация значения, созданного внутри текущего render, допустима, если она не наблюдается снаружи:

```tsx
function List({
  items,
}: {
  items: Item[];
}) {
  const rows = [];

  for (const item of items) {
    rows.push(
      <li key={item.id}>
        {item.name}
      </li>,
    );
  }

  return <ul>{rows}</ul>;
}
```

Чистота render необходима, потому что React может вызвать вычисление повторно.

При конкурентном рендеринге React способен:

- приостановить незавершённую работу;
- уступить главный поток более срочной задаче;
- продолжить работу позднее;
- начать render заново;
- полностью отбросить промежуточный результат.

Например, ввод текста может быть срочным обновлением, а перестроение тяжёлого списка внутри transition — менее срочным.

```tsx
startTransition(() => {
  setSearchResults(nextResults);
});
```

Побочный эффект внутри компонента может выполниться во время render, который затем будет отброшен и никогда не дойдёт до commit.

Поэтому побочные эффекты обычно выполняют:

- в обработчиках событий, если они вызваны действием пользователя;
- в Effect, если нужно синхронизироваться с внешней системой.

Не каждый render обязательно прерывается.

React может выполнить срочное обновление синхронно, не уступая главный поток. Конкурентная архитектура предоставляет возможность управлять приоритетами и прерывать работу, но не обещает, что любой render будет разбит на части.

После успешного завершения render React переходит к commit phase.

Во время commit React DOM применяет подготовленный результат к браузерному DOM.

В эту работу входят:

- создание DOM-узлов;
- обновление свойств и текста;
- удаление DOM-узлов;
- очистка и установка `ref`;
- выполнение layout effects.

Упрощённо порядок можно представить так:

```text
подготовленное React-дерево
→ DOM mutations
→ refs
→ useLayoutEffect
→ возможность browser paint
→ useEffect
```

`useLayoutEffect` выполняется после изменения DOM, но до следующей отрисовки экрана браузером:

```tsx
useLayoutEffect(() => {
  const rect =
    elementRef.current?.getBoundingClientRect();

  // Измерение DOM до следующего paint.
}, []);
```

Код и синхронные обновления внутри `useLayoutEffect` блокируют browser paint, поэтому его используют только тогда, когда измерение или изменение должно произойти до отображения кадра.

Пассивные эффекты из `useEffect` запускаются после commit:

```tsx
useEffect(() => {
  const connection =
    createConnection();

  connection.connect();

  return () => {
    connection.disconnect();
  };
}, []);
```

React часто позволяет браузеру сначала обновить экран, а затем запускает `useEffect`.

Но это не строгая гарантия для каждого обновления. Effect, вызванный взаимодействием пользователя, может выполниться до paint, если это необходимо для системы событий React. Поэтому `useEffect` нельзя использовать как точный механизм планирования работы относительно кадра браузера.

После commit браузер самостоятельно выполняет свои стадии:

```text
style calculation
→ layout
→ paint
→ compositing
```

Render React, commit React DOM и browser rendering являются разными процессами.

Компонент может быть вызван повторно, но React не изменить ни одного DOM-узла, если новое описание не требует изменений.

Fiber — внутренняя архитектура React, которая представляет дерево и организует работу reconciliation.

Fiber-узел является единицей работы, связанной со смонтированной частью React-дерева.

Он может хранить:

- тип компонента или host-элемента;
- `key`;
- текущие и новые `props`;
- состояние;
- очередь обновлений;
- сведения о запланированной работе;
- флаги необходимых изменений;
- ссылки на родителя, ребёнка и соседний узел;
- связь с альтернативной версией узла.

Связи дерева упрощённо выглядят так:

```text
parent
  ↓ child

first child
  → sibling
  → sibling
```

React различает:

- **current tree** — дерево последнего успешно применённого интерфейса;
- **work-in-progress tree** — рабочую версию, которую React подготавливает для возможного следующего commit.

Текущий и рабочий Fiber-узлы могут быть связаны внутренней ссылкой:

```text
alternate
```

Во время обновления React старается переиспользовать существующие Fiber-узлы и их alternate, а не создавать полностью независимое дерево с нуля при каждом render.

Если render успешно завершён и выбран для применения, work-in-progress tree становится новым current tree.

Если render был прерван или устарел, React может его отбросить. Пользователь продолжает видеть последнее успешно применённое дерево.

Fiber позволяет представить render не как один неделимый рекурсивный вызов, а как последовательность небольших единиц работы.

Благодаря этому React может:

- назначать обновлениям разные приоритеты;
- приостанавливать менее срочную работу;
- обрабатывать срочное обновление;
- повторно использовать уже выполненную работу;
- отбрасывать устаревший render.

Это не означает, что JavaScript компонентов выполняется параллельно в нескольких потоках.

В браузере React обычно кооперативно планирует JavaScript-работу на основном потоке и периодически возвращает управление среде выполнения.

Незавершённая render phase может быть прервана.

Commit выбранного дерева выполняется согласованно и не прерывается посередине. React не должен показать состояние, в котором применена только часть одного связанного commit.

Fiber является внутренней деталью реализации, а не публичным API.

На практике разработчику важно понимать следствия этой архитектуры:

- render может выполняться повторно;
- render может не завершиться commit;
- побочные эффекты нельзя выполнять внутри компонента;
- обновления могут иметь разные приоритеты;
- вызов компонента не означает изменение DOM;
- render, commit и browser paint нужно измерять отдельно.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем рендер React отличается от отрисовки браузером?</strong></summary>

<dl>
<dd>
<h2></h2>

Render React выполняется в JavaScript и вычисляет следующее описание интерфейса.

Commit React DOM применяет необходимые изменения к DOM.

После этого браузер выполняет собственную работу:

```text
React render
→ вычисление дерева

React commit
→ изменение DOM

Browser rendering
→ styles, layout, paint, compositing
```

Компонент может быть вызван во время render, но DOM и экран при этом не обязаны измениться.

Например, родитель может рендериться с новым объектом `props`, а дочерний компонент вернуть то же описание DOM. React вызовет компонент, но во время commit не найдёт необходимых изменений.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему рендер должен быть чистым?</strong></summary>

<dl>
<dd>
<h2></h2>

React вправе:

- вызвать компонент несколько раз;
- приостановить render;
- начать его заново;
- отбросить результат до commit.

Побочный эффект внутри render тогда может:

- выполниться несколько раз;
- выполниться для устаревшего состояния;
- выполниться для интерфейса, который пользователь никогда не увидит.

Неправильно:

```tsx
function Profile({
  user,
}: {
  user: User;
}) {
  analytics.track(
    "profile_rendered",
  );

  return <h1>{user.name}</h1>;
}
```

Для действия пользователя используют event handler:

```tsx
function SaveButton() {
  function handleClick() {
    analytics.track(
      "profile_saved",
    );
  }

  return (
    <button onClick={handleClick}>
      Сохранить
    </button>
  );
}
```

Для синхронизации с внешней системой используют Effect:

```tsx
useEffect(() => {
  const connection =
    connect(roomId);

  return () => {
    connection.disconnect();
  };
}, [roomId]);
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли любой рендер быть прерван?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Fiber предоставляет React возможность разделять render на единицы работы, но конкретное обновление не обязано быть прерванным.

Срочные обновления, связанные с непосредственным вводом пользователя, React может обработать синхронно:

```tsx
setInputValue(nextValue);
```

Менее срочную работу можно отметить через transition:

```tsx
startTransition(() => {
  setFilteredItems(nextItems);
});
```

Такая работа может быть:

- приостановлена;
- продолжена позднее;
- перезапущена;
- отброшена после более нового обновления.

Прерываемость зависит от типа и приоритета обновления, текущей работы и возможностей React.

Код render должен оставаться чистым независимо от того, будет конкретное обновление прервано или нет.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означают current tree и work-in-progress tree?</strong></summary>

<dl>
<dd>
<h2></h2>

Current tree — текущее дерево последнего успешно применённого интерфейса.

Оно соответствует тому состоянию React-приложения, которое сейчас считается committed.

Во время render React подготавливает work-in-progress tree с новыми:

- `props`;
- состоянием;
- дочерними узлами;
- флагами изменений.

```text
current tree
→ уже применён к DOM

work-in-progress tree
→ возможное следующее состояние
```

После успешного commit рабочее дерево становится текущим.

Если render устарел или был отброшен, work-in-progress не применяется, а пользователь продолжает видеть прежнее current tree.

Current и work-in-progress Fiber-узлы могут переиспользоваться и связываться через внутреннее поле `alternate`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Fiber является Virtual DOM?</strong></summary>

<dl>
<dd>
<h2></h2>

Не полностью.

Virtual DOM — общее упрощённое название подхода, при котором описания интерфейса хранятся в памяти и сопоставляются между обновлениями.

React elements описывают желаемый интерфейс:

```tsx
<Button label="Сохранить" />
```

Fiber является внутренней структурой React, которая дополнительно хранит:

- связи дерева;
- состояние;
- очередь обновлений;
- сведения о работе;
- приоритеты;
- подготовленные изменения.

Упрощённо:

```text
React elements
→ описание желаемого UI

Fiber tree
→ внутренняя структура reconciliation и планирования

DOM
→ применённый результат React DOM
```

Fiber участвует в реализации подхода, который часто называют Virtual DOM, но эти понятия не являются синонимами.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему Strict Mode может вызвать компонент дважды в режиме разработки?</strong></summary>

<dl>
<dd>
<h2></h2>

Strict Mode включает дополнительные development-проверки.

React может:

- повторно вызвать функцию компонента;
- повторно вызвать функции, которые должны быть чистыми;
- выполнить дополнительный цикл setup и cleanup эффектов;
- повторно вызвать callback refs с очисткой.

Это помогает обнаружить:

- мутацию входных данных;
- побочный эффект внутри render;
- отсутствующую очистку Effect;
- отсутствующую очистку callback ref.

Поэтому:

```tsx
console.log("render");
```

может появиться дважды в development.

Эти проверки не выполняются таким же образом в production.

Повторный вызов функции компонента также не означает, что React обязательно дважды применил одно и то же изменение к DOM.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```tsx
function Profile({ user }) {
  console.log("render");
  return <h1>{user.name}</h1>;
}
```

<details>
<summary><strong>Доказывает ли этот лог, что React изменил DOM?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Лог доказывает только, что React вызвал функцию компонента во время render phase.

После этого React может:

- получить то же описание интерфейса;
- не найти изменений DOM;
- отбросить незавершённый конкурентный render;
- повторно вызвать компонент в Strict Mode.

Фактическое изменение DOM происходит только во время commit phase и только при наличии подготовленных изменений.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Почему важна модель |
| --- | --- |
| Побочный эффект внутри компонента | Может выполниться повторно или для отброшенного render |
| Медленное взаимодействие | Нужно отделить стоимость render React от DOM mutations и browser paint |
| `useLayoutEffect` | Выполняется после изменения DOM до следующего paint и может задержать его |
| `useEffect` | Запускается после commit, но не даёт строгой гарантии порядка относительно paint |
| Transition и Suspense | Используют приоритеты и возможность перезапускать render |
| Strict Mode | Помогает обнаружить нечистые вычисления и неправильную очистку |
