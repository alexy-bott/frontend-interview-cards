## Вопрос

Что такое React Compiler? Как он работает и заменяет ли ручные `useMemo`, `useCallback` и `memo`?

<details>
<summary><strong>Показать ответ</strong></summary>

React Compiler является инструментом этапа сборки, который анализирует компоненты и хуки и автоматически добавляет мемоизацию там, где может доказать её безопасность. Он преобразует исходный код до выполнения приложения и не является браузерным API или хуком. Стабильный React Compiler 1.0 выпущен 7 октября 2025 года.

Compiler получает AST, то есть абстрактное синтаксическое дерево JavaScript или TypeScript, преобразует его во внутреннее представление и анализирует поток данных и мутации. На основании этого он может сохранить вычисленное значение или JSX до изменения фактических зависимостей. Анализ точнее вручную заданного массива зависимостей и способен мемоизировать условные вычисления, но полагается на правила React.

```tsx
function ProductList({ products, filter }) {
  const visible = products.filter((product) => product.type === filter);
  return <List items={visible} />;
}
```

Без Compiler родительский рендер снова запускает фильтрацию и создаёт новый массив. Compiler может определить, что результат зависит от `products` и `filter`, и переиспользовать его при неизменных входных данных. Аналогично он способен пропускать часть повторной работы компонента без ручного `memo`.

Compiler уменьшает потребность в `useMemo`, `useCallback` и `memo`, но не превращает их в ошибки. Существующий код с обоснованной ручной мемоизацией поддерживается, а правило линтера `preserve-manual-memoization` помогает не сломать её случайно. Новый ручной кеш добавляют только для конкретного контракта или после измерения участка, который Compiler не оптимизировал.

`useMemo` и `useCallback` сами являются оптимизациями, а не гарантией вечной ссылки. Если внешнему императивному API требуется долгоживущий объект, обычно нужен `ref` или состояние. Compiler также не создаёт общий кеш данных между компонентами, не виртуализирует список, не уменьшает объём сетевых данных и не переносит тяжёлую функцию в Web Worker.

Компоненты и хуки должны быть чистыми: нельзя мутировать `props`, выполнять побочные эффекты во время рендера, читать `ref` как реактивное состояние или нарушать порядок хуков. Compiler выполняет несколько этапов проверки, а диагностика выводится через `eslint-plugin-react-hooks`. Код, который нельзя безопасно скомпилировать, может быть пропущен, но ошибку линтера всё равно нужно разобрать как потенциальный дефект, а не считать обычным состоянием.

Compiler 1.0 напрямую совместим с React 19. Для React 17/18 указывают минимальный `target` и добавляют `react-compiler-runtime`. Плагин фиксируют точной версией, потому что изменение стратегии мемоизации между версиями может проявить скрытый эффект, зависящий от стабильности ссылки.

Типичный процесс внедрения:

1. Обновить `eslint-plugin-react-hooks` и исправить нарушения правил React.
2. Добавить `babel-plugin-react-compiler` или официальную интеграцию фреймворка или Vite.
3. Начать с части приложения либо режима компиляции, подходящего кодовой базе.
4. Запустить модульные, интеграционные и end-to-end тесты.
5. Сравнить production-профили, отзывчивость интерфейса и потребление памяти.
6. Обновлять Compiler отдельно и осознанно.

Директива `"use no memo"` временно исключает компонент или хук из компиляции и помогает локализовать несовместимость. `"use memo"` принудительно запрашивает компиляцию и особенно полезна в режиме явных аннотаций, где код компилируется только по отметке. В обычном режиме не следует расставлять `"use memo"` во всех файлах.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Что означает «инструмент этапа сборки»?</summary>

Compiler работает во время сборки до запуска кода пользователем. Он читает исходники и генерирует оптимизированный JavaScript, который попадает в бандл. Компонент не импортирует и не вызывает Compiler во время рендера.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему Compiler зависит от Rules of React?</summary>

Мемоизация безопасна только для чистого вычисления. Если рендер мутирует внешний объект или зависит от скрытого изменяемого значения, повторное использование результата изменит поведение. Правила React делают зависимости вычисления анализируемыми и предсказуемыми.

</details>

<details>
<summary><strong>Вопрос:</strong> Удаляет ли Compiler необходимость в <code>memo</code> и <code>useCallback</code>?</summary>

Во многих компонентах он даёт тот же эффект автоматически, поэтому новый повторяющийся код ручной мемоизации часто не нужен. Но часть проекта может не компилироваться, а внешний API или библиотека может иметь контракт по ссылке. Решение принимают по результату Compiler и профилировщику, а не по универсальному запрету.

</details>

<details>
<summary><strong>Вопрос:</strong> Оптимизирует ли Compiler любую тяжёлую функцию?</summary>

Он оптимизирует вычисления в React-компонентах и хуках. Он не создаёт глобальный кеш для вызовов вне React и не ускоряет сам алгоритм при новых входных данных. Тяжёлому поиску всё равно может потребоваться другой алгоритм или Web Worker.

</details>

<details>
<summary><strong>Вопрос:</strong> Что означают <code>"use memo"</code> и <code>"use no memo"</code>?</summary>

Это директивы Compiler на уровне функции или файла. `"use no memo"` временно запрещает компиляцию области. `"use memo"` требует попытаться её скомпилировать и используется для внедрения по явной отметке. Это не директивы среды выполнения React и не аналоги хука `useMemo`.

</details>

<details>
<summary><strong>Вопрос:</strong> Как подключить Compiler в Vite или Next.js?</summary>

В Vite его подключают через конфигурацию Babel в React-плагине либо через соответствующую интеграцию, устанавливая `babel-plugin-react-compiler` точной версией. В Next.js используют поддерживаемую настройку конкретной версии фреймворка, которая включает Compiler в процесс сборки. Перед копированием конфигурации нужно сверить документацию версий Vite или Next.js, потому что интеграция менялась по мере стабилизации.

</details>

<details>
<summary><strong>Вопрос:</strong> Как безопасно внедрить Compiler в существующий проект?</summary>

Сначала включают актуальные правила линтера и исправляют нечистые компоненты, затем компилируют ограниченную область. Нужны тесты взаимодействий и профили production-сборки, особенно для эффектов, зависящих от ссылок. Версию Compiler фиксируют точно и обновляют отдельным изменением.

</details>

## Где это встречается во frontend

| Ситуация | Роль Compiler |
| --- | --- |
| Много ручных `useCallback` | Может автоматически сохранить ссылки и убрать повторяющийся код |
| Дорогой повторный рендер с теми же входами | Мемоизирует вычисления и JSX |
| Нарушение чистоты рендера | Диагностика линтера указывает потенциальную ошибку |
| Проект на React 17/18 | Нужны `target` и `react-compiler-runtime` |
| Большая существующая кодовая база | Постепенное включение и точная версия |
| Медленный первоначальный бандл | Нужны разделение кода и анализ зависимостей, а не Compiler |
