## Вопрос

<br>

 💬 **Как диагностировать и исправлять проблемы производительности React-приложения?**

<h2></h2>

<br>
<dl>
<dd>

Оптимизацию начинают с наблюдаемого пользовательского симптома и измерения, а не с добавления `useMemo`.

Медленной может быть:

- сеть;
- серверный ответ;
- загрузка и выполнение JavaScript;
- рендер React;
- применение изменений к DOM;
- выполнение эффектов;
- расчёт стилей и layout;
- paint и composite;
- длинная задача JavaScript;
- работа с памятью.

Инструмент и исправление зависят от слоя проблемы.

Практический порядок:

1. Определить пользовательский симптом: медленная загрузка, задержка ввода, рывок прокрутки, медленная навигация или постепенное ухудшение работы.
2. Посмотреть field data, то есть данные реальных пользователей: RUM, CrUX, PageSpeed Insights или собственную аналитику.
3. Определить проблемную метрику, страницу, устройство, взаимодействие и сегмент пользователей.
4. Воспроизвести тот же сценарий в production-сборке на реалистичном устройстве, соединении и объёме данных.
5. Проверить Network и записать профиль во вкладке Performance браузера.
6. Найти длинные задачи, выполнение JavaScript, React-работу, пересчёт стилей, layout, paint, загрузку или сборку мусора.
7. Если основное время находится в React, записать React DevTools Profiler или React Performance Tracks.
8. Изменить одну причину, повторить тот же сценарий и сравнить выбранную метрику до и после.

Core Web Vitals описывают разные части пользовательского опыта:

| Метрика | Что измеряет |
| --- | --- |
| LCP | Скорость появления основного крупного содержимого |
| INP | Отзывчивость страницы на взаимодействия |
| CLS | Визуальную стабильность и неожиданные сдвиги |

Core Web Vitals прежде всего являются field-метриками.

Для оценки страницы или сайта обычно используют 75-й перцентиль реальных посещений, отдельно учитывая хотя бы мобильные и desktop-устройства.

Например:

```text
INP p75 = 180 мс
```

означает, что не менее 75% измеренных посещений получили INP не хуже 180 мс.

Локальный lab-тест не заменяет field data.

Он выполняется:

- на одном устройстве;
- с одним сетевым профилем;
- в одном месте;
- по заранее выбранному сценарию.

Field data показывает, что испытывают реальные пользователи, а lab-профиль помогает воспроизвести проблему и найти техническую причину.

Особенно важно это для INP: результат зависит от того, с какими элементами пользователи действительно взаимодействуют и в какой момент.

Вкладка Network помогает проверить:

- длительность запросов;
- серверное время ответа;
- каскадную загрузку;
- блокирующие ресурсы;
- размер ответов;
- кеширование;
- повторные запросы;
- загрузку JavaScript;
- изображения и шрифты.

Вкладка Performance показывает общую временную шкалу браузера:

- network;
- события ввода;
- выполнение JavaScript;
- React Performance Tracks;
- style recalculation;
- layout;
- paint;
- composite;
- garbage collection.

Long task, то есть длинная задача, — непрерывная задача на главном потоке длительностью 50 мс или дольше.

Пока она выполняется, браузер не может начать обработку другой задачи на этом потоке. Если пользователь взаимодействует со страницей в это время, ввод ждёт завершения текущей задачи.

Chrome DevTools отмечает long task красным треугольником, а часть после первых 50 мс показывает как blocking time.

React DevTools Profiler группирует React-работу по commits и показывает:

- какие компоненты участвовали в рендере;
- сколько времени занял их рендер;
- mount это или update;
- какие части дерева оказались дорогими;
- причины обновления, если включена их запись.

Commit в Profiler — группа React-изменений, применённых вместе.

Длительность компонента в flamegraph прежде всего относится к его рендеру и рендеру дочернего дерева, а не ко всей стоимости отображения результата браузером.

React Profiler не показывает напрямую:

- загрузку сети;
- полный серверный ответ;
- стоимость CSS;
- layout;
- paint;
- composite;
- всю работу стороннего JavaScript.

Поэтому React flamegraph сопоставляют с общей временной шкалой Chrome Performance.

Например:

```text
React render: 4 мс
Layout: 80 мс
Paint: 20 мс
```

В этом случае добавление `memo` почти не поможет. Основная проблема находится в DOM, CSS или принудительном layout.

Профилирование добавляет накладные расходы.

Development-профиль может дополнительно искажаться:

- `StrictMode`;
- development-проверками;
- отсутствием production-оптимизаций;
- подробной диагностикой компонентов.

Обычная production-сборка React не содержит полную profiling-инструментацию.

Для измерения React в условиях, близких к production, используют специальную profiling-сборку, например через:

```text
react-dom/profiling
```

и повторно проверяют пользовательский сценарий.

React 19.2 добавил React Performance Tracks, которые отображаются внутри общей временной шкалы Performance DevTools.

Scheduler track содержит четыре уровня работы:

| Поддорожка | Работа |
| --- | --- |
| Blocking | Синхронные и срочные обновления, часто связанные с пользовательским вводом |
| Transition | Несрочные обновления, обычно созданные через transition |
| Suspense | Показ fallback и раскрытие Suspense boundaries |
| Idle | Работа с самым низким приоритетом |

Для обновления Scheduler может показать этапы:

```text
Update
→ Render
→ Commit
→ Remaining Effects
```

`Update` показывает причину постановки обновления.

`Render` показывает вычисление следующего React-дерева.

`Commit` включает применение React-изменений к DOM и выполнение layout effects.

`Remaining Effects` включает пассивные эффекты, например `useEffect`. Обычно они выполняются после paint, но при некоторых дискретных пользовательских событиях могут выполняться раньше.

Components track показывает:

- длительность рендера компонентов и их потомков;
- длительность эффектов;
- mount и unmount;
- reconnect и disconnect для `<Activity>`;
- изменившиеся props в development;
- блокировку React-работы из-за передачи управления другой работе.

React Performance Tracks доступны не в обычной production-сборке, а в:

- development-сборке;
- специальной profiling-сборке.

В development Components track включает все компоненты.

В profiling-сборке Scheduler включён по умолчанию, а Components track показывает деревья под `<Profiler>`. При установленном React DevTools он может включать все компоненты.

Server Requests и Server Components tracks доступны только в development-сборке.

Типовые причины и решения:

| Причина | Возможное решение |
| --- | --- |
| Состояние расположено слишком высоко | Перенести состояние ближе к потребителю, разделить компоненты |
| `value` Context меняется по ссылке без изменения данных | Стабилизировать объект или функцию, разделить Context |
| Часто меняется только часть большого Context | Разделить Context по причинам изменения или использовать хранилище с селекторами |
| Дорогое вычисление повторяется с теми же входами | React Compiler или точечный `useMemo` |
| Тяжёлый ребёнок повторно рендерится с прежними props | React Compiler или `memo` после профилирования |
| Тысячи DOM-строк | Виртуализация, пагинация и уменьшение DOM |
| Ввод конкурирует с рендером списка | `useDeferredValue` или transition |
| Длинная непрерывная задача на CPU | Другой алгоритм, дробление или Web Worker |
| Большой первоначальный JavaScript | Разделение по маршрутам, `lazy`, tree shaking и анализ бандла |
| Последовательные независимые запросы | Параллельная загрузка, preload и устранение waterfall |
| Повторяются одинаковые запросы | Кеширование или дедупликация на подходящем уровне |
| Растёт память | Cleanup, Heap Snapshot и поиск удерживаемых объектов |

Состояние стараются располагать настолько близко к потребителям, насколько позволяет архитектура.

Например, если состояние открытия tooltip хранится в корне страницы:

```text
Page state changes
→ повторно рассматривается большое дочернее дерево
```

его перенос в сам tooltip уменьшает область обновления:

```text
Tooltip state changes
→ обновляется локальная интерактивная область
```

Это не означает, что любое состояние нужно опускать вниз. Общее состояние должно оставаться у ближайшего общего владельца данных.

Context обновляет компоненты, которые читают конкретный Context, когда значение ближайшего Provider изменилось по сравнению с предыдущим через `Object.is`.

Например:

```tsx
<AuthContext
  value={{
    currentUser,
    login,
  }}
>
  {children}
</AuthContext>
```

создаёт новый объект на каждом рендере Provider.

Даже если `currentUser` и `login` фактически не изменились, новое значение отличается по ссылке.

В зависимости от архитектуры можно:

- не создавать новый объект без необходимости;
- стабилизировать его с помощью Compiler или ручной мемоизации;
- разделить данные и действия по разным Context;
- разделить часто и редко меняющиеся значения;
- использовать внешнее хранилище с подписками по селектору.

`memo` не останавливает обновление Context, который непосредственно читает компонент. `memo` сравнивает props, но используемый Context является отдельным источником обновления.

Виртуализация рендерит видимую часть списка и небольшой запас элементов за границами viewport вместо тысяч строк одновременно.

Она уменьшает:

- количество React-компонентов;
- число DOM-узлов;
- время commit;
- стоимость layout и paint;
- потребление памяти.

Мемоизация строк не заменяет виртуализацию, если тысячи строк всё равно находятся в DOM.

Виртуализация добавляет отдельные требования:

- фиксированная или измеряемая высота элементов;
- восстановление scroll position;
- корректная клавиатурная навигация;
- управление focus;
- доступность;
- поиск элемента, который ещё не находится в DOM;
- динамическое изменение размеров.

Поэтому сложную виртуализацию обычно реализуют через проверенную библиотеку.

`useDeferredValue` и transitions меняют приоритет React-обновления, но не делают саму работу быстрее.

Например:

```tsx
const deferredQuery =
  useDeferredValue(query);
```

позволяет сначала обновить поле ввода, а список отрендерить с меньшим приоритетом.

Но если рендер списка занимает 200 мс, его вычислительная стоимость остаётся примерно той же. React только получает возможность отложить и при необходимости перезапустить эту работу.

Чтобы отложенное значение помогло пропустить работу дочернего компонента при срочном рендере, дочерняя часть должна поддерживать пропуск повторного рендера, например через React Compiler или `memo`.

Transitions также:

- не уменьшают сетевой запрос;
- не исправляют медленный алгоритм;
- не уменьшают DOM;
- не прерывают произвольную синхронную функцию посередине её выполнения.

React может прерывать собственную конкурентную работу между доступными точками планирования, но не может остановить уже выполняющийся синхронный цикл:

```ts
for (let index = 0; index < 10_000_000; index += 1) {
  // Долгое непрерывное вычисление
}
```

Для такой задачи могут потребоваться:

- более быстрый алгоритм;
- индексация данных;
- разделение на небольшие задачи;
- Web Worker;
- перенос вычисления на сервер.

React Compiler уменьшает повторные вычисления и повторные рендеры с теми же входными данными.

Он не уменьшает:

- первоначальный JavaScript-бандл;
- количество уже созданных DOM-узлов;
- стоимость CSS layout;
- сетевой ответ;
- сложность нового вычисления при новых входных данных.

Цепочки:

```text
effect
→ setState
→ render
→ effect
→ setState
→ render
```

часто создают лишние commits.

Например, вычисляемые данные не нужно без необходимости синхронизировать через effect:

```tsx
const [fullName, setFullName] =
  useState("");

useEffect(() => {
  setFullName(`${firstName} ${lastName}`);
}, [firstName, lastName]);
```

Их можно вычислить во время рендера:

```tsx
const fullName =
  `${firstName} ${lastName}`;
```

React Performance Tracks также может показать cascading update — обновление, поставленное во время уже выполняющегося React-прохода. Такое обновление способно заставить React выполнить дополнительную работу или начать новый проход.

Постепенное ухудшение приложения может быть связано не с отдельным медленным рендером, а с памятью.

Проверяют cleanup для:

- `setInterval` и `setTimeout`;
- DOM-событий;
- `IntersectionObserver`;
- `ResizeObserver`;
- `MutationObserver`;
- WebSocket;
- подписок внешнего хранилища;
- сторонних виджетов;
- созданных вручную DOM-узлов.

Нужно различать:

| Проблема | Проявление |
| --- | --- |
| Memory leak | Использование памяти постепенно растёт и не возвращается |
| Memory bloat | Страница постоянно удерживает больше памяти, чем требуется |
| Частый garbage collection | Интерфейс периодически приостанавливается из-за очистки памяти |

Для диагностики используют:

- Chrome Task Manager;
- Memory timeline;
- Heap Snapshot;
- Allocation Timeline;
- поиск detached DOM trees;
- сравнение снимков до и после повторения сценария.

## Дополнительные вопросы

<details>
<summary><strong>Что показывает React DevTools Profiler?</strong></summary>

<dl>
<dd>
<h2></h2>

React DevTools Profiler группирует React-работу по commits и показывает:

- компоненты, участвовавшие в рендере;
- длительность их рендера;
- mount или update;
- дорогие поддеревья;
- причины обновления, если включена соответствующая запись.

Profiler измеряет React-часть работы.

Он не показывает полностью:

- сеть;
- серверную обработку;
- JavaScript вне React;
- layout;
- paint;
- composite;
- потребление памяти.

Development-профиль может искажаться `StrictMode` и дополнительными проверками React.

Обычная production-сборка не включает profiling-инструментацию. Для более реалистичного измерения React используют специальную production-сборку с profiling и сравнивают её с общей записью Chrome Performance.

Сама profiling-инструментация добавляет накладные расходы, поэтому абсолютные значения интерпретируют осторожно. Важнее сравнивать один и тот же сценарий до и после изменения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем длительность рендера отличается от длительности commit?</strong></summary>

<dl>
<dd>
<h2></h2>

Render phase — React вызывает компоненты и вычисляет следующее дерево:

```text
props + state + context
→ JSX
→ определение необходимых изменений
```

Эта фаза не обязана сразу изменять DOM и при конкурентном рендеринге может быть прервана или перезапущена.

Commit phase применяет подготовленные изменения:

- изменяет DOM;
- обновляет `ref`;
- выполняет layout effects;
- запускает связанный жизненный цикл commit.

После commit браузер отдельно может выполнить:

```text
style recalculation
→ layout
→ paint
→ composite
```

Длительности компонентов в React Profiler прежде всего показывают стоимость render phase.

React Performance Tracks позволяют отдельно увидеть render, commit и effects, а Chrome Performance показывает следующую браузерную работу.

Оптимизация рендера не поможет, если основное время уходит на layout или paint большого DOM.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>useMemo</code> не уменьшает размер бандла?</strong></summary>

<dl>
<dd>
<h2></h2>

`useMemo` кеширует результат вычисления во время выполнения уже загруженного компонента:

```tsx
const visibleItems = useMemo(
  () => filterItems(items),
  [items],
);
```

Код самого компонента и `filterItems` всё равно:

- скачивается;
- разбирается браузером;
- компилируется JavaScript-движком;
- находится в памяти.

Поэтому объём первоначального JavaScript не уменьшается.

Для уменьшения бандла нужны:

- анализ импортов;
- tree shaking;
- route-level code splitting;
- `lazy`;
- динамический import;
- удаление или замена тяжёлой зависимости;
- разделение Client и Server Components во фреймворке.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое виртуализация списка?</strong></summary>

<dl>
<dd>
<h2></h2>

Виртуализация хранит в DOM только видимые строки и небольшой запас вокруг области просмотра.

Например, список содержит:

```text
100 000 элементов
```

но в DOM одновременно находятся:

```text
30–60 строк
```

Контейнер или вспомогательные элементы имитируют полный размер списка, поэтому scrollbar соответствует всей коллекции.

Это уменьшает:

- число компонентов;
- число DOM-узлов;
- стоимость рендера;
- layout и paint;
- память.

Реализацию обычно доверяют библиотеке, потому что сложность создают:

- переменная высота строк;
- изменение размеров;
- сохранение scroll position;
- клавиатурная навигация;
- focus;
- доступность;
- переход к произвольному элементу.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему Context может создавать широкие обновления?</strong></summary>

<dl>
<dd>
<h2></h2>

React сравнивает предыдущее и новое значение Provider через `Object.is`.

Если Provider получает новый объект:

```tsx
<AppContext
  value={{
    user,
    permissions,
    setUser,
  }}
>
  {children}
</AppContext>
```

он отличается по ссылке при каждом создании.

Компоненты, читающие этот Context, получают обновление. `memo` не блокирует изменение Context, который использует компонент.

Если одно поле Context меняется часто, оно может затрагивать потребителей, которым логически требуется только другое поле.

Возможные решения:

- не создавать новое `value` без необходимости;
- использовать React Compiler или точечную мемоизацию объекта;
- разделить Context по причинам изменения;
- отделить данные от действий;
- использовать внешнее хранилище с подписками через селекторы.

Разделение Context полезно не потому, что объект большой, а потому, что его части имеют разные потребители и разную частоту изменения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое длинная задача и почему она мешает React?</strong></summary>

<dl>
<dd>
<h2></h2>

Long task — непрерывная задача на главном потоке длительностью 50 мс или дольше.

Пока она выполняется, главный поток не может начать:

- обработку следующего события;
- выполнение другой JavaScript-задачи;
- подготовку следующего кадра;
- часть браузерной отрисовки.

Если пользователь нажал кнопку во время long task, обработчик ждёт освобождения потока. Это увеличивает задержку взаимодействия и может ухудшить INP.

Возможные решения:

- удалить лишнюю работу;
- улучшить алгоритм;
- разделить работу на небольшие задачи;
- выполнять часть работы во время idle;
- перенести CPU-вычисление в Web Worker.

`useTransition` не может прервать произвольную синхронную функцию, которая уже выполняется внутри одной JavaScript-задачи.

Он меняет приоритет React-обновления, а не превращает любой JavaScript в прерываемую работу.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить, что оптимизация помогла?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно повторить тот же сценарий:

- на том же устройстве;
- с тем же CPU throttling;
- с тем же сетевым профилем;
- с теми же данными;
- в той же сборке;
- с одинаковой последовательностью действий.

До изменения выбирают конкретную метрику:

- LCP;
- INP;
- длительность выбранного взаимодействия;
- render duration;
- commit;
- long-task blocking time;
- количество DOM-узлов;
- размер JavaScript;
- использование памяти.

Затем выполняют несколько измерений до и после, потому что один профиль может зависеть от случайных фоновых процессов, кеша и прогрева JavaScript.

Важно проверить:

- медианное или типичное значение;
- медленные сценарии;
- field data после deployment;
- память;
- отсутствие функциональной регрессии.

Уменьшение числа `console.log` о рендере само по себе не является пользовательской метрикой.

Компонент может рендериться чаще, но оставаться быстрым. И наоборот, один редкий рендер может заблокировать интерфейс на сотни миллисекунд.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```tsx
function Page({ items }) {
  const [query, setQuery] = useState("");
  const visibleItems = items.filter((item) => item.name.includes(query));

  return (
    <>
      <input value={query} onChange={(event) => setQuery(event.target.value)} />
      <BigList items={visibleItems} />
    </>
  );
}
```

<details>
<summary><strong>Что нужно измерить и какие решения возможны?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала нужно измерить:

- размер `items`;
- длительность `filter`;
- рендер `BigList`;
- количество DOM-строк;
- layout и paint;
- задержку поля ввода;
- частоту изменения `items`;
- необходимость показывать результат после каждого символа.

Если `Page` повторно рендерится с теми же `items` и `query`, Compiler или `useMemo` могут не выполнять фильтрацию снова:

```tsx
const visibleItems = useMemo(
  () =>
    items.filter(
      (item) =>
        item.name.includes(query),
    ),
  [items, query],
);
```

Но при вводе каждый новый символ изменяет `query`.

Следовательно:

```text
query изменился
→ зависимости изменились
→ filter всё равно выполняется
```

В таком сценарии `useMemo` не устраняет стоимость новой фильтрации на каждом символе.

Если фильтрация сама по себе медленная при каждом новом запросе, возможны:

- более эффективный поиск;
- предварительная нормализация данных;
- индекс;
- поиск на сервере;
- Web Worker для тяжёлого CPU-вычисления;
- уменьшение объёма входных данных.

Если фильтрация быстрая, но `BigList` долго рендерится, можно отложить список:

```tsx
function Page({ items }) {
  const [query, setQuery] =
    useState("");

  const deferredQuery =
    useDeferredValue(query);

  const visibleItems = items.filter(
    (item) =>
      item.name.includes(deferredQuery),
  );

  return (
    <>
      <input
        value={query}
        onChange={(event) =>
          setQuery(event.target.value)
        }
      />

      <BigList
        items={visibleItems}
      />
    </>
  );
}
```

Поле обновляется по актуальному `query`, а список может временно показывать результат для `deferredQuery`.

`useDeferredValue` не делает `filter` или `BigList` быстрее. Он позволяет React обрабатывать рендер списка с меньшим приоритетом.

Если проблема в тысячах DOM-строк, нужна виртуализация. `useMemo`, `memo` и deferred value не уменьшают уже созданный DOM.

Если поиск выполняется на сервере, отдельно рассматривают:

- debounce;
- отмену устаревшего запроса;
- защиту от race condition;
- кеш;
- pagination;
- серверную индексацию.

Debounce не нужен автоматически для локальной фильтрации. Он добавляет задержку и оправдан только при конкретной дорогой операции, которую не нужно запускать на каждый символ.

<h2></h2>
</dd>
</dl>

</details>
