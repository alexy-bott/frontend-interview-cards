#### Вопрос

Чем отличаются `props` и `state` в React? Что означает однонаправленный поток данных?

#### Ответ

`Props` являются входными данными компонента, которые передаёт родитель. `State` является памятью компонента, которую React хранит между рендерами. И `props`, и `state` нужно считать неизменяемыми снимками данных текущего рендера: их нельзя мутировать напрямую.

Компонент читает `props`, но не меняет полученный объект. Если дочерний компонент должен повлиять на данные родителя, родитель передаёт функцию обратного вызова, например `onChange`. Ребёнок сообщает о событии вызовом этой функции, а владелец данных решает, как изменить состояние. Это и есть однонаправленный поток: значение идёт сверху вниз, а намерение изменить его сообщается вверх через функцию.

Состояние обновляют setter-функцией из `useState`, отправкой действия в reducer или через API внешнего хранилища. Вызов setter не меняет переменную внутри уже выполняющегося обработчика: каждое выполнение компонента видит собственный снимок состояния. React ставит обновление в очередь и использует новое значение в следующем рендере.

Состояние должно содержать минимальный набор данных, необходимый для восстановления интерфейса. Значение, которое можно надёжно вычислить из `props` и `state` во время рендера, обычно не хранят отдельно. Например, `filteredItems` вычисляют из `items` и `query`. Дублирование создаёт два источника истины и требует дополнительной синхронизации.

Место хранения выбирают по владельцу данных:

| Данные нужны | Где обычно хранить |
| --- | --- |
| Одному компоненту | Локальное состояние |
| Нескольким соседним компонентам | В ближайшем общем родителе |
| Глубокому поддереву | В родителе и передавать через Context |
| Многим независимым частям приложения | Во внешнем хранилище, если локальной композиции недостаточно |
| Приходят с сервера | В кеше серверного состояния, например RTK Query |
| Должны восстанавливаться по ссылке | В URL |

Перенос состояния к ближайшему общему родителю называют lifting state up, или подъёмом состояния. Родитель становится единым источником истины, а дочерние компоненты получают согласованные значения. Поднимать всё состояние к корню не нужно: это увеличивает область повторных рендеров и связывает независимые части интерфейса.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Что означает «компонент владеет состоянием»?
>
> **Ответ:** Компонент определяет источник текущего значения и правила его изменения. Другие компоненты могут читать значение через `props` и отправлять намерения через функции обратного вызова, но не меняют источник истины напрямую. Владелец также решает, когда сбрасывать, сохранять или передавать состояние дальше.

> [!followup]
> **Вопрос:** Почему props нельзя изменять?
>
> **Ответ:** `Props` принадлежат конкретному рендеру родителя и используются как входной снимок данных. Мутация создаёт скрытое изменение, о котором React не знает, и нарушает предсказуемость компонентов. Для нового результата родитель обновляет собственное состояние и передаёт новый объект `props`.

> [!followup]
> **Вопрос:** Почему вычисляемое значение не стоит дублировать в состоянии?
>
> **Ответ:** Копия может перестать соответствовать исходным `items` или `query`, и тогда понадобится дополнительная синхронизация. Если вычисление дешёвое, результат получают прямо во время рендера. Если оно действительно дорогое и измерения это подтверждают, можно отдельно рассмотреть мемоизацию, но не второй источник истины.

> [!followup]
> **Вопрос:** Что такое lifting state up?
>
> **Ответ:** Это перенос состояния к ближайшему общему родителю компонентов, которым нужно согласованное значение. Родитель передаёт значение и функции изменения вниз через `props`. Например, фильтр и таблица могут получать `query` от общего контейнера, чтобы всегда показывать одно состояние поиска.

> [!followup]
> **Вопрос:** Нужно ли копировать prop в состояние?
>
> **Ответ:** Обычно нет. Инициализация `useState(prop)` использует prop только при первом монтировании и не синхронизирует последующие изменения. Копия оправдана, если компонент намеренно создаёт независимый черновик. Тогда контракт должен явно определять, когда черновик сбрасывается, например через смену `key` или отдельное действие.

#### Где это встречается во frontend

| Ситуация | Источник данных |
| --- | --- |
| Открыт ли локальный выпадающий список | Локальное состояние компонента |
| Значение общего фильтра | Родитель таблицы или URL |
| Черновик формы | Состояние формы, отдельно от исходного DTO |
| Тема приложения | Context или внешнее хранилище |
| Данные API | Кеш серверного состояния |
