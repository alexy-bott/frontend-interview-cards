## Вопрос

<br>

 💬 **Чем отличаются `props` и `state` в React? Что означает однонаправленный поток данных?**

<h2></h2>

<br>
<dl>
<dd>

`Props` — входные данные компонента, которые передаёт родитель.

Через `props` можно передавать:

- строки, числа и объекты;
- функции обратного вызова;
- React-элементы;
- `children`.

`State` — память компонента, которую React сохраняет между рендерами и связывает с позицией компонента в React-дереве.

И `props`, и `state` нужно считать неизменяемыми снимками данных конкретного рендера.

Компонент не должен:

- изменять полученный объект `props`;
- мутировать объект или массив внутри `state`;
- ожидать, что вызов setter сразу изменит значение в выполняющемся коде.

Для обновления объекта или массива состояния создают новое значение:

```tsx
setUser({
  ...user,
  name: "Анна",
});
```

Компонент читает `props`, но не изменяет данные родителя напрямую.

Если дочерний компонент должен повлиять на данные родителя, родитель передаёт ему функцию обратного вызова:

```tsx
type SearchInputProps = {
  value: string;
  onChange: (
    value: string,
  ) => void;
};

function SearchInput({
  value,
  onChange,
}: SearchInputProps) {
  return (
    <input
      value={value}
      onChange={(event) => {
        onChange(
          event.target.value,
        );
      }}
    />
  );
}
```

Родитель остаётся владельцем значения:

```tsx
function ProductsPage() {
  const [
    query,
    setQuery,
  ] = useState("");

  return (
    <SearchInput
      value={query}
      onChange={setQuery}
    />
  );
}
```

Однонаправленный поток данных означает:

```text
данные
→ передаются от родителя к ребёнку через props

намерение изменить данные
→ ребёнок сообщает вызовом callback

изменение источника истины
→ выполняет его владелец
```

Callback также передаётся сверху вниз через `props`. Данные не начинают автоматически двигаться в обратном направлении — дочерний компонент только сообщает владельцу о событии.

Состояние обновляют:

- setter-функцией из `useState`;
- отправкой действия через `dispatch` в reducer;
- публичным API внешнего хранилища.

Вызов setter не изменяет переменную внутри уже выполняющегося обработчика:

```tsx
function Counter() {
  const [
    count,
    setCount,
  ] = useState(0);

  function handleClick() {
    setCount(count + 1);

    console.log(count);
    // Остаётся значением
    // текущего рендера.
  }

  return (
    <button onClick={handleClick}>
      {count}
    </button>
  );
}
```

Каждое выполнение компонента и созданные в нём обработчики видят снимок состояния своего рендера.

Setter ставит обновление в очередь, после чего React использует новое значение в следующем рендере.

Если следующее состояние вычисляется из предыдущего, используют updater-функцию:

```tsx
setCount(
  previousCount =>
    previousCount + 1,
);
```

Она особенно важна, когда несколько обновлений одного значения ставятся в очередь:

```tsx
setCount(count => count + 1);
setCount(count => count + 1);
setCount(count => count + 1);
```

Состояние должно содержать минимальный набор данных, необходимый для восстановления интерфейса.

Следует избегать:

- противоречивых значений;
- дублирующихся данных;
- значений, которые можно вычислить;
- ненужной глубокой вложенности.

Значение, которое можно надёжно вычислить из `props` и `state` во время рендера, обычно не хранят отдельно.

Нежелательный вариант:

```tsx
const [
  filteredItems,
  setFilteredItems,
] = useState<Item[]>([]);
```

если `filteredItems` полностью определяется через:

```tsx
items
query
```

Вместо этого результат вычисляют во время рендера:

```tsx
const filteredItems =
  items.filter((item) =>
    item.name
      .toLowerCase()
      .includes(
        query.toLowerCase(),
      ),
  );
```

Отдельный `state` создал бы второй источник истины и потребовал бы синхронизировать его с `items` и `query`.

Место хранения состояния выбирают по владельцу данных:

| Данные нужны | Где обычно хранить |
| --- | --- |
| Одному компоненту | Локальное состояние |
| Нескольким соседним компонентам | В ближайшем общем родителе |
| Глубокому поддереву | У подходящего владельца и передавать через Context |
| Многим независимым частям приложения | Во внешнем хранилище, если локальной композиции и Context недостаточно |
| Приходят с сервера | В кеше серверного состояния, например RTK Query |
| Должны восстанавливаться по ссылке | В URL |

Context обычно не является отдельным хранилищем состояния.

Состояние по-прежнему принадлежит компоненту или внешнему store, а Context предоставляет способ передать значение глубоким потребителям без промежуточных `props`.

Перед Context стоит рассмотреть:

- обычную передачу `props`;
- передачу готового JSX через `children`;
- размещение состояния ближе к потребителям.

Перенос состояния к ближайшему общему родителю называют lifting state up, или подъёмом состояния.

Например, фильтр и таблица должны использовать одно значение поиска:

```text
ProductsPage
├── SearchInput
└── ProductsTable
```

Состояние `query` размещают в `ProductsPage`, а дочерние компоненты получают согласованные данные через `props`.

Родитель становится единым источником истины.

Поднимать всё состояние к корню приложения не нужно.

Это:

- расширяет область владения состоянием;
- связывает независимые части интерфейса;
- усложняет публичные контракты;
- может увеличить область компонентов, затрагиваемых обновлением.

Состояние размещают у ближайшего владельца, который должен координировать всех его потребителей.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что означает «компонент владеет состоянием»?</strong></summary>

<dl>
<dd>
<h2></h2>

Владелец определяет:

- источник текущего значения;
- правила его изменения;
- момент сброса;
- способ сохранения;
- компоненты, которым значение доступно.

Другие компоненты могут читать значение через `props` и сообщать о намерениях через callbacks, но не изменяют источник истины напрямую.

Например:

```tsx
function Parent() {
  const [
    value,
    setValue,
  ] = useState("");

  return (
    <Child
      value={value}
      onChange={setValue}
    />
  );
}
```

`Parent` владеет состоянием, а `Child` использует предоставленный контракт.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему props нельзя изменять?</strong></summary>

<dl>
<dd>
<h2></h2>

`Props` принадлежат конкретному рендеру родителя и являются входным снимком данных для дочернего компонента.

Мутация:

```tsx
props.user.name = "Анна";
```

создаёт скрытое изменение:

- React не получает запрос на новый рендер;
- объект может использоваться другими компонентами;
- результат начинает зависеть от порядка выполнения;
- нарушается предсказуемость компонентов.

Для нового результата владелец обновляет своё состояние и передаёт новый `props`:

```tsx
setUser({
  ...user,
  name: "Анна",
});
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему вычисляемое значение не стоит дублировать в состоянии?</strong></summary>

<dl>
<dd>
<h2></h2>

Копия может перестать соответствовать исходным данным.

Например, если одновременно хранить:

```tsx
items
query
filteredItems
```

то после изменения `items` или `query` придётся отдельно обновлять `filteredItems`.

Можно получить противоречивое состояние:

```text
query уже изменился
filteredItems ещё остался старым
```

Если результат можно вычислить во время рендера, его получают напрямую:

```tsx
const filteredItems =
  filterItems(
    items,
    query,
  );
```

Если вычисление действительно дорогое и измерения подтверждают проблему, можно отдельно рассмотреть мемоизацию.

Мемоизация оптимизирует вычисление, но не создаёт второй источник истины.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое lifting state up?</strong></summary>

<dl>
<dd>
<h2></h2>

Lifting state up — перенос состояния к ближайшему общему родителю компонентов, которым нужно согласованное значение.

Например:

```text
ProductsPage
├── SearchInput
└── ProductsTable
```

`SearchInput` изменяет поисковую строку, а `ProductsTable` использует её для отображения данных.

Состояние размещают в `ProductsPage`:

```tsx
function ProductsPage() {
  const [
    query,
    setQuery,
  ] = useState("");

  return (
    <>
      <SearchInput
        value={query}
        onChange={setQuery}
      />

      <ProductsTable
        query={query}
      />
    </>
  );
}
```

Так оба компонента используют один источник истины.

Состояние поднимают только до ближайшего владельца, которому действительно нужно координировать потребителей.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли копировать prop в состояние?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычно нет.

Код:

```tsx
const [
  name,
  setName,
] = useState(props.name);
```

использует `props.name` только при первоначальной инициализации данного состояния.

Если родитель позднее передаст другое значение, локальный `name` автоматически не обновится.

Копия оправдана, если компонент намеренно создаёт независимый черновик:

```text
исходные данные
→ принадлежат родителю

черновик редактирования
→ принадлежит форме
```

Тогда контракт должен явно определять, когда черновик:

- сохраняется;
- отменяется;
- сбрасывается;
- инициализируется для другой сущности.

Например, при смене редактируемого пользователя форму можно явно пересоздать:

```tsx
<ProfileForm
  key={user.id}
  user={user}
/>
```

Либо предоставить отдельное действие сброса.

Не следует копировать каждый prop в `state` только ради возможности читать и изменять его локально.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Источник данных |
| --- | --- |
| Открыт ли локальный выпадающий список | Локальное состояние компонента |
| Значение общего фильтра | Ближайший общий родитель или URL |
| Черновик формы | Состояние формы, отдельно от исходного DTO |
| Тема приложения | Состояние подходящего владельца, переданное через Context, или внешний store |
| Данные API | Кеш серверного состояния |
