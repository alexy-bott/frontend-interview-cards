## Вопрос

Почему React-компонент рендерится повторно? Что такое batching?

<details>
<summary><strong>Показать ответ</strong></summary>

Повторный рендер означает, что React снова вызывает компонент, чтобы вычислить следующее описание интерфейса. Основные причины: обновилось собственное состояние, родитель рендерится, изменилось значение прочитанного Context или внешнее хранилище уведомило React через подписку. Повторный вызов компонента не означает, что React обязательно изменит DOM.

`Props` сами по себе не являются отдельным источником события. Новые `props` появляются потому, что родитель уже начал рендер и создал дочерний React-элемент с новыми значениями. По умолчанию React продолжает рендер дочерних компонентов даже при равных `props`. `memo` может пропустить вызов ребёнка, если `props` равны по поверхностному сравнению и у самого ребёнка не изменились состояние или Context.

При обновлении состояния React сравнивает новое значение с предыдущим через `Object.is`. Если значение совпадает, React обычно пропускает обновление. Мутация объекта и передача той же ссылки поэтому не работает как корректное обновление: React не видит нового значения, а снимки данных предыдущих рендеров оказываются изменены задним числом.

Batching, или пакетная обработка, означает объединение нескольких обновлений состояния перед следующим рендером. React сначала выполняет обработчик, ставит обновления в очередь, а затем обрабатывает их вместе. Это уменьшает число промежуточных рендеров и не позволяет интерфейсу показать наполовину обновлённое состояние.

Начиная с React 18 при использовании `createRoot` автоматическая пакетная обработка распространяется не только на обработчики React, но и на обновления из Promise, таймеров и нативных обработчиков событий. React не объединяет независимые пользовательские события: второй клик обрабатывается с уже обновлённым интерфейсом. Граница `await` также разделяет выполнение, поэтому не стоит рассчитывать на один общий пакет через всю асинхронную функцию.

Состояние внутри текущего рендера является неизменяемым снимком. Три вызова `setCount(count + 1)` вычисляют одно и то же следующее значение из одного `count`. Когда новое значение зависит от предыдущего элемента очереди, используют функцию обновления: `setCount((previous) => previous + 1)`. React последовательно применит такие функции и получит увеличение на три.

`flushSync` может принудительно завершить ожидающие обновления синхронно, например перед вызовом стороннего DOM API, которому немедленно нужен обновлённый DOM. Это редкое средство обхода обычной модели React: оно нарушает пакетную обработку, может ухудшить производительность и преждевременно показать резервный интерфейс Suspense.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Если родитель рендерится, ребёнок всегда вызывается повторно?</summary>

По умолчанию React продолжает вычисление дочернего дерева и вызывает функцию ребёнка. DOM при этом может не измениться. Вызов можно пропустить с помощью `memo`, если `props` поверхностно равны, но собственное состояние ребёнка или прочитанный им Context всё равно способны запустить его рендер.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему три <code>setCount(count + 1)</code> обычно увеличивают значение только на один?</summary>

Все три выражения читают `count` из одного снимка состояния и ставят в очередь одинаковое значение. Функция обновления получает результат предыдущего обновления очереди, поэтому три `setCount((value) => value + 1)` последовательно дадут прибавление на три.

</details>

<details>
<summary><strong>Вопрос:</strong> Что изменилось в batching в React 18?</summary>

При использовании `createRoot` React начал автоматически объединять больше обновлений, включая обновления из Promise, таймеров и нативных событий. До React 18 пакетная обработка в основном была ограничена обработчиками событий React. `flushSync` позволяет принудительно завершить пакет, но нужен редко.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему мутация состояния может не вызвать рендер?</summary>

React сравнивает переданное setter-функции значение с предыдущим через `Object.is`. После мутации объекта ссылка остаётся той же, поэтому обновление может быть пропущено. Кроме того, мутация изменяет данные старых снимков состояния. Нужно создать новый объект или массив на изменившемся пути.

</details>

<details>
<summary><strong>Вопрос:</strong> Всегда ли повторный рендер является проблемой производительности?</summary>

Нет. Большинство рендеров дёшевы, а согласование деревьев может не привести к DOM-изменениям. Оптимизация оправдана после измерения React Profiler или браузерным профилировщиком. Нужно найти дорогой компонент или слишком широкое обновление, а не механически мемоизировать каждую функцию.

</details>

## Мини-задача

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  function increment() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
  }

  return <button onClick={increment}>{count}</button>;
}
```

<details>
<summary><strong>Вопрос:</strong> Что покажет кнопка после одного клика и как получить прибавление на три?</summary>

При начальном `count = 0` все три вызова ставят значение `1`, поэтому кнопка покажет `1`. Нужно трижды передать функцию обновления: `setCount((value) => value + 1)`. React применит функции к очереди как `0 → 1 → 2 → 3`.

</details>

## Где это встречается во frontend

| Ситуация | Что проверить |
| --- | --- |
| Рендерится большая таблица | Какое обновление запускает родителя и можно ли сузить область состояния |
| Context обновляет всё поддерево | Стабильность `value` и границы провайдеров |
| Несколько setter-функций подряд | Пакетная обработка и зависимость от предыдущего значения |
| Объект состояния изменили на месте | Новая ссылка и иммутабельное обновление |
| Подозрение на лишние рендеры | React Profiler, а не только `console.log` |
