## Вопрос

<br>

 💬 **Чем отличаются обычный HTTP request/response, polling, long polling, SSE и WebSocket? Как выбрать механизм realtime-обновлений?**

<h2></h2>

<br>
<dl>
<dd>

Эти механизмы отличаются направлением обмена, длительностью отдельного запроса, форматом данных, способом восстановления и сложностью прикладного протокола.

Realtime, или обновление в реальном времени, не означает отдельный универсальный протокол. Сначала определяют:

- кто инициирует передачу;
- в какую сторону идут данные;
- насколько быстро изменение должно появиться у пользователя;
- как часто возникают события;
- нужны ли бинарные сообщения;
- как восстанавливаются пропущенные данные;
- что поддерживают proxy, CDN и load balancer.

| Механизм | Направление | Жизненный цикл | Данные | Reconnect |
|---|---|---|---|---|
| HTTP request/response | клиент → сервер → клиент | один запрос получает один конечный ответ | любой поддерживаемый media type | новый запрос запускает приложение |
| Polling, или опрос | клиент периодически запрашивает сервер | последовательность коротких HTTP-запросов | обычные HTTP-ответы | следующий запрос запускает приложение |
| Long polling, или длинный опрос | клиент запрашивает, сервер задерживает ответ | последовательность долгих HTTP-запросов | обычные HTTP-ответы | новый long poll запускает приложение |
| SSE | сервер → клиент | длительный HTTP-response `text/event-stream` | текст UTF-8 | обычно выполняется браузером автоматически |
| WebSocket | двусторонний | постоянное WebSocket-соединение после handshake | текстовые и бинарные сообщения | реализует приложение |

Обычный HTTP использует request/response-модель:

```text
клиент отправляет request
→
сервер возвращает response
```

Это подходит для:

- загрузки данных;
- CRUD;
- отправки формы;
- выполнения команды;
- загрузки и скачивания файла;
- получения актуального snapshot, то есть полного снимка состояния.

Один HTTP request не обязательно означает новое физическое сетевое соединение.

HTTP/1.1 может переиспользовать persistent connection для нескольких последовательных запросов. HTTP/2 и HTTP/3 могут передавать несколько request/response-потоков через одно соединение.

Поэтому нужно различать:

```text
HTTP request lifecycle
network connection lifecycle
```

Обычный HTTP-response также может передаваться потоком. В Fetch API frontend может читать:

```ts
response.body
```

как `ReadableStream`.

Однако произвольный streaming response не предоставляет автоматически:

- формат событий;
- идентификаторы;
- reconnect;
- `Last-Event-ID`;
- обработку частично полученного сообщения;
- восстановление после разрыва.

SSE является стандартизированным текстовым форматом поверх долгого HTTP-response. При собственном streaming-протоколе через `fetch` framing и восстановление реализует приложение.

Polling периодически выполняет обычный HTTP-запрос:

```text
request
→ response
→ ожидание
→ request
→ response
```

Он прост, использует обычную HTTP-инфраструктуру и подходит, когда:

- данные изменяются редко;
- задержка в несколько секунд допустима;
- постоянное соединение неоправданно;
- важна простая диагностика;
- endpoint уже существует как обычный HTTP API.

Цена polling:

- пустые ответы при отсутствии изменений;
- задержка до следующего запроса;
- дополнительная нагрузка на сеть и сервер;
- большое количество запросов при маленьком интервале.

Polling-запросы не должны бесконтрольно перекрываться.

Например, `setInterval()` запускается каждые пять секунд, но запрос выполняется восемь секунд. Тогда одновременно могут существовать несколько запросов, а более старый ответ может прийти после нового и перезаписать актуальные данные.

Безопаснее дождаться завершения текущей попытки и только потом запланировать следующую:

```ts
async function poll() {
  try {
    await loadStatus();
  } finally {
    setTimeout(poll, 10_000);
  }
}
```

В реальном приложении также учитывают остановку, ошибки и уничтожение владельца polling.

Интервал можно:

- уменьшать во время активной операции;
- увеличивать после ошибок;
- снижать в фоновой вкладке;
- останавливать после завершения задачи;
- запускать при возвращении focus;
- корректировать по `Retry-After`.

Обычный интервал обновления и retry-задержка после ошибки являются разными настройками.

Для уменьшения передаваемых данных polling может использовать validators:

```http
If-None-Match: "task-v7"
```

Если данные не изменились, сервер возвращает:

```http
304 Not Modified
```

Long polling тоже использует HTTP request/response, но сервер не отвечает сразу.

Типичный цикл:

```text
клиент отправляет request
→
сервер ждёт событие или timeout
→
сервер возвращает полный HTTP-response
→
клиент сразу отправляет следующий request
```

Long polling уменьшает задержку по сравнению с периодическим опросом: сервер может вернуть ответ сразу после появления события.

При этом он не становится постоянным потоком. Каждый ответ завершает текущий HTTP-запрос, после чего клиент создаёт следующий.

Новое сетевое TCP- или QUIC-соединение для каждого цикла не обязательно: существующее соединение может быть переиспользовано. Но сервер всё равно удерживает открытый HTTP-запрос и связанные ресурсы.

Штатный timeout long polling не обязательно является ошибкой. Сервер может вернуть пустой ответ, чтобы запрос не превысил ограничения proxy или load balancer. После этого клиент открывает следующий long poll.

Между ответом и следующим запросом существует небольшой промежуток. Чтобы не потерять появившееся в этот момент событие, контракт использует:

- последний `eventId`;
- cursor;
- sequence number;
- версию данных;
- запрос событий после известной позиции.

После реальной ошибки нельзя мгновенно запускать бесконечный цикл запросов. Используют ограниченный backoff и учитывают возможность отмены.

SSE, или Server-Sent Events, является стандартным способом передавать текстовые события от сервера к клиенту через длительный HTTP-response.

Браузерный API называется `EventSource`:

```ts
const source = new EventSource("/api/events");

source.addEventListener("order-updated", (event) => {
  const message = JSON.parse(event.data);
  handleOrderUpdate(message);
});
```

Сервер отвечает:

```http
Content-Type: text/event-stream
```

Поток всегда декодируется как UTF-8.

Событие состоит из строк и заканчивается пустой строкой:

```text
id: 1842
event: order-updated
data: {"orderId":"42","status":"paid"}

```

Основные поля:

- `event` — имя события;
- `data` — данные;
- `id` — идентификатор для последующего восстановления;
- `retry` — рекомендуемая задержка перед reconnect в миллисекундах.

Если `event` отсутствует, браузер создаёт обычное событие `message`.

Несколько последовательных строк `data` объединяются через перевод строки:

```text
data: first line
data: second line

```

Frontend получит:

```text
first line
second line
```

SSE является однонаправленным каналом:

```text
сервер → клиент
```

Если клиенту нужно выполнить действие, он обычно отправляет отдельный HTTP-запрос:

```text
HTTP POST: клиент → сервер
SSE event: сервер → клиент
```

Такой подход хорошо подходит для:

- прогресса фоновой задачи;
- уведомлений;
- серверных логов;
- ленты;
- статусов;
- событий об изменении ресурса.

`EventSource` имеет состояния:

```text
CONNECTING
OPEN
CLOSED
```

При временном сетевом разрыве браузер обычно автоматически пытается восстановить соединение.

Событие `error` не всегда означает окончательное закрытие. Объект может перейти в `CONNECTING`, подождать установленную задержку и выполнить новый запрос.

Сервер может изменить задержку через:

```text
retry: 5000

```

Для окончательного закрытия со стороны frontend вызывают:

```ts
source.close();
```

После этого состояние становится `CLOSED`, а автоматический reconnect прекращается.

Сервер может вернуть:

```http
204 No Content
```

Такой ответ сообщает `EventSource`, что соединение больше не нужно восстанавливать.

Если сервер передавал `id`, браузер хранит последнее значение. При восстановлении он может отправить:

```http
Last-Event-ID: 1842
```

Но `Last-Event-ID` сам по себе не создаёт гарантию доставки.

Сервер должен:

1. Хранить журнал событий либо уметь восстановить изменение после указанной позиции.
2. Проверить, относится ли идентификатор к текущему пользователю и подписке.
3. Вернуть события после известной позиции.
4. Сообщить клиенту, если история уже недоступна.

Если replay невозможен, клиент получает новый snapshot через обычный HTTP API.

События после reconnect могут быть продублированы. Обработчики должны учитывать `eventId`, sequence number или версию сущности.

Нативный `EventSource` не позволяет произвольно добавлять request headers, например:

```http
Authorization: Bearer ...
```

Для same-origin-соединения применяются обычные правила credentials.

Для cross-origin-соединения с cookies можно использовать:

```ts
const source = new EventSource(
  "https://api.example.com/events",
  {
    withCredentials: true,
  },
);
```

Сервер должен разрешить конкретный origin и credentials через CORS.

Если нужен произвольный `Authorization` header, используют streaming `fetch` или подходящую библиотеку. Тогда приложение самостоятельно реализует:

- разбор событий;
- reconnect;
- backoff;
- передачу последнего `id`;
- остановку соединения.

Долгоживущий token в URL использовать опасно: URL может попасть в логи, аналитику, мониторинг и историю диагностики. Если применяется URL-ticket, он должен быть короткоживущим, одноразовым и ограниченным конкретным назначением.

SSE не поддерживает нативные бинарные сообщения. Бинарные данные можно закодировать в текст, например Base64, но это увеличивает размер. Крупные файлы лучше передавать отдельным HTTP-запросом.

Промежуточная инфраструктура может буферизовать SSE-response. Тогда сервер создаёт события по одному, а клиент получает их большой пачкой.

Нужно проверить:

- выполняется ли flush после каждого события;
- не накапливает ли ответ reverse proxy;
- не задерживает ли данные сжатие;
- поддерживает ли CDN streaming;
- не закрывает ли load balancer тихое соединение.

Для поддержания активности сервер может периодически отправлять комментарий:

```text
: heartbeat

```

Строка с `:` не создаёт событие в JavaScript, но передаёт данные по соединению и помогает избежать idle timeout.

WebSocket предоставляет постоянный full-duplex-канал:

```text
клиент ⇄ сервер
```

Обе стороны могут независимо отправлять сообщения без нового HTTP request для каждого события.

Сообщения могут быть:

- текстовыми;
- бинарными.

В браузере соединение создают так:

```ts
const socket = new WebSocket(
  "wss://api.example.com/realtime",
);
```

`WebSocket` имеет состояния:

```text
CONNECTING
OPEN
CLOSING
CLOSED
```

Перед отправкой приложение должно учитывать `readyState`:

```ts
if (socket.readyState === WebSocket.OPEN) {
  socket.send(JSON.stringify(message));
}
```

Классический opening handshake через HTTP/1.1 выглядит так:

```http
GET /realtime HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: ...
Sec-WebSocket-Version: 13
```

Сервер подтверждает переключение:

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: ...
```

После этого стороны передают WebSocket frames, а не обычную последовательность HTTP request/response.

WebSocket также может устанавливаться поверх HTTP/2 и HTTP/3 через Extended CONNECT.

В таком случае классические:

```text
GET
Upgrade
101 Switching Protocols
```

не используются в том же виде. WebSocket передаётся внутри отдельного HTTP/2- или HTTP/3-потока.

Поддержка зависит от браузера, сервера и промежуточной инфраструктуры. Frontend API при этом остаётся тем же:

```ts
new WebSocket(url);
```

Нативный браузерный WebSocket не выполняет автоматический reconnect. После `close` приложение решает:

- является ли закрытие намеренным;
- допускает ли код закрытия повтор;
- нужно ли обновить credentials;
- какую задержку использовать;
- как восстановить подписки и данные.

WebSocket Protocol определяет служебные frames:

- `Ping`;
- `Pong`;
- `Close`.

Браузерный JavaScript не может отправлять или обрабатывать протокольные Ping/Pong напрямую. Браузер выполняет эту часть внутри реализации.

Сервер может использовать Ping/Pong для проверки соединения.

Если frontend должен самостоятельно измерять задержку или время последней активности, прикладной протокол вводит обычные сообщения:

```json
{
  "type": "heartbeat"
}
```

и:

```json
{
  "type": "heartbeat_ack"
}
```

Это не протокольные Ping/Pong frames, а обычные WebSocket messages.

Открытие WebSocket не является пользовательской аутентификацией.

Браузерный конструктор:

```ts
new WebSocket(url, protocols);
```

не позволяет произвольно задать `Authorization` header.

Возможные способы аутентификации:

- session cookie;
- короткоживущий одноразовый WebSocket ticket;
- первое authentication message после открытия;
- BFF, который выдаёт ограниченные credentials для соединения.

Параметр `protocols` предназначен для выбора прикладного subprotocol:

```ts
new WebSocket(url, ["graphql-transport-ws"]);
```

Он не является универсальной заменой `Authorization`.

Некоторые системы используют `Sec-WebSocket-Protocol` для передачи дополнительных данных из-за ограничений браузерного API, но это специальное соглашение конкретной системы. Долгоживущий секрет не следует передавать таким способом без отдельного анализа угроз.

При cookie-аутентификации сервер должен проверять `Origin`. Иначе вредоносная страница может попытаться открыть WebSocket от имени уже вошедшего пользователя.

При этом `Origin` не является самостоятельной аутентификацией: небраузерный клиент способен отправить произвольное значение.

До завершения аутентификации сервер не должен:

- принимать остальные прикладные команды;
- создавать защищённые подписки;
- отправлять пользовательские данные;
- бесконечно держать неаутентифицированное соединение.

После аутентификации сервер всё равно проверяет право на каждую подписку, канал, ресурс и команду.

WebSocket сохраняет порядок messages внутри одного живого соединения.

Классический RFC 6455 работает поверх TCP. WebSocket поверх HTTP/2 или HTTP/3 использует соответствующий надёжный упорядоченный поток.

Но порядок внутри соединения не означает, что вся бизнес-история будет полной.

После reconnect событие может:

- быть пропущено;
- прийти повторно;
- оказаться устаревшим;
- относиться к предыдущей подписке;
- конфликтовать со свежим HTTP-snapshot.

Ни WebSocket, ни SSE, ни long polling автоматически не гарантируют exactly-once, то есть обработку каждого прикладного события ровно один раз.

Прикладной протокол определяет:

- `type`;
- `version`;
- `eventId`;
- sequence number;
- `requestId`;
- channel;
- payload;
- acknowledgement;
- стабильный формат ошибки.

Например:

```json
{
  "type": "order.updated",
  "version": 2,
  "eventId": "1842",
  "sequence": 1842,
  "payload": {
    "orderId": "42",
    "status": "paid"
  }
}
```

Timestamp полезен для отображения и диагностики, но не всегда подходит для строгого упорядочивания: часы разных серверов могут отличаться. Для порядка используют серверную последовательность или версию.

Входящее сообщение является внешними данными.

Недостаточно выполнить:

```ts
const message = JSON.parse(event.data);
```

После разбора нужно проверить:

- тип сообщения;
- версию;
- обязательные поля;
- допустимые значения;
- размер;
- право пользователя на данные.

TypeScript type не выполняет runtime validation.

Сервер также должен:

- ограничивать размер сообщений;
- ограничивать частоту;
- проверять каждую команду;
- закрывать нарушающие протокол соединения;
- не доверять данным только потому, что WebSocket уже открыт.

Для важных исходящих команд используют acknowledgement:

```text
client command
→
server acknowledgement
```

Но отсутствие acknowledgement не доказывает, что команда не выполнилась. Соединение могло оборваться после обработки команды сервером, но до получения ответа клиентом.

Для платежа, создания заказа и других критичных операций нужны:

- уникальный идентификатор операции;
- серверная дедупликация;
- идемпотентность;
- повторное получение результата.

Стратегия reconnect WebSocket обычно выглядит так:

1. Отличить намеренное закрытие от сбоя.
2. Обработать `close`, его `code`, `reason` и `wasClean`.
3. Проверить, допускает ли причина повтор.
4. Использовать exponential backoff и jitter.
5. Повторно аутентифицироваться.
6. Восстановить подписки.
7. Запросить replay или новый HTTP-snapshot.
8. Согласовать snapshot с событиями.
9. Сбросить backoff после стабильной работы соединения.

Reconnect лучше планировать в одном месте, обычно в обработчике `close`.

Событие `error` часто не содержит полезной причины, а после него возникает `close`. Если создавать таймер и в `error`, и в `close`, можно случайно открыть два параллельных соединения.

Exponential backoff увеличивает задержку:

```text
1 секунда
2 секунды
4 секунды
8 секунд
...
```

Jitter добавляет случайный разброс, чтобы тысячи клиентов не подключились одновременно после восстановления сервера.

Не следует автоматически переподключаться после:

- logout;
- окончательной ошибки аутентификации;
- запрета политики;
- удаления владельца соединения;
- закрытия приложения;
- несовместимой версии протокола.

Состояние `navigator.onLine` является только подсказкой. Оно не доказывает доступность конкретного сервера.

После открытия соединения недостаточно сразу показать пользователю состояние «данные синхронизированы».

Сначала нужно:

```text
open
→ authentication
→ subscriptions
→ replay или snapshot
→ synchronized
```

Если snapshot загружается параллельно с новыми событиями, старый HTTP-response не должен затереть более свежие изменения. Решение использует версии, временный буфер или согласованный порядок синхронизации.

Backpressure возникает, когда producer создаёт данные быстрее, чем consumer или сеть успевает их обработать.

У классического браузерного WebSocket нет полноценного backpressure для входящих сообщений.

Если сервер отправляет данные слишком быстро:

- растёт очередь событий;
- увеличивается расход памяти;
- перегружается main thread;
- интерфейс обрабатывает уже устаревшие состояния.

Помогают:

- серверное ограничение частоты;
- подписка только на нужные данные;
- агрегация событий;
- batching;
- sampling;
- хранение только последнего допустимого значения;
- уменьшение частоты рендера;
- разрыв соединения при превышении лимита.

Критичные события нельзя просто отбрасывать без правил прикладного протокола.

Для исходящих WebSocket messages доступно:

```ts
socket.bufferedAmount
```

Значение показывает количество application bytes, поставленных через `send()` в очередь, но ещё не переданных в сеть.

Большой `bufferedAmount` означает, что приложение отправляет быстрее, чем данные уходят.

Это не означает:

- что сервер получил сообщение;
- что сервер обработал сообщение;
- что нужен только один конкретный порог для всех устройств;
- что входящий поток тоже находится под контролем.

SSE через `EventSource` также не предоставляет frontend прямой механизм замедлить серверный поток. При высокой частоте сервер должен агрегировать события, а клиент — ограничивать стоимость обработки и рендера.

Выбор транспорта зависит не от того, какая технология выглядит современнее, а от требований.

Практическое правило:

- **Обычный HTTP request/response** — клиент запрашивает данные или выполняет отдельную команду.
- **Polling** — изменения редкие, задержка допустима, важна простота.
- **Long polling** — нужна быстрая доставка серверного события, но SSE или WebSocket недоступны.
- **SSE** — основной поток идёт от сервера к клиенту, данные текстовые, полезен автоматический reconnect.
- **WebSocket** — нужен частый двусторонний обмен, бинарные сообщения или собственный интерактивный протокол.

Часто используется гибридная модель:

```text
HTTP GET
→ начальный snapshot

SSE или WebSocket
→ уведомления об изменениях

HTTP conditional GET
→ получение актуального representation
```

Realtime-событие может содержать только:

```json
{
  "type": "order.changed",
  "orderId": "42",
  "version": 7
}
```

После этого frontend обновляет ресурс через HTTP API. Такой подход сохраняет HTTP-кеширование и уменьшает сложность realtime-протокола.

При уничтожении владельца транспорта нужно освободить ресурсы:

- остановить polling-таймер;
- отменить активный HTTP-запрос;
- вызвать `EventSource.close()`;
- закрыть WebSocket;
- отменить reconnect;
- остановить heartbeat;
- удалить обработчики;
- очистить пользовательские очереди;
- не применять запоздавшие ответы и события.

Иначе приложение создаст дубли запросов, соединений и подписок либо продолжит получать данные после logout.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Открывает ли каждый HTTP request новое сетевое соединение?</strong></summary>

<dl>
<dd>
<h2></h2>

Не обязательно.

HTTP request и сетевое соединение имеют разные жизненные циклы.

HTTP/1.1 может последовательно передавать несколько запросов через одно persistent TCP-соединение.

HTTP/2 может передавать несколько параллельных HTTP streams через одно TCP-соединение.

HTTP/3 делает то же поверх QUIC.

Polling и long polling создают новые HTTP requests, но браузер может переиспользовать уже установленное соединение.

При этом long polling всё равно удерживает открытый request и server-side-ресурсы до события или timeout.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем polling отличается от long polling?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычный polling отправляет запрос через определённый интервал независимо от наличия события.

Если интервал равен десяти секундам, обновление может задержаться почти на десять секунд, а большинство ответов могут не содержать изменений.

При long polling сервер удерживает запрос до появления события или timeout. После ответа клиент сразу открывает следующий request.

Задержка обычно меньше, но серверу нужно держать открытые запросы, а клиенту — обрабатывать timeout, backoff и промежуток между двумя long polls.

Штатный timeout не обязательно считается ошибкой: он может возвращать пустой ответ, после которого открывается следующий запрос.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как избежать перекрывающихся polling-запросов?</strong></summary>

<dl>
<dd>
<h2></h2>

Не следует безусловно запускать асинхронный request через `setInterval`, если запрос может выполняться дольше интервала.

Один вариант — планировать следующий запуск после завершения текущего:

```ts
async function poll() {
  try {
    await loadData();
  } finally {
    timeoutId = window.setTimeout(poll, interval);
  }
}
```

Другой вариант — отменять предыдущий request, если его результат больше не нужен.

Также используют request generation или sequence number, чтобы поздний ответ старого запроса не перезаписал новое состояние.

При уничтожении компонента нужно отменить request и следующий timer.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда SSE лучше WebSocket?</strong></summary>

<dl>
<dd>
<h2></h2>

SSE подходит, если основной поток идёт от сервера к клиенту, события текстовые, а действия пользователя можно отправлять обычным HTTP.

Он предоставляет:

- стандартный формат событий;
- автоматический reconnect;
- `Last-Event-ID`;
- поле `retry`;
- простой `EventSource` API.

WebSocket нужен для:

- частого двустороннего обмена;
- бинарных сообщений;
- собственного request/response-протокола;
- интерактивного канала с командами в обе стороны.

SSE всё равно требует проверки proxy buffering, timeout, авторизации и восстановления серверного журнала.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда <code>EventSource</code> прекращает автоматический reconnect?</strong></summary>

<dl>
<dd>
<h2></h2>

Frontend может явно вызвать:

```ts
source.close();
```

После этого `readyState` становится `CLOSED`, текущий request отменяется и новые попытки не выполняются.

Сервер может вернуть:

```http
204 No Content
```

Такой ответ также сообщает браузеру не восстанавливать соединение.

Некорректный response, неподдерживаемый `Content-Type` или окончательная ошибка могут перевести объект в `CLOSED`.

При временном сетевом разрыве событие `error` может сопровождаться состоянием `CONNECTING`, после чего браузер продолжит reconnect.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем SSE отличается от потокового <code>fetch</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Оба варианта могут использовать длительный HTTP-response.

SSE определяет стандартный формат `text/event-stream` с полями:

```text
event
data
id
retry
```

`EventSource` самостоятельно разбирает события и обычно выполняет reconnect.

Потоковый `fetch` предоставляет `ReadableStream` и позволяет задавать доступные Fetch headers, включая `Authorization`.

Но приложение самостоятельно реализует:

- разделение сообщений;
- decoding;
- reconnect;
- backoff;
- resume position;
- обработку незавершённого сообщения;
- отмену.

Потоковый `fetch` полезен для нестандартного протокола, бинарного потока или авторизации, которую нельзя выразить через `EventSource`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как работает opening handshake WebSocket?</strong></summary>

<dl>
<dd>
<h2></h2>

В классическом варианте HTTP/1.1 браузер отправляет `GET` с:

```http
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: ...
Sec-WebSocket-Version: 13
```

Также он может предложить один или несколько subprotocols:

```http
Sec-WebSocket-Protocol: graphql-transport-ws
```

Сервер отвечает:

```http
101 Switching Protocols
Sec-WebSocket-Accept: ...
```

и указывает выбранный subprotocol, если он был согласован.

Handshake подтверждает переключение на WebSocket framing, но не является аутентификацией пользователя.

После успешного handshake стороны передают WebSocket frames.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли WebSocket работать поверх HTTP/2 и HTTP/3?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

RFC 8441 определяет WebSocket поверх HTTP/2, а RFC 9220 адаптирует этот механизм для HTTP/3.

Вместо классического HTTP/1.1 Upgrade используется Extended CONNECT с протоколом `websocket`.

WebSocket передаётся в отдельном HTTP/2- или HTTP/3-потоке.

Frontend API при этом не меняется:

```ts
new WebSocket("wss://example.com/realtime");
```

Выбор конкретного варианта выполняют браузер и инфраструктура.

Сервер, proxy и load balancer должны поддерживать используемый механизм. Наличие HTTP/2 или HTTP/3 у обычных API-запросов не гарантирует, что WebSocket автоматически будет установлен тем же способом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как аутентифицировать браузерное WebSocket-соединение?</strong></summary>

<dl>
<dd>
<h2></h2>

Конструктор `new WebSocket(url, protocols)` не позволяет произвольно добавить `Authorization` header.

Частые варианты:

- session cookie;
- короткоживущий одноразовый ticket;
- первое authentication message после `open`;
- выдача ограниченных credentials через BFF.

При cookie-аутентификации сервер проверяет `Origin`, чтобы вредоносная страница не открыла соединение от имени вошедшего пользователя.

`Origin` не заменяет credentials и может быть подделан небраузерным клиентом.

`Sec-WebSocket-Protocol` предназначен прежде всего для согласования прикладного subprotocol, а не для обычной передачи access token.

До завершения аутентификации сервер запрещает остальные сообщения, устанавливает timeout и не отправляет защищённые данные.

После входа сервер проверяет права каждой подписки и команды.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое heartbeat и зачем он нужен?</strong></summary>

<dl>
<dd>
<h2></h2>

Соединение может фактически исчезнуть без немедленного `close`.

Например:

- устройство потеряло сеть;
- NAT удалил сопоставление;
- proxy закрыл тихое соединение;
- вкладка была заморожена.

WebSocket Protocol определяет Ping/Pong frames. Сервер может отправить Ping, а браузер ответит Pong внутри реализации.

JavaScript не имеет прямого доступа к этим frames.

Если frontend должен самостоятельно контролировать время последнего ответа, прикладной протокол использует обычные сообщения:

```json
{
  "type": "heartbeat"
}
```

Частота должна учитывать батарею, фоновые вкладки и timeout инфраструктуры.

SSE может использовать комментарии `: heartbeat`, которые не создают JavaScript-событие.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как строить стратегию переподключения?</strong></summary>

<dl>
<dd>
<h2></h2>

Для WebSocket reconnect обычно планируют в обработчике `close`, а не одновременно в `error` и `close`.

Клиент:

1. Отличает намеренное закрытие от сбоя.
2. Проверяет `code`, `reason` и `wasClean`.
3. Решает, можно ли повторять подключение.
4. Использует exponential backoff и jitter.
5. Повторно проходит аутентификацию.
6. Восстанавливает подписки.
7. Запрашивает replay или snapshot.
8. Согласует новые события с загруженным состоянием.

Попытки прекращают после logout, постоянной ошибки аутентификации и уничтожения владельца соединения.

Backoff лучше сбрасывать после устойчивой работы, а не сразу после краткого `open`, иначе нестабильный сервер будет получать частые попытки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Гарантирует ли WebSocket порядок и доставку каждого прикладного события?</strong></summary>

<dl>
<dd>
<h2></h2>

Внутри одного живого соединения WebSocket сохраняет порядок messages.

Но это не гарантирует полноту истории после reconnect.

Событие могло:

- появиться до подписки;
- потеряться во время разрыва;
- быть обработано до потери acknowledgement;
- повторно прийти после восстановления;
- устареть до применения.

Для прикладных гарантий используют:

- `eventId`;
- sequence number;
- acknowledgement;
- журнал событий;
- resume cursor;
- version;
- дедупликацию;
- идемпотентные обработчики.

Exactly-once обеспечивается не одним транспортом, а сочетанием серверного состояния, протокола и клиентской обработки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое message schema и зачем ей version?</strong></summary>

<dl>
<dd>
<h2></h2>

Message schema определяет структуру прикладного сообщения:

- `type`;
- `version`;
- `eventId`;
- sequence number;
- `requestId`;
- channel;
- payload;
- error.

Версия помогает независимо разворачивать frontend и backend.

Совместимые изменения обычно добавляют необязательные поля. Несовместимую структуру вводят под новой версией или новым типом сообщения.

Frontend должен безопасно обрабатывать неизвестный тип или версию.

TypeScript type существует только во время разработки и не проверяет фактическое сообщение. На сетевой границе нужна runtime validation или защитный parser.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое backpressure?</strong></summary>

<dl>
<dd>
<h2></h2>

Backpressure возникает, когда producer создаёт данные быстрее, чем consumer или сеть успевает их обработать.

В исходящем WebSocket-потоке проверяют:

```ts
socket.bufferedAmount
```

Большое значение показывает накопление application data до передачи в сеть.

Оно не подтверждает, что сервер получил или обработал сообщение.

Для входящих WebSocket и SSE-событий браузерный API не предоставляет полноценный механизм замедлить сервер.

Поэтому применяют:

- rate limit на сервере;
- batching;
- агрегацию;
- sampling;
- обработку только последнего некритичного значения;
- уменьшение частоты рендера;
- ограничение размера очереди.

Критичные события нельзя отбрасывать без явной семантики протокола.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как SSE восстанавливает пропущенные события?</strong></summary>

<dl>
<dd>
<h2></h2>

Сервер добавляет событию поле:

```text
id: 1842
```

Браузер запоминает последнее значение и при reconnect может отправить:

```http
Last-Event-ID: 1842
```

Сервер должен хранить журнал и вернуть события после этой позиции.

`EventSource` не создаёт историю автоматически.

Если журнал уже очищен, сервер предлагает клиенту получить новый snapshot.

Последнее событие может прийти повторно, поэтому обработчик учитывает `eventId` или версию.

Пустое поле:

```text
id

```

сбрасывает сохранённый идентификатор, и при следующем reconnect `Last-Event-ID` не отправляется.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как аутентификация работает с <code>EventSource</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Нативный `EventSource` не позволяет задавать произвольные request headers.

Same-origin cookies применяются по обычным правилам.

Для cross-origin cookies используют:

```ts
new EventSource(url, {
  withCredentials: true,
});
```

Сервер должен корректно настроить CORS и credentials.

Если нужен Bearer header, используют streaming `fetch`, библиотеку или короткоживущий одноразовый ticket.

Постоянный access token в query опасен из-за логов и мониторинга.

При истёкшей сессии сервер и клиент должны прекратить бессмысленный reconnect, например через окончательный ответ и закрытие `EventSource`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выбрать между realtime transport и повторным запросом данных?</strong></summary>

<dl>
<dd>
<h2></h2>

Если данные меняются редко и допустима задержка, polling или refetch on focus проще постоянного соединения.

Если сервер должен быстро передавать текстовые события, а клиентские команды остаются обычными HTTP-запросами, подходит SSE.

Для частого двустороннего обмена и бинарных сообщений подходит WebSocket.

Часто лучшим является гибридный вариант:

```text
realtime event
→ содержит id и version

HTTP request
→ получает актуальное representation
```

Так realtime-канал остаётся небольшим, а источник истины, авторизация и кеширование остаются в обычном HTTP API.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Подходящий механизм |
|---|---|
| CRUD и отправка формы | HTTP request/response |
| Статус фоновой задачи раз в минуту | Polling |
| Редкое событие сервера без streaming-инфраструктуры | Long polling |
| Уведомления и прогресс | SSE |
| Чат и совместное редактирование | WebSocket |
| Биржевые котировки | WebSocket с batching или обработкой последнего значения |
| Авторизованный текстовый stream с Bearer token | Потоковый `fetch` |
| Потеря соединения | Backoff, resume cursor и повторная загрузка snapshot |
