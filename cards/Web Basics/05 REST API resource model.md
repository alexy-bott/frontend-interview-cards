## Вопрос

<br>

 💬 **Что такое REST? Как строится ресурсная модель в HTTP API?**

<h2></h2>

<br>
<dl>
<dd>

REST, или Representational State Transfer, — архитектурный стиль для распределённых гипермедиа-систем.

REST задаёт не конкретный формат API, а набор ограничений на взаимодействие компонентов. Поэтому API не становится RESTful автоматически только потому, что использует HTTP, JSON и методы `GET`, `POST`, `PUT` или `DELETE`.

REST не является:

- сетевым протоколом;
- форматом JSON;
- синонимом CRUD;
- правилом «URL должны содержать только существительные».

Основные ограничения REST:

| Ограничение | Смысл |
|---|---|
| Client-server | Клиент и сервер разделены по ответственности и могут развиваться независимо |
| Stateless | Каждый запрос содержит контекст, необходимый для его обработки, и не зависит от скрытого контекста предыдущего шага диалога на сервере |
| Cacheable | Ответ сообщает правила его повторного использования |
| Uniform interface | Компоненты взаимодействуют через единообразную модель ресурсов, представлений и сообщений |
| Layered system | Клиент не обязан знать, находится ли за ближайшим компонентом proxy, gateway, cache или origin server |
| Code on demand | Необязательное ограничение: сервер может передавать клиенту исполняемый код |

Ключевая абстракция REST — **ресурс** (`resource`).

Ресурс — это понятие, которому можно назначить устойчивый идентификатор. Например:

```text
/users/42
```

может идентифицировать пользователя `42`.

Сам ресурс не обязан быть строкой базы данных или физическим файлом. Его состояние может меняться, а идентификатор при этом остаётся тем же.

В HTTP ресурс обычно идентифицируется URI:

```text
https://api.example.com/users/42
```

URI указывает, **к какому ресурсу обращается запрос**, но не является самим ресурсом.

Между клиентом и сервером передаётся **представление ресурса** (`representation`) — данные, которые описывают его текущее или желаемое состояние.

Например:

```http
GET /users/42
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 42,
  "name": "Ada"
}
```

JSON здесь является представлением пользователя, а не самим ресурсом.

Один ресурс может иметь разные представления: JSON, HTML, изображение, локализованный вариант или ответ с другим набором данных. Какое представление передавать, может зависеть, например, от `Accept` и `Accept-Language`.

В HTTP смысл запроса определяется не одним URL, а сочетанием стандартных элементов протокола:

```text
метод + target URI + заголовки + при необходимости тело
```

Например:

```text
GET /orders/42
```

запрашивает представление ресурса.

```text
PUT /orders/42
```

передаёт состояние, которое должно быть установлено для известного URI согласно контракту API.

```text
PATCH /orders/42
```

передаёт описание частичного изменения.

```text
DELETE /orders/42
```

просит удалить ресурс или прекратить его связь с данным URI согласно семантике API.

Query-параметры являются частью URI и вместе с path участвуют в определении цели запроса:

```text
/users?status=active&sort=-createdAt
```

Конкретный API может использовать их для фильтрации, сортировки, пагинации или выбора полей. Это не то же самое, что выбор формата представления через HTTP content negotiation.

Центральное ограничение REST — **uniform interface**, или единообразный интерфейс. В исходной модели REST оно включает четыре части:

1. идентификацию ресурсов;
2. изменение ресурсов через representations;
3. самодостаточные сообщения;
4. hypermedia как механизм переходов состояния приложения.

Последний пункт обычно называют HATEOAS.

Ещё одно важное ограничение — **stateless**. Сервер может хранить пользователей, заказы, права, задачи и другие данные системы, но обработка текущего запроса не должна зависеть от скрытого server-side-контекста предыдущих шагов диалога с этим клиентом.

На практике многие frontend API используют ресурсную модель, HTTP-методы, статусы и кеширование, но не реализуют hypermedia полностью. Такие API часто называют REST API в широком практическом смысле, хотя точнее может быть:

```text
resource-oriented HTTP API
```

или:

```text
REST-inspired API
```

При проектировании такого API полезно начинать не с названий endpoints, а с вопросов:

- какие ресурсы и коллекции существуют;
- как они идентифицируются;
- какие representations передаются;
- какие HTTP-операции над ними допустимы;
- как описаны кеширование, конкурентные изменения и ошибки;
- какие переходы и связи должен понимать клиент.

Главный критерий — согласованная семантика контракта, а не внешнее сходство с «REST-стилем» URL.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем resource, или ресурс, отличается от representation, или представления?</strong></summary>

<dl>
<dd>
<h2></h2>

Ресурс — концептуальная цель обращения, которой назначен идентификатор.

Например:

```text
/users/42
```

идентифицирует пользователя `42`.

Representation — данные, передаваемые между компонентами и описывающие состояние ресурса:

```json
{
  "id": 42,
  "name": "Ada"
}
```

Ресурс сохраняет идентичность, хотя его состояние и представления могут меняться.

Один ресурс может иметь:

- JSON-представление;
- HTML-представление;
- сокращённый вариант для списка;
- подробный вариант;
- разные языковые варианты;
- разные представления для разных прав пользователя.

`Content-Type` сообщает media type фактически переданного представления.

Если выбор ответа зависит от заголовков вроде `Accept` или `Accept-Language`, сервер может использовать `Vary`, чтобы кеш различал варианты:

```http
Vary: Accept, Accept-Language
```

Representation не обязано повторять внутреннюю server-side-модель. Оно является частью публичного контракта API и может скрывать внутренние или недоступные пользователю данные.

`ETag` относится к выбранному представлению ресурса и используется как HTTP validator, а не обязан быть глобальным номером версии всей внутренней сущности.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>REST требует JSON и HTTP?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

REST — архитектурный стиль, а не формат данных. Представлением ресурса может быть:

- HTML;
- JSON;
- XML;
- изображение;
- видео;
- другой media type.

REST также не определяется конкретным сетевым протоколом.

При этом HTTP особенно хорошо соответствует REST-модели: он уже предоставляет URI, стандартные методы, статусы, заголовки, кеширование, content negotiation, conditional requests и работу посредников.

Но сам факт использования HTTP и JSON ещё не делает API RESTful.

Например:

```http
POST /execute

{
  "procedure": "createUser"
}
```

может быть вполне рабочим RPC over HTTP.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое uniform interface?</strong></summary>

<dl>
<dd>
<h2></h2>

Uniform interface, или единообразный интерфейс, уменьшает связанность компонентов: клиент и сервер взаимодействуют через общие правила, а не через уникальный протокол для каждой операции.

В REST он включает четыре ограничения:

1. **Identification of resources** — ресурсы имеют идентификаторы.
2. **Manipulation through representations** — клиент передаёт representations, чтобы выразить желаемое состояние или изменение.
3. **Self-descriptive messages** — сообщение содержит достаточно информации для его обработки.
4. **Hypermedia as the engine of application state** — доступные переходы выражаются через hypermedia controls.

В HTTP часть этой семантики передаётся через:

- method;
- target URI;
- status code;
- headers;
- media type;
- validators;
- link relations;
- representation.

Например:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=60
ETag: "user-42-v5"
Link: </users/42/orders>; rel="related"
```

Здесь видны формат, правила кеширования, validator и связь с другим ресурсом.

Один `Content-Type: application/json` сообщает синтаксис представления, но не описывает всю бизнес-семантику полей. Для неё могут использоваться schema, media type, link relations, OpenAPI и документация API.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что на практике означает stateless API?</strong></summary>

<dl>
<dd>
<h2></h2>

Stateless означает, что каждый запрос содержит информацию, необходимую для его понимания, и не зависит от скрытого server-side-контекста предыдущих шагов диалога.

Например:

```http
GET /orders/42
Authorization: Bearer <access-token>
Accept: application/json
```

Сервер при этом продолжает хранить **resource state**:

- пользователей;
- заказы;
- права;
- настройки;
- фоновые задачи.

Ограничение относится прежде всего к **session state** между запросами.

Традиционная server-side session выглядит так:

```text
Cookie: sessionId=abc
                 │
                 └─ сервер ищет сохранённый контекст сессии
```

Если перенести session store в Redis, запросы смогут обрабатываться разными экземплярами приложения и исчезнет необходимость в sticky sessions. Но взаимодействие всё равно не станет строго stateless, потому что сервер продолжает хранить session state между запросами.

Cookie само по себе stateless не нарушает. Важно, что именно хранится на сервере и нужен ли скрытый контекст предыдущих шагов.

Stateless также не требует JWT. Например, сервер может проверять opaque access token через отдельное хранилище полномочий. Наличие authentication state не обязательно означает наличие session state диалога.

Полезно различать:

```text
resource state
session state
application state
authentication state
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означают cacheable, layered system и code on demand?</strong></summary>

<dl>
<dd>
<h2></h2>

**Cacheable** означает, что ответ сообщает правила повторного использования.

Например:

```http
Cache-Control: public, max-age=300
ETag: "catalog-v7"
```

Кеш может повторно использовать ответ или выполнить условный запрос вместо повторной передачи всего тела.

REST не требует кешировать каждый ответ. Для чувствительных данных сервер может явно запретить хранение:

```http
Cache-Control: no-store
```

**Layered system** означает, что клиент взаимодействует только с ближайшим компонентом и не обязан знать полную внутреннюю топологию:

```text
frontend
→ CDN
→ reverse proxy
→ API gateway
→ application service
```

Промежуточные компоненты могут кешировать, балансировать нагрузку, проверять доступ, ограничивать частоту или маршрутизировать запросы.

**Code on demand** — единственное необязательное ограничение REST. Сервер может передавать исполняемый код, расширяющий возможности клиента. Классический пример Web — JavaScript, загружаемый браузером.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое HATEOAS?</strong></summary>

<dl>
<dd>
<h2></h2>

HATEOAS означает, что доступные переходы приложения клиент получает из текущего representation, а не обязан заранее жёстко знать каждый возможный URL и действие.

Например:

```json
{
  "id": "42",
  "status": "pending",
  "links": {
    "payment": {
      "href": "/orders/42/payment",
      "method": "POST"
    },
    "cancellation": {
      "href": "/orders/42/cancellation",
      "method": "POST"
    }
  }
}
```

После изменения состояния сервер может вернуть другой набор доступных переходов.

Hypermedia control может быть:

- ссылкой в теле;
- формой;
- кнопкой с описанной операцией;
- заголовком `Link`;
- другим элементом конкретного media type.

Например:

```http
Link: </orders?cursor=abc>; rel="next"
```

Клиент всё равно должен заранее понимать семантику media type и link relations. HATEOAS не означает, что клиент вообще ничего не знает о контракте.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли считать API без HATEOAS полноценным REST?</strong></summary>

<dl>
<dd>
<h2></h2>

В строгом смысле исходной REST-модели — нет.

Hypermedia as the Engine of Application State является одной из четырёх частей uniform interface.

API без hypermedia всё ещё может качественно использовать:

- ресурсы;
- HTTP-методы;
- статусы;
- кеширование;
- stateless-запросы;
- conditional requests.

Но точнее называть его:

```text
resource-oriented HTTP API
```

или:

```text
REST-inspired API
```

В прикладной разработке термин «REST API» часто используется шире исходного определения. Полезнее понимать, какие свойства и ограничения система действительно реализует, чем спорить только о названии.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Должны ли REST endpoints содержать только существительные?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Правило «только существительные» не является отдельным формальным ограничением REST.

В ресурсно-ориентированном API существительные часто удобны, потому что URI идентифицирует ресурс, а HTTP-метод задаёт стандартную операцию:

```text
GET /users/42
DELETE /users/42
```

Endpoint:

```text
GET /getUserById
```

частично дублирует семантику метода и больше похож на удалённую процедуру.

Но URI прежде всего является идентификатором. Для сложной бизнес-команды понятный command endpoint иногда лучше искусственной ресурсной модели.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда использовать вложенный URL ресурса?</strong></summary>

<dl>
<dd>
<h2></h2>

Вложенный URI удобно использовать, когда родитель задаёт естественную область или отношение:

```text
/users/42/orders
```

Например, он подходит для коллекции заказов конкретного пользователя.

Если заказ имеет собственный глобальный идентификатор, детали можно получать независимо:

```text
/orders/99
```

Слишком глубокая вложенность:

```text
/companies/1/departments/2/users/3/orders/4/items/5
```

делает URI хрупким и заставляет дублировать внутренние связи данных в адресе.

Обычно полезно оставлять только те уровни, которые действительно помогают идентифицировать или естественно адресовать ресурс.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как моделировать действие, которое не укладывается в CRUD?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала нужно понять природу операции:

- это изменение существующего ресурса;
- создание нового ресурса;
- запуск долгой операции;
- самостоятельная бизнес-команда.

Например, отмену заказа можно представить изменением состояния:

```http
PATCH /orders/42
Content-Type: application/merge-patch+json

{
  "status": "cancelled"
}
```

или созданием отдельного ресурса отмены:

```text
POST /orders/42/cancellations
```

Долгую операцию можно представить ресурсом задачи:

```http
POST /reports
202 Accepted
Location: /report-jobs/123
```

Но если явный command endpoint остаётся самым понятным контрактом:

```text
POST /orders/42/cancel
```

его использование само по себе не делает API плохим.

Важно документировать семантику операции: идемпотентность, допустимые состояния, результат повторного вызова, коды ответа, ошибки и конкурентные изменения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как query-параметры связаны с ресурсом, фильтрацией и пагинацией?</strong></summary>

<dl>
<dd>
<h2></h2>

В HTTP path и необязательный query являются частями URI, который определяет target resource.

Например:

```text
/orders?status=active&sort=-createdAt&limit=20&cursor=...
```

Конкретный API может договориться, что query-параметры задают:

- фильтр;
- сортировку;
- размер страницы;
- cursor;
- набор возвращаемых полей;
- другие параметры выборки.

Это не общее HTTP-правило выбора representation.

Выбор формата представления обычно относится к content negotiation, например через:

```http
Accept: application/json
Accept-Language: ru
```

Для пагинации API должен документировать стабильный порядок, максимальный размер страницы, формат cursor и способ получить следующую страницу.

Offset pagination проста, но на быстро меняющемся наборе может пропускать или повторять элементы.

Cursor pagination лучше подходит для последовательной загрузки. Сам cursor обычно является opaque token: frontend не должен самостоятельно разбирать или конструировать его.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как защитить обновление ресурса от потери чужих изменений?</strong></summary>

<dl>
<dd>
<h2></h2>

Для optimistic concurrency можно использовать HTTP validators и preconditions.

Клиент получает представление с `ETag`:

```http
ETag: "order-42-v5"
```

и при изменении отправляет условие:

```http
If-Match: "order-42-v5"
```

Если текущее представление уже изменилось и условие больше не выполняется, сервер может вернуть:

```http
412 Precondition Failed
```

Тогда frontend не перезаписывает новое состояние вслепую, а может:

- обновить данные;
- показать конфликт пользователю;
- повторно применить изменение к свежей версии.

Такой механизм отделяет контроль конкурентных изменений от произвольного поля вроде `version`, хотя конкретный API может использовать и собственные механизмы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как должен выглядеть контракт ошибок API?</strong></summary>

<dl>
<dd>
<h2></h2>

HTTP status code задаёт общий класс результата, а тело ответа может содержать стабильные машинно-читаемые детали.

API может использовать собственный формат или Problem Details из RFC 9457:

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json
```

```json
{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Request validation failed",
  "status": 422,
  "detail": "One or more fields are invalid",
  "instance": "/requests/01HXYZ",
  "errors": [
    {
      "pointer": "/email",
      "code": "EMAIL_TAKEN"
    }
  ]
}
```

Стандартные поля Problem Details:

- `type`;
- `title`;
- `status`;
- `detail`;
- `instance`.

`errors`, машинные коды и другие данные могут добавляться как extensions конкретного problem type.

Для программной логики frontend должен опираться на стабильные поля контракта, а не разбирать пользовательский текст ошибки.

Correlation ID не является обязательным стандартным полем Problem Details. Его можно передавать заголовком или документированным extension-полем.

Ответ об ошибке не должен раскрывать секреты, stack trace, SQL или внутренние пути.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как версионировать REST API?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала лучше по возможности развивать контракт обратно совместимо:

- добавлять новые необязательные поля;
- добавлять новые ресурсы и endpoints;
- не менять смысл существующих полей;
- заранее помечать устаревающие возможности.

Если несовместимая версия необходима, её можно отделить, например, через путь:

```text
/api/v2/users
```

отдельный host или отдельный media type.

Любая параллельная версия увеличивает стоимость поддержки: её нужно развёртывать, тестировать и сопровождать во время миграции клиентов.

Сам номер версии не заменяет:

- период миграции;
- deprecation policy;
- мониторинг использования;
- дату отключения;
- поддержку старых клиентов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда REST становится неудобен по сравнению с GraphQL или RPC?</strong></summary>

<dl>
<dd>
<h2></h2>

REST, GraphQL и RPC решают разные задачи и могут сосуществовать.

Resource-oriented HTTP API особенно удобен, когда важны:

- стандартная HTTP-семантика;
- кеширование;
- независимые ресурсы;
- CDN и intermediaries;
- conditional requests;
- простая диагностика.

GraphQL удобен, когда экрану нужен сложный граф связанных данных и клиенту важно выбирать форму ответа.

RPC естественно моделирует операции, которые по смыслу являются командами или процедурами.

Например, в одной системе можно использовать:

- HTTP resources для обычных сущностей и файлов;
- GraphQL или BFF для сложного экрана;
- RPC endpoint для бизнес-команды;
- SSE или WebSocket для realtime-изменений.

Выбор определяется не «чистотой REST», а стоимостью и понятностью контракта.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Задача | Связь с ресурсной моделью REST |
|---|---|
| RTK Query endpoint | Метод, URI и representation ресурса |
| Таблица | Ресурс коллекции, фильтрация, сортировка и пагинация |
| Редактирование | `PUT`/`PATCH`, `ETag`, `If-Match` и обработка конфликтов |
| OpenAPI client | Контракт методов, representations и ошибок |
| Инвалидация кеша | Идентичность ресурса и связанные representations |
| Backend с несколькими экземплярами | Независимые запросы и отсутствие server-side session context |
| BFF | Агрегация данных для конкретного экрана |
| Обработка ошибок | HTTP status и стабильный Problem Details-контракт |
| Навигация API | Links и link relations между ресурсами |
