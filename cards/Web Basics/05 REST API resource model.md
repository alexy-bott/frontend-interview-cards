## Вопрос

Что такое REST? Как строится ресурсная модель в HTTP API?

<details>
<summary><strong>Показать ответ</strong></summary>

REST, или Representational State Transfer (передача состояния через представления), - архитектурный стиль для распределённых гипермедиа-систем, а не протокол и не синоним JSON API. Он задаёт ограничения, которые делают взаимодействие масштабируемым и позволяют клиенту, серверу и посредникам развиваться независимо. HTTP хорошо поддерживает эти ограничения, но API с HTTP-методами автоматически не становится RESTful.

Основные ограничения REST:

| Ограничение | Смысл |
|---|---|
| Client-server | пользовательский интерфейс и хранение данных разделены по ответственности и могут развиваться отдельно |
| Stateless, без состояния диалога | каждый запрос содержит достаточно контекста для обработки; сервер не полагается на скрытую память о предыдущих запросах клиента |
| Cacheable, кэшируемость | ответ сообщает, можно ли и как его переиспользовать |
| Uniform interface, единообразный интерфейс | ресурсы идентифицируются одинаковым способом, а сообщения самодостаточны и используют представления и гипермедиа |
| Layered system, слоистая система | клиент не обязан знать, отвечает исходный сервер, прокси, gateway или кэш |
| Code on demand, код по требованию | необязательное ограничение: сервер может передавать исполняемый код, например JavaScript |

Resource, или ресурс, - адресуемое понятие: пользователь, заказ, список комментариев или текущие настройки. Ресурс идентифицируется URI. Representation, или представление, - данные, описывающие состояние ресурса в конкретном формате, например JSON или HTML. Один ресурс может иметь разные представления в зависимости от `Accept`, языка и прав пользователя.

```http
GET /users/42
Accept: application/json

200 OK
Content-Type: application/json

{"id":42,"name":"Ada"}
```

Uniform interface означает, что смысл операции выражается стандартными HTTP-методами, кодами состояния, заголовками и форматами данных (media types), а не скрыт только в имени endpoint. `GET /orders/42` читает представление, `PUT` заменяет состояние по известному URI, `PATCH` применяет документ изменения, `DELETE` удаляет связь ресурса с URI. Благодаря этому браузерный кэш, прокси, средства мониторинга и универсальные клиенты понимают часть семантики без знания бизнес-кода.

Stateless не означает «на сервере нет базы данных, сессий или состояния». Сервер хранит состояние ресурсов и может хранить данные сессии. Ограничение требует, чтобы каждый запрос был понятен сам по себе: он содержит session cookie, token, целевой URI и необходимые заголовки. Обработчик не должен зависеть от того, что предыдущий запрос клиента выполнился на том же экземпляре сервера.

Resource-oriented HTTP API, или ресурсно-ориентированный HTTP API, обычно наследует часть идей REST, но редко реализует стиль полностью. Особенно часто отсутствует HATEOAS (Hypermedia as the Engine of Application State): клиент заранее знает маршруты и собирает URL, а не узнает доступные переходы по ссылкам и элементам управления из ответов. Поэтому API стоит оценивать по его фактическим свойствам, а не объявлять любой CRUD endpoint «чистым REST».

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Чем resource, или ресурс, отличается от representation, или представления?</summary>

Ресурс - адресуемое понятие, идентичность которого сохраняется во времени, например пользователь `42`. Представление - конкретные данные, описывающие его текущее или желаемое состояние. JSON `{ "id": 42, "name": "Ada" }` является представлением, а не самим пользователем.

Один ресурс может иметь представления в JSON и HTML, сокращённый вариант для списка и подробный для карточки. `Content-Type` сообщает формат переданного представления, а validators, или валидаторы кэша, вроде `ETag` относятся к его версии.

</details>

<details>
<summary><strong>Вопрос:</strong> Что на практике означает stateless API?</summary>

Каждый запрос должен содержать контекст аутентификации, целевой URI, представление и условия, необходимые для обработки. Балансировщик нагрузки может отправить следующий запрос другому экземпляру приложения без скрытой памяти о предыдущем шаге.

Session cookie не нарушает stateless автоматически: cookie является частью каждого запроса, а данные сессии можно получить из общего хранилища. Нарушением будет протокол, где экземпляр приложения ожидает «шаг 2», потому что только он помнит «шаг 1», а сам запрос этого не выражает.

</details>

<details>
<summary><strong>Вопрос:</strong> REST требует JSON и HTTP?</summary>

Нет. REST является архитектурным стилем и не привязан к JSON. Web использует HTML, изображения, JSON и другие media types. HTTP предоставляет URI, методы, самодостаточные заголовки, кэширование и посредников, поэтому большинство обсуждений REST связано именно с HTTP.

API, возвращающий JSON по HTTP, может быть RPC (Remote Procedure Call, удаленный вызов процедуры): например, один `POST /execute` с именем процедуры внутри тела. Формат и транспорт сами по себе не определяют архитектурный стиль.

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое uniform interface?</summary>

Uniform interface, или единообразный интерфейс, уменьшает связанность: все ресурсы доступны через общую семантику протокола. В оригинальном REST это включает идентификацию ресурсов, изменение состояния через представления, самодостаточные сообщения и переходы по гипермедиа-ссылкам.

Практически это означает осмысленные URI, корректные методы, коды состояния, заголовки, media types и достаточную информацию в сообщении. Цена единообразия - оно иногда менее эффективно, чем специально оптимизированная процедура для конкретного экрана.

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое HATEOAS?</summary>

HATEOAS означает, что клиент меняет состояние приложения, следуя ссылкам и доступным действиям из полученных представлений, а не зная все переходы заранее. Например, ответ с заказом может содержать ссылки `cancel`, `pay` или `track` в зависимости от текущего состояния и прав пользователя.

Большинство frontend JSON APIs использует заранее известные маршруты и поэтому не реализует HATEOAS полностью. Ссылки всё равно полезны для пагинации и обнаружения доступных переходов, но наличие одного поля `next` не делает всю архитектуру RESTful.

</details>

<details>
<summary><strong>Вопрос:</strong> Должны ли REST endpoints содержать только существительные?</summary>

Ресурсно-ориентированный дизайн обычно выражает адресуемые сущности существительными: `/orders/42`, `/users/7/orders`. Смысл действия задаёт HTTP-метод, поэтому `/getUserById` дублирует `GET` и связывает URI с именем процедуры.

Но бизнес-действие не всегда удобно представить обычным CRUD. `POST /orders/42/cancellation` может создать ресурс отмены, а `/orders/42/cancel` может быть понятным командным endpoint. Важнее стабильная семантика, идемпотентность и документация, чем формальный запрет глаголов.

</details>

<details>
<summary><strong>Вопрос:</strong> Когда использовать вложенный URL ресурса?</summary>

Вложенный URL выражает принадлежность или область: `/users/42/orders` обозначает заказы пользователя. Он удобен, когда родительский ресурс обязателен для идентификации или авторизации.

Слишком глубокая вложенность делает маршруты хрупкими и дублирует связи. Если заказ имеет глобальный `id`, детали можно получать как `/orders/99`, а `/users/42/orders` оставить для отфильтрованной коллекции. Связь также можно выразить query-параметром.

</details>

<details>
<summary><strong>Вопрос:</strong> Как моделировать действие, которое не укладывается в CRUD?</summary>

Сначала проверяют, является ли действие изменением состояния ресурса или созданием нового ресурса. Отмена заказа может быть `PATCH` с переходом статуса или `POST /orders/42/cancellations`. Подтверждение email может создавать отдельный ресурс подтверждения.

Если командный endpoint остаётся самым понятным, его используют явно. Нужно определить идемпотентность, возможные состояния, коды ответа, схему ошибки и результат повторного запроса. Искусственное маскирование команды под CRUD не улучшает контракт.

</details>

<details>
<summary><strong>Вопрос:</strong> Как версионировать REST API?</summary>

По возможности изменения делают обратно совместимыми: добавляют необязательные поля и новые endpoints, сохраняя смысл существующих. Несовместимое изменение можно вынести в path вроде `/v2`, отдельный media type или другой host. Каждый способ усложняет поддержку и развертывание.

Frontend должен терпимо относиться к неизвестным полям ответа, но не к исчезновению обязательных. Версия API не заменяет правила вывода старой версии из эксплуатации, наблюдаемость и период миграции старых клиентов.

</details>

<details>
<summary><strong>Вопрос:</strong> Как оформлять пагинацию, фильтрацию и сортировку?</summary>

Для коллекции параметры запроса обычно передают в query: `?status=active&sort=-createdAt&limit=20&cursor=...`. API документирует допустимые поля, стабильный порядок и форму метаданных или ссылки для следующей страницы.

Offset pagination, или пагинация по смещению, проста, но при изменяющемся наборе может пропускать или повторять элементы. Cursor pagination, или курсорная пагинация, устойчивее для ленты и больших данных. Cursor является opaque token, то есть непрозрачным значением: frontend не должен разбирать его внутреннюю структуру.

</details>

<details>
<summary><strong>Вопрос:</strong> Как должен выглядеть контракт ошибок API?</summary>

Код состояния задаёт общий класс, а тело ответа стабильно сообщает машинно-читаемый код, понятное сообщение, ошибки полей и correlation id, то есть идентификатор запроса для поиска в журналах. Frontend должен отличать ошибку валидации, конфликт, отсутствие доступа, превышение rate limit и временную ошибку сервера без разбора случайной строки.

Ответ с ошибкой не должен раскрывать stack trace, SQL-запросы или секретные данные. Единый формат ошибок уменьшает количество условного кода и позволяет централизованно сопоставлять сетевую ошибку с состоянием интерфейса.

</details>

<details>
<summary><strong>Вопрос:</strong> Когда REST становится неудобен по сравнению с GraphQL или RPC?</summary>

Ресурсная модель REST может требовать несколько запросов для сложного графа связанных данных, возвращать лишние поля или неудобно выражать пакетные команды. GraphQL позволяет клиенту выбрать состав связанных данных, а RPC прямо моделирует операции.

Выбор не определяется только количеством endpoints. Учитывают кэширование, авторизацию, наблюдаемость, генерацию кода, realtime, сложность backend и предсказуемость клиентов. Ресурсные endpoints, GraphQL и команды могут разумно сосуществовать.

</details>

## Где это встречается во frontend

> [!NOTE]
> | Задача | Связь с ресурсной моделью REST |
> |---|---|
> | RTK Query endpoint | метод, URI, представление и tags ресурса |
> | Таблица | ресурс коллекции, фильтрация, сортировка и пагинация |
> | Редактирование | `PUT`/`PATCH`, валидаторы версии и обработка конфликтов |
> | OpenAPI client | контракт методов, схем данных и ошибок |
> | Инвалидация кэша | тип и `id` ресурса, изменение представления |
> | Backend с несколькими экземплярами | stateless-запросы и общее хранилище сессий |
> | BFF | сбор данных для экрана из нескольких ресурсов |
