## Вопрос

<br>

 💬 **Что такое REST? Как строится ресурсная модель в HTTP API?**

<h2></h2>

<br>
<dl>
<dd>

REST, или Representational State Transfer (передача состояния через представления), — архитектурный стиль для распределённых гипермедиа-систем.

REST не является:

- сетевым протоколом;
- форматом JSON;
- соглашением о названиях URL;
- синонимом CRUD;
- обязательным набором HTTP endpoints.

Архитектурный стиль определяется совокупностью ограничений. Они уменьшают связанность компонентов, позволяют клиентам, серверам и посредникам развиваться независимо и создают свойства, необходимые системе Web: масштабируемость, кеширование и наблюдаемость взаимодействий.

HTTP хорошо поддерживает ограничения REST, но API не становится RESTful автоматически только потому, что использует JSON, URL и методы `GET`, `POST`, `PUT` и `DELETE`.

Основные ограничения REST:

| Ограничение | Смысл |
|---|---|
| Client-server | Пользовательский интерфейс и хранение данных разделены по ответственности и могут развиваться независимо |
| Stateless | Каждый запрос содержит контекст, необходимый для его обработки, и не зависит от сохранённого сервером состояния предыдущего шага диалога |
| Cacheable | Ответ определяет, можно ли и как его повторно использовать |
| Uniform interface | Все компоненты взаимодействуют через единообразную семантику ресурсов, representations, сообщений и hypermedia |
| Layered system | Клиент взаимодействует только с ближайшим компонентом и не обязан знать, находится ли дальше origin server, proxy, gateway или cache |
| Code on demand | Необязательное ограничение: сервер может расширять клиент, передавая исполняемый код, например JavaScript |

Client-server разделяет ответственность.

Клиент отвечает за пользовательский интерфейс и управление состоянием взаимодействия пользователя. Сервер отвечает за хранение ресурсов, бизнес-правила и доступ к данным.

Благодаря этому frontend можно изменять без замены серверного хранилища, а backend — масштабировать и перестраивать без изменения интерфейса пользователя, пока сохраняется контракт взаимодействия.

Resource, или ресурс, — ключевая абстракция REST.

Ресурсом может быть любое понятие, которому можно назначить идентификатор:

- пользователь;
- заказ;
- коллекция комментариев;
- текущая погода;
- состояние фоновой задачи;
- настройки текущего пользователя;
- результат поиска;
- документ;
- изображение.

Ресурс не обязательно равен строке базы данных или физическому файлу. Это концептуальная цель обращения, значение которой может изменяться со временем.

Например:

```text
/users/42
```

может продолжать идентифицировать одного пользователя, хотя его имя, фотография и настройки меняются.

Ресурс идентифицируется URI:

```text
https://api.example.com/users/42
```

URI является идентификатором ресурса, а не самим ресурсом и не обязательно адресом таблицы или файла внутри backend.

Representation, или представление, — данные, передаваемые между компонентами и описывающие текущее или желаемое состояние ресурса.

Например:

```http
GET /users/42
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
ETag: "user-42-v5"

{
  "id": 42,
  "name": "Ada"
}
```

JSON является представлением ресурса пользователя, а не самим пользователем.

Один ресурс может иметь разные representations:

- JSON для API;
- HTML для браузера;
- сокращённый объект для списка;
- подробный объект для карточки;
- локализованное представление;
- представление с учётом прав пользователя;
- изображение в разных форматах.

Выбор может зависеть от:

- `Accept`;
- `Accept-Language`;
- других заголовков согласования;
- прав пользователя;
- параметров запроса;
- возможностей сервера.

Сервер сообщает фактический формат через:

```http
Content-Type: application/json
```

Если ответ меняется в зависимости от request headers, сервер может использовать `Vary`, чтобы кеш различал варианты:

```http
Vary: Accept, Accept-Language
```

Representation не обязано содержать все поля внутренней server-side-модели. Оно является частью публичного контракта и может скрывать технические или недоступные пользователю данные.

Uniform interface, или единообразный интерфейс, является центральным ограничением REST.

Он состоит из четырёх частей:

| Часть uniform interface | Смысл |
|---|---|
| Identification of resources | Ресурсы имеют устойчивые идентификаторы |
| Manipulation through representations | Клиент изменяет ресурс, передавая representation желаемого состояния или изменения |
| Self-descriptive messages | Каждое сообщение содержит достаточно информации для понимания его семантики |
| Hypermedia as the engine of application state | Доступные переходы клиент узнаёт из полученных representations и links |

В HTTP часть семантики выражается стандартными элементами протокола:

- request method;
- target URI;
- status code;
- headers;
- media type;
- validators;
- link relations;
- representation.

Например:

```text
GET /orders/42
```

запрашивает текущее выбранное представление заказа.

```text
PUT /orders/42
```

передаёт representation состояния, которое должно быть установлено для известного URI согласно контракту ресурса.

```text
PATCH /orders/42
```

передаёт patch-документ определённого media type.

```text
DELETE /orders/42
```

просит удалить связь текущего ресурса с указанным URI.

Метод и URI рассматриваются вместе:

```text
method + target resource
```

Смысл действия не должен быть скрыт только в произвольном поле тела:

```http
POST /execute

{
  "method": "deleteOrder",
  "id": 42
}
```

Такой API может быть корректным RPC over HTTP, но посредники не видят бизнес-семантику операции через стандартный HTTP-интерфейс.

Self-descriptive message, или самодостаточное сообщение, содержит достаточно метаданных, чтобы получатель и посредники понимали правила обработки.

Например:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=60
ETag: "user-42-v5"
Link: </users/42/orders>; rel="related"
```

Из сообщения видно:

- результат операции;
- формат содержимого;
- правила кеширования;
- версия representation;
- связь с другим ресурсом.

Один `Content-Type: application/json` описывает синтаксис JSON, но не всю бизнес-семантику полей. Дополнительный контракт может определяться media type, schema, link relations, OpenAPI-документом и документацией API.

Stateless означает отсутствие server-side session state между запросами в строгой REST-модели.

Каждый запрос должен быть понятен независимо от предыдущих:

```http
GET /orders/42
Authorization: Bearer <access-token>
Accept: application/json
```

Запрос содержит:

- target URI;
- authentication context;
- условия запроса;
- поддерживаемые форматы;
- при необходимости representation.

Серверу не требуется помнить:

```text
этот клиент ранее выполнил шаг 1
и теперь должен выполнить шаг 2
```

если текущий запрос сам не выражает этот переход.

Stateless не означает, что сервер вообще не хранит состояние.

Сервер хранит resource state:

- пользователей;
- заказы;
- платежи;
- роли;
- настройки;
- историю операций;
- выданные полномочия;
- состояние фоновых задач.

Ограничение относится к session state, то есть к контексту текущего диалога клиента с сервером.

В строгом REST состояние приложения и навигации между шагами находится у клиента и передаётся через representations, ссылки, URI и новые запросы.

Традиционная server-side session, где cookie содержит только случайный идентификатор, а сервер хранит связанный с ним контекст диалога, не соответствует строгому stateless-ограничению:

```text
Cookie: sessionId=abc
                 │
                 └─ сервер ищет сохранённый контекст сессии
```

Перенос session store в Redis или другую общую базу позволяет обрабатывать запросы разными экземплярами приложения и устраняет необходимость sticky sessions.

Это улучшает горизонтальное масштабирование, но не делает взаимодействие строго REST-stateless: сервер всё ещё хранит session state между запросами.

При этом использование cookie само по себе не нарушает stateless.

Cookie может переносить самодостаточный подписанный token либо другие данные, необходимые запросу. Важен не механизм передачи credentials, а наличие или отсутствие скрытого server-side-контекста предыдущего взаимодействия.

Stateless также не требует JWT. Сервер может проверять opaque access token через отдельное хранилище полномочий. Если это хранилище описывает состояние выданного доступа, а не шаги клиентского диалога, запрос всё ещё может быть самодостаточным на уровне взаимодействия.

Важно различать:

```text
resource state
session state
application state
authentication state
```

Эти понятия связаны, но не являются одним и тем же.

Cacheable означает, что ответ сообщает возможность повторного использования.

Ответ может быть:

- явно кешируемым;
- явно некешируемым;
- кешируемым только в private cache;
- требующим повторной проверки;
- различающим варианты через `Vary`.

Например:

```http
Cache-Control: public, max-age=300
ETag: "catalog-v7"
```

Кеширование может полностью устранить повторное обращение к серверу либо заменить передачу полного тела условным запросом.

REST не требует кешировать каждый ответ. Ответ с персональными или быстро меняющимися данными может содержать:

```http
Cache-Control: no-store
```

Главное — чтобы правила повторного использования были определены, а не оставались скрытыми в бизнес-логике клиента.

Layered system означает, что клиент взаимодействует только с ближайшим компонентом.

Схема может выглядеть так:

```text
frontend
→ CDN
→ reverse proxy
→ API gateway
→ application service
→ internal service
```

Frontend не обязан знать, какой компонент сформировал или получил representation, если промежуточные слои сохраняют публичную семантику сообщения.

Посредники могут:

- кешировать;
- балансировать нагрузку;
- проверять аутентификацию;
- ограничивать частоту;
- сжимать данные;
- выполнять маршрутизацию;
- добавлять tracing.

Самодостаточные сообщения и единообразный интерфейс позволяют посредникам обрабатывать запросы без знания всей бизнес-логики.

Code on demand является единственным необязательным ограничением REST.

Сервер может отправить исполняемый код, который расширяет возможности клиента. Главный пример в Web — JavaScript, загружаемый браузером.

Это повышает расширяемость, но уменьшает наблюдаемость: посреднику сложнее заранее понять полное поведение загруженного кода.

HATEOAS (Hypermedia as the Engine of Application State) означает, что клиент получает доступные переходы из текущего representation.

Например:

```json
{
  "id": "42",
  "status": "pending",
  "links": {
    "self": {
      "href": "/orders/42"
    },
    "payment": {
      "href": "/orders/42/payment",
      "method": "POST"
    },
    "cancellation": {
      "href": "/orders/42/cancellation",
      "method": "POST"
    }
  }
}
```

После оплаты сервер может вернуть другое представление, в котором ссылки `payment` и `cancellation` уже отсутствуют, но появилась ссылка `receipt`.

Клиент знает:

- media type;
- семантику link relations;
- правила обработки representations;
- начальную точку входа.

Но он не обязан заранее жёстко хранить каждый возможный URL и переход состояния.

Hypermedia control может быть представлен:

- ссылкой в теле;
- формой;
- кнопкой с описанной операцией;
- заголовком `Link`;
- другим элементом конкретного media type.

Link relation сообщает смысл связи, например:

```http
Link: </orders?cursor=abc>; rel="next"
```

Само наличие поля `next` в одном ответе ещё не означает полную реализацию HATEOAS. В полноценной hypermedia-driven-системе доступные действия и переходы системно определяются representations.

Большинство frontend JSON APIs не реализует HATEOAS полностью.

Frontend обычно заранее знает:

- endpoints;
- маршруты;
- названия операций;
- структуру workflow.

Поэтому такие системы точнее называть:

```text
resource-oriented HTTP API
```

или:

```text
REST-inspired API
```

Они используют полезные свойства HTTP и часть REST-ограничений, но не обязательно соответствуют полному архитектурному стилю.

При проектировании ресурсно-ориентированного API обычно выделяют:

- отдельные ресурсы;
- коллекции ресурсов;
- отношения между ресурсами;
- representations;
- операции изменения;
- условия конкурентного обновления;
- правила кеширования;
- ссылки и доступные переходы;
- единый контракт ошибок.

Например:

```text
/users
/users/42
/users/42/orders
/orders/99
/orders/99/cancellation
```

Коллекция тоже является ресурсом:

```text
GET /users?status=active
```

Query-параметры выбирают representation коллекции:

- фильтр;
- сортировку;
- страницу;
- cursor;
- набор полей.

Они не обязательно создают новый тип сущности backend, но полный URI идентифицирует конкретную цель запроса и вариант выборки.

Изменения ресурса полезно защищать от потерянного обновления.

Клиент получает:

```http
ETag: "order-42-v5"
```

и при редактировании отправляет:

```http
If-Match: "order-42-v5"
```

Если ресурс уже изменён, сервер возвращает:

```http
412 Precondition Failed
```

Frontend не перезаписывает чужое изменение и предлагает пользователю обновить данные или разрешить конфликт.

Для ошибок API можно определить собственный стабильный формат либо использовать Problem Details из RFC 9457:

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json
```

```json
{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Request validation failed",
  "status": 422,
  "detail": "One or more fields are invalid",
  "instance": "/requests/01HXYZ",
  "errors": [
    {
      "pointer": "/email",
      "code": "EMAIL_TAKEN"
    }
  ]
}
```

Стандартные поля Problem Details:

- `type` — стабильный идентификатор типа проблемы;
- `title` — краткое описание типа;
- `status` — HTTP-статус;
- `detail` — детали конкретного случая;
- `instance` — идентификатор конкретного возникновения проблемы.

Ошибки полей, машинные коды и другие данные добавляют как extensions конкретного problem type.

Correlation ID не является обязательным стандартным полем Problem Details. Его можно передавать отдельным заголовком:

```http
X-Request-Id: 01HXYZ
```

либо документированным extension-полем.

Resource-oriented API, GraphQL и RPC не исключают друг друга.

Например:

- обычные сущности и файлы обслуживаются HTTP resources;
- сложный экран получает агрегированные данные через BFF или GraphQL;
- бизнес-команда вызывается через RPC endpoint;
- realtime-изменения приходят через SSE или WebSocket.

Главный критерий — не формальная чистота названий, а согласованная семантика, предсказуемое поведение посредников и понятный контракт между командами.

## Дополнительные вопросы

<details>
<summary><strong>Чем resource, или ресурс, отличается от representation, или представления?</strong></summary>

<dl>
<dd>
<h2></h2>

Ресурс — концептуальная цель обращения, которой назначен идентификатор.

Например:

```text
/users/42
```

идентифицирует пользователя `42`.

Representation — данные, передаваемые клиенту или серверу и описывающие состояние ресурса:

```json
{
  "id": 42,
  "name": "Ada"
}
```

Ресурс сохраняет идентичность, хотя его состояние и representations могут меняться.

Один ресурс может иметь:

- JSON-представление;
- HTML-представление;
- сокращённый вариант для списка;
- подробный вариант;
- разные языковые варианты;
- разные представления для разных прав.

`Content-Type` сообщает media type переданного representation.

`ETag` является validator, то есть идентификатором версии выбранного representation, а не глобальным номером всей внутренней server-side-сущности во всех форматах.

</dd>
</dl>

</details>

<details>
<summary><strong>Что на практике означает stateless API?</strong></summary>

<dl>
<dd>
<h2></h2>

Каждый запрос содержит информацию, необходимую для его обработки:

- URI;
- credentials;
- representation;
- условия;
- параметры;
- заголовки согласования.

Обработчик не должен зависеть от скрытого знания:

```text
предыдущий запрос этого клиента был шагом 1
```

В строгом REST session state хранится у клиента.

Сервер при этом продолжает хранить resource state: пользователей, заказы, права, задачи и другие данные системы.

Обычная server-side session с идентификатором в cookie хранит контекст между запросами и поэтому не соответствует строгому REST stateless.

Общий session store позволяет обрабатывать запросы разными экземплярами и устраняет sticky session, но решает задачу масштабирования, а не полностью выполняет REST-ограничение.

Stateless не требует JWT. Важна независимость текущего запроса от сохранённого контекста предыдущих шагов, а не конкретный формат token.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>REST требует JSON и HTTP?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

REST является архитектурным стилем и не привязан к JSON. В Web используются:

- HTML;
- JSON;
- XML;
- изображения;
- видео;
- другие media types.

REST также не определяется конкретным сетевым протоколом, хотя HTTP предоставляет почти все необходимые механизмы:

- URI;
- методы;
- статусы;
- заголовки;
- content negotiation;
- кеширование;
- conditional requests;
- links;
- intermediaries.

API, возвращающий JSON по HTTP, может оставаться RPC:

```http
POST /execute

{
  "procedure": "createUser"
}
```

Формат и транспорт сами по себе не определяют архитектурный стиль.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое uniform interface?</strong></summary>

<dl>
<dd>
<h2></h2>

Uniform interface, или единообразный интерфейс, уменьшает связанность между компонентами.

Он включает четыре ограничения:

1. Идентификацию ресурсов.
2. Изменение ресурсов через representations.
3. Самодостаточные сообщения.
4. Hypermedia как механизм переходов состояния приложения.

В HTTP это выражается через:

- URI;
- методы;
- коды состояния;
- заголовки;
- media types;
- validators;
- links.

Корректные названия endpoints являются полезным соглашением, но не заменяют остальные части uniform interface.

Цена единообразия состоит в том, что общий интерфейс иногда менее эффективен, чем специализированная процедура для конкретного экрана или операции.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое HATEOAS?</strong></summary>

<dl>
<dd>
<h2></h2>

HATEOAS означает, что клиент узнаёт доступные переходы из полученного representation.

Например, заказ может содержать ссылки:

```json
{
  "links": {
    "payment": {
      "href": "/orders/42/payment",
      "method": "POST"
    },
    "cancellation": {
      "href": "/orders/42/cancellation",
      "method": "POST"
    }
  }
}
```

После изменения состояния набор доступных links меняется.

Клиент заранее знает правила media type и значения link relations, но не обязан жёстко хранить все адреса workflow.

Hypermedia может передаваться в теле или через HTTP `Link`.

Большинство frontend JSON APIs знает endpoints заранее и не реализует этот принцип полностью.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли считать API без HATEOAS полноценным REST?</strong></summary>

<dl>
<dd>
<h2></h2>

В строгом смысле нет.

Hypermedia as the Engine of Application State является одной из четырёх частей REST uniform interface.

API без hypermedia может качественно использовать:

- ресурсы;
- HTTP-методы;
- статусы;
- кеширование;
- stateless-запросы;
- conditional requests.

Но точнее называть его resource-oriented, HTTP API или REST-inspired API.

В практической разработке слово REST часто используется шире исходного определения. Важно понимать, какие ограничения система действительно выполняет, а не спорить только о названии.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Должны ли REST endpoints содержать только существительные?</strong></summary>

<dl>
<dd>
<h2></h2>

Ресурсно-ориентированный дизайн обычно выражает адресуемые понятия существительными:

```text
/orders/42
/users/7/orders
```

Смысл операции задаёт HTTP-метод:

```text
GET /users/42
DELETE /users/42
```

Поэтому endpoint:

```text
GET /getUserById
```

дублирует семантику метода и выглядит как удалённая процедура.

Но требование «только существительные» не является отдельным формальным ограничением REST.

URI рассматривается клиентом прежде всего как идентификатор. Семантику взаимодействия должны задавать метод, media type, representation и links, а не попытка клиента разобрать слова в URL.

Для сложной бизнес-команды понятный командный endpoint иногда лучше искусственной ресурсной модели.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда использовать вложенный URL ресурса?</strong></summary>

<dl>
<dd>
<h2></h2>

Вложенный URL выражает отношение или область:

```text
/users/42/orders
```

Он удобен, когда родитель:

- задаёт область коллекции;
- необходим для идентификации;
- влияет на авторизацию;
- является естественной точкой навигации.

Если заказ имеет глобальный идентификатор, детали можно получать независимо:

```text
/orders/99
```

а вложенный endpoint оставить для коллекции заказов пользователя:

```text
/users/42/orders
```

Слишком глубокая вложенность:

```text
/companies/1/departments/2/users/3/orders/4/items/5
```

делает URI хрупким и дублирует связи данных.

Обычно достаточно одного или двух уровней, а дальнейшие связи выражаются отдельными ресурсами, links или query-параметрами.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как моделировать действие, которое не укладывается в CRUD?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала определяют, является ли действие:

- изменением состояния существующего ресурса;
- созданием нового ресурса;
- запуском долгой операции;
- самостоятельной бизнес-командой.

Отмена заказа может быть изменением состояния:

```http
PATCH /orders/42
Content-Type: application/merge-patch+json

{
  "status": "cancelled"
}
```

Либо созданием ресурса отмены:

```text
POST /orders/42/cancellations
```

Долгую операцию можно представить отдельным ресурсом задачи:

```text
POST /reports
202 Accepted
Location: /report-jobs/123
```

Если явный command endpoint остаётся наиболее понятным:

```text
POST /orders/42/cancel
```

его можно использовать.

Нужно документировать:

- идемпотентность;
- допустимые состояния;
- результат повторного запроса;
- коды ответа;
- схему ошибки;
- конкурентные изменения.

Искусственное маскирование команды под CRUD не делает контракт автоматически лучше.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как версионировать REST API?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала стараются развивать контракт обратно совместимо:

- добавлять необязательные поля;
- добавлять новые ресурсы;
- добавлять новые endpoints;
- не менять смысл существующего поля;
- поддерживать старые link relations;
- заранее помечать устаревающие возможности.

Несовместимую версию можно вынести:

```text
/api/v2/users
```

в отдельный host:

```text
https://api-v2.example.com
```

либо в отдельный media type.

Каждый способ увеличивает стоимость поддержки: нужно параллельно развёртывать версии, тестировать их и мигрировать клиентов.

Frontend должен игнорировать неизвестные поля ответа, если контракт не запрещает их, но не обязан выдерживать исчезновение обязательного поля или изменение его типа.

Номер версии не заменяет:

- период миграции;
- deprecation policy;
- мониторинг использования;
- дату отключения;
- поддержку старых мобильных клиентов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как оформлять пагинацию, фильтрацию и сортировку?</strong></summary>

<dl>
<dd>
<h2></h2>

Для representation коллекции параметры обычно передают в query:

```text
?status=active&sort=-createdAt&limit=20&cursor=...
```

API документирует:

- разрешённые фильтры;
- поля сортировки;
- стабильный уникальный порядок;
- максимальный размер страницы;
- формат cursor;
- метаданные или links следующей страницы.

Offset pagination проста и позволяет перейти к номеру страницы, но при изменяющемся наборе может пропускать или повторять элементы.

Cursor pagination удобна для последовательной загрузки. Сам cursor является opaque token, то есть непрозрачным значением: frontend не должен самостоятельно разбирать или создавать его.

Ответ может содержать hypermedia link:

```http
Link: </orders?cursor=abc>; rel="next"
```

либо аналогичное поле в representation.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как должен выглядеть контракт ошибок API?</strong></summary>

<dl>
<dd>
<h2></h2>

HTTP status code задаёт общий класс результата, а тело содержит стабильные машинно-читаемые детали.

API может использовать собственный формат или `application/problem+json` из RFC 9457:

```json
{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Request validation failed",
  "status": 422,
  "detail": "One or more fields are invalid",
  "instance": "/requests/01HXYZ",
  "errors": [
    {
      "pointer": "/email",
      "code": "EMAIL_TAKEN"
    }
  ]
}
```

Frontend должен отличать:

- validation error;
- conflict;
- authentication error;
- отсутствие прав;
- rate limit;
- временную server-side-ошибку.

Для программной логики используют стабильный `type`, `code` или другое документированное поле, а не разбор пользовательской строки `message`.

Correlation ID можно передавать заголовком или extension-полем, но он не относится к обязательным стандартным полям Problem Details.

Ответ не должен раскрывать:

- stack trace;
- SQL;
- внутренние пути;
- секреты;
- подробности, упрощающие атаку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда REST становится неудобен по сравнению с GraphQL или RPC?</strong></summary>

<dl>
<dd>
<h2></h2>

Ресурсный HTTP API может быть неудобен, когда экрану требуется сложный граф данных из множества ресурсов.

Frontend тогда выполняет несколько запросов либо использует специальный BFF endpoint.

GraphQL позволяет клиенту выбрать состав связанных данных, а RPC прямо моделирует бизнес-операции.

REST и resource-oriented API особенно полезны, когда важны:

- стандартная HTTP-семантика;
- кеширование;
- независимые ресурсы;
- простая диагностика;
- CDN;
- conditional requests;
- понятные операции над сущностями.

GraphQL удобен для сложных связанных выборок, а RPC — для операций, естественно представленных командами.

Подходы могут сосуществовать в одной системе. Выбор зависит от полной стоимости контракта, а не только от количества endpoints.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Задача | Связь с ресурсной моделью REST |
|---|---|
| RTK Query endpoint | Метод, URI, representation и tags ресурса |
| Таблица | Ресурс коллекции, фильтрация, сортировка и пагинация |
| Редактирование | `PUT`/`PATCH`, `ETag`, `If-Match` и обработка конфликтов |
| OpenAPI client | Контракт методов, representations и ошибок |
| Инвалидация кеша | Тип и `id` ресурса, изменение связанных representations |
| Backend с несколькими экземплярами | Независимые запросы и отсутствие instance-local session context |
| BFF | Сбор representations для конкретного экрана |
| Обработка ошибок | HTTP status и стабильный Problem Details-контракт |
| Навигация API | Links и link relations между ресурсами |
