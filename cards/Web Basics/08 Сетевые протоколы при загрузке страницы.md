## Вопрос

<br>

 💬 **Что такое DNS, TCP, UDP, HTTP/2 и HTTP/3? Как они участвуют в загрузке страницы?**

<h2></h2>

<br>
<dl>
<dd>

Загрузка страницы проходит через несколько уровней сетевых протоколов.

DNS помогает найти сетевые адреса и параметры сервиса по доменному имени. Затем браузер устанавливает или переиспользует транспортное соединение. HTTP/1.1 и HTTP/2 обычно работают поверх TCP, а HTTP/3 — поверх QUIC, который передаёт пакеты через UDP.

Уже по этому транспорту браузер отправляет HTTP-запросы и получает HTTP-ответы.

Упрощённая последовательность выглядит так:

1. Браузер разбирает URL и получает hostname, например `example.com`.
2. Проверяет HTTP-кеш, Service Worker, существующие соединения и DNS-кеши.
3. При необходимости получает через DNS адреса `A`/`AAAA` и дополнительные сведения о сервисе.
4. Выбирает подходящий IP-адрес и сетевой маршрут, иногда параллельно проверяя IPv6 и IPv4.
5. Определяет поддерживаемый вариант HTTP.
6. Для HTTP/1.1 или HTTP/2 устанавливает TCP-соединение и выполняет TLS handshake при HTTPS.
7. Для HTTP/3 устанавливает QUIC-соединение, в которое встроен TLS 1.3.
8. Отправляет HTTP-запрос и получает документ.
9. Разбирает HTML и запрашивает дополнительные ресурсы: CSS, JavaScript, изображения и шрифты.

Этапы не всегда выполняются последовательно с нуля.

Например:

- DNS-ответ уже может находиться в кеше;
- TCP-, TLS- или QUIC-соединение может быть открыто;
- HTTP-response может прийти из кеша;
- браузер может заранее выполнить `preconnect`;
- Service Worker может вернуть собственный response без сетевого запроса к origin server;
- несколько адресов или вариантов соединения могут проверяться параллельно.

**DNS (Domain Name System, система доменных имён)** является распределённой системой данных, которая сопоставляет доменные имена с DNS-записями.

Для загрузки сайта особенно важны:

| Запись | Назначение |
|---|---|
| `A` | IPv4-адрес |
| `AAAA` | IPv6-адрес |
| `CNAME` | каноническое имя, на которое ссылается alias |
| `HTTPS` | параметры HTTP-сервиса, альтернативные endpoints и поддерживаемые протоколы |
| `NS` | authoritative servers DNS-зоны |

DNS не обязательно возвращает только один IP-адрес. Один hostname может иметь:

- несколько IPv4-адресов;
- несколько IPv6-адресов;
- alias через `CNAME`;
- разные ответы в зависимости от региона;
- адрес ближайшего CDN-узла;
- параметры сервиса через `HTTPS` resource record.

Сначала браузер, операционная система или локальный сетевой слой проверяет доступные кеши.

Если готового ответа нет, запрос обычно получает recursive resolver, или рекурсивный DNS-резолвер. Это может быть resolver:

- интернет-провайдера;
- корпоративной сети;
- публичного DNS-сервиса;
- браузера;
- VPN.

Recursive resolver должен вернуть клиенту конечный ответ или ошибку. Если нужной записи нет в его кеше, он выполняет дальнейшее разрешение имени.

Упрощённо он может обратиться:

```text
root server
→ server доменной зоны, например .com
→ authoritative server домена
```

Root server не хранит IP-адрес каждого сайта. Он сообщает, какие servers обслуживают нужную верхнеуровневую зону.

Server зоны `.com` сообщает authoritative servers для `example.com`.

Authoritative server возвращает данные зоны, например записи `A`, `AAAA`, `CNAME` или `HTTPS`.

На практике часть шагов обычно пропускается благодаря DNS-кешам.

TTL (Time To Live) указывает, сколько времени запись разрешено считать пригодной для использования в кеше.

Например:

```text
example.com. 300 IN A 192.0.2.10
```

означает TTL, равный 300 секундам.

Пока запись находится в пределах TTL, resolver обычно может вернуть её без нового обращения к authoritative server.

Низкий TTL позволяет быстрее переключить клиентов на новый адрес, но увеличивает количество DNS-запросов.

Высокий TTL уменьшает нагрузку и задержку повторных разрешений, но часть клиентов дольше использует старый ответ после изменения записи.

Фактическое переключение зависит не только от TTL:

- существуют кеши на разных уровнях;
- браузер может иметь собственную политику кеширования;
- уже установленное соединение может продолжать работать со старым адресом;
- CDN и load balancer могут менять маршрутизацию без изменения DNS;
- некоторые resolvers при сбое могут временно использовать stale data.

DNS помогает найти endpoint, но не передаёт HTTP-запрос до приложения и не выбирает маршрут каждого IP-пакета.

Сам DNS также может использовать разные транспорты:

- UDP;
- TCP;
- DNS over TLS;
- DNS over HTTPS;
- DNS over QUIC.

Поэтому выражение «DNS всегда работает через UDP» неверно.

Обычный небольшой DNS-запрос часто передаётся через UDP. TCP может использоваться, например, если ответ не помещается в доступную датаграмму, требуется повтор после усечённого ответа или выбран соответствующий режим работы.

Зашифрованные DNS-протоколы скрывают содержимое DNS-запроса от части промежуточных наблюдателей, но не отменяют необходимость получить сетевой адрес сервиса.

Если DNS возвращает и IPv6-, и IPv4-адреса, браузер не обязан последовательно ждать полного сбоя одного семейства.

Алгоритмы семейства Happy Eyeballs позволяют с небольшой задержкой проверять несколько подходящих вариантов и использовать соединение, которое успешно установилось первым.

Упрощённо:

```text
AAAA → попытка IPv6
A    → попытка IPv4

успешный подходящий маршрут → используется
остальные попытки → отменяются
```

Это предотвращает долгую задержку, если IPv6 формально доступен, но конкретный маршрут не работает.

**TCP (Transmission Control Protocol, протокол управления передачей)** предоставляет надёжный упорядоченный поток байтов между двумя endpoints.

Перед обычной передачей данных устанавливается соединение с помощью three-way handshake:

```text
клиент → SYN
сервер → SYN-ACK
клиент → ACK
```

`SYN` начинает установление соединения и передаёт начальный sequence number клиента.

`SYN-ACK` подтверждает данные клиента и сообщает начальный sequence number сервера.

Завершающий `ACK` подтверждает ответ сервера.

После этого стороны могут передавать данные.

TCP:

- нумерует байты;
- подтверждает полученные диапазоны;
- обнаруживает потерю;
- повторно передаёт неподтверждённые данные;
- устраняет дубликаты;
- восстанавливает порядок;
- контролирует объём данных, который способен принять получатель;
- регулирует скорость с учётом перегрузки сети.

TCP предоставляет поток байтов, а не поток HTTP-сообщений.

Например, один вызов отправки приложения не обязан соответствовать одному получению на другой стороне. Данные могут быть разделены на несколько TCP-segments или объединены.

Границы HTTP messages определяет HTTP/1.1 framing либо HTTP/2 frames, а не TCP.

Надёжность TCP не означает, что соединение никогда не оборвётся.

Она означает, что пока соединение можно поддерживать, TCP старается предоставить приложению байты:

```text
без пропусков
без дубликатов
в правильном порядке
```

Если соединение окончательно потеряно, приложение не всегда знает, успел ли сервер обработать уже отправленный HTTP-запрос. Поэтому правила retry дополнительно зависят от идемпотентности операции.

TCP использует два связанных, но разных механизма управления скоростью:

- **Flow control** защищает получателя от отправителя, который передаёт данные быстрее, чем получатель может их принять.
- **Congestion control** защищает сеть от чрезмерной нагрузки и регулирует скорость на основе признаков перегрузки.

Потерянные TCP-данные создают transport head-of-line blocking.

Даже если последующие сегменты уже пришли, TCP не выдаёт приложению более поздние байты до восстановления пропуска:

```text
получено: 1, 2, _, 4, 5
приложение ждёт сегмент 3
```

Это особенно заметно для HTTP/2, где несколько HTTP-streams используют один общий упорядоченный TCP-поток.

**UDP (User Datagram Protocol, протокол пользовательских датаграмм)** передаёт отдельные datagrams между endpoints.

Каждая UDP-датаграмма имеет собственную границу сообщения.

Сам UDP:

- не устанавливает TCP-подобное соединение;
- не гарантирует доставку;
- не гарантирует порядок;
- не устраняет дубликаты;
- не выполняет повторную передачу;
- не предоставляет готовое congestion control.

Это не означает, что протокол поверх UDP не может устанавливать логическое соединение и обеспечивать надёжность.

Например, QUIC использует UDP как базовый интерфейс передачи датаграмм, но самостоятельно реализует:

- установление защищённого соединения;
- подтверждения;
- повторную передачу;
- контроль перегрузки;
- flow control;
- упорядоченные streams.

Поэтому утверждение «UDP всегда быстрее TCP» некорректно.

UDP предоставляет меньше готовых транспортных гарантий. Производительность зависит от того, какие механизмы реализует протокол верхнего уровня и насколько они подходят конкретной задаче.

**QUIC** является защищённым мультиплексированным транспортным протоколом поверх UDP.

HTTP/3 использует QUIC, но QUIC не является только частью HTTP/3: поверх него могут работать и другие прикладные протоколы.

QUIC предоставляет:

- защищённое установление соединения с TLS 1.3;
- надёжные упорядоченные streams;
- независимую повторную передачу данных streams;
- flow control;
- congestion control;
- connection IDs;
- возможность миграции соединения между сетевыми путями;
- session resumption;
- возможность `0-RTT` для повторного соединения.

TLS 1.3 встроен в установление QUIC-соединения. Нельзя использовать обычный незашифрованный QUIC для HTTP/3.

QUIC обычно реализуется в user space, то есть внутри браузера или server application, поверх широко поддерживаемого UDP-интерфейса.

Это позволяет обновлять транспортный протокол быстрее, чем если бы каждое изменение требовало обновления TCP-стека операционной системы и сетевого оборудования.

Connection ID позволяет QUIC идентифицировать соединение не только по комбинации IP-адресов и портов.

Благодаря этому соединение может пережить смену сетевого пути, например переход с Wi-Fi на мобильную сеть, если:

- клиент и сервер поддерживают migration;
- новый путь успешно проверен;
- политика приложения и сети разрешает продолжение;
- соединение ещё не было окончательно закрыто.

Миграция не является гарантией сохранения любого соединения при любой смене сети.

QUIC предоставляет несколько логически независимых streams внутри одного соединения.

Потеря данных одного stream не требует задерживать выдачу уже полученных данных другого stream:

```text
stream A: потеряна часть данных → A ждёт повтор
stream B: данные получены       → B может продолжаться
```

При этом независимость streams не означает полную независимость производительности.

Все streams одного QUIC-соединения обычно используют общий сетевой путь и общую congestion control. Потеря пакетов может уменьшить допустимую скорость всего соединения, поэтому остальные streams тоже могут передаваться медленнее.

Потерянные данные внутри конкретного stream по-прежнему создают ожидание последующих байтов этого же stream.

QUIC поддерживает `0-RTT` при возобновлении ранее установленного соединения. Клиент может отправить часть данных до завершения нового handshake.

Это уменьшает задержку, но ранние данные могут быть повторно воспроизведены. Поэтому их используют только для операций, которые безопасно повторить или дополнительно защищены от replay.

Версии HTTP различаются прежде всего способом передачи одной и той же HTTP-семантики:

| Версия HTTP | Обычный транспорт | Что важно |
|---|---|---|
| HTTP/1.1 | TCP | Persistent connections, текстовое framing сообщений, отсутствие полноценного multiplexing в одном соединении |
| HTTP/2 | TCP | Binary framing, multiplexing streams и HPACK-сжатие заголовков |
| HTTP/3 | QUIC поверх UDP | Независимые QUIC-streams, QPACK-сжатие и встроенная защита TLS 1.3 |

HTTP-методы, коды состояния и основная семантика сохраняются между версиями:

```text
GET
POST
200
404
Cache-Control
Content-Type
```

Frontend-код через `fetch()` обычно не формирует HTTP frames и не выбирает версию протокола вручную. Этим управляют браузер и серверная инфраструктура.

**HTTP/1.1** поддерживает persistent connections: после одного request/response TCP-соединение можно оставить открытым и использовать снова.

Без повторного использования каждый новый origin мог бы потребовать:

```text
TCP handshake
+
TLS handshake
+
HTTP request
```

HTTP/1.1 не предоставляет полноценного multiplexing независимых ответов в одном соединении.

Стандарт допускает HTTP pipelining, при котором клиент отправляет несколько запросов, не ожидая предыдущих ответов. Но ответы всё равно должны возвращаться в порядке запросов, поэтому медленный первый ответ задерживает следующие.

Браузеры исторически не полагаются на HTTP/1.1 pipelining и обычно открывают несколько параллельных соединений к origin, чтобы загружать несколько ресурсов одновременно.

Большое количество соединений тоже имеет цену:

- дополнительные handshakes;
- отдельная congestion control;
- больше ресурсов браузера и сервера;
- конкуренция сетевых потоков.

**HTTP/2** сохраняет HTTP-семантику, но использует бинарный framing layer.

HTTP message разбивается на frames, например:

- `HEADERS`;
- `DATA`;
- `SETTINGS`;
- `WINDOW_UPDATE`;
- `RST_STREAM`.

Каждый frame принадлежит определённому stream.

Stream является двунаправленным логическим потоком внутри одного HTTP/2-соединения. Один обмен request/response обычно использует один stream.

Multiplexing позволяет чередовать frames разных streams:

```text
HEADERS stream 1
HEADERS stream 3
DATA stream 1
DATA stream 3
DATA stream 1
```

Получатель собирает данные каждого stream по его идентификатору.

Благодаря этому медленный HTTP-response не обязан на уровне HTTP/2 полностью завершиться до начала передачи другого response.

HTTP/2 использует HPACK для сжатия полей HTTP. Он уменьшает повторную передачу одинаковых названий и значений заголовков.

HTTP/2 также имеет flow control:

- для отдельного stream;
- для всего соединения.

Это позволяет получателю ограничивать объём данных, который отправитель может передать до получения `WINDOW_UPDATE`.

В браузерном HTTPS HTTP/2 обычно согласуется через ALPN во время TLS handshake.

Клиент предлагает, например:

```text
h2
http/1.1
```

Сервер выбирает поддерживаемый вариант без дополнительного HTTP round trip.

Спецификация также описывает HTTP/2 без TLS, который называют `h2c`, но обычная браузерная загрузка сайтов практически использует HTTP/2 через HTTPS.

HTTP/2 не устраняет transport head-of-line blocking TCP.

Все streams одного соединения сериализуются в общий TCP-поток. Если потерян TCP-сегмент, более поздние байты временно не передаются HTTP/2-реализации, даже если они относятся к другому stream.

**HTTP/3** переносит HTTP-семантику на QUIC.

Каждый HTTP request/response использует QUIC-stream. Потеря данных одного stream не заставляет транспорт ждать их восстановления перед выдачей данных других streams.

HTTP/3 использует QPACK для сжатия HTTP fields.

QPACK спроектирован с учётом независимых QUIC-streams. Однако сжатие может создавать зависимости: если декодирование headers требует ещё не полученной записи динамической таблицы, обработка конкретного stream временно блокируется.

Поэтому корректнее говорить:

```text
HTTP/3 устраняет TCP head-of-line blocking между streams
```

а не:

```text
HTTP/3 полностью устраняет любые блокировки
```

HTTP/3 endpoint может быть обнаружен несколькими способами.

Origin может сообщить о нём в HTTP-response:

```http
Alt-Svc: h3=":443"
```

Браузер запоминает, что тот же origin доступен через HTTP/3, и может установить QUIC-соединение для последующих запросов.

DNS-запись `HTTPS` также может сообщить параметры сервиса, включая поддерживаемые ALPN-протоколы и альтернативные endpoints.

Браузер может иметь ранее сохранённую информацию об HTTP/3 из предыдущего посещения.

Поэтому первая загрузка иногда начинается через HTTP/2, после чего сервер сообщает поддержку HTTP/3. В других случаях клиент может узнать о ней раньше через DNS.

Наличие HTTP/3 не гарантирует, что браузер всегда выберет его.

Выбор зависит от:

- поддержки клиента и сервера;
- DNS и `Alt-Svc`;
- доступности UDP;
- proxy и firewall;
- результатов предыдущих соединений;
- сетевой политики;
- скорости установления доступных вариантов.

Если QUIC не работает, браузер может использовать HTTP/2 или HTTP/1.1 поверх TCP.

Multiplexing, или мультиплексирование, означает передачу нескольких логически независимых потоков через одно соединение.

В HTTP/2 frames разных streams чередуются в общем TCP-потоке.

В HTTP/3 данные разных HTTP streams передаются через отдельные QUIC-streams.

Multiplexing уменьшает необходимость открывать множество соединений, но не отменяет:

- ограниченную пропускную способность;
- задержку сервера;
- congestion control;
- приоритеты ресурсов;
- стоимость обработки headers;
- размер JavaScript bundle;
- время выполнения JavaScript;
- декодирование изображений и шрифтов.

HTTP/2 или HTTP/3 не исправят большой bundle и медленный backend автоматически.

Во frontend отдельные сетевые этапы видны в DevTools Network.

В зависимости от браузера можно увидеть:

- Queueing или Stalled;
- DNS Lookup;
- Initial connection;
- SSL;
- Request sent;
- Waiting for server response;
- Content download.

DNS Lookup показывает время разрешения имени, если оно потребовалось для этого запроса.

Initial connection показывает установление TCP- или другого транспортного соединения.

SSL показывает TLS handshake, если он выполнялся отдельно и интерфейс браузера выводит его как отдельный этап.

Waiting for server response включает ожидание первого байта после отправки запроса.

TTFB (Time to First Byte) измеряет время от начала запроса до получения первого байта ответа. В него могут входить:

- ожидание доступного соединения;
- DNS;
- транспортный handshake;
- TLS;
- сетевой путь до сервера;
- очередь и обработка на сервере;
- путь первого байта обратно.

Точное разбиение зависит от инструмента и от того, с какой точки считается метрика.

Отсутствующее или нулевое время DNS, connection или SSL не означает, что эти протоколы вообще не использовались.

Возможные причины:

- DNS уже был в кеше;
- соединение переиспользовано;
- запрос использовал уже открытый HTTP/2- или HTTP/3-stream;
- response получен из HTTP-кеша;
- response вернул Service Worker;
- измерение началось после установки соединения.

Для frontend-производительности важны не только DNS и версия HTTP, но и:

- число origins;
- количество запросов;
- размер ресурсов;
- порядок загрузки;
- HTTP-кеширование;
- CDN;
- сжатие;
- code splitting;
- server response time;
- работа main thread.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Как DNS находит IP-адрес домена?</strong></summary>

<dl>
<dd>
<h2></h2>

Браузер и операционная система сначала проверяют доступные DNS-кеши.

Если готового ответа нет, запрос обычно передаётся recursive resolver. Он либо возвращает значение из своего кеша, либо выполняет дальнейшее разрешение.

Упрощённая цепочка:

```text
root server
→ server зоны .com
→ authoritative server example.com
```

Authoritative server возвращает данные зоны, например:

```text
A
AAAA
CNAME
HTTPS
```

На практике recursive resolver обычно уже знает адреса части servers благодаря кешу, поэтому не выполняет всю цепочку для каждого запроса.

DNS может вернуть несколько адресов. Браузер выбирает подходящий вариант с учётом IPv4, IPv6, доступности маршрута и политики соединений.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое TTL DNS-записи и почему он важен при деплое?</strong></summary>

<dl>
<dd>
<h2></h2>

TTL определяет, сколько времени DNS-запись разрешено использовать из кеша без обычного повторного получения актуального значения.

Низкий TTL помогает быстрее распространить изменение адреса, но увеличивает количество DNS-запросов.

Высокий TTL снижает нагрузку и ускоряет повторные разрешения, но после изменения записи часть клиентов продолжает использовать старое значение до окончания срока.

Перед плановой миграцией TTL часто уменьшают заранее, чтобы старое большое значение успело исчезнуть из кешей.

После переключения TTL возвращают к обычному значению.

Даже при низком TTL уже открытые TCP- и QUIC-соединения могут продолжать работать со старым endpoint, пока браузер не создаст новое соединение.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли DNS использует UDP?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Обычные DNS queries часто используют UDP, поскольку небольшие request и response помещаются в отдельные датаграммы.

DNS также может использовать TCP, например после усечённого UDP-response или при необходимости передать больше данных.

Существуют зашифрованные варианты:

- DNS over TLS;
- DNS over HTTPS;
- DNS over QUIC.

Браузер может использовать собственный зашифрованный resolver, системный resolver или настройки корпоративной сети.

Независимо от транспорта задача DNS остаётся той же: получить resource records для имени.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как браузер выбирает между IPv4 и IPv6?</strong></summary>

<dl>
<dd>
<h2></h2>

DNS может вернуть:

```text
AAAA → IPv6
A    → IPv4
```

Браузер учитывает доступность локальной сети, историю соединений и результаты предыдущих попыток.

Алгоритмы Happy Eyeballs позволяют не ждать долгого timeout сломанного IPv6- или IPv4-маршрута. Клиент начинает попытки с небольшим смещением и использует первый успешно установленный подходящий вариант.

Это не означает, что IPv4 и IPv6 всегда запускаются строго одновременно или что один из них имеет постоянный приоритет. Конкретное расписание определяет реализация клиента.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит во время TCP handshake?</strong></summary>

<dl>
<dd>
<h2></h2>

Клиент отправляет:

```text
SYN
```

со своим начальным sequence number.

Сервер отвечает:

```text
SYN-ACK
```

подтверждает sequence number клиента и сообщает собственный.

Клиент завершает установление соединения:

```text
ACK
```

После этого стороны могут передавать данные.

Handshake требует сетевого round trip до обычной прикладной передачи, поэтому повторное использование соединения экономит задержку.

Для HTTPS поверх TCP затем выполняется TLS handshake, если соединение ещё не защищено.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>За счёт чего TCP обеспечивает надёжность и порядок?</strong></summary>

<dl>
<dd>
<h2></h2>

TCP нумерует байты потока.

Получатель подтверждает принятые данные, а отправитель повторно передаёт диапазоны, подтверждение которых не было получено.

Контрольная сумма помогает обнаруживать повреждённые segments.

Receive window ограничивает объём данных, который получатель готов принять.

Congestion control регулирует скорость отправителя с учётом состояния сети.

TCP скрывает от HTTP перестановку, дубликаты и потерю отдельных IP-пакетов, пока соединение можно поддерживать.

При окончательном разрыве транспорт не гарантирует, что приложение сможет определить, была ли конкретная команда уже обработана сервером.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем TCP отличается от UDP?</strong></summary>

<dl>
<dd>
<h2></h2>

TCP предоставляет:

- логическое соединение;
- надёжный упорядоченный поток байтов;
- повторную передачу;
- flow control;
- congestion control.

UDP передаёт отдельные datagrams и сам не гарантирует:

- доставку;
- порядок;
- устранение дубликатов;
- повторную передачу.

Протокол верхнего уровня может реализовать эти свойства самостоятельно.

Например:

```text
HTTP/2 → TCP
HTTP/3 → QUIC → UDP
```

Надёжность HTTP/3 обеспечивает QUIC, а не сам UDP.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему QUIC построен поверх UDP, если ему всё равно нужна надёжность?</strong></summary>

<dl>
<dd>
<h2></h2>

UDP предоставляет широко доступный минимальный интерфейс передачи datagrams.

Поверх него QUIC самостоятельно реализует:

- соединение;
- шифрование;
- streams;
- подтверждения;
- повторную передачу;
- flow control;
- congestion control;
- migration.

QUIC обычно работает в user space, поэтому браузер и сервер могут обновлять реализацию без ожидания массового обновления TCP-стеков операционных систем.

UDP также помогает пройти существующую сетевую инфраструктуру, хотя некоторые сети блокируют или ограничивают QUIC. В таком случае браузер может вернуться к HTTP/2 или HTTP/1.1 через TCP.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что изменил HTTP/2 по сравнению с HTTP/1.1?</strong></summary>

<dl>
<dd>
<h2></h2>

HTTP/2 сохранил HTTP-семантику:

- методы;
- коды состояния;
- заголовки;
- URI;
- кеширование.

Он изменил формат передачи сообщений.

HTTP/2 использует:

- binary frames;
- несколько streams в одном соединении;
- multiplexing;
- HPACK-сжатие полей;
- flow control для stream и соединения.

Это позволяет передавать части нескольких responses через одно TCP-соединение, не ожидая полного завершения каждого предыдущего HTTP-response.

При этом потеря TCP-сегмента всё ещё временно задерживает данные всех streams соединения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое stream, frame и multiplexing в HTTP/2?</strong></summary>

<dl>
<dd>
<h2></h2>

Stream — двунаправленный логический поток внутри HTTP/2-соединения, обычно связанный с одним обменом request/response.

Frame — минимальная единица HTTP/2, например:

```text
HEADERS
DATA
SETTINGS
WINDOW_UPDATE
```

Frame содержит идентификатор stream, которому принадлежит.

Multiplexing позволяет чередовать frames разных streams в одном TCP-соединении.

Получатель собирает сообщения каждого stream отдельно по идентификаторам и правилам framing.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему в HTTP/2 остаётся head-of-line blocking?</strong></summary>

<dl>
<dd>
<h2></h2>

HTTP/2 разделяет HTTP messages на независимые streams, но все их frames передаются внутри одного упорядоченного TCP-потока.

Если один TCP-segment потерян, TCP не выдаёт приложению последующие байты до восстановления пропуска.

Эти байты могут относиться к разным HTTP/2 streams, поэтому временно задерживаются все они.

HTTP/2 устраняет необходимость ждать полного предыдущего HTTP-response на уровне протокола, но не устраняет transport head-of-line blocking TCP.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как браузер выбирает HTTP/1.1, HTTP/2 или HTTP/3?</strong></summary>

<dl>
<dd>
<h2></h2>

Для HTTPS поверх TCP браузер использует ALPN внутри TLS handshake.

Клиент может предложить:

```text
h2
http/1.1
```

Сервер выбирает поддерживаемый протокол.

HTTP/3 работает поверх QUIC и требует отдельного способа обнаружения.

Браузер может узнать о поддержке HTTP/3 через:

- ранее сохранённую информацию;
- `Alt-Svc`;
- DNS-запись `HTTPS`.

Например:

```http
Alt-Svc: h3=":443"
```

После этого браузер может попытаться установить QUIC-соединение.

Если HTTP/3 недоступен или UDP блокируется, клиент может использовать HTTP/2 или HTTP/1.1.

Frontend-код через `fetch()` обычно не выбирает версию вручную.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что HTTP/3 улучшает и чего он не исправляет?</strong></summary>

<dl>
<dd>
<h2></h2>

HTTP/3 переносит HTTP streams на QUIC и устраняет transport head-of-line blocking между независимыми streams.

Если данные одного stream потеряны, другой stream может продолжить выдавать уже полученные данные.

HTTP/3 также:

- объединяет установление QUIC и TLS 1.3;
- поддерживает connection migration;
- использует QPACK для сжатия полей;
- допускает быстрое возобновление соединения.

Но HTTP/3 не исправляет автоматически:

- медленный backend;
- большой JavaScript bundle;
- long tasks;
- лишние запросы;
- отсутствие кеширования;
- низкую пропускную способность;
- перегруженный main thread.

Потеря пакетов может снизить congestion window всего QUIC-соединения, поэтому скорость других streams тоже может уменьшиться.

Внутри одного stream потеря данных по-прежнему задерживает его последующие байты.

QPACK-зависимости также могут временно заблокировать декодирование headers конкретного stream.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем повторно использовать соединение?</strong></summary>

<dl>
<dd>
<h2></h2>

Новое соединение может потребовать:

- DNS lookup;
- TCP handshake либо QUIC handshake;
- TLS handshake;
- разгона congestion control.

При повторном использовании готового соединения запрос может начать передачу раньше.

HTTP/1.1 позволяет последовательно использовать persistent connection для нескольких запросов.

HTTP/2 и HTTP/3 позволяют передавать несколько параллельных streams через одно соединение.

Браузер всё равно может создать дополнительное соединение из-за:

- ограничений streams;
- разных credentials;
- сетевой политики;
- смены адреса;
- недоступности существующего соединения;
- требований приватности.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означают DNS, connection, SSL и TTFB в DevTools Network?</strong></summary>

<dl>
<dd>
<h2></h2>

DNS показывает время разрешения hostname, если оно потребовалось.

Connection показывает установление транспортного соединения.

SSL показывает TLS handshake, если инструмент выделяет его отдельно.

TTFB (Time to First Byte) — время до получения первого байта ответа.

В TTFB могут входить:

- очередь браузера;
- DNS;
- установка соединения;
- TLS;
- сетевой round trip;
- обработка запроса сервером;
- доставка первого байта обратно.

По одному TTFB нельзя точно определить причину задержки.

Если DNS, connection или SSL отсутствуют, браузер мог использовать кеш, уже открытое соединение или response от Service Worker.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делают <code>dns-prefetch</code> и <code>preconnect</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`dns-prefetch` заранее запускает разрешение hostname:

```html
<link rel="dns-prefetch" href="//cdn.example.com">
```

`preconnect` идёт дальше:

```html
<link
  rel="preconnect"
  href="https://cdn.example.com"
  crossorigin
>
```

Браузер может заранее:

- выполнить DNS lookup;
- установить транспортное соединение;
- выполнить TLS handshake;
- подготовить соединение к будущему запросу.

Конкретные действия зависят от выбранного протокола и браузера.

Resource hints полезны для небольшого числа внешних origins, которые точно понадобятся в начале загрузки.

Лишний `preconnect` расходует sockets, память и сетевые ресурсы, поэтому не следует добавлять его для каждого возможного домена.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

- По waterfall, или диаграмме последовательности запросов, в DevTools можно отделить DNS, установление соединения, TLS, ожидание сервера и загрузку тела ответа.
- CDN приближает ресурсы к пользователю и может сократить задержку, но результат зависит от DNS, кеширования и маршрута до выбранного узла.
- Happy Eyeballs уменьшает задержку при частично неработающем IPv4- или IPv6-маршруте.
- ALPN позволяет согласовать HTTP/2 или HTTP/1.1 внутри TLS handshake.
- `Alt-Svc` и DNS-запись `HTTPS` помогают браузеру обнаружить HTTP/3.
- HTTP/2 и HTTP/3 меняют способ передачи нескольких ресурсов, но не отменяют code splitting, сжатие и контроль размера bundle.
- `preconnect` применяют для критичного origin, когда соединение точно понадобится в начале загрузки.
- Повторное использование соединения и HTTP-кеш ускоряют последующие запросы без изменения кода компонента.
