## Вопрос

<br>

 💬 **Что такое DNS, TCP, UDP, HTTP/2 и HTTP/3? Как они участвуют в загрузке страницы?**

<h2></h2>

<br>
<dl>
<dd>

Загрузка страницы проходит через несколько уровней сетевых протоколов. DNS помогает найти IP-адрес сервера по доменному имени. Затем браузер устанавливает транспортное соединение: HTTP/1.1 и HTTP/2 обычно работают поверх TCP, а HTTP/3 работает поверх QUIC, который использует UDP. Уже по этому соединению передаются HTTP-запросы и ответы.

Упрощенная последовательность выглядит так:

1. Браузер получает hostname, или имя хоста, из URL, например `example.com`.
2. DNS возвращает один или несколько IP-адресов, по которым доступен сайт.
3. Браузер устанавливает соединение с подходящим сервером. Для HTTP/1.1 и HTTP/2 это TCP-соединение; для HTTP/3 - QUIC-соединение.
4. Для HTTPS стороны выполняют TLS handshake, или TLS-рукопожатие: согласуют параметры шифрования и проверяют сертификат сервера. В QUIC TLS 1.3 встроен в установление соединения.
5. Браузер отправляет HTTP-запрос, получает ответ и при необходимости запрашивает дополнительные ресурсы: CSS, JavaScript, изображения и шрифты.

**DNS (Domain Name System, система доменных имен)** сопоставляет доменное имя с сетевыми данными, чаще всего с IP-адресом. Сначала браузер и операционная система проверяют свои кэши. Если ответа нет, запрос обычно получает recursive resolver, или рекурсивный DNS-резолвер провайдера либо публичного сервиса. Он ищет ответ по иерархии DNS и обращается к authoritative DNS server, авторитетному серверу, где хранится запись нужного домена. Результат кэшируется на время, заданное TTL (Time To Live, временем жизни записи).

DNS не доставляет HTTP-запрос до приложения и не выбирает маршрут для каждого сетевого пакета. Его задача на этом этапе - помочь клиенту найти адрес сервера. Один домен может возвращать несколько адресов для балансировки нагрузки или ближайший адрес CDN.

**TCP (Transmission Control Protocol, протокол управления передачей)** предоставляет надежный упорядоченный поток байтов. Перед передачей данных клиент и сервер устанавливают соединение с помощью трехэтапного handshake: `SYN`, `SYN-ACK`, `ACK`. TCP нумерует данные, подтверждает получение и повторно передает потерянные сегменты. Приложение получает байты в правильном порядке, но TCP не сохраняет границы сообщений: разбиение данных на отдельные HTTP-сообщения выполняет протокол HTTP.

Надежность TCP не означает, что соединение никогда не оборвется и запрос не придется повторить. Она означает, что пока соединение работает, TCP обнаруживает потерю и повреждение данных, восстанавливает порядок и регулирует скорость передачи. Потеря сегмента задерживает выдачу следующих байтов, даже если они уже пришли. Это называют head-of-line blocking - блокировкой следующих данных из-за отсутствующего элемента в начале очереди.

**UDP (User Datagram Protocol, протокол пользовательских датаграмм)** передает отдельные datagrams, или датаграммы, без установки TCP-соединения. Каждая датаграмма является самостоятельным сообщением. Сам UDP не гарантирует доставку, порядок, устранение дубликатов и повторную передачу. Поэтому утверждение «UDP всегда быстрее TCP» некорректно: он дает приложению меньше готовых гарантий, а нужные механизмы приходится реализовывать протоколу более высокого уровня.

**QUIC** использует UDP как основу, но сам добавляет надежную доставку, контроль перегрузки, шифрование TLS и несколько независимых потоков в одном соединении. Поэтому HTTP/3 не является «ненадежным HTTP поверх UDP». Потеря данных одного QUIC-потока не должна останавливать выдачу данных других потоков, хотя потерянные данные внутри самого потока все равно нужно получить повторно.

| Версия HTTP | Транспорт | Что важно |
|---|---|---|
| HTTP/1.1 | TCP | Постоянные соединения позволяют отправлять несколько запросов последовательно. Настоящего multiplexing в одном соединении нет, поэтому браузеры обычно открывают несколько соединений к одному origin, то есть сочетанию scheme, host и port. |
| HTTP/2 | TCP | Binary framing делит сообщения на frames, multiplexing чередует frames разных streams в одном соединении, а алгоритм HPACK сжимает заголовки. Потеря TCP-сегмента временно задерживает все streams этого соединения. |
| HTTP/3 | QUIC поверх UDP | Сохраняет семантику HTTP, но переносит streams на QUIC. Потеря данных в одном stream не блокирует остальные streams на транспортном уровне. TLS 1.3 встроен в QUIC handshake. |

Multiplexing, или мультиплексирование, - передача нескольких логически независимых потоков через одно соединение. Например, браузер может одновременно получать CSS и JavaScript по разным HTTP/2 streams, а их frames будут чередоваться в TCP-потоке. Это уменьшает необходимость открывать много соединений, но не отменяет ограничения пропускной способности, приоритеты ресурсов и стоимость большого bundle.

Во frontend влияние сети видно в DevTools Network: поиск адреса через DNS, установка соединения, TLS, ожидание первого байта, загрузка ответа и повторное использование соединения. Для производительности важны не только версия HTTP, но и количество запросов, размер ресурсов, кэширование, CDN и порядок загрузки критических ресурсов.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Как DNS находит IP-адрес домена?</strong></summary>

<dl>
<dd>
<h2></h2>

Браузер сначала проверяет собственный кэш, затем кэш операционной системы. Если готового ответа нет, запрос получает recursive resolver. Он может обратиться к root DNS server, корневому DNS-серверу, затем к серверу доменной зоны, например `.com`, и после этого к authoritative server домена. Последний возвращает DNS-запись, например `A` для IPv4 или `AAAA` для IPv6. На практике часть шагов пропускается благодаря кэшам.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое TTL DNS-записи и почему он важен при деплое?</strong></summary>

<dl>
<dd>
<h2></h2>

TTL задает, сколько времени DNS-ответ разрешено хранить в кэше. Низкий TTL помогает быстрее распространить смену адреса, но увеличивает количество DNS-запросов. Высокий TTL снижает нагрузку и задержки повторных запросов, но после изменения записи часть клиентов продолжит использовать старый адрес, пока кэш не истечет. TTL обычно уменьшают заранее, если планируется миграция.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит во время TCP handshake?</strong></summary>

<dl>
<dd>
<h2></h2>

Клиент отправляет `SYN` и свое начальное sequence number, то есть номер позиции в потоке байтов. Сервер отвечает `SYN-ACK`: подтверждает номер клиента и сообщает свой. Клиент завершает установление соединения сообщением `ACK`. После этого стороны могут передавать данные. Рукопожатие требует сетевого обмена до полезной нагрузки, поэтому повторное использование существующего соединения экономит задержку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>За счет чего TCP обеспечивает надежность и порядок?</strong></summary>

<dl>
<dd>
<h2></h2>

TCP нумерует байты, получатель подтверждает принятый диапазон, а отправитель повторяет данные, подтверждение которых не пришло. Контрольная сумма помогает обнаруживать повреждение, receive window, или окно приема, ограничивает объем неподтвержденных данных, а congestion control, управление перегрузкой, регулирует скорость передачи. Эти механизмы скрывают от HTTP перестановку и потерю отдельных IP-пакетов, пока соединение можно восстановить.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем TCP отличается от UDP?</strong></summary>

<dl>
<dd>
<h2></h2>

TCP дает соединение и упорядоченный надежный поток байтов. UDP передает отдельные datagrams и сам не обеспечивает доставку, порядок или повторную отправку. Выбор зависит от протокола верхнего уровня: WebSocket и HTTP/2 используют TCP, а HTTP/3 использует QUIC поверх UDP, причем надежность HTTP/3 реализует QUIC, а не UDP.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему QUIC построен поверх UDP, если ему все равно нужна надежность?</strong></summary>

<dl>
<dd>
<h2></h2>

UDP предоставляет минимальный интерфейс доставки datagrams, поверх которого QUIC реализует транспорт в user space, то есть в обычном процессе браузера или сервера, а не только в ядре операционной системы. Благодаря этому протокол можно обновлять вместе с приложением. QUIC объединяет транспортный и TLS handshake, поддерживает независимые streams и идентификаторы соединения. Последние позволяют сохранить соединение при смене IP-адреса, например при переходе с Wi-Fi на мобильную сеть, если это поддерживают обе стороны.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что изменил HTTP/2 по сравнению с HTTP/1.1?</strong></summary>

<dl>
<dd>
<h2></h2>

HTTP/2 сохранил методы, коды состояния, заголовки и остальную семантику HTTP, но изменил передачу сообщений. Он использует binary frames, несколько streams в одном TCP-соединении и HPACK для сжатия повторяющихся заголовков. Это позволяет не ждать полного ответа на один запрос перед передачей данных другого запроса и уменьшает размер служебных данных.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое stream, frame и multiplexing в HTTP/2?</strong></summary>

<dl>
<dd>
<h2></h2>

Stream, или поток, - двунаправленный логический канал внутри HTTP/2-соединения, обычно связанный с одним обменом запрос-ответ. Frame, или кадр, - минимальная единица HTTP/2, например `HEADERS` или `DATA`, принадлежащая конкретному stream. Multiplexing позволяет чередовать frames разных streams в одном TCP-соединении, а получателю - собирать их обратно по идентификаторам потоков.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему в HTTP/2 остается head-of-line blocking?</strong></summary>

<dl>
<dd>
<h2></h2>

HTTP/2 разделяет данные на независимые streams, но все они входят в один упорядоченный TCP-поток. Если TCP-сегмент потерян, операционная система не передаст приложению последующие байты до восстановления пропуска. Поэтому временно задерживаются данные всех HTTP/2 streams этого соединения, а не только потока, чьи данные были потеряны.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что HTTP/3 улучшает и чего он не исправляет?</strong></summary>

<dl>
<dd>
<h2></h2>

HTTP/3 переносит HTTP на QUIC и уменьшает блокировку между streams при потере пакета. Он также объединяет установление защищенного соединения с TLS 1.3 и лучше переносит смену сети. Но он сам по себе не уменьшает размер JavaScript, время ответа backend, long tasks на main thread или число ненужных запросов. Нестабильная сеть и потеря данных все равно увеличивают время доставки затронутого потока.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем повторно использовать соединение?</strong></summary>

<dl>
<dd>
<h2></h2>

Новое соединение требует поиска адреса через DNS при отсутствии кэша, транспортного рукопожатия и для HTTPS криптографического TLS handshake. При повторном использовании готового соединения запрос может начаться раньше. HTTP/2 и HTTP/3 дополнительно позволяют обслуживать много streams через одно соединение, хотя браузер применяет ограничения и может создавать новые соединения при необходимости.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означают DNS, connection, SSL и TTFB в DevTools Network?</strong></summary>

<dl>
<dd>
<h2></h2>

DNS - время поиска адреса, connection - установка транспортного соединения, SSL - TLS handshake, а TTFB (Time to First Byte, время до первого байта) - период от начала запроса до получения первого байта ответа. TTFB включает сетевые задержки и ожидание обработки на сервере, поэтому по одному этому показателю нельзя точно определить причину задержки без дополнительной диагностики.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делают <code>dns-prefetch</code> и <code>preconnect</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`dns-prefetch` заранее запускает DNS lookup для указанного hostname. `preconnect` идет дальше: браузер может заранее выполнить DNS lookup, установить транспортное соединение и TLS для cross-origin ресурса. Эти resource hints, или подсказки загрузки, полезны для небольшого числа действительно критичных внешних origins; большое количество `preconnect` расходует соединения и ресурсы без гарантии пользы.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

- По waterfall, или диаграмме последовательности запросов, в DevTools можно отделить DNS, установление соединения, TLS, ожидание сервера и загрузку тела ответа.
- CDN приближает ресурсы к пользователю и может сократить задержку, но результат зависит от кэширования и маршрута до выбранного узла.
- HTTP/2 и HTTP/3 меняют способ передачи нескольких ресурсов, но не отменяют разделение кода (code splitting), сжатие и контроль размера bundle.
- `preconnect` применяют для критичного origin, например CDN со шрифтами, когда соединение точно понадобится в начале загрузки.
- Повторное использование соединения и HTTP-кэш ускоряют последующие запросы без изменения кода компонента.
