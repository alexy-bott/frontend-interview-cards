## Вопрос

<br>

 💬 **Чем HTTP отличается от HTTPS? Как работают TLS handshake и цифровые сертификаты?**

<h2></h2>

<br>
<dl>
<dd>

HTTPS - это обмен HTTP-сообщениями через защищённое TLS-соединение. Обычный HTTP не защищает сетевой трафик: участник сети может прочитать запрос, изменить JavaScript в ответе или подменить данные. TLS создаёт канал с тремя основными свойствами:

- **Confidentiality, или конфиденциальность:** содержимое шифруется.
- **Integrity, или целостность:** изменение данных при передаче обнаруживается.
- **Authentication, или аутентификация:** браузер проверяет подлинность сервера по цифровому сертификату.

TLS handshake, или TLS-рукопожатие, выполняется до обычного HTTP-обмена. В упрощённом виде процесс выглядит так:

1. Клиент отправляет `ClientHello`: поддерживаемые версии TLS, наборы криптографических алгоритмов, данные для согласования ключей и расширения, включая имя сервера.
2. Сервер выбирает параметры и отвечает `ServerHello` со своей частью данных для обмена ключами.
3. Сервер передаёт certificate chain, или цепочку сертификатов, и цифровой подписью доказывает владение закрытым ключом.
4. Браузер проверяет доменное имя, срок действия и назначение сертификата, подписи промежуточных сертификатов и связь с доверенным корневым центром сертификации.
5. Стороны независимо вычисляют общие session keys, или сеансовые ключи, и сообщениями `Finished` подтверждают целостность рукопожатия.
6. Дальнейшие HTTP-данные шифруются быстрым симметричным алгоритмом с помощью сеансовых ключей.

Certificate, или цифровой сертификат, связывает public key, то есть открытый ключ, с именем сервиса. Серверный сертификат обычно содержит допустимые доменные имена в поле Subject Alternative Name и подписан промежуточным центром сертификации. Цепочка заканчивается root CA, или корневым центром, которому браузер или операционная система доверяет заранее. Корневой сертификат обычно не передаётся сервером: он уже находится в trust store, хранилище доверенных сертификатов клиента.

Сертификат не доказывает, что владелец сайта честен, а приложение безопасно. Он подтверждает, что защищённое соединение установлено с сервером, которому разрешено представлять указанное доменное имя, и что этот сервер владеет соответствующим private key, или закрытым ключом. HTTPS не исправляет XSS, неверную авторизацию, утечку данных самим сервером или логические ошибки.

Для frontend HTTPS нужен не только при вводе пароля. Он предотвращает подмену загружаемых scripts и ответов API. Многие browser APIs доступны только в secure context, то есть в контексте, который браузер считает надежно доставленным: например, Service Worker, часть Clipboard API и geolocation. Cookie с атрибутом `Secure` также не отправляется по обычному HTTP, кроме специальных правил для localhost.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему в TLS используются и асимметричная, и симметричная криптография?</strong></summary>

<dl>
<dd>
<h2></h2>

Asymmetric cryptography, или асимметричная криптография с парой открытого и закрытого ключей, помогает аутентифицировать сервер и согласовать общий секрет без заранее известного обеим сторонам пароля. Она вычислительно дороже и не используется для шифрования всего тела HTTP-сообщения.

После рукопожатия стороны получают symmetric session keys, или симметричные сеансовые ключи. Они позволяют быстро шифровать и проверять большие объёмы прикладных данных. Сеансовые ключи временные и не передаются по сети в открытом виде.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как браузер проверяет цепочку сертификатов?</strong></summary>

<dl>
<dd>
<h2></h2>

Браузер проверяет, что конечный сертификат подходит для целевого домена, действует по времени и разрешён для серверной аутентификации. Затем он проверяет цифровые подписи: сертификат сайта подписан промежуточным CA, тот - следующим CA, пока цепочка не дойдёт до корневого сертификата из локального хранилища доверия.

Сервер должен прислать необходимые промежуточные сертификаты. Если цепочку нельзя построить до доверенного корня, имя не совпадает или подпись неверна, браузер прекращает автоматическое соединение и показывает ошибку сертификата.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что доказывает <code>CertificateVerify</code> в TLS 1.3?</strong></summary>

<dl>
<dd>
<h2></h2>

Сервер подписывает hash, или хеш, сообщений рукопожатия закрытым ключом, соответствующим сертификату. Клиент проверяет подпись через открытый ключ. Это доказывает владение закрытым ключом и связывает выбранные параметры рукопожатия с аутентифицированным сервером.

Одной передачи сертификата было бы недостаточно: злоумышленник может скопировать публичный сертификат, но не должен иметь закрытого ключа для правильной подписи.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему self-signed certificate, или самоподписанный сертификат, вызывает предупреждение?</strong></summary>

<dl>
<dd>
<h2></h2>

Самоподписанный сертификат подписан собственным закрытым ключом и не строит цепочку к CA из хранилища доверия браузера. Шифрование технически возможно, но клиент не имеет независимого основания доверять заявленному имени: такой сертификат мог создать и атакующий.

Во внутренней инфраструктуре собственный root CA можно явно установить как доверенный. Для локальной разработки используют локальный CA или инструменты dev-сертификатов, но отключать проверку сертификата для production-запросов опасно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что именно остаётся видимым сети при HTTPS?</strong></summary>

<dl>
<dd>
<h2></h2>

Path, query-параметры, HTTP-заголовки и тело находятся внутри защищённого соединения. Участник сети всё ещё видит IP-адреса, факт и время соединения, объём трафика и транспортный протокол. Домен может быть известен из DNS, сопоставления IP-адресов или незашифрованных частей установки соединения; Encrypted Client Hello уменьшает часть этой утечки.

HTTPS не скрывает данные от самого браузера, frontend-кода и сервера после расшифрования. Поэтому token в URL остаётся опасным из-за истории браузера, журналов, аналитики и копирования ссылки, хотя сеть не видит query в открытом виде.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое mixed content, или смешанный контент?</strong></summary>

<dl>
<dd>
<h2></h2>

Mixed content возникает, когда защищённая HTTPS-страница загружает вложенный ресурс по HTTP. Активный ресурс, например script, stylesheet или iframe, может изменить поведение всей страницы, поэтому браузер его блокирует. Часть пассивных ресурсов также блокируется или автоматически переводится на HTTPS по современным правилам.

Исправление - отдавать все ресурсы через HTTPS и обновить абсолютные URL, настройки CDN и адреса API. Добавление CORS-заголовков не делает HTTP-ресурс безопасным и не решает проблему mixed content.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое HSTS?</strong></summary>

<dl>
<dd>
<h2></h2>

HSTS, или HTTP Strict Transport Security, - заголовок ответа, который сообщает браузеру обращаться к домену только по HTTPS в течение `max-age`. После получения политики браузер сам заменяет будущий `http://` на `https://` до сетевого запроса и не позволяет обойти ошибку сертификата обычным подтверждением.

Первый визит до получения заголовка остаётся отдельным риском. HSTS preload позволяет заранее включить домены в список браузера, но требует корректной настройки HTTPS для основного домена и нужных поддоменов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>HTTPS защищает от XSS, CSRF и плохой авторизации?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. TLS защищает данные во время передачи между сторонами. XSS выполняется внутри доверенной страницы, CSRF использует автоматическую отправку credentials, а ошибка авторизации находится в правилах backend. Все эти атаки работают уже на концах защищённого канала.

HTTPS является обязательным нижним слоем, но поверх него нужны CSP, безопасная обработка данных, SameSite/CSRF-защита, корректная проверка прав и управление tokens.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое TLS termination?</strong></summary>

<dl>
<dd>
<h2></h2>

TLS termination, или завершение TLS, означает, что HTTPS-соединение заканчивается на reverse proxy, балансировщике нагрузки или CDN, а не в процессе приложения. Этот компонент хранит сертификат, выполняет TLS handshake и передаёт запрос дальше.

Внутренний участок сети тоже должен соответствовать threat model, то есть принятой модели угроз: он может повторно использовать TLS или находиться в защищённой частной сети. Приложению важно доверять forwarded headers только от известных прокси, иначе атакующий сможет подделать исходную схему запроса или IP-адрес клиента.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему TLS добавляет задержку и как её уменьшить?</strong></summary>

<dl>
<dd>
<h2></h2>

До передачи прикладных данных стороны должны обменяться сообщениями рукопожатия и выполнить криптографические операции. TLS 1.3 сокращает число round trips, или сетевых обменов туда и обратно, по сравнению со старыми версиями. Session resumption позволяет возобновить ранее установленную сессию и сократить часть этой работы.

В реальном frontend важны повторное использование соединения, HTTP/2 или HTTP/3, близкий к пользователю CDN и отсутствие лишних origins. `0-RTT` early data позволяет отправить данные до завершения нового рукопожатия при возобновлении сессии, но эти данные могут быть повторно воспроизведены атакующим. Поэтому механизм подходит только для операций, безопасных при повторе.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>localhost</code> часто считается secure context без HTTPS?</strong></summary>

<dl>
<dd>
<h2></h2>

Браузеры считают локальные адреса потенциально доверенными для разработки, потому что соединение остаётся на устройстве. Это позволяет тестировать Service Worker и некоторые другие APIs без публичного сертификата.

Исключение не распространяется на обычный production-домен и не гарантирует полного совпадения поведения. Cookies, тестирование с другого устройства, OAuth callbacks и mixed content иногда требуют локального HTTPS.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Роль HTTPS/TLS |
|---|---|
| Загрузка JS bundle | защищает script от подмены в сети |
| Запрос к API | шифрует URL, заголовки и тело на транспортном участке |
| Session cookie | атрибут `Secure` требует HTTPS |
| Service Worker | требует secure context, кроме localhost |
| CDN или reverse proxy | завершает TLS-соединение и управляет сертификатами |
| Mixed content | приводит к блокировке HTTP-ресурсов на HTTPS-странице |
| Ошибка сертификата | возникает до выполнения React-приложения |
