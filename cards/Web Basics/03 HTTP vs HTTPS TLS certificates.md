## Вопрос

<br>

 💬 **Чем HTTP отличается от HTTPS? Как работают TLS handshake и цифровые сертификаты?**

<h2></h2>

<br>
<dl>
<dd>

HTTPS — это передача HTTP-сообщений через защищённый TLS-транспорт. Методы, коды состояния, заголовки и тело сохраняют обычную HTTP-семантику, но передаются внутри криптографически защищённого соединения.

HTTP/1.1 и HTTP/2 обычно используют TLS поверх TCP. HTTP/3 работает поверх QUIC, где TLS 1.3 встроен в установку защищённого транспортного соединения.

Обычный HTTP не защищает сетевой трафик. Участник сети может прочитать запрос, подменить ответ API, внедрить JavaScript или изменить загружаемый файл.

TLS создаёт канал с тремя основными свойствами:

- **Confidentiality, или конфиденциальность:** содержимое шифруется и недоступно пассивному наблюдателю.
- **Integrity, или целостность:** незаметно изменить защищённые данные при передаче нельзя.
- **Authentication, или аутентификация:** клиент проверяет, что соединяется с сервером, который имеет право представлять запрошенное доменное имя.

В обычном веб-сценарии сервер аутентифицируется перед браузером, а пользователь затем аутентифицируется перед приложением через пароль, cookie, token или другой механизм.

TLS также поддерживает client certificates, то есть сертификаты клиента, но в обычных публичных сайтах они используются редко.

Полный certificate-based TLS 1.3 handshake, или TLS-рукопожатие на основе сертификата, в упрощённом виде выглядит так:

1. Клиент отправляет `ClientHello`.
2. Сервер отвечает `ServerHello`.
3. Стороны вычисляют ключи, защищающие оставшуюся часть handshake.
4. Сервер отправляет параметры соединения, цепочку сертификатов, доказательство владения закрытым ключом и сообщение `Finished`.
5. Браузер проверяет сертификат и криптографические сообщения.
6. Клиент отправляет собственное `Finished`.
7. Стороны переходят к защищённому обмену HTTP-данными.

`ClientHello` содержит, в частности:

- поддерживаемые версии TLS;
- поддерживаемые cipher suites;
- случайные данные;
- `key_share` для согласования общего секрета;
- SNI с именем запрашиваемого сервера;
- ALPN со списком поддерживаемых прикладных протоколов;
- дополнительные расширения;
- при возобновлении сессии — информацию о ранее полученном PSK.

Cipher suite в TLS 1.3 определяет алгоритм симметричной защиты записей и используемую hash-функцию. Механизм аутентификации и обмена ключами согласуется отдельно.

Сервер выбирает совместимые параметры и отправляет `ServerHello`, включающий собственный `key_share`.

На основе временных ключей ECDHE стороны независимо вычисляют общий секрет. Сам секрет по сети не передаётся.

После `ServerHello` большая часть оставшихся сообщений TLS 1.3 уже зашифрована с использованием handshake traffic keys.

Сервер затем передаёт:

- `EncryptedExtensions` — выбранные расширения, не вошедшие в `ServerHello`;
- `Certificate` — сертификат сервера и обычно промежуточные сертификаты;
- `CertificateVerify` — цифровую подпись над данными handshake;
- `Finished` — криптографическое подтверждение целостности всего предыдущего handshake.

`CertificateVerify` доказывает, что сервер владеет закрытым ключом, соответствующим открытому ключу сертификата. Копии публичного сертификата для этого недостаточно: злоумышленнику потребовался бы закрытый ключ.

`Finished` вычисляется из ключей, полученных во время handshake, и transcript, то есть последовательности предыдущих сообщений. Несовпадение означает, что параметры были изменены либо стороны получили разные ключи, поэтому соединение завершается.

Браузер проверяет сертификат сервера:

1. Подходит ли доменное имя из URL под имена в сертификате.
2. Действует ли сертификат в текущий момент.
3. Разрешено ли его ключу использоваться для серверной аутентификации.
4. Корректны ли цифровые подписи сертификатов.
5. Можно ли построить certification path, то есть путь сертификации, до доверенного корня.
6. Соответствуют ли алгоритмы и параметры политике безопасности браузера.
7. Не считается ли сертификат отозванным по применяемой браузером политике.

Если хотя бы обязательная проверка не пройдена, браузер показывает ошибку до загрузки React-приложения и получения обычного HTTP-ответа.

После проверки серверного `Finished` клиент отправляет собственное сообщение `Finished`. Затем обе стороны получают application traffic keys и начинают передавать защищённые HTTP-данные.

HTTP-трафик шифруется не открытым ключом сертификата, а быстрыми симметричными AEAD-алгоритмами. Они одновременно обеспечивают конфиденциальность и проверку целостности каждой TLS-записи.

Таким образом, в современном TLS 1.3 роли разделены:

- сертификат связывает открытый ключ с именем сервиса;
- цифровая подпись доказывает владение закрытым ключом;
- ECDHE создаёт общий временный секрет;
- симметричные traffic keys защищают прикладные данные.

ALPN (Application-Layer Protocol Negotiation) позволяет сторонам во время установки защищённого соединения согласовать прикладной протокол.

Например, клиент может сообщить поддержку:

```text
h2
http/1.1
```

а сервер выбрать `h2`.

Для HTTP/3 через QUIC используется ALPN-идентификатор семейства `h3`. Frontend-код обычно не управляет выбором напрямую: браузер, сервер и инфраструктура согласуют протокол автоматически.

Certificate, или цифровой сертификат, связывает public key, то есть открытый ключ, с удостоверенными именами сервиса.

Серверный сертификат обычно содержит:

- открытый ключ;
- допустимые DNS-имена в `Subject Alternative Name`;
- срок действия;
- серийный номер;
- сведения об издателе;
- назначение ключа;
- цифровую подпись центра сертификации.

Сертификат сайта обычно подписан промежуточным CA, то есть центром сертификации. Промежуточный сертификат может быть подписан другим промежуточным CA или доверенным корнем.

Сервер обычно передаёт:

```text
сертификат сайта
→ промежуточный сертификат
→ при необходимости другие промежуточные сертификаты
```

Корневой сертификат обычно не передаётся сервером. Он заранее находится в trust store, то есть хранилище доверенных корней браузера или операционной системы.

Браузер строит путь от сертификата сайта до одного из доверенных trust anchors. Цепочка, присланная сервером, помогает построить этот путь, но доверие возникает не из самого факта передачи сертификатов, а из наличия подходящего корня в локальном trust store.

Сертификат не доказывает, что владелец сайта честен, что товар настоящий или что приложение не содержит уязвимостей.

Он подтверждает более узкое свойство: согласно используемой PKI и политике браузера данный ключ разрешено связывать с указанным именем, а сервер доказал владение соответствующим закрытым ключом.

HTTPS не исправляет:

- XSS;
- CSRF;
- неправильную авторизацию;
- SQL injection;
- утечку данных самим сервером;
- вредоносную бизнес-логику;
- скомпрометированную конечную точку;
- небезопасное хранение tokens.

TLS защищает данные во время передачи между конкретными TLS endpoints. До шифрования и после расшифрования данные доступны приложению на соответствующей стороне.

TLS 1.3 поддерживает session resumption, то есть возобновление ранее установленной сессии. Сервер может выдать клиенту session ticket, связанный с PSK. При следующем соединении стороны используют его, чтобы сократить повторный handshake.

Возобновление не означает бессрочное использование прежних traffic keys. Из PSK и новых параметров стороны получают новые ключи соединения.

TLS 1.3 также допускает `0-RTT early data`: при возобновлении клиент может отправить часть прикладных данных до полного завершения нового handshake.

Это уменьшает задержку, но ранние данные имеют ослабленные свойства:

- они не обладают полной forward secrecy;
- злоумышленник может попытаться воспроизвести их;
- серверу сложно гарантировать уникальность обработки без дополнительного состояния.

Поэтому `0-RTT` подходит только для операций, которые безопасно повторить. Его нельзя без отдельной защиты применять к платежам, созданию заказов и другим неидемпотентным действиям.

Для frontend HTTPS нужен не только при вводе пароля.

Он предотвращает сетевую подмену:

- JavaScript bundle;
- HTML;
- CSS;
- ответов API;
- Service Worker;
- загружаемых файлов;
- конфигурации приложения.

Если основной JavaScript загружен по HTTP, атакующий в сети может заменить его и получить те же возможности, что имеет само приложение.

Многие browser APIs доступны только в secure context, то есть контексте с минимально необходимыми свойствами аутентификации и конфиденциальности.

К ним относятся, например:

- Service Worker;
- `getUserMedia()`;
- `getDisplayMedia()`;
- часть Clipboard API;
- geolocation;
- Web Authentication API;
- часть возможностей хранения и устройств.

Текущее состояние можно проверить:

```ts
console.log(window.isSecureContext);
```

Обычно удалённый ресурс должен быть загружен по HTTPS. Локальные адреса вроде `http://localhost` и `http://127.0.0.1` браузер может считать potentially trustworthy, то есть потенциально доверенными, для удобства разработки.

Это исключение не означает, что локальное HTTP-соединение стало криптографически защищённым, и не распространяется на обычные production-домены.

Cookie с атрибутом `Secure` отправляется только через защищённый запрос HTTPS, кроме специальных правил браузеров для localhost.

HTTPS скрывает содержимое HTTP-сообщения от пассивного участника сети:

- path;
- query;
- HTTP-заголовки;
- cookie;
- тело запроса;
- тело ответа.

Однако часть метаданных остаётся наблюдаемой:

- IP-адреса;
- время соединения;
- длительность;
- объём и направление трафика;
- используемый транспорт;
- часть сведений о сетевом маршруте.

Домен может стать известен через:

- обычный незашифрованный DNS;
- сопоставление IP-адреса;
- SNI в `ClientHello`;
- другие побочные признаки.

Encrypted Client Hello (ECH) позволяет зашифровать чувствительную часть `ClientHello`, включая реальный SNI и ALPN. Для работы ECH нужна поддержка клиента, сервера и механизма получения ECH-конфигурации.

ECH не скрывает IP-адрес и не защищает незашифрованный DNS самостоятельно. Для уменьшения этих утечек дополнительно применяются шифрованный DNS и инфраструктура, где несколько доменов используют общие IP-адреса.

Token в URL остаётся опасным даже при HTTPS. Хотя query зашифрован во время передачи, URL может попасть в:

- историю браузера;
- серверные и proxy-логи;
- аналитику;
- отчёты об ошибках;
- скриншоты;
- буфер обмена;
- отправленную другому человеку ссылку.

При TLS termination, или завершении TLS, браузерское HTTPS-соединение заканчивается на CDN, load balancer или reverse proxy.

Например:

```text
браузер ⇄ HTTPS ⇄ CDN ⇄ HTTPS или HTTP ⇄ приложение
```

CDN расшифровывает запрос, потому что является конечной точкой первого TLS-соединения. Дальнейший участок является отдельным соединением и должен защищаться согласно threat model, то есть модели угроз системы.

Если между proxy и приложением снова используется TLS, создаётся новый защищённый участок со своими ключами и проверкой сертификата.

Если внутри используется HTTP, данные на этом участке не защищены TLS. Допустимость такого решения зависит от изоляции сети, уровня доверия и требований системы.

Приложение за proxy часто использует:

```http
Forwarded: proto=https
```

или:

```http
X-Forwarded-Proto: https
```

Такие заголовки можно считать достоверными только от известных доверенных proxy. Если приложение принимает их напрямую от любого клиента, атакующий может подделать исходную схему, IP-адрес или host.

## Дополнительные вопросы

<details>
<summary><strong>Почему в TLS используются и асимметричная, и симметричная криптография?</strong></summary>

<dl>
<dd>
<h2></h2>

У них разные задачи.

Асимметричная криптография используется для аутентификации и безопасного согласования ключей:

- цифровая подпись доказывает владение закрытым ключом сертификата;
- ECDHE позволяет сторонам получить общий временный секрет.

Она вычислительно дороже симметричной и не используется для шифрования всего HTTP-ответа.

После handshake стороны получают симметричные traffic keys. С их помощью AEAD-алгоритмы быстро защищают большие объёмы прикладных данных.

Ключи временные, зависят от конкретного соединения и не передаются по сети в открытом виде.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Используется ли сертификат для шифрования HTTP-трафика?</strong></summary>

<dl>
<dd>
<h2></h2>

Не напрямую.

Сертификат предоставляет открытый ключ и подтверждает его связь с доменным именем. Сервер через `CertificateVerify` использует соответствующий закрытый ключ, чтобы подписать данные handshake и доказать владение им.

Общий секрет для соединения стороны обычно получают через временный ECDHE key exchange.

Затем из этого секрета выводятся симметричные traffic keys, которыми и защищаются HTTP-запросы и ответы.

Поэтому фраза «данные шифруются сертификатом» является упрощением. Сертификат участвует в аутентификации сервера, но непосредственную защиту трафика выполняют сеансовые симметричные ключи.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое forward secrecy?</strong></summary>

<dl>
<dd>
<h2></h2>

Forward secrecy означает, что последующая утечка долговременного закрытого ключа сервера не должна позволить расшифровать ранее записанные сессии.

В TLS 1.3 стороны обычно используют временные ключи ECDHE. После завершения соединения эти ephemeral secrets, то есть временные секреты, удаляются.

Если злоумышленник позже получит закрытый ключ сертификата, он сможет выдавать себя за сервер до отзыва или замены сертификата, но не должен автоматически получить ключи прошлых соединений.

Forward secrecy не помогает, если во время соединения скомпрометирован сам endpoint, память процесса или текущие traffic keys.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как браузер проверяет цепочку сертификатов?</strong></summary>

<dl>
<dd>
<h2></h2>

Браузер проверяет, что конечный сертификат:

- подходит для целевого домена;
- действует по времени;
- разрешён для серверной аутентификации;
- использует допустимые алгоритмы;
- имеет корректную цифровую подпись.

Затем строится certification path:

```text
сертификат сайта
→ промежуточный CA
→ доверенный root CA
```

У каждого сертификата проверяется подпись издателя и ограничения CA. Корень должен присутствовать в trust store браузера или операционной системы.

Сервер должен прислать необходимые промежуточные сертификаты. Корневой обычно не передаётся, поскольку клиент уже доверяет собственной локальной копии.

Проверка статуса отзыва выполняется согласно политике браузера с использованием доступных механизмов и локальных данных.

Если путь нельзя построить, имя не совпадает, сертификат истёк или подпись неверна, браузер прекращает автоматическое соединение и показывает ошибку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что доказывает <code>CertificateVerify</code> в TLS 1.3?</strong></summary>

<dl>
<dd>
<h2></h2>

Сервер подписывает данные, включающие hash, или хеш, предыдущих сообщений handshake, закрытым ключом, соответствующим сертификату.

Клиент проверяет подпись через открытый ключ сертификата.

Это доказывает:

- владение закрытым ключом;
- связь подписи с текущим handshake;
- целостность согласованных параметров.

Одной передачи сертификата было бы недостаточно. Публичный сертификат может скопировать любой человек, но сформировать правильную подпись без закрытого ключа он не должен.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое ALPN?</strong></summary>

<dl>
<dd>
<h2></h2>

ALPN (Application-Layer Protocol Negotiation) — расширение TLS, позволяющее клиенту и серверу выбрать прикладной протокол во время установки защищённого соединения.

Например, клиент предлагает:

```text
h2
http/1.1
```

а сервер выбирает один поддерживаемый вариант.

Это позволяет не открывать отдельное соединение и не выполнять дополнительный HTTP-запрос только для определения версии протокола.

Для HTTP/3 через QUIC используются идентификаторы семейства `h3`.

Frontend-код обычно не задаёт ALPN вручную: этим управляют браузер, сервер и сетевая инфраструктура.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему self-signed certificate, или самоподписанный сертификат, вызывает предупреждение?</strong></summary>

<dl>
<dd>
<h2></h2>

Самоподписанный сертификат подписан собственным закрытым ключом и сам объявляет себя доверенным корнем.

С его помощью технически можно установить зашифрованное соединение, но браузер не имеет независимого основания доверять указанному имени. Такой же сертификат мог создать атакующий.

Во внутренней инфраструктуре организация может создать собственный root CA и явно установить его как доверенный на управляемые устройства. Тогда выпущенные им сертификаты будут проходить проверку в рамках этой инфраструктуры.

Для локальной разработки используют локальный CA или инструменты dev-сертификатов.

Отключать проверку сертификата или заставлять пользователей игнорировать предупреждение в production опасно: это уничтожает аутентификацию сервера и делает возможной MITM-атаку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что именно остаётся видимым сети при HTTPS?</strong></summary>

<dl>
<dd>
<h2></h2>

Внутри TLS защищены:

- path;
- query-параметры;
- HTTP-заголовки;
- cookie;
- тело запроса;
- тело ответа.

Наблюдатель сети всё ещё может видеть:

- IP-адреса;
- время и длительность соединения;
- объём переданных данных;
- направление трафика;
- транспортный протокол.

Домен может быть известен из DNS, IP-адреса и незашифрованного SNI.

ECH шифрует реальный SNI и другие чувствительные части `ClientHello`, если его поддерживают клиент и сервер. Шифрованный DNS дополнительно скрывает DNS-запрос от локального наблюдателя, но IP-адрес назначения остаётся видимым.

HTTPS не скрывает данные от браузера, frontend-кода, расширения с достаточными правами, CDN с TLS termination и конечного сервера после расшифрования.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое mixed content, или смешанный контент?</strong></summary>

<dl>
<dd>
<h2></h2>

Mixed content возникает, когда HTTPS-страница пытается загрузить вложенный ресурс через незашифрованный HTTP.

Блокируемый активный ресурс, например:

- script;
- stylesheet;
- `iframe`;
- `fetch`;
- `XMLHttpRequest`;
- `ws://` WebSocket,

может изменить поведение всей страницы или раскрыть данные, поэтому браузер блокирует его.

Некоторые ресурсы вроде отдельных изображений или аудио браузер может автоматически перевести с HTTP на HTTPS. Если ресурс не доступен по HTTPS, загрузка завершится ошибкой.

Точное поведение зависит от типа ресурса и браузера, поэтому приложение не должно рассчитывать на автоматическое исправление.

Надёжное решение — отдавать HTML, API, scripts, styles, media и CDN-ресурсы через HTTPS.

Добавление CORS-заголовков не шифрует HTTP-ресурс и не решает mixed content.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое HSTS?</strong></summary>

<dl>
<dd>
<h2></h2>

HSTS (HTTP Strict Transport Security) — заголовок HTTPS-ответа, который сообщает браузеру обращаться к указанному host только через HTTPS:

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

После получения политики браузер перед будущим сетевым запросом заменяет `http://` на `https://`.

Для HSTS-host браузер также не позволяет пользователю обычным способом обойти серьёзную ошибку сертификата.

Заголовок учитывается только в HTTPS-ответе. Если отправить его по HTTP, браузер должен проигнорировать значение, иначе сетевой атакующий мог бы устанавливать или удалять политику.

HSTS начинает защищать только после первого успешного HTTPS-соединения и получения заголовка. Первый HTTP-визит до этого остаётся уязвимым.

HSTS preload позволяет заранее включить домен в поставляемый браузерами список. Это уменьшает риск первого визита, но программа preload не является частью самого стандарта HSTS и требует долговременно корректного HTTPS для домена и указанных поддоменов.

`includeSubDomains` нужно включать осторожно: после этого каждый поддомен должен поддерживать HTTPS.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>HTTPS защищает от XSS, CSRF и плохой авторизации?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

TLS защищает данные во время передачи между TLS endpoints.

XSS выполняет вредоносный код уже внутри страницы после расшифрования данных.

CSRF использует автоматическую отправку браузером учётных данных к настоящему серверу.

Ошибка авторизации находится в правилах backend, который может неправильно разрешить пользователю чужое действие даже через идеально защищённое TLS-соединение.

Поэтому поверх HTTPS всё равно нужны:

- безопасная обработка недоверенных данных;
- CSP;
- `HttpOnly`, `Secure` и `SameSite`;
- CSRF-защита;
- серверная проверка прав;
- безопасное управление tokens и сессиями.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое TLS termination?</strong></summary>

<dl>
<dd>
<h2></h2>

TLS termination означает, что HTTPS-соединение заканчивается на reverse proxy, load balancer или CDN, а не непосредственно в процессе приложения.

Этот компонент:

- хранит сертификат и закрытый ключ;
- выполняет TLS handshake;
- расшифровывает HTTP-запрос;
- применяет правила безопасности и маршрутизации;
- передаёт запрос следующему сервису.

Внутренний участок может использовать новый TLS-сеанс или незашифрованный HTTP в изолированной сети. HTTPS в браузере защищает только те участки, на которых действительно используется TLS.

Приложение должно доверять `Forwarded`, `X-Forwarded-Proto` и аналогичным заголовкам только от известных proxy. Иначе внешний клиент сможет подделать сведения об исходной схеме, host или IP-адресе.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему TLS добавляет задержку и как её уменьшить?</strong></summary>

<dl>
<dd>
<h2></h2>

До передачи обычных прикладных данных стороны должны согласовать параметры, выполнить обмен ключами и проверить криптографические сообщения.

Полный TLS 1.3 handshake обычно требует одного round trip после установления транспортной связи.

Для HTTPS поверх TCP отдельно требуется установка TCP-соединения. HTTP/3 использует QUIC и объединяет установку транспорта с TLS 1.3, уменьшая часть последовательных сетевых обменов.

Задержку уменьшают:

- повторным использованием соединения;
- HTTP/2 или HTTP/3 multiplexing;
- session resumption;
- близким к пользователю CDN;
- сокращением числа независимых origins;
- предварительным подключением к действительно нужным origin.

`0-RTT early data` может отправляться до полного завершения возобновляемого handshake, но допускает replay.

Поэтому механизм разрешают только для сообщений, которые безопасно повторить. Неидемпотентные операции должны ждать завершения обычного handshake либо иметь самостоятельную защиту от повторного выполнения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>localhost</code> часто считается secure context без HTTPS?</strong></summary>

<dl>
<dd>
<h2></h2>

Браузер может считать loopback-адреса потенциально доверенными, поскольку соединение предназначено для процесса на том же устройстве:

```text
http://localhost
http://127.0.0.1
http://*.localhost
```

Это позволяет использовать многие powerful APIs во время разработки без публичного TLS-сертификата.

Такое исключение не означает, что HTTP был зашифрован. Браузер исходит из того, что корректно разрешённый loopback-трафик не покидает устройство.

Правила могут различаться для:

- произвольного имени локальной сети;
- доступа с другого устройства;
- `iframe`;
- cookies;
- OAuth callback;
- mixed content;
- конкретного browser API.

Поэтому сценарии, зависящие от настоящего HTTPS, нужно отдельно тестировать с локальным доверенным сертификатом.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Роль HTTPS/TLS |
|---|---|
| Загрузка JS bundle | Защищает script от подмены в сети |
| Запрос к API | Шифрует URL, заголовки и тело на каждом TLS-защищённом участке |
| Session cookie | Атрибут `Secure` требует защищённого запроса |
| Service Worker | Требует secure context, кроме потенциально доверенных локальных адресов |
| CDN или reverse proxy | Завершает один TLS-сеанс и при необходимости открывает следующий |
| Mixed content | Приводит к обновлению или блокировке HTTP-ресурса на HTTPS-странице |
| Ошибка сертификата | Возникает до выполнения React-приложения |
| HTTP/2 и HTTP/3 | ALPN помогает согласовать прикладной протокол |
| Повторное соединение | Session resumption уменьшает стоимость нового handshake |
