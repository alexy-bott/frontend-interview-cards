## Вопрос

<br>

 💬 **Что такое SPA и MPA? Чем они отличаются от CSR и SSR?**

<h2></h2>

<br>
<dl>
<dd>

SPA и MPA описывают прежде всего модель навигации между экранами:

- остаётся ли текущий HTML-документ;
- или браузер загружает новый документ.

CSR, SSR и SSG описывают, где и когда формируется HTML и интерфейс:

- в браузере;
- на сервере при запросе;
- заранее при сборке или регенерации.

Это независимые характеристики. Одно приложение может получить серверный HTML, выполнить hydration в браузере и затем использовать SPA-навигацию без полной замены документа.

Упрощённо:

```text
SPA / MPA
→ как выполняется навигация

CSR / SSR / SSG
→ где и когда формируется UI
```

**SPA (Single Page Application, одностраничное приложение)** обычно использует same-document navigation, то есть навигацию внутри текущего `Document`.

При первом входе браузер загружает HTML-документ. После запуска JavaScript client router:

1. Обрабатывает подходящий переход по ссылке.
2. Меняет URL через History API.
3. Определяет новый маршрут.
4. При необходимости загружает данные и JavaScript chunk.
5. Обновляет нужную часть DOM.

Полная загрузка нового HTML-документа при таком переходе не выполняется:

```text
текущий Document сохраняется
→ URL меняется
→ UI обновляется
```

Благодаря этому могут сохраниться:

- JavaScript context;
- in-memory store;
- открытое WebSocket-соединение;
- состояние общих layouts;
- данные уже загруженных экранов;
- состояние компонентов, которые не были размонтированы.

Состояние сохраняется не просто потому, что приложение называется SPA. Оно сохраняется только там, где router и React сохраняют соответствующую часть дерева.

Если компонент получил другой `key`, был удалён из дерева или маршрут использует другой layout, его локальное состояние может сброситься и при SPA-переходе.

**MPA (Multi Page Application, многостраничное приложение)** обычно использует cross-document navigation.

При переходе браузер:

1. Отправляет запрос нового документа.
2. Получает HTML для нового URL.
3. Делает новый `Document` активным.
4. Строит DOM.
5. Загружает и выполняет scripts новой страницы.

Упрощённо:

```text
старый Document
→ запрос нового HTML
→ новый Document
```

Обычные JavaScript-переменные и состояние старого документа при такой навигации больше недоступны новому документу.

Состояние, которое должно пережить переход, сохраняют отдельно:

- в URL;
- в cookie;
- в `sessionStorage`;
- в `localStorage`;
- в IndexedDB;
- на сервере.

MPA не означает приложение без JavaScript. Каждая страница может содержать:

- React-компоненты;
- формы с клиентской валидацией;
- интерактивные виджеты;
- клиентские запросы;
- отдельные SPA-области;
- islands, то есть независимые интерактивные блоки.

Cross-document navigation также не всегда означает повторную загрузку страницы с сервера.

При переходах назад и вперёд браузер может использовать back/forward cache, или bfcache. Тогда предыдущий документ сохраняется в памяти вместе с DOM и JavaScript-состоянием, временно приостанавливается, а затем восстанавливается.

Поэтому MPA-страница после кнопки «назад» иногда возвращается почти мгновенно с прежним состоянием формы и прокрутки.

Приложение не должно полностью полагаться на bfcache: возможность сохранения зависит от браузера, поведения страницы и доступных ресурсов.

**CSR (Client-Side Rendering, клиентский рендеринг)** означает, что интерфейс или его значимая часть формируется JavaScript-кодом в браузере.

В чистом CSR-сценарии сервер может вернуть минимальный HTML:

```html
<div id="root"></div>
<script src="/app.js"></script>
```

Затем браузер:

1. Загружает JavaScript bundle.
2. Разбирает и выполняет код.
3. Создаёт React root.
4. При необходимости запрашивает данные.
5. Создаёт элементы интерфейса.

До выполнения этих шагов основное содержимое может отсутствовать либо быть представлено только статическим placeholder.

CSR часто используется в SPA, но эти понятия не являются синонимами.

Возможны разные сочетания:

```text
SPA + CSR
```

Client router и весь интерфейс работают в браузере.

```text
SPA + SSR + hydration
```

Первый HTML приходит с сервера, а последующая навигация выполняется в текущем документе.

```text
MPA + CSR widgets
```

Каждый маршрут загружает новый документ, но отдельные части страницы создаются или обновляются JavaScript-кодом.

```text
MPA + server-rendered HTML
```

Каждый переход получает готовый HTML нового документа.

**SSR (Server-Side Rendering, серверный рендеринг)** означает, что HTML создаётся сервером для конкретного запроса.

Например:

```text
GET /products/42
→ сервер получает данные товара
→ формирует HTML
→ отправляет документ браузеру
```

Браузер может показать содержимое до загрузки и выполнения всего клиентского JavaScript.

SSR не означает, что страница обязательно интерактивна без JavaScript. Если серверный React-интерфейс содержит клиентские обработчики и состояние, после загрузки выполняется hydration.

SSR также не является общим названием для любого HTML, созданного не в браузере.

Если HTML сформирован заранее при сборке, это обычно называют:

- static rendering;
- prerendering;
- SSG.

Если HTML формируется для каждого запроса, это SSR.

Если заранее созданная страница периодически обновляется после deployment, framework может называть подход regeneration или ISR.

**SSG (Static Site Generation, статическая генерация)** создаёт HTML до пользовательского запроса:

```text
build или regeneration
→ готовый HTML-файл
→ CDN
→ пользователь
```

При запросе серверу не нужно заново выполнять полный рендер страницы. Он может вернуть уже готовый документ из файлового хранилища или CDN.

SSG хорошо подходит для:

- документации;
- статей;
- маркетинговых страниц;
- каталогов, которые можно обновлять с допустимой задержкой.

Статически созданная страница после загрузки тоже может гидратироваться и использовать SPA-переходы.

Следовательно:

```text
server-generated HTML ≠ обязательно SSR
```

Нужно уточнять момент генерации:

```text
на каждый request → SSR
заранее             → SSG/prerendering
```

**Hydration, или гидратация**, связывает уже существующий серверный HTML с клиентским деревом React.

Сервер отправляет, например:

```html
<button>Добавить в корзину</button>
```

Браузер может показать кнопку сразу. Затем React запускается в браузере, сопоставляет существующую разметку с компонентами и подключает интерактивное поведение.

```text
серверный HTML
+
клиентские компоненты
=
интерактивный интерфейс
```

Hydration не должна без необходимости удалить весь серверный DOM и создать его заново. React ожидает, что начальный клиентский результат соответствует серверной разметке.

Hydration mismatch возникает, если сервер и клиент при первом рендере получили различный результат.

Частые причины:

- использование `Date.now()` непосредственно в render;
- случайное значение;
- чтение `window` только на клиенте;
- различное форматирование даты;
- HTML, изменённый расширением браузера;
- зависимость от локального хранилища без согласованного начального значения;
- недопустимая HTML-вложенность.

Mismatch может привести к предупреждению, дополнительному клиентскому рендеру и потере преимуществ серверного HTML. Такое несовпадение нужно исправлять, а не скрывать без необходимости.

Не каждый server-rendered HTML требует hydration.

Если страница является обычным документом с native links и forms, она может работать без React в браузере.

Hydration нужна тем областям, которым требуется клиентская интерактивность:

- обработчики событий;
- локальное состояние;
- effects;
- browser APIs;
- клиентский router.

Современный framework может передавать HTML частями через streaming и постепенно делать интерактивными отдельные области, не ожидая полной готовности всей страницы.

SPA/MPA и CSR/SSR можно представить как две независимые оси:

| Модель | Что описывает | Основной вопрос |
|---|---|---|
| SPA | Навигацию | Сохраняется ли текущий `Document` при переходе? |
| MPA | Навигацию | Загружается ли новый `Document` для страницы? |
| CSR | Рендеринг | Формирует ли UI JavaScript в браузере? |
| SSR | Рендеринг | Формирует ли сервер HTML для текущего запроса? |
| SSG | Рендеринг | Формируется ли HTML заранее? |

Сравнение SPA- и MPA-навигации:

| Событие | SPA с client router | Классическая MPA |
|---|---|---|
| Первый вход по URL | Выполняется обычная загрузка документа; HTML может быть создан через CSR, SSR или SSG | Выполняется обычная загрузка документа; HTML обычно соответствует конкретной странице |
| Внутренний переход | Обычно same-document transition | Обычно cross-document navigation |
| Новый HTML-документ | Обычно нет | Обычно да |
| JavaScript context | Сохраняется | Создаётся заново, кроме восстановления через bfcache |
| Состояние общих компонентов | Может сохраниться, если соответствующая часть дерева остаётся | Обычно передаётся через URL, storage или сервер |
| Серверный маршрут при прямом входе | Нужен route handler или корректный SPA fallback | Сервер возвращает документ соответствующей страницы |
| Обновление страницы | Всегда создаёт обычный document request | Также создаёт обычный document request |
| Back/forward | Router восстанавливает состояние маршрута; возможен собственный кеш | Браузер может загрузить документ или восстановить его из bfcache |

Client router обычно использует History API:

```ts
history.pushState(
  { selectedTab: "orders" },
  "",
  "/profile?tab=orders",
);
```

`pushState()`:

- меняет URL;
- добавляет запись в session history;
- сохраняет переданное serializable state;
- не выполняет HTTP-навигацию;
- не создаёт новый `Document`;
- сам по себе не вызывает `popstate`.

URL должен относиться к тому же origin, что и текущий документ. Через `pushState()` нельзя незаметно превратить страницу одного origin в страницу другого origin.

`replaceState()` изменяет текущую запись:

```ts
history.replaceState(
  null,
  "",
  "/profile?tab=orders",
);
```

Он полезен для:

- нормализации URL;
- удаления временного параметра;
- исправления текущей записи;
- перенаправления, к которому пользователь не должен возвращаться кнопкой «назад».

Когда пользователь перемещается по истории через кнопки назад и вперёд, `history.back()`, `history.forward()` или `history.go()`, браузер может создать событие:

```ts
window.addEventListener("popstate", (event) => {
  renderRoute(window.location, event.state);
});
```

Router читает новый URL и восстанавливает соответствующий экран.

Сам вызов `pushState()` или `replaceState()` `popstate` не создаёт. Поэтому router обычно сам обновляет UI сразу после программного изменения истории.

Fragment-навигация:

```text
/docs#installation
```

тоже может быть same-document navigation. Она может создавать `hashchange`, но `pushState()` не создаёт `hashchange`, даже если новый URL отличается fragment.

В production-router не следует превращать любой клик в client-side transition.

Обычно перехватывают подходящий переход, если:

- нажата основная кнопка мыши;
- не используется `Ctrl`, `Cmd`, `Shift` или `Alt`;
- ссылка относится к поддерживаемому маршруту;
- переход остаётся внутри приложения;
- отсутствуют `download` и специальные target;
- событие не было отменено другим обработчиком.

Для навигации следует сохранять настоящий link:

```html
<a href="/profile">Профиль</a>
```

а не заменять его на:

```html
<div onclick="openProfile()">Профиль</div>
```

Настоящий `<a href>`:

- доступен клавиатуре;
- имеет правильную семантику;
- позволяет открыть ссылку в новой вкладке;
- поддерживает копирование адреса;
- продолжает работать как полная навигация, если JavaScript не запустился;
- может быть улучшен router через client-side transition.

Такой подход является progressive enhancement: базовая навигация работает средствами браузера, а JavaScript делает её быстрее и сохраняет состояние приложения.

При прямом открытии URL запрос всегда сначала получает сервер:

```text
GET /profile/settings
```

Если маршрут обслуживается SSR/SSG-framework, сервер или CDN возвращает соответствующий HTML.

Если это client-only SPA и отдельного файла `/profile/settings` нет, сервер настраивают на внутренний rewrite:

```text
/profile/settings
→ /index.html
```

Адрес в браузере при этом остаётся:

```text
/profile/settings
```

После загрузки client router читает URL и показывает нужный экран.

Нельзя безусловно перенаправлять на `index.html` все неизвестные запросы.

Например:

```text
/api/users
/assets/app.js
/images/avatar.png
```

должны обрабатываться API или статическим сервером. Если файл отсутствует, сервер должен вернуть правильный `404`, а не HTML.

Иначе браузер может получить:

```text
Content-Type: text/html
```

вместо JavaScript или JSON, что приведёт к ошибкам вроде:

```text
Unexpected token '<'
```

SPA также должна корректно различать:

- существующий client route;
- неизвестный route;
- отсутствующий ресурс.

Простой wildcard fallback часто возвращает `200 OK` даже для несуществующего маршрута. Для публичного сайта с требованиями к SEO и корректным HTTP-статусам лучше, чтобы сервер или framework понимал маршруты и мог вернуть настоящий `404`.

SPA не обязана использовать только client-side navigation.

Приложение может намеренно выполнить полную навигацию:

```ts
window.location.assign("/logout");
```

или использовать обычную ссылку на:

- другой origin;
- файл;
- legacy-приложение;
- страницу с отдельным frontend;
- маршрут, который должен полностью сбросить состояние.

MPA, в свою очередь, может содержать вложенную SPA-область. Поэтому реальные системы часто сочетают обе модели.

Производительность нельзя определить только по словам SPA, MPA, CSR или SSR.

CSR может иметь дорогой initial load:

```text
HTML shell
→ большой JavaScript bundle
→ выполнение JavaScript
→ запрос данных
→ рендер
```

После загрузки последующие client-side transitions могут быть быстрыми благодаря:

- сохранённому документу;
- кешу данных;
- route-level code splitting;
- prefetch;
- сохранённым layouts.

SSR может раньше показать основное содержимое, но интерактивность всё ещё может задерживаться из-за:

- большого клиентского bundle;
- hydration;
- long tasks;
- медленных third-party scripts;
- последовательных запросов данных.

MPA может быть быстрой благодаря:

- небольшому JavaScript;
- HTTP-кешу;
- CDN;
- prerendering;
- bfcache;
- browser-native navigation.

SPA может быть медленной, если каждый маршрут загружает большой код и выполняет дорогой render.

Поэтому измеряют отдельно:

- время появления содержимого;
- время до интерактивности;
- скорость переходов;
- размер JavaScript;
- количество запросов;
- server response time;
- main-thread work;
- использование кеша.

SSR и SSG также не являются автоматической гарантией хорошего SEO.

Они упрощают получение:

- содержимого в HTML;
- корректного `<title>`;
- metadata;
- canonical URL;
- HTTP-статуса;
- ссылок.

Но поисковая доступность всё равно зависит от:

- качества HTML;
- индексируемости маршрута;
- `robots`;
- canonical;
- статуса `404`;
- скорости;
- отсутствия ошибок;
- согласованности контента.

Client-rendered страницу тоже могут обработать современные crawlers, но серверный или заранее созданный HTML уменьшает зависимость от выполнения JavaScript.

Для SPA-навигации приложение берёт на себя часть поведения, которую при полной навигации выполняет браузер.

После перехода router или UI-слой должен продумать:

- обновление `document.title`;
- фокус клавиатуры;
- позицию прокрутки;
- announcement для assistive technologies;
- состояния загрузки;
- ошибки маршрута;
- отмену старых запросов;
- восстановление при back/forward.

Если ссылка заменяет основное содержимое без document navigation, focus может остаться на элементе, который исчез или больше не соответствует новому экрану.

Часто после завершения перехода focus переводят на основной заголовок или контейнер нового содержимого:

```html
<h1 tabindex="-1">Настройки профиля</h1>
```

Конкретная политика зависит от приложения. Не следует безусловно переводить focus при каждом небольшом изменении query-параметра, если пользователь остаётся в том же контексте.

Для существенного перехода полезно:

- обновить title;
- обеспечить логичный focus;
- восстановить или сбросить scroll;
- сообщить screen reader о завершении загрузки.

Полная MPA-навигация предоставляет большую часть этого поведения браузеру автоматически, но разработчик всё равно отвечает за корректный title, структуру headings и focus order новой страницы.

Современные frameworks часто создают гибридную модель.

В Next.js App Router:

- Pages и Layouts являются Server Components по умолчанию;
- сервер формирует Server Component Payload;
- на первом входе создаётся HTML для быстрого отображения;
- JavaScript Client Components загружается в браузер;
- интерактивные Client Components гидратируются;
- последующие переходы через `<Link>` могут выполняться без полной загрузки документа;
- route payload может загружаться заранее через prefetch;
- общие layouts могут сохранять состояние и оставаться интерактивными;
- отдельные части маршрута могут передаваться через streaming.

React Server Components и SSR — связанные, но разные понятия.

Server Component:

- выполняется на сервере;
- может получать серверные данные;
- не отправляет свой component code в клиентский JavaScript bundle;
- не использует browser APIs;
- не содержит обычное клиентское интерактивное состояние.

Server Components сами по себе не гидратируются.

Client Component:

- может использовать state и effects;
- может содержать event handlers;
- получает JavaScript в браузере;
- участвует в hydration при первом server-rendered отображении.

SSR отвечает за создание HTML для загрузки страницы, а Server Components определяют, какие компоненты выполняются только на сервере и какой payload передаётся React.

При client-side transition Next.js может запросить новый Server Component Payload, обновить изменившиеся route segments и сохранить общие layouts без полной замены документа.

Поэтому приложение может одновременно использовать:

```text
server rendering
+
React Server Components
+
hydration Client Components
+
SPA-like client navigation
```

Наличие SSR не превращает его автоматически в классическую MPA, а наличие React не делает любую систему чистой SPA.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>SPA и CSR - одно и то же?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

SPA описывает модель навигации: внутренние переходы обычно сохраняют текущий `Document` и обновляют UI через client router.

CSR описывает место формирования интерфейса: UI создаётся JavaScript-кодом в браузере.

Возможна SPA с SSR:

```text
первый запрос
→ server-rendered HTML
→ hydration
→ client-side transitions
```

Возможна MPA с CSR-компонентами:

```text
новый документ для каждого маршрута
+
интерактивные React-виджеты внутри страниц
```

Поэтому термины связаны, но отвечают на разные вопросы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>SSR превращает SPA в MPA?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

SSR определяет, что HTML для запроса создаётся сервером.

SPA/MPA определяют, что происходит при переходе между маршрутами.

Если после серверного HTML client router меняет маршрут без загрузки нового документа, приложение сохраняет SPA-поведение.

Если каждый переход получает новый HTML-документ, используется MPA-поведение.

Одно приложение может поддерживать оба варианта:

- client-side transition при обычном клике;
- полную document navigation при reload, прямом входе или переходе между независимыми частями системы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем SSR отличается от SSG?</strong></summary>

<dl>
<dd>
<h2></h2>

SSR создаёт HTML для конкретного запроса:

```text
request
→ server render
→ HTML response
```

SSG создаёт HTML заранее:

```text
build или regeneration
→ готовый HTML
→ CDN
→ request
```

SSR подходит для данных, которые должны вычисляться для каждого запроса или пользователя.

SSG подходит для содержимого, которое можно подготовить заранее и эффективно раздавать через CDN.

Оба варианта могут отправить браузеру готовый HTML, а затем выполнить hydration и SPA-навигацию.

Поэтому по одному содержимому HTML-response нельзя определить, был ли он создан при запросе или заранее.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое hydration и зачем она нужна?</strong></summary>

<dl>
<dd>
<h2></h2>

Hydration — процесс, при котором React присоединяет клиентское дерево компонентов к HTML, ранее созданному сервером.

React повторно использует существующие DOM-элементы и подключает:

- обработчики событий;
- state;
- effects;
- последующие обновления.

До hydration HTML уже может быть виден. Обычные links и forms могут работать средствами браузера, но React-интерактивность ещё не обязательно доступна.

Серверный и первый клиентский render должны выдавать согласованную разметку. Различие вызывает hydration mismatch и может привести к дополнительному клиентскому рендеру.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем React Server Components отличаются от SSR?</strong></summary>

<dl>
<dd>
<h2></h2>

SSR создаёт HTML для начальной загрузки страницы.

React Server Components определяют компоненты, которые выполняются только на сервере и передают клиенту сериализованный React payload, а не собственный JavaScript-код компонента.

Server Components:

- не используют browser APIs;
- не содержат обычные event handlers;
- не гидратируются;
- могут читать серверные данные напрямую.

Client Components:

- получают JavaScript в браузере;
- могут использовать state, effects и events;
- гидратируются при initial server rendering.

В Next.js App Router эти механизмы работают совместно: сервер формирует HTML и RSC payload, а браузер гидратирует только клиентские интерактивные части.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем client-side transition, или клиентский переход, отличается от полной навигации документа?</strong></summary>

<dl>
<dd>
<h2></h2>

При client-side transition текущий `Document` остаётся активным.

Router:

- меняет URL;
- загружает данные или route chunk;
- обновляет часть UI;
- может сохранить общий layout и in-memory state.

При полной навигации браузер загружает другой документ:

```text
старый Document
→ новый HTML
→ новый Document
→ новый JavaScript context
```

Старое состояние в памяти обычно становится недоступным.

При переходе назад браузер может восстановить предыдущий документ из bfcache, но приложение не должно считать такое восстановление гарантированным.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое back/forward cache и как он влияет на MPA?</strong></summary>

<dl>
<dd>
<h2></h2>

Back/forward cache, или bfcache, может сохранить весь документ при переходе на другую страницу:

- DOM;
- JavaScript heap;
- положение прокрутки;
- состояние формы;
- часть browser state.

Выполнение JavaScript приостанавливается.

Если пользователь возвращается кнопкой «назад», браузер может восстановить документ вместо повторной загрузки и выполнения scripts с нуля.

Страница получает события `pagehide` и `pageshow`. У `pageshow` можно проверить:

```ts
window.addEventListener("pageshow", (event) => {
  if (event.persisted) {
    refreshPossiblyStaleData();
  }
});
```

После восстановления часть серверных данных могла устареть, поэтому приложение при необходимости выполняет revalidation.

bfcache делает MPA-переходы назад и вперёд быстрее, но не превращает обычную cross-document navigation в SPA.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему SPA работает по ссылке, но после обновления вложенного URL сервер отвечает <code>404</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

При клике внутри SPA маршрут обрабатывает client router, и новый HTML-документ не запрашивается.

При reload или прямом открытии браузер отправляет серверу обычный запрос:

```text
GET /profile/settings
```

Если сервер знает только файл `/index.html`, он может вернуть `404`.

Для client-only SPA настраивают fallback rewrite:

```text
/profile/settings
→ /index.html
```

После загрузки router читает исходный URL и показывает нужный экран.

Fallback должен применяться только к document routes. API, JavaScript, CSS, изображения и другие статические файлы должны возвращать собственный response или правильный `404`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>pushState</code>, <code>replaceState</code> и <code>popstate</code> отличаются друг от друга?</strong></summary>

<dl>
<dd>
<h2></h2>

`pushState()` добавляет запись в session history:

```ts
history.pushState(data, "", "/products?page=2");
```

Пользователь сможет вернуться к предыдущей записи.

`replaceState()` заменяет текущую запись:

```ts
history.replaceState(data, "", "/products?page=2");
```

Он подходит для нормализации URL или удаления временного параметра без создания лишнего шага истории.

`popstate` возникает при переходе к другой записи истории, например через кнопки назад и вперёд.

Вызовы `pushState()` и `replaceState()` сами по себе `popstate` не вызывают.

Они также не загружают новый документ. Router должен самостоятельно обновить интерфейс для нового URL.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда используют hash routing?</strong></summary>

<dl>
<dd>
<h2></h2>

При hash routing маршрут хранится во fragment:

```text
/index.html#/profile
```

Fragment не отправляется серверу. Поэтому сервер всегда получает запрос одного документа:

```text
/index.html
```

Отдельный fallback для `/profile` не нужен, поскольку этот path не отправляется в HTTP-запросе.

Преимущества:

- работает на простом статическом hosting;
- не требует server rewrite для вложенных маршрутов.

Недостатки:

- менее привычный URL;
- fragment нельзя использовать независимо для перехода к части документа;
- сложнее интеграция с серверными routes и metadata;
- сервер не знает клиентский маршрут из HTTP-запроса.

History routing с обычными paths чаще предпочтительнее, если сервер можно правильно настроить.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли SPA работать без JavaScript?</strong></summary>

<dl>
<dd>
<h2></h2>

Client-side transition требует работающего JavaScript-router.

Но приложение можно построить с progressive enhancement:

```html
<a href="/products/42">Товар</a>
```

Без JavaScript браузер выполнит обычную document navigation.

После запуска JavaScript router перехватит подходящий клик и выполнит client-side transition.

Для такого fallback сервер должен уметь вернуть HTML по каждому публичному URL.

Чистая CSR SPA, где сервер всегда возвращает пустой `<div id="root">`, без JavaScript не сможет показать основной интерфейс.

Поэтому устойчивость без JavaScript зависит не от названия SPA, а от серверного HTML и использования native links/forms.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где хранить состояние: в router, памяти приложения или storage?</strong></summary>

<dl>
<dd>
<h2></h2>

В URL хранят состояние, которое должно:

- переживать reload;
- работать с back/forward;
- передаваться ссылкой;
- участвовать в маршрутизации.

Например:

- фильтры;
- сортировку;
- пагинацию;
- выбранную вкладку;
- идентификатор открытой сущности.

В памяти компонентов или store хранят временное состояние текущего документа:

- открытый dropdown;
- состояние modal;
- несохранённый UI selection;
- локальный кеш.

В `sessionStorage` сохраняют данные конкретной page session.

В `localStorage` или IndexedDB сохраняют состояние, которое должно пережить закрытие страницы, если это соответствует требованиям безопасности.

Критичные данные хранят на сервере.

Одно значение не следует без необходимости дублировать в URL, store и storage: нужен один источник истины и явные правила синхронизации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Достаточно ли protected route на клиенте для защиты данных?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Client route guard улучшает UX:

- скрывает экран;
- показывает login;
- выполняет redirect;
- не запускает ненужный запрос.

Но пользователь контролирует browser code и может вызвать API напрямую.

Backend обязан для каждого защищённого запроса проверить:

- authentication;
- authorization;
- доступ к конкретному ресурсу;
- допустимость операции.

Скрытый route или отсутствующая кнопка не являются security boundary.

Для SSR-route сервер также должен проверить права до передачи защищённых данных в HTML или server payload.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что router должен делать для доступности после клиентского перехода?</strong></summary>

<dl>
<dd>
<h2></h2>

Полная document navigation автоматически создаёт новый контекст страницы. В SPA тот же документ остаётся активным, поэтому часть поведения должен организовать код приложения.

Для существенного перехода обычно продумывают:

- новый `document.title`;
- логичное перемещение focus;
- восстановление или сброс scroll;
- сообщение о загрузке и ошибке;
- announcement для assistive technologies;
- правильный основной heading.

Focus часто переводят на заголовок нового экрана или основной контейнер:

```html
<h1 tabindex="-1">История заказов</h1>
```

Но focus не нужно безусловно перемещать при каждом небольшом изменении фильтра или query-параметра.

Router должен различать новую страницу и обновление части текущего экрана.

Навигационные элементы должны оставаться настоящими links, чтобы работать с клавиатурой, новой вкладкой и контекстным меню браузера.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как code splitting и prefetch влияют на SPA-навигацию?</strong></summary>

<dl>
<dd>
<h2></h2>

Route-level code splitting не включает JavaScript всех экранов в initial bundle.

Код маршрута загружается при необходимости:

```text
переход
→ загрузка route chunk
→ выполнение кода
→ отображение экрана
```

Prefetch начинает загрузку вероятного маршрута заранее, например когда ссылка появилась во viewport или пользователь навёл на неё указатель.

Тогда к моменту клика код и данные уже могут находиться в кеше.

Слишком агрессивный prefetch:

- тратит трафик;
- нагружает backend;
- занимает память;
- конкурирует с критичными ресурсами;
- загружает маршруты, которые пользователь не откроет.

Стратегию выбирают с учётом вероятности перехода, типа сети, размера route payload и чувствительности данных.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Гарантирует ли SSR хорошую производительность и SEO?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

SSR может раньше предоставить HTML и основное содержимое, но пользователь всё ещё может ждать:

- медленный server render;
- загрузку JavaScript;
- hydration;
- выполнение long tasks;
- клиентские данные;
- third-party scripts.

Для SEO server-rendered HTML упрощает получение контента, metadata и ссылок, но нужны также:

- правильные HTTP-статусы;
- canonical URL;
- title и description;
- доступная структура;
- отсутствие блокировки индексации;
- стабильный контент.

CSR-страницы тоже могут индексироваться поддерживающими JavaScript crawlers, но сильнее зависят от успешной загрузки и выполнения кода.

SSR является инструментом, а не автоматической гарантией результата.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда MPA может быть лучше SPA?</strong></summary>

<dl>
<dd>
<h2></h2>

MPA может быть удобнее, когда:

- страницы слабо связаны;
- требуется мало общего client state;
- важен минимальный JavaScript;
- navigation flow управляется сервером;
- разные разделы развёртываются независимо;
- нужна простая progressive enhancement;
- интерфейс состоит преимущественно из документов и форм.

SPA удобна для долгоживущего интерактивного интерфейса:

- редактора;
- административной панели;
- карты;
- почтового клиента;
- системы с частыми переходами и общим состоянием.

MPA может быть быстрой благодаря CDN, HTTP-кешу, prerendering и bfcache.

SPA может быть медленной из-за большого bundle и дорогого client render.

Решение принимают по поведению продукта, стоимости JavaScript, серверной архитектуре и требованиям к навигации, а не по правилу «SPA современнее».

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

- React Router связывает URL с деревом UI и выполняет same-document transitions в SPA.
- Next.js сочетает server rendering, Server Components, hydration Client Components, streaming, prefetch и client-side transitions.
- SSG заранее создаёт HTML, но после hydration страница может использовать SPA-навигацию.
- Фильтры каталога и пагинацию удобно хранить в query-параметрах, чтобы состояние переживало обновление страницы и передавалось ссылкой.
- Для client-only SPA сервер или CDN настраивают на возврат `index.html` для клиентских document routes, не затрагивая API и статические ресурсы.
- Настоящие `<a href>` позволяют использовать client router как улучшение, сохраняя обычную browser navigation как fallback.
- После клиентского перехода приложение отвечает за focus, title, scroll, состояния загрузки и ошибки.
- При cross-document navigation браузер может восстановить страницу из bfcache, поэтому данные после `pageshow` иногда нужно проверить на актуальность.
