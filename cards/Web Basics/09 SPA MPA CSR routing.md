## Вопрос

Что такое SPA и MPA? Чем они отличаются от CSR и SSR?

<details>
<summary><strong>Показать ответ</strong></summary>

SPA и MPA описывают прежде всего модель навигации между экранами. CSR и SSR описывают место, где формируется интерфейс. Эти характеристики связаны, но не являются взаимоисключающими: одно приложение может сочетать server rendering, или серверный рендеринг, первой страницы, hydration, или гидратацию, в браузере и дальнейшие клиентские переходы.

**SPA (Single Page Application, одностраничное приложение)** загружает HTML-документ, после чего переходы между маршрутами обычно происходят без полной загрузки нового документа. Client router, или клиентский маршрутизатор, меняет URL через History API, выбирает нужный экран и при необходимости загружает JavaScript chunks и данные. DOM текущего документа обновляется, поэтому состояние общих компонентов может сохраняться между переходами.

**MPA (Multi Page Application, многостраничное приложение)** при переходе обычно запрашивает новый HTML-документ у сервера. Браузер заменяет старый документ новым, заново строит DOM и запускает подключенные scripts, или скрипты. В таком приложении каждая страница может содержать клиентскую интерактивность, поэтому MPA не означает «приложение без JavaScript».

**CSR (Client-Side Rendering, клиентский рендеринг)** означает, что интерфейс формируется JavaScript-кодом в браузере. Сервер может вернуть минимальный HTML с контейнером, после чего bundle загрузится, код запросит данные и создаст UI. CSR часто используется в SPA, но это не синоним SPA: отдельная страница MPA тоже может дорисовывать часть интерфейса на клиенте.

**SSR (Server-Side Rendering, серверный рендеринг)** означает, что сервер создает HTML для конкретного запроса. Браузер может показать этот HTML до выполнения всего клиентского JavaScript. Если серверный React-интерфейс должен стать интерактивным, React выполняет hydration, или гидратацию: связывает существующую HTML-разметку с компонентами и обработчиками событий. После гидратации приложение может продолжить работу как SPA с клиентскими переходами.

| Событие | SPA с клиентским router | Классическая MPA |
|---|---|---|
| Первый вход по URL | Браузер загружает документ, scripts и данные; HTML может быть создан сервером или клиентом | Браузер загружает готовый документ для страницы |
| Переход внутри приложения | Router меняет URL и UI без замены документа | Браузер запрашивает и загружает новый документ |
| Состояние в памяти | Может сохраниться, если соответствующие компоненты не размонтированы | Обычно сбрасывается вместе со старым документом |
| Ошибка настройки маршрута | Прямой вход на вложенный URL может получить серверный `404` | Сервер изначально знает отдельный URL каждой страницы |

Для клиентской навигации router обычно вызывает `history.pushState()` или `history.replaceState()`. Эти методы меняют URL и запись в истории без загрузки документа. При переходе пользователя назад или вперед браузер создает событие `popstate`, и router восстанавливает экран для нового URL. Сам вызов `pushState()` событие `popstate` не создает.

При прямом открытии `/profile/settings` запрос всегда сначала получает сервер. Если это чистая SPA без серверного route handler, то есть обработчика маршрута, сервер должен выполнить rewrite, или внутреннее перенаправление, и вернуть основной `index.html` для неизвестного клиентского маршрута. При этом запросы к API и отсутствующим статическим файлам нельзя без разбора перенаправлять на `index.html`, иначе вместо правильного `404` клиент получит HTML там, где ожидал JSON или JavaScript.

Современные фреймворки часто создают гибридную модель. Например, Next.js может сформировать HTML на сервере для первого входа, отправить React Server Component payload, то есть данные дерева серверных компонентов, при следующем переходе и обновить страницу через client-side transition, или клиентский переход, без полной перезагрузки. Поэтому по одному признаку SSR нельзя назвать приложение MPA, а по наличию React - SPA.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> SPA и CSR - одно и то же?</summary>

Нет. SPA описывает навигацию без обязательной замены HTML-документа, а CSR - создание UI в браузере. SPA может получить готовый HTML через SSR, выполнить гидратацию и затем использовать клиентскую навигацию. MPA тоже может применять CSR для отдельных интерактивных блоков внутри страницы.

</details>

<details>
<summary><strong>Вопрос:</strong> SSR превращает SPA в MPA?</summary>

Нет. SSR определяет, где создан HTML для конкретной загрузки, а SPA/MPA - как устроены переходы между страницами. Если после серверного HTML router выполняет переходы без загрузки нового документа, приложение сохраняет SPA-поведение. Если каждый переход загружает новый документ, это MPA-поведение.

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое hydration и зачем она нужна?</summary>

Hydration, или гидратация, - запуск клиентского React поверх HTML, который уже сформирован сервером. React сопоставляет существующую разметку с деревом компонентов и подключает интерактивное поведение. Серверный и первый клиентский результат должны совпадать; иначе возникает hydration mismatch, то есть несовпадение разметки. До гидратации HTML может быть виден, но зависящие от JavaScript элементы еще не обязательно реагируют на действия пользователя.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем client-side transition, или клиентский переход, отличается от полной навигации документа?</summary>

При client-side transition текущий документ остается загруженным: router меняет URL, получает нужные данные или код и обновляет часть UI. При полной навигации браузер запрашивает новый HTML, уничтожает старый document и JavaScript context, то есть среду выполнения кода документа, затем заново строит страницу. Из-за этого обычные переменные и состояние в памяти теряются.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему SPA работает по ссылке, но после обновления вложенного URL сервер отвечает <code>404</code>?</summary>

При клике внутри SPA маршрут обрабатывает client router. При обновлении страницы браузер делает обычный HTTP-запрос `/profile/settings` к серверу, а сервер может не знать такого файла или route. Для client-only SPA настраивают fallback rewrite на `index.html`, после чего router разбирает URL в браузере. Серверные маршруты, API и статические файлы должны обрабатываться отдельно.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем <code>pushState</code>, <code>replaceState</code> и <code>popstate</code> отличаются друг от друга?</summary>

`pushState` добавляет новую запись в историю, поэтому пользователь может вернуться назад. `replaceState` заменяет текущую запись и подходит, например, для служебной нормализации URL. `popstate` сообщает приложению о переходе к другой записи истории, обычно через кнопки назад и вперед. Вызовы `pushState` и `replaceState` сами по себе `popstate` не вызывают.

</details>

<details>
<summary><strong>Вопрос:</strong> Когда используют hash routing?</summary>

При hash routing маршрут хранится во fragment, части URL после `#`, например `/index.html#/profile`. Fragment не отправляется серверу, поэтому тот всегда получает запрос одного и того же документа и отдельный fallback обычно не нужен. Недостатки - менее привычные URL, ограничения интеграции с серверной маршрутизацией и необходимость отдельно обрабатывать fragment. History routing с обычными путями чаще предпочтительнее, когда сервер можно настроить.

</details>

<details>
<summary><strong>Вопрос:</strong> Где хранить состояние: в router, памяти приложения или storage?</summary>

В URL хранят состояние, которое должно переживать обновление и быть доступно по ссылке: фильтры, сортировку, страницу пагинации, выбранную вкладку. В памяти компонентов или store хранят временное UI-состояние, которое не нужно отражать в ссылке. В persistent storage, или постоянном хранилище, сохраняют данные, которые должны переживать закрытие страницы. Дублирование одного значения в нескольких местах требует правил синхронизации и часто приводит к рассогласованию.

</details>

<details>
<summary><strong>Вопрос:</strong> Достаточно ли protected route на клиенте для защиты данных?</summary>

Нет. Client route guard, или клиентская проверка маршрута, улучшает UX: скрывает экран или перенаправляет пользователя до рендера. Но пользователь контролирует браузерный код и может вызвать API напрямую. Сервер обязан отдельно проверить authentication и authorization, то есть личность и права пользователя, для каждого защищенного запроса. Клиентская проверка не является границей безопасности.

</details>

<details>
<summary><strong>Вопрос:</strong> Что router должен делать для доступности после клиентского перехода?</summary>

При полной навигации браузер сам загружает новый документ, меняет title и начинает работу с новой страницей. В SPA это должен организовать код: обновить `document.title`, переместить focus, или фокус клавиатуры, к основному заголовку либо контейнеру содержимого, корректно восстановить scroll и сообщить о существенном изменении экрана assistive technologies, то есть вспомогательным технологиям. Простая замена DOM без управления фокусом может оставить пользователя клавиатуры в исчезнувшем элементе.

</details>

<details>
<summary><strong>Вопрос:</strong> Как code splitting и prefetch влияют на SPA-навигацию?</summary>

Route-level code splitting, или разделение кода по маршрутам, не включает код всех экранов в initial bundle: chunk маршрута загружается перед его показом. Prefetch, предварительная загрузка, начинает получать вероятный маршрут заранее, например когда ссылка попала во viewport, видимую область страницы. Это ускоряет переход, но слишком агрессивный prefetch тратит трафик, память и серверные ресурсы, поэтому его применяют к действительно вероятным переходам.

</details>

<details>
<summary><strong>Вопрос:</strong> Когда MPA может быть лучше SPA?</summary>

MPA подходит, когда страницы слабо связаны, требуется мало клиентского состояния и важны простой управляемый сервером поток страниц, минимальный JavaScript или независимый деплой частей системы. SPA удобна для долгоживущих интерактивных интерфейсов с частыми переходами и общим состоянием, например редактора или административной панели. Решение принимают по сценарию, а не по правилу «SPA современнее».

</details>

## Где это встречается во frontend

- React Router связывает URL с деревом UI и выполняет клиентские переходы в SPA.
- Next.js сочетает server rendering, hydration, Server Components, prefetch и client-side transitions.
- Фильтры каталога и пагинацию удобно хранить в query-параметрах, чтобы состояние переживало обновление страницы и передавалось ссылкой.
- Для чистой SPA сервер или CDN настраивают на возврат `index.html` для клиентских маршрутов, не затрагивая API и статические ресурсы.
- После клиентского перехода приложение отвечает за focus, title, восстановление прокрутки и состояния загрузки и ошибки.
