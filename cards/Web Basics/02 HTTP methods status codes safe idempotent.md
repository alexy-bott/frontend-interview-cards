## Вопрос

<br>

 💬 **Какие HTTP-методы и коды состояния важно знать frontend-разработчику? Что означают safe и idempotent methods?**

<h2></h2>

<br>
<dl>
<dd>

HTTP method, или HTTP-метод, задаёт семантику запроса: намерение клиента относительно целевого ресурса. URL отвечает на вопрос «с чем работаем», а метод - «что хотим сделать». Сервер не должен придавать `GET /orders/42?delete=true` удаляющий смысл, потому что посредники и браузеры ориентируются на стандартную семантику метода.

| Метод | Основной смысл | Safe, безопасный | Idempotent, идемпотентный |
|---|---|---|---|
| `GET` | получить representation, или представление ресурса | да | да |
| `HEAD` | получить заголовки как у `GET`, но без тела | да | да |
| `POST` | обработать представление по правилам ресурса, часто создать сущность или выполнить действие | нет | обычно нет |
| `PUT` | создать или полностью заменить состояние ресурса по известному URI | нет | да |
| `PATCH` | частично изменить ресурс по формату patch-документа | нет | не гарантируется |
| `DELETE` | удалить связь ресурса с URI | нет | да |
| `OPTIONS` | узнать возможности ресурса; используется и в CORS preflight | да | да |

Safe method, или безопасный метод, имеет семантику чтения: клиент не просит изменить состояние исходного сервера. Это не означает абсолютное отсутствие побочных эффектов. Сервер может записать запрос в журнал или обновить внутреннюю статистику, но `GET` не должен оформлять заказ, удалять запись или списывать деньги. Благодаря этой семантике поисковый робот, предварительная загрузка и кэш могут обращаться к ссылкам без ожидаемого вреда.

Idempotent method, или идемпотентный метод, при нескольких одинаковых запросах должен иметь тот же намеренный эффект на сервере, что и один запрос. Ответы при этом могут различаться: первый `DELETE /users/42` вернёт `204`, повторный - `404`, но пользователь `42` не будет удалён дважды и другой ресурс не пострадает. Идемпотентность позволяет осторожно повторять запрос, если соединение оборвалось до получения ответа.

`POST` можно сделать идемпотентным на уровне конкретного API, например принять `Idempotency-Key` и вернуть результат уже обработанной команды. `PATCH` также может быть идемпотентным для операции «установить `name` в Ada», но операция «увеличить `counter` на 1» при повторе изменит результат снова. Свойство определяется сочетанием метода и семантики API-операции, а не только названием.

Status code, или код состояния, сообщает класс результата:

| Класс | Смысл | Частые коды состояния |
|---|---|---|
| `1xx` | промежуточная информация | `100 Continue`, `103 Early Hints` |
| `2xx` | запрос успешно принят и обработан | `200`, `201`, `202`, `204` |
| `3xx` | перенаправление или использование сохранённого представления | `301`, `302`, `304`, `307`, `308` |
| `4xx` | запрос клиента нельзя выполнить в текущем виде или контексте | `400`, `401`, `403`, `404`, `409`, `412`, `422`, `429` |
| `5xx` | сервер или gateway, то есть промежуточный шлюз, не смог обработать корректный запрос | `500`, `502`, `503`, `504` |

Frontend не должен строить всю логику только на классе. `401` может запустить refresh flow, `403` показать отсутствие прав, `409` потребовать обновить устаревшие данные, `422` привязать ошибки к полям, а `429` отложить повтор с учётом `Retry-After`.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем <code>POST</code>, <code>PUT</code> и <code>PATCH</code> отличаются на практике?</strong></summary>

<dl>
<dd>
<h2></h2>

`POST` передаёт данные ресурсу для обработки по его собственной семантике. Коллекция `/users` может создать новый элемент и сама назначить URI. Команда `/payments` может инициировать платёж, не являясь обычным CRUD-созданием.

`PUT /users/42` задаёт желаемое полное представление ресурса по известному URI и потому идемпотентен. `PATCH /users/42` передаёт набор частичных изменений; их формат определяет media type, например JSON Merge Patch. Нельзя универсально считать любой объект с двумя полями корректным `PATCH` без контракта API.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>DELETE</code> идемпотентен, если второй запрос может вернуть другой код состояния?</strong></summary>

<dl>
<dd>
<h2></h2>

Идемпотентность относится к намеренному эффекту на сервере, а не к равенству ответов. После одного и после нескольких одинаковых `DELETE` ресурс больше не связан с указанным URI. Первый ответ может быть `204`, повторный `404` или другой документированный код.

Метод перестанет быть идемпотентным, если `DELETE /last-order` при каждом повторе удаляет следующий заказ. Такой URI описывает меняющуюся команду, а не конкретный ресурс, и противоречит ожидаемой семантике `DELETE`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>200</code>, <code>201</code>, <code>202</code> и <code>204</code> отличаются?</strong></summary>

<dl>
<dd>
<h2></h2>

`200 OK` означает успешную обработку и обычно содержит представление результата. `201 Created` сообщает, что создан новый ресурс; его URI часто передают в `Location`. `202 Accepted` означает, что запрос принят, но обработка ещё не завершена, поэтому клиенту нужен способ узнать состояние операции.

`204 No Content` означает успешный результат без тела. Frontend не должен вызывать `response.json()` для пустого ответа. Для создания через `POST` точный выбор зависит от контракта, но `201` лучше выражает появление нового адресуемого ресурса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>401 Unauthorized</code> отличается от <code>403 Forbidden</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Несмотря на историческое название, `401` означает отсутствие действительных authentication credentials, то есть данных аутентификации. Сервер обычно сообщает поддерживаемую схему через `WWW-Authenticate`. Клиент может получить новый access token или предложить вход.

`403` означает, что сервер понял запрос, но отказывается его выполнять. Повтор с той же личностью не поможет: у пользователя нет роли, ресурс закрыт политикой либо операция запрещена. Не каждый backend раскрывает существование защищённого ресурса и иногда намеренно возвращает `404`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>400 Bad Request</code> отличается от <code>422 Unprocessable Content</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`400` означает, что сервер считает запрос ошибочным и не может или не хочет обрабатывать его, например из-за некорректного JSON, отсутствующего обязательного заголовка или неверного синтаксиса параметра.

`422` означает, что media type и синтаксис понятны, но инструкции невозможно выполнить из-за содержания: email занят, дата недопустима, сумма нарушает бизнес-правило. На практике граница зависит от API-контракта, поэтому frontend ориентируется на документированный код состояния и стабильную схему ошибки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>409 Conflict</code> отличается от <code>412 Precondition Failed</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`409` сообщает о конфликте запроса с текущим состоянием ресурса: например, имя уже занято или переход статуса невозможен. Ответ должен дать клиенту информацию для понимания конфликта.

`412` означает, что условие из заголовков запроса не выполнилось. Например, клиент отправил `If-Match` со старым `ETag`, а ресурс уже изменён. Это точный механизм optimistic concurrency control, или оптимистичного контроля одновременных изменений, тогда как `409` является более общей ошибкой состояния.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означают <code>301</code>, <code>302</code>, <code>303</code>, <code>307</code> и <code>308</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`301` и `308` описывают постоянное перенаправление, `302` и `307` - временное. `307` и `308` требуют сохранить исходные метод и тело при повторном запросе к новому URL.

`303 See Other` предлагает получить результат через `GET` и часто используется после `POST`. Историческое поведение клиентов для `301` и `302` может менять `POST` на `GET`, поэтому для строгого сохранения метода выбирают `307` или `308`. Fetch обычно следует перенаправлениям автоматически, если режим не изменён.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать frontend при <code>429 Too Many Requests</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`429` означает превышение ограничения частоты запросов. Сервер может прислать `Retry-After` с количеством секунд или датой, после которой повтор допустим. UI блокирует бессмысленные повторы, показывает состояние и сохраняет введённые данные.

Автоматический retry, или повтор, ограничивает число попыток и использует exponential backoff: увеличивает задержку после каждой неудачи. Jitter добавляет случайный разброс, чтобы множество клиентов не повторили запрос одновременно. Для mutation, то есть изменяющего запроса, дополнительно учитывают идемпотентность: нельзя автоматически повторять платёж, если неизвестно, применился ли первый запрос.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>500</code>, <code>502</code>, <code>503</code> и <code>504</code> отличаются?</strong></summary>

<dl>
<dd>
<h2></h2>

`500 Internal Server Error` - общая необработанная ошибка исходного сервера. `502 Bad Gateway` означает, что proxy или gateway получил некорректный ответ от upstream, то есть следующего сервера по цепочке. `503 Service Unavailable` сообщает о временной перегрузке или обслуживании и может содержать `Retry-After`. `504 Gateway Timeout` означает, что gateway не дождался ответа upstream.

Для пользователя эти ответы часто выглядят как временная серверная проблема, но различие важно для мониторинга и повторных попыток. Frontend не должен показывать внутренние подробности ошибки и обязан сохранять пользовательский ввод, если повтор возможен.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое idempotency key?</strong></summary>

<dl>
<dd>
<h2></h2>

Idempotency key, или ключ идемпотентности, - уникальный идентификатор логической операции, который клиент отправляет, например, в заголовке вместе с `POST`. Сервер сохраняет связь ключа с результатом и при повторе не выполняет команду заново, а возвращает тот же или эквивалентный результат.

Ключ должен повторно использоваться только для той же операции и иметь ограниченный срок хранения. Кнопка, заблокированная после клика, улучшает UX, но не заменяет серверную идемпотентность: запрос может повторить сеть, SDK или сам пользователь после перезагрузки страницы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие запросы можно автоматически повторять?</strong></summary>

<dl>
<dd>
<h2></h2>

Идемпотентные запросы обычно безопаснее повторять после временного сетевого сбоя, но даже для них нужны предел попыток, backoff и понимание ошибки. `400`, `401`, `403` или `422` без изменения запроса повторять бессмысленно.

Неидемпотентную mutation автоматически повторяют только при специальной гарантии: ключе идемпотентности, известном отсутствии отправки либо соответствующем контракте операции. Отмена `fetch` на клиенте не доказывает, что сервер не успел применить запрос.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Семантика HTTP |
|---|---|
| Получение страницы списка | безопасный и идемпотентный `GET` с query-параметрами |
| Создание заказа | `POST`, `201` или `202`, idempotency key |
| Полная замена настроек | идемпотентный `PUT` |
| Частичное редактирование | `PATCH` по документированному формату |
| Устаревшая версия | `If-Match`, `ETag`, `412` либо общий `409` |
| Ошибка формы | `422` и стабильная схема ошибок полей |
| Rate limit | `429`, `Retry-After`, backoff и сохранённое состояние UI |
