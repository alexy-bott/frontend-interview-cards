## Вопрос

<br>

 💬 **Какие HTTP-методы и коды состояния важно знать frontend-разработчику? Что означают safe и idempotent methods?**

<h2></h2>

<br>
<dl>
<dd>

HTTP method, или HTTP-метод, задаёт семантику запроса: намерение клиента относительно целевого ресурса. URL отвечает на вопрос «с чем работаем», а метод — «что хотим сделать».

Сервер не должен придавать безопасному методу изменяющий смысл. Например, `GET /orders/42?delete=true` не должен удалять заказ, потому что браузеры, поисковые роботы, кеши и механизмы предварительной загрузки ориентируются на стандартную семантику `GET`.

Основные методы, с которыми frontend работает чаще всего:

| Метод | Основной смысл | Safe, безопасный | Idempotent, идемпотентный |
|---|---|---|---|
| `GET` | Получить representation, или представление ресурса | да | да |
| `HEAD` | Получить метаданные как для `GET`, но без тела ответа | да | да |
| `POST` | Передать данные ресурсу для обработки, часто создать сущность или выполнить команду | нет | не гарантируется |
| `PUT` | Создать или заменить состояние ресурса по известному URI | нет | да |
| `PATCH` | Применить к ресурсу частичное изменение, описанное patch-документом | нет | не гарантируется |
| `DELETE` | Удалить связь целевого ресурса с его URI | нет | да |
| `OPTIONS` | Узнать возможности ресурса; используется и в CORS preflight | да | да |

Safe method, или безопасный метод, имеет семантику чтения: клиент не просит исходный сервер изменить состояние.

Это не означает абсолютного отсутствия побочных эффектов. Сервер может:

- записать запрос в журнал;
- увеличить счётчик просмотров;
- обновить статистику;
- начислить внутреннюю стоимость обработки.

Такие эффекты допустимы, если клиент не запрашивал их как основную цель операции. `GET` не должен оформлять заказ, удалять запись или списывать деньги.

Благодаря safe-семантике браузер, поисковый робот, кеш или механизм prefetch может обращаться к ссылке без ожидаемого изменения бизнес-состояния.

Idempotent method, или идемпотентный метод, при нескольких одинаковых запросах должен иметь тот же намеренный эффект на сервере, что и один такой запрос.

Ответы при этом могут различаться. Например:

```text
DELETE /users/42 → 204 No Content
DELETE /users/42 → 404 Not Found
```

После одного и после двух запросов пользователь больше не связан с URI `/users/42`. Идемпотентность относится к эффекту операции, а не к равенству статусов, заголовков и тела ответа.

Каждый safe-метод является идемпотентным, но обратное неверно:

- `GET` является safe и idempotent;
- `PUT` является idempotent, но не safe;
- `DELETE` является idempotent, но не safe.

Идемпотентность уменьшает риск повторной отправки запроса, если соединение оборвалось до получения ответа. Но она не означает, что frontend обязан автоматически повторять такой запрос при любой ошибке.

Перед retry нужно учитывать:

- тип ошибки;
- число попыток;
- `Retry-After`;
- exponential backoff;
- актуальность действия;
- возможные ограничения сервера;
- отмену пользователем.

Например, повтор `PUT` может быть идемпотентным по семантике метода, но уже не соответствовать намерению пользователя, если с момента первой попытки ресурс изменился. Для защиты от перезаписи используют условные запросы с `If-Match` и `ETag`.

`POST` можно сделать идемпотентным на уровне конкретного API. Например, клиент отправляет уникальный ключ логической операции:

```http
Idempotency-Key: "7d47a9df-0ec9-4d34-982f-760759f0e95c"
```

Сервер связывает ключ с параметрами и результатом операции. При повторе той же команды он не создаёт второй заказ или платёж, а возвращает сохранённый либо эквивалентный результат.

На август 2026 года `Idempotency-Key` описан в IETF Internet-Draft, который имеет статус expired, а не в окончательно опубликованном RFC. Поэтому конкретный API должен документировать:

- формат ключа;
- область его уникальности;
- срок хранения;
- допустимость повторного использования;
- сравнение request body;
- поведение параллельных запросов;
- статус и тело ответа при конфликте.

Один ключ нельзя использовать для разных операций или разных payload. Блокировка кнопки после клика улучшает UX, но не заменяет серверную идемпотентность.

`PATCH` сам по себе не является идемпотентным. Свойство зависит от формата и смысла patch-документа.

Например, операция:

```text
установить name = "Ada"
```

может быть идемпотентной, а операция:

```text
увеличить counter на 1
```

при каждом повторе создаёт новый эффект.

По RFC 5789 сервер должен применить patch-документ атомарно: либо выполнить весь набор изменений, либо не применять ни одно из них. Клиент не должен наблюдать промежуточно изменённое представление.

Если patch рассчитан на конкретную исходную версию ресурса, клиенту следует использовать условие:

```http
If-Match: "<etag>"
```

При несовпадении версии сервер возвращает `412 Precondition Failed`, а не применяет изменение к неожиданному состоянию.

Поддерживаемые форматы patch-документов сервер может сообщить через:

```http
Accept-Patch: application/merge-patch+json, application/json-patch+json
```

Поэтому `PATCH` — это не просто «отправить объект только с изменившимися полями». Семантика определяется media type и контрактом API.

Safe, idempotent и cacheable, то есть кешируемый, являются разными свойствами.

Например:

- `PUT` идемпотентен, но его ответ по стандартной семантике не используется как обычный кешируемый ответ на повторный `PUT`;
- `POST` не гарантирует идемпотентность, но его ответ при явных правилах кеширования может быть сохранён для последующего `GET` или `HEAD`;
- `GET` является safe, idempotent и обычно допускает кеширование.

Нельзя определять кешируемость только по тому, является ли метод безопасным или идемпотентным. Она зависит от определения метода, кода состояния и HTTP-заголовков кеширования.

Кроме перечисленных методов, HTTP определяет и другие.

В 2026 году RFC 10008 стандартизировал метод `QUERY`. Он предназначен для безопасного и идемпотентного запроса, критерии которого передаются в теле:

```http
QUERY /feed HTTP/1.1
Content-Type: application/json

{"search":"react","limit":20}
```

`QUERY` закрывает промежуток между `GET` с длинной строкой запроса и `POST /search`, у которого safe- и idempotent-семантика не видна посредникам автоматически.

Метод является новым, поэтому поддержку нужно проверять в серверном framework, proxy, gateway, CDN и инструментах документации. При cross-origin-вызове из браузера `QUERY` требует CORS preflight, поскольку к CORS-safelisted methods относятся только `GET`, `HEAD` и `POST`.

Методы `TRACE` и `CONNECT` также существуют в HTTP, но обычный frontend почти не использует их. Браузерный Fetch API запрещает JavaScript отправлять `CONNECT`, `TRACE` и исторический `TRACK`.

Status code, или код состояния, сообщает общий класс результата:

| Класс | Смысл | Частые коды состояния |
|---|---|---|
| `1xx` | Промежуточная информация | `100 Continue`, `101 Switching Protocols`, `103 Early Hints` |
| `2xx` | Запрос успешно обработан или принят | `200`, `201`, `202`, `204`, `206` |
| `3xx` | Перенаправление или использование сохранённого представления | `301`, `302`, `303`, `304`, `307`, `308` |
| `4xx` | Запрос нельзя выполнить в текущем виде или контексте | `400`, `401`, `403`, `404`, `405`, `409`, `412`, `413`, `415`, `422`, `429` |
| `5xx` | Сервер или gateway не смог обработать запрос из-за server-side-проблемы | `500`, `501`, `502`, `503`, `504` |

Frontend не должен строить всю логику только на классе статуса.

Например:

- `401` может запустить предусмотренный контрактом refresh flow;
- `403` показывает отсутствие прав;
- `404` показывает отсутствие ресурса;
- `409` требует разрешить конфликт с текущим состоянием;
- `412` сообщает о несработавшем условии запроса;
- `413` означает слишком большое содержимое запроса;
- `415` означает неподдерживаемый media type или content coding;
- `422` позволяет привязать ошибки содержимого к полям формы;
- `429` откладывает повтор с учётом `Retry-After`;
- `503` может означать временную перегрузку или обслуживание.

Код состояния описывает результат на уровне HTTP, а тело ошибки передаёт детали конкретного API. Frontend использует стабильный машинный формат ошибки, а не пытается принимать решения через разбор произвольной строки `message`.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Чем <code>POST</code>, <code>PUT</code> и <code>PATCH</code> отличаются на практике?</strong></summary>

<dl>
<dd>
<h2></h2>

`POST` передаёт данные ресурсу для обработки по его собственной семантике.

Например:

```text
POST /users
```

может создать новый элемент коллекции и позволить серверу самостоятельно назначить URI.

```text
POST /payments
```

может инициировать платёж, не являясь обычным CRUD-созданием.

`PUT /users/42` задаёт желаемое состояние ресурса по известному URI. Если выполнить одинаковый `PUT` несколько раз, итоговое состояние должно остаться тем же, поэтому метод является идемпотентным.

`PATCH /users/42` передаёт patch-документ с набором изменений. Его формат определяется `Content-Type`, например:

```http
Content-Type: application/merge-patch+json
```

или:

```http
Content-Type: application/json-patch+json
```

Нельзя универсально считать любой объект с двумя полями корректным `PATCH` без контракта API.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем safe, idempotent и cacheable отличаются друг от друга?</strong></summary>

<dl>
<dd>
<h2></h2>

Safe означает, что клиент не просит изменить состояние исходного сервера.

Idempotent означает, что несколько одинаковых запросов имеют тот же намеренный эффект, что один запрос.

Cacheable означает, что ответ разрешено сохранить и повторно использовать по правилам HTTP-кеша.

Это независимые свойства:

| Метод | Safe | Idempotent | Кеширование |
|---|---|---|---|
| `GET` | да | да | обычно поддерживается |
| `PUT` | нет | да | ответ на `PUT` не переиспользуется как повторный `PUT` |
| `POST` | нет | не гарантируется | возможно только при явных условиях |
| `DELETE` | нет | да | не следует из идемпотентности |

Поэтому выражения «идемпотентный значит кешируемый» и «небезопасный значит неидемпотентный» неверны.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое метод <code>QUERY</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`QUERY` — стандартизированный в RFC 10008 метод для безопасной и идемпотентной операции, входные данные которой передаются в теле запроса.

Например:

```http
QUERY /products/search HTTP/1.1
Content-Type: application/json

{"brands":["Acme"],"price":{"max":10000}}
```

Он полезен, когда query слишком сложный или большой для URL, но использовать `POST` нежелательно, потому что его safe- и idempotent-семантика не видна HTTP-посредникам.

Метод новый, поэтому перед использованием нужно проверить поддержку сервера, proxy, gateway, CDN и клиентских инструментов.

Fetch API позволяет использовать такой метод, но cross-origin-запрос потребует CORS preflight.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>DELETE</code> идемпотентен, если второй запрос может вернуть другой код состояния?</strong></summary>

<dl>
<dd>
<h2></h2>

Идемпотентность относится к намеренному эффекту на сервере, а не к равенству ответов.

После одного и после нескольких одинаковых `DELETE` ресурс больше не связан с указанным URI.

Первый ответ может быть:

```text
204 No Content
```

а повторный:

```text
404 Not Found
```

Метод перестанет соответствовать идемпотентной семантике, если endpoint при каждом повторе воздействует на другой ресурс. Например:

```text
DELETE /last-order
```

может при каждом запросе удалять новый «последний» заказ. Такой URI описывает меняющуюся команду, а не конкретный ресурс.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>200</code>, <code>201</code>, <code>202</code> и <code>204</code> отличаются?</strong></summary>

<dl>
<dd>
<h2></h2>

`200 OK` означает успешную обработку и обычно содержит представление результата.

`201 Created` сообщает, что создан один или несколько ресурсов. URI основного созданного ресурса часто передают в `Location`.

`202 Accepted` означает, что запрос принят для обработки, но выполнение ещё не завершено. Оно может завершиться позднее успешно, завершиться ошибкой или вообще не быть выполнено. Клиенту нужен способ узнать состояние операции, например URL задачи или идентификатор процесса.

`204 No Content` означает успешный результат без тела ответа. Frontend не должен вызывать `response.json()` для пустого ответа.

Для создания через `POST` точный выбор зависит от контракта, но `201` лучше выражает появление нового адресуемого ресурса, а `202` — запуск асинхронной обработки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>401 Unauthorized</code> отличается от <code>403 Forbidden</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Несмотря на историческое название, `401` означает отсутствие действительных authentication credentials, то есть данных аутентификации.

Сервер должен сообщить подходящую схему через `WWW-Authenticate`. Клиент может выполнить предусмотренный контрактом refresh, предложить вход или показать окончание сессии.

`403` означает, что сервер понял запрос, но отказывается его выполнять. Повтор с той же личностью и теми же правами проблему не исправит.

Причиной может быть:

- отсутствие нужной роли;
- запрет операции политикой;
- недоступность конкретного ресурса;
- ограничение аккаунта.

Сервер иногда намеренно возвращает `404` вместо `403`, чтобы не раскрывать существование защищённого ресурса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>400 Bad Request</code>, <code>409 Conflict</code> и <code>422 Unprocessable Content</code> отличаются?</strong></summary>

<dl>
<dd>
<h2></h2>

`400` означает, что сервер считает запрос некорректным и не может или не хочет его обрабатывать.

Например:

- повреждённый JSON;
- неправильный синтаксис параметра;
- отсутствующее обязательное служебное поле;
- несогласованные данные и `Content-Type`.

`422` означает, что сервер понимает media type и синтаксис содержимого, но не может выполнить содержащиеся в нём инструкции.

Например:

- дата имеет допустимый формат, но запрещена бизнес-правилом;
- значение поля находится вне допустимого диапазона;
- patch-документ синтаксически корректен, но создаёт недопустимый результат.

`409` означает конфликт с текущим состоянием ресурса или системы.

Например:

- имя уже занято;
- заказ уже оплачен;
- переход в запрошенный статус невозможен;
- операция конфликтует с параллельным изменением.

Граница зависит от контракта. Ошибка формата отдельного поля часто описывается через `422`, а уникальность или конфликт с существующей сущностью — через `409`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>405 Method Not Allowed</code> отличается от <code>501 Not Implemented</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`405` означает, что сервер знает указанный HTTP-метод, но целевой ресурс его не поддерживает.

Например:

```text
DELETE /reports/monthly → 405 Method Not Allowed
```

Ответ `405` должен содержать `Allow` со списком поддерживаемых методов:

```http
Allow: GET, HEAD
```

`501` означает, что сервер вообще не поддерживает или не распознаёт функциональность, необходимую для выполнения метода.

Например, старый сервер может вернуть `501` на новый метод `QUERY`, если его HTTP-стек не умеет обрабатывать этот метод.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>409 Conflict</code> отличается от <code>412 Precondition Failed</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`409` сообщает о конфликте запроса с текущим состоянием ресурса или системы.

Например:

- имя уже занято;
- переход статуса невозможен;
- операция конфликтует с параллельным изменением.

Ответ должен дать клиенту достаточно информации для понимания и возможного разрешения конфликта.

`412` означает, что одно или несколько условий из заголовков запроса оказались ложными.

Например, клиент отправил:

```http
If-Match: "version-5"
```

но текущий `ETag` ресурса уже равен `"version-6"`.

Это точный механизм optimistic concurrency control, или оптимистичного контроля одновременных изменений. `409` является более общей ошибкой состояния, когда клиент не передавал подходящую HTTP-precondition или конфликт не сводится к ней.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означают <code>301</code>, <code>302</code>, <code>303</code>, <code>307</code> и <code>308</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`301` и `308` описывают постоянное перенаправление, а `302` и `307` — временное.

`307` и `308` требуют сохранить исходные метод и тело при повторном запросе к новому URL.

`303 See Other` предлагает получить результат через `GET` и часто используется после `POST`.

Историческое поведение клиентов для `301` и `302` может менять `POST` на `GET`, поэтому для строгого сохранения метода выбирают `307` или `308`.

Fetch обычно следует перенаправлениям автоматически, если `redirect` не установлен в другой режим. В `Response` можно проверить итоговый URL и свойство `redirected`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать frontend при <code>429 Too Many Requests</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`429` означает превышение ограничения частоты запросов.

Сервер может прислать `Retry-After`:

```http
Retry-After: 30
```

или HTTP-дату, после которой повтор допустим.

Frontend:

- не запускает мгновенный цикл повторов;
- временно блокирует бессмысленное действие;
- сохраняет пользовательский ввод;
- показывает понятное состояние;
- учитывает серверную задержку;
- ограничивает общее число попыток.

Автоматический retry использует exponential backoff. Jitter добавляет случайный разброс, чтобы множество клиентов не повторили запрос одновременно.

Для mutation дополнительно учитывают идемпотентность. Нельзя автоматически повторять платёж, если неизвестно, применился ли первый запрос и сервер не поддерживает дедупликацию операции.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>500</code>, <code>502</code>, <code>503</code> и <code>504</code> отличаются?</strong></summary>

<dl>
<dd>
<h2></h2>

`500 Internal Server Error` — общая непредвиденная ошибка сервера.

`502 Bad Gateway` означает, что proxy или gateway получил некорректный ответ от upstream, то есть следующего сервера по цепочке.

`503 Service Unavailable` сообщает о временной перегрузке или обслуживании и может содержать `Retry-After`.

`504 Gateway Timeout` означает, что gateway не дождался ответа upstream.

Для пользователя эти ответы часто выглядят как временная серверная проблема, но различие важно для диагностики, мониторинга и политики retry.

Frontend не должен показывать внутренние stack traces и другие технические подробности ответа. Если повтор возможен, приложение сохраняет введённые пользователем данные.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое idempotency key?</strong></summary>

<dl>
<dd>
<h2></h2>

Idempotency key, или ключ идемпотентности, — уникальный идентификатор логической операции, который клиент отправляет вместе с неидемпотентным запросом, например `POST`.

Сервер сохраняет связь между:

- ключом;
- параметрами операции;
- состоянием выполнения;
- результатом.

При повторе той же команды сервер не выполняет действие заново, а возвращает сохранённый или эквивалентный результат.

Ключ должен повторно использоваться только для той же операции и того же payload. Сервер также задаёт срок хранения и поведение параллельных запросов с одинаковым ключом.

На август 2026 года HTTP-поле `Idempotency-Key` описано в истёкшем IETF Internet-Draft, а не в окончательном RFC. Поэтому его точная семантика определяется контрактом API.

Блокировка кнопки после клика улучшает UX, но не заменяет серверную идемпотентность: запрос может повторить сеть, SDK или пользователь после перезагрузки страницы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие запросы можно автоматически повторять?</strong></summary>

<dl>
<dd>
<h2></h2>

Идемпотентные запросы обычно безопаснее повторять после временного сетевого сбоя, но даже для них нужны:

- предел попыток;
- backoff;
- jitter;
- проверка актуальности операции;
- учёт `Retry-After`;
- возможность отмены.

`400`, `401`, `403`, `405`, `409`, `412`, `415` или `422` без изменения запроса обычно бессмысленно повторять автоматически.

`429`, `502`, `503` и `504` могут допускать ограниченный retry, но решение зависит от метода, контракта и серверных заголовков.

Неидемпотентную mutation автоматически повторяют только при специальной гарантии:

- idempotency key;
- серверной дедупликации;
- известном отсутствии отправки запроса;
- явно идемпотентной семантике операции.

Отмена `fetch`, timeout или потеря ответа не доказывают, что сервер не успел применить запрос.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Семантика HTTP |
|---|---|
| Получение страницы списка | Безопасный и идемпотентный `GET` с query-параметрами |
| Сложный безопасный поиск с телом | `QUERY`, если его поддерживает вся инфраструктура |
| Создание заказа | `POST`, `201` или `202`, серверная идемпотентность |
| Полная замена настроек | Идемпотентный `PUT` |
| Частичное редактирование | `PATCH` по документированному формату |
| Устаревшая версия | `If-Match`, `ETag`, `412` либо общий `409` |
| Ошибка формы | `422` и стабильная схема ошибок полей |
| Rate limit | `429`, `Retry-After`, backoff и сохранённое состояние UI |
