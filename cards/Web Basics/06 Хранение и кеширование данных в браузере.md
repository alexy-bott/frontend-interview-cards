## Вопрос

<br>

 💬 **Чем отличаются HTTP cache, cookies, Web Storage, IndexedDB и Cache API?**

<h2></h2>

<br>
<dl>
<dd>

Это разные браузерные механизмы. Они могут хранить похожие данные, но отличаются областью действия, форматом, временем жизни и участием в сетевом обмене.

| Механизм | Что хранит | Автоматически участвует в HTTP | Основная задача |
|---|---|---|---|
| HTTP cache, или HTTP-кеш | HTTP-ответы и метаданные | да, браузер или промежуточный кеш сам переиспользует ответ | уменьшить количество сетевых запросов и передаваемых данных |
| Cookies | небольшие пары имя/значение с атрибутами области действия | да, браузер добавляет подходящие cookies в запрос | сессия, серверная аутентификация и небольшие настройки |
| `localStorage` | строки key/value | нет | небольшое постоянное состояние frontend |
| `sessionStorage` | строки key/value для отдельной page session | нет | временное состояние конкретной вкладки |
| IndexedDB | структурированные значения, object stores и indexes | нет | большие наборы клиентских и offline-данных |
| Cache API | пары HTTP(S) `Request`/`Response` для `GET` | только по явной логике JavaScript или Service Worker | offline-режим и программные стратегии загрузки |

HTTP cache является частью сетевого слоя.

Когда браузер выполняет запрос, он может:

1. Найти подходящий сохранённый ответ.
2. Проверить его свежесть.
3. Вернуть его без обращения к сети.
4. Проверить его актуальность у сервера.
5. Выполнить обычный сетевой запрос.

В HTTP существуют private и shared caches.

Private cache принадлежит одному пользователю, например встроенный кеш браузера.

Shared cache обслуживает нескольких пользователей:

```text
browser
→ corporate proxy
→ CDN
→ reverse proxy
→ origin server
```

CDN и другие shared caches должны особенно внимательно учитывать персонализацию, `Authorization`, cookies, `private` и `Vary`, чтобы не вернуть данные одного пользователя другому.

Базовый cache key обычно строится из request method и target URI.

Например, это разные записи:

```text
GET /users?page=1
GET /users?page=2
```

Заголовок `Vary` добавляет к сопоставлению выбранные request headers:

```http
Vary: Accept-Encoding, Accept-Language
```

Кеш может хранить разные representations одного URL для разных языков или способов сжатия.

`Vary` должен перечислять только те заголовки, которые действительно меняют representation. Слишком широкий список резко уменьшает количество cache hits.

Значение:

```http
Vary: *
```

означает, что сохранённый ответ нельзя обычным образом сопоставить с последующим запросом без обращения к origin server.

Кроме стандартного HTTP cache key браузер может применять privacy partitioning. Например, private network cache может дополнительно учитывать top-level site, чтобы один и тот же third-party-ресурс не использовался как общий идентификатор пользователя на несвязанных сайтах.

Такие privacy-ключи являются дополнительным поведением браузера и не отменяют обычные правила `Cache-Control`, URL и `Vary`.

HTTP-ответ может быть:

- **fresh**, то есть находиться внутри срока актуальности;
- **stale**, то есть выйти за срок актуальности.

Fresh response обычно можно использовать без обращения к origin server.

Stale response обычно нужно:

- проверить через validator;
- заново загрузить;
- использовать только при наличии специального разрешения.

Основные directives, или директивы `Cache-Control`:

| Directive | Смысл |
|---|---|
| `max-age=60` | response считается fresh в течение 60 секунд |
| `s-maxage=300` | срок свежести для shared cache, например CDN |
| `private` | response нельзя хранить в shared cache, но можно в private cache |
| `public` | явно разрешает хранение в shared cache там, где оно иначе могло быть запрещено |
| `no-cache` | response можно сохранить, но перед повторным использованием нужно проверить у сервера |
| `no-store` | кеш не должен намеренно сохранять request и response |
| `must-revalidate` | stale response нельзя использовать без успешной проверки, если нет отдельного разрешения |
| `immutable` | пока response остаётся fresh, клиенту не следует проверять, изменился ли он |
| `stale-while-revalidate=30` | разрешает временно отдать stale response и обновить его в фоне |
| `stale-if-error=300` | разрешает временно использовать stale response при ошибке origin server |

`no-cache` не означает «не кешировать».

Например:

```http
Cache-Control: no-cache
ETag: "document-v7"
```

Браузер может сохранить тело. При следующем запросе он проверит актуальность и при совпадении версии повторно использует сохранённые данные.

`no-store` запрещает намеренное сохранение request и response HTTP-кешем.

При этом `no-store`:

- не удаляет автоматически старую запись, сохранённую по другому ответу;
- не очищает `localStorage`, IndexedDB и Cache API;
- не является полной защитой от вредоносного или скомпрометированного клиента;
- не заменяет HTTPS и правильную работу с чувствительными данными.

`immutable` является утверждением сервера, что representation по этому URL не изменится во время срока свежести.

Эта директива хорошо подходит для content-addressed assets:

```text
/app.a1b2c3.js
/styles.41c9d2.css
```

Если содержимое изменится, сборка создаст новый URL.

HTML по постоянному адресу обычно кешируют иначе:

```http
Cache-Control: no-cache
```

или задают небольшой `max-age`, поскольку документ должен быстро получить ссылки на новую версию assets.

Для hashed assets применяют:

```http
Cache-Control: public, max-age=31536000, immutable
```

Если надолго закешировать HTML под неизменным URL, пользователь может продолжать открывать старый документ, который ссылается на уже удалённые JavaScript chunks.

Если сервер не задаёт явные правила свежести, некоторые HTTP-ответы могут кешироваться эвристически. Браузер вычисляет примерный срок на основе доступных заголовков, например `Last-Modified`.

Поэтому для контролируемого поведения серверу лучше явно отправлять `Cache-Control`.

Проверка актуальности использует validators, или валидаторы кеша.

Сервер может вернуть:

```http
ETag: "user-42-v7"
Last-Modified: Thu, 06 Aug 2026 10:00:00 GMT
```

После истечения freshness lifetime кеш выполняет условный запрос:

```http
If-None-Match: "user-42-v7"
```

или:

```http
If-Modified-Since: Thu, 06 Aug 2026 10:00:00 GMT
```

Если выбранное representation не изменилось, сервер отвечает:

```http
304 Not Modified
```

Тело повторно не передаётся. Кеш использует сохранённое тело и обновляет его метаданные заголовками из ответа `304`.

Если одновременно доступны `ETag` и `Last-Modified`, для проверки кеша обычно используется `ETag`, поскольку он точнее описывает выбранную сервером версию.

`ETag` бывает strong и weak:

```http
ETag: "version-7"
ETag: W/"version-7"
```

Strong validator означает побайтово эквивалентные representations.

Weak validator означает семантически эквивалентное содержимое, которое может не совпадать побайтово.

Для обычного `If-None-Match` при проверке кеша weak validator может быть достаточен. Для `If-Match`, защищающего изменение ресурса от потерянного обновления, требуется strong comparison.

HTTP cache работает автоматически по правилам HTTP.

Cache API является отдельным программным хранилищем. Оно не является интерфейсом для просмотра или изменения встроенного HTTP-кеша браузера.

Например:

```ts
const cache = await caches.open("app-v1");
const response = await fetch("/api/catalog");

await cache.put("/api/catalog", response.clone());

return response;
```

`Response` клонируют, потому что её body является потоком. Без `clone()` один потребитель может прочитать тело, после чего оно станет недоступно другому.

Cache API:

- доступен JavaScript в secure context;
- работает в окне и workers;
- хранит именованные caches;
- сохраняет пары HTTP(S) `Request`/`Response`;
- разрешает сохранять только запросы с методом `GET`;
- по умолчанию сопоставляет URL и учитывает `Vary`;
- не применяет freshness lifetime из `Cache-Control`;
- не удаляет запись автоматически после `max-age`;
- не обновляет запись без явного кода приложения.

То есть сохранённый в Cache API ответ:

```http
Cache-Control: max-age=60
```

не исчезнет автоматически через 60 секунд. Приложение само определяет срок, версию кеша и стратегию обновления.

Service Worker может использовать Cache API для разных стратегий:

- cache-first;
- network-first;
- stale-while-revalidate;
- cache-only;
- network-only.

Например, cache-first:

```ts
self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then(async (cachedResponse) => {
      if (cachedResponse) {
        return cachedResponse;
      }

      const networkResponse = await fetch(event.request);
      const cache = await caches.open("runtime-v1");

      await cache.put(event.request, networkResponse.clone());

      return networkResponse;
    }),
  );
});
```

Это упрощённый пример. В production нужно учитывать:

- метод запроса;
- тип ответа;
- ошибки сети;
- допустимость кеширования персональных данных;
- срок актуальности;
- очистку старых версий;
- query-параметры;
- `Vary`;
- ограничение квоты.

Cookies являются небольшими записями, которые браузер хранит с атрибутами области действия и автоматически добавляет в подходящие HTTP-запросы.

Сервер устанавливает cookie через:

```http
Set-Cookie: session=abc; Secure; HttpOnly; SameSite=Lax; Path=/
```

При подходящем запросе браузер отправляет:

```http
Cookie: session=abc
```

Cookie не является origin-bound storage в том же смысле, что `localStorage` или IndexedDB.

Для выбора cookie учитываются:

- host и `Domain`;
- request path и `Path`;
- `Secure`;
- `SameSite`;
- срок жизни;
- partition key для partitioned cookie;
- браузерная privacy policy;
- режим credentials запроса.

Port не входит в область действия cookie.

Cookie для `example.com` может отправляться и на:

```text
https://example.com:443
https://example.com:8443
```

если остальные условия совпали.

Основные атрибуты:

- `Domain`: отсутствие создаёт host-only cookie; явное значение разрешает подходящие subdomains.
- `Path`: ограничивает request paths, но не является надёжной границей безопасности.
- `Secure`: ограничивает отправку защищённым соединением.
- `HttpOnly`: запрещает чтение через `document.cookie`, но cookie продолжает отправляться в HTTP-запросах.
- `SameSite`: ограничивает отправку в cross-site context.
- `Max-Age`: задаёт срок жизни в секундах.
- `Expires`: задаёт абсолютное время истечения.
- `Partitioned`: хранит cookie отдельно для разных top-level sites.

Если одновременно указаны `Max-Age` и `Expires`, приоритет имеет `Max-Age`.

Cookie без `Max-Age` и `Expires` называют session cookie. Она предназначена для текущей browser session, но не следует рассчитывать, что значение обязательно исчезнет сразу после закрытия окна: браузер может восстановить предыдущую сессию после перезапуска.

`Domain` отсутствует:

```http
Set-Cookie: session=abc; Path=/; Secure
```

Создаётся host-only cookie. Если её установил `api.example.com`, она не отправляется `app.example.com`.

Явно указан:

```http
Set-Cookie: theme=dark; Domain=example.com; Path=/
```

Cookie может отправляться:

```text
example.com
app.example.com
api.example.com
```

Сервер не может установить cookie для несвязанного домена или public suffix вроде `com` и `co.uk`.

Чем шире `Domain`, тем больше приложений и поддоменов могут влиять на cookie. Для сессионных cookies безопаснее использовать host-only область, если совместный доступ поддоменов не требуется.

Cookie prefixes позволяют браузеру проверить часть настроек:

```http
Set-Cookie: __Secure-session=abc; Secure; HttpOnly
```

Префикс `__Secure-` требует `Secure`.

```http
Set-Cookie: __Host-session=abc; Secure; HttpOnly; Path=/
```

Префикс `__Host-` требует:

- `Secure`;
- `Path=/`;
- отсутствия `Domain`.

Такая cookie привязана к установившему host и не может быть расширена на поддомены через `Domain`.

`SameSite` имеет основные режимы:

- `Strict` — наиболее ограниченная cross-site-отправка;
- `Lax` — допускает часть top-level navigations;
- `None` — разрешает cross-site context и требует `Secure`.

Нужно задавать `SameSite` явно, а не полагаться на browser default. Подходящее значение зависит от login flow, OAuth redirect, embedded content и CSRF-модели.

Partitioned cookie используется в third-party-контексте отдельно для каждого top-level site:

```http
Set-Cookie: __Host-widget=abc; Secure; SameSite=None; Path=/; Partitioned
```

Например, один chat widget на двух несвязанных сайтах получит разные cookie partitions:

```text
top-level site A + widget origin
top-level site B + widget origin
```

Атрибут `Partitioned` требует `Secure`.

Даже с `SameSite=None; Secure` third-party cookie может быть заблокирована browser privacy policy. Приложение не должно считать cross-site cookies гарантированно доступными во всех браузерах и режимах.

При использовании `fetch` автоматическая отправка cookie дополнительно зависит от `credentials`.

По умолчанию:

```ts
fetch("/api/users");
```

использует режим:

```text
credentials: "same-origin"
```

Для cross-origin API может потребоваться:

```ts
fetch("https://api.example.com/users", {
  credentials: "include",
});
```

При этом сервер должен корректно настроить CORS:

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
```

`Access-Control-Allow-Origin: *` нельзя использовать для credentialed-ответа.

`HttpOnly` защищает значение cookie от прямого чтения JavaScript, но не делает XSS безвредной. Вредоносный script может отправлять запросы от имени пользователя, даже не зная session ID.

Web Storage предоставляет два синхронных строковых хранилища:

```text
localStorage
sessionStorage
```

Значения хранятся только как строки:

```ts
localStorage.setItem("theme", "dark");

localStorage.setItem(
  "settings",
  JSON.stringify({
    compact: true,
  }),
);
```

При чтении объект нужно разобрать:

```ts
const rawSettings = localStorage.getItem("settings");

const settings = rawSettings
  ? JSON.parse(rawSettings)
  : null;
```

`localStorage` в обычном first-party-контексте связан с origin и сохраняется между page sessions, пока данные не будут удалены пользователем, браузером или приложением.

`sessionStorage` разделяется по origin и top-level browsing context, то есть по page session конкретной вкладки.

Он:

- сохраняется при reload;
- используется при переходах в пределах той же вкладки;
- отделён от другой независимо открытой вкладки;
- удаляется после завершения page session.

`sessionStorage` не означает «данные одного HTTP-сеанса» и не связан с server session cookie.

Web Storage является синхронным API. Чтение, запись, JSON-сериализация и JSON-разбор выполняются на main thread.

Поэтому туда не следует помещать:

- большие массивы;
- файлы;
- крупные API-ответы;
- часто изменяемые данные;
- объекты, требующие сложных запросов.

Доступ может завершиться исключением, например если:

- хранение запрещено настройками браузера;
- origin является opaque;
- превышена квота;
- действует privacy policy.

Запись нужно выполнять с учётом ошибки:

```ts
try {
  localStorage.setItem("theme", "dark");
} catch {
  // Хранилище недоступно или заполнено.
}
```

При изменении `localStorage` браузер отправляет событие `storage` другим подходящим документам, использующим ту же storage area.

Событие обычно не приходит в тот же window, который выполнил изменение:

```ts
window.addEventListener("storage", (event) => {
  if (event.key === "theme") {
    applyTheme(event.newValue);
  }
});
```

IndexedDB является асинхронной транзакционной базой данных браузера.

Она хранит записи в object stores:

```text
database
└─ object store
   ├─ key
   ├─ value
   └─ indexes
```

IndexedDB поддерживает:

- первичные keys;
- indexes;
- cursors;
- readonly и readwrite transactions;
- структурированные JavaScript-значения;
- массивы и объекты;
- `Blob`;
- schema version;
- миграции.

Значения сохраняются через structured clone. Это не JSON-сериализация, поэтому IndexedDB может хранить больше типов данных, но функции, DOM-элементы и другие неклонируемые значения сохранять нельзя.

Изменение структуры выполняется при открытии новой версии:

```ts
const request = indexedDB.open("app", 2);

request.addEventListener("upgradeneeded", () => {
  const database = request.result;

  if (!database.objectStoreNames.contains("tasks")) {
    const tasks = database.createObjectStore("tasks", {
      keyPath: "id",
    });

    tasks.createIndex("status", "status");
  }
});
```

Object stores и indexes можно создавать или удалять только в versionchange transaction.

Открытые соединения из других вкладок могут блокировать миграцию. Приложение должно обрабатывать `versionchange` и закрывать устаревшее соединение, иначе новый deployment может ждать завершения старой вкладки.

Обычные операции IndexedDB выполняются внутри transaction.

Readwrite transaction применяет связанные изменения атомарно в пределах своей области: либо transaction завершается, либо её изменения откатываются.

IndexedDB подходит для:

- offline-first данных;
- локального каталога;
- очереди изменений;
- большого черновика;
- справочников;
- кеша нормализованных сущностей;
- частей файлов;
- сложного поиска по indexes.

Локальную IndexedDB не следует считать единственной копией критичных данных. Пользователь или браузер может удалить storage, а локальная схема может устареть.

Cache API хранит HTTP-like `Request`/`Response`, тогда как IndexedDB хранит прикладные записи.

Упрощённо:

```text
Cache API:
GET /images/logo.svg
→ Response

IndexedDB:
task id=42
→ { title, status, updatedAt }
```

Cache API удобнее для готовых сетевых representations и offline-навигации.

IndexedDB удобнее, когда нужно:

- получать отдельные сущности;
- изменять поля;
- строить indexes;
- выполнять transactions;
- хранить прикладную структуру данных.

Иногда приложение использует оба механизма:

- Cache API хранит HTML, JS, CSS, изображения и HTTP responses;
- IndexedDB хранит сущности, очередь синхронизации и metadata.

Браузерное storage не является гарантированно вечным.

Данные могут исчезнуть из-за:

- очистки пользователем;
- private browsing;
- нехватки дискового пространства;
- browser eviction;
- сброса сайта;
- privacy policy;
- удаления приложения;
- истечения внутренних правил браузера.

IndexedDB и Cache API обычно относятся к best-effort storage: браузер старается сохранять данные, но может удалить их при нехватке места.

Получить приблизительную квоту и использование можно через:

```ts
const estimate = await navigator.storage.estimate();

console.log(estimate.usage);
console.log(estimate.quota);
```

Значения являются оценкой, а не обещанием точного свободного места для следующей операции.

Приложение может запросить persistent storage:

```ts
const isPersistent = await navigator.storage.persist();
```

Браузер самостоятельно решает, предоставить ли его. Persistent storage уменьшает вероятность автоматического eviction, но:

- пользователь всё равно может очистить данные;
- приложение всё равно может удалить их;
- это не резервная копия;
- критичные данные всё равно нужно синхронизировать с сервером.

Современные браузеры применяют storage partitioning для ограничения cross-site tracking.

В first-party-контексте данные обычно выглядят origin-bound:

```text
https://app.example.com
```

Но если `https://widget.example` встроен в iframe на двух несвязанных сайтах, браузер может создать разные storage partitions:

```text
top-level site A + widget origin
top-level site B + widget origin
```

Partitioning может затрагивать:

- cookies;
- `localStorage`;
- IndexedDB;
- Cache API;
- network cache;
- другие browser state.

Точное поведение и возможность запросить unpartitioned storage зависят от браузера и Storage Access API.

Поэтому third-party iframe не должен рассчитывать, что его данные будут одинаково доступны на всех встраивающих сайтах.

Все хранилища, доступные JavaScript текущего origin, находятся внутри одной XSS-границы.

При успешной XSS вредоносный код потенциально может прочитать:

- `localStorage`;
- `sessionStorage`;
- IndexedDB;
- Cache API;
- обычные cookies без `HttpOnly`;
- данные frontend-кеша в памяти.

Перенос access token из `localStorage` в IndexedDB не делает его недоступным вредоносному JavaScript.

`HttpOnly` cookie нельзя прочитать через JavaScript, но XSS может выполнять аутентифицированные действия через браузер.

Поэтому выбор storage не заменяет:

- предотвращение XSS;
- CSP;
- ограниченный срок жизни credentials;
- ротацию;
- отзыв;
- проверку прав на сервере;
- безопасный logout.

Практический выбор механизма:

- **HTTP cache** — повторное использование HTTP-response по правилам сервера.
- **Cookie** — небольшое значение, которое должно автоматически участвовать в HTTP-запросах.
- **`localStorage`** — небольшая строковая настройка между page sessions.
- **`sessionStorage`** — временное строковое состояние конкретной вкладки.
- **IndexedDB** — большой структурированный клиентский набор данных.
- **Cache API** — программное хранение HTTP responses и offline-стратегии.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Чем HTTP cache отличается от Cache API?</strong></summary>

<dl>
<dd>
<h2></h2>

HTTP cache является частью сетевого слоя браузера и посредников.

Он автоматически учитывает:

- URL;
- request method;
- `Cache-Control`;
- freshness;
- validators;
- `Vary`;
- HTTP status;
- правила private/shared cache.

JavaScript обычно не открывает и не перечисляет его записи.

Cache API является отдельным программным хранилищем:

```ts
const cache = await caches.open("app-v1");

await cache.put(request, response);
```

Код приложения самостоятельно решает:

- что сохранить;
- когда использовать;
- когда обновить;
- когда удалить;
- как версионировать cache.

Cache API не даёт JavaScript доступ к внутренним записям HTTP cache. Один response может одновременно пройти через HTTP cache и быть отдельно сохранён в Cache API.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Соблюдает ли Cache API заголовки <code>Cache-Control</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Не как обычный HTTP cache.

Если приложение сохранило response через:

```ts
await cache.put(request, response);
```

запись не исчезнет автоматически после указанного `max-age` и не станет автоматически проходить revalidation.

Cache API хранит запись, пока:

- приложение её не заменит;
- приложение её не удалит;
- не будет удалён весь named cache;
- браузер не удалит storage.

`Vary` учитывается при обычном `match()`, но freshness и expiration являются ответственностью приложения.

Поэтому Service Worker должен явно реализовать cache-first, network-first, stale-while-revalidate или другую стратегию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>no-cache</code> отличается от <code>no-store</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`no-cache` разрешает сохранить HTTP-response, но запрещает повторно использовать его без успешной проверки актуальности у origin server.

Например:

```http
Cache-Control: no-cache
ETag: "version-7"
```

может привести к условному запросу и ответу:

```http
304 Not Modified
```

Тело берётся из сохранённого кеша.

`no-store` запрещает HTTP-кешу намеренно сохранять request и response.

Он не очищает автоматически:

- `localStorage`;
- IndexedDB;
- Cache API;
- frontend state;
- ранее сохранённые данные под другим URL.

`no-store` также не является полной защитой приватности и не заменяет HTTPS.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое fresh и stale response?</strong></summary>

<dl>
<dd>
<h2></h2>

Fresh response находится внутри рассчитанного срока актуальности и обычно может использоваться без обращения к origin server.

Например:

```http
Cache-Control: max-age=60
```

разрешает считать response fresh в течение 60 секунд с учётом его возраста.

Stale response вышел за срок freshness.

Устаревшая запись не обязательно удаляется. Кеш может:

- выполнить revalidation через `ETag`;
- загрузить новый response;
- временно использовать stale response при специальном разрешении;
- удалить запись по внутренней политике.

`stale-while-revalidate` разрешает отдать устаревшее значение и обновить его в фоне.

`stale-if-error` разрешает временно использовать его, если origin server недоступен.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>ETag</code> отличается от <code>Last-Modified</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`ETag` — выбранный сервером идентификатор версии representation.

Он может быть strong:

```http
ETag: "catalog-v7"
```

или weak:

```http
ETag: W/"catalog-v7"
```

Для проверки кеша клиент отправляет:

```http
If-None-Match: "catalog-v7"
```

`Last-Modified` содержит время изменения:

```http
Last-Modified: Thu, 06 Aug 2026 10:00:00 GMT
```

и проверяется через:

```http
If-Modified-Since: Thu, 06 Aug 2026 10:00:00 GMT
```

Время имеет ограниченную точность и не всегда различает быстрые изменения.

`ETag` обычно является более точным validator. Если сервер передал оба и клиент использует `If-None-Match`, оно имеет приоритет при оценке условного запроса.

Strong `ETag` также можно использовать с `If-Match` для защиты изменения ресурса от перезаписи новой версии.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Для чего нужен <code>Vary</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`Vary` сообщает кешу, какие request headers повлияли на выбор representation.

Например:

```http
Vary: Accept-Encoding
```

означает, что response для клиента с поддержкой Brotli нельзя без проверки отдать клиенту с другим набором поддерживаемых кодирований.

```http
Vary: Accept-Language
```

разделяет языковые representations.

```http
Vary: Origin
```

важен, если CORS-response формируется для конкретного origin.

Без корректного `Vary` shared cache может вернуть response, созданный для другого языка, формата или CORS-origin.

Слишком широкий `Vary` уменьшает повторное использование. `Vary: *` практически не позволяет сопоставлять сохранённую запись с новым запросом без обращения к серверу.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему HTML и hashed assets, или ресурсы с хешем в имени, кешируют по-разному?</strong></summary>

<dl>
<dd>
<h2></h2>

HTML содержит ссылки на актуальные версии JS и CSS и должен быстро узнать о новом deployment.

Поэтому его обычно заставляют проходить revalidation:

```http
Cache-Control: no-cache
ETag: "index-v12"
```

либо задают небольшой `max-age`.

Hashed asset меняет URL при изменении содержимого:

```text
app.a1b2c3.js
app.91d6fe.js
```

Старое содержимое по старому URL больше не меняется, поэтому можно использовать:

```http
Cache-Control: public, max-age=31536000, immutable
```

Если надолго закешировать HTML под постоянным URL, пользователь может получить старые ссылки на assets, уже удалённые после deployment.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем host-only cookie отличается от cookie с <code>Domain</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Если `Domain` отсутствует:

```http
Set-Cookie: session=abc; Path=/; Secure
```

создаётся host-only cookie.

Cookie, установленная `api.example.com`, отправляется только этому host и не отправляется `app.example.com`.

Если указано:

```http
Domain=example.com
```

cookie может отправляться:

```text
example.com
app.example.com
api.example.com
```

Сервер не может установить cookie для чужого домена или public suffix вроде `com`.

Host-only область безопаснее по умолчанию, поскольку уменьшает количество поддоменов, способных влиять на cookie.

Префикс `__Host-` помогает зафиксировать это правило: такая cookie должна иметь `Secure`, `Path=/` и не должна иметь `Domain`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делают <code>Secure</code>, <code>HttpOnly</code> и <code>SameSite</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`Secure` ограничивает отправку cookie защищённым соединением.

`HttpOnly` запрещает читать cookie через `document.cookie`. Это уменьшает риск непосредственной кражи session ID при XSS, но вредоносный script всё ещё может отправлять аутентифицированные запросы.

`SameSite` управляет отправкой cookie в cross-site context:

- `Strict` — наиболее ограниченный режим;
- `Lax` — допускает часть top-level navigations;
- `None` — разрешает cross-site-отправку и требует `Secure`.

Значение нужно выбирать с учётом:

- CSRF;
- OAuth redirects;
- embedded приложений;
- cross-site login;
- browser privacy policy.

HTTPS и `SameSite` не заменяют серверную проверку прав пользователя.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое partitioned cookie?</strong></summary>

<dl>
<dd>
<h2></h2>

Partitioned cookie хранится отдельно для каждого top-level site.

Например, `widget.example` встроен на:

```text
shop-a.example
shop-b.example
```

Для него создаются две независимые cookie partitions, поэтому состояние с одного сайта не переносится на другой.

Cookie устанавливается с атрибутом:

```http
Set-Cookie: __Host-widget=abc; Secure; SameSite=None; Path=/; Partitioned
```

`Partitioned` требует `Secure`.

Такой механизм также называют CHIPS.

Он позволяет сохранить отдельное состояние embedded-компонента, не создавая одну общую third-party cookie для отслеживания пользователя на разных сайтах.

Поддержка старых браузеров может отличаться, поэтому приложение должно иметь fallback или работать без такого состояния.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>localStorage</code> отличается от <code>sessionStorage</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Оба API:

- хранят строки;
- работают синхронно;
- доступны через `Window`;
- в обычном first-party-контексте разделяются по origin.

`localStorage` сохраняется между page sessions, пока не будет очищен пользователем, браузером или приложением.

`sessionStorage` дополнительно привязан к page session конкретного top-level browsing context.

Он:

- сохраняется после reload;
- отделён от другой независимой вкладки;
- очищается после завершения page session.

Оба механизма подходят только для небольших данных. Большие операции блокируют main thread, а структурированные значения приходится сериализовать через JSON.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое storage partitioning?</strong></summary>

<dl>
<dd>
<h2></h2>

Storage partitioning дополнительно разделяет browser state по top-level site.

Исторически embedded origin мог использовать одно общее хранилище на разных сайтах:

```text
site-a.example → iframe widget.example
site-b.example → iframe widget.example
```

Это позволяло связывать посещения пользователя.

При partitioning браузер создаёт отдельные области:

```text
site A + widget origin
site B + widget origin
```

Разделяться могут:

- cookies;
- `localStorage`;
- IndexedDB;
- Cache API;
- network cache;
- другие browser данные.

Точное поведение зависит от браузера. Embedded-приложению может понадобиться Storage Access API для доступа к unpartitioned storage, но такое разрешение не гарантируется.

First-party-приложение не должно считать third-party storage стабильным способом общей идентификации пользователя.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужен IndexedDB?</strong></summary>

<dl>
<dd>
<h2></h2>

IndexedDB нужен для большого или структурированного клиентского набора данных.

Он подходит для:

- offline-first приложения;
- очереди изменений;
- большого каталога;
- локального поиска по indexes;
- черновиков;
- нормализованных сущностей;
- частей файлов.

В отличие от Web Storage, IndexedDB:

- асинхронный;
- хранит структурированные значения;
- поддерживает indexes;
- выполняет операции через transactions;
- имеет versioned schema.

Структура меняется в обработчике `upgradeneeded`.

Приложение должно учитывать, что старая вкладка может блокировать upgrade, а данные могут быть удалены из-за очистки или storage policy.

Критичные серверные данные нельзя хранить только в IndexedDB без синхронизации и восстановления.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда записи Cache API удаляются автоматически?</strong></summary>

<dl>
<dd>
<h2></h2>

Cache API не удаляет запись после `max-age` и не выполняет автоматическую HTTP-revalidation.

Запись остаётся, пока:

- код не вызовет `cache.delete()`;
- код не удалит named cache;
- новая запись не заменит старую;
- браузер не удалит storage из-за квоты или политики;
- пользователь не очистит данные сайта.

Обычно caches версионируют:

```text
static-v1
static-v2
runtime-v1
```

После активации новой версии Service Worker удаляет старые caches.

Приложение также может хранить собственное время сохранения и проверять возраст записи перед использованием.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли хранить access token в localStorage?</strong></summary>

<dl>
<dd>
<h2></h2>

Технически можно, но любой JavaScript текущего origin может прочитать значение.

При успешной XSS токен доступен вредоносному коду.

Перенос в:

- `sessionStorage`;
- IndexedDB;
- Cache API;

не создаёт принципиально новую XSS-границу. Эти механизмы также доступны JavaScript origin.

`HttpOnly` cookie нельзя прочитать через script, но она отправляется автоматически и требует продуманной защиты от CSRF, CORS и session fixation.

Универсально безопасного места нет. Выбор зависит от:

- BFF-архитектуры;
- модели угроз;
- срока жизни access token;
- refresh flow;
- CSP;
- необходимости cross-origin API.

В любом варианте credentials должны иметь ограниченный срок, ротацию, отзыв и минимальные полномочия.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Гарантируют ли браузерные хранилища постоянное хранение?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Данные может удалить:

- пользователь;
- браузер при нехватке места;
- private browsing policy;
- автоматический eviction;
- очистка сайта;
- переустановка приложения;
- сам frontend.

Даже `localStorage`, которое обычно сохраняется между запусками браузера, не является резервной копией.

IndexedDB и Cache API обычно используют best-effort storage.

Приложение может вызвать:

```ts
await navigator.storage.persist();
```

чтобы попросить более устойчивое хранение, но решение принимает браузер.

Persistent storage уменьшает риск автоматического eviction, но пользователь всё равно может очистить данные.

Критичное состояние сохраняют на сервере, а browser storage рассматривают как кеш, offline-копию или черновик согласно требованиям продукта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как узнать доступную квоту браузерного хранилища?</strong></summary>

<dl>
<dd>
<h2></h2>

Можно получить приблизительную оценку:

```ts
const { usage, quota } =
  await navigator.storage.estimate();
```

`usage` показывает примерный используемый объём, а `quota` — примерный доступный лимит.

Это не гарантия, что следующая запись указанного размера обязательно завершится успешно.

Квоты зависят от:

- браузера;
- устройства;
- свободного места;
- режима просмотра;
- активности сайта;
- storage policy.

Операция записи всё равно может завершиться `QuotaExceededError`.

Приложение должно:

- ограничивать объём;
- удалять старый кеш;
- обрабатывать ошибку;
- не сохранять дубли;
- уметь заново загрузить удалённые данные.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему cookies увеличивают размер каждого запроса?</strong></summary>

<dl>
<dd>
<h2></h2>

Все подходящие cookies сериализуются в заголовок:

```http
Cookie: session=abc; theme=dark; experiment=B
```

Они отправляются автоматически даже тогда, когда конкретному endpoint не нужны все значения.

Большие cookies и слишком широкие `Domain`/`Path`:

- увеличивают сетевой трафик;
- добавляются к большому количеству запросов;
- усложняют приватность;
- могут превышать ограничения браузера или сервера.

Поэтому cookie оставляют небольшой и задают минимальную область действия.

Для server session обычно передают непрозрачный идентификатор, а профиль пользователя и большие данные хранят на сервере или получают отдельным API-запросом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что нужно очистить при logout?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала сервер должен завершить или отозвать сессию. Простого удаления frontend-состояния недостаточно, если credential остаётся действительным.

Затем frontend очищает данные, которые не должны перейти следующему пользователю:

- in-memory API cache;
- Redux/RTK Query state;
- пользовательские записи `localStorage`;
- `sessionStorage`;
- IndexedDB;
- именованные Cache API caches;
- очереди offline-операций;
- WebSocket и другие активные соединения.

Сессионную `HttpOnly` cookie удаляет сервер через новый `Set-Cookie` с истёкшим сроком.

Не обязательно удалять общие публичные assets, например hashed JS/CSS, если они не содержат пользовательских данных.

Особенно важно не оставлять персональный API-response в Cache API или IndexedDB после смены аккаунта.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Данные | Подходящий механизм |
|---|---|
| JS/CSS с версией в имени | HTTP cache с большим `max-age` и `immutable` |
| Главный HTML-документ | revalidation через `no-cache` и `ETag` |
| Идентификатор сессии | host-only cookie с `Secure; HttpOnly; SameSite` |
| Состояние embedded widget | partitioned cookie или partitioned storage |
| Настройка темы | небольшое значение в `localStorage` |
| Черновик вкладки | `sessionStorage` либо состояние формы |
| Большие offline-данные | IndexedDB |
| Offline HTTP-responses | Service Worker и Cache API |
| Проверка квоты | `navigator.storage.estimate()` |
| Logout | отзыв сессии и очистка пользовательских client-side caches |
