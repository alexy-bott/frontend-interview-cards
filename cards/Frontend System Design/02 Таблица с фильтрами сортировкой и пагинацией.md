## Вопрос

<br>

 💬 **Как спроектировать таблицу с фильтрами, сортировкой и пагинацией?**

<h2></h2>

<br>
<dl>
<dd>

Сначала уточняют пользовательский сценарий и ограничения:

- объём данных;
- частоту изменений;
- допустимую задержку;
- количество колонок;
- нужные фильтры и сортировки;
- выбор строк и массовые действия;
- редактирование ячеек;
- экспорт;
- права;
- обновление в реальном времени;
- целевые устройства;
- необходимость перехода к конкретной странице;
- необходимость точного общего количества строк.

От этого зависит, нужен ли обычный список, семантическая HTML-таблица или полноценная интерактивная data grid.

Обычная `<table>` подходит для табличных данных, которые пользователь в основном читает, сортирует и фильтрует.

Data grid может понадобиться, если есть:

- редактирование ячеек;
- клавиатурная навигация между ячейками;
- изменение ширины и порядка колонок;
- закреплённые колонки;
- группировка;
- большое количество интерактивных операций.

На мобильном экране широкая таблица может превратиться в список карточек или показывать только приоритетные колонки. При этом нельзя терять важные данные и действия только из-за другого визуального представления.

Затем выбирают, где выполняются фильтрация, сортировка и пагинация.

Если весь набор:

- небольшой;
- уже безопасно загружен;
- помещается в память;
- не требует постоянной актуальности,

операции можно выполнить на клиенте.

Например:

```text
получить 100 элементов
→ фильтровать
→ сортировать
→ разбивать на страницы в браузере
```

Для большого, защищённого или часто меняющегося набора операции должен выполнять сервер:

```text
URL state
→ параметры API
→ серверная фильтрация
→ серверная сортировка
→ серверная пагинация
→ текущая страница
```

Не следует загружать на клиент сотни тысяч строк только ради локального поиска.

Клиентская фильтрация также не является механизмом безопасности. Сервер обязан самостоятельно учитывать пользователя, tenant, права и доступность строк.

Нельзя смешивать модели так, чтобы результат становился неверным.

Например:

```text
сервер вернул 20 строк текущей страницы
→ клиент отсортировал только эти 20 строк
```

Это не создаёт правильный порядок всего набора. Пользователь увидит локальную сортировку текущей страницы, а не глобальную сортировку результатов.

Фильтрация, сортировка и пагинация должны применяться к одному и тому же полному набору данных на одной стороне.

Состояние таблицы разделяют по назначению.

| Вид состояния | Пример | Место хранения |
| --- | --- | --- |
| Применённые параметры представления | Фильтры, сортировка, страница | URL |
| Черновик ввода | Текст, который пользователь ещё вводит | Локальное состояние |
| Server state | Строки, loading, error, pagination metadata | Query cache |
| Локальный UI | Открытое меню, раскрытая строка | Компонент |
| Выбор строк | Выбранные `id` или правило выбора | Feature state |

В URL обычно хранят:

- фильтры;
- строку поиска;
- поле сортировки;
- направление сортировки;
- номер страницы или cursor;
- размер страницы;
- активную вкладку.

Например:

```text
/orders?status=paid&sort=createdAt&direction=desc&page=3
```

Это позволяет:

- восстановить экран после reload;
- поделиться ссылкой;
- использовать Back/Forward;
- сохранить состояние при переходе на карточку и обратно.

URL становится источником истины для применённых параметров таблицы.

Параметры нужно парсить и валидировать.

Например:

```text
page=-2
sort=unknownField
direction=sideways
```

не должны безусловно отправляться в API.

Неизвестные значения заменяют безопасными значениями по умолчанию или удаляют из URL.

Полезно нормализовать URL:

```text
page=1
direction=asc
пустой search
```

можно не хранить, если это значения по умолчанию.

Тогда одинаковое состояние не имеет нескольких разных представлений:

```text
/orders
/orders?page=1
/orders?page=1&search=
```

При изменении набора данных текущая страница может перестать существовать.

Поэтому при изменении:

- фильтра;
- строки поиска;
- сортировки;
- размера страницы

обычно сбрасывают страницу на первую.

Для cursor pagination очищают текущий cursor и начинают новую последовательность с начала.

Поисковую строку можно разделить на черновик и применённое значение:

```text
input draft
→ debounce
→ URL search parameter
→ API request
```

Так поле реагирует на ввод сразу, а запрос выполняется после короткой паузы.

API должен принимать типизированные и ограниченные параметры.

Например:

```text
page
pageSize
status
createdFrom
createdTo
sort
direction
```

Сервер должен использовать allowlist разрешённых полей сортировки и фильтрации, а не безусловно подставлять произвольную строку пользователя в запрос к базе.

Ответ offset pagination может выглядеть концептуально так:

```text
items
page
pageSize
total
```

Ответ cursor pagination:

```text
items
nextCursor
hasNextPage
```

Точное поле `total` нужно не всегда.

Для большого или часто меняющегося набора вычисление точного количества может быть дорогим. Если интерфейсу достаточно кнопки «Показать ещё» или информации о наличии следующей страницы, cursor-модель может не возвращать общий `total`.

Сортировка должна быть детерминированной.

Например, сортировки только по дате недостаточно:

```text
ORDER BY createdAt DESC
```

Несколько записей могут иметь одинаковую дату, и база не обязана возвращать их в одном порядке между запросами.

Добавляют уникальный вторичный ключ:

```text
ORDER BY createdAt DESC, id DESC
```

Тогда порядок становится стабильным.

Это важно и для offset-, и для cursor-пагинации:

- строки меньше прыгают между страницами;
- снижается риск повторов;
- снижается риск пропусков;
- можно построить cursor по последней записи.

Cursor должен соответствовать полной сортировке.

Если порядок:

```text
createdAt DESC, id DESC
```

cursor должен кодировать значения, необходимые для продолжения именно этого порядка.

Клиенту лучше считать cursor непрозрачной строкой:

```text
eyJjcmVhdGVkQXQiOi...
```

Не нужно разбирать его или самостоятельно изменять. Смысл cursor принадлежит серверу.

Offset pagination использует номер страницы или смещение:

```text
page=4
pageSize=20
```

Она удобна, когда пользователь должен:

- видеть номера страниц;
- переходить к произвольной странице;
- понимать примерное положение в наборе.

Недостатки:

- большое смещение может быть дорогим;
- вставки и удаления между запросами приводят к повторам и пропускам;
- точный `total` может быть дорогим.

Cursor pagination продолжает выборку после конкретной позиции:

```text
cursor=opaqueValue
```

Она лучше подходит для:

- больших наборов;
- лент;
- журналов;
- часто изменяющихся данных;
- последовательной загрузки вперёд.

Но cursor обычно не позволяет дёшево перейти сразу на страницу 57.

Для Back/Forward cursor можно хранить в URL или использовать историю переходов, не пытаясь вычислять его на клиенте.

Ключ кэша запроса строят из нормализованных применённых параметров:

```text
filters
sort
direction
page/cursor
pageSize
tenant/workspace
```

Например, эти запросы должны иметь разные cache keys:

```text
status=paid&page=1
status=paid&page=2
status=cancelled&page=1
```

Если результат зависит от tenant или workspace, этот контекст тоже должен участвовать в изоляции кэша.

После logout или смены пользователя персональные server-state данные очищают либо гарантированно изолируют.

В cache key не помещают секреты и access tokens.

При переходе между страницами можно сохранять предыдущие данные до получения следующего ответа:

```text
страница 2 видна
→ пользователь открыл страницу 3
→ показывается неблокирующий индикатор
→ приходит страница 3
```

Это уменьшает визуальные скачки.

Но интерфейс должен ясно показывать, что отображаемые строки ещё относятся к предыдущим параметрам, если это может ввести пользователя в заблуждение.

Полезно различать:

```text
initial loading
→ данных ещё нет

background fetching
→ данные уже есть, выполняется обновление
```

Следующую страницу можно предварительно загрузить, если:

- вероятность перехода высока;
- запрос недорогой;
- это не создаёт лишнюю нагрузку;
- данные не являются чувствительными для недоступного пользователю сценария.

При вводе фильтра возможна гонка:

```text
запрос A: "rea"
→ запрос B: "react"
→ B завершился первым
→ A завершился позже
```

Старый ответ A не должен заменить актуальный результат B.

Debounce уменьшает число запросов, но не гарантирует порядок ответов.

Актуальность обеспечивают:

- отмена старого запроса через `AbortController`;
- query library с отдельными ключами;
- идентификатор запроса;
- проверка параметров перед применением ответа.

Выбор строк хранят по стабильным идентификаторам:

```ts
Set<id>
```

Нельзя хранить выбор по индексам:

```text
выбрана строка с index 3
```

После сортировки, фильтрации или перехода на другую страницу под индексом 3 окажется другая запись.

Нужно заранее определить семантику:

```text
выбрать все строки на текущей странице
выбрать все загруженные строки
выбрать все результаты текущего фильтра
```

Это разные операции.

Для выбора текущей страницы достаточно сохранить `id` видимых строк.

Для выбора всех результатов фильтра нельзя загружать и хранить миллионы идентификаторов.

Обычно состояние выглядит концептуально так:

```text
mode: allMatching
filterSnapshot: текущие фильтры
excludedIds: несколько снятых строк
```

Массовую операцию выполняет сервер по тому же фильтру:

```text
выполнить действие
для всех строк, соответствующих фильтру,
кроме excludedIds
```

В некоторых системах сервер создаёт selection token, который фиксирует выбранный набор или условия выборки.

Перед выполнением сервер должен повторно проверить:

- права;
- актуальность фильтра;
- доступность строк;
- лимиты операции.

Если набор мог измениться между выбором и подтверждением, интерфейс должен показать фактическое количество затронутых строк.

Например:

```text
Было выбрано 120 записей.
Операция применена к 117 доступным записям.
```

Таблица должна иметь полноценные состояния интерфейса:

- initial loading;
- background refresh;
- успешные данные;
- набор вообще пуст;
- фильтр не нашёл совпадений;
- ошибка;
- отсутствие доступа;
- частичные данные;
- offline;
- устаревшие данные.

Нужно различать:

```text
В системе пока нет записей.
```

и:

```text
По выбранным фильтрам ничего не найдено.
```

Во втором случае полезно предложить сбросить фильтры.

Ошибка загрузки должна позволять повторить запрос, не теряя применённые параметры URL.

Фоновое обновление не обязано заменять всю таблицу полноэкранным spinner, если предыдущие данные ещё можно безопасно показывать.

Для доступности обычных табличных данных предпочтительна нативная семантика:

```html
<table>
  <thead>
    <tr>
      <th>...</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>...</td>
    </tr>
  </tbody>
</table>
```

Заголовки используют `<th>`.

Если колонка сортируется, внутри заголовка размещают настоящую кнопку:

```html
<th aria-sort="ascending">
  <button type="button">
    Дата создания
  </button>
</th>
```

`aria-sort` указывают на `<th>` текущей сортируемой колонки.

Для остальных колонок атрибут обычно не нужен либо имеет значение `none`, если этого требует выбранная реализация.

Checkbox выбора строки должен иметь доступное имя:

```text
Выбрать заказ №123
```

Состояния загрузки и обновления можно объявлять через доступный status region, не перехватывая фокус при каждом запросе.

После сортировки, пагинации или ошибки фокус не должен неожиданно исчезать.

Роль:

```text
grid
```

не следует добавлять только потому, что таблица интерактивная.

ARIA grid предполагает отдельную клавиатурную модель навигации между ячейками. Если она не реализована полностью, нативная таблица с обычными кнопками и checkbox обычно доступнее.

На мобильном экране возможны варианты:

- горизонтальная прокрутка;
- скрытие второстепенных колонок;
- раскрытие подробностей строки;
- представление строк карточками;
- отдельный компактный экран.

При переходе к карточкам нужно сохранить:

- подписи значений;
- сортировку и фильтры;
- выбор строк;
- основные действия;
- доступ к скрытым данным.

Нельзя полагаться только на визуальное положение колонок: в карточке каждое значение должно иметь понятную подпись.

Виртуализация нужна, когда одновременно смонтировано столько строк, что становятся дорогими:

- создание DOM;
- React render;
- layout;
- paint;
- прокрутка.

Она оставляет в DOM только видимые строки и небольшой запас.

Виртуализация не заменяет серверную пагинацию:

```text
серверная пагинация
→ ограничивает объём полученных данных

виртуализация
→ ограничивает число элементов в DOM
```

Они могут использоваться вместе, но только при подтверждённой необходимости.

Виртуализация усложняет:

- клавиатурную навигацию;
- screen reader;
- высоту строк;
- sticky headers;
- раскрывающиеся строки;
- восстановление scroll position;
- поиск средствами браузера;
- печать.

Поэтому её добавляют после измерений, а не автоматически для каждой таблицы.

При проектировании также определяют наблюдаемость:

- время загрузки страницы;
- ошибки запросов;
- ошибки фильтрации;
- частоту пустого результата;
- длительность массовой операции;
- размер ответа;
- release ID;
- request ID.

В logs и analytics не передают секреты, персональные значения фильтров и полный URL без проверки его содержимого.

Практический порядок проектирования:

```text
1. Уточнить объём данных и сценарии.
2. Выбрать table, grid или мобильный список.
3. Выбрать клиентскую или серверную обработку.
4. Зафиксировать URL-параметры.
5. Согласовать API и стабильную сортировку.
6. Выбрать offset или cursor pagination.
7. Определить query cache и обработку гонок.
8. Определить семантику выбора строк.
9. Спроектировать loading, empty и error states.
10. Проверить accessibility и mobile.
11. Добавить virtualization только после измерения.
12. Покрыть критичные сценарии тестами.
```

## Дополнительные вопросы

<details>
<summary><strong>Когда сортировать и фильтровать на клиенте, а когда на сервере?</strong></summary>

<dl>
<dd>
<h2></h2>

Клиент подходит, если весь набор:

- уже безопасно загружен;
- небольшой;
- помещается в память;
- не требует постоянной актуальности;
- доступен текущему пользователю целиком.

Сервер нужен для:

- больших наборов;
- полнотекстового поиска;
- сложных прав;
- частых изменений;
- дорогой агрегации;
- защищённых данных.

Фильтрация, сортировка и пагинация должны применяться к одному полному набору на одной стороне.

Сортировка только текущей серверной страницы на клиенте не создаёт корректный порядок всей выборки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему состояние таблицы часто помещают в URL?</strong></summary>

<dl>
<dd>
<h2></h2>

Фильтры, сортировку и страницу можно:

- восстановить после reload;
- передать ссылкой;
- вернуть через Back/Forward;
- сохранить при переходе на карточку и обратно.

URL становится источником применённого состояния представления.

Параметры нужно парсить, валидировать и нормализовать.

Неизвестное поле сортировки, отрицательная страница или неподдерживаемый фильтр не должны безусловно попадать в API.

Временное состояние вроде открытого меню строки в URL обычно не помещают.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как обновлять URL и не создавать запись истории на каждый введённый символ?</strong></summary>

<dl>
<dd>
<h2></h2>

Строку input можно сначала хранить как локальный черновик:

```text
локальный input
→ debounce
→ применённый search parameter
```

Промежуточные изменения поиска часто записывают через замену текущей записи history, а явные действия пользователя — через добавление новой.

Например:

```text
ввод текста
→ replace

переход на другую страницу
→ push
```

Точная модель зависит от UX.

Главное — сохранить предсказуемую работу Back/Forward и не создавать десятки записей history за несколько секунд ввода.

После изменения поиска страницу или cursor сбрасывают.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что важно в API для таблицы?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно согласовать:

- типизированные фильтры;
- разрешённые поля сортировки;
- направление сортировки;
- pagination model;
- стабильный вторичный порядок;
- поля, допускающие `null`;
- формат ошибок;
- права;
- metadata следующей страницы.

Для offset-модели ответ может содержать:

```text
items
page
pageSize
total
```

Для cursor-модели:

```text
items
nextCursor
hasNextPage
```

Сервер должен повторно проверять права и не доверять переданному клиентом имени поля или tenant ID.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли всегда возвращать точное общее количество строк?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Точный `total` полезен, если интерфейс показывает:

- номера страниц;
- общее количество результатов;
- переход к последней странице;
- прогресс массовой операции.

Но для большого или часто изменяющегося набора точный count может быть дорогим и быстро устаревать.

Для cursor pagination часто достаточно:

```text
hasNextPage
nextCursor
```

Иногда сервер возвращает приблизительное количество или вычисляет точный `total` отдельным запросом.

Контракт выбирают по реальной потребности интерфейса, а не добавляют count автоматически.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем пагинация по смещению (<code>offset pagination</code>) отличается от пагинации по позиции (<code>cursor pagination</code>)?</strong></summary>

<dl>
<dd>
<h2></h2>

Пагинация по смещению использует номер страницы или количество пропущенных записей:

```text
page=5
offset=100
```

Она позволяет перейти к произвольной странице, но большое смещение может быть дорогим, а изменения набора приводят к дубликатам или пропускам.

Cursor pagination продолжает выборку после конкретной позиции в стабильном порядке:

```text
cursor=opaqueValue
```

Она устойчивее при вставках, удалениях и больших объёмах, но обычно не позволяет дёшево перейти сразу к произвольной странице.

Cursor считают непрозрачным значением и очищают при изменении фильтра или сортировки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем добавлять вторичную сортировку по <code>id</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Основное поле может быть одинаковым у нескольких строк.

Например:

```text
createdAt = 2026-08-05T10:00:00
```

Без дополнительного уникального ключа база не обязана возвращать равные записи в одном порядке.

Между запросами возможны:

- повтор строки;
- пропуск строки;
- переход строки на соседнюю страницу.

Порядок:

```text
createdAt DESC, id DESC
```

делает сортировку детерминированной.

Для cursor pagination оба значения должны учитываться при построении cursor.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как избежать гонки запросов при вводе фильтра?</strong></summary>

<dl>
<dd>
<h2></h2>

После короткой паузы запускают запрос для актуального значения.

Старый запрос:

- отменяют через `AbortController`;
- отделяют другим query key;
- либо помечают устаревшим.

Перед применением ответа можно проверить, что его параметры совпадают с текущими применёнными параметрами.

Debounce уменьшает количество запросов, но не гарантирует порядок завершения.

Поэтому одной задержки недостаточно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как хранить выбор строк между страницами?</strong></summary>

<dl>
<dd>
<h2></h2>

Конкретные выбранные строки хранят по стабильным `id`:

```text
Set<id>
```

Для «выбрать все результаты текущего фильтра» нельзя сохранять миллионы идентификаторов.

Хранят:

```text
режим выбора всех совпадений
snapshot фильтра
excludedIds
```

Либо получают от сервера специальный selection token.

Массовую операцию выполняет сервер, повторно проверяя:

- фильтр;
- права;
- существование строк;
- актуальность набора.

Интерфейс должен ясно объяснять, выбрана только текущая страница или все результаты фильтра.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как адаптировать таблицу для мобильного экрана?</strong></summary>

<dl>
<dd>
<h2></h2>

Возможные варианты:

- горизонтальная прокрутка;
- показ только приоритетных колонок;
- раскрытие подробностей строки;
- карточки вместо строк;
- отдельный компактный экран.

Выбор зависит от количества колонок и действий.

При переходе к карточкам каждое значение должно иметь подпись, потому что контекст заголовка колонки больше не виден.

Нужно сохранить:

- фильтры;
- сортировку;
- пагинацию;
- выбор;
- основные действия;
- доступ к скрытым данным.

Мобильное представление должно использовать тот же источник состояния и тот же API-контракт, а не становиться отдельной несогласованной реализацией.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужна виртуализация списка?</strong></summary>

<dl>
<dd>
<h2></h2>

Виртуализация нужна, когда большое количество строк в DOM заметно ухудшает:

- render;
- layout;
- paint;
- прокрутку;
- использование памяти.

Она оставляет смонтированными только видимые строки и небольшой запас.

Виртуализация не заменяет серверную пагинацию.

Она усложняет:

- accessibility;
- focus;
- высоту строк;
- sticky elements;
- scroll restoration;
- печать.

Поэтому её добавляют после измерения через profiler и browser Performance tools.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что тестировать у такой таблицы?</strong></summary>

<dl>
<dd>
<h2></h2>

Проверяют:

- parsing и сериализацию URL;
- восстановление после reload;
- Back/Forward;
- сброс страницы при изменении фильтра;
- стабильный порядок;
- offset- и cursor-переходы;
- ответы запросов в обратном порядке;
- initial loading и background fetching;
- пустой набор и пустой результат фильтра;
- ошибку и retry;
- выбор строк между страницами;
- «выбрать все результаты»;
- повторную проверку прав;
- клавиатурную сортировку;
- checkbox labels;
- focus после обновления;
- мобильное представление;
- отсутствие регрессии после виртуализации.

Для серверной модели отдельно проверяют, что сортировка и фильтрация применяются ко всему набору, а не только к текущей странице.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Ключевое решение |
| --- | --- |
| Небольшой справочник | Полная загрузка и клиентские операции |
| Журнал из миллионов записей | Серверные фильтры и cursor pagination |
| Поиск пользователей | Локальный черновик, URL, debounce и отмена старого запроса |
| Таблица с номерами страниц | Offset pagination и при необходимости `total` |
| Бесконечная лента | Cursor и `hasNextPage` без обязательного точного `total` |
| Массовое действие | Явная семантика выбора, snapshot фильтра и проверка прав |
| Часто меняющийся набор | Стабильный порядок и cursor |
| Мобильный экран | Карточки или приоритетные колонки с тем же состоянием |
| Длинный локальный список | Виртуализация после измерения DOM и рендера |
