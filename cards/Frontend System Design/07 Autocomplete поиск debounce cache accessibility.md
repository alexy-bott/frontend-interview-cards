## Вопрос

<br>

 💬 **Как спроектировать поиск с автодополнением (`autocomplete`) и серверными подсказками?**

<h2></h2>

<br>
<dl>
<dd>

Сначала определяют назначение autocomplete.

Основные варианты:

```text
свободный поиск
→ пользователь вводит произвольную строку

выбор сущности
→ пользователь должен выбрать существующий объект с id
```

Например, поиск по документации может разрешать любой текст, а поле выбора пользователя должно сохранить конкретный `userId`.

Для выбора сущности отдельно хранят:

```text
inputValue
selectedItem
```

Например:

```ts
type UserOption = {
  id: string;
  label: string;
};

type AutocompleteState = {
  inputValue: string;
  selectedItem: UserOption | null;
};
```

Пользователь может выбрать:

```ts
{
  id: "42",
  label: "React Team"
}
```

а затем изменить текст на:

```text
React T
```

В этом случае старый `id` уже не соответствует отображаемому значению.

По правилу продукта выбранный объект:

- очищают сразу после изменения текста;
- либо сохраняют только до тех пор, пока текст совпадает с его label;
- либо разрешают отдельное редактирование с явным подтверждением.

Нельзя отправлять старый `id`, если пользователь визуально видит уже другой текст.

Полезно разделять несколько значений:

```text
inputValue
→ текущий текст в поле

query
→ нормализованная строка, для которой выполняется запрос

activeOptionId
→ подсказка, выбранная клавиатурной навигацией

selectedItem
→ подтверждённая пользователем сущность
```

Упрощённая модель:

```ts
type AutocompleteState<T> = {
  inputValue: string;
  query: string;
  results: T[];
  activeOptionId: string | null;
  selectedItem: T | null;
  isOpen: boolean;
  status:
    | "idle"
    | "debouncing"
    | "loading"
    | "success"
    | "empty"
    | "refreshing"
    | "offline"
    | "rateLimited"
    | "error";
};
```

Сначала уточняют требования:

- локальный или серверный источник;
- минимальная длина запроса;
- допустимая задержка;
- максимальное число подсказок;
- правила ranking;
- локаль;
- права;
- tenant или workspace;
- возможность свободного ввода;
- необходимость пагинации;
- мобильные устройства;
- поведение Enter и Tab;
- допустимость хранения поисковых строк.

Если набор небольшой и уже загружен, можно фильтровать локально:

```text
короткий список тегов
список стран
предзагруженный справочник
```

Для большого, защищённого или часто меняющегося набора поиск выполняет сервер.

Сервер видит:

- полный набор данных;
- актуальные права;
- поисковый индекс;
- правила ranking;
- tenant;
- ограничения доступа.

Клиентская фильтрация не должна использоваться как защита скрытых сущностей.

Перед запросом строку нормализуют по согласованным правилам.

Часто применяют:

```text
trim
схлопывание лишних пробелов
нормализацию регистра
учёт локали
```

Например:

```text
"  React   Query "
→
"React Query"
```

Правила должны совпадать с ожиданиями API.

Нельзя автоматически переводить любой запрос в нижний регистр, если регистр имеет бизнес-смысл или сервер использует другую модель поиска.

До минимальной длины запрос обычно не выполняют:

```text
0 символов
→ показать недавние или популярные варианты либо закрыть список

1 символ
→ не отправлять запрос

2–3 символа
→ начать серверный поиск
```

Конкретное значение зависит от:

- размера набора;
- нагрузки;
- качества подсказок;
- языка;
- продукта.

При слишком коротком запросе старые результаты очищают или заменяют предусмотренным начальным состоянием.

Текст input обновляют сразу.

Сетевой запрос запускают после небольшой паузы:

```text
inputValue изменился
→ debounce
→ query обновился
→ запрос
```

Debounce уменьшает количество запросов, но не решает гонку ответов.

Например:

```text
запрос A: "rea"
→ запрос B: "react"
→ B завершился первым
→ A завершился позже
```

Результат A не должен заменить подсказки для `react`.

Для каждого нового запроса:

```text
1. Отменить предыдущий запрос.
2. Создать новый AbortController.
3. Запомнить query.
4. Выполнить запрос.
5. Проверить, что query всё ещё актуален.
6. Только после этого применить результат.
```

Пример:

```ts
const controller = new AbortController();

const response = await fetch(
  `/api/search?q=${encodeURIComponent(query)}`,
  {
    signal: controller.signal,
  },
);
```

При изменении query:

```ts
controller.abort();
```

Отмена запроса не является пользовательской ошибкой.

Не нужно показывать:

```text
Не удалось загрузить подсказки
```

если запрос отменён только потому, что пользователь продолжил ввод.

Для нового запроса создают новый `AbortController`.

Уже отменённый signal нельзя повторно использовать как обычный активный signal.

Если используется query library, гонки могут дополнительно контролироваться через:

- query key;
- lifecycle подписки;
- request ID;
- отмену предыдущей операции;
- проверку аргументов ответа.

Даже при отмене полезно проверять актуальный query: сервер мог успеть сформировать ответ до обработки abort, либо транспорт не поддерживает полноценную отмену.

Отдельно учитывают ввод через IME — Input Method Editor, который используется, например, для китайского, японского и корейского текста.

Во время composition пользователь ещё не закончил формировать символ.

Нельзя преждевременно:

- запускать поиск;
- выбирать option по Enter;
- считать промежуточный текст окончательным.

Обычно отслеживают:

```text
compositionstart
compositionend
```

или свойство:

```text
event.isComposing
```

Запрос запускают после завершения composition и обычного debounce.

API autocomplete может принимать:

```text
query
limit
cursor
locale
tenant
category
context
```

Например:

```http
GET /api/users/search?q=react&limit=10&cursor=...
```

Сервер должен использовать ограниченный контракт, а не принимать произвольные поля сортировки или tenant от клиента без проверки.

Ответ может выглядеть концептуально так:

```json
{
  "items": [
    {
      "id": "42",
      "label": "React Team",
      "secondaryLabel": "Frontend department",
      "highlights": [
        {
          "start": 0,
          "end": 5
        }
      ]
    }
  ],
  "nextCursor": null,
  "hasNextPage": false
}
```

Каждый вариант должен иметь стабильный идентификатор.

Нельзя использовать label как единственный ID:

```text
Алексей Иванов
```

может относиться к нескольким сущностям.

Сервер отвечает за:

- права;
- tenant isolation;
- ranking;
- лимит;
- pagination;
- rate limit;
- безопасное журналирование;
- защиту от перебора данных.

Если требуется подсветка совпадения, сервер может вернуть диапазоны символов:

```text
start
end
```

либо клиент может безопасно найти совпавший текст.

Не следует возвращать готовый HTML и вставлять его через:

```text
dangerouslySetInnerHTML
```

иначе API начинает управлять разметкой и появляется риск XSS.

При подсветке учитывают Unicode.

JavaScript-индексы строк могут не совпадать с тем, что пользователь воспринимает как один символ, поэтому формат диапазонов должен быть согласован между сервером и клиентом.

Ranking большого или защищённого набора выполняет сервер.

Он может учитывать:

- текстовое совпадение;
- популярность;
- историю пользователя;
- права;
- категорию;
- локаль;
- бизнес-приоритет.

Клиент не должен повторно сортировать серверный результат по label, если порядок отражает релевантность.

Кэш строят по всем параметрам результата:

```text
нормализованный query
locale
tenant/workspace
category
user context
limit
filters
```

Например:

```text
query=react
tenant=42
locale=ru
category=users
```

не должен использовать тот же cache entry, что и другой tenant или категория.

Access token и другие secrets в ключ кэша не помещают.

Для подсказок обычно подходит короткий срок свежести.

Кэш помогает при сценарии:

```text
react
→ react q
→ пользователь удалил q
→ снова react
```

Можно сразу показать сохранённый результат и при необходимости обновить его в фоне.

Для кэша определяют:

- freshness;
- максимальное время хранения;
- максимальное число entries;
- стратегию удаления старых запросов;
- очистку при logout или смене tenant.

Без ограничения autocomplete может накопить cache entry почти для каждой введённой строки.

Можно применять LRU-подобное ограничение или возможности используемой query library.

Нельзя считать результат короткого запроса полным источником для длинного:

```text
результаты "rea"
→ локально отфильтровать как результаты "react"
```

Серверный ranking, права и изменение данных могут привести к другому составу и порядку.

Локальная фильтрация старого ответа допустима только как явно согласованная временная оптимизация, а не как окончательный серверный результат.

Интерфейс различает состояния.

**Idle:**

```text
поле пустое
или запрос короче минимальной длины
```

**Debouncing:**

```text
текст уже изменился
запрос ещё не отправлен
```

Обычно отдельный spinner на несколько сотен миллисекунд не требуется.

**Loading:**

```text
запрос выполняется
актуальных результатов ещё нет
```

**Refreshing:**

```text
кэшированные результаты показаны
выполняется обновление
```

**Success:**

```text
получены подсказки
```

**Empty:**

```text
запрос успешно выполнен
совпадений нет
```

**Offline:**

```text
сеть недоступна
```

**Rate limited:**

```text
сервер ограничил частоту запросов
```

**Error:**

```text
результат неизвестен из-за сбоя
```

Пустой результат и ошибка — разные состояния.

Нельзя показывать:

```text
Ничего не найдено
```

при сетевом сбое.

Это ложное утверждение о данных.

При новом query возможны две стратегии:

```text
очистить старые результаты
```

или:

```text
оставить их до нового ответа
```

Если старые результаты оставляют, нужно явно показать, что они относятся к предыдущей строке, и не позволять случайно выбрать устаревшую option.

Чаще безопаснее закрыть старый список или заменить его loading-состоянием, если query заметно изменился.

После успешного ответа:

- обновляют список;
- сбрасывают active option по выбранному правилу;
- открывают popup при наличии результатов;
- объявляют число найденных вариантов при необходимости.

Активная option и выбранная сущность — разные состояния.

```text
active option
→ пользователь временно переместился к варианту стрелками

selected item
→ пользователь подтвердил вариант
```

Перемещение Arrow Down не должно автоматически менять сохранённый `selectedItem`, если продуктом не предусмотрено selection follows focus.

Enter без active option должен иметь заранее определённое поведение:

- выполнить полный поиск по строке;
- выбрать единственный вариант;
- оставить свободный текст;
- ничего не делать.

Нельзя случайно выбирать первый результат только потому, что пользователь нажал Enter для отправки формы.

Если autocomplete находится внутри формы, нужно согласовать:

- Enter при открытом списке;
- Enter при закрытом списке;
- выбор option;
- отправку всей формы.

Для выбора сущности Enter при active option обычно подтверждает option и не отправляет форму тем же нажатием.

После выбора:

```text
selectedItem сохраняется
inputValue становится label выбранной сущности
popup закрывается
activeOptionId очищается
```

При очистке поля:

```text
inputValue = ""
selectedItem = null
results очищены или заменены начальными вариантами
```

Доступный autocomplete реализуют по паттерну combobox.

Для редактируемого поля может использоваться:

```html
<input
  role="combobox"
  aria-autocomplete="list"
  aria-expanded="true"
  aria-controls="user-options"
  aria-activedescendant="user-option-42"
>
```

Popup:

```html
<ul
  id="user-options"
  role="listbox"
>
  <li
    id="user-option-42"
    role="option"
    aria-selected="true"
  >
    React Team
  </li>
</ul>
```

Основной DOM-фокус остаётся в input.

Это позволяет пользователю продолжать ввод.

`aria-activedescendant` указывает, какая option логически активна, пока реальный focus остаётся на combobox.

Значение `aria-activedescendant` должно ссылаться на существующий стабильный `id`.

Когда активной option нет, атрибут удаляют или не задают.

`aria-expanded` сообщает, открыт ли popup:

```text
true
false
```

`aria-controls` связывает combobox с popup.

`aria-autocomplete="list"` сообщает, что приложение показывает список предложений.

Options получают:

```text
role="option"
```

а выбранная или активная по принятой модели option получает корректное `aria-selected`.

Нужно согласованно различать:

```text
активный вариант
выбранный вариант
```

Если активная option управляется через `aria-activedescendant`, браузер сам не обязан прокручивать её в видимую часть списка.

Приложение должно проверить положение элемента и при необходимости выполнить прокрутку.

Клавиатурная модель обычно включает:

```text
Arrow Down
→ открыть список или перейти к следующей option

Arrow Up
→ перейти к предыдущей option

Enter
→ выбрать active option

Escape
→ закрыть popup без неожиданного изменения значения

Tab
→ продолжить обычную навигацию фокуса
```

Home и End не должны без необходимости ломать обычное редактирование текста в input. Их поведение выбирают в соответствии с принятой моделью combobox.

При закрытии popup focus остаётся в input.

Не нужно переносить DOM-фокус в каждую option при движении стрелками.

Pointer и keyboard должны изменять одно согласованное состояние active option.

Наведение мыши не должно быть единственным способом определить активный вариант.

Количество результатов, загрузку и ошибки можно объявлять через status region:

```html
<div
  role="status"
  aria-live="polite"
>
  Найдено 5 вариантов
</div>
```

Объявления не должны происходить на каждый символ слишком агрессивно и перегружать screen reader.

Сообщения должны быть короткими:

```text
Загрузка вариантов
5 вариантов
Совпадений нет
Не удалось загрузить варианты
```

Popup должен корректно работать при:

- увеличении текста;
- browser zoom;
- экранной клавиатуре;
- узком viewport;
- прокрутке страницы;
- touch-вводе.

На мобильном устройстве список не должен скрываться под экранной клавиатурой или выходить за пределы доступной области.

Options должны иметь достаточную touch-зону.

Нельзя строить взаимодействие только на hover.

Для длинного списка подсказок обычно лучше ограничить число результатов на сервере:

```text
10–20 вариантов
```

чем сразу виртуализировать popup.

Если всё же используется виртуализация, активная option, указанная в `aria-activedescendant`, должна существовать в DOM и оставаться доступной вспомогательным технологиям.

Pagination autocomplete может использовать:

- кнопку «Показать ещё»;
- загрузку следующей страницы при прокрутке;
- полный экран результатов.

Cursor считают непрозрачным и сбрасывают при изменении query или фильтров.

Безопасность включает не только XSS.

Autocomplete может использоваться для перебора существующих данных:

```text
email
username
клиент
внутренний документ
```

Сервер применяет:

- authorization;
- tenant isolation;
- rate limit;
- минимальную длину;
- ограничение количества результатов;
- аудит подозрительных запросов;
- нейтральные ответы в чувствительных сценариях.

Например, публичная форма восстановления пароля не должна через подсказки раскрывать существование аккаунтов.

Поисковая строка может содержать персональные или чувствительные данные.

Не следует безусловно передавать её:

- в analytics;
- в error tracking;
- в URL стороннего сервиса;
- в длительно хранящиеся логи.

Для observability безопаснее записывать:

- длительность запроса;
- длину query;
- количество результатов;
- cache hit;
- error code;
- факт выбора;
- request ID;
- release.

Полный текст query логируют только при явной необходимости, ограниченной политике доступа и сроке хранения.

Полезные метрики:

- время от завершения debounce до результата;
- общее время от ввода до подсказок;
- cache hit rate;
- error rate;
- empty result rate;
- число отменённых запросов;
- частота выбора;
- позиция выбранной option;
- доля переходов к полному поиску.

Тестовая стратегия включает:

- минимальную длину;
- нормализацию;
- debounce;
- IME composition;
- отмену запроса;
- ответы в обратном порядке;
- cache hit;
- истечение cache;
- смену tenant или пользователя;
- очистку после logout;
- пустой результат;
- offline;
- rate limit;
- server error;
- выбор option;
- изменение текста после выбора;
- очистку selected item;
- Enter внутри формы;
- Escape;
- Tab;
- Arrow Up/Down;
- стабильные ID;
- `aria-activedescendant`;
- прокрутку active option;
- объявление количества результатов;
- touch и мобильную клавиатуру.

Практический порядок проектирования:

```text
1. Определить свободный поиск или выбор сущности.
2. Разделить inputValue и selectedItem.
3. Согласовать нормализацию и минимальную длину.
4. Определить debounce и IME-поведение.
5. Спроектировать API и ranking.
6. Защититься от гонок и отменять старые запросы.
7. Определить cache key и срок хранения.
8. Описать loading, empty, stale и error states.
9. Реализовать keyboard и ARIA combobox.
10. Добавить rate limit, privacy и безопасные метрики.
```

Главный принцип:

```text
debounce
→ уменьшает частоту запросов

AbortController или request identity
→ защищает от устаревших ответов

server ranking
→ определяет релевантность и права

combobox pattern
→ делает подсказки доступными с клавиатуры
```

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем debounce отличается от throttle для поиска?</strong></summary>

<dl>
<dd>
<h2></h2>

Debounce запускает действие после паузы:

```text
ввод
ввод
ввод
→ пауза
→ запрос
```

Это подходит для текстового поиска, потому что сервер получает более законченную строку.

Throttle запускает действие не чаще заданного интервала:

```text
не более одного вызова за 200 мс
```

Он чаще применяется для:

- scroll;
- resize;
- pointer events;
- частых realtime-обновлений.

Оба механизма управляют частотой вызовов, но не решают гонку сетевых ответов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему одного debounce недостаточно?</strong></summary>

<dl>
<dd>
<h2></h2>

Запрос для короткой строки может начаться раньше, но завершиться позже нового запроса:

```text
"rea"   → медленный ответ
"react" → быстрый ответ
```

Если применять последний физически пришедший response, интерфейс покажет результаты для устаревшего текста.

Старый запрос:

- отменяют через `AbortController`;
- отделяют request ID;
- либо игнорируют, если его query не совпадает с текущим.

Отмена запроса не показывается как пользовательская ошибка.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем отдельно хранить введённый текст и выбранное значение?</strong></summary>

<dl>
<dd>
<h2></h2>

Пользователь выбирает сущность:

```ts
{
  id: "42",
  label: "React Team"
}
```

После этого он может изменить текст:

```text
React T
```

Старый `id` уже не соответствует отображению.

Если хранить только строку, невозможно надёжно различить сущности с одинаковым названием.

Если хранить только объект, неудобно поддерживать свободный ввод и состояние поиска.

Поэтому разделяют:

```text
inputValue
selectedItem
```

и определяют правило очистки выбранного объекта после редактирования текста.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что включать в ключ кэша подсказок?</strong></summary>

<dl>
<dd>
<h2></h2>

Ключ включает все параметры, влияющие на ответ:

- нормализованный query;
- locale;
- tenant или workspace;
- category;
- фильтры;
- пользователя, если права меняют результат;
- limit;
- версию поискового контекста.

Персональные результаты разных пользователей не должны попадать в один cache entry.

Access token в ключ не включают.

Cache ограничивают по времени и количеству записей, а после logout персональные данные очищают.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему недостаточно просто показать <code>&lt;div&gt;</code> под полем ввода?</strong></summary>

<dl>
<dd>
<h2></h2>

Без семантики вспомогательная технология не узнает:

- что поле управляет popup;
- открыт ли список;
- какой вариант активен;
- сколько вариантов найдено;
- что произойдёт после Enter.

Паттерн combobox определяет:

```text
combobox
listbox
option
aria-expanded
aria-controls
aria-activedescendant
```

DOM-фокус остаётся в input, а активный вариант меняется логически.

Hover не заменяет клавиатурную навигацию и доступный active option.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем пустой результат отличается от ошибки?</strong></summary>

<dl>
<dd>
<h2></h2>

Пустой результат означает:

```text
запрос успешно выполнен
совпадений нет
```

Пользователь может изменить строку или перейти к полному поиску.

Ошибка означает:

```text
достоверный результат не получен
```

Нужно показать сообщение и при необходимости retry.

При сетевой ошибке нельзя утверждать:

```text
Ничего не найдено
```

потому что серверный набор неизвестен.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где выполнять ranking и подсветку совпадения?</strong></summary>

<dl>
<dd>
<h2></h2>

Ranking большого или защищённого набора выполняет сервер.

Только он видит:

- полный набор;
- поисковый индекс;
- права;
- tenant;
- бизнес-приоритеты.

Клиент отображает полученный порядок.

Подсветку можно выполнить по безопасным диапазонам символов или локально по тексту.

Сервер не должен возвращать непроверенный HTML для прямой вставки в DOM.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что тестировать у autocomplete?</strong></summary>

<dl>
<dd>
<h2></h2>

Проверяют:

- минимальную длину;
- нормализацию;
- debounce;
- composition events;
- отмену;
- ответы в обратном порядке;
- cache;
- смену пользователя и tenant;
- пустой ответ;
- offline;
- rate limit;
- ошибку;
- выбор и очистку значения;
- изменение текста после выбора;
- Enter внутри формы;
- Arrow Up/Down;
- Escape;
- Tab;
- роли combobox, listbox и option;
- `aria-expanded`;
- `aria-controls`;
- `aria-activedescendant`;
- прокрутку active option;
- объявление результатов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем autocomplete для свободного поиска отличается от выбора сущности?</strong></summary>

<dl>
<dd>
<h2></h2>

При свободном поиске итоговым значением может быть любая строка:

```text
"react architecture"
```

Подсказки только помогают сформировать запрос.

При выборе сущности итоговым значением является стабильный идентификатор:

```text
userId = "42"
```

Строка используется только для поиска и отображения.

Поэтому выбор сущности требует отдельно хранить `selectedItem` и не отправлять label как идентификатор.

Поведение Enter без active option у этих режимов может отличаться.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как учитывать IME и composition events?</strong></summary>

<dl>
<dd>
<h2></h2>

При вводе через IME несколько клавиатурных событий могут формировать один итоговый символ.

Во время composition нельзя считать промежуточный текст окончательным.

Приложение отслеживает:

```text
compositionstart
compositionend
```

или `event.isComposing`.

Поиск и выбор по Enter выполняют после завершения composition.

Иначе autocomplete может отправлять лишние запросы или случайно выбирать option до завершения ввода.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие состояния должен различать autocomplete?</strong></summary>

<dl>
<dd>
<h2></h2>

Основные состояния:

```text
idle
debouncing
loading
success
empty
refreshing
offline
rateLimited
error
```

`loading` означает, что актуальных данных ещё нет.

`refreshing` означает, что показан cache и выполняется обновление.

`empty` является успешным ответом без совпадений.

`error` означает, что результат неизвестен.

Каждое состояние должно иметь понятное отображение и не сбрасывать введённый текст.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему активную option нужно вручную прокручивать в видимую область?</strong></summary>

<dl>
<dd>
<h2></h2>

При использовании `aria-activedescendant` реальный DOM-фокус остаётся в input.

Браузер не обязан автоматически прокручивать логически активную option так, как он прокручивает обычный сфокусированный элемент.

После изменения `activeOptionId` приложение проверяет положение option и при необходимости вызывает прокрутку.

Это особенно важно для длинного popup и увеличенного масштаба страницы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда очищать выбранную сущность?</strong></summary>

<dl>
<dd>
<h2></h2>

Если пользователь изменил текст после выбора, старый `id` обычно очищают:

```text
выбран userId=42
→ inputValue изменён
→ selectedItem=null
```

Иначе форма может отправить сущность, которая не соответствует видимому тексту.

Исключение возможно, если продукт явно разрешает редактировать label независимо от выбранного объекта.

Правило должно быть однозначным и покрываться тестом.

<h2></h2>
</dd>
</dl>

</details>
