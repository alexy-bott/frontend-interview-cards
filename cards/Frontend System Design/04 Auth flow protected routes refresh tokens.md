## Вопрос

<br>

 💬 **Как спроектировать вход, защищённые маршруты и обновление токенов?**

<h2></h2>

<br>
<dl>
<dd>

Сначала разделяют три задачи. Аутентификация (`authentication`) устанавливает личность пользователя. Авторизация (`authorization`) проверяет право выполнить конкретное действие над конкретным ресурсом. Управление сессией определяет срок жизни входа, обновление, выход, отзыв, синхронизацию вкладок и реакцию на изменение прав.

Архитектура зависит от типа приложения. Для собственного веб-приложения (`first-party`), где клиент и сервер принадлежат одному продукту, часто проще серверная сессия или BFF (`Backend for Frontend`): браузер хранит только случайный идентификатор сессии в cookie, а промежуточный сервер хранит токены и обращается к API. Cookie ограничивают атрибутами `Secure`, `HttpOnly`, `SameSite`, узкими `Path` и `Domain`; для cookie одного конкретного хоста подходит префикс `__Host-`.

Если одностраничное приложение (SPA) напрямую использует OAuth 2.0 и OpenID Connect (OIDC), современный поток - Authorization Code с PKCE, а не устаревший Implicit Flow. PKCE связывает начало входа с обменом authorization code - одноразового кода авторизации - и мешает использовать перехваченный код другому клиенту. Access token, или токен доступа, делают короткоживущим и ограничивают нужным API и правами. Refresh token, или токен обновления, является долгоживущей учётной информацией и служит для получения нового access token, поэтому для публичного клиента требуется rotation - смена токена при каждом обновлении с обнаружением повторного использования - либо криптографическая привязка к клиенту. OWASP не рекомендует хранить идентификатор сессии, access token или refresh token в `localStorage` и `sessionStorage`, потому что любой JavaScript того же источника (`origin`) может прочитать их при XSS - внедрении вредоносного скрипта.

Атрибут `HttpOnly` не делает приложение неуязвимым. Он запрещает JavaScript читать cookie, но вредоносный скрипт всё ещё может отправлять запросы от имени пользователя. Cookie также отправляется браузером автоматически, поэтому нужна защита от CSRF - подделки межсайтового запроса: проверка `Origin`, подходящий `SameSite` и CSRF-токен там, где модель запросов этого требует. От XSS защищаются отдельно: безопасным выводом данных, Content Security Policy (CSP) - политикой допустимых источников содержимого - и контролем сторонних скриптов.

Защищённый маршрут (`protected route`) в браузере улучшает UX, но не защищает данные. Пользователь может изменить клиентское состояние или вызвать API напрямую. Сервер проверяет сессию, права, tenant - организацию или аккаунт в многопользовательской системе, - и доступ к ресурсу на каждом запросе. `401 Unauthorized` означает, что действующей аутентификации нет; `403 Forbidden` - личность известна, но действие запрещено. Интерфейс должен различать вход, отсутствие права и временную проверку сессии.

При старте состояние сессии считается неизвестным, пока его не подтвердил сервер. При SSR, то есть серверном рендеринге, сервер может сразу вернуть разрешённую страницу или перенаправление, чтобы не показывать защищённый контент до клиентской проверки. В SPA на это время отображают стабильное состояние загрузки. Параметр возврата после входа проверяют по разрешённым внутренним адресам, иначе возникает open redirect - перенаправление на произвольный сайт.

Если API использует обновление токена, клиент обрабатывает `401` через single flight - один общий запрос обновления, который ожидают остальные запросы. После успеха каждый исходный запрос повторяется не более одного раза; после отказа очередь завершается ошибкой, состояние очищается и пользователь переходит к входу. Операцию обновления исключают из общего перехватчика ответов (`interceptor`), иначе её собственный `401` создаст бесконечный цикл.

Выход завершает серверную сессию или отзывает refresh token, а не только очищает интерфейс. Клиент удаляет персональные данные из кэша, закрывает WebSocket/SSE, отменяет запросы и сообщает другим вкладкам через `BroadcastChannel`. В журналирование не передают cookie и токены; для диагностики используют безопасный идентификатор сессии или операции.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем аутентификация отличается от авторизации?</strong></summary>

<dl>
<dd>
<h2></h2>

Аутентификация определяет, кто пользователь: например, серверная сессия или access token подтверждает его личность. Авторизация определяет, что этому пользователю разрешено: вызвать операцию API, изменить конкретный ресурс или видеть данные tenant - отдельной организации в общей системе.

Пользователь может успешно войти, но получить `403 Forbidden` на конкретное действие. Frontend скрывает недоступные команды и объясняет состояние, однако сервер остаётся источником истины по правам.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему клиентская проверка маршрута (<code>route guard</code>) не является настоящей защитой?</strong></summary>

<dl>
<dd>
<h2></h2>

Такая проверка выполняется в браузере перед показом маршрута. Пользователь может изменить состояние приложения, открыть DevTools или вызвать API напрямую. Поэтому она защищает пользовательский сценарий, а не данные.

Настоящая защита находится на сервере: каждая операция проверяет сессию или токен, права, tenant, доступ к ресурсу и актуальное состояние пользователя. Клиентская проверка нужна, чтобы не показывать лишний экран и направить пользователя к входу или странице отсутствия доступа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где хранить идентификатор сессии, access token и refresh token?</strong></summary>

<dl>
<dd>
<h2></h2>

Для собственного веб-приложения (`first-party`) предпочтительна защищённая `HttpOnly` cookie с идентификатором серверной сессии или BFF, который хранит OAuth-токены вне JavaScript браузера. `HttpOnly` мешает XSS прочитать значение, `Secure` ограничивает передачу HTTPS-соединениями, а `SameSite` уменьшает часть CSRF-риска. Хранить учётные данные в `localStorage` или `sessionStorage` не следует: любой скрипт из того же источника (`origin`) может их прочитать. Если архитектура прямого SPA вынуждает работать с access token, его обычно держат в памяти и получают безопасным OAuth-потоком.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>HttpOnly</code> cookie не отменяет защиту от CSRF?</strong></summary>

<dl>
<dd>
<h2></h2>

Браузер автоматически прикладывает cookie к подходящему запросу, даже если JavaScript не может прочитать её. Злоумышленник может попытаться инициировать изменение с другого сайта. Поэтому сервер проверяет `Origin`, использует подходящий `SameSite` и при необходимости CSRF token. `HttpOnly` защищает конфиденциальность cookie при XSS, но не гарантирует, что запрос был инициирован доверенным интерфейсом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>401</code> отличается от <code>403</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`401 Unauthorized` означает, что запрос не имеет действующей аутентификации: сессия отсутствует или access token истёк. Тогда допустима одна попытка обновления, если такой механизм предусмотрен. `403 Forbidden` означает, что пользователь распознан, но не имеет права; повторное обновление токена обычно ничего не изменит. Интерфейс показывает вход для `401` и понятное отсутствие доступа для `403`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как обрабатывать поток обновления через refresh token?</strong></summary>

<dl>
<dd>
<h2></h2>

При подходящем `401` API-слой один раз обращается к операции обновления, получает новый access token или продлевает серверную сессию и повторяет исходный запрос. Если обновление не прошло, нужно завершить ожидающие запросы, очистить персональный кэш и перевести пользователя к входу.

Важная деталь - single flight, то есть одно общее обновление для конкурентных запросов. Если десять запросов одновременно получили `401`, они ждут один промис. После успеха каждый повторяется с новой учётной информацией, после провала завершается ошибкой. Так клиент не создаёт гонку при смене refresh token.

Операцию обновления исключают из этого механизма, а исходный запрос повторяют не более одного раза. Не каждый `401` нужно обрабатывать автоматически: ошибка входа или самого обновления является окончательной.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое refresh token rotation и обнаружение повторного использования (<code>reuse detection</code>)?</strong></summary>

<dl>
<dd>
<h2></h2>

Refresh token rotation означает, что при каждом успешном обновлении сервер выдаёт новый refresh token и делает предыдущий недействительным, сохраняя связь между ними. Если старый токен используют снова, это может означать кражу: сервер отзывает активную цепочку и требует нового входа. Для публичных OAuth-клиентов RFC 9700 требует такую смену с обнаружением повторного использования либо sender-constrained token - токен, криптографически привязанный к экземпляру клиента.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое бесконечный цикл обновления (<code>refresh loop</code>)?</strong></summary>

<dl>
<dd>
<h2></h2>

Это ситуация, когда клиент бесконечно пытается обновить сессию. Например, обычный запрос получил `401`, операция обновления тоже вернула `401`, а общий перехватчик снова запустил обновление.

Для защиты операцию обновления исключают из перехватчика, используют один общий промис, помечают уже повторённый запрос и при ошибке завершают очередь. Затем приложение переходит в состояние без аутентификации, а не делает ещё один скрытый запрос.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как защищать маршрут при SSR в Next.js?</strong></summary>

<dl>
<dd>
<h2></h2>

Серверный код читает сессию из cookie, проверяет её и до отправки защищённого содержимого возвращает страницу, перенаправление или состояние `403`. Middleware может рано отсечь часть запросов, но не заменяет проверку в Route Handler, Server Action или серверном API, где выполняется операция. Клиентская проверка после hydration - активации серверной разметки React - нужна для обновления интерфейса, но не должна быть единственным барьером.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как синхронизировать выход между вкладками?</strong></summary>

<dl>
<dd>
<h2></h2>

Одна вкладка завершает серверную сессию или отзывает refresh token, затем передаёт локальное событие через `BroadcastChannel`. Остальные вкладки очищают персональный кэш и состояние, закрывают WebSocket/SSE, отменяют запросы и переходят к экрану входа.

Событие между вкладками улучшает UX, но не является защитой. Даже если вкладка его пропустила, сервер после выхода больше не должен принимать старую сессию. Для cookie-сессии это удаление или отзыв записи на сервере; для refresh token - отзыв выданного набора прав (`grant`) или цепочки токенов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как безопасно вернуть пользователя на исходную страницу после входа?</strong></summary>

<dl>
<dd>
<h2></h2>

Клиент сохраняет внутренний путь вроде `/orders/42`, а после входа проверяет, что это разрешённый маршрут того же источника (`origin`). Нельзя без проверки перенаправлять по произвольному `returnUrl=https://evil.example`, иначе приложение становится open redirect и помогает фишингу. Для OAuth redirect URI заранее регистрируют и сравнивают точным совпадением.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Архитектурное решение |
| --- | --- |
| First-party Next.js | BFF или серверная сессия в защищённой cookie |
| Прямой OAuth из SPA | Authorization Code + PKCE и защита refresh token |
| Десять одновременных `401` | Один refresh и очередь ожидающих запросов |
| Пользователь без права | `403` и отсутствие защищённых данных, а не новый вход |
| Выход в одной вкладке | Отзыв на сервере, `BroadcastChannel` и очистка всех клиентов |
