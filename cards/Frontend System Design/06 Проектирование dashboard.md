## Вопрос

<br>

 💬 **Как спроектировать dashboard с несколькими виджетами, API-запросами, кэшированием и состояниями ошибок?**

<h2></h2>

<br>
<dl>
<dd>

Сначала уточняют назначение dashboard, или информационной панели:

- кто его использует;
- какие решения принимает пользователь;
- какие виджеты критичны;
- насколько свежими должны быть данные;
- должны ли виджеты относиться к одному моменту времени;
- допустим ли частичный результат;
- как часто данные обновляются;
- какой объём данных отображается;
- какие роли и tenant имеют доступ;
- нужны ли экспорт, полноэкранный режим и мобильное представление.

Практический порядок проектирования:

```text
требования
→ общие параметры страницы
→ границы виджетов
→ API и согласованность данных
→ кэш и обновление
→ состояния ошибок
→ рендеринг
→ производительность
→ доступность
→ наблюдаемость и тестирование
```

Dashboard обычно разделяют на:

```text
DashboardPage
├── общие фильтры
├── критичный контекст страницы
├── Widget A
├── Widget B
└── Widget C
```

Общие параметры представления хранят на уровне страницы или в URL:

- временной диапазон;
- timezone;
- tenant или workspace;
- выбранный объект;
- валюта;
- группировка;
- глобальные фильтры.

Например:

```text
/dashboard?range=7d&timezone=Europe/Moscow&team=sales
```

URL позволяет:

- восстановить dashboard после reload;
- поделиться ссылкой;
- использовать Back/Forward;
- сохранить фильтры при переходе на другой экран.

Локальное состояние виджета оставляют внутри него:

- раскрыта ли легенда;
- выбран ли тип графика;
- открыт ли tooltip;
- включён ли локальный режим сравнения;
- свёрнут ли блок.

Не следует помещать каждое визуальное состояние в глобальное хранилище.

Дальше определяют критичные и независимые данные.

**Критичные данные** нужны для существования всего экрана:

- текущий tenant;
- права пользователя;
- доступные организации;
- базовый контекст отчёта;
- обязательная runtime-конфигурация.

Если они не загрузились, dashboard может быть невозможно показать вообще.

**Данные виджета** обычно можно загружать и обрабатывать независимо:

```text
выручка
конверсия
последние операции
график нагрузки
ошибки
```

Сбой одного необязательного виджета не должен автоматически скрывать остальные.

Границы виджетов выбирают по ответственности.

Хороший виджет имеет:

- понятные входные параметры;
- собственный запрос или явно разделяемый источник;
- собственные состояния загрузки и ошибки;
- ограниченную область повторного рендера;
- отдельные метрики;
- возможность повторить запрос независимо.

Один источник данных не обязательно означает один компонент.

Например, несколько виджетов могут использовать один query cache:

```text
GET /dashboard/summary
→ общий cache entry
→ RevenueWidget читает revenue
→ OrdersWidget читает orders
```

Это не должно создавать несколько одинаковых запросов.

При использовании query library компоненты подписываются на один ключ и при необходимости выбирают только нужную часть результата.

Стратегию API выбирают по зависимостям и требованиям согласованности.

Основные варианты:

```text
отдельный endpoint на каждый виджет
агрегирующий dashboard endpoint
BFF с несколькими логическими ресурсами
смешанная модель
```

**Отдельные запросы** подходят, если виджеты:

- загружаются независимо;
- имеют разную свежесть;
- используют разные права;
- обновляются с разной частотой;
- должны повторяться независимо;
- могут отсутствовать на странице.

Преимущества:

- изоляция ошибок;
- независимый cache;
- отдельный retry;
- возможность ленивой загрузки;
- меньшие ответы.

Недостатки:

- больше сетевых переходов;
- возможен request waterfall;
- данные могут относиться к разным моментам времени;
- возрастает риск request storm.

**Агрегирующий endpoint** полезен, если:

- данные нужны для первого критичного экрана;
- сервер может эффективнее выполнить агрегацию;
- виджетам нужен единый snapshot;
- браузер иначе выполняет слишком много мелких запросов;
- операции требуют общего контекста прав.

Например:

```text
GET /dashboard
→ summary
→ revenue
→ orders
→ asOf
```

Преимущества:

- меньше сетевых переходов;
- единый момент данных;
- централизованная агрегация;
- проще получить критичный первый экран.

Недостатки:

- жизненные циклы виджетов связываются;
- медленный источник задерживает общий ответ;
- меняется весь cache entry;
- частичная ошибка может стать ошибкой всего запроса.

Агрегирующий контракт может поддерживать частичный результат:

```json
{
  "asOf": "2026-08-05T18:00:00Z",
  "widgets": {
    "revenue": {
      "status": "success",
      "data": {}
    },
    "alerts": {
      "status": "error",
      "errorCode": "SOURCE_UNAVAILABLE"
    }
  }
}
```

Тогда клиент всё равно должен обработать состояние каждого блока отдельно.

Частый компромисс:

```text
один критичный summary endpoint
+
отдельные запросы тяжёлых и второстепенных виджетов
```

Независимые запросы запускают параллельно.

Опасный request waterfall:

```text
загрузить пользователя
→ загрузить dashboard
→ загрузить summary
→ загрузить график
```

Если запросы не зависят друг от друга, их начинают одновременно:

```text
summary ──────┐
chart ────────┼→ dashboard
recent items ─┘
```

Последовательность оставляют только там, где следующему запросу действительно нужен результат предыдущего.

Для согласованности данных определяют момент, к которому относится ответ.

Сервер может вернуть:

```text
asOf
snapshotId
dataVersion
```

Например:

```json
{
  "snapshotId": "dashboard-1842",
  "asOf": "2026-08-05T18:00:00Z"
}
```

Если строгая согласованность обязательна, все критичные виджеты получают данные одного snapshot.

Если допустима eventual consistency, каждый виджет показывает собственное время последнего обновления.

Нельзя подписывать весь dashboard одним временем:

```text
Обновлено в 18:00
```

если часть блоков фактически получила данные в 17:55, а часть — в 18:03.

Нужно различать несколько уровней кэширования.

```text
HTTP/CDN cache
server/framework cache
client query cache
локальные вычисления
```

**HTTP/CDN cache** хранит сетевой ответ между клиентом и origin.

Он управляется через:

```text
Cache-Control
ETag
Last-Modified
CDN rules
```

**Server/framework cache** может хранить результат запроса или рендера на сервере, например в Next.js или BFF.

**Client query cache** хранит server state уже внутри приложения:

```text
data
error
status
timestamp
subscriptions
```

Эти уровни не заменяют друг друга.

Например, RTK Query может выполнить refetch, но HTTP cache вернёт ещё свежий ответ без обращения к origin.

Или Next.js server cache может вернуть старые данные ещё до того, как запрос попадёт в client query cache.

Для каждого ресурса задают:

- сколько данные считаются свежими;
- можно ли показывать старый результат;
- когда выполнять background refetch;
- как инвалидировать данные;
- нужно ли обновление при focus;
- нужен ли polling;
- как обрабатывается ручной refresh.

Ключ client cache должен включать все параметры, меняющие ответ:

- endpoint или тип виджета;
- tenant или workspace;
- фильтры;
- временной диапазон;
- timezone;
- currency;
- группировку;
- детализацию;
- другие параметры доступа или представления, влияющие на данные.

Например:

```text
revenue:
tenant=42
range=7d
timezone=Europe/Moscow
currency=RUB
```

не должен использовать тот же cache entry, что и:

```text
revenue:
tenant=18
range=30d
timezone=UTC
currency=USD
```

Параметры перед построением ключа нормализуют.

Одинаковые состояния не должны создавать несколько ключей только из-за разного порядка свойств или значений по умолчанию.

Access token и другие secrets в cache key не помещают.

После logout или смены пользователя персональные cache entries очищают либо гарантированно изолируют новой сессией и store.

Если два компонента используют один endpoint с одинаковыми нормализованными параметрами, query library может разделить результат и не выполнять второй сетевой запрос.

При смене фильтра возможна гонка:

```text
запрос A для range=7d
→ запрос B для range=30d
→ B завершился первым
→ A завершился позже
```

Старый ответ A не должен вернуть dashboard к прежнему состоянию.

Для этого:

- запрос отменяют;
- параметры входят в query key;
- устаревший request ID игнорируют;
- ответ применяют только к соответствующему cache entry.

Нужно различать:

```text
initial loading
background fetching
```

**Initial loading** означает, что пригодных данных ещё нет.

Виджет показывает skeleton или другое начальное состояние.

**Background fetching** означает, что предыдущие данные уже есть и выполняется обновление.

Обычно не нужно заменять весь виджет skeleton при каждом refetch.

Можно оставить данные и показать небольшой индикатор:

```text
Обновляем…
```

Каждый виджет может иметь состояния:

- initial loading;
- success;
- empty;
- background fetching;
- stale;
- partial;
- error;
- forbidden;
- rate limited;
- offline;
- realtime disconnected.

**Empty state** означает, что запрос выполнился успешно, но данных нет.

Например:

```text
За выбранный период операций не было.
```

Это отличается от ошибки.

**Stale state** означает, что показаны предыдущие данные, но обновление не удалось или срок свежести истёк.

Например:

```text
Не удалось обновить.
Показаны данные на 17:42.
```

Старые данные можно показывать, если это безопасно для пользовательского решения.

Для финансовой операции, актуальных прав или аварийного мониторинга устаревшие данные могут быть недопустимы.

Тогда виджет должен явно заблокировать зависящее от них действие.

**Partial state** означает, что показана только часть результата.

Например:

```text
основные показатели загружены
+
разбивка по регионам недоступна
```

Сбой необязательного виджета изолируют внутри его границы:

```text
данные или предыдущий результат
→ сообщение об ошибке
→ повтор запроса
```

Общая ошибка страницы нужна, только если не загрузилась обязательная основа:

- tenant;
- права;
- базовая конфигурация;
- критичный snapshot.

Если предыдущие данные сохранены, пользователь должен понимать:

- когда они были получены;
- почему не обновились;
- можно ли им доверять;
- какое действие доступно.

Retry одного виджета не должен без необходимости перезапускать все остальные запросы.

Для автоматического обновления задают политику по каждому ресурсу.

Например:

```text
summary
→ каждые 60 секунд

alerts
→ каждые 10 секунд

historical chart
→ только при смене фильтра
```

Нельзя запускать десятки polling-запросов одновременно в одну и ту же секунду.

Это создаёт request storm:

```text
10 виджетов
×
10 000 клиентов
→ одновременный всплеск запросов
```

Возможные меры:

- общий scheduler;
- объединение запросов;
- разный интервал;
- случайный jitter;
- остановка polling в скрытой вкладке;
- обновление после возвращения focus;
- SSE или WebSocket для действительно частых изменений.

Ручная кнопка обновления должна:

- предотвращать бесконтрольные повторные нажатия;
- показывать процесс;
- обновлять нужную область;
- не стирать пригодные данные без необходимости.

В Next.js оболочку и доступные на сервере данные можно отрендерить до отправки страницы.

Интерактивные графики, фильтры и browser-only компоненты остаются клиентскими.

Границы ожидания располагают по пользовательским блокам:

```text
Dashboard shell
├── Suspense: Summary
├── Suspense: Revenue chart
└── Suspense: Recent operations
```

Так медленный график не обязан задерживать summary.

`loading.tsx` подходит для loading-состояния route segment.

Более точечные `<Suspense>` boundaries используют рядом с медленными или динамическими участками.

Suspense и Error Boundary решают разные задачи:

```text
Suspense
→ ожидание данных или кода

Error Boundary
→ изоляция ошибки рендера поддерживаемого поддерева
```

Границы ошибок располагают так, чтобы ошибка одного виджета не уничтожила весь dashboard.

При этом Error Boundary не заменяет обычную обработку ожидаемой ошибки API.

Состояние:

```text
сервер вернул 403
```

или:

```text
запрос завершился 500
```

обычно преобразуют в контролируемое состояние виджета.

Серверные данные не следует повторно запрашивать на клиенте без необходимости.

Возможные подходы:

- серверный компонент сразу рендерит данные;
- сервер передаёт сериализуемые данные клиентскому виджету;
- сервер передаёт Promise в поддерживаемый Suspense-flow;
- client query cache гидратируется тем же ключом;
- клиент начинает refetch только по своей политике свежести.

Важно, чтобы серверная и клиентская части использовали одинаковые:

- tenant;
- фильтры;
- timezone;
- права;
- cache key;
- snapshot.

Иначе после hydration пользователь сначала увидит серверные данные, а затем другой клиентский результат.

Производительность dashboard зависит от:

- initial JavaScript;
- числа запросов;
- размера ответов;
- тяжёлых библиотек графиков;
- количества DOM/SVG-узлов;
- числа точек;
- частоты обновления;
- вычислений на main thread;
- количества одновременно рендерящихся виджетов.

Тяжёлый график можно загрузить лениво:

```text
критичный summary
→ initial bundle

сложная chart library
→ отдельный chunk
```

Но lazy loading не должен скрывать критичную информацию без альтернативы.

Данные для графиков часто выгоднее агрегировать на сервере.

Например:

```text
1 000 000 событий
→ сервер группирует по часу
→ клиент получает 168 точек
```

Прореживание должно сохранять смысл данных.

Для финансового графика простое удаление каждой второй точки может скрыть минимум или максимум. Алгоритм агрегации должен соответствовать предметной области.

Если клиенту всё же нужны тяжёлые вычисления, их можно перенести в Web Worker:

```text
main thread
→ UI и события

Web Worker
→ агрегация и преобразование
```

Для таблиц применяют:

- серверную пагинацию;
- ограничение количества строк;
- виртуализацию после измерения.

Для графиков:

- ограничивают количество точек;
- объединяют частые обновления;
- не перерисовывают весь график на каждое событие;
- при необходимости используют Canvas или WebGL.

Skeleton должен сохранять размеры будущего виджета.

Иначе после загрузки графика остальные блоки сдвинутся и увеличат layout shift.

Нужно избегать skeleton, который визуально не похож на итоговый блок или бесконечно анимируется при долгой ошибке.

Dashboard должен оставаться доступным.

Для каждого графика полезны:

- понятный заголовок;
- текстовое резюме;
- ключевые значения;
- доступная таблица данных или другой эквивалент;
- управление с клавиатуры, если график интерактивный;
- видимый focus;
- подписи, не зависящие только от цвета.

Например:

```text
Выручка выросла на 12% относительно прошлого периода.
Минимум — 1 августа.
Максимум — 5 августа.
```

Tooltip, доступный только по hover, недостаточен для клавиатуры и touch-устройств.

Цвет графика не должен быть единственным способом отличить серии. Дополнительно используют подписи, маркеры, линии или паттерны.

При автообновлении нельзя постоянно перемещать фокус или перегружать screen reader сообщениями.

Значимые изменения объявляют через ограниченную status-область, если пользователь действительно должен узнать об обновлении сразу.

Права проверяются сервером для каждого ресурса.

Frontend может скрыть недоступный виджет, но это не защищает API.

Кэш не должен смешивать данные:

- разных пользователей;
- разных tenant;
- разных ролей;
- разных окружений.

Особенно осторожно работают с SSR и shared server cache: персонализированный ответ нельзя случайно сделать общим для всех пользователей.

Наблюдаемость строят по dashboard и отдельным виджетам.

Полезные метрики:

- время до готовности оболочки;
- время до первого полезного виджета;
- время до готовности критичных виджетов;
- error rate по виджету;
- доля stale-ответов;
- размер ответа;
- cache hit;
- частота retry;
- длительные задачи main thread;
- LCP;
- INP;
- CLS;
- размер chart chunk.

Полезный контекст события:

```text
widgetName
operationName
environment
release
tenant type
range type
requestId
snapshotId
```

Не следует передавать:

- access token;
- персональные значения фильтров;
- полный URL с чувствительными query;
- данные отчёта;
- содержимое ответа;
- пользовательские идентификаторы без необходимости.

Чтобы отличить сетевую проблему от тяжёлого рендера, измеряют отдельно:

```text
request duration
data transformation duration
render duration
```

Тестовая стратегия включает:

- загрузку всех виджетов;
- параллельные запросы;
- ошибку одного виджета;
- ошибку критичного контекста;
- предыдущие stale-данные;
- retry;
- смену фильтра;
- поздний ответ старого запроса;
- разные tenant и права;
- общий snapshot;
- polling;
- скрытие и возврат вкладки;
- server rendering и hydration;
- keyboard navigation;
- доступную альтернативу графика;
- мобильное представление.

Главный принцип:

```text
общий контекст
→ управляется страницей

независимый виджет
→ самостоятельно загружается и восстанавливается

cache
→ учитывает все параметры результата

ошибка одной части
→ не уничтожает весь dashboard

производительность
→ измеряется по сети, вычислениям и рендеру
```

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Как избежать последовательной цепочки запросов (<code>request waterfall</code>)?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала определяют реальные зависимости.

Если запросы независимы, их запускают параллельно:

```text
summary ─────┐
chart ───────┼→ render
operations ──┘
```

Параметры, необходимые всем виджетам, получают до запуска дочерних запросов.

Также помогают:

- server-side aggregation;
- BFF;
- prefetch;
- общий query cache;
- запуск Promise до точки `await`;
- Suspense boundaries вокруг независимых блоков.

Последовательность оставляют только тогда, когда второй запрос действительно использует результат первого.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужна общая операция API для dashboard, а когда отдельные запросы виджетов?</strong></summary>

<dl>
<dd>
<h2></h2>

Общий endpoint полезен, если:

- данные должны относиться к одному snapshot;
- сервер эффективнее выполняет агрегацию;
- экран иначе делает много критичных запросов;
- все блоки имеют похожую свежесть.

Отдельные запросы лучше, если виджеты:

- независимы;
- обновляются с разной частотой;
- имеют разные права;
- должны повторяться отдельно;
- загружаются лениво.

Частый компромисс:

```text
агрегированный summary
+
отдельные тяжёлые или второстепенные виджеты
```

Общий ответ может содержать отдельный статус каждого блока, чтобы одна ошибка не превращалась в полный сбой.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать при сбое одного из виджетов?</strong></summary>

<dl>
<dd>
<h2></h2>

Ошибку изолируют внутри виджета.

Если предыдущие данные пригодны, их оставляют и показывают:

- время последнего успеха;
- предупреждение об ошибке обновления;
- кнопку повторного запроса.

Если данных нет, показывают локальное error state.

Остальные виджеты продолжают работать.

Общая ошибка страницы нужна только при сбое обязательного контекста, без которого невозможно определить пользователя, tenant, права или параметры dashboard.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как кэшировать данные dashboard?</strong></summary>

<dl>
<dd>
<h2></h2>

Для каждого ресурса определяют:

- cache key;
- срок свежести;
- срок хранения;
- background refetch;
- invalidation;
- polling;
- refetch при focus;
- ручное обновление.

Ключ включает все параметры ответа:

```text
tenant
filters
range
timezone
currency
granularity
```

В RTK Query одинаковые endpoint и сериализованные параметры используют общий cache entry.

Для обновления применяют:

- tags;
- `refetchOnFocus`;
- `refetchOnMountOrArgChange`;
- `pollingInterval`;
- ручной `refetch`.

Персональный cache очищают после logout или смены пользователя.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как показать, что несколько виджетов относятся к одному моменту времени?</strong></summary>

<dl>
<dd>
<h2></h2>

Сервер возвращает общий:

```text
snapshotId
asOf
```

Все критичные данные получают относительно этой версии.

Например:

```json
{
  "snapshotId": "report-1842",
  "asOf": "2026-08-05T18:00:00Z"
}
```

Если запросы независимы и строгая согласованность не требуется, каждый виджет показывает собственное время обновления.

Нельзя указывать одно общее время, если блоки фактически построены по разным версиям данных.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему библиотеки графиков могут ухудшать производительность?</strong></summary>

<dl>
<dd>
<h2></h2>

Chart library может:

- увеличить initial bundle;
- создать много SVG или DOM-узлов;
- выполнять агрегацию на main thread;
- часто перерасчитывать layout;
- перерисовывать график на каждое обновление.

Возможные меры:

- lazy loading;
- server-side aggregation;
- ограничение числа точек;
- batching обновлений;
- Web Worker;
- Canvas или WebGL.

Решение подтверждают bundle analyzer и browser profiler, а не названием библиотеки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие состояния должен иметь виджет?</strong></summary>

<dl>
<dd>
<h2></h2>

Базовые состояния:

- initial loading;
- data;
- empty;
- error.

По сценарию добавляются:

- background fetching;
- stale;
- partial;
- forbidden;
- rate limited;
- offline;
- realtime disconnected.

Пользователь должен понимать:

```text
есть ли данные
насколько они свежие
почему не обновились
что можно сделать дальше
```

Состояние виджета не сводится к наличию или отсутствию spinner.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как серверный рендеринг и потоковая передача помогают dashboard в Next.js?</strong></summary>

<dl>
<dd>
<h2></h2>

Сервер может раньше вернуть:

- оболочку;
- заголовок;
- права;
- критичный summary.

Независимые медленные блоки передаются по мере готовности через Suspense boundaries.

Route-level состояние можно задать через:

```text
loading.tsx
```

Для отдельных виджетов используют более точечные `<Suspense>`.

Интерактивные графики остаются Client Components.

Важно не запрашивать те же данные повторно после hydration без необходимости. Серверный и клиентский слой должны использовать одинаковые фильтры, tenant и cache key.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что тестировать и измерять?</strong></summary>

<dl>
<dd>
<h2></h2>

Тестируют:

- критичный пользовательский путь;
- независимую загрузку виджетов;
- частичный сбой;
- общий сбой контекста;
- stale-данные;
- retry;
- поздний ответ старого запроса;
- права;
- смену tenant;
- polling;
- SSR и hydration;
- доступность.

Измеряют:

- LCP;
- INP;
- CLS;
- время готовности критичных виджетов;
- request duration;
- render duration;
- размер ответов;
- размер lazy chunks;
- error rate;
- долю stale-данных;
- long tasks.

Для графиков отдельно проверяют клавиатуру и текстовую альтернативу данным.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем HTTP cache отличается от query cache и server cache?</strong></summary>

<dl>
<dd>
<h2></h2>

HTTP cache хранит сетевой response и управляется HTTP-заголовками:

```text
Cache-Control
ETag
Last-Modified
```

Server или framework cache хранит данные либо результат рендера на серверной стороне.

Query cache хранит server state внутри запущенного frontend-приложения.

Один уровень может вернуть старые данные, даже если другой запросил обновление.

Поэтому политика свежести должна быть согласована между:

```text
CDN
server
browser HTTP cache
client query cache
```

Особенно осторожно кэшируют персонализированные ответы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как обновлять много виджетов и не создавать request storm?</strong></summary>

<dl>
<dd>
<h2></h2>

Необязательно давать каждому виджету независимый таймер на одинаковом интервале.

Можно использовать:

- общий scheduler;
- агрегирующий endpoint;
- разные интервалы;
- jitter;
- дедупликацию одинаковых запросов;
- остановку polling в скрытой вкладке;
- refetch после возврата focus;
- realtime-транспорт для действительно частых изменений.

При ошибках интервал увеличивают через backoff.

Ручное обновление не должно создавать несколько одинаковых параллельных запросов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда можно продолжать показывать устаревшие данные?</strong></summary>

<dl>
<dd>
<h2></h2>

Stale-данные допустимы, если:

- они всё ещё помогают пользователю;
- время обновления явно показано;
- пользователь понимает ограничение;
- на их основе не выполняется опасное действие.

Например, исторический график можно оставить при временном сетевом сбое.

Актуальные права, остаток денежных средств или состояние аварии могут требовать блокировки действия до успешного обновления.

Решение зависит от бизнес-риска, а не только от технического наличия cache.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как сделать график доступным?</strong></summary>

<dl>
<dd>
<h2></h2>

График должен иметь:

- понятный заголовок;
- краткое текстовое резюме;
- ключевые значения;
- таблицу данных или другой доступный эквивалент;
- клавиатурный доступ к интерактивным элементам;
- видимый focus;
- подписи, не зависящие только от цвета.

Tooltip только по hover недостаточен.

Частые автоматические обновления не должны постоянно перехватывать фокус или перегружать screen reader сообщениями.

Если визуализация декоративная, её скрывают от вспомогательных технологий, а смысл передают текстом.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Ключевое решение |
| --- | --- |
| Операционный dashboard | Свежесть и время обновления каждого виджета |
| Финансовый отчёт | Общие `snapshotId` и `asOf` |
| Один API недоступен | Изолированная ошибка и предыдущие данные виджета |
| Критичный первый экран | Агрегированный summary и независимые вторичные запросы |
| Тяжёлый график во второй вкладке | Lazy loading и server-side aggregation |
| Частое автообновление | Общий scheduler, jitter или realtime-транспорт |
| Разные права пользователей | Изолированный cache и серверная авторизация |
| Next.js dashboard | Server shell, Suspense и независимые Error Boundaries |
| Доступный отчёт | Текстовое резюме и таблица данных для графика |
