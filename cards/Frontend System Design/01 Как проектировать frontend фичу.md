## Вопрос

<br>

 💬 **Как бы ты проектировал новую frontend-фичу от требований до релиза?**

<h2></h2>

<br>
<dl>
<dd>

Проектирование frontend-фичи начинается не с выбора библиотеки или структуры папок, а с понимания задачи.

Упрощённый процесс:

```text
цель и границы
→ пользовательские сценарии
→ данные и API
→ состояние
→ архитектура и рендеринг
→ ошибки и безопасность
→ производительность
→ тестирование
→ rollout
→ наблюдение после релиза
```

На каждом этапе нужно не просто перечислить технологии, а принять решение и объяснить его компромиссы.

Сначала уточняют **цель фичи**:

- кто пользователь;
- какую проблему он решает;
- какой сценарий является основным;
- как выглядит успешный результат;
- по какой метрике оценивается эффект;
- что входит в первую версию;
- что сознательно остаётся за её пределами.

Например:

```text
Цель:
помочь менеджеру быстрее найти подходящее предложение поставщика.

Основной сценарий:
открыть список → применить фильтры → выбрать предложение.

Не входит в первую версию:
массовое редактирование и сохранённые наборы фильтров.
```

Это защищает от ситуации, когда команда технически реализовала интерфейс, но не решила пользовательскую задачу.

Требования разделяют на **функциональные** и **нефункциональные**.

Функциональные описывают поведение:

- какие действия доступны;
- какие данные показываются;
- какие роли имеют доступ;
- какие правила валидации действуют;
- что происходит после успешной операции;
- какие ошибки должен увидеть пользователь.

Нефункциональные задают ограничения:

- объём данных;
- частоту обновления;
- допустимое время ответа;
- целевые устройства;
- поддерживаемые браузеры;
- доступность;
- SEO;
- работу при плохой сети;
- требования безопасности;
- срок выпуска.

Необязательно заранее знать точные цифры для всего, но ключевые ограничения должны быть сформулированы.

Например:

```text
до 100 000 записей
→ фильтрация и сортировка на сервере

до 100 элементов
→ допустима клиентская обработка
```

Затем описывают пользовательские сценарии.

Полезно начать с основного happy path:

```text
пользователь открывает экран
→ получает данные
→ изменяет параметры
→ подтверждает действие
→ видит результат
```

После этого добавляют альтернативные сценарии:

- данных нет;
- доступ запрещён;
- запрос завершился ошибкой;
- пользователь повторил действие;
- данные изменил другой пользователь;
- сеть пропала;
- пользователь закрыл или перезагрузил страницу;
- сервер вернул частичный результат.

Для каждого сценария определяют:

```text
что видит пользователь
какое действие ему доступно
можно ли безопасно повторить операцию
```

Критерии приёмки должны быть проверяемыми.

Вместо:

```text
таблица должна быть удобной
```

лучше:

```text
фильтры сохраняются в URL;
при reload результат восстанавливается;
пустой результат показывает причину и кнопку сброса;
ошибка загрузки позволяет повторить запрос.
```

После уточнения сценариев проектируют **модель данных и контракт API**.

Определяют:

- основные сущности;
- идентификаторы;
- обязательные поля;
- поля, допускающие `null`;
- форматы дат и чисел;
- операции чтения и изменения;
- пагинацию;
- фильтрацию;
- сортировку;
- права;
- формат ошибок;
- правила конкурентного изменения.

Сетевая DTO-модель не обязана полностью совпадать с моделью интерфейса.

Например, сервер может вернуть:

```ts
type ProductDto = {
  id: string;
  price_cents: number;
  created_at: string;
};
```

А внутри приложения удобнее использовать:

```ts
type Product = {
  id: string;
  price: number;
  createdAt: Date;
};
```

Преобразование выполняют на границе API:

```text
response DTO
→ validation/mapping
→ frontend model
```

Это уменьшает зависимость компонентов от формата backend.

До реализации нужно согласовать:

- как кодируются фильтры;
- какая пагинация используется;
- стабильна ли сортировка;
- как выглядит ошибка валидации;
- как отличить отсутствие доступа от отсутствия данных;
- можно ли отменить запрос;
- допускается ли повтор mutation;
- как обнаружить конфликт версий.

Для операций изменения важна идемпотентность.

Если пользователь или клиент повторит запрос из-за timeout:

```text
POST отправлен
→ ответ потерян
→ клиент повторил запрос
```

сервер не должен случайно создать два одинаковых результата.

Для этого могут использоваться:

- idempotency key;
- operation ID;
- уникальное бизнес-ограничение;
- отдельная идемпотентная операция.

Для конкурентного редактирования можно использовать:

- номер версии;
- `updatedAt`;
- `ETag` и `If-Match`;
- другой optimistic concurrency control.

Например:

```text
пользователь открыл версию 4
→ сервер уже хранит версию 5
→ update версии 4 отклоняется как конфликт
```

Интерфейс должен объяснить конфликт и предложить получить актуальные данные, а не молча перезаписать чужое изменение.

Следующий этап — распределение **состояния по владельцам**.

Полезная классификация:

| Вид состояния | Пример | Где хранить |
| --- | --- | --- |
| URL state | Фильтры, сортировка, вкладка, страница | Search params или route |
| Local UI state | Открыта ли модалка, выбран ли элемент | Ближайший компонент |
| Form state | Значения, touched, validation | Форма или form library |
| Server state | Данные API, loading, error, freshness | Query cache |
| Shared client state | Тема, текущий workspace | Глобальное хранилище при необходимости |
| Persistent draft | Большой локальный черновик | IndexedDB или сервер |

URL подходит для состояния, которое:

- должно переживать reload;
- должно работать с Back/Forward;
- должно копироваться ссылкой;
- влияет на представление страницы.

Например:

```text
/products?brand=bosch&page=3&sort=price
```

Локальное состояние используют для временной детали интерфейса:

```text
isModalOpen
hoveredRow
expandedSection
```

Серверные данные не нужно без необходимости копировать из query cache в глобальное клиентское хранилище.

Иначе появляются два источника истины:

```text
RTK Query cache
+
Redux slice с теми же products
```

и требуется ручная синхронизация.

Вычисляемое значение обычно не хранят отдельным state.

Вместо:

```ts
const [filteredItems, setFilteredItems] =
  useState<Item[]>([]);
```

если результат полностью определяется `items` и `filter`, его вычисляют из исходных данных.

Главный вопрос:

```text
Кто является источником истины для этого значения?
```

Одно значение не должно без необходимости одновременно жить:

- в URL;
- в local state;
- в global store;
- в server cache.

Если копия необходима, например редактируемый черновик серверных данных, нужно определить момент синхронизации:

```text
server value
→ создать draft
→ пользователь редактирует draft
→ сохранить
→ обновить server cache
```

После состояния определяют **границы feature, модулей и компонентов**.

Компонент имеет смысл отделить, если у части интерфейса:

- самостоятельная ответственность;
- отдельный источник данных;
- собственные состояния ошибок;
- другая частота обновления;
- отдельная тестируемая логика;
- возможность повторного использования.

Но дробить каждый `div` на отдельный компонент не нужно.

Архитектурную границу выбирают по ответственности, а не по длине файла.

Например:

```text
ProductFilters
→ состояние и UI фильтров

ProductTable
→ отображение данных

ProductPagination
→ управление страницей

ProductPage
→ связывает URL, запрос и состояния экрана
```

Инфраструктурный код отделяют от UI:

```text
API client
DTO mapping
query definitions
feature permissions
analytics
```

Shared-слой используют только для действительно общих вещей.

Если компонент используется один раз и его требования принадлежат одной feature, преждевременный перенос в глобальный UI kit может усложнить изменения.

Нужно различать:

```text
одинаково выглядит
```

и:

```text
имеет один стабильный контракт и общую ответственность
```

Для сложной feature полезно сначала реализовать один вертикальный пользовательский срез:

```text
получить данные
→ показать минимальный экран
→ выполнить одно основное действие
```

а затем расширять:

```text
фильтры
→ ошибки
→ права
→ оптимизация
→ дополнительные сценарии
```

Это быстрее проверяет контракт и архитектурные решения, чем создание всех абстракций до первого работающего сценария.

Декомпозиция реализации может выглядеть так:

```text
1. Контракт API и типы.
2. Запрос и mapping.
3. Основной read-only экран.
4. URL-фильтры.
5. Mutation.
6. Ошибочные состояния.
7. Права и доступность.
8. Метрики и rollout.
```

Зависимости между задачами должны быть явными.

Например, UI можно разрабатывать на mock-данных параллельно с backend, если контракт уже согласован.

Для React и Next.js отдельно выбирают **границы серверного и клиентского выполнения**.

Нужно определить:

- нужен ли SEO;
- важно ли быстрое первое содержимое;
- зависит ли результат от cookies или пользователя;
- можно ли кэшировать HTML или данные;
- где требуется браузерный API;
- где нужна интерактивность;
- насколько дорогой будет hydration;
- возможен ли streaming.

Серверный рендеринг полезен, когда:

- содержимое должно появиться до загрузки client JavaScript;
- важна поисковая индексация;
- данные удобно получать рядом с backend;
- сервер может безопасно читать server-only credentials.

Клиентский код необходим, когда используются:

- события пользователя;
- local state;
- browser APIs;
- эффекты;
- интерактивные библиотеки.

Выбор делают не для всего приложения сразу, а по границам:

```text
server-rendered page
└── client interactive filters
    └── client modal
```

В Next.js директиву:

```ts
"use client";
```

ставят на границе интерактивного клиентского поддерева, а не автоматически в каждом файле.

Данные, передаваемые из server component в client component, должны быть сериализуемыми и не содержать secrets.

Нужно избегать request waterfall:

```text
страница получила пользователя
→ компонент получил профиль
→ дочерний компонент получил настройки
```

если независимые запросы можно начать параллельно:

```text
user request ─────┐
profile request ──┼→ render
settings request ─┘
```

Последовательность оставляют только там, где следующий запрос действительно зависит от результата предыдущего.

Полный дизайн включает **состояния загрузки и ошибок**.

Для чтения различают:

- initial loading;
- данные получены;
- empty state;
- background refresh;
- stale data;
- partial data;
- recoverable error;
- access denied;
- offline.

Initial loading означает, что данных ещё нет.

Background refresh означает, что старые данные уже показываются, а новое значение загружается:

```text
данные видны
+
неблокирующий индикатор обновления
```

Не нужно заменять весь интерфейс spinner при каждом refetch, если предыдущие данные остаются пригодными.

Stale data можно показать, если это допустимо бизнес-правилами.

Например:

```text
Показаны данные на 10:42.
Не удалось обновить.
```

Для критичных финансовых или permission-данных устаревший ответ может быть недопустим.

При частичном сбое не всегда нужно скрывать весь экран.

Например:

```text
основная таблица загрузилась
+
блок рекомендаций завершился ошибкой
```

можно показать таблицу и локальную ошибку дополнительного блока.

Для mutation учитывают:

- pending;
- success;
- validation error;
- conflict;
- timeout;
- повторную отправку;
- optimistic update;
- rollback.

Оптимистическое обновление подходит, когда:

- вероятность успеха высока;
- изменение легко откатить;
- пользователь выигрывает от мгновенной реакции;
- конфликт можно корректно обработать.

Например, optimistic toggle обычно проще, чем создание платежа.

Если ответ запроса больше не нужен после ухода пользователя или изменения параметров, его можно отменить через механизм query library или `AbortController`.

Отмена уменьшает лишнюю работу и риск применения устаревшего результата, но не заменяет проверку актуальности ответа.

При быстро меняющихся параметрах возможна гонка:

```text
запрос A начался раньше
→ запрос B начался позже
→ B завершился
→ A завершился после B
```

Система должна не позволить старому ответу A перезаписать результат B.

Query libraries обычно решают часть этой задачи через ключи запросов и lifecycle подписок.

Отдельно проектируют **доступность**.

Нужно учитывать:

- семантические HTML-элементы;
- управление с клавиатуры;
- видимый focus;
- корректные labels;
- связь ошибки с полем;
- focus management в modal;
- доступные loading и status messages;
- достаточный контраст;
- работу при увеличении текста.

Например, после открытия modal focus должен перейти внутрь, а после закрытия вернуться на элемент, который её открыл.

Ошибка формы должна быть не только красной рамкой, но и текстом, связанным с полем.

Безопасность рассматривают на этапе проектирования, а не после реализации.

Нужно определить:

- какие данные являются чувствительными;
- какие роли имеют доступ;
- где проверяется авторизация;
- можно ли доверять параметрам URL;
- какой пользовательский ввод отображается;
- как работает authentication;
- используются ли cookies;
- есть ли риск CSRF;
- подключаются ли сторонние scripts.

Frontend может скрыть кнопку:

```tsx
{canDelete && (
  <DeleteButton />
)}
```

но backend всё равно обязан проверить право на удаление.

Клиентская проверка улучшает UX, а не создаёт границу безопасности.

Пользовательские строки нельзя без необходимости вставлять через:

```text
innerHTML
dangerouslySetInnerHTML
```

Если HTML действительно нужен, должен быть определён доверенный источник и sanitization.

Параметры redirect и внешние URL проверяют по allowlist, чтобы не создать open redirect или отправку данных на неожиданный origin.

В logs, analytics и error tracking не передают без необходимости:

- tokens;
- cookies;
- пароли;
- содержимое форм;
- персональные данные;
- полный URL с чувствительными query-параметрами.

Производительность рассматривают через измеряемые ограничения.

Полезно определить бюджет:

- размер initial JavaScript;
- число критических запросов;
- объём ответа;
- время первого содержимого;
- задержку взаимодействия;
- максимальный размер списка;
- допустимую частоту обновлений.

После этого ищут предполагаемые узкие места:

```text
тяжёлая библиотека
последовательные запросы
большой список
дорогой render
частое вычисление
слишком большой response
layout shift
```

Решение выбирают под конкретную проблему:

- code splitting;
- prefetch;
- server pagination;
- cache;
- virtualization;
- Web Worker;
- уменьшение данных;
- перенос агрегации на сервер;
- lazy loading.

Например, виртуализация нужна не каждой таблице.

Если список содержит 30 строк, она только усложнит:

- accessibility;
- sticky elements;
- измерение высоты;
- тестирование.

Если отображаются десятки тысяч строк, виртуализация может стать необходимой.

`useMemo`, `useCallback` и `React.memo` также не добавляют автоматически.

Сначала подтверждают проблему через:

- React Profiler;
- Performance panel;
- network waterfall;
- bundle analyzer;
- RUM.

Затем измеряют результат оптимизации.

Тестовую стратегию строят по рискам feature.

**Unit tests** подходят для чистой бизнес-логики:

- преобразование DTO;
- расчёт прав;
- формирование параметров;
- валидация.

**Integration/component tests** проверяют взаимодействие UI, состояния и API:

- фильтр меняет запрос;
- ошибка показывает retry;
- mutation обновляет интерфейс;
- права скрывают недоступное действие.

**Contract tests** или проверяемая схема помогают обнаружить несовместимость API.

**End-to-end tests** покрывают несколько критичных пользовательских сценариев в окружении, близком к production:

```text
открыть экран
→ найти запись
→ выполнить действие
→ увидеть результат
```

Не нужно проверять каждый визуальный вариант только через E2E: такие тесты медленнее и сложнее диагностируются.

Для доступности полезны:

- автоматические проверки;
- keyboard test;
- ручная проверка focus;
- screen reader для критичных сценариев.

До релиза нужно определить **наблюдаемость**.

Технические события связывают с:

- environment;
- release;
- route pattern;
- feature flag variant;
- operation ID;
- request ID;
- типом ошибки;
- длительностью.

Продуктовые события показывают, достигает ли пользователь цели:

```text
открыл feature
применил фильтр
получил результат
завершил действие
```

Метрики выбирают до rollout.

Иначе после выпуска команда видит ошибки, но не понимает, помогла ли feature пользователю.

Рискованную функциональность выпускают постепенно.

Возможный процесс:

```text
feature выключена
→ включена для команды
→ 5% пользователей
→ 25%
→ 100%
```

Перед rollout определяют:

- технические метрики;
- продуктовую метрику;
- контрольную группу;
- минимальный объём данных;
- условие остановки;
- способ отключения;
- необходимость rollback.

Feature flag должен иметь владельца и срок удаления.

Иначе временные ветки остаются в коде и увеличивают число возможных состояний системы.

Feature flag не заменяет серверную авторизацию и не помогает, если приложение падает до его загрузки.

После релиза проверяют:

- error rate;
- успешность сценария;
- performance;
- обращения пользователей;
- неожиданные сегменты;
- корректность feature flag;
- отсутствие роста API-ошибок.

Релиз не завершает проектирование: production-данные проверяют исходные предположения.

Если результат отличается от ожиданий, команда:

- исправляет feature;
- меняет UX;
- ограничивает rollout;
- откатывает изменение;
- пересматривает требования.

Результат проектирования — не обязательно большая диаграмма.

Для обычной feature достаточно зафиксировать:

```text
1. Цель и scope.
2. Основные сценарии.
3. Контракт API.
4. Источники состояния.
5. Границы компонентов.
6. Поток данных.
7. Ошибки и права.
8. Риски.
9. Проверки.
10. План rollout.
```

Для сложного взаимодействия полезна sequence diagram:

```text
User
→ UI
→ API
→ Service
→ UI update
```

ADR, или Architecture Decision Record, нужен для значимого решения с долгосрочными последствиями:

- выбор способа realtime-связи;
- изменение общего API-контракта;
- новая стратегия рендеринга;
- новая модель хранения данных.

ADR фиксирует:

```text
контекст
варианты
решение
последствия
```

Для локального состояния кнопки отдельный ADR не нужен.

Главный принцип — достаточная архитектура под известные требования.

Нужно оставить понятные точки расширения, но не проектировать заранее все гипотетические варианты.

Хорошее решение:

- выполняет текущий сценарий;
- имеет ясные границы;
- допускает проверяемые изменения;
- не дублирует источники истины;
- наблюдается в production;
- может быть безопасно отключено или заменено.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>С чего начать проектирование?</strong></summary>

<dl>
<dd>
<h2></h2>

С цели и границ задачи.

Нужно выяснить:

- кто пользователь;
- какую проблему он решает;
- какой путь является критичным;
- как измеряется успех;
- какие роли участвуют;
- что входит в первую версию;
- что явно не входит.

Затем уточняют ограничения:

- объём данных;
- частоту обновления;
- допустимую задержку;
- браузеры;
- устройства;
- права;
- доступность;
- SEO;
- плохую сеть;
- срок выпуска.

Только после этого сравнивают технические варианты.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как декомпозировать реализацию большой фичи?</strong></summary>

<dl>
<dd>
<h2></h2>

Лучше идти вертикальными пользовательскими срезами, каждый из которых даёт работающий результат.

Например:

```text
1. Получить и показать данные.
2. Добавить фильтрацию через URL.
3. Добавить изменение записи.
4. Добавить права.
5. Добавить ошибки и восстановление.
6. Добавить rollout и метрики.
```

Отдельно фиксируют зависимости:

```text
API contract
→ query layer
→ UI

feature flag
→ rollout

analytics schema
→ production monitoring
```

Сначала полезно проверить самый рискованный контракт или сценарий, а не начинать с универсального design system для будущих экранов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие состояния интерфейса нужно учитывать?</strong></summary>

<dl>
<dd>
<h2></h2>

Для чтения обычно рассматривают:

- initial loading;
- успешные данные;
- empty state;
- background refresh;
- stale data;
- partial data;
- recoverable error;
- access denied;
- offline.

Для изменения добавляются:

- pending;
- success;
- server validation;
- conflict;
- timeout;
- повторная отправка;
- optimistic state;
- rollback.

Каждое состояние должно объяснять:

```text
что произошло
сохранены ли данные
что пользователь может сделать дальше
```

Необязательно показывать отдельный полноэкранный UI для каждого состояния. Ошибка дополнительного блока может оставаться локальной, не скрывая остальную страницу.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выбрать место для состояния?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно спросить:

```text
Кто является источником актуального значения?
Кому оно нужно?
Должно ли оно переживать reload?
Можно ли поделиться им ссылкой?
```

Параметры навигации и представления хранят в URL.

Временное состояние одного участка — в ближайшем компоненте.

Form state — рядом с формой.

Данные удалённого источника — в query cache.

Общее клиентское состояние — в global store, только если у него действительно несколько независимых потребителей.

Persistent draft — в IndexedDB или на сервере, если он должен переживать закрытие страницы.

Дублирование одного значения в нескольких местах требует явной синхронизации и часто указывает на неправильно выбранную границу.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как определить источник истины?</strong></summary>

<dl>
<dd>
<h2></h2>

Источник истины — место, которое определяет актуальное значение.

Например:

```text
текущая страница таблицы
→ URL

данные заказа
→ backend и query cache

открыта ли локальная подсказка
→ component state
```

Остальные представления должны либо вычисляться из источника, либо быть контролируемыми копиями с понятным lifecycle.

Например, форма создаёт локальный draft из серверных данных, но после сохранения должна:

- обновить query cache;
- получить актуальный ответ;
- обработать конфликт;
- сбросить или синхронизировать draft.

Наличие нескольких независимых записываемых копий одного значения почти всегда приводит к рассинхронизации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что нужно согласовать с серверной командой до реализации?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно согласовать:

- сущности и операции;
- идентификаторы;
- обязательные поля;
- поля с `null`;
- форматы дат и чисел;
- пагинацию;
- сортировку;
- фильтрацию;
- права;
- коды и структуру ошибок;
- rate limits;
- отмену;
- идемпотентность;
- конкурентные изменения.

Контракт фиксируют в OpenAPI или другом проверяемом формате.

Сетевую DTO-модель при необходимости преобразуют в frontend-модель на границе API.

Для breaking change заранее определяют переходный период, в течение которого backend поддерживает старый и новый frontend.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выбрать между серверным и клиентским рендерингом?</strong></summary>

<dl>
<dd>
<h2></h2>

Серверный рендеринг полезен для:

- быстрого первого содержимого;
- SEO;
- server-only доступа к данным;
- получения данных рядом с backend.

Клиентский рендеринг нужен для:

- событий пользователя;
- local state;
- browser APIs;
- интерактивных компонентов;
- обновлений после загрузки.

Выбор делают по частям страницы, а не одним переключателем для всего приложения.

Дополнительно учитывают:

- кэширование;
- персонализацию;
- стоимость hydration;
- streaming;
- request waterfalls;
- сериализуемость данных;
- риск рассинхронизации server и client output.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие требования безопасности учитывать при проектировании фичи?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно определить:

- какие данные чувствительны;
- кто имеет право выполнять операцию;
- где проверяется авторизация;
- отображается ли пользовательский HTML;
- используются ли cookies;
- возможен ли CSRF;
- есть ли внешние redirect URL;
- какие данные попадут в logs и analytics.

Frontend-проверка права улучшает UX, но backend обязан проверить действие повторно.

Пользовательский ввод не вставляют через `innerHTML` без безопасной обработки.

Токены, cookies, пароли и персональные поля не отправляют в error tracking без отдельной необходимости и политики обработки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что входит в технические риски?</strong></summary>

<dl>
<dd>
<h2></h2>

Примеры рисков:

- неизвестный контракт API;
- непривычный объём данных;
- сторонний SDK;
- миграция старого состояния;
- сложная модель прав;
- realtime-синхронизация;
- неподтверждённая поддержка браузера;
- невозможность безопасного rollback;
- слишком большой bundle;
- конфликт нескольких открытых вкладок.

Риск описывают через:

```text
условие
→ возможное влияние
→ способ проверки
→ план снижения
```

Если ключевое неизвестное нельзя снять обсуждением, проводят spike — ограниченное по времени исследование с заранее заданным вопросом и результатом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как учитывать производительность до реализации?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала задают бюджет или ожидаемое ограничение:

- initial JavaScript;
- объём ответа;
- число запросов;
- максимальный размер списка;
- частоту обновлений;
- Web Vitals;
- допустимое время реакции.

Затем проверяют вероятные узкие места:

- request waterfall;
- тяжёлая библиотека;
- длинный список;
- дорогое вычисление;
- частые renders;
- большой response.

Оптимизацию выбирают под подтверждённый риск и после реализации проверяют:

- профилировщиком;
- network waterfall;
- bundle analyzer;
- RUM.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выбрать тестовую стратегию для фичи?</strong></summary>

<dl>
<dd>
<h2></h2>

Тесты выбирают по рискам.

Unit tests подходят для:

- mapping;
- валидации;
- расчётов;
- permission logic.

Integration tests проверяют:

- загрузку данных;
- фильтрацию;
- ошибки;
- mutations;
- обновление UI.

Contract tests защищают границу frontend и API.

End-to-end tests оставляют для нескольких критичных пользовательских сценариев.

Дополнительно проверяют:

- keyboard navigation;
- focus;
- доступные labels;
- основные responsive-состояния;
- production build.

Цель — не максимальное количество тестов, а быстрое обнаружение наиболее дорогих ошибок.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как не переусложнить архитектуру?</strong></summary>

<dl>
<dd>
<h2></h2>

Каждая абстракция должна решать текущую повторяющуюся проблему или изолировать известный риск.

Не следует заранее добавлять:

- глобальное хранилище для локального state;
- универсальный event bus;
- plugin-систему для одного сценария;
- repository layer без нескольких источников данных;
- отдельный design-system-компонент для единичного UI;
- memoization без измеренной проблемы.

Полезный вопрос:

```text
Какое конкретное изменение станет проще благодаря этой абстракции?
```

Если ответа нет, решение можно оставить локальным и вынести позже, когда появится реальное повторение.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие документы или схемы нужны после проектирования?</strong></summary>

<dl>
<dd>
<h2></h2>

Для обычной feature достаточно коротко зафиксировать:

- цель;
- scope;
- основной сценарий;
- контракт;
- состояние;
- поток данных;
- риски;
- тесты;
- rollout.

Sequence diagram полезна для сложного взаимодействия нескольких систем.

ADR нужен для решения с долгосрочными архитектурными последствиями.

Диаграмма не является самоцелью. Она должна помогать команде понять границы, последовательность и компромиссы, а не просто украшать документ.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что нужно подготовить для безопасного постепенного выпуска (<code>rollout</code>)?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужны:

- feature flag;
- release ID;
- технические метрики;
- продуктовая метрика;
- контрольная группа;
- минимальный объём данных;
- условие остановки;
- способ быстрого отключения;
- план rollback.

Выпуск расширяют постепенно:

```text
internal
→ 5%
→ 25%
→ 100%
```

Наличие feature flag без наблюдения за результатом не делает rollout безопасным.

Flag должен иметь владельца и срок удаления после завершения выпуска.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как понять, что фича готова к релизу?</strong></summary>

<dl>
<dd>
<h2></h2>

Готовность означает проверяемое состояние результата.

Должны быть выполнены:

- acceptance criteria;
- Definition of Done;
- критичные сценарии;
- production build;
- CI-проверки;
- обработка ошибок;
- права;
- accessibility;
- security requirements;
- observability;
- release metadata.

Для рискованной фичи дополнительно готовы:

- feature flag;
- rollout plan;
- stop conditions;
- smoke test;
- rollback или kill switch.

Завершение написания кода само по себе не означает готовность к production.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Решение | Пример вопроса |
| --- | --- |
| Требования | Какой пользовательский сценарий критичен и что не входит в первую версию? |
| Декомпозиция | Какой минимальный вертикальный срез первым проверит контракт? |
| Данные | Кто является источником истины и как обнаруживается конфликт обновления? |
| Состояние | Должно ли значение жить в URL, query cache или локальном компоненте? |
| Рендеринг | Какая часть должна появиться с сервера, а где нужна интерактивность? |
| Надёжность | Что увидит пользователь при частичном сбое или потере сети? |
| Безопасность | Где проверяются права и какие данные нельзя передавать клиенту? |
| Производительность | Какой бюджет задан и какое узкое место предполагается? |
| Тестирование | Какой самый дорогой сбой должен остановить CI? |
| Выпуск | По каким метрикам расширять rollout и когда отключать фичу? |
| Наблюдаемость | Как связать ошибку с release, flag и запросом? |
