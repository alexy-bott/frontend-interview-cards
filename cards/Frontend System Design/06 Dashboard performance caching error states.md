## Вопрос

<br>

 💬 **Как спроектировать dashboard с несколькими виджетами, API-запросами, кэшированием и состояниями ошибок?**

<h2></h2>

<br>
<dl>
<dd>

Сначала уточняют назначение dashboard, или информационной панели: кто его использует, какие решения принимает, какие виджеты критичны, общий ли у них временной диапазон, насколько свежими должны быть данные и можно ли показывать частичный результат. Также важны права, tenant - организация или аккаунт в многопользовательской системе, - часовой пояс, экспорт, автообновление и ожидаемый объём точек в графиках.

Dashboard разбивают на оболочку и виджеты с явными входными параметрами. Общие фильтры и временной диапазон хранят в URL или на уровне страницы, а локальное состояние раскрытия и вида графика - внутри виджета. Один источник данных не обязательно означает один компонент: разные части могут читать общий кэш с одинаковым ключом, не дублируя запрос.

Стратегию API выбирают по зависимостям. Независимые запросы запускают параллельно. Агрегирующая операция API или BFF (`Backend for Frontend`) полезны, если экран иначе делает десятки сетевых переходов, сервер может эффективнее объединить вычисления или данные должны соответствовать одному моменту времени. Но один огромный ответ связывает жизненный цикл виджетов и превращает частичную ошибку в общий сбой, поэтому границу выбирают по требованиям, а не по числу карточек.

Ключ кэша включает все параметры результата: тип виджета, фильтры, временной диапазон, часовой пояс, пользователя или tenant. Для каждого запроса задают, сколько данные считаются свежими, когда обновляются в фоне и можно ли оставить предыдущий результат. При смене фильтра старые ответы отменяют или игнорируют, чтобы поздний ответ не вернул dashboard к прежнему состоянию.

Сбой одного необязательного виджета не должен убирать остальные. Для каждого участка нужны первичная загрузка, данные, пустой результат, ошибка, фоновое обновление, устаревшие и частичные данные. Если сохранён старый результат, показывают время последнего успешного обновления и отдельную кнопку повторного запроса. Общая ошибка страницы нужна только тогда, когда без базовых данных сценарий действительно невозможен.

В Next.js оболочку и доступные на сервере данные можно отрендерить до отправки страницы, а независимые участки передавать потоком. Интерактивные графики остаются клиентскими компонентами. Границы `Suspense`, показывающие временное содержимое (`fallback`) до готовности основного, и границы ошибок располагают по пользовательским блокам, чтобы медленный или упавший виджет не задерживал весь экран. Серверные данные не запрашивают повторно на клиенте без необходимости.

Производительность зависит от размера начальной JavaScript-сборки (`bundle`), числа запросов, объёма ответа, тяжёлых библиотек графиков и работы главного потока. Графики загружают по необходимости, данные агрегируют или прореживают на сервере, дорогие клиентские вычисления при необходимости переносят в Web Worker - отдельный поток для JavaScript-вычислений. Для таблиц применяют пагинацию или виртуализацию, для графиков ограничивают число точек и частоту перерисовки. Skeleton - каркас загрузки - сохраняет размеры виджета, чтобы не возникал layout shift, то есть сдвиг уже показанного содержимого.

Наблюдаемость строят по виджетам и запросам: время загрузки, частота ошибок, доля устаревших данных, размер ответа и длительные задачи главного потока браузера (`main thread`). В лог передают безопасный идентификатор операции и название виджета, но не персональные данные. Это позволяет отличить медленный общий API от тяжёлого рендера одного графика.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Как избежать последовательной цепочки запросов (<code>request waterfall</code>)?</strong></summary>

<dl>
<dd>
<h2></h2>

Независимые данные запрашивают параллельно, а необходимые параметры получают до рендера дочернего компонента. Помогают серверная агрегация, предварительная загрузка и общий кэш. Запрос оставляют последовательным только тогда, когда ему действительно нужен результат предыдущего; в остальных случаях цепочка лишь увеличивает общее время ожидания.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужна общая операция API для dashboard, а когда отдельные запросы виджетов?</strong></summary>

<dl>
<dd>
<h2></h2>

Общая операция API уменьшает сетевые переходы и может вернуть согласованный snapshot - снимок данных на одной версии, - но связывает скорость, кэш и ошибки всех виджетов. Отдельные запросы позволяют независимо загружать, обновлять и повторять части экрана, но создают больше соединений и могут показать данные разных моментов времени. Частый компромисс - BFF с несколькими логическими ресурсами или агрегирующий запрос только для критичного первого экрана.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать при сбое одного из виджетов?</strong></summary>

<dl>
<dd>
<h2></h2>

Изолировать ошибку в границе виджета, оставить работающие части и предложить повтор именно упавшего запроса. Если предыдущие данные ещё полезны, их сохраняют с отметкой времени и сообщением об ошибке обновления. Общий экран ошибки показывают только при сбое обязательной основы, например списка доступных tenant или общего контекста прав.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как кэшировать данные dashboard?</strong></summary>

<dl>
<dd>
<h2></h2>

Ключ кэша включает все параметры, меняющие ответ: пользователя или tenant, фильтры, временной диапазон, часовой пояс и детализацию. Для каждого ресурса задают срок свежести, способ инвалидировать устаревший кэш, обновление при фокусе, периодические запросы (`polling`) и ручное обновление. В RTK Query для этого используют теги, `refetchOnFocus`, `refetchOnMountOrArgChange`, `pollingInterval` и явный повтор запроса в зависимости от сценария. Персональные ответы нельзя переиспользовать между пользователями, а данные с разной валютой или часовым поясом не должны случайно иметь общий ключ.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как показать, что несколько виджетов относятся к одному моменту времени?</strong></summary>

<dl>
<dd>
<h2></h2>

Сервер может вернуть общий `asOf` или версию snapshot для агрегированного ответа. При независимых запросах страница фиксирует временной диапазон и показывает время последнего обновления каждого виджета; если строгая согласованность обязательна, запросы получают общий идентификатор snapshot. Нельзя просто подписать весь dashboard одним временем, если части фактически обновились в разные моменты.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему библиотеки графиков могут ухудшать производительность?</strong></summary>

<dl>
<dd>
<h2></h2>

Библиотека может заметно увеличить начальный bundle, создать много DOM/SVG-узлов и выполнять агрегацию на главном потоке. График загружают только при необходимости, данные агрегируют или прореживают на сервере, вычисления переносят в Web Worker, а для большого числа точек рассматривают Canvas или WebGL. Решение подтверждают размером загружаемой части сборки (`chunk`) и профилированием, а не названием библиотеки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие состояния должен иметь виджет?</strong></summary>

<dl>
<dd>
<h2></h2>

Как минимум первичная загрузка, данные, пустой результат и ошибка. По сценарию добавляются фоновое обновление, устаревшие или частичные данные, отсутствие права и потеря соединения реального времени. Состояния не сводятся к спиннеру: пользователь должен видеть, есть ли пригодные данные, насколько они свежие и что можно сделать дальше.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как серверный рендеринг и потоковая передача помогают dashboard в Next.js?</strong></summary>

<dl>
<dd>
<h2></h2>

SSR может раньше вернуть оболочку, заголовки и критичные данные, не ожидая клиентского JavaScript. Потоковая передача (`streaming`) позволяет отправлять независимые части по мере готовности через границы Suspense. Это не отменяет клиентские запросы для интерактивного автообновления. Важно не создать двойную загрузку и передавать одинаковый контекст прав, фильтров и кэша серверной и клиентской части.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что тестировать и измерять?</strong></summary>

<dl>
<dd>
<h2></h2>

Критичный пользовательский путь, независимую загрузку и ошибку каждого виджета, частичный сбой, смену фильтра с поздним старым ответом, права и ручной повтор запроса. Измеряют Web Vitals - метрики скорости загрузки, отзывчивости и визуальной стабильности, - время до полезных данных, длительные задачи главного потока, размер лениво загружаемых частей сборки, число и длительность запросов. Отдельно проверяют клавиатурное управление графиками и таблицами и читаемую альтернативу визуальным данным.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Ключевое решение |
| --- | --- |
| Операционный dashboard | Свежесть и время последнего обновления каждого виджета |
| Финансовый отчёт | Общая версия snapshot и строгая согласованность |
| Один API недоступен | Изолированная ошибка и предыдущие данные виджета |
| Тяжёлый график во второй вкладке | Ленивая загрузка (`lazy loading`) и серверная агрегация |
| Разные права пользователей | Ключ кэша с tenant и серверная авторизация каждого ресурса |
