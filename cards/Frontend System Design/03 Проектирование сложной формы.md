## Вопрос

<br>

 💬 **Как спроектировать сложную форму с асинхронной валидацией и серверными ошибками?**

<h2></h2>

<br>
<dl>
<dd>

Сначала уточняют сценарий формы:

- создание или редактирование;
- количество и типы полей;
- условные поля;
- динамические списки;
- несколько шагов;
- загрузка файлов;
- автосохранение;
- роли и права;
- возможность параллельного редактирования;
- требования к восстановлению черновика;
- критичность повторной отправки.

Например, форма изменения профиля, создание заказа и платёжная форма требуют разных решений по валидации, повторной отправке и сохранению состояния.

Дальше разделяют несколько моделей данных:

```text
DOM values
→ form values
→ submit DTO
→ server response
```

**DOM values** — значения элементов ввода.

Даже поле:

```html
<input type="number">
```

обычно предоставляет строковое значение, пока приложение явно не выполнило преобразование.

**Form values** — модель, удобная для редактирования:

```ts
type FormValues = {
  name: string;
  birthday: string;
  country: CountryOption | null;
  addresses: AddressFormValue[];
};
```

**Submit DTO** — формат API:

```ts
type UpdateUserDto = {
  name: string;
  birthday: string | null;
  countryCode: string | null;
  addresses: {
    id?: string;
    city: string;
  }[];
};
```

**Server response** — подтверждённое сервером состояние:

```ts
type UserDto = {
  id: string;
  version: number;
  name: string;
  birthday: string | null;
  countryCode: string | null;
};
```

Эти модели не обязаны совпадать.

Например, составной `Select` может хранить объект:

```ts
{
  label: "Россия",
  value: "RU"
}
```

а API ожидает только:

```text
"RU"
```

Файл в форме может быть объектом `File`, тогда как DTO содержит идентификатор уже загруженного файла.

Поэтому перед отправкой выполняют явное преобразование:

```text
form values
→ normalize
→ validate
→ map to DTO
→ send
```

Не следует незаметно смешивать отображаемые значения, сетевой контракт и подтверждённую серверную модель.

Валидацию разделяют по уровням.

```text
1. Нативные ограничения браузера.
2. Синхронная клиентская схема.
3. Асинхронная предварительная проверка.
4. Окончательная серверная валидация.
```

**Нативная валидация** помогает с базовой семантикой:

```html
<input
  type="email"
  required
  maxlength="100"
>
```

Она полезна для браузера и вспомогательных технологий, но не заменяет остальные проверки.

**Синхронная клиентская валидация** проверяет то, что уже известно браузеру:

- обязательность;
- формат;
- минимальную и максимальную длину;
- диапазон;
- связи между полями;
- допустимый тип файла;
- локальные бизнес-ограничения.

Например:

```text
дата окончания не раньше даты начала
пароль и подтверждение совпадают
при выбранной доставке адрес обязателен
```

Клиентская схема быстро даёт обратную связь, но не является границей безопасности.

**Асинхронная валидация** обращается к внешнему источнику:

- доступно ли имя;
- существует ли промокод;
- допустим ли адрес;
- можно ли использовать выбранную дату;
- не занят ли временной слот.

Такая проверка является предварительной.

Даже успешный ответ:

```text
email свободен
```

не гарантирует, что значение останется свободным до окончательной отправки.

Между проверкой и submit другой пользователь может занять его.

Поэтому сервер при сохранении повторно проверяет:

- формат;
- права;
- бизнес-правила;
- уникальность;
- лимиты;
- актуальное состояние данных.

Клиентскую проверку можно изменить, отключить или полностью обойти прямым HTTP-запросом.

Для async validation выбирают момент запуска.

Частые варианты:

```text
onBlur
```

или:

```text
debounce после ввода
```

`onBlur` подходит, если проверка не обязана выполняться на каждый введённый символ.

Debounce подходит для сценария, где пользователь ожидает быструю реакцию во время ввода:

```text
ввод
→ короткая пауза
→ запрос
```

Перед запросом значение нормализуют.

Например, email можно привести к согласованному виду:

```text
trim
→ при необходимости нормализация регистра
→ проверка формата
→ async request
```

Нет смысла отправлять запрос, если синхронная проверка уже обнаружила неправильный формат.

У поля полезно иметь отдельное состояние:

```text
idle
checking
valid
invalid
unavailable
```

Например:

```text
Проверяем доступность имени…
Имя доступно
Имя уже занято
Не удалось выполнить проверку
```

Сетевая ошибка проверки не всегда означает, что значение невалидно.

Иногда правильнее показать:

```text
Не удалось проверить значение.
Окончательная проверка будет выполнена при сохранении.
```

Поведение зависит от критичности операции.

При async validation возможна гонка:

```text
запрос A для "alex"
→ запрос B для "alexander"
→ B завершился первым
→ A завершился позже
```

Старый ответ A не должен изменить состояние текущего значения `alexander`.

Для защиты используют:

- `AbortController`;
- последовательный идентификатор проверки;
- сравнение проверенного значения с текущим;
- query key;
- игнорирование устаревшего результата.

Упрощённый алгоритм:

```text
1. Запомнить проверяемое значение.
2. Отменить предыдущий запрос.
3. Запустить новую проверку.
4. Получить ответ.
5. Сравнить значение ответа с текущим значением поля.
6. Применить результат только при совпадении.
```

Debounce уменьшает количество запросов, но сам по себе не гарантирует правильный порядок ответов.

Результат async validation можно ненадолго кэшировать по нормализованному значению:

```text
"alex" → занято
```

Это уменьшает повторные запросы при возврате к тому же значению.

Но такой cache является только оптимизацией. Он не заменяет серверную проверку при submit и должен иметь ограниченный срок жизни.

Состояния формы можно представить как переходы:

```text
idle
→ validating
→ submitting
→ success
```

или:

```text
idle
→ validating
→ submitting
→ server error
→ editing
```

Нужно различать:

- поле проверяется асинхронно;
- вся форма валидируется;
- запрос сохранения выполняется;
- данные успешно сохранены;
- сервер отклонил значения;
- произошла сетевая ошибка;
- возник конфликт версии.

Контракт серверных ошибок должен быть стабильным и машинно читаемым.

Например:

```json
{
  "code": "VALIDATION_FAILED",
  "fieldErrors": [
    {
      "field": "user.email",
      "code": "EMAIL_TAKEN",
      "params": {}
    }
  ]
}
```

Для общей ошибки:

```json
{
  "code": "ORDER_LIMIT_EXCEEDED",
  "params": {
    "limit": 10
  }
}
```

Полезные части ошибки:

- стабильный `code`;
- необязательный путь поля;
- безопасные параметры;
- request или correlation ID;
- необязательный общий код операции.

Не следует строить клиентскую логику по тексту:

```text
"Email already exists"
```

Текст может измениться из-за локализации или редактирования сообщения.

Клиентский адаптер преобразует серверный контракт в ошибки формы:

```text
server field path
→ form field name
→ локализованное сообщение
```

Например:

```text
user.email
→ email
```

или:

```text
addresses[2].city
→ addresses.2.city
```

Серверные ошибки разделяют по уровню.

**Field error** относится к конкретному полю:

```text
email уже занят
дата недоступна
значение слишком велико
```

Её показывают рядом с полем.

**Form error** относится ко всей операции:

```text
невозможно создать заказ
лимит операций превышен
выбранные параметры несовместимы
```

Её показывают в постоянной области формы или error summary.

**Conflict error** означает, что данные изменились после открытия формы:

```text
409 Conflict
```

Пользователю предлагают получить новую версию, сравнить изменения или повторить действие после обновления.

**Authentication error** означает, что сессия отсутствует или истекла.

**Authorization error** означает, что пользователь больше не имеет права выполнить операцию.

**Network error** означает, что клиент не получил подтверждённый серверный результат.

При timeout нельзя автоматически утверждать, что операция не выполнилась. Сервер мог сохранить данные, но ответ не дошёл до клиента.

**Unexpected error** — необработанный серверный или инфраструктурный сбой.

Пользователю показывают безопасное сообщение и при возможности request ID, а технические детали отправляют в observability.

Сообщение сервера нельзя безусловно выводить пользователю.

Оно может:

- быть техническим;
- не соответствовать локали;
- раскрывать внутренние детали;
- содержать небезопасные данные;
- быть непредсказуемым.

Лучше сопоставлять стабильные коды с контролируемыми сообщениями интерфейса.

При серверной ошибке введённые значения не сбрасывают.

Пользователь должен исправить конкретную проблему, а не заполнять всю форму заново.

Server field error может устареть после изменения поля.

Например:

```text
email уже занят
→ пользователь изменил email
```

Старое сообщение больше не относится к новому значению.

Такую ошибку очищают при изменении соответствующего поля или перед новой проверкой.

Но нельзя безусловно очищать все серверные ошибки при любом вводе.

Например, общая ошибка может зависеть от сочетания нескольких полей:

```text
выбранный тариф недоступен в этом регионе
```

Нужно знать, какие поля делают ошибку устаревшей.

Жизненный цикл submit:

```text
1. Пользователь отправляет форму.
2. Выполняется клиентская валидация.
3. Координируются незавершённые async-проверки.
4. Значения преобразуются в DTO.
5. Форма переходит в submitting.
6. Выполняется запрос.
7. Ответ классифицируется.
8. Обновляется UI и server cache.
9. После успеха обновляется базовое состояние формы.
```

Во время отправки повторное действие обычно блокируют:

```text
button disabled
```

и показывают состояние:

```text
Сохраняем…
```

Но блокировка кнопки защищает только текущий интерфейс.

Повтор может прийти:

- из другой вкладки;
- после сетевого retry;
- из мобильного клиента;
- через повторный HTTP-запрос;
- после двойного нажатия до обновления UI.

Критичные операции сервер делает идемпотентными.

Например:

```http
Idempotency-Key: operation-uuid
```

Один ключ должен обозначать одну логическую операцию.

Повтор с тем же ключом не должен создать второй заказ или второй платёж.

После успешного submit серверный ответ становится подтверждённым состоянием.

Например:

```text
отправили name и email
→ сервер нормализовал значения
→ вернул новую version
→ ответ используется как актуальная модель
```

Дальше:

- обновляют query cache;
- инвалидируют связанные запросы;
- обновляют зависимые списки;
- сохраняют новый идентификатор или версию;
- делают сохранённые значения новой базой формы.

Для React Hook Form это часто выглядит концептуально так:

```ts
const savedValues =
  mapResponseToFormValues(response);

reset(savedValues);
```

После этого:

```text
isDirty = false
```

относительно новых сохранённых значений.

Не следует выполнять `reset()` без данных, если сервер мог:

- нормализовать строку;
- добавить идентификатор;
- изменить дату;
- применить значения по умолчанию;
- увеличить номер версии.

Подтверждённый server response надёжнее отправленного DTO.

React Hook Form позволяет сочетать uncontrolled и controlled поля.

Нативные элементы обычно подключают через:

```ts
register("email")
```

Это уменьшает необходимость хранить каждое нажатие клавиши в React state.

Составные controlled-компоненты подключают через:

```text
Controller
```

или:

```text
useController
```

Например:

- составной `Select`;
- Date Picker;
- компонент выбора файлов;
- UI-компонент с `value` и `onValueChange`;
- маскированное поле.

Поле нельзя одновременно подключать через `register` и `Controller`.

`Controller` уже предоставляет адаптер:

```text
value
onChange
onBlur
ref
name
```

Дополнительный `register` создаст две конкурирующие регистрации.

Подписки располагают как можно ближе к потребителю.

Если отдельному полю нужны:

- его значение;
- его ошибка;
- его состояние проверки,

необязательно подписывать на все изменения весь родительский компонент формы.

Для точечной подписки применяют возможности form library, например:

- `useController`;
- `useWatch`;
- отдельный компонент поля;
- подписку на нужную часть `formState`.

Это особенно важно для больших форм с десятками полей и составными компонентами.

Но оптимизацию подтверждают профилированием. Обычная форма из нескольких полей не требует сложной архитектуры подписок.

Начальные данные формы требуют отдельного решения.

Для создания сущности обычно известны статические начальные значения:

```ts
{
  name: "",
  email: ""
}
```

Для редактирования данные приходят асинхронно:

```text
открыть страницу
→ загрузить entity
→ преобразовать DTO
→ заполнить форму
```

Важно различать:

- первая загрузка;
- повторное получение тех же данных;
- фоновое обновление;
- изменение данных другим пользователем.

Нельзя безусловно выполнять:

```text
каждый новый server response
→ reset всей формы
```

Если пользователь уже начал ввод, это сотрёт локальные изменения.

Возможные стратегии:

- заполнить форму только после первой загрузки;
- не применять фоновое обновление к dirty-форме автоматически;
- обновить только неизменённые поля;
- показать уведомление о новой серверной версии;
- предложить перезагрузить или сравнить данные.

В React Hook Form для разных сценариев могут использоваться:

- `defaultValues`;
- асинхронные `defaultValues`;
- реактивные `values`;
- `reset`;
- опции сохранения dirty-полей.

Выбор зависит от того, должен ли внешний источник постоянно управлять формой или только установить её начальную базу.

Для редактирования полезно хранить серверную версию:

```text
version
updatedAt
ETag
```

При submit клиент передаёт ожидаемую версию:

```http
If-Match: "version-4"
```

Если сервер уже хранит другую версию, он возвращает конфликт.

Сценарий:

```text
пользователь A открыл version 4
пользователь B сохранил version 5
пользователь A отправил изменение version 4
→ 409 Conflict
```

Нельзя молча перезаписывать version 5.

Интерфейс может предложить:

- загрузить новую версию;
- сравнить значения;
- скопировать свой ввод;
- повторить изменение поверх актуальных данных;
- отменить редактирование.

Автоматическое слияние допустимо только для полей, где понятны правила конфликта.

Для динамических списков используют стабильные идентификаторы.

Например, в React Hook Form `useFieldArray` предоставляет служебный `field.id`, который используют как React key:

```tsx
fields.map((field, index) => (
  <AddressField
    key={field.id}
    index={index}
  />
))
```

Нельзя использовать только индекс как key, если строки можно добавлять, удалять или перемещать.

Иначе локальное состояние и ошибки могут перейти к другой строке.

Для существующих серверных элементов дополнительно сохраняют бизнес-идентификатор:

```text
addressId
```

Нужно различать:

```text
field.id
→ стабильность React-элемента формы

addressId
→ идентификатор сущности на сервере
```

Ошибки вложенных полей могут приходить по пути:

```text
addresses.2.city
```

Но индекс может измениться после reorder.

Для сложных динамических списков надёжнее, если серверная ошибка содержит идентификатор элемента:

```json
{
  "itemId": "address-42",
  "field": "city",
  "code": "CITY_NOT_SUPPORTED"
}
```

Клиент находит текущий индекс элемента и устанавливает ошибку правильному полю.

Для многошаговой формы определяют:

- какие данные принадлежат каждому шагу;
- можно ли переходить назад;
- что валидируется при переходе;
- когда выполняется окончательная проверка;
- где хранится черновик;
- как восстанавливается сессия;
- когда данные считаются сохранёнными.

Проверка текущего шага улучшает UX, но финальный submit должен проверить всю форму и актуальные серверные правила.

Черновик можно хранить:

- локально;
- в IndexedDB;
- на сервере;
- в отдельной draft-сущности.

Чувствительные данные нельзя бездумно сохранять в `localStorage`.

Серверный draft удобен, если пользователь должен:

- продолжить на другом устройстве;
- вернуться через несколько дней;
- совместно редактировать;
- загружать большие файлы.

Автосохранение — отдельный жизненный цикл, а не просто частый submit.

Упрощённо:

```text
изменение
→ debounce
→ autosave request
→ saved / error / conflict
```

При autosave возможны гонки:

```text
save A
→ save B
→ B завершился
→ A завершился позже
```

Старый ответ A не должен сделать новую версию устаревшей.

Используют:

- последовательную очередь;
- отмену ещё не отправленного сохранения;
- version;
- operation ID;
- игнорирование старого ответа;
- отправку только последнего snapshot.

Интерфейс показывает состояние:

```text
Есть несохранённые изменения
Сохраняем…
Сохранено
Не удалось сохранить
Возник конфликт
```

Autosave не всегда заменяет явную кнопку подтверждения.

Например, черновик заказа можно сохранять автоматически, но окончательное размещение заказа остаётся отдельной подтверждаемой операцией.

Загрузка файлов также имеет отдельный lifecycle.

Для небольшого файла возможна отправка вместе с формой.

Для больших файлов чаще используют:

```text
получить signed upload URL
→ загрузить файл
→ получить fileId
→ отправить form DTO с fileId
```

Форма должна учитывать:

- выбор файла;
- локальную проверку размера и типа;
- прогресс;
- отмену;
- retry;
- ошибку загрузки;
- удаление загруженного файла;
- финальное подтверждение file ID.

Клиентская проверка расширения и MIME нужна для UX, но сервер повторно проверяет:

- размер;
- тип;
- содержимое;
- права;
- вредоносные файлы;
- лимиты.

Нельзя доверять только:

```text
file.name
file.type
```

Если upload завершился, а submit формы не состоялся, серверу может понадобиться очистка временных файлов.

Для несохранённых изменений проектируют навигацию.

Внутри приложения можно показать подтверждение при попытке уйти с dirty-формы.

Для закрытия вкладки браузер предоставляет ограниченный механизм `beforeunload`.

Нельзя рассчитывать на собственный произвольный текст системного диалога: браузеры ограничивают его отображение.

Предупреждение включают только при реальных несохранённых изменениях и снимают после успешного сохранения.

Навигационный guard не должен блокировать переход после submit или программного redirect.

При сохранении draft локально нужно учитывать:

- чувствительность данных;
- срок хранения;
- очистку после успеха;
- версию схемы;
- шифрование на уровне платформы, если оно требуется;
- общий компьютер пользователя.

Доступность формы строится на нативной семантике:

```html
<form>
<label>
<input>
<button type="submit">
```

Каждое поле должно иметь доступное имя.

Ошибка связывается с полем:

```html
<input
  aria-invalid="true"
  aria-describedby="email-error"
>

<p id="email-error">
  Этот email уже используется.
</p>
```

Асинхронное состояние можно связать с тем же полем:

```text
Проверяем…
Имя доступно
```

Но не следует перемещать фокус при каждой ошибке, появившейся во время ввода или `blur`.

После неудачного submit можно:

- перевести фокус на первое ошибочное поле;
- либо на сводку ошибок.

Error summary должна быть доступна с клавиатуры и содержать ссылки на проблемные поля.

Например:

```text
Не удалось сохранить форму.
Исправьте 3 поля.
```

Форму или её секцию можно отмечать:

```text
aria-busy="true"
```

во время загрузки или отправки, если это помогает передать состояние вспомогательным технологиям.

Кнопка submit должна иметь понятное состояние:

```text
Сохранить
Сохраняем…
```

Отправка по Enter должна работать предсказуемо.

Не следует блокировать Enter глобально без необходимости: это нарушает нативное поведение формы и клавиатурную доступность.

Безопасность формы не ограничивается валидацией.

Сервер не должен доверять:

- скрытым полям;
- disabled-полям;
- role или user ID от клиента;
- рассчитанной клиентом цене;
- разрешению, проверенному только в UI.

Например:

```html
<input
  type="hidden"
  name="role"
  value="admin"
>
```

не делает значение доверенным.

Сервер получает роль из аутентифицированной сессии и повторно проверяет права.

Для cookie-authenticated mutation учитывают CSRF-защиту:

- `SameSite`;
- CSRF token;
- проверку origin;
- другие механизмы backend.

Пользовательский ввод не вставляют как HTML без безопасной обработки.

Серверные ошибки и введённые значения не логируют целиком без необходимости.

Особенно чувствительны:

- пароль;
- платёжные данные;
- документы;
- адрес;
- медицинская информация;
- токены;
- содержимое текстовых полей.

Асинхронная проверка существования пользователя может раскрывать данные.

Например:

```text
Такой email зарегистрирован.
```

на форме входа или восстановления пароля позволяет перебирать адреса.

В таких сценариях используют нейтральное сообщение:

```text
Если аккаунт существует, инструкция будет отправлена.
```

Сервер также применяет rate limit и мониторинг злоупотреблений.

Для observability формы полезно записывать:

- имя формы;
- release;
- тип операции;
- длительность;
- результат;
- стабильный error code;
- request ID;
- шаг многошаговой формы.

Не следует отправлять:

- значения полей;
- пароли;
- токены;
- содержимое файлов;
- полный server response;
- персональные данные без отдельной необходимости.

Тестовую стратегию строят по рискам.

Проверяют:

- обязательные поля;
- форматы;
- межполевые правила;
- преобразование form values в DTO;
- async validation;
- ответы async validation в обратном порядке;
- отмену проверки;
- field errors;
- form errors;
- сетевую ошибку;
- конфликт версии;
- double submit;
- idempotency;
- успешный `reset`;
- асинхронные initial values;
- сохранение dirty-полей;
- динамические списки;
- загрузку файлов;
- autosave;
- навигацию с несохранёнными изменениями;
- клавиатурную отправку;
- доступные имена и ошибки;
- положение фокуса после submit.

Практический порядок проектирования:

```text
1. Уточнить сценарии и критичность операции.
2. Разделить form model, DTO и server model.
3. Определить синхронные и серверные правила.
4. Спроектировать async validation и защиту от гонок.
5. Согласовать контракт server errors.
6. Описать submit lifecycle и идемпотентность.
7. Определить initial values и конфликт обновлений.
8. Спроектировать динамические поля, файлы и draft.
9. Проверить accessibility и security.
10. Добавить тесты и безопасную observability.
```

Главный принцип:

```text
клиентская валидация
→ быстрый UX

асинхронная предварительная проверка
→ ранняя обратная связь

серверная валидация
→ окончательное решение

server response
→ подтверждённое состояние
```

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Почему серверная валидация всё равно нужна?</strong></summary>

<dl>
<dd>
<h2></h2>

Клиентскую проверку можно изменить, отключить или полностью обойти прямым запросом к API.

Сервер обязан повторно проверить:

- формат;
- права;
- бизнес-правила;
- лимиты;
- уникальность;
- актуальное состояние данных.

Даже успешная предварительная проверка уникальности не гарантирует результат.

Сценарий:

```text
клиент проверил email
→ email свободен
→ другой запрос занял email
→ исходная форма отправлена
```

Сервер должен отклонить окончательный submit как конфликт или ошибку валидации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как избежать гонки запросов при асинхронной валидации?</strong></summary>

<dl>
<dd>
<h2></h2>

Пользователь может изменить значение до получения ответа.

Например:

```text
запрос A для "alex"
→ запрос B для "alexander"
→ B завершился первым
→ A завершился позже
```

Предыдущий запрос отменяют через `AbortController` либо помечают последовательным идентификатором.

Перед установкой результата сравнивают:

```text
проверенное значение
текущее значение поля
```

Ошибка применяется только при совпадении.

Debounce уменьшает число запросов, но сам по себе не гарантирует правильный порядок ответов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какой формат серверных ошибок удобен форме?</strong></summary>

<dl>
<dd>
<h2></h2>

Удобен стабильный машинный код, необязательный путь поля и безопасные параметры:

```json
{
  "code": "VALIDATION_FAILED",
  "fieldErrors": [
    {
      "field": "user.email",
      "code": "EMAIL_TAKEN",
      "params": {}
    }
  ]
}
```

Клиентский адаптер:

```text
сопоставляет server path с form field
→ выбирает локализованный текст
→ устанавливает ошибку
```

По тексту server message не следует строить программную логику.

Сообщение сервера нельзя безусловно показывать пользователю: оно может быть техническим, небезопасным или нелокализованным.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где показывать серверные ошибки?</strong></summary>

<dl>
<dd>
<h2></h2>

Field error показывают рядом с конкретным полем и связывают через:

```text
aria-describedby
aria-invalid
```

Form error размещают в постоянной области формы или сводке ошибок.

Сетевой сбой сообщает, что подтверждённый результат не получен, и при безопасной операции предлагает повтор.

Конфликт версии показывает отдельный сценарий разрешения конфликта.

Введённые значения при ошибке сохраняют.

После неудачной отправки фокус переводят на первое проблемное поле или error summary, но не перемещают его при каждой async-ошибке во время ввода.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда использовать управляемые (<code>controlled</code>) и неуправляемые (<code>uncontrolled</code>) поля?</strong></summary>

<dl>
<dd>
<h2></h2>

Нативное uncontrolled-поле хранит текущее значение в DOM и хорошо подключается через:

```ts
register("email")
```

Controlled-поле получает `value` из React и сообщает изменение через callback.

Оно нужно, когда составной компонент работает через:

```text
value
onChange
onValueChange
```

Например:

- сложный `Select`;
- Date Picker;
- autocomplete;
- маскированное поле;
- составной переключатель.

В React Hook Form controlled-компонент подключают через `Controller` или `useController`.

Поле не регистрируют второй раз через `register`, потому что `Controller` уже передаёт необходимые свойства.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как защитить форму от повторной отправки (<code>double submit</code>)?</strong></summary>

<dl>
<dd>
<h2></h2>

Пока запрос выполняется:

- submit блокируют;
- показывают pending-состояние;
- обработчик возвращает Promise запроса;
- повторный обработчик не запускают.

Но UI-защита не предотвращает повтор:

- из другой вкладки;
- после сетевого retry;
- через прямой API-запрос;
- до обновления состояния кнопки.

Критичные операции сервер делает идемпотентными.

Например, один `Idempotency-Key` должен соответствовать одной логической операции и возвращать тот же результат при повторе.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать, если серверные данные обновились во время редактирования?</strong></summary>

<dl>
<dd>
<h2></h2>

Нельзя молча выполнить полный `reset` и потерять пользовательский ввод.

Форма хранит версию:

```text
version
updatedAt
ETag
```

При сохранении сервер сравнивает её с актуальной.

Если данные изменились, сервер возвращает конфликт:

```text
409 Conflict
```

Пользователю предлагают:

- получить новую версию;
- сравнить изменения;
- сохранить свой ввод отдельно;
- повторить изменение поверх новой версии;
- отменить редактирование.

Неизменённые поля иногда можно обновить автоматически, но конфликтующие значения требуют явного решения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что тестировать у такой формы?</strong></summary>

<dl>
<dd>
<h2></h2>

Проверяют:

- основной сценарий;
- обязательность и формат;
- межполевые правила;
- преобразование в DTO;
- async validation;
- async-ответы в обратном порядке;
- field и form server errors;
- очистку устаревшей ошибки;
- network error;
- double submit;
- успешный reset;
- асинхронные исходные данные;
- конфликт версии;
- dynamic fields;
- file upload;
- autosave;
- unsaved changes;
- клавиатурную отправку;
- связь ошибок с полями;
- положение фокуса.

Критичные правила повторно проверяют на уровне API, потому что component test не доказывает корректность server validation.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем модель формы отличается от DTO запроса?</strong></summary>

<dl>
<dd>
<h2></h2>

Модель формы оптимизирована для редактирования.

Она может содержать:

- строки из input;
- объекты `Select`;
- `File`;
- временные поля;
- отдельные части составного значения;
- локальные идентификаторы строк.

DTO соответствует контракту API.

Например:

```text
CountryOption
→ countryCode

File
→ uploadedFileId

строка даты
→ ISO date или null
```

Перед submit выполняют явный mapping.

Это не позволяет UI-компонентам напрямую зависеть от случайного формата backend и упрощает изменение обеих сторон.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда очищать серверную ошибку поля?</strong></summary>

<dl>
<dd>
<h2></h2>

Если ошибка относится к конкретному значению, её очищают после изменения этого поля.

Например:

```text
email уже занят
→ email изменён
→ старая ошибка больше неактуальна
```

Затем поле может пройти новую async-проверку или окончательную проверку при submit.

Общую ошибку нельзя безусловно очищать при любом вводе.

Если она зависит от нескольких полей, нужно определить, какие именно изменения делают её устаревшей.

Независимые ошибки других полей сохраняют.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проектировать динамические списки полей?</strong></summary>

<dl>
<dd>
<h2></h2>

Каждая строка должна иметь стабильный key.

В `useFieldArray` для React key используют служебный:

```text
field.id
```

Серверный идентификатор сущности хранят отдельно.

Нельзя использовать только индекс, если строки можно:

- добавлять;
- удалять;
- менять местами.

Иначе значение, локальное состояние или ошибка могут перейти к другой строке.

Для server errors предпочтителен путь поля вместе со стабильным ID элемента. Клиент сопоставляет ID с текущим индексом формы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проектировать многошаговую форму и автосохранение?</strong></summary>

<dl>
<dd>
<h2></h2>

Для многошаговой формы определяют:

- данные каждого шага;
- возможность перехода назад;
- проверку текущего шага;
- финальную проверку всей формы;
- место хранения draft;
- срок жизни draft;
- восстановление сессии.

Autosave имеет собственные состояния:

```text
изменено
→ сохраняем
→ сохранено
→ ошибка
→ конфликт
```

Запросы autosave должны выполняться последовательно или защищаться версией, чтобы поздний старый ответ не перезаписал новый результат.

Автосохранение черновика не обязано означать окончательное подтверждение бизнес-операции.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проектировать загрузку файлов в форме?</strong></summary>

<dl>
<dd>
<h2></h2>

Для большого файла upload обычно отделяют от основного submit:

```text
выбрать файл
→ проверить базовые ограничения
→ получить signed URL
→ загрузить файл
→ получить fileId
→ отправить form DTO
```

Нужно предусмотреть:

- progress;
- cancellation;
- retry;
- удаление;
- ошибку;
- временные uploads;
- повторную server validation.

Клиентская проверка размера, расширения и MIME нужна только для UX.

Сервер повторно проверяет содержимое и права.

Если форма не была сохранена, временно загруженный файл должен очищаться по отдельной политике.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как предупреждать об уходе с несохранённой формы?</strong></summary>

<dl>
<dd>
<h2></h2>

Внутри приложения используют navigation guard, если форма действительно содержит несохранённые изменения.

Для закрытия вкладки можно подключить `beforeunload`, но браузер сам управляет текстом системного диалога.

После успешного сохранения предупреждение отключают.

Нельзя бесконечно блокировать навигацию после submit или программного redirect.

При локальном сохранении draft учитывают чувствительность данных и не помещают пароли или другие секретные значения в `localStorage`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как async validation может раскрывать существование пользователя?</strong></summary>

<dl>
<dd>
<h2></h2>

Сообщение:

```text
Такой email зарегистрирован.
```

позволяет автоматизированно проверять существование аккаунтов.

Особенно это опасно в:

- форме входа;
- восстановлении пароля;
- приглашениях;
- публичной регистрации.

Используют нейтральные ответы:

```text
Если аккаунт существует, инструкция будет отправлена.
```

Дополнительно сервер применяет rate limit, аудит и защиту от автоматического перебора.

## Где это встречается во frontend

| Сценарий | Ключевое решение |
| --- | --- |
| Регистрация | Гонка проверки email и повторная серверная проверка |
| Восстановление пароля | Нейтральный ответ без раскрытия существования аккаунта |
| Редактирование профиля | Асинхронные значения, `isDirty` и конфликт версии |
| Список адресов | `useFieldArray`, стабильные `id` и вложенные ошибки |
| Составной `Select` | `Controller` и явное преобразование в DTO |
| Многошаговая анкета | Server draft, проверка шагов и финальный submit |
| Автосохранение | Версия, последовательность запросов и статус сохранения |
| Загрузка файла | Отдельный upload lifecycle и server validation |
| Создание заказа | Блокировка UI и серверная идемпотентность |
| Несохранённые изменения | Navigation guard и ограниченный `beforeunload` |
