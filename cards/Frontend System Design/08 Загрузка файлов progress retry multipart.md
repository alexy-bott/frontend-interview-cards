## Вопрос

<br>

 💬 **Как спроектировать загрузку файлов с прогрессом, отменой, повтором и возобновлением?**

<h2></h2>

<br>
<dl>
<dd>

Сначала уточняют ограничения: число и максимальный размер файлов, разрешённые форматы, требования к приватности, допустима ли фоновая обработка после передачи, нужно ли возобновлять загрузку после перезагрузки страницы и как приложение должно работать при нестабильной сети. Для аватара размером в несколько мегабайт и для видео на несколько гигабайт нужны разные решения.

Небольшой файл можно отправить на сервер приложения одним запросом в формате `multipart/form-data`, который передаёт файл и дополнительные поля формы. Для крупных файлов обычно используют прямую загрузку в объектное хранилище. Клиент сначала просит сервер создать операцию загрузки, получает `uploadId` и ограниченные по времени подписанные URL, затем отправляет байты напрямую в хранилище и сообщает серверу о завершении. Сервер приложения всё равно проверяет право загрузки, задаёт допустимый путь, размер и тип файла и после завершения связывает объект с нужной сущностью.

Состояние файла лучше представить явно: выбран, проходит клиентскую проверку, загружается, приостановлен, отменён, завершил передачу, обрабатывается сервером, готов или завершился ошибкой. Сто процентов передачи означает только то, что браузер отправил все байты. Антивирусная проверка, создание превью или перекодирование видео могут продолжаться отдельно, поэтому для них нужен собственный статус, получаемый через периодические запросы (`polling`), SSE или WebSocket.

Большой файл делят на части (`multipart upload`). Сервер или хранилище возвращает идентификатор загрузки, а клиент передаёт части с номерами и ограничивает число параллельных запросов. Успешные части сохраняются вместе с их `ETag` - идентификатором, возвращённым хранилищем, - или контрольной суммой; при сетевом сбое повторяется только неудачная часть. После передачи всех частей клиент отправляет запрос завершения, а сервер проверяет список частей и собирает объект в правильном порядке.

Для возобновления нужно сохранить не сам файл, а идентификатор операции, параметры частей и уже подтверждённый прогресс. После перезагрузки пользователь снова предоставляет доступ к локальному файлу, клиент проверяет имя, размер и при необходимости контрольную сумму, узнаёт у сервера подтверждённые части и продолжает с нужной позиции. Вместо собственного протокола можно использовать готовый протокол возобновляемой загрузки, например tus, где сервер сообщает принятый байтовый offset - смещение от начала файла.

Прогресс отправки удобно получать через события `XMLHttpRequest.upload`: они сообщают число переданных байтов и общий размер, если он известен. Нативный Fetch API не предоставляет аналогичного стандартного события сетевого прогресса загрузки на сервер, поэтому выбор транспорта зависит не только от привычки использовать `fetch`. Отмена останавливает активные запросы через `AbortController` или `xhr.abort()` и вызывает серверную операцию очистки. Незавершённые части нельзя оставлять бессрочно: хранилище должно удалять их по явной отмене и по правилу жизненного цикла.

Клиентская проверка файла нужна для быстрого сообщения пользователю, но не является защитой. Сервер повторно проверяет размер, разрешённое расширение, фактический тип и сигнатуру содержимого, создаёт собственное имя хранения, проверяет права и при необходимости запускает антивирус или изолированную обработку. Пользовательское имя не используют как путь, а недоверенный файл не раздают как исполняемый контент с произвольным `Content-Type`.

Интерфейс показывает имя, размер, отдельный прогресс каждого файла, общий прогресс очереди, текущую стадию и понятную причину ошибки. Повтор не должен создавать дубликат уже завершённого объекта: операции создания и завершения делают идемпотентными либо привязывают к одному `uploadId`. Для нескольких файлов ограничивают параллелизм, чтобы не занять все соединения и пропускную способность одним экраном.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Зачем загружать файл напрямую в объектное хранилище через подписанный URL?</strong></summary>

<dl>
<dd>
<h2></h2>

Сервер приложения не принимает и не пересылает каждый байт, поэтому тратит меньше памяти, сетевой пропускной способности и времени соединения. При этом сервер сохраняет контроль: он аутентифицирует пользователя, проверяет право, создаёт ограниченный ключ объекта и выдаёт короткоживущий URL только для конкретной операции.

Подписанный URL не означает, что файл стал доверенным. После загрузки сервер проверяет объект, запускает необходимую обработку и только затем помечает его готовым. URL ограничивают сроком, методом и конкретным ключом объекта; размер и фактический тип сервер проверяет отдельно либо включает в условия подписи, если выбранный механизм это поддерживает. Ключ хранилища генерирует сервер, а не пользователь.

Для прямой загрузки из браузера хранилищу настраивают CORS - правила межсайтовых запросов - только для нужного источника (`origin`), методов и заголовков. При multipart upload браузеру также может понадобиться доступ к ответному `ETag`, поэтому его явно добавляют в список открытых заголовков (`Access-Control-Expose-Headers`).

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужен multipart upload, а когда достаточно одного запроса?</strong></summary>

<dl>
<dd>
<h2></h2>

Один запрос проще и подходит для небольших файлов, которые недорого отправить заново после сбоя. Multipart upload оправдан для крупных файлов и нестабильной сети: части можно передавать параллельно и повторять независимо, не начиная всё сначала. Порог зависит от хранилища, сети и продукта; например, Amazon S3 рекомендует рассматривать multipart upload для объектов от 100 МБ.

Цена разбиения - дополнительный протокол: создание загрузки, номера частей, хранение `ETag`, завершение, отмена и очистка незавершённых операций. Для маленького аватара эта сложность обычно не окупается.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему после 100% прогресса файл может быть ещё не готов?</strong></summary>

<dl>
<dd>
<h2></h2>

Прогресс браузера отражает передачу байтов, а не весь серверный процесс. После неё сервер может проверить контрольную сумму, просканировать файл, извлечь метаданные, создать превью или перекодировать видео. Поэтому интерфейс разделяет «загрузка завершена» и «обработка завершена», а статус обработки получает отдельным запросом или событием.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как безопасно повторять неудачные части?</strong></summary>

<dl>
<dd>
<h2></h2>

Каждая часть относится к одному `uploadId` и имеет стабильный номер. При временной сетевой ошибке повторяют ту же часть с растущей задержкой и небольшим случайным разбросом, не меняя её место в файле. После успеха сохраняют подтверждение хранилища, например `ETag`.

Ошибки авторизации, превышения размера или истечения операции нельзя повторять бесконечно. Клиент обновляет разрешение либо завершает загрузку понятной ошибкой. Перед финализацией сервер сверяет полный список частей и выполняет завершение один раз или идемпотентно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что нужно сохранить для продолжения загрузки после перезагрузки страницы?</strong></summary>

<dl>
<dd>
<h2></h2>

Идентификатор загрузки, размер частей, список подтверждённых номеров и их серверные подтверждения. Эти метаданные можно хранить в браузерной базе IndexedDB, но доступ к байтам локального файла обычно нужно получить от пользователя снова. После выбора клиент проверяет, что это тот же файл, и сверяет состояние с сервером, потому что локальные данные могли устареть.

В протоколе tus сервер отвечает текущим смещением (`Upload-Offset`), а клиент продолжает отправку с этого байта. В S3 multipart upload клиент восстанавливает список уже загруженных частей и отправляет отсутствующие.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что должна делать отмена загрузки?</strong></summary>

<dl>
<dd>
<h2></h2>

Остановить активные сетевые запросы, перевести интерфейс в состояние отмены и сообщить серверу или хранилищу, что операция больше не нужна. Для multipart upload это важно: уже переданные части занимают место и могут тарифицироваться до завершения или явного удаления.

На сервере дополнительно настраивают автоматическую очистку старых незавершённых загрузок. Если часть уже обрабатывается, отмена может стать запросом на остановку, а интерфейс должен честно показать, удалось ли её прервать.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему нельзя доверять <code>accept</code>, расширению и <code>Content-Type</code> из браузера?</strong></summary>

<dl>
<dd>
<h2></h2>

Атрибут `accept` лишь помогает выбрать подходящий файл, а клиентский запрос можно изменить. Расширение переименовывается, `Content-Type` задаёт отправитель, и даже сигнатура файла не доказывает, что содержимое безопасно. Сервер применяет несколько проверок: список разрешённых типов, размер, расширение, сигнатуру, права и безопасное имя хранения.

Для рискованных форматов добавляют антивирус, изолированную обработку или Content Disarm and Reconstruction (CDR) - разбор и безопасную пересборку документа. Файлы хранят вне исполняемого веб-каталога или на отдельном домене и отдают с контролируемыми заголовками.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как не создать два объекта при повторе запроса завершения?</strong></summary>

<dl>
<dd>
<h2></h2>

Сервер связывает завершение с одним `uploadId` или ключом идемпотентности. Первый успешный запрос создаёт итоговую запись и сохраняет результат, а повтор с тем же ключом возвращает тот же объект. Если состав частей отличается, сервер отклоняет конфликт, а не создаёт вторую версию молча.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что тестировать у загрузчика файлов?</strong></summary>

<dl>
<dd>
<h2></h2>

Ограничения размера и типа, один и несколько файлов, прогресс, отмену, повтор части и восстановление после перезагрузки. Проверяют ответы в неправильном порядке, истёкший подписанный URL, потерю сети, ошибку финализации, очистку незавершённых частей и отсутствие дубликата при повторе.

Отдельно проверяют клавиатурный выбор файла, доступное название кнопки, объявление ошибок и стадий, фокус после удаления элемента и отсутствие секретов или пользовательских имён файлов в журналах.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Базовое решение |
| --- | --- |
| Аватар пользователя | Один запрос, клиентское превью и повторная серверная проверка |
| Несколько документов | Очередь с ограниченным параллелизмом и отдельным статусом каждого файла |
| Большое видео | Прямая multipart-загрузка, повтор частей и отдельная стадия обработки |
| Нестабильная мобильная сеть | Сохранение подтверждённых частей и возобновляемый протокол |
| Приватный документ | Серверная авторизация, случайный ключ хранения и контролируемая выдача |
