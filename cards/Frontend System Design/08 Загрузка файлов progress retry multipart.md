## Вопрос

<br>

 💬 **Как спроектировать загрузку файлов с прогрессом, отменой, повтором и возобновлением?**

<h2></h2>

<br>
<dl>
<dd>

Сначала уточняют ограничения:

- количество файлов;
- максимальный размер одного файла и всей очереди;
- разрешённые форматы;
- требования к приватности;
- допустимая длительность загрузки;
- нестабильная сеть;
- необходимость паузы и возобновления;
- восстановление после reload;
- последующая серверная обработка;
- срок хранения незавершённых загрузок;
- целевые браузеры и устройства.

Для аватара размером несколько мегабайт и видео размером несколько гигабайт нужны разные решения.

Основные варианты:

```text
небольшой файл
→ один запрос на application server

небольшой или средний файл
→ один прямой запрос в object storage по signed URL

крупный файл
→ multipart upload

обязательное стандартизированное возобновление
→ resumable protocol, например tus
```

Перед реализацией определяют протокол загрузки.

Упрощённый жизненный цикл:

```text
1. Пользователь выбирает файл.
2. Клиент выполняет предварительную проверку.
3. Сервер создаёт upload session.
4. Клиент передаёт файл или части.
5. Сервер подтверждает полученные данные.
6. Клиент завершает upload.
7. Сервер проверяет и обрабатывает файл.
8. Файл становится доступен продукту.
```

Важно разделять:

```text
upload transfer
→ передача байтов

server processing
→ проверка, сканирование, превью, транскодирование

business attachment
→ привязка готового файла к сущности
```

Сто процентов сетевого progress не означают, что файл уже безопасно сохранён, проверен и готов к использованию.

Небольшой файл можно передать application server одним запросом:

```text
multipart/form-data
```

Например, вместе с файлом можно отправить:

- тип документа;
- описание;
- идентификатор сущности;
- дополнительные поля формы.

При использовании `FormData` браузер сам формирует заголовок:

```http
Content-Type: multipart/form-data; boundary=...
```

Не следует вручную задавать:

```http
Content-Type: multipart/form-data
```

без `boundary`, потому что сервер не сможет корректно разобрать тело.

Простой поток:

```text
browser
→ application server
→ storage
```

подходит, если:

- файл небольшой;
- сервер может безопасно принять его целиком;
- повторная отправка после сбоя недорога;
- длительное соединение не создаёт проблемы;
- нагрузка соответствует возможностям сервера.

Недостаток — каждый байт проходит через application server.

Это увеличивает:

- сетевую нагрузку;
- время соединения;
- использование памяти или временного диска;
- стоимость горизонтального масштабирования.

Для прямой загрузки в object storage клиент сначала обращается к application server:

```text
POST /uploads
```

Сервер:

- аутентифицирует пользователя;
- проверяет право;
- проверяет заявленный размер и тип;
- создаёт безопасный object key;
- создаёт `uploadId`;
- выбирает способ загрузки;
- возвращает короткоживущие разрешения.

Дальше:

```text
browser
→ signed URL
→ object storage
```

После передачи клиент сообщает application server:

```text
POST /uploads/{uploadId}/complete
```

Сервер проверяет объект и только после этого связывает его с бизнес-сущностью.

Пример upload session:

```json
{
  "uploadId": "upload-42",
  "strategy": "single",
  "uploadUrl": "https://storage.example/...",
  "expiresAt": "2026-08-05T19:00:00Z"
}
```

Для multipart:

```json
{
  "uploadId": "upload-42",
  "strategy": "multipart",
  "partSize": 8388608,
  "partCount": 120
}
```

Signed URL является временным credential.

Тот, кто получил действующий URL, может выполнить разрешённую им операцию.

Поэтому signed URL:

- имеет короткий срок;
- ограничивается конкретным методом;
- относится к конкретному object key или части;
- не записывается в analytics;
- не выводится в error tracking;
- скрывается в proxy logs, если это возможно;
- не сохраняется дольше upload session.

Пользователь не должен самостоятельно задавать object key:

```text
../../../public/app.js
```

Ключ генерирует сервер.

Часто файл сначала помещают в отдельную область:

```text
quarantine/uploads/{uploadId}
```

После проверки его переводят в готовое состояние или публикуют через контролируемую запись приложения.

Состояние одного файла лучше представить явно.

Например:

```text
selected
validating
readyToUpload
uploading
paused
retrying
uploaded
processing
ready
cancelled
failed
```

Можно разделить два независимых состояния:

```ts
type TransferStatus =
  | "idle"
  | "uploading"
  | "paused"
  | "retrying"
  | "uploaded"
  | "cancelled"
  | "failed";

type ProcessingStatus =
  | "notStarted"
  | "queued"
  | "scanning"
  | "processing"
  | "ready"
  | "rejected"
  | "failed";
```

Это не позволяет смешивать:

```text
байты переданы
```

и:

```text
файл готов к использованию
```

Например:

```text
transfer: uploaded
processing: scanning
```

интерфейс показывает:

```text
Файл загружен. Выполняется проверка.
```

Для крупных файлов используют multipart upload.

Файл делят на последовательные диапазоны:

```text
part 1
part 2
part 3
...
```

Каждая часть имеет:

- `uploadId`;
- `partNumber`;
- диапазон байтов;
- размер;
- состояние;
- число попыток;
- подтверждение storage;
- checksum, если используется.

Упрощённый процесс:

```text
create multipart upload
→ загрузить части
→ собрать подтверждения частей
→ complete multipart upload
→ проверить итоговый объект
```

Клиент получает часть файла через `Blob.slice()`:

```ts
const part = file.slice(
  startByte,
  endByte,
);
```

Размер части выбирают с учётом:

- размера файла;
- лимита количества частей;
- минимального размера части в storage;
- качества сети;
- стоимости повторной отправки;
- памяти;
- нужного параллелизма.

Слишком маленькие части создают:

- много HTTP-запросов;
- большой объём metadata;
- риск превысить лимит частей;
- высокую нагрузку на server и storage.

Слишком большие части означают:

- дорогой retry;
- медленную реакцию на pause;
- грубый progress;
- большую потерю работы при сбое.

Размер части может рассчитываться динамически:

```text
ceil(fileSize / maximumPartCount)
```

с учётом минимального и рекомендуемого размера конкретного storage.

Параллельно загружают ограниченное число частей.

Например:

```text
3–6 активных частей
```

Конкретное значение зависит от:

- браузера;
- HTTP-версии;
- мобильной сети;
- размера частей;
- возможностей storage;
- количества одновременно загружаемых файлов.

Без ограничения один файл может занять всю пропускную способность и ухудшить работу остального приложения.

Для очереди из нескольких файлов задают общий предел:

```text
не более 4 активных part requests
```

а scheduler распределяет их между файлами.

После успешной загрузки части storage возвращает подтверждение.

В Amazon S3 для завершения multipart upload клиент должен передать:

```text
partNumber
ETag
```

для каждой загруженной части.

`ETag` в этом протоколе нужно считать непрозрачным идентификатором части, который требуется для completion.

Нельзя безусловно считать его:

```text
MD5 файла
```

или универсальным доказательством целостности.

Если нужна проверка целостности, используют поддерживаемый storage checksum:

```text
CRC32
CRC32C
SHA-1
SHA-256
другой согласованный алгоритм
```

и отдельно проверяют итоговый объект по правилам выбранного провайдера.

Состояние части может выглядеть так:

```ts
type UploadPart = {
  partNumber: number;
  start: number;
  end: number;
  status:
    | "pending"
    | "uploading"
    | "uploaded"
    | "retrying"
    | "failed";
  etag?: string;
  checksum?: string;
  attempt: number;
};
```

При сетевом сбое повторяют только неуспешную часть.

Уже подтверждённые части заново не отправляют, пока сервер или storage подтверждает их наличие.

Retry выполняют только для временных ошибок.

Обычно повтор допустим при:

- разрыве сети;
- timeout;
- временном `408`;
- `429`;
- части `5xx`;
- временной недоступности storage.

При `429` или `503` полезно учитывать:

```http
Retry-After
```

Не следует автоматически повторять:

- отсутствие права;
- недопустимый тип;
- превышение размера;
- неизвестный `uploadId`;
- отклонённый checksum;
- окончательно истёкшую upload session;
- бизнес-запрет.

Для retry применяют:

```text
exponential backoff
+
jitter
+
maximum attempts
```

Например:

```text
1 секунда
2 секунды
4 секунды
8 секунд
```

со случайным отклонением.

Неограниченный retry скрывает ошибку и создаёт постоянную нагрузку.

Если истёк только signed URL конкретной части, application server может выдать новый URL для того же:

```text
uploadId
partNumber
```

Уже загруженные части при этом не должны теряться.

Если истекла или была отозвана вся upload session, клиент завершает операцию ошибкой либо создаёт новую с явным решением продукта.

Перед completion сервер проверяет:

- пользователь владеет `uploadId`;
- операция ещё активна;
- ожидаемые части присутствуют;
- номера частей допустимы;
- размеры соответствуют контракту;
- checksum корректны, если предусмотрены;
- объект не был уже завершён другим запросом.

После этого части собираются в правильном порядке.

Completion должен быть идемпотентным.

Сценарий:

```text
клиент отправил complete
→ сервер создал объект
→ ответ потерялся
→ клиент повторил complete
```

не должен создать вторую бизнес-запись.

Сервер связывает результат с одним:

```text
uploadId
```

или idempotency key.

Повторный запрос возвращает уже созданный результат.

Если новый completion содержит другой список частей, сервер возвращает конфликт, а не молча создаёт другой объект.

Progress нужно определить точно.

`XMLHttpRequest.upload` предоставляет события:

```text
loaded
total
```

Упрощённо:

```ts
xhr.upload.addEventListener(
  "progress",
  (event) => {
    if (!event.lengthComputable) {
      return;
    }

    const percent =
      (event.loaded / event.total) * 100;
  },
);
```

Нативный Fetch API не предоставляет такого же стандартного высокоуровневого события upload-progress, как `xhr.upload`.

В отдельных окружениях можно строить отправку через streams и считать прочитанные байты вручную, но это не следует считать универсальной заменой без проверки целевых браузеров и реального сетевого поведения.

Для multipart общий переданный progress вычисляют по частям:

```text
байты подтверждённых частей
+
текущий progress активных частей
```

Но полезно различать:

```text
sent progress
confirmed progress
```

**Sent progress** показывает, сколько байтов браузер попытался отправить.

**Confirmed progress** показывает, сколько частей уже подтверждено storage.

Если активная часть завершилась ошибкой, её временный sent-progress может исчезнуть при retry.

Чтобы индикатор не вводил пользователя в заблуждение, можно:

- показывать подтверждённый progress как основной;
- отображать активную передачу отдельно;
- не утверждать, что данные сохранены, пока часть не подтверждена.

Для нескольких файлов общий progress рассчитывают по байтам:

```text
сумма подтверждённых и активных байтов
/
общий размер всех файлов
```

Нельзя просто усреднять проценты:

```text
файл 1: 1 МБ, 100%
файл 2: 1 ГБ, 0%
→ среднее 50%
```

Хотя фактически передана лишь малая часть общего объёма.

Сто процентов upload-progress означает только завершение передачи тела запроса со стороны клиента или конкретного transport API.

После этого ещё могут выполняться:

- сохранение object storage;
- completion multipart;
- checksum verification;
- антивирусная проверка;
- извлечение metadata;
- создание preview;
- распаковка;
- транскодирование;
- модерация;
- привязка к бизнес-сущности.

Поэтому после `100%` интерфейс переходит, например, в:

```text
Обрабатываем файл…
```

Статус обработки получают через:

- polling;
- SSE;
- WebSocket;
- обновление серверной сущности.

Пауза и отмена — разные операции.

**Pause** означает:

```text
остановить активную передачу
сохранить upload session
сохранить подтверждённые части
позже продолжить
```

Активные part requests можно прервать через:

```text
AbortController
xhr.abort()
```

После resume клиент сверяет состояние с сервером и отправляет отсутствующие части.

**Cancel** или **abort upload** означает:

```text
операция больше не нужна
```

Клиент:

- останавливает активные запросы;
- отменяет retry timers;
- вызывает серверный abort endpoint;
- очищает локальные metadata;
- обновляет UI.

Для multipart сервер или storage удаляет загруженные части.

Одна только остановка браузерного запроса не удаляет ранее переданные части.

Незавершённые multipart uploads могут занимать место и создавать стоимость.

Поэтому нужна серверная lifecycle policy:

```text
удалять незавершённые uploads старше N дней
```

Она страхует случаи, когда:

- пользователь закрыл вкладку;
- устройство выключилось;
- cancel request не дошёл;
- frontend упал;
- upload session была забыта.

Отмена серверной обработки может быть не мгновенной.

Если антивирус или транскодирование уже началось, сервер может:

- принять запрос отмены;
- попытаться остановить job;
- пометить результат ненужным;
- удалить итоговые данные после завершения.

Интерфейс должен честно различать:

```text
Отмена запрошена
```

и:

```text
Загрузка отменена
```

Для возобновления после reload сохраняют metadata upload session:

- `uploadId`;
- object key или безопасную ссылку на операцию;
- размер части;
- количество частей;
- подтверждённые номера частей;
- `ETag` или checksum частей;
- срок действия операции;
- слабый fingerprint локального файла.

Metadata можно хранить в IndexedDB.

Signed URL обычно хранить не нужно: после reload безопаснее получить новые URL для ещё не загруженных частей.

Нельзя полагаться только на локальные metadata.

Перед resume клиент спрашивает сервер:

```text
какие части подтверждены?
активна ли upload session?
каков её текущий статус?
```

Локальный список мог устареть.

После reload браузеру нужен повторный доступ к байтам файла.

Базовый совместимый сценарий:

```text
пользователь повторно выбирает файл
```

Клиент сравнивает:

- имя;
- размер;
- `lastModified`;
- при необходимости checksum или fingerprint.

Имя, размер и дата изменения не являются криптографическим доказательством идентичности.

Для более надёжной проверки можно вычислить checksum:

- всего файла;
- отдельных частей;
- выбранных диапазонов.

Полный hash гигабайтного файла сам по себе может быть дорогим, поэтому стратегию выбирают по риску.

В поддерживаемых браузерах приложение может сохранить `FileSystemFileHandle`, например в IndexedDB, и позднее повторно запросить доступ.

Но это дополнительная возможность, а не универсальная гарантия:

- API поддерживается не везде одинаково;
- разрешение может потребоваться снова;
- файл мог измениться;
- пользователь мог удалить файл;
- данные сайта могли быть очищены.

Для стандартизированного resumable upload можно использовать tus.

В базовой модели сервер сообщает принятый offset:

```http
Upload-Offset: 10485760
```

Клиент продолжает передачу с этого байта.

Готовый протокол уменьшает количество собственных решений для:

- creation;
- offset;
- retry;
- termination;
- checksum;
- expiration.

Но всё равно остаются продуктовые задачи:

- authentication;
- authorization;
- business attachment;
- scanning;
- privacy;
- UI;
- lifecycle cleanup.

Обычная веб-страница не гарантирует, что upload продолжится после:

- закрытия вкладки;
- завершения браузера;
- перезагрузки;
- выгрузки страницы операционной системой.

Нельзя строить критичный сценарий на `beforeunload` и пытаться завершить большой upload при закрытии страницы.

Надёжная модель:

```text
сохраняет upload session
→ позволяет продолжить после возвращения
```

Специализированные browser API или установленное приложение могут дать дополнительные возможности, но их поддержку и ограничения проверяют отдельно.

Клиентская проверка файла нужна для быстрого UX:

- максимальный размер;
- количество файлов;
- разрешённые расширения;
- ожидаемый MIME type;
- размеры изображения;
- длительность видео;
- повторный файл в очереди.

Но клиент не является границей безопасности.

Можно изменить запрос и обойти:

```html
accept=".jpg"
```

Сервер повторно проверяет:

- право загрузки;
- ожидаемую бизнес-сущность;
- максимальный размер;
- расширение по allowlist;
- заявленный MIME type;
- фактическую сигнатуру;
- checksum;
- лимиты пользователя;
- количество файлов.

Атрибут `accept` только помогает интерфейсу выбора файла.

Расширение можно переименовать.

`Content-Type` задаёт отправитель.

Сигнатура также не доказывает, что сложный документ безопасен.

Для рискованных форматов применяют:

- антивирус;
- sandbox;
- Content Disarm and Reconstruction;
- повторное кодирование изображений;
- безопасное извлечение архивов;
- запрет активного содержимого.

Пользовательское имя файла не используют как путь хранения.

Его можно сохранить только как отображаемую metadata после:

- нормализации;
- ограничения длины;
- безопасного вывода;
- удаления управляющих символов по правилам продукта.

Object key создаёт сервер:

```text
tenant-id/random-uuid
```

Недоверенные файлы хранят:

- вне executable webroot;
- в object storage;
- на отдельном host;
- в quarantine до проверки.

При выдаче сервер контролирует:

```text
Content-Type
Content-Disposition
X-Content-Type-Options
authorization
```

HTML, SVG и другие активные форматы требуют отдельной политики.

Нельзя раздавать пользовательский файл как доверенный исполняемый контент основного origin.

Для direct upload из браузера object storage должен иметь ограниченный CORS:

- конкретные разрешённые origins;
- только нужные методы;
- только нужные request headers;
- только необходимые response headers.

Если браузеру требуется прочитать `ETag`, его добавляют в:

```http
Access-Control-Expose-Headers
```

Нельзя разрешать произвольный origin с credentials без необходимости.

Для нескольких файлов используют очередь.

Каждый файл имеет независимые:

- progress;
- pause;
- retry;
- cancel;
- processing status;
- error.

Scheduler ограничивает:

- число одновременно загружаемых файлов;
- число активных частей;
- общий сетевой параллелизм.

Пользователь может:

- повторить один файл;
- отменить один файл;
- приостановить очередь;
- продолжить остальные файлы;
- удалить завершённый элемент из UI.

Ошибка одного файла не должна автоматически отменять всю очередь, если файлы независимы.

Если они являются одной атомарной операцией, это правило должно быть явно определено.

Интерфейс показывает:

- безопасное отображаемое имя;
- размер;
- текущую стадию;
- прогресс;
- скорость, если она достаточно стабильна;
- примерное оставшееся время как приблизительное;
- причину ошибки;
- доступные действия.

Не следует обещать точное время окончания: скорость сети может резко меняться.

Для доступности используют нативный file input с `<label>` либо доступную кнопку, которая вызывает его.

Progress можно представить через:

```html
<progress
  value="45"
  max="100"
>
  45%
</progress>
```

У каждого progress должен быть понятный контекст:

```text
Загрузка файла report.pdf: 45%
```

Кнопки:

```text
Приостановить
Продолжить
Повторить
Отменить
Удалить
```

должны иметь доступные имена для конкретного файла.

Состояния объявляют через ограниченную status region:

```text
Загрузка началась
Загрузка приостановлена
Файл передан и обрабатывается
Загрузка завершена
Ошибка загрузки
```

Не следует объявлять screen reader каждое изменение процента.

После удаления элемента фокус переводят в предсказуемое место:

- следующий файл;
- предыдущий файл;
- кнопку добавления.

Drag and drop является дополнительным способом выбора, а не единственным.

Клавиатурный пользователь должен иметь обычный file input или доступную кнопку.

Для observability полезны:

- `uploadId`;
- стратегия загрузки;
- размеровой диапазон файла;
- количество частей;
- число retries;
- длительность;
- причина отмены;
- стабильный error code;
- стадия processing;
- release;
- тип сети, если это допустимо.

Не следует записывать:

- signed URL;
- access token;
- содержимое файла;
- полное пользовательское имя файла;
- приватный object key;
- персональные metadata;
- request headers с credentials.

Тестовая стратегия включает:

- один небольшой файл;
- несколько файлов;
- максимальный размер;
- недопустимый тип;
- single upload;
- multipart upload;
- progress;
- pause и resume;
- cancel;
- retry временной ошибки;
- отсутствие retry окончательной ошибки;
- `Retry-After`;
- истечение signed URL;
- ответы частей в разном порядке;
- checksum mismatch;
- потерю сети;
- reload;
- сверку локальных и серверных частей;
- ошибку completion;
- повтор completion;
- конкурентный completion;
- очистку незавершённых частей;
- server processing;
- отклонение после антивирусной проверки;
- logout;
- смену пользователя;
- CORS;
- доступный file picker;
- клавиатуру;
- объявления стадий;
- focus после удаления.

Практический порядок проектирования:

```text
1. Определить размеры, типы и требования к resume.
2. Выбрать single, direct, multipart или готовый protocol.
3. Спроектировать upload session.
4. Разделить transfer и processing states.
5. Определить part size и параллелизм.
6. Спроектировать progress и подтверждение частей.
7. Определить retry, pause, cancel и cleanup.
8. Спроектировать resume после reload.
9. Добавить server validation, checksum и scanning.
10. Сделать completion идемпотентным.
11. Добавить доступный UI и безопасную observability.
```

Главный принцип:

```text
клиентская проверка
→ быстрый UX

upload session
→ управляемая операция

multipart
→ независимый retry частей

checksum
→ проверка целостности

server processing
→ решение, можно ли доверять файлу

idempotent completion
→ отсутствие дубликатов
```

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Зачем загружать файл напрямую в объектное хранилище через подписанный URL?</strong></summary>

<dl>
<dd>
<h2></h2>

Application server не принимает и не пересылает каждый байт.

Это уменьшает:

- использование памяти;
- сетевой трафик сервера;
- длительность его соединений;
- стоимость масштабирования.

Сервер при этом сохраняет контроль:

```text
аутентифицирует пользователя
→ создаёт upload session
→ задаёт object key
→ выдаёт ограниченный signed URL
→ проверяет итоговый объект
```

Signed URL не делает файл доверенным.

После передачи объект проходит:

- проверку размера;
- checksum;
- проверку типа;
- антивирус;
- обработку;
- авторизацию привязки.

Для браузера storage настраивает ограниченный CORS.

Если multipart completion требует прочитать `ETag`, заголовок явно открывают через `Access-Control-Expose-Headers`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужен multipart upload, а когда достаточно одного запроса?</strong></summary>

<dl>
<dd>
<h2></h2>

Один запрос проще и подходит, если:

- файл небольшой;
- повторная отправка недорога;
- соединение достаточно стабильное;
- resume не требуется.

Multipart оправдан, если:

- файл большой;
- сеть нестабильна;
- нужен независимый retry частей;
- полезен ограниченный параллелизм;
- повтор всего файла слишком дорог.

Для Amazon S3 рекомендуется рассматривать multipart upload для объектов от 100 МБ.

Это не универсальный порог для всех систем.

Цена multipart:

- отдельная upload session;
- выбор part size;
- номера частей;
- подтверждения;
- completion;
- abort;
- lifecycle cleanup.

Для маленького аватара эта сложность обычно не окупается.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему после 100% прогресса файл может быть ещё не готов?</strong></summary>

<dl>
<dd>
<h2></h2>

Upload-progress отражает передачу байтов, а не весь серверный lifecycle.

После передачи могут выполняться:

- multipart completion;
- checksum verification;
- антивирус;
- извлечение metadata;
- создание preview;
- транскодирование;
- модерация.

Поэтому UI разделяет:

```text
Файл передан
```

и:

```text
Файл обработан и готов
```

Статус обработки получают отдельно через polling, SSE или WebSocket.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как безопасно повторять неудачные части?</strong></summary>

<dl>
<dd>
<h2></h2>

Часть имеет стабильные:

```text
uploadId
partNumber
диапазон байтов
```

При временной ошибке повторяют ту же часть с:

- exponential backoff;
- jitter;
- ограничением попыток;
- учётом `Retry-After`.

Успешные подтверждённые части не отправляют заново.

Ошибки права, размера, типа и checksum не повторяют автоматически.

Если истёк только signed URL, получают новый URL для того же `partNumber`.

Перед completion сервер сверяет полный список частей и делает операцию идемпотентной.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что нужно сохранить для продолжения загрузки после перезагрузки страницы?</strong></summary>

<dl>
<dd>
<h2></h2>

В IndexedDB можно сохранить:

- `uploadId`;
- part size;
- список подтверждённых частей;
- их `ETag` или checksum;
- срок действия операции;
- fingerprint файла.

После reload клиент сначала сверяется с сервером.

Локальное состояние нельзя считать окончательным.

Обычно пользователь повторно выбирает файл, после чего клиент проверяет имя, размер, `lastModified` и при необходимости checksum.

В поддерживаемых браузерах можно сохранять `FileSystemFileHandle`, но доступ и неизменность файла всё равно нужно перепроверить.

Signed URL лучше получить заново, а не хранить как долгоживущий credential.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что должна делать отмена загрузки?</strong></summary>

<dl>
<dd>
<h2></h2>

Отмена должна:

1. Остановить активные запросы.
2. Отменить retry timers.
3. Перевести UI в состояние отмены.
4. Сообщить серверу об abort.
5. Удалить удалённые multipart parts.
6. Очистить локальные metadata.

Если server processing уже началась, отмена может быть асинхронной.

Интерфейс различает:

```text
Отмена запрошена
```

и:

```text
Операция отменена
```

Дополнительно storage должен автоматически удалять забытые незавершённые uploads по lifecycle policy.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему нельзя доверять <code>accept</code>, расширению и <code>Content-Type</code> из браузера?</strong></summary>

<dl>
<dd>
<h2></h2>

`accept` только помогает пользователю выбрать файл.

Клиентский запрос можно изменить.

Расширение можно переименовать.

`Content-Type` задаёт отправитель.

Даже правильная сигнатура сложного документа не гарантирует безопасность его содержимого.

Сервер применяет несколько проверок:

- allowlist типов;
- размер;
- расширение;
- сигнатуру;
- checksum;
- права;
- антивирус;
- безопасную обработку.

Файл хранят вне executable webroot или на отдельном host и раздают с контролируемыми заголовками.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как не создать два объекта при повторе запроса завершения?</strong></summary>

<dl>
<dd>
<h2></h2>

Completion связывают с одним:

```text
uploadId
```

или idempotency key.

Первый успешный запрос сохраняет результат.

Повтор с тем же набором частей возвращает тот же объект.

Если запрос содержит другой состав частей, сервер возвращает конфликт.

Это защищает сценарий:

```text
complete выполнился
→ ответ потерялся
→ клиент повторил запрос
```

от создания дубликата.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что тестировать у загрузчика файлов?</strong></summary>

<dl>
<dd>
<h2></h2>

Проверяют:

- ограничения размера и типа;
- один и несколько файлов;
- progress;
- pause;
- resume;
- cancel;
- retry;
- ошибки без retry;
- истёкший signed URL;
- checksum mismatch;
- multipart parts в разном порядке;
- ограничение параллелизма;
- reload;
- повторный выбор другого файла;
- completion;
- повтор completion;
- server processing;
- очистку orphan uploads;
- logout;
- CORS;
- клавиатурный выбор;
- доступные названия кнопок;
- status announcements;
- focus после удаления.

Отдельно проверяют отсутствие signed URL, имён файлов и credentials в logs и error tracking.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем пауза отличается от отмены?</strong></summary>

<dl>
<dd>
<h2></h2>

Пауза сохраняет upload session и подтверждённые части:

```text
остановить активные запросы
→ оставить remote parts
→ позже продолжить
```

Отмена означает, что операция больше не нужна:

```text
остановить запросы
→ abort multipart
→ удалить remote parts
→ очистить metadata
```

Кнопка «Пауза» не должна вызывать серверное удаление уже загруженных частей.

Кнопка «Отмена» должна освобождать удалённые ресурсы либо запускать такую очистку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как рассчитывать общий прогресс нескольких файлов?</strong></summary>

<dl>
<dd>
<h2></h2>

Общий progress рассчитывают по байтам:

```text
сумма переданных или подтверждённых байтов
/
суммарный размер файлов
```

Нельзя просто усреднять проценты файлов разных размеров.

Для multipart полезно отдельно учитывать:

- подтверждённые части;
- текущий progress активных частей.

После ошибки активной части временный sent-progress может уменьшиться перед retry.

Поэтому интерфейс может показывать основной подтверждённый progress и отдельное состояние текущей передачи.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выбрать размер части multipart upload?</strong></summary>

<dl>
<dd>
<h2></h2>

Учитывают:

- размер файла;
- лимит частей storage;
- минимальный размер части;
- стоимость одного запроса;
- качество сети;
- стоимость retry;
- желаемый параллелизм.

Слишком маленькие части создают много запросов.

Слишком большие делают retry дорогим и замедляют pause.

Размер можно рассчитывать от:

```text
fileSize / maximumPartCount
```

с округлением вверх и учётом ограничений storage.

Для Amazon S3 число частей не может превышать 10 000, а все части, кроме последней, должны соответствовать минимальному размеру сервиса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Является ли <code>ETag</code> контрольной суммой файла?</strong></summary>

<dl>
<dd>
<h2></h2>

Не всегда.

В S3 `ETag` зависит от способа создания объекта, multipart upload и шифрования.

Для multipart он нужен как непрозрачное подтверждение каждой части при completion.

Нельзя универсально сравнивать итоговый `ETag` с MD5 всего файла.

Если требуется проверка целостности, используют явно выбранный checksum-механизм storage и проверяют part-level или object-level checksum по его контракту.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать, если подписанный URL истёк во время загрузки?</strong></summary>

<dl>
<dd>
<h2></h2>

Если upload session ещё активна, клиент обращается к application server и получает новый signed URL для того же объекта или части.

Уже подтверждённые части повторно не загружаются.

Сервер повторно проверяет:

- пользователя;
- право;
- `uploadId`;
- `partNumber`;
- срок жизни операции.

Если истекла вся upload session или право было отозвано, клиент завершает загрузку понятной ошибкой, а не бесконечно запрашивает новые URL.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Продолжится ли загрузка после закрытия вкладки?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычная веб-страница не может гарантировать продолжение большого upload после закрытия вкладки или завершения браузера.

`beforeunload` не подходит для завершения длительной сетевой операции.

Надёжный сценарий сохраняет upload session и позволяет продолжить после возвращения пользователя:

```text
сохранить metadata
→ повторно получить доступ к файлу
→ сверить части с сервером
→ продолжить
```

Дополнительные browser API могут расширить возможности, но их поддержку и ограничения проверяют отдельно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему передачу и обработку файла нужно показывать отдельно?</strong></summary>

<dl>
<dd>
<h2></h2>

Передача отвечает только за доставку байтов.

После неё сервер может выполнять:

- checksum verification;
- antivirus scan;
- preview generation;
- transcoding;
- moderation.

Поэтому возможное состояние:

```text
transfer: uploaded
processing: scanning
```

Если объединить всё в один progress, пользователь увидит `100%`, а затем непонятную задержку.

Лучше показать отдельные стадии и финальное состояние `ready`.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Базовое решение |
| --- | --- |
| Аватар пользователя | Один запрос, preview и повторная серверная проверка |
| Небольшой файл в object storage | Один короткоживущий signed upload |
| Несколько документов | Очередь с общим лимитом параллелизма |
| Большое видео | Multipart, retry частей и отдельный processing status |
| Нестабильная мобильная сеть | Сохранение подтверждённых частей и resume |
| Стандартизированное возобновление | Протокол tus и серверный offset |
| Приватный документ | Quarantine, случайный object key и контролируемая выдача |
| Истёкший signed URL | Новый URL для действующей upload session |
| Закрытие вкладки | Восстановление операции после возвращения |
| Повтор completion | Идемпотентный результат по `uploadId` |
