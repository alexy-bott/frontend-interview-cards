## Вопрос

<br>

 💬 **Как спроектировать экран с данными в реальном времени? Когда выбрать WebSocket, SSE или polling?**

<h2></h2>

<br>
<dl>
<dd>

Сначала определяют требования к данным:

- в какую сторону передаются сообщения;
- допустимая задержка;
- частота и размер сообщений;
- число одновременных подписок;
- нужен ли строгий порядок;
- допустимы ли дубликаты;
- можно ли потерять событие;
- нужен ли полный журнал;
- что видит пользователь без сети;
- как долго данные можно считать актуальными.

Также учитывают инфраструктуру:

- reverse proxy и load balancer;
- ограничения времени жизни соединения;
- авторизацию;
- фоновые вкладки;
- мобильную сеть;
- поддерживаемые браузеры;
- возможность хранить историю событий.

Упрощённый выбор:

```text
редкие обновления и допустима задержка
→ polling

частый поток только от сервера к браузеру
→ SSE

частый двусторонний обмен
→ WebSocket
```

Выбор определяют требования, а не само слово `realtime`.

**Polling** — периодические HTTP-запросы.

Он подходит, когда:

- обновления происходят редко;
- задержка в несколько секунд или минут допустима;
- обычная HTTP-инфраструктура предпочтительнее постоянного соединения;
- простота эксплуатации важнее минимальной задержки.

Преимущества polling:

- обычные HTTP-запросы;
- понятные статусы и логи;
- простые retry и timeout;
- совместимость с proxy и cache;
- отсутствие отдельного протокола сообщений.

Недостатки:

- пустые запросы при отсутствии изменений;
- свежесть ограничена интервалом;
- большое число клиентов создаёт постоянную нагрузку;
- браузер замедляет таймеры фоновой вкладки.

Запросы лучше планировать после завершения предыдущего, а не безусловным `setInterval`.

Опасный вариант:

```text
каждые 5 секунд запускается запрос
→ предыдущий запрос ещё не завершился
→ запросы начинают накладываться
```

Безопаснее:

```text
запрос
→ дождаться ответа
→ подождать интервал
→ следующий запрос
```

При ошибках используют backoff, а если сервер вернул `Retry-After`, учитывают рекомендованную задержку.

Для уменьшения объёма ответа можно применять условные HTTP-запросы:

```text
ETag
If-None-Match
Last-Modified
If-Modified-Since
```

Если данные не изменились, сервер возвращает:

```http
304 Not Modified
```

После возвращения вкладки в видимое состояние выполняют немедленную проверку, потому что таймеры могли долго не запускаться.

**SSE**, или Server-Sent Events, создаёт длительное HTTP-соединение для потока от сервера к браузеру.

SSE подходит для:

- уведомлений;
- статусов операций;
- журналов;
- прогресса;
- событий мониторинга;
- обновлений, где команды клиента можно отправлять обычными HTTP-запросами.

Нативный клиент:

```js
const source =
  new EventSource("/api/events");
```

SSE использует текстовый формат событий.

Событие может содержать:

```text
event
data
id
retry
```

Например:

```text
event: order.updated
id: 1842
data: {"orderId":"42","status":"paid"}
```

`EventSource` автоматически пытается переподключиться после обрыва.

Если сервер отправлял `id`, браузер может передать последнее значение через:

```http
Last-Event-ID
```

Но автоматический reconnect сам по себе не гарантирует восстановление.

Сервер должен:

- хранить события хотя бы ограниченное время;
- уметь продолжить поток после `Last-Event-ID`;
- либо сообщить клиенту, что история потеряна и нужен новый snapshot.

Если сервер уже удалил пропущенные события, клиент повторно загружает полное состояние.

Стандартный `EventSource` не позволяет передать произвольный заголовок:

```http
Authorization: Bearer ...
```

Поэтому аутентификацию проектируют заранее.

Частые варианты:

- защищённая cookie;
- same-origin BFF;
- `withCredentials` для согласованного cross-origin cookie-сценария;
- короткоживущий одноразовый connection token.

Долгоживущий access token нежелательно передавать в query string: URL может попасть в browser history, proxy logs и monitoring.

**WebSocket** создаёт постоянный двусторонний канал:

```text
client ↔ server
```

Он подходит для:

- чата;
- совместного редактирования;
- multiplayer;
- частых пользовательских команд;
- bidirectional-сигнализации;
- высокочастотных обновлений с низкой задержкой.

После установления соединения приложение самостоятельно определяет протокол:

```text
типы сообщений
подписки
подтверждения
ошибки
версии
повторную доставку
reconnect
```

Например:

```json
{
  "type": "order.updated",
  "eventId": "1842",
  "entityId": "42",
  "version": 7,
  "occurredAt": "2026-08-05T18:00:00Z",
  "payload": {
    "status": "paid"
  }
}
```

Браузерный `WebSocket` не предоставляет встроенный автоматический reconnect.

После `close` или ошибки приложение само решает:

- нужно ли переподключаться;
- через какую задержку;
- нужно ли обновить сессию;
- как восстановить подписки;
- откуда продолжить поток.

Как и `EventSource`, браузерный WebSocket API не позволяет произвольно добавить HTTP-заголовок `Authorization` в handshake.

Для аутентификации обычно используют:

- защищённую cookie;
- BFF;
- короткоживущий одноразовый connection token;
- отдельное auth-сообщение после открытия канала, если протокол это допускает.

Если token передаётся через URL, он должен быть короткоживущим и одноразовым, а серверные логи должны его скрывать.

Внутри одного активного WebSocket- или SSE-соединения сообщения приходят клиенту в порядке передачи по этому соединению.

Но этого недостаточно для общей согласованности.

Порядок может нарушаться на прикладном уровне, если:

- события создают несколько серверных узлов;
- после reconnect выполняется replay;
- событие доставляется повторно;
- несколько сущностей обновляются независимо;
- snapshot и stream относятся к разным моментам.

Поэтому сообщение получает:

- уникальный `eventId`;
- идентификатор сущности;
- версию сущности или sequence number;
- тип;
- время события;
- версию схемы протокола при необходимости.

Надёжная модель обычно сочетает **snapshot** и **events**.

```text
snapshot
→ полное состояние на известной версии

events
→ изменения после этой версии
```

Нельзя просто:

```text
получить snapshot
→ затем открыть соединение
```

Между двумя действиями сервер может создать событие, которое клиент никогда не увидит.

Безопасные варианты:

```text
snapshot содержит cursor
→ подписка запрашивает события после cursor
```

или:

```text
сначала открыть stream и временно буферизовать события
→ получить snapshot
→ применить события новее версии snapshot
```

или:

```text
сервер атомарно возвращает snapshot и позицию журнала
→ клиент продолжает поток с этой позиции
```

Главное — иметь точную границу:

```text
snapshot включает события до N
stream начинается после N
```

Обработчик событий должен быть идемпотентным.

Повторное применение одного события не должно менять результат второй раз.

Например:

```text
eventId 1842 уже обработан
→ повтор игнорируется
```

Версия сущности защищает от старого обновления:

```text
текущая version = 7
пришла version = 6
→ событие не заменяет новое состояние
```

Если ожидалась версия 8, но пришла 9, обнаружен пропуск.

Клиент:

```text
помечает данные устаревшими
→ запрашивает пропущенные события
```

либо:

```text
получает новый snapshot
```

Обычно проще проектировать доставку так, чтобы дубликаты были допустимы, а потеря обнаруживалась через sequence или version.

Жизненный цикл realtime-соединения:

```text
получить актуальную сессию
→ подключиться
→ авторизовать подписки
→ получить snapshot или cursor
→ обрабатывать события
→ контролировать живость
→ закрыть или переподключиться
```

Авторизация открытия соединения не означает право на каждую тему.

Сервер отдельно проверяет:

```text
может ли пользователь подписаться на order:42
может ли он отправить команду
принадлежит ли ресурс его tenant
```

Права могут измениться во время соединения.

Сервер должен уметь:

- отозвать конкретную подписку;
- отправить auth error;
- закрыть соединение;
- потребовать повторную аутентификацию.

Для обнаружения неработающего соединения используют heartbeat.

В WebSocket protocol существуют ping/pong frames, но browser JavaScript не управляет ими напрямую.

Proxy или сервер может использовать protocol-level ping/pong самостоятельно.

Если приложению нужно контролировать живость на клиентском уровне, протокол добавляет сообщения:

```json
{
  "type": "ping",
  "sentAt": 123
}
```

и:

```json
{
  "type": "pong",
  "sentAt": 123
}
```

Для SSE сервер может периодически отправлять comment или служебное событие, чтобы соединение не считалось бездействующим:

```text
: keep-alive
```

Heartbeat должен быть достаточно редким, чтобы не создавать лишнюю нагрузку, но меньше timeout используемых proxy и load balancer.

После обрыва используют exponential backoff с jitter:

```text
1 секунда
2 секунды
4 секунды
8 секунд
```

со случайным отклонением.

Jitter не позволяет тысячам клиентов одновременно создать reconnect storm.

Задержку обычно ограничивают максимальным значением.

После успешного стабильного соединения счётчик попыток можно сбросить.

Нельзя бесконечно переподключаться при окончательной ошибке:

```text
сессия отозвана
нет права на тему
протокол не поддерживается
```

Такие ошибки переводят приложение в соответствующее состояние, а не повторяют запрос каждую секунду.

После reconnect клиент:

```text
проверяет сессию
→ восстанавливает подписки
→ передаёт последний eventId
→ получает пропущенные события
```

Если восстановление невозможно:

```text
очищает непроверенную очередь
→ получает новый snapshot
```

Браузерный WebSocket не предоставляет автоматический backpressure для входящих сообщений.

Если сервер отправляет события быстрее, чем приложение их обрабатывает:

- растёт очередь;
- увеличивается память;
- блокируется main thread;
- React выполняет слишком много renders;
- интерфейс начинает отставать от реального состояния.

Нельзя обязательно рендерить каждое событие отдельно.

Используют:

- batching;
- coalescing;
- агрегацию;
- ограниченную частоту обновления UI;
- Web Worker для тяжёлого преобразования;
- ограничение размера очереди;
- server-side rate limit.

Например, для котировки может быть важным только последнее значение:

```text
100 промежуточных updates
→ оставить последнее
```

Для журнала операций отбрасывать промежуточные события нельзя — их нужно обработать или повторно получить.

Стратегия зависит от предметной области.

Если очередь превысила безопасный лимит, клиент может:

```text
пометить данные устаревшими
→ закрыть соединение
→ получить новый snapshot
```

Состояние транспорта и состояние данных нужно разделять.

Например:

```text
connection: reconnecting
data: stale
```

или:

```text
connection: connected
data: synchronizing
```

Полезные состояния интерфейса:

- connecting;
- connected;
- reconnecting;
- offline;
- unauthorized;
- stale;
- synchronizing;
- failed.

При временном обрыве можно оставить последние данные, если пользователь явно видит:

```text
Соединение потеряно.
Показаны данные на 18:42.
```

Для критичных данных устаревший результат может быть недопустим. Тогда действия блокируют до восстановления актуальности.

Через Page Visibility API приложение узнаёт, что вкладка скрыта.

Для polling можно:

- увеличить интервал;
- временно остановить запросы;
- выполнить немедленный refresh после возврата.

Для WebSocket и SSE соединение можно оставить активным, если события нужны, но тяжёлое обновление интерфейса объединять.

После длительного нахождения в фоне нельзя автоматически считать данные актуальными.

Нужно:

```text
проверить соединение
→ проверить sequence
→ при необходимости загрузить snapshot
```

При переходе страницы в bfcache или восстановлении из него также проверяют фактическое состояние соединения, а не полагаются на старый флаг `connected`.

При logout или смене пользователя:

- закрывают WebSocket и SSE;
- прекращают polling;
- отменяют reconnect timer;
- очищают персональную очередь;
- очищают snapshot;
- удаляют подписки;
- сообщают другим вкладкам при необходимости.

Старое соединение не должно продолжать принимать персональные события после смены аккаунта.

Безопасность остаётся серверной обязанностью.

Нужны:

- HTTPS или `wss`;
- проверка `Origin`;
- аутентификация соединения;
- авторизация каждой подписки и команды;
- ограничение размера сообщения;
- rate limit;
- ограничение числа подписок;
- валидация payload;
- защита от повторного использования token.

Клиент тоже проверяет входящие сообщения.

Нельзя считать корректным любой JSON, пришедший из соединения.

Проверяют:

- тип;
- обязательные поля;
- допустимый размер;
- формат version;
- структуру payload.

Неизвестный тип:

- безопасно игнорируют;
- либо фиксируют в monitoring;
- либо запускают обновление клиента по согласованной политике.

Нельзя безусловно применять payload к состоянию или вставлять полученные строки как HTML.

Для observability полезны:

- состояние соединения;
- длительность подключения;
- число reconnect;
- причина закрытия;
- размер очереди;
- отставание от последнего события;
- пропущенные sequence;
- время обработки batch;
- release;
- transport type.

Не следует логировать:

- access token;
- session cookie;
- полный приватный payload;
- персональные сообщения;
- connection URL с token.

Практический порядок проектирования:

```text
1. Определить допустимую задержку и направление данных.
2. Выбрать polling, SSE или WebSocket.
3. Согласовать аутентификацию и авторизацию подписок.
4. Определить message schema.
5. Связать snapshot и event cursor.
6. Определить дедупликацию и порядок.
7. Спроектировать heartbeat и reconnect.
8. Ограничить очередь и частоту обновления UI.
9. Определить stale и offline states.
10. Проверить logout, фоновые вкладки и изменение прав.
11. Добавить метрики и тесты восстановления.
```

</dd>

## Дополнительные вопросы

<details>
<summary><strong>Чем WebSocket отличается от SSE?</strong></summary>

<dl>
<dd>
<h2></h2>

WebSocket предоставляет двусторонний канал:

```text
client ↔ server
```

SSE передаёт события только от сервера к браузеру:

```text
server → client
```

Команды клиента при SSE отправляются отдельными HTTP-запросами.

SSE проще для:

- уведомлений;
- статусов;
- журналов;
- прогресса.

WebSocket оправдан при:

- чате;
- совместном редактировании;
- частых командах клиента;
- низкой задержке двустороннего обмена.

Выбор определяется направлением и характером нагрузки, а не самим требованием realtime.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда polling лучше постоянного соединения?</strong></summary>

<dl>
<dd>
<h2></h2>

Polling подходит, если:

- обновления редкие;
- задержка до следующего интервала допустима;
- число клиентов невелико;
- важна простота HTTP-инфраструктуры;
- постоянное соединение не даёт существенной пользы.

Он хорошо работает с:

- HTTP logs;
- timeout;
- retry;
- cache validators;
- обычными балансировщиками.

Следующий запрос лучше запускать после завершения предыдущего, чтобы медленные ответы не создавали несколько параллельных polling-запросов.

В фоновой вкладке polling замедляют, а после возвращения выполняют немедленное обновление.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать при переподключении (<code>reconnect</code>)?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала определяют, является ли ошибка временной.

При временном обрыве:

```text
проверить сессию
→ подождать backoff с jitter
→ подключиться
→ восстановить подписки
→ передать последний eventId
```

Если сервер сохранил историю, он возвращает пропущенные события.

Если история потеряна:

```text
получить новый snapshot
→ продолжить поток с новой позиции
```

При окончательной ошибке авторизации бесконечный reconnect не запускают.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое схема сообщения (<code>message schema</code>)?</strong></summary>

<dl>
<dd>
<h2></h2>

Это проверяемый контракт события.

Например:

```json
{
  "type": "order.updated",
  "eventId": "1842",
  "entityId": "42",
  "version": 7,
  "occurredAt": "2026-08-05T18:00:00Z",
  "payload": {
    "status": "paid"
  }
}
```

`type` выбирает обработчик.

`eventId` используется для дедупликации и восстановления.

`version` помогает обнаружить старое событие или пропуск.

Клиент валидирует сообщение до применения и должен иметь политику для неизвестного типа или версии протокола.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как обрабатывать события не по порядку или повторно?</strong></summary>

<dl>
<dd>
<h2></h2>

У события должен быть уникальный `eventId`, а у сущности — версия или sequence number.

Правила:

```text
eventId уже обработан
→ игнорировать дубликат

version меньше текущей
→ не применять старое состояние

version больше ожидаемой
→ обнаружен пропуск
```

При пропуске клиент временно считает данные устаревшими и запрашивает:

- недостающий диапазон;
- либо новый snapshot.

Обработчик события должен быть идемпотентным.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему нельзя строить состояние только из событий после подключения?</strong></summary>

<dl>
<dd>
<h2></h2>

Клиент не знает, что произошло до открытия соединения.

Он также может потерять события во время обрыва.

Snapshot даёт полное состояние на известной версии:

```text
состояние до event N
```

Stream продолжает после этой позиции:

```text
event N + 1
event N + 2
```

Без snapshot новый клиент должен был бы воспроизвести всю историю событий с самого начала, что обычно слишком дорого или невозможно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать, если сообщения приходят быстрее, чем интерфейс их обрабатывает?</strong></summary>

<dl>
<dd>
<h2></h2>

Нельзя обязательно выполнять отдельный React render для каждого сообщения.

Используют:

- batching;
- coalescing;
- ограниченную частоту обновления;
- агрегацию;
- Web Worker;
- ограничение очереди.

Для котировок может быть достаточно последнего значения.

Для журнала событий пропуск недопустим, поэтому нужна обработка всей очереди или повторная загрузка.

Если очередь переполнена:

```text
пометить данные stale
→ остановить поток
→ получить новый snapshot
```

Обычный browser `WebSocket` не предоставляет автоматический backpressure для входящих сообщений.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как учитывать видимость вкладки?</strong></summary>

<dl>
<dd>
<h2></h2>

Через Page Visibility API приложение узнаёт, что вкладка скрыта.

Polling можно:

- замедлить;
- остановить;
- немедленно повторить после возврата.

Для SSE и WebSocket можно продолжить приём, но объединять тяжёлые UI-обновления.

После возврата проверяют:

- состояние соединения;
- последний `eventId`;
- наличие пропуска sequence;
- актуальность snapshot.

Нельзя считать данные свежими только потому, что до скрытия вкладки соединение было открыто.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Достаточно ли авторизовать только открытие WebSocket?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Пользователь с действующей сессией не обязательно имеет право подписаться на:

```text
order:42
tenant:other-company
admin-events
```

Сервер проверяет:

- каждую подписку;
- каждую команду;
- tenant;
- доступ к ресурсу;
- актуальные permissions.

Права могут измениться во время соединения.

Тогда сервер отзывает подписку, возвращает ошибку или закрывает канал.

Клиентское скрытие темы не является защитой.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как аутентифицировать SSE или WebSocket?</strong></summary>

<dl>
<dd>
<h2></h2>

Для first-party приложения часто используют защищённую session cookie или BFF.

`EventSource` поддерживает cookie и при согласованном cross-origin-сценарии может использовать `withCredentials`.

Стандартные browser API `EventSource` и `WebSocket` не позволяют произвольно передать HTTP-заголовок `Authorization`.

Другой вариант — короткоживущий одноразовый connection token.

Долгоживущий token не следует помещать в URL: он может попасть в history, proxy logs и monitoring.

После подключения сервер всё равно отдельно авторизует каждую подписку и команду.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как избежать потери события между snapshot и началом подписки?</strong></summary>

<dl>
<dd>
<h2></h2>

Snapshot должен содержать позицию журнала:

```text
snapshotVersion = 1842
```

После него клиент запрашивает:

```text
события после 1842
```

Другой вариант:

```text
сначала открыть stream
→ временно буферизовать события
→ загрузить snapshot
→ применить события новее snapshot
```

Небезопасная схема:

```text
получить snapshot
→ открыть stream без cursor
```

создаёт окно, в котором новое событие может быть потеряно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужен heartbeat и чем он отличается от WebSocket ping/pong?</strong></summary>

<dl>
<dd>
<h2></h2>

Heartbeat помогает обнаружить соединение, которое формально не закрылось, но больше не передаёт данные.

WebSocket protocol содержит ping/pong frames, однако browser JavaScript напрямую ими не управляет.

Сервер и proxy могут использовать protocol-level ping/pong самостоятельно.

При необходимости приложение добавляет собственные сообщения:

```text
ping
pong
```

SSE-сервер может периодически отправлять comment:

```text
: keep-alive
```

Интервал выбирают с учётом timeout proxy, но heartbeat не должен создавать значительную дополнительную нагрузку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что тестировать у realtime-экрана?</strong></summary>

<dl>
<dd>
<h2></h2>

Проверяют:

- первоначальный snapshot;
- применение обычного события;
- повторный `eventId`;
- старую версию сущности;
- пропуск sequence;
- события в неожиданном порядке;
- неизвестный тип сообщения;
- разрыв соединения;
- reconnect с backoff;
- восстановление подписок;
- невозможность replay и новый snapshot;
- истечение сессии;
- отзыв permission;
- logout;
- скрытие и возврат вкладки;
- переполнение входящей очереди;
- batching UI-обновлений.

Отдельно проверяют, что пользователь видит состояния `reconnecting`, `offline` и `stale`, а персональные события не продолжают обрабатываться после logout.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Базовый вариант |
| --- | --- |
| Статус заказа раз в минуту | Последовательный polling с обновлением после возврата вкладки |
| Поток уведомлений | SSE с `eventId`, replay и новым snapshot при потере истории |
| Чат | WebSocket, подтверждения и дедупликация сообщений |
| Биржевые значения | WebSocket, coalescing и ограничение входящей очереди |
| Совместное редактирование | Протокол конфликтов и версий поверх двустороннего транспорта |
| Прогресс долгой операции | SSE или polling в зависимости от требуемой задержки |
| Истечение сессии | Остановка reconnect и повторная аутентификация |
| Потеря части событий | Sequence gap и повторный snapshot |
