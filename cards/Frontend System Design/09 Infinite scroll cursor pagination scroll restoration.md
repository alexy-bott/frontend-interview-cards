## Вопрос

<br>

 💬 **Как спроектировать бесконечную ленту с пагинацией, обновлениями и восстановлением прокрутки?**

<h2></h2>

<br>
<dl>
<dd>

Сначала уточняют назначение и поведение ленты:

- хронологическая она или ранжированная;
- как часто появляются новые записи;
- изменяются и удаляются ли существующие записи;
- нужно ли загружать данные только вперёд или в обе стороны;
- должен ли пользователь открыть конкретный элемент по ссылке;
- нужно ли вернуться на прежнее место после страницы детали;
- важны ли SEO и серверный HTML;
- должен ли пользователь добраться до footer;
- сколько элементов может накопиться за одну сессию;
- допустимо ли показывать устаревший порядок.

Infinite scroll подходит для последовательного просмотра:

```text
новостная лента
каталог рекомендаций
журнал событий
социальная лента
```

Но это не всегда лучший интерфейс.

Обычная пагинация удобнее, если пользователь должен:

- перейти к конкретной странице;
- сравнивать результаты;
- запомнить положение по номеру;
- быстро добраться до конца;
- использовать стабильные серверные URL.

Кнопка:

```text
Загрузить ещё
```

часто является хорошим компромиссом:

- пользователь контролирует добавление;
- footer остаётся достижимым;
- проще доступность;
- меньше неожиданных сетевых запросов;
- сохраняется последовательный просмотр.

Автоматическую загрузку и кнопку можно сочетать:

```text
IntersectionObserver
→ автоматически запускает тот же обработчик

кнопка «Загрузить ещё»
→ остаётся доступным fallback
```

Для изменяющейся ленты обычно используют **cursor pagination**.

API принимает непрозрачный cursor:

```http
GET /feed?cursor=opaque-value&limit=20
```

и возвращает:

```json
{
  "items": [],
  "nextCursor": "next-opaque-value",
  "hasNextPage": true
}
```

Cursor описывает позицию в стабильном порядке.

Например, сервер сортирует:

```text
createdAt DESC
id DESC
```

Если несколько записей имеют одинаковый `createdAt`, уникальный `id` создаёт детерминированный вторичный порядок.

Упрощённая граница:

```text
createdAt < lastCreatedAt

или:

createdAt = lastCreatedAt
и id < lastId
```

Клиент не должен самостоятельно разбирать cursor, изменять его или вычислять следующий.

Для клиента это непрозрачная строка, смысл которой принадлежит серверу.

Offset pagination использует:

```text
page
offset
```

Например:

```http
GET /feed?offset=40&limit=20
```

Она проще для перехода к конкретному номеру страницы, но хуже переносит изменения перед текущей позицией.

Сценарий:

```text
клиент получил записи 1–20
→ сверху добавилась новая запись
→ запрос offset=20
```

После сдвига прежняя запись 20 может прийти повторно, а другая запись будет пропущена.

Cursor означает:

```text
продолжить после известной стабильной границы
```

поэтому вставка новых элементов перед этой границей меньше влияет на продолжение.

Cursor pagination не делает любой порядок стабильным автоматически.

Если выдача ранжируется персональным алгоритмом, её порядок может зависеть от:

- пользователя;
- времени;
- версии модели;
- эксперимента;
- feature flag;
- истории действий;
- изменившихся оценок релевантности.

В таком случае cursor можно связать с:

```text
feedSessionId
rankingVersion
snapshotId
expiresAt
```

Например:

```json
{
  "items": [],
  "nextCursor": "opaque-cursor",
  "feedVersion": "feed-1842",
  "expiresAt": "2026-08-05T22:00:00Z"
}
```

Все страницы одной сессии относятся к согласованному порядку.

Если cursor или версия выдачи истекли, API возвращает явный код:

```text
FEED_CURSOR_EXPIRED
```

Клиент не должен незаметно соединять:

```text
старое ранжирование
+
новое ранжирование
```

Иначе пользователь получает непредсказуемые повторы и пропуски.

Возможные действия:

- показать кнопку обновления выдачи;
- сохранить текущие элементы и начать новую ленту сверху;
- восстановить позицию по конкретному элементу;
- запросить новый диапазон вокруг anchor.

Состояние ленты полезно разделить на несколько частей.

```text
query state
page state
entity state
update state
scroll state
```

**Query state**:

- фильтры;
- пользователь;
- tenant;
- ranking mode;
- направление;
- версия выдачи.

Обычно параметры, которыми нужно делиться, хранят в URL:

```text
/feed?category=frontend&sort=recent
```

**Page state**:

- загруженные страницы;
- cursor каждой границы;
- `hasNextPage`;
- `hasPreviousPage`;
- состояния запросов;
- ошибки отдельных направлений.

**Entity state**:

```text
entitiesById
```

или аналогичное нормализованное хранилище записей.

**Update state**:

- новые элементы, ещё не вставленные сверху;
- удалённые ID;
- изменённые версии;
- realtime-события.

**Scroll state**:

- anchor ID;
- смещение anchor;
- направление;
- приблизительная позиция;
- запись history;
- состояние восстановления.

Концептуально:

```ts
type FeedState = {
  orderedIds: string[];
  entitiesById: Record<string, FeedItem>;
  pages: FeedPage[];
  pendingNewIds: string[];
  activeCursors: Set<string>;
  scrollAnchor: {
    itemId: string;
    offset: number;
  } | null;
};
```

Порядок элементов и сами сущности лучше рассматривать отдельно.

```text
orderedIds
→ определяет порядок ленты

entitiesById
→ хранит актуальную версию записи
```

Это упрощает:

- дедупликацию;
- обновление существующего элемента;
- удаление;
- получение новых версий через realtime;
- повторное использование данных на странице детали.

При объединении страниц элементы дедуплицируют по стабильному `id`.

Например:

```text
page 1: A B C
page 2: C D E
```

результат:

```text
A B C D E
```

Повтор `C` не обязательно означает критичную ошибку API.

Причиной могут быть:

- изменение набора между запросами;
- повторная доставка;
- realtime update;
- граница snapshot;
- retry страницы.

Но большое число дублей нужно измерять: оно может указывать на нестабильный порядок или ошибку cursor.

Если существующий элемент пришёл повторно, сравнивают его версию:

```text
version
updatedAt
revision
```

Правило:

```text
новая version > текущей
→ обновить сущность

новая version < текущей
→ игнорировать старое состояние
```

Нельзя безусловно применять последний физически пришедший ответ.

Запрос более старой страницы может завершиться позже realtime-обновления и вернуть устаревшую версию записи.

React key строят по стабильному `id`:

```tsx
items.map((item) => (
  <FeedItem
    key={item.id}
    item={item}
  />
))
```

Индекс массива использовать нельзя:

```tsx
key={index}
```

При вставке сверху индексы всех элементов изменятся, и React может повторно использовать состояние одного компонента для другой записи.

Следующую страницу обычно загружают через `IntersectionObserver`.

В конце списка располагают sentinel:

```html
<div ref={loadMoreRef}></div>
```

Наблюдатель сообщает, что элемент приблизился к viewport или scroll container.

Важные параметры:

```text
root
rootMargin
threshold
```

`root` определяет область прокрутки.

Если прокручивается не окно браузера, а отдельный контейнер, нужно наблюдать относительно него.

`rootMargin` позволяет начать загрузку заранее:

```text
0px 0px 600px 0px
```

Тогда следующая страница начинает загружаться до того, как пользователь дойдёт до конца.

Слишком большой `rootMargin` создаёт преждевременные запросы, а слишком маленький — заметную паузу у границы.

Обработчик перед запросом проверяет:

```text
hasNextPage
не выполняется ли запрос
cursor ещё актуален
фильтры не изменились
```

Концептуально:

```text
sentinel пересёк границу
→ есть nextCursor?
→ нет активного запроса для cursor?
→ запустить fetch
```

`IntersectionObserver` может вызвать callback несколько раз.

Один cursor не должен создавать несколько одинаковых параллельных запросов.

Полезное правило:

```text
один активный request
на один cursor
```

Query library может дедуплицировать одинаковые запросы, но проверка состояния загрузки всё равно делает логику интерфейса понятнее.

После ответа проверяют, что он относится к актуальной выдаче:

- пользователь не сменился;
- фильтры не изменились;
- feed version совпадает;
- cursor принадлежит текущему списку.

Старый ответ другой выдачи не объединяют с новой.

При изменении:

- фильтра;
- сортировки;
- tenant;
- пользователя;
- режима ранжирования

старые запросы отменяют или игнорируют, очищают порядок и начинают с нового начального cursor.

Если первая порция не заполнила viewport, sentinel может сразу остаться видимым и инициировать загрузку следующей страницы.

Это допустимо, но нужны ограничения:

- `hasNextPage`;
- один запрос за раз;
- максимальное число автоматических догрузок;
- защита от пустых страниц с неизменившимся cursor.

Сервер не должен бесконечно возвращать:

```text
items: []
hasNextPage: true
nextCursor: тот же cursor
```

Клиент может обнаружить такой протокольный сбой и остановить автоматическую загрузку.

Некоторые ленты требуют загрузки в двух направлениях.

Например:

```text
старые сообщения ↑
текущая позиция
новые сообщения ↓
```

или переход по ссылке на элемент в середине истории.

Тогда API может возвращать:

```json
{
  "items": [],
  "previousCursor": "...",
  "nextCursor": "...",
  "hasPreviousPage": true,
  "hasNextPage": true
}
```

Клиент поддерживает два независимых состояния:

```text
loadingPrevious
loadingNext
```

и два sentinel.

При добавлении элементов перед текущим viewport нужно сохранять визуальную позицию.

Иначе список прыгнет вниз на высоту добавленных записей.

Новые записи сверху — отдельная задача.

Если пользователь находится у начала ленты, автоматическая вставка может быть ожидаемой:

```text
новый чат
новые записи журнала
live feed
```

Если пользователь читает середину списка, автоматическая вставка сдвинет текст под глазами.

Безопасная модель:

```text
realtime получил новые записи
→ сохранить их отдельно
→ показать «Появилось 12 новых»
```

По нажатию пользователь:

- переходит к началу;
- либо вставляет записи с сохранением позиции;
- либо открывает новую версию выдачи.

Сохранить позицию можно через опорный элемент.

Перед вставкой запоминают:

```text
anchorElement
anchorTopBefore
```

После вставки измеряют:

```text
anchorTopAfter
```

и компенсируют разницу:

```text
scrollBy(anchorTopAfter - anchorTopBefore)
```

Визуально anchor остаётся на том же месте.

Другой вариант — измерить изменение общей высоты:

```text
scrollHeightBefore
scrollHeightAfter
```

и добавить разницу к `scrollTop`.

Опорный элемент обычно надёжнее при сложных изменениях, потому что изменение высоты может происходить не только сверху.

Если пользователь нажимает:

```text
Показать новые записи
```

интерфейс может явно прокрутить к началу и не выполнять компенсацию.

Правило зависит от ожидаемого сценария.

Чат, новостная лента и журнал мониторинга требуют разного поведения.

Изменение существующей записи не должно менять её место без серверного решения.

Например, изменение текста поста обычно обновляет содержимое на прежней позиции.

Если ranking изменился, сервер может:

- прислать отдельное событие перемещения;
- предложить обновить выдачу;
- оставить порядок неизменным до новой сессии.

Самостоятельная пересортировка одной записи на клиенте может разрушить cursor-модель текущего snapshot.

Удалённую запись убирают из текущего порядка по `id`.

Клиент не пересчитывает cursor из новых индексов.

Продолжение выдачи по-прежнему определяет серверный cursor.

Если удалённый элемент был scroll anchor, выбирают fallback:

- ближайший следующий элемент;
- ближайший предыдущий;
- сохранённый `scrollY`;
- начало загруженного диапазона.

Это лучше определить заранее, чем оставлять случайный скачок.

Для возврата со страницы детали нужно восстановить:

```text
данные
+
структуру списка
+
визуальную позицию
```

Одного `scrollY` часто недостаточно.

Пока пользователь был на странице детали:

- изображения могли загрузиться иначе;
- записи могли обновиться;
- часть DOM могла быть виртуализирована;
- шрифты могли изменить высоту;
- новые элементы могли появиться сверху.

Надёжнее сохранить anchor:

```ts
type ScrollAnchor = {
  itemId: string;
  offsetFromViewportTop: number;
};
```

Также полезно сохранить:

- query и фильтры;
- feed version;
- загруженные страницы;
- cursors;
- направление;
- приблизительный `scrollY`;
- timestamp сохранения;
- navigation entry ID.

Порядок восстановления:

```text
1. Восстановить параметры выдачи.
2. Получить страницы из cache или повторно загрузить их.
3. Отрендерить элемент anchor.
4. Дождаться необходимых размеров.
5. Прокрутить anchor к сохранённому смещению.
6. Проверить последующие layout shifts.
7. Снять состояние restoring.
```

Прокрутка к anchor:

```text
найти DOM-элемент по itemId
→ получить его позицию
→ компенсировать offset
```

Если нужный элемент не загружен, возможны варианты:

- восстановить сохранённые страницы из query cache;
- загрузить страницы до нахождения элемента;
- использовать серверный endpoint «диапазон вокруг ID»;
- перейти к ближайшему доступному элементу;
- показать, что прежняя позиция больше недоступна.

Для очень глубокой позиции последовательная загрузка всех страниц от начала может быть слишком дорогой.

Полезен API:

```http
GET /feed/around/{itemId}
```

который возвращает:

- сам элемент;
- несколько записей до него;
- несколько после;
- cursors обоих направлений.

Это также помогает открывать стабильную ссылку на элемент внутри длинной выдачи.

Для обычных документов браузер умеет восстанавливать scroll position через history.

```js
history.scrollRestoration = "auto";
```

Если браузер возвращает страницу из bfcache, DOM и положение могут сохраниться почти полностью.

В этом случае приложение не должно без необходимости:

- очищать список;
- повторно прокручивать страницу;
- запускать конкурирующее ручное восстановление.

После события восстановления проверяют:

- была ли страница восстановлена из bfcache;
- сохранились ли данные;
- актуальны ли соединения и запросы;
- требуется ли refetch.

Ручной режим:

```js
history.scrollRestoration = "manual";
```

включают только тогда, когда приложение действительно полностью управляет восстановлением.

Иначе можно отключить нативное поведение и не реализовать эквивалент.

Ручная логика особенно нужна для:

- виртуализированного списка;
- клиентского router;
- удалённых страниц;
- перехода по anchor;
- изменяемых высот.

Медиа должно резервировать место заранее.

Для изображения задают:

- `width` и `height`;
- `aspect-ratio`;
- placeholder;
- стабильный контейнер.

Иначе после восстановления:

```text
anchor установлен
→ изображение загрузилось
→ высота элемента выросла
→ позиция снова сдвинулась
```

Для неизвестной высоты можно:

- использовать приблизительную высоту;
- сохранять измерения;
- наблюдать изменения через `ResizeObserver`;
- повторно компенсировать положение anchor.

Компенсация должна иметь предел, чтобы интерфейс не продолжал бороться с пользовательской прокруткой.

После того как пользователь сам прокрутил экран, автоматическое восстановление обычно прекращают.

Длинная сессия может накопить:

- тысячи React-компонентов;
- тысячи DOM-узлов;
- большой query cache;
- изображения;
- обработчики;
- измерения размеров.

Сначала измеряют:

- число DOM-узлов;
- использование памяти;
- render duration;
- layout;
- paint;
- long tasks;
- плавность прокрутки.

Возможные меры:

```text
виртуализация DOM
windowing страниц в памяти
ограничение cache
lazy media
удаление тяжёлых ресурсов
```

Виртуализация оставляет в DOM только видимый диапазон и небольшой overscan.

Она не заменяет server pagination.

```text
pagination
→ ограничивает количество полученных данных

virtualization
→ ограничивает количество смонтированных элементов
```

Для элементов переменной высоты виртуализатор должен:

- оценивать начальную высоту;
- измерять фактическую;
- обновлять offsets;
- сохранять anchor при изменении измерений.

Виртуализация усложняет:

- focus;
- screen reader;
- browser find;
- печать;
- восстановление прокрутки;
- раскрывающиеся элементы;
- переход по hash;
- загрузку в двух направлениях.

Старые страницы можно удалять не только из DOM, но и из памяти.

Это называется windowing данных.

Например:

```text
оставить текущие 5 страниц
→ удалить далёкие страницы сверху
```

Но перед удалением нужно сохранить:

- высоту удалённого диапазона;
- cursor для обратной загрузки;
- anchor;
- порядок ID;
- возможность восстановить страницу.

Вместо удалённых элементов может оставаться spacer:

```text
верхний placeholder высотой 12 400 px
```

Когда пользователь возвращается вверх, клиент:

```text
загружает предыдущую страницу
→ заменяет часть spacer реальными элементами
→ компенсирует изменение высоты
```

Если просто удалить старые элементы без сохранения геометрии, scroll position резко изменится.

Windowing данных оправдан только при реальной проблеме памяти.

Он значительно сложнее обычной cursor pagination с DOM-виртуализацией.

Интерфейс должен различать состояния:

- initial loading;
- initial error;
- empty;
- loaded;
- loading next page;
- loading previous page;
- next page error;
- previous page error;
- refreshing;
- new items available;
- stale feed;
- cursor expired;
- end of list;
- offline;
- restoring scroll.

Ошибка первой страницы означает, что основного содержимого ещё нет.

Показывают:

```text
сообщение
кнопку повторить
```

Ошибка продолжения не должна удалять уже загруженные элементы.

На границе списка показывают:

```text
Не удалось загрузить продолжение.
Повторить
```

Повтор использует тот же cursor.

Ошибка не должна превращаться в:

```text
Вы дошли до конца
```

потому что достоверно неизвестно, существуют ли следующие записи.

При `cursor expired` интерфейс может показать:

```text
Лента обновилась.
Получить актуальную выдачу
```

и отдельно сохранить текущий просмотр до решения пользователя.

Для доступности каждая самостоятельная запись может использовать:

```html
<article>
```

с доступным заголовком или подписью.

Автоматическое добавление элементов не должно переносить focus.

Если пользователь активировал кнопку:

```text
Загрузить ещё
```

после добавления focus обычно остаётся на кнопке либо перемещается по заранее определённому правилу.

Не следует автоматически отправлять focus на первый новый элемент без необходимости.

Кнопка «Загрузить ещё» обеспечивает:

- доступный fallback;
- контроль пользователя;
- работу без автоматического observer;
- понятную точку повторной загрузки.

Нужен способ перейти за пределы ленты:

```text
Перейти к содержимому после списка
```

или постоянная навигация, потому что автоматически растущая лента может сделать footer недостижимым.

Сообщение:

```text
Появилось 12 новых записей
```

можно объявить через спокойную status region.

Не следует объявлять screen reader каждую новую запись отдельно в активном потоке.

Контейнер можно временно пометить:

```html
aria-busy="true"
```

во время группового обновления, обязательно возвращая значение `false`.

Роль:

```text
feed
```

добавляют только при реализации полного ARIA-паттерна.

Она предполагает согласованную структуру статей, клавиатурное поведение и корректные сведения о позиции элементов.

Обычный семантический список или набор `<article>` часто проще и надёжнее.

Infinite scroll должен иметь серверно доступную основу, если важны:

- SEO;
- sharing;
- работа без JavaScript;
- стабильные ссылки.

Модель progressive enhancement:

```text
сервер возвращает первую страницу
→ в HTML есть ссылка на следующую страницу
→ JavaScript перехватывает её и добавляет данные в ленту
```

Например:

```html
<a href="/feed?page=2">
  Следующая страница
</a>
```

Для cursor API публичное индексируемое представление может отдельно использовать серверные page URL.

Поисковый робот не должен зависеть от прокрутки viewport и `IntersectionObserver`, чтобы найти продолжение.

У каждой записи должен быть собственный стабильный URL:

```text
/posts/42
```

Ссылка на позицию внутри ленты может содержать:

- фильтры;
- anchor ID;
- режим выдачи.

Например:

```text
/feed?category=frontend&anchor=post-42
```

Не следует использовать непрозрачный краткоживущий cursor как единственную публичную ссылку.

Он может:

- истечь;
- зависеть от пользователя;
- быть непонятен серверу страницы;
- измениться после нового ranking.

Безопасность и права остаются серверной обязанностью.

Сервер проверяет:

- пользователя;
- tenant;
- доступ к каждой записи;
- фильтры;
- разрешённые поля;
- лимит страницы.

Cache key должен включать контекст, влияющий на выдачу:

```text
user
tenant
filters
ranking version
experiment
locale
```

После logout или смены пользователя персональные страницы и сущности очищают либо строго изолируют.

В URL, analytics и logs не следует без необходимости записывать чувствительные параметры выдачи.

Для observability полезны:

- время первой страницы;
- время следующей страницы;
- error rate продолжения;
- число повторов observer;
- количество дублей;
- количество cursor-expired;
- число элементов в DOM;
- размер кэша;
- число восстановлений scroll;
- успешность восстановления anchor;
- величина layout shift;
- длительность long tasks;
- число новых элементов, ожидающих вставки.

Полезный контекст:

```text
feed type
page direction
page size
release
ranking version
request ID
```

Не нужно записывать:

- полный персонализированный cursor;
- содержимое записей;
- access token;
- чувствительные фильтры;
- персональные данные.

Тестовая стратегия включает:

- первую страницу;
- следующую страницу;
- предыдущую страницу;
- конец списка;
- повторное срабатывание observer;
- один request на cursor;
- смену фильтра;
- устаревший ответ;
- дубликаты;
- более новую и старую версии сущности;
- удаление;
- новые элементы сверху;
- сохранение anchor;
- ошибка продолжения;
- retry;
- cursor expiration;
- возврат со страницы детали;
- восстановление из cache;
- удалённый anchor;
- медленные изображения;
- bfcache;
- virtualization;
- windowing данных;
- долгую сессию;
- клавиатуру;
- screen reader;
- кнопку загрузки;
- переход за пределы ленты;
- SEO-ссылки продолжения.

Практический порядок проектирования:

```text
1. Определить, нужен ли infinite scroll.
2. Зафиксировать стабильный порядок и cursor contract.
3. Разделить pages, entities и scroll state.
4. Настроить загрузку через observer и явную кнопку.
5. Защититься от повторных и устаревших запросов.
6. Спроектировать дедупликацию и версии сущностей.
7. Определить поведение новых и удалённых записей.
8. Сохранять anchor, cache страниц и параметры URL.
9. Восстанавливать позицию после готовности размеров.
10. Добавить virtualization только после измерений.
11. Проверить accessibility, SEO и длительную сессию.
```

Главный принцип:

```text
cursor
→ определяет серверное продолжение

stable id
→ определяет сущность и React key

version
→ определяет актуальное содержимое

anchor
→ определяет визуальную позицию

cache страниц
→ позволяет восстановить структуру ленты

observer
→ только запускает загрузку,
но не гарантирует её уникальность
```

</dd>

## Дополнительные вопросы

<details>
<summary><strong>Почему для изменяющейся ленты cursor pagination обычно надёжнее offset pagination?</strong></summary>

<dl>
<dd>
<h2></h2>

Offset означает:

```text
пропусти N записей
```

Если перед следующим запросом сверху добавилась новая запись, позиции сдвинутся.

Возможны:

- дубликаты;
- пропуски;
- переход записи на соседнюю страницу.

Cursor означает:

```text
продолжи после известной границы стабильного порядка
```

Для корректности порядок должен быть детерминированным:

```text
createdAt DESC, id DESC
```

Cursor создаёт сервер и возвращает клиенту как непрозрачное значение.

Если выдача ранжированная, cursor дополнительно связывают с версией или snapshot порядка.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как обрабатывать повторяющиеся, изменённые и удалённые элементы?</strong></summary>

<dl>
<dd>
<h2></h2>

Элементы дедуплицируют по стабильному `id`.

Если существующая запись пришла повторно, сравнивают:

```text
version
updatedAt
revision
```

Более новая версия обновляет сущность, а старая не должна перезаписывать актуальные данные.

Удаление убирает `id` из текущего порядка.

Клиент не пересчитывает cursor по индексам: точку продолжения по-прежнему определяет сервер.

Дубликаты могут появляться из-за изменения данных, retry или realtime, поэтому защита нужна даже при корректном API.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать, если <code>IntersectionObserver</code> несколько раз заметил нижний элемент?</strong></summary>

<dl>
<dd>
<h2></h2>

Перед запросом проверяют:

```text
hasNextPage
nextCursor
нет активного запроса для cursor
выдача всё ещё актуальна
```

Один cursor должен соответствовать не более чем одному активному запросу.

После ответа sentinel перемещается за новые элементы, и observer может запустить следующую страницу.

Если первая порция не заполнила viewport, последовательная догрузка допустима, но нужен предел и защита от ответа:

```text
items=[]
hasNextPage=true
nextCursor не изменился
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как добавлять новые записи и не сдвигать то, что пользователь читает?</strong></summary>

<dl>
<dd>
<h2></h2>

Если пользователь находится не у начала, новые записи временно хранят отдельно:

```text
Появилось 12 новых записей
```

По действию пользователя их:

- вставляют и переходят к началу;
- либо добавляют с компенсацией позиции anchor.

Для компенсации запоминают положение опорного элемента до и после вставки и корректируют `scrollTop` на разницу.

Если пользователь уже находится вверху и ожидает живой поток, автоматическая вставка может быть допустима.

Поведение зависит от сценария: чат, журнал и новостная лента имеют разные ожидания.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как восстановить прокрутку после возврата со страницы детали?</strong></summary>

<dl>
<dd>
<h2></h2>

Сохраняют:

- фильтры;
- feed version;
- загруженные страницы;
- cursors;
- anchor ID;
- смещение anchor от верхней границы;
- приблизительный `scrollY`.

При возврате:

```text
восстановить данные
→ отрендерить anchor
→ дождаться размеров
→ прокрутить к сохранённому смещению
```

Одного `scrollY` недостаточно, если изменяются высоты, загружаются изображения или список виртуализирован.

Нативное восстановление history сохраняют, если оно корректно работает.

Ручной режим включают только при полноценной собственной реализации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда ленте нужна виртуализация?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда измерения показывают проблемы:

- слишком много DOM-узлов;
- дорогой render;
- частые layout;
- рост памяти;
- потеря плавности прокрутки.

Виртуализация оставляет в DOM видимый диапазон и overscan.

Она не заменяет server pagination.

Для элементов переменной высоты нужно измерять строки и сохранять anchor при изменении размеров.

Виртуализация усложняет focus, screen reader, browser find, печать и scroll restoration, поэтому её не добавляют заранее для короткой ленты.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как сделать бесконечную ленту доступной с клавиатуры и экранным диктором?</strong></summary>

<dl>
<dd>
<h2></h2>

Самостоятельные записи размечают семантически, например через:

```html
<article>
```

Автоматическое добавление не переносит focus.

Оставляют явную кнопку:

```text
Загрузить ещё
```

и способ перейти к содержимому после ленты.

Новые записи не объявляют по одной непрерывным потоком.

Можно сообщить:

```text
Появилось 12 новых записей
```

через спокойную status region.

`role="feed"` используют только при реализации полного ARIA-паттерна. Обычный список или набор статей часто проще и надёжнее.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как показывать ошибку загрузки продолжения?</strong></summary>

<dl>
<dd>
<h2></h2>

Уже загруженные записи остаются на месте.

На нижней или верхней границе показывают:

```text
Не удалось загрузить продолжение.
Повторить
```

Повтор использует тот же cursor.

Ошибка не подменяется концом списка.

После успешного retry страницу объединяют идемпотентно, а элементы дедуплицируют по `id`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как совместить бесконечную прокрутку с поисковой индексацией и ссылками на результат?</strong></summary>

<dl>
<dd>
<h2></h2>

У ленты должно оставаться серверно доступное представление.

Первая страница возвращает содержимое без обязательного JavaScript, а продолжение имеет обычную ссылку или URL пагинации.

Infinite scroll становится улучшением интерфейса:

```text
серверная ссылка
→ JavaScript перехватывает переход
→ данные добавляются в текущий список
```

У записи должен быть собственный стабильный URL.

Для позиции внутри ленты сохраняют фильтры и anchor ID.

Краткоживущий персональный cursor не используют как единственную публичную ссылку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что меняется, если порядок рассчитывается персональным алгоритмом?</strong></summary>

<dl>
<dd>
<h2></h2>

Порядок зависит от:

- пользователя;
- времени;
- версии модели;
- эксперимента;
- истории действий.

Сервер связывает cursor с краткоживущей версией выдачи:

```text
feedSessionId
rankingVersion
snapshotId
```

Cache key также включает пользовательский контекст и параметры ranking.

При истечении версии API возвращает явную ошибку.

Клиент не должен незаметно продолжать страницы с новым алгоритмом, смешивая два разных порядка.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что тестировать у бесконечной ленты?</strong></summary>

<dl>
<dd>
<h2></h2>

Проверяют:

- первую страницу;
- загрузку вперёд и назад;
- конец списка;
- повторный observer callback;
- один запрос на cursor;
- ответы в обратном порядке;
- смену фильтра;
- дубликаты;
- версии сущностей;
- удаление;
- новые записи сверху;
- сохранение anchor;
- ошибку продолжения;
- cursor expiration;
- возврат со страницы детали;
- медиа с изменяемой высотой;
- bfcache;
- виртуализацию;
- удаление страниц из памяти;
- долгую сессию.

Отдельно проверяют клавиатуру, screen reader, кнопку загрузки, сохранение focus и возможность перейти за пределы ленты.

Производительность измеряют по памяти, DOM-узлам, long tasks, layout shifts и плавности прокрутки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда выбрать infinite scroll, кнопку «Загрузить ещё» или обычную пагинацию?</strong></summary>

<dl>
<dd>
<h2></h2>

Infinite scroll подходит для последовательного просмотра без заранее известной цели.

Кнопка «Загрузить ещё» подходит, когда нужен пользовательский контроль и достижимый footer.

Обычная пагинация удобнее, если пользователь должен:

- перейти к номеру страницы;
- вернуться к известному диапазону;
- сравнивать страницы;
- использовать стабильные URL;
- искать конкретный результат.

Можно сочетать observer и кнопку, используя один обработчик загрузки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужна загрузка ленты в двух направлениях?</strong></summary>

<dl>
<dd>
<h2></h2>

Она нужна для:

- истории чата;
- журнала вокруг выбранного события;
- открытия ссылки на элемент в середине списка;
- восстановления глубокой позиции без загрузки от начала.

API возвращает:

```text
previousCursor
nextCursor
```

Клиент отдельно управляет загрузкой вверх и вниз.

При добавлении элементов сверху нужно компенсировать изменение высоты, чтобы текущий anchor не прыгнул.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как настроить <code>IntersectionObserver</code> для предварительной загрузки?</strong></summary>

<dl>
<dd>
<h2></h2>

Указывают правильный `root` и положительный нижний `rootMargin`.

Например:

```text
0px 0px 600px 0px
```

запускает загрузку до непосредственного появления sentinel.

Значение подбирают по:

- скорости сети;
- размеру страницы;
- скорости прокрутки;
- стоимости запроса.

Слишком маленькое значение создаёт паузу у конца списка.

Слишком большое загружает данные, до которых пользователь может не дойти.

Observer должен запускать тот же доступный обработчик, что и кнопка «Загрузить ещё».

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как удалять старые страницы из памяти и не ломать прокрутку?</strong></summary>

<dl>
<dd>
<h2></h2>

Перед удалением сохраняют:

- суммарную высоту диапазона;
- cursor обратной загрузки;
- anchor;
- порядок элементов;
- измерения строк при необходимости.

Удалённый диапазон заменяют spacer соответствующей высоты.

При возврате пользователя:

```text
загрузить страницу
→ заменить часть spacer
→ компенсировать разницу высот
```

Простое удаление DOM и данных изменит `scrollHeight` и вызовет скачок.

Такой windowing добавляют только при подтверждённой проблеме памяти.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем обратная лента чата отличается от обычной infinite scroll?</strong></summary>

<dl>
<dd>
<h2></h2>

В чате пользователь обычно находится около новых сообщений внизу, а старые загружаются сверху.

При загрузке старой страницы текущие сообщения должны остаться на том же месте viewport.

Новые сообщения можно автоматически добавлять внизу, только если пользователь уже находится около нижней границы.

Если он читает историю выше, показывают:

```text
Новые сообщения
```

без автоматической прокрутки.

Кнопка перехода вниз возвращает пользователя к актуальным сообщениям.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать, если сохранённый опорный элемент был удалён?</strong></summary>

<dl>
<dd>
<h2></h2>

Используют заранее определённый fallback:

- следующий элемент после anchor;
- предыдущий элемент;
- ближайший элемент из восстановленной страницы;
- сохранённый `scrollY`;
- начало загруженного диапазона.

Если сервер поддерживает endpoint диапазона вокруг ID, он может сообщить, что элемент удалён, и вернуть ближайшее доступное окружение.

Интерфейс не должен бесконечно пытаться найти отсутствующий DOM-элемент.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Ключевое решение |
| --- | --- |
| Хронологический журнал | Cursor по дате и `id`, дедупликация и стабильная граница |
| Персональная лента | Версия выдачи внутри cursor и отдельный cache пользователя |
| Возврат из карточки товара | Cache страниц, anchor ID и восстановление после размеров |
| Новые записи во время чтения | Счётчик новых элементов без автоматического сдвига |
| История чата | Загрузка вверх и сохранение позиции при prepend |
| Ссылка на глубокий элемент | API диапазона вокруг ID и cursors двух направлений |
| Очень длинная сессия | Виртуализация и windowing после измерений |
| Индексируемый каталог | Серверные page URL и progressive enhancement |
| Доступная лента | Явная кнопка загрузки и достижимое содержимое после списка |
