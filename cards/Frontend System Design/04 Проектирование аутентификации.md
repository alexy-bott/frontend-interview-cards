## Вопрос

<br>

 💬 **Как спроектировать вход, защищённые маршруты и обновление токенов?**

<h2></h2>

<br>
<dl>
<dd>

Сначала разделяют несколько задач:

- **authentication** — установить, кто пользователь;
- **authorization** — проверить, что ему разрешено;
- **session management** — управлять сроком жизни входа, обновлением, выходом и отзывом;
- **frontend UX** — показывать правильные маршруты и состояния интерфейса.

OAuth 2.0 и OpenID Connect тоже решают разные задачи.

**OAuth 2.0** предоставляет клиенту право обращаться к защищённому API.

**OpenID Connect**, или OIDC, добавляет поверх OAuth механизм аутентификации пользователя.

Упрощённо:

```text
ID token
→ информация о результате аутентификации для клиента

access token
→ право обращаться к resource server
```

ID token не следует использовать как произвольный access token для API, если такой контракт явно не определён identity provider.

Архитектуру выбирают до реализации frontend-кода.

Основные варианты:

```text
серверная сессия
BFF
прямой OAuth client в SPA
```

Для собственного веб-приложения, где frontend и backend принадлежат одному продукту, часто проще использовать серверную сессию или BFF — Backend for Frontend.

При серверной сессии браузер хранит только случайный идентификатор:

```text
browser
→ session cookie
→ application server
→ session storage
```

Права, пользователь и остальные данные сессии находятся на сервере.

Session ID не должен содержать:

- email;
- user ID;
- роль;
- персональные данные;
- бизнес-информацию.

Он должен быть случайным непрозрачным идентификатором.

При BFF браузер также работает с cookie-сессией, а BFF хранит OAuth tokens вне JavaScript-контекста браузера:

```text
browser
→ HttpOnly session cookie
→ BFF
→ access token
→ API
```

Frontend вызывает BFF, а не получает access token для прямой работы с API.

Преимущества BFF:

- refresh token не доступен JavaScript;
- access token не нужно хранить в SPA;
- обновление токенов централизовано;
- проще синхронизировать несколько вкладок;
- API можно скрыть за same-origin endpoint;
- уменьшается ущерб от кражи token через XSS.

BFF не делает XSS безопасным.

Вредоносный script всё ещё может отправлять разрешённые запросы через BFF от имени пользователя, пока выполняется в его браузере. Поэтому отдельно нужны защита от XSS, ограничение прав и серверная авторизация каждой операции.

Session cookie обычно получает:

```text
Secure
HttpOnly
SameSite
```

`Secure` ограничивает передачу HTTPS-соединением.

`HttpOnly` не позволяет обычному JavaScript прочитать cookie.

`SameSite` ограничивает часть cross-site-сценариев отправки cookie.

Для cookie конкретного host можно использовать префикс:

```text
__Host-
```

Например:

```http
Set-Cookie: __Host-session=<value>; Path=/; Secure; HttpOnly; SameSite=Lax
```

Cookie с `__Host-` должна:

- иметь `Secure`;
- иметь `Path=/`;
- не иметь атрибут `Domain`.

Она привязана к конкретному host и действует для всех его путей.

Если cookie нужен более узкий `Path`, префикс `__Host-` для неё не подходит.

Значение `SameSite` выбирают по архитектуре.

`Strict` даёт более жёсткое ограничение, но может мешать некоторым переходам на сайт извне.

`Lax` часто является компромиссом для first-party web application.

`None` требуется для отдельных cross-site-сценариев и обязательно сочетается с `Secure`.

Cookie должна иметь ограниченный срок жизни.

Серверная сессия может использовать:

- idle timeout — срок бездействия;
- absolute timeout — максимальную продолжительность сессии;
- принудительный отзыв;
- повторную аутентификацию перед критичным действием.

После успешного входа session ID обновляют, чтобы идентификатор, существовавший до аутентификации, нельзя было использовать для session fixation.

После повышения привилегий, например включения административной роли, сессию также полезно обновить или повторно проверить по политике системы.

Если SPA напрямую работает с OAuth 2.0 и OIDC, она является public client: браузерное приложение не может надёжно хранить client secret.

Современный поток:

```text
Authorization Code Flow
+
PKCE
```

Implicit Flow для нового browser-based приложения не используют.

Упрощённый процесс:

```text
1. SPA создаёт code_verifier.
2. Вычисляет code_challenge.
3. Перенаправляет пользователя на authorization server.
4. Получает одноразовый authorization code.
5. Обменивает code вместе с code_verifier.
6. Получает tokens.
```

PKCE связывает начало входа и обмен authorization code.

Перехваченного code недостаточно без соответствующего `code_verifier`.

При входе также используют:

- `state`;
- OIDC `nonce`;
- заранее зарегистрированный redirect URI.

`state` связывает callback с начатой клиентом операцией и помогает защищать flow от подмены.

`nonce` связывает OIDC authentication request и полученный ID token.

Redirect URI проверяют точным способом по правилам identity provider. Нельзя принимать произвольный callback URL.

Access token делают:

- короткоживущим;
- ограниченным нужными scopes;
- ограниченным ожидаемым API;
- минимальным по привилегиям.

Refresh token является более долгоживущей учётной информацией.

Для public client refresh token должен использовать:

- rotation с обнаружением повторного использования;
- либо sender-constraining.

При refresh token rotation каждый успешный обмен выдаёт новый refresh token:

```text
refresh token 1
→ access token 2 + refresh token 2
```

Предыдущий refresh token становится недействительным.

Если старый token неожиданно применяется повторно, сервер может считать цепочку скомпрометированной и отозвать текущую сессию или grant.

Sender-constrained token дополнительно требует доказать владение криптографическим ключом, например через DPoP.

Это уменьшает пользу украденной строки token, но не устраняет все последствия XSS: вредоносный код, выполняющийся внутри приложения, может инициировать операции в пользовательском контексте.

Для browser application предпочтительно не хранить credentials в:

```text
localStorage
sessionStorage
```

Любой JavaScript, выполняющийся в том же origin, может прочитать их при XSS.

Кроме того, `localStorage` сохраняет значение между browser sessions и увеличивает период возможной утечки.

Если прямой SPA вынужден получать access token, его часто держат только в памяти либо изолируют в отдельном browser-контексте по выбранной архитектуре.

Хранение в памяти:

- уменьшает срок сохранения;
- не оставляет token после полного закрытия приложения;
- не делает token доступным через Web Storage.

Но оно не защищает от активного XSS.

Вредоносный script может:

- получить token через доступный код приложения;
- инициировать запрос;
- начать новый OAuth flow;
- действовать от имени пользователя.

Поэтому основная защита включает:

- предотвращение XSS;
- CSP;
- контроль third-party scripts;
- короткий срок access token;
- минимальные scopes;
- server-side authorization.

Cookie-authentication требует защиты от CSRF.

`HttpOnly` запрещает читать cookie, но браузер автоматически прикладывает её к подходящему запросу.

Для state-changing операций применяют сочетание:

- подходящего `SameSite`;
- проверки `Origin`;
- при необходимости проверки `Referer`;
- CSRF token;
- запрета изменяющих операций через `GET`;
- дополнительных browser headers или Fetch Metadata по политике backend.

CORS не является полноценной CSRF-защитой.

CORS регулирует, может ли frontend-код прочитать cross-origin response. Он не гарантирует, что браузер вообще не отправит запрос с cookie.

От XSS защищаются отдельно:

- безопасным выводом данных;
- отказом от небезопасного HTML;
- Content Security Policy;
- контролем сторонних scripts;
- обновлением зависимостей;
- ограничением возможных действий session.

Защищённый маршрут в браузере является UX-механизмом, а не границей безопасности.

Например:

```tsx
if (!isAuthenticated) {
  return <Navigate to="/login" />;
}
```

помогает не показывать пользователю страницу приложения.

Но пользователь может:

- изменить client state;
- вызвать API напрямую;
- повторить запрос из другого клиента;
- открыть route без frontend router.

Сервер обязан проверять на каждом защищённом запросе:

- действующую сессию или token;
- пользователя;
- роль;
- permission;
- tenant;
- доступ к конкретному ресурсу;
- актуальный статус аккаунта.

Frontend скрывает недоступную кнопку для удобства:

```tsx
{canDelete && <DeleteButton />}
```

но backend повторно проверяет право удаления.

Полезно различать статусы:

```text
401 Unauthorized
→ действующей аутентификации нет

403 Forbidden
→ пользователь распознан, но действие запрещено
```

При `401` может быть допустима попытка обновления сессии.

При `403` обычный refresh чаще всего ничего не изменит.

Иногда API намеренно возвращает `404` вместо `403`, чтобы не раскрывать существование защищённого ресурса. Это должно быть частью согласованного серверного контракта.

Frontend-состояние authentication не должно начинаться с предположения:

```text
пользователь не вошёл
```

Пока серверная сессия не проверена, состояние неизвестно.

Полезная модель:

```text
unknown
authenticated
unauthenticated
forbidden
error
```

`unknown` означает, что приложение ещё загружает или проверяет сессию.

В SPA при старте можно выполнить запрос:

```text
GET /session
```

или:

```text
GET /me
```

До ответа показывают стабильное loading-состояние, а не защищённый контент и не мгновенный redirect на login.

Иначе возникает мигание:

```text
login
→ protected page
```

или:

```text
protected content
→ login
```

При SSR сервер может проверить cookie до отправки страницы:

```text
authenticated
→ вернуть защищённый HTML

unauthenticated
→ redirect на login

authenticated без permission
→ вернуть 403-состояние
```

Так защищённый контент не появляется до клиентской проверки.

В Next.js middleware может выполнить раннюю грубую проверку наличия сессии или cookie.

Но middleware не заменяет авторизацию в:

- Route Handler;
- Server Action;
- backend API;
- операции с конкретным ресурсом.

Права могут измениться между navigation и mutation, поэтому проверку выполняют в месте защищённой операции.

После входа пользователя часто возвращают на исходный маршрут.

Например:

```text
/orders/42
→ login
→ /orders/42
```

`returnUrl` должен быть проверенным внутренним путём.

Нельзя безусловно использовать:

```text
?returnUrl=https://evil.example
```

иначе приложение создаёт open redirect.

Безопасный вариант принимает только:

- относительный внутренний путь;
- маршрут из allowlist;
- URL того же ожидаемого origin.

OAuth redirect URI регистрируют у identity provider заранее и не смешивают с произвольным пользовательским `returnUrl`.

Если API использует access token и refresh flow, обработку `401` централизуют в API-слое.

Не каждый `401` автоматически означает:

```text
access token истёк
```

Это может быть:

- неверный login;
- отозванная сессия;
- неправильная аудитория token;
- ошибка самого refresh endpoint;
- окончательная блокировка пользователя.

Запускать refresh лучше по согласованному признаку:

- endpoint допускает обновление;
- ответ содержит стабильный auth error code;
- `WWW-Authenticate` или другой контракт указывает на истёкший token.

При нескольких одновременных `401` используют **single flight** — один общий refresh request.

Сценарий без координации:

```text
request A → 401
request B → 401
request C → 401

A запускает refresh
B запускает refresh
C запускает refresh
```

При rotation первый refresh может сделать прежний refresh token недействительным, а остальные запросы создадут конфликт или reuse detection.

Правильная модель:

```text
A, B, C получили подходящий 401
→ создаётся один refreshPromise
→ остальные запросы ожидают его
→ refresh успешен
→ исходные запросы повторяются
```

После ошибки refresh:

```text
refreshPromise rejected
→ ожидающие запросы завершаются ошибкой
→ session state очищается
→ пользователь переводится к login
```

Refresh endpoint исключают из общего механизма.

Иначе:

```text
API → 401
refresh → 401
interceptor запускает refresh снова
→ бесконечный цикл
```

Исходный запрос повторяют не более одного раза.

У запроса можно хранить внутренний признак:

```text
alreadyRetried
```

Повтор mutation требует отдельной осторожности.

Клиент должен быть уверен, что `401` был возвращён до выполнения бизнес-операции и что request body можно повторно отправить.

Для операций вроде:

- создания заказа;
- платежа;
- отправки большого stream;
- загрузки файла

нужны согласованный контракт API и при необходимости idempotency key.

Иначе автоматический retry может создать повторный эффект.

Несколько вкладок создают отдельную проблему.

Даже если внутри одной вкладки используется single flight, две вкладки могут одновременно выполнить refresh:

```text
tab A → refresh token 1
tab B → refresh token 1
```

При rotation один запрос обновит token, а второй применит уже недействительный token.

В BFF или серверной сессии refresh централизован на сервере, поэтому браузерные вкладки не управляют token chain напрямую.

Для прямого browser client возможны:

- координация через `BroadcastChannel`;
- browser lock;
- общий worker;
- повторное получение актуального auth state;
- обработка reuse detection как завершения сессии.

Межвкладочная координация сложна и является дополнительным аргументом в пользу BFF для first-party приложения.

Выход должен завершать сессию на сервере.

Недостаточно выполнить:

```text
isAuthenticated = false
```

Правильный logout:

```text
1. Отозвать серверную сессию или refresh grant.
2. Удалить session cookie.
3. Очистить персональный query cache.
4. Очистить auth и permission state.
5. Отменить пользовательские запросы.
6. Закрыть WebSocket и SSE.
7. Удалить чувствительные drafts.
8. Сообщить другим вкладкам.
9. Перейти к публичному экрану.
```

При удалении cookie сервер должен использовать совместимые атрибуты пути и домена, с которыми cookie была установлена.

Для `__Host-` cookie это тот же host и:

```text
Path=/
```

Другим вкладкам отправляют событие через:

```text
BroadcastChannel
```

Они очищают локальное состояние и закрывают realtime-соединения.

Это улучшает UX, но сервер остаётся источником истины.

Даже если вкладка пропустила событие, отозванная сессия больше не должна принимать запросы.

Права пользователя могут измениться без logout:

- роль отозвана;
- пользователь заблокирован;
- tenant отключён;
- доступ к ресурсу удалён.

Frontend не должен считать permissions вечными.

Актуальность можно поддерживать через:

- ответ `/me` или `/session`;
- ограниченный cache time;
- реакцию на `403`;
- realtime-событие;
- принудительную инвалидацию session.

После изменения прав сервер сразу начинает применять новое правило. Frontend затем обновляет интерфейс, но не является источником авторизации.

Auth-события нужно наблюдать без раскрытия credentials.

Полезно логировать:

- результат входа;
- тип flow;
- стабильный error code;
- environment;
- release;
- request ID;
- факт refresh success/failure;
- причину logout;
- факт `401` или `403`;
- длительность проверки сессии.

Нельзя логировать:

- access token;
- refresh token;
- session cookie;
- authorization code;
- code verifier;
- password;
- полный `Authorization` header;
- полный callback URL с чувствительными параметрами.

Для диагностики используют безопасные идентификаторы операции или сессии, которые сами не являются credentials.

Практический порядок проектирования:

```text
1. Разделить authentication, authorization и session management.
2. Выбрать server session, BFF или direct browser OAuth.
3. Определить cookie и CSRF-защиту.
4. Зафиксировать OAuth/OIDC flow и callback validation.
5. Определить состояния auth при старте.
6. Защитить API независимо от route guard.
7. Спроектировать single-flight refresh.
8. Учесть retry mutation и несколько вкладок.
9. Спроектировать server-side logout и отзыв.
10. Очистить персональные данные и realtime после logout.
11. Добавить наблюдаемость без tokens.
12. Проверить flow автоматическими и security-тестами.
```

</dd>

## Дополнительные вопросы

<details>
<summary><strong>Чем аутентификация отличается от авторизации?</strong></summary>

<dl>
<dd>
<h2></h2>

Аутентификация определяет, кто пользователь:

```text
session
OIDC login
access token
```

Авторизация определяет, что ему разрешено:

```text
открыть операцию API
изменить конкретный ресурс
видеть данные tenant
```

Пользователь может успешно войти, но получить:

```http
403 Forbidden
```

на отдельное действие.

Frontend скрывает недоступные команды и объясняет состояние, но сервер остаётся источником истины по правам.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему клиентская проверка маршрута (<code>route guard</code>) не является настоящей защитой?</strong></summary>

<dl>
<dd>
<h2></h2>

Route guard выполняется в браузере перед отображением страницы.

Пользователь может:

- изменить client state;
- открыть DevTools;
- вызвать API напрямую;
- использовать другой HTTP-клиент.

Поэтому route guard защищает пользовательский сценарий, а не данные.

Настоящая защита находится на сервере.

Каждая операция проверяет:

- сессию или token;
- permission;
- tenant;
- доступ к конкретному ресурсу;
- актуальный статус пользователя.

Клиентская проверка нужна, чтобы направить пользователя к login или показать отсутствие доступа без лишнего запроса интерфейса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где хранить идентификатор сессии, access token и refresh token?</strong></summary>

<dl>
<dd>
<h2></h2>

Для first-party web application предпочтительна:

- серверная сессия;
- либо BFF.

Браузер хранит session ID в защищённой cookie:

```text
Secure
HttpOnly
SameSite
```

OAuth tokens остаются на сервере.

`localStorage` и `sessionStorage` не подходят для credentials: JavaScript того же origin может прочитать их при XSS.

Если direct SPA вынужден работать с access token, его часто держат только в памяти или изолированном browser-контексте.

Это уменьшает постоянство token, но не защищает от активного вредоносного script.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>HttpOnly</code> cookie не отменяет защиту от CSRF?</strong></summary>

<dl>
<dd>
<h2></h2>

`HttpOnly` запрещает JavaScript читать cookie.

Но браузер автоматически прикладывает её к подходящему запросу.

Поэтому злоумышленник может попытаться инициировать state-changing запрос с другого сайта, не зная значения cookie.

Для защиты используют:

- подходящий `SameSite`;
- проверку `Origin`;
- CSRF token;
- запрет изменения через `GET`;
- дополнительные серверные проверки.

`HttpOnly` защищает конфиденциальность cookie при XSS, но не доказывает, что запрос создан доверенным интерфейсом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>401</code> отличается от <code>403</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`401 Unauthorized` означает, что запрос не имеет действующей аутентификации:

- session отсутствует;
- access token истёк;
- token недействителен.

При подходящем контракте допустима одна попытка refresh.

`403 Forbidden` означает, что пользователь распознан, но не имеет права выполнить действие.

Повторный refresh обычно не меняет `403`.

Frontend показывает:

```text
401
→ login или восстановление сессии

403
→ понятное отсутствие доступа
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как обрабатывать поток обновления через refresh token?</strong></summary>

<dl>
<dd>
<h2></h2>

При подходящем `401` API-слой:

```text
1. Проверяет, что запрос ещё не повторялся.
2. Запускает один общий refresh.
3. Остальные запросы ожидают тот же Promise.
4. После успеха повторяет каждый запрос не более одного раза.
5. После отказа завершает очередь и очищает auth state.
```

Refresh endpoint исключают из interceptor.

Не каждый `401` должен запускать refresh. Нужен стабильный признак истёкшей учётной информации.

Для mutation автоматический retry допустим только при согласованной серверной семантике и защите от повторного бизнес-эффекта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое refresh token rotation и обнаружение повторного использования (<code>reuse detection</code>)?</strong></summary>

<dl>
<dd>
<h2></h2>

При refresh token rotation сервер после каждого успешного обновления выдаёт новый refresh token:

```text
token 1
→ token 2
→ token 3
```

Предыдущий token становится недействительным.

Если token 1 используется повторно после выдачи token 2, это может означать, что его скопировал злоумышленник.

Сервер отзывает активную цепочку или grant и требует нового входа.

Для public OAuth clients применяют rotation с reuse detection либо sender-constrained refresh tokens.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое бесконечный цикл обновления (<code>refresh loop</code>)?</strong></summary>

<dl>
<dd>
<h2></h2>

Refresh loop возникает, если общий interceptor обрабатывает `401` самого refresh request:

```text
API → 401
refresh → 401
interceptor → refresh
refresh → 401
```

Для защиты:

- refresh endpoint исключают из interceptor;
- используют один общий refresh Promise;
- исходный запрос помечают как уже повторённый;
- после отказа refresh завершают auth session;
- не запускают ещё один скрытый refresh.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как защищать маршрут при SSR в Next.js?</strong></summary>

<dl>
<dd>
<h2></h2>

Серверный код читает session cookie и до отправки защищённого содержимого выбирает:

```text
вернуть страницу
redirect на login
вернуть 403-состояние
```

Это предотвращает показ защищённого HTML до клиентской проверки.

Middleware может выполнить раннюю грубую проверку, но не заменяет авторизацию в:

- Route Handler;
- Server Action;
- backend API;
- операции над конкретным ресурсом.

Клиентская проверка после hydration обновляет UX, но не должна быть единственным барьером.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как синхронизировать выход между вкладками?</strong></summary>

<dl>
<dd>
<h2></h2>

Одна вкладка:

```text
завершает серверную сессию
→ очищает локальные данные
→ отправляет logout через BroadcastChannel
```

Остальные вкладки:

- очищают query cache;
- сбрасывают auth state;
- закрывают WebSocket/SSE;
- отменяют запросы;
- переходят к login.

Событие между вкладками улучшает UX, но не является защитой.

Даже если вкладка его не получила, сервер после logout не должен принимать отозванную сессию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как безопасно вернуть пользователя на исходную страницу после входа?</strong></summary>

<dl>
<dd>
<h2></h2>

Сохраняют внутренний путь:

```text
/orders/42
```

После входа проверяют, что это:

- относительный URL;
- разрешённый маршрут;
- адрес того же ожидаемого origin.

Нельзя без проверки перенаправлять по:

```text
returnUrl=https://evil.example
```

иначе возникает open redirect.

OAuth redirect URI регистрируется у authorization server отдельно и не должен зависеть от произвольного пользовательского параметра.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда выбирать BFF, а когда прямой OAuth client в SPA?</strong></summary>

<dl>
<dd>
<h2></h2>

Для first-party приложения BFF часто является предпочтительным вариантом:

```text
browser
→ session cookie
→ BFF
→ API
```

Tokens остаются вне JavaScript, а refresh централизован.

Прямой browser OAuth client может быть нужен, если:

- backend-компонент отсутствует;
- SPA должна обращаться к стороннему API напрямую;
- инфраструктура не позволяет использовать BFF;
- риски и ограничения приняты осознанно.

Тогда нужны:

- Authorization Code + PKCE;
- защита callback;
- короткий access token;
- rotation или sender-constraining refresh token;
- строгая XSS-защита;
- продуманная координация вкладок.

BFF сложнее инфраструктурно, но обычно даёт более сильную модель защиты tokens.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие состояния authentication должен различать frontend?</strong></summary>

<dl>
<dd>
<h2></h2>

Минимальная модель:

```text
unknown
authenticated
unauthenticated
forbidden
error
```

`unknown` означает, что session ещё проверяется.

Нельзя сразу считать пользователя вышедшим, иначе при загрузке возникнет ложный redirect на login.

`forbidden` отличается от `unauthenticated`: пользователь вошёл, но не имеет нужного permission.

`error` позволяет отдельно показать временную проблему проверки session, не смешивая её с окончательным logout.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как избежать гонки refresh token между несколькими вкладками?</strong></summary>

<dl>
<dd>
<h2></h2>

Single flight внутри одной вкладки не координирует другие вкладки.

При rotation возможен сценарий:

```text
tab A использует refresh token 1
tab B использует refresh token 1
```

Один запрос обновит token, второй применит уже отозванное значение.

Наиболее простой способ избежать браузерной гонки — централизовать refresh в BFF или серверной сессии.

Для direct SPA используют отдельную координацию:

- `BroadcastChannel`;
- browser lock;
- shared worker;
- обновление общего auth state;
- корректную обработку reuse detection.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое session fixation и как от неё защищаются?</strong></summary>

<dl>
<dd>
<h2></h2>

Session fixation возникает, если приложение продолжает использовать session ID, существовавший до успешной аутентификации.

Злоумышленник может попытаться заранее навязать пользователю известный идентификатор, а затем использовать его после входа.

После успешной аутентификации сервер создаёт новый session ID и делает предыдущий недействительным.

Session ID принимают только через ожидаемый механизм, обычно cookie, а не через URL или произвольный request parameter.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что тестировать в auth flow?</strong></summary>

<dl>
<dd>
<h2></h2>

Проверяют:

- успешный login;
- неправильные credentials;
- состояние `unknown` при старте;
- SSR redirect;
- protected route;
- `401` и `403`;
- один refresh для нескольких `401`;
- отказ refresh;
- отсутствие refresh loop;
- повтор запроса только один раз;
- безопасный retry mutation;
- rotation;
- две вкладки;
- server-side logout;
- очистку персонального cache;
- закрытие realtime;
- open redirect;
- CSRF-защиту;
- изменение permission во время session.

Security-тесты отдельно проверяют cookie attributes, отсутствие tokens в browser storage, logs, URLs и error tracking.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Архитектурное решение |
| --- | --- |
| First-party Next.js | BFF или серверная сессия в защищённой cookie |
| Прямой OAuth из SPA | Authorization Code + PKCE и защита refresh token |
| Инициализация приложения | Состояние `unknown` до ответа `/session` |
| Десять одновременных `401` | Один refresh и очередь ожидающих запросов |
| Refresh из нескольких вкладок | BFF или межвкладочная координация |
| Пользователь без права | `403` и отсутствие защищённых данных, а не новый login |
| SSR protected page | Серверная проверка до отправки HTML |
| Выход в одной вкладке | Отзыв на сервере, `BroadcastChannel` и очистка всех клиентов |
| Критичная mutation после `401` | Один retry и серверная идемпотентность |
| Изменение роли | Серверная повторная авторизация и обновление permission state |
