## Вопрос

<br>

 💬 **Что показывает покрытие кода тестами (test coverage)? Как использовать coverage и тесты в CI, не превращая процент покрытия в самоцель?**

<h2></h2>

<br>
<dl>
<dd>

Test coverage показывает, какие части исходного кода выполнялись во время тестов. Оно помогает найти непроверенные области, но не доказывает правильность assertions, качество сценариев или соответствие продукта требованиям. Строка может быть выполнена тестом без единой содержательной проверки.

Основные метрики:

| Метрика | Что считается покрытым | Какой пробел помогает увидеть |
| --- | --- | --- |
| Инструкции (`statements`) | исполняемые инструкции были выполнены | часть кода ни разу не запускалась |
| Ветви (`branches`) | выполнены отдельные ветви `if`, ternary, `switch` и логических условий | проверен успешный путь, но не ошибка или граничный случай |
| Функции (`functions`) | функция была вызвана | callback или handler не участвовал в сценарии |
| Строки (`lines`) | на строке выполнился инструментированный код | часть файла не достигалась |

Покрытие ветвей часто даёт больше информации о бизнес-логике, чем покрытие строк. Например, строка:

```ts
return value >= 18
  ? "allowed"
  : "denied";
```

может считаться выполненной по `lines` после проверки взрослого пользователя, хотя ветвь несовершеннолетнего ни разу не проверялась.

При этом даже `100%` branch coverage не доказывает, что проверены все значимые сочетания состояний. Метрика видит отдельные пути выполнения, но не понимает бизнес-смысл сценария и качество результата.

Jest собирает coverage через provider, то есть выбранный механизм сбора:

- `babel` — provider по умолчанию, добавляющий instrumentation через Babel и Istanbul;
- `v8` — использует механизм покрытия движка V8.

```ts
const config = {
  collectCoverage: true,
  coverageProvider: "v8",
};
```

Coverage включают через:

```text
collectCoverage: true
```

или команду:

```bash
jest --coverage
```

Сбор покрытия добавляет дополнительную работу и может заметно замедлять тесты. Поэтому coverage обычно собирают в CI или отдельной команде, а не при каждом локальном запуске в watch mode.

Правильное сопоставление результата с TypeScript и JSX зависит от source maps — карт соответствия преобразованного JavaScript исходному коду. Если transform формирует неправильные source maps, отчёт может указывать не на те строки.

`collectCoverageFrom` определяет, какие исходные файлы включить в отчёт, даже если тесты их не импортировали.

Без него полностью забытый модуль может вообще не появиться в статистике, хотя его фактическое покрытие равно нулю.

```ts
const config = {
  collectCoverageFrom: [
    "src/**/*.{ts,tsx}",
    "!src/**/*.d.ts",
    "!src/generated/**",
  ],
};
```

Из области покрытия осмысленно исключают:

- сгенерированный код;
- декларации типов;
- сторонний код;
- файлы конфигурации, не содержащие проверяемой логики;
- простые barrel-файлы с повторными экспортами.

Не следует исключать сложный или неудобный код только ради повышения процента.

`coverageThreshold`, или минимальный порог покрытия, заставляет Jest завершиться с ошибкой, если результат оказался ниже согласованного уровня:

```ts
const config = {
  collectCoverageFrom: [
    "src/**/*.{ts,tsx}",
    "!src/**/*.d.ts",
    "!src/generated/**",
  ],

  coverageThreshold: {
    global: {
      branches: 75,
      functions: 80,
      lines: 80,
      statements: 80,
    },

    "./src/domain/": {
      branches: 90,
    },
  },
};
```

Положительное значение означает минимальный процент:

```ts
branches: 80
```

Отрицательное значение означает максимально допустимое количество непокрытых сущностей:

```ts
statements: -10
```

В этом случае допускается не более десяти непокрытых instructions.

Порог можно задать:

- глобально;
- для glob;
- для каталога;
- для отдельного файла.

Если отдельный путь или glob указан рядом с `global`, Jest применяет его порог независимо и исключает соответствующее покрытие из глобального расчёта.

Единый высокий процент для всего репозитория не учитывает риск.

Например:

```text
алгоритм расчёта цены
→ нужен сильный branch coverage

декларативная обёртка над иконкой
→ достаточно умеренной проверки публичного поведения
```

Полезнее использовать:

- разумный глобальный baseline;
- повышенные требования к критичным модулям;
- diff coverage для нового кода;
- анализ непокрытых ветвей на code review.

Coverage threshold защищает согласованный уровень, но не определяет качество тестов автоматически.

В CI проверки располагают так, чтобы быстро и однозначно обнаруживать ошибки:

1. Воспроизводимо установить зависимости из lockfile.
2. Запустить статические проверки.
3. Выполнить быстрые unit-, component- и integration-тесты.
4. Собрать production bundle.
5. Запустить критичные E2E на подготовленном окружении.
6. Сохранить отчёты и диагностические артефакты.

Для PNPM воспроизводимая установка:

```bash
pnpm install --frozen-lockfile
```

Для npm:

```bash
npm ci
```

Пример CI-потока:

```text
Install
→ pnpm install --frozen-lockfile

Static checks
→ format check
→ ESLint
→ tsc --noEmit

Tests
→ jest --ci --coverage

Build
→ production build

E2E
→ критичные пользовательские пути

Artifacts
→ test report
→ coverage
→ screenshots
→ traces
```

Флаг:

```bash
jest --ci
```

переводит Jest в CI-режим. Например, новый snapshot не записывается автоматически, а приводит к падению теста до явного обновления snapshot.

Production build выполняют отдельно от Jest, потому что тестовый transform может успешно обработать код, который реальный bundler собрать не сможет.

Независимые проверки можно запускать параллельно:

```text
lint
typecheck
unit tests
```

Если один шаг логически зависит от другого, его запускают после успешного завершения зависимости.

Долгий тестовый набор можно разделить на shards — части, выполняемые разными CI jobs:

```bash
jest --shard=1/3
jest --shard=2/3
jest --shard=3/3
```

Значения являются однобазовыми:

```text
1/3
2/3
3/3
```

Если используется пользовательский test sequencer, он должен реализовывать метод:

```ts
shard()
```

Shards желательно балансировать по реальному времени выполнения, иначе один медленный shard определит длительность всего pipeline.

Если каждый shard собирает coverage, он должен записывать результат в отдельный файл или каталог:

```text
coverage/shard-1
coverage/shard-2
coverage/shard-3
```

После завершения частей данные объединяют в общий отчёт. Общий threshold применяют к объединённому coverage, если целью является порог для всего набора, а не для каждого отдельного shard.

Кэш ускоряет:

- установку зависимостей;
- transform;
- сборку;
- работу test runner.

Ключ кэша должен учитывать данные, влияющие на результат:

- lockfile;
- версию Node.js;
- операционную систему;
- конфигурацию сборки;
- версию инструмента;
- значимые environment variables.

Кэширование не должно заменять воспроизводимую установку зависимостей.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Может ли тест без проверок (assertions) повысить coverage?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

Если тест просто вызывает функцию или рендерит компонент, выполненные инструкции, строки и функции попадут в coverage:

```ts
test("renders form", () => {
  render(<ProfileForm />);
});
```

Отчёт не знает:

- проверял ли тест результат;
- упал бы он после неправильного изменения;
- соответствует ли результат требованиям;
- защищает ли тест пользовательское поведение.

Поэтому coverage используют как карту пробелов, а качество оценивают по значимым сценариям и assertions.

Полезный вопрос:

```text
Какое неправильное изменение production-кода сломает этот тест?
```

Mutation testing может дополнительно показать код, изменение которого существующие тесты не замечают.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем покрытие ветвей (branch coverage) отличается от покрытия строк (line coverage)?</strong></summary>

<dl>
<dd>
<h2></h2>

Line coverage показывает, выполнялся ли инструментированный код на строке.

Branch coverage отслеживает альтернативные пути условия:

```ts
if (isAdmin) {
  return "admin";
}

return "user";
```

Проверка только `isAdmin === true` может покрыть строки первой ветви, но не путь обычного пользователя.

Одна строка с ternary также может быть покрыта по lines, но только частично по branches:

```ts
return enabled
  ? start()
  : stop();
```

Особенно важны:

- ветви ошибок;
- граничные сравнения;
- необязательное поведение;
- права доступа;
- fallback;
- отсутствующие данные.

При этом `100%` branches не гарантирует проверку всех комбинаций состояний. Метрика считает отдельные ветви, а не полный смысл бизнес-сценария.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужен <code>collectCoverageFrom</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

При сборе coverage только из загруженных модулей файл без единого импорта может отсутствовать в отчёте.

Например:

```text
src/domain/calculateDiscount.ts
```

не импортируется ни одним тестом.

Без `collectCoverageFrom` он может не попасть в итоговую таблицу, хотя фактически не проверен.

Настройка заранее задаёт область исходников:

```ts
collectCoverageFrom: [
  "src/**/*.{ts,tsx}",
  "!src/**/*.d.ts",
  "!src/generated/**",
]
```

Glob должен соответствовать реальной структуре проекта и исключать только обоснованные категории.

После появления новой директории нужно проверить, входит ли она в область отчёта. Иначе новый production-код может оказаться за пределами coverage незаметно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем providers <code>babel</code> и <code>v8</code> отличаются?</strong></summary>

<dl>
<dd>
<h2></h2>

Provider `babel` является значением по умолчанию и добавляет instrumentation через Babel и Istanbul во время преобразования кода.

Provider `v8` получает coverage из встроенного механизма движка V8 и преобразует результат в отчёт Jest.

```ts
const config = {
  coverageProvider: "v8",
};
```

Providers могут отличаться:

- скоростью;
- результатами для отдельных конструкций;
- отображением преобразованного кода;
- взаимодействием с конкретным transform pipeline.

Выбор проверяют на реальном TypeScript и JSX toolchain проекта.

В обоих случаях корректность отображения исходных строк зависит от transform и source maps.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Стоит ли требовать 100% coverage?</strong></summary>

<dl>
<dd>
<h2></h2>

Иногда это оправдано для:

- маленькой чистой библиотеки;
- критического алгоритма;
- модуля с конечным количеством ясных ветвей;
- публичного пакета с жёстким контрактом.

Для большого frontend-приложения глобальная цель `100%` часто порождает:

- тесты без содержательных assertions;
- проверки внутренних деталей;
- лишние исключения из coverage;
- дорогое обслуживание;
- ложное ощущение безопасности.

Порог должен защищать от регрессии и направлять внимание, а не заменять оценку риска.

Непокрытая сложная ветвь оплаты важнее десятка покрытых строк компонента раскладки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое diff coverage?</strong></summary>

<dl>
<dd>
<h2></h2>

Diff coverage, или покрытие изменённого кода, считает метрики только для строк и ветвей, добавленных или изменённых относительно базовой ветки.

Это помогает постепенно улучшать legacy-проект:

```text
общее покрытие остаётся 45%
→ новый изменённый код должен иметь 80%
```

Jest самостоятельно не вычисляет diff coverage. Для этого используют:

- возможности CI-сервиса;
- сервис анализа качества;
- отдельный инструмент;
- собственную обработку coverage report и Git diff.

Метрика требует корректно определить:

- базовую ветку;
- базовый commit;
- изменённые строки;
- соответствие diff исходным source maps.

Diff coverage не заменяет регрессионные тесты. Изменение одной строки может сломать старый путь в другом модуле, который не входит в непосредственный diff.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое mutation testing?</strong></summary>

<dl>
<dd>
<h2></h2>

Mutation testing, или мутационное тестирование, автоматически вносит небольшие изменения в production-код.

Например:

```ts
value >= 18
```

может быть заменено на:

```ts
value > 18
```

Затем тесты запускаются против изменённого варианта.

Если хотя бы один тест падает, мутант обнаружен:

```text
killed
```

Если тесты проходят, мутант выжил:

```text
survived
```

Это может означать, что тесты выполняют строку, но не проверяют её поведение достаточно точно.

Mutation score показывает долю обнаруженных мутантов среди учитываемых инструментом изменений.

Отдельные мутанты могут получить другие статусы, например:

- `NoCoverage`;
- `Timeout`;
- `Ignored`;
- ошибку выполнения или компиляции.

Mutation testing оценивает способность тестов замечать изменения поведения, а не только выполнять строки.

Он значительно дороже обычного coverage, потому что тестовый набор запускается для множества изменённых вариантов кода.

Поэтому его обычно применяют:

- к критическим модулям;
- только к изменённому коду;
- по расписанию;
- в отдельном pipeline.

Некоторые мутанты могут быть эквивалентны исходному поведению. Такой мутант невозможно уничтожить тестом, потому что его изменение не влияет на наблюдаемый результат. Эти случаи требуют ручной оценки или исключения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>В каком порядке запускать проверки в CI?</strong></summary>

<dl>
<dd>
<h2></h2>

Быстрые и дешёвые проверки ставят раньше дорогих, если шаги выполняются последовательно:

```text
install
→ lint
→ typecheck
→ unit/component tests
→ build
→ E2E
```

Это позволяет остановить pipeline до дорогих E2E, если код не проходит статическую проверку.

Независимые проверки часто запускают параллельно:

```text
lint
typecheck
unit tests
```

Production build выполняют отдельно от тестового transform, потому что Jest может успешно выполнить код, который реальный bundler не соберёт.

E2E запускают после появления проверяемого build artifact или deployment.

В CI Jest запускают с:

```bash
jest --ci
```

чтобы исключить интерактивное поведение и автоматическую запись новых snapshots.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как ускорить большой набор тестов в CI?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала устраняют лишнюю работу:

- реальные ожидания;
- общий тяжёлый setup;
- ненужный coverage на каждом локальном запуске;
- чрезмерное число E2E;
- повторную инициализацию дорогой инфраструктуры;
- неограниченное количество workers в слабом CI.

Затем используют:

- workers;
- кэш;
- запуск тестов, связанных с изменёнными файлами;
- sharding между CI jobs.

Jest поддерживает:

```bash
jest --shard=1/3
jest --shard=2/3
jest --shard=3/3
```

При пользовательском test sequencer нужен метод:

```ts
shard()
```

Shards должны иметь близкое время выполнения, иначе самый медленный определит длительность всего pipeline.

Если coverage собирается параллельно:

1. Каждый shard пишет отдельный отчёт.
2. Отчёты объединяются.
3. На объединённом результате строится итоговый HTML или LCOV.
4. После объединения проверяется общий threshold.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что нужно сохранять при падении тестов в CI?</strong></summary>

<dl>
<dd>
<h2></h2>

Для Jest полезны:

- структурированный отчёт тестов;
- stack trace;
- вывод консоли;
- coverage report;
- seed при случайном порядке;
- информация о повторных попытках.

Для браузерных E2E дополнительно сохраняют:

- screenshot;
- video при необходимости;
- trace;
- DOM snapshot;
- сетевой лог.

Артефакт должен позволять понять состояние теста без немедленного повторного запуска.

Перед публикацией очищают:

- secrets;
- authorization headers;
- cookies;
- персональные данные;
- чувствительное содержимое запросов.

Срок хранения и объём артефактов выбирают по стоимости хранения и среднему времени расследования.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как использовать coverage при code review?</strong></summary>

<dl>
<dd>
<h2></h2>

На review смотрят не только на общий процент, но и на непокрытые строки и ветви рядом с изменённой логикой.

Автор должен понимать:

- какой риск закрывает тест;
- почему выбрана эта граница;
- какие ветви проверены;
- какие случаи сознательно не проверяются;
- упадёт ли тест при значимой ошибке.

Coverage report помогает найти пропущенную ветвь ошибки.

Но финальный вопрос остаётся поведенческим:

```text
Какой дефект вызовет падение этого теста?
```

Если ответ сводится только к снижению процента, тест может не защищать продукт.

</dd>
</dl>

</details>

## Где это встречается во frontend

| Область | Подход к качеству |
| --- | --- |
| Расчёт цены и скидок | Высокое покрытие ветвей и mutation testing |
| Формы | Успешная отправка, клиентская и серверная валидация, повторная отправка |
| Авторизация | Истечение token, refresh, отказ и очистка пользовательских данных |
| UI-обёртки | Умеренный coverage, акцент на публичном поведении |
| Legacy-код | Diff coverage и регрессионные тесты вокруг изменяемой области |
| Pull request | Быстрые обязательные проверки и критические E2E |
| Ночной pipeline | Широкие E2E, visual regression и дорогие проверки |
| Несколько CI jobs | Sharding и объединение coverage reports |
