## Вопрос

<br>

 💬 **Что такое нестабильные тесты (flaky tests)? Почему они появляются и как их устранять?**

<h2></h2>

<br>
<dl>
<dd>

Flaky test, или нестабильный тест, при одном и том же коде иногда проходит, а иногда падает без ожидаемого изменения поведения продукта.

Он разрушает доверие к тестам: команда перестаёт отличать настоящую регрессию от случайного сбоя и начинает без анализа перезапускать CI.

Основные источники нестабильности:

| Источник | Типичный пример |
| --- | --- |
| Незавершённая асинхронная работа | Promise или действие `userEvent` не ожидается через `await` |
| Общее изменяемое состояние | Один store, QueryClient, DOM-контейнер или module-level singleton используется несколькими тестами |
| Реальное время | `sleep(1000)`, debounce или таймер анимации |
| Случайность и окружение | `Math.random`, текущая дата, timezone, locale или размер viewport |
| Зависимость от порядка | Один тест оставляет изменённый global, storage, handler, mock или timer |
| Параллельное выполнение | Тесты используют одну базу, пользователя, порт, файл или внешнюю сущность |
| Внешняя система | Настоящий API, сеть или сервис периодически недоступны |
| Хрупкий поиск элемента | Неоднозначный selector или ожидание промежуточного DOM |
| Настройки библиотеки | Автоматические retries, refetch или кеш меняют число и время запросов |
| Race condition в продукте | Результат зависит от порядка завершения запросов |

Изоляция означает, что каждый тест:

1. Сам создаёт необходимое начальное состояние.
2. Не зависит от выполнения другого теста.
3. Не использует случайно оставшиеся данные.
4. После завершения не оставляет изменений для следующего сценария.

Для frontend это обычно означает:

- новый Redux store;
- новый QueryClient;
- новый memory router;
- новый экземпляр изменяемого кеша;
- сброс runtime handlers MSW;
- восстановление spies и заменённых globals;
- обработку fake timers;
- очистку `localStorage` и `sessionStorage`;
- удаление вручную созданных DOM-узлов;
- закрытие подписок, серверов и соединений.

React Testing Library автоматически вызывает `cleanup`, если test runner предоставляет глобальный `afterEach`.

Cleanup:

- размонтирует React-деревья, созданные через `render`;
- запускает cleanup React effects;
- удаляет созданные RTL DOM-контейнеры.

Но RTL не знает о состоянии приложения и внешних ресурсах.

Он не очищает автоматически:

- Redux store;
- QueryClient;
- RTK Query cache;
- runtime handlers MSW;
- `localStorage`;
- `sessionStorage`;
- mocks;
- fake timers;
- изменённые environment variables;
- вручную добавленные DOM-контейнеры;
- внешний тестовый сервер.

Поэтому типичный setup может выглядеть так:

```ts
afterEach(() => {
  server.resetHandlers();

  jest.restoreAllMocks();

  localStorage.clear();
  sessionStorage.clear();
});
```

Store и QueryClient обычно не очищают после теста, а создают заново для каждого render:

```ts
function createTestQueryClient() {
  return new QueryClient({
    defaultOptions: {
      queries: {
        retry: false,
      },
    },
  });
}
```

Retries в тестах ошибок задают явно.

По умолчанию TanStack Query повторяет неуспешный query три раза с задержкой. Из-за этого тест может:

- выполнить больше запросов, чем ожидается;
- дольше оставаться в loading-состоянии;
- упасть по timeout;
- получить другой ответ runtime handler.

Если проверяется не сама retry-логика, её обычно отключают:

```ts
const queryClient =
  new QueryClient({
    defaultOptions: {
      queries: {
        retry: false,
      },
    },
  });
```

Если проверяется retry, тест явно задаёт:

- количество попыток;
- задержку;
- последовательность ответов;
- виртуальное время.

Для fake timers cleanup выбирают по контракту теста.

Если оставшиеся callback должны завершиться:

```ts
afterEach(() => {
  jest.runOnlyPendingTimers();
  jest.useRealTimers();
});
```

Если тест проверяет, что таймер был отменён при cleanup:

```ts
afterEach(() => {
  jest.clearAllTimers();
  jest.useRealTimers();
});
```

Слепой вызов `runOnlyPendingTimers()` способен скрыть ошибку, если production-код обязан был вызвать `clearTimeout`.

Например, тест cleanup компонента должен сначала размонтировать его:

```tsx
const {
  unmount,
} = render(<Notification />);

unmount();

jest.advanceTimersByTime(
  5000,
);

expect(
  removeNotification,
).not.toHaveBeenCalled();
```

Затем оставшиеся timers очищают согласно сценарию.

Диагностику flaky test начинают с классификации причины, а не с увеличения timeout.

Практический порядок:

1. Воспроизвести тест многократным запуском в том же окружении.
2. Запустить test file отдельно.
3. Запустить его вместе со всем набором.
4. Сравнить параллельный запуск с `--runInBand`.
5. Перемешать порядок и сохранить seed.
6. Проверить незавершённые Promise, timers, запросы и внешние ресурсы.
7. Зафиксировать время, timezone, locale, случайные данные и размер среды.
8. Упростить тест до минимального воспроизводимого сценария.

Сначала запускают конкретный файл:

```bash
jest --runTestsByPath \
  src/example.test.ts
```

Затем повторяют его несколько раз:

```bash
for index in {1..20}; do
  pnpm jest \
    --runTestsByPath \
    src/example.test.ts \
    || break
done
```

Если тест стабилен отдельно, но падает в полном наборе, вероятны:

- протекание состояния;
- зависимость от порядка;
- конкуренция за общий ресурс;
- нехватка ресурсов при параллельном запуске.

Последовательный запуск:

```bash
jest --runInBand
```

отключает worker pool и выполняет test suites в одном процессе.

Если при `--runInBand` тест стабилен, проверяют общие ресурсы:

- одну базу данных;
- одного пользователя;
- одинаковый файл;
- фиксированный TCP-порт;
- общую серверную сущность;
- лимит внешнего API;
- недостаток CPU или памяти.

`--runInBand` является диагностическим инструментом, а не универсальным исправлением.

Оставить весь набор последовательным можно только тогда, когда это осознанное ограничение инфраструктуры. В остальных случаях лучше изолировать данные или выдавать каждому worker собственный ресурс.

Jest генерирует seed для каждого запуска.

Он используется для определения порядка test suites. Значение можно вывести:

```bash
jest --showSeed
```

Для дополнительного перемешивания тестов внутри файлов используют:

```bash
jest --randomize
```

Jest при этом выводит seed автоматически.

Падение повторяют с тем же значением:

```bash
jest \
  --randomize \
  --seed 1234
```

`--randomize` перемешивает тесты внутри файла и `describe`, а seed также помогает воспроизвести порядок test suites.

Если падение зависит от порядка двух конкретных файлов, их запускают вместе:

```bash
jest --runTestsByPath \
  src/polluting.test.ts \
  src/failing.test.ts
```

Затем определяют минимальную пару:

```text
загрязняющий тест
+
падающий тест
```

Если Jest не завершает процесс после выполнения тестов, используют:

```bash
jest --detectOpenHandles
```

Команда помогает найти открытые ресурсы:

- таймер;
- сервер;
- socket;
- незакрытое соединение;
- файловый handle;
- активную подписку Node.js.

`--detectOpenHandles`:

- автоматически включает `--runInBand`;
- использует диагностику Node.js;
- заметно замедляет запуск;
- предназначен только для отладки.

Не следует сразу добавлять:

```bash
jest --forceExit
```

`--forceExit` принудительно завершает процесс, но не устраняет удерживаемый ресурс. Он может скрыть:

- незакрытый сервер;
- потерянную подписку;
- ожидающий timer;
- неправильный teardown.

Сначала находят и корректно освобождают ресурс.

Для незавершённой асинхронной работы проверяют:

- каждый ли Promise возвращён или awaited;
- каждое ли действие `userEvent` ожидается;
- не завершился ли тест до callback;
- нет ли обновления React после окончания теста;
- перехвачен ли запрос MSW;
- был ли продвинут fake timer;
- не осталась ли ожидающая retry-попытка.

Нестабильное ожидание:

```ts
await sleep(1000);
```

заменяют ожиданием конкретного условия:

```tsx
expect(
  await screen.findByRole(
    "alert",
  ),
).toHaveTextContent(
  "Профиль сохранён",
);
```

Или управляемым временем:

```ts
await jest.advanceTimersByTimeAsync(
  300,
);
```

Timeout увеличивают только после того, как подтверждено, что операция действительно имеет обоснованно долгую верхнюю границу.

Различают:

```text
Jest test timeout
→ ограничивает весь тест

findBy / waitFor timeout
→ ограничивает одно ожидание
```

Увеличение общего timeout не исправляет:

- неверный selector;
- отсутствующий handler;
- пропущенный `await`;
- запрос, который не запускается;
- fake timer, который не продвинут;
- бесконечный loading state.

Повторный запуск теста также не является исправлением.

Jest предоставляет:

```ts
jest.retryTimes(2);
```

Для временной диагностики полезно сохранить ошибки первых попыток:

```ts
jest.retryTimes(
  2,
  {
    logErrorsBeforeRetry: true,
  },
);
```

Retry допустим как краткосрочная мера, если:

- причина уже расследуется;
- создана задача на исправление;
- у теста есть владелец;
- сохраняется ошибка первой попытки;
- измеряется частота повторов.

Постоянный retry для детерминированного unit- или component-теста превращает реальную проблему в случайно зелёный pipeline.

Flaky test иногда обнаруживает настоящий race condition в приложении.

Например:

```text
запрос A начался
→ запрос B начался
→ B завершился первым
→ UI показал данные B
→ A завершился позже
→ устаревшие данные A перезаписали B
```

Такой тест не нужно «стабилизировать» ожиданием большего timeout.

Нужно исправить production-код:

- отменять устаревший запрос;
- хранить request id;
- проверять актуальность ответа;
- использовать возможности query-библиотеки;
- не применять результат после смены сущности.

После исправления тест должен детерминированно управлять порядком завершения:

```text
второй запрос завершается первым
→ первый завершается позже
→ UI сохраняет результат второго
```

Тогда тест перестаёт быть flaky и превращается в стабильный регрессионный тест реальной ошибки.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Почему тест проходит отдельно, но падает в полном наборе?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычно на него влияет состояние другого теста:

- незакрытый spy;
- изменённый global;
- runtime handler MSW;
- `localStorage`;
- общий QueryClient;
- module-level singleton внутри test suite;
- ожидающий timer;
- внешний серверный ресурс.

Другая причина — конкуренция при параллельном запуске:

```text
два test suites
→ используют одного пользователя
→ одновременно изменяют его
```

Полезно:

1. Запустить падающий файл отдельно.
2. Запустить подозрительные файлы вместе.
3. Изменить их порядок.
4. Использовать `--runInBand`.
5. Найти минимальную пару тестов.

Исправление заключается в локальной подготовке и очистке либо в уникальных ресурсах, а не в принудительном последовательном запуске всего набора.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему увеличение timeout обычно не решает проблему flaky test?</strong></summary>

<dl>
<dd>
<h2></h2>

Если ожидаемое условие никогда не наступает из-за:

- неверного handler;
- пропущенного `await`;
- неправильного query;
- непродвинутого timer;
- запроса, который не запускается;

больший timeout только дольше ждёт ту же ошибку.

Если условие иногда наступает позже из-за реальной сети или фиксированной задержки, тест всё равно останется зависимым от нагрузки CI.

Timeout увеличивают только для операции с обоснованно долгой верхней границей.

В компонентном тесте внешнее время чаще заменяют:

- управляемым response;
- fake timer;
- ожиданием конкретного DOM-состояния.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как правильно очищать fake timers?</strong></summary>

<dl>
<dd>
<h2></h2>

Перед возвратом real timers нужно осознанно обработать оставшуюся виртуальную работу.

Если callbacks должны завершиться:

```ts
afterEach(() => {
  jest.runOnlyPendingTimers();
  jest.useRealTimers();
});
```

Это важно для библиотек, которые могли незаметно поставить собственный timer.

Если тест проверяет отмену таймера:

```ts
afterEach(() => {
  jest.clearAllTimers();
  jest.useRealTimers();
});
```

Сначала выполняют проверяемый cleanup:

```tsx
unmount();

jest.advanceTimersByTime(
  1000,
);

expect(
  callback,
).not.toHaveBeenCalled();
```

Слепой вызов всех pending timers может скрыть отсутствие необходимого:

```ts
clearTimeout
```

Поэтому cleanup выбирают с учётом контракта конкретного теста.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему текущая дата и часовой пояс (timezone) делают тест нестабильным?</strong></summary>

<dl>
<dd>
<h2></h2>

Один и тот же timestamp в разных timezone может соответствовать разной календарной дате.

Тест около:

- полуночи;
- перехода на летнее время;
- конца месяца;
- конца года;

способен менять результат в зависимости от машины и момента запуска.

Locale также влияет на формат строки:

```text
08/06/2026
06.08.2026
6 Aug 2026
```

Для бизнес-логики передают clock как зависимость либо фиксируют время:

```ts
jest.useFakeTimers();

jest.setSystemTime(
  new Date(
    "2026-08-06T12:00:00Z",
  ),
);
```

В CI задают известный timezone.

Assertions строят на явном формате или отдельных значениях даты, а не на неявных настройках компьютера.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как сделать случайные тестовые данные воспроизводимыми?</strong></summary>

<dl>
<dd>
<h2></h2>

Используют:

- фиксированные fixtures;
- генератор псевдослучайных данных с seed.

Seed записывают в отчёт, чтобы тот же набор можно было создать повторно.

Jest предоставляет seed запуска через:

```ts
jest.getSeed();
```

Его можно вывести командой:

```bash
jest --showSeed
```

И повторить:

```bash
jest --seed 1234
```

Для уникальности параллельных ресурсов можно учитывать идентификатор worker или тестового запуска, но значение должно позволять воспроизвести падение.

Property-based testing также должно выводить:

- seed;
- исходные данные;
- минимальный контрпример.

Случайность полезна для поиска новых входов только тогда, когда найденное падение можно повторить.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как кэш запросов и retries создают нестабильность?</strong></summary>

<dl>
<dd>
<h2></h2>

Общий QueryClient может вернуть данные предыдущего теста:

```text
данные уже в cache
→ ожидаемый запрос не выполняется
→ handler MSW не вызывается
```

Автоматический retry:

- откладывает окончательную ошибку;
- меняет число запросов;
- может использовать следующую одноразовую response;
- увеличивает длительность теста.

Для каждого теста создают новый QueryClient:

```ts
const queryClient =
  new QueryClient({
    defaultOptions: {
      queries: {
        retry: false,
      },
    },
  });
```

Если конкретный query явно задаёт собственный `retry`, это значение имеет приоритет над общими defaults.

Если проверяется retry-логика, тест явно управляет:

- числом попыток;
- последовательностью ответов;
- задержкой;
- виртуальным временем.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как обнаружить зависимость от порядка тестов?</strong></summary>

<dl>
<dd>
<h2></h2>

Jest использует seed для порядка test suites.

Значение можно вывести:

```bash
jest --showSeed
```

Порядок тестов внутри файлов дополнительно перемешивают:

```bash
jest --randomize
```

Для воспроизведения:

```bash
jest \
  --randomize \
  --seed 1234
```

Если подозревается зависимость между файлами, запускают конкретную пару:

```bash
jest --runTestsByPath \
  src/polluting.test.ts \
  src/failing.test.ts
```

После обнаружения сравнивают состояние до и после загрязняющего теста:

- mocks;
- globals;
- storage;
- timers;
- handlers;
- cache;
- внешние данные.

Фиксированный порядок не является исправлением, если между тестами нет намеренного общего сценария.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что проверять, если тест падает только в CI?</strong></summary>

<dl>
<dd>
<h2></h2>

Сравнивают:

- версию Node.js;
- версию браузера;
- операционную систему;
- timezone;
- locale;
- environment variables;
- lockfile;
- число workers;
- доступную память;
- доступный CPU;
- файловую систему;
- используемую команду.

Проверяют регистр символов в путях:

```text
import "./UserForm"
```

может работать в регистронезависимой файловой системе Windows, но падать в Linux, если файл называется:

```text
userForm.tsx
```

Также проверяют, не конкурируют ли параллельные тесты за ограниченный ресурс.

В CI сохраняют диагностические артефакты:

- stack trace;
- отчёт test runner;
- console output;
- screenshot;
- trace;
- сетевой лог;
- seed;
- список retries.

Локально воспроизводят тот же контейнер, environment и команду, а не только запускают тест из IDE.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли временно поместить нестабильный тест в quarantine?</strong></summary>

<dl>
<dd>
<h2></h2>

Quarantine, или исключение известного нестабильного теста из обязательной проверки CI, допустима только как управляемая временная мера.

У теста должны быть:

- владелец;
- ссылка на задачу;
- срок исправления;
- записанная причина;
- отдельный запуск;
- статистика падений.

Простое:

```ts
test.skip(...)
```

без наблюдения фактически удаляет защиту.

Критический сценарий лучше временно покрыть другой устойчивой проверкой, пока первопричина устраняется.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда flaky test указывает на ошибку production-кода?</strong></summary>

<dl>
<dd>
<h2></h2>

Если результат приложения зависит от допустимого порядка событий, проблема реальна.

Примеры:

- два запроса обновляют одно состояние;
- debounce отправляет устаревшее значение;
- двойной submit создаёт две операции;
- событие приходит после закрытия экрана;
- поздний response перезаписывает актуальные данные.

Тест делают управляемым:

```text
запрос A начинается
→ запрос B начинается
→ B завершается
→ A завершается
```

Затем проверяют, что UI сохраняет результат B.

После исправления такой тест становится детерминированным регрессионным тестом race condition.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Стоит ли оставлять <code>jest.retryTimes</code> навсегда?</strong></summary>

<dl>
<dd>
<h2></h2>

Для детерминированного unit- или component-теста — нет.

Retry:

- уменьшает вероятность увидеть красный результат;
- скрывает частоту проблемы;
- увеличивает время pipeline;
- может превратить регрессию в случайно успешный запуск.

Для временной диагностики можно использовать:

```ts
jest.retryTimes(
  2,
  {
    logErrorsBeforeRetry: true,
  },
);
```

Так сохраняются причины первых падений.

Для теста настоящей внешней системы retry иногда допустим, но его:

- ограничивают;
- измеряют;
- документируют;
- не используют вместо исправления controllable test environment.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Нестабильный сценарий | Детерминированное решение |
| --- | --- |
| Debounce | Fake timers и явное продвижение времени |
| Ошибка API с retry | Управляемая последовательность ответов MSW |
| Общий кэш RTK Query | Новый Redux store для каждого теста |
| Общий TanStack Query cache | Новый QueryClient и явная настройка retry |
| Текущая дата | Фиксированный clock, timezone и locale |
| Portal | Собственный контейнер с удалением после теста |
| Два конкурирующих запроса | Ручное управление порядком ответов |
| Зависимость от порядка | `--randomize`, seed и поиск загрязняющего теста |
| Jest не завершает процесс | `--detectOpenHandles` и правильный teardown |
| Падение E2E только в CI | Screenshot, trace, сетевой лог и одинаковый контейнер |
