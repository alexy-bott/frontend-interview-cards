## Вопрос

<br>

 💬 **Как выстроить стратегию тестирования frontend-приложения? Какие уровни тестов использовать?**

<h2></h2>

<br>
<dl>
<dd>

Стратегия тестирования определяет:

- какие риски нужно закрыть;
- на какой границе дефект дешевле обнаружить;
- какую уверенность даёт каждый тест;
- насколько быстро команда получает обратную связь.

Цель не в максимальном количестве тестов и не в покрытии каждой строки, а в быстрой и надёжной защите поведения, важного для пользователя и бизнеса.

Сначала выделяют риски:

- потеря данных формы;
- неверный расчёт;
- неправильные права доступа;
- ошибки оплаты;
- истечение авторизации;
- несовместимость с API;
- повреждение пользовательских данных;
- критичные переходы между страницами;
- недоступность приложения после deployment.

Чем выше вероятность и ущерб дефекта, тем сильнее должна быть защита.

Полезная упрощённая формула:

```text
Приоритет теста
=
вероятность дефекта
×
ущерб
×
частота изменения области
```

Стратегия frontend-приложения обычно включает несколько уровней:

| Уровень | Что проверяет | Подходящая задача | Ограничение |
| --- | --- | --- | --- |
| Статическая проверка | Типы, синтаксис и формальные правила без запуска приложения | TypeScript, ESLint, проверка схем и импортов | Не проверяет runtime-поведение |
| Модульный тест, unit test | Небольшой модуль с контролируемыми зависимостями | Формула цены, reducer, selector, алгоритм, схема валидации | Не подтверждает интеграцию частей |
| Компонентный тест | Поведение компонента или небольшой части UI | Форма, таблица, modal, состояния загрузки и ошибки | Среда вроде `jsdom` не воспроизводит весь браузер |
| Интеграционный тест | Совместную работу нескольких реальных модулей | UI, Router, store, кеш запросов и сетевой слой | Подготовка и диагностика сложнее unit-теста |
| Тест контракта, contract test | Совместимость consumer и provider на их границе | Frontend-клиент и REST или GraphQL API | Не проверяет весь пользовательский путь |
| E2E-тест | Пользовательский путь через развёрнутое приложение в браузере | Вход, оформление заказа, создание сущности, smoke-сценарий | Медленнее, дороже и имеет больше источников нестабильности |

Статические проверки являются самым дешёвым защитным слоем:

```text
исходный код
→ TypeScript
→ ESLint
→ сборка
```

Например, TypeScript может обнаружить:

- несовместимый тип аргумента;
- отсутствие обязательного поля;
- неправильное использование union;
- недопустимое возвращаемое значение.

Но типизация не доказывает, что:

- кнопка действительно работает;
- сервер вернул корректные runtime-данные;
- пользователь может пройти форму;
- браузер правильно отобразил layout;
- приложение авторизует действие.

Поэтому статические проверки дополняют тесты, но не заменяют их.

Границы тестов не определяются названием инструмента.

Например, тест React-компонента может использовать:

- настоящий React Router;
- настоящий Redux store;
- RTK Query;
- React Hook Form;
- запрос, перехваченный MSW.

Такой тест остаётся компонентным по размеру отображаемого UI, но одновременно является интеграционным по количеству совместно работающих модулей.

И наоборот, Jest или Vitest сами по себе не делают тест модульным. Эти инструменты являются test runners, внутри которых можно запустить тесты разных границ.

Полезнее описывать тест конкретно:

```text
Отрисовываем страницу оформления заказа
с настоящими Router, store и query cache,
но заменяем backend через MSW
```

чем ограничиваться названием:

```text
integration test
```

Проверку размещают на самой узкой границе, которая способна надёжно поймать нужный дефект.

Например, формулу скидки удобно проверить unit-тестом:

```text
цена + скидка + ограничения
→ ожидаемая итоговая сумма
```

Отправку формы лучше проверить через компонент:

```text
пользователь заполняет поля
→ нажимает кнопку
→ приложение отправляет запрос
→ показывает серверный результат
```

Работу приложения после deployment проверяет E2E:

```text
открыть приложение
→ авторизоваться
→ выполнить критичное действие
→ увидеть подтверждение
```

Хороший компонентный тест обычно взаимодействует с интерфейсом через публичное поведение:

- роль элемента;
- доступное имя;
- текст;
- label;
- пользовательский ввод;
- видимый результат.

Например:

```text
найти кнопку по role и name
→ нажать
→ проверить результат в интерфейсе
```

Вместо:

```text
найти компонент Button по имени класса
→ вызвать его внутренний метод
→ проверить useState
```

Чем сильнее тест похож на реальное использование интерфейса, тем больше уверенности он обычно даёт при безопасном рефакторинге.

При этом нужно учитывать среду выполнения.

Компонентный тест в `jsdom` хорошо проверяет:

- DOM-структуру;
- доступные роли;
- текст;
- атрибуты;
- события;
- состояние формы;
- асинхронные обновления UI.

Но `jsdom` не выполняет полноценный браузерный layout.

Такой тест не подтверждает:

- реальные размеры элемента;
- позиционирование;
- пересечение областей;
- фактический hit testing указателя;
- визуальное перекрытие;
- корректность CSS-анимации;
- работу конкретного браузерного движка.

Для этих рисков используют:

- component test в реальном браузере;
- E2E;
- visual regression;
- ручную проверку конкретного сложного сценария.

Для API-запросов удобно заменять сетевую границу, а не внутреннюю функцию компонента.

Например:

```text
Component
→ fetch или Axios
→ MSW
→ тестовый HTTP-ответ
```

Компонент продолжает использовать настоящий код:

- формирования запроса;
- сериализации;
- API-клиента;
- кеширования;
- обработки ответа;
- обновления UI.

Для отдельного сценария можно изменить поведение сети:

```text
обычный handler
→ успешный ответ

override конкретного теста
→ 500 или validation error
```

Обычно тест проверяет наблюдаемый результат:

```text
пользователь отправил форму
→ сервер вернул 400
→ UI показал ошибку поля
```

Необязательно отдельно проверять факт вызова внутренней функции:

```text
expect(apiClient.post).toHaveBeenCalled()
```

Требования к запросу можно выразить через поведение сетевого handler:

```text
если отсутствует обязательное поле
→ handler возвращает ошибку
→ UI-тест падает
```

Прямую проверку метода, URL или body добавляют, когда сам сетевой контракт является целью теста.

E2E-тест выполняется в настоящем браузере через собранное или развёрнутое приложение.

Он способен проверить совместную работу:

- frontend;
- Router;
- browser APIs;
- CSS;
- backend;
- authentication;
- cookies;
- базы тестовых данных;
- инфраструктуры окружения.

Но широкий охват увеличивает количество возможных причин падения.

Поэтому E2E-тесты должны быть изолированы.

Каждый тест самостоятельно подготавливает:

- пользователя;
- авторизацию;
- данные;
- cookies;
- local storage;
- server state.

Тест не должен зависеть от того, что предыдущий тест:

- создал заказ;
- вошёл в систему;
- оставил нужную запись;
- не очистил storage.

Нежелательно:

```text
Тест 1 создаёт сущность
→ Тест 2 редактирует ту же сущность
→ Тест 3 удаляет её
```

Падение первого теста вызовет каскадное падение остальных.

Предпочтительнее:

```text
Каждый тест
→ создаёт собственные данные
→ выполняет сценарий
→ очищает или изолирует состояние
```

Внешние сторонние сервисы также не следует бесконтрольно включать в каждый E2E.

Например, вместо реальной отправки платежа или письма используют:

- sandbox;
- тестовый provider;
- контролируемый stub;
- специальный test endpoint.

Собственная интеграция с этим сервисом всё равно должна быть проверена на подходящей границе.

Contract test проверяет, что consumer и provider одинаково понимают взаимодействие.

Для HTTP-контракта важны:

- метод;
- путь;
- query parameters;
- headers;
- request body;
- обязательные поля ответа;
- статусы;
- формат ошибок;
- семантика используемых данных.

Есть несколько близких, но разных проверок.

Schema validation проверяет соответствие общей схеме:

```text
реальный ответ
→ соответствует OpenAPI schema
```

Consumer-driven contract фиксирует конкретные ожидания frontend:

```text
frontend ожидает GET /users/42
→ status 200
→ обязательные id и name
```

Затем эти взаимодействия воспроизводятся против provider.

Схема описывает множество допустимых ответов, но не всегда доказывает, что конкретный consumer получит нужное ему поведение.

Contract test также не проверяет внутренний side effect provider.

Например, контракт может подтвердить:

```text
POST /orders
→ status 201
→ ответ содержит orderId
```

Но фактическое сохранение заказа в базе является задачей функциональных тестов backend.

Кроме уровней существуют поперечные виды проверок:

- accessibility;
- visual regression;
- performance;
- security;
- compatibility;
- localization.

Они могут выполняться на разных уровнях.

Например, accessibility проверяют через:

- статические правила JSX;
- компонентный тест ролей и labels;
- автоматический анализ страницы;
- E2E клавиатурного сценария;
- ручное тестирование screen reader.

Visual regression можно выполнять для:

- отдельного компонента;
- страницы;
- нескольких viewport;
- разных тем;
- состояний ошибки и загрузки.

Такую проверку не нужно считать отдельным уровнем вроде unit или E2E. Важно определить, какая реальная граница запускается.

Хороший набор тестов балансирует четыре свойства:

- **Уверенность:** тест падает при значимой регрессии.
- **Скорость:** разработчик быстро получает обратную связь.
- **Детерминизм:** один код и вход дают одинаковый результат.
- **Поддерживаемость:** безопасный рефакторинг не требует переписывать тест без изменения поведения.

Для детерминизма контролируют:

- текущее время;
- случайные значения;
- тестовые данные;
- сеть;
- таймеры;
- локаль;
- часовой пояс;
- порядок выполнения;
- состояние браузера.

Например, тест не должен зависеть от реального:

```ts
Date.now()
Math.random()
```

без фиксации времени или входных данных, если это влияет на результат.

Критичный сценарий иногда проверяют на нескольких уровнях без бессмысленного дублирования.

Например, для оплаты:

```text
Unit
→ граничные случаи расчёта суммы

Component
→ форма, pending и серверная ошибка

Contract
→ формат запроса и ответа платёжного API

E2E
→ один основной успешный пользовательский путь
```

Каждый тест защищает другую границу.

Не нужно повторять десятки одинаковых комбинаций на каждом уровне. Подробные варианты остаются в быстрых тестах, а широкие тесты подтверждают несколько основных интеграций.

Практический CI-поток может выглядеть так:

```text
Локально и перед commit
→ TypeScript
→ ESLint
→ быстрые unit и component tests

Pull request
→ полная детерминированная test suite
→ contract tests
→ критичные E2E

После deployment
→ smoke tests
→ наблюдаемость и реальные метрики
```

Code coverage помогает найти непроверенные области, но само число покрытия не доказывает качество стратегии.

Например:

```text
100% строк
```

можно получить тестами, которые вызывают код, но не проверяют важный результат.

Полезнее связать каждый значимый тест с вопросом:

```text
Какую регрессию он обнаружит?
```

Если ответ неясен, тест может закреплять реализацию без продуктовой ценности.

## Дополнительные вопросы

<details>
<summary><strong>Что означают пирамида тестирования (testing pyramid) и testing trophy?</strong></summary>

<dl>
<dd>
<h2></h2>

Пирамида тестирования предлагает иметь:

```text
много быстрых unit-тестов
→ меньше интеграционных
→ ещё меньше дорогих E2E
```

Она подчёркивает скорость и стоимость широких тестов.

Testing trophy, или «трофей тестирования», добавляет статические проверки в основание и сильнее подчёркивает интеграционные тесты:

```text
E2E
Integration
Unit
Static
```

Идея заключается в том, что интеграционные тесты frontend-приложения часто дают хороший баланс:

- реалистичного поведения;
- скорости;
- стоимости поддержки;
- качества диагностики.

Это модели для принятия решений, а не обязательные проценты.

Баланс зависит от продукта.

Библиотеке алгоритмов полезно больше unit-тестов.

Приложению с формами, Router, store и API полезно больше компонентных интеграций.

Проекту с критичными browser workflows нужен надёжный слой E2E.

Решение принимают по рискам и истории реальных дефектов, а не по требованию нарисовать конкретную геометрическую фигуру.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем компонентный тест отличается от интеграционного?</strong></summary>

<dl>
<dd>
<h2></h2>

Компонентный тест описывает размер тестируемой UI-области:

```text
один компонент
или
небольшое поддерево
```

Интеграционный тест описывает количество совместно работающих настоящих частей:

```text
UI
+
Router
+
store
+
query cache
+
network layer
```

Поэтому один тест может относиться к обеим категориям.

Например, форма отрисована как один компонент, но использует настоящие:

- React Hook Form;
- Router;
- Redux store;
- RTK Query;
- HTTP-клиент.

Запрос перехватывается MSW.

Такой тест является компонентным по области UI и интеграционным по границе системы.

Среда также имеет значение.

Тест в `jsdom` проверяет DOM-поведение, но не настоящий browser layout.

Browser component test запускает тот же ограниченный компонент, но уже внутри реального браузера и лучше подходит для:

- размеров;
- CSS;
- focus;
- scroll;
- browser APIs.

Поэтому полезнее явно описать:

- какой UI рендерится;
- какие providers настоящие;
- что заменено;
- какая среда используется;
- какой контракт проверяется.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что покрывать тестами в первую очередь?</strong></summary>

<dl>
<dd>
<h2></h2>

В первую очередь проверяют:

- критичные пользовательские действия;
- сложные бизнес-правила;
- обработку ошибок;
- потерю данных;
- права и доступные действия в UI;
- места с историей регрессий;
- часто изменяемые важные области.

Для frontend-теста прав доступа важно понимать границу.

Он может проверить:

```text
пользователь без роли
→ не видит действие
→ получает правильное состояние UI
```

Но такой тест не доказывает серверную авторизацию.

Backend должен независимо отклонять запрещённую операцию, даже если пользователь вручную отправил запрос.

Полезный вопрос перед написанием теста:

```text
Какой реальный дефект останется незамеченным без него?
```

Если ответ неясен, тест может закреплять случайную деталь реализации без значимой защиты.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему хрупко тестировать внутренние детали реализации (implementation details)?</strong></summary>

<dl>
<dd>
<h2></h2>

Внутренние детали не являются обещанием пользователю или потребителю модуля.

Например, пользователь не знает:

- имя внутреннего метода;
- количество `useState`;
- структуру reducer;
- имя служебного CSS-класса;
- наличие конкретного custom hook.

Тест таких деталей может сломаться после безопасного рефакторинга, хотя наблюдаемое поведение осталось прежним.

Предпочтительнее проверять:

```text
пользователь вводит данные
→ нажимает кнопку
→ получает результат
```

через:

- role;
- доступное имя;
- label;
- текст;
- состояние элемента;
- публичный ответ модуля.

Внутреннюю деталь проверяют отдельно, если она сама является публичным контрактом библиотеки или самостоятельным сложным модулем.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему не покрыть всё E2E-тестами?</strong></summary>

<dl>
<dd>
<h2></h2>

E2E включает много частей:

- браузер;
- frontend;
- сеть;
- backend;
- базу данных;
- авторизацию;
- тестовое окружение;
- инфраструктуру.

Такой тест даёт высокую уверенность в целом пути, но:

- медленнее выполняется;
- сложнее диагностируется;
- требует подготовки данных;
- имеет больше источников нестабильности;
- дороже поддерживается.

При падении E2E причина может находиться в любом слое.

Через E2E проверяют небольшой набор критичных путей:

- приложение открывается;
- пользователь входит;
- основная сущность создаётся;
- критичная операция завершается;
- основные страницы доступны.

Комбинации формул, форматов и граничных значений дешевле покрывать unit-тестами.

Состояния формы и ответы API удобнее подробно проверять компонентными интеграциями.

E2E-тесты должны быть изолированы и не зависеть от порядка запуска.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое тест контракта (contract test)?</strong></summary>

<dl>
<dd>
<h2></h2>

Contract test проверяет, что взаимодействующие стороны одинаково понимают формат и семантику обмена.

Для REST-контракта это могут быть:

- HTTP-метод;
- путь;
- query parameters;
- headers;
- request body;
- обязательные поля ответа;
- статусы;
- формат ошибки.

Для пакета:

- публичные функции;
- экспортируемые типы;
- сигнатуры;
- поведение публичного API.

Нужно различать schema test и consumer-driven contract.

Schema test проверяет:

```text
ответ соответствует OpenAPI
```

Consumer-driven contract фиксирует минимальные реальные ожидания frontend и затем проверяет их на provider:

```text
consumer создаёт ожидаемое взаимодействие
→ provider воспроизводит его
→ ответ соответствует ожиданиям
```

OpenAPI помогает проверять допустимую форму, но сама по себе не гарантирует бизнес-смысл конкретного сценария.

Contract tests дополняют component и E2E:

- ловят несовместимость границы;
- не проверяют весь интерфейс;
- не доказывают внутренние side effects backend.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли отдельно тестировать пользовательские hooks (custom hooks)?</strong></summary>

<dl>
<dd>
<h2></h2>

Если hook обслуживает один компонент, его поведение часто лучше проверять через этот компонент.

Например:

```text
hook управляет загрузкой формы
→ тест заполняет форму
→ проверяет пользовательский результат
```

Такой тест видит поведение через публичную UI-границу.

Отдельный `renderHook` полезен, если hook:

- переиспользуется несколькими компонентами;
- имеет самостоятельный публичный контракт;
- содержит сложный автомат состояний;
- принимает много входных параметров;
- возвращает независимые действия;
- является частью библиотеки.

Не нужно проверять внутренние:

- `useState`;
- количество рендеров без продуктовой причины;
- вызовы других hooks;
- локальные служебные функции.

Проверяют:

- возвращаемые значения;
- публичные действия;
- ошибки;
- реакцию на изменение входных параметров;
- cleanup внешней подписки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда snapshot-тест оправдан?</strong></summary>

<dl>
<dd>
<h2></h2>

Snapshot является способом сравнения результата с сохранённым эталоном, а не отдельным уровнем тестирования.

Он полезен для компактного стабильного значения, например:

- небольшого React-дерева;
- сериализованного AST;
- набора design tokens;
- публичного объекта конфигурации;
- форматированного сообщения;
- небольшого accessibility tree.

Snapshot полезен, когда:

- результат сложно удобно перечислить вручную;
- структура изменяется редко;
- diff остаётся читаемым;
- каждое обновление проверяют осознанно.

Большой DOM snapshot быстро превращается в шум.

Разработчик может выполнить:

```text
update snapshots
```

и принять одновременно много изменений, не проверив пользовательское поведение.

Для UI часто понятнее точные assertions:

```text
есть кнопка с доступным именем
→ она disabled во время запроса
→ после ошибки появляется сообщение
```

Snapshot не должен заменять проверки критичного поведения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нормально ли проверять один критичный сценарий на нескольких уровнях?</strong></summary>

<dl>
<dd>
<h2></h2>

Да, если разные уровни ловят разные дефекты.

Для оплаты:

```text
Unit
→ расчёт итоговой суммы и граничные значения

Component
→ поля, pending, validation и ошибка API

Contract
→ frontend и payment backend согласны по формату

E2E
→ один успешный путь через систему
```

Это не бессмысленное дублирование, потому что каждый уровень проверяет свою границу.

Бесполезно полностью повторять десятки одинаковых комбинаций на всех уровнях.

Подробные варианты оставляют в быстрых тестах, а широкие тесты подтверждают несколько ключевых интеграций и пользовательских путей.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>С чего начать тестирование унаследованного кода (legacy code) без тестов?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала выбирают область, которую предстоит изменить, и фиксируют её текущее значимое поведение.

Characterization test отвечает на вопрос:

```text
Как система ведёт себя сейчас?
```

Он создаёт защиту перед рефакторингом, даже если существующее поведение или архитектура неудобны.

Затем:

1. добавляют регрессионный тест на исправляемый баг;
2. выполняют изменение;
3. выделяют более узкие публичные контракты;
4. постепенно заменяют хрупкие внутренние проверки поведенческими;
5. удаляют дублирующие тесты, не добавляющие уверенности.

Не нужно начинать с попытки покрыть весь legacy-проект заданным процентом.

Полезнее защищать:

- изменяемые области;
- критичные пути;
- места с частыми дефектами;
- сложные бизнес-правила.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Риск | Подходящая проверка |
| --- | --- |
| Ошибка типов или несовместимый импорт | TypeScript, ESLint и сборка |
| Формула цены | Unit-тест граничных значений |
| Форма и серверные ошибки | Component integration test с MSW |
| Права в UI | Component test ролей и доступных действий |
| Реальная серверная авторизация | Backend integration или E2E с запрещённым запросом |
| Совместимость DTO | Schema check и contract test |
| Истечение авторизации | Integration test refresh flow |
| Сложный layout, focus или scroll | Browser component test или E2E |
| Визуальная регрессия | Screenshot в реальном браузере |
| Критичное оформление заказа | Небольшой набор изолированных E2E-сценариев |
| Исправленная ошибка в production | Regression test на минимальной полезной границе |
| Приложение доступно после deployment | Post-deploy smoke test |
