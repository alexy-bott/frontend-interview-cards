## Вопрос

Что показывает покрытие кода тестами (test coverage)? Как использовать coverage и тесты в CI, не превращая процент покрытия в самоцель?

<details>
<summary><strong>Показать ответ</strong></summary>

Test coverage показывает, какие части исходного кода выполнялись во время тестов. Оно помогает найти непроверенные области, но не доказывает правильность проверок (assertions), качество сценариев или соответствие продукта требованиям. Строка может быть выполнена тестом без единой содержательной проверки.

Основные метрики:

| Метрика | Что считается покрытым | Какой пробел помогает увидеть |
|---|---|---|
| Выражения (statements) | исполняемые выражения были выполнены | код ни разу не запускался |
| Ветви (branches) | выполнены отдельные ветви `if`, ternary, `switch` и логических условий | проверен успешный путь, но не ошибка или граничный случай |
| Функции (functions) | функция была вызвана | callback или handler не участвовал в сценарии |
| Строки (lines) | на строке выполнился инструментированный код | часть файла не достигалась |

Покрытие ветвей (branch coverage) часто даёт больше информации о бизнес-логике, чем покрытие строк (line coverage). Например, строка `return value >= 18 ? 'allowed' : 'denied'` может считаться выполненной после проверки взрослого пользователя, хотя ветвь несовершеннолетнего ни разу не проверялась.

Jest собирает coverage через provider, то есть выбранный механизм сбора. `babel` добавляет служебные инструкции (instrumentation) при преобразовании кода, а `v8` использует данные покрытия движка V8. Правильное сопоставление результата с TypeScript и JSX зависит от source maps - карт соответствия сгенерированного JavaScript исходному коду. Если transform выдаёт неверные source maps, отчёт может указывать не на те строки.

`collectCoverageFrom` определяет, какие исходные файлы включить в отчёт, даже если тесты их не импортировали. Без него полностью забытый модуль может вообще не появиться в статистике. Из области осмысленно исключают сгенерированный код, декларации типов, простые файлы с повторными экспортами и конфигурацию, но не сложный код только ради повышения процента.

```ts
const config = {
  collectCoverageFrom: [
    'src/**/*.{ts,tsx}',
    '!src/**/*.d.ts',
    '!src/generated/**',
  ],
  coverageThreshold: {
    global: {
      branches: 75,
      functions: 80,
      lines: 80,
      statements: 80,
    },
    'src/domain/': {
      branches: 90,
    },
  },
};
```

Coverage threshold, или минимальный порог покрытия, не даёт незаметно ухудшать согласованный уровень. Единый высокий процент для всего репозитория не учитывает риск: алгоритм расчёта цены требует более сильной проверки ветвей, чем декларативная обёртка над иконкой. Полезнее иметь разумный базовый порог, отдельные требования к критическим модулям и проверку непокрытых изменений на code review.

В CI проверки располагают так, чтобы быстро и однозначно обнаруживать ошибки:

1. Воспроизводимо установить зависимости из lockfile, например через `npm ci`.
2. Запустить статические проверки: форматирование при необходимости, lint и проверку типов TypeScript.
3. Запустить быстрые модульные, компонентные и интеграционные тесты.
4. Собрать production bundle, чтобы проверить реальный конвейер сборки.
5. Запустить небольшой набор критических E2E на подготовленном окружении.
6. Сохранить отчёты, coverage, screenshots и traces как артефакты CI.

Независимые шаги можно выполнять параллельно. Долгий тестовый набор делят на shards, то есть части, запускаемые разными workers. Кэш ускоряет установку и сборку, но его ключ должен учитывать lockfile, версию Node.js и настройки, влияющие на результат. Кэширование не должно заменять воспроизводимую установку зависимостей.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Может ли тест без проверок (assertions) повысить coverage?</summary>

Да. Если тест просто вызывает функцию или рендерит компонент, выполненные строки и функции попадут в coverage. Отчёт не знает, проверял ли тест результат и упал бы он при ошибке.

Поэтому coverage используют как карту пробелов, а качество оценивают по значимым сценариям и проверкам. Мутационное тестирование может дополнительно показать код, изменение которого существующие тесты не замечают.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем покрытие ветвей (branch coverage) отличается от покрытия строк (line coverage)?</summary>

Line coverage показывает, выполнялся ли код на строке. Branch coverage отслеживает альтернативные пути условия. Одна строка с ternary-оператором может быть покрыта по lines, но только наполовину по branches, если тест всегда выбирает одну ветвь.

Особенно важны ветви ошибок, граничные сравнения, необязательное поведение и условия прав доступа. При этом 100% branches не гарантирует проверку всех комбинаций состояний: метрика считает отдельные ветви, а не полный смысл бизнес-сценария.

</details>

<details>
<summary><strong>Вопрос:</strong> Зачем нужен <code>collectCoverageFrom</code>?</summary>

При сборе coverage только из загруженных модулей файл без единого импорта может отсутствовать в отчёте, хотя его покрытие фактически равно нулю. `collectCoverageFrom` заранее задаёт область исходников и включает такие файлы.

Glob, то есть шаблон путей, должен соответствовать реальной структуре и исключать только обоснованные категории. После изменения структуры репозитория его проверяют, иначе новые директории могут остаться за пределами отчёта.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем providers <code>babel</code> и <code>v8</code> отличаются?</summary>

Provider `babel` добавляет instrumentation через Istanbul во время Babel transform. Provider `v8` получает данные от встроенного механизма покрытия V8 и преобразует их в отчёт Jest. Они могут отличаться скоростью и тем, как отображают преобразованный код и некоторые конструкции.

Выбор проверяют на конкретном TypeScript/JSX toolchain. В обоих случаях нужны корректные source maps, иначе покрытие сгенерированного JavaScript неверно сопоставится с исходными файлами.

</details>

<details>
<summary><strong>Вопрос:</strong> Стоит ли требовать 100% coverage?</summary>

Иногда это оправдано для маленькой чистой библиотеки или критического модуля с конечным числом ветвей. Для большого frontend-приложения глобальная цель 100% часто порождает тесты без ценности, лишние исключения и проверки деталей реализации.

Порог должен защищать от регрессии и направлять внимание, а не заменять оценку риска. Непокрытая сложная ветвь оплаты важнее десятка покрытых строк компонента раскладки.

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое diff coverage?</summary>

Diff coverage, или покрытие изменённого кода, считает метрики только для строк и ветвей, добавленных или изменённых относительно базовой ветки. Это помогает постепенно улучшать старый проект: общий процент может оставаться низким, но новый риск не добавляется без тестов.

Метрика требует корректно определить базовый commit и сопоставить diff с отчётом coverage. Она также не заменяет регрессионные тесты: изменение одной строки может сломать старый путь в другом модуле.

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое mutation testing?</summary>

Mutation testing, или мутационное тестирование, автоматически вносит небольшие изменения в production-код: заменяет `>=` на `>`, удаляет условие или меняет возвращаемое значение. Затем тесты запускаются снова. Если хотя бы один тест падает, мутант считается обнаруженным (`killed`). Если все проходят, мутант выжил (`survived`): тесты не заметили изменение, что указывает на возможный слабый сценарий.

Метод оценивает способность тестов замечать ошибки, а не только выполнять строки. Он значительно дороже обычного coverage, поэтому его обычно запускают для критических модулей, по расписанию или только для изменённого кода. Некоторые mutants эквивалентны исходному поведению и требуют ручной оценки.

</details>

<details>
<summary><strong>Вопрос:</strong> В каком порядке запускать проверки в CI?</summary>

Быстрые и дешёвые проверки ставят раньше дорогих, если шаги зависят друг от друга: lint и typecheck могут остановить pipeline до E2E. Независимые lint, typecheck и модульные тесты часто запускают параллельно, чтобы сократить общее время.

Production build выполняют отдельно от тестового transform, потому что Jest может успешно преобразовать код, который реальный bundler собрать не сможет. E2E запускают после появления проверяемого артефакта сборки или deployment.

</details>

<details>
<summary><strong>Вопрос:</strong> Как ускорить большой набор тестов в CI?</summary>

Сначала устраняют лишнюю работу: реальные ожидания, общий тяжёлый setup, ненужный coverage на каждом локальном запуске и чрезмерные E2E. Затем используют workers, кэши и sharding, то есть разделение набора тестов между несколькими CI jobs. Jest поддерживает `--shard=N/M`, если test sequencer умеет разделять набор.

Shards должны иметь близкое время выполнения, иначе один медленный shard определит длительность всей CI job. Результаты всех частей объединяют в общий отчёт тестов и coverage, если покрытие собирается параллельно.

</details>

<details>
<summary><strong>Вопрос:</strong> Что нужно сохранять при падении тестов в CI?</summary>

Для Jest полезны структурированный отчёт тестов, stack trace, вывод консоли и отчёт coverage. Для браузерных E2E дополнительно сохраняют screenshot, video при необходимости, trace, DOM snapshot и сетевой лог. Артефакт должен позволять понять состояние без немедленного повторного запуска.

Секреты, authorization headers и пользовательские данные перед публикацией очищают. Срок хранения и объём артефактов выбирают по стоимости и времени расследования.

</details>

<details>
<summary><strong>Вопрос:</strong> Как использовать coverage при code review?</summary>

На review смотрят не только на процент, но и на непокрытые строки рядом с изменённой логикой. Автор должен объяснить, какие риски закрывает тест, почему выбрана эта граница и какие ветви сознательно не проверяются.

Coverage report помогает найти пропущенную ветвь ошибки, но финальный вопрос остаётся поведенческим: какой дефект вызовет падение этого теста? Если ответ сводится только к снижению процента, тест может не защищать продукт.

</details>

## Где это встречается во frontend

> [!NOTE]
> | Область | Подход к качеству |
> |---|---|
> | Расчёт цены и скидок | высокое покрытие ветвей и мутационное тестирование |
> | Формы | успешная отправка, клиентская и серверная валидация, повторная отправка |
> | Авторизация | истечение token, refresh, отказ и очистка пользовательских данных |
> | UI-обёртки | умеренный coverage, акцент на публичном поведении |
> | Legacy-код | diff coverage и регрессионные тесты вокруг изменяемой области |
> | Pull request | быстрые обязательные проверки и критические E2E |
> | Ночной pipeline | широкий E2E, visual regression и дорогие проверки |
