## Вопрос

Что проверяют E2E-тесты? Как организовать устойчивые браузерные тесты с Playwright или Cypress?

<details>
<summary><strong>Показать ответ</strong></summary>

E2E, или end-to-end testing, проверяет пользовательский сценарий от начала до конца через запущенное приложение в настоящем браузере. Тест взаимодействует со страницей через DOM, навигацию и браузерные API, а приложение проходит реальные границы между UI, маршрутизацией, состоянием, HTTP-клиентом и окружением. В зависимости от цели backend может быть настоящим тестовым сервисом или контролируемой сетевой заменой.

E2E не должен повторять все комбинации модульных и компонентных тестов. Он особенно полезен для небольшого числа критических путей:

- вход и восстановление авторизации;
- оформление заказа или другая ключевая операция;
- создание, изменение и удаление основной сущности;
- переходы между страницами и прямые ссылки на внутренние страницы (deep links);
- загрузка и скачивание файлов;
- работа с browser APIs, которую `jsdom` не воспроизводит;
- базовая smoke-проверка после deployment.

Playwright и Cypress предоставляют средство запуска тестов, управление браузером, locators для поиска элементов, ожидания, сетевой контроль и диагностические артефакты. Конкретный инструмент выбирают по требованиям проекта, браузерам, существующей инфраструктуре и опыту команды. Устойчивость теста в большей степени зависит от его границ и данных, чем от названия framework.

Хороший E2E-тест соблюдает четыре правила:

1. **Независимость.** Он не требует, чтобы другой тест сначала создал пользователя или изменил настройки.
2. **Управляемые данные.** Начальное состояние создаётся через API, подготовленный набор данных (fixture) или отдельный setup и имеет уникальные идентификаторы для параллельного запуска.
3. **Пользовательские locators.** Элементы ищутся по роли, доступному имени, label или осмысленному test id, а не по цепочке CSS-классов.
4. **Ожидание состояния.** Тест ждёт конкретный URL, response или видимый результат через встроенное автоматическое ожидание (auto-waiting), а не `sleep(3000)`.

```ts
import { test, expect } from '@playwright/test';

test('пользователь создаёт проект', async ({ page, request }) => {
  const user = await createUser(request);

  await page.goto('/login');
  await page.getByLabel('Email').fill(user.email);
  await page.getByLabel('Пароль').fill(user.password);
  await page.getByRole('button', { name: 'Войти' }).click();

  await page.getByRole('link', { name: 'Новый проект' }).click();
  await page.getByLabel('Название').fill('Interview notes');
  await page.getByRole('button', { name: 'Создать' }).click();

  await expect(page).toHaveURL(/\/projects\/[^/]+$/);
  await expect(page.getByRole('heading', { name: 'Interview notes' }))
    .toBeVisible();
});
```

В Playwright каждый тест по умолчанию получает изолированный BrowserContext - отдельный профиль браузера со своими cookies, storage и страницами. Cypress при включённой test isolation также очищает состояние браузера между E2E-тестами. Эта изоляция клиента не решает конфликт серверных данных: параллельным рабочим процессам (workers) всё равно нужны уникальные пользователи, сущности или отдельные пространства имён (namespaces).

Авторизацию необязательно проходить через UI в каждом тесте. Один специальный тест может проверять сам login form, а остальные получают заранее подготовленный `storageState`, cookie или API-сессию. Это ускоряет набор и убирает ненужную зависимость каждого сценария от страницы входа. Сохранённое состояние авторизации содержит секреты, поэтому файл не коммитят и не публикуют в CI artifacts.

При падении браузерный тест должен оставлять достаточно данных для расследования: screenshot, трассировку (trace) с DOM и действиями, сообщения консоли, сетевые запросы и при необходимости video. Retry может подтвердить нестабильность, но исходное падение и его trace сохраняют; случайно прошедшая повторная попытка не делает тест исправным.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Чем E2E-тест отличается от интеграционного компонентного теста?</summary>

Компонентный тест обычно выполняется в `jsdom`, рендерит часть React tree и контролирует сетевую границу через MSW. Он быстрый и удобный для множества состояний, но не проверяет настоящий движок браузера, production build и полную навигацию.

E2E открывает собранное приложение в браузере и проверяет более широкий путь. Он может обнаружить ошибку маршрутизации, CSP, cookies, загрузки bundle или browser API, но медленнее выполняется и хуже локализует причину. Эти уровни дополняют друг друга.

</details>

<details>
<summary><strong>Вопрос:</strong> Как выбирать между Playwright и Cypress?</summary>

Сравнивают поддержку нужных браузеров и платформ, модель параллелизма, сетевые возможности, component testing, качество traces, интеграцию с CI и уже существующие тесты команды. Небольшой пробный прототип на двух реальных сценариях показывает больше, чем абстрактная таблица функций.

Playwright предоставляет BrowserContext и единый API для Chromium, Firefox и WebKit. Cypress имеет собственную модель очереди команд, встроенное повторение queries и развитый интерактивный runner. Оба инструмента способны создать хороший набор; миграция оправдана конкретным ограничением, а не популярностью.

</details>

<details>
<summary><strong>Вопрос:</strong> Какие locators считаются устойчивыми?</summary>

Сначала используют locators, отражающие восприятие пользователя: роль и доступное имя, label поля, видимый текст. Они одновременно проверяют часть семантики интерфейса. Если текст нестабилен из-за i18n или элемент не имеет пользовательской семантики, вводят явный test id как контракт тестирования.

Цепочки CSS-классов, `nth-child` и XPath по структуре DOM хрупки: безопасная перестановка контейнеров ломает тест. Playwright locators повторно находят актуальный элемент перед действием, поэтому не следует хранить старый DOM handle без необходимости.

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое auto-waiting и почему оно лучше фиксированного sleep?</summary>

Auto-waiting, или автоматическое ожидание, повторяет поиск и проверяет готовность элемента до разрешённого timeout. Например, Playwright перед click ждёт, что locator разрешится в один видимый, стабильный и доступный для взаимодействия элемент. Assertions вроде `toBeVisible` тоже повторяются до успеха или timeout.

`sleep(3000)` не связан с состоянием приложения: на быстрой машине он тратит время, а на медленной заканчивается раньше результата. Ожидать нужно наблюдаемое условие: URL изменился, кнопка стала доступной или появился heading.

</details>

<details>
<summary><strong>Вопрос:</strong> Как подготавливать данные для E2E?</summary>

Начальное состояние создают через публичный API, специальный test-support endpoint, fixture базы или управляемый seed. Через UI создают данные только тогда, когда сам этот процесс является проверяемым сценарием.

Данные должны быть независимыми и удаляемыми. Для параллельного запуска в email, имени сущности или namespace добавляют идентификатор worker и запуска. Cleanup можно выполнять после теста, но окружение также должно периодически удалять остатки после аварийно завершившихся jobs.

</details>

<details>
<summary><strong>Вопрос:</strong> Нужно ли использовать настоящий backend во всех E2E?</summary>

Нет, граница зависит от цели. Небольшой набор сквозных тестов с настоящим backend проверяет совместимость deployment, auth, cookies и API. Для редкой server error или сторонней оплаты сетевой response можно перехватить, чтобы получить детерминированное состояние без опасного побочного эффекта.

Если каждый запрос замокан, тест уже не доказывает интеграцию с backend и ближе к browser integration test. Это допустимо, если название и назначение набора отражают границу, а реальный контракт проверяется отдельно.

</details>

<details>
<summary><strong>Вопрос:</strong> Как ускорить авторизацию в E2E-тестах?</summary>

Сессию создают один раз через API или отдельный setup project и сохраняют cookies и storage в `storageState`. Следующие тесты открывают новый BrowserContext уже с этим состоянием. Сам UI login проверяют отдельным сценарием.

Если тесты изменяют серверное состояние, один общий account для всех workers создаёт конфликты. Тогда каждому worker выдают отдельного пользователя или создают новую сессию для теста. Файл `storageState` добавляют в `.gitignore`, поскольку он способен содержать действующие credentials.

</details>

<details>
<summary><strong>Вопрос:</strong> Нужен ли Page Object, то есть объект страницы?</summary>

Page Object полезен, когда объединяет устойчивые locators и повторяемые действия предметной области, например `checkoutPage.submitOrder()`. Он уменьшает дублирование и даёт одно место для изменения контракта страницы.

Большой Page Object, который скрывает assertions, test data и все детали сценария, ухудшает читаемость. Часто лучше небольшие fixtures и helpers по пользовательским задачам. Из текста теста должно быть видно, что сделал пользователь и какой результат проверяется.

</details>

<details>
<summary><strong>Вопрос:</strong> Как запускать E2E параллельно без конфликтов?</summary>

Каждый тест получает изолированный browser context, а серверные данные разделяют по уникальному пользователю, tenant или namespace. Нельзя использовать одну корзину, один черновик или один mutable account для нескольких workers.

Большой набор распределяют по shards между CI jobs. Setup не должен создавать один незащищённый глобальный ресурс, а cleanup должен учитывать падение процесса. Если сценарий действительно меняет общий ресурс, его либо сериализуют точечно, либо дают ему отдельное окружение.

</details>

<details>
<summary><strong>Вопрос:</strong> Что сохранять при падении browser test?</summary>

Минимальный набор - stack trace, screenshot, ошибки консоли и сетевой лог. Trace полезнее одного screenshot: он позволяет пройти по шагам, увидеть DOM snapshot, locators и запросы до падения. Video добавляют, если движение или последовательность окон важны и trace недостаточен.

Артефакты сохраняют хотя бы для первой неуспешной попытки. Из headers, URL и storage удаляют tokens и персональные данные перед публикацией или длительным хранением.

</details>

<details>
<summary><strong>Вопрос:</strong> Когда нужен visual regression test?</summary>

Visual regression, или тест визуальной регрессии, сравнивает screenshot с утверждённым эталоном и обнаруживает изменения layout, цветов, шрифтов и перекрытий, которые DOM-проверки не видят. Он полезен для design system, ключевых экранов и адаптивных состояний.

Чтобы сравнение было стабильным, фиксируют браузер, OS, viewport, fonts, animation и тестовые данные. Динамические области маскируют осмысленно. Изменившийся screenshot требует просмотра человеком: автоматическое обновление эталона без анализа уничтожает проверку.

</details>

## Где это встречается во frontend

> [!NOTE]
> | Сценарий | Подходящая E2E-проверка |
> |---|---|
> | Login | один UI-сценарий входа, остальные тесты используют подготовленную сессию |
> | Checkout | один основной путь и несколько критических отказов |
> | Права доступа | отдельные browser contexts пользователей с разными ролями |
> | Deep link | прямой переход по URL и восстановление состояния страницы |
> | File download | событие скачивания, имя и содержимое файла |
> | Production deployment | smoke-сценарий на развёрнутом артефакте |
> | Design system | visual regression на фиксированной среде |
