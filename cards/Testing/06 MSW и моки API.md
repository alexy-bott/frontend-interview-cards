#### Вопрос

Что такое MSW и как с его помощью тестировать работу frontend с API?

#### Ответ

MSW, или Mock Service Worker, перехватывает сетевые запросы и возвращает подготовленные ответы. Приложение при этом выполняет настоящий код HTTP-клиента: формирует URL, заголовки (headers) и тело запроса (body), обрабатывает код состояния (status) и преобразует ответ (response). Подменяется сетевая граница, а не `fetch`, RTK Query hook или функция сервиса.

В браузере MSW регистрирует Service Worker - фоновый браузерный процесс, способный перехватывать запросы страницы. Это удобно для разработки и браузерных тестов. В Node.js, где обычно выполняются компонентные тесты Jest, `setupServer` не поднимает настоящий HTTP-сервер. Он перехватывает запросы, выполненные сетевыми модулями процесса, и передаёт их подходящему обработчику запроса (request handler).

Handler, или обработчик, описывает метод, URL и ответ. В MSW 2 REST-обработчик создают через `http`, а ответ - через `HttpResponse`:

```ts
import { http, HttpResponse } from 'msw';

export const handlers = [
  http.get('/api/users/:id', ({ params }) => {
    return HttpResponse.json({
      id: Number(params.id),
      name: 'Ada',
    });
  }),
];
```

Для Jest сервер обычно подключают один раз в setup-файле:

```ts
import { setupServer } from 'msw/node';
import { handlers } from './handlers';

export const server = setupServer(...handlers);

beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());
```

Исходный набор handlers описывает поведение API по умолчанию. Конкретный тест меняет только нужный сценарий через `server.use`; временный обработчик (runtime handler) получает приоритет над исходным. `resetHandlers()` после теста удаляет такие переопределения и восстанавливает исходный набор. Без очистки ошибка, заданная одним тестом, может попасть в следующий.

```ts
server.use(
  http.get('/api/users/:id', () => {
    return HttpResponse.json(
      { message: 'Пользователь не найден' },
      { status: 404 },
    );
  }),
);
```

HTTP-ошибку и сетевой сбой проверяют отдельно. Ответ со status `500` является корректным HTTP-ответом: нативный `fetch` успешно завершает Promise, а приложение должно проверить `response.ok` или status. `HttpResponse.error()` имитирует сетевой сбой, при котором `fetch` отклоняет Promise. Интерфейс часто должен по-разному обрабатывать ошибку валидации `422`, отсутствие авторизации `401`, серверную ошибку `500`, превышение времени ожидания и полное отсутствие сети.

MSW не очищает состояние самого приложения. Для каждого теста также создают свежий Redux store, состояние RTK Query API или QueryClient. Иначе повторный render может взять данные из кэша и вообще не отправить запрос, хотя handler настроен правильно.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Чем MSW лучше mock-функции `fetch`?
>
> **Ответ:** Mock `fetch` привязывает тест к конкретному способу выполнения запроса и обычно возвращает вручную собранный объект, который может не соответствовать настоящему `Response`. Он также обходит сетевой перехватчик, сериализацию и настройки HTTP-клиента.
>
> MSW перехватывает запрос после того, как клиент его сформировал. Поэтому тот же handler работает с `fetch`, Axios, RTK Query и другими клиентами, если они используют поддерживаемый сетевой слой. Тест остаётся ближе к реальной интеграции, но не зависит от доступности backend.

> [!followup]
> **Вопрос:** Поднимает ли `setupServer` настоящий сервер?
>
> **Ответ:** Нет. Название описывает API настройки для Node.js, но TCP-порт не открывается. MSW расширяет сетевое поведение текущего процесса и перехватывает исходящий запрос до фактической отправки.
>
> Поэтому относительный URL должен быть разрешим в тестовой среде так же, как в приложении, а запрос из другого процесса MSW этого Jest-процесса не увидит. Для E2E отдельного browser-процесса используют browser integration или настоящий test backend.

> [!followup]
> **Вопрос:** Чем исходный handler отличается от временного runtime handler?
>
> **Ответ:** Исходные handlers передают в `setupServer` или `setupWorker` при создании и считают базовым поведением API. Runtime handler добавляют во время теста через `server.use`, обычно для ошибки, пустого ответа или особого пользователя. Он имеет приоритет при совпадении запроса.
>
> `resetHandlers()` удаляет временные runtime handlers и возвращает исходные. Если вызвать `resetHandlers(newHandlers)`, можно заменить базовый набор, но в обычном `afterEach` аргументы не передают, чтобы каждый тест начинался с одной известной конфигурации.

> [!followup]
> **Вопрос:** Что делает `onUnhandledRequest`?
>
> **Ответ:** Настройка определяет поведение для запроса, которому не подошёл ни один handler. Режим `error` полезен в тестах: неожиданный запрос сразу показывает опечатку в URL, лишнюю аналитику или отсутствующий сценарий. `warn` только печатает предупреждение, а `bypass` пропускает запрос в реальную сеть.
>
> Иногда разрешают статические ресурсы или заранее известные внешние адреса через callback-функцию. Полностью отключать проверку опасно: тест может незаметно обратиться к настоящему API и стать нестабильным.

> [!followup]
> **Вопрос:** Чем HTTP 500 отличается от network error для `fetch`?
>
> **Ответ:** При HTTP 500 соединение состоялось и сервер вернул response с кодом состояния `500`. Promise `fetch` успешно выполняется, но `response.ok` равен `false`. HTTP-клиент или прикладной код решает, считать ли это исключением.
>
> Сетевой сбой (network error) означает, что корректного HTTP-ответа нет: соединение оборвалось, DNS не сработал или браузер заблокировал запрос. Тогда `fetch` возвращает отклонённый Promise. В MSW первый случай задают `HttpResponse` с кодом состояния, второй - `HttpResponse.error()`.

> [!followup]
> **Вопрос:** Как проверить тело запроса, headers и параметры пути?
>
> **Ответ:** Handler получает разобранные параметры пути (path params) и объект `request`. JSON-тело читают через `await request.json()`, headers - через `request.headers`. Handler может вернуть `400`, если контракт нарушен, и тем самым проверить сериализацию на сетевой границе.
>
> Но не каждое внутреннее поле запроса нужно проверять напрямую. Если пользовательский результат возможен только при корректном запросе, обработчик ответа и итоговый UI уже дают полезную интеграционную проверку. Прямую проверку запроса оставляют для важного контракта: заголовка авторизации, ключа идемпотентности или точной структуры команды.

> [!followup]
> **Вопрос:** Как тестировать задержку и timeout, то есть превышение времени ожидания?
>
> **Ответ:** MSW предоставляет `delay`, который можно ожидать через `await` внутри handler перед возвратом response. Это позволяет проверить состояние загрузки или собственную логику отмены. Для большой задержки тест можно сочетать с fake timers, но нужно аккуратно координировать API таймеров, `userEvent` и обновления React.
>
> Timeout не является свойством `fetch` сам по себе: приложение обычно реализует его через `AbortController` или HTTP-клиент. Тест должен моделировать задержку дольше порога и проверять именно результат отмены, а не просто ждать реальную секунду.

> [!followup]
> **Вопрос:** Как тестировать последовательность разных ответов одного endpoint?
>
> **Ответ:** Runtime handler может хранить локальный счётчик и возвращать разные ответы, например первый `500`, затем `200`, чтобы проверить повторную попытку (retry). Другой вариант - после первого шага вызвать `server.use` с новым handler. Важно, чтобы состояние последовательности создавалось внутри теста и не было общим для всего файла.
>
> Сценарий должен отражать реальный контракт. Длинная программа ответов в одном handler делает тест трудным для чтения; часто понятнее разбить независимые состояния на отдельные тесты.

> [!followup]
> **Вопрос:** Почему handler не вызывается, хотя компонент отрендерен?
>
> **Ответ:** Возможные причины: условие запроса не выполнено, URL или HTTP method не совпали, данные уже лежат в cache, запрос отключён параметром `skip`, либо server начал слушать после render. Режим `onUnhandledRequest: 'error'` помогает отличить несовпадение handler от полного отсутствия запроса.
>
> Для RTK Query и TanStack Query создают новый store или QueryClient на тест. Также проверяют base URL: handler `/api/user` не совпадёт с другим origin или путём, если шаблон описан неверно.

> [!followup]
> **Вопрос:** Как тестировать cache и повторную загрузку данных?
>
> **Ответ:** В одном тесте можно отрендерить двух потребителей одного query, записать число обращений в handler и проверить, что клиент переиспользовал данные согласно своему контракту. Для invalidation выполняют mutation, меняют ответ handler и ожидают новый запрос и обновлённый UI.
>
> Между независимыми тестами cache очищают созданием нового store или QueryClient. Иначе проверяется не сценарий из Arrange, а случайное состояние предыдущего теста.

> [!followup]
> **Вопрос:** Может ли MSW гарантировать совместимость с настоящим backend?
>
> **Ответ:** Нет. Handler написан frontend-командой и может повторить её неверное представление о контракте. TypeScript также проверяет только локальные типы, а не фактический JSON из production.
>
> Риск уменьшают тесты контрактов, валидация responses по OpenAPI-схеме, генерация типов и handlers из общего контракта либо тесты против контролируемого backend-окружения. MSW отвечает за управляемые сценарии интерфейса, но не заменяет проверку реального соглашения между системами.

> [!followup]
> **Вопрос:** Нужно ли проверять количество всех HTTP-запросов?
>
> **Ответ:** Только если количество является важным поведением: debounce не должен отправлять запрос на каждый символ, дедупликация должна объединить одинаковые query или mutation не должна повториться после двойного click. Тогда счётчик в handler выражает конкретный контракт.
>
> Тотальная проверка каждого запроса делает тест чувствительным к prefetch, retry и внутренней стратегии cache. В большинстве UI-сценариев достаточно настроить handlers и проверить состояние, которое пользователь получает в результате.

#### Где это встречается во frontend

> [!context]
> | Сценарий | Что моделирует MSW |
> |---|---|
> | Успешная загрузка | JSON response и status `200` |
> | Ошибки валидации | status `422` и ошибки отдельных полей |
> | Истёкший access token | `401`, refresh request и повтор исходного запроса |
> | Server failure | `500` и доступное пользователю сообщение |
> | Потеря сети | `HttpResponse.error()` |
> | Медленный запрос | `delay` и loading/abort behavior |
> | Инвалидация кэша RTK Query | изменённый response после mutation и refetch |
