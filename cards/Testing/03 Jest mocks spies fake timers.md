## Вопрос

<br>

 💬 **Как в Jest работают mocks, spies и fake timers? Когда использовать эти тестовые инструменты?**

<h2></h2>

<br>
<dl>
<dd>

Mock, или тестовая замена, позволяет изолировать проверяемый код от зависимости и управлять её поведением. В Jest для этого чаще всего используют `jest.fn`, `jest.spyOn` и `jest.mock`. Fake timers, или поддельные таймеры, заменяют системные API времени, чтобы тест мог управлять ходом времени без реального ожидания.

`jest.fn()` создаёт функцию с записываемой историей вызовов. Ей можно назначить результат или реализацию:

```ts
const loadUser = jest
  .fn<() => Promise<{ id: number }>>()
  .mockResolvedValue({ id: 1 });

await loadUser();

expect(loadUser).toHaveBeenCalledTimes(1);
```

Такая функция полезна, когда зависимость передаётся в код явно: callback-функция, logger, adapter или функция загрузки. Тест может проверить наблюдаемый результат и, если вызов зависимости является частью контракта, её аргументы.

`jest.spyOn(object, 'method')` создаёт spy, то есть наблюдатель за существующим методом. По умолчанию метод продолжает вызывать исходную реализацию. Чтобы заменить поведение, нужно явно указать `mockImplementation`, `mockReturnValue` или похожий метод. После теста исходный метод восстанавливают через `mockRestore()` либо общей настройкой `restoreMocks`.

`jest.mock('./module')` подменяет модуль для тестового файла. Это более широкая граница: все импорты этого модуля получают mock. Модульные mocks удобны для недетерминированной или дорогой зависимости, но сильнее связывают тест со структурой импортов. Для HTTP обычно полезнее MSW, который оставляет реальный клиентский код и перехватывает запрос на сетевой границе.

У mock-функций есть три разных вида очистки:

| Операция | История вызовов | Реализация mock | Исходная реализация spy |
|---|---|---|---|
| `mockClear()` | очищает | сохраняет | не восстанавливает |
| `mockReset()` | очищает | сбрасывает | не восстанавливает |
| `mockRestore()` | очищает | сбрасывает | восстанавливает |

`jest.clearAllMocks`, `jest.resetAllMocks` и `jest.restoreAllMocks` применяют соответствующее действие ко всем mock-объектам, известным Jest. Они не очищают произвольные глобальные переменные, localStorage, кэш или обработчики MSW.

Fake timers нужны, когда поведение зависит от `setTimeout`, `setInterval`, `Date` или других API времени. После `jest.useFakeTimers()` тест сам продвигает виртуальное время:

```ts
afterEach(() => {
  jest.runOnlyPendingTimers();
  jest.useRealTimers();
});

test('вызывает поиск после debounce', async () => {
  jest.useFakeTimers();
  const search = jest.fn();

  scheduleSearch(search, 300);
  expect(search).not.toHaveBeenCalled();

  await jest.advanceTimersByTimeAsync(300);
  expect(search).toHaveBeenCalledTimes(1);
});
```

Асинхронные методы, например `advanceTimersByTimeAsync`, позволяют обработчикам Promise выполниться между срабатываниями таймеров. Это важно, когда callback таймера запускает `async`-функцию или продолжение Promise. После теста сначала выполняют или явно отменяют ожидающие таймеры, затем возвращают реальные: иначе отложенная работа может потеряться или попасть в следующий тест.

Главное правило изоляции: подменять минимальную нестабильную границу. Если чистую функцию удобно вызвать с обычными значениями, mock не нужен. Чем больше внутренних модулей подменено, тем выше вероятность получить зелёный тест для комбинации, которой в приложении не существует.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем mock отличается от stub, fake и spy?</strong></summary>

<dl>
<dd>
<h2></h2>

Эти термины описывают роли тестовых замен. Stub, или заглушка, возвращает заранее заданный результат. Spy наблюдает за вызовами существующего объекта; в Jest `spyOn` по умолчанию сохраняет исходное поведение. Fake - упрощённая, но рабочая реализация зависимости, например in-memory repository. Mock в узком смысле содержит ожидания о взаимодействии, а в повседневной речи словом mock часто называют любую замену.

Один объект может сочетать роли. `jest.fn().mockResolvedValue(data)` одновременно является заглушкой результата и записывает вызовы как spy. На собеседовании важнее объяснить поведение замены, чем спорить о границах терминов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда проверять вызов mock-функции, а когда только результат?</strong></summary>

<dl>
<dd>
<h2></h2>

Вызов проверяют, если взаимодействие само является частью контракта: аналитическое событие отправлено один раз, транзакция сохранена, callback получил конкретное значение. Если пользователю важен только итог, тест устойчивее проверять через этот итог.

Проверка каждого внутреннего вызова фиксирует способ реализации. Например, требование вызвать `formatPrice` ничего не говорит о том, правильно ли показана цена, и ломается после безопасного встраивания функции. Проверка видимого текста защищает поведение.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает <code>mockImplementationOnce</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Он задаёт реализацию только для следующего вызова. Последовательность таких настроек позволяет смоделировать меняющееся поведение зависимости: первая попытка завершилась ошибкой, повторная успешно вернула данные. Когда одноразовые реализации заканчиваются, используется обычная реализация, заданная через `mockImplementation`, либо пустая функция.

Метод полезен для небольшого протокола вызовов. Если тест строит длинный сценарий из десятка `Once`, зависимость лучше представить понятным fake-объектом или проверить на более подходящей границе.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>jest.spyOn</code> может неожиданно выполнить настоящий код?</strong></summary>

<dl>
<dd>
<h2></h2>

Потому что spy в Jest по умолчанию вызывает исходный метод. Он только оборачивает его и записывает обращения. Если метод отправляет запрос, меняет хранилище или пишет в файл, побочный эффект действительно произойдёт.

Для полной подмены после `spyOn` задают `mockImplementation` или подходящее возвращаемое значение. Затем spy восстанавливают, чтобы изменённый метод не протёк в следующий тест.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что выбрать: module mock или dependency injection?</strong></summary>

<dl>
<dd>
<h2></h2>

Dependency injection, или передача зависимости снаружи, делает границу явной и позволяет заменить её обычным объектом или функцией. Такой тест меньше зависит от механики импорта и обычно проще для чистых сервисов.

Module mock удобен, когда архитектура уже использует прямые импорты или замена нужна в небольшом числе тестов. Не стоит менять всю архитектуру только ради mock, но и массовая подмена внутренних модулей часто показывает, что зависимости слишком скрыты или тест выбрал слишком узкую границу.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>jest.mock</code> сложнее использовать с нативными ESM?</strong></summary>

<dl>
<dd>
<h2></h2>

Статические ESM-импорты связываются и вычисляются до выполнения остального кода модуля. Поэтому Jest не может применить к ним привычное поднятие вызова `jest.mock` так же, как в CommonJS или после некоторых трансформаций.

Для нативного ESM Jest предоставляет экспериментальный `jest.unstable_mockModule`; после его вызова модуль загружают динамическим `await import()`. Возможности и ограничения зависят от версии Jest, поэтому перед настройкой проверяют официальную документацию и сначала рассматривают замену на более явной границе.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>clear</code>, <code>reset</code> и <code>restore</code> отличаются на практике?</strong></summary>

<dl>
<dd>
<h2></h2>

`clear` нужен, когда между тестами следует забыть только количество вызовов и аргументы, сохранив общую заглушку. `reset` дополнительно убирает заданное поведение, поэтому следующий вызов обычного `jest.fn` вернёт `undefined`. `restore` возвращает оригинал метода, заменённого через `spyOn` или поддерживаемый API замены свойства.

Если тесты проходят только в определённом порядке, первым делом проверяют именно очистку mock-состояния, но также cache, DOM, timers, storage и серверные handlers.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>runAllTimers</code> отличается от <code>runOnlyPendingTimers</code> и <code>advanceTimersByTime</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`runAllTimers` выполняет все запланированные таймеры, включая новые таймеры, которые создают их callback-функции, пока очередь не опустеет. Для рекурсивного таймера это может создать бесконечный цикл, поэтому Jest имеет защитный предел.

`runOnlyPendingTimers` выполняет только текущий слой ожидающих таймеров. `advanceTimersByTime(ms)` сдвигает виртуальные часы на заданный интервал и выполняет то, что должно сработать за это время. Выбор зависит от проверяемого контракта: для debounce обычно важен конкретный интервал, для очистки перед возвратом реальных таймеров - текущие ожидающие callback-функции.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как связаны fake timers, microtasks и Promise?</strong></summary>

<dl>
<dd>
<h2></h2>

Callback `setTimeout` является задачей таймера, а продолжение `Promise.then` попадает в очередь микрозадач (microtasks). Синхронный вариант продвижения таймера может вызвать callback, но продолжение Promise выполнится только после освобождения текущего стека.

Асинхронные API Jest с суффиксом `Async` позволяют обработчикам Promise выполниться в нужных промежутках. Однако fake timers не превращают весь асинхронный код в синхронный: HTTP-запросы, обновления React и ожидаемые изменения DOM всё равно нужно корректно `await`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как тестировать текущую дату?</strong></summary>

<dl>
<dd>
<h2></h2>

При включённых fake timers можно зафиксировать системное время через `jest.setSystemTime(new Date(...))`. Тогда код, читающий `Date.now()` или создающий `new Date()`, получает предсказуемое значение. В тесте следует использовать явный часовой пояс или формат, не зависящий от локальных настроек машины.

Если функции достаточно передать дату аргументом, это проще и не требует глобальной замены. Fake clock нужен для кода, чей контракт действительно связан с системным временем.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как использовать fake timers вместе с <code>userEvent</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`userEvent` может планировать задержки между отдельными DOM-событиями. При fake timers эти таймеры сами не двигаются, поэтому взаимодействие способно зависнуть. При создании пользователя передают функцию продвижения времени:

```ts
const user = userEvent.setup({
  advanceTimers: jest.advanceTimersByTime,
});
```

Отключать задержки через `delay: null` не рекомендуется: это меняет модель взаимодействия и может скрыть проблему. Все действия пользователя по-прежнему ожидают через `await`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что обычно не следует мокать?</strong></summary>

<dl>
<dd>
<h2></h2>

Не следует без причины мокать собственные компоненты, reducers, hooks и простые функции, которые можно дёшево выполнить вместе. Такой mock подтверждает договорённость теста с самим mock, но не интеграцию реальных частей.

Обычно заменяют внешнюю или недетерминированную границу: сеть, системное время, случайность, тяжёлый SDK или необратимый побочный эффект. Даже тогда mock должен воспроизводить важные свойства настоящего контракта, включая ошибки и форму данных.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Зависимость | Подходящая граница |
|---|---|
| Callback-функция компонента | `jest.fn` |
| Метод аналитики | `jest.spyOn` с явной подменой отправки |
| Debounce и throttle | fake timers и продвижение заданного интервала |
| Текущая дата | передача clock-зависимости или `jest.setSystemTime` |
| HTTP API | MSW вместо mock всей функции `fetch` |
| Сторонний SDK | небольшой adapter и его mock |
| Последовательные попытки | `mockImplementationOnce` или stateful fake |
