## Вопрос

<br>

 💬 **Что такое design patterns, или шаблоны проектирования? Зачем они нужны во frontend и как понять, что конкретный паттерн уместен?**

<h2></h2>

<br>
<dl>
<dd>

Design pattern, или шаблон проектирования, — известная схема решения повторяющейся задачи проектирования.

Паттерн обычно описывает:

```text
контекст
→ где возникает проблема

проблему
→ что затрудняет изменение системы

ограничения
→ какие требования приходится учитывать

структуру решения
→ какие роли появляются и как взаимодействуют

последствия
→ что становится проще, а что сложнее
```

Паттерн не является готовым фрагментом кода для копирования.

Например, Adapter не означает конкретный класс `Adapter`. Его смысл — поставить преобразующий слой между двумя несовместимыми контрактами:

```text
внешний DTO
→ Adapter
→ модель приложения
```

Реализация может быть обычной функцией:

```ts
const mapUserDto = (
  dto: UserDto,
): User => ({
  id: dto.user_id,
  name: dto.full_name,
});
```

Ценность паттернов состоит в двух вещах:

```text
повторное использование накопленного опыта
+
общий язык команды
```

Фраза:

```text
Изолируем внешний SDK фасадом.
```

короче и точнее длинного описания того, что приложение не должно напрямую зависеть от десятков методов сторонней библиотеки.

Но название паттерна полезно только тогда, когда команда одинаково понимает его роль и последствия.

Само употребление слова:

```text
Facade
Strategy
Factory
Observer
```

не делает решение хорошим.

Во frontend паттерны помогают управлять зависимостями между:

- UI;
- бизнес-правилами;
- server state;
- API;
- браузерными API;
- внешними SDK;
- design system;
- инфраструктурным кодом.

Например:

```text
backend DTO неудобен для компонентов
→ Adapter

внешний SDK имеет сложный API
→ Facade

есть несколько взаимозаменяемых алгоритмов
→ Strategy

несколько потребителей реагируют на событие
→ Observer или Pub/Sub

составные части UI используют общее состояние
→ Compound Components

создание объекта зависит от типа или окружения
→ Factory
```

Паттерны часто делят на три классические группы.

**Порождающие** описывают создание объектов:

```text
Factory
Builder
Singleton
```

**Структурные** описывают связи между частями:

```text
Adapter
Facade
Decorator
Proxy
```

**Поведенческие** описывают распределение поведения и взаимодействие:

```text
Strategy
Observer
State
Command
Mediator
```

Эта классификация помогает ориентироваться, но не должна становиться целью.

Frontend-разработчик сначала ищет проблему, а не подходящую категорию из книги.

Классические паттерны часто описаны через:

- классы;
- наследование;
- интерфейсы;
- объектные графы.

Во frontend та же идея может быть реализована через:

- функции;
- объекты;
- модули;
- closures;
- hooks;
- React Context;
- композицию компонентов;
- props;
- подписки;
- reducer.

Например, Strategy может быть набором функций одинакового типа:

```ts
type PriceStrategy = (
  price: number,
) => number;

const regularPrice: PriceStrategy = (
  price,
) => price;

const discountedPrice: PriceStrategy = (
  price,
) => price * 0.9;
```

Compound Components могут использовать Context:

```text
Tabs
├── Tabs.List
├── Tabs.Trigger
└── Tabs.Content
```

Observer может быть представлен API подписки:

```text
subscribe
unsubscribe
notify
```

Facade может быть обычным модулем:

```ts
export const analytics = {
  trackPageView,
  trackPurchase,
  identifyUser,
};
```

Наличие класса не делает код реализацией паттерна.

Отсутствие класса не мешает использовать его идею.

Паттерн выбирают от наблюдаемой проблемы.

Плохой порядок:

```text
Я изучил Factory.
→ Где бы теперь применить Factory?
```

Хороший порядок:

```text
Объект создаётся в нескольких местах по разным правилам.
→ Создание дублируется.
→ Добавление нового варианта требует менять потребителей.
→ Проверяем, поможет ли Factory.
```

Практический процесс выбора:

```text
1. Определить конкретную проблему.
2. Найти причину сложности.
3. Рассмотреть прямое решение.
4. Определить ожидаемые изменения.
5. Сравнить подходящие паттерны.
6. Оценить их стоимость.
7. Выбрать самое простое достаточное решение.
```

Сначала формулируют проблему без названия паттерна.

Например:

```text
Компоненты напрямую используют методы платёжного SDK.

При замене SDK придётся менять десятки компонентов.

Формат ошибок SDK протекает в UI.
```

После этого можно рассмотреть Facade или Adapter.

Если начать сразу со слов:

```text
Нам нужен Facade.
```

можно скрыть настоящую проблему и выбрать лишний слой.

Следующий вопрос:

```text
Что именно должно стать проще после применения паттерна?
```

Например:

```text
заменить внешний SDK
добавить новый алгоритм
изменить формат API
протестировать бизнес-логику отдельно
координировать связанные UI-части
```

Если нельзя объяснить, какое изменение станет дешевле, паттерн может быть преждевременным.

Паттерн часто уместен, когда существует одна из следующих ситуаций.

**Нестабильная внешняя граница**

```text
SDK
API
browser storage
third-party provider
```

Изменения внешней системы не должны распространяться по всему приложению.

Подходящие идеи:

```text
Adapter
Facade
Proxy
```

**Несколько взаимозаменяемых вариантов поведения**

```text
разные способы расчёта
разные правила валидации
разные payment providers
разные алгоритмы сортировки
```

Подходящая идея:

```text
Strategy
```

**Сложное создание объекта**

```text
зависит от окружения
зависит от типа
требует нескольких зависимостей
повторяется в разных местах
```

Подходящие идеи:

```text
Factory
Builder
```

**Связанные части интерфейса должны координироваться**

```text
Tabs
Accordion
Select
Dialog
```

Подходящие идеи:

```text
Compound Components
Context
State
```

**Несколько независимых потребителей реагируют на одно событие**

```text
изменение сессии
событие аналитики
обновление внешнего store
```

Подходящие идеи:

```text
Observer
Pub/Sub
```

Но даже при подходящей проблеме нужно оценить цену решения.

Паттерн может добавить:

- новый интерфейс;
- дополнительные файлы;
- косвенные вызовы;
- новые правила расширения;
- сложность навигации по коду;
- более трудную отладку;
- необходимость документировать lifecycle.

Например:

```text
Component
→ service interface
→ service implementation
→ API adapter
→ HTTP client
```

может быть оправдано в большой системе с несколькими источниками данных.

Для одного простого запроса такая цепочка может только затруднить чтение.

Прямой код часто лучше, если:

- существует один стабильный вариант;
- зависимость локальна;
- изменение маловероятно;
- логика короткая;
- абстракция ничего не изолирует;
- слой только перенаправляет аргументы.

Например:

```ts
const total =
  price * quantity;
```

не требует отдельного:

```text
TotalCalculationStrategyFactory
```

только потому, что расчёт теоретически может измениться в будущем.

Это называется speculative abstraction — абстракция под гипотетическое требование.

Проблема такого подхода:

```text
предполагаемая гибкость
→ уже оплачивается сложностью

реальное требование
→ может никогда не появиться
```

Ещё одна ошибка — pattern-driven design, когда структура выбирается ради демонстрации знания паттернов.

Признаки:

- названия паттернов появляются раньше требований;
- для каждой операции создаётся отдельный интерфейс;
- существует одна реализация и нет нестабильной границы;
- слой только передаёт вызов дальше;
- изменение требует править все уровни;
- код сложно объяснить через бизнес-задачу.

Например:

```text
UserAdapterFactoryStrategyManager
```

скорее скрывает предметный смысл, чем помогает его понять.

Имена лучше строить по роли в продукте:

```text
mapUserDto
createPaymentProvider
analyticsClient
dialogManager
priceCalculation
```

Название паттерна можно использовать, если оно действительно делает назначение яснее:

```text
analyticsFacade
storageAdapter
```

Но оно не должно заменять предметное имя.

Паттерн отличается от принципа проектирования.

Принцип задаёт общее направление:

```text
снижать связанность
разделять ответственности
зависеть от стабильных контрактов
```

Паттерн предлагает конкретную структуру для определённой ситуации:

```text
Adapter между внешним API и приложением
```

Например, Dependency Inversion является принципом.

Adapter, Facade и Strategy могут помогать ему следовать, но сами по себе не гарантируют хорошую архитектуру.

Паттерн также отличается от архитектуры.

Архитектура определяет крупные решения:

- границы модулей;
- направления зависимостей;
- разделение frontend и backend;
- способ рендеринга;
- модель поставки;
- общие правила системы.

Паттерн обычно решает более локальную задачу внутри этих границ.

Например:

```text
feature-модуль
→ архитектурная граница

mapper DTO внутри API-слоя
→ Adapter
```

Паттерн отличается и от библиотеки.

Библиотека является готовой реализацией:

```text
React Hook Form
Redux Toolkit
Radix UI
```

Паттерн является идеей организации решения.

Одна библиотека может использовать несколько паттернов внутри, а один паттерн можно реализовать без сторонней библиотеки.

Паттерн также не равен idiom — привычному приёму конкретного языка или платформы.

Например:

```text
optional chaining
destructuring
React custom hook
```

сами по себе не являются классическими design patterns.

Custom hook является механизмом повторного использования stateful-логики.

Внутри него может быть реализован:

- Adapter;
- Facade;
- Observer;
- Strategy;
- State.

Но наличие функции с именем `useSomething` ещё не доказывает наличие отдельного паттерна.

Один фрагмент кода может сочетать несколько паттернов.

Например:

```text
Facade аналитики
→ использует Factory для создания клиента
→ внутри публикует события подписчикам
```

Но перечислять все возможные названия в документации обычно не нужно.

Полезно называть только те паттерны, которые объясняют важное архитектурное решение.

Паттерн стоит документировать, если без контекста непонятно:

- почему появился дополнительный слой;
- какую нестабильность он изолирует;
- какие варианты разрешено добавлять;
- где находится владелец состояния;
- какие последствия имеет решение.

Короткое описание может выглядеть так:

```text
Проблема:
компоненты зависели от API стороннего SDK.

Решение:
введён analytics facade с контрактом приложения.

Плюсы:
SDK можно заменить без изменения компонентов.

Цена:
нужно поддерживать mapping событий и ошибок.
```

Это полезнее записи:

```text
Использован Facade Pattern.
```

потому что название без контекста не объясняет принятое решение.

При рефакторинге существующего кода паттерн лучше вводить постепенно.

Например:

```text
1. Найти нестабильную зависимость.
2. Определить минимальный контракт приложения.
3. Перевести одного потребителя.
4. Проверить тестируемость и удобство.
5. Перевести остальные места.
6. Удалить прямые обращения.
```

Необязательно заранее перестраивать весь проект.

Паттерн должен уменьшать риск изменений, а не создавать большой риск миграции.

Проверить уместность можно вопросами:

```text
Какая реальная проблема уже существует?

Какие варианты поведения действительно нужны?

Какая зависимость должна быть изолирована?

Кто владеет новым слоем?

Какие изменения теперь локализованы?

Какие ограничения добавляет паттерн?

Проще ли прямое решение?

Можно ли удалить абстракцию без потери пользы?
```

Если ответ сводится к:

```text
возможно, когда-нибудь понадобится
```

паттерн, вероятно, преждевременен.

Если после применения можно сказать:

```text
при добавлении нового provider
существующие компоненты не меняются
```

или:

```text
при изменении SDK
правится только один адаптер
```

польза паттерна измерима.

На собеседовании паттерн лучше объяснять по структуре:

```text
1. Проблема.
2. Суть решения.
3. Frontend-пример.
4. Ограничения.
```

Например:

```text
Strategy нужен, когда есть несколько
взаимозаменяемых вариантов поведения.

Каждый вариант реализует общий контракт,
а вызывающий код не знает деталей.

Во frontend это могут быть разные функции
расчёта цены или валидации.

Для двух простых условий отдельный Strategy
может быть лишней абстракцией.
```

Такой ответ показывает понимание, а не заученное определение.

Главный принцип:

```text
паттерн
→ не цель

паттерн
→ инструмент для конкретной повторяющейся проблемы
```

Хороший паттерн локализует изменение и делает взаимодействие частей понятнее.

Плохое применение паттерна добавляет новые сущности, но не уменьшает количество причин для изменения.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Чем design pattern отличается от принципа проектирования?</strong></summary>

<dl>
<dd>
<h2></h2>

Принцип задаёт общее направление:

```text
снижать связанность
разделять ответственности
зависеть от стабильных контрактов
```

Паттерн предлагает более конкретную структуру взаимодействия для определённой проблемы.

Например:

```text
Dependency Inversion
→ принцип

Adapter между приложением и внешним API
→ паттерн
```

Один паттерн может поддерживать несколько принципов, но его наличие не гарантирует хорошую архитектуру.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем паттерн отличается от архитектуры?</strong></summary>

<dl>
<dd>
<h2></h2>

Архитектура определяет крупные границы системы:

- модули;
- направления зависимостей;
- модель данных;
- способ рендеринга;
- взаимодействие frontend и backend;
- правила поставки.

Паттерн обычно решает локальную повторяющуюся задачу внутри этих границ.

Например:

```text
feature-модуль
→ архитектурная единица

Adapter DTO внутри API-слоя
→ локальный паттерн
```

Несколько паттернов могут использоваться внутри одной архитектуры.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как понять, что паттерн действительно нужен?</strong></summary>

<dl>
<dd>
<h2></h2>

Должна существовать наблюдаемая проблема:

- несколько взаимозаменяемых вариантов;
- нестабильный внешний контракт;
- повторяющееся сложное создание;
- сложная координация состояния;
- зависимость протекает во множество компонентов.

Нужно уметь объяснить:

```text
какое изменение сейчас дорого
→ какой слой локализует его
→ какие потребители перестанут меняться
```

Также оценивают цену:

- новые интерфейсы;
- дополнительные переходы;
- усложнение отладки;
- правила расширения.

Если прямой код остаётся понятнее и дешевле, паттерн пока не нужен.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>По каким признакам паттерн стал лишней абстракцией?</strong></summary>

<dl>
<dd>
<h2></h2>

Признаки:

- существует одна простая реализация;
- нестабильная зависимость отсутствует;
- слой только передаёт аргументы дальше;
- изменение приходится делать на всех уровнях;
- чтение требует много переходов между файлами;
- абстракция названа паттерном, но не изолирует проблему;
- польза объясняется только гипотетическим будущим.

Например:

```text
interface
→ одна implementation
→ один consumer
```

не всегда является ошибкой, но требует конкретного обоснования.

Если слой можно удалить и код станет понятнее без потери изоляции, абстракция, вероятно, лишняя.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли реализовывать паттерн точно как в книге?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Классическая схема объясняет роли и взаимодействия, а конкретная форма зависит от языка и платформы.

Во frontend:

```text
Strategy
→ функция

Facade
→ модуль с публичными методами

Observer
→ subscribe/unsubscribe API

State
→ reducer или объект переходов

Compound Components
→ React Context и композиция
```

Важно сохранить смысл паттерна и понимать его последствия, а не копировать диаграмму классов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли использовать название паттерна в имени файла или класса?</strong></summary>

<dl>
<dd>
<h2></h2>

Только если название помогает понять роль.

Допустимые примеры:

```text
analyticsFacade
storageAdapter
```

Но предметное имя часто полезнее:

```text
mapUserDto
createPaymentProvider
dialogManager
```

Имя:

```text
UserAdapterFactoryStrategy
```

скорее усложняет понимание.

Код должен прежде всего объяснять бизнес-назначение, а не демонстрировать список известных паттернов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли один фрагмент кода сочетать несколько паттернов?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

Например:

```text
analytics Facade
→ получает provider через Factory
→ публикует события через Observer
```

Или Compound Component может использовать внутри State и Context.

Но не нужно перечислять все возможные паттерны в названии или документации.

Называют только те роли, которые объясняют важные границы, lifecycle или способ расширения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как обсуждать паттерн на собеседовании?</strong></summary>

<dl>
<dd>
<h2></h2>

Полезная структура:

```text
1. Назвать проблему.
2. Объяснить суть решения.
3. Привести frontend-пример.
4. Назвать ограничение.
```

Например:

```text
Adapter изолирует несовместимый внешний контракт.

Во frontend он может преобразовать backend DTO
в модель, удобную компонентам.

При изменении API правится граница,
а не все потребители.

Для полностью совпадающих стабильных моделей
отдельный Adapter может быть лишним.
```

Такой ответ показывает условия применения, а не только заученное определение.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем паттерн отличается от библиотеки и idiom?</strong></summary>

<dl>
<dd>
<h2></h2>

Паттерн — идея организации решения.

Библиотека — готовый код, который можно подключить:

```text
Redux Toolkit
React Hook Form
Radix UI
```

Одна библиотека может реализовывать несколько паттернов.

Idiom — привычный приём конкретного языка или платформы:

```text
optional chaining
destructuring
custom hook
```

Custom hook сам по себе не является отдельным классическим паттерном, но внутри него может быть реализована идея Adapter, Facade, Observer или State.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как безопасно внедрить паттерн в существующий код?</strong></summary>

<dl>
<dd>
<h2></h2>

Лучше начать с конкретной проблемной границы.

Например:

```text
1. Определить минимальный контракт приложения.
2. Создать Adapter или Facade.
3. Перевести одного потребителя.
4. Проверить тесты и удобство.
5. Постепенно перевести остальные места.
6. Удалить прямые обращения.
```

Необязательно сразу перестраивать весь проект.

Постепенная миграция уменьшает риск и позволяет проверить, действительно ли новый слой упрощает изменения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Является ли custom hook паттерном?</strong></summary>

<dl>
<dd>
<h2></h2>

Custom hook — механизм React для повторного использования stateful-логики.

Он может реализовывать разные идеи:

```text
useAnalytics
→ Facade

useExternalStore
→ Observer

usePaymentProvider
→ Strategy или Factory

useDialog
→ управление State
```

Но само наличие функции с префиксом `use` не означает применение конкретного design pattern.

Сначала нужно смотреть на проблему и структуру взаимодействия.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда обычное условие лучше Strategy?</strong></summary>

<dl>
<dd>
<h2></h2>

Для небольшого числа простых вариантов обычное условие часто понятнее:

```ts
const price =
  isDiscounted
    ? basePrice * 0.9
    : basePrice;
```

Strategy становится полезнее, когда:

- вариантов много;
- каждый вариант содержит отдельную логику;
- варианты добавляются независимо;
- их нужно тестировать отдельно;
- вызывающий код не должен знать детали.

Strategy не должен заменять каждое короткое `if`.

Он нужен, когда варианты поведения действительно являются самостоятельными взаимозаменяемыми алгоритмами.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Проблема | Возможное решение |
|---|---|
| Формат backend DTO неудобен компонентам | Adapter или отдельный mapper на границе API |
| Есть несколько вариантов расчёта или валидации | Strategy с общим контрактом |
| Внешний SDK имеет сложный и нестабильный API | Facade с API, принадлежащим приложению |
| Tabs или Dialog состоят из связанных частей | Compound Components и общий state |
| Несвязанные модули получают одно событие | Observer или Pub/Sub с явным владельцем |
| Создание клиента зависит от окружения | Factory |
| Поведение объекта зависит от текущего этапа | State или reducer с явными переходами |
| Слой только перенаправляет один стабильный вызов | Прямой код без дополнительного паттерна |
