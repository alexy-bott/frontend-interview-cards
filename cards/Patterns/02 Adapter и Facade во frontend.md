## Вопрос

<br>

 💬 **Чем отличаются Adapter и Facade? Где они применяются во frontend?**

<h2></h2>

<br>
<dl>
<dd>

Adapter, или адаптер, приводит существующий интерфейс к контракту, который ожидает приложение.

Он нужен, когда две части системы должны взаимодействовать, но отличаются:

- названиями методов;
- форматом параметров;
- структурой данных;
- моделью ошибок;
- синхронностью;
- способом вызова;
- правилами версионирования.

Упрощённо:

```text
внешний несовместимый контракт
→ Adapter
→ контракт приложения
```

Facade, или фасад, предоставляет простой API поверх сложной подсистемы.

Он скрывает:

- несколько зависимостей;
- конфигурацию;
- порядок вызовов;
- инфраструктурные детали;
- общие правила взаимодействия с подсистемой.

Упрощённо:

```text
компонент
→ простой Facade
→ сложная подсистема
```

Главное различие:

```text
Adapter
→ делает несовместимый интерфейс совместимым

Facade
→ делает сложную подсистему проще для использования
```

Сравнение:

| Критерий | Adapter | Facade |
|---|---|---|
| Основная проблема | Несовместимые контракты | Слишком сложный публичный API |
| Что изменяет | Форму взаимодействия | Способ доступа к подсистеме |
| Типичная граница | API, SDK, browser API | Analytics, auth, storage, feature flags |
| Может использовать несколько зависимостей | Да, но не обязательно | Часто использует |
| Публичный API | Соответствует ожиданиям клиента | Упрощает частые сценарии |
| Может использовать mapper | Да | Да, через внутренние зависимости |

Один слой может одновременно выполнять обе роли.

Например, модуль аналитики может:

- предоставлять простой метод `track` — роль Facade;
- преобразовывать предметное событие в формат конкретного SDK — роль Adapter.

Но различать роли полезно по решаемой проблеме, а не по имени файла.

### Adapter для backend API

Предположим, backend возвращает транспортную модель:

```ts
type UserDto = {
  id: string;
  display_name: string;
  created_at: string;
};
```

Приложению удобнее использовать собственную модель:

```ts
type User = {
  id: string;
  displayName: string;
  createdAt: Date;
};
```

Чистое преобразование данных:

```ts
function toUser(dto: UserDto): User {
  return {
    id: dto.id,
    displayName: dto.display_name,
    createdAt: new Date(dto.created_at),
  };
}
```

Это mapper — преобразователь одной структуры данных в другую.

Полноценный Adapter может дополнительно привести к контракту приложения всю операцию:

```ts
type GetUserError =
  | { type: "notFound" }
  | { type: "forbidden" }
  | { type: "unavailable" };

type UserApi = {
  getUser(
    userId: string,
  ): Promise<User>;
};

function createUserApi(
  client: HttpClient,
): UserApi {
  return {
    async getUser(userId) {
      try {
        const dto =
          await client.get<UserDto>(
            `/users/${userId}`,
          );

        return toUser(dto);
      } catch (error) {
        throw mapGetUserError(error);
      }
    },
  };
}
```

Теперь потребитель зависит от собственного контракта:

```text
getUser(userId): Promise<User>
```

и не знает:

- URL endpoint;
- `snake_case`;
- формат даты;
- структуру HTTP-клиента;
- транспортный формат ошибки.

Adapter локализует знание о внешней системе.

Если backend изменит:

```text
display_name
→ full_name
```

правка останется на границе API, а не распространится по React-компонентам.

Mapper и Adapter не являются одним и тем же.

```text
Mapper
→ преобразует данные

Adapter
→ приводит весь интерфейс взаимодействия
```

Adapter может использовать несколько mapper:

```text
request mapper
response mapper
error mapper
```

Для отправки данных обычно существует отдельное направление.

Например:

```ts
type UserFormValues = {
  displayName: string;
};

type UpdateUserDto = {
  display_name: string;
};

function toUpdateUserDto(
  values: UserFormValues,
): UpdateUserDto {
  return {
    display_name:
      values.displayName.trim(),
  };
}
```

Преобразования не обязаны быть симметричными:

```text
UserDto
→ содержит read-only и вычисляемые поля

UserFormValues
→ содержит только редактируемые значения

UpdateUserDto
→ содержит только разрешённые изменения
```

Поэтому функции:

```text
toUser
toUserFormValues
toUpdateUserDto
```

обычно имеют разные контракты.

Adapter располагают на границе внешней системы:

```text
HTTP client
→ transport DTO
→ Adapter
→ application model
→ feature
→ UI
```

React-компонент не должен знать, что конкретный endpoint:

- возвращает `snake_case`;
- кодирует дату нестандартной строкой;
- использует особый формат пагинации;
- называет одно поле иначе;
- возвращает собственную структуру ошибок.

Если входящие данные нельзя полностью считать доверенными, Adapter может включать runtime validation:

```text
HTTP response
→ runtime validation
→ mapping
→ application model
```

TypeScript проверяет код во время разработки, но не гарантирует, что сервер действительно вернул ожидаемую структуру.

При несовместимом ответе Adapter должен вернуть контролируемую ошибку интеграции, а не передавать повреждённые данные глубже в приложение.

Ошибки внешней системы также адаптируют.

Например:

```text
404
→ notFound

403
→ forbidden

timeout или временный 503
→ unavailable

422 с field_errors
→ ошибки полей формы
```

Нельзя сводить все ошибки к одной строке:

```ts
throw new Error(
  "Something went wrong",
);
```

Так теряются:

- тип ошибки;
- возможность retry;
- путь поля;
- необходимость повторного входа;
- диагностический код.

При этом Adapter не обязан самостоятельно выполнять все инфраструктурные действия.

Например, он может классифицировать:

```text
401
→ unauthenticated
```

а single-flight refresh token flow останется ответственностью общего auth/API-слоя.

Иначе каждый Adapter начнёт самостоятельно:

- обновлять токен;
- повторять запрос;
- выполнять logout;
- перенаправлять пользователя.

Это размоет границы ответственности.

### Facade для внешнего SDK

Предположим, компоненты напрямую используют analytics SDK:

```ts
sdk.track("purchase", {
  user_id: userId,
  amount,
});
```

Другой компонент:

```ts
sdk.sendEvent({
  name: "purchase",
  payload: {
    amount,
  },
});
```

В результате компоненты знают:

- API поставщика;
- формат событий;
- правила добавления пользователя;
- состояние инициализации;
- consent;
- обработку недоступности SDK.

Facade предоставляет API, принадлежащий приложению:

```ts
type AnalyticsEvent =
  | {
      type: "productViewed";
      productId: string;
    }
  | {
      type: "purchaseCompleted";
      orderId: string;
      amount: number;
    };

type Analytics = {
  track(
    event: AnalyticsEvent,
  ): void;
};
```

Реализация скрывает подсистему:

```ts
function createAnalyticsFacade({
  provider,
  getContext,
  hasConsent,
}: {
  provider: AnalyticsProvider;
  getContext: () => {
    userId?: string;
    sessionId: string;
  };
  hasConsent: () => boolean;
}): Analytics {
  return {
    track(event) {
      if (!hasConsent()) {
        return;
      }

      provider.track(
        mapAnalyticsEvent(event),
        getContext(),
      );
    },
  };
}
```

Компонент передаёт предметное событие:

```ts
analytics.track({
  type: "purchaseCompleted",
  orderId,
  amount,
});
```

и не управляет:

- consent;
- конфигурацией SDK;
- идентификатором сессии;
- vendor-specific именами;
- обработкой отсутствующего provider.

Facade полезен, когда несколько потребителей должны одинаково работать со связной подсистемой.

Frontend-примеры:

```text
analytics.track(event)

auth.login()
auth.logout()
auth.getSession()

featureFlags.isEnabled(flag)

storage.get(key)
storage.set(key, value)

notifications.show(message)
```

Facade может координировать несколько внутренних действий.

Например:

```text
auth.logout()
→ завершить серверную сессию
→ очистить query cache
→ закрыть WebSocket
→ уведомить другие вкладки
```

Но Facade не должен автоматически становиться владельцем всей бизнес-логики приложения.

Например, `analyticsFacade` может:

- проверять consent;
- добавлять общий контекст;
- выбирать provider;
- преобразовывать событие.

Он не должен решать, успешно ли завершён заказ. Это знает feature создания заказа, которая и вызывает предметное событие.

Публичный контракт Facade проектируют от потребностей приложения.

Плохой Facade:

```ts
analytics.trackEvent();
analytics.setSuperProperties();
analytics.flushQueue();
analytics.resetDeviceId();
analytics.getVendorSession();
```

Если он полностью копирует API поставщика, зависимость только получила новое имя.

Лучше предоставить небольшой предметный контракт:

```ts
analytics.track(event);
analytics.identify(user);
analytics.reset();
```

Приложение должно зависеть от собственной модели, а различия поставщиков остаются внутри.

Facade уменьшает vendor lock-in, но не устраняет его полностью.

Поставщики могут различаться:

- возможностями;
- гарантиями доставки;
- моделью идентификации;
- лимитами;
- форматом событий;
- поддержкой offline.

Если приложение использует уникальную возможность одного SDK, полностью скрыть это различие может быть невозможно или невыгодно.

Тогда ограничение фиксируют явно, а не создают видимость полной взаимозаменяемости.

Facade должен представлять одну связную подсистему.

Хорошие границы:

```text
analytics
authentication
feature flags
client storage
notifications
```

Опасная граница:

```text
appServices
```

которая одновременно содержит:

- auth;
- API;
- analytics;
- storage;
- dialogs;
- permissions;
- заказы;
- платежи.

Такой объект становится God Object:

- имеет слишком много причин для изменения;
- создаёт глобальную зависимость;
- усложняет тестирование;
- скрывает реальные связи модулей.

Если части подсистемы не связаны одной ответственностью, им нужны отдельные Facade или прямые зависимости.

### Adapter, Gateway и антикоррупционный слой

В реальном frontend названия могут пересекаться.

**Gateway** обычно обозначает объект, через который приложение обращается к внешней системе:

```text
PaymentGateway
UserApi
FeatureFlagGateway
```

Gateway отвечает за границу вызова.

**Adapter** подчёркивает преобразование несовместимого интерфейса.

**Антикоррупционный слой** — более широкая граница, которая не позволяет модели внешней системы проникать в собственную модель приложения.

Он может включать:

- Gateway;
- Adapter;
- mapper;
- runtime validation;
- error mapping;
- перевод терминов;
- несколько интеграционных сервисов.

Например:

```text
внешняя платёжная система
→ Gateway
→ Adapter и mapping
→ модель платежей приложения
```

Необязательно создавать отдельные файлы под каждое название.

Важно, чтобы граница действительно локализовала внешнюю модель.

### Признаки протекающей абстракции

Adapter или Facade не выполняет свою задачу, если потребителям всё равно приходится знать детали внешней системы.

Примеры:

```text
компонент получает VendorUserDto

компонент проверяет vendor error code

компонент обязан вызвать initializeSdk()

компонент знает, что provider не поддерживает событие

компонент передаёт vendor-specific configuration
```

В таком случае абстракция протекает.

Исправление не всегда означает полностью скрыть все возможности.

Иногда различия являются существенной частью продукта. Тогда их лучше выразить собственным явным контрактом:

```ts
type PaymentCapability = {
  supportsRefund: boolean;
};
```

чем заставлять потребителя проверять:

```ts
providerName === "vendorA"
```

Adapter или Facade не нужен, если:

- внешний API простой и стабильный;
- используется в одном локальном месте;
- преобразование отсутствует;
- общих правил нет;
- дополнительный слой только повторяет методы.

Лишний слой:

```ts
function getUser(id: string) {
  return sdk.getUser(id);
}
```

не даёт пользы, если:

- контракт полностью совпадает;
- зависимость локальна;
- изменение SDK не является реальным риском;
- нет mapping, политики или изоляции.

Проверочный вопрос:

```text
Какое изменение теперь локализовано
внутри Adapter или Facade?
```

Если ответа нет, прямой вызов может быть понятнее.

### Тестирование

Mapper тестируют как чистое преобразование:

```text
DTO
→ application model
```

Проверяют:

- переименование полей;
- даты;
- `null`;
- enum;
- необязательные значения;
- некорректный вход.

Adapter тестируют как границу:

```text
параметры приложения
→ внешний вызов
→ результат приложения
```

Проверяют:

- правильный endpoint;
- request mapping;
- response mapping;
- error mapping;
- runtime validation;
- несовместимую версию ответа.

Facade тестируют через его публичное поведение.

Например:

```text
нет consent
→ provider не вызывается

есть consent
→ добавляется общий контекст

provider недоступен
→ UI не падает по согласованному правилу
```

В тесте React-компонента подставляют контракт приложения:

```ts
const analytics: Analytics = {
  track: vi.fn(),
};
```

Компонент не обязан импортировать и настраивать настоящий SDK.

Но mock не доказывает, что реальная интеграция соответствует контракту.

Поэтому отдельно нужны интеграционные или contract-тесты границы:

```text
реальный SDK или тестовый backend
→ Adapter/Facade
→ ожидаемый контракт приложения
```

Custom hook может предоставлять удобный доступ к Facade:

```ts
const analytics =
  useAnalytics();
```

Но custom hook сам по себе не является Facade.

Роль определяется не синтаксисом, а задачей:

```text
useAnalytics
→ может получать Facade из Context

analytics
→ является публичным API подсистемы
```

Не стоит помещать интеграционную логику прямо в каждый hook, если она должна использоваться также:

- вне React;
- в middleware;
- в обработчике API;
- в обычной функции;
- в тестовой инфраструктуре.

В таком случае Facade существует отдельно, а hook только предоставляет его React-компонентам.

Практический выбор:

```text
контракты несовместимы
→ Adapter

подсистема слишком сложна
→ Facade

нужно только преобразовать объект
→ mapper

нужна единая точка обращения к внешней системе
→ Gateway

нужно защитить собственную модель от внешней
→ антикоррупционный слой
```

Главный принцип:

```text
Adapter
→ переводит внешний язык
на язык приложения

Facade
→ скрывает сложность подсистемы
за небольшим API
```

Оба паттерна полезны, когда создают реальную границу владения.

Если слой только добавляет ещё один переход между файлами, но не изолирует несовместимость, сложность или общую политику, прямой код будет понятнее.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Adapter и mapper - одно и то же?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Mapper преобразует одну структуру данных в другую:

```text
UserDto
→ User
```

Adapter приводит весь внешний интерфейс к контракту приложения.

Он может изменить:

- параметры;
- способ вызова;
- request DTO;
- response DTO;
- ошибки;
- асинхронность;
- набор доступных операций.

Полноценный Adapter часто использует mapper внутри.

Если задача ограничена переименованием полей и преобразованием даты, честнее назвать функцию:

```text
toUser
mapUserDto
```

а не создавать отдельную сущность только ради названия паттерна.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где размещать Adapter для backend API?</strong></summary>

<dl>
<dd>
<h2></h2>

На границе транспортного слоя и модели приложения:

```text
HTTP client
→ DTO
→ validation
→ Adapter
→ application model
```

React-компонент или бизнес-логика не должны знать:

- URL endpoint;
- `snake_case`;
- особенности сериализации;
- формат сетевой ошибки;
- специальные значения конкретного backend.

Adapter может принадлежать конкретной feature, если контракт используется только ею.

В общий слой его выносят, когда одна и та же граница действительно используется несколькими независимыми потребителями.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли преобразовывать данные в обе стороны?</strong></summary>

<dl>
<dd>
<h2></h2>

Если UI отправляет данные в формате, отличном от API, нужны отдельные преобразования:

```text
UserDto
→ User

UserFormValues
→ UpdateUserDto
```

Они не обязаны быть обратными.

Серверная модель может содержать:

- read-only поля;
- вычисляемые значения;
- версию;
- служебные metadata.

Форма может содержать:

- объект `Select`;
- `File`;
- временное поле;
- только редактируемую часть модели.

Каждое направление получает собственный явный контракт.

</dd>
</dl>

</details>

<details>
<summary><strong>Как адаптировать ошибки API?</strong></summary>

<dl>
<dd>
<h2></h2>

Транспортную ошибку преобразуют в ограниченный набор ошибок приложения.

Например:

```text
404
→ notFound

403
→ forbidden

422 field_errors
→ ошибки полей

timeout или временный 503
→ unavailable
```

Нужно сохранять информацию, необходимую потребителю:

- стабильный тип;
- возможность retry;
- путь поля;
- безопасные параметры;
- request ID.

Все ошибки нельзя превращать в одну строку.

При этом Adapter обычно только классифицирует `401`, а общий refresh flow остаётся ответственностью auth/API-инфраструктуры.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему не использовать внешний SDK прямо в компонентах?</strong></summary>

<dl>
<dd>
<h2></h2>

Тогда компоненты начинают зависеть от:

- названий методов SDK;
- типов поставщика;
- порядка инициализации;
- формата ошибок;
- consent;
- vendor-specific configuration.

Смена поставщика или добавление общего правила потребуют массовых изменений.

Facade предоставляет компонентам небольшой API приложения:

```text
analytics.track(event)
```

а конфигурация, mapping и жизненный цикл остаются внутри интеграционной границы.

Для одного простого локального вызова отдельный Facade может быть не нужен.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли Facade превратиться в God Object?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

Если один объект содержит:

- auth;
- analytics;
- storage;
- notifications;
- payments;
- dialogs;
- бизнес-правила,

у него слишком много причин для изменения.

Такой Facade:

- создаёт глобальную связанность;
- скрывает реальные зависимости;
- усложняет тестирование;
- становится центральной точкой всех изменений.

Facade должен представлять одну связную подсистему и иметь небольшой публичный API.

Несвязанные обязанности разделяют.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как Adapter и Facade влияют на тестирование?</strong></summary>

<dl>
<dd>
<h2></h2>

Они создают контракт приложения, который можно подменить в тесте.

UI-тест использует fake или mock:

```ts
const userApi: UserApi = {
  getUser: vi.fn(),
};
```

и не воспроизводит реальные детали backend или SDK.

Отдельно проверяют:

- mapper;
- request mapping;
- response mapping;
- error mapping;
- политику Facade;
- реальную интеграцию с внешней системой.

Mock потребителя не заменяет contract или integration test самой границы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Полностью ли Facade устраняет vendor lock-in, то есть зависимость от конкретного поставщика?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Он уменьшает количество прямых зависимостей, но возможности поставщиков могут отличаться.

Если контракт Facade полностью копирует API одного SDK, vendor lock-in только получает другое имя.

Собственный API должен отражать потребности приложения:

```text
track предметное событие
проверить feature flag
получить session
```

а не все технические возможности поставщика.

Уникальные возможности конкретного SDK иногда приходится выражать явно как ограничение или capability.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда Adapter или Facade не нужен?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда внешний API:

- простой;
- стабильный;
- используется локально;
- уже соответствует модели приложения;
- не требует общей политики.

Дополнительный слой не нужен, если он только повторяет вызов:

```ts
function getUser(id: string) {
  return sdk.getUser(id);
}
```

Абстракция оправдана реальной несовместимостью, сложностью, повторением правил или важной границей владения, а не возможностью когда-нибудь заменить любую библиотеку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем Adapter отличается от Gateway и антикоррупционного слоя?</strong></summary>

<dl>
<dd>
<h2></h2>

Gateway является точкой обращения к внешней системе:

```text
PaymentGateway
UserApi
```

Adapter подчёркивает преобразование несовместимого интерфейса.

Антикоррупционный слой защищает собственную модель приложения от внешней модели и может включать:

- Gateway;
- Adapter;
- mapper;
- validation;
- error mapping.

В небольшом frontend один модуль может выполнять несколько этих ролей.

Необязательно создавать отдельный класс под каждое название: важнее сохранить ясную границу.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли проверять DTO во время выполнения?</strong></summary>

<dl>
<dd>
<h2></h2>

TypeScript проверяет использование типов во время разработки, но не контролирует фактический HTTP-response.

Backend может вернуть:

- отсутствующее поле;
- неправильный тип;
- неизвестный enum;
- несовместимую версию.

Для критичных или нестабильных границ полезна runtime validation:

```text
response
→ validation
→ mapping
→ application model
```

При ошибке клиент получает контролируемую integration error и не передаёт повреждённые данные в UI.

Глубину проверки выбирают по риску и стоимости.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли custom hook быть Facade?</strong></summary>

<dl>
<dd>
<h2></h2>

Custom hook может предоставлять компоненту простой API:

```ts
const analytics =
  useAnalytics();
```

Но hook сам по себе не становится Facade только из-за префикса `use`.

Часто архитектура выглядит так:

```text
Analytics Facade
→ существует независимо от React

Context
→ передаёт зависимость

useAnalytics
→ получает Facade из Context
```

Это позволяет использовать интеграцию также вне компонентов и отдельно тестировать её.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как понять, что Adapter или Facade протекает?</strong></summary>

<dl>
<dd>
<h2></h2>

Абстракция протекает, если потребитель всё равно знает:

- DTO поставщика;
- vendor error codes;
- порядок инициализации SDK;
- технические имена методов;
- особенности конкретного provider;
- формат внутренней конфигурации.

Например:

```text
if providerName === "vendorA"
```

в React-компоненте означает, что различие поставщиков не изолировано.

Если различие важно продукту, его выражают собственным контрактом или capability, а не передают технические детали наружу.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```text
Три компонента напрямую вызывают SDK аналитики. Каждый по-разному добавляет userId,
а один отправляет событие до получения согласия пользователя. Как изменить границу?
```

Ожидаемый ответ: ввести небольшой Facade аналитики с API приложения, например `track(event)`. Компоненты передают предметные типизированные события, а Facade централизует проверку согласия, общий безопасный контекст, mapping в формат поставщика, выбор SDK и обработку его недоступности.

Если формат событий поставщика несовместим с предметной моделью приложения, внутри Facade используется Adapter или mapper. Бизнес-решение о том, когда произошло событие, остаётся в соответствующей feature.

## Где это встречается во frontend

| Граница | Adapter или Facade |
|---|---|
| REST/OpenAPI | Adapter преобразует DTO, даты, enum и ошибки в модель приложения |
| Analytics | Facade скрывает SDK, consent и общий контекст событий |
| Auth | Facade предоставляет API сессии, а Adapter скрывает контракт провайдера |
| Storage | Facade задаёт сериализацию, префиксы ключей и fallback |
| Feature flags | Facade предоставляет `isEnabled`, не раскрывая vendor SDK |
| Платёжный provider | Gateway и Adapter переводят внешний контракт в модель приложения |
| Runtime validation | Adapter не пропускает несовместимый response в feature |
| Простой локальный SDK-вызов | Прямой вызов без лишнего слоя |
