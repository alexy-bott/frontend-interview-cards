## Вопрос

<br>

 💬 **Чем отличаются Adapter и Facade? Где они применяются во frontend?**

<h2></h2>

<br>
<dl>
<dd>

Adapter, или адаптер, приводит существующий интерфейс к форме, которую ожидает клиентский код. Он нужен, когда две части системы должны работать вместе, но их методы, параметры, данные или модель ошибок несовместимы. Приложение зависит от собственного контракта, а адаптер знает детали внешней системы.

Например, API возвращает `UserDto` со строковой датой и именами полей в `snake_case`, а приложению нужен `User` с `Date` и `camelCase`:

```ts
type UserDto = {
  id: string;
  display_name: string;
  created_at: string;
};

type User = {
  id: string;
  displayName: string;
  createdAt: Date;
};

function toUser(dto: UserDto): User {
  return {
    id: dto.id,
    displayName: dto.display_name,
    createdAt: new Date(dto.created_at),
  };
}
```

Эта функция является mapper, то есть преобразователем данных. Она становится частью полноценного Adapter, если слой также приводит к контракту приложения способ вызова, параметры, успешный результат и ошибки внешнего API.

Facade, или фасад, предоставляет простой API поверх сложной подсистемы. Он может скрыть несколько SDK, обязательную конфигурацию и порядок вызовов, не меняя фундаментально их модель. Например, `analytics.track(name, properties)` внутри выбирает поставщика аналитики, добавляет данные сессии, учитывает согласие пользователя и обрабатывает недоступность SDK.

Коротко: Adapter делает несовместимый интерфейс совместимым, Facade упрощает работу с подсистемой. Один слой может выполнять обе роли, но различать их полезно по задаче, а не по имени файла.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Adapter и mapper - одно и то же?</strong></summary>

<dl>
<dd>
<h2></h2>

Mapper только преобразует одну структуру данных в другую. Adapter может использовать mapper, но также меняет интерфейс операции: параметры, способ вызова, асинхронность, формат ошибок или набор методов. Если задача ограничена преобразованием DTO, честнее назвать функцию mapper.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где размещать Adapter для backend API?</strong></summary>

<dl>
<dd>
<h2></h2>

На границе между транспортным слоем и моделью приложения. Код запроса получает DTO и сетевую ошибку, Adapter преобразует их в результат, понятный конкретному сценарию или feature. React-компонент не должен знать имена полей и особые форматы конкретного endpoint.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли преобразовывать данные в обе стороны?</strong></summary>

<dl>
<dd>
<h2></h2>

Если UI отправляет данные в формате, отличном от API, нужны отдельные направления: например, `toUser(dto)` и `toUpdateUserDto(form)`. Их не следует считать автоматически обратными: форма может содержать только часть полей, а сервер - вычисляемые и read-only значения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как адаптировать ошибки API?</strong></summary>

<dl>
<dd>
<h2></h2>

Adapter сопоставляет транспортные форматы с конечным набором ошибок приложения. Например, ответ `422` с `field_errors` превращается в ошибки конкретных полей, `401` - в требование обновить авторизацию, а временная сетевая ошибка - в результат, который можно повторить. Нельзя сводить все ошибки к одной строке и терять важный код или причину.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему не использовать внешний SDK прямо в компонентах?</strong></summary>

<dl>
<dd>
<h2></h2>

Тогда множество компонентов зависит от названий методов, типов и жизненного цикла конкретного SDK. Смена поставщика или единое правило согласия пользователя потребуют массовых правок. Facade оставляет компонентам небольшой API приложения и локализует интеграционные детали.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли Facade превратиться в God Object?</strong></summary>

<dl>
<dd>
<h2></h2>

Да. Если один `appServices` скрывает аналитику, авторизацию, storage, уведомления и бизнес-правила, у него слишком много причин для изменения. Facade должен представлять одну связную подсистему и иметь небольшой API, а не становиться глобальным контейнером всего приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как Adapter и Facade влияют на тестирование?</strong></summary>

<dl>
<dd>
<h2></h2>

Они создают собственную границу приложения. В тесте UI можно подставить реализацию этого контракта, не воспроизводя внутренности SDK или нестабильный ответ backend. Отдельно тестируют преобразование данных, ошибок и вызовы реальной интеграции на границе.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Полностью ли Facade устраняет vendor lock-in, то есть зависимость от конкретного поставщика?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Он уменьшает число прямых зависимостей, но возможности поставщиков могут различаться. Если API фасада копирует модель одного SDK, зависимость только получает другое имя. Собственный контракт должен отражать потребности приложения, а различия поставщиков обрабатываются внутри или явно признаются ограничением.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда Adapter или Facade не нужен?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда простой стабильный API используется в одном месте и дополнительный слой только повторяет его методы. Абстракция оправдана не потенциальной сменой любой библиотеки, а реальной несовместимостью, сложностью, повторением правил или важной границей владения.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```text
Три компонента напрямую вызывают SDK аналитики. Каждый по-разному добавляет userId,
а один отправляет событие до получения согласия пользователя. Как изменить границу?
```

Ожидаемый ответ: ввести небольшой Facade аналитики с API приложения, например `track(event)`. Внутри централизовать проверку согласия, добавление допустимого контекста, выбор SDK и обработку недоступности. Компоненты должны передавать предметное событие, а не управлять жизненным циклом и настройками поставщика.

## Где это встречается во frontend

| Граница | Adapter или Facade |
|---|---|
| REST/OpenAPI | DTO, даты, enum и ошибки преобразуются в модель приложения |
| Analytics | Один Facade скрывает SDK, проверку согласия и общий контекст событий |
| Auth | API приложения скрывает процесс обновления токена и особенности провайдера авторизации |
| Storage | Обёртка задаёт сериализацию, префикс ключей и поведение при недоступности storage |
| Feature flags | Facade предоставляет `isEnabled`, не раскрывая SDK поставщика компонентам |
