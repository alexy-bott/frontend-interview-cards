## Вопрос

<br>

 💬 **Как распознать God Object и безопасно разделить его? Что REP и CCP говорят о границах frontend-модулей и packages, то есть переиспользуемых пакетов?**

<h2></h2>

<br>
<dl>
<dd>

God Object, или объект с чрезмерной ответственностью, знает слишком много частей системы и принимает слишком много независимых решений.

Во frontend им может стать:

- page component;
- custom hook;
- Redux slice или store;
- service;
- Context Provider;
- API-модуль;
- manager;
- общий `utils`-модуль.

Например, один `CheckoutPage` одновременно:

```text
загружает cart
→ преобразует backend DTO
→ хранит форму
→ валидирует поля
→ рассчитывает доставку
→ управляет payment SDK
→ проверяет permissions
→ отправляет analytics
→ выполняет navigation
→ рендерит всю страницу
```

Любое изменение checkout проходит через один центр с большим числом зависимостей.

Главная проблема God Object — не размер файла, а отсутствие связной ответственности.

```text
много независимых причин для изменения
+
много знаний о разных подсистемах
+
централизованное управление несвязанными процессами
```

Компонент на тысячу строк не обязательно является God Object.

Например, большой декларативный компонент может описывать одну сложную, но связную форму:

```text
один сценарий
один владелец state
одна причина изменения
```

И наоборот, небольшой service может зависеть от:

```text
router
store
API
analytics
permissions
storage
WebSocket
```

и связывать половину приложения.

Поэтому число строк является только сигналом для проверки.

Полезнее оценивать:

- cohesion;
- coupling;
- причины изменения;
- владельца данных;
- количество зависимостей;
- сложность тестовой изоляции;
- историю совместных изменений.

**Cohesion**, или внутренняя связность, показывает, насколько данные и операции модуля относятся к одной задаче.

Высокая cohesion:

```text
модуль содержит связанные операции,
которые изменяются по одной причине
```

Низкая cohesion:

```text
модуль содержит несколько процессов,
случайно оказавшихся рядом
```

**Coupling**, или связанность, показывает, сколько знаний модулю требуется о других частях системы.

Высокая связанность проявляется, когда модуль знает:

- транспортные DTO;
- внутреннее устройство store;
- URL маршрутов;
- методы стороннего SDK;
- формат analytics events;
- правила permissions;
- структуру нескольких features.

### Признаки God Object

Один сигнал ещё не доказывает проблему.

Обычно совпадает несколько признаков.

**Много независимых причин для изменения**

Один файл меняется из-за:

```text
редизайна
изменения backend API
нового payment provider
изменения аналитики
нового permission
другой навигации
изменения правил валидации
```

Это означает, что в одной границе смешаны разные ответственности.

**Большой fan-out**

Fan-out — количество внешних зависимостей модуля.

Например:

```text
CheckoutPage
├── cartApi
├── userApi
├── deliveryApi
├── paymentSdk
├── analytics
├── router
├── featureFlags
├── permissions
└── storage
```

Большой fan-out не всегда является ошибкой.

Composition root может собирать много зависимостей.

Проблема возникает, если он не только собирает их, но и знает внутренние правила каждой подсистемы.

**Сложный общий state**

Компонент содержит множество несвязанных состояний:

```text
form fields
payment state
dialog state
delivery state
analytics flags
WebSocket state
navigation flags
```

Изменение одного состояния запускает effects, относящиеся к другим процессам.

**Большое количество effects**

Например:

```text
effect загружает данные
effect синхронизирует URL
effect отправляет analytics
effect управляет SDK
effect подписывается на события
effect выполняет navigation
```

Проблемой является не число `useEffect`, а смешивание нескольких lifecycle с разными владельцами.

**Трудная тестовая изоляция**

Чтобы проверить простой расчёт, тест должен настроить:

- router;
- store;
- API mocks;
- SDK;
- Context;
- timers;
- analytics.

Это означает, что отдельную ответственность трудно использовать независимо.

**Изменения из разных задач конфликтуют в одном файле**

Например:

```text
разработчик A меняет payment
разработчик B меняет delivery
разработчик C меняет analytics
```

и все регулярно получают merge conflicts в одном модуле.

Merge conflict сам по себе не определяет архитектуру, но может указывать на смешение причин изменения.

**Низкая переиспользуемость из-за багажа**

Полезную часть невозможно использовать отдельно, потому что она тянет:

```text
весь store
router
API
permissions
feature flags
```

Вместо переиспользования разработчики копируют код.

**Изменение распространяется каскадом**

Небольшая задача требует править:

```text
page
shared hook
global store
shared utils
API layer
analytics helper
```

Это называют большим blast radius — областью распространения изменения.

### God Component, God Hook и God Store

Во frontend проблема не ограничивается классическим объектом.

**God Component**

Компонент одновременно:

- получает данные;
- выполняет бизнес-правила;
- координирует процессы;
- управляет внешними интеграциями;
- содержит всю разметку.

**God Hook**

Например:

```ts
const checkout = useCheckout();
```

возвращает десятки значений и методов:

```text
cart
user
form
delivery
payment
dialogs
analytics
navigation
```

Само вынесение логики из компонента в один огромный hook не разделяет ответственности.

```text
God Component
→ переместили код
→ God Hook
```

Архитектура не улучшилась, если hook сохранил тот же общий state и зависимости.

**God Store**

Один глобальный store содержит:

- server state;
- поля форм;
- временное UI-состояние;
- SDK lifecycle;
- данные нескольких независимых features.

Любая feature начинает читать и изменять общую структуру.

**God Service**

Например:

```text
appService
applicationManager
globalController
```

имеет методы для:

- авторизации;
- заказов;
- аналитики;
- уведомлений;
- навигации;
- файлов.

Такой service становится скрытым глобальным владельцем приложения.

### Большой composition root не обязательно является God Object

Composition root — место, где приложение собирает зависимости и связывает крупные части.

Например, page может:

```tsx
function CheckoutPage() {
  const checkout =
    useCheckoutModel();

  return (
    <CheckoutLayout>
      <CartSummary
        cart={checkout.cart}
      />

      <DeliverySection
        delivery={checkout.delivery}
      />

      <PaymentSection
        payment={checkout.payment}
      />
    </CheckoutLayout>
  );
}
```

Page знает, какие части составляют checkout, но не обязан знать:

- формат backend DTO;
- методы payment SDK;
- правила retry;
- внутреннюю валидацию;
- формат analytics provider.

Допустимая роль page:

```text
получить готовые зависимости
→ связать крупные части
→ определить layout
```

Опасная роль:

```text
самостоятельно реализовать
внутренние правила всех частей
```

Composition root может иметь большой fan-out, но небольшой объём предметной логики.

### Как выбрать границу для extraction

Extract Class, Extract Module и Extract Function выделяют связную часть ответственности.

Во frontend результатом extraction чаще становится не класс, а:

- чистая функция;
- React component;
- custom hook;
- model;
- Adapter;
- service;
- use case;
- repository;
- отдельный module.

Границу выбирают не по длине фрагмента, а по причине изменения и владельцу данных.

Полезные вопросы:

```text
Какие данные используются вместе?

Какие операции меняются вместе?

Кто является владельцем этого state?

Каков lifecycle этих данных?

Какая внешняя система скрывается за кодом?

Можно ли назвать извлекаемую ответственность
одной короткой фразой?
```

Примеры.

**Чистое преобразование**

```text
UserDto
→ User
```

выносится в mapper или Adapter.

**Самостоятельная часть интерфейса**

```text
DeliveryAddressForm
```

выносится в component с узкими props.

**React-логика со своим lifecycle**

```text
управление полями доставки
```

может быть вынесена в hook, если она действительно является одной связной ответственностью.

**Бизнес-сценарий**

```text
создать заказ
→ подтвердить payment
→ обновить cache
```

выносится в use case или model с явной последовательностью.

**Внешняя интеграция**

```text
payment SDK
```

изолируется Adapter или Facade.

**Server state**

```text
cart query
```

остаётся в query layer, а не копируется без необходимости в локальный store.

### Простое разрезание файла не разделяет ответственность

Предположим, большой page разбили так:

```text
CheckoutPage.tsx
checkoutHelpers.ts
checkoutEffects.ts
checkoutHandlers.ts
checkoutUtils.ts
```

Но все функции продолжают принимать:

```ts
{
  cart,
  user,
  form,
  delivery,
  payment,
  router,
  analytics,
  permissions,
}
```

Такой extraction только переместил строки.

Связанность осталась прежней.

Признаки плохой границы:

- функция принимает почти весь исходный state;
- component получает десятки props и callbacks;
- новый module импортирует те же зависимости;
- файлы всегда меняются вместе;
- операции читают и изменяют чужой state;
- для понимания одного сценария нужно прыгать между множеством файлов;
- появились циклические зависимости.

Полезный extraction уменьшает знания каждой части.

Например, вместо:

```tsx
<DeliverySection
  cart={cart}
  user={user}
  form={form}
  errors={errors}
  payment={payment}
  router={router}
  analytics={analytics}
  setField={setField}
  submit={submit}
  openDialog={openDialog}
/>
```

лучше стремиться к контракту:

```tsx
<DeliverySection
  value={delivery}
  onChange={changeDelivery}
/>
```

или к автономной model, если состояние принадлежит самой секции.

Узкий контракт не означает минимальное число props любой ценой.

Он означает, что часть получает только знания, относящиеся к её ответственности.

### Безопасный процесс разделения

Большой модуль нельзя безопасно переписать одним движением только потому, что его архитектура неудобна.

Рефакторинг выполняют постепенно.

```text
1. Зафиксировать текущее поведение.
2. Найти причины изменения.
3. Выбрать одну связную ответственность.
4. Создать минимальный контракт.
5. Перенести код без изменения поведения.
6. Перевести одного потребителя.
7. Проверить тесты и runtime.
8. Перевести остальные обращения.
9. Удалить старый путь.
10. Повторить для следующей ответственности.
```

#### 1. Зафиксировать поведение

Перед extraction полезны:

- unit tests чистой логики;
- integration tests сценария;
- component tests;
- characterization tests;
- критичные end-to-end проверки.

Characterization test фиксирует фактическое текущее поведение, даже если внутренний код пока неудобен.

Цель:

```text
рефакторинг меняет структуру,
но не меняет наблюдаемое поведение
```

Необязательно покрывать весь God Object целиком.

Сначала защищают сценарий вокруг извлекаемой ответственности.

#### 2. Изучить реальные причины изменения

Источники:

- история задач;
- `git log`;
- pull requests;
- повторяющиеся bugs;
- merge conflicts;
- владельцы кода;
- roadmap.

Можно посмотреть, какие файлы часто меняются вместе.

Это называется change coupling, или связанность по совместным изменениям.

Например:

```text
deliveryForm.tsx
deliveryValidation.ts
deliveryApi.ts
```

регулярно меняются одной задачей.

Это сигнал, что они могут принадлежать одной feature-границе.

Но история изменений не является абсолютным правилом.

Файлы могли меняться вместе из-за временной миграции или неудачного текущего размещения.

#### 3. Начать с низкорисковой ответственности

Обычно проще сначала извлечь:

- чистое преобразование;
- formatter;
- validation;
- mapper;
- независимый presentational component.

Такие части:

- имеют меньше side effects;
- проще тестируются;
- требуют меньше lifecycle-решений.

После этого переходят к:

- server state;
- orchestration;
- SDK;
- подпискам;
- сложному локальному state.

#### 4. Создать seam

Seam — граница, через которую реализацию можно заменить или переместить без переписывания всего потребителя.

Например:

```ts
type PaymentGateway = {
  createPayment(
    orderId: string,
  ): Promise<Payment>;
};
```

Сначала старый код может реализовать этот контракт внутри исходного модуля.

Затем реализация переносится за границу.

Потребителю уже не требуется знать детали SDK.

#### 5. Сохранить одну работающую цепочку

Не нужно одновременно:

- менять API;
- переписывать state;
- заменять библиотеку;
- менять UI;
- переносить файлы.

Безопаснее:

```text
сначала структурный refactoring
→ затем изменение поведения
```

Иначе при ошибке трудно определить её источник.

#### 6. Перемещать владельца state осознанно

State не следует автоматически переносить в каждый извлечённый component.

Нужно определить владельца.

```text
state нужен только одной секции
→ локализовать в секции

state координирует несколько checkout-частей
→ оставить в checkout model

server state
→ оставить в query cache

состояние URL
→ хранить в router/search params
```

Дублирование одного значения в нескольких владельцах создаёт рассинхронизацию.

#### 7. Удалить старый путь

Временная миграционная обёртка полезна, но не должна оставаться навсегда.

После перевода потребителей удаляют:

- старые функции;
- дублирующий state;
- compatibility props;
- устаревшие imports;
- мёртвые feature flags.

Иначе новая граница добавится поверх старой сложности.

### Когда Extract Function достаточно

Extract Function подходит, когда внутри одной ответственности есть связный фрагмент, которому можно дать ясное имя.

Например:

```ts
function submitOrder() {
  validateOrder();
  createPayment();
  saveOrder();
}
```

Извлечение улучшает чтение:

```text
что выполняется
```

отделяется от:

```text
как это выполняется
```

Но функция остаётся частью той же архитектурной ответственности.

Если извлечённые функции используют общий state родителя, это не обязательно проблема.

Проблема возникает, когда первоначальный модуль всё ещё владеет несколькими независимыми сценариями.

### Когда нужен отдельный component

Component извлекают, когда часть UI имеет:

- самостоятельную семантику;
- собственный контракт;
- отдельные изменения;
- локальное поведение;
- возможность тестирования через пользовательский интерфейс.

Например:

```text
PaymentMethodSelector
DeliveryAddressForm
OrderSummary
```

Не стоит извлекать каждый `<div>` только ради уменьшения файла.

Компонентная граница должна отражать UI-роль или владельца поведения.

### Когда нужен custom hook

Hook подходит для связной React-логики:

- локальный state;
- effects;
- subscriptions;
- обработчики;
- взаимодействие с Context.

Например:

```text
useDeliveryAddress
usePaymentSession
useScrollRestoration
```

Плохое имя:

```text
useCheckoutEverything
usePageLogic
useAppManager
```

может указывать на сохранение чрезмерной ответственности.

Hook не должен становиться контейнером для всего кода, который мешает читать JSX.

### Когда нужен отдельный module или service

Module или service подходит, если логика:

- не зависит от render;
- используется вне React;
- имеет собственные зависимости;
- координирует предметную операцию;
- должна тестироваться отдельно.

Например:

```text
calculateDelivery
checkoutUseCase
paymentGateway
analyticsFacade
```

Service не должен автоматически становиться классом.

Функция или объектный модуль часто достаточно ясно выражает контракт.

### Как проверить результат extraction

Полезный refactoring должен изменить стоимость последующих изменений.

Проверяют:

```text
Стало ли меньше причин изменения у исходного модуля?

Уменьшилось ли число внешних зависимостей?

Стал ли контракт новой части уже?

Можно ли протестировать её отдельно?

Можно ли изменить реализацию,
не меняя потребителя?

Стало ли яснее владение state?

Исчезло ли дублирование?

Не появились ли циклические зависимости?
```

Увеличение числа файлов само по себе ничего не доказывает.

Плохой результат:

```text
одна задача
→ нужно открыть 14 мелких файлов
```

Хороший результат:

```text
изменение payment provider
→ затрагивает payment boundary
→ checkout page не меняется
```

Другой хороший результат:

```text
изменение layout
→ затрагивает components
→ API Adapter не меняется
```

### REP

REP — **Release Reuse Equivalency Principle**.

Основная идея:

```text
единица переиспользования
=
единица выпуска
```

Если код используется независимыми потребителями, они должны получать определённый release этого кода.

Для frontend package это означает:

- идентифицируемую версию;
- публичный API;
- правила совместимости;
- changelog;
- контролируемый выпуск;
- владельца;
- возможность обновляться не одновременно с автором;
- при необходимости deprecation policy.

Например, несколько приложений используют:

```text
@company/design-system
```

Потребитель должен понимать:

```text
какую версию он устанавливает
что изменилось
есть ли breaking changes
как выполнить migration
```

Если изменение исходников package мгновенно и без выбора попадает во все приложения, фактической независимой единицы переиспользования и выпуска может не быть.

REP не требует публиковать package в публичный npm registry.

Release может быть:

- внутренней npm-версией;
- workspace artifact;
- git tag;
- собранным package;
- версией внутреннего registry.

Суть заключается в управляемой границе между владельцем и потребителем.

### Что считать package во frontend

Слово `package` может означать разные уровни:

```text
TypeScript module
→ отдельный файл или набор imports/exports

feature module
→ внутренняя архитектурная граница приложения

workspace package
→ package в monorepo

published npm package
→ независимо устанавливаемый artifact

deployment unit
→ приложение или bundle, выпускаемый целиком
```

REP сильнее всего относится к независимо переиспользуемой и выпускаемой единице.

Обычная внутренняя папка:

```text
src/features/checkout
```

не обязана иметь:

- отдельную npm-версию;
- changelog;
- собственный release pipeline.

Она выпускается вместе с приложением.

При этом у неё всё равно должен быть ясный внутренний API и направление зависимостей.

### REP в monorepo

Наличие `package.json` внутри monorepo не делает модуль независимой release unit автоматически.

Возможны две модели.

**Lockstep release**

```text
все packages
→ выпускаются вместе
→ имеют согласованный version cycle
```

Фактической крупной единицей релиза может оставаться весь продукт.

**Independent release**

```text
каждый package
→ имеет собственную версию
→ обновляется потребителями отдельно
```

Здесь REP требует особенно ясных:

- public exports;
- compatibility rules;
- changelog;
- versioning;
- dependency ranges.

Отдельный workspace package оправдан, когда есть:

- несколько самостоятельных потребителей;
- независимый владелец;
- отдельная скорость развития;
- собственные требования к сборке;
- контролируемый public API;
- необходимость независимого обновления.

Если два модуля всегда:

- меняются вместе;
- тестируются вместе;
- выпускаются вместе;
- принадлежат одной feature,

искусственное разделение на independently versioned packages может только усложнить работу.

### Public API package

Потребители должны зависеть от публичной границы:

```ts
import {
  Button,
  Dialog,
} from "@company/ui";
```

а не от случайной внутренней структуры:

```ts
import {
  Button,
} from "@company/ui/src/components/button/internal/Button";
```

Public API определяет:

- поддерживаемые exports;
- типы;
- доступные entry points;
- совместимость;
- допустимые способы расширения.

Изменение внутреннего файла не должно автоматически считаться breaking change, если публичный контракт сохранился.

REP относится не просто к версии архива, а к управляемому контракту релиза.

### SemVer и REP

Semantic Versioning обычно разделяет изменения на:

```text
major
→ несовместимое изменение публичного API

minor
→ обратно совместимая функциональность

patch
→ обратно совместимое исправление
```

Но наличие номера версии само по себе не гарантирует соблюдение REP.

Также нужны:

- определённый public API;
- предсказуемый выпуск;
- информация об изменениях;
- совместимость зависимостей;
- процесс migration.

Если package выпускается случайно и потребители не понимают последствия обновления, формальная версия мало помогает.

### CCP

CCP — **Common Closure Principle**.

Основная формула:

```text
код, который изменяется вместе,
стоит группировать вместе
```

Цель — уменьшить число packages или modules, затрагиваемых одним изменением.

Например, feature checkout содержит:

```text
UI
model
API Adapter
validation
tests
```

Если они регулярно изменяются из-за одних checkout-требований, их разумно держать внутри одной feature-границы.

```text
features/checkout/
  api/
  model/
  ui/
  tests/
```

Тогда продуктовая задача чаще остаётся локальной.

Плохая группировка:

```text
components/
hooks/
services/
validators/
utils/
```

если изменение checkout требует искать его части во всех технических папках проекта.

Технические слои сами по себе не являются ошибкой.

Проблема возникает, когда они разрывают код, который постоянно изменяется одной задачей.

### CCP и feature-based структура

Feature-based структура часто поддерживает CCP:

```text
всё, что меняется по причине checkout,
находится рядом
```

Преимущества:

- меньше затронутых областей;
- яснее ownership;
- проще локальные тесты;
- меньше случайных imports;
- проще удалять feature;
- ниже вероятность merge conflicts между несвязанными задачами.

Но нельзя механически помещать всё, что использует feature, внутрь неё.

Например:

```text
общий Button
общий HTTP client
общий date formatter
```

могут иметь другие причины изменения и других потребителей.

Граница определяется не только местом использования, но и причиной изменения.

### История совместных изменений

CCP можно проверять по истории репозитория.

Например, файлы:

```text
checkoutForm.tsx
checkoutValidation.ts
checkoutApi.ts
```

часто входят в одни commits и pull requests.

Это сигнал change coupling.

Полезные данные:

- какие файлы меняются вместе;
- какие команды их изменяют;
- какие задачи вызывают изменения;
- какие modules затрагивает один release;
- где возникают повторные merge conflicts.

Но co-change является диагностикой, а не автоматическим решением.

Иногда файлы меняются вместе из-за:

- крупной миграции;
- массового форматирования;
- изменения общего API;
- текущей неправильной архитектуры.

Нужно понимать причину совместного изменения.

### CCP и SRP

SRP и CCP связаны идеей причины изменения.

```text
SRP
→ ответственность класса,
  функции или модуля

CCP
→ состав более крупного component
  или package
```

SRP спрашивает:

```text
есть ли у модуля одна связная причина изменения?
```

CCP спрашивает:

```text
собраны ли вместе модули,
которые закрыты от одних и тех же изменений?
```

Практическая цель CCP:

```text
одна продуктовая задача
→ минимальное число архитектурных единиц
  нужно изменить и выпустить
```

### CCP и Common Reuse Principle

CCP не применяется изолированно.

Если следовать только ему, можно поместить слишком много кода в один package, чтобы формально изменять только его.

Другой принцип — Common Reuse Principle, CRP:

```text
код, который не переиспользуется вместе,
не следует принуждать переиспользовать вместе
```

Например, design system package содержит:

```text
Button
Dialog
редактор диаграмм
payment SDK Adapter
```

Приложению, которому нужен только `Button`, приходится зависеть от несвязанных частей и реагировать на их releases.

CCP удобен сопровождающим:

```text
группировать совместно изменяемый код
```

CRP защищает потребителей:

```text
не заставлять их зависеть
от ненужного кода
```

REP связывает переиспользование и выпуск:

```text
что переиспользуется как единица,
то выпускается как единица
```

Границы packages являются компромиссом между этими силами.

### Shared не является причиной изменения

Папка:

```text
shared/
```

часто превращается в новый God Object на уровне архитектуры.

Туда попадает код только потому, что:

```text
он используется больше одного раза
```

Но повторное использование не объясняет:

- владельца;
- причину изменения;
- public API;
- lifecycle;
- допустимые зависимости.

Например:

```text
shared/utils
shared/hooks
shared/services
```

могут содержать несвязанные функции со всего приложения.

Полезнее различать:

```text
shared UI primitives
shared infrastructure
shared domain library
feature-owned reusable module
```

Не каждый повторяющийся фрагмент нужно сразу переносить в общий package.

Иногда локальное дублирование дешевле преждевременной общей абстракции.

### Когда отдельный package не нужен

Отдельный package обычно не нужен, если код:

- используется только одним приложением;
- выпускается вместе с приложением;
- не имеет самостоятельного владельца;
- постоянно меняется вместе с одной feature;
- не требует отдельной сборки;
- не имеет независимого public API.

Внутренний module может обеспечить:

- инкапсуляцию;
- явные exports;
- тестирование;
- направление зависимостей.

Без дополнительных:

- версий;
- releases;
- dependency ranges;
- migrations.

Package является организационной и релизной границей, а не наградой за чистый код.

### Признаки неверной package-границы

**Слишком широкий package**

- несвязанные части;
- частые releases из-за разных причин;
- потребители обновляются из-за кода, который не используют;
- большой public API;
- разные владельцы;
- трудно определить breaking change.

**Слишком мелкие packages**

- одно изменение требует выпускать цепочку packages;
- много pass-through APIs;
- постоянные синхронные версии;
- сложный dependency graph;
- циклические зависимости;
- потребители всегда устанавливают весь набор вместе.

**Нестабильная граница**

- внутренние файлы импортируются напрямую;
- public API постоянно меняется;
- package зависит от feature потребителя;
- невозможно обновить package независимо;
- версия не объясняет совместимость.

### Практический процесс выбора границ

```text
1. Определить причины изменения.
2. Найти данные и операции,
   которые изменяются вместе.
3. Определить владельца state и lifecycle.
4. Выделить минимальный внутренний module.
5. Создать узкий public API.
6. Проверить направление зависимостей.
7. Посмотреть историю следующих изменений.
8. Создавать отдельный package,
   только если появилась независимая
   единица переиспользования и выпуска.
```

Границы не являются постоянными.

В начале продукта CCP может быть важнее:

```text
быстро изменять feature
в одной области
```

Когда архитектура стабилизируется и появляются независимые потребители, границы можно пересмотреть с учётом REP и CRP.

### Краткая модель

```text
God Object
→ слишком много независимых причин изменения

Extraction
→ выделение связной ответственности
  с небольшим контрактом

REP
→ переиспользуемая единица
  должна иметь управляемый release

CCP
→ совместно изменяемый код
  стоит группировать вместе

CRP
→ потребителя не следует заставлять
  зависеть от ненужных частей
```

Главный принцип:

```text
хорошая граница
→ локализует изменение

плохая граница
→ только перемещает строки
  или распространяет задачу
  по множеству модулей
```

- загружает cart;

- проверяет permissions;
- отправляет analytics;
- выполняет navigation;

Он одновременно является:

```text
API layer
model
use case
integration layer
UI
```

Любое изменение checkout затрагивает один центр с большим числом зависимостей.

Решение заключается не просто в уменьшении JSX, а в выделении владельцев данных и самостоятельных причин изменения.

<details>
<summary><strong>Является ли компонент на тысячу строк автоматически God Object?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Размер является сигналом, но не определением.

Большой компонент может иметь:

- одну связанную ответственность;
- один источник данных;
- простой декларативный render;
- небольшое число зависимостей.

Небольшой service уже может быть God Object, если знает router, store, API, analytics и несколько независимых features.

Важнее оценивать cohesion, coupling и причины изменения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выбрать границу для извлечения?</strong></summary>

<dl>
<dd>
<h2></h2>

Ищут данные и операции, которые:

- используются вместе;
- изменяются по одной причине;
- имеют одного владельца;
- обладают общим lifecycle;
- можно назвать одной ролью.

Типичные соответствия:

```text
чистое преобразование
→ function или mapper

внешний контракт
→ Adapter

React state и lifecycle
→ custom hook

самостоятельная часть UI
→ component

бизнес-сценарий
→ use case или model

сложная подсистема
→ Facade
```

Новая граница должна уменьшать объём знаний потребителя.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему Extract Class не обязан создавать class?</strong></summary>

<dl>
<dd>
<h2></h2>

Название refactoring возникло в объектно-ориентированном контексте.

Его смысл:

```text
выделить связную ответственность
и принадлежащие ей данные
```

В функциональном TypeScript результатом может быть:

- module функций;
- closure;
- Factory;
- service object;
- pure function.

В React это может быть component или hook.

Форма реализации зависит от языка, а не от названия refactoring.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда extraction ухудшает код?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда границу выбирают только по длине файла.

Признаки:

- десятки одноразовых функций;
- для понимания сценария нужно открыть множество файлов;
- параметры повторяют весь исходный state;
- появились pass-through components;
- modules всегда меняются вместе;
- возникли циклические зависимости;
- новый слой только перенаправляет вызов.

Полезный extraction уменьшает знания и причины изменения каждой части.

Он не должен только перемещать строки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как REP связан с npm package?</strong></summary>

<dl>
<dd>
<h2></h2>

Если несколько приложений независимо используют package, они должны получать определённый release.

Для этого нужны:

- версия;
- public API;
- совместимость;
- changelog;
- controlled release;
- migration для breaking changes.

Package становится контрактом между владельцем и потребителями.

REP не требует публичного npm.

Внутренняя registry или versioned artifact также могут быть единицей выпуска.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужен ли отдельный package для кода, который используется в двух features одного приложения?</strong></summary>

<dl>
<dd>
<h2></h2>

Не обязательно.

Сначала достаточно внутреннего module с ясным API.

Отдельный package оправдан, если появляются:

- самостоятельные потребители;
- независимый владелец;
- отдельный release cycle;
- собственная сборка;
- необходимость версионирования;
- стабильный public API.

Если код всегда изменяется и выпускается вместе с одним приложением, package может добавить лишнюю релизную сложность.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как CCP связан с feature-based структурой?</strong></summary>

<dl>
<dd>
<h2></h2>

Feature-based структура размещает рядом код, который меняется из-за одной продуктовой причины:

```text
feature/
  api/
  model/
  ui/
  tests/
```

Тогда задача чаще затрагивает одну область.

Это уменьшает:

- blast radius;
- число случайных imports;
- количество затронутых packages;
- сложность удаления feature.

Но действительно общие primitives и infrastructure не нужно копировать внутрь каждой feature.

Причину изменения определяют по ответственности, истории задач и ownership.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем CCP похож на Single Responsibility Principle?</strong></summary>

<dl>
<dd>
<h2></h2>

Оба принципа используют причину изменения.

SRP чаще применяют к:

- функции;
- классу;
- module;
- component.

CCP применяют к более крупной единице:

- архитектурному component;
- package;
- library.

Практическая цель CCP — чтобы одно изменение требовало пересобрать, протестировать и выпустить минимальное число компонентов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить, что разделение помогло?</strong></summary>

<dl>
<dd>
<h2></h2>

После следующих задач проверяют:

- затрагивается ли меньше независимых modules;
- стали ли контракты уже;
- уменьшился ли fan-out;
- можно ли тестировать части отдельно;
- стало ли понятнее владение state;
- исчезли ли циклические зависимости;
- локализовались ли изменения API или SDK.

Увеличение числа файлов не является самостоятельным улучшением.

Результат оценивают по стоимости последующих изменений.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли page component с большим числом зависимостей оставаться нормальным composition root?</strong></summary>

<dl>
<dd>
<h2></h2>

Да, если page в основном собирает готовые части:

```text
получает models
→ передаёт узкие props
→ определяет layout
```

Composition root может знать, какие feature-компоненты участвуют в странице.

Он не должен знать внутренние:

- DTO;
- SDK methods;
- retry rules;
- error formats;
- validation algorithms.

Большой fan-out допустим в точке сборки, если предметная логика делегирована владельцам.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему перенос всей логики из component в один custom hook не решает God Object?</strong></summary>

<dl>
<dd>
<h2></h2>

Если hook продолжает владеть:

- формой;
- API;
- payment;
- analytics;
- dialogs;
- navigation,

изменилась только физическая позиция кода.

```text
God Component
→ God Hook
```

Полезное разделение создаёт несколько связных границ с отдельными владельцами и небольшими контрактами.

Hook нужен для самостоятельной React-логики, а не как контейнер всего, что мешает читать JSX.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>В каком порядке безопасно разделять God Object?</strong></summary>

<dl>
<dd>
<h2></h2>

Безопасный порядок:

```text
1. Зафиксировать поведение тестами.
2. Выбрать одну ответственность.
3. Начать с чистой логики.
4. Создать минимальный контракт.
5. Перенести код без изменения поведения.
6. Перевести одного потребителя.
7. Проверить результат.
8. Перевести остальные обращения.
9. Удалить старый путь.
```

Не стоит одновременно менять архитектуру, API и пользовательское поведение.

Небольшие последовательные изменения проще проверять и откатывать.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое change coupling и как он помогает искать границы?</strong></summary>

<dl>
<dd>
<h2></h2>

Change coupling показывает, какие файлы или modules регулярно меняются вместе.

Источники:

- commits;
- pull requests;
- задачи;
- merge conflicts;
- история bugs.

Если `deliveryForm`, `deliveryValidation` и `deliveryApi` постоянно изменяются одной задачей, они могут принадлежать одной feature-границе.

Это диагностический сигнал, а не автоматическое правило.

Нужно проверить причину совместных изменений.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как REP применять в monorepo?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала определяют фактическую release unit.

При lockstep-модели все packages выпускаются вместе, поэтому крупной единицей релиза может оставаться весь продукт.

При независимых releases каждому package нужны:

- собственная версия;
- public API;
- changelog;
- compatibility rules;
- управляемые dependency ranges.

Само наличие `package.json` не доказывает независимость package.

Она должна существовать для его потребителей и процесса выпуска.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как соотносятся CCP и Common Reuse Principle?</strong></summary>

<dl>
<dd>
<h2></h2>

CCP предлагает группировать код, который изменяется вместе.

Это уменьшает число packages, затронутых задачей.

CRP предлагает не группировать код, который потребители не используют вместе.

Это защищает их от ненужных зависимостей и releases.

Между принципами существует компромисс:

```text
CCP
→ удобство сопровождения

CRP
→ удобство потребителей
```

REP связывает результат с управляемой единицей выпуска.

Границу выбирают с учётом всех трёх сил.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как понять, что modules стали слишком мелкими?</strong></summary>

<dl>
<dd>
<h2></h2>

Признаки:

- одно изменение затрагивает длинную цепочку modules;
- большая часть API только перенаправляет вызовы;
- параметры передаются через несколько уровней без преобразования;
- невозможно понять сценарий без постоянных переходов;
- modules всегда изменяются и выпускаются вместе;
- появляются циклические зависимости;
- публичных контрактов больше, чем самостоятельных ответственностей.

Модульная архитектура не означает максимальное количество файлов.

Граница должна локализовать изменение и сохранять связный код рядом.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```text
DashboardPage загружает данные из пяти API endpoints, преобразует ответы, управляет фильтрами,
строит widgets и отправляет аналитику. Стоит ли просто разбить JSX на пять файлов?
```

Ожидаемый ответ: извлечение JSX уменьшит размер `DashboardPage`, но не обязательно разделит ответственность.

Сначала нужно определить:

- кто владеет данными каждого widget;
- какие запросы являются общими;
- какие фильтры координируют всю страницу;
- какие части изменяются независимо;
- где находится граница внешнего API.

Возможное разделение:

```text
API DTO mapping
→ Adapter на границе API

связанные фильтры dashboard
→ dashboard model или hook

самостоятельные widgets
→ components с узкими props
  или собственными query boundaries

аналитика
→ Analytics Facade

DashboardPage
→ composition root
```

Если пять извлечённых components продолжают получать весь dashboard state и десятки callbacks, God Object только распределён по нескольким файлам.

## Где это встречается во frontend

| Симптом | Возможное изменение границы |
|---|---|
| Page знает DTO и ошибки backend | Вынести API Adapter и преобразование данных |
| Page реализует несколько независимых процессов | Разделить по причинам изменения и владельцам state |
| Hook возвращает десятки несвязанных значений | Выделить самостоятельные models или hooks |
| Store содержит server, form и UI state всех features | Вернуть state его реальным владельцам |
| Composition root знает детали каждой интеграции | Передавать готовые Facade и models |
| Общий package меняется без понятной версии | Ввести public API и release process по REP |
| Одна feature правит много случайных shared-файлов | Пересмотреть размещение по CCP |
| Потребитель обновляет package из-за ненужного кода | Разделить границу с учётом CRP |
| Workspace packages всегда выпускаются вместе | Проверить, нужна ли независимая package-граница |
| После extraction все файлы меняются одновременно | Объединить связную ответственность обратно |
