## Вопрос

<br>

 💬 **Как распознать God Object и безопасно разделить его? Что REP и CCP говорят о границах frontend-модулей и packages, то есть переиспользуемых пакетов?**

<h2></h2>

<br>
<dl>
<dd>

God Object, или объект с чрезмерной ответственностью, знает слишком много частей системы и принимает слишком много решений. Во frontend им может стать page component, то есть компонент страницы, hook, store или service, где одновременно находятся загрузка и преобразование данных, валидация, права доступа, аналитика, навигация и рендеринг.

Проблема определяется не числом строк. Большой декларативный компонент может быть понятным, а небольшой service - связывать половину приложения. Основные признаки: множество независимых причин для изменения, большое число зависимостей, трудная изоляция в тестах и правки из разных задач в одном файле.

Extract Class, Extract Module и Extract Function - рефакторинги, которые выносят связную часть ответственности за отдельную границу. Во frontend это часто не класс, а компонент, custom hook, чистая функция, Adapter или service. Сначала находят данные и операции, которые меняются вместе, затем переносят их с небольшим контрактом. Простое разрезание файла на вспомогательные функции не уменьшает связанность, если они продолжают читать общий state и изменяться одновременно.

REP и CCP применяются к более крупным единицам кода:

| Принцип | Смысл | Frontend-пример |
|---|---|---|
| REP, Reuse/Release Equivalence Principle | Единица переиспользования должна быть единицей релиза | Общий npm package имеет версию, правила совместимости и описание выпуска |
| CCP, Common Closure Principle | Код, который меняется по одной причине и в одно время, стоит группировать вместе | UI, API Adapter и тесты одной feature находятся в её границе |

REP не требует превращать каждую папку в отдельный package. Он говорит, что переиспользуемая библиотека должна выпускаться управляемо: потребитель понимает, какую версию получает и что изменилось. CCP уменьшает число модулей, затронутых одной задачей. Если изменение checkout постоянно требует правок в случайных `shared/utils`, код сгруппирован не по причине изменения.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Как выглядит God Object в React?</strong></summary>

<dl>
<dd>
<h2></h2>

Например, `CheckoutPage` сам загружает cart, преобразует DTO, хранит поля формы, валидирует их, рассчитывает доставку, управляет платёжным SDK, отправляет аналитику и рендерит всю страницу. Любое изменение checkout затрагивает один центр с большим числом зависимостей и состояний.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Является ли компонент на тысячу строк автоматически God Object?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Размер является сигналом для проверки, но важнее cohesion, или внутренняя связность ответственности. Большой компонент, который только явно описывает одну сложную форму, может быть цельным. Маленький глобальный service с доступом к router, store, API и аналитике уже имеет опасную связанность.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выбрать границу для извлечения?</strong></summary>

<dl>
<dd>
<h2></h2>

Искать изменения, которые происходят по одной причине и используют общий набор данных. Чистое преобразование выносится в функцию, внешняя интеграция - в Adapter, повторяемая логика React с собственным state - в hook, самостоятельная часть UI - в component. Новая граница должна иметь меньший и ясный контракт.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему Extract Class не обязан создавать class?</strong></summary>

<dl>
<dd>
<h2></h2>

Название рефакторинга возникло в объектно-ориентированном контексте. Его смысл - выделить связную ответственность и данные. В функциональном TypeScript ту же задачу часто решает модуль функций с замыканием, а в React - hook или component.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда extraction ухудшает код?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда граница выбрана по длине файла, а не по причине изменения. Появляются десятки одноразовых вспомогательных функций, параметры повторяют весь исходный state, а для понимания одного действия нужно открыть множество файлов. Полезное извлечение уменьшает знания каждой части, а не только перемещает строки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как REP связан с npm package?</strong></summary>

<dl>
<dd>
<h2></h2>

Если несколько приложений устанавливают общий package, им нужна определённая выпущенная версия, правила совместимости и информация об изменениях. Изменение исходников без нового выпуска не достигает потребителей, а публикация случайного набора файлов не даёт надёжной единицы переиспользования. Версия package становится контрактом между владельцем и приложениями.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужен ли отдельный package для кода, который используется в двух features одного приложения?</strong></summary>

<dl>
<dd>
<h2></h2>

Не обязательно. Внутренний module может иметь ясный API без отдельной публикации и SemVer. Package оправдан, когда есть самостоятельные потребители, отдельный владелец, собственный график выпусков или требования к сборке. Иначе он добавит отдельное версионирование без реальной независимости релизов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как CCP связан с feature-based структурой?</strong></summary>

<dl>
<dd>
<h2></h2>

Feature-based структура, то есть группировка кода по features, размещает component, API Adapter, model и тесты сценария рядом, если они меняются из-за одних продуктовых требований. Тогда задача затрагивает одну область. Но код, действительно общий для разных причин изменения, не нужно искусственно дублировать; границу уточняют по истории изменений и владельцам.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем CCP похож на Single Responsibility Principle?</strong></summary>

<dl>
<dd>
<h2></h2>

Оба группируют код по причине изменения. SRP чаще обсуждают для класса или модуля, CCP - для package или компонента архитектуры. Цель CCP состоит в том, чтобы одно изменение требовало выпуска минимального числа компонентов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить, что разделение помогло?</strong></summary>

<dl>
<dd>
<h2></h2>

Изменение одного сценария затрагивает меньше независимых модулей, контракты между частями стали уже, тесты можно запускать и понимать локально, а зависимости направлены явно. Увеличение числа файлов само по себе не является улучшением; полезность видна по стоимости следующих изменений.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```text
DashboardPage загружает данные из пяти API endpoints, преобразует ответы, управляет фильтрами,
строит widgets и отправляет аналитику. Стоит ли просто разбить JSX на пять файлов?
```

Ожидаемый ответ: извлечение JSX уменьшит размер page, но не обязательно разделит ответственность. Сначала определить независимые причины изменения и владельцев данных. Преобразование ответов вынести на API-границу, управление связанными фильтрами - в отдельную model или hook, самостоятельные widgets - в компоненты с узкими props, а аналитику - за Facade. Page остаётся composition root, то есть местом сборки этих частей.

## Где это встречается во frontend

| Симптом | Возможное изменение границы |
|---|---|
| Page знает DTO и формат ошибок backend | Вынести API Adapter и преобразование данных |
| Hook содержит несколько независимых процессов | Разделить по причинам изменения и владельцам state |
| Общий package меняется без понятной версии | Ввести процесс выпуска, SemVer и список изменений по REP |
| Одна feature правит много случайных shared-файлов | Пересмотреть размещение по CCP |
