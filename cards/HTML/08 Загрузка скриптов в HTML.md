## Вопрос

<br>

 💬 **Как загружаются скрипты в HTML? Чем отличаются обычный `script`, `defer`, `async`, `type="module"` и `preload`?**

<h2></h2>

<br>
<dl>
<dd>

При встрече с внешним `<script src="...">` без `defer` и `async` HTML parser — механизм разбора разметки — останавливается. Браузер загружает и выполняет скрипт и только после этого продолжает строить DOM. Поэтому синхронный внешний скрипт в `<head>` может задержать появление содержимого страницы.

Inline-скрипту не требуется загрузка, но parser также останавливается на время его выполнения.

`defer` относится только к внешним классическим скриптам. Файл загружается параллельно с разбором HTML, а выполняется после завершения parsing и до события `DOMContentLoaded`. Несколько `defer`-скриптов выполняются в порядке элементов `<script>` в документе.

Поэтому `defer` подходит основному коду, которому нужен готовый DOM и предсказуемый порядок. У inline-скрипта атрибут `defer` не меняет поведение.

`async` тоже позволяет загружать внешний скрипт параллельно, но выполняет его сразу после готовности файла. Если HTML в этот момент ещё разбирается, выполнение временно остановит parser.

Порядок нескольких `async`-скриптов определяется моментом их готовности, а не расположением в документе. Поэтому `async` подходит независимому коду, который не зависит от DOM, других скриптов и фиксированного порядка выполнения.

`type="module"` включает JavaScript-модули с `import`/`export`. Браузер загружает точку входа и её граф зависимостей параллельно с parsing, а обычный module script выполняет после разбора HTML. Отдельный `defer` ему не нужен.

Module script имеет собственную область видимости, автоматически работает в strict mode и загружается по правилам CORS. Обычные module scripts выполняются до `DOMContentLoaded`, поэтому их загрузка или выполнение могут задержать это событие.

Если модулю добавить `async`, он выполнится после готовности точки входа и необходимого графа зависимостей, не ожидая завершения parsing. Порядок относительно других async-модулей не гарантируется.

`preload` только заранее загружает ресурс и не выполняет его. Для классического скрипта используют `rel="preload"` с `as="script"`. URL, назначение и CORS-параметры должны совпадать с последующим реальным запросом, иначе браузер может загрузить ресурс повторно.

Для JavaScript-модулей используют `modulepreload`: браузер может заранее загрузить, разобрать и подготовить модуль, а также начать загрузку его зависимостей. Сам код выполняется только тогда, когда модуль будет подключён через `<script type="module">` или `import`.

Эти подсказки нужны, когда критичный ресурс обнаруживается слишком поздно. Ставить их на каждый файл нельзя, потому что ранние запросы конкурируют с CSS, изображениями, шрифтами и другими важными ресурсами.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Когда использовать <code>defer</code>, а когда <code>async</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`defer` используют для внешних классических скриптов, которым важен порядок и которые должны выполниться после разбора HTML.

`async` используют для независимых внешних скриптов, которые могут выполниться сразу после загрузки и не зависят от порядка относительно других скриптов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем модульный скрипт отличается от классического?</strong></summary>

<dl>
<dd>
<h2></h2>

Модульный скрипт поддерживает `import`/`export`, имеет отдельную область видимости и автоматически работает в strict mode. Браузер строит граф зависимостей и загружает модули по CORS-правилам.

Обычный module script выполняется после разбора HTML. Классический скрипт без специальных атрибутов блокирует parser.

В classic script верхнеуровневые объявления `var` и function declaration могут стать свойствами глобального объекта `window`. Объявления `let`, `const` и `class` свойствами `window` не становятся.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как <code>defer</code> связан с <code>DOMContentLoaded</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Скрипты с `defer` выполняются после разбора HTML, но до `DOMContentLoaded`. Поэтому тяжёлый deferred-скрипт может задержать это событие.

Обычные module scripts без `async` имеют похожее поведение: `DOMContentLoaded` ожидает их выполнение.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где лучше подключать <code>&lt;script&gt;</code> и почему?</strong></summary>

<dl>
<dd>
<h2></h2>

Современный основной скрипт с `type="module"` или внешний классический скрипт с `defer` можно подключать в `<head>`. Так браузер раньше обнаружит ресурс, загрузит его параллельно и выполнит после разбора HTML.

Обычный скрипт без атрибутов блокирует parser, поэтому его традиционно помещали перед `</body>`, когда основная разметка уже разобрана.

Для нового кода предпочтительнее явно выбрать `module`, `defer` или `async` по зависимостям, а не полагаться только на положение тега.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>preload</code> скрипта отличается от <code>modulepreload</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`<link rel="preload" as="script">` заранее загружает классический скрипт, но не выполняет его.

`<link rel="modulepreload">` предназначен для модулей: он загружает, разбирает и подготавливает модуль к последующему выполнению. Браузер также может начать загрузку его зависимостей.

В обоих случаях реальный `<script>` или `import` всё равно нужен. Предварительная загрузка сама по себе не запускает код.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему нельзя ставить <code>preload</code> на все скрипты?</strong></summary>

<dl>
<dd>
<h2></h2>

Сеть, соединения и приоритеты ограничены. Если заранее загружать все файлы, они начнут конкурировать с CSS, шрифтами и LCP-изображением, а смысл подсказки исчезнет.

`preload` и `modulepreload` применяют к небольшому числу ресурсов, которые действительно нужны рано, но без подсказки обнаруживаются поздно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужен ли <code>defer</code> у <code>&lt;script type="module"&gt;</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Module script без `async` уже ожидает завершения разбора документа. Атрибут `defer` на нём не меняет это поведение.

`async` переключает режим: модуль выполняется, как только готова точка входа и её зависимости, поэтому он может выполниться до завершения parsing, а порядок относительно других async-модулей не гарантируется.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Скрипт/ресурс | Подход |
| --- | --- |
| Главный бандл приложения | `type="module"` или бандл с `defer` |
| Независимая аналитика | `async` |
| Скрипт с зависимостью порядка | `defer` |
| Критическая зависимость модуля | `modulepreload` |
| Сторонний виджет | Проверить порядок и влияние на производительность |
