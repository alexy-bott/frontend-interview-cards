## Вопрос

<br>

 💬 **Что важно знать про доступность в HTML: ARIA, доступное имя и клавиатурную навигацию?**

<h2></h2>

<br>
<dl>
<dd>

Доступность HTML начинается с нативной семантики. Браузер преобразует DOM и связанные с ним свойства в accessibility tree - дерево доступности, которое используют скринридеры (программы экранного доступа) и другие вспомогательные технологии. Нативные элементы уже передают роль, имя, состояние и ожидаемое клавиатурное поведение.

ARIA - стандарт ролей и атрибутов, которые дополняют информацию в дереве доступности. Он нужен, когда нативного HTML недостаточно: например, для вкладок, составного combobox с полем ввода и списком вариантов или live region - области, изменения которой скринридер объявляет без перемещения фокуса.

ARIA не добавляет поведение. `role="button"` не делает `div` кнопкой для клавиатуры, а `aria-disabled="true"` не блокирует события. Разработчик обязан реализовать поведение, соответствующее объявленной роли. Неправильная роль или состояние хуже отсутствующего атрибута, потому что создаёт ложные ожидания.

Accessible name, или доступное имя, - краткое название элемента для вспомогательных технологий. У кнопки оно обычно берётся из видимого текста. Поле ввода получает имя из связанного `<label>`. `aria-labelledby` ссылается на текст другого элемента, а `aria-label` задаёт строку напрямую и подходит, например, кнопке только с иконкой.

Доступное описание дополняет имя, но не заменяет его. Например, `aria-describedby` может связать поле с пояснением или текстом ошибки. Кнопка «Удалить» должна сначала иметь понятное имя, а описание может уточнить, какой объект будет удалён.

Клавиатурная навигация должна следовать логичному порядку DOM. Нативные интерактивные элементы входят в последовательность Tab автоматически. `tabindex="0"` добавляет элемент в естественный порядок, `tabindex="-1"` разрешает программный фокус, но исключает переход по Tab, а положительные значения создают отдельный ручной порядок и обычно не используются.

Индикатор фокуса должен быть заметен. Нельзя удалять `outline` без равноценной замены. Компонент также должен поддерживать ожидаемые клавиши: например, Escape закрывает модальный диалог, а стрелки переключают активную вкладку согласно выбранному ARIA-паттерну.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Как элемент получает доступное имя?</strong></summary>

<dl>
<dd>
<h2></h2>

Зависит от элемента. Кнопка может получить имя из текста, `aria-label`, `aria-labelledby`. Поле ввода обычно получает имя из `label`. Изображение получает альтернативный текст через `alt`, если оно несёт смысл.

Предпочтителен видимый текст или `<label>`, потому что его одновременно воспринимают все пользователи. `aria-labelledby` полезен, когда нужный текст уже есть в интерфейсе; `aria-label` используют, когда видимой подписи действительно нет.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда использовать <code>aria-label</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда интерактивному элементу нужно доступное имя, но видимой текстовой подписи нет, например у кнопки поиска только с иконкой. Значение должно описывать действие: `aria-label="Поиск"`, а не внешний вид `aria-label="Лупа"`.

Если текст уже отображается, обычно лучше использовать его или связать через `aria-labelledby`. Иначе визуальная подпись и имя, объявляемое скринридером, могут расходиться; это также мешает управлению голосом по видимому тексту.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>tabindex &gt; 0</code> обычно плохая идея?</strong></summary>

<dl>
<dd>
<h2></h2>

Положительное значение помещает элемент в отдельный приоритетный порядок перед элементами с обычным фокусом. Такой порядок трудно поддерживать при изменении DOM и легко рассинхронизировать с визуальным расположением.

Обычно используют нативные интерактивные элементы. `tabindex="0"` добавляет нестандартный элемент в естественный порядок, а `tabindex="-1"` позволяет сфокусировать его из JavaScript, не добавляя в последовательность Tab.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли просто добавить <code>role</code> и считать элемент доступным?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Роль описывает назначение элемента в accessibility tree, но не добавляет клавиатуру, управление фокусом и изменение состояний. Самодельный компонент должен фактически выполнять контракт выбранной роли из ARIA Authoring Practices.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем доступное имя отличается от <code>aria-describedby</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Доступное имя отвечает на вопрос «что это за элемент?» и является основной короткой подписью. `aria-describedby` добавляет отдельное описание с инструкцией, ограничением или ошибкой.

Например, имя поля - «Пароль», а описание - «Не менее 12 символов». Одно длинное `aria-label` с инструкциями хуже, потому что смешивает название поля и дополнительную информацию.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| UI | Что проверить |
| --- | --- |
| Кнопка только с иконкой | Есть доступное имя |
| Модальное окно | Удержание фокуса, `aria-modal`, Escape |
| Самодельный select | Управление с клавиатуры и ARIA-паттерн |
| Поле формы | Подпись и описание ошибки |
| Ссылка быстрого перехода | Переход к основному контенту |
