## Вопрос

<br>

 💬 **Что важно знать про доступность в HTML: ARIA, доступное имя и клавиатурную навигацию?**

<h2></h2>

<br>
<dl>
<dd>

Доступность HTML начинается с нативной семантики. На основе DOM, семантики элементов, их состояний, применённых стилей и ARIA браузер формирует accessibility tree — дерево доступности, которое используют скринридеры и другие вспомогательные технологии.

Нативные интерактивные элементы уже предоставляют роль, состояния и ожидаемое клавиатурное поведение. Для формирования доступного имени они поддерживают стандартные источники: видимый текст, `<label>`, `alt` и другие связанные подписи.

ARIA — стандарт ролей и атрибутов, которые дополняют или уточняют информацию в дереве доступности. Он нужен, когда нативного HTML недостаточно: например, для вкладок, составного combobox с полем ввода и списком вариантов или live region — области, изменения которой скринридер объявляет без перемещения фокуса.

ARIA не добавляет поведение. `role="button"` не делает `div` кнопкой для клавиатуры, а `aria-disabled="true"` не блокирует события. ARIA меняет представление элемента для вспомогательных технологий, но разработчик обязан самостоятельно реализовать поведение, соответствующее объявленной роли.

Неправильная роль или состояние могут быть хуже отсутствующего атрибута, потому что создают ложные ожидания о возможностях компонента.

Accessible name, или доступное имя, — краткое название элемента для вспомогательных технологий. У кнопки оно обычно берётся из видимого текста. Поле ввода получает имя из связанного `<label>`. `aria-labelledby` ссылается на текст другого элемента, а `aria-label` задаёт строку напрямую и подходит, например, кнопке только с иконкой.

Источники доступного имени не обязательно объединяются: браузер применяет алгоритм с определённым порядком приоритетов. Поэтому не следует одновременно задавать несколько противоречащих друг другу подписей.

Доступное описание дополняет имя, но не заменяет его. Например, `aria-describedby` может связать поле с пояснением, ограничением или текстом ошибки. Кнопка «Удалить» должна сначала иметь понятное имя, а описание может уточнить, какой объект будет удалён.

Клавиатурная навигация должна следовать логичному порядку DOM. Нативные интерактивные элементы входят в последовательность Tab автоматически. `tabindex="0"` добавляет элемент в естественный порядок, `tabindex="-1"` разрешает программный фокус, но исключает переход по Tab, а положительные значения создают отдельный ручной порядок и обычно не используются.

Визуальный порядок также не должен неожиданно расходиться с DOM-порядком. Например, CSS-свойство `order` может переставить элементы визуально, не изменив последовательность клавиатурного фокуса.

Индикатор фокуса должен быть заметен. Нельзя удалять `outline` без равноценной замены.

Сложный компонент должен поддерживать клавиши, предусмотренные его ARIA-паттерном. Например, Escape закрывает модальный диалог, а стрелки перемещают активную вкладку. При открытии модального окна фокус переводят внутрь, удерживают в диалоге и после закрытия возвращают на элемент, который его открыл.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Как элемент получает доступное имя?</strong></summary>

<dl>
<dd>
<h2></h2>

Источник имени зависит от элемента и применяется по правилам accessible name computation.

Кнопка может получить имя из видимого текста, `aria-labelledby` или `aria-label`. Поле ввода обычно получает имя из связанного `<label>`. Изображение получает альтернативный текст через `alt`, если оно несёт смысл.

Предпочтителен видимый текст или `<label>`, потому что такую подпись одновременно воспринимают все пользователи.

`aria-labelledby` полезен, когда подходящий текст уже присутствует в интерфейсе. `aria-label` используют, когда видимой подписи действительно нет.

Одновременно заданные источники имени не обязательно складываются вместе: источник с более высоким приоритетом может заменить остальные.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда использовать <code>aria-label</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда интерактивному элементу нужно доступное имя, но видимой текстовой подписи нет, например у кнопки поиска только с иконкой.

Значение должно описывать назначение или действие:

```html
<button aria-label="Поиск">
  <!-- иконка -->
</button>
```

Имя «Поиск» описывает действие лучше, чем «Лупа», которое сообщает только внешний вид иконки.

Если текст уже отображается, обычно лучше использовать его или связать через `aria-labelledby`. `aria-label` может заменить имя из видимого содержимого, поэтому визуальная подпись и имя, объявляемое скринридером, способны разойтись.

Такое расхождение также мешает пользователям голосового управления выбирать элемент по тексту, который они видят на экране.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>tabindex &gt; 0</code> обычно плохая идея?</strong></summary>

<dl>
<dd>
<h2></h2>

Положительное значение помещает элемент в отдельный приоритетный порядок перед элементами с обычным фокусом.

Такой порядок трудно поддерживать при изменении DOM и легко рассинхронизировать с визуальным расположением элементов.

Обычно используют нативные интерактивные элементы. `tabindex="0"` добавляет нестандартный элемент в естественный порядок, а `tabindex="-1"` позволяет сфокусировать его из JavaScript, не добавляя в последовательность Tab.

Само добавление `tabindex="0"` не делает элемент полноценной кнопкой, ссылкой или другим интерактивным компонентом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли просто добавить <code>role</code> и считать элемент доступным?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Роль описывает назначение элемента в accessibility tree, но не добавляет клавиатурное управление, управление фокусом, нативные состояния и обработку действий.

Самодельный компонент должен фактически выполнять контракт выбранной роли из ARIA Authoring Practices: поддерживать нужные клавиши, состояния и переходы фокуса.

Например, `role="button"` требует не только обработчика клика, но и доступного имени, возможности фокусировки и клавиатурной активации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем доступное имя отличается от <code>aria-describedby</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Доступное имя отвечает на вопрос «что это за элемент?» и является его основной короткой подписью.

`aria-describedby` добавляет отдельное описание с инструкцией, ограничением, пояснением или ошибкой.

Например, имя поля — «Пароль», а описание — «Не менее 12 символов».

Одно длинное `aria-label` с инструкциями обычно хуже, потому что смешивает основное название элемента и дополнительную информацию.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| UI | Что проверить |
| --- | --- |
| Кнопка только с иконкой | Есть доступное имя |
| Модальное окно | Перевод фокуса внутрь, удержание, возврат, `aria-modal`, Escape |
| Самодельный select | Управление с клавиатуры и соответствующий ARIA-паттерн |
| Поле формы | Подпись, инструкция и описание ошибки |
| Ссылка быстрого перехода | Переход фокуса к основному контенту |
