## Вопрос

<br>

 💬 **Как обеспечить доступность HTML-интерфейса, начиная с нативной семантики и дополняя её только там, где нужны ARIA или ручное управление фокусом?**

<h2></h2>

<br>
<dl>
<dd>

Доступность HTML начинается с нативной семантики. Браузер сопоставляет DOM, состояния элементов, CSS и ARIA с accessibility tree — представлением интерфейса, которое используют скринридеры и другие вспомогательные технологии.

Нативные интерактивные элементы уже имеют подходящую роль и ожидаемое клавиатурное поведение. Например, `<button>` можно сфокусировать и активировать с клавиатуры без ручного воспроизведения поведения кнопки через `div`.

ARIA добавляет или уточняет семантическую информацию, когда нативного HTML недостаточно: роль виджета, его имя, состояние или связь с другими элементами. Это нужно, например, для вкладок, составного combobox или live region.

ARIA не добавляет поведение. `role="button"` не реализует фокус и клавиатурную активацию, а `aria-disabled="true"` не блокирует события. Код компонента должен фактически поддерживать поведение объявленной роли. Неверная ARIA может создать для пользователя ложную модель интерфейса, поэтому нативный HTML предпочтителен, когда он уже решает задачу.

Accessible name, или доступное имя, — краткое программное название элемента. Кнопка обычно получает его из видимого текста, поле ввода — из связанного `<label>`, `aria-labelledby` может взять имя из другого элемента, а `aria-label` задаёт строку напрямую, например для кнопки только с иконкой.

Если у элемента есть несколько возможных источников имени, браузер вычисляет одно итоговое имя по алгоритму приоритетов: значения не обязаны складываться. `aria-labelledby` и `aria-label` могут переопределить имя из нативной подписи или текста. Если видимая текстовая подпись уже есть, её текст должен сохраняться в доступном имени, чтобы элемент можно было надёжно выбрать в том числе голосовой командой.

Доступное описание дополняет имя, но не заменяет его. Например, `aria-describedby` может связать поле с инструкцией, ограничением или текстом ошибки.

Клавиатурный фокус должен идти в логичном порядке. Нативные интерактивные элементы участвуют в последовательной навигации автоматически. `tabindex="0"` включает элемент в последовательность фокуса по его месту в DOM, `tabindex="-1"` позволяет сфокусировать его программно, но исключает из обычного перехода по Tab, а положительные значения создают отдельный приоритетный порядок и настоятельно не рекомендуются.

Визуальный порядок не должен неожиданно расходиться с порядком фокуса. Например, CSS-свойство `order` может переставить элементы на экране, не изменив их последовательность в DOM.

Индикатор фокуса должен оставаться заметным. Если стандартный `outline` убирают, его заменяют равноценным видимым индикатором.

Сложный компонент должен реализовать клавиатурный контракт своего паттерна. В модальном диалоге при открытии фокус переводят внутрь; `Tab` и `Shift+Tab` не выпускают его за пределы диалога, `Escape` закрывает диалог, а после закрытия фокус обычно возвращают на элемент, который его открыл.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Когда использовать <code>aria-label</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда интерактивному элементу нужно доступное имя, но видимой текстовой подписи нет, например у кнопки поиска только с иконкой.

Значение должно описывать назначение или действие:

```html
<button aria-label="Поиск">
  <!-- иконка -->
</button>
```

Имя «Поиск» описывает действие лучше, чем «Лупа», которое сообщает только внешний вид иконки.

Если текст уже отображается, обычно лучше использовать его как источник имени или связать через `aria-labelledby`. `aria-label` может переопределить имя из видимого содержимого, поэтому при видимой подписи её текст должен оставаться частью доступного имени. Иначе пользователю голосового управления может не сработать команда по надписи, которую он видит на экране.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>tabindex &gt; 0</code> обычно плохая идея?</strong></summary>

<dl>
<dd>
<h2></h2>

Положительное значение помещает элемент в отдельный приоритетный порядок перед элементами с обычным фокусом.

Такой порядок трудно поддерживать при изменении DOM и легко рассинхронизировать с визуальным расположением элементов.

Обычно используют нативные интерактивные элементы. `tabindex="0"` добавляет нестандартный элемент в естественный порядок, а `tabindex="-1"` позволяет сфокусировать его из JavaScript, не добавляя в последовательность Tab.

Само добавление `tabindex="0"` не делает элемент полноценной кнопкой, ссылкой или другим интерактивным компонентом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли просто добавить <code>role</code> и считать элемент доступным?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Роль описывает назначение элемента в accessibility tree, но не добавляет клавиатурное управление, управление фокусом, нативные состояния и обработку действий.

Самодельный компонент должен фактически выполнять контракт выбранной роли из ARIA Authoring Practices: поддерживать нужные клавиши, состояния и переходы фокуса.

Например, `role="button"` требует не только обработчика клика, но и доступного имени, возможности фокусировки и клавиатурной активации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем доступное имя отличается от <code>aria-describedby</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Доступное имя отвечает на вопрос «что это за элемент?» и является его основной короткой подписью.

`aria-describedby` добавляет отдельное описание с инструкцией, ограничением, пояснением или ошибкой.

Например, имя поля — «Пароль», а описание — «Не менее 12 символов».

Одно длинное `aria-label` с инструкциями обычно хуже, потому что смешивает основное название элемента и дополнительную информацию.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| UI | Что проверить |
| --- | --- |
| Кнопка только с иконкой | Есть доступное имя |
| Модальное окно | Фокус внутри, циклический Tab, возврат фокуса, `aria-modal`, Escape |
| Самодельный select | Управление с клавиатуры и соответствующий ARIA-паттерн |
| Поле формы | Подпись, инструкция и описание ошибки |
| Ссылка быстрого перехода | Переход фокуса к основному контенту |
