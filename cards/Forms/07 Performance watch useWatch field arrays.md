## Вопрос

<br>

 💬 **Как оптимизировать большие формы? Что важно знать про `watch`, `useWatch` и массивы полей (`field arrays`)?**

<h2></h2>

<br>
<dl>
<dd>

Производительность формы определяется не самим числом полей, а объёмом работы после их изменения.

Если управляемое значение хранится в верхнем компоненте, каждый символ может повторно рендерить большое дерево, запускать тяжёлую валидацию, фильтрацию списков и зависимые вычисления.

Сначала проблему подтверждают с помощью React Profiler, то есть инструмента измерения render и commit, затем сужают область состояния, подписок и вычислений.

`watch(name)` читает значение во время render компонента, в котором используется экземпляр формы. Изменение отслеживаемого значения обновляет этот компонент.

`watch()` без имени подписывает компонент на значения всей формы и значительно расширяет область повторного render.

Если обновлять интерфейс не нужно, используют `subscribe`, чтобы наблюдать значения и состояние формы без render React-компонента. Устаревший вариант `watch` с callback-функцией для новых реализаций не используют.

`useWatch({ control, name })` создаёт подписку внутри компонента, где вызван hook. Если разместить его в небольшом дочернем компоненте, изменение поля обновит только этот участок интерфейса.

Параметр `exact` включает точное совпадение имени, а `compute` позволяет подписаться на значения формы, но возвращать только необходимый вычисленный результат.

Например, компонент может следить за всем списком товаров, но получать только их общую стоимость.

Порядок создания подписки имеет значение. Если вызвать `setValue` до того, как компонент с `useWatch` подписался, раннее изменение может не прийти в эту подписку как новое событие.

При необходимости подписанное значение объединяют с текущим результатом `getValues()`:

```ts
const watchedValues = useWatch();

const values = {
  ...getValues(),
  ...watchedValues,
};
```

`useFormState({ control, name, exact })` так же локализует обновления состояния формы на уровне компонента, где вызван hook.

`name` и `exact` позволяют сузить подписку на состояние конкретного поля. Подписку располагают там, где результат отображается:

- ошибка — рядом с полем;
- `isSubmitting` — рядом с кнопкой;
- состояние группы полей — внутри этой группы;
- счётчик ошибок — в отдельной сводке.

`useFieldArray` управляет динамическим списком: телефонами, адресами, участниками или товарами заказа.

Каждый объект из `fields` содержит стабильный `id`, который используют как React `key`:

```tsx
{fields.map((field, index) => (
  <Row
    key={field.id}
    index={index}
  />
))}
```

Индекс после удаления или перестановки меняется и может привязать DOM или локальное состояние компонента не к той строке.

`fields` описывает структуру массива, порядок строк и начальные данные для render. Его не следует вручную изменять или считать единственным источником текущих значений каждого зарегистрированного поля.

Актуальные значения читают через:

- `useWatch`;
- `watch`;
- `getValues`;
- данные `handleSubmit`.

Операции `append`, `prepend`, `insert` и `update` ожидают объект с полноценной структурой строки, а не случайный частичный объект.

Операции с массивом имеют разное поведение.

`update(index, value)` заменяет строку, размонтирует её поля и монтирует заново. Для точечного изменения без перемонтирования используют `setValue` с путём конкретного поля:

```ts
setValue(`items.${index}.name`, value);
```

Не следует без необходимости складывать несколько структурных операций, например `append` и `remove`, подряд в одном обработчике. Если изменение можно выразить одной операцией, лучше использовать её; зависимую следующую операцию при необходимости выполняют отдельно.

С `shouldUnregister` нужно быть осторожным. При значении `true` размонтированное поле удаляется из данных формы. Перестановка строк или виртуализация могут временно размонтировать элементы и привести к потере значений.

Дополнительно:

- уменьшают частоту тяжёлой проверки схемы;
- отменяют или игнорируют устаревшие асинхронные проверки;
- не пересоздают большие списки вариантов без причины;
- изолируют сложные controlled-компоненты;
- виртуализируют действительно длинные списки.

Виртуализация оставляет в DOM только видимую часть элементов. Поскольку остальные строки размонтируются, перед её внедрением нужно проверить сохранение значений, фокуса, ошибок и работу `shouldUnregister`.

Оптимизацию применяют к измеренному узкому месту, а не оборачивают каждое поле в `memo` заранее.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем <code>watch</code> отличается от <code>useWatch</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`watch` вызывается через экземпляр формы и обновляет компонент, в котором читаются отслеживаемые значения.

Если `watch` используется в корневом компоненте формы, изменение значения может повторно рендерить всё его поддерево.

`useWatch` создаёт подписку в том компоненте, где вызван, и позволяет локализовать повторный render:

```tsx
function PriceTotal({ control }: Props) {
  const items = useWatch({
    control,
    name: "items",
  });

  return <span>{calculateTotal(items)}</span>;
}
```

Для наблюдения без обновления интерфейса используют `subscribe`, а не устаревший вариант `watch` с callback-функцией.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему в массиве полей нельзя использовать индекс как <code>key</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

При удалении или перестановке индекс меняется, и React может переиспользовать DOM и локальное состояние для другой строки.

`useFieldArray` создаёт для каждой строки стабильный `field.id`. Его используют как `key`:

```tsx
{fields.map((field, index) => (
  <input
    key={field.id}
    {...register(`items.${index}.name`)}
  />
))}
```

`field.id` используется как React `key`, а индекс остаётся частью пути регистрации:

```text
items.0.name
items.1.name
```

Не следует заменять `field.id` бизнес-идентификатором, который может отсутствовать, повторяться или изменяться во время редактирования.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как режим валидации влияет на производительность?</strong></summary>

<dl>
<dd>
<h2></h2>

`mode: "onChange"` может запускать проверку схемы и обновлять ошибки на каждый символ.

Если схема тяжёлая или содержит межполевые проверки, стоимость становится заметной на большой форме.

В зависимости от сценария используют:

- `onBlur`;
- `onSubmit`;
- точечный `trigger`;
- отдельную асинхронную проверку нужного поля;
- `debounce` для сетевого запроса.

Дорогую удалённую проверку не следует без необходимости помещать в resolver, который запускается при каждом изменении всей формы.

Решение зависит от стоимости проверки и требуемой пользователю скорости обратной связи.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему сложные UI-компоненты могут замедлить форму?</strong></summary>

<dl>
<dd>
<h2></h2>

`Select`, `DatePicker` или `Autocomplete` могут:

- рендерить большое всплывающее окно;
- фильтровать список вариантов;
- выполнять позиционирование;
- обновлять управляемое значение;
- пересчитывать зависимые данные.

Их изолируют через `Controller` или `useController`, размещённые в отдельном компоненте, и не поднимают значение выше необходимого.

Большой список вариантов не пересоздают без причины. Если в нём действительно много элементов, применяют виртуализацию или серверный поиск.

Само использование `Controller` не оптимизирует компонент автоматически: область render зависит от того, где расположены подписки и какие props получает компонент.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает <code>shouldUnregister</code> в динамической форме?</strong></summary>

<dl>
<dd>
<h2></h2>

По умолчанию RHF сохраняет значение размонтированного поля.

При `shouldUnregister: true` поле после размонтирования удаляется из значений, и поведение становится ближе к нативной форме.

Это может быть полезно для условных полей или шагов формы, данные которых не должны отправляться после скрытия.

Однако строки `useFieldArray` могут размонтироваться при:

- перестановке;
- `update`;
- условном отображении;
- виртуализации списка.

При `shouldUnregister: true` такое размонтирование может удалить значения. Поэтому совместное поведение настройки и динамического списка нужно проверять отдельно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>update</code> в <code>useFieldArray</code> может сбросить локальное состояние строки?</strong></summary>

<dl>
<dd>
<h2></h2>

`update(index, value)` заменяет данные строки, размонтирует её поля и монтирует их заново.

Из-за перемонтирования могут сброситься:

- локальный state компонента строки;
- состояние фокуса;
- открытый dropdown;
- DOM-состояние неуправляемого стороннего компонента.

Если нужно изменить одно поле и сохранить существующий экземпляр строки, используют:

```ts
setValue(`items.${index}.name`, value);
```

Для замены всей строки перемонтирование может быть ожидаемым.

Объект для `update` должен содержать полноценные данные строки, а не только изменяемое поле.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Проблема | Решение |
| --- | --- |
| Большая форма тормозит на вводе | Измерить render, локализовать подписки и дробить компоненты |
| Зависимое поле | `useWatch` рядом с зависимой логикой |
| Наблюдение без render | `subscribe` |
| Динамический список полей | `useFieldArray` и `field.id` как `key` |
| Точечное изменение строки | `setValue` вместо `update`, если перемонтирование не нужно |
| Тяжёлая валидация | `onBlur`/`onSubmit`, точечная проверка, задержка сетевого запроса |
| Большой `Select` | Стабильный список вариантов, серверный поиск или виртуализация |
