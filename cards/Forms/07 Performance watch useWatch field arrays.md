## Вопрос

<br>

 💬 **Как оптимизировать большие формы? Что важно знать про `watch`, `useWatch` и массивы полей (`field arrays`)?**

<h2></h2>

<br>
<dl>
<dd>

Производительность формы определяется не самим числом полей, а объёмом работы после их изменения. Если управляемое значение хранится в верхнем компоненте, каждый символ может повторно рендерить всю форму, тяжёлые списки вариантов и зависимые вычисления. Сначала проблему подтверждают с помощью React Profiler, инструмента измерения рендеров, затем сужают область состояния и подписок.

`watch(name)` читает значение во время рендера компонента с `useForm`; изменение подписанных значений обновляет этот корневой компонент. `watch()` без имени подписывает его на всю форму и расширяет область повторного рендера. Если обновлять интерфейс не нужно, используют `subscribe`, чтобы наблюдать значения без рендера React-компонента.

`useWatch({ control, name })` размещают внутри небольшого дочернего компонента. Тогда изменение поля обновляет только этот участок. Параметр `exact` включает точное совпадение имени, а `compute` позволяет подписаться на данные формы, но возвращать только вычисленный результат. Подписку создают до `setValue`, иначе очень раннее изменение может быть пропущено; при необходимости подписанное значение объединяют с текущим результатом `getValues()`.

`useFormState({ control, name, exact })` так же локализует `errors`, `isDirty` и другие части состояния. Подписку располагают там, где результат отображается: ошибка рядом с полем, `isSubmitting` рядом с кнопкой, счётчик ошибок в сводке.

`useFieldArray` управляет динамическим списком: телефонами, адресами, участниками. Каждый объект из `fields` содержит стабильный `id`, который используют как React `key`; индекс после удаления или перестановки меняется и может привязать DOM-состояние не к той строке.

Операции с массивом полей имеют разную стоимость. `update(index, value)` перемонтирует соответствующую строку; для точечного изменения без перемонтирования используют `setValue` с путём нужного поля. Не стоит без необходимости последовательно вызывать несколько `append` и `remove` в одном обработчике. С `shouldUnregister` нужно быть осторожным: при перестановке строк временное размонтирование может удалить значение.

Дополнительно уменьшают частоту тяжёлой проверки схемы, отменяют устаревшие асинхронные проверки, не пересоздают большие списки вариантов без причины и виртуализируют действительно длинные списки. Виртуализация оставляет в DOM только видимую часть элементов. Оптимизацию применяют к измеренному узкому месту, а не оборачивают каждое поле в `memo` заранее.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем <code>watch</code> отличается от <code>useWatch</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`watch` вызывается из компонента-владельца `useForm`, поэтому изменение отслеживаемых значений рендерит его заново. `useWatch` создаёт подписку в том компоненте, где вызван, и локализует повторный рендер. Для наблюдения без обновления интерфейса используют `subscribe`, а не устаревший вариант `watch` с callback-функцией.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему в массиве полей нельзя использовать индекс как <code>key</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

При удалении или перестановке индекс меняется, и React может переиспользовать DOM и локальное состояние для другой строки. `useFieldArray` даёт стабильный `field.id`; его используют как `key`, а индекс оставляют только частью пути регистрации: `items.${index}.name`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как режим валидации влияет на производительность?</strong></summary>

<dl>
<dd>
<h2></h2>

`mode: 'onChange'` может запускать проверку схемы и обновлять ошибки на каждый символ. Для тяжёлой формы выбирают `onBlur` или `onSubmit`, повторно проверяют только нужные поля и выносят сетевую проверку из часто вызываемого общего resolver. Решение зависит от стоимости проверки и требуемой обратной связи.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему сложные UI-компоненты могут замедлить форму?</strong></summary>

<dl>
<dd>
<h2></h2>

`Select`, `DatePicker` или `Autocomplete` могут рендерить большое всплывающее окно, фильтровать список и получать управляемое значение при каждом изменении. Их изолируют через `Controller` или `useController`, не поднимают значение выше необходимого, не пересоздают дорогой список вариантов и при большом числе элементов используют виртуализацию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает <code>shouldUnregister</code> в динамической форме?</strong></summary>

<dl>
<dd>
<h2></h2>

По умолчанию RHF сохраняет значение размонтированного поля. При `shouldUnregister: true` поле после размонтирования удаляется из значений, и поведение становится ближе к нативной форме. Это важно для условных шагов многошаговой формы. Однако перестановка строк в `useFieldArray` может временно размонтировать поля, поэтому сохранение данных при такой настройке нужно проверить отдельно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>update</code> в <code>useFieldArray</code> может сбросить локальное состояние строки?</strong></summary>

<dl>
<dd>
<h2></h2>

`update(index, value)` размонтирует и заново монтирует обновлённую строку. Если нужно изменить одно поле и сохранить DOM и локальное состояние компонента, используют `setValue('items.0.name', value)`. Для замены всей строки перемонтирование может быть ожидаемым.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Проблема | Решение |
| --- | --- |
| Большая форма тормозит на вводе | Локализовать подписки, RHF, дробление компонентов |
| Зависимое поле | `useWatch` рядом с зависимой логикой |
| Динамический список полей | `useFieldArray` и `field.id` как `key` |
| Тяжёлая валидация | `onBlur`/`onSubmit`, точечная проверка, задержка сетевого запроса |
| Большой `Select` | Стабильный список вариантов, виртуализация при необходимости |
