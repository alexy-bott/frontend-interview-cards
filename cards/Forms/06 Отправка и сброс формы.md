## Вопрос

<br>

 💬 **Что происходит при отправке формы? Как обрабатывать серверные ошибки, `reset` и `defaultValues`?**

<h2></h2>

<br>
<dl>
<dd>

Отправка начинается нативным сценарием формы, а не только кликом по кнопке: пользователь может нажать Enter или использовать другой элемент отправки (`submitter`).

До события `submit` браузер выполняет constraint validation — встроенную проверку HTML-ограничений вроде `required` и `min`. Если форма не прошла проверку, событие `submit` не возникает, поэтому обработчик React Hook Form и `onInvalid` не вызываются.

Если приложение хочет полностью управлять проверкой через RHF, форме обычно задают `noValidate`.

`SubmitEvent.submitter` содержит элемент, который инициировал отправку. Если отправка не связана с конкретной кнопкой, значение может быть `null`.

В React Hook Form `handleSubmit` проверяет правила библиотеки и вызывает `onValid` либо `onInvalid`.

`onValid` запускает запрос и возвращает его `Promise`, чтобы `formState.isSubmitting` отражал весь период ожидания.

Во время отправки:

- блокируют повторный запуск обработчика;
- отключают кнопку отправки;
- показывают понятный статус;
- сохраняют введённые значения.

Необязательно делать `disabled` все поля. Отключённые таким способом значения не участвуют в нативной отправке и могут стать `undefined` в данных RHF. Если значение нужно сохранить, но запретить его изменение, можно использовать `readOnly` или другой подходящий интерфейс.

При использовании RTK Query trigger мутации по умолчанию возвращает результат вида `{ data }` или `{ error }`.

Чтобы получить успешные данные напрямую, а ошибку передать в `catch`, используют `.unwrap()`:

```ts
try {
  const updatedValues = await updateProfile(data).unwrap();

  reset(updatedValues);
} catch (error) {
  // Преобразовать ошибку API в ошибки формы.
}
```

После успешной операции приложение согласует форму с server state:

- использует подтверждённые данные из ответа mutation;
- инвалидирует теги RTK Query;
- при необходимости точечно обновляет существующую запись кэша;
- закрывает диалог, выполняет переход или вызывает `reset(updatedValues)`.

Автоматическая инвалидация тегов обычно проще и безопаснее ручного изменения нескольких записей кэша. `updateQueryData` используют, когда нужно осознанно изменить уже существующую запись.

`reset(updatedValues)` без сохраняющих параметров обновляет текущие значения и делает их новой базой для сравнения `dirty`. После сохранения форма больше не выглядит изменённой.

Ошибки разделяют по уровню:

- ошибку конкретного поля привязывают через `setError`;
- общую ошибку отправки задают в `root.serverError` или отдельном состоянии операции;
- сетевую или системную ошибку показывают как невозможность завершить запрос;
- неизвестное исключение регистрируют в monitoring и показывают безопасное общее сообщение.

Ошибка `root.serverError` относится к конкретной попытке отправки и не должна автоматически переноситься на следующую попытку.

`handleSubmit` не поглощает исключения из `onValid`.

`Error Boundary`, то есть граница ошибок React, также не перехватывает автоматически ошибку асинхронного обработчика события. Ожидаемые ошибки запроса обрабатывают внутри сценария отправки, а непредусмотренные при необходимости передают уровню приложения.

`defaultValues` кэшируются и задают исходную точку формы.

Если данные приходят позже, используют:

- асинхронные `defaultValues`;
- `reset(fetchedValues)`;
- реактивный prop `values`.

`values` применяет внешние значения при их изменении, поэтому может перезаписать текущий черновик пользователя. При повторной загрузке нельзя молча затирать уже изменённые поля.

В зависимости от сценария:

- сохраняют изменённые поля через `keepDirtyValues`;
- откладывают применение новых данных;
- показывают уведомление об обновлении;
- предлагают пользователю выбрать локальную или серверную версию.

Блокировка повторной отправки остаётся только защитой интерфейса.

Для заказа, платежа и другой критичной операции сервер использует `idempotency key` — уникальный ключ логической операции, по которому распознаётся повтор, — либо уникальное ограничение в базе данных.

Это необходимо, потому что запрос можно повторить из другой вкладки, после перезагрузки или напрямую через API.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем <code>reset(values)</code> отличается от ручной очистки полей?</strong></summary>

<dl>
<dd>
<h2></h2>

`reset` согласованно обновляет текущие значения и служебное состояние формы.

Без сохраняющих параметров он сбрасывает:

- ошибки;
- `dirty`;
- `touched`;
- счётчики и флаги отправки;
- текущие значения.

Если передать новые значения, они становятся новой базой для сравнения `dirty`, если не используется `keepDefaultValues`.

Например, форма редактирования профиля получила:

```text
name: "Ann"
```

Пользователь изменил значение на:

```text
name: "Anna"
```

Сервер сохранил и вернул `"Anna"`. После:

```ts
reset(updatedValues);
```

форма больше не считается изменённой, потому что `"Anna"` стала новой исходной точкой.

Ручная очистка через несколько вызовов `setValue` меняет отдельные значения, но не обязательно согласует `defaultValues`, ошибки, `dirty`, `touched` и остальные состояния.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Сервер вернул ошибку поля email. Что делать?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно преобразовать путь и код из ответа в имя и локализованное сообщение формы, затем вызвать:

```ts
setError("email", {
  type: "server",
  message,
});
```

Для перевода фокуса можно передать:

```ts
setError(
  "email",
  {
    type: "server",
    message,
  },
  {
    shouldFocus: true,
  },
);
```

Фокус сработает, если поле зарегистрировано, имеет доступный `ref` и не находится в состоянии `disabled`.

Общую ошибку не привязывают к случайному полю. Её помещают в:

```ts
setError("root.serverError", {
  type: "server",
  message,
});
```

либо в отдельное состояние операции.

Ошибка `root.serverError` относится к текущей попытке и не сохраняется автоматически между следующими отправками.

Сообщения связывают с контролами и объявляют доступным способом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему важно блокировать повторную отправку во время запроса?</strong></summary>

<dl>
<dd>
<h2></h2>

Чтобы пользователь не запустил один сценарий несколько раз и не получил конфликтующие ответы.

`onValid` должен вернуть `Promise` запроса или дождаться его через `await`, иначе `isSubmitting` сбросится слишком рано.

Проверять состояние полезно и внутри обработчика:

```ts
if (isSubmitting) {
  return;
}
```

Отключённая кнопка защищает только основной интерфейсный путь. Отправку могут инициировать Enter, другой submitter или внешний код.

Для критичных операций сервер всё равно обеспечивает идемпотентность, потому что клиентская блокировка не защищает от повторного запроса из другой вкладки или напрямую через API.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать с данными в RTK Query после успешной отправки?</strong></summary>

<dl>
<dd>
<h2></h2>

Mutation может инвалидировать связанные теги, чтобы активные запросы RTK Query получили актуальные данные повторно.

Другой вариант — точечно обновить существующий кэш через `updateQueryData`.

Автоматическая инвалидация обычно предпочтительнее, потому что сохраняет server state синхронизированным без ручного поиска всех зависимых записей.

`updateQueryData` подходит, когда:

- нужная запись уже существует в кэше;
- повторный запрос слишком дорог;
- изменение локально и предсказуемо;
- понятен источник подтверждённых данных.

Источником server state остаётся RTK Query, а форма хранит редактируемый черновик.

Оптимистическое обновление (`optimistic update`) оправдано, если операция обратима и понятен rollback.

Для формы с серверной нормализацией часто надёжнее получить подтверждённый результат:

```ts
const updatedValues = await updateProfile(data).unwrap();
```

затем обновить кэш или дождаться повторного запроса и вызвать:

```ts
reset(updatedValues);
```

Без `.unwrap()` RTK Query mutation trigger возвращает объект с `data` или `error`, поэтому API-ошибка не обязательно попадёт в обычный `catch`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать, если исходные данные пришли после первого рендера?</strong></summary>

<dl>
<dd>
<h2></h2>

Можно:

- использовать `defaultValues: async () => ...`;
- дождаться данных до монтирования формы;
- вызвать `reset(fetchedValues)`;
- передать реактивный prop `values`.

Обычные `defaultValues` кэшируются, поэтому новый объект на следующем render сам по себе не заменяет состояние формы.

Если серверные данные обновились во время редактирования, нельзя автоматически затирать пользовательский ввод.

Возможные стратегии:

- сохранить изменённые поля через `keepDirtyValues`;
- показать уведомление о новой версии;
- отложить обновление до завершения редактирования;
- предложить сравнить версии;
- перезаписать форму только после явного подтверждения.

Нужно определить один источник подтверждённых данных и не поддерживать независимо несколько несогласованных копий.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Для чего нужны <code>keepDirtyValues</code>, <code>keepErrors</code> и <code>keepDefaultValues</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Они позволяют сохранить выбранные части состояния при `reset`.

- `keepDirtyValues` сохраняет значения изменённых полей, а новыми данными обновляет только неизменённые поля. `dirtyFields` и `isDirty` также сохраняются.
- `keepErrors` временно оставляет текущие ошибки, но последующая проверка может их изменить.
- `keepDefaultValues` сохраняет прежние исходные значения и продолжает сравнивать форму именно с ними.

Например:

```ts
reset(fetchedValues, {
  keepDirtyValues: true,
});
```

обновит нетронутые поля свежими серверными данными, но оставит пользовательские изменения.

Случайный набор `keep*` может оставить текущие значения и служебное состояние несогласованными. Параметры выбирают исходя из того, что именно должно считаться новым источником истины.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что делать |
| --- | --- |
| Успешное сохранение | Получить подтверждённые данные, обновить кэш, вызвать `reset` или перейти дальше |
| Ошибка поля от сервера | `setError(fieldName, serverError)` |
| Общая ошибка | `root.serverError` или постоянное сообщение уровня формы |
| Повторная отправка | `isSubmitting`, защита обработчика, отключённая кнопка, идемпотентность сервера |
| Данные пришли позже | Асинхронные `defaultValues`, `values` или `reset(fetchedValues)` |
