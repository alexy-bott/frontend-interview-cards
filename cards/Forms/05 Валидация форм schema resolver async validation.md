## Вопрос

<br>

 💬 **Как организовать валидацию формы? Чем отличаются правила поля, schema resolver и асинхронная валидация?**

<h2></h2>

<br>
<dl>
<dd>

Проверка формы строится слоями.

- Нативные ограничения HTML (`required`, `min`, `pattern`, `type="email"`) позволяют браузеру выполнить базовую проверку.
- Правила поля (`field-level rules`) проверяют одно значение.
- Межполевая валидация (`cross-field validation`) проверяет связь нескольких значений, например совпадение паролей или порядок дат.
- Сервер окончательно проверяет права, уникальность, бизнес-правила, лимиты и актуальное состояние данных.

Серверная валидация обязательна, потому что клиентский код можно изменить или обойти прямым запросом к API.

Схемная валидация (`schema validation`) описывает данные формы целиком через Zod, Yup, Ajv или другую библиотеку.

`Resolver` — адаптер между схемой и React Hook Form. Он получает значения формы, `context` и сведения о проверяемых полях, запускает схему и возвращает:

- проверенные `values`;
- объект `errors` в формате RHF.

Многие готовые resolvers могут вывести TypeScript-типы из схемы.

Если схема преобразует значения, входной и выходной типы могут различаться. Например, пользователь вводит строку, а схема возвращает число.

В таком случае можно позволить resolver вывести типы автоматически либо указать их явно:

```ts
useForm<Input, Context, Output>({
  resolver,
});
```

`Input` описывает значения до преобразования, а `Output` — данные, которые получит успешный `handleSubmit`.

DTO, то есть транспортный объект запроса к API, при этом не обязан полностью совпадать с моделью формы. Преобразование модели формы в DTO можно выполнить отдельно перед отправкой.

Если RHF использует resolver, встроенные правила валидации `register`, такие как `required`, `min` или `validate`, с ним не комбинируют. Эти ограничения переносят в схему, чтобы сохранить один согласованный источник клиентских ошибок.

При этом преобразования значения в `register`, например `valueAsNumber`, `valueAsDate` или `setValueAs`, использовать можно: они подготавливают значение до запуска resolver.

Асинхронная валидация нужна, когда результат зависит от внешнего ресурса:

- занят ли email;
- существует ли приглашение;
- действует ли промокод;
- доступно ли выбранное имя.

Её можно реализовать через асинхронную функцию `validate` или внутри асинхронной схемы.

Удалённый запрос не следует отправлять на каждый символ без необходимости. Обычно выбирают проверку после потери фокуса (`blur`) либо ждут паузу во вводе с помощью `debounce`.

Если асинхронный запрос находится внутри resolver всей формы, он может выполняться при каждой повторной проверке схемы. Поэтому дорогую проверку одного поля иногда лучше изолировать и запускать только в подходящий момент.

Устаревший запрос отменяют через `AbortController` либо сверяют идентификатор запроса и проверенное значение с текущим значением поля.

`Debounce` уменьшает количество запросов, но сам по себе не защищает от неправильного порядка ответов.

Во время асинхронной проверки RHF может предоставлять:

- `formState.isValidating` — выполняется ли валидация;
- `formState.validatingFields` — какие поля сейчас проверяются асинхронно.

У поля можно показать отдельное состояние ожидания. Окончательная отправка всё равно повторяет проверку на сервере, потому что данные могли измениться после предварительного запроса.

Момент показа ошибок зависит от сценария.

- `mode: "onSubmit"` не показывает ошибки до первой отправки.
- `mode: "onBlur"` проверяет поле после потери фокуса.
- `mode: "onChange"` проверяет во время изменения значения, но может чаще запускать render и схему.
- `mode: "onTouched"` начинает проверку после первого blur, а затем проверяет при изменениях.
- `mode: "all"` использует и blur, и change.

После отправки `reValidateMode` определяет, когда повторно проверять поля, в которых уже были найдены ошибки. Часто используют первоначальную проверку через `onSubmit` или `onBlur`, а исправления проверяют через `reValidateMode: "onChange"`.

Если проверка одного поля зависит от другого, зависимое поле нужно повторно проверить после изменения исходного. В RHF это можно сделать через `trigger`.

Сервер возвращает стабильные коды ошибок и пути полей, а frontend сопоставляет их с именами формы и локализованным текстом.

Ошибку поля задают через:

```ts
setError("email", {
  type: "server",
  message,
});
```

Общую ошибку можно сохранить через:

```ts
setError("root.serverError", {
  type: "server",
  message,
});
```

либо в отдельном состоянии операции.

Ручная серверная ошибка зарегистрированного поля может быть удалена, когда поле успешно проходит следующую клиентскую проверку. Поэтому нужно заранее определить, когда серверная ошибка очищается: при изменении поля, при повторной отправке или после нового ответа backend.

Введённые значения при ошибке сохраняют, сообщение связывают с соответствующим полем и объявляют доступным способом.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что такое resolver в React Hook Form?</strong></summary>

<dl>
<dd>
<h2></h2>

Resolver — адаптер между RHF и библиотекой схемной валидации.

Он получает:

- значения формы;
- объект дополнительных данных `context`;
- сведения о проверяемых полях.

Затем resolver запускает схему и возвращает объект с `values` и `errors`.

Ошибки должны иметь вложенную структуру, совпадающую с путями полей. Например, ошибка для:

```text
participants.1.name
```

должна находиться в соответствующей вложенной части объекта, а не только под плоским строковым ключом.

Готовые resolvers для Zod, Yup и других библиотек выполняют это преобразование и часто выводят выходной TypeScript-тип из схемы.

При преобразованиях тип до проверки и тип после проверки могут различаться:

```ts
useForm<Input, Context, Output>({
  resolver,
});
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли одновременно использовать resolver и rules из <code>register</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

В React Hook Form resolver не комбинируется со встроенными правилами валидации `register`, например:

- `required`;
- `min`;
- `maxLength`;
- `pattern`;
- `validate`.

Если форма использует схему, эти правила описывают в ней, а `register` оставляют для подключения поля.

Преобразования значения использовать можно:

```tsx
<input
  type="number"
  {...register("age", {
    valueAsNumber: true,
  })}
/>
```

Так у формы остаётся один источник клиентских ошибок, а resolver получает значение нужного типа.

Нативные HTML-атрибуты могут сохраняться ради семантики и возможностей браузера, но если форма использует `noValidate`, встроенный интерфейс браузерной проверки не блокирует отправку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда использовать нативную валидацию, а когда <code>noValidate</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Нативные `required`, `type`, `min` и другие ограничения позволяют браузеру проверить форму без дополнительной библиотеки.

Если приложение хочет самостоятельно управлять моментом и видом сообщений через RHF и схему, форме задают `noValidate`:

```tsx
<form
  noValidate
  onSubmit={handleSubmit(onSubmit)}
>
```

Тогда браузер не остановит отправку собственным всплывающим сообщением до вызова обработчика RHF.

При этом сохраняют:

- семантически подходящие типы полей;
- `required` и другие полезные атрибуты, если они нужны;
- доступные подписи;
- связь поля с сообщением ошибки;
- серверную проверку данных.

Нужно выбрать один понятный пользовательский механизм сообщений, чтобы ошибка браузера и ошибка приложения не конкурировали друг с другом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где проверять, что пароль и его подтверждение совпадают?</strong></summary>

<dl>
<dd>
<h2></h2>

Это межполевое правило, потому что результат зависит от двух значений.

В схеме проверяют объект целиком и привязывают ошибку к `confirmPassword`.

Если использовать функцию `validate` без resolver, она может получить остальные значения формы:

```ts
validate: (confirmPassword, values) => {
  return confirmPassword === values.password
    || "Пароли не совпадают";
}
```

После изменения исходного `password` подтверждение нужно повторно проверить:

```ts
trigger("confirmPassword");
```

Иначе ошибка подтверждения может остаться рассчитанной по старому значению пароля.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое race condition при асинхронной валидации?</strong></summary>

<dl>
<dd>
<h2></h2>

Пользователь быстро меняет значение, и старый запрос может вернуться позже нового.

Если без проверки применить старый результат, форма покажет ошибку не для текущего значения.

Пример: пользователь ввёл `alex`, затем быстро заменил его на `alex2`. Ответ для `alex` может прийти последним и не должен установить ошибку текущему значению.

Для защиты используют:

- `AbortController`;
- последовательный идентификатор запроса;
- сравнение проверенного значения с актуальным;
- библиотеку запросов, которая умеет отменять или игнорировать устаревшие результаты.

`Debounce`, то есть ожидание паузы во вводе, уменьшает число запросов, но не гарантирует правильный порядок ответов.

При отмене запроса `AbortError` не следует показывать пользователю как ошибку значения поля.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Если есть клиентская валидация, зачем ещё серверная?</strong></summary>

<dl>
<dd>
<h2></h2>

Клиентская проверка быстрее подсказывает ошибку и не отправляет очевидно неверные данные.

Но код браузера находится под контролем пользователя и не является доверенной средой.

Сервер повторно проверяет:

- формат данных;
- права;
- бизнес-правила;
- уникальность;
- лимиты;
- актуальное состояние системы.

Например, email мог быть свободен во время предварительной проверки, но занят другим запросом к моменту отправки формы.

Поэтому асинхронная проверка доступности улучшает UX, но не резервирует значение и не заменяет проверку при сохранении.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как показать ошибку поля, которую вернул backend?</strong></summary>

<dl>
<dd>
<h2></h2>

Слой адаптации сопоставляет путь и код из ответа с именем и локализованным текстом формы, затем вызывает:

```ts
setError("email", {
  type: "server",
  message,
});
```

Для общей ошибки используют:

```ts
setError("root.serverError", {
  type: "server",
  message,
});
```

либо отдельное состояние запроса.

Сервер может вернуть:

```text
user.email
```

а форма ожидать:

```text
email
```

Если это сопоставление размазано по компонентам, изменение API станет дорогим, а ошибки будут отображаться непоследовательно.

Нужно также определить момент очистки серверной ошибки. Например, её можно очистить при изменении соответствующего поля или заменить результатом следующей отправки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выбрать <code>mode</code> в React Hook Form?</strong></summary>

<dl>
<dd>
<h2></h2>

`onSubmit` подходит, когда не нужно показывать ошибки до первой попытки отправки.

`onBlur` даёт обратную связь после завершения ввода в поле.

`onChange` нужен для требований, которые полезно проверять сразу, но увеличивает количество запусков проверки и обновлений интерфейса.

`onTouched` начинает проверять поле после первого blur и затем повторяет проверку при изменениях.

`all` запускает проверку и при blur, и при change.

Часто выбирают:

```ts
useForm({
  mode: "onSubmit",
  reValidateMode: "onChange",
});
```

В таком случае первая проверка происходит при отправке, а поля с найденными ошибками перепроверяются во время исправления.

Для дорогой асинхронной проверки режим выбирают отдельно и не полагаются только на общий `onChange` всей формы.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Проверка | Где делать |
| --- | --- |
| `required`/`minLength` | Нативные правила, RHF rules или схема |
| Подтверждение пароля | Межполевая проверка в схеме |
| Доступность имени пользователя | Асинхронная проверка с защитой от устаревших ответов |
| Бизнес-правило | Обязательная проверка на сервере и ранняя подсказка во frontend |
| Ошибки полей API | Адаптер путей и `setError` |
