## Вопрос

<br>

 💬 **Что важно учитывать для доступности форм?**

<h2></h2>

<br>
<dl>
<dd>

Доступность формы начинается с нативного HTML.

У каждого элемента управления должно быть доступное имя. Для полей ввода предпочтителен видимый `<label>`, связанный через `htmlFor`/`id` в React или вложение поля внутрь label.

`placeholder` остаётся подсказкой, а не заменой подписи: он исчезает при вводе и не даёт постоянного контекста.

Логически связанные переключатели (`radio`) и флажки (`checkbox`) группируют через `<fieldset>` и `<legend>`. Legend сообщает общее назначение группы, а у каждого варианта остаётся собственный label.

Правильные `type`, `name`, `autocomplete` и `inputMode` помогают браузеру, экранной клавиатуре и менеджеру паролей понять назначение поля.

Обязательность передают нативным `required`, а не только красной звёздочкой или цветом.

После обнаружения ошибки поле получает:

```html
aria-invalid="true"
```

Текст ошибки связывают с полем через `aria-describedby`.

Значение `aria-describedby` может содержать несколько `id`, разделённых пробелами, например идентификаторы постоянной подсказки и появившейся ошибки.

Сообщение должно объяснять, что именно нужно исправить, и оставаться видимым. Одной красной рамки недостаточно.

Общую серверную ошибку помещают в постоянную область формы. Если сообщение появляется динамически, его при необходимости объявляют через live region:

- `role="alert"` — для срочной ошибки;
- `role="status"` или `aria-live="polite"` — для менее срочного статуса.

Live region желательно создать в DOM заранее, а затем обновить её содержимое. Такое объявление не переводит фокус автоматически.

После неудачной отправки React Hook Form по умолчанию может сфокусировать первое зарегистрированное поле с ошибкой, если его `ref` достигает реального фокусируемого DOM-элемента.

Для длинной формы удобна сводка ошибок с `tabIndex="-1"` и ссылками на соответствующие поля.

Отрицательный `tabIndex` позволяет перевести фокус программно, но не добавляет элемент в обычный порядок обхода по Tab.

Выбор зависит от сценария:

- первое ошибочное поле быстро приводит к конкретной проблеме;
- сводка показывает все ошибки и особенно полезна в длинной форме.

Фокус меняют после попытки отправки, а не при каждом вводе или появлении новой ошибки.

`disabled` полностью исключает нативное поле из фокуса, проверки и отправки.

`readOnly` запрещает изменение, но сохраняет фокус и значение там, где этот атрибут поддерживается. Например, он применим к текстовым полям, но не заменяет `disabled` для `<select>` или checkbox.

`aria-disabled="true"` только объявляет состояние вспомогательным технологиям. Оно само не запрещает клик, ввод или отправку, поэтому поведение нужно блокировать в коде.

На время запроса обычно блокируют повторную отправку, показывают понятный текст состояния и оставляют введённые данные доступными для чтения.

React Hook Form хранит ошибки и управляет фокусом, но не создаёт доступную разметку автоматически.

Компонент поля обязан передать на правильные DOM-узлы:

- `id`;
- `name`;
- `aria-describedby`;
- `aria-invalid`;
- `ref`;
- видимый текст ошибки.

Для стабильных идентификаторов нескольких экземпляров компонента используют `useId()`. Он подходит для связи label, поля, подсказки и ошибки, но не используется как React `key` элементов списка.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему <code>placeholder</code> не заменяет <code>&lt;label&gt;</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`Placeholder` исчезает после ввода, может иметь низкий контраст и не является постоянной видимой подписью.

`<label>`:

- даёт полю доступное имя;
- остаётся на экране после ввода;
- увеличивает область нажатия;
- помогает понять назначение поля до и после заполнения.

В React используют `htmlFor`, который рендерится как HTML-атрибут `for`:

```tsx
<label htmlFor={emailId}>
  Email
</label>

<input
  id={emailId}
  name="email"
  type="email"
/>
```

Если видимая подпись действительно невозможна, контролу всё равно требуется доступное имя, например через `aria-label` или `aria-labelledby`. Но для обычной формы видимый label предпочтительнее.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем <code>aria-describedby</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`aria-describedby` связывает поле с дополнительным описанием:

- подсказкой;
- ограничением формата;
- сообщением об ошибке.

Доступное имя при этом по-прежнему приходит из `<label>`.

Значение может содержать несколько `id` через пробел:

```tsx
<input
  aria-describedby={`${hintId} ${errorId}`}
  aria-invalid={Boolean(error)}
/>
```

Если ошибки нет, её идентификатор не нужно добавлять в значение.

Подсказка и ошибка должны дополнять доступное имя, а не повторять его без необходимости.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>disabled</code> отличается от <code>readOnly</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`disabled`-поле:

- нельзя сфокусировать;
- нельзя изменить;
- оно не участвует во встроенной валидации;
- оно не отправляется с формой.

`readOnly` запрещает редактирование поддерживаемого поля, но сохраняет возможность фокуса и отправку значения.

`readOnly` применим не ко всем контролам. Например, он не делает нативный `<select>` или checkbox только для чтения.

Если значение только показывается и не является частью пользовательского ввода, иногда правильнее использовать обычный текст, а не визуально имитировать недоступное поле.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли фокусировать первое поле с ошибкой?</strong></summary>

<dl>
<dd>
<h2></h2>

После неудачной отправки — часто да: пользователь сразу попадает к конкретной проблеме.

В большой форме сводка ошибок может быть полезнее первого поля, потому что она показывает масштаб проблемы и содержит ссылки на все ошибочные контролы.

Выбор зависит от структуры формы:

- короткая форма — обычно первое поле;
- длинная или многошаговая форма — часто сводка;
- ошибка относится ко всей операции — общая область ошибки.

Во время обычного ввода фокус не перехватывают.

В RHF автоматический фокус работает только у поля с корректно переданным `ref`, который указывает на реальный фокусируемый элемент.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>required</code> отличается от <code>aria-required</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Нативный `required`:

- участвует во встроенной HTML constraint validation;
- сообщает браузеру, что поле обязательно;
- передаёт обязательность вспомогательным технологиям.

`aria-required="true"` только объявляет обязательность вспомогательным технологиям.

Он нужен пользовательскому виджету, где нативный атрибут неприменим, но сам по себе не остановит отправку и не проверит значение.

Для нативного поля используют `required`, а не заменяют его ARIA-атрибутом без причины.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как объявить серверную ошибку после отправки?</strong></summary>

<dl>
<dd>
<h2></h2>

Ошибку поля:

- показывают рядом с контролом;
- связывают через `aria-describedby`;
- отмечают через `aria-invalid="true"`;
- при необходимости переводят фокус к полю или сводке.

Общую ошибку помещают в постоянную область формы.

Для срочной ошибки можно использовать:

```html
<div role="alert">
  Не удалось сохранить данные.
</div>
```

Для менее срочного сообщения подходит:

```html
<div role="status">
  Данные проверяются.
</div>
```

`role="alert"` обычно объявляется более настойчиво, поэтому его не используют для каждого обычного обновления состояния.

Live region желательно добавить в DOM до выполнения запроса, а после ответа изменить её текст.

Нельзя показывать ошибку только во временном toast-уведомлении: оно может быстро исчезнуть и быть недоступно для повторного чтения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить доступность формы тестом?</strong></summary>

<dl>
<dd>
<h2></h2>

React Testing Library находит поле по доступному имени из `<label>`, а кнопку — по роли и имени.

`userEvent` имитирует ввод, переходы по Tab и отправку со стороны пользователя.

Проверяют:

- доступное имя поля;
- видимый текст ошибки;
- `aria-invalid`;
- связь через `aria-describedby`;
- состояние ожидания;
- блокировку повторной отправки;
- фокус после неудачной отправки.

Автоматические инструменты могут обнаружить отсутствие label, неверные ARIA-атрибуты и часть других проблем, но они не проверяют весь пользовательский сценарий.

Форму дополнительно проходят:

- только клавиатурой;
- с увеличением масштаба;
- при необходимости с экранным диктором.

Тестовая DOM-среда jsdom не воспроизводит всё поведение браузера и вспомогательных технологий.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Требование | Как реализовать |
| --- | --- |
| Название поля | Видимый `label` + связь `htmlFor`/`id` |
| Ошибка поля | Текст + `aria-describedby` + `aria-invalid` |
| Отправка с клавиатуры | Нативный `<form>` и `<button type="submit">` |
| Ожидание ответа | Блокировка повторной отправки + понятный статус |
| Большая форма | Сводка ошибок или фокус первого поля |
