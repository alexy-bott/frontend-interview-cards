## Вопрос

<br>

 💬 **Что такое web performance? Как понять, что именно в приложении работает медленно?**

<h2></h2>

<br>
<dl>
<dd>

Web performance, или производительность web-приложения, — измеримое качество пользовательского опыта.

Она показывает не просто, насколько быстро загрузился документ, а насколько быстро пользователь может:

```text
увидеть нужный контент
→ понять состояние интерфейса
→ выполнить действие
→ получить визуальный результат
```

Performance всегда относится к конкретному сценарию.

Например:

```text
открыть главную страницу

перейти в каталог

отфильтровать таблицу

добавить товар в корзину

открыть Dialog

отправить форму

работать в редакторе в течение часа
```

Один сценарий может работать быстро, а другой — медленно.

Поэтому фраза:

```text
Сайт загружается за две секунды.
```

неполна.

Нужно уточнить:

- какое событие считается завершением;
- какой маршрут измеряется;
- используется ли первое или повторное посещение;
- какое устройство используется;
- какая скорость и задержка сети;
- где находится пользователь относительно сервера;
- включён ли cache;
- авторизован ли пользователь;
- какая версия приложения проверяется;
- происходит ли полная загрузка или клиентский переход.

Например, сервер может вернуть HTML за 300 мс, но пользователь увидит основной контент только через четыре секунды:

```text
быстрый TTFB
→ поздно обнаружено LCP-изображение
→ большой файл
→ LCP остаётся плохим
```

Другой пример:

```text
страница визуально загрузилась быстро
→ пользователь нажал кнопку
→ main thread занят 600 мс
→ интерфейс долго не показывает результат
```

Здесь проблема относится не к загрузке, а к отзывчивости.

### Пользовательская модель performance

Упрощённый пользовательский сценарий можно представить так:

```text
пользователь начинает действие
→ браузер или приложение принимает его
→ выполняется сеть и вычисления
→ React и браузер обновляют интерфейс
→ новый кадр появляется на экране
```

Для первоначальной загрузки:

```text
navigation
→ DNS/TCP/TLS
→ HTTP request
→ server response
→ HTML parsing
→ critical resources
→ render
→ основной контент
→ hydration и interactivity
```

Для взаимодействия:

```text
input
→ ожидание свободного main thread
→ event handler
→ JavaScript и React update
→ style/layout/paint
→ следующий кадр
```

Для длительной сессии:

```text
повторные действия
→ новые данные и DOM
→ subscriptions и timers
→ использование памяти
→ возможное постепенное замедление
```

Web performance охватывает всю эту цепочку.

### Основные области измерений

| Область | Что показывает | Примеры |
|---|---|---|
| Сервер и сеть | Когда начинается и заканчивается доставка данных | DNS, TCP/TLS, TTFB, download time |
| Визуальная загрузка | Когда пользователь видит первый и основной контент | FCP, LCP |
| Отзывчивость | Как быстро взаимодействие приводит к следующему кадру | INP, input delay, long tasks |
| Визуальная стабильность | Насколько неожиданно перемещается контент | CLS |
| Rendering | Где браузер тратит процессорное время | style, layout, paint, composite |
| JavaScript | Сколько кода загружается, парсится и выполняется | bundle size, chunks, execution time |
| React | Где происходят дорогие render и commit | React Profiler, rerenders |
| Ресурсы | Сколько данных загружается и декодируется | изображения, шрифты, API, third-party scripts |
| Память | Растёт ли использование ресурсов во время сессии | heap, DOM nodes, listeners, detached nodes |

Эти области связаны.

Например:

```text
большой JavaScript bundle
→ долгая загрузка
→ parsing и compilation
→ long tasks
→ поздняя hydration
→ плохая отзывчивость
```

Но одна техника не исправляет любую проблему.

```text
сжатие изображения
→ может улучшить LCP

React.memo
→ не ускорит медленный backend

CDN
→ не исправит тяжёлый click handler

code splitting
→ не устранит layout shift
```

Сначала определяют ограничивающий участок.

### Метрика, симптом и причина

Нужно разделять три уровня.

**Симптом:**

```text
пользователь долго видит пустой экран
```

**Метрика:**

```text
LCP = 4,5 секунды
```

**Техническая причина:**

```text
LCP-ресурс обнаруживается только
после выполнения большого JavaScript chunk
```

Метрика подтверждает проблему и помогает сравнивать результаты, но обычно не объясняет причину сама по себе.

Другой пример:

```text
симптом
→ кнопка долго не реагирует

метрика
→ INP = 700 мс

причина
→ обработчик синхронно фильтрует
  100 000 элементов и запускает
  дорогой render
```

Нельзя переходить от плохой метрики сразу к случайной оптимизации.

Правильная последовательность:

```text
симптом
→ подходящая метрика
→ trace или attribution
→ bottleneck
→ гипотеза
→ изменение
→ повторное измерение
```

### Core Web Vitals

Текущие Core Web Vitals охватывают три важных аспекта пользовательского опыта:

| Метрика | Что измеряет | Хорошее значение |
|---|---|---|
| LCP | Загрузку основного видимого контента | не более 2,5 с |
| INP | Отзывчивость взаимодействий | не более 200 мс |
| CLS | Визуальную стабильность | не более 0,1 |

Для оценки сайта используют 75-й процентиль реальных посещений отдельно для мобильных и настольных устройств.

Упрощённо:

```text
p75 LCP = 2,4 с
```

означает, что:

```text
75% измеренных посещений
имели LCP не хуже 2,4 с
```

а оставшиеся 25% могли быть медленнее.

Core Web Vitals являются верхнеуровневыми пользовательскими сигналами, но не покрывают всю производительность.

Они не отвечают напрямую на вопросы:

- сколько JavaScript загружено;
- почему запрос начался поздно;
- какой React-компонент рендерится долго;
- растёт ли память;
- плавна ли конкретная анимация;
- сколько времени занимает бизнес-операция;
- сколько данных загружается после перехода;
- насколько быстро работает редкий сценарий.

Поэтому Core Web Vitals дополняют диагностическими и предметными метриками.

### Диагностические метрики

Примеры диагностических показателей:

```text
DNS lookup
connection time
TLS time
TTFB
resource download
FCP
TBT
long tasks
JavaScript execution
style recalculation
layout
paint
bundle size
request count
cache hit rate
DOM size
memory
```

Они помогают понять, почему пользовательская метрика получила конкретное значение.

Например, плохой LCP можно разложить на фазы:

```text
TTFB
→ задержка до получения HTML

resource load delay
→ когда браузер обнаружил LCP-ресурс

resource load duration
→ сколько загружался ресурс

element render delay
→ сколько прошло до отображения элемента
```

Два маршрута могут иметь одинаковый LCP, но разные bottleneck.

```text
страница A
→ медленный server response

страница B
→ быстрый server,
  но поздний image request
```

Для них нужны разные решения.

### Предметные метрики приложения

Не каждое важное событие описывается стандартной browser-метрикой.

Примеры:

```text
время от submit до подтверждения заказа

время открытия редактора

время применения фильтра

время до отображения результатов поиска

время импорта файла

время перехода между шагами checkout
```

Такие измерения называют custom или business-oriented performance metrics.

Они связывают техническое время с конкретным пользовательским действием.

Например:

```text
checkout-submit-to-result
```

полезнее абстрактной метки:

```text
operation-17
```

Имя должно объяснять сценарий.

### Лабораторные данные

Lab data, или synthetic data, получают в контролируемом тесте.

Примеры инструментов:

- Lighthouse;
- Chrome DevTools;
- WebPageTest;
- автоматизированный performance-тест в CI.

В тесте фиксируют:

- URL и сценарий;
- production build;
- устройство или его профиль;
- CPU throttling;
- network throttling;
- географию тестового агента;
- состояние cache;
- авторизацию;
- размер viewport;
- версию браузера;
- версию приложения.

Преимущества lab data:

- воспроизводимость;
- возможность проверять приложение до релиза;
- подробный trace;
- удобное сравнение до и после;
- возможность тестировать одну гипотезу;
- использование в CI.

Ограничения:

- один профиль устройства не представляет всю аудиторию;
- синтетический пользователь не повторяет реальное поведение;
- лаборатория может не открыть редкий сценарий;
- сервер и сеть могут отличаться от production;
- расширения и фоновые процессы создают шум;
- один запуск не является статистикой.

Lighthouse обычно измеряет загрузку страницы в заданных синтетических условиях.

Он может показать:

- LCP;
- CLS во время теста;
- TBT;
- Speed Index;
- потенциальные проблемы ресурсов и main thread.

Но обычный Lighthouse page-load test не знает, когда и с чем взаимодействуют реальные пользователи.

Поэтому он не измеряет реальный field INP.

TBT используется как лабораторный диагностический proxy:

```text
много blocking time
→ выше риск плохой responsiveness
```

Но:

```text
TBT
≠
INP
```

Для анализа конкретного взаимодействия нужно воспроизвести его в DevTools или записанном user flow.

### Полевые данные

Field data собираются во время реальных посещений.

Также используется название:

```text
RUM
→ Real User Monitoring
```

Field data учитывают реальные:

- устройства;
- CPU;
- сети;
- регионы;
- viewport;
- маршруты;
- состояния cache;
- пользовательские действия;
- длительные сессии;
- версии браузеров;
- сторонние расширения и приложения.

Они лучше отвечают на вопрос:

```text
Какой опыт на самом деле получает аудитория?
```

Но хуже изолируют одну техническую причину, потому что условия различаются.

Обычно используется цикл:

```text
field data
→ найти масштаб и сегмент проблемы

lab data
→ воспроизвести и диагностировать

field data после релиза
→ проверить реальное улучшение
```

### CrUX и собственный RUM

Полевые данные могут поступать из разных источников.

**Chrome User Experience Report, CrUX:**

- агрегированные данные реальных пользователей Chrome;
- применяются в PageSpeed Insights и других инструментах;
- показывают origin-level или доступные URL-level распределения;
- используют скользящее окно данных;
- не содержат внутренний контекст конкретного приложения.

**Собственный RUM:**

- отправляется из production-приложения;
- может содержать маршрут;
- версию релиза;
- тип навигации;
- категорию устройства;
- собственную attribution;
- feature flag;
- техническое имя сценария.

CrUX удобен как внешний общий сигнал.

Собственный RUM обычно полезнее для диагностики конкретного продукта.

Например, CrUX может показать плохой INP для origin, но не объяснить:

```text
какая кнопка
на каком маршруте
в какой версии релиза
создала задержку
```

Собственный RUM может добавить этот технический контекст без отправки пользовательского содержимого.

### Что сохранять в RUM

Вместе со значением метрики полезно сохранять безопасный технический контекст:

```text
metric name
metric value
metric rating
route
release
navigation type
device class
viewport category
connection category
country или крупный region
attribution
feature flag variant
```

Не следует отправлять:

- access token;
- cookies;
- email;
- содержимое формы;
- поисковую строку пользователя;
- текст сообщений;
- полный URL с чувствительными query params;
- DOM-текст страницы;
- персональные данные без законного основания.

Для уменьшения стоимости применяют:

- sampling;
- агрегацию;
- batching;
- `sendBeacon`;
- `fetch` с `keepalive`;
- лимиты частоты;
- фильтрацию ненужных событий.

Сама телеметрия не должна заметно ухудшать измеряемый интерфейс.

### Почему смотрят распределение

Производительность разных пользователей может сильно различаться.

Например:

```text
быстрый desktop + Wi-Fi
→ LCP 1,2 с

бюджетный smartphone + mobile network
→ LCP 5,5 с
```

Среднее может скрыть медленную группу.

Поэтому для Core Web Vitals используют p75.

Дополнительно могут анализироваться:

```text
p50
→ типичный центральный опыт

p75
→ основной пользовательский порог

p90 и p95
→ тяжёлый хвост
```

Высокий процентиль требует достаточного количества измерений.

Например:

```text
p99 по 20 посещениям
```

почти не даёт устойчивого статистического вывода.

Нужно учитывать:

- размер выборки;
- период сбора;
- сезонность;
- изменение аудитории;
- rollout релиза;
- различия маршрутов;
- отдельные mobile и desktop сегменты.

### Первый и повторный визит

Cold load — загрузка без подготовленного HTTP cache и ранее установленных соединений.

Она может включать:

```text
DNS
TCP или QUIC
TLS
HTML
CSS
JavaScript
fonts
images
data
```

Warm load может переиспользовать:

- HTTP cache;
- memory cache;
- service worker cache;
- открытое соединение;
- DNS;
- уже загруженные chunks;
- Router Cache.

Поэтому warm load обычно быстрее.

Оба сценария важны.

```text
cold load
→ опыт нового пользователя
  или посещения после очистки cache

warm load
→ опыт возвращающегося пользователя
```

Тест только тёплого сценария может скрыть слишком большой initial payload.

Тест только холодного сценария не покажет эффективность cache и повторной навигации.

### Клиентская навигация

В SPA и framework-приложениях отдельно измеряют client-side navigation.

```text
HTML уже загружен
→ пользователь нажимает ссылку
→ загружается route chunk
→ запрашиваются данные
→ React обновляет дерево
→ отображается новый экран
```

Здесь могут быть свои bottleneck:

- поздняя загрузка chunk;
- отсутствующий prefetch;
- медленный API;
- тяжёлый render;
- блокирующий state update;
- последовательная цепочка запросов;
- большой объём данных;
- дорогая hydration нового Client Component.

Cold document load и client navigation нельзя считать одним сценарием.

Для клиентского перехода можно измерять:

```text
route-navigation-start
→ route-content-visible
```

через framework-интеграцию или User Timing API.

Нужно заранее определить, что считается завершением:

```text
URL изменился

route component смонтировался

основной контент появился

данные полностью загрузились
```

Это разные события.

### Как выбрать измерение по жалобе

| Жалоба пользователя | Первые метрики и инструменты |
|---|---|
| Долго вижу пустую страницу | TTFB, FCP, Network waterfall |
| Основной блок появляется поздно | LCP и его фазы |
| Кнопка зависает | INP phases, Event Timing, Performance trace |
| Анимация дёргается | Frames, long animation frames, style/layout/paint |
| Контент прыгает | CLS entries и screenshots |
| Переход между маршрутами долгий | Chunk/data waterfall, custom navigation timing |
| После часа работы всё медленнее | Memory, DOM size, listeners, heap snapshots |
| Новый релиз стал тяжелее | Bundle size, requests, CI budget, RUM по release |
| Локально быстро, у пользователей медленно | Field data по устройствам, сети и регионам |

### Диагностика загрузки

Для загрузки сначала смотрят Network waterfall.

Он показывает:

- когда начался каждый запрос;
- что блокировало его начало;
- приоритет;
- connection setup;
- TTFB;
- download;
- cache;
- redirect;
- зависимость ресурсов друг от друга.

Вопросы:

```text
HTML пришёл поздно?

CSS блокирует render?

Главное изображение обнаружено поздно?

Есть redirect chain?

Запросы выполняются последовательно?

Слишком много origin?

Ресурс загружается повторно?

Используется cache?

Загружается ненужный JavaScript?
```

Critical request chain показывает последовательность ресурсов, без которых браузер не может быстро отобразить важный контент.

Например:

```text
HTML
→ CSS
→ background image из CSS
→ LCP
```

Если LCP-ресурс обнаруживается только после загрузки CSS, его запрос начинается позже, чем у обычного `<img>` в HTML.

### Диагностика LCP

Плохой LCP разбирают по этапам:

```text
TTFB

resource load delay

resource load duration

element render delay
```

Возможные причины:

**Большой TTFB:**

- медленный backend;
- cache miss;
- удалённый сервер;
- последовательные server requests;
- медленная база данных.

**Большой resource load delay:**

- изображение добавляется через JavaScript;
- lazy loading у LCP;
- ресурс находится в CSS;
- поздний preload;
- client-only render.

**Большой resource load duration:**

- слишком большой файл;
- неподходящий формат;
- медленный CDN;
- отсутствует responsive image;
- низкий сетевой приоритет.

**Большой element render delay:**

- main thread занят JavaScript;
- элемент скрыт до hydration;
- дорогой layout;
- animation задерживает отображение;
- stylesheet блокирует render.

Само уменьшение image size поможет только части этих причин.

### Диагностика взаимодействия

INP учитывает путь от взаимодействия до следующего отображённого кадра.

Упрощённо взаимодействие состоит из фаз:

```text
input delay
→ ожидание начала handlers

processing duration
→ выполнение handlers

presentation delay
→ React/browser rendering
  до следующего paint
```

**Большой input delay:**

```text
main thread уже занят
другой long task
third-party JavaScript
долгая hydration
```

**Большая processing duration:**

```text
дорогой event handler
синхронный цикл
JSON parsing
валидация большого объекта
несколько последовательных state updates
```

**Большая presentation delay:**

```text
дорогой React render
style recalculation
layout
paint
большое DOM-дерево
```

Оптимизация зависит от фазы.

Например:

```text
useMemo
```

не устранит input delay, вызванный сторонним long task до запуска React-handler.

### Long tasks

Задача main thread длительностью более 50 мс считается long task.

Например:

```text
JavaScript task = 180 мс
```

Её blocking portion:

```text
180 - 50
= 130 мс
```

Пока main thread занят, браузер не может своевременно:

- запустить другой handler;
- выполнить style и layout;
- нарисовать следующий кадр;
- обработать часть пользовательских действий.

Long task может возникнуть из-за:

- большого JavaScript chunk;
- тяжёлого вычисления;
- синхронного parsing;
- third-party script;
- длинного React render;
- обработки большого массива;
- повторяющегося layout.

Решения:

- удалить ненужную работу;
- разбить вычисление;
- перенести некритичную работу;
- уменьшить обрабатываемые данные;
- виртуализировать большой список;
- использовать Worker для подходящего CPU-вычисления;
- сократить third-party JavaScript.

Разбиение задачи улучшает возможность браузера обслуживать ввод и rendering, но не уменьшает общий объём работы автоматически.

### Long Animation Frames

Long task показывает отдельную задачу JavaScript.

Long Animation Frame позволяет анализировать целый медленный кадр, в который могут входить:

- несколько tasks;
- script;
- style;
- layout;
- rendering delay.

Это особенно полезно для диагностики плохого INP и дёргающихся интерфейсов.

Например:

```text
handler завершился сравнительно быстро
→ затем браузер выполнял дорогой layout
→ кадр всё равно появился поздно
```

Один анализ JavaScript handler не покажет полную причину.

### Rendering pipeline

После изменения DOM или CSS браузер может выполнять:

```text
style calculation
→ определить применяемые CSS-правила

layout
→ вычислить размеры и позиции

paint
→ нарисовать пиксели слоёв

composite
→ собрать слои на экране
```

Не каждое изменение проходит все этапы.

Например, transform и opacity часто позволяют обойти дорогой layout и paint, но это зависит от конкретной сцены и слоёв.

Проблемы:

- слишком большое DOM-дерево;
- сложные CSS-селекторы;
- частые чтения и записи layout;
- forced synchronous layout;
- большие области paint;
- слишком много слоёв;
- тяжёлые эффекты;
- анимация layout-свойств.

Forced synchronous layout возникает, когда код изменяет DOM, а затем сразу читает геометрию:

```ts
element.style.width =
  "200px";

const width =
  element.offsetWidth;
```

Браузер может быть вынужден немедленно пересчитать layout, чтобы вернуть актуальное значение.

Повторение такого шаблона в цикле создаёт layout thrashing.

### React performance

React Profiler показывает работу React:

- какие компоненты рендерились;
- сколько занял render;
- сколько занял commit;
- почему мог произойти render;
- какие обновления были дорогими.

Он полезен, если trace показывает, что задержка находится в React-работе.

Но React Profiler не заменяет browser Performance panel.

Например, React render может занять 20 мс, а затем браузер потратит:

```text
120 мс на layout и paint
```

React Profiler не объяснит всю задержку кадра.

Обычно инструменты применяют вместе:

```text
Chrome Performance
→ определить медленный участок общего кадра

React Profiler
→ детализировать React render/commit
```

Не каждый rerender является проблемой.

Оптимизировать нужно render, который:

- происходит часто;
- занимает заметное время;
- влияет на пользовательский сценарий;
- подтверждён профилированием.

### Память и деградация долгой сессии

Не все проблемы видны при коротком page-load test.

После длительной работы приложение может замедляться из-за:

- растущего DOM;
- забытых event listeners;
- незакрытых WebSocket subscriptions;
- timers;
- observer;
- cache без лимита;
- detached DOM nodes;
- замыканий, удерживающих большие объекты;
- сохранения старых состояний;
- повторного подключения после mount.

Симптомы:

```text
каждое действие становится медленнее

память постоянно растёт

обработчик вызывается несколько раз

после переходов остаются старые элементы

garbage collection становится частым
```

Инструменты:

- Memory panel;
- heap snapshot;
- allocation instrumentation;
- Performance Monitor;
- DOM node count;
- event listener inspection.

Нужно сравнивать одинаковые точки сценария:

```text
до 20 повторений действия
→ memory snapshot

после 20 повторений
→ GC
→ второй snapshot
```

Рост памяти не всегда является утечкой: cache может расти намеренно.

Нужно проверить, освобождаются ли объекты после завершения их lifecycle.

### `PerformanceObserver`

`PerformanceObserver` подписывается на записи Performance Timeline.

Пример:

```ts
const observer =
  new PerformanceObserver(
    (list) => {
      for (
        const entry
        of list.getEntries()
      ) {
        console.log(
          entry.entryType,
          entry.name,
          entry.startTime,
          entry.duration,
        );
      }
    },
  );

observer.observe({
  type: "longtask",
  buffered: true,
});
```

Возможные типы записей зависят от браузера.

Поддержку можно проверить:

```ts
const isSupported =
  PerformanceObserver
    .supportedEntryTypes
    .includes("longtask");
```

Разные API создают разные entries:

```text
navigation
resource
paint
largest-contentful-paint
layout-shift
event
longtask
long-animation-frame
mark
measure
```

Некоторые записи доступны только через `PerformanceObserver`, а не через:

```ts
performance.getEntries();
```

Option:

```text
buffered: true
```

позволяет получить поддерживаемые браузером записи, созданные до регистрации observer.

Но внутренние буферы не бесконечны.

Observer нужно подключать достаточно рано и отключать, когда он больше не нужен:

```ts
observer.disconnect();
```

Не следует подписываться на все возможные типы без необходимости: сбор и обработка большого числа записей сами создают нагрузку.

Для Core Web Vitals обычно используют библиотеку:

```text
web-vitals
```

потому что итоговый расчёт LCP, INP и CLS сложнее чтения одной browser entry.

### User Timing API

User Timing API измеряет предметные участки приложения.

```ts
performance.mark(
  "search-submit",
);

// Выполняется запрос,
// React update и отображение.

performance.mark(
  "search-results-visible",
);

performance.measure(
  "search-submit-to-results",
  "search-submit",
  "search-results-visible",
);
```

Получение результата:

```ts
const entries =
  performance.getEntriesByName(
    "search-submit-to-results",
    "measure",
  );

const duration =
  entries.at(-1)?.duration;
```

После отправки значения можно очистить записи:

```ts
performance.clearMarks(
  "search-submit",
);

performance.clearMarks(
  "search-results-visible",
);

performance.clearMeasures(
  "search-submit-to-results",
);
```

Метка должна соответствовать понятному событию.

Хорошие имена:

```text
editor-open-to-ready
checkout-submit-to-result
route-start-to-content
```

Плохие:

```text
start
end
test
operation
```

User Timing не определяет автоматически, какое событие важно пользователю.

Команда должна согласовать:

- начало сценария;
- конец сценария;
- обработку ошибок;
- отменённые действия;
- повторные операции;
- sampling.

| Lighthouse | Лабораторная проверка загрузки и общих рекомендаций |

Например:

```text
→ показывает высокий TBT

```

### Воспроизводимый lab-тест

Чтобы сравнение было полезным, фиксируют протокол.

Пример:

```text
Build:
production

Route:
/catalog

Scenario:
cold document load

Browser:
конкретная версия Chrome

Viewport:
390 × 844

CPU:
4× slowdown

Network:
заданный mobile profile

Cache:
disabled

Authentication:
anonymous

Runs:
5–10

Result:
median и разброс
```

Для runtime-сценария:

```text
1. Открыть каталог.
2. Дождаться стабилизации.
3. Начать запись Performance.
4. Ввести запрос.
5. Открыть первый результат.
6. Остановить запись.
```

До и после изменения сценарий должен оставаться одинаковым.

Полезно использовать:

- production build;
- Incognito;
- отключённые расширения;
- одинаковый сервер;
- одинаковый test data;
- несколько запусков;
- сохранённые traces.

CPU и network throttling моделируют условия, но не превращают desktop в настоящий слабый smartphone полностью.

Критичные сценарии полезно проверять и на реальном устройстве.

### Почему одного Lighthouse-запуска недостаточно

Результат может изменяться из-за:

- фоновой нагрузки CPU;
- температуры устройства;
- сети;
- работы сервера;
- cache;
- расширений;
- случайной очереди задач;
- third-party scripts;
- различий тестовых данных.

Например:

```text
LCP 2,4 с
→ первый запуск

LCP 2,7 с
→ второй запуск
```

не обязательно означает реальную регрессию.

Сначала оценивают естественный разброс baseline.

Для сравнения выполняют несколько запусков и смотрят:

- целевую метрику;
- медиану;
- диапазон;
- trace;
- устойчивость причины.

Общий Lighthouse score является агрегатом.

Его изменение не заменяет проверку конкретной метрики.

### Bottleneck

Bottleneck — участок, который в данный момент ограничивает пользовательский сценарий.

Например:

```text
симптом
→ LCP 5 секунд

возможный bottleneck
→ TTFB 3,5 секунды
```

После ускорения сервера:

```text
TTFB 600 мс
```

новым bottleneck может стать:

```text
LCP image загружается 2 секунды
```

Поэтому после каждой оптимизации измерение повторяют.

Нельзя предполагать, что один bottleneck остаётся главным навсегда.

### Рабочий цикл диагностики

```text
1. Описать пользовательский сценарий.
2. Зафиксировать конкретный симптом.
3. Выбрать пользовательскую метрику.
4. Зафиксировать условия теста.
5. Получить baseline.
6. Найти медленную фазу.
7. Найти технический bottleneck.
8. Сформулировать одну проверяемую гипотезу.
9. Внести минимальное изменение.
10. Повторить тот же тест.
11. Проверить соседние метрики.
12. После релиза проверить RUM.
```

Пример гипотезы:

```text
LCP начинается поздно,
потому что hero image появляется
только после client-side render.
```

Изменение:

```text
добавить изображение
в server-rendered HTML
```

Ожидаемый результат:

```text
resource load delay
уменьшится
```

После правки проверяют именно эту фазу, а не только общий Lighthouse score.

### Как доказать улучшение

До изменения фиксируют:

- сценарий;
- окружение;
- baseline;
- trace;
- предполагаемую причину;
- целевую метрику;
- соседние показатели.

После изменения проверяют:

```text
Исчезла ли предполагаемая причина?

Стала ли целевая фаза быстрее?

Устойчиво ли изменение в нескольких запусках?

Не ухудшились ли другие метрики?

Не выросли ли ошибки?

Подтвердил ли результат production RUM?
```

Например, улучшение нельзя считать полным, если:

```text
LCP стал быстрее
→ но вырос CLS

INP уменьшился
→ но действие теперь показывает
  устаревший результат

initial JS уменьшился
→ но каждый переход загружает
  слишком много мелких chunks
```

Performance является одним из требований продукта, а не заменой корректности.

### Performance budgets

Performance budget задаёт допустимый предел до появления регрессии.

Примеры:

```text
initial JavaScript
≤ 200 KB compressed

LCP lab median
≤ 2,5 с

route chunk
≤ 80 KB

third-party JavaScript
≤ заданного лимита

число requests
≤ заданного значения
```

Budgets применяют в:

- CI;
- bundle analysis;
- Lighthouse CI;
- release dashboards;
- RUM alerts.

Budget не объясняет причину проблемы.

Он сообщает:

```text
изменение вышло
за согласованный предел
```

После этого всё равно нужна диагностика.

Пределы выбирают по продукту, аудитории и текущему baseline, а не копируют без контекста из другого проекта.

### Локальная скорость не доказывает production performance

Локально разработчик часто использует:

- быстрый desktop;
- localhost;
- стабильный интернет;
- небольшие тестовые данные;
- прогретый cache;
- отключённые third-party integrations;
- один регион;
- короткую сессию.

Production-пользователь может иметь:

- слабый smartphone;
- высокую network latency;
- большой аккаунт;
- сотни строк;
- несколько открытых вкладок;
- cookie banner;
- analytics и chat scripts;
- длительную сессию.

Поэтому:

```text
локально быстро
```

не опровергает плохие field data.

И наоборот, плохой Lighthouse score одного искусственного теста не доказывает, что большинство реальных пользователей получают такой же опыт.

Нужны оба вида данных.

### Главный принцип

```text
Web performance
→ качество конкретного
  пользовательского сценария
```

Процесс оптимизации:

```text
не выбирать технику заранее

а:

симптом
→ измерение
→ bottleneck
→ гипотеза
→ изменение
→ повторное измерение
```

Оптимизация без baseline может улучшить не тот участок.

Уменьшение изображения не исправит задержку обработчика клика.

`React.memo` не ускорит медленный API.

Более быстрый backend не устранит дорогой layout.

Сначала находят ограничивающий участок и только затем выбирают подходящее решение.

```text
→ memory, DOM, listeners
```

Метрика задаёт направление, но не является готовым объяснением причины.

После неё используют Network, Performance, React Profiler или Memory tools.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое bottleneck и чем он отличается от симптома?</strong></summary>

<dl>
<dd>
<h2></h2>

Симптом — наблюдаемая проблема:

```text
LCP = 4,5 с
```

Bottleneck — участок, ограничивающий сценарий:

```text
TTFB = 3 с
```

или:

```text
LCP image обнаружено поздно
```

После устранения одного bottleneck ограничивающим может стать другой.

Поэтому измерение повторяют после каждой оптимизации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Для чего нужен <code>PerformanceObserver</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`PerformanceObserver` получает записи Performance Timeline по мере их появления.

Он позволяет наблюдать поддерживаемые browser entries:

```text
resource
navigation
paint
event
layout-shift
longtask
mark
measure
```

Option:

```text
buffered: true
```

может вернуть записи, созданные до регистрации observer.

Набор entry types отличается между браузерами, поэтому поддержку проверяют через:

```ts
PerformanceObserver
  .supportedEntryTypes;
```

Для Core Web Vitals обычно используют библиотеку `web-vitals`, которая реализует итоговую логику метрик и их lifecycle.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое User Timing API?</strong></summary>

<dl>
<dd>
<h2></h2>

User Timing измеряет предметные сценарии приложения.

```ts
performance.mark(
  "checkout-submit",
);

performance.mark(
  "checkout-result-visible",
);

performance.measure(
  "checkout-submit-to-result",
  "checkout-submit",
  "checkout-result-visible",
);
```

`performance.mark()` создаёт именованную точку.

`performance.measure()` вычисляет длительность между точками.

Метрика должна иметь понятные правила начала и завершения и не содержать чувствительные пользовательские данные в имени.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему один запуск Lighthouse не доказывает улучшение?</strong></summary>

<dl>
<dd>
<h2></h2>

Результат зависит от:

- фоновых процессов;
- загрузки CPU;
- температуры устройства;
- сети;
- cache;
- работы сервера;
- third-party scripts;
- тестовых данных.

Небольшая разница может быть обычным шумом.

Для сравнения:

```text
фиксируют условия
→ выполняют несколько запусков
→ смотрят медиану и разброс
→ сравнивают конкретную метрику
→ проверяют trace
```

Общий Lighthouse score не заменяет анализ целевого показателя.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как доказать, что оптимизация помогла?</strong></summary>

<dl>
<dd>
<h2></h2>

До изменения фиксируют:

- сценарий;
- условия;
- baseline;
- trace;
- гипотезу;
- целевую метрику.

После изменения повторяют тот же тест и проверяют:

```text
исчезла ли причина
стала ли быстрее нужная фаза
устойчив ли результат
не ухудшились ли соседние метрики
```

После релиза сравнивают RUM по версии приложения и нужному сегменту аудитории.

Улучшение lab data без изменения реального пользовательского опыта требует дополнительного анализа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Достаточно ли Core Web Vitals для оценки всей производительности?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

LCP, INP и CLS покрывают важные аспекты:

```text
loading
responsiveness
visual stability
```

Но они не показывают напрямую:

- размер JavaScript;
- memory leaks;
- плавность конкретной анимации;
- скорость редкого бизнес-сценария;
- загрузку route chunk;
- стоимость backend-операции;
- cache efficiency.

Core Web Vitals используют как верхнеуровневые пользовательские сигналы, а причины ищут через диагностические и предметные метрики.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем CrUX отличается от собственного RUM?</strong></summary>

<dl>
<dd>
<h2></h2>

CrUX содержит агрегированные данные реальных пользователей Chrome и удобен для общей оценки origin или доступных страниц.

Собственный RUM может добавить внутренний контекст:

- route;
- release;
- feature flag;
- navigation type;
- техническую attribution;
- предметный сценарий.

CrUX не знает архитектуру приложения.

Собственный RUM обычно лучше помогает связать регрессию с конкретным маршрутом и релизом, но требует собственной безопасной телеметрии.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как измерять client-side navigation в SPA?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала определяют начало и конец сценария.

Например:

```text
начало
→ пользователь активировал Link

конец
→ основной контент нового маршрута отображён
```

Затем используют:

- User Timing;
- API router или framework;
- RUM-интеграцию;
- Network и Performance trace.

Отдельно анализируют:

- route chunk;
- prefetch;
- запросы данных;
- React render;
- rendering browser.

Изменение URL само по себе не всегда означает, что пользователь уже видит готовый экран.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем long task отличается от Long Animation Frame?</strong></summary>

<dl>
<dd>
<h2></h2>

Long task — отдельная задача main thread длительностью более 50 мс.

Long Animation Frame описывает медленный кадр целиком и может включать:

- несколько tasks;
- обработчики;
- style;
- layout;
- rendering delay.

Long task помогает найти блокирующий JavaScript.

Long Animation Frame полезен, когда кадр задержался не только из-за одной JavaScript-задачи, но и из-за последующей работы rendering pipeline.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда использовать React Profiler?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда browser trace показывает, что заметная часть задержки связана с React render или commit.

Profiler помогает определить:

- какие components рендерились;
- какие commits были дорогими;
- какие обновления повторяются;
- где находится тяжёлая часть React-дерева.

Он не показывает полностью network, style, layout и paint.

Поэтому его используют вместе с Chrome Performance panel, а не вместо него.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как составить воспроизводимый performance-тест?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно зафиксировать:

- production build;
- URL;
- последовательность действий;
- browser version;
- viewport;
- CPU profile;
- network profile;
- cache state;
- authentication;
- test data;
- число запусков.

До и после изменения выполняют один сценарий.

Для runtime-проблем сохраняют trace, а для загрузки — также Network waterfall.

Один запуск используют для поиска причины, но не для статистического доказательства небольшой разницы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли сама performance-телеметрия замедлить приложение?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

Проблемы создают:

- подписка на слишком много entry types;
- отправка каждого события;
- тяжёлая обработка payload;
- частые network requests;
- сериализация большого DOM-контекста;
- синхронное логирование.

Используют:

- sampling;
- batching;
- минимальный payload;
- ограничение частоты;
- `sendBeacon`;
- отключение ненужных observers.

Нужно измерять стоимость самой RUM-интеграции и не отправлять чувствительные данные.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Симптом | Первые измерения |
|---|---|
| Основной контент появляется поздно | TTFB, фазы LCP, Network waterfall |
| После клика интерфейс долго не обновляется | Фазы INP, Event Timing, long tasks, React Profiler |
| Контент сдвигается при загрузке | CLS entries, screenshots, размеры ресурсов |
| Анимация или scroll дёргаются | Frames, Long Animation Frames, style/layout/paint |
| Клиентский переход долго ждёт | Route chunk, prefetch, data waterfall, User Timing |
| После долгой работы всё замедляется | Heap snapshots, DOM nodes, listeners, timers |
| Новый релиз увеличил загрузку | Initial JS, route chunks, requests, performance budget |
| Локально быстро, у пользователей медленно | RUM по устройству, маршруту, сети и release |
| Lighthouse нестабилен | Несколько запусков, фиксированные условия, сохранённый trace |
| Метрика ухудшилась без понятной причины | Attribution, Performance trace и сегментация RUM |
