## Вопрос

<br>

 💬 **Что измеряют Core Web Vitals: LCP, INP и CLS? Как интерпретировать эти метрики?**

<h2></h2>

<br>
<dl>
<dd>

Core Web Vitals — набор пользовательских метрик, которые оценивают три важных свойства web-интерфейса:

```text
LCP
→ насколько быстро появился основной контент

INP
→ насколько быстро интерфейс отвечает на действия

CLS
→ насколько стабильно расположены элементы
```

В актуальный набор входят:

- LCP, Largest Contentful Paint;
- INP, Interaction to Next Paint;
- CLS, Cumulative Layout Shift.

| Метрика | Что измеряет | Хорошо | Требует улучшения | Плохо |
|---|---|---:|---:|---:|
| LCP | Появление крупнейшего подходящего элемента в области просмотра | `<= 2,5 с` | `> 2,5 с` и `<= 4 с` | `> 4 с` |
| INP | Задержку взаимодействия до следующего отображённого кадра | `<= 200 мс` | `> 200 мс` и `<= 500 мс` | `> 500 мс` |
| CLS | Максимальную сумму неожиданных сдвигов в одном session window | `<= 0,1` | `> 0,1` и `<= 0,25` | `> 0,25` |

Официальную оценку страницы или origin строят по полевым данным реальных посещений.

Для каждой метрики берут p75:

```text
75% посещений
должны иметь значение
не хуже выбранной границы
```

Например:

```text
p75 LCP = 2,4 с
→ хорошая категория

p75 LCP = 3,2 с
→ требует улучшения

p75 LCP = 4,5 с
→ плохая категория
```

Мобильные и настольные устройства оценивают отдельно, потому что различаются:

- мощность CPU;
- размер viewport;
- скорость сети;
- latency;
- стоимость выполнения JavaScript.

Для общей успешной оценки Core Web Vitals все три метрики должны находиться в хорошей категории на p75.

При этом метрика является сигналом, а не готовым объяснением причины.

Например:

```text
LCP = 4,5 с
```

не сообщает автоматически, что виновато изображение.

Причиной может быть:

- медленный сервер;
- позднее обнаружение ресурса;
- длительная загрузка;
- занятый main thread;
- скрытие элемента до hydration.

Правильная модель:

```text
значение метрики
→ найти медленную фазу
→ определить техническую причину
→ внести изменение
→ измерить повторно
```

### LCP

LCP, Largest Contentful Paint, показывает, когда браузер отобразил крупнейший подходящий содержательный элемент в видимой области страницы.

Упрощённо:

```text
navigation start
→ основной видимый элемент появился
→ LCP
```

LCP оценивает воспринимаемую скорость загрузки.

Он отвечает на вопрос:

```text
Когда пользователь, вероятно,
увидел основной контент страницы?
```

LCP не определяет семантическую важность элемента.

Крупнейший элемент может оказаться:

- главным изображением;
- заголовком;
- текстовым блоком;
- рекламным блоком;
- poster видео.

При этом самый важный элемент продукта может быть меньше.

Поэтому LCP является универсальным приближением, а не полным пониманием интерфейса.

#### Какие элементы могут стать LCP

Кандидатами могут быть:

- `<img>`;
- `<image>` внутри `<svg>`;
- `<video>`;
- элемент с CSS `background-image: url(...)`;
- block-level элемент с текстом.

Для `<video>` учитывается:

```text
poster
или первый отображённый кадр
→ что появилось раньше
```

Сам `<svg>` целиком обычно не является LCP-кандидатом, хотя отдельный `<image>` внутри него может учитываться.

CSS gradient не считается LCP-изображением.

Браузер применяет эвристики и может исключать элементы, похожие не на содержательный контент, а на заглушки или фон:

- полностью прозрачный элемент;
- низкоинформативный placeholder;
- элемент, закрывающий весь viewport как фон.

Фактический LCP-элемент проверяют через DevTools, Lighthouse или RUM attribution, а не определяют только по имени `hero` в коде.

#### Как выбирается кандидат

Во время загрузки крупнейший элемент может меняться.

Например:

```text
1. Отобразился заголовок.
2. Заголовок временно стал LCP-кандидатом.
3. Загрузилось крупное hero-изображение.
4. Изображение стало новым кандидатом.
```

Браузер создаёт новые LCP entries, когда появляется более крупный подходящий элемент.

Итоговым значением обычно становится последний допустимый кандидат.

Браузер прекращает сообщать новые LCP-кандидаты после взаимодействия пользователя:

- tap;
- scroll;
- keypress.

Это нужно, потому что действие пользователя может само изменить видимую область и добавить новый контент, который уже не относится к первоначальной загрузке.

Если страница была открыта в фоновой вкладке, такое посещение нельзя интерпретировать как обычный пользовательский LCP: пользователь мог увидеть страницу значительно позже её фактической загрузки.

#### Как определяется размер

Для LCP учитывается видимая площадь элемента внутри viewport.

Если часть изображения:

- находится за пределами viewport;
- обрезана;
- скрыта через overflow,

эта часть не увеличивает размер кандидата.

Для изображения, растянутого больше его исходного размера, браузер не обязан считать всю искусственно увеличенную площадь.

У текста оценивается прямоугольник, содержащий текстовые узлы.

Margin, padding и border не включаются в размер содержимого LCP-кандидата.

#### Фазы LCP

Для ресурсного LCP-элемента, например изображения, значение удобно разделять на четыре части:

```text
LCP
=
TTFB
+
resource load delay
+
resource load duration
+
element render delay
```

**1. TTFB**

Время от начала навигации до получения первого байта HTML.

Причины большого TTFB:

- медленный backend;
- database query;
- cache miss;
- последовательные server requests;
- географически удалённый сервер;
- redirect;
- медленная CDN-граница.

**2. Resource load delay**

Время между TTFB и началом запроса LCP-ресурса.

Эта фаза растёт, если ресурс:

- появляется только после выполнения JavaScript;
- находится в поздно загруженном CSS;
- добавляется после client render;
- ошибочно использует lazy loading;
- зависит от другого запроса;
- отсутствует в первоначальном HTML.

Например:

```text
HTML
→ JavaScript bundle
→ client render
→ появился <img>
→ только теперь началась загрузка
```

**3. Resource load duration**

Время загрузки самого ресурса.

Причины:

- слишком большой файл;
- неподходящий формат;
- слишком широкое изображение;
- медленный origin;
- отсутствующий CDN;
- низкий приоритет;
- плохое соединение.

**4. Element render delay**

Время между завершением загрузки ресурса и его фактическим отображением.

Причины:

- main thread занят JavaScript;
- элемент скрыт до hydration;
- блокирующий CSS;
- декодирование большого изображения;
- дорогой layout;
- ожидание animation;
- элемент ещё не добавлен в DOM.

Для текстового LCP отдельная загрузка изображения отсутствует.

В таком случае основная задержка обычно находится в:

```text
TTFB
+
element render delay
```

Текст могут задерживать:

- render-blocking CSS;
- font block period;
- client-only render;
- большой JavaScript bundle;
- скрытие до hydration.

Фазы resource load delay и resource load duration особенно полезны для LCP, зависящего от отдельного сетевого ресурса.

#### Как интерпретировать LCP

Плохой LCP не означает автоматически:

```text
нужно уменьшить изображение
```

Сначала смотрят, какая фаза занимает больше времени.

| Крупная фаза | Основное направление |
|---|---|
| TTFB | Backend, cache, CDN, server waterfall |
| Resource load delay | Раннее обнаружение ресурса, HTML, preload, отказ от lazy loading |
| Resource load duration | Размер, формат, responsive image, CDN |
| Element render delay | JavaScript, CSS, hydration, layout и paint |

Например:

```text
изображение загружается за 300 мс,
но запрос начинается через 2 секунды
```

В этом случае дополнительное сжатие файла не устраняет главный bottleneck.

### INP

INP, Interaction to Next Paint, оценивает общую отзывчивость страницы на протяжении жизни пользовательского посещения.

Он учитывает взаимодействия:

- мышью;
- touch;
- указателем;
- физической или экранной клавиатурой.

Примеры:

```text
клик по кнопке

tap по карточке

выбор option

ввод символа

открытие Dialog

переключение вкладки
```

Обычные hover и scroll не являются самостоятельными INP-взаимодействиями.

Но тяжёлая работа во время hover или scroll способна занять main thread и задержать следующее учитываемое действие.

INP отвечает на вопрос:

```text
Насколько долго пользователь
ждал визуального результата действия?
```

#### Что считается взаимодействием

Одно логическое действие может состоять из нескольких browser events.

Например, tap способен вызвать:

```text
pointerdown
pointerup
click
```

Эти события группируются как одно interaction.

Длительность interaction определяется самым долгим связанным событием от начала пользовательского действия до момента, когда браузер смог показать следующий кадр.

Поэтому INP не является простой суммой длительностей всех событий одного жеста.

#### Фазы взаимодействия

Упрощённо задержка состоит из трёх частей:

```text
input delay
+
processing duration
+
presentation delay
```

**1. Input delay**

Пользователь уже совершил действие, но обработчик ещё не начал выполняться.

Main thread может быть занят:

- большим JavaScript task;
- hydration;
- third-party script;
- обработкой предыдущего события;
- parsing;
- garbage collection;
- React render.

Пример:

```text
пользователь нажал кнопку
→ main thread занят ещё 250 мс
→ только затем запустился onClick
```

**2. Processing duration**

Выполняются связанные event handlers.

Причины большой длительности:

- синхронный цикл;
- сортировка большого массива;
- сложная валидация;
- JSON parsing;
- дорогое обновление state;
- несколько последовательных вычислений;
- синхронная работа сторонней библиотеки.

**3. Presentation delay**

Handlers завершились, но новый кадр ещё не появился.

Браузер или React могут выполнять:

- render;
- commit;
- style recalculation;
- layout;
- paint;
- composite;
- callbacks перед следующим кадром.

Например:

```text
onClick занял 20 мс
→ React render и browser layout заняли 300 мс
→ пользователь всё равно увидел результат поздно
```

#### Как выбирается итоговый INP

INP наблюдает все подходящие взаимодействия за время посещения страницы.

Для большинства страниц итогом становится самое медленное взаимодействие.

Но на страницах с большим количеством действий случайный единичный скачок мог бы слишком сильно искажать результат.

Поэтому алгоритм исключает:

```text
одно худшее взаимодействие
на каждые 50 взаимодействий
```

Примеры:

```text
1–49 взаимодействий
→ обычно берётся худшее

50–99 взаимодействий
→ одно худшее исключается

100–149 взаимодействий
→ два худших исключаются
```

После этого среди посещений страницы для общей оценки используют p75.

Фраза:

```text
INP — средняя задержка кликов
```

неверна.

Один очень медленный сценарий может определить INP всего посещения.

Если пользователь не совершил ни одного подходящего взаимодействия, у посещения нет значения INP.

Это не означает, что страница быстрая или медленная: просто не было события, по которому можно измерить отзывчивость.

#### Как интерпретировать INP

Плохой INP нужно разложить по фазам.

| Крупная фаза | Возможная причина |
|---|---|
| Input delay | Main thread занят предыдущей работой |
| Processing duration | Тяжёлый handler или вычисление |
| Presentation delay | React render, style, layout или paint |

Пример:

```text
input delay = 350 мс
processing = 20 мс
presentation = 30 мс
```

Handler сам по себе быстрый.

Главная проблема возникла до его запуска.

Другой пример:

```text
input delay = 10 мс
processing = 400 мс
presentation = 40 мс
```

Нужно искать дорогую синхронную работу внутри действия.

Третий пример:

```text
input delay = 10 мс
processing = 25 мс
presentation = 350 мс
```

Вероятная проблема находится в обновлении интерфейса:

- большой React render;
- крупное DOM-дерево;
- дорогой layout;
- тяжёлый paint.

#### INP и визуальная обратная связь

INP заканчивается на следующем кадре, а не на полном завершении бизнес-операции.

Например:

```text
пользователь нажал «Сохранить»
→ кнопка сразу показала spinner
→ сервер ответил через 2 секунды
```

Первичная визуальная реакция может дать хороший INP, хотя вся операция длится дольше.

Для полного сценария дополнительно измеряют предметную метрику:

```text
submit-to-result
```

INP оценивает отзывчивость интерфейса, а не всю продолжительность сетевой операции.

### CLS

CLS, Cumulative Layout Shift, измеряет визуальную нестабильность — неожиданные перемещения видимого контента между отрисованными кадрами.

Пример:

```text
пользователь читает текст
→ сверху появляется баннер
→ текст сдвигается вниз
```

Такой сдвиг способен привести к:

- потере места чтения;
- ошибочному клику;
- неожиданному изменению интерфейса;
- ощущению незавершённой загрузки.

#### Оценка отдельного сдвига

Упрощённая формула:

```text
layout shift score
=
impact fraction
*
distance fraction
```

**Impact fraction** показывает, какая доля viewport была затронута нестабильными элементами до и после перемещения.

**Distance fraction** показывает максимальную дистанцию перемещения относительно размера viewport.

Например, заметную оценку может получить:

- большая область, сдвинувшаяся немного;
- небольшой элемент, переместившийся далеко.

Обычно формулу не вычисляют вручную.

Chrome DevTools показывает:

- конкретный Layout Shift;
- affected nodes;
- значение;
- визуальное воспроизведение сдвига.

#### Session windows

CLS не является бесконечной суммой всех сдвигов за всё время жизни страницы.

Сдвиги группируются в session windows.

Одно окно содержит последовательность сдвигов, если:

```text
между соседними сдвигами
меньше 1 секунды
```

и общая длительность окна не превышает:

```text
5 секунд
```

Итоговым CLS становится окно с максимальной суммой:

```text
CLS
=
самый плохой burst сдвигов
```

Пример:

```text
window A = 0,08
window B = 0,21
window C = 0,05

CLS = 0,21
```

Это делает метрику применимой к долгоживущим страницам и SPA, где отдельные изменения могут происходить значительно позже первоначальной загрузки.

#### Что считается сдвигом

Layout shift возникает, когда видимый элемент меняет начальную позицию между двумя кадрами.

Например:

```text
top: 200px
→ top: 320px
```

Если новый элемент добавился в DOM, но не сдвинул существующий видимый контент, он сам по себе не создаёт layout shift.

Изменение размера элемента учитывается через последствия:

```text
элемент стал выше
→ сдвинул соседний текст
→ появился layout shift
```

Если размер изменился, но другие видимые элементы не поменяли позицию, оценка может не увеличиться.

#### Ожидаемые сдвиги

Не каждый сдвиг считается неожиданным.

Layout Instability API использует свойство:

```text
hadRecentInput
```

Сдвиг может быть исключён из CLS, если произошёл примерно в течение `500 мс` после подходящего пользовательского действия.

Например:

```text
клик по Accordion
→ Content сразу раскрылся
```

Такое движение ожидаемо.

Но если:

```text
клик
→ долгий запрос
→ через 2 секунды
  контент вставился над текстом
```

сдвиг уже может считаться неожиданным.

Прокрутка не предоставляет такого исключения автоматически.

Даже ожидаемый сдвиг не должен мешать пользователю.

Метрика может не наказать интерфейс, но движение всё равно способно быть слишком резким или неудобным.

#### Частые причины CLS

- `<img>` без зарезервированных размеров;
- iframe без стабильного контейнера;
- реклама, появляющаяся над контентом;
- cookie banner, встроенный в layout;
- skeleton другого размера;
- поздно появившаяся ошибка формы;
- подмена текста после загрузки;
- web-шрифт с другими метриками;
- динамически добавленный header;
- animation свойств, влияющих на layout.

Способы предотвращения:

```text
width и height
aspect-ratio
стабильный min-height
одинаковая геометрия skeleton
резервирование рекламного slot
overlay вместо вставки над контентом
font metrics adjustment
```

Анимации через:

```text
transform
opacity
```

обычно не меняют layout и не увеличивают CLS.

Но это не означает, что любая transform-анимация автоматически удобна или производительна.

CLS измеряет перемещение layout, а не все возможные визуальные проблемы.

### Field и lab data

Core Web Vitals предназначены для оценки реального пользовательского опыта, поэтому итоговый статус строится по field data.

Источники:

- Chrome User Experience Report;
- PageSpeed Insights;
- Search Console;
- собственный RUM;
- библиотека `web-vitals`.

Lab tools помогают воспроизвести и диагностировать причину:

- Lighthouse;
- Chrome Performance panel;
- Performance Insights;
- WebPageTest;
- React Profiler.

Field и lab значения могут отличаться из-за:

- устройств;
- сети;
- географии;
- cache;
- пользовательского поведения;
- продолжительности сессии;
- тестовых данных;
- third-party content;
- версии приложения.

Например, стандартный Lighthouse page-load test способен измерить лабораторные LCP и CLS.

Но он обычно не воспроизводит набор реальных действий пользователя, поэтому не показывает полноценный field INP.

Вместо этого Lighthouse использует TBT как диагностический сигнал блокировки main thread.

```text
TBT
≠
INP
```

INP можно анализировать в лаборатории, если вручную или автоматически воспроизвести нужное взаимодействие и записать Performance trace.

### Диагностика Core Web Vitals

Для каждой метрики используется свой основной путь.

**LCP:**

```text
найти LCP-element
→ разложить LCP по фазам
→ открыть Network waterfall
→ проверить main thread и render
```

**INP:**

```text
найти медленное interaction
→ разделить input, processing, presentation
→ воспроизвести действие
→ изучить call stack, React и rendering
```

**CLS:**

```text
найти худшее session window
→ открыть Layout Shift entries
→ определить affected nodes
→ найти источник изменения геометрии
```

Полезно сохранять в RUM attribution:

- route;
- release;
- LCP-element;
- URL LCP-ресурса;
- interaction target;
- event type;
- фазы INP;
- layout shift sources;
- navigation type;
- device class.

Нельзя без необходимости отправлять:

- содержимое полей;
- текст пользователя;
- token;
- персональные URL parameters;
- секреты.

### Как интерпретировать результат

Core Web Vitals отвечают на разные вопросы:

```text
LCP
→ насколько быстро пользователь увидел
  главный крупный контент

INP
→ насколько быстро интерфейс
  визуально ответил на действие

CLS
→ насколько предсказуемо
  оставался на месте контент
```

Они не являются взаимозаменяемыми.

Например:

```text
хороший LCP
+
плохой INP
→ страница быстро появилась,
  но плохо реагирует

хорошие LCP и INP
+
плохой CLS
→ интерфейс быстрый,
  но элементы неожиданно прыгают
```

Улучшение одной метрики не должно ухудшать другую.

Например:

```text
убрать зарезервированное место
→ изображение может появиться раньше
→ но CLS станет хуже
```

или:

```text
загрузить весь JavaScript заранее
→ client navigation ускорится
→ initial loading и INP могут ухудшиться
```

### Главный принцип

```text
LCP
→ loading

INP
→ responsiveness

CLS
→ visual stability
```

Метрика показывает, какой аспект пользовательского опыта требует внимания.

Она не заменяет поиск причины.

Правильный процесс:

```text
field metric
→ attribution
→ lab reproduction
→ bottleneck
→ минимальное изменение
→ повторное измерение
→ проверка field data после релиза
```

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Какие элементы могут стать LCP-элементом?</strong></summary>

<dl>
<dd>
<h2></h2>

Кандидатами могут быть:

- `<img>`;
- `<image>` внутри `<svg>`;
- `<video>`;
- CSS background image через `url()`;
- block-level элемент с текстом.

Для `<video>` используется poster или первый отображённый кадр — что появилось раньше.

CSS gradient не считается изображением-кандидатом.

Браузер может исключить полностью прозрачный элемент, низкоинформативный placeholder или изображение, похожее на фон всего viewport.

LCP определяется фактическим отображением, а не именем компонента в коде.

На разных viewport крупнейшими могут стать разные элементы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему LCP-ресурс может начать загружаться поздно?</strong></summary>

<dl>
<dd>
<h2></h2>

Браузер быстрее обнаруживает ресурс, который присутствует в первоначальном HTML:

```html
<img src="...">
```

Запрос начинается позже, если URL появляется:

- после выполнения JavaScript;
- после client render;
- в поздно загруженном CSS;
- после запроса данных;
- через custom lazy loading;
- внутри условно отображаемого компонента.

Исправление зависит от причины:

- сделать ресурс обнаружимым в HTML;
- убрать lazy loading у LCP;
- использовать responsive `srcset`;
- применить обоснованный `fetchpriority="high"`;
- добавить preload только при действительно позднем обнаружении.

Preload всех изображений создаёт конкуренцию и может ухудшить загрузку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли плохой LCP означает медленную сеть?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

LCP состоит из нескольких возможных задержек:

```text
TTFB
resource load delay
resource load duration
element render delay
```

Например, файл может загрузиться быстро, но его запрос начался поздно.

Другой вариант:

```text
ресурс уже загружен
→ main thread занят
→ элемент долго не отображается
```

В Network сравнивают начало и конец запроса, а в Performance trace — работу JavaScript, style, layout и paint.

Оптимизируют самую крупную фазу, а не случайно выбранный ресурс.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие действия входят в INP?</strong></summary>

<dl>
<dd>
<h2></h2>

INP учитывает:

- click;
- tap;
- действия указателем;
- ввод с физической или экранной клавиатуры.

Один жест может объединять несколько событий:

```text
pointerdown
pointerup
click
```

Hover и обычная прокрутка не являются самостоятельными INP-взаимодействиями.

Но их тяжёлые handlers могут занять main thread и увеличить input delay следующего клика или нажатия клавиши.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как понять, какая часть INP плохая?</strong></summary>

<dl>
<dd>
<h2></h2>

Interaction разделяют на три фазы:

```text
input delay
processing duration
presentation delay
```

Большой input delay:

```text
main thread был занят
до запуска handler
```

Большой processing duration:

```text
тяжёлый handler
или синхронное вычисление
```

Большой presentation delay:

```text
дорогой React render,
style, layout или paint
```

Attribution из `web-vitals`, Event Timing и Long Animation Frames помогает определить целевой элемент и фазы.

Затем действие воспроизводят в Performance panel и изучают конкретный call stack.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем INP отличается от FID?</strong></summary>

<dl>
<dd>
<h2></h2>

FID измерял только input delay первого взаимодействия:

```text
действие
→ начало handler
```

Он не учитывал:

- выполнение handler;
- следующий paint;
- последующие взаимодействия.

INP наблюдает взаимодействия на протяжении жизни страницы и включает:

```text
input delay
+
processing
+
presentation
```

С марта 2024 года INP заменил FID в наборе Core Web Vitals.

FID может встречаться в старых отчётах, но не является текущей основной метрикой отзывчивости.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем INP отличается от TBT?</strong></summary>

<dl>
<dd>
<h2></h2>

INP измеряет реальные пользовательские взаимодействия.

TBT — лабораторная page-load метрика, которая суммирует blocking portions long tasks после FCP в заданном окне.

Для task длительностью `180 мс` blocking portion составляет:

```text
180 - 50
= 130 мс
```

TBT полезен как сигнал загруженности main thread во время загрузки.

Но:

```text
TBT
≠
INP
```

Страница может иметь хороший TBT при открытии, но плохой INP при позднем запуске тяжёлого фильтра или редактора.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как рассчитывается оценка отдельного сдвига layout?</strong></summary>

<dl>
<dd>
<h2></h2>

Упрощённо:

```text
layout shift score
=
impact fraction
*
distance fraction
```

Impact fraction показывает долю viewport, затронутую нестабильными элементами.

Distance fraction показывает максимальную дистанцию их перемещения относительно viewport.

Небольшой элемент, переместившийся далеко, и большая область, сдвинувшаяся немного, могут дать заметную оценку.

DevTools показывает конкретные affected nodes, поэтому формулу обычно не считают вручную.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему CLS не является суммой всех сдвигов за бесконечную сессию?</strong></summary>

<dl>
<dd>
<h2></h2>

Сдвиги группируются в session windows.

Они входят в одно окно, если между соседними сдвигами проходит меньше одной секунды.

Максимальная продолжительность окна:

```text
5 секунд
```

Итоговым CLS становится окно с самой большой суммой.

Это не позволяет показателю бесконечно расти только из-за продолжительности работы SPA, но поздние сдвиги всё равно могут образовать новое худшее окно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие сдвиги чаще всего ухудшают CLS?</strong></summary>

<dl>
<dd>
<h2></h2>

Частые причины:

- изображения без `width`, `height` или `aspect-ratio`;
- реклама без зарезервированного slot;
- iframe без стабильного контейнера;
- skeleton другого размера;
- поздний banner над контентом;
- появление ошибки формы над полями;
- шрифт с сильно отличающимися метриками;
- вставка нового header;
- изменение размеров загруженного компонента.

Решения:

- резервировать место;
- сохранять одинаковую геометрию placeholder;
- добавлять новый контент ниже существующего;
- использовать Overlay;
- подбирать fallback font;
- анимировать через `transform`, когда это соответствует дизайну.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему сдвиг после клика иногда не входит в CLS?</strong></summary>

<dl>
<dd>
<h2></h2>

Layout Shift entry получает:

```text
hadRecentInput = true
```

если сдвиг произошёл примерно в течение `500 мс` после подходящего пользовательского действия.

Например:

```text
клик по Accordion
→ Content сразу раскрылся
```

Такой сдвиг считается ожидаемым.

Если результат появился значительно позже, например после долгого запроса, исключение уже может не действовать.

Прокрутка сама по себе не создаёт такое исключение.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где брать полевые значения Core Web Vitals?</strong></summary>

<dl>
<dd>
<h2></h2>

Основные источники:

- CrUX;
- PageSpeed Insights;
- Search Console;
- собственный RUM;
- библиотека `web-vitals`.

CrUX показывает агрегированные данные подходящих Chrome-посещений.

Собственный RUM может добавить:

- route;
- release;
- device class;
- navigation type;
- LCP-element;
- interaction target;
- CLS sources.

Значения разных источников могут отличаться из-за аудитории, периода, покрытия браузеров и правил агрегации.

Нельзя напрямую сравнивать одно число CrUX с единичным запуском Lighthouse.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как рассчитывается общая оценка Core Web Vitals?</strong></summary>

<dl>
<dd>
<h2></h2>

Для LCP, INP и CLS отдельно вычисляют p75 полевых посещений.

Страница или origin успешно проходит Core Web Vitals, когда все три значения находятся в хорошей категории:

```text
LCP <= 2,5 с

INP <= 200 мс

CLS <= 0,1
```

Хорошее среднее значение не гарантирует прохождение p75.

Также mobile и desktop аудиторию анализируют отдельно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит с INP, если пользователь не взаимодействовал со страницей?</strong></summary>

<dl>
<dd>
<h2></h2>

Если не произошло ни одного подходящего click, tap или keyboard interaction, посещение не получает значение INP.

Нельзя записывать вместо него:

```text
0 мс
```

Ноль искусственно улучшил бы распределение, хотя отзывчивость фактически не проверялась.

Для стабильной оценки INP нужен достаточный объём посещений с реальными взаимодействиями.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему Lighthouse обычно не показывает реальный INP?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычный Lighthouse page-load test загружает страницу, но не воспроизводит полноценный набор пользовательских действий на протяжении сессии.

Поэтому он использует TBT как лабораторный диагностический сигнал.

Реальный INP получают:

- из field data;
- через собственный RUM;
- в лаборатории при воспроизведении конкретного interaction;
- через Performance trace и Event Timing.

Хороший TBT снижает риск проблем, но не гарантирует хороший INP поздних сценариев.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли LCP-элемент является самым важным контентом страницы?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

LCP выбирает крупнейший подходящий элемент в viewport по правилам браузера.

Самым важным для продукта может быть:

- меньший заголовок;
- цена;
- кнопка;
- результат поиска;
- статус операции.

Для важного элемента можно дополнительно использовать собственные метрики или Element Timing API.

LCP остаётся универсальным сигналом perceived loading, но не заменяет предметное понимание страницы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Покрывают ли Core Web Vitals все проблемы интерфейса?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Они не измеряют напрямую:

- полный срок бизнес-операции;
- утечки памяти;
- плавность каждой animation;
- размер JavaScript;
- скорость редкого маршрута;
- доступность;
- корректность интерфейса;
- все визуальные движения.

Например, transform-анимация обычно не увеличивает CLS, но может оставаться раздражающей.

Core Web Vitals используют как верхнеуровневые сигналы вместе с предметными метриками, DevTools и пользовательскими исследованиями.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Симптом | Возможная причина |
|---|---|
| LCP-изображение загружается после основного JS | Ресурс поздно обнаружен или ошибочно использует lazy loading |
| Изображение загружено, но LCP наступает поздно | Main thread, hydration или rendering задерживают отображение |
| Клик быстрый локально, но медленный на слабых устройствах | Input delay, тяжёлый handler или дорогой render |
| Форма задерживается только на одном действии | Худшее взаимодействие определяет INP посещения |
| Lighthouse показывает хороший TBT, а RUM — плохой INP | Медленный сценарий происходит после первоначальной загрузки |
| Карточки прыгают при появлении изображений | Размеры или `aspect-ratio` не зарезервированы |
| После загрузки шрифта меняется перенос строк | Метрики fallback и web-шрифта различаются |
| Accordion двигает контент после клика | Ожидаемый сдвиг может не войти в CLS |
| Баннер появляется после запроса и сдвигает страницу | Поздний сдвиг может увеличить CLS |
| Все средние значения хорошие, но CWV не пройдены | p75 одной или нескольких метрик находится вне хорошей категории |
