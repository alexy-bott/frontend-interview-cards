## Вопрос

Как сеть, HTTP cache, CDN и сжатие влияют на производительность frontend-приложения?

<details>
<summary><strong>Показать ответ</strong></summary>

Скорость загрузки зависит не только от размера файлов. Для нового соединения браузеру могут потребоваться DNS-разрешение домена, установка транспортного соединения и TLS, ожидание ответа сервера и передача тела ответа. **Latency**, или задержка, особенно заметна при большом числе последовательных запросов. **Bandwidth**, или пропускная способность, сильнее влияет на загрузку крупных ресурсов.

В DevTools различают **transfer size** и **resource size**. Resource size - размер содержимого после распаковки, с которым затем работает браузер. Transfer size - объем, переданный по сети с учетом сжатия и служебных данных. Сжатие уменьшает передачу, но не отменяет стоимость разбора и выполнения большого JavaScript.

**HTTP cache**, или HTTP-кеш, хранит ответы и повторно использует их по правилам заголовков. Типичная стратегия зависит от ресурса:

| Ресурс | Частая стратегия | Причина |
| --- | --- | --- |
| JS, CSS и изображения с content hash в имени | `Cache-Control: public, max-age=31536000, immutable` | Изменение содержимого создает новый URL |
| HTML приложения | `Cache-Control: no-cache` или небольшой `max-age` | Документ должен быстро получить ссылки на актуальные файлы сборки |
| Персональный ответ API | `private` либо `no-store`, если хранить ответ нельзя | Общий кеш не должен смешать данные пользователей |
| Публичный редко меняющийся API | Явный `max-age`, при необходимости `s-maxage` и валидатор | Браузер и CDN могут уменьшить число обращений к origin-серверу |

`no-cache` не запрещает хранение: кеш может сохранить ответ, но перед повторным использованием должен проверить его актуальность. Для проверки применяются `ETag` с `If-None-Match` или `Last-Modified` с `If-Modified-Since`. Ответ `304 Not Modified` не передает тело заново, однако сетевой запрос и ожидание сервера остаются. `no-store` означает, что кешу не следует сохранять ответ.

**CDN**, или сеть доставки контента, располагает пограничные серверы ближе к пользователям. При cache hit нужный ответ уже есть на узле CDN; при cache miss CDN запрашивает его у исходного origin-сервера, может сохранить и затем отдать пользователю. Результат зависит от cache key - набора данных, по которому различаются варианты ответа. Обычно туда входят URL и выбранные заголовки из `Vary`; лишние cookies или уникальные query-параметры могут резко снизить долю cache hit.

Для текстовых ресурсов сервер выбирает Brotli или gzip по `Accept-Encoding` и указывает фактический алгоритм в `Content-Encoding`. Brotli часто уменьшает JS, CSS, HTML и JSON сильнее gzip. JPEG, WebP, AVIF, видео и другие уже сжатые форматы повторно сжимать обычно бесполезно. Для них важнее формат, размеры и качество исходного файла.

HTTP/2 и HTTP/3 позволяют нескольким запросам использовать одно соединение, но не устраняют последовательные зависимости. Если CSS поздно обнаруживает шрифт или JavaScript только после выполнения запрашивает следующий chunk, возникает request chain - цепочка, в которой каждый следующий ресурс ждет предыдущий. Поэтому важны не только кеш и сжатие, но и раннее обнаружение критических ресурсов, корректный приоритет и отсутствие лишних перенаправлений.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Из каких этапов складывается время сетевого запроса?</summary>

Возможны постановка запроса в очередь, DNS, установка TCP или QUIC-соединения, TLS, отправка запроса, ожидание первого байта и загрузка тела ответа. При повторном запросе часть этапов может исчезнуть благодаря уже открытому соединению или кешу. В Network panel точный набор фаз виден в разделе Timing конкретного запроса.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем задержка сети (latency) отличается от пропускной способности (bandwidth)?</summary>

Latency - задержка до начала получения результата, а bandwidth - объем данных, который канал способен передать за единицу времени. Маленькие последовательные запросы могут быть медленными из-за многократного ожидания даже при высокой пропускной способности. Крупный файл дольше загружается при низкой пропускной способности, даже если соединение установилось быстро.

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое TTFB и почему он может быть большим?</summary>

TTFB, или Time to First Byte, - время от начала навигации или запроса до первого байта ответа. В него могут входить DNS, соединение, TLS, путь до сервера, очередь и обработка на backend, обращение к базе данных и CDN cache miss. Для запроса HTML-документа высокий TTFB откладывает обнаружение остальных ресурсов и часто ухудшает LCP.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем transfer size отличается от resource size?</summary>

Transfer size показывает объем сетевой передачи, а resource size - размер содержимого после распаковки. Например, JavaScript может занимать 300 КБ по сети после Brotli и 1 МБ после распаковки. Браузеру все равно нужно разобрать и выполнить код, поэтому маленький transfer size не гарантирует дешевую работу main thread.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему файлы с content hash можно кешировать надолго?</summary>

Content hash вычисляется из содержимого файла и включается в имя, например `app.a81f3c.js`. При изменении кода сборка создает другой URL, поэтому старый ответ не нужно принудительно обновлять. HTML новой версии ссылается на новые имена, а неизменившиеся файлы продолжают браться из кеша.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему HTML обычно не кешируют так же, как файлы с hash в имени?</summary>

HTML является точкой входа и содержит ссылки на chunks текущего релиза. Старый документ может запросить файлы, уже удаленные после развертывания, или оставить пользователя на прежней версии. Поэтому HTML обычно перепроверяют или кешируют ненадолго, а несколько поколений файлов сборки сохраняют на CDN достаточно долго для открытых вкладок и постепенного обновления клиентов.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем <code>no-cache</code>, <code>no-store</code> и <code>max-age=0</code> отличаются друг от друга?</summary>

`no-store` запрещает сохранять ответ в HTTP cache. `no-cache` разрешает хранение, но требует успешной проверки у сервера перед использованием. `max-age=0` делает ответ устаревшим сразу; он тоже обычно потребует проверки, но его смысл задается через срок свежести. Для конфиденциальных данных выбирают политику по требованиям безопасности, а не только ради производительности.

</details>

<details>
<summary><strong>Вопрос:</strong> Как работают <code>ETag</code> и ответ <code>304 Not Modified</code>?</summary>

Сервер присваивает версии ответа идентификатор `ETag`. При следующем запросе браузер отправляет его в `If-None-Match`. Если представление не изменилось, сервер отвечает `304` без тела, и браузер использует сохраненное содержимое. Это экономит передачу, но не устраняет сетевую задержку, поэтому еще свежий ответ из кеша быстрее проверки у сервера (revalidation).

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое <code>stale-while-revalidate</code>?</summary>

Эта директива разрешает временно отдать устаревший ответ, пока кеш обновляет его в фоне. Пользователь быстро получает прежнее содержимое, а следующий запрос сможет использовать новую версию. Стратегия подходит не всем данным: нужно заранее определить, допустима ли кратковременная устарелость ответа.

</details>

<details>
<summary><strong>Вопрос:</strong> Что происходит при CDN cache hit и cache miss?</summary>

При hit нужный вариант ответа уже находится на пограничном сервере CDN, и запрос не доходит до origin. При miss CDN обращается к исходному серверу, получает ответ и может сохранить его по правилам кеширования. Первый пользователь получает полную задержку cache miss, а последующие выигрывают только при совпадающем cache key и еще свежем ответе.

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое cache key и как <code>Vary</code> на него влияет?</summary>

Cache key определяет, какие запросы могут использовать один сохраненный ответ. Помимо URL CDN или браузер учитывает заголовки, перечисленные в `Vary`, например `Accept-Encoding`. Если добавить заголовок или cookie с множеством уникальных значений, кеш создаст слишком много вариантов и доля hit снизится. Если не указать значимый признак, разные клиенты могут получить неправильный вариант ответа.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем <code>max-age</code> отличается от <code>s-maxage</code>?</summary>

`max-age` задает свежесть ответа для кешей в общем случае, включая браузер. `s-maxage` переопределяет этот срок для shared cache, то есть общего промежуточного кеша вроде CDN. Так публичный ответ можно дольше держать на CDN, но чаще обновлять в браузере. Ответ с `private` общий кеш хранить не должен.

</details>

<details>
<summary><strong>Вопрос:</strong> Когда использовать Brotli, а когда gzip?</summary>

Для HTTPS-сайтов обычно включают оба варианта и позволяют согласованию `Accept-Encoding` выбрать поддерживаемый алгоритм. Brotli часто дает меньший размер текста, gzip остается совместимым запасным вариантом. Статические файлы выгодно сжимать заранее на высоком уровне, а динамические ответы - с настройкой, которая не создает чрезмерную нагрузку на сервер.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему сжатие JavaScript не решает проблему большого bundle полностью?</summary>

Оно уменьшает сетевую передачу, но браузер распаковывает код, разбирает синтаксис, компилирует и выполняет его. На слабом устройстве эти CPU-затраты могут доминировать. Поэтому одновременно уменьшают сам код, начальный chunk и число модулей, выполняемых до готовности интерфейса.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем HTTP cache отличается от Cache API и Service Worker cache?</summary>

HTTP cache управляется браузером автоматически по HTTP-заголовкам. Cache API - JavaScript API для явного хранения пар `Request` и `Response`; его часто использует Service Worker для работы без сети. Эти хранилища независимы: запись в Cache API не означает появление того же ответа в HTTP cache, а правила актуальности и удаления приложение должно продумать самостоятельно.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему после нового деплоя может возникнуть <code>ChunkLoadError</code>?</summary>

Открытая вкладка или старый HTML могут запросить chunk предыдущей сборки, который уже удален с сервера. Защита состоит из content hash, корректного кеширования HTML, хранения старых файлов сборки дольше времени жизни клиентов и управляемого восстановления: приложение может предложить обновить страницу, но не должно бесконечно повторять загрузку отсутствующего файла.

</details>

## Где это встречается во frontend

| Ситуация | Что проверяют |
| --- | --- |
| Повторная загрузка приложения снова скачивает JS | `Cache-Control`, content hash и источник ответа в Network panel |
| CDN почти не уменьшает TTFB | Долю cache hit, cache key, cookies, query-параметры и время origin |
| JS мало весит по сети, но долго блокирует страницу | Resource size, разбор и выполнение, а не только Brotli |
| После деплоя часть пользователей получает ошибку chunk | Политику HTML, срок хранения старых файлов и обработку обновления |
| LCP-изображение начинает загружаться поздно | Цепочку запросов, момент обнаружения, приоритет, preload и состояние кеша |
