## Вопрос

<br>

 💬 **Как находить и устранять проблемы производительности в React? Когда нужны `memo`, `useMemo`, `useCallback` и виртуализация списков?**

<h2></h2>

<br>
<dl>
<dd>

Оптимизацию React начинают не с добавления `memo`, а с конкретного медленного пользовательского сценария и измерения.

Например:

```text
ввод в поле задерживается

Dialog долго открывается

таблица дёргается при прокрутке

переключение вкладки занимает 500 мс

после обновления context рендерится вся страница
```

Большое число rerender само по себе не доказывает проблему.

Повторный вызов маленького компонента может занимать доли миллисекунды, а реальная задержка может находиться в:

- обработчике события;
- сортировке большого массива;
- сетевом запросе;
- стороннем скрипте;
- React render;
- commit;
- `useLayoutEffect`;
- style calculation;
- layout;
- paint;
- большом DOM;
- декодировании изображения.

Правильная последовательность:

```text
симптом
→ измерение
→ медленная фаза
→ причина
→ минимальная оптимизация
→ повторное измерение
```

### Как React обновляет интерфейс

Упрощённо обновление проходит через четыре шага:

```text
trigger
→ render
→ commit
→ browser rendering
```

#### Trigger

React получает причину подготовить новое состояние интерфейса.

Например:

- первоначальный запуск root;
- обновление state;
- обновление state предка;
- изменение context;
- обновление внешнего хранилища по подписке;
- завершение Suspense-ресурса.

Props сами по себе не являются отдельным событием, запускающим render.

Компонент получает новые props, когда его родитель уже обновляется и возвращает новый React element.

#### Render phase

Во время render React вызывает компоненты и вычисляет, каким должен стать интерфейс:

```text
props + state + context
→ React elements
```

Render должен быть чистым:

```text
одинаковые входные данные
→ одинаковый результат
```

Во время render нельзя выполнять внешние побочные эффекты:

- отправлять аналитику;
- изменять DOM вручную;
- запускать сетевой запрос без подходящего механизма;
- изменять внешнюю переменную;
- подписываться на событие;
- запускать timer.

React может:

- вызвать компонент повторно;
- прервать render;
- начать его заново;
- отказаться от подготовленного результата.

Поэтому корректность не должна зависеть от того, что render выполнится ровно один раз.

#### Commit phase

После подготовки результата React выполняет commit.

На этой фазе React:

- применяет необходимые изменения к DOM;
- обновляет ref;
- запускает layout Effects;
- завершает одно согласованное обновление дерева.

Commit не означает, что весь DOM создаётся заново.

При повторном render React применяет только необходимые DOM-операции.

Например:

```tsx
function Clock({
  time,
}: {
  time: string;
}) {
  return (
    <>
      <h1>{time}</h1>
      <input />
    </>
  );
}
```

При изменении `time` React обновит текст `<h1>`, но не обязан пересоздавать `<input>`.

#### Browser rendering

После DOM-изменений браузеру может понадобиться:

```text
style
→ layout
→ paint
→ composite
```

React Profiler измеряет React-работу, но не объясняет полностью последующий layout и paint.

Например:

```text
React render
→ 15 мс

browser layout и paint
→ 180 мс
```

В React Profiler обновление может выглядеть приемлемым, хотя пользователь получает заметную задержку.

Поэтому React DevTools Profiler используют вместе с Chrome Performance.

### Rerender, DOM update и remount

Это разные процессы.

**Rerender:**

```text
React снова вызвал компонент
```

**DOM update:**

```text
React обнаружил отличие результата
и изменил DOM
```

**Remount:**

```text
React удалил прежний экземпляр
и создал новый
```

Rerender не обязательно приводит к DOM update.

Remount обычно приводит к:

- сбросу локального state;
- cleanup Effects;
- новому mount Effects;
- пересозданию DOM соответствующего поддерева;
- потере пользовательского состояния элемента.

Remount может произойти, если изменился:

- тип компонента в той же позиции;
- его `key`;
- положение в дереве так, что React больше не сопоставляет экземпляры.

Например:

```tsx
<UserForm
  key={userId}
/>
```

при изменении `userId` намеренно сбросит state формы.

Нестабильный случайный key:

```tsx
<Item
  key={Math.random()}
/>
```

заставит React пересоздавать элементы при каждом обновлении и ухудшит как производительность, так и корректность.

### Из-за чего компонент рендерится повторно

Основные причины:

```text
изменился собственный state

обновился предок

изменился читаемый context

обновилось внешнее хранилище
```

#### Собственный state

```tsx
const [
  count,
  setCount,
] = useState(0);
```

Вызов:

```ts
setCount(1);
```

планирует обновление компонента.

Если новое значение совпадает с предыдущим через `Object.is`, React обычно может пропустить дальнейшее обновление.

```ts
setCount(0);
```

при уже существующем `0` не является способом принудительно перерисовать компонент.

#### Обновление родителя

По умолчанию при render родителя React рекурсивно обрабатывает возвращённое им поддерево.

```text
Parent render
→ Child render
→ Grandchild render
```

Даже если props ребёнка визуально выглядят одинаковыми, обычный функциональный компонент будет вызван снова.

Пропустить этот вызов могут:

- `memo`;
- React Compiler;
- переиспользованный React element;
- другая внутренняя оптимизация React.

#### Context

Если Provider передал другое значение, React обновляет компоненты, которые читают этот context.

```tsx
<ThemeContext.Provider
  value={{
    theme,
    setTheme,
  }}
>
```

Новый объект создаётся при каждом render Provider.

Если значение действительно изменилось по ссылке, потребители получают обновление.

`memo` не блокирует изменение context, прочитанного внутри компонента.

#### Внешнее хранилище

Redux, Zustand и другие хранилища подписывают компонент на внешнее состояние.

Эффективность зависит от того, насколько узкие данные выбирает подписка.

```text
подписка на весь store
→ больше обновлений

подписка на конкретное поле
→ меньше обновлений
```

Selector должен возвращать стабильный результат, если выбранные данные не изменились.

### Сначала уменьшают ненужную работу архитектурно

До ручной мемоизации проверяют более простые причины.

#### Локализовать state

Transient state не следует поднимать выше, чем нужно.

Например:

```text
hover одной карточки
состояние открытого tooltip
значение локального input
```

обычно не должны находиться в root-компоненте страницы.

Плохо:

```text
Root state изменился
→ обновилось большое поддерево
```

Лучше:

```text
state находится рядом
с использующим компонентом
```

#### Использовать композицию

Компонент-обёртка может принимать готовое содержимое через `children`:

```tsx
function ExpandablePanel({
  children,
}: {
  children: React.ReactNode;
}) {
  const [
    expanded,
    setExpanded,
  ] = useState(false);

  return (
    <section>
      <button
        onClick={() => {
          setExpanded(
            (value) => !value,
          );
        }}
      >
        Переключить
      </button>

      {expanded && children}
    </section>
  );
}
```

`children` создан родителем обёртки.

Когда меняется локальный state `ExpandablePanel`, React может переиспользовать ранее переданный element вместо повторного выполнения всего содержимого только из-за state обёртки.

Это часто устраняет необходимость вручную оборачивать содержимое в `memo`.

#### Не хранить производные данные в Effect

Плохо:

```tsx
const [
  filteredItems,
  setFilteredItems,
] = useState<Item[]>([]);

useEffect(() => {
  setFilteredItems(
    filterItems(
      items,
      query,
    ),
  );
}, [
  items,
  query,
]);
```

Последовательность:

```text
render со старым filteredItems
→ commit
→ Effect
→ setState
→ второй render
```

Если вычисление чистое, результат можно получить во время render:

```tsx
const filteredItems =
  filterItems(
    items,
    query,
  );
```

Если оно действительно дорогое, затем рассматривают `useMemo`.

Цепочки Effects, которые только преобразуют React state в другой React state, часто создают лишние render и commit.

#### Разделить независимые обновления

Если одна часть страницы обновляется часто, её state и component boundary можно отделить от тяжёлой части.

Например:

```text
SearchInput
→ срочное обновление каждого символа

ResultsTable
→ тяжёлое обновление результата
```

Необязательно хранить оба процесса в одном большом компоненте.

#### Уменьшить передаваемые данные

Вместо большого изменяемого объекта:

```tsx
<UserCard
  user={user}
/>
```

иногда полезнее передать минимальные значения:

```tsx
<UserCard
  name={user.name}
  avatarUrl={
    user.avatarUrl
  }
/>
```

Это упрощает контракт и повышает вероятность неизменности props.

Но не нужно механически превращать каждый объект в десятки props.

Граница должна оставаться понятной.

### `React.memo`

`memo` возвращает мемоизированную версию компонента:

```tsx
import {
  memo,
} from "react";

type ProductRowProps = {
  name: string;
  price: number;
};

export const ProductRow =
  memo(function ProductRow({
    name,
    price,
  }: ProductRowProps) {
    return (
      <div>
        {name}: {price}
      </div>
    );
  });
```

Когда родитель обновляется, React сравнивает прежние и новые props.

По умолчанию каждый prop сравнивается через:

```ts
Object.is(
  previousProp,
  nextProp,
);
```

Если все props равны, React обычно пропускает render компонента.

`memo` является оптимизацией производительности, а не смысловой гарантией.

Код должен оставаться корректным и без пропуска render.

Компонент в `memo` всё равно обновится, если:

- изменился его собственный state;
- изменился читаемый context;
- изменилась внешняя подписка;
- изменился хотя бы один prop;
- React по внутренней причине решил выполнить render.

### Когда `memo` помогает

Обычно должны одновременно выполняться условия:

```text
родитель обновляется часто

component render измеримо дорогой

props часто остаются прежними

сравнение props дешевле render
```

Пример:

```text
график строится дорого

родитель обновляет состояние tooltip

данные графика не меняются
```

Здесь `memo` может пропустить дорогое построение графика.

`memo` обычно бесполезен, если:

- компонент дешёвый;
- родитель обновляется редко;
- props меняются при каждом render;
- задержка находится не в React;
- один prop всегда получает новую ссылку;
- сравнение сложнее самого render.

Плохо:

```tsx
<MemoizedChart
  options={{
    legend: true,
  }}
  onSelect={() => {
    selectItem(id);
  }}
/>
```

Объект и функция создаются заново:

```text
previous options !== next options
previous onSelect !== next onSelect
```

Мемоизация компонента нарушается.

### Стабильность props

Ссылочные значения сравниваются по identity:

```ts
Object.is(
  {},
  {},
);
// false
```

```ts
Object.is(
  [],
  [],
);
// false
```

```ts
Object.is(
  () => {},
  () => {},
);
// false
```

Способы получить стабильную ссылку:

- объявить константу на уровне module;
- передать primitive;
- сохранить вычисленный объект через `useMemo`;
- сохранить callback через `useCallback`;
- изменить API компонента;
- перенести создание значения ближе к месту использования.

Константа, не зависящая от component state:

```ts
const DEFAULT_COLUMNS = [
  "name",
  "price",
];
```

не требует `useMemo`.

### `useMemo`

`useMemo` сохраняет результат чистого вычисления между render, пока зависимости не изменились:

```tsx
const visibleProducts =
  useMemo(
    () =>
      products
        .filter((product) =>
          product.name
            .toLowerCase()
            .includes(
              query.toLowerCase(),
            ),
        )
        .toSorted(
          (left, right) =>
            left.price -
            right.price,
        ),
    [
      products,
      query,
    ],
  );
```

React сравнивает зависимости через `Object.is`.

Если они прежние, возвращается сохранённый результат.

Если хотя бы одна зависимость изменилась, вычисление выполняется снова.

Функция внутри `useMemo` должна:

- быть чистой;
- возвращать значение;
- не выполнять side effects;
- не изменять входные props;
- содержать полный список зависимостей.

Плохо:

```tsx
useMemo(() => {
  sendAnalytics();
}, []);
```

`useMemo` не предназначен для побочных эффектов.

### Когда нужен `useMemo`

Основные случаи:

**Дорогое чистое вычисление**

```text
сортировка большого массива
агрегация данных
построение сложной структуры
```

при условии, что его входные данные меняются реже, чем компонент рендерится.

**Стабильный prop для мемоизированного компонента**

```tsx
const options =
  useMemo(
    () => ({
      scale,
      showLegend,
    }),
    [
      scale,
      showLegend,
    ],
  );

return (
  <MemoizedChart
    options={options}
  />
);
```

**Стабильная зависимость другого Hook**

Такое применение допустимо, но сначала стоит проверить, нельзя ли:

- создать объект внутри Effect;
- вынести константу из компонента;
- передавать primitives;
- убрать сам Effect.

### Когда `useMemo` не нужен

```tsx
const fullName =
  `${firstName} ${lastName}`;
```

```tsx
const isEmpty =
  items.length === 0;
```

```tsx
const total =
  price * quantity;
```

Подобные операции дешевле выполнить заново, чем усложнять код кешем и dependency array.

`useMemo` имеет собственную стоимость:

- сравнение dependencies;
- хранение значения;
- усложнение чтения;
- риск неверных зависимостей;
- дополнительную работу сборщика и runtime.

Кеш не должен быть смысловым хранилищем.

React может удалить значение `useMemo`, например при первоначальном suspension или в некоторых development-сценариях.

Если значение должно сохраняться для корректности, используют:

- state;
- ref;
- внешнее хранилище;
- cache с явным lifecycle.

### Strict Mode и измерение вычислений

В development Strict Mode React может вызвать функцию вычисления дважды, чтобы обнаружить нечистую логику.

```tsx
const result =
  useMemo(
    () =>
      calculate(items),
    [items],
  );
```

`calculate` должна корректно выдерживать повторный вызов.

В production такое development-поведение отсутствует.

Поэтому нельзя оценивать итоговую стоимость только по числу `console.log` в development.

Для измерения используют:

- production build;
- React Profiler;
- Chrome Performance;
- повторяемый сценарий.

### `useCallback`

`useCallback` сохраняет ссылку на функцию:

```tsx
const handleSelect =
  useCallback(
    (productId: string) => {
      selectProduct(
        productId,
        categoryId,
      );
    },
    [
      categoryId,
      selectProduct,
    ],
  );
```

Он эквивалентен по смыслу:

```tsx
const handleSelect =
  useMemo(
    () =>
      (
        productId: string,
      ) => {
        selectProduct(
          productId,
          categoryId,
        );
      },
    [
      categoryId,
      selectProduct,
    ],
  );
```

`useCallback`:

- не ускоряет выполнение функции;
- не выполняет её заранее;
- не уменьшает стоимость её тела;
- не предотвращает создание function expression в исходном render-коде;
- возвращает прежнюю функцию, если dependencies не изменились.

### Когда нужен `useCallback`

Основные случаи:

**Функция передаётся в компонент с `memo`**

```tsx
const handleDelete =
  useCallback(
    (id: string) => {
      deleteProduct(id);
    },
    [
      deleteProduct,
    ],
  );

return (
  <MemoizedList
    onDelete={handleDelete}
  />
);
```

**Identity функции является частью API**

Например, подписка должна удалить тот же обработчик, который был добавлен.

Однако часто правильнее организовать подписку внутри одного Effect, чтобы handler не становился внешней зависимостью без необходимости.

**Функция возвращается из custom Hook**

Custom Hook может стабилизировать публичные команды, чтобы потребитель мог оптимизировать собственные зависимости.

### Когда `useCallback` не нужен

```tsx
<button
  onClick={() => {
    setOpen(true);
  }}
>
  Открыть
</button>
```

Если функция передаётся обычному DOM-элементу и не используется как зависимость другой оптимизации, `useCallback` обычно ничего не улучшит.

Создание маленькой функции редко является главным bottleneck.

Проблемой становится не сам факт создания, а изменение identity для потребителя, который пытается пропускать работу.

### Dependencies и stale closures

Нельзя удалять зависимость только ради стабильной ссылки.

Плохо:

```tsx
const handleSubmit =
  useCallback(() => {
    saveForm(form);
  }, []);
```

`form` отсутствует в dependencies.

Callback сохранит значение из старого render и может отправить устаревшие данные.

Правильно:

```tsx
const handleSubmit =
  useCallback(() => {
    saveForm(form);
  }, [
    form,
    saveForm,
  ]);
```

Если dependency меняется слишком часто, сначала выясняют причину:

- объект создаётся заново;
- state расположен слишком высоко;
- API компонента слишком широкий;
- Effect построен неправильно;
- можно использовать updater function;
- функция вообще не нуждается в мемоизации.

Оптимизация не должна нарушать модель данных React.

### Updater function и зависимости

Если callback читает state только для вычисления следующего state, можно использовать updater:

```tsx
const addTodo =
  useCallback(
    (title: string) => {
      setTodos(
        (currentTodos) => [
          ...currentTodos,
          {
            id: crypto.randomUUID(),
            title,
          },
        ],
      );
    },
    [],
  );
```

Callback не читает `todos` из замыкания, поэтому dependency не нужна.

Это уменьшает зависимости без сокрытия данных от linter.

### Пользовательский `arePropsEqual`

`memo` позволяет передать собственную функцию сравнения:

```tsx
const Chart =
  memo(
    ChartComponent,
    (
      previousProps,
      nextProps,
    ) => {
      return (
        previousProps.data ===
          nextProps.data &&
        previousProps.width ===
          nextProps.width
      );
    },
  );
```

Функция должна вернуть `true`, только если компонент с новыми props:

- покажет тот же результат;
- будет вести себя так же;
- не должен получить новое замыкание.

Нужно сравнить все props, включая функции.

Если считать разные callbacks одинаковыми, компонент может продолжить использовать функцию, замкнувшую старые state или props.

Опасно выполнять неограниченное глубокое сравнение:

```text
большой массив
вложенные объекты
неограниченная глубина
```

Сравнение может оказаться дороже render или заблокировать интерфейс при изменении структуры данных.

Custom comparator оправдан, если:

- форма данных ограничена;
- сравнение дешёвое;
- render действительно дорогой;
- выигрыш подтверждён Profiler.

### Context и производительность

Provider часто передаёт объект:

```tsx
const value = {
  user,
  logout,
};

return (
  <AuthContext.Provider
    value={value}
  >
    {children}
  </AuthContext.Provider>
);
```

При каждом render создаётся новая ссылка.

Если Provider обновляется по несвязанной причине, читающие context компоненты могут получить обновление.

Возможные изменения:

**Разместить Provider ниже**

```text
меньше потребителей
→ меньше область обновления
```

**Разделить независимые Context**

```text
AuthUserContext
AuthActionsContext
ThemeContext
```

Вместо одного объекта со всеми данными приложения.

**Стабилизировать value**

```tsx
const value =
  useMemo(
    () => ({
      user,
      logout,
    }),
    [
      user,
      logout,
    ],
  );
```

Это полезно, только если Provider действительно обновляется при неизменных `user` и `logout`.

**Использовать внешнее хранилище с selectors**

Context не предоставляет встроенный selector отдельного поля.

Внешнее хранилище может уведомлять компонент только при изменении выбранного фрагмента.

Нельзя исправить большой Context только оборачиванием каждого consumer в `memo`: изменение читаемого context всё равно обновляет его.

### React DevTools Profiler

Profiler показывает React render и commit.

Основные данные:

- commits;
- компоненты, участвовавшие в обновлении;
- длительность render;
- flamegraph;
- ranked view;
- обновления отдельных поддеревьев.

Программный `<Profiler>`:

```tsx
import {
  Profiler,
} from "react";

function onRender(
  id: string,
  phase: "mount" |
    "update" |
    "nested-update",
  actualDuration: number,
  baseDuration: number,
  startTime: number,
  commitTime: number,
) {
  console.log({
    id,
    phase,
    actualDuration,
    baseDuration,
    startTime,
    commitTime,
  });
}

export function App() {
  return (
    <Profiler
      id="Products"
      onRender={onRender}
    >
      <Products />
    </Profiler>
  );
}
```

`actualDuration` показывает время render поддерева в конкретном обновлении с учётом успешной мемоизации.

`baseDuration` оценивает стоимость render всего поддерева без пропущенных вычислений на основе последних длительностей компонентов.

Упрощённо:

```text
actualDuration
→ сколько React потратил сейчас

baseDuration
→ примерная стоимость полного render
```

Если `actualDuration` значительно ниже `baseDuration`, мемоизация поддерева, вероятно, пропускает часть работы.

Но эти числа не включают всю пользовательскую задержку.

После commit браузер может выполнять дорогие layout и paint.

Profiling также создаёт overhead.

Обычный production build отключает часть profiling-возможностей; для production-измерений нужен специальный profiling build либо подходящий framework-инструмент.

### Chrome Performance и React Profiler

Инструменты отвечают на разные вопросы.

**React Profiler:**

```text
какие React-компоненты рендерились

сколько занял React render

какой commit дорогой
```

**Chrome Performance:**

```text
что происходило на main thread

какой handler был долгим

сколько заняли script, style, layout и paint

почему поздно появился следующий кадр
```

Пример расследования:

```text
1. Клик задерживается 500 мс.
2. Performance показывает long task.
3. Внутри task React render занимает 300 мс.
4. React Profiler показывает дорогую таблицу.
5. После render browser layout занимает ещё 120 мс.
```

Здесь одной мемоизации может быть недостаточно.

Возможно, нужно:

- уменьшить число строк;
- виртуализировать список;
- упростить layout;
- локализовать state;
- сократить вычисление.

### Почему DevTools в development может вводить в заблуждение

Development build содержит:

- дополнительные проверки;
- Strict Mode;
- source maps;
- warning;
- HMR;
- неминифицированный код.

React может намеренно вызывать некоторые функции повторно.

Поэтому development profiling полезен для поиска направления, но итоговый результат подтверждают на production build или profiling build.

Нельзя сравнивать:

```text
development до изменения
```

с:

```text
production после изменения
```

Условия должны быть одинаковыми.

### Виртуализация списков

Виртуализация означает, что приложение создаёт только видимое окно списка и небольшой запас вокруг него.

Без виртуализации:

```text
10 000 records
→ 10 000 React-компонентов
→ тысячи DOM-узлов
→ дорогие render, layout и paint
```

С виртуализацией:

```text
видно 20 строк
+
overscan 10 строк
→ около 30–40 строк в DOM
```

Оставшиеся элементы представлены общей виртуальной геометрией списка, но не смонтированы одновременно.

Виртуализация уменьшает:

- mount cost;
- число React-компонентов;
- размер DOM;
- style calculation;
- layout;
- paint;
- использование памяти.

Она не уменьшает автоматически:

- размер исходного массива;
- стоимость получения данных;
- стоимость фильтрации всех records;
- сетевой payload;
- серверную работу.

### Когда нужна виртуализация

Не существует универсального числа строк.

Она нужна, когда измерения показывают, что большое количество одновременно созданных элементов ухудшает:

- первый render;
- обновление;
- прокрутку;
- layout;
- paint;
- память.

Например, 500 простых строк могут работать нормально, а 100 сложных карточек с изображениями, меню и Effects — уже плохо.

Перед виртуализацией проверяют:

- стоимость одной строки;
- количество DOM-узлов;
- частоту обновлений;
- browser rendering;
- возможность pagination;
- требования доступности.

### Ограничения виртуализации

**Динамическая высота**

Строки разной высоты нужно измерять и корректировать без скачка scroll position.

**Overscan**

Слишком маленький запас показывает пустую область при быстрой прокрутке.

Слишком большой запас уменьшает выигрыш.

**Фокус**

Сфокусированный элемент может быть удалён из DOM после выхода из виртуального окна.

Нужна продуманная keyboard navigation.

**Screen reader**

Необходимо корректно сообщать:

- общее количество элементов;
- позицию текущей строки;
- структуру таблицы или списка;
- доступные команды.

**Поиск по странице**

Browser find не найдёт текст элементов, которых нет в DOM.

**Печать и копирование**

Виртуализированное содержимое может потребовать отдельного режима.

**SSR и hydration**

Server HTML и первоначальное client window должны согласовываться, чтобы избежать mismatch и скачка layout.

**Scroll restoration**

После возврата на маршрут нужно восстановить как scroll offset, так и соответствующее виртуальное окно.

### Виртуализация, pagination и infinite scroll

Это разные подходы.

**Виртуализация**

```text
данные могут быть загружены
→ в DOM находится только видимая часть
```

**Pagination**

```text
пользователь получает отдельную страницу данных
```

Уменьшает и данные, и DOM конкретной страницы.

**Infinite scroll**

```text
следующая порция загружается
при приближении к концу
```

Без виртуализации DOM может продолжать расти после каждой порции.

Эти подходы можно сочетать:

```text
постраничная загрузка данных
+
виртуализированное отображение
```

### `useTransition`

`useTransition` позволяет пометить state update как несрочное:

```tsx
const [
  isPending,
  startTransition,
] = useTransition();

function handleTabChange(
  nextTab: Tab,
) {
  setSelectedTab(
    nextTab,
  );

  startTransition(() => {
    setRenderedTab(
      nextTab,
    );
  });
}
```

Срочное обновление может отобразиться раньше, а transition render:

- выполняться с более низким приоритетом;
- быть прерван новым срочным обновлением;
- начаться заново;
- показать pending state.

Transition не откладывает вызов callback как `setTimeout`.

Callback запускается сразу, а синхронные state updates внутри помечаются как transition.

Transition нельзя использовать для state, непосредственно управляющего текстовым input: ввод должен обновляться синхронно.

### `useDeferredValue`

`useDeferredValue` создаёт отложенную версию значения:

```tsx
const [
  query,
  setQuery,
] = useState("");

const deferredQuery =
  useDeferredValue(
    query,
  );

return (
  <>
    <SearchInput
      value={query}
      onChange={setQuery}
    />

    <Results
      query={
        deferredQuery
      }
    />
  </>
);
```

Input получает актуальный `query` сразу.

Тяжёлая часть может временно отображать предыдущий `deferredQuery`, пока React готовит обновление.

Это помогает отзывчивости, но не уменьшает общий объём вычисления.

Если фильтрация миллиона элементов занимает секунду, её всё равно нужно:

- оптимизировать;
- выполнять на сервере;
- уменьшить набор данных;
- перенести в Worker;
- кешировать;
- заменить индексированным поиском.

`useDeferredValue` также не является debounce.

### Transitions и debounce

**Transition:**

```text
обновления могут начинаться часто
→ React меняет их приоритет
→ устаревший render может быть прерван
```

**Debounce:**

```text
операция запускается
только после паузы
```

Например:

```text
ввод поиска
→ debounce API request
```

может уменьшить число запросов.

Но debounce тяжёлой локальной фильтрации только откладывает блокировку:

```text
пользователь закончил ввод
→ через 300 мс
→ main thread всё равно блокируется
```

Инструменты могут использоваться вместе:

- актуальный input state;
- debounce сетевого запроса;
- transition отображения большого результата;
- виртуализация списка.

### Web Worker

Worker подходит для тяжёлого CPU-вычисления, которое:

- не требует DOM;
- можно передать сообщением;
- занимает main thread;
- достаточно крупное, чтобы оправдать сериализацию данных.

Например:

- parsing большого файла;
- сложная агрегация;
- обработка изображения;
- расчёт layout графа;
- поиск по большому локальному индексу.

Worker не может напрямую выполнить React render или изменить DOM.

Результат всё равно нужно передать обратно и отобразить.

Для небольшого вычисления стоимость сообщений и копирования данных может быть выше выигрыша.

### React Compiler

React Compiler анализирует components и Hooks во время build и автоматически добавляет мемоизацию.

Он помогает пропускать:

- каскадные rerender;
- повторные вычисления внутри components и Hooks;
- создание некоторых значений и React elements.

Compiler не включается только из-за установки React 19.

Он является отдельным build-time инструментом и должен быть настроен в сборке.

Текущая совместимость:

```text
React 19
→ встроенный compiler runtime

React 17 или 18
→ target соответствующей версии
  и react-compiler-runtime
```

Для React 18:

```js
{
  target: "18",
}
```

и runtime package должен находиться в обычных `dependencies`, потому что нужен во время выполнения.

В Next.js:

```text
Next.js 14
→ нет встроенной SWC-интеграции
  React Compiler этой версии

Next.js 15.3.1+
→ доступен вызов Compiler через SWC

Next.js 16
→ встроенная интеграция объявлена стабильной
```

Для Next.js 14 отдельное подключение через Babel является самостоятельным изменением toolchain, а не встроенной возможностью версии.

### Нужны ли ручные мемоизации с React Compiler

Для нового кода в проекте с включённым Compiler обычно сначала полагаются на его автоматическую мемоизацию.

Ручные:

- `memo`;
- `useMemo`;
- `useCallback`;

оставляют, когда требуется точный контроль или измерения показывают конкретную необходимость.

Существующую мемоизацию не удаляют механически.

Compiler сохраняет ручные оптимизации, а их удаление способно изменить compilation output.

Порядок:

```text
включить Compiler постепенно
→ проверить Rules of React
→ запустить тесты
→ профилировать
→ удалять ручную мемоизацию
  только осознанно
```

Compiler не заменяет:

- виртуализацию;
- уменьшение DOM;
- оптимизацию алгоритма;
- Worker;
- правильное размещение state;
- устранение Effects;
- оптимизацию браузерного layout;
- уменьшение JavaScript bundle.

### Практический порядок диагностики

```text
1. Выбрать конкретное действие.
2. Зафиксировать условия и baseline.
3. Записать Chrome Performance.
4. Определить: JavaScript, React или browser rendering.
5. Если дорог React — открыть React Profiler.
6. Найти дорогой commit и поддерево.
7. Проверить причины обновлений.
8. Сначала изменить state boundaries и data flow.
9. Затем рассмотреть memo/useMemo/useCallback.
10. Для большого DOM проверить виртуализацию.
11. Для тяжёлого CPU проверить Worker или server.
12. Повторить тот же тест.
13. Проверить INP и соседние показатели.
```

### Как выбрать инструмент

```text
дешёвые лишние rerender
→ ничего не делать

дорогой component,
props часто прежние
→ memo

дорогое чистое вычисление,
dependencies меняются редко
→ useMemo

стабильная function identity
нужна memoized consumer
→ useCallback

context обновляет слишком много
→ изменить Provider и границы данных

тысячи DOM-элементов
→ virtualization

ввод должен оставаться срочным,
результат можно отложить
→ transition/deferred value

тяжёлое CPU-вычисление
→ оптимизация алгоритма,
server или Worker

дорогой layout/paint
→ browser rendering optimization
```

Главный принцип:

```text
оптимизируют не количество render,
а задержку пользовательского сценария
```

## Дополнительные вопросы

<details>
<summary><strong>Что такое rerender и всегда ли он приводит к изменению DOM?</strong></summary>

<dl>
<dd>
<h2></h2>

Rerender означает, что React снова вызвал компонент и вычислил следующий React element tree.

После этого React сравнивает результат с предыдущим.

Если отображаемые данные и структура не изменились, DOM update может не потребоваться.

```text
rerender
≠
обязательное изменение DOM
```

Искать нужно не каждый вызов компонента, а частые или дорогие обновления, влияющие на пользовательскую задержку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Из-за чего компонент повторно рендерится?</strong></summary>

<dl>
<dd>
<h2></h2>

Основные причины:

- обновление собственного state;
- render родителя;
- изменение читаемого context;
- обновление внешнего store по подписке;
- завершение Suspense-ресурса.

Props сами не запускают render.

Новые props приходят во время обновления родителя.

Изменение `ref.current` само по себе render не планирует.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем render отличается от commit?</strong></summary>

<dl>
<dd>
<h2></h2>

Во время render React вызывает компоненты и вычисляет следующий интерфейс.

Render должен быть чистым и может быть повторён или прерван.

Во время commit React применяет необходимые DOM-изменения, обновляет ref и запускает layout Effects.

После этого browser может выполнить:

```text
style
layout
paint
composite
```

Поэтому медленным может быть React render, commit или последующая работа браузера.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда <code>React.memo</code> действительно помогает?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда одновременно выполняются условия:

- родитель обновляется часто;
- component render измеримо дорогой;
- props часто остаются прежними;
- сравнение props дешевле повторного render.

Если компонент дешёвый или каждый раз получает новый объект, массив либо функцию, `memo` может не дать выигрыша.

Решение подтверждают Profiler, а не количеством добавленных обёрток.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему компонент в <code>memo</code> всё равно может рендериться?</strong></summary>

<dl>
<dd>
<h2></h2>

`memo` сравнивает только props родителя.

Компонент продолжает обновляться при:

- изменении собственного state;
- изменении используемого context;
- изменении внешней подписки;
- изменении хотя бы одного prop.

Кроме того:

```tsx
{}
[]
() => {}
```

создают новые ссылки при каждом render и нарушают сравнение props.

`memo` является оптимизацией, а не абсолютной гарантией пропуска.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означает поверхностное сравнение props в <code>memo</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

React сравнивает каждый prop через `Object.is`.

Он не обходит вложенные поля объекта.

```ts
Object.is(
  {
    id: 1,
  },
  {
    id: 1,
  },
);
// false
```

Объекты имеют разные ссылки, хотя содержимое выглядит одинаково.

Поэтому для полезной мемоизации важны стабильные props и узкий контракт компонента.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужен <code>useMemo</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Основные случаи:

- чистое вычисление измеримо дорогое;
- его dependencies меняются редко;
- результат передаётся как prop компоненту с `memo`;
- identity значения нужна другому Hook.

Для дешёвой арифметики, простого доступа к полю или небольшой строки `useMemo` обычно добавляет больше сложности, чем пользы.

Корректность нельзя строить на гарантированном сохранении кеша.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужен <code>useCallback</code> и ускоряет ли он функцию?</strong></summary>

<dl>
<dd>
<h2></h2>

`useCallback` не ускоряет тело функции.

Он сохраняет её identity между render, пока dependencies не изменились.

Это полезно, когда функция:

- передаётся memoized component;
- является зависимостью другого Hook;
- возвращается из custom Hook;
- используется API, которому важна та же ссылка.

Без потребителя стабильной ссылки `useCallback` обычно ничего не улучшает.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем опасна собственная функция сравнения в <code>memo</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Она выполняется при каждом соответствующем обновлении и может оказаться дороже render.

Нужно корректно сравнить все props, включая callbacks.

Если разные функции считать одинаковыми, компонент может продолжить использовать замыкание со старыми props или state.

Неограниченное deep equality опасно для больших или изменяемых структур.

Custom comparator применяют только после измерения и при ограниченном контракте данных.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что показывают <code>actualDuration</code> и <code>baseDuration</code> в Profiler?</strong></summary>

<dl>
<dd>
<h2></h2>

`actualDuration` показывает время React render поддерева в конкретном обновлении с учётом сработавшей мемоизации.

`baseDuration` оценивает стоимость полного render поддерева без пропущенных компонентов на основе их последних длительностей.

```text
actualDuration
→ текущая стоимость

baseDuration
→ приблизительная полная стоимость
```

Сравнение помогает оценить мемоизацию, но не включает всю работу browser layout и paint.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как уменьшить обновления большого context?</strong></summary>

<dl>
<dd>
<h2></h2>

Возможные способы:

- поместить Provider ниже;
- разделить независимые данные по разным Context;
- не передавать один огромный объект приложения;
- стабилизировать `value`, когда он создаётся заново без изменения данных;
- использовать внешнее хранилище с selectors.

`memo` не предотвращает обновление компонента при изменении context, который он читает.

Сначала определяют, какие данные действительно должны обновляться вместе.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Отменяет ли React Compiler ручные <code>memo</code>, <code>useMemo</code> и <code>useCallback</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Compiler автоматически добавляет мемоизацию и уменьшает потребность в ручных API, но сохраняет существующую ручную мемоизацию.

Для нового кода в проекте с Compiler сначала доверяют автоматической оптимизации.

Ручные Hooks используют для точного контроля и подтверждённых сценариев.

Существующие оптимизации не удаляют механически: это может изменить compilation output.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Ускоряют ли <code>useTransition</code> и <code>useDeferredValue</code> вычисления?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Они изменяют приоритет отображения обновлений.

Срочное обновление, например ввод символа, может появиться раньше, а тяжёлая часть будет подготовлена позже и может быть прервана новым вводом.

Общий объём работы не исчезает.

Если вычисление само по себе слишком тяжёлое, нужны:

- лучший алгоритм;
- уменьшение данных;
- серверная обработка;
- виртуализация;
- Web Worker.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужна виртуализация списка и какие у неё ограничения?</strong></summary>

<dl>
<dd>
<h2></h2>

Она нужна, когда большое число одновременно смонтированных строк делает дорогими:

- render;
- mount;
- layout;
- paint;
- прокрутку;
- использование памяти.

В DOM оставляют видимое окно и overscan.

Проверяют:

- динамическую высоту;
- scroll restoration;
- focus;
- keyboard navigation;
- screen reader;
- поиск по странице;
- SSR и hydration;
- печать и копирование.

Для короткого списка такая сложность обычно неоправданна.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как последовательно расследовать медленное обновление React-интерфейса?</strong></summary>

<dl>
<dd>
<h2></h2>

Порядок:

```text
1. Зафиксировать медленное действие.
2. Записать Chrome Performance.
3. Определить JavaScript, React или rendering bottleneck.
4. Открыть React Profiler, если дорог React.
5. Найти commit и тяжёлое поддерево.
6. Проверить state, context, props и Effects.
7. Изменить одну причину.
8. Повторить тот же сценарий.
9. Сравнить INP, render и browser work.
```

Количество rerender без длительности и пользовательского контекста недостаточно для вывода.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем rerender отличается от remount?</strong></summary>

<dl>
<dd>
<h2></h2>

При rerender React сохраняет экземпляр компонента и его state, затем вычисляет новый результат.

При remount прежний экземпляр удаляется и создаётся новый.

Remount вызывает:

- cleanup Effects;
- сброс state;
- новые mount Effects;
- пересоздание соответствующего DOM.

Частые причины remount:

- изменившийся `key`;
- другой component type в той же позиции;
- изменение структуры дерева.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Запустит ли <code>setState</code> обновление, если значение не изменилось?</strong></summary>

<dl>
<dd>
<h2></h2>

Если следующее значение равно предыдущему через `Object.is`, React обычно может пропустить обновление.

Например:

```ts
setCount(0);
```

при уже существующем `0` не является способом принудительного render.

Для объектов сравнивается ссылка:

```ts
setUser({
  ...user,
});
```

создаёт новое значение, даже если поля совпадают.

State следует обновлять только при реальном изменении данных.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как композиция через <code>children</code> уменьшает rerender?</strong></summary>

<dl>
<dd>
<h2></h2>

Обёртка может получать готовый React element через `children`.

Когда меняется локальный state обёртки, сам `children` может остаться прежним значением, созданным её родителем.

React способен переиспользовать его без повторного выполнения содержимого только из-за обновления обёртки.

Это особенно полезно для:

- panel;
- modal shell;
- scroll container;
- визуальной обёртки с локальным state.

Подход часто проще ручной мемоизации каждого дочернего компонента.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как Effects создают лишние render?</strong></summary>

<dl>
<dd>
<h2></h2>

Effect выполняется после commit.

Если он сразу обновляет React state:

```text
render
→ commit
→ Effect
→ setState
→ новый render
```

Возникает дополнительный цикл.

Особенно часто это происходит, когда Effect вычисляет производные данные из props или другого state.

Чистые производные значения получают во время render, а дорогое вычисление при необходимости мемоизируют.

Effect оставляют для синхронизации с внешней системой.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему стабильные <code>key</code> важны для производительности?</strong></summary>

<dl>
<dd>
<h2></h2>

Key помогает React сопоставить элементы между обновлениями.

Стабильный идентификатор позволяет сохранить:

- component instance;
- state;
- DOM;
- Effects;
- focus.

Случайный или постоянно меняющийся key приводит к remount.

Index может быть допустим для неизменяемого статического списка, но опасен при сортировке, вставке и удалении элементов.

Key выбирают по идентичности данных, а не по позиции render.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем debounce отличается от <code>useDeferredValue</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Debounce уменьшает частоту запуска операции:

```text
выполнить после паузы
```

`useDeferredValue` не отменяет промежуточные значения как отдельный timer. Он позволяет React отложить отображение части интерфейса и прервать устаревший render.

Debounce полезен для:

- API-запроса;
- сохранения;
- тяжёлой операции, которую не нужно запускать на каждый символ.

`useDeferredValue` полезен для сохранения отзывчивости React UI.

Они могут использоваться вместе.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему в Strict Mode component может рендериться дважды?</strong></summary>

<dl>
<dd>
<h2></h2>

В development React намеренно повторяет некоторые вызовы, чтобы обнаружить нечистую render-логику и проблемы cleanup.

Это не означает, что production всегда выполнит тот же render дважды.

Код компонента должен оставаться корректным при повторном вызове.

Performance сравнивают на одинаковых production-like сборках, а не по количеству `console.log` в Strict Mode.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как Server Components влияют на React performance?</strong></summary>

<dl>
<dd>
<h2></h2>

Server Component выполняется на сервере, а его implementation JavaScript не требуется браузеру как client component code.

Это может уменьшить:

- client bundle;
- parsing;
- hydration;
- количество клиентских компонентов.

Но Server Components не исправляют автоматически:

- медленный server request;
- большой HTML/RSC payload;
- дорогой Client Component;
- layout и paint;
- плохую стратегию кэша.

Границу `"use client"` размещают как можно ниже, сохраняя необходимую интерактивность.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выбрать между мемоизацией, виртуализацией и Web Worker?</strong></summary>

<dl>
<dd>
<h2></h2>

Выбор зависит от bottleneck.

```text
дорогой повторный React render
при прежних inputs
→ memoization

слишком много одновременно
смонтированных элементов
→ virtualization

тяжёлое CPU-вычисление,
не требующее DOM
→ Web Worker

дорогой layout или paint
→ browser rendering optimization

медленный backend
→ server и network optimization
```

Инструменты не взаимозаменяемы.

Перед выбором записывают пользовательский сценарий и определяют медленную фазу.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что проверяют |
| --- | --- |
| Таблица из тысяч строк тормозит при прокрутке | Размер DOM, виртуализацию, стоимость строки, layout и paint |
| Каждый ввод в поле обновляет большую страницу | Расположение state, component boundaries, context и transition |
| Компонент с `memo` продолжает рендериться | Новые ссылки в props, собственный state и читаемый context |
| `useMemo` пересчитывается каждый раз | Нестабильную dependency и полноту массива зависимостей |
| Фильтрация большого массива блокирует ввод | Алгоритм, debounce, transition, server или Web Worker |
| После клика долго не появляется результат | Input delay, handler, React render, commit, layout и paint |
| Строки списка теряют state после сортировки | Нестабильные или позиционные keys |
| Context обновляет всю страницу | Размер Provider, состав value и границы Context |
| Development показывает множество render | Strict Mode и проверку production build |
| React Profiler быстрый, но интерфейс тормозит | Chrome Performance, layout, paint и third-party scripts |
| Dialog впервые открывается медленно | Lazy chunk, mount cost и тяжёлые Effects |
| После часа работы интерфейс замедляется | Растущие subscriptions, DOM, timers и memory |
