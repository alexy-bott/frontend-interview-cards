## Вопрос

<br>

 💬 **Как находить и устранять проблемы производительности в React? Когда нужны `memo`, `useMemo`, `useCallback` и виртуализация списков?**

<h2></h2>

<br>
<dl>
<dd>

Оптимизацию React начинают с конкретного медленного сценария и измерений. Большое число повторных render само по себе не доказывает проблему: пересчет небольшого компонента может быть дешевым, а задержка может находиться в обработчике события, layout браузера, сетевом запросе или стороннем скрипте.

Обновление интерфейса в React проходит две основные фазы:

1. **Render**: React вызывает компоненты и вычисляет новое дерево элементов. Эта фаза должна оставаться чистой: одинаковые props, state и context должны давать одинаковый результат без побочных эффектов.
2. **Commit**: React применяет необходимые изменения к DOM, обновляет ref и запускает соответствующие эффекты. После этого браузер может выполнить layout, paint и composite, то есть рассчитать геометрию, нарисовать изменившиеся пиксели и собрать итоговый кадр.

Props - данные, полученные от родителя, state - собственное состояние компонента, а context - значение, получаемое от ближайшего Provider без передачи через каждый промежуточный компонент. Компонент может повторно рендериться из-за изменения собственного state, рендера родителя, изменения читаемого context или обновления внешнего хранилища, на которое он подписан. При этом повторный render не означает обязательного изменения DOM: React сравнивает прежний и новый результат и применяет только необходимые изменения.

`React.memo` позволяет пропустить render компонента, если его props не изменились. По умолчанию каждый prop сравнивается через `Object.is`. Поэтому новый объект, массив или функция считаются новым значением, даже если содержимое выглядит одинаково. `memo` полезен, когда компонент заметно дорогой, родитель обновляется часто, а props большую часть времени остаются прежними. Изменение собственного state или используемого context все равно вызовет render такого компонента.

`useMemo` сохраняет результат вычисления, а `useCallback` сохраняет саму функцию между render, пока не изменились зависимости. Они нужны не для каждого значения и обработчика, а для измеримо дорогого вычисления или стабильной ссылки, от которой зависит другая оптимизация. React рассматривает `useMemo` как оптимизацию производительности, а не как смысловую гарантию: корректность компонента не должна зависеть от сохранения кешированного значения.

Для диагностики React DevTools Profiler показывает, какие компоненты участвовали в commit и сколько занял их render. `actualDuration` отражает время текущего обновления, а `baseDuration` оценивает стоимость рендера всего поддерева без успешной мемоизации. Chrome DevTools Performance нужен дополнительно, чтобы увидеть обработчики событий, long tasks, layout, paint и остальную работу main thread.

Для очень длинных списков применяют **виртуализацию**: в DOM находятся только видимые элементы и небольшой запас вокруг них. Это уменьшает число компонентов и DOM-узлов, но усложняет работу с динамической высотой строк, прокруткой, фокусом, клавиатурной навигацией и доступностью. `useTransition` и `useDeferredValue` решают другую задачу: позволяют сделать часть обновления менее приоритетной, но не уменьшают объем вычислений сами по себе.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что такое rerender и всегда ли он приводит к изменению DOM?</strong></summary>

<dl>
<dd>
<h2></h2>

Rerender, или повторный render, означает, что React снова вызвал компонент для вычисления следующего состояния интерфейса. Затем React сопоставляет новый результат с предыдущим. Если отображаемые данные и структура не изменились, обновление DOM может не потребоваться. Поэтому искать нужно не любое повторное выполнение компонента, а частые или дорогие render, которые создают заметную задержку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Из-за чего компонент повторно рендерится?</strong></summary>

<dl>
<dd>
<h2></h2>

Основные причины: изменение собственного state; render родителя; изменение значения context, которое компонент читает; обновление внешнего хранилища по подписке. Render родителя обычно приводит к render его дочерних компонентов, если React не может пропустить их благодаря `memo` или уже подготовленному элементу. Изменение `ref.current` само по себе render не запускает.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем render отличается от commit?</strong></summary>

<dl>
<dd>
<h2></h2>

Во время render React вычисляет, каким должен стать интерфейс. Во время commit он применяет рассчитанные изменения к DOM. Дорогим может оказаться любой этап: вычисление большого дерева компонентов, синхронная работа `useLayoutEffect` перед отображением кадра, многочисленные DOM-изменения или последующие layout и paint браузера. Поэтому React Profiler и браузерный Performance panel отвечают на разные части одного расследования.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда <code>React.memo</code> действительно помогает?</strong></summary>

<dl>
<dd>
<h2></h2>

Он помогает, если родитель обновляется часто, props дочернего компонента обычно не меняются, а его render достаточно дорогой. Если компонент дешевый или каждый раз получает новые объекты и функции, сравнение props и поддержка мемоизации могут не дать выигрыша. Решение проверяют по замерам Profiler, а не по числу компонентов, обернутых в `memo`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему компонент в <code>memo</code> все равно может рендериться?</strong></summary>

<dl>
<dd>
<h2></h2>

`memo` сравнивает только props. Компонент все равно обновится при изменении собственного state или context, который он читает. Кроме того, `{}`, `[]` и стрелочная функция создают новые ссылки при каждом render родителя, поэтому поверхностное сравнение обнаружит изменение соответствующего prop.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означает поверхностное сравнение props в <code>memo</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

React сравнивает каждый prop с предыдущим через `Object.is`, не обходя поля вложенных объектов. Две отдельные переменные `{ id: 1 }` считаются разными объектами, потому что у них разные ссылки. Это сравнение дешевое, но требует сохранять стабильные ссылки там, где от них действительно зависит оптимизация.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужен <code>useMemo</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Первый случай: чистое вычисление заметно дорогое, например сортировка большого массива, и его входные данные меняются редко. Второй: нужна стабильная ссылка на объект или массив, передаваемый в мемоизированный компонент. Для дешевой арифметики и простого доступа к полю `useMemo` обычно добавляет зависимости и расход памяти без полезного выигрыша.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужен <code>useCallback</code> и ускоряет ли он функцию?</strong></summary>

<dl>
<dd>
<h2></h2>

`useCallback` не ускоряет выполнение функции. Он возвращает ту же ссылку на функцию между render, пока не изменились зависимости. Это полезно, когда функция передается в компонент с `memo`, входит в зависимости другого Hook или используется API, для которого важна идентичность обработчика. Hook - функция React вроде `useEffect` или `useMemo`, которая подключает возможность React к компоненту. Без потребителя стабильной ссылки `useCallback` обычно ничего не улучшает.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем опасна собственная функция сравнения в <code>memo</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Она сама выполняется при обновлении и может оказаться дороже render компонента. Кроме того, необходимо корректно сравнить каждый prop, включая функции. Если считать изменившуюся функцию прежней, компонент может продолжить использовать замыкание со старыми props или state. Пользовательская проверка оправдана только после измерения и при понятном контракте данных.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что показывают <code>actualDuration</code> и <code>baseDuration</code> в Profiler?</strong></summary>

<dl>
<dd>
<h2></h2>

`actualDuration` показывает, сколько времени React потратил на render поддерева в конкретном commit с учетом сработавшей мемоизации. `baseDuration` оценивает стоимость рендера всего поддерева без пропущенных вычислений. Снижение `actualDuration` относительно `baseDuration` может показывать пользу мемоизации, но итоговую задержку все равно нужно сопоставить с полной записью в Chrome Performance.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как уменьшить обновления большого context?</strong></summary>

<dl>
<dd>
<h2></h2>

Значение context сравнивается по ссылке, поэтому новый объект провайдера уведомляет всех потребителей этого context. Обычно state располагают ближе к использующим его компонентам, разделяют независимые данные на несколько context и стабилизируют значение провайдера, если это подтверждено измерениями. Внешнее хранилище с selectors, то есть функциями выбора данных, позволяет компоненту подписаться на конкретный фрагмент состояния, а не на весь объект.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Отменяет ли React Compiler ручные <code>memo</code>, <code>useMemo</code> и <code>useCallback</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

React Compiler - отдельный build-time инструмент, который анализирует компоненты и автоматически добавляет мемоизацию там, где считает ее полезной. Он поддерживает React 17, 18 и 19, но для React 17/18 требуется дополнительный `react-compiler-runtime`; наличие React 19 само по себе также не означает, что Compiler включен в сборку.

В проекте с настроенным Compiler новый код обычно сначала доверяют автоматической мемоизации, а ручные Hooks оставляют для точного контроля. Существующую мемоизацию не удаляют механически: это может изменить результат компиляции и требует тестов и профилирования. Для Next.js встроенная интеграция через SWC доступна начиная с Next.js 15.3.1, поэтому к проекту на Next.js 14 ее нельзя относить как включенную возможность версии.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Ускоряют ли <code>useTransition</code> и <code>useDeferredValue</code> вычисления?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Они меняют приоритет обновления: срочное обновление, например ввод символа, может отобразиться раньше, а тяжелая часть интерфейса будет рассчитана позже и может быть прервана новым срочным обновлением. Если само вычисление слишком тяжелое, дополнительно нужны уменьшение объема работы, серверная обработка, виртуализация или Web Worker.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужна виртуализация списка и какие у нее ограничения?</strong></summary>

<dl>
<dd>
<h2></h2>

Она нужна, когда большое число одновременно созданных компонентов и DOM-узлов делает render, layout или прокрутку дорогими. В DOM оставляют видимое окно и несколько элементов вокруг него. При внедрении нужно проверить измерение динамической высоты, сохранение позиции прокрутки, поиск по странице, фокус при управлении с клавиатуры, чтение screen reader, то есть программы экранного доступа, и серверный render. Для короткого списка эта сложность обычно неоправданна.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как последовательно расследовать медленное обновление React-интерфейса?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала фиксируют конкретное действие и воспроизводимые условия. Затем React Profiler показывает дорогие компоненты и причины их render. Chrome Performance помогает проверить обработчик события, long tasks, layout и paint. После этого изменяют одну предполагаемую причину, повторяют тот же сценарий и сравнивают время и пользовательскую метрику. Так оптимизация связывается с измеримым результатом, а не с предположением.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что проверяют |
| --- | --- |
| Таблица из тысяч строк тормозит при прокрутке | Размер DOM, виртуализацию, стоимость строки, layout и paint |
| Каждый ввод в поле обновляет большую страницу | Расположение state, границы компонентов, context и приоритет обновления |
| Компонент с `memo` продолжает рендериться | Новые ссылки в props, собственный state и используемый context |
| Фильтрация большого массива блокирует ввод | Стоимость вычисления, debounce после паузы ввода, серверную фильтрацию или Web Worker |
| После клика долго не появляется результат | Обработчик, React render и commit, layout, paint и long tasks |
