## Вопрос

Что выполняется на main thread браузера, почему возникают long tasks и когда вычисления стоит переносить в Web Worker?

<details>
<summary><strong>Показать ответ</strong></summary>

**Main thread**, или главный поток страницы, выполняет JavaScript, обрабатывает пользовательские события, строит DOM, рассчитывает стили и layout, а также подготавливает команды для отрисовки. Современный браузер использует и другие потоки: raster threads превращают команды рисования в пиксели, а compositor thread собирает слои в итоговый кадр. Но JavaScript страницы и большая часть работы с DOM остаются на main thread.

Event loop передает main thread задачи: выполнение скрипта, обработчик клика, callback таймера, то есть функцию, вызванную после срабатывания таймера, и другие. Пока одна задача не завершится, следующая не начнется. Microtasks, или микрозадачи, в том числе обработчики Promise, выполняются после текущей задачи до перехода к следующей, поэтому длинная цепочка microtasks тоже может задержать ввод и новый кадр.

**Long task** - задача на main thread длительностью не менее 50 мс. Все время сверх первых 50 мс называют blocking duration, то есть блокирующей частью задачи. Пока такая задача выполняется, браузер не может своевременно запустить другой JavaScript-обработчик на main thread. Это увеличивает задержку взаимодействия и может ухудшить INP. Частые причины: тяжелый цикл, синхронный разбор большого JSON, дорогое преобразование данных, чрезмерный React render, layout thrashing и сторонний скрипт.

Сначала объем работы уменьшают, затем при необходимости делят ее на части и добровольно уступают main thread между частями. Благодаря этому браузер получает возможность обработать пользовательский ввод и отрисовать кадр. Однако дробление не сокращает общее число вычислений и может увеличить их суммарное время.

**Web Worker** запускает JavaScript в отдельном потоке и отдельном глобальном окружении. Обычный Dedicated Worker принадлежит создавшей его странице. У него нет прямого доступа к DOM, но доступны многие API для вычислений и работы с данными, например `fetch`, таймеры, Web Crypto и WebAssembly. Main thread и Worker обмениваются сообщениями через `postMessage`.

По умолчанию данные сообщения копируются алгоритмом **structured clone**, который умеет переносить многие встроенные структуры и циклические ссылки, но не копирует функции и DOM-узлы. Большой `ArrayBuffer` можно передать как **transferable object**: владение буфером перемещается без копирования его содержимого, а исходный буфер становится недоступен. Передача и сериализация данных тоже имеют стоимость, поэтому Worker особенно полезен для достаточно крупных независимых вычислений, а не для множества мелких операций.

Worker не может напрямую обновить интерфейс. Он вычисляет результат и отправляет его main thread, который меняет state приложения или DOM. Для реального проекта также нужны обработка ошибок, идентификатор запроса, отмена устаревшей работы и завершение Worker через `terminate`, когда он больше не нужен.

```js
const worker = new Worker(new URL('./filter.worker.js', import.meta.url), {
  type: 'module',
});

worker.postMessage({ requestId: 1, rows, query });

worker.addEventListener('message', ({ data }) => {
  if (data.requestId === 1) {
    showResult(data.filteredRows);
  }
});
```

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Что именно main thread делает при работе страницы?</summary>

Он выполняет JavaScript страницы, обрабатывает события, разбирает HTML, изменяет DOM, рассчитывает CSS-стили и layout и создает команды рисования. Часть последующей работы браузер способен передать другим потокам: raster threads превращают команды рисования в пиксели, а compositor thread собирает слои в кадр. Поэтому main thread не выполняет буквально всю отрисовку, но его длительная занятость часто задерживает и обработку ввода, и подготовку нового кадра.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем задача event loop отличается от microtask?</summary>

Задачей может быть выполнение скрипта, callback таймера или обработчик события. После завершения текущей задачи браузер очищает очередь microtasks, куда попадают, например, обработчики Promise и функция, переданная в `queueMicrotask`. Только затем браузер получает возможность перейти к следующей задаче и обычно рассмотреть отрисовку. Поэтому рекурсивно добавляемые microtasks способны надолго занять main thread, хотя каждая из них короткая.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему граница long task равна 50 мс и что такое blocking duration?</summary>

Long Tasks API отмечает задачу, занявшую не менее 50 мс. Блокирующей частью считается время после первых 50 мс: у задачи длительностью 120 мс это 70 мс. Порог не означает, что задача в 49 мс безвредна, особенно если она попала между вводом пользователя и следующим кадром. Это диагностическая граница для поиска крупных блоков работы.

</details>

<details>
<summary><strong>Вопрос:</strong> Как long task влияет на INP?</summary>

Если взаимодействие происходит, когда main thread занят, обработчик не может начаться сразу: растет input delay, то есть задержка до выполнения обработчика. Сам обработчик также может стать long task и увеличить длительность обработки (processing duration). Наконец, синхронный render или layout после обработчика увеличивает задержку отображения (presentation delay) до следующего кадра. Поэтому для плохого INP важно определить, на какой из трех фаз возникла задержка.

</details>

<details>
<summary><strong>Вопрос:</strong> Как найти long tasks?</summary>

В Chrome DevTools Performance длинные задачи отмечаются на дорожке Main, а красный угол указывает на long task. Flame chart, или временная диаграмма стека вызовов, показывает, какие функции заняли время. В коде `PerformanceObserver` может получать записи типа `longtask`, если этот тип поддерживается браузером. Для взаимодействий дополнительно полезны сведения о причине INP и Long Animation Frames API, которые связывают задержку с обработчиками и кадрами.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем Web Worker отличается от <code>Promise</code> или <code>async/await</code>?</summary>

`Promise` и `async/await` организуют асинхронное продолжение кода, но сами по себе не переносят JavaScript-вычисление с main thread. Если после `await` запустить тяжелый цикл, он по-прежнему заблокирует страницу. Worker действительно выполняет JavaScript в другом потоке, поэтому подходит для CPU-bound работы, то есть вычислений, скорость которых ограничена процессором.

</details>

<details>
<summary><strong>Вопрос:</strong> Какие задачи подходят для Web Worker?</summary>

Независимые и достаточно тяжелые вычисления: разбор большого CSV, агрегация и фильтрация больших наборов данных, обработка изображений, сжатие, криптография, геометрические расчеты или запуск WebAssembly. Плохие кандидаты - маленькие операции, задачи с постоянным доступом к DOM и сценарии, где стоимость передачи данных выше самого вычисления.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему Worker не имеет доступа к DOM?</summary>

DOM страницы принадлежит main thread и не является потокобезопасной общей структурой. Worker работает в отдельном глобальном окружении `WorkerGlobalScope`. Он отправляет результат сообщением, а main thread решает, как изменить state или DOM. Такой контракт предотвращает одновременное несогласованное изменение одного DOM-дерева из разных потоков.

</details>

<details>
<summary><strong>Вопрос:</strong> Что делает structured clone и какие у него ограничения?</summary>

Алгоритм structured clone создает независимую копию передаваемого значения. Он поддерживает объекты, массивы, `Map`, `Set`, `Date`, типизированные массивы и циклические ссылки. Функции и DOM-узлы клонировать нельзя, прототипы пользовательских классов и некоторые свойства могут не сохраниться как у исходного объекта. Копирование большого графа данных расходует время и память на обеих сторонах.

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое transferable object?</summary>

Это объект, внутренний ресурс которого можно передать другому контексту без копирования содержимого. Частый пример - `ArrayBuffer`. Его указывают во втором аргументе `postMessage`; после передачи исходный буфер становится detached, то есть его память больше недоступна отправителю. Такой способ снижает стоимость передачи больших бинарных данных, но требует явно учитывать смену владельца.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем Dedicated Worker, Shared Worker и Service Worker отличаются друг от друга?</summary>

Dedicated Worker связан с одной создающей страницей и обычно используется для ее вычислений. Shared Worker может обслуживать несколько вкладок одного origin, то есть источника с одинаковыми scheme, host и port, через отдельные порты связи, но поддержка и применение у него уже. Service Worker работает как событийный посредник между приложением и сетью: поддерживает offline-кеш, перехват запросов и push-уведомления, но не предназначен как постоянно работающий вычислительный поток страницы.

</details>

<details>
<summary><strong>Вопрос:</strong> Как разделить тяжелую работу, если Worker использовать нельзя?</summary>

Вычисление делят на небольшие части и между ними уступают управление браузеру, например через подходящий scheduling API, то есть API планирования задач, или следующую задачу event loop. Размер части выбирают по профилю, чтобы обработка ввода не ждала длинного блока. Для визуальной работы вычисления можно распределять по кадрам. Очередь microtasks для уступки отрисовке не подходит: браузер очищает ее до перехода к следующей задаче.

</details>

<details>
<summary><strong>Вопрос:</strong> Какие расходы и ошибки нужно учитывать при использовании Worker?</summary>

Создание Worker и загрузка его модуля занимают время, сообщения могут копировать большие данные, а результат все равно нужно применить на main thread. Возможны ответы не по порядку, устаревший результат после нового запроса и утечка работающего Worker после ухода со страницы. Поэтому сообщения снабжают идентификаторами, устаревшую работу отменяют или игнорируют, ошибки обрабатывают, а ненужный Worker завершают.

</details>

## Где это встречается во frontend

| Ситуация | Подход |
| --- | --- |
| Разбор большого CSV блокирует форму | Парсить данные в Worker и отправлять промежуточный прогресс |
| Фильтрация сотен тысяч записей задерживает ввод | Уменьшить данные, проверить серверную фильтрацию, затем рассмотреть Worker |
| Сторонний скрипт создает long tasks | Отложить загрузку, сократить функциональность или изолировать влияние поставщика |
| Длинный обработчик клика ухудшает INP | Найти медленную фазу, уменьшить или разделить синхронную работу |
| Worker передает большой бинарный файл | Использовать transferable `ArrayBuffer`, если отправителю буфер больше не нужен |
