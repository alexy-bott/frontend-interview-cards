## Вопрос

<br>

 💬 **Как изображения, шрифты и приоритет ресурсов влияют на LCP, CLS и загрузку страницы?**

<h2></h2>

<br>
<dl>
<dd>

Изображения часто составляют значительную часть передаваемых данных и становятся LCP-элементом. Шрифты влияют на момент появления текста, его размеры и переносы строк. Неправильная загрузка этих ресурсов способна одновременно ухудшить LCP, CLS и конкуренцию за сеть.

Оптимизация состоит не в выборе одного формата или атрибута, а в нескольких связанных задачах:

```text
выбрать подходящий ресурс
→ зарезервировать его место
→ сделать критичный URL обнаружимым
→ назначить разумный приоритет
→ не загружать второстепенное слишком рано
→ проверить фактический результат
```

Для изображения проверяют:

1. **Размер в layout:** `width`/`height` или `aspect-ratio` резервируют место и защищают от CLS.
2. **Фактический размер файла:** браузер не должен скачивать изображение шириной 3000 пикселей для карточки шириной 300 CSS-пикселей.
3. **Плотность экрана:** устройству с device pixel ratio `2` для блока шириной `300 CSS px` может понадобиться файл около `600` физических пикселей, а не ровно `300`.
4. **Формат и качество:** WebP или AVIF часто уменьшают размер фотографий, но результат зависит от конкретного изображения, качества кодирования и инфраструктуры.
5. **Адаптивный источник:** `srcset` предлагает варианты, а `sizes` сообщает ожидаемую ширину места под изображение.
6. **Момент обнаружения:** LCP-изображение должно быть известно браузеру как можно раньше.
7. **Момент загрузки:** некритичные изображения можно загружать лениво, но LCP-кандидат откладывать нельзя.
8. **Приоритет:** `fetchpriority`, preload и обычное планирование браузера применяют точечно.
9. **Отображение:** уже загруженное изображение не улучшит LCP, если JavaScript, CSS или hydration продолжают скрывать элемент.

`width` и `height` у `<img>` задают intrinsic-размер и соотношение сторон:

```html
<img
  src="product.webp"
  width="800"
  height="600"
  alt="Красное кресло"
>
```

Браузер может зарезервировать место с пропорцией:

```text
800 / 600
→ 4 / 3
```

ещё до загрузки файла.

CSS при этом может изменить визуальную ширину:

```css
img {
  width: 100%;
  height: auto;
}
```

Атрибуты не обязаны фиксировать изображение на `800 × 600 CSS px`. Они сообщают исходные пропорции, а итоговый размер определяет layout.

Если изображение должно заполнять контейнер с обрезкой, геометрию резервируют на контейнере:

```css
.image-container {
  aspect-ratio: 4 / 3;
  overflow: hidden;
}

.image-container img {
  width: 100%;
  height: 100%;
  object-fit: cover;
}
```

Само `object-fit` не создаёт размеры контейнера и не предотвращает CLS, если место заранее неизвестно.

Адаптивные изображения позволяют браузеру выбрать подходящий файл:

```html
<img
  src="product-800.webp"
  srcset="
    product-400.webp 400w,
    product-800.webp 800w,
    product-1200.webp 1200w
  "
  sizes="(max-width: 640px) 100vw, 50vw"
  width="800"
  height="600"
  alt="Красное кресло"
>
```

`srcset` с дескрипторами `w` сообщает исходную ширину каждого доступного файла:

```text
product-400.webp
→ 400 физических пикселей

product-800.webp
→ 800 физических пикселей
```

`sizes` сообщает предполагаемую ширину image slot в layout:

```text
до 640 px viewport
→ примерно 100vw

на более широком viewport
→ примерно 50vw
```

Браузер учитывает:

- `sizes`;
- ширину viewport;
- device pixel ratio;
- доступные кандидаты;
- собственные сетевые и cache-эвристики.

Разработчик не выбирает конкретный файл через JavaScript. Фактически выбранный URL доступен через:

```js
image.currentSrc;
```

Если `sizes` ошибочно сообщает `100vw`, хотя карточка занимает `33vw`, браузер может скачать значительно более крупный файл.

Для фиксированного изображения с дескрипторами плотности можно использовать:

```html
<img
  src="avatar.png"
  srcset="
    avatar.png 1x,
    avatar@2x.png 2x
  "
  width="48"
  height="48"
  alt="Аватар пользователя"
>
```

Но для адаптивных grid и card layouts обычно удобнее `w`-дескрипторы вместе с `sizes`.

`<picture>` применяют, когда одного набора разрешений недостаточно:

```html
<picture>
  <source
    media="(max-width: 640px)"
    srcset="hero-mobile.avif"
    type="image/avif"
  >

  <source
    media="(max-width: 640px)"
    srcset="hero-mobile.webp"
    type="image/webp"
  >

  <source
    srcset="hero-desktop.avif"
    type="image/avif"
  >

  <img
    src="hero-desktop.jpg"
    width="1600"
    height="900"
    alt="Команда работает в офисе"
  >
</picture>
```

У `<picture>` две основные задачи:

```text
art direction
→ другая композиция или обрезка

format selection
→ другой codec для поддерживающего браузера
```

Для обычного изменения разрешения одного изображения достаточно `srcset` и `sizes`.

`<img>` внутри `<picture>` остаётся обязательным:

- является fallback;
- содержит `alt`;
- задаёт intrinsic-размер;
- участвует в layout;
- является фактическим image element.

Выбор формата выполняют по реальным данным.

AVIF часто даёт меньший файл для фотографий, но:

- кодирование может быть дороже;
- выигрыш зависит от изображения;
- при одинаковом числовом quality визуальное качество разных codec несопоставимо напрямую;
- инфраструктура может хранить отдельные варианты для разных форматов;
- небольшое изображение иногда почти не выигрывает относительно WebP.

SVG подходит для:

- иконок;
- логотипов;
- простых схем;
- векторной графики.

Но SVG не является автоматически лёгким: сложный файл может содержать большое число paths, filters, embedded raster images или script.

PNG нужен, когда важны:

- lossless-данные;
- прозрачность;
- пиксельная графика;
- интерфейсные изображения, плохо переносящие lossy compression.

Для фотографии PNG обычно значительно тяжелее подходящего JPEG, WebP или AVIF.

`loading="lazy"` откладывает загрузку изображения, пока оно не приблизится к viewport:

```html
<img
  src="gallery-42.webp"
  loading="lazy"
  width="800"
  height="600"
  alt="Фотография товара"
>
```

Точное расстояние, на котором браузер начинает загрузку, не стандартизировано как фиксированное число для приложения. Оно зависит от браузера, сети и его эвристик.

Поэтому нельзя рассчитывать:

```text
lazy image всегда начнёт загружаться
ровно за 300 px до viewport
```

Lazy loading полезен для:

- длинных страниц;
- галерей;
- карточек ниже первого экрана;
- iframe вне viewport;
- изображений с небольшой вероятностью просмотра.

Он уменьшает:

- initial network traffic;
- конкуренцию за bandwidth;
- декодирование невидимых изображений;
- использование памяти.

Для вероятного LCP-кандидата `loading="lazy"` обычно является ошибкой:

```text
LCP-изображение уже нужно
→ lazy откладывает запрос
→ растёт resource load delay
→ LCP ухудшается
```

У критичного изображения обычно:

- отсутствует `loading="lazy"`;
- URL находится в первоначальном HTML;
- указан корректный `src` или `srcset`;
- при необходимости используется `fetchpriority="high"`;
- preload применяется только при позднем естественном обнаружении.

Для оптимизации LCP нужно разделять этапы:

```text
1. Browser узнал URL.
2. Browser назначил запросу приоритет.
3. Ресурс загрузился.
4. Ресурс декодирован.
5. Элемент отобразился.
```

Проблемы на этих этапах требуют разных решений.

| Проблема | Возможное направление |
|---|---|
| URL обнаружен поздно | HTML, preload, отказ от client-only создания |
| URL обнаружен рано, но приоритет низкий | `fetchpriority="high"` |
| Передача долгая | Размер, формат, CDN, responsive image |
| Ресурс загружен, но не отображён | JavaScript, CSS, hydration, decode, layout |
| Другие ресурсы конкурируют с LCP | Убрать лишний preload и eager loading |

Основные механизмы загрузки отличаются:

| Механизм | Что делает |
|---|---|
| Обычный `<img>` в HTML | Делает URL обнаружимым preload scanner |
| `loading="lazy"` | Разрешает отложить загрузку |
| `loading="eager"` | Запрещает lazy loading |
| `fetchpriority="high"` | Даёт браузеру подсказку повысить приоритет |
| `<link rel="preload">` | Объявляет ресурс в `<head>` для раннего запроса |
| `preconnect` | Заранее устанавливает соединение с внешним origin |

`loading="eager"` не означает:

```text
загрузить с максимальным приоритетом
```

Он означает:

```text
не откладывать как lazy resource
```

`fetchpriority="high"` не обнаруживает URL раньше:

```html
<img
  src="hero.webp"
  fetchpriority="high"
  alt="..."
>
```

Сначала браузер должен увидеть сам `<img>`.

`fetchpriority` является подсказкой, а окончательное внутреннее планирование остаётся за браузером.

Preload объявляет ресурс раньше:

```html
<link
  rel="preload"
  as="image"
  href="/hero.webp"
  fetchpriority="high"
>
```

Он особенно полезен, когда критичное изображение иначе обнаруживается поздно:

- находится в CSS `background-image`;
- добавляется JavaScript;
- находится за зависимым запросом;
- появляется в позднем HTML-фрагменте;
- определяется slideshow до выполнения его script.

Если обычный `<img>` уже находится в раннем HTML, preload может не дать пользы и только продублировать подсказку браузеру.

Для CSS background:

```css
.hero {
  background-image:
    url("/hero.webp");
}
```

естественная цепочка выглядит так:

```text
HTML
→ stylesheet
→ загрузка CSS
→ parsing CSS
→ обнаружение background image
```

Точечный preload может сократить задержку:

```html
<link
  rel="preload"
  as="image"
  href="/hero.webp"
  fetchpriority="high"
>
```

Но если изображение несёт смысловой контент, обычный `<img>` часто лучше:

- URL обнаруживается непосредственно в HTML;
- доступен `alt`;
- проще responsive loading;
- яснее intrinsic-размер;
- легче анализировать LCP.

Для responsive image preload должен использовать ту же логику выбора:

```html
<link
  rel="preload"
  as="image"
  href="hero-800.webp"
  imagesrcset="
    hero-400.webp 400w,
    hero-800.webp 800w,
    hero-1600.webp 1600w
  "
  imagesizes="100vw"
  fetchpriority="high"
>
```

Последующий `<img>` должен быть согласован:

```html
<img
  src="hero-800.webp"
  srcset="
    hero-400.webp 400w,
    hero-800.webp 800w,
    hero-1600.webp 1600w
  "
  sizes="100vw"
  width="1600"
  height="900"
  alt="..."
>
```

Если preload содержит только один фиксированный файл, а `<img>` выбирает другой responsive candidate, браузер может скачать оба.

Preload-запрос должен совпадать с последующим использованием по важным параметрам:

- URL;
- resource destination через `as`;
- CORS mode;
- credentials mode;
- responsive candidate;
- `type`, если он указан;
- media condition.

Иначе ответ может не переиспользоваться.

В DevTools проверяют:

```text
ресурс загружен один раз

Initiator соответствует preload

последующий request использовал cache

нет предупреждения unused preload
```

Большое количество preload вредно.

Каждый такой ресурс начинает конкурировать с:

- render-blocking CSS;
- шрифтами;
- LCP-изображением;
- JavaScript;
- HTML;
- другими сетевыми запросами.

Preload является инструментом исправления конкретного позднего обнаружения, а не списком всех ресурсов страницы.

`fetchpriority="low"` также может быть полезен для некритичного ресурса, который браузер иначе загрузил бы слишком активно:

```html
<img
  src="/carousel-next.webp"
  fetchpriority="low"
  width="800"
  height="600"
  alt=""
>
```

Но сначала следует проверить фактическую конкуренцию в Network panel.

`preconnect` заранее выполняет часть работы для внешнего origin:

```html
<link
  rel="preconnect"
  href="https://images.example.com"
  crossorigin
>
```

Он может заранее подготовить:

- DNS;
- TCP или QUIC;
- TLS.

Это полезно, если критический ресурс точно будет загружен с другого origin.

Но preconnect также расходует sockets и CPU, поэтому его используют для небольшого числа действительно важных origins.

Если соединение лишь возможно, более дешёвой подсказкой является:

```html
<link
  rel="dns-prefetch"
  href="//images.example.com"
>
```

Resource hints не исправляют:

- слишком большой файл;
- позднее появление `<img>`;
- плохой `sizes`;
- долгий element render delay.

Для шрифтов загрузочная цепочка часто выглядит так:

```text
HTML
→ stylesheet
→ CSSOM
→ style calculation
→ браузер понял,
  какой font-face нужен
→ запрос font file
```

Поэтому font-файл может обнаруживаться позже изображения, URL которого находится прямо в HTML.

Основные задачи оптимизации шрифтов:

1. Использовать современный формат WOFF2.
2. Загружать только необходимые families, weights и styles.
3. Применять subsetting.
4. Выбирать подходящий `font-display`.
5. Подбирать близкий fallback.
6. При необходимости корректировать fallback metrics.
7. Preload только действительно критичных файлов.
8. Не подключать декоративный шрифт глобально, если он используется на одной странице.

Пример:

```css
@font-face {
  font-family: "App Sans";
  src:
    url("/fonts/app-sans-regular.woff2")
    format("woff2");
  font-weight: 400;
  font-style: normal;
  font-display: swap;
}
```

FOIT и FOUT описывают разные стратегии ожидания.

**FOIT, Flash of Invisible Text:**

```text
web-font не готов
→ browser временно показывает
  невидимый fallback
```

Пользователь видит пустое место вместо текста.

**FOUT, Flash of Unstyled Text:**

```text
сначала видимый fallback
→ затем web-font
```

Текст доступен раньше, но после замены могут измениться:

- ширина символов;
- перенос строк;
- высота line box;
- положение соседних элементов.

`font-display` управляет периодами block, swap и failure.

| Значение | Общая стратегия |
|---|---|
| `auto` | Поведение выбирает браузер |
| `block` | Короткий период невидимого текста и длительная возможность замены |
| `swap` | Почти сразу показать fallback и заменить позже |
| `fallback` | Короткий block и ограниченный период замены |
| `optional` | Короткий block и возможность вообще не заменять fallback |

Точная длительность внутренних периодов определяется браузером.

Для основного текста часто рассматривают:

```text
swap
→ текст виден быстро,
  но возможна поздняя замена

optional
→ меньше риска поздней замены,
  но web-font может не примениться
```

`block` редко подходит для основного содержимого, потому что способен задержать видимость текста.

Выбор зависит от роли шрифта.

Например:

```text
body text
→ важнее ранняя читаемость

короткий логотип или display heading
→ бренд может требовать web-font
```

Шрифт может влиять и на LCP.

Если LCP-элемент является текстовым блоком, его позднее отображение может быть связано с:

- render-blocking CSS;
- font block period;
- поздним font request;
- большим font-файлом;
- client-only render.

При `font-display: swap` текст обычно появляется через fallback раньше, но поздняя замена может создать CLS.

При `font-display: optional` браузер может оставить fallback для текущего посещения, если web-font не успел загрузиться достаточно рано.

Preload font-файла выглядит так:

```html
<link
  rel="preload"
  href="/fonts/app-sans-regular.woff2"
  as="font"
  type="font/woff2"
  crossorigin
>
```

Для переиспользования preload должны совпасть:

- точный URL;
- `as="font"`;
- CORS mode;
- credentials;
- фактический font-файл.

Font fetch обычно использует CORS-режим, поэтому preload задают с совместимым `crossorigin`, в том числе для типичного same-origin font preload.

Preload оправдан, если шрифт:

- точно используется на первом экране;
- влияет на LCP или раннюю читаемость;
- иначе обнаруживается поздно через CSS;
- не имеет более дешёвой альтернативы.

Не следует preloading:

- все веса;
- все italic-варианты;
- все subsets;
- шрифты нижней части страницы;
- шрифты редкого Dialog;
- файлы, которые могут не понадобиться.

Preload конкретного font-файла запускает его напрямую и не ждёт выбора через `unicode-range`.

Поэтому при нескольких subsets:

```css
@font-face {
  font-family: "App Sans";
  src:
    url("/fonts/app-sans-latin.woff2")
    format("woff2");
  unicode-range:
    U+0000-00FF;
}

@font-face {
  font-family: "App Sans";
  src:
    url("/fonts/app-sans-cyrillic.woff2")
    format("woff2");
  unicode-range:
    U+0400-04FF;
}
```

бездумный preload обоих файлов может загрузить subset, символов которого нет на странице.

Subsetting уменьшает font-файл, оставляя нужные глифы:

```text
latin
cyrillic
greek
CJK
```

Нужно учитывать:

- все локали приложения;
- пользовательские имена;
- числа;
- валюты;
- знаки пунктуации;
- специальные символы;
- emoji и fallback для них.

Если нужного глифа нет, браузер применит font fallback только для соответствующих символов.

Variable font объединяет диапазон параметров:

```text
weight 100–900
width
slant
другие axes
```

Он может быть выгоден, если приложение действительно использует много весов и стилей.

Если нужен только один regular и один bold, два отдельных WOFF2-файла иногда меньше одного полного variable font.

Сравнивают:

- transfer size;
- используемый диапазон axes;
- browser support целевой аудитории;
- стоимость subsetting;
- качество rendering.

Fallback-шрифт создаёт CLS, если его метрики заметно отличаются от web-font.

Например:

```text
fallback шире
→ строка переносится раньше

web-font загрузился
→ строка стала короче
→ блок изменил высоту
→ нижний контент сдвинулся
```

Для приближения fallback можно определить отдельный `@font-face`:

```css
@font-face {
  font-family:
    "App Sans Fallback";
  src:
    local("Arial");
  size-adjust:
    98%;
  ascent-override:
    92%;
  descent-override:
    24%;
  line-gap-override:
    0%;
}
```

Затем:

```css
body {
  font-family:
    "App Sans",
    "App Sans Fallback",
    sans-serif;
}
```

`size-adjust` масштабирует glyph outlines и связанные метрики.

Остальные descriptors корректируют:

- ascent;
- descent;
- line gap.

Значения получают из реальных метрик пары шрифтов. Случайные проценты могут сделать layout менее стабильным.

Даже при корректировке нужно тестировать:

- мобильную и desktop-ширину;
- крупные заголовки;
- длинные строки;
- кириллицу;
- цифры;
- разные font weights;
- пользовательский контент.

Ресурсы конкурируют не только по размеру, но и по времени обнаружения и приоритету.

Например:

```text
10 lazy images ниже viewport
→ обычно не мешают первому экрану

10 preload images
→ сразу конкурируют с CSS и LCP

1 большой font preload
→ может отложить LCP image

1 late CSS background
→ начинает загружаться слишком поздно
```

Приоритет браузера зависит от:

- типа ресурса;
- позиции в документе;
- способа обнаружения;
- render-blocking статуса;
- lazy loading;
- `fetchpriority`;
- preload;
- текущей сетевой конкуренции;
- реализации браузера.

Priority Hints не являются строгой очередью:

```text
high
→ подсказка браузеру,
  а не гарантия первого места
```

Для этого стека важна версия Next.js.

В Next.js 14 для вероятного LCP-изображения используется:

```tsx
<Image
  src="/hero.jpg"
  alt="..."
  width={1600}
  height={900}
  priority
/>
```

`priority` отключает lazy loading и позволяет Next.js применить ранние loading hints.

Для проекта на Next.js 14 это корректный API.

Начиная с Next.js 16 prop `priority` объявлен устаревшим в пользу более явного:

```tsx
<Image
  src="/hero.jpg"
  alt="..."
  width={1600}
  height={900}
  preload
/>
```

Текущая модель разделяет намерения:

```text
preload
→ создать <link> в head

loading="eager"
→ не откладывать загрузку

fetchPriority="high"
→ повысить приоритет img request
```

Не нужно механически задавать все три параметра одновременно.

В актуальном `next/image` preload не рекомендуется сочетать с `loading` или `fetchPriority`. В большинстве обычных случаев сначала рассматривают `loading="eager"` или `fetchPriority="high"`, а `preload` используют, когда изображение действительно должно начинать загрузку из `<head>`.

При разных LCP-кандидатах для mobile и desktop preload особенно опасен: браузер может начать загрузку нескольких изображений.

Для `next/image` с responsive layout важен `sizes`:

```tsx
<Image
  src={product.imageUrl}
  alt={product.name}
  fill
  sizes="
    (max-width: 768px) 100vw,
    33vw
  "
/>
```

Без корректного `sizes` браузер может выбрать слишком широкий вариант из сгенерированного `srcset`.

`next/font` автоматизирует часть font-оптимизации:

- self-hosting;
- создание `@font-face`;
- preload в области layout или page;
- fallback metrics;
- подключение через `className` или CSS variable.

Но он не может решить вместо разработчика:

- сколько families использовать;
- какие weights нужны;
- какие subsets покрывают контент;
- где подключать редкий декоративный шрифт;
- приемлема ли поздняя замена.

Диагностику начинают с конкретного симптома.

Для LCP-изображения:

```text
1. Найти фактический LCP-element.
2. Проверить URL ресурса.
3. Сравнить TTFB и начало image request.
4. Проверить request priority.
5. Проверить transfer size.
6. Проверить element render delay.
7. Посмотреть currentSrc и rendered size.
```

Для CLS изображения:

```text
1. Открыть Layout Shift entry.
2. Найти affected nodes.
3. Проверить width/height или aspect-ratio.
4. Проверить размер placeholder.
5. Проверить позднее изменение контейнера.
```

Для шрифта:

```text
1. Отфильтровать Font в Network.
2. Проверить момент обнаружения.
3. Проверить preload reuse.
4. Проверить число файлов.
5. Проверить font-display.
6. Сравнить fallback и web-font.
7. Проверить Layout Shift после swap.
```

Главный принцип:

```text
LCP
→ критичный ресурс должен
  обнаруживаться и загружаться рано

CLS
→ место и текстовая геометрия
  должны быть стабильны

общая загрузка
→ некритичные ресурсы
  не должны конкурировать
  с первым экраном
```

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Почему <code>width</code> и <code>height</code> уменьшают CLS, но не обязаны фиксировать визуальный размер?</strong></summary>

<dl>
<dd>
<h2></h2>

Атрибуты задают intrinsic-размер и соотношение сторон, по которому браузер резервирует место до загрузки файла.

```html
<img
  width="800"
  height="600"
>
```

создаёт пропорцию:

```text
4 / 3
```

CSS всё равно может сделать изображение адаптивным:

```css
img {
  width: 100%;
  height: auto;
}
```

Если пропорции атрибутов не совпадают с файлом или CSS независимо задаёт несовместимые ширину и высоту, изображение может исказиться или изменить layout.

Для обрезки используют контейнер с известным `aspect-ratio` и `object-fit`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как работают <code>srcset</code> и <code>sizes</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`srcset` перечисляет доступные файлы и их исходную ширину:

```html
srcset="
  image-400.webp 400w,
  image-800.webp 800w
"
```

`sizes` описывает ожидаемую ширину image slot в layout:

```html
sizes="
  (max-width: 640px) 100vw,
  50vw
"
```

Браузер учитывает:

- viewport;
- device pixel ratio;
- `sizes`;
- доступные кандидаты;
- cache и собственные эвристики.

Фактически выбранный URL можно проверить через:

```js
image.currentSrc;
```

Ошибочный `sizes` часто приводит к загрузке файла больше необходимого.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужен <code>&lt;picture&gt;</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`<picture>` используют для:

- art direction;
- выбора формата.

Art direction означает, что mobile и desktop получают не просто разные размеры, а другую композицию или обрезку.

```text
desktop
→ широкий кадр

mobile
→ вертикальная крупная область
```

Для обычного выбора разрешения одной фотографии достаточно `srcset` и `sizes`.

Внутренний `<img>` обязателен и остаётся владельцем `alt`, intrinsic-размера и fallback URL.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему нельзя загружать вероятное LCP-изображение через lazy loading?</strong></summary>

<dl>
<dd>
<h2></h2>

Lazy loading разрешает браузеру отложить image request до приближения элемента к viewport.

LCP-кандидат уже нужен на первом экране:

```text
lazy loading
→ позднее начало запроса
→ больший resource load delay
→ поздний LCP
```

Для него обычно:

- убирают `loading="lazy"`;
- делают URL обнаружимым в HTML;
- применяют корректный `srcset` и `sizes`;
- при необходимости используют `fetchpriority="high"`;
- preload добавляют только при позднем естественном обнаружении.

На разных viewport LCP-кандидатом могут быть разные элементы, поэтому результат проверяют отдельно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем preload отличается от <code>fetchpriority="high"</code> и <code>loading="eager"</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Preload объявляет ресурс в `<head>` и позволяет начать запрос раньше естественного обнаружения.

`fetchpriority="high"` сообщает браузеру, что уже обнаруженный запрос важнее других ресурсов того же типа.

`loading="eager"` запрещает отложить изображение через lazy loading.

```text
preload
→ раннее обнаружение

fetchpriority
→ сетевой приоритет

eager
→ не откладывать загрузку
```

Если `<img>` уже находится в раннем HTML, preload может быть лишним.

Для CSS background preload полезнее, потому что без него URL обнаруживается только после загрузки и разбора stylesheet.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как preload может вызвать двойную загрузку?</strong></summary>

<dl>
<dd>
<h2></h2>

Preload и последующее использование должны совпасть по:

- URL;
- `as`;
- CORS mode;
- credentials;
- типу ресурса;
- responsive candidate.

Для responsive image нужно согласовать:

```text
imagesrcset
imagesizes
```

с последующими:

```text
srcset
sizes
```

Если preload загрузил `hero-1600.webp`, а `<img>` выбрал `hero-800.webp`, браузер может получить оба файла.

В Network panel проверяют, что запрос один и ответ preload переиспользован.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что изменилось у <code>next/image</code> между Next.js 14 и 16?</strong></summary>

<dl>
<dd>
<h2></h2>

В Next.js 14 для вероятного LCP-изображения используется:

```tsx
priority
```

Он отключает lazy loading и позволяет Next.js применить ранние loading hints.

Начиная с Next.js 16 `priority` deprecated в пользу:

```tsx
preload
```

Актуальная модель различает:

```text
preload
loading
fetchPriority
```

Не нужно механически задавать все props одновременно.

Для проекта на Next.js 14 `priority` остаётся корректным API этой версии.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означают FOIT и FOUT?</strong></summary>

<dl>
<dd>
<h2></h2>

FOIT, Flash of Invisible Text:

```text
web-font загружается
→ текст временно невидим
```

FOUT, Flash of Unstyled Text:

```text
сначала fallback
→ затем web-font
```

FOIT ухудшает раннюю видимость текста.

FOUT показывает текст быстрее, но замена может изменить переносы строк и создать CLS.

`font-display` управляет этой стратегией.

Цель не всегда состоит в полном исключении FOUT: быстро видимый fallback часто лучше пустого текста, если его метрики близки к итоговому шрифту.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выбирать значение <code>font-display</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`swap` почти сразу показывает fallback и допускает позднюю замену.

`fallback` использует короткий block и ограниченный период замены.

`optional` позволяет браузеру не заменять fallback, если font не успел достаточно рано.

`block` допускает период невидимого текста и длительную возможность замены.

Для основного текста обычно важнее ранняя читаемость, поэтому чаще рассматривают `swap` или `optional`.

Решение проверяют по:

- FCP/LCP текста;
- CLS;
- скорости сети;
- повторному визиту;
- требованиям бренда.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда preload шрифта оправдан и зачем нужен <code>crossorigin</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Preload оправдан для небольшого числа font-файлов, которые:

- точно используются на первом экране;
- влияют на ранний текст;
- иначе обнаруживаются поздно через CSS.

```html
<link
  rel="preload"
  href="/fonts/app.woff2"
  as="font"
  type="font/woff2"
  crossorigin
>
```

Font request использует CORS-режим, поэтому preload должен быть совместим с последующим запросом.

Без совпадения browser может не переиспользовать ответ.

Preload всех weights и subsets создаёт конкуренцию с CSS и LCP-изображением.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое подмножество шрифта и <code>unicode-range</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Font subsetting оставляет в файле только нужные glyphs.

Например:

```text
Latin
Cyrillic
Greek
CJK
```

`unicode-range` сообщает, какие символы покрывает конкретный `@font-face`.

Браузер может загрузить только subset, необходимый для текста страницы.

Но прямой preload конкретного файла запускает его независимо от обычного выбора по `unicode-range`.

Поэтому preload всех subsets может уничтожить выгоду разделения.

Нужно учитывать локали и пользовательский контент, иначе часть символов отобразится другим fallback-шрифтом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как резервный шрифт создаёт CLS и как это уменьшить?</strong></summary>

<dl>
<dd>
<h2></h2>

У fallback и web-font отличаются:

- ширина glyphs;
- ascent;
- descent;
- line gap;
- переносы строк.

После замены меняются размеры текстового блока и положение соседнего контента.

Для уменьшения сдвига:

- выбирают похожий fallback;
- задают стабильный `line-height`;
- используют `size-adjust`;
- используют `ascent-override`;
- используют `descent-override`;
- используют `line-gap-override`.

Значения рассчитывают по реальным метрикам шрифтов и проверяют на разных строках и viewport.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли сжимать изображения gzip или Brotli?</strong></summary>

<dl>
<dd>
<h2></h2>

JPEG, PNG, WebP и AVIF уже используют собственное сжатие.

Дополнительный gzip или Brotli обычно почти не уменьшает их transfer size и только расходует CPU.

Изображения оптимизируют через:

- codec;
- размеры;
- quality;
- responsive variants;
- metadata removal.

Gzip и Brotli особенно полезны для текстовых ресурсов:

- HTML;
- CSS;
- JavaScript;
- JSON;
- SVG.

Фактический `Content-Encoding` и transfer size проверяют в Network panel.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как device pixel ratio влияет на выбор изображения?</strong></summary>

<dl>
<dd>
<h2></h2>

CSS-пиксель не всегда равен одному физическому пикселю экрана.

При:

```text
slot width = 300 CSS px
device pixel ratio = 2
```

браузеру может понадобиться изображение около:

```text
600 физических пикселей
```

чтобы оно выглядело резким.

Поэтому файл ровно `300 px` может быть размытым, а `3000 px` — избыточным.

`srcset` и `sizes` позволяют браузеру выбрать разумный кандидат с учётом плотности устройства.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>На каком расстоянии от viewport начинается native lazy loading?</strong></summary>

<dl>
<dd>
<h2></h2>

Приложение не получает фиксированной гарантированной дистанции.

Порог зависит от:

- браузера;
- реализации;
- типа соединения;
- состояния cache;
- внутренних эвристик.

Поэтому нельзя использовать native lazy loading как точный callback появления элемента.

Для бизнес-логики видимости применяют `IntersectionObserver`.

Lazy loading используют только как подсказку загрузки некритичного ресурса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему CSS background часто ухудшает загрузку LCP?</strong></summary>

<dl>
<dd>
<h2></h2>

URL background image обычно становится известен после цепочки:

```text
HTML
→ CSS request
→ CSS parsing
→ style calculation
→ image request
```

Обычный `<img>` в HTML preload scanner обнаруживает раньше.

Если background действительно является LCP и заменить его на `<img>` нельзя, можно рассмотреть точечный preload с `fetchpriority="high"`.

Смысловое изображение обычно лучше делать HTML-элементом из-за доступности, intrinsic-размера и responsive loading.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли AVIF лучше WebP?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

AVIF часто даёт меньший файл для фотографий, но результат зависит от:

- изображения;
- encoder;
- quality;
- размера;
- требуемой резкости;
- стоимости генерации;
- cache инфраструктуры.

WebP может быть проще и быстрее обрабатываться системой оптимизации.

Для каждого варианта сравнивают:

- визуальное качество;
- transfer size;
- время первого создания;
- поддержку целевой аудитории.

Нельзя выбирать codec только по общему рейтингу форматов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли variable font меньше нескольких обычных файлов?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Variable font выгоден, если приложение использует широкий диапазон:

```text
weights
width
slant
```

Если нужны только:

```text
regular
bold
```

два статических subset-файла могут оказаться меньше.

Нужно сравнить фактический WOFF2 transfer size после subsetting и используемые variation axes.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужен <code>preconnect</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`preconnect` заранее устанавливает соединение с внешним origin:

```html
<link
  rel="preconnect"
  href="https://fonts.example.com"
  crossorigin
>
```

Он полезен, когда критичный ресурс точно будет запрошен с этого origin, но сам URL файла пока неизвестен.

Подсказка может заранее выполнить DNS, transport connection и TLS.

Слишком много preconnect расходует sockets и CPU, поэтому выбирают только несколько критичных origins.

Для менее вероятного соединения можно использовать `dns-prefetch`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что оптимизирует <code>next/font</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`next/font` может:

- загрузить Google Font во время build;
- self-host font files;
- создать `@font-face`;
- добавить preload в области page или layout;
- настроить fallback metrics;
- предоставить `className` или CSS variable.

Он не отменяет необходимости выбрать:

- families;
- weights;
- subsets;
- `display`;
- место подключения.

Шрифт, вызванный в root layout, может загружаться шире, чем font, подключённый только на конкретной странице.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как диагностировать медленное LCP-изображение?</strong></summary>

<dl>
<dd>
<h2></h2>

Порядок проверки:

```text
1. Найти фактический LCP-element.
2. Проверить его URL.
3. Посмотреть, когда browser обнаружил ресурс.
4. Проверить request priority.
5. Сравнить rendered size и natural size.
6. Проверить currentSrc.
7. Проверить transfer size.
8. Проверить время между load end и paint.
```

Если запрос начинается поздно, проблема в discoverability.

Если начинается рано, но долго загружается, проверяют размер, CDN и формат.

Если файл уже загружен, но LCP наступает поздно, анализируют JavaScript, hydration, CSS и rendering.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Решение |
|---|---|
| Главное изображение является LCP | Раннее обнаружение, без lazy loading, обоснованный приоритет |
| LCP background обнаруживается после CSS | Рассмотреть `<img>` или точечный responsive preload |
| Сетка товаров загружает слишком большие файлы | Корректные `srcset`, `sizes` и реальные breakpoints |
| Retina-экран показывает размытые карточки | Учитывать device pixel ratio в responsive candidates |
| Карточки прыгают до загрузки изображений | `width`/`height`, `aspect-ratio`, стабильный контейнер |
| Preload загружает не тот responsive-файл | Согласовать `imagesrcset`, `imagesizes`, `srcset` и `sizes` |
| Все изображения первого экрана имеют высокий приоритет | Оставить приоритет только фактическому LCP-кандидату |
| После замены шрифта меняются строки | Близкий fallback и корректировка font metrics |
| Загружаются все языковые subsets | Проверить `unicode-range` и убрать лишние preload |
| Font-файлы конкурируют с hero image | Ограничить preload критичными weights и subsets |
| Next.js 14 предупреждает об LCP-изображении | Проверить `priority` по документации версии 14 |
| Next.js 16 использует старый `priority` | Пересмотреть `preload`, `loading` и `fetchPriority` |
| Изображение маленькое по Brotli, но LCP плохой | Проверить discovery, priority и element render delay |
