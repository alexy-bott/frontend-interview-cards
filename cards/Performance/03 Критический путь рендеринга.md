## Вопрос

<br>

 💬 **Что такое critical rendering path? Как браузер превращает HTML, CSS и JavaScript в пиксели?**

<h2></h2>

<br>
<dl>
<dd>

Critical rendering path, или критический путь рендеринга, — последовательность загрузки и обработки данных, необходимых браузеру для появления первого содержательного кадра страницы.

Упрощённая последовательность:

```text
получить HTML
→ построить DOM
→ получить и разобрать CSS
→ построить CSSOM
→ выполнить необходимый JavaScript
→ вычислить стили
→ выполнить layout
→ подготовить команды рисования
→ растрировать
→ собрать и вывести кадр
```

Critical rendering path относится прежде всего к первоначальному отображению страницы.

Render pipeline — более широкое понятие. Он продолжает работать после первого кадра при:

- изменении DOM;
- изменении CSS;
- вводе пользователя;
- анимации;
- изменении viewport;
- загрузке изображения или шрифта;
- обновлении React state.

Поэтому полезно разделять:

```text
critical rendering path
→ что задерживает первоначальный видимый результат

rendering pipeline
→ как браузер создаёт каждый следующий кадр
```

### Что является критическим ресурсом

Ресурс является критическим, если его задержка мешает вовремя показать нужный пользовательский контент.

Например:

- HTML;
- CSS первого экрана;
- JavaScript, создающий основной контент;
- LCP-изображение;
- шрифт, необходимый для отображения основного текста.

Но критический ресурс не обязательно блокирует HTML parser или весь первый render.

Например, hero-изображение может:

```text
не блокировать построение DOM
не блокировать первый текстовый paint
но определять LCP
```

Полезно различать три понятия.

| Тип | Что задерживает | Пример |
|---|---|---|
| Parser-blocking | Продолжение разбора HTML | Классический `<script>` без `async` и `defer` |
| Render-blocking | Первый render подходящего контента | Stylesheet с подходящим `media` |
| Critical resource | Важный пользовательский результат | LCP-изображение, CSS, HTML или JavaScript |

Один ресурс может относиться сразу к нескольким категориям.

Например, ранний классический script:

```text
блокирует parser
+
может задерживать render
+
может быть частью critical path
```

Но обычное изображение карточки ниже первого экрана:

```text
не блокирует parser
не блокирует первый render
не является критическим
```

### Получение и разбор HTML

Браузер получает HTML как поток байтов.

Упрощённо:

```text
bytes
→ characters
→ tokens
→ DOM nodes
→ DOM tree
```

Браузеру не обязательно ждать получения всего HTML-файла.

Он может начинать разбор документа по мере поступления данных.

Например:

```html
<!doctype html>
<html>
  <head>
    <link
      rel="stylesheet"
      href="/styles.css"
    >
  </head>

  <body>
    <h1>Каталог</h1>
  </body>
</html>
```

После обнаружения `<link>` браузер может начать загрузку CSS, пока оставшаяся часть HTML ещё поступает или разбирается.

Во время разбора parser встречает:

- DOM-элементы;
- stylesheets;
- scripts;
- изображения;
- шрифты через preload;
- iframe;
- другие сетевые зависимости.

Некоторые элементы создают DOM-узлы, а некоторые дополнительно запускают загрузку внешнего ресурса.

### Preload scanner

Помимо основного HTML parser браузер обычно использует preload scanner — дополнительный сканер, который заранее ищет очевидные ссылки на ресурсы.

Упрощённо:

```text
основной parser
→ последовательно строит DOM

preload scanner
→ заглядывает вперёд
→ начинает сетевые запросы
```

Он помогает обнаруживать:

- `<link rel="stylesheet">`;
- `<script src>`;
- `<img src>`;
- `srcset`;
- `<link rel="preload">`;
- другие явные URL в HTML.

Это особенно полезно, когда основной parser временно остановлен классическим script.

Preload scanner может продолжить изучать будущую HTML-разметку и заранее начать загрузку следующих ресурсов.

Но он не выполняет JavaScript и не знает результат будущего render.

Поэтому он не может заранее обнаружить ресурс, если URL:

- создаётся JavaScript;
- появляется после client render;
- загружается через dynamic `import()`;
- находится внутри ещё не загруженного внешнего CSS;
- получается только после API-запроса;
- формируется сторонней библиотекой во время выполнения.

Например:

```tsx
useEffect(() => {
  setImageUrl(
    "/hero.jpg",
  );
}, []);
```

приведёт к позднему обнаружению изображения:

```text
HTML
→ JavaScript
→ hydration
→ useEffect
→ появился URL
→ началась загрузка
```

Если изображение определяет LCP, такая цепочка ухудшает resource load delay.

Критический ресурс лучше делать обнаружимым непосредственно в server-rendered HTML, когда это возможно.

### DOM

DOM, Document Object Model, описывает:

- элементы;
- текстовые узлы;
- атрибуты;
- вложенность;
- связи между частями документа.

Например:

```html
<main>
  <h1>Каталог</h1>
  <p>Список товаров</p>
</main>
```

превращается в структурированное дерево узлов.

DOM сам по себе не содержит полного ответа на вопросы:

- какого размера элемент;
- где он находится;
- каким цветом отображается;
- видим ли он;
- как переносится текст.

Для этого нужны CSS и результаты вычисления стилей.

### CSSOM

CSS разбирается в CSSOM, CSS Object Model.

Например:

```css
main {
  width: 800px;
}

h1 {
  color: darkblue;
}
```

Браузер учитывает:

- каскад;
- наследование;
- специфичность;
- origin правил;
- media queries;
- container queries;
- пользовательские стили;
- browser defaults.

CSSOM представляет CSS-правила и используется при вычислении итоговых стилей элементов.

Упрощённо:

```text
DOM
→ что находится в документе

CSSOM
→ какие правила могут применяться

style calculation
→ какие итоговые значения получил элемент
```

### Render tree как упрощённая модель

Во frontend-объяснениях часто используется понятие render tree:

```text
DOM
+
CSSOM
→ render tree
```

Это полезная концептуальная модель, показывающая видимые объекты и их стили.

Но современные браузеры внутри используют несколько специализированных структур:

- style data;
- layout tree;
- fragment tree;
- property trees;
- paint chunks;
- compositing layers.

Поэтому render tree не следует понимать как единственное буквальное дерево, одинаковое во всех браузерах.

Соответствие DOM и визуальных объектов не является взаимно однозначным.

Например:

- `<script>` существует в DOM, но не создаёт видимого CSS-бокса;
- `display: none` исключает элемент из layout;
- `visibility: hidden` сохраняет геометрию элемента;
- `::before` создаёт визуальный контент без отдельного DOM-узла;
- один текстовый узел может разбиться на несколько строк и фрагментов;
- один элемент может создать несколько layout fragments при переносе между колонками или страницами.

DOM описывает документ, а rendering structures — его фактическое визуальное представление.

### Почему CSS блокирует первый render

Stylesheet с подходящим текущему окружению `media` обычно является render-blocking ресурсом.

Например:

```html
<link
  rel="stylesheet"
  href="/styles.css"
>
```

До получения и разбора CSS браузер может не знать:

- `display`;
- размеры;
- позиционирование;
- шрифт;
- видимость;
- порядок;
- перенос текста.

Если сначала показать страницу без CSS, а затем применить стили, пользователь увидит Flash of Unstyled Content и крупное перестроение интерфейса.

Поэтому браузер обычно ждёт построения необходимого CSSOM перед первым render.

Это не означает, что любой stylesheet одинаково критичен.

Например:

```html
<link
  rel="stylesheet"
  href="/print.css"
  media="print"
>
```

не должен блокировать обычный экранный render, пока условие `print` не применяется.

Другой пример:

```html
<link
  rel="stylesheet"
  href="/desktop.css"
  media="(min-width: 1200px)"
>
```

не блокирует текущий render на маленьком viewport, если media query не совпадает.

Браузер при этом всё равно может загрузить файл с другим приоритетом, потому что media condition способно измениться.

Оптимизация CSS обычно включает:

- уменьшение общего объёма;
- удаление неиспользуемых правил;
- разделение CSS по маршрутам;
- раннюю загрузку CSS первого экрана;
- отсутствие длинных цепочек `@import`;
- точные `media`;
- осторожное inline critical CSS.

Inline CSS уменьшает число сетевых переходов, но увеличивает HTML и не кэшируется как отдельный общий файл.

Поэтому весь CSS приложения не следует автоматически помещать в `<style>`.

### JavaScript и HTML parser

Классический внешний script без `async`, `defer` и `type="module"` блокирует HTML parser.

```html
<script src="/app.js"></script>
```

Упрощённо:

```text
parser встретил script
→ остановил построение DOM
→ загрузил script
→ выполнил script
→ продолжил HTML
```

Это необходимо, потому что script может изменить документ прямо во время разбора:

```js
document.write(
  "<p>Новый узел</p>",
);
```

Он также может:

- прочитать уже построенный DOM;
- удалить элементы;
- добавить новые элементы;
- добавить stylesheet;
- изменить CSS classes;
- запросить вычисленный style;
- прочитать layout.

Браузер не может безопасно предположить, что script никак не влияет на последующую структуру документа.

#### JavaScript и CSS

Классический script может читать вычисленные стили:

```js
getComputedStyle(element);
```

или геометрию:

```js
element.offsetWidth;
```

Поэтому выполнение parser-blocking script может ожидать загрузку уже обнаруженных перед ним render-blocking stylesheets.

Возможна цепочка:

```text
HTML parser
→ обнаружил CSS
→ обнаружил classic script
→ script ждёт CSSOM
→ parser ждёт script
→ продолжение DOM задержано
```

Это одна из причин, почему ранний классический script без `defer` способен сильно увеличить critical path.

### `defer`

```html
<script
  src="/app.js"
  defer
></script>
```

`defer` означает:

```text
загружать параллельно с HTML parsing
→ не останавливать parser ради загрузки
→ выполнить после разбора документа
→ до DOMContentLoaded
```

Несколько classic scripts с `defer` выполняются в порядке документа:

```html
<script
  src="/vendor.js"
  defer
></script>

<script
  src="/app.js"
  defer
></script>
```

Выполнение:

```text
vendor.js
→ app.js
```

даже если `app.js` загрузился раньше.

`defer` подходит для основного application script, который:

- зависит от готового DOM;
- должен сохранить порядок;
- не нужен во время самого HTML parsing.

Атрибут `defer` применяется к внешним classic scripts.

Для inline classic script он не создаёт такое же отложенное поведение.

### `async`

```html
<script
  src="/analytics.js"
  async
></script>
```

`async` означает:

```text
загружать параллельно
→ выполнить сразу после готовности
```

Когда файл загрузился, браузер может временно остановить parser для его выполнения.

Порядок нескольких `async` scripts не гарантируется:

```text
какой загрузился раньше
→ тот обычно выполняется раньше
```

`async` подходит для независимого кода:

- аналитики;
- рекламы;
- виджета;
- скрипта без зависимости от DOM;
- скрипта без зависимости от других файлов.

`DOMContentLoaded` не обязан ждать `async` scripts.

Но конкретный async script может успеть выполниться до этого события, если загрузился достаточно рано.

### `type="module"`

```html
<script
  type="module"
  src="/app.js"
></script>
```

Module script:

- поддерживает `import` и `export`;
- загружает граф зависимостей;
- выполняется в strict mode;
- отложен по умолчанию;
- выполняется после разбора документа;
- задерживает `DOMContentLoaded` до завершения выполнения.

Поэтому обычно не нужно писать:

```html
<script
  type="module"
  defer
></script>
```

Для module script `defer` не меняет стандартное поведение.

Module dependencies могут загружаться параллельно после обнаружения import graph.

Для раннего получения модулей существует:

```html
<link
  rel="modulepreload"
  href="/module.js"
>
```

Module script также может использовать `async`.

Тогда его граф загружается параллельно, а выполнение начинается после готовности без обычного отложенного порядка.

### `DOMContentLoaded` и `load`

Эти события отражают разные этапы.

`DOMContentLoaded` происходит, когда:

- HTML полностью разобран;
- DOM построен;
- deferred classic scripts выполнены;
- module scripts выполнены.

Он не ждёт обычную загрузку всех:

- изображений;
- iframe;
- lazy resources;
- других необязательных ресурсов.

`load` происходит позже, когда загрузились основные зависимые ресурсы страницы:

- stylesheets;
- scripts;
- изображения без lazy loading;
- iframe.

Упрощённо:

```text
HTML parsed
+
defer/module executed
→ DOMContentLoaded

основные зависимые ресурсы загружены
→ load
```

Но ни одно из событий не означает автоматически:

```text
пользователь увидел основной контент

приложение стало полностью отзывчивым

закончилась hydration

получены все API-данные
```

Для пользовательского опыта используют:

- FCP;
- LCP;
- INP;
- собственные User Timing metrics.

### Этапы rendering pipeline

Точные внутренние этапы отличаются между browser engines.

Для frontend удобно использовать упрощённую модель Chromium:

| Этап | Что происходит |
|---|---|
| Style | Вычисляются итоговые CSS-свойства |
| Layout | Определяются размеры, позиции и фрагменты |
| Pre-paint | Обновляются paint-свойства и invalidation |
| Paint | Создаются команды рисования и paint chunks |
| Raster | Команды превращаются в пиксельные tiles |
| Composite | Слои и tiles собираются в итоговый кадр |
| Draw | Кадр передаётся для вывода на экран |

Между этими крупными этапами Chromium использует дополнительные внутренние операции:

- commit;
- layerization;
- activation;
- aggregation;
- управление property trees;
- работу renderer и compositor processes.

Для прикладной оптимизации обычно достаточно модели:

```text
style
→ layout
→ paint
→ composite
```

Но важно понимать, что `paint` и `raster` — не одно и то же.

### Style calculation

Style calculation отвечает на вопрос:

```text
Какие итоговые CSS-свойства
получил каждый затронутый элемент?
```

Учитываются:

- selectors;
- cascade;
- inheritance;
- specificity;
- media queries;
- container queries;
- pseudo-classes;
- CSS variables.

Например:

```js
element.classList.add(
  "active",
);
```

может потребовать пересчитать style для элемента и зависимых частей дерева.

Если итоговое изменение касается только цвета:

```css
color: red;
```

layout может не потребоваться.

Но paint обычно потребуется.

Если изменилось:

```css
width: 300px;
```

после style calculation потребуется layout.

### Layout

Layout определяет геометрию CSS-боксов:

- ширину;
- высоту;
- позицию;
- перенос строк;
- расположение flex/grid children;
- размер scroll container;
- фрагментацию.

Layout зависит от связей элементов.

Например, изменение ширины родителя может изменить:

- размеры детей;
- перенос текста;
- высоту секции;
- позицию всех элементов ниже.

Поэтому небольшой DOM update иногда вызывает дорогой layout большого поддерева.

При этом браузер старается выполнять частичный layout только для invalidated области, а не пересчитывать весь документ при каждом изменении.

Стоимость зависит от:

- размера затронутого дерева;
- layout-модели;
- зависимостей между элементами;
- количества повторений;
- необходимости синхронного результата.

### Pre-paint

В Chromium Pre-paint подготавливает данные перед созданием paint-команд.

На этом этапе обновляются сведения о:

- transform;
- clip;
- effect;
- scroll;
- paint invalidation;
- областях, которые нужно перерисовать.

Frontend-разработчику редко нужно оптимизировать Pre-paint отдельно.

Обычно проблема проявляется как:

- большой объём rendering work;
- крупная область paint;
- частое обновление properties;
- неожиданный compositing.

### Paint

Paint не обязательно сразу рисует пиксели.

Браузер создаёт описание того, что и в каком порядке нужно нарисовать:

```text
фон
→ border
→ текст
→ изображение
→ тень
→ псевдоэлемент
```

Результат часто представляется как display list, paint records или paint chunks.

Paint требуется, когда меняется визуальное содержимое:

- цвет;
- background;
- border;
- box-shadow;
- текст;
- изображение;
- часть filter.

Чем больше область, которую нужно перерисовать, тем выше потенциальная стоимость.

### Raster

Raster превращает paint-команды в пиксели.

Страница может делиться на tiles:

```text
paint commands
→ raster tiles
→ textures/pixel buffers
```

Raster может выполняться:

- на дополнительных raster threads;
- с аппаратным ускорением;
- частично для видимой области;
- по мере прокрутки.

Большой слой не обязательно растрируется целиком сразу.

Но крупные изображения, blur, shadows и большие области paint способны увеличить raster cost.

### Composite

Composite собирает готовые слои и tiles в итоговый кадр.

На этом этапе учитываются:

- transform;
- opacity;
- clipping;
- порядок слоёв;
- scroll offset;
- stacking;
- visual effects.

Если нужное содержимое уже растрировано в отдельном composited layer, некоторые изменения можно выполнить без нового layout и paint.

Например:

```css
transform: translateX(20px);
opacity: 0.5;
```

могут ограничиться compositing.

Но это не гарантируется только именем CSS-свойства.

Браузер самостоятельно решает:

- создавать ли отдельный слой;
- сохранять ли его;
- когда выполнить raster;
- достаточно ли памяти.

### Pipeline выполняется не всегда целиком

После изменения браузер инвалидирует только необходимые данные.

Упрощённо:

| Изменение | Возможные этапы |
|---|---|
| `width` | Style → Layout → Paint → Composite |
| `color` | Style → Paint → Composite |
| `background-image` | Style → Paint/Raster → Composite |
| `transform` готового слоя | Composite |
| `opacity` готового слоя | Composite |
| Добавление большого DOM-поддерева | Style → Layout → Paint → Composite |

Это ориентировочная модель.

Фактический путь зависит от:

- browser engine;
- текущего layering;
- размера элемента;
- других CSS-свойств;
- способа изменения;
- содержимого слоя;
- состояния cache.

Например, изменение `transform` может потребовать первоначального paint и raster, если слой ещё не подготовлен.

### `transform` и `opacity`

Эти свойства часто подходят для анимации, потому что могут не изменять геометрию layout.

Например:

```css
.card {
  transition:
    transform 200ms;
}

.card:hover {
  transform:
    translateY(-4px);
}
```

Соседние элементы не пересчитывают своё положение из-за visual transform.

Но `transform` и `opacity` не бесплатны.

Возможные расходы:

- создание composited layer;
- память под texture;
- первоначальный raster;
- загрузка данных в GPU;
- raster новых tiles;
- сложные clipping и filters;
- большое количество слоёв;
- обновление огромной области.

Анимация маленькой кнопки и полноэкранного blur-layer имеют разную стоимость.

Результат проверяют через:

- Performance panel;
- Frames;
- Layers;
- Paint flashing;
- GPU и raster tracks.

### `will-change`

`will-change` сообщает браузеру, что свойство, вероятно, скоро изменится:

```css
.panel {
  will-change:
    transform;
}
```

Браузер может заранее:

- создать layer;
- подготовить данные;
- изменить стратегию оптимизации.

Но это подсказка, а не команда.

Не следует применять:

```css
* {
  will-change:
    transform;
}
```

или постоянно держать `will-change` на сотнях элементов.

Это может увеличить:

- число слоёв;
- потребление памяти;
- raster cost;
- compositing cost.

Обычно `will-change` добавляют незадолго до действительно частого изменения и убирают после завершения, если браузер не справляется хорошо без подсказки.

Сначала проблему подтверждают измерением.

### Forced synchronous layout

Браузер старается группировать DOM-изменения и выполнять style/layout перед следующим кадром.

Например:

```js
element.style.width =
  "300px";
```

не обязано немедленно запускать layout.

Браузер может пометить геометрию как устаревшую и пересчитать её позже.

Но если код сразу запросит актуальный размер:

```js
element.style.width =
  "300px";

const width =
  element.offsetWidth;
```

браузер должен вернуть правильное значение.

Поэтому он вынужденно выполняет:

```text
style calculation
→ layout
→ вернуть offsetWidth
```

внутри текущего JavaScript-вызова.

Это называется forced synchronous layout или forced reflow.

Операции, способные потребовать актуальную геометрию, включают:

- `offsetWidth`;
- `offsetHeight`;
- `clientWidth`;
- `clientHeight`;
- `scrollWidth`;
- `getBoundingClientRect()`;
- некоторые вызовы `getComputedStyle()`.

Не каждое такое чтение автоматически дорого.

Проблема возникает, когда:

- layout invalidated;
- дерево большое;
- чтение повторяется часто;
- операция происходит в критическом взаимодействии.

### Layout thrashing

Layout thrashing — многократное чередование записей и чтений геометрии.

Плохо:

```js
for (
  const item of items
) {
  item.style.width =
    `${container.offsetWidth}px`;
}
```

Каждая итерация может выполнять:

```text
read layout
→ write style
→ invalidate layout
→ read layout снова
```

Лучше сначала прочитать нужные данные:

```js
const width =
  container.offsetWidth;

for (
  const item of items
) {
  item.style.width =
    `${width}px`;
}
```

Общий принцип:

```text
сначала все reads
→ затем все writes
```

Для нескольких кадров можно организовать очередь:

```text
текущий кадр
→ прочитать геометрию

следующий этап
→ изменить DOM
```

Главная оптимизация заключается не в конкретном API, а в уменьшении числа принудительных layout.

### `requestAnimationFrame`

`requestAnimationFrame()` планирует callback перед одной из следующих возможностей отрисовки.

```js
requestAnimationFrame(
  () => {
    element.style.transform =
      "translateX(20px)";
  },
);
```

Он полезен для:

- визуальных обновлений;
- синхронизации animation с кадрами;
- группировки DOM writes;
- измерения работы вокруг render opportunity.

Но `requestAnimationFrame` сам по себе не исправляет layout thrashing.

Плохо:

```js
requestAnimationFrame(
  () => {
    element.style.width =
      "300px";

    console.log(
      element.offsetWidth,
    );

    element.style.height =
      "200px";

    console.log(
      element.offsetHeight,
    );
  },
);
```

Чередование write/read остаётся внутри callback.

Также callback может быть задержан, если main thread занят long task.

`requestAnimationFrame` не гарантирует:

- ровно 60 вызовов в секунду;
- отдельный кадр после каждого callback;
- отсутствие layout;
- выполнение в фоновой вкладке.

### Когда браузер может показать кадр

JavaScript на main thread выполняется задачами event loop.

Упрощённо:

```text
task
→ microtasks
→ возможная rendering opportunity
→ следующий task
```

Пока выполняется длинная JavaScript-задача, браузер обычно не может:

- обработать следующее действие;
- выполнить своевременный layout;
- нарисовать новый кадр.

Например:

```js
button.addEventListener(
  "click",
  () => {
    status.textContent =
      "Загрузка...";

    runHeavyCalculation();
  },
);
```

Если `runHeavyCalculation()` занимает 500 мс, пользователь может не увидеть текст «Загрузка...» до завершения всей задачи.

DOM изменился, но paint ещё не произошёл.

Promise microtasks также выполняются до следующей rendering opportunity.

Поэтому перенос тяжёлого вычисления из обычного кода в:

```js
Promise.resolve().then(
  runHeavyCalculation,
);
```

не гарантирует появление промежуточного кадра.

Чтобы дать браузеру возможность отрисовать интерфейс, работу иногда разделяют между задачами или переносят подходящее вычисление в Web Worker.

### Большой DOM

Большой DOM не обязательно делает каждый render медленным.

Но он увеличивает потенциальный объём работы для:

- style matching;
- layout;
- paint invalidation;
- accessibility tree;
- DOM queries;
- memory;
- garbage collection.

Особенно опасно сочетание:

```text
большой DOM
+
частые глобальные style changes
+
layout зависимого дерева
+
повторение в каждом кадре
```

Например, изменение class на корневом элементе может повлиять на множество descendants через:

- inheritance;
- CSS variables;
- descendant selectors;
- media или container conditions.

Оптимизация зависит от сценария:

- не создавать невидимые элементы без необходимости;
- виртуализировать большие списки;
- ограничивать область state update;
- применять containment;
- уменьшать затронутое поддерево;
- проверять фактические Style/Layout durations.

Число DOM-узлов само по себе не является достаточной метрикой без trace.

### CSS containment

`contain` позволяет сообщить браузеру, что определённые вычисления внутри элемента ограничены его границей.

Например:

```css
.widget {
  contain:
    layout paint;
}
```

Возможные виды containment связаны со:

- size;
- inline-size;
- layout;
- style;
- paint.

Containment может уменьшить область, которую нужно пересчитывать или перерисовывать.

Но он также меняет поведение layout и paint.

Например, size containment способен повлиять на автоматические размеры элемента.

Поэтому `contain` применяют к действительно независимым областям интерфейса, а не ко всему дереву без анализа.

### `content-visibility`

```css
.section {
  content-visibility:
    auto;
}
```

`content-visibility: auto` позволяет браузеру пропускать часть rendering work для содержимого далеко вне viewport.

Браузер может отложить:

- style для внутреннего содержимого;
- layout;
- paint.

При приближении секции работа выполняется.

Чтобы зарезервировать ожидаемое место, используют:

```css
.section {
  content-visibility:
    auto;

  contain-intrinsic-size:
    auto 600px;
}
```

Без подходящего intrinsic size размер offscreen-секции может быть оценён неточно и измениться при фактическом render, создавая layout shift.

`content-visibility` полезен для:

- длинных страниц;
- крупных независимых секций;
- сложных блоков ниже первого экрана.

Но он не заменяет virtualization.

DOM-узлы продолжают существовать, а данные и JavaScript могут быть уже загружены.

Нужно тестировать:

- программный focus;
- tab navigation;
- поиск по странице;
- scroll anchoring;
- accessibility;
- CLS;
- переход к anchor.

### Как найти медленный этап

Для первоначальной загрузки начинают с Network waterfall.

Проверяют:

- TTFB;
- момент обнаружения CSS;
- parser-blocking scripts;
- начало загрузки LCP-ресурса;
- redirect chains;
- приоритеты;
- cache;
- последовательные запросы.

В Chrome Performance записывают конкретный сценарий.

На Main thread ищут:

- Parse HTML;
- Evaluate Script;
- Recalculate Style;
- Layout;
- Paint;
- long tasks;
- forced reflow warnings.

Дополнительно проверяют:

- Raster threads;
- Frames;
- Compositor;
- Screenshots;
- Layout Shifts;
- Layers;
- Paint flashing.

Важны не только количество событий, но и:

- длительность;
- площадь;
- частота;
- затронутое дерево;
- связь с пользовательским кадром.

Например:

```text
один Layout = 3 мс
```

обычно не является проблемой.

Но:

```text
100 Layout по 3 мс
в одном interaction
```

уже создают заметную задержку.

### Практический процесс диагностики

```text
1. Определить пользовательский симптом.
2. Разделить initial load и runtime update.
3. Найти критический визуальный результат.
4. Открыть Network waterfall.
5. Проверить момент обнаружения ресурсов.
6. Найти parser-blocking и render-blocking цепочки.
7. Записать Performance trace.
8. Определить JavaScript, style, layout, paint или composite bottleneck.
9. Сформулировать одну гипотезу.
10. Внести минимальное изменение.
11. Повторить измерение.
12. Проверить LCP, INP и CLS после релиза.
```

Пример:

```text
симптом
→ hero появляется поздно

Network
→ запрос изображения начался после hydration

причина
→ URL создаётся в useEffect

решение
→ отрендерить img в server HTML

проверка
→ resource load delay уменьшился
```

Другой пример:

```text
симптом
→ drag дёргается

Performance
→ повторяющиеся forced layouts

причина
→ write/read в каждой итерации

решение
→ сгруппировать reads и writes

проверка
→ Layout events и frame duration уменьшились
```

### Главная модель

Первоначальный путь:

```text
HTML
→ DOM

CSS
→ CSSOM

DOM + computed styles
→ layout structures

layout
→ paint commands

paint commands
→ raster

layers и tiles
→ composite

frame
→ screen
```

При обновлении браузер старается выполнить только необходимые этапы:

```text
style
→ layout
→ paint
→ composite
```

или более короткий путь:

```text
composite
```

Главный принцип оптимизации:

```text
сделать критические ресурсы
ранними и обнаружимыми

не блокировать parser без необходимости

уменьшить объём render-blocking CSS

не запускать лишний layout и paint

подтверждать bottleneck через trace
```

## Дополнительные вопросы

<details>
<summary><strong>Почему CSS блокирует первый render?</strong></summary>

<dl>
<dd>
<h2></h2>

До применения CSS браузер не знает итоговые:

- размеры;
- `display`;
- шрифты;
- видимость;
- позиционирование;
- переносы текста.

Если сначала показать DOM без стилей, а затем применить CSS, интерфейс может полностью перестроиться.

Поэтому подходящий текущему `media` stylesheet обычно блокирует первый render до построения необходимого CSSOM.

CSS с неподходящим `media` не должен блокировать текущий render, хотя браузер может загрузить его для возможного будущего использования.

Большой неиспользуемый CSS увеличивает:

- передачу;
- parsing;
- style calculation;
- время ожидания первого render.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему обычный <code>&lt;script&gt;</code> блокирует разбор HTML?</strong></summary>

<dl>
<dd>
<h2></h2>

Классический script может:

- выполнить `document.write`;
- изменить уже построенный DOM;
- добавить новый HTML;
- прочитать computed style;
- запросить layout;
- добавить stylesheet.

Браузер не может продолжить parsing так, словно script никак не повлияет на документ.

Поэтому последовательность выглядит так:

```text
parser встретил script
→ остановился
→ загрузил и выполнил script
→ продолжил parsing
```

Если script зависит от уже обнаруженного CSS, его выполнение также может ждать CSSOM.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>defer</code>, <code>async</code> и <code>type="module"</code> отличаются по выполнению?</strong></summary>

<dl>
<dd>
<h2></h2>

`defer`:

```text
загружается параллельно
→ выполняется после HTML parsing
→ сохраняет порядок
→ задерживает DOMContentLoaded
```

`async`:

```text
загружается параллельно
→ выполняется сразу после готовности
→ порядок не гарантируется
→ DOMContentLoaded его не ждёт
```

`type="module"`:

```text
загружает module graph
→ отложен по умолчанию
→ выполняется после parsing
→ задерживает DOMContentLoaded
```

`async` можно применить и к module script, если порядок и обычное отложенное выполнение не нужны.

Выбор определяется зависимостями кода, а не только желанием «загрузить быстрее».

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем DOM, CSSOM и render tree отличаются друг от друга?</strong></summary>

<dl>
<dd>
<h2></h2>

DOM описывает структуру и содержимое документа.

CSSOM представляет разобранные CSS-правила.

Вычисление стилей определяет итоговые свойства конкретных элементов.

Render tree — упрощённое название визуальных структур, которые браузер использует для layout и rendering.

Соответствие не является взаимно однозначным:

- `display: none` не создаёт layout box;
- `visibility: hidden` сохраняет место;
- псевдоэлемент не имеет отдельного DOM-узла;
- текст может создать несколько fragments;
- один DOM-элемент способен участвовать в нескольких layout-фрагментах.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем расчёт style отличается от layout?</strong></summary>

<dl>
<dd>
<h2></h2>

Style calculation отвечает на вопрос:

```text
Какие CSS-значения применены?
```

Он учитывает:

- selectors;
- cascade;
- inheritance;
- CSS variables;
- media queries;
- container queries.

Layout отвечает на вопрос:

```text
Каковы размеры и позиции?
```

Изменение класса может потребовать style calculation.

Если изменённое свойство влияет на геометрию, затем выполняется layout.

Изменение только цвета обычно не требует layout, но требует paint.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем paint отличается от raster и composite?</strong></summary>

<dl>
<dd>
<h2></h2>

Paint создаёт команды:

```text
нарисовать фон
нарисовать текст
нарисовать border
```

Raster превращает эти команды в пиксельные tiles.

Composite собирает готовые слои и tiles в итоговый кадр с учётом:

- transform;
- opacity;
- clipping;
- scroll;
- порядка слоёв.

Такое разделение позволяет иногда перемещать уже растрированный слой без повторных layout и paint.

Если содержимое слоя изменилось или нужные tiles отсутствуют, raster потребуется снова.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>transform</code> и <code>opacity</code> часто дешевле <code>top</code>, <code>left</code>, <code>width</code> и <code>height</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Геометрические свойства могут изменить положение соседей:

```text
style
→ layout
→ paint
→ composite
```

`transform` меняет визуальное размещение уже вычисленного box, не перестраивая обычный flow.

`opacity` меняет прозрачность.

Для подготовленного composited layer путь может ограничиться:

```text
composite
```

Но отдельный слой требует памяти и первоначального raster.

Браузер сам решает, создавать ли его, поэтому преимущество подтверждают в Performance и Layers.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое forced synchronous layout?</strong></summary>

<dl>
<dd>
<h2></h2>

После изменения DOM браузер может отложить layout до подготовки следующего кадра.

Если JavaScript сразу запросил актуальную геометрию:

```js
element.style.width =
  "300px";

const width =
  element.offsetWidth;
```

браузер вынужден синхронно выполнить style calculation и layout перед возвратом `offsetWidth`.

Одна операция не обязательно критична.

Проблема возникает при большом затронутом дереве или частом повторении внутри одного пользовательского действия.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое layout thrashing?</strong></summary>

<dl>
<dd>
<h2></h2>

Layout thrashing возникает при многократном чередовании:

```text
изменить геометрию
→ прочитать layout
→ изменить геометрию
→ прочитать layout
```

Каждое чтение может принудительно запустить новый layout.

Оптимизация:

```text
сначала собрать все layout reads
→ затем выполнить все DOM writes
```

`requestAnimationFrame` помогает организовать работу относительно кадра, но не исправляет чередование reads и writes автоматически.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает preload scanner и почему он не находит все ресурсы?</strong></summary>

<dl>
<dd>
<h2></h2>

Preload scanner параллельно с основным parser ищет явные URL в HTML:

- stylesheets;
- scripts;
- images;
- preload;
- другие ресурсы.

Он может начать запрос, пока основной parser заблокирован.

Но scanner:

- не выполняет JavaScript;
- не строит React-дерево;
- не знает результат API-запроса;
- не разбирает ещё не загруженный внешний CSS.

Поэтому CSS background и URL, созданные JavaScript, обнаруживаются позже.

Критический ресурс лучше помещать в первоначальный HTML либо точечно предварительно загружать, когда естественное обнаружение невозможно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Для чего нужны <code>contain</code> и <code>content-visibility</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`contain` ограничивает влияние поддерева на внешние вычисления:

```text
layout
paint
size
style
```

`content-visibility: auto` позволяет пропускать часть rendering work для содержимого далеко от viewport.

```css
.section {
  content-visibility:
    auto;

  contain-intrinsic-size:
    auto 600px;
}
```

`contain-intrinsic-size` задаёт ожидаемую геометрию, пока реальное содержимое не отрендерено, и помогает уменьшить CLS.

Эти свойства полезны для крупных независимых секций, но требуют проверки layout, фокуса, навигации, accessibility и переходов к anchors.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как определить, какой этап rendering создаёт задержку?</strong></summary>

<dl>
<dd>
<h2></h2>

Записывают конкретный сценарий в Chrome Performance.

На Main thread ищут:

- Evaluate Script;
- Recalculate Style;
- Layout;
- Paint;
- long tasks;
- forced reflow.

Дополнительно проверяют:

- Frames;
- Raster;
- Compositor;
- Screenshots;
- Layers;
- Paint flashing;
- Layout Shift Regions.

Важны:

- длительность;
- частота;
- площадь обновления;
- затронутые nodes;
- связь с нужным кадром.

Большое число событий не всегда является проблемой, если каждое занимает незначительное время и не задерживает пользовательский результат.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем critical resource отличается от parser-blocking и render-blocking resource?</strong></summary>

<dl>
<dd>
<h2></h2>

Parser-blocking ресурс останавливает продолжение разбора HTML.

Render-blocking ресурс задерживает первый render.

Critical resource влияет на важный пользовательский результат.

Например:

```text
classic script
→ parser-blocking

stylesheet
→ render-blocking

hero image
→ critical для LCP,
  но обычно не parser-blocking
```

Категории могут пересекаться, но не являются синонимами.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>DOMContentLoaded</code> отличается от <code>load</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`DOMContentLoaded` происходит после:

- полного HTML parsing;
- выполнения deferred classic scripts;
- выполнения module scripts.

Он не ждёт все изображения и iframe.

`load` происходит после загрузки основных зависимых ресурсов страницы, кроме ресурсов с отложенной загрузкой.

Оба события являются техническими milestones.

Они не гарантируют хороший LCP, завершённую hydration или получение всех данных приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда браузер может показать новый кадр относительно JavaScript?</strong></summary>

<dl>
<dd>
<h2></h2>

Упрощённо event loop выполняет:

```text
task
→ microtasks
→ возможный render
→ следующая task
```

Пока выполняется длинная JavaScript-задача, browser не может своевременно показать новый кадр.

Promise microtasks также завершаются до следующей rendering opportunity.

Поэтому обновление DOM и последующее тяжёлое синхронное вычисление в той же task могут привести к тому, что пользователь увидит результат только после вычисления.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Исправляет ли <code>requestAnimationFrame</code> проблемы rendering автоматически?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

`requestAnimationFrame` планирует callback перед одной из следующих возможностей отрисовки.

Он полезен для визуальных обновлений и группировки DOM writes.

Но внутри callback всё ещё можно создать:

- forced layout;
- layout thrashing;
- long task;
- дорогой paint.

Главное правило остаётся прежним:

```text
сгруппировать reads
→ сгруппировать writes
→ не выполнять лишнюю работу
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему большой DOM может замедлять rendering?</strong></summary>

<dl>
<dd>
<h2></h2>

Большое дерево увеличивает потенциальную стоимость:

- style matching;
- inheritance;
- layout;
- paint invalidation;
- DOM queries;
- accessibility tree;
- memory.

Особенно заметна проблема, когда часто изменяется крупное поддерево или геометрия его родителя.

Само количество nodes не доказывает bottleneck.

Нужно проверить в trace продолжительность Style, Layout и Paint и определить затронутую область.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Затронутый участок |
|---|---|
| Большой CSS-файл в `<head>` | Загрузка CSS, CSSOM и первый render |
| `<script>` без `defer` в начале HTML | Остановка parser и возможное ожидание CSS |
| LCP-изображение создаётся после hydration | Позднее обнаружение сетевого ресурса |
| CSS background используется для hero | Ресурс обнаруживается после загрузки и разбора CSS |
| Цикл меняет стили и читает `offsetHeight` | Forced layout и layout thrashing |
| Long task изменяет DOM в начале выполнения | Paint не появляется до завершения задачи |
| Анимация большого элемента через `transform` | Composite, а также память слоя и raster |
| Сотни элементов получают `will-change` | Избыточные layers и потребление памяти |
| Длинная страница с тяжёлыми offscreen-секциями | `content-visibility` и containment |
| Большое DOM-дерево обновляется целиком | Style, Layout, Paint и React update |
