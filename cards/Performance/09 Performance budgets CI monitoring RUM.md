## Вопрос

<br>

 💬 **Что такое performance budget и как контролировать производительность в CI и production-приложении?**

<h2></h2>

<br>
<dl>
<dd>

Performance budget, или бюджет производительности, — заранее согласованный предел для характеристики приложения, влияющей на пользовательский опыт.

Он превращает требование:

```text
страница должна быть быстрой
```

в проверяемое условие:

```text
initial JavaScript страницы входа
≤ 200 КБ после Brotli

p75 LCP мобильных посещений
≤ 2,5 с

CLS страницы товара
≤ 0,1

редактор не входит
в initial bundle страницы входа
```

Бюджет нужен не только для фиксации текущей скорости, но и для защиты от постепенной регрессии:

```text
каждое изменение
добавляет немного кода

→ отдельные изменения
  выглядят незначительными

→ через несколько месяцев
  страница становится заметно медленнее
```

Для полезного бюджета определяют:

- **метрику:** что именно измеряется;
- **область действия:** какой маршрут или сценарий;
- **условия:** устройство, сеть, cache и версия приложения;
- **предел:** какое значение допустимо;
- **источник данных:** build, Lighthouse, RUM или CrUX;
- **владельца:** кто отвечает за показатель;
- **действие:** что происходит при превышении.

Упрощённо:

```text
метрика
+
граница
+
контекст
+
владелец
+
реакция
→ рабочий performance budget
```

Запись:

```text
LCP ≤ 2,5 с
```

неполна без уточнения:

- лабораторный это или полевой LCP;
- какой маршрут проверяется;
- mobile или desktop;
- cold или warm load;
- какой percentile;
- за какой период;
- при каком объёме выборки.

### Performance budget, baseline и SLO

Эти понятия связаны, но не полностью совпадают.

**Baseline**

Исходное измеренное состояние:

```text
initial JS = 180 КБ

p75 INP = 170 мс
```

Baseline нужен для сравнения до и после изменения.

**Performance budget**

Максимально допустимая стоимость:

```text
initial JS
≤ 200 КБ
```

**SLO, Service Level Objective**

Целевой уровень production-сервиса за период:

```text
не менее 75% мобильных посещений
имеют LCP ≤ 2,5 с
```

**Alert threshold**

Условие, при котором команда получает уведомление:

```text
p75 INP checkout
> 250 мс

в течение 30 минут

при достаточном числе измерений
```

Budget защищает от внесения регрессии.

SLO описывает ожидаемый production-уровень.

Alert помогает вовремя заметить нарушение.

### Типы бюджетов

Полезно сочетать несколько видов.

| Тип | Пример | Где проверять |
| --- | --- | --- |
| Размер | Initial JS не больше 200 КБ Brotli | Production build в CI |
| Количество | Не больше 25 initial requests | Build report или Lighthouse |
| Структура | Editor SDK отсутствует на login route | Module graph или analyzer |
| Лабораторная метрика | LCP preview не превышает установленный предел | Lighthouse CI |
| User Timing | Открытие редактора занимает не больше 400 мс | Автоматизированный сценарий |
| Полевая метрика | p75 INP checkout не больше 200 мс | Собственный RUM |
| Относительное изменение | Route chunk вырос не больше чем на 10 КБ | Сравнение с base branch |
| Сторонний код | Не больше заданного объёма third-party JS | Network или Lighthouse |
| Backend/сеть | p75 TTFB не больше установленного значения | RUM и server monitoring |

Один общий показатель:

```text
весь JavaScript проекта
```

плохо отражает пользовательский сценарий.

Проект может содержать тяжёлый редактор, но пользователь страницы входа не должен его загружать.

Поэтому важнее:

```text
initial JavaScript конкретного entry point

route JavaScript

критическая цепочка запросов

стоимость конкретного действия
```

### Абсолютный бюджет

Абсолютный бюджет задаёт постоянную границу:

```text
initial JS
≤ 200 КБ
```

Он защищает от накопительного роста.

Но если текущее приложение уже занимает `260 КБ`, такой budget сразу заблокирует все изменения и не поможет определить вклад конкретного merge request.

На переходном этапе можно использовать:

```text
текущий baseline
+
план постепенного снижения
```

Например:

```text
текущий размер = 260 КБ

сейчас budget = 260 КБ

через квартал target = 220 КБ
```

### Относительный бюджет

Относительный budget ограничивает регрессию конкретного изменения:

```text
merge request
не увеличивает initial JS
более чем на 10 КБ
```

Преимущество:

```text
разработчик сразу видит,
какое изменение увеличило стоимость
```

Но только относительного бюджета недостаточно.

Если каждый merge request добавляет по `2 КБ`, а разрешено `10 КБ`, приложение продолжит медленно расти.

Поэтому используют:

```text
абсолютный предел
+
относительное сравнение
```

### Структурный бюджет

Не все ограничения удобно выражать только в байтах.

Примеры:

```text
chart library
не должна попадать
на маршруты без графика

analytics script
не должен загружаться
до consent

PDF library
должна загружаться
только после действия

не допускается
две версии React
```

Такие правила проверяют через:

- dependency graph;
- bundle analyzer;
- manifests;
- lockfile;
- Network;
- custom CI scripts.

Структурный budget часто лучше объясняет причину, чем итоговое число.

### Уровни контроля

Производительность контролируют на нескольких этапах:

```text
source/build
→ лабораторный CI
→ preview или canary
→ production RUM
→ долгосрочный CrUX
```

Каждый уровень отвечает на свой вопрос.

| Уровень | Главный вопрос |
| --- | --- |
| Build | Что именно вошло в сборку? |
| Lab CI | Как страница ведёт себя в фиксированных условиях? |
| Preview/canary | Как новая версия работает в близком к production окружении? |
| RUM | Что испытывают реальные пользователи текущего релиза? |
| CrUX | Как выглядит агрегированный внешний Chrome UX за длительный период? |

Нельзя заменить один уровень другим.

Например:

```text
bundle не вырос
```

не гарантирует:

```text
INP не ухудшился
```

Код мог остаться того же размера, но начать выполнять более тяжёлую инициализацию.

### Build budgets в CI

Наиболее стабильные CI-проверки основаны на результате production build.

Можно проверять:

- initial JavaScript;
- route chunks;
- CSS;
- отдельные async chunks;
- число chunks;
- крупные изображения;
- дубли packages;
- лишние locales;
- third-party modules;
- изменения module graph;
- наличие тяжёлой зависимости в запрещённом маршруте.

Production build выполняют в закреплённом окружении:

- версия Node.js;
- package manager;
- lockfile;
- bundler;
- framework;
- browser targets;
- environment variables;
- feature flags;
- алгоритм и уровень сжатия.

Иначе размер может измениться не из-за кода merge request, а из-за другой версии инструмента.

Полезно хранить два размера:

```text
raw/minified size
+
Brotli или gzip size
```

Raw size ближе к объёму кода после распаковки.

Compressed size ближе к сетевой передаче.

Оба значения не показывают полную CPU-стоимость, поэтому дополняются runtime-профилированием.

### Source maps

Source map часто значительно больше JavaScript-файла, но обычный пользователь не обязан загружать его вместе со страницей.

```text
app.js
→ загружается приложением

app.js.map
→ обычно запрашивается DevTools
  или системой мониторинга
```

Поэтому размер source map не следует автоматически прибавлять к initial JavaScript.

Но в CI полезно проверять:

- не импортируется ли `.map` как обычный ресурс;
- не попадает ли inline source map внутрь production JavaScript;
- не публикуются ли карты там, где это запрещено политикой;
- загружены ли private source maps в error monitoring;
- не учитывает ли analyzer карты как пользовательский transfer.

### Лабораторный CI

Lighthouse или другой synthetic test запускает страницу в контролируемых условиях.

Фиксируют:

- URL;
- production build;
- тестовые данные;
- размер viewport;
- CPU throttling;
- network throttling;
- cache state;
- browser version;
- Lighthouse version;
- состояние backend;
- отсутствие случайных animation и баннеров.

Полезные лабораторные показатели:

- LCP;
- FCP;
- CLS;
- TBT;
- Speed Index;
- TTFB;
- размер ресурсов;
- число запросов;
- DOM size;
- User Timing.

Стандартный page-load запуск Lighthouse не воспроизводит полноценную пользовательскую сессию и поэтому не измеряет реальный INP.

Для раннего сигнала main-thread blocking обычно используют:

```text
TBT
```

Для конкретного действия создают отдельный flow:

```text
открыть страницу
→ выполнить авторизацию
→ нажать кнопку
→ измерить User Timing
```

или используют другой инструмент автоматизации взаимодействий.

```text
TBT
≠
INP
```

Хороший TBT уменьшает риск проблем при загрузке, но не гарантирует хороший INP позднего фильтра, редактора или формы.

### Lighthouse CI

Пример конфигурации:

```js
module.exports = {
  ci: {
    collect: {
      startServerCommand:
        "pnpm start",
      url: [
        "http://localhost:3000/",
        "http://localhost:3000/catalog",
      ],
      numberOfRuns: 5,
      settings: {
        preset: "desktop",
      },
    },

    assert: {
      assertions: {
        "largest-contentful-paint": [
          "error",
          {
            maxNumericValue: 2500,
            aggregationMethod:
              "median",
          },
        ],

        "total-blocking-time": [
          "error",
          {
            maxNumericValue: 300,
            aggregationMethod:
              "median",
          },
        ],

        "cumulative-layout-shift": [
          "error",
          {
            maxNumericValue: 0.1,
            aggregationMethod:
              "pessimistic",
          },
        ],

        "resource-summary:script:size": [
          "error",
          {
            maxNumericValue:
              220 * 1024,
          },
        ],

        "resource-summary:third-party:count": [
          "warn",
          {
            maxNumericValue: 5,
          },
        ],
      },
    },

    upload: {
      target: "filesystem",
      outputDir:
        "./artifacts/lighthouse",
    },
  },
};
```

Конкретные пределы выбирают по проекту и тестовому окружению.

Порог `2,5 с` в лаборатории не является автоматически тем же контрактом, что field p75 LCP `2,5 с`.

Lab test создаёт одно искусственное распределение, а field p75 строится по множеству реальных посещений.

### Несколько запусков Lighthouse

Лабораторные результаты колеблются из-за:

- фоновой нагрузки CPU;
- shared CI runner;
- server startup;
- garbage collection;
- сетевого proxy;
- динамического контента;
- font и image decoding;
- случайной animation;
- third-party response.

Поэтому выполняют несколько запусков.

Lighthouse CI поддерживает разные способы агрегации:

**`median`**

Использовать медиану значений всех запусков.

Подходит как устойчивое центральное значение.

**`optimistic`**

Использовать наиболее благоприятный результат.

Для жёсткой защиты от регрессии обычно слишком мягкий вариант.

**`pessimistic`**

Использовать худший результат.

Полезен для критичных стабильных проверок, но может быть чувствителен к единичному шуму.

**`median-run`**

Использовать показатели одного запуска, выбранного как наиболее репрезентативный.

Он сохраняет внутреннюю согласованность одного отчёта, но значение конкретного audit не обязано совпасть с медианой этого audit по всем запускам.

### Hard gate и warning

Не каждое превышение должно сразу блокировать merge.

**Hard gate:**

```text
CI завершается с ошибкой
```

Подходит для:

- размера initial bundle;
- запрещённой зависимости;
- критического CLS;
- явной крупной регрессии;
- нарушения стабильного абсолютного предела.

**Warning:**

```text
отчёт показывает ухудшение,
но merge технически разрешён
```

Подходит для:

- шумных лабораторных показателей;
- нового бюджета в период настройки;
- слабого сигнала без достаточной повторяемости;
- показателя, для которого ещё нет автоматического remediation.

Хорошая стратегия:

```text
сначала наблюдение
→ затем warning
→ после стабилизации hard gate
```

Если каждое второе изменение требует ручного перезапуска из-за случайного провала, команда начнёт игнорировать budget.

### Почему общий Lighthouse score недостаточен

Performance score является взвешенной комбинацией нескольких лабораторных метрик.

Он может измениться из-за:

- одной метрики;
- изменения весов Lighthouse;
- новой версии Lighthouse;
- округления;
- лабораторного шума.

Например:

```text
score = 91
```

не объясняет:

- вырос ли LCP;
- увеличился ли TBT;
- появился ли CLS;
- вырос ли JavaScript;
- изменился ли TTFB.

Поэтому основной контракт задают через конкретные метрики и ресурсы.

Score можно оставить как обзорный сигнал:

```text
performance score
≥ 90
```

но не как единственную причину блокировки релиза.

### Сравнение с базовой веткой

Для merge request полезно сохранять build report обеих версий:

```text
base branch
→ production build

merge request
→ production build

→ сравнить одинаковые routes
```

Отчёт должен показывать:

- старое значение;
- новое значение;
- абсолютную разницу;
- относительную разницу;
- изменившиеся chunks;
- modules, внесшие вклад;
- превышенный budget.

Пример:

```text
/catalog initial JS

до:
182 КБ Brotli

после:
207 КБ Brotli

изменение:
+25 КБ

причина:
chart-library
```

Сообщение:

```text
budget exceeded
```

без причины плохо помогает разработчику.

### Артефакты CI

При провале сохраняют:

- Lighthouse HTML;
- Lighthouse JSON;
- build stats;
- bundle analyzer report;
- Network trace;
- screenshots;
- browser log;
- версии инструментов;
- конфигурацию throttling.

Это позволяет расследовать ошибку без попыток воспроизвести исчезнувшее CI-окружение.

Отчёты полезно связывать с:

- commit SHA;
- branch;
- pull request;
- release candidate;
- датой запуска.

### RUM

RUM, Real User Monitoring, собирает измерения непосредственно в браузерах реальных пользователей.

Он показывает производительность при реальных:

- устройствах;
- браузерах;
- сетях;
- регионах;
- размерах viewport;
- состояниях cache;
- пользовательских данных;
- длительностях сессий;
- сценариях взаимодействия;
- версиях приложения.

RUM отвечает на вопрос:

```text
Что фактически испытывают пользователи?
```

Лабораторный тест отвечает:

```text
Что происходит
в воспроизводимом тестовом окружении?
```

Оба источника нужны одновременно.

### Сбор Web Vitals

Для стандартного сбора можно использовать:

```ts
import {
  onCLS,
  onINP,
  onLCP,
} from "web-vitals";

type MetricPayload = {
  name: string;
  value: number;
  id: string;
  rating: string;
  route: string;
  releaseId: string;
  navigationType: string;
};

function sendMetric(
  payload: MetricPayload,
) {
  const body =
    JSON.stringify(payload);

  if (
    navigator.sendBeacon(
      "/rum",
      body,
    )
  ) {
    return;
  }

  void fetch(
    "/rum",
    {
      method: "POST",
      body,
      keepalive: true,
      headers: {
        "Content-Type":
          "application/json",
      },
    },
  );
}

function reportMetric(
  metric: {
    name: string;
    value: number;
    id: string;
    rating: string;
    navigationType:
      string;
  },
) {
  sendMetric({
    name:
      metric.name,
    value:
      metric.value,
    id:
      metric.id,
    rating:
      metric.rating,
    route:
      normalizeRoute(
        location.pathname,
      ),
    releaseId:
      RELEASE_ID,
    navigationType:
      metric.navigationType,
  });
}

onCLS(reportMetric);
onINP(reportMetric);
onLCP(reportMetric);
```

Для диагностики причин используют:

```ts
import {
  onCLS,
  onINP,
  onLCP,
} from "web-vitals/attribution";
```

Attribution может добавить сведения о:

- LCP-element;
- LCP-resource;
- фазах LCP;
- interaction target;
- фазах INP;
- largest layout shift;
- сдвинувшихся элементах.

Attribution build немного увеличивает клиентский код, поэтому собирают только действительно используемые поля.

### Повторные callbacks

Callback одной метрики может быть вызван больше одного раза.

Например:

- значение CLS увеличилось;
- найдено более медленное INP-взаимодействие;
- страница стала hidden;
- страница восстановлена из bfcache;
- включён `reportAllChanges`.

Нельзя считать каждый callback отдельным посещением:

```text
одна page view
→ три callback CLS

не означает:
→ три независимых CLS samples
```

Для одной метрики и page view используют `metric.id`.

В собственном хранилище можно:

- обновлять запись по `id`;
- сохранять только финальное значение;
- хранить изменения отдельно, но не смешивать их с page-view distribution.

Для GA-подобных систем иногда передают `delta`, чтобы значения одной метрики корректно суммировались.

Для собственного p75 обычно нужна одна итоговая величина на одно измеряемое посещение.

### Отсутствующие значения

Не каждое посещение создаёт значение каждой метрики.

**INP**

Не сообщается, если пользователь не совершил подходящего взаимодействия.

Нельзя подставлять:

```text
INP = 0
```

Это искусственно улучшит distribution.

**LCP и CLS**

Могут не сообщаться, если страница была загружена в фоновой вкладке.

Такие пропуски нужно хранить как отсутствие измерения, а не как хорошее значение.

Dashboard должен показывать:

- число page views;
- число измерений метрики;
- coverage;
- долю пропущенных значений.

### bfcache

При возврате через back/forward cache страница восстанавливается из памяти без обычной полной загрузки.

Такое посещение часто быстрее обычной навигации.

RUM должен учитывать bfcache отдельно или корректно поддерживать повторное измерение после restore.

Иначе собственный RUM и CrUX могут различаться:

```text
CrUX учитывает bfcache experience

собственный RUM
игнорирует restore

→ RUM показывает
  более медленные данные
```

Полезно сохранять:

```text
navigationType
```

и сравнивать:

- navigate;
- reload;
- back-forward;
- prerender;
- soft navigation, если она поддерживается.

### Что передавать вместе с метрикой

Минимальный полезный контекст:

- название метрики;
- итоговое значение;
- `metric.id`;
- route template;
- release id;
- тип навигации;
- mobile/desktop class;
- browser family;
- приблизительный network class;
- feature flag cohort;
- время измерения.

Для диагностики можно добавить:

- LCP resource type;
- LCP phases;
- interaction type;
- безопасный component identifier;
- first-party или third-party;
- affected UI area;
- server timing.

Сегмент должен помогать принять решение.

Не нужно собирать все доступные browser properties только потому, что они существуют.

### Route template

Вместо полного URL:

```text
/orders/938412?token=...
```

отправляют нормализованный route:

```text
/orders/:id
```

Это:

- уменьшает cardinality;
- объединяет одинаковые страницы;
- защищает пользовательские данные;
- делает dashboard читаемым.

Не следует отправлять:

- access token;
- email в URL;
- search query пользователя;
- содержимое формы;
- текст сообщения;
- полный DOM-текст;
- персональный identifier без необходимости.

### Attribution и приватность

Автоматически созданный CSS selector может содержать:

- пользовательский `id`;
- значение `data-*`;
- динамическое имя;
- структуру приватного интерфейса.

Лучше преобразовывать DOM attribution в безопасный идентификатор:

```text
checkout-submit-button

product-gallery

search-results-list
```

а не передавать сырой HTML или полный selector.

Для `web-vitals/attribution` можно определить собственную функцию преобразования target.

### Sampling

RUM создаёт клиентский и серверный трафик.

Поэтому часто собирают только часть посещений.

Правильный sampling должен быть:

- случайным или детерминированным;
- независимым от значения метрики;
- стабильным внутри выбранной page view или сессии;
- одинаково понятным для разных релизов;
- отражённым в dashboard.

Нельзя отправлять только плохие значения:

```text
отправлять только LCP > 4 с
```

и затем вычислять по ним p75.

Distribution окажется предвзятым.

Допустимая схема:

```ts
const shouldSample =
  Math.random() < 0.1;

if (shouldSample) {
  onCLS(reportMetric);
  onINP(reportMetric);
  onLCP(reportMetric);
}
```

Для стабильного выбора на протяжении сессии sampling decision можно сохранить в session storage.

Нельзя использовать постоянный пользовательский identifier без необходимости только ради sampling.

### RUM overhead

Сам мониторинг не должен заметно ухудшать измеряемый интерфейс.

Проверяют:

- размер библиотеки;
- время её инициализации;
- число observers;
- количество событий;
- объём payload;
- частоту отправки;
- main-thread работу сериализации;
- network requests;
- память.

Не следует многократно вызывать:

```ts
onLCP(...)
onINP(...)
onCLS(...)
```

на каждом React render.

Каждый вызов создаёт observer и listeners на время жизни страницы.

Инициализацию выполняют один раз для page lifecycle.

### p75

p75 — значение, в которое уложились 75% измеренных пользовательских experiences.

Пример отсортированных значений LCP:

```text
1,2
1,4
1,7
2,0
2,3
2,6
3,1
4,5
```

p75 находится ближе к верхней части distribution и лучше среднего показывает опыт заметной доли медленных пользователей.

Для Core Web Vitals проверяют, чтобы все три метрики находились в хорошей категории на p75.

p75 вычисляют по:

```text
одному итоговому значению метрики
на одну подходящую page experience
```

а не по:

- каждому callback;
- каждому layout shift;
- каждой фазе LCP;
- среднему по одному пользователю;
- только плохим событиям.

### Сегментация

Глобальный p75 может скрыть проблему.

Например:

```text
desktop p75 INP
= 120 мс

mobile p75 INP
= 420 мс

общий p75
= 190 мс
```

Общий показатель выглядит приемлемо, хотя мобильный интерфейс плохой.

Обычно анализируют:

- route;
- release;
- mobile/desktop;
- browser;
- navigation type;
- регион;
- network class;
- feature flag;
- authenticated/anonymous;
- cold/warm experience;
- hard/soft navigation.

Сегментация должна сохранять достаточную выборку.

Слишком мелкая комбинация:

```text
route
+
browser version
+
city
+
device model
+
release
+
feature cohort
```

может создать:

- статистический шум;
- высокую cardinality;
- риск идентификации пользователя;
- дорогие dashboards.

### Размер выборки

Alert нельзя строить по нескольким событиям.

Например:

```text
p75 INP = 900 мс

samples = 4
```

недостаточно для уверенного вывода.

Условие alert обычно включает:

- минимальное число samples;
- минимальное число sessions;
- продолжительность нарушения;
- сравнение с baseline;
- величину абсолютного отклонения;
- величину относительного отклонения.

Пример:

```text
mobile checkout

p75 INP > 250 мс

не менее 500 interactions

в течение 30 минут

регрессия относительно baseline
не менее 20%
```

Точные числа зависят от трафика и риска продукта.

### Release id

Каждое событие связывают с неизменяемой версией:

- commit SHA;
- build id;
- deployment id;
- asset version.

Не следует использовать только:

```text
latest
production
main
```

Эти значения меняются со временем и не позволяют восстановить историю.

Release id должен соответствовать реально загруженному клиентскому коду, а не только текущей backend-версии.

При постепенной раскатке одновременно могут существовать несколько frontend releases.

### Canary и поэтапная раскатка

Новая версия сначала получает небольшую долю трафика:

```text
5% пользователей
→ новая версия

95%
→ контрольная версия
```

RUM сравнивает одинаковые сегменты:

- route;
- device class;
- browser;
- регион;
- navigation type;
- период времени.

Если новая версия ухудшает показатель:

```text
остановить rollout

отключить feature flag

откатить release

исправить проблему
```

Нельзя сравнивать:

```text
новый mobile traffic
```

с:

```text
старым desktop traffic
```

или разные сезонные периоды без поправки на изменение аудитории.

### Alerts

Хороший alert содержит:

- метрику;
- текущую величину;
- baseline;
- абсолютное и относительное изменение;
- route;
- device segment;
- release id;
- объём выборки;
- время начала;
- ссылку на dashboard;
- основные attribution-поля.

Плохой alert:

```text
Performance degraded
```

не объясняет:

- где;
- насколько;
- у кого;
- после какого релиза;
- что делать.

Чтобы уменьшить шум, используют:

- минимальную продолжительность;
- минимальную выборку;
- окно агрегации;
- cooldown;
- разные уровни severity;
- подтверждение несколькими последовательными окнами.

### Собственный RUM и CrUX

Оба источника являются field data, но охватывают разную аудиторию.

**Собственный RUM:**

- можно внедрить во все поддерживаемые браузеры;
- доступен для авторизованных маршрутов;
- содержит release id;
- содержит продуктовый контекст;
- появляется почти сразу после релиза;
- управляется владельцем приложения.

**CrUX:**

- собирается из подходящих Chrome users;
- показывает публично обнаруживаемые и достаточно популярные страницы или origin;
- доступен как URL- или origin-distribution;
- использует скользящее окно в 28 дней;
- обновляется ежедневно;
- не содержит ваш release id;
- не покрывает все браузеры и внутренние страницы.

CrUX полезен как независимый внешний ориентир.

Но из-за 28-дневного окна он медленно отражает резкое изменение отдельного релиза.

Для оперативной реакции нужен собственный RUM.

### URL и origin в CrUX

**URL-level**

Показывает данные конкретной страницы, если у неё достаточно подходящих посещений.

**Origin-level**

Объединяет experiences всех страниц origin:

```text
https://example.com
```

Быстрые популярные страницы могут скрыть медленный редкий маршрут.

PageSpeed Insights при отсутствии URL-level данных может показать origin-level данные.

Нужно проверять, какой уровень отображается, прежде чем связывать значение с конкретной страницей.

### Авторизованные маршруты

CrUX требует публичной обнаруживаемости и достаточного трафика.

Поэтому обычно он не показывает:

- внутреннюю admin panel;
- личный кабинет за авторизацией;
- корпоративное приложение;
- preview deployment;
- route с `noindex`;
- редкую страницу.

Для них используют:

- собственный RUM;
- synthetic tests;
- автоматизированные user flows;
- server monitoring;
- controlled test accounts.

### SPA и soft navigations

Исторически Core Web Vitals измеряли жизненный цикл полной document navigation.

SPA-переход:

```text
history.pushState
→ загрузка данных
→ новый React route
```

не создавал новую обычную page navigation, поэтому работа нескольких client routes могла относиться к первоначальной странице.

В Chromium 151+ появилась поддержка измерения soft navigations.

`web-vitals` может отдельно сообщать такие метрики через настройку:

```ts
onLCP(
  reportSoftNavigation,
  {
    reportSoftNavs: true,
  },
);
```

При soft navigation:

- TTFB имеет другое значение и не отражает обычный document request;
- LCP учитывает новые отображённые элементы;
- INP и CLS начинают новый интервал;
- поведение отличается от hard navigation;
- поддержка зависит от браузера.

Hard и soft navigation metrics нельзя бездумно складывать в одну series.

Нужно сохранять navigation type и отдельно проверять:

- browser support;
- версию `web-vitals`;
- соответствие данным CrUX;
- false positive и false negative soft navigations.

### Lab и field могут расходиться

Например:

```text
Lighthouse LCP = 1,8 с

RUM p75 LCP = 3,6 с
```

Причины:

- у пользователей слабее CPU;
- другая сеть;
- другой контент;
- холодный cache;
- другое географическое положение;
- third-party scripts;
- авторизация;
- длительные сессии;
- bfcache;
- SPA-переходы;
- laboratory throttling не соответствует аудитории.

Обратная ситуация тоже возможна:

```text
Lighthouse медленный

field хороший
```

Например, пользователи часто получают:

- CDN hit;
- warm cache;
- preloaded navigation;
- более быстрые устройства;
- bfcache restore.

Lab используют для воспроизведения и диагностики.

Field используют для оценки реального масштаба проблемы.

### Что делать при превышении бюджета

Порядок:

```text
1. Проверить корректность измерения.
2. Подтвердить превышение повторным запуском.
3. Определить route и segment.
4. Найти изменение относительно baseline.
5. Открыть build report или trace.
6. Определить причину.
7. Исправить или откатить изменение.
8. Повторить измерение.
9. Проверить production после release.
```

Возможные причины:

- новая dependency;
- дубли пакета;
- слишком крупное изображение;
- новый third-party script;
- тяжёлый React render;
- длинный handler;
- медленный backend;
- CDN miss;
- изменение контента;
- ошибка sampling;
- новый состав аудитории.

### Исключение из бюджета

Иногда продуктовое изменение оправданно увеличивает стоимость.

Например:

```text
добавлена обязательная
платёжная библиотека
```

Budget можно изменить, но решение должно содержать:

- причину;
- измеренную продуктовую пользу;
- размер регрессии;
- владельца;
- срок исключения;
- компенсирующую оптимизацию;
- новый утверждённый предел.

Плохо:

```text
CI красный
→ увеличить лимит
```

Так budget постепенно теряет защитный смысл.

Полезный формат:

```text
+18 КБ initial JS

причина:
новая обязательная 3DS-интеграция

решение:
разрешено до 1 сентября

компенсация:
удалить старый payment SDK
```

### Практический процесс

```text
1. Выбрать критические routes и actions.
2. Зафиксировать baseline.
3. Задать абсолютные budgets.
4. Добавить relative diff для merge request.
5. Проверять production build.
6. Запускать несколько lab tests.
7. Сохранять отчёты как CI artifacts.
8. Добавить RUM с release id.
9. Собирать безопасную attribution.
10. Строить distributions и p75.
11. Сегментировать по route и device.
12. Добавить минимальный sample size.
13. Настроить alerts.
14. Проверять canary rollout.
15. Подтверждать field result после release.
```

### Главная модель

```text
Build budget
→ не позволить приложению
  незаметно стать тяжелее

Lab CI
→ воспроизвести основные проблемы
  до release

RUM
→ измерить реальный UX
  конкретной версии

CrUX
→ получить внешний
  долгосрочный field benchmark
```

Главный принцип:

```text
performance budget
имеет смысл только тогда,
когда превышение приводит
к понятному инженерному действию
```

<details>
<summary><strong>Чем абсолютный бюджет отличается от относительного?</strong></summary>

<dl>
<dd>
<h2></h2>

Абсолютный budget задаёт постоянную границу:

```text
initial JS
≤ 200 КБ
```

Относительный ограничивает изменение:

```text
merge request
≤ +10 КБ
```

Только относительный budget допускает накопление множества небольших регрессий.

Только абсолютный может поздно показать конкретного виновника.

Поэтому их используют вместе:

```text
не превысить общий предел

и:

не допустить крупную
регрессию одного изменения
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему бюджеты лучше задавать по маршрутам?</strong></summary>

<dl>
<dd>
<h2></h2>

Разные routes требуют разный код.

Страница входа не должна оплачивать:

- редактор;
- графики;
- admin tools;
- PDF export;
- тяжёлую карту.

Общий размер всех chunks проекта не показывает, сколько получит пользователь конкретной точки входа.

Поэтому отдельно контролируют:

- initial route;
- shared runtime;
- route-specific code;
- async features;
- third-party resources.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверять размер bundle в CI?</strong></summary>

<dl>
<dd>
<h2></h2>

Выполняют production build в закреплённом окружении.

Сохраняют:

- raw/minified size;
- Brotli или gzip size;
- initial chunks;
- async chunks;
- route mapping;
- module contribution;
- dependency duplicates.

Затем сравнивают:

```text
текущий build
с budget

и:

merge request
с base branch
```

При провале отчёт должен показывать изменившийся chunk и modules, внесшие вклад.

<h2></h2>
</dd>
</dl>

<details>
<summary><strong>Почему Lighthouse в CI даёт разные результаты?</strong></summary>

<dl>
<dd>
<h2></h2>

На результат влияют:

- CPU runner;
- browser version;
- server startup;
- network proxy;
- garbage collection;
- cache;
- динамический контент;
- animation;
- third-party services.

Поэтому:

- фиксируют окружение;
- выполняют несколько прогонов;
- выбирают явный aggregation method;
- хранят каждый отчёт;
- оставляют допуск для нестабильной метрики;
- не блокируют release по случайному score одного запуска.

Для стабильных build-размеров допустим более жёсткий gate, чем для шумного laboratory timing.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем итоговый балл Lighthouse отличается от бюджета конкретной метрики?</strong></summary>

<dl>
<dd>
<h2></h2>

Performance score объединяет несколько лабораторных показателей с определёнными весами.

Он удобен как обзор, но не объясняет причину.

Budget конкретной метрики показывает точное нарушение:

```text
LCP > 2,5 с

TBT > 300 мс

initial JS > 200 КБ
```

Изменение версии Lighthouse или весов способно изменить score без аналогичного изменения пользовательского сценария.

Поэтому конкретные metrics являются основным контрактом, а score — дополнительным сигналом.

</dd>

<details>
<summary><strong>Что такое RUM и какие данные он должен отправлять?</strong></summary>

<dl>
<dd>
<h2></h2>

RUM собирает performance measurements в браузерах реальных пользователей.

Минимальное событие содержит:

- имя метрики;
- значение;
- metric id;
- route template;
- release id;
- navigation type;
- время.

Для диагностики добавляют безопасный контекст:

- device class;
- browser;
- network class;
- LCP resource type;
- interaction category;
- feature cohort.

Не отправляют token, содержимое форм, пользовательский текст и чувствительный полный URL.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему для Web Vitals смотрят p75, а не среднее?</strong></summary>

<dl>
<dd>
<h2></h2>

p75 — значение, в которое уложились 75% измерений.

Среднее может скрыть заметную медленную группу или сильно измениться из-за отдельных выбросов.

Core Web Vitals оценивают по p75 distribution.

В p75 должны входить итоговые значения отдельных page experiences, а не:

- каждый callback;
- каждый layout shift;
- каждая фаза interaction;
- только плохие события.

Для внутренней диагностики дополнительно смотрят p50, p90 и p95 при достаточной выборке.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как сегментировать полевые данные?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычно сравнивают:

- routes;
- releases;
- mobile и desktop;
- browser families;
- navigation types;
- regions;
- network classes;
- feature cohorts.

Сегмент должен быть достаточно крупным для устойчивой статистики.

Слишком детальное разбиение создаёт:

- шум;
- высокую cardinality;
- риск идентификации;
- дорогие dashboards.

Сначала используют крупные практически значимые сегменты, затем уточняют проблемную группу.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем собственный RUM отличается от CrUX?</strong></summary>

<dl>
<dd>
<h2></h2>

Собственный RUM:

- содержит release id;
- покрывает авторизованные routes;
- появляется почти сразу;
- может включать нужные браузеры;
- содержит продуктовую attribution.

CrUX:

- использует подходящие Chrome experiences;
- требует публично обнаруживаемый и достаточно популярный URL или origin;
- показывает скользящее окно за 28 дней;
- не содержит release id;
- предоставляет независимый внешний benchmark.

CrUX не заменяет оперативный release monitoring, а собственный RUM не обязан полностью совпадать с аудиторией CrUX.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как связать ухудшение с конкретным релизом?</strong></summary>

<dl>
<dd>
<h2></h2>

Вместе с метрикой отправляют неизменяемый:

- build id;
- commit SHA;
- deployment id;
- asset version.

Dashboard сравнивает одинаковые route и device segments до и после rollout.

Нужно учитывать, что во время постепенной раскатки пользователи одновременно работают с несколькими frontend releases.

Release id должен соответствовать коду, реально загруженному браузером.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как настроить уведомление об ухудшении производительности?</strong></summary>

<dl>
<dd>
<h2></h2>

Alert привязывают к:

- метрике;
- route;
- segment;
- threshold;
- минимальному объёму samples;
- продолжительности нарушения;
- release id;
- baseline.

Например:

```text
mobile checkout

p75 INP > 250 мс

не менее 500 interactions

30 минут подряд
```

В уведомлении нужны текущее значение, baseline, величина изменения и ссылка на dashboard.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать при превышении бюджета?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала проверяют корректность теста.

Затем определяют:

- изменившийся route;
- metric;
- segment;
- module;
- resource;
- release.

После этого:

- исправляют причину;
- откатывают изменение;
- отключают feature;
- останавливают rollout;
- либо явно согласуют изменение budget.

Молчаливое увеличение лимита уничтожает смысл защиты.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие ограничения есть у RUM?</strong></summary>

<dl>
<dd>
<h2></h2>

RUM:

- добавляет клиентский код и telemetry;
- зависит от browser API;
- видит только реальные посещённые scenarios;
- медленно накапливает данные редких routes;
- может отличаться от CrUX;
- требует sampling;
- требует защиты приватности;
- зависит от качества aggregation.

Отсутствие INP без взаимодействия и повторные metric callbacks нужно учитывать отдельно.

RUM не заменяет controlled lab reproduction, когда требуется найти конкретную строку кода.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем hard budget отличается от warning?</strong></summary>

<dl>
<dd>
<h2></h2>

Hard budget завершает CI с ошибкой и блокирует изменение.

Он подходит для стабильных и критичных ограничений:

- bundle size;
- запрещённая dependency;
- крупная регрессия;
- стабильный CLS.

Warning сообщает о риске, но не блокирует merge.

Он подходит для:

- шумных timings;
- бюджета в период настройки;
- слабого сигнала;
- метрики без автоматического remediation.

Со временем стабильный warning можно повысить до hard gate.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли жёстко блокировать CI по LCP одного запуска?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычно это ненадёжно.

Laboratory LCP зависит от CPU, server response, image decoding, browser version и других условий.

Используют:

- несколько запусков;
- median или другой явный aggregation method;
- стабильное окружение;
- разумный допуск;
- сохранённые отчёты.

Жёсткий gate оправдан только после проверки повторяемости теста.

Build size обычно является более детерминированным показателем.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как правильно агрегировать повторные callbacks <code>web-vitals</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Callbacks одной метрики могут приходить несколько раз в рамках одной page experience.

Они имеют общий `metric.id`.

Нельзя считать каждый callback отдельным посещением.

Варианты:

- обновлять запись по `metric.id`;
- сохранять итоговое значение;
- отправлять `delta` в систему, которая суммирует изменения;
- отделять debug changes от итоговой distribution.

Для p75 нужна одна итоговая величина на одну подходящую page experience.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как sampling может исказить RUM?</strong></summary>

<dl>
<dd>
<h2></h2>

Sampling искажает данные, если вероятность отправки зависит от результата.

Плохо:

```text
отправлять только
медленные посещения
```

После этого нельзя вычислить реальный p75.

Решение принимают до получения метрики:

```text
эта page view участвует в RUM
или не участвует
```

Выбор должен быть независимым от скорости и одинаково применяться к сравниваемым releases.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как учитывать восстановление страницы из bfcache?</strong></summary>

<dl>
<dd>
<h2></h2>

Back/forward cache восстанавливает уже загруженную страницу из памяти.

Такой переход отличается от обычной полной navigation и часто значительно быстрее.

RUM должен:

- распознавать restore;
- корректно запускать новое измерение;
- сохранять navigation type;
- не смешивать callbacks разных experiences.

Игнорирование bfcache может привести к расхождению собственного RUM и CrUX.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как измерять client-side переходы SPA?</strong></summary>

<dl>
<dd>
<h2></h2>

Исторически стандартные Core Web Vitals относились к полной document navigation.

В Chromium 151+ появилась поддержка soft navigation measurement, а `web-vitals` может сообщать её через:

```ts
{
  reportSoftNavs: true,
}
```

Поддержка различается между браузерами.

Soft navigation имеет другую модель TTFB, LCP, INP и CLS.

Поэтому данные сохраняют отдельно от hard navigation и явно отмечают тип перехода.

Также полезны предметные User Timing metrics:

```text
route-change-start
→ route-content-visible
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли получить CrUX для личного кабинета?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычно нет.

CrUX требует публично обнаруживаемые страницы и достаточный объём подходящих Chrome experiences.

Авторизованный route, admin panel или страница с `noindex` обычно не получает URL-level CrUX.

Для таких страниц используют:

- собственный RUM;
- synthetic user flows;
- preview tests;
- controlled accounts;
- backend monitoring.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли включать source maps в размер пользовательского bundle?</strong></summary>

<dl>
<dd>
<h2></h2>

Не всегда.

Отдельный `.map` обычно не загружается при обычной работе приложения.

Он запрашивается DevTools или передаётся отдельно системе error monitoring.

Но inline source map находится внутри JavaScript и увеличивает transfer.

В CI проверяют фактический Network graph и способ публикации source maps, а не механически складывают все build artifacts.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как performance monitoring связан с постепенной раскаткой?</strong></summary>

<dl>
<dd>
<h2></h2>

Новую версию сначала получают несколько процентов пользователей.

RUM сравнивает новую и контрольную группы при одинаковых:

- routes;
- devices;
- browsers;
- regions;
- navigation types.

При подтверждённой регрессии можно:

- остановить rollout;
- отключить feature flag;
- вернуть предыдущую версию;
- продолжить после исправления.

Для решения нужны достаточная выборка и release id каждого события.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Контроль |
| --- | --- |
| Merge request добавляет тяжёлую библиотеку | Сравнение chunks, module graph и bundle analyzer |
| Preview deployment стал медленнее | Несколько запусков Lighthouse CI с сохранёнными отчётами |
| После релиза вырос INP только на мобильных | RUM по route, device class и release id |
| Lighthouse score изменился без понятной причины | Проверка конкретных metrics и версии Lighthouse |
| Метрика колеблется без изменения кода | Проверка sample size, аудитории, backend и third-party |
| RUM p75 неожиданно стал лучше после sampling | Проверка unbiased sampling и отсутствующих значений |
| Один CLS callback учитывается несколько раз | Агрегация по metric id и итоговому значению |
| Авторизованный маршрут отсутствует в CrUX | Собственный RUM и synthetic user flow |
| SPA route кажется быстрым, но hard-navigation RUM этого не показывает | Soft navigation или предметный User Timing |
| Новая возможность оправданно увеличивает bundle | Формальное исключение с причиной, сроком и компенсацией |
| Canary ухудшает p75 LCP | Остановить rollout или отключить feature |
| CI стабильно проходит, а production ухудшается | Анализ реальных устройств, контента, cache и сети |
