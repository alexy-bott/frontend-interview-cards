## Вопрос

<br>

 💬 **Как размер bundle влияет на производительность? Как уменьшать JavaScript и строить стратегию загрузки?**

<h2></h2>

<br>
<dl>
<dd>

Bundle - файл или группа файлов, которые сборщик создает из модулей приложения. Его стоимость не заканчивается скачиванием: браузер получает сжатые байты, распаковывает их, разбирает JavaScript, компилирует и выполняет код. На слабом мобильном CPU небольшой по объему сетевой передачи файл может надолго занять main thread.

Поэтому различают несколько размеров и этапов:

| Показатель | Что показывает |
|---|---|
| Raw size | размер файла сборки без сетевого сжатия |
| Transfer size | сколько байтов фактически передано после gzip или Brotli с учетом кеша |
| Resource size | размер ресурса после распаковки |
| Parse/compile time | время разбора и компиляции JavaScript |
| Execution time | время инициализации модулей и выполнения прикладного кода |

Для первого экрана важнее начальный JavaScript и цепочка критических запросов, чем сумма всех lazy chunks проекта. Код редактора, который загружается только после явного открытия, не должен попадать в initial bundle страницы входа. Но если первый экран сразу требует lazy chunk, code splitting только добавит последовательный запрос и создаст waterfall, то есть зависимую цепочку загрузки.

Основная стратегия загрузки:

1. Измерить initial bundle и bundles отдельных маршрутов через статистику сборки и bundle analyzer.
2. Разделить код по маршрутам и тяжелым функциям, которые действительно используются позже.
3. Удалить неиспользуемые exports через tree shaking и проверить побочные эффекты модулей.
4. Найти крупные библиотеки, дубли версий, лишние локали, polyfills и слишком старые целевые браузеры.
5. Настроить стабильные content hash и разумные общие chunks для повторного кеширования.
6. Включить minification и сетевое сжатие на сервере или CDN.
7. Проверить временную диаграмму Network и запись Performance: размер файла и стоимость выполнения являются разными проблемами.

Code splitting, или разделение кода, создает отдельные chunks. В JavaScript границей часто является динамический `import()`:

```ts
async function openReportEditor() {
  const { ReportEditor } = await import('./ReportEditor');
  mountEditor(ReportEditor);
}
```

Этот код полезен, если редактор открывается не при каждом посещении. Для обязательного компонента первого экрана такой import может отложить rendering до завершения дополнительного сетевого запроса.

Tree shaking, или удаление неиспользуемых exports, требует статически анализируемых ES modules и production-сборки с оптимизацией. Bundler должен доказать, что модуль можно не выполнять. Поле `sideEffects` в `package.json` помогает исключать целые файлы, но ошибочное `sideEffects: false` может удалить импорт CSS, polyfill или регистрацию глобального обработчика.

Hash в имени, например `app.a1b2c3.js`, связывает URL с содержимым. Такой chunk можно кешировать надолго. Однако изменение общего vendor chunk с кодом зависимостей может заставить пользователей скачать его заново, даже если изменилась одна небольшая библиотека. Стратегия разбиения балансирует число начальных запросов, повторное использование кеша и стабильность имен, а не стремится создать минимально или максимально возможное число файлов.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем module, bundle и chunk отличаются друг от друга?</strong></summary>

<dl>
<dd>
<h2></h2>

Module - исходная единица кода с `import` и `export`. Bundle - результат сборки одного или многих модулей. Chunk - часть графа сборки, которая может быть выведена в отдельный файл и загружена независимо.

Один chunk не обязательно равен одному исходному файлу, а один маршрут может потребовать несколько chunks: собственный код, общие зависимости и CSS.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое code splitting и где ставить границы?</strong></summary>

<dl>
<dd>
<h2></h2>

Code splitting делит приложение на части, которые загружаются по необходимости. Естественные границы - маршруты, редко открываемые модальные окна, тяжелые редакторы, графики и административные функции. В React для компонентов используют `lazy`, а роутеры и Next.js создают часть границ по маршрутам автоматически.

Граница полезна, если код с высокой вероятностью не нужен сейчас. Если сразу после первого render запускается import обязательного chunk, пользователь получает дополнительную последовательную загрузку без уменьшения работы текущего сценария.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает dynamic <code>import()</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`import()` возвращает Promise с объектом exports загруженного модуля. Bundler обычно использует место вызова как асинхронную границу и создает отдельный chunk. Браузер загружает его при выполнении import либо раньше, если framework настроил prefetch или preload.

Ошибки загрузки chunk нужно обрабатывать. После деплоя старый HTML или открытая SPA-вкладка может запросить уже удаленный файл, поэтому старые файлы сборки некоторое время сохраняют, а приложению добавляют контролируемое обновление страницы или error boundary с восстановлением.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>При каких условиях работает tree shaking?</strong></summary>

<dl>
<dd>
<h2></h2>

Bundler должен видеть статические `import`/`export`, знать используемые exports и выполнять production-оптимизацию с minimizer. Если Babel заранее превращает ES modules в CommonJS, пакет скрывает структуру exports или код выбирает свойства динамически, анализ становится слабее.

Tree shaking не обязан удалить каждую неиспользуемую функцию. Bundler сохраняет код, если его выполнение может иметь побочный эффект или если безопасность удаления нельзя доказать.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означает <code>sideEffects</code> в <code>package.json</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`"sideEffects": false` сообщает bundler, что импорт файлов пакета не выполняет важную работу помимо предоставления exports. Тогда полностью неиспользуемый модуль и его поддерево можно удалить. Массив позволяет перечислить файлы, которые должны выполняться, например `"*.css"` или setup-модуль.

Неверная декларация ломает поведение production build: может исчезнуть CSS, polyfill, регистрация custom element или обработчика. Значение проверяют в собранном приложении, а не выставляют только ради меньших цифр в analyzer.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем tree shaking отличается от dead code elimination?</strong></summary>

<dl>
<dd>
<h2></h2>

Tree shaking анализирует граф модулей и исключает неиспользуемые exports и модули. Dead code elimination удаляет недостижимые или доказуемо ненужные инструкции внутри кода, например ветку `if (false)` после подстановки константы сборки.

На практике bundler и minimizer выполняют оба вида оптимизации вместе. Результат зависит от статического анализа, побочных эффектов и production-констант.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему размер после gzip или Brotli не показывает всю стоимость JavaScript?</strong></summary>

<dl>
<dd>
<h2></h2>

Сжатый размер показывает объем сетевой передачи, но после получения браузер восстанавливает исходный текст, разбирает, компилирует и выполняет его. Повторяющийся код отлично сжимается, но все равно может создавать большое синтаксическое дерево (AST) и выполнять дорогую инициализацию.

Поэтому отчет о bundle сравнивают с записью Performance и Coverage. Для слабого CPU сокращение времени выполнения может быть важнее еще нескольких килобайт Brotli.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем опасны слишком мелкие chunks?</strong></summary>

<dl>
<dd>
<h2></h2>

Каждый chunk добавляет служебные данные запроса, планирование загрузки и риск последовательной зависимости. Если chunk A только после выполнения обнаруживает B, возникает waterfall. Большое число крошечных chunks также усложняет управление кешем и может создавать конкуренцию за сетевой приоритет.

HTTP/2 и HTTP/3 уменьшают стоимость нескольких запросов, но не отменяют сетевую задержку и обработку каждого ресурса. Границы выбирают по сценариям, а результат проверяют по дереву зависимостей в Network panel.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем выделять shared или vendor chunks?</strong></summary>

<dl>
<dd>
<h2></h2>

Общий chunk позволяет нескольким маршрутам один раз загрузить React или другую зависимость и переиспользовать кеш. Если общий код стабилен, изменение chunk отдельной функции не меняет его content hash.

Слишком большой vendor chunk ухудшает начальную загрузку и получает новый hash при изменении любой зависимости внутри. Слишком мелкое дробление создает много запросов. Настройки bundler по умолчанию являются отправной точкой, а не универсально идеальной стратегией.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как две версии одной зависимости попадают в bundle?</strong></summary>

<dl>
<dd>
<h2></h2>

Разные пакеты могут требовать несовместимые диапазоны semver, либо package manager не может объединить одинаковые зависимости в одну версию. Тогда дерево зависимостей содержит несколько копий. Это видно в lock-файле, через `npm ls`, `pnpm why` и bundle analyzer.

Возможные исправления: выровнять версии, обновить зависимые пакеты, корректно использовать peer dependency или заменить библиотеку. Принудительный override применяют только после проверки совместимости, иначе уменьшение bundle может привести к ошибке во время выполнения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как понять, что именно попало в bundle?</strong></summary>

<dl>
<dd>
<h2></h2>

Статистика сборки и analyzer показывают модули, chunks, причины включения и размеры. Source maps позволяют связать минифицированный результат с исходными пакетами. Coverage в DevTools показывает код, который не выполнился в записанном сценарии.

Coverage не доказывает, что код не нужен вообще: пользователь мог не открыть модальное окно или не вызвать обработку ошибки. Проверяют несколько критичных маршрутов и действий, а затем меняют границу загрузки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему development build нельзя использовать для оценки bundle?</strong></summary>

<dl>
<dd>
<h2></h2>

Development build содержит HMR runtime, предупреждения, исходные имена и упрощенные настройки оптимизации. Tree shaking и минификация могут работать иначе, а React добавляет development-проверки.

Размер, граф chunks и время выполнения измеряют на production build с теми же переменными окружения и целевыми браузерами, которые используются при реальном деплое. Source maps можно генерировать отдельно, не включая их загрузку пользователем по умолчанию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли импорт одной функции загрузить всю библиотеку?</strong></summary>

<dl>
<dd>
<h2></h2>

Может, если пакет публикует CommonJS bundle, файл с повторными exports выполняет побочные эффекты или bundler не видит отдельные exports. В ESM-пакете точечный named import обычно позволяет удалить неиспользуемое, но только если пакет корректно собран и описан.

Менять `import { fn } from 'lib'` на внутренний путь стоит только по документированному публичному API: внутренние пути могут исчезнуть после обновления. Фактический результат проверяют в analyzer, а не угадывают по синтаксису import.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что проверять |
|---|---|
| Код редактора попал на страницу входа | разделение по маршрутам или функциям и причины включения модуля |
| После деплоя возникает ChunkLoadError | срок хранения старых файлов сборки и сценарий восстановления |
| Bundle вырос после установки пакета | модули, локали, polyfills и дубли версий |
| Первый экран ждет lazy chunk | неправильная граница code splitting и последовательная загрузка |
| Частое изменение hash общего кода | состав shared chunk и долгосрочное кеширование |
