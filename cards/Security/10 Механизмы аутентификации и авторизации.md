## Вопрос

<br>

 💬 **Чем отличаются server-side session, JWT, OAuth 2.0 и OpenID Connect? Как работает сценарий Authorization Code с PKCE?**

<h2></h2>

<br>
<dl>
<dd>

Server-side session, JWT, OAuth 2.0 и OpenID Connect описывают разные уровни системы.

| Понятие | Что оно описывает |
| --- | --- |
| Server-side session | Где приложение хранит состояние пользовательского входа |
| JWT | В каком формате передаются подписанные или зашифрованные claims |
| OAuth 2.0 | Как client получает ограниченный доступ к resource server |
| OpenID Connect | Как client получает проверяемый результат аутентификации пользователя |
| Авторизация приложения | Может ли конкретный пользователь выполнить действие над конкретным ресурсом |

Они не являются взаимоисключающими.

Например:

```text
OpenID Connect
→ используется для входа

OAuth
→ выдаёт access token для API

ID token
→ имеет формат JWT

BFF
→ хранит OAuth tokens на server

Browser
→ получает server-side session ID
  в HttpOnly cookie
```

### Три независимые оси

При проектировании authentication полезно отдельно ответить на три вопроса.

#### 1. Где хранится состояние входа?

```text
server-side session

или:

данные переносятся
в самостоятельно проверяемом token
```

#### 2. В каком формате передаются credentials?

```text
непрозрачная случайная строка

JWT

другой формат
```

#### 3. Как client получил доступ или identity?

```text
собственный login приложения

OAuth 2.0

OpenID Connect

другой federation protocol
```

Поэтому утверждение:

```text
Мы используем JWT вместо OAuth
```

сравнивает понятия разных уровней.

JWT может быть одним из форматов token внутри OAuth.

А OAuth access token вообще не обязан быть JWT.

---

### Server-side session

При server-side session приложение хранит состояние входа на server.

Browser обычно получает только случайный идентификатор:

```http
Set-Cookie:
  __Host-session=RANDOM_SESSION_ID;
  Secure;
  HttpOnly;
  SameSite=Lax;
  Path=/
```

Server хранит:

```text
session ID
→ user ID
→ roles
→ authentication time
→ expiration
→ CSRF state
→ OAuth tokens
→ другие session attributes
```

Request:

```http
Cookie:
  __Host-session=RANDOM_SESSION_ID
```

Server находит session и определяет текущего пользователя.

Схема:

```text
Browser
  |
  | session ID
  v
Application server
  |
  | lookup
  v
Session store
```

### Session ID является credential

Хотя session ID ничего не сообщает о пользователе, тот, кто получил действительное значение, обычно может предъявить его server.

Поэтому session ID является bearer credential:

```text
кто предъявляет ID
→ получает связанную session
```

Он должен быть:

- случайным;
- непредсказуемым;
- достаточно длинным;
- непрозрачным;
- не содержащим персональные данные;
- передаваемым только через HTTPS;
- защищённым cookie attributes;
- отзываемым server.

Плохо:

```text
session ID =
userId + timestamp
```

Лучше:

```text
session ID =
криптографически случайная строка
```

Вся бизнес-информация остаётся в session store.

### Lifecycle server-side session

#### Создание

До входа пользователь может иметь анонимную session.

После успешной аутентификации server создаёт новый session ID.

#### Rotation

Session ID заменяют после:

- login;
- MFA;
- повышения privileges;
- смены роли;
- смены пользователя;
- критичного изменения authentication state.

Старый ID инвалидируют.

Это защищает от session fixation.

#### Idle timeout

Session завершается после периода бездействия:

```text
нет активности N минут
→ повторная аутентификация
```

#### Absolute timeout

Session имеет максимальную продолжительность независимо от активности:

```text
с момента login прошло N часов
→ session завершается
```

Атакующий не должен иметь возможность бесконечно продлевать украденную session обычными requests.

#### Logout

При logout server:

- инвалидирует session;
- удаляет или помечает запись недействительной;
- очищает cookie;
- отзывает связанные refresh tokens при необходимости;
- записывает событие в audit.

Удаления React state недостаточно.

### Преимущества server-side session

- немедленный централизованный отзыв;
- server всегда видит актуальные права;
- можно изменить session без перевыпуска client credential;
- session ID не раскрывает claims;
- удобно завершать отдельные устройства;
- удобно применять idle и absolute timeout;
- OAuth tokens могут не попадать в browser.

### Недостатки server-side session

- требуется session store;
- нужно очищать истёкшие записи;
- состояние нужно масштабировать между instances;
- отказ session store может повлиять на login;
- cookie-authenticated requests требуют CSRF-защиту.

Общий Redis, database или другой distributed store позволяет нескольким application instances работать с одной session без хранения состояния только в памяти конкретного процесса.

### JWT

**JWT, JSON Web Token**, — формат передачи набора claims в JSON.

JWT не является:

- полным login flow;
- способом хранения session по определению;
- заменой OAuth;
- заменой authorization;
- обязательным access token;
- автоматически stateless-архитектурой.

### JWS

Типичный подписанный JWT имеет три части:

```text
header.payload.signature
```

Пример структуры:

```json
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "key-2026-08"
}
```

```json
{
  "iss": "https://auth.example.com",
  "sub": "user-42",
  "aud": "orders-api",
  "exp": 1786020000,
  "iat": 1786019400,
  "scope": "orders:read"
}
```

Это обычно **JWS**, то есть подписанное сообщение.

Signature защищает:

- целостность header;
- целостность payload;
- подлинность издателя при доверенном ключе.

Signature не скрывает payload.

Любой получивший token может выполнить base64url decoding и прочитать claims.

```text
base64url
≠
шифрование
```

Поэтому в обычный подписанный JWT не помещают:

- passwords;
- client secrets;
- refresh tokens;
- лишние персональные данные;
- данные, которые получатель token не должен видеть.

### JWE

**JWE** используется для шифрования.

Compact JWE обычно содержит пять частей:

```text
protected-header
.encrypted-key
.iv
.ciphertext
.authentication-tag
```

JWT может быть:

- подписанным JWS;
- зашифрованным JWE;
- вложенным, например signed JWT внутри encrypted JWE.

Шифрование повышает сложность key management и не заменяет signature, validation, TLS и authorization.

### Decode и verify

Это разные операции.

#### Decode

```text
base64url decode
→ получить JSON
```

Decode не доказывает, что token:

- выпустил доверенный issuer;
- не был изменён;
- предназначен этому API;
- ещё действует;
- является access token нужного типа.

#### Verify

```text
проверить cryptography
+
проверить claims
+
проверить назначение
```

Backend принимает решения только после полной verification.

Плохо:

```ts
const payload =
  decodeJwt(token);

if (payload.role === "admin") {
  allow();
}
```

Здесь payload прочитан, но не доказана его подлинность.

### Что проверять в JWT

#### Algorithm

Приложение задаёт allowlist ожидаемых algorithms:

```text
RS256
```

или:

```text
ES256
```

Нельзя принимать любой algorithm только потому, что он указан в token header.

Плохо:

```text
token говорит alg=...

→ library автоматически доверяет
  выбранному token алгоритму
```

Server configuration определяет допустимые algorithms и подходящие keys.

`alg: none` отклоняется, если приложение явно не реализует специальный сценарий unsecured JWT.

#### Signature или MAC

Проверяется криптографическая целостность token с доверенным key.

#### Issuer

```text
iss
```

должен точно совпадать с ожидаемым issuer.

```text
https://auth.example.com
```

не равно:

```text
https://attacker.example
```

даже если attacker token имеет похожие claims.

#### Audience

```text
aud
```

показывает предполагаемого получателя token.

Access token для:

```text
payments-api
```

нельзя принимать в:

```text
admin-api
```

только потому, что оба API доверяют одному issuer.

#### Expiration

```text
exp
```

ограничивает срок действия.

Server использует собственное доверенное время и допускает только небольшой контролируемый clock skew.

#### Not before

```text
nbf
```

может запрещать использование token до указанного времени.

#### Issued at

```text
iat
```

помогает оценивать возраст token и применять дополнительные policy.

Но само наличие `iat` не доказывает, что token свежий или не был отозван.

#### Subject

```text
sub
```

идентифицирует subject в контексте конкретного issuer.

Одинаковый `sub` у разных issuers не обязан обозначать одного пользователя.

Составной identity key обычно выглядит так:

```text
issuer + subject
```

#### Token type и назначение

Приложение должно понимать:

```text
это access token?

ID token?

logout token?

authorization response JWT?

security event token?
```

Для разных видов JWT применяют разные validation rules.

Нельзя принимать ID token в API только потому, что:

- signature корректна;
- issuer тот же;
- внутри есть `sub`;
- внутри есть roles.

### Подмена разных видов JWT

Один issuer может выпускать:

- ID tokens;
- access tokens;
- refresh-related assertions;
- logout tokens;
- client authentication assertions.

Если все они принимаются одной общей функцией с одинаковыми правилами, возможна cross-JWT confusion.

Защита:

- разные expected audiences;
- разные обязательные claims;
- разные `typ`;
- разные keys при необходимости;
- отдельные validation functions;
- взаимоисключающие правила.

Например, JWT access token по соответствующему профилю может иметь:

```json
{
  "typ": "at+jwt"
}
```

ID token не должен автоматически проходить access-token validator.

### `kid` и JWKS

JWT header может содержать:

```text
kid
```

Он помогает выбрать key среди набора доверенных публичных ключей issuer.

Типичный процесс:

```text
1. Приложение заранее доверяет issuer.
2. Получает его metadata.
3. Получает JWKS с доверенного jwks_uri.
4. Находит key по kid.
5. Проверяет algorithm и signature.
6. Проверяет claims.
```

`kid` не является доказательством доверия.

Нельзя использовать его как:

- filename без validation;
- SQL fragment;
- URL;
- команду;
- произвольный путь к key.

Header-параметры вроде `jku` или `x5u` нельзя безусловно использовать для загрузки key с URL, указанного самим атакующим token.

Иначе возможны:

- SSRF;
- использование attacker key;
- обход trusted issuer configuration.

### Key rotation

Issuer может менять signing keys.

При rotation:

```text
старый key
→ некоторое время остаётся в JWKS

новый key
→ используется для новых tokens
```

Verifier должен:

- кешировать JWKS разумное время;
- обновлять keys при неизвестном `kid`;
- ограничивать частоту refresh;
- не обращаться к произвольному host;
- учитывать срок старых tokens;
- корректно переживать временный сетевой сбой.

### JWT не обязательно означает stateless

JWT может проверяться локально без session lookup.

Но система может всё равно хранить server state для:

- revocation;
- token version;
- consent;
- user status;
- role changes;
- refresh token family;
- device sessions;
- audit;
- logout;
- risk decisions.

И наоборот, JWT может храниться внутри server-side session и вообще не передаваться browser.

```text
JWT format
≠
обязательная stateless architecture
```

### Устаревшие claims

Если JWT содержит:

```json
{
  "role": "admin"
}
```

claim отражает состояние на момент выпуска token.

Если роль была отозвана, token может сохранять старое значение до:

- `exp`;
- server-side revocation;
- изменения token version;
- introspection;
- другой проверки актуального состояния.

Поэтому критичная authorization может требовать server-side проверки актуальных данных.

### OAuth 2.0

**OAuth 2.0** — authorization framework, через который client получает ограниченный доступ к protected resource.

OAuth отвечает на вопрос:

```text
Как client получил право
обратиться к resource server?
```

OAuth не определяет универсальный способ:

```text
войти пользователя
в client-приложение
```

Для этого применяется OpenID Connect либо собственная authentication-система.

### Роли OAuth

#### Resource owner

Участник, способный предоставить доступ к ресурсу.

В пользовательском flow это обычно пользователь.

#### Client

Приложение, которое запрашивает доступ.

Например:

- SPA;
- mobile application;
- backend;
- CLI;
- BFF;
- machine-to-machine service.

#### Authorization server

- аутентифицирует пользователя при необходимости;
- получает authorization decision;
- выдаёт authorization code;
- выдаёт access и refresh tokens;
- управляет OAuth grant.

#### Resource server

Защищённый API, который принимает access token.

Он проверяет:

- token;
- issuer;
- audience;
- scope;
- срок действия;
- права на конкретный ресурс;
- tenant;
- business rules.

Authorization server и resource server могут принадлежать одной компании, но логически выполняют разные обязанности.

### Delegated access

Классический пользовательский сценарий:

```text
Пользователь разрешает
calendar-client

читать calendar-api

без передачи client
пароля от аккаунта
```

Client получает ограниченный access token:

```text
scope:
calendar:read

audience:
calendar-api

lifetime:
10 минут
```

OAuth также поддерживает сценарии без пользователя, например доступ service client от своего имени.

Поэтому OAuth не ограничивается только формулировкой:

```text
действовать от имени пользователя
```

### Public и confidential clients

#### Confidential client

Способен надёжно хранить credentials и аутентифицироваться перед authorization server.

Примеры:

- server-side web application;
- BFF;
- backend service.

#### Public client

Не способен сохранить постоянный secret от пользователя или атакующего, контролирующего среду выполнения.

Примеры:

- browser SPA;
- mobile application;
- desktop application.

SPA bundle доставляется пользователю, поэтому значение:

```text
client_secret
```

можно извлечь.

Authorization server не должен считать такой secret доказательством identity browser client.

`client_id` является публичным идентификатором, а не secret.

### OpenID Connect

**OpenID Connect, OIDC**, — identity layer поверх OAuth 2.0.

OIDC отвечает на вопрос client:

```text
Какой пользователь
прошёл аутентификацию
у OpenID Provider?
```

Для OIDC authorization request содержит scope:

```text
openid
```

Без `openid` request является обычным OAuth request, а не OIDC authentication request.

### Роли OIDC

#### OpenID Provider

Authorization server, поддерживающий OIDC и выпускающий ID tokens.

Сокращение:

```text
OP
```

#### Relying Party

Client, который использует OIDC для authentication.

Сокращение:

```text
RP
```

### ID token

ID token:

- адресован client;
- описывает authentication event;
- содержит subject пользователя;
- обычно имеет формат подписанного JWT;
- проверяется client;
- не предназначен для произвольного resource server.

Типичные claims:

```json
{
  "iss": "https://login.example.com",
  "sub": "user-42",
  "aud": "frontend-client",
  "exp": 1786020000,
  "iat": 1786019400,
  "nonce": "random-value"
}
```

ID token сообщает client:

```text
OP аутентифицировал subject
для этого client
```

Он не означает:

```text
пользователь может читать
любой document
```

### Access token

Access token адресован resource server.

```text
ID token
→ client

Access token
→ API
```

Неправильно:

```http
Authorization:
  Bearer ID_TOKEN
```

если API ожидает access token.

У ID token и access token:

- разные audiences;
- разные consumers;
- разные validation rules;
- разное назначение.

### UserInfo endpoint

OIDC может предоставлять UserInfo endpoint.

Client вызывает его с access token:

```http
Authorization:
  Bearer ACCESS_TOKEN
```

и получает разрешённые claims пользователя.

При использовании UserInfo client проверяет, что:

```text
sub из UserInfo
===
sub из ID token
```

чтобы response относился к той же identity.

### Authorization Code + PKCE

Современный browser flow использует:

```text
Authorization Code
+
PKCE
```

Implicit flow не выбирают для нового browser client.

Access token выдаётся token endpoint, а не возвращается непосредственно в URL authorization response.

### Участники flow

```text
Browser / User Agent

Client:
SPA или BFF

Authorization Server / OP

Resource Server
```

Конкретный исполнитель шагов зависит от архитектуры.

#### Browser-only SPA

```text
SPA JavaScript
→ является OAuth public client
→ создаёт PKCE transaction
→ обменивает code
→ получает tokens
```

#### BFF

```text
BFF
→ является confidential client
→ создаёт transaction
→ обменивает code
→ хранит tokens server-side

Browser
→ получает application session cookie
```

### Шаг 1. Создание authorization transaction

Client создаёт:

- `code_verifier`;
- `code_challenge`;
- `state` либо другой выбранный CSRF-binding mechanism;
- OIDC `nonce`, если он используется;
- сведения об ожидаемом issuer;
- исходный безопасный destination после login.

#### `code_verifier`

Криптографически случайное значение, известное client.

Упрощённо:

```text
code_verifier =
random high-entropy string
```

#### `code_challenge`

Для метода `S256`:

```text
code_challenge =
BASE64URL(
  SHA-256(code_verifier)
)
```

Authorization request содержит challenge, но не verifier.

Используют:

```text
code_challenge_method=S256
```

Метод `plain` не выбирают для нового приложения, потому что он раскрывает verifier в authorization request и не защищает от атакующего, способного прочитать request.

#### Transaction storage

Client должен сохранить связь:

```text
transaction ID
→ code_verifier
→ state
→ nonce
→ issuer
→ redirect destination
→ expiration
```

В BFF transaction обычно хранится server-side.

В browser-only SPA она находится в ограниченном browser context согласно реализации OAuth library.

Transaction:

- короткоживущая;
- одноразовая;
- удаляется после успеха или ошибки;
- не должна позволять attacker выбирать произвольный redirect.

---

### Шаг 2. Authorization request

Browser перенаправляется на authorization endpoint.

Пример:

```text
https://login.example.com/authorize
  ?response_type=code
  &client_id=frontend-client
  &redirect_uri=https%3A%2F%2Fapp.example.com%2Fcallback
  &scope=openid%20profile%20orders%3Aread
  &code_challenge=...
  &code_challenge_method=S256
  &state=...
  &nonce=...
```

Client передаёт:

- `response_type=code`;
- `client_id`;
- точный `redirect_uri`;
- необходимые scopes;
- PKCE challenge;
- transaction-binding parameters.

### Redirect URI

Authorization server заранее регистрирует допустимые redirect URIs.

Он выполняет точное сравнение.

Правильно:

```text
https://app.example.com/oauth/callback
```

Нельзя разрешать:

```text
https://app.example.com/*
```

или проверять только:

```text
host содержит example.com
```

Слабая проверка может направить authorization code:

- attacker path;
- attacker subdomain;
- open redirect;
- другому приложению.

Browser-based application не должна использовать свой callback как произвольный redirect:

```text
/callback?returnUrl=https://attacker.example
```

После завершения flow destination выбирают из:

- server-side transaction;
- относительного пути;
- точного allowlist.

---

### Шаг 3. Authentication и authorization decision

Authorization server:

1. Аутентифицирует пользователя.
2. Определяет client.
3. Показывает consent, если он нужен.
4. Создаёт authorization code.
5. Связывает code с:
   - client ID;
   - redirect URI;
   - PKCE challenge;
   - resource owner;
   - scopes;
   - сроком действия.

Пароль вводится на странице authorization server, а не передаётся OAuth client.

Это позволяет provider использовать:

- MFA;
- passkeys;
- federation;
- risk-based authentication;
- собственные security controls.

---

### Шаг 4. Authorization response

Authorization server возвращает browser на callback:

```text
https://app.example.com/oauth/callback
  ?code=ONE_TIME_CODE
  &state=...
```

Либо возвращает ошибку:

```text
error=access_denied
```

Authorization code:

- короткоживущий;
- одноразовый;
- предназначен token endpoint;
- связан с client;
- связан с redirect URI;
- связан с PKCE challenge;
- не является access token;
- не используется для API requests.

### Проверка callback

Client проверяет:

- callback относится к активной transaction;
- response не содержит неожиданную ошибку;
- `state` совпадает, если он используется;
- issuer соответствует ожидаемому;
- code ещё не был обработан;
- transaction не истекла;
- callback пришёл на ожидаемый redirect URI.

После обработки transaction инвалидируется.

Нельзя обрабатывать один authorization code несколько раз.

---

### Шаг 5. Обмен code на tokens

Client отправляет token request:

```http
POST /token HTTP/1.1
Host: login.example.com
Content-Type:
  application/x-www-form-urlencoded

grant_type=authorization_code
&code=ONE_TIME_CODE
&redirect_uri=https%3A%2F%2Fapp.example.com%2Foauth%2Fcallback
&client_id=frontend-client
&code_verifier=ORIGINAL_VERIFIER
```

Authorization server проверяет:

- code существует;
- code не использован;
- code не истёк;
- code выпущен этому client;
- redirect URI совпадает;
- verifier соответствует challenge;
- confidential client корректно аутентифицирован, если это требуется.

При успехе возвращаются:

- access token;
- ID token для OIDC;
- refresh token, если он разрешён;
- срок действия;
- token type;
- granted scopes.

### Public client

Browser SPA не отправляет постоянный client secret как доказательство identity.

Даже если provider требует строку `client_secret`, встроенную в bundle, такой client всё равно остаётся public client.

Основная привязка конкретной browser transaction к code выполняется через PKCE.

### Confidential client

BFF аутентифицируется перед token endpoint с помощью поддерживаемого server-side механизма.

Client credentials остаются на server и не передаются browser.

---

### Шаг 6. Проверка token response

Client не просто сохраняет полученные strings.

Он проверяет:

- response пришёл от ожидаемого token endpoint;
- response соответствует OAuth contract;
- token type поддерживается;
- scope не превышает ожидаемый;
- ID token полностью валиден;
- transaction соответствует пользователю и issuer.

### Проверка ID token

OIDC client проверяет:

- signature;
- ожидаемый algorithm;
- trusted key;
- точное значение `iss`;
- `aud`, содержащую собственный `client_id`;
- `azp`, если он требуется используемым профилем;
- `exp`;
- `iat` согласно policy;
- `nonce`, если он был отправлен;
- другие обязательные claims профиля.

После validation client создаёт собственное authentication state.

ID token не следует использовать как бессрочную application session.

### Кто проверяет ID token

#### Browser-only SPA

ID token проверяет OIDC client library в browser.

#### BFF

ID token проверяет BFF.

Browser не обязан получать ID token.

После проверки BFF создаёт собственную server-side session:

```text
OAuth/OIDC tokens
→ server-side

Browser
→ HttpOnly session cookie
```

---

### Шаг 7. Вызов resource server

Client или BFF отправляет access token:

```http
GET /orders HTTP/1.1
Host: api.example.com
Authorization:
  Bearer ACCESS_TOKEN
```

Resource server проверяет:

- token format или introspection;
- signature, если token JWT;
- issuer;
- audience;
- expiration;
- token type;
- scopes;
- authorization для конкретного объекта;
- tenant;
- business rules.

Scope:

```text
orders:read
```

не означает:

```text
можно читать
любой заказ любого пользователя
```

После scope server проверяет ownership:

```text
order.userId
===
authenticatedUser.id
```

---

### Что делает PKCE

PKCE связывает authorization code с client instance, которая создала verifier.

Путь:

```text
client создаёт verifier

→ отправляет challenge

→ authorization server
  связывает challenge с code

→ token request
  содержит verifier

→ server проверяет связь
```

Если attacker перехватил только code:

```text
code есть

verifier нет

→ exchange отклоняется
```

PKCE защищает authorization code от обмена другим client.

Он не:

- шифрует access token;
- защищает token в `localStorage`;
- предотвращает XSS;
- заменяет authorization;
- превращает public client в confidential;
- скрывает client ID.

---

### `state`, PKCE и `nonce`

У параметров разные основные роли, хотя современные рекомендации допускают частичное пересечение защит.

| Механизм | Основная связь |
| --- | --- |
| `state` | Authorization response ↔ browser transaction |
| PKCE | Authorization code ↔ client instance, создавшая verifier |
| OIDC `nonce` | ID token ↔ authentication request |

### `state`

Классический CSRF token для redirect flow.

Client создаёт случайное одноразовое значение:

```text
state=random
```

и связывает его с browser transaction.

На callback проверяет точное совпадение.

`state` не следует использовать как открытый контейнер:

```text
state=https://attacker.example
```

Если в нём хранится application state, данные защищают от:

- подмены;
- swapping между transactions;
- изменения return URL.

Безопаснее хранить данные server-side, а в `state` передавать случайный transaction identifier.

### PKCE как CSRF-защита

Современная OAuth security guidance допускает использовать PKCE как защиту redirect endpoint от CSRF, если client убедился, что authorization server:

- поддерживает PKCE;
- требует PKCE для этого client;
- правильно связывает challenge с code;
- защищён от PKCE downgrade.

Если это нельзя гарантировать, используют проверяемый `state` или другой определённый протоколом binding mechanism.

На практике OAuth libraries часто одновременно используют PKCE и `state`, потому что:

- PKCE защищает code exchange;
- `state` удобно связывает transaction и application navigation;
- несколько независимых controls упрощают безопасную реализацию.

### OIDC `nonce`

Client отправляет:

```text
nonce=random
```

Authorization server помещает то же значение в ID token.

Client проверяет:

```text
ID token nonce
===
nonce текущей transaction
```

Это связывает ID token с authentication request и снижает риск replay и подмены authentication response.

`nonce` не является заменой:

- access-token audience;
- signature validation;
- `iss`;
- `exp`;
- PKCE code binding.

---

### Authorization server mix-up

Client может поддерживать несколько providers:

```text
corporate IdP

Google

partner IdP
```

Attacker пытается заставить client отправить code одному issuer, а token request — другому.

Защита:

- сохранять ожидаемый issuer в transaction;
- проверять issuer identifier в authorization response;
- использовать metadata конкретного issuer;
- не выбирать token endpoint по непроверенному callback input;
- при необходимости использовать отдельные redirect URIs для issuers.

Плохо:

```text
callback содержит provider=attacker

→ client отправляет code
  на token endpoint из параметра
```

Token endpoint выбирается только из доверенной конфигурации ожидаемого issuer.

---

### BFF и browser-only client

#### Browser-only SPA

```text
Authorization Code + PKCE

access token:
доступен JavaScript

refresh token:
может быть доступен JavaScript

API:
вызывается напрямую
```

Риски:

- XSS может украсть token;
- third-party script имеет возможности origin;
- нужно спроектировать storage;
- token endpoint должен поддерживать browser client;
- нужна координация refresh между вкладками.

#### BFF

```text
Authorization Code

BFF:
confidential client

OAuth tokens:
server-side

Browser:
application session cookie
```

Преимущества:

- OAuth tokens не выдаются JavaScript;
- refresh token остаётся server-side;
- проще централизованный logout;
- легче выполнять client authentication;
- API requests можно контролировать в одном server layer.

Остаются риски:

- XSS может выполнять действия через активную session;
- cookie требует CSRF-защиту;
- BFF должен выполнять authorization;
- нужен session store и server infrastructure.

### Token-mediating backend

Промежуточный вариант:

```text
backend хранит refresh token

browser получает access token

browser вызывает API напрямую
```

Он уменьшает риск кражи refresh token, но access token остаётся доступным JavaScript.

По уровню изоляции:

```text
BFF
→ OAuth tokens не попадают в browser

Token-mediating backend
→ access token попадает в browser

Browser-only client
→ access и иногда refresh token
  находятся в browser
```

---

### OAuth не заменяет authorization приложения

Даже полностью валидный access token не отвечает на все вопросы.

Token может подтвердить:

```text
issuer выдал client доступ
со scope orders:read
```

Resource server отдельно проверяет:

```text
Может ли subject
прочитать именно order-42?

Принадлежит ли order
текущему tenant?

Можно ли читать order
в текущем состоянии?

Не была ли роль отозвана?
```

Frontend route guard:

```tsx
if (!user.isAdmin) {
  return <Navigate to="/" />;
}
```

улучшает UX, но не защищает API.

Backend повторяет authorization для каждого request.

---

### Типичные ошибки

#### Считать JWT authentication-протоколом

```text
Мы авторизуемся через JWT
```

не объясняет:

- кто выдал token;
- как пользователь вошёл;
- где token хранится;
- кто его проверяет;
- как выполняется logout;
- как обновляется доступ.

#### Использовать ID token для API

ID token адресован client, а не resource server.

#### Только декодировать JWT

Base64url decoding не проверяет signature.

#### Доверять `alg` из token

Допустимый algorithm задаёт verifier configuration.

#### Не проверять audience

Token другого API может иметь правильную signature, но неправильного получателя.

#### Использовать один validator для всех JWT

ID token может быть принят вместо access token.

#### Хранить secret в SPA

Любой secret из bundle доступен пользователю.

#### Использовать Implicit flow

Access token не должен возвращаться непосредственно через authorization response URL для нового browser client.

#### Принимать приблизительный redirect URI

Wildcard и substring matching позволяют утечку code.

#### Сохранять `returnUrl` без проверки

Callback может превратиться в open redirect.

#### Полагаться только на scopes

Scope не заменяет object-level authorization.

#### Класть лишние данные в JWT

Подписанный payload остаётся читаемым.

#### Делать JWT слишком долгоживущим

Роль и статус пользователя могут измениться раньше `exp`.

#### Считать logout очисткой React state

Server credential может оставаться действительным.

---

### Практический выбор

#### Обычное приложение со своим backend

```text
server-side session

Browser:
Secure + HttpOnly cookie

Server:
user/session state
```

Federated login можно выполнить через OIDC, а полученные tokens оставить server-side.

#### Frontend вызывает внешние API от имени пользователя

```text
OAuth Authorization Code
+
PKCE

для identity:
OIDC
```

Для чувствительного приложения предпочтителен BFF.

#### Service-to-service

Используется OAuth flow без browser пользователя, например client credentials, если он соответствует threat model.

OIDC для machine identity пользователя обычно не нужен.

#### Нужно передать проверяемые claims между services

JWT может быть подходящим форматом, если:

- определён issuer;
- определена audience;
- есть key management;
- есть lifecycle;
- есть строгие validation rules;
- claims действительно нужны без database lookup.

JWT не выбирают только ради отсутствия session store.

---

### Главная модель

```text
Server-side session:
где хранится состояние входа

JWT:
в каком формате передаются claims

OAuth:
как client получает доступ к API

OIDC:
как client получает
проверяемую identity пользователя

Authorization:
можно ли выполнить
конкретное действие
над конкретным ресурсом
```

Authorization Code + PKCE:

```text
client создаёт verifier

→ отправляет challenge

→ получает одноразовый code

→ возвращает verifier
  на token endpoint

→ получает tokens

→ использует access token
  только для нужного API

→ проверяет ID token
  только как OIDC client
```

Главный принцип:

```text
Валидный token подтверждает
только то,
что определено его протоколом,
типом, issuer, audience
и claims.

Он не отменяет
server-side authorization
конкретной операции.
```

## Дополнительные вопросы

<details>
<summary><strong>Что такое claims в JWT?</strong></summary>

<dl>
<dd>
<h2></h2>

Claims — поля, описывающие token и его контекст.

Registered claims:

- `iss` — issuer;
- `sub` — subject;
- `aud` — audience;
- `exp` — expiration;
- `nbf` — not before;
- `iat` — issued at;
- `jti` — identifier token.

Private claims могут описывать:

- scopes;
- tenant;
- roles;
- permissions.

Наличие claim не означает, что ему можно доверять.

Сначала проверяют cryptography, issuer, audience, token type и остальные обязательные правила.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>JWT зашифрован?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычно JWT является подписанным JWS:

```text
header.payload.signature
```

Payload читается после base64url decoding.

Signature защищает целостность и подлинность, но не confidentiality.

JWE является отдельным форматом шифрования и обычно содержит пять частей.

Данные, которые получатель token не должен видеть, не помещают в обычный подписанный JWT.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что именно backend должен проверить в JWT?</strong></summary>

<dl>
<dd>
<h2></h2>

Как минимум:

- разрешённый algorithm;
- signature или MAC;
- доверенный key;
- `iss`;
- `aud`;
- `exp`;
- `nbf`, если присутствует;
- назначение и тип token;
- обязательные claims конкретного профиля.

После validation проверяются:

- scope;
- permissions;
- tenant;
- ownership;
- актуальное состояние пользователя;
- бизнес-правила.

Token header не должен самостоятельно выбирать доверенный algorithm или произвольный key source.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли изменить payload JWT и сохранить валидность?</strong></summary>

<dl>
<dd>
<h2></h2>

Payload можно прочитать, изменить и снова закодировать.

Но изменение подписанных:

```text
header.payload
```

нарушает signature.

Корректный verifier отклонит token.

Атака становится возможной, если приложение:

- только декодирует token;
- принимает `alg: none`;
- путает symmetric и asymmetric algorithms;
- использует неверный key;
- не проверяет signature;
- принимает token другого типа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли отозвать JWT до <code>exp</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Локально проверяемый JWT обычно действует до `exp`, пока выполняются validation rules.

Для досрочного отзыва добавляют server state:

- denylist по `jti`;
- token version пользователя;
- session record;
- OAuth introspection;
- список отозванных grants;
- проверку статуса пользователя;
- смену signing key в исключительном случае.

Часто используют:

```text
короткий access token
+
управляемая refresh session
```

Чем быстрее нужен централизованный отзыв, тем меньше система является полностью stateless.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем session ID отличается от JWT?</strong></summary>

<dl>
<dd>
<h2></h2>

Session ID обычно является случайной непрозрачной ссылкой:

```text
session ID
→ server-side state
```

JWT может самостоятельно переносить проверяемые claims:

```text
JWT
→ signature
→ claims
```

Но оба значения могут быть bearer credentials.

JWT может храниться внутри server-side session, а непрозрачный OAuth access token может проверяться через introspection.

Сравнивать нужно всю архитектуру:

- storage;
- transport;
- validation;
- revocation;
- lifetime;
- authorization.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое session fixation?</strong></summary>

<dl>
<dd>
<h2></h2>

Атакующий заставляет жертву использовать заранее известный session ID.

После того как жертва войдёт, атакующий пытается использовать тот же ID как авторизованную session.

Защита:

- новый session ID после login;
- rotation после MFA и privilege change;
- инвалидирование старого ID;
- запрет session ID из URL;
- случайный server-generated identifier.

HTTPS само по себе не исправляет session fixation.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>OAuth 2.0 является протоколом аутентификации?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

OAuth определяет delegated authorization и получение access token.

Access token адресован resource server и не является стандартизированным сообщением client:

```text
этот пользователь вошёл
```

Для federated authentication используют OpenID Connect.

OIDC добавляет:

- ID token;
- `openid` scope;
- стандартизированные identity claims;
- UserInfo endpoint;
- правила validation authentication response.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие роли есть в OAuth?</strong></summary>

<dl>
<dd>
<h2></h2>

Основные роли:

- resource owner;
- client;
- authorization server;
- resource server.

Resource owner предоставляет доступ к ресурсу.

Client запрашивает доступ.

Authorization server выдаёт tokens.

Resource server принимает access token и предоставляет API.

Client дополнительно классифицируется как:

- public;
- confidential.

Одна компания может реализовывать несколько ролей, но security responsibilities остаются разными.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем authorization code отличается от access token?</strong></summary>

<dl>
<dd>
<h2></h2>

Authorization code:

- короткоживущий;
- одноразовый;
- предназначен token endpoint;
- связан с client и redirect URI;
- при PKCE связан с challenge;
- не вызывает resource API.

Access token:

- предназначен resource server;
- имеет audience и scope;
- используется для API requests;
- действует до expiration или отзыва.

Code обменивается на token, но сам token не заменяет.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое PKCE и от какой атаки он защищает?</strong></summary>

<dl>
<dd>
<h2></h2>

Client создаёт:

```text
code_verifier
```

и отправляет его hash:

```text
code_challenge
```

При token exchange предъявляется исходный verifier.

Authorization server проверяет связь verifier с challenge, сохранённым для authorization code.

Перехватив code без verifier, другой client не сможет получить tokens.

Для нового flow используют:

```text
code_challenge_method=S256
```

PKCE не защищает access token после его выдачи и не предотвращает XSS.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>state</code>, PKCE и OIDC <code>nonce</code> отличаются?</strong></summary>

<dl>
<dd>
<h2></h2>

`state` связывает authorization response с browser transaction и часто используется как CSRF token.

PKCE связывает authorization code с client instance, создавшей verifier.

OIDC `nonce` связывает ID token с authentication request.

Современный client может использовать несколько механизмов одновременно.

Каждое значение:

- случайное;
- короткоживущее;
- одноразовое;
- связано с конкретной transaction;
- проверяется до создания session.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем access token отличается от ID token?</strong></summary>

<dl>
<dd>
<h2></h2>

Access token:

```text
audience
→ resource server

назначение
→ доступ к API
```

ID token:

```text
audience
→ OIDC client

назначение
→ результат authentication
```

ID token нельзя отправлять в API вместо access token.

Access token нельзя использовать как authentication assertion client, если protocol не определяет такой сценарий.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое scope и является ли он полной авторизацией?</strong></summary>

<dl>
<dd>
<h2></h2>

Scope ограничивает общую возможность token:

```text
orders:read
```

Но он не доказывает право на конкретный объект.

Resource server дополнительно проверяет:

- owner;
- tenant;
- роль;
- состояние заказа;
- связь пользователя с организацией;
- business restrictions.

```text
scope
→ можно запрашивать операции этого класса

object authorization
→ можно выполнить операцию
  над этим объектом
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему SPA не должна хранить OAuth client secret?</strong></summary>

<dl>
<dd>
<h2></h2>

SPA code и configuration доставляются пользователю.

Secret можно получить из:

- bundle;
- source map;
- Network;
- browser memory;
- DevTools;
- frontend environment variables.

SPA регистрируется как public client.

Если нужен confidential client, authorization code обменивает BFF или другой server-side component.

`client_id` не является secret.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему implicit flow больше не выбирают для нового browser client?</strong></summary>

<dl>
<dd>
<h2></h2>

Implicit flow выдаёт access token через authorization response в browser URL.

Это увеличивает exposure token и не даёт преимуществ перед современным Authorization Code + PKCE.

Новый browser client использует:

```text
response_type=code

+
PKCE S256
```

Access token выдаётся token endpoint после проверки одноразового code и verifier.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему Resource Owner Password Credentials grant считается устаревшим?</strong></summary>

<dl>
<dd>
<h2></h2>

Client получает password пользователя напрямую и самостоятельно передаёт его authorization server.

Это:

- расширяет круг компонентов, видящих password;
- плохо работает с MFA;
- плохо работает с federation;
- не поддерживает современные authentication methods;
- приучает пользователя вводить credentials provider в client.

OAuth Security BCP запрещает использовать этот grant.

Пользователя перенаправляют на доверенный интерфейс authorization server.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что проверять в OAuth callback?</strong></summary>

<dl>
<dd>
<h2></h2>

Проверяют:

- callback соответствует активной transaction;
- ожидаемый issuer;
- `state`, если он используется;
- отсутствие неожиданной ошибки;
- срок transaction;
- одноразовость code;
- точный callback route;
- сохранённый PKCE verifier;
- OIDC `nonce`, если он был отправлен.

После code exchange проверяют token response и ID token.

Callback не должен доверять произвольным:

- token endpoint;
- issuer;
- redirect destination;
- return URL;

полученным из query.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему redirect URI проверяют по точному совпадению?</strong></summary>

<dl>
<dd>
<h2></h2>

Слабое сопоставление может направить code:

- attacker domain;
- attacker subdomain;
- другой path;
- open redirect;
- другому application client.

Authorization server регистрирует полные redirect URIs и сравнивает их точно.

Client также проверяет внутренний destination после callback и не выполняет redirect на произвольный `returnUrl`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где хранить tokens в browser-based приложении?</strong></summary>

<dl>
<dd>
<h2></h2>

Для чувствительного приложения предпочтителен BFF:

```text
OAuth tokens
→ server-side

Browser
→ Secure + HttpOnly
  application session cookie
```

Если token находится в SPA:

- memory уменьшает persistence;
- `sessionStorage` ограничивает page session;
- `localStorage` переживает browser restart;
- любое JavaScript-доступное место доступно active XSS.

Storage является отдельным архитектурным решением и не определяется только выбором OAuth flow.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли OAuth access token быть непрозрачной строкой, а не JWT?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

Access token может быть:

- opaque random string;
- JWT;
- другим форматом, согласованным authorization server и resource server.

Opaque token resource server может проверять через:

- собственное shared storage;
- introspection endpoint;
- внутренний gateway.

Client не должен зависеть от внутренней структуры access token.

Даже если token визуально похож на JWT, client не должен использовать его claims как стабильный application contract без соответствующей спецификации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Означает ли JWT, что server больше не хранит состояние?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Server может хранить:

- refresh session;
- revocation;
- user status;
- role version;
- consent;
- device sessions;
- risk state;
- audit.

JWT лишь позволяет проверить часть claims без обязательного session lookup.

Полностью stateless logout, мгновенный отзыв и актуальные права часто конфликтуют друг с другом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое JWKS и для чего нужен <code>kid</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

JWKS — набор публичных JSON Web Keys issuer.

`kid` помогает выбрать конкретный key из набора.

Verifier:

1. Доверяет заранее настроенному issuer.
2. Получает его metadata.
3. Загружает JWKS с доверенного URL.
4. Выбирает key по `kid`.
5. Проверяет algorithm и signature.
6. Проверяет claims.

Нельзя загружать key с произвольного URL, переданного внутри attacker-controlled token.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое authorization server mix-up attack?</strong></summary>

<dl>
<dd>
<h2></h2>

Client поддерживает несколько authorization servers, а attacker пытается перепутать:

- issuer, начавший flow;
- issuer, вернувший response;
- token endpoint, куда отправляется code.

Защита:

- сохранить issuer в transaction;
- проверить issuer authorization response;
- использовать metadata ожидаемого issuer;
- применять точные redirect URIs;
- не выбирать token endpoint из callback query.

Code одного provider нельзя отправлять другому provider.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Кто проверяет ID token при использовании BFF?</strong></summary>

<dl>
<dd>
<h2></h2>

ID token проверяет BFF как OIDC Relying Party.

BFF валидирует:

- signature;
- issuer;
- audience;
- expiration;
- nonce;
- другие обязательные claims.

После этого BFF создаёт application session.

Browser получает session cookie и не обязан получать ID token или OAuth tokens.

Frontend может запросить у BFF минимальную информацию о текущем пользователе через session endpoint.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Для чего нужен scope <code>openid</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Он сообщает authorization server, что request является OpenID Connect authentication request.

```text
scope=openid
```

позволяет client получить ID token.

Scopes:

```text
profile
email
address
phone
```

запрашивают дополнительные стандартные claims, но сами по себе без `openid` не превращают OAuth request в OIDC.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Для чего нужен UserInfo endpoint?</strong></summary>

<dl>
<dd>
<h2></h2>

Это OIDC protected resource, возвращающий разрешённые claims authenticated user.

Client вызывает его с access token.

UserInfo может использоваться, когда:

- claims не помещаются в ID token;
- нужны актуальные profile fields;
- provider возвращает минимальный ID token.

Client проверяет, что `sub` UserInfo response совпадает с `sub` проверенного ID token.

UserInfo response не заменяет ID token validation.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Что различать |
| --- | --- |
| Вход через корпоративного provider | OAuth authorization и OIDC authentication |
| Callback route | Code, transaction, issuer, `state`, PKCE verifier и OIDC `nonce` |
| Browser-only SPA | Public client, PKCE, JavaScript-доступные tokens и XSS-risk |
| BFF | Confidential client, server-side tokens и session cookie browser |
| Вызов API | Access token с правильной audience, а не ID token |
| Защищённый route | Client-side UX guard и независимая backend authorization |
| JWT resource server | Signature, algorithm, issuer, audience, type и object permissions |
| Несколько identity providers | Transaction должна хранить ожидаемый issuer |
| Rotation signing keys | JWKS cache, `kid` и доверенный metadata endpoint |
| Роль пользователя изменилась | Claims старого JWT могут оставаться актуальными до `exp` |
| Logout | Инвалидация server session или refresh grant, а не только UI state |
| Callback содержит `returnUrl` | Относительный путь или точный allowlist, чтобы не создать open redirect |
| UserInfo | Access token для endpoint и совпадение `sub` с ID token |
| API принимает JWT разных типов | Отдельные взаимоисключающие validation rules |
| OAuth provider требует secret в SPA | Secret не подтверждает public client и доступен из bundle |
