## Вопрос

<br>

 💬 **Какие способы хранения данных есть в браузере и чем отличаются cookie, localStorage, sessionStorage, IndexedDB и Cache API?**

<h2></h2>

<br>
<dl>
<dd>

Способ хранения выбирают по:

- назначению данных;
- владельцу данных;
- объёму;
- сроку жизни;
- необходимости поиска и транзакций;
- участию данных в HTTP-запросах;
- требованиям к offline-режиму;
- модели угроз.

Основные механизмы решают разные задачи:

| Механизм | Что хранит | API | Отправляется с HTTP |
| --- | --- | --- | --- |
| Cookie | Небольшие строки и атрибуты | HTTP-заголовки, частично `document.cookie` | Да, автоматически при совпадении условий |
| `localStorage` | Строковые пары | Синхронный Web Storage API | Нет |
| `sessionStorage` | Строковые пары вкладки | Синхронный Web Storage API | Нет |
| IndexedDB | Структурированные значения | Асинхронная транзакционная база | Нет |
| Cache API | Пары `Request`/`Response` | Асинхронный Cache API | Нет, но используется при обработке запросов |

Эти механизмы не являются взаимозаменяемыми.

**Cookie** — небольшая пара имени и значения с набором атрибутов.

Сервер создаёт cookie через заголовок:

```http
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax; Path=/
```

При последующих подходящих запросах браузер может автоматически добавить:

```http
Cookie: sessionId=abc123
```

Автоматическая отправка удобна для серверной сессии: frontend не обязан вручную читать идентификатор и добавлять его в каждый запрос.

Но она же создаёт риск CSRF, потому что браузер может приложить cookie к запросу независимо от того, кто инициировал действие.

Cookie отправляется только при совпадении условий:

- host и `Domain`;
- URL и `Path`;
- HTTPS-требование `Secure`;
- правила `SameSite`;
- срок жизни;
- тип запроса и его credentials mode.

Для `fetch()` cookie текущего origin обычно учитываются автоматически. Для cross-origin-запроса может потребоваться:

```js
fetch("https://api.example.com/data", {
  credentials: "include",
});
```

При этом сервер также должен разрешить credentialed CORS-запрос.

Cookie бывает session или persistent.

Если отсутствуют:

```text
Expires
Max-Age
```

cookie считается session cookie. Её жизненный цикл связан с browser session, хотя браузеры могут восстанавливать сессию вместе с открытыми вкладками.

Persistent cookie имеет срок жизни:

```http
Set-Cookie: theme=dark; Max-Age=2592000
```

`Max-Age` задаёт срок в секундах, а `Expires` — абсолютную дату.

Основные атрибуты безопасности:

```text
HttpOnly
Secure
SameSite
```

`HttpOnly` запрещает читать cookie через:

```js
document.cookie
```

Это уменьшает риск прямой кражи session cookie при XSS.

Но вредоносный JavaScript всё ещё выполняется в origin приложения и может отправлять разрешённые запросы от имени пользователя. Поэтому `HttpOnly` защищает значение cookie от чтения, но не устраняет XSS.

`Secure` разрешает отправлять cookie только по защищённому HTTPS-соединению.

Он не запрещает JavaScript читать cookie. Для запрета чтения нужен `HttpOnly`.

`SameSite` ограничивает отправку cookie в межсайтовом контексте:

```text
Strict
Lax
None
```

`Strict` наиболее жёстко ограничивает межсайтовую отправку.

`Lax` допускает часть top-level navigation, но ограничивает многие фоновые cross-site-запросы.

`None` разрешает cross-site-использование и требует:

```text
Secure
```

`SameSite` помогает против CSRF, но не должен быть единственным уровнем защиты.

Для чувствительных операций сервер дополнительно проверяет:

- HTTP-метод;
- `Origin`;
- при необходимости `Referer`;
- CSRF-токен;
- авторизацию пользователя;
- ожидаемую бизнес-операцию.

Если атрибут `Domain` отсутствует, cookie является host-only:

```text
app.example.com
```

Она не будет автоматически доступна соседнему host:

```text
api.example.com
```

Если указать:

```http
Domain=example.com
```

cookie может подходить соответствующим поддоменам.

Чем уже scope cookie, тем меньше поверхность случайного использования.

`Path` ограничивает URL-пути, к которым cookie должна отправляться:

```http
Path=/admin
```

Но `Path` не является надёжной границей безопасности между частями одного origin.

Cookie имеет небольшие лимиты на размер одной записи и количество записей. Точные ограничения зависят от браузера.

Кроме того, cookie увеличивают размер подходящих HTTP-запросов, поэтому в них не хранят:

- большие профили;
- списки товаров;
- JSON-ответы;
- историю интерфейса;
- файлы.

**localStorage** — синхронное строковое хранилище в пределах origin.

Origin определяется сочетанием:

```text
scheme + host + port
```

Например:

```text
https://example.com
```

и:

```text
http://example.com
```

относятся к разным origin.

API хранит строки:

```js
localStorage.setItem("theme", "dark");

const theme = localStorage.getItem("theme");
```

Для объекта требуется сериализация:

```js
const settings = {
  theme: "dark",
  compact: true,
};

localStorage.setItem(
  "settings",
  JSON.stringify(settings),
);
```

При чтении данные нужно разбирать и проверять:

```js
function readSettings() {
  const rawSettings = localStorage.getItem("settings");

  if (!rawSettings) return null;

  try {
    const parsedSettings = JSON.parse(rawSettings);

    if (
      typeof parsedSettings !== "object" ||
      parsedSettings === null
    ) {
      return null;
    }

    return parsedSettings;
  } catch {
    return null;
  }
}
```

Данные могут быть:

- повреждены;
- записаны старой версией приложения;
- вручную изменены пользователем;
- удалены браузером или пользователем;
- недоступны из-за настроек приватности.

`localStorage` не имеет встроенного TTL.

Запись обычно переживает:

- reload;
- закрытие вкладки;
- закрытие и повторный запуск браузера.

Но приложение не должно считать её постоянной или гарантированной копией данных.

Web Storage API синхронный:

```js
localStorage.getItem(...)
localStorage.setItem(...)
localStorage.removeItem(...)
```

Операции выполняются на main thread.

Крупное значение или частая запись могут задерживать:

- обработку пользовательского ввода;
- React render;
- создание кадра;
- другую JavaScript-работу.

Дополнительную стоимость создают:

```js
JSON.stringify(...)
JSON.parse(...)
```

Поэтому `localStorage` подходит для небольших значений:

- тема;
- язык;
- плотность таблицы;
- согласие с настройкой;
- идентификатор последнего открытого раздела.

Не следует записывать крупный state при каждом нажатии клавиши без ограничения частоты.

**sessionStorage** использует такой же синхронный строковый API:

```js
sessionStorage.setItem("step", "payment");
```

Но данные дополнительно разделяются по top-level browsing context, то есть обычно по вкладке или окну.

Упрощённо scope выглядит так:

```text
origin + вкладка
```

Данные переживают reload текущей вкладки:

```text
reload → sessionStorage сохраняется
```

Но обычно удаляются после завершения соответствующей tab session.

Две независимо открытые вкладки одного origin обычно имеют разные `sessionStorage`.

Если новая вкладка открыта через `window.open` и сохраняет связь с opener, браузер может создать для неё начальную копию `sessionStorage` исходной вкладки. После открытия хранилища изменяются независимо.

`sessionStorage` подходит для:

- шага многоэтапного сценария;
- временного фильтра;
- черновика конкретной вкладки;
- состояния, которое не должно автоматически разделяться между окнами.

Для данных, общих между вкладками, чаще используют:

- `localStorage`;
- IndexedDB;
- сервер;
- `BroadcastChannel` для обмена сообщениями.

`localStorage` и `sessionStorage` доступны JavaScript текущего origin.

При XSS вредоносный скрипт может их прочитать:

```js
localStorage.getItem("accessToken");
```

Поэтому Web Storage не считают безопасным хранилищем секретов.

**IndexedDB** — асинхронная транзакционная база данных браузера.

Она подходит, когда нужны:

- большие объёмы данных;
- структурированные объекты;
- индексы;
- транзакции;
- offline-режим;
- локальные файлы;
- очереди синхронизации.

Данные организуются в object stores:

```text
products
drafts
syncQueue
files
```

Внутри store значения могут иметь primary key, а дополнительные indexes ускоряют поиск по отдельным полям.

Например, каталог можно искать по:

```text
brand
category
updatedAt
status
```

IndexedDB использует structured clone.

Он поддерживает многие типы:

- обычные объекты;
- массивы;
- строки и числа;
- `Date`;
- `Map`;
- `Set`;
- `ArrayBuffer`;
- typed arrays;
- `Blob`;
- `File`.

Не все значения можно сохранить.

Например, structured clone не предназначен для хранения:

- функций;
- DOM-узлов;
- объектов с произвольным живым поведением;
- части platform objects.

Также нельзя рассчитывать, что prototype пользовательского class instance восстановится как полноценный экземпляр класса со всеми методами.

IndexedDB асинхронна и не блокирует main thread так же, как крупная синхронная операция `localStorage`.

При этом сериализация, обработка результатов и пользовательский JavaScript всё равно требуют ресурсов.

Операции объединяются в транзакции:

```text
readonly
readwrite
versionchange
```

Транзакция позволяет выполнить группу изменений атомарно: либо применятся все её операции, либо при ошибке произойдёт rollback.

Схема базы имеет числовую версию:

```js
indexedDB.open("app", 3);
```

Создание и изменение object stores и indexes выполняют в:

```text
upgradeneeded
```

внутри `versionchange` transaction.

Например:

```js
const request = indexedDB.open("app", 2);

request.addEventListener("upgradeneeded", () => {
  const database = request.result;

  if (!database.objectStoreNames.contains("drafts")) {
    database.createObjectStore("drafts", {
      keyPath: "id",
    });
  }
});
```

Открытая старая вкладка может удерживать соединение с предыдущей версией базы и блокировать upgrade.

Поэтому обрабатывают:

```text
versionchange
blocked
```

Старое соединение закрывают:

```js
database.addEventListener("versionchange", () => {
  database.close();
});
```

А пользователю при необходимости предлагают обновить другую вкладку.

Транзакция IndexedDB автоматически завершается, когда у неё больше нет активных запросов и управление вернулось event loop.

Поэтому опасно внутри native transaction ждать произвольную внешнюю операцию:

```js
await fetch(...);
```

Пока выполняется посторонний `await`, транзакция может стать неактивной и автоматически завершиться.

Правильнее:

1. Получить внешние данные.
2. Открыть короткую IndexedDB-транзакцию.
3. Выполнить связанные операции.
4. Завершить транзакцию.

При использовании wrapper-библиотеки нужно понимать, как она сохраняет активность транзакции и какие `await` поддерживает.

**Cache API** хранит пары:

```text
Request → Response
```

Пример:

```js
const cache = await caches.open("app-v1");

await cache.add("/offline.html");
```

Получение:

```js
const response = await cache.match("/offline.html");
```

Cache API чаще всего используется вместе с Service Worker:

```js
self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((cachedResponse) => {
      return cachedResponse ?? fetch(event.request);
    }),
  );
});
```

Service Worker может перехватить запрос и выбрать стратегию:

- cache first;
- network first;
- stale while revalidate;
- только network;
- offline fallback.

Сам Cache API доступен не только в Service Worker. Его можно использовать и из window context:

```js
const cache = await caches.open("data-cache");
```

Но обычный код страницы без Service Worker не может автоматически перехватывать все навигационные и ресурсные запросы браузера.

Он должен явно вызвать:

```js
cache.match(...)
```

Cache API не обновляет записи автоматически после выпуска новой версии на сервере.

Приложение само отвечает за:

- имя и версию cache;
- добавление записей;
- проверку свежести;
- invalidation;
- удаление старых cache;
- поведение offline;
- разделение данных пользователей.

Например, при активации новой версии Service Worker можно удалить старые cache:

```js
const CURRENT_CACHE = "app-v3";

self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches.keys().then((cacheNames) => {
      return Promise.all(
        cacheNames
          .filter((cacheName) => {
            return cacheName !== CURRENT_CACHE;
          })
          .map((cacheName) => {
            return caches.delete(cacheName);
          }),
      );
    }),
  );
});
```

`Response` содержит body stream.

Если один response нужно одновременно вернуть клиенту и сохранить, его обычно клонируют:

```js
const response = await fetch(request);

await cache.put(
  request,
  response.clone(),
);

return response;
```

Cache API не следует автоматически всем правилам HTTP cache так, как сетевой кэш.

Например, наличие записи в Cache API не означает, что она:

- ещё свежая;
- соответствует текущей версии приложения;
- принадлежит текущему пользователю;
- должна использоваться без проверки сервера.

**HTTP cache** является частью сетевого стека браузера.

Он управляется HTTP-заголовками:

```text
Cache-Control
ETag
Last-Modified
Expires
Vary
```

Браузер может:

- использовать свежий ответ;
- выполнить revalidation;
- отправить условный запрос;
- получить `304 Not Modified`;
- запросить полный новый ответ.

Cache API управляется JavaScript, а HTTP cache — сетевыми правилами.

Один запрос может пройти через несколько уровней:

```text
страница
→ Service Worker
→ Cache API
→ fetch()
→ HTTP cache
→ сеть
```

Если Service Worker нашёл ответ в Cache API и сразу его вернул, сетевой запрос и HTTP cache вообще могут не использоваться.

Данные браузерных хранилищ ограничены quota.

Точные правила зависят от:

- браузера;
- устройства;
- свободного диска;
- режима просмотра;
- активности origin;
- политики пользователя.

Cookie имеют собственные небольшие ограничения.

Web Storage обычно имеет относительно небольшой лимит.

IndexedDB и Cache API могут использовать значительно больше места, но их данные не являются безусловно постоянными.

Примерное использование origin storage можно запросить:

```js
const estimate = await navigator.storage.estimate();

console.log(estimate.usage);
console.log(estimate.quota);
```

Это приблизительные значения. Точный состав учитываемых данных и алгоритм расчёта зависят от браузера.

По умолчанию данные часто хранятся в best-effort-режиме. Браузер может удалить их при нехватке места.

Можно запросить более устойчивое хранение:

```js
const isPersistent =
  await navigator.storage.persist();
```

Но браузер не обязан удовлетворять запрос.

Даже persistent storage не заменяет серверную копию критичных данных и не защищает от:

- очистки данных пользователем;
- удаления профиля браузера;
- потери устройства;
- ошибок приложения;
- повреждения данных.

Запись может завершиться ошибкой:

```text
QuotaExceededError
```

Поэтому приложение должно:

- обрабатывать исключения;
- удалять устаревшие cache;
- ограничивать объём;
- иметь миграции;
- восстанавливаться после отсутствующей записи;
- не считать browser storage единственной копией важных данных.

Доступ к Web Storage также может завершиться исключением, например из-за настроек безопасности или недопустимого origin.

Даже чтение лучше выполнять в контролируемом месте:

```js
function safeReadTheme() {
  try {
    return localStorage.getItem("theme");
  } catch {
    return null;
  }
}
```

Все JS-доступные хранилища текущего origin находятся в зоне риска при XSS:

```text
localStorage
sessionStorage
IndexedDB
Cache API
```

`HttpOnly` cookie отличается тем, что JavaScript не может прочитать её значение.

Но выбор между cookie и другими способами нельзя свести к правилу:

```text
cookie всегда безопаснее
```

При cookie-based authentication нужно учитывать:

- CSRF;
- `SameSite`;
- `Secure`;
- `HttpOnly`;
- CORS и credentials;
- срок сессии;
- logout;
- rotation;
- серверную проверку прав.

При token-based authentication с JS-доступным token нужно учитывать риск кражи при XSS.

Безопасность определяется всей архитектурой, а не только местом хранения одной строки.

Персональные ответы и cache нужно очищать или разделять при смене пользователя.

Например, после logout старый ответ в Cache API или IndexedDB может остаться на устройстве и случайно отобразиться следующему пользователю.

Поэтому logout может включать:

- очистку state приложения;
- завершение серверной сессии;
- удаление пользовательских IndexedDB-записей;
- удаление private Cache API;
- остановку фоновой синхронизации;
- уведомление других вкладок.

Хранилище выбирают по задаче:

```text
Cookie
→ небольшие данные, связанные с HTTP и серверной сессией.

localStorage
→ небольшие несекретные настройки origin.

sessionStorage
→ временное состояние конкретной вкладки.

IndexedDB
→ большие структурированные данные, индексы и offline.

Cache API
→ Request/Response и управляемые сетевые стратегии.
```

## Дополнительные вопросы

<details>
<summary><strong>Почему cookie автоматически отправляются с запросами?</strong></summary>

<dl>
<dd>
<h2></h2>

Так определён HTTP-механизм cookie.

Браузер хранит cookie и перед запросом проверяет:

- domain или host;
- path;
- `Secure`;
- `SameSite`;
- срок жизни;
- тип запроса;
- credentials mode.

После этого он формирует заголовок:

```http
Cookie: sessionId=abc123
```

JavaScript не должен вручную создавать этот заголовок.

Это удобно для серверной сессии, но создаёт CSRF-риск: браузер может приложить авторизационную cookie к запросу, инициированному не интерфейсом приложения.

Поэтому сервер проверяет не только наличие cookie, но и допустимость самой операции.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем session cookie отличается от persistent cookie?</strong></summary>

<dl>
<dd>
<h2></h2>

Session cookie не имеет явного срока:

```http
Set-Cookie: sessionId=abc123
```

Она связана с browser session.

Persistent cookie содержит:

```text
Max-Age
```

или:

```text
Expires
```

Например:

```http
Set-Cookie: theme=dark; Max-Age=2592000
```

Такая cookie может сохраняться между запусками браузера до истечения срока или ручного удаления.

Граница browser session зависит от поведения браузера. Восстановление предыдущей сессии может восстановить и часть session cookies.

Поэтому критичную безопасность нельзя строить только на ожидании, что cookie обязательно исчезнет после закрытия окна.

Серверная сессия должна иметь собственный срок жизни и возможность отзыва.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужен <code>HttpOnly</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`HttpOnly` запрещает JavaScript читать cookie:

```js
document.cookie
```

Поэтому XSS-код не может просто получить строку session cookie и отправить её злоумышленнику.

Но вредоносный скрипт всё ещё выполняется внутри origin приложения.

Он может:

- отправлять запросы;
- читать DOM;
- подменять интерфейс;
- получать доступ к `localStorage`;
- выполнять действия от имени пользователя.

`HttpOnly` защищает значение cookie от чтения, но не устраняет саму XSS-уязвимость.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что именно делает <code>SameSite</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`SameSite` управляет отправкой cookie в межсайтовом контексте.

Основные значения:

```text
Strict
Lax
None
```

`Strict` максимально ограничивает отправку при переходах с другого сайта.

`Lax` разрешает часть top-level navigation, но блокирует многие фоновые cross-site-запросы.

`None` разрешает cross-site-отправку и требует:

```text
Secure
```

`SameSite` помогает против CSRF, потому что cookie не прикладывается к части запросов с чужого сайта.

Но этого недостаточно для всех сценариев.

Для чувствительных операций дополнительно применяют:

- безопасные HTTP-методы;
- проверку `Origin`;
- CSRF-токены;
- повторную авторизацию;
- серверную валидацию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему localStorage может вредить производительности?</strong></summary>

<dl>
<dd>
<h2></h2>

Web Storage API синхронный:

```js
localStorage.getItem(...)
localStorage.setItem(...)
```

Операция выполняется на main thread.

Если часто записывать крупный JSON:

```js
localStorage.setItem(
  "state",
  JSON.stringify(largeState),
);
```

главный поток выполняет:

1. `JSON.stringify()`.
2. Синхронный вызов Storage API.
3. Дополнительную внутреннюю работу браузера.

Это может задерживать:

- ввод;
- анимацию;
- React render;
- следующий кадр.

Небольшие настройки обычно читают один раз при инициализации, а рабочее значение держат в памяти приложения.

Большие структурированные данные хранят в IndexedDB.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит с <code>sessionStorage</code> при reload и открытии новой вкладки?</strong></summary>

<dl>
<dd>
<h2></h2>

При обычном reload текущей вкладки `sessionStorage` сохраняется.

Например:

```js
sessionStorage.setItem("step", "delivery");
```

после reload обычно останется доступным в той же tab session.

Независимо открытая новая вкладка того же origin обычно получает собственное хранилище.

Если вкладка открыта через `window.open` и сохраняет связь с opener, браузер может создать начальную копию `sessionStorage` исходной вкладки.

После этого изменения независимы:

```text
вкладка A меняет значение
≠
вкладка B автоматически получает изменение
```

Для постоянной синхронизации между вкладками используют другой механизм, например `BroadcastChannel`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда использовать IndexedDB?</strong></summary>

<dl>
<dd>
<h2></h2>

IndexedDB используют, когда нужны:

- большие структурированные данные;
- поиск по индексам;
- транзакции;
- offline-режим;
- файлы и `Blob`;
- очередь несинхронизированных операций;
- локальный каталог.

Примеры:

```text
каталог товаров
черновики документов
история сообщений
offline-карта
очередь upload
```

Для одного небольшого значения IndexedDB может быть избыточна:

```text
theme=dark
```

Такую настройку проще хранить в `localStorage`.

При выборе также учитывают миграции схемы, ошибки quota и несколько одновременно открытых вкладок.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему IndexedDB-транзакция может завершиться после <code>await</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Транзакция IndexedDB остаётся активной, пока у неё есть незавершённые запросы и выполняется связанная с ними задача.

Если внутри транзакции начать ждать посторонний Promise:

```js
await fetch("/data");
```

у транзакции может не остаться активных IndexedDB-запросов.

Браузер получает возможность автоматически завершить её.

После `await` новая операция может привести к:

```text
TransactionInactiveError
```

Поэтому транзакции делают короткими:

```text
получить внешние данные
→ открыть transaction
→ прочитать или записать данные
→ завершить transaction
```

Wrapper-библиотеки могут предоставлять собственную Promise-модель, но её гарантии нужно проверять отдельно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем Cache API отличается от HTTP cache?</strong></summary>

<dl>
<dd>
<h2></h2>

Cache API явно управляется JavaScript:

```js
const cache = await caches.open("app-v1");

await cache.put(request, response);
```

Код сам определяет:

- что сохранить;
- когда использовать;
- когда обновить;
- когда удалить.

HTTP cache является частью сетевого стека и управляется заголовками:

```text
Cache-Control
ETag
Last-Modified
Expires
Vary
```

Браузер может автоматически использовать или revalidate ответ.

Кратко:

```text
Cache API
→ программно управляемые Request/Response.

HTTP cache
→ автоматическое сетевое кэширование по HTTP.
```

Один запрос может сначала проверяться Service Worker в Cache API, а при обращении к сети дополнительно использовать HTTP cache.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли использовать Cache API без Service Worker?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

Cache API доступен и из JavaScript страницы:

```js
const cache = await caches.open("data-v1");

await cache.put(request, response);
```

Но без Service Worker приложение должно явно обращаться к cache:

```js
const response =
  await cache.match(request);
```

Обычная загрузка страницы:

```html
<img src="/image.jpg">
```

не начнёт автоматически использовать пользовательскую запись Cache API только потому, что код страницы её сохранил.

Для перехвата запросов и выбора стратегии нужен Service Worker с обработчиком `fetch`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что хранить в localStorage допустимо?</strong></summary>

<dl>
<dd>
<h2></h2>

Подходят небольшие несекретные настройки:

- тема;
- язык;
- плотность интерфейса;
- последний раздел;
- скрытие ознакомительного сообщения;
- локальный UI-флаг.

Данные должны допускать:

- отсутствие;
- очистку;
- повреждение;
- старую версию;
- ручное изменение.

Не следует без отдельного анализа хранить:

- access token;
- персональные данные;
- большой API cache;
- файлы;
- единственную копию важного черновика;
- данные другого пользователя.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли доступ к storage завершиться ошибкой?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

Запись может выбросить:

```text
QuotaExceededError
```

Доступ также может быть ограничен политиками браузера, режимом просмотра или настройками пользователя.

Поэтому безопасный код учитывает исключение:

```js
function writeTheme(theme) {
  try {
    localStorage.setItem("theme", theme);

    return true;
  } catch {
    return false;
  }
}
```

Асинхронные операции IndexedDB и Cache API также могут завершиться ошибкой или быть прерваны.

Приложение не должно предполагать, что браузерное хранилище:

- всегда доступно;
- никогда не очищается;
- содержит корректные данные;
- имеет достаточно места.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему сохранённые данные могут сломать приложение после релиза?</strong></summary>

<dl>
<dd>
<h2></h2>

После обновления кода в storage остаются данные старой структуры.

Например, приложение раньше хранило:

```json
{
  "theme": "dark"
}
```

а новая версия ожидает:

```json
{
  "appearance": {
    "theme": "dark"
  }
}
```

Без проверки новый код может завершиться ошибкой.

Данным добавляют версию:

```json
{
  "version": 2,
  "data": {}
}
```

После чтения выполняют:

- валидацию;
- миграцию;
- заполнение defaults;
- безопасный сброс.

В IndexedDB изменение object stores и indexes выполняют в `upgradeneeded`.

При этом старая открытая вкладка может заблокировать upgrade, поэтому обрабатывают `versionchange` и `blocked`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что произойдёт при превышении quota или нехватке диска?</strong></summary>

<dl>
<dd>
<h2></h2>

Запись может завершиться ошибкой:

```text
QuotaExceededError
```

Кроме того, browser storage в best-effort-режиме может быть удалено при нехватке места.

Примерную оценку можно получить:

```js
const {
  usage,
  quota,
} = await navigator.storage.estimate();
```

Но это не точная гарантия доступного объёма для следующей записи.

Приложение должно:

- ограничивать cache;
- удалять устаревшие версии;
- повторять операцию только осознанно;
- показывать ошибку пользователю;
- сохранять критичные данные на сервере;
- уметь восстановиться после eviction.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что нужно очищать при logout или смене пользователя?</strong></summary>

<dl>
<dd>
<h2></h2>

Недостаточно удалить только access token из state.

На устройстве могут остаться:

- данные профиля в store;
- API cache;
- IndexedDB;
- Cache API;
- `localStorage`;
- `sessionStorage`;
- background sync queue;
- открытые WebSocket;
- Service Worker messages.

Очистка зависит от архитектуры, но пользовательские данные должны быть отделены по account ID или удалены при logout.

Особенно опасно сохранить private response в общем Cache API:

```text
/profile
/orders
/messages
```

После входа другого пользователя приложение не должно показать предыдущий ответ.

Серверная сессия также должна быть завершена на backend. Очистка только frontend storage не отзывает уже действующую server session.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как синхронизировать logout или настройку между вкладками?</strong></summary>

<dl>
<dd>
<h2></h2>

Изменение `localStorage` создаёт событие `storage` в других документах того же origin:

```js
window.addEventListener("storage", (event) => {
  if (
    event.key === "auth-event" &&
    event.newValue === "logout"
  ) {
    clearClientSession();
  }
});
```

Событие не вызывается в той же вкладке, которая выполнила запись.

Для явного двустороннего обмена можно использовать:

```js
const channel =
  new BroadcastChannel("auth");

channel.postMessage({
  type: "logout",
});
```

Другие вкладки получают сообщение:

```js
channel.addEventListener("message", (event) => {
  if (event.data?.type === "logout") {
    clearClientSession();
  }
});
```

Каждая вкладка очищает локальный state, но серверная сессия всё равно должна быть завершена на backend.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Подходящее хранилище |
| --- | --- |
| Серверная сессия | Cookie с `HttpOnly`, `Secure`, `SameSite` |
| Настройка темы | `localStorage` |
| Временное состояние вкладки | `sessionStorage` |
| Черновики для работы без сети | IndexedDB |
| Большой структурированный каталог | IndexedDB + indexes |
| Ресурсы PWA и ответы без сети | Cache API + Service Worker |
| HTTP revalidation | HTTP cache, `ETag`, `Cache-Control` |
| Logout между вкладками | Событие `storage` или BroadcastChannel |
| Проверка свободного места | `navigator.storage.estimate()` |
| Запрос устойчивого хранения | `navigator.storage.persist()` |
| Смена пользователя | Очистка или разделение пользовательских cache и данных |
