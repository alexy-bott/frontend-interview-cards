## Вопрос

<br>

 💬 **Что такое memory leak (утечка памяти) во frontend, почему он возникает и как его искать?**

<h2></h2>

<br>
<dl>
<dd>

Memory leak, или утечка памяти, возникает, когда приложению объект уже не нужен, но он остаётся достижимым и поэтому не может быть освобождён garbage collector.

Нужно различать:

- **memory leak** — ненужные данные продолжают занимать память;
- **resource leak** — приложение не завершило timer, observer, WebSocket, Worker или другой внешний ресурс.

Эти проблемы часто связаны. Например, активный `setInterval` сам является незавершённым ресурсом, а его callback может удерживать замыкание с большим массивом и тем самым создавать утечку JavaScript-памяти.

Garbage collector, GC, освобождает объект не потому, что приложение больше логически его не использует, а потому, что до объекта больше нельзя добраться от корневых ссылок.

К корням относятся, например:

- глобальные объекты вроде `window`;
- активные execution contexts и стеки вызовов;
- текущий DOM-документ;
- callbacks, зарегистрированные во внутренних структурах браузера;
- выполняющиеся или ожидающие завершения асинхронные операции;
- ссылки, удерживаемые инструментами отладки.

Упрощённо GC работает по принципу достижимости:

```text
GC roots
→ достижимые объекты считаются живыми
→ недостижимые объекты можно освободить
```

GC не понимает бизнес-смысл данных.

Если глобальный массив продолжает хранить старую страницу результатов:

```js
const history = [];

history.push(largePageData);
```

объекты остаются достижимыми, даже если интерфейс больше их не показывает.

Циклические ссылки сами по себе не являются утечкой:

```js
const first = {};
const second = {};

first.second = second;
second.first = first;
```

Если до `first` и `second` больше нельзя добраться от GC roots, современный garbage collector может освободить весь цикл.

Проблема появляется, когда хотя бы одна внешняя ссылка продолжает удерживать эту группу объектов.

Момент запуска GC не гарантирован. Движок может откладывать сборку, сохранять выделенную память для повторного использования или выполнять разные виды GC постепенно.

Поэтому кратковременный рост графика памяти ещё не доказывает утечку.

Нормальный график часто выглядит как пила:

```text
allocation ↑
allocation ↑
GC ↓
allocation ↑
GC ↓
```

Признак возможной утечки — постепенный рост нижнего уровня после повторяющихся GC:

```text
baseline 100 MB
→ 120 MB
→ 145 MB
→ 170 MB
```

В SPA один документ может жить часами. Поэтому подписка, listener или неограниченный cache накапливаются после каждого перехода между экранами.

Полная навигация к новому документу обычно уничтожает старый JavaScript context, если он не сохранён браузером для повторного использования.

Однако bfcache может намеренно сохранить целый живой экземпляр страницы:

- DOM;
- JavaScript heap;
- значения форм;
- позицию прокрутки.

Это ожидаемое удержание, а не утечка. При профилировании важно отличать объекты активного SPA от страницы, которую браузер временно сохранил для Back/Forward navigation.

Типичные причины утечек:

- listener на долгоживущем объекте без удаления;
- timer или повторяющаяся задача без остановки;
- observer без `disconnect()`;
- WebSocket, SSE, `BroadcastChannel` или `MessagePort` без завершения;
- Worker без `terminate()`;
- неограниченный cache, массив, `Map`, `Set` или история;
- замыкание, которое слишком долго удерживает большой объект;
- object URL без `URL.revokeObjectURL()`;
- detached DOM tree, удерживаемое JavaScript-ссылкой;
- повторное создание ресурсов при каждом монтировании;
- очередь callbacks или Promise, которая никогда не завершается;
- MediaStream с неостановленными tracks;
- сторонняя библиотека, сохраняющая ссылки на уничтоженные компоненты.

Частый пример — listener на `window`:

```js
function mountWidget() {
  const largeData = loadLargeData();

  function handleResize() {
    renderWidget(largeData);
  }

  window.addEventListener("resize", handleResize);
}
```

`window` живёт столько же, сколько документ.

Его внутренняя таблица listeners удерживает `handleResize`, а замыкание `handleResize` удерживает `largeData`.

Если при удалении виджета не вызвать:

```js
window.removeEventListener("resize", handleResize);
```

данные останутся достижимыми.

При этом не каждый listener на DOM-элементе создаёт утечку.

Например, если кнопка, её listener и все связанные объекты образуют полностью недостижимое поддерево, GC способен освободить их вместе, даже если listener не был явно удалён.

Опасны прежде всего ссылки от долгоживущих объектов:

```text
window
document
global store
singleton
active timer
WebSocket
observer registry
```

к короткоживущему компоненту.

Для `removeEventListener()` нужны:

- тот же тип события;
- та же функция;
- то же значение `capture`.

Например, такой cleanup не сработает:

```js
window.addEventListener("resize", () => {
  updateLayout();
});

window.removeEventListener("resize", () => {
  updateLayout();
});
```

Созданы две разные функции.

Нужно сохранить callback:

```js
const handleResize = () => {
  updateLayout();
};

window.addEventListener("resize", handleResize);
window.removeEventListener("resize", handleResize);
```

Альтернатива — связать listener с `AbortSignal`:

```js
const controller = new AbortController();

window.addEventListener("resize", handleResize, {
  signal: controller.signal,
});

controller.abort();
```

После `abort()` браузер удалит связанные listeners.

Timers тоже могут удерживать данные:

```js
const intervalId = setInterval(() => {
  processLargeData(largeData);
}, 1000);
```

Пока interval активен, callback и его замыкание остаются достижимыми.

При завершении владельца ресурса вызывают:

```js
clearInterval(intervalId);
```

Однократный `setTimeout` обычно освобождает callback после выполнения, если на него не осталось других ссылок.

Но timer всё равно может быть проблемой, если:

- задержка очень большая;
- создаются тысячи timers;
- callback повторно планирует сам себя;
- timer никогда не очищается при смене экрана;
- callback удерживает крупное состояние.

Observer необходимо явно отключать, когда он больше не нужен:

```js
const observer = new ResizeObserver(handleResize);

observer.observe(element);

// cleanup
observer.disconnect();
```

Это относится, например, к:

```text
ResizeObserver
IntersectionObserver
MutationObserver
PerformanceObserver
```

Конкретный observer и браузер могут по-разному удерживать цели и callbacks, поэтому lifecycle всё равно задают явно.

Долгоживущие соединения и каналы также требуют владельца:

```js
const socket = new WebSocket(url);

// cleanup
socket.close();
```

Аналогично завершают:

```text
EventSource
BroadcastChannel
MessagePort
Web Worker
SharedWorker connection
MediaStreamTrack
AudioContext
```

Метод завершения зависит от API:

```js
eventSource.close();
channel.close();
port.close();
worker.terminate();
track.stop();
audioContext.close();
```

Замыкание само по себе не является утечкой.

Замыкания — обычная часть JavaScript:

```js
function createHandler(data) {
  return () => {
    console.log(data);
  };
}
```

Проблема появляется, когда возвращённая функция живёт дольше, чем должна, и удерживает ненужные данные.

Например:

```text
window listener
→ callback
→ lexical environment
→ большой массив
```

Исправляют не само наличие closure, а неправильный срок жизни владельца callback.

Неограниченные caches тоже остаются полностью достижимыми и поэтому не будут очищены GC:

```js
const cache = new Map();

function remember(id, data) {
  cache.set(id, data);
}
```

Если ключей становится всё больше, нужна политика:

- максимальное число записей;
- максимальный объём;
- TTL;
- LRU-вытеснение;
- ручная invalidation;
- очистка при logout или смене workspace.

Кэш отличается от утечки тем, что данные хранятся намеренно и повторно используются. Но неограниченный кэш с бесконечным ростом практически приводит к той же проблеме памяти.

`URL.createObjectURL()` создаёт URL, связанный с `Blob` или `File`:

```js
const url = URL.createObjectURL(file);
```

Пока URL существует, браузер может удерживать связанные данные вне обычного JavaScript heap.

После завершения использования вызывают:

```js
URL.revokeObjectURL(url);
```

Для preview изображения URL обычно отзывают после загрузки нового ресурса или при cleanup компонента:

```js
image.addEventListener("load", () => {
  URL.revokeObjectURL(url);
}, { once: true });
```

Нельзя отзывать URL до того, как потребитель успел его прочитать.

**Detached DOM node** — DOM-узел, который больше не входит в документ, но остаётся достижимым из JavaScript.

Например:

```js
const retainedNodes = [];

const panel = document.querySelector(".panel");

retainedNodes.push(panel);
panel.remove();
```

Узел удалён из документа, но массив продолжает хранить ссылку.

Вместе с родительским элементом могут удерживаться:

- всё его поддерево;
- тексты;
- attributes;
- listeners;
- связанные данные;
- closures.

Само наличие detached node в snapshot ещё не доказывает утечку.

Узел может временно удерживаться:

- логикой приложения;
- анимацией выхода;
- framework reconciliation;
- History или bfcache;
- Console;
- переменной `$0` выбранного элемента DevTools;
- раскрытым объектом в DevTools.

Нужно проверить retaining path и понять, кто является реальным владельцем.

В React effect должен симметрично завершать созданную им внешнюю работу:

```tsx
useEffect(() => {
  const controller = new AbortController();
  const observer = new ResizeObserver(handleResize);
  const intervalId = window.setInterval(refresh, 5000);

  window.addEventListener("resize", handleResize, {
    signal: controller.signal,
  });

  observer.observe(element);

  return () => {
    controller.abort();
    observer.disconnect();
    window.clearInterval(intervalId);
  };
}, []);
```

Cleanup запускается:

- перед удалением компонента;
- перед повторным запуском effect с изменившимися зависимостями;
- в дополнительном проверочном цикле Strict Mode в development.

Полезная модель:

```text
setup создал ресурс
→ cleanup завершил тот же ресурс
```

Effect должен очищать только тот ресурс, которым он владеет.

Если WebSocket используется несколькими компонентами, его не должен закрывать первый размонтировавшийся consumer. Lifecycle такого соединения лучше хранить у общего владельца:

- service;
- provider;
- store;
- connection manager.

В React Strict Mode при разработке effect может пройти дополнительную последовательность:

```text
setup
→ cleanup
→ setup
```

Это помогает обнаружить несимметричную логику.

Если после цикла остаются:

- два timers;
- два WebSocket;
- два listeners;
- две подписки;

значит cleanup не полностью отменяет setup.

В production этот проверочный цикл не выполняется, но ошибка всё равно проявится при реальном повторном монтировании, изменении dependencies или переходе между экранами.

React сам управляет JSX-listeners:

```tsx
<button onClick={handleClick} />
```

При удалении компонента не нужно вручную выполнять `removeEventListener` для этого JSX-handler.

Но React не может автоматически завершить произвольный внешний ресурс, созданный внутри effect.

Незавершённый `fetch` не всегда является утечкой памяти:

```tsx
useEffect(() => {
  fetch(url).then(handleResponse);
}, [url]);
```

Обычный запрос обычно завершится, после чего связанные Promise и callbacks смогут стать недостижимыми.

Но остаются другие проблемы:

- запрос расходует сеть;
- ответ может прийти после смены параметров;
- устаревший результат может перезаписать новые данные;
- callback временно удерживает замыкание;
- долгий streaming response может жить значительно дольше.

Если запрос принадлежит effect, его можно отменить:

```tsx
useEffect(() => {
  const controller = new AbortController();

  void fetch(url, {
    signal: controller.signal,
  });

  return () => {
    controller.abort();
  };
}, [url]);
```

Если API нельзя отменить, результат можно признать неактуальным через request ID, флаг или сравнение параметров.

Важно различать:

```text
memory leak
→ данные остаются достижимыми без ограничения

race condition
→ старый результат применяется не в тот момент

лишняя работа
→ запрос больше не нужен, но продолжает выполняться
```

Одна проблема может существовать без остальных.

Искать утечку начинают не с одного случайного snapshot, а с воспроизводимого сценария.

Например:

```text
открыть модальное окно
→ закрыть модальное окно
→ вернуться в нейтральное состояние
```

или:

```text
открыть страницу чата
→ подключиться
→ уйти со страницы
```

Рекомендуемый процесс:

1. Открыть production-подобную сборку.
2. Убрать постороннюю активность.
3. Один или несколько раз выполнить сценарий для прогрева.
4. Вернуться в одинаковое нейтральное состояние.
5. Запустить GC через DevTools.
6. Сделать первый Heap Snapshot.
7. Повторить сценарий несколько раз.
8. Снова вернуться в нейтральное состояние.
9. Запустить GC.
10. Сделать второй snapshot.
11. Сравнить количество и retained size объектов.
12. Исследовать retaining paths подозрительных экземпляров.
13. Повторить проверку после исправления.

Прогрев нужен, потому что первый запуск может создавать нормальные долгоживущие структуры:

- compiled code;
- caches движка;
- framework metadata;
- lazy-loaded modules;
- шрифты;
- singleton services.

После прогрева эти структуры должны выйти на устойчивый уровень.

Heap Snapshot показывает объекты JavaScript heap на конкретный момент.

В режиме Comparison ищут типы объектов, у которых после одинакового сценария повторяемо растут:

- количество экземпляров;
- retained size;
- число detached nodes;
- число listeners или closures;
- массивы и коллекции приложения.

**Shallow size** — память самого объекта без объектов, на которые он ссылается.

Например, небольшой объект может иметь маленький shallow size, но удерживать большой массив.

**Retained size** — объём памяти, который потенциально освободится, если этот объект и удерживаемое только через него поддерево станут недостижимыми.

Поэтому объект с маленьким shallow size может быть важнее большого объекта:

```text
маленький listener
→ closure
→ store
→ тысячи записей
```

**Retaining path**, или путь удержания, показывает цепочку ссылок от GC root до исследуемого объекта:

```text
Window
→ event listener
→ callback
→ closure
→ component data
→ detached DOM tree
```

Исправлять нужно неправильную удерживающую ссылку, а не случайный объект в конце цепочки.

В анализе heap также используется понятие **dominator** — объект, через который проходят пути к удерживаемой группе объектов.

Удаление ссылки от такого владельца может освободить большое поддерево памяти.

Для разных задач используют разные режимы Memory panel.

**Heap Snapshot** подходит, когда нужно:

- увидеть оставшиеся объекты;
- сравнить два состояния;
- найти detached DOM;
- изучить retaining path;
- оценить retained size.

**Allocation instrumentation on timeline** записывает allocations во времени и помогает связать выжившие объекты с местом создания.

Этот режим полезен, если утечка появляется во время повторяющегося действия, но создаёт дополнительную нагрузку и может менять timing приложения.

**Allocation sampling** с меньшими накладными расходами приблизительно показывает, какие call stacks создают больше всего памяти.

Он удобен для поиска горячих мест allocations, но не заменяет точный retaining path конкретного объекта.

**Performance Monitor** помогает наблюдать динамику:

- JavaScript heap;
- число DOM nodes;
- число listeners;
- CPU;
- layout activity.

Task Manager браузера помогает сравнивать память процессов и вкладок.

При этом Heap Snapshot не описывает всю память браузерного процесса.

Вне или частично вне JavaScript heap могут находиться:

- декодированные изображения;
- `Blob`;
- backing stores `ArrayBuffer`;
- canvas buffers;
- WebGL textures;
- видео;
- шрифты;
- GPU layers;
- внутренние сетевые buffers;
- структуры browser engine.

Например, object URL может удерживать большой `Blob`, а Heap Snapshot покажет только небольшую JavaScript-обёртку.

Для таких проблем дополнительно используют:

- Performance panel;
- Performance Monitor;
- браузерный Task Manager;
- инструменты для canvas/WebGL;
- анализ количества DOM nodes и ресурсов.

DevTools сам способен влиять на результаты.

Console может удерживать:

- выведенные объекты;
- результаты последних expressions;
- выбранный DOM-элемент через `$0`;
- раскрытые структуры.

Поэтому во время чистого эксперимента:

- очищают Console;
- не сохраняют подозрительные объекты в глобальные переменные;
- не держат выбранным удалённый узел;
- сравнивают одинаковые состояния;
- повторяют тест после перезапуска страницы.

Один snapshot содержит множество нормальных объектов браузера, framework и DevTools.

Утечку подтверждает не само наличие объекта, а сочетание признаков:

- объект больше не нужен по логике приложения;
- он остаётся достижимым;
- retaining path ведёт к неправильному долгоживущему владельцу;
- число экземпляров растёт после одинакового сценария;
- память не возвращается к устойчивому уровню после GC;
- после исправления рост исчезает.

Практический алгоритм:

```text
1. Найти повторяемый сценарий.
2. Вернуться в одинаковое нейтральное состояние.
3. Подтвердить растущий baseline.
4. Найти растущий тип объектов.
5. Открыть retaining path.
6. Определить долгоживущего владельца.
7. Исправить lifecycle или политику хранения.
8. Повторить тот же эксперимент.
```

</dl>

## Дополнительные вопросы

<details>
<summary><strong>Почему garbage collector не всегда освобождает память?</strong></summary>

<dl>
<dd>
<h2></h2>

GC освобождает только недостижимые объекты.

Он начинает с корневых ссылок и проходит по всем доступным связям:

```text
GC root
→ object
→ callback
→ closure
→ data
```

Если путь существует, объект считается живым, даже если бизнес-логике он больше не нужен.

GC не знает, что пользователь закрыл модальное окно или покинул экран.

Кроме того, GC не обязан запускаться сразу после удаления последней ссылки. Движок выбирает момент с учётом:

- объёма allocations;
- нагрузки;
- поколения объектов;
- доступной памяти;
- пауз main thread.

Движок также может не возвращать освобождённую память операционной системе немедленно, а оставить её в heap для будущих allocations.

Поэтому размер процесса может не уменьшиться сразу, даже если объекты уже были собраны.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Являются ли циклические ссылки утечкой?</strong></summary>

<dl>
<dd>
<h2></h2>

Не сами по себе.

Например:

```js
const parent = {};
const child = {};

parent.child = child;
child.parent = parent;
```

Если внешние ссылки на `parent` и `child` исчезнут, весь цикл станет недостижимым и современный GC сможет его освободить.

Утечка возникает, если цикл удерживается извне:

```text
window
→ listener
→ parent
↔ child
```

Проблемой является путь от GC root, а не наличие взаимных ссылок внутри группы.

Это одно из отличий tracing garbage collector от простого подсчёта ссылок.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда event listener действительно создаёт утечку?</strong></summary>

<dl>
<dd>
<h2></h2>

Listener создаёт риск утечки, когда долгоживущий target удерживает callback короткоживущего компонента.

Например:

```js
window.addEventListener("resize", handleResize);
```

Цепочка может выглядеть так:

```text
window
→ listener registry
→ handleResize
→ closure
→ component state
```

После удаления компонента listener остаётся у `window`, поэтому state продолжает жить.

Если же listener находится на кнопке и вся кнопка вместе с listener стала недостижимой, GC может собрать их вместе.

Для корректного удаления нужна та же функция:

```js
window.addEventListener("resize", handleResize);

// cleanup
window.removeEventListener("resize", handleResize);
```

И то же значение `capture`.

Также можно использовать:

```js
window.addEventListener("resize", handleResize, {
  signal: controller.signal,
});
```

и удалить listener через:

```js
controller.abort();
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое retaining path?</strong></summary>

<dl>
<dd>
<h2></h2>

Retaining path — цепочка ссылок от GC root до исследуемого объекта.

Например:

```text
Window
→ resize listener
→ callback
→ closure
→ array
→ detached DOM node
```

Пока эта цепочка существует, объект достижим и не может быть освобождён.

В Heap Snapshot подозрительный объект раскрывают в разделе retainers и поднимаются вверх по цепочке.

Искать нужно владельца с неправильным сроком жизни:

- глобальный listener;
- singleton cache;
- timer;
- observer;
- store;
- замыкание;
- DevTools Console.

Удаление случайного объекта в конце цепочки не решит проблему, если долгоживущий владелец продолжит накапливать новые экземпляры.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое detached DOM node?</strong></summary>

<dl>
<dd>
<h2></h2>

Detached DOM node — узел, который больше не является частью текущего документа, но остаётся достижимым из JavaScript или внутренней структуры браузера.

Например:

```js
const nodes = [];

const modal = document.querySelector(".modal");

nodes.push(modal);
modal.remove();
```

`modal` исчез из интерфейса, но массив `nodes` продолжает его удерживать.

Ссылка на корневой узел может удерживать всё поддерево:

- дочерние элементы;
- тексты;
- attributes;
- listeners;
- связанные closures.

Однако detached node не всегда означает leak.

Он может временно использоваться framework, анимацией или DevTools.

Подтверждение получают через retaining path и повторяемый рост после одинакового сценария.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли DevTools сам удерживать объекты?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

DevTools может сохранять ссылки на:

- объект, выведенный через `console.log`;
- результат последнего expression;
- выбранный DOM-элемент через `$0`;
- раскрытый объект в Console;
- результаты профилирования.

Например:

```js
console.log(largeObject);
```

может оставить объект доступным для дальнейшего исследования в Console.

При чистом эксперименте полезно:

- очистить Console;
- убрать глобальные debug-переменные;
- не держать выбранным удалённый DOM-узел;
- повторить тест после reload;
- сравнивать несколько одинаковых циклов.

Поэтому наличие retaining path через DevTools или Console не обязательно означает ошибку production-кода.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какую очистку нужно выполнять в React effects?</strong></summary>

<dl>
<dd>
<h2></h2>

Cleanup должен отменить внешнюю работу, созданную effect.

Например:

- удалить нативный listener;
- очистить timer;
- отписаться от store;
- вызвать `disconnect()` у observer;
- закрыть принадлежащее effect соединение;
- отменить запрос;
- завершить Worker;
- освободить object URL.

Модель должна быть симметричной:

```text
addEventListener → removeEventListener
setInterval      → clearInterval
observe          → disconnect/unobserve
subscribe        → unsubscribe
createObjectURL  → revokeObjectURL
```

React сам удаляет JSX-handlers вместе с компонентом:

```tsx
<button onClick={handleClick} />
```

Но произвольные внешние ресурсы он завершить не может.

Shared-ресурс нельзя безусловно уничтожать в cleanup одного consumer. Его lifecycle должен контролировать общий владелец.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Кто должен выполнять cleanup общего ресурса?</strong></summary>

<dl>
<dd>
<h2></h2>

Cleanup выполняет владелец ресурса.

Если компонент самостоятельно создал timer:

```tsx
useEffect(() => {
  const id = setInterval(refresh, 5000);

  return () => {
    clearInterval(id);
  };
}, []);
```

компонент является владельцем и должен его остановить.

Если несколько компонентов используют один WebSocket, отдельный consumer не должен закрывать соединение при своём unmount.

Владельцем может быть:

- provider;
- singleton service;
- store;
- connection manager;
- верхнеуровневый feature-модуль.

Общий владелец может использовать:

- reference counting;
- явные `connect()`/`disconnect()`;
- lifecycle приложения;
- idle timeout.

Главное правило:

```text
Кто создал и контролирует срок жизни ресурса,
тот и отвечает за его завершение.
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем Strict Mode повторно запускает effect при разработке?</strong></summary>

<dl>
<dd>
<h2></h2>

React выполняет дополнительную проверочную последовательность:

```text
setup
→ cleanup
→ setup
```

Она помогает обнаружить effect, который создаёт ресурс, но не полностью его завершает.

Например, после проверки могут остаться:

- два timers;
- два WebSocket;
- два нативных listeners;
- две подписки.

Это означает, что cleanup несимметричен setup.

В production дополнительный проверочный цикл не выполняется.

Но ошибка всё равно может проявиться при:

- реальном remount;
- изменении dependencies;
- условном отображении компонента;
- переходе между страницами.

Strict Mode не создаёт проблему, а делает существующую проблему заметнее во время разработки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли незавершённый <code>fetch</code> является memory leak?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Обычный `fetch` обычно когда-нибудь завершится или завершится ошибкой. После этого Promise и callbacks смогут быть освобождены, если на них не осталось ссылок.

Но незавершённый запрос может создавать:

- лишний сетевой трафик;
- временное удержание closure;
- race condition;
- применение устаревшего результата;
- лишнюю работу сервера.

Если запрос принадлежит effect, его обычно отменяют:

```tsx
useEffect(() => {
  const controller = new AbortController();

  void fetch(url, {
    signal: controller.signal,
  });

  return () => {
    controller.abort();
  };
}, [url]);
```

Действительная утечка возможна, если операция неограниченно долго остаётся pending или связана с постоянно живущей очередью, подпиской или streaming response.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как object URL может течь?</strong></summary>

<dl>
<dd>
<h2></h2>

`URL.createObjectURL()` создаёт URL, связанный с `Blob` или `File`:

```js
const url = URL.createObjectURL(file);
```

Браузер может удерживать данные, пока URL не будет отозван или документ не завершится.

После использования вызывают:

```js
URL.revokeObjectURL(url);
```

Для image preview это делают:

- после успешной загрузки изображения;
- при выборе нового файла;
- при cleanup компонента.

Отзывать URL слишком рано нельзя: изображение или другой потребитель должен успеть прочитать ресурс.

Память `Blob` может находиться вне обычного JS heap, поэтому проблема не всегда полностью видна в Heap Snapshot.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Решают ли <code>WeakMap</code> и <code>WeakRef</code> проблему утечек?</strong></summary>

<dl>
<dd>
<h2></h2>

Только в специальных структурах данных.

`WeakMap` не удерживает объект-ключ:

```js
const metadata = new WeakMap();

metadata.set(element, {
  state: "active",
});
```

Если `element` больше нигде не используется, наличие записи в `WeakMap` не должно удерживать его в памяти.

Это подходит для metadata, срок жизни которых связан со сроком жизни объекта-ключа.

`WeakRef` позволяет получить слабую ссылку:

```js
const reference = new WeakRef(object);
```

Но момент GC непредсказуем, и `deref()` в любой момент может вернуть `undefined`.

`WeakMap` и `WeakRef` не:

- удаляют event listeners;
- закрывают WebSocket;
- очищают timers;
- ограничивают растущий массив;
- заменяют правильный lifecycle.

`FinalizationRegistry` также не используют для критичного cleanup, потому что callback может выполниться поздно или не выполниться до завершения процесса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как отличить утечку от нормального кэша?</strong></summary>

<dl>
<dd>
<h2></h2>

Кэш хранит данные намеренно и имеет понятную пользу.

У управляемого кэша есть хотя бы одна политика:

- максимальное число записей;
- максимальный объём;
- TTL;
- LRU;
- invalidation;
- очистка при logout;
- привязка к версии данных.

Записи повторно используются и уменьшают стоимость запросов или вычислений.

Утечка обычно:

- растёт после каждого одинакового действия;
- не имеет полезного повторного использования;
- не освобождается после ухода с экрана;
- не имеет ограничения;
- удерживается случайным владельцем.

Неограниченный кэш формально хранит данные намеренно, но практически создаёт такую же проблему неконтролируемого роста памяти.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем Heap Snapshot, Allocation instrumentation и Allocation sampling отличаются?</strong></summary>

<dl>
<dd>
<h2></h2>

**Heap Snapshot** показывает состояние heap в конкретный момент.

Он подходит для:

- сравнения состояний;
- поиска retaining path;
- detached DOM;
- анализа shallow и retained size.

**Allocation instrumentation on timeline** записывает allocations во времени и связывает выжившие объекты с местом создания.

Он полезен для сценария:

```text
открыть
→ закрыть
→ открыть
→ закрыть
```

но создаёт заметные накладные расходы.

**Allocation sampling** приблизительно показывает call stacks, создающие больше всего памяти, с меньшим влиянием на приложение.

Он удобен для поиска общего источника allocations, но не показывает точный путь удержания конкретного объекта так же подробно, как snapshot.

Обычно инструменты комбинируют:

```text
граф показал рост
→ snapshot нашёл объект
→ retaining path нашёл владельца
→ allocation profiling нашёл место создания
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему Heap Snapshot не показывает всю память вкладки?</strong></summary>

<dl>
<dd>
<h2></h2>

Heap Snapshot в первую очередь описывает JavaScript heap и связанные объекты.

Значительная память может находиться в других подсистемах:

- декодированные изображения;
- видео;
- canvas buffers;
- WebGL textures;
- GPU layers;
- `Blob`;
- backing stores `ArrayBuffer`;
- шрифты;
- DOM-структуры движка;
- сетевые buffers.

JavaScript-объект может иметь маленький shallow size, но быть обёрткой над крупным внешним ресурсом.

Поэтому при росте памяти дополнительно проверяют:

- браузерный Task Manager;
- Performance Monitor;
- количество DOM nodes;
- размеры изображений;
- canvas/WebGL lifecycle;
- object URLs;
- Workers и MediaStream.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать, если leak проявляется только со временем?</strong></summary>

<dl>
<dd>
<h2></h2>

Долгий сценарий стараются заменить коротким повторяемым циклом.

Например, вместо ожидания часа:

```text
открыть чат
→ подключиться
→ уйти
```

повторяют десятки раз.

Дальше:

1. Выполняют прогрев.
2. Фиксируют начальный baseline после GC.
3. Повторяют цикл одинаковое число раз.
4. Возвращаются в нейтральное состояние.
5. Снова запускают GC.
6. Сравнивают snapshots и граф.
7. Проверяют retaining paths растущих объектов.

Allocation instrumentation помогает увидеть, где создаются объекты, которые пережили цикл.

Смотрят именно на устойчивый тренд после GC, потому что рост между GC может быть нормальной активностью приложения.

После исправления повторяют тот же сценарий с тем же количеством итераций.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Возможная причина утечки |
| --- | --- |
| Модальное окно открывали много раз | Listener на `document` добавляется повторно и не удаляется |
| Компонент удалён, но работа продолжается | Timer, observer или подписка не остановлены |
| Чат дублирует сообщения | WebSocket listeners регистрируются повторно |
| После переходов растёт число соединений | Shared-ресурс не имеет явного владельца |
| Предварительный просмотр файлов увеличивает память | Object URLs не отзываются |
| Таблица становится тяжелее | Store или cache хранит старые страницы без лимита |
| Удалённый элемент остаётся в памяти | Detached DOM tree удерживается JavaScript-ссылкой |
| Память растёт только с открытым DevTools | Console или выбранный `$0` удерживает объект |
| Heap стабилен, но процесс растёт | Изображения, canvas, Blob, GPU или другой внешний ресурс |
| Старый запрос перезаписывает новые данные | Race condition, не обязательно memory leak |
