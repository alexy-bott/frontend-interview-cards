#### Вопрос

Какие способы хранения данных есть в браузере и чем отличаются cookie, localStorage, sessionStorage, IndexedDB и Cache API?

#### Ответ

Способ хранения выбирают по владельцу данных, объёму, сроку жизни, требованиям к запросам и модели угроз. Cookie участвуют в HTTP, Web Storage хранит небольшие строки, IndexedDB - структурированные данные, а Cache API - объекты сетевых запросов и ответов. Эти механизмы не являются взаимозаменяемыми.

**Cookie** - небольшая пара имени и значения с атрибутами. Браузер автоматически добавляет подходящие cookie к HTTP-запросу с учётом домена, пути, протокола и правила `SameSite`. Это удобно для серверной сессии: сервер получает идентификатор сессии без ручного добавления токена в каждый запрос. Объём одной cookie и число cookie на сайт ограничены, а их автоматическая отправка увеличивает запрос и создаёт риск CSRF.

`HttpOnly` запрещает чтение cookie через JavaScript, `Secure` разрешает передачу только по HTTPS, а `SameSite` ограничивает отправку в межсайтовых запросах. Значение `SameSite=None` требует `Secure`; `Lax` и `Strict` дают более жёсткие ограничения. Если атрибут `Domain` отсутствует, cookie является host-only, то есть относится только к текущему host и не отправляется на соседние поддомены. `Path` выбирает подходящие URL, но не является границей безопасности.

`HttpOnly` уменьшает риск кражи cookie сессии при XSS, но не обезвреживает сам XSS: вредоносный код всё ещё может отправлять запросы от имени пользователя. `SameSite` помогает против CSRF, но серверу всё равно нужны корректные проверки метода, origin и при необходимости CSRF-токен.

**localStorage** - синхронное хранилище строковых пар «ключ-значение» в пределах origin, то есть сочетания схемы, host и порта. Данные не имеют встроенного срока истечения и обычно переживают закрытие браузера. Хранилище подходит для небольших пользовательских настроек, но доступно любому JavaScript того же origin и может блокировать главный поток при крупных или частых операциях. Объекты приходится сериализовать, например через JSON, и безопасно разбирать после чтения.

**sessionStorage** имеет такой же синхронный строковый API, но дополнительно разделён по top-level browsing context, то есть обычно по вкладке. Он живёт до закрытия вкладки и подходит для временного черновика или шага сценария, который не должен быть общим между окнами.

**IndexedDB** - асинхронная транзакционная база данных в пределах origin. Она сохраняет значения алгоритмом structured clone, который копирует поддерживаемые структуры вроде объектов, массивов, `Blob` и `File` без ручного JSON. Данные организуются в object stores, или хранилища объектов, а indexes, или индексы, ускоряют поиск по выбранным полям. IndexedDB подходит для данных приложения, работающего без сети, больших черновиков, очередей синхронизации и локальных каталогов.

Схема IndexedDB имеет числовую версию. Изменение object stores и indexes выполняют в транзакции `versionchange` обработчика `upgradeneeded`. Открытая вкладка со старой версией может заблокировать обновление схемы, поэтому приложение обрабатывает события `versionchange` и `blocked`, закрывает старое соединение и предлагает пользователю обновить вкладку. Операции внутри транзакции планируют без долгих посторонних `await`, иначе транзакция может автоматически завершиться до следующего запроса.

**Cache API** хранит пары `Request`/`Response` и обычно используется Service Worker для ресурсов, доступных без сети. Записи добавляет и удаляет JavaScript; они не обновляются автоматически только потому, что на сервере вышла новая версия. **HTTP cache**, напротив, управляется сетевым стеком браузера по `Cache-Control`, `ETag` и другим HTTP-заголовкам. Наличие ответа в Cache API не означает, что его данные свежие или безопасны для другого пользователя.

Все хранилища ограничены quota, то есть выделенным объёмом, который зависит от браузера, устройства и свободного места. Данные в обычном непостоянном режиме (best effort) могут быть удалены браузером при нехватке диска. `navigator.storage.estimate()` показывает примерное использование и лимит, а `navigator.storage.persist()` может запросить более устойчивый режим, но не гарантирует его выдачу. Приложение обязано обрабатывать `QuotaExceededError`, повреждённые данные и отсутствие записи.

Секреты нельзя автоматически складывать в самое удобное хранилище. Access token в `localStorage` доступен при XSS. HttpOnly-cookie уменьшает возможность прочитать токен, но требует защиты от CSRF и корректной серверной сессии. Выбор определяется моделью угроз, архитектурой backend и способом восстановления доступа, а не универсальным правилом «cookie всегда безопаснее».

#### Встречные вопросы

> [!followup]
> **Вопрос:** Почему cookie автоматически отправляются с запросами?
>
> **Ответ:** Так определён HTTP-механизм cookie. Браузер сопоставляет домен, путь, `Secure`, `SameSite`, срок жизни и другие атрибуты, после чего формирует заголовок `Cookie`. Приложение не добавляет его вручную через JavaScript. Поэтому серверная сессия работает удобно, но запрос может уйти автоматически и требует CSRF-защиты.

> [!followup]
> **Вопрос:** Зачем нужен `HttpOnly`?
>
> **Ответ:** `HttpOnly` запрещает чтение cookie через `document.cookie`, поэтому XSS-код не может просто скопировать её значение. Но вредоносный скрипт всё ещё выполняется на странице и может отправлять разрешённые запросы от имени пользователя. Флаг защищает секрет от чтения, а не приложение от всех последствий XSS.

> [!followup]
> **Вопрос:** Почему localStorage может вредить производительности?
>
> **Ответ:** API синхронный: чтение, сериализация и запись выполняются на главном потоке. Крупный JSON или частые операции во время рендера и пользовательского ввода задерживают кадр. Для больших структурированных данных используют IndexedDB, а небольшие настройки читают один раз и держат рабочее значение в состоянии приложения.

> [!followup]
> **Вопрос:** Когда использовать IndexedDB?
>
> **Ответ:** Когда нужны структурированные объекты, индексы, транзакции, большой объём или работа без сети: каталог товаров, черновики, файлы и очередь несинхронизированных действий. IndexedDB сложнее Web Storage, поэтому для одного небольшого строкового значения она избыточна.

> [!followup]
> **Вопрос:** Чем Cache API отличается от HTTP cache?
>
> **Ответ:** Cache API явно управляется JavaScript и хранит выбранные пары `Request`/`Response`; код сам определяет стратегию свежести и удаления. HTTP cache является частью сетевого стека и повторно использует ответы по HTTP-заголовкам. Один ресурс может последовательно пройти через Service Worker, Cache API и сетевой запрос, который отдельно использует HTTP cache.

> [!followup]
> **Вопрос:** Что хранить в localStorage допустимо?
>
> **Ответ:** Небольшие несекретные настройки: тема, язык, плотность таблицы или последний открытый раздел. Данные должны допускать сброс, потому что пользователь или браузер может очистить storage. Токены, персональные данные и большие ответы сервера требуют отдельного анализа безопасности, объёма и актуальности.

> [!followup]
> **Вопрос:** Почему сохранённые данные могут сломать приложение после релиза?
>
> **Ответ:** После обновления приложения в хранилище остаётся значение старой схемы или повреждённый JSON. Сохраняемым данным добавляют версию, проверяют форму после чтения и выполняют миграцию либо безопасный сброс. В IndexedDB изменение схемы делают в `upgradeneeded`; нужно учитывать вкладки со старой версией, способные заблокировать обновление.

> [!followup]
> **Вопрос:** Что произойдёт при превышении quota или нехватке диска?
>
> **Ответ:** Запись может завершиться `QuotaExceededError`, а данные в режиме best effort браузер способен удалить для освобождения места. Приложение обрабатывает ошибку, очищает старые кэши и не считает браузерное хранилище единственной копией критичных данных. Примерный лимит и использование можно получить через `navigator.storage.estimate()`.

> [!followup]
> **Вопрос:** Как синхронизировать logout или настройку между вкладками?
>
> **Ответ:** Изменение `localStorage` создаёт событие `storage` в других документах того же origin, но не в самой вкладке, которая выполнила запись. Для явного двустороннего обмена подходит `BroadcastChannel`. Получив сигнал logout, каждая вкладка очищает клиентское состояние, однако серверная сессия всё равно должна быть завершена на backend.

#### Где это встречается во frontend

| Сценарий | Подходящее хранилище |
| --- | --- |
| Серверная сессия | Cookie с `HttpOnly`, `Secure`, `SameSite` |
| Настройка темы | `localStorage` |
| Временное состояние вкладки | `sessionStorage` |
| Черновики для работы без сети | IndexedDB |
| Ресурсы PWA и ответы без сети | Cache API + Service Worker |
| Logout между вкладками | Событие `storage` или BroadcastChannel |
