## Вопрос

<br>

 💬 **Как работает rendering pipeline браузера? Чем отличаются layout/reflow, paint и composite?**

<h2></h2>

<br>
<dl>
<dd>

Rendering pipeline, или конвейер рендеринга, — последовательность этапов, через которые браузер превращает HTML, CSS и изменения JavaScript в пиксели на экране.

Упрощённо полный pipeline выглядит так:

```text
style calculation
→ layout
→ paint
→ rasterization
→ composite
```

Это концептуальная модель, а не обязательный полный набор операций для каждого кадра. Браузер может:

- отложить вычисления;
- объединить несколько изменений;
- ограничить работу частью дерева;
- повторно использовать готовые данные;
- пропустить ненужные стадии.

Например, изменение ширины обычно затрагивает layout и последующие стадии, изменение фона может обойтись без layout, а подготовленная анимация `transform` иногда обновляется только на compositor thread.

При первой загрузке браузер строит DOM из HTML и внутреннее представление CSS-правил из таблиц стилей.

После изменений DOM или CSS браузер сначала выполняет invalidation — отмечает, какие стили, геометрия или области рисования могли устареть.

Invalidation ещё не означает, что браузер немедленно выполнил полный пересчёт. Он часто откладывает фактическую работу до момента, когда она понадобится:

- перед следующим кадром;
- перед выполнением script, которому нужны актуальные данные;
- перед чтением геометрии из JavaScript.

На этапе **style calculation**, или пересчёта стилей, браузер определяет итоговые CSS-значения для затронутых элементов.

Он учитывает:

- selectors;
- origin правил;
- cascade layers;
- специфичность;
- порядок;
- наследование;
- CSS custom properties;
- media и container queries;
- inline styles;
- user-agent styles.

Например:

```css
.button {
  color: red;
}

.container .button {
  color: blue;
}
```

Для подходящего элемента computed value свойства `color` будет `blue`.

Браузер старается пересчитывать только затронутую часть дерева. Но изменение наследуемого свойства у крупного контейнера может повлиять на множество потомков:

```css
.page {
  color: blue;
}
```

А изменение CSS custom property на корневом элементе способно потребовать проверки всех элементов, которые прямо или косвенно используют эту переменную:

```css
:root {
  --color-text: black;
}
```

На этапе **layout** рассчитывается геометрия визуальных коробок:

- ширина и высота;
- координаты;
- перенос строк;
- размеры Flexbox- и Grid-дорожек;
- положение обычных и позиционированных элементов;
- области прокрутки;
- геометрия потомков.

Термин **reflow** обычно используют для повторного layout после изменения уже отображённой страницы.

Layout могут вызвать изменения:

```css
width
height
min-width
padding
margin
display
position
font-size
line-height
```

а также:

- добавление или удаление DOM-элемента;
- изменение текста;
- загрузка шрифта;
- изменение размера viewport;
- изменение содержимого изображения;
- появление scrollbar.

Изменение геометрии одного элемента может повлиять не только на него.

Например, новая ширина контейнера способна изменить:

- перенос текста у потомков;
- размеры Grid-дорожек;
- распределение Flexbox;
- положение соседних элементов;
- высоту всех следующих блоков.

Браузер старается ограничить layout затронутой областью, но изменение высокоуровневого контейнера может распространиться на большое поддерево.

На этапе **paint** браузер определяет, что и в каком порядке нужно нарисовать.

Формируются paint records или display list с командами для:

- текста;
- фонов;
- границ;
- изображений;
- теней;
- outline;
- декоративных эффектов.

Например:

```css
.element {
  background-color: red;
}
```

Изменение `background-color` обычно не меняет геометрию, поэтому новый layout не требуется. Но изменились будущие пиксели, следовательно, затронутая область должна быть заново painted.

**Repaint** — распространённое название повторного paint после визуального изменения без обязательного перерасчёта геометрии.

Paint не создаёт готовые экранные пиксели. Он описывает команды рисования и их порядок.

На этапе **rasterization**, или растеризации, paint-команды превращаются в пиксельные данные.

Контент может разбиваться на tiles, или плитки. В первую очередь браузер старается подготовить области, которые находятся во viewport или скоро могут стать видимыми.

Растеризация может выполняться:

- raster threads;
- GPU process;
- программными средствами;
- сочетанием нескольких механизмов.

Наличие GPU process не означает, что вся страница и каждая операция обязательно рисуются непосредственно видеокартой.

На этапе **composite** браузер собирает подготовленные визуальные слои в итоговый кадр.

Compositor учитывает:

- положение слоя;
- порядок наложения;
- `transform`;
- `opacity`;
- clipping;
- scrolling;
- некоторые визуальные эффекты.

Если элемент находится в отдельном подготовленном compositing layer, изменение его `transform` или `opacity` часто можно обработать без нового layout и paint содержимого:

```css
.panel {
  transform: translateX(100%);
  opacity: 0;
}

.panel.is-open {
  transform: translateX(0);
  opacity: 1;
}
```

При добавлении класса браузеру всё равно может понадобиться пересчитать стили. Но последующие кадры CSS-анимации или transition иногда выполняются compositor thread без работы main thread на каждом кадре.

Это особенно полезно, если main thread одновременно выполняет JavaScript.

Отдельный compositing layer не создаётся для каждого DOM-элемента.

Браузер может создать слой из-за:

- анимируемого `transform`;
- анимируемого `opacity`;
- 3D-transform;
- видео;
- canvas;
- fixed/sticky-содержимого;
- некоторых фильтров;
- `will-change`;
- внутренних эвристик движка.

Но конкретное решение принимает браузер. Само наличие:

```css
transform: translateZ(0);
```

не является надёжным публичным контрактом создания отдельного слоя.

Также нужно различать stacking context и compositing layer.

`transform`, `opacity` и некоторые другие свойства могут создать stacking context, но stacking context — правило наложения CSS, а compositing layer — внутренняя оптимизация браузера. Эти понятия связаны, но не равны.

Для визуального движения обычно предпочитают:

```css
transform: translate(...)
```

вместо:

```css
top
left
```

`transform` меняет визуальное положение уже рассчитанной коробки и не заставляет соседние элементы перераспределять место.

`top` и `left` изменяют геометрическое положение позиционированного элемента и обычно требуют layout или paint.

Но это не абсолютное правило стоимости.

Например:

- изменение `top` небольшого изолированного absolute-элемента может быть относительно дешёвым;
- transform огромного слоя может дорого стоить при растеризации и composite;
- масштабирование текста может ухудшить визуальную резкость;
- большое количество движущихся слоёв расходует память.

Поэтому `transform` и `opacity` являются хорошим базовым выбором для анимаций, но реальный сценарий проверяют профилированием.

**Forced synchronous layout**, или принудительный синхронный layout, возникает, когда JavaScript сначала делает изменение, после которого геометрия становится устаревшей, а затем сразу запрашивает актуальное значение.

Например:

```js
element.style.width = "200px";

const height = element.offsetHeight;
```

После записи:

```js
element.style.width = "200px";
```

браузер может только пометить стили и layout как требующие обновления.

Но `offsetHeight` должен вернуть актуальную геометрию. Поэтому перед возвратом значения браузеру может потребоваться синхронно выполнить style calculation и layout прямо внутри текущей JavaScript-задачи.

Не каждое чтение `offsetHeight` автоматически вызывает layout. Если геометрия уже актуальна, браузер может вернуть сохранённое значение без пересчёта.

Частые API, чтение которых при наличии pending changes может потребовать актуальной геометрии:

```js
offsetWidth
offsetHeight
clientWidth
clientHeight
scrollWidth
scrollHeight
getBoundingClientRect()
```

Некоторые вызовы `getComputedStyle()` также могут заставить браузер обновить стили или layout в зависимости от запрашиваемого свойства и состояния документа.

**Layout thrashing** возникает при многократном чередовании записей и чтений:

```js
for (const item of items) {
  item.style.width = `${container.offsetWidth}px`;
}
```

На каждой итерации происходит:

1. изменение style;
2. invalidation;
3. чтение геометрии;
4. возможный синхронный layout;
5. следующее изменение.

Лучше сначала выполнить чтения:

```js
const width = container.offsetWidth;
```

а затем записи:

```js
for (const item of items) {
  item.style.width = `${width}px`;
}
```

То есть использовать порядок:

```text
read
read
read
→
write
write
write
```

вместо:

```text
write
→ read
→ write
→ read
```

`requestAnimationFrame` позволяет запланировать визуальное обновление перед следующим кадром:

```js
requestAnimationFrame(() => {
  element.style.transform = "translateX(100px)";
});
```

Но сам по себе `requestAnimationFrame` не устраняет layout thrashing.

Внутри одного callback всё ещё можно создать проблему:

```js
requestAnimationFrame(() => {
  element.style.width = "200px";
  console.log(element.offsetHeight);

  element.style.width = "300px";
  console.log(element.offsetHeight);
});
```

Поэтому даже внутри `requestAnimationFrame` чтения и записи группируют осознанно.

При частоте экрана 60 Гц новый кадр появляется примерно каждые:

```text
16.7 ms
```

Но это не означает, что все 16.7 ms доступны JavaScript: часть времени нужна браузеру на style, layout, paint, rasterization и composite.

На дисплее 120 Гц бюджет кадра уже около:

```text
8.3 ms
```

Длинная JavaScript-задача на main thread может задержать:

- обработку ввода;
- style calculation;
- layout;
- paint;
- отправку нового кадра compositor.

Compositor-анимация иногда продолжает двигаться даже при занятом main thread, но новые DOM-изменения и пользовательская логика всё равно могут задерживаться.

`will-change` сообщает браузеру, какое свойство скоро изменится:

```css
.panel {
  will-change: transform;
}
```

Браузер может заранее подготовить оптимизацию, например слой или растеризацию.

Но `will-change`:

- не гарантирует создание слоя;
- не гарантирует ускорение;
- расходует память и другие ресурсы;
- может изменить stacking-поведение;
- способен ухудшить производительность при массовом использовании.

Его применяют точечно, когда профилирование показало проблему, и по возможности незадолго до анимации.

Реальную стоимость проверяют в DevTools Performance.

В записи ищут:

- длинные `Recalculate Style`;
- события `Layout`;
- большие или частые `Paint`;
- dropped frames;
- long tasks;
- forced layout, связанный с JavaScript;
- большое количество обновляемых слоёв;
- дорогое выполнение обработчиков ввода.

Дополнительно в DevTools Rendering можно использовать:

- Paint flashing;
- Layout Shift Regions;
- Layer borders;
- FPS meter.

После обнаружения дорогого события проверяют его call stack и связывают работу браузера с конкретным:

- DOM-изменением;
- чтением геометрии;
- CSS-свойством;
- обработчиком события;
- анимацией.

Оптимизируют измеренную причину, а не просто заменяют все свойства на `transform` или добавляют `will-change`.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Что такое layout/reflow?</strong></summary>

<dl>
<dd>
<h2></h2>

Layout — расчёт геометрии визуальных коробок:

- размеров;
- координат;
- переносов строк;
- Grid- и Flexbox-раскладки;
- областей прокрутки;
- положения соседних элементов.

Термин reflow обычно означает повторный layout после изменения уже отображённого документа.

Например:

```js
element.textContent = longText;
```

может изменить ширину или высоту текста, положение соседей и размер родительского контейнера.

Layout не обязательно пересчитывает всю страницу. Браузер старается ограничить работу затронутой частью дерева.

Но изменение верхнего контейнера:

```css
.page {
  width: 80%;
}
```

может повлиять на множество потомков, потому что изменятся доступная ширина, переносы строк и размеры вложенных компонентов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Каждое ли изменение DOM вызывает layout?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Сначала изменение обычно вызывает invalidation — браузер отмечает, какие данные могли устареть.

Фактический layout нужен только тогда, когда изменение влияет на геометрию.

Например, добавление элемента с:

```css
display: none;
```

может изменить DOM, но не создать layout box.

Изменение атрибута, который не используется CSS и не влияет на содержимое, также может не потребовать layout:

```js
element.dataset.analyticsId = "42";
```

Изменение класса может вызвать разные стадии в зависимости от правил:

```css
.color {
  color: red;
}
```

может потребовать style и paint.

```css
.large {
  width: 500px;
}
```

может потребовать style, layout, paint и composite.

```css
.moved {
  transform: translateX(100px);
}
```

может потребовать style и composite, если слой уже подготовлен.

Браузер также может объединить несколько изменений и выполнить один layout перед следующим кадром.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое repaint?</strong></summary>

<dl>
<dd>
<h2></h2>

Repaint — повторное формирование paint-команд для изменившейся визуальной области.

Например:

```css
.element {
  background-color: blue;
}
```

не меняет размеры коробки, но меняет её пиксели.

Обычно последовательность будет близка к:

```text
style
→ paint
→ rasterization
→ composite
```

без нового layout.

После paint затронутую область всё равно нужно растеризовать и включить в новый кадр.

Стоимость repaint зависит от:

- площади области;
- количества элементов;
- теней;
- фильтров;
- clipping;
- перекрывающихся слоёв;
- разрешения экрана.

Небольшое изменение цвета у маленькой кнопки и repaint полноэкранного контейнера имеют разную стоимость.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем paint отличается от rasterization?</strong></summary>

<dl>
<dd>
<h2></h2>

Paint определяет, что и в каком порядке нужно нарисовать.

Например:

```text
нарисовать фон
→ нарисовать границу
→ нарисовать текст
→ нарисовать тень
```

Результатом является набор команд, часто описываемый как display list или paint records.

Rasterization выполняет эти команды и превращает их в пиксельные данные.

Страница может быть разделена на tiles, чтобы браузер в первую очередь растеризовал видимую область.

Упрощённо:

```text
Paint          → инструкция, что рисовать.
Rasterization  → создание пикселей по этой инструкции.
```

В статьях и инструментах оба этапа иногда упрощённо называют отрисовкой, но технически это разные виды работы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое composite?</strong></summary>

<dl>
<dd>
<h2></h2>

Composite — сборка уже подготовленных визуальных слоёв в итоговый кадр.

Compositor учитывает:

- позицию;
- `transform`;
- `opacity`;
- порядок наложения;
- clipping;
- прокрутку.

Если содержимое элемента уже растеризовано в отдельный слой, compositor может переместить этот слой:

```css
transform: translateX(100px);
```

без повторного paint его содержимого.

Это позволяет части анимаций выполняться независимо от main thread.

Но composite тоже имеет стоимость:

- слои занимают память;
- большие прозрачные слои нужно смешивать;
- множество слоёв усложняет сборку кадра;
- при увеличении элемента может понадобиться новая растеризация;
- дорогое содержимое слоя всё равно нужно первоначально нарисовать.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем stacking context отличается от compositing layer?</strong></summary>

<dl>
<dd>
<h2></h2>

Stacking context — часть CSS-модели наложения.

Он определяет, внутри какой локальной группы сравниваются значения `z-index`.

Его могут создавать, например:

```css
position: relative;
z-index: 1;
```

```css
opacity: 0.9;
```

```css
transform: translateX(0);
```

Compositing layer — внутренняя структура браузера, используемая для растеризации и сборки кадра.

Браузер может создать отдельный слой для:

- анимации;
- видео;
- scrolling;
- fixed-элемента;
- сложного эффекта;
- собственной оптимизации.

Создание stacking context определяется CSS-правилами. Создание compositing layer определяется реализацией и эвристиками browser engine.

Один stacking context не обязан соответствовать одному compositing layer.

Поэтому утверждение:

```text
transform всегда создаёт отдельный GPU-слой
```

некорректно.

`transform` создаёт stacking context, но решение о layer promotion принимает браузер.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие стадии обычно вызывают разные CSS-свойства?</strong></summary>

<dl>
<dd>
<h2></h2>

Упрощённая модель:

| Изменение | Возможные стадии |
| --- | --- |
| `width`, `height`, `padding` | Style → Layout → Paint → Composite |
| `font-size`, `line-height` | Style → Layout → Paint → Composite |
| `display`, изменение DOM | Style → Layout → Paint → Composite |
| `background-color`, `border-color` | Style → Paint → Composite |
| `box-shadow` | Style → Paint → Composite |
| `transform` подготовленного слоя | Style/Composite или только Composite во время анимации |
| `opacity` подготовленного слоя | Style/Composite или только Composite во время анимации |

Это ориентир, а не гарантия.

Результат зависит от:

- браузера;
- способа изменения;
- наличия слоя;
- размера области;
- соседних элементов;
- текущей растеризации;
- конкретного значения свойства.

Например, первый запуск transform-анимации может потребовать paint и layer preparation, а последующие кадры — только composite.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>transform</code> часто быстрее, чем <code>top</code>/<code>left</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`top` и `left` изменяют геометрическое положение позиционированного элемента:

```css
.element {
  position: absolute;
  left: 100px;
}
```

Это обычно требует обновления layout или paint.

`transform` применяется к уже рассчитанной коробке:

```css
.element {
  transform: translateX(100px);
}
```

Он визуально перемещает элемент, но не меняет место, которое layout выделил ему и соседним элементам.

Если элемент находится в отдельном подготовленном слое, перемещение может выполнять compositor thread.

Но `transform` не всегда дешевле:

- большой слой занимает память;
- масштабирование может потребовать новой растеризации;
- текст при transform может выглядеть менее чётко;
- множество движущихся слоёв увеличивает стоимость composite;
- сложные filters внутри слоя остаются дорогими.

Поэтому `transform` — предпочтительный базовый инструмент для визуального движения, но результат проверяют в реальном сценарии.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое forced reflow?</strong></summary>

<dl>
<dd>
<h2></h2>

Браузер обычно откладывает style и layout до подходящего момента перед кадром.

После записи:

```js
element.style.width = "200px";
```

геометрия может стать устаревшей, но layout ещё не обязательно выполнен.

Если затем прочитать:

```js
element.offsetHeight;
```

браузер должен вернуть актуальное значение.

Поэтому он может синхронно выполнить:

```text
style calculation
→ layout
```

внутри текущей JavaScript-задачи.

Это называется forced synchronous layout или forced reflow.

Если pending changes отсутствуют, то же чтение может использовать уже рассчитанные данные и не вызвать новую работу.

Особенно дорого повторять такой шаблон в цикле:

```js
for (const item of items) {
  item.style.width = "200px";
  console.log(item.offsetHeight);
}
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Устраняет ли <code>requestAnimationFrame</code> forced layout?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет, не автоматически.

`requestAnimationFrame` планирует callback перед следующим отображением кадра:

```js
requestAnimationFrame(() => {
  element.style.transform = "translateX(100px)";
});
```

Это удобно для визуальных обновлений, потому что браузер может согласовать их с циклом рендеринга.

Но внутри callback по-прежнему можно вызвать forced layout:

```js
requestAnimationFrame(() => {
  element.style.width = "200px";
  console.log(element.offsetHeight);
});
```

После записи чтение может заставить браузер немедленно обновить геометрию.

Правильная организация важнее самого API:

```js
const width = element.offsetWidth;

requestAnimationFrame(() => {
  otherElement.style.width = `${width}px`;
});
```

Сначала выполняются чтения актуальной геометрии, затем планируются записи.

Для сложного интерфейса может потребоваться отдельное управление фазами read и write, чтобы разные компоненты не чередовали их случайным образом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>will-change</code> не ставят на всё подряд?</strong></summary>

<dl>
<dd>
<h2></h2>

`will-change` сообщает браузеру, какое свойство скоро изменится:

```css
.element {
  will-change: transform;
}
```

Движок может заранее:

- создать compositing layer;
- подготовить растеризацию;
- выделить память;
- изменить внутреннюю стратегию отображения.

Но это подсказка, а не обязательная команда.

Если добавить:

```css
* {
  will-change: transform;
}
```

браузер может подготовить слишком много элементов.

Это приводит к:

- повышенному расходу памяти;
- большему количеству слоёв;
- дорогому composite;
- дополнительной служебной работе;
- ухудшению производительности.

`will-change` используют точечно для подтверждённой проблемы и по возможности убирают после завершения кратковременного эффекта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Могут ли <code>contain</code> и <code>content-visibility</code> уменьшить стоимость рендеринга?</strong></summary>

<dl>
<dd>
<h2></h2>

CSS containment позволяет сообщить браузеру, что определённые аспекты компонента изолированы от окружающей страницы.

Например:

```css
.widget {
  contain: layout paint;
}
```

`layout` ограничивает влияние внутренней раскладки на внешние элементы, а `paint` запрещает содержимому рисоваться за границами containment box.

`content-visibility: auto` позволяет браузеру пропускать часть работы для содержимого вне viewport:

```css
.section {
  content-visibility: auto;
  contain-intrinsic-size: auto 500px;
}
```

`contain-intrinsic-size` предоставляет приблизительный размер, пока содержимое не отрисовывается, чтобы уменьшить скачки scrollbar и layout.

Эти свойства полезны для больших независимых секций и длинных страниц, но могут изменить:

- containing block;
- clipping;
- intrinsic sizing;
- поведение position;
- доступность поиска и прокрутки в отдельных сценариях.

Их применяют после проверки реальной структуры, а не как универсальную оптимизацию для каждого компонента.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как искать дорогие layout и paint на практике?</strong></summary>

<dl>
<dd>
<h2></h2>

В Chrome DevTools записывают реальный сценарий в Performance panel:

- открытие модального окна;
- scroll;
- ввод текста;
- drag-and-drop;
- раскрытие списка;
- запуск анимации.

На main thread ищут:

- `Recalculate Style`;
- `Layout`;
- `Paint`;
- long tasks;
- обработчики событий;
- JavaScript-вызовы, после которых началась работа браузера.

Для forced layout проверяют call stack и последовательность:

```text
изменение DOM/style
→ чтение геометрии
→ Layout
```

В Rendering panel можно включить Paint flashing. Браузер будет подсвечивать области, которые перерисовываются.

Layer borders помогают увидеть, какие части страницы находятся в отдельных слоях.

FPS meter позволяет заметить пропуски кадров, но сам по себе не объясняет причину.

Проверять нужно:

- на реальном объёме DOM;
- с настоящими данными;
- на менее мощном устройстве;
- при нужной частоте взаимодействия;
- в production-сборке.

После измерения оптимизируют конкретную причину:

- уменьшают область layout;
- группируют чтения и записи;
- сокращают DOM;
- меняют дорогое анимируемое свойство;
- уменьшают paint area;
- удаляют лишние слои;
- разбивают long task.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что важно понимать |
| --- | --- |
| Drag-and-drop или анимация | Двигать через `transform`, если это соответствует сценарию |
| Большая таблица или список | Размер DOM и intrinsic-содержимое влияют на layout |
| Измерение элемента после изменения style | Можно вызвать forced synchronous layout |
| Цикл чтения и записи DOM | Возможен layout thrashing |
| `requestAnimationFrame` | Согласует обновление с кадром, но не заменяет batching |
| Tooltip, модальное окно, fixed header | Различать stacking context и compositing layer |
| Длинная страница | Рассмотреть containment после измерений |
| `will-change` | Использовать точечно перед подтверждённой анимацией |
| Медленная анимация | Проверить main thread, paint areas и layers в DevTools |
