#### Вопрос

Что такое Service Worker и зачем он нужен во frontend?

#### Ответ

Service Worker - специальный JavaScript worker, который браузер запускает отдельно от страницы для обработки событий. У него нет доступа к DOM, но он может обслуживать запросы контролируемых страниц, работать с Cache API, получать push-события и участвовать в Background Sync - отложенной повторной отправке после восстановления сети. Поддержка Background Sync различается между браузерами. Браузер вправе остановить worker между событиями, поэтому его нельзя считать постоянно работающим фоновым процессом.

Активный Service Worker в подходящем scope, то есть области URL, получает событие `fetch` только для страниц, которые он уже **контролирует**. Обработчик вызывает `event.respondWith(promise)` и передаёт браузеру будущий `Response`: сетевой, сохранённый в Cache API или созданный как резервный offline-ответ. Если `respondWith()` не вызван во время обработки события, запрос продолжает обычный сетевой путь.

Для асинхронной работы, которая должна пережить завершение обработчика, используется `event.waitUntil(promise)`. Переданный Promise сообщает браузеру, что установка, активация или фоновая операция ещё не закончены. Глобальные переменные worker могут исчезнуть после остановки процесса; устойчивое состояние хранят в IndexedDB, Cache API или на сервере.

Жизненный цикл начинается с **registration**, или регистрации: страница вызывает `navigator.serviceWorker.register("/sw.js")`. По умолчанию scope определяется директорией файла: `/sw.js` может контролировать origin от `/`, а `/app/sw.js` - только `/app/`. Регистрация ещё не означает, что текущая страница контролируется worker.

На этапе **install** подготавливают обязательный app shell - минимальный набор HTML, CSS и JavaScript для запуска интерфейса - или другую базовую версию кэша. `event.waitUntil()` связывает успех установки с promise: если обязательное кэширование завершается ошибкой, новый worker не устанавливается. Большой динамический каталог обычно не загружают целиком на install, иначе одна сетевая ошибка заблокирует обновление.

После install новая версия переходит в **waiting**, то есть ожидает, пока старая версия контролирует открытые страницы, называемые clients. Когда старые clients исчезают, начинается **activate**, или активация. Здесь завершают миграцию и удаляют только те кэши, которые больше не нужны ни одной поддерживаемой версии. Слишком раннее удаление кэша может сломать вкладку со старым HTML.

Состояние **active** означает, что worker активирован и готов к работе, а **controlled** - что конкретная страница направляет запросы через него. Без `clients.claim()` уже открытая страница обычно начинает контролироваться после следующей навигации. Поэтому самая первая загрузка сайта часто проходит без перехвата, затем worker устанавливается и обслуживает следующие открытия.

`skipWaiting()` просит ожидающий worker немедленно перейти к активации, а `clients.claim()` - взять под контроль уже открытые подходящие страницы. Вместе они ускоряют обновление, но могут смешать старый выполняющийся код с новой стратегией ресурсов. Их применяют только при совместимом протоколе обновления или после согласованной перезагрузки вкладок.

Стратегию кэширования выбирают по допустимой устарелости:

- **cache first** сначала использует Cache API и подходит для неизменяемых файлов с hash, то есть идентификатором содержимого, в имени;
- **network first** предпочитает сеть и при ошибке использует кэш, что подходит для HTML или данных с требованием свежести;
- **stale-while-revalidate** сразу возвращает старую запись и параллельно обновляет её для следующего запроса;
- **network only** и **cache only** применяются в узких сценариях.

Главная практическая сложность - согласованное обновление. Старый HTML может ссылаться на hash-chunk, уже удалённый при новом развёртывании, а агрессивная очистка worker-кэша может лишить открытую вкладку её файлов. Обычно HTML перепроверяют чаще, статические файлы получают уникальные имена и долгий неизменяемый кэш, старые ресурсы сохраняют на период миграции, а новую версию worker активируют через предложение обновить страницу или совместимый автоматический сценарий.

Персональные ответы API нельзя безусловно класть в общий кэш только по URL. Стратегия должна учитывать пользователя, авторизацию, заголовок `Vary`, выход из аккаунта и срок свежести. Cache API не обновляет записи автоматически и расходует выделенный браузером объём хранилища.

Service Worker работает только в secure context, то есть в доверенном контексте HTTPS или на `localhost` при разработке. Скрипт worker и его scope также ограничены одним origin. Эти требования нужны потому, что worker способен менять сетевое поведение целого раздела приложения.

Service Worker сам по себе не равен PWA. Progressive Web App сочетает обычное веб-приложение с возможностями установки и устойчивой работы: web app manifest, или манифест приложения, описывает имя, иконки и режим запуска; Service Worker может дать offline-поведение; HTTPS защищает доставку. Точные критерии возможности установки зависят от браузера и меняются, поэтому приложение должно оставаться полезным и без установки.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Почему Service Worker работает только на HTTPS?
>
> **Ответ:** Worker способен перехватывать запросы и подменять ответы для контролируемых страниц. Без HTTPS атакующий в сети мог бы изменить его скрипт и закрепить вредоносную логику для всего origin. `localhost` считается доверенным контекстом для разработки.

> [!followup]
> **Вопрос:** Что происходит на install?
>
> **Ответ:** Браузер загружает новый скрипт и отправляет событие `install`. В `event.waitUntil()` передают Promise подготовки обязательного кэша. Если Promise отклоняется, установка считается неуспешной, а предыдущая рабочая версия продолжает обслуживать пользователей.

> [!followup]
> **Вопрос:** Что происходит на activate?
>
> **Ответ:** После освобождения старой версии новый worker получает событие `activate`. Здесь завершают миграцию и аккуратно чистят устаревшие кэши через `event.waitUntil()`. Активированный worker готов обслуживать запросы, но открытая страница не обязательно уже контролируется им без новой навигации или `clients.claim()`.

> [!followup]
> **Вопрос:** Почему новый Service Worker может ждать?
>
> **Ответ:** Если старая версия контролирует открытые вкладки, новая после install переходит в waiting. Это сохраняет согласованность: страница продолжает работать с той версией worker и ресурсов, с которой была загружена.
>
> Например, открытая вкладка использует старый HTML и chunks с hash в имени. Немедленная активация новой стратегии может удалить или заменить нужные ей файлы. Приложение либо показывает предложение обновить страницу, либо гарантирует обратную совместимость ресурсов во время перехода.

> [!followup]
> **Вопрос:** Что делают `skipWaiting()` и `clients.claim()`?
>
> **Ответ:** `skipWaiting()` позволяет установленной версии не ждать исчезновения старых clients и перейти к активации. `clients.claim()` просит уже активный worker начать контролировать открытые страницы своего scope. Первый метод переключает версию worker, второй - назначает ей страницы.
>
> Эти методы не гарантируют согласованность кода. Если старая страница ожидает прежний формат кэша или API, немедленный переход может её сломать. Нужны версионированные ресурсы, совместимая миграция и контролируемая перезагрузка либо явное предложение обновить страницу.

> [!followup]
> **Вопрос:** Почему нельзя хранить важное состояние только в памяти Service Worker?
>
> **Ответ:** Браузер может остановить Service Worker после завершения события и позже запустить новый экземпляр. Глобальные переменные тогда исчезнут. Очередь offline-изменений и метаданные синхронизации хранят в IndexedDB, сетевые ответы - в Cache API, а подтверждённое состояние - на backend. Повторная отправка должна быть идемпотентной, то есть не создавать новый результат при повторе одной операции, либо использовать уникальный ключ и явное разрешение конфликтов.

> [!followup]
> **Вопрос:** Какие стратегии кэширования бывают?
>
> **Ответ:** Cache first подходит для неизменяемых файлов с hash в имени. Network first выбирают для HTML или данных, где важна свежесть и допустим резервный offline-ответ. Stale-while-revalidate уменьшает задержку, но пользователь сначала видит потенциально устаревшие данные. Стратегию выбирают отдельно для каждого класса ресурсов, а не одну для всего origin.

> [!followup]
> **Вопрос:** Почему после нового deploy пользователь может видеть старую версию?
>
> **Ответ:** Старая вкладка может оставаться под управлением старого worker, HTML может лежать в Cache API, а новое развёртывание - удалить chunk, на который он ссылается. Чтобы версии не смешивались, используют hash-имена, контролируемую свежесть HTML, версионирование worker-кэшей и хранение старых ресурсов на время обновления клиентов.

> [!followup]
> **Вопрос:** Почему Service Worker не перехватывает самую первую загрузку?
>
> **Ответ:** Во время первого открытия worker ещё не зарегистрирован, не установлен и не активирован. Даже после активации текущая страница обычно остаётся неконтролируемой до следующей навигации. `clients.claim()` может изменить последнее правило, но обработчик первой навигации всё равно не существовал в момент её начала.

> [!followup]
> **Вопрос:** Чем Service Worker отличается от Web Worker?
>
> **Ответ:** Web Worker создаётся страницей для вычислений в отдельном потоке и обычно живёт вместе с ней. Service Worker регистрируется для заданного origin и scope, запускается браузером по событиям и может обслуживать запросы нескольких контролируемых страниц. Ни один из них не имеет прямого доступа к DOM, но их жизненный цикл и назначение различаются.

> [!followup]
> **Вопрос:** Зачем нужны `respondWith()` и `waitUntil()`?
>
> **Ответ:** `respondWith()` задаёт ответ конкретного события `fetch` и должен быть вызван во время его обработки, хотя переданный Promise может завершиться позже. `waitUntil()` продлевает жизнь события до завершения Promise и применяется при установке, активации и фоновой работе. Без него браузер вправе остановить worker после завершения обработчика.

#### Где это встречается во frontend

| Ситуация | Что важно понимать |
| --- | --- |
| PWA без сети | Service Worker может вернуть сохранённый app shell или offline-страницу |
| Статические ресурсы | Chunks с hash в имени обычно подходят для cache first |
| HTML-навигация | Нужны проверка свежести и продуманный резервный ответ |
| Данные API | Стратегия зависит от допустимой устарелости и пользователя |
| Deploy новой версии | Нужны версионирование, безопасная очистка кэша и понятное обновление UI |
| Ошибка загрузки chunk | Часто связана со старым HTML и удалённым hash-файлом |
| Offline-очередь | Не хранить операции только в памяти worker |
