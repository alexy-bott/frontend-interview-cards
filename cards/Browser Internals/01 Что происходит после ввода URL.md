## Вопрос

<br>

 💬 **Что происходит в браузере после того, как пользователь ввёл URL и нажал Enter?**

<h2></h2>

<br>
<dl>
<dd>

Браузер начинает навигацию: разбирает адрес, пытается получить документ из уже подготовленного состояния, кэша, Service Worker или сети, передаёт данные процессу рендеринга и превращает HTML, CSS и JavaScript в отображаемую и интерактивную страницу.

Конкретная архитектура различается между браузерами. Ниже описана общая последовательность с названиями процессов Chromium.

Также это последовательность полной cross-document navigation, при которой загружается новый документ. Если изменился только fragment текущего URL, браузер может выполнить same-document navigation без повторного сетевого запроса и замены документа.

1. **Browser process принимает ввод.**

Адресная строка относится к интерфейсу браузера, а не к JavaScript открытой страницы.

Browser process определяет, введён URL или поисковый запрос, создаёт navigation request и начинает навигацию.

Если текущая страница зарегистрировала `beforeunload`, браузер может предоставить ей возможность предупредить пользователя о потере несохранённых данных. Показ диалога ограничен правилами браузера и обычно требует предшествующего пользовательского взаимодействия.

2. **Браузер разбирает URL.**

В адресе:

```text
https://example.com/products?page=2#reviews
```

части называются так:

- `https` — scheme, или схема;
- `example.com` — host;
- `/products` — path;
- `?page=2` — query;
- `#reviews` — fragment.

Scheme определяет правила доступа к ресурсу. При `https` браузер использует защищённый HTTP, который может работать через HTTP/1.1, HTTP/2 или HTTP/3.

Fragment не входит в обычный HTTP-запрос. Он остаётся в браузере и используется, например, для перехода к элементу документа или клиентской маршрутизации.

Политика HSTS может ещё до сетевого запроса заменить:

```text
http://example.com
```

на:

```text
https://example.com
```

для домена, который браузер уже знает как HTTPS-only.

Если новый URL отличается от текущего только fragment:

```text
/page#description
→
/page#reviews
```

браузер обычно не загружает документ заново, а меняет историю, обновляет URL и переходит к соответствующей части текущего документа.

3. **Проверяется возможность использовать уже готовую страницу или ответ.**

Не каждая навигация требует полного прохождения сети.

При переходе Back или Forward браузер может восстановить страницу из `bfcache`. В нём хранится целое состояние документа: DOM, JavaScript heap и позиция прокрутки.

Если браузер заранее выполнил prerender именно этой страницы, он может активировать уже подготовленный документ.

Для обычной навигации browser process создаёт запрос документа. Если URL находится в scope активного Service Worker, навигационный запрос может быть передан его обработчику `fetch`.

Service Worker может:

- вернуть ответ из Cache API;
- вернуть offline-страницу;
- изменить стратегию получения данных;
- выполнить обычный сетевой `fetch`.

Если запрос доходит до сетевого слоя, браузер может использовать HTTP cache:

- сразу вернуть свежую запись;
- отправить условный запрос для проверки записи;
- запросить полный новый ответ.

Cache API и HTTP cache — разные хранилища. Cache API явно управляется кодом Service Worker или страницы, а HTTP cache автоматически работает по HTTP-заголовкам.

4. **Проверяется возможность переиспользовать соединение.**

Для origin или совместимого endpoint уже может существовать открытое соединение.

В таком случае браузер способен повторно использовать:

- TCP-соединение HTTP/1.1;
- мультиплексированное HTTP/2-соединение;
- QUIC-соединение HTTP/3.

При переиспользовании соединения новый DNS lookup, TCP handshake или полный TLS handshake могут не потребоваться.

Если подходящего соединения нет, браузер выполняет следующие сетевые стадии.

5. **Выполняется DNS lookup.**

Доменное имя нужно сопоставить с IP-адресом.

Браузер и операционная система сначала проверяют доступные DNS-кэши. При отсутствии подходящей записи системный resolver обращается к настроенному DNS-сервису.

Результатом становятся один или несколько IPv4- или IPv6-адресов.

Полученный адрес может принадлежать не исходному application server, а:

- CDN;
- reverse proxy;
- load balancer;
- edge-серверу.

Браузер выбирает подходящий адрес и пытается установить соединение.

6. **Устанавливается транспортное и защищённое соединение.**

HTTP/1.1 и HTTP/2 обычно работают поверх TCP.

Для TCP сначала выполняется handshake, после которого стороны могут обмениваться байтами.

При HTTPS поверх соединения выполняется TLS handshake:

- клиент и сервер согласуют параметры шифрования;
- сервер предъявляет сертификат;
- браузер проверяет доменное имя;
- проверяет срок действия сертификата;
- строит цепочку до доверенного центра сертификации;
- стороны получают ключевой материал для защищённого обмена.

Через ALPN клиент и сервер могут согласовать использование HTTP/2 или HTTP/1.1.

HTTP/3 работает поверх QUIC, использующего UDP. TLS 1.3 встроен в процесс установления QUIC-соединения, поэтому транспортное и криптографическое согласование тесно связаны.

Возобновление предыдущей TLS- или QUIC-сессии может уменьшить количество необходимых сетевых обменов.

7. **Отправляется HTTP-запрос.**

Для обычного ввода URL браузер, как правило, отправляет `GET`.

В HTTP/1.1 начальная часть запроса концептуально выглядит так:

```http
GET /products?page=2 HTTP/1.1
Host: example.com
```

Path и query входят в request target.

Host передаётся:

- через заголовок `Host` в HTTP/1.1;
- через псевдозаголовок `:authority` в HTTP/2 и HTTP/3.

В HTTP/2 и HTTP/3 также используются псевдозаголовки вроде `:method`, `:scheme` и `:path`.

Fragment:

```text
#reviews
```

в запрос не попадает.

Браузер добавляет подходящие заголовки, например:

- `Accept`;
- `Accept-Encoding`;
- сведения о языке;
- `Referer` согласно Referrer Policy;
- Client Hints, если они используются;
- cookie, подходящие по domain, path, `Secure`, `SameSite` и другим правилам.

Если в HTTP cache есть устаревшая запись с валидаторами, браузер может отправить:

```http
If-None-Match: "version-123"
```

или:

```http
If-Modified-Since: ...
```

Сервер тогда может ответить `304 Not Modified` без повторной передачи полного тела.

8. **Сервер обрабатывает запрос и возвращает HTTP-ответ.**

Ответ содержит:

- status code;
- headers;
- body, если оно предусмотрено статусом и методом.

Например:

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Encoding: br
Cache-Control: max-age=60
```

Важные заголовки могут сообщать:

- тип содержимого;
- кодировку;
- способ сжатия;
- правила кэширования;
- cookie;
- Content Security Policy;
- Referrer Policy;
- правила изоляции документа.

Браузер распаковывает тело согласно `Content-Encoding` и обрабатывает данные по мере их поступления.

При ответе `3xx` с `Location` браузер разрешает новый URL и начинает следующий запрос. Цепочка может повторно включать HSTS, Service Worker, кэш, DNS и соединение — в зависимости от нового адреса и уже доступных ресурсов.

Если ответ должен быть загружен как файл или относится к типу, который браузер не отображает как HTML-документ, навигация может закончиться загрузкой файла или открытием встроенного viewer.

Далее рассматривается ответ с HTML-документом.

9. **Browser process выбирает renderer process и выполняет commit навигации.**

Browser process проверяет ответ и выбирает renderer process для нового документа.

В Chromium Site Isolation влияет на то, какие сайты могут находиться в одном renderer process. Это ограничивает совместное размещение недоверенных документов и усиливает изоляцию.

После commit навигации:

- новый документ становится текущим документом вкладки;
- адресная строка и история связываются с новой записью;
- renderer получает данные документа;
- предыдущий документ может быть уничтожен, сохранён в `bfcache` или завершён другим способом.

Browser process и renderer process взаимодействуют через IPC — межпроцессные сообщения.

10. **Renderer process потоково разбирает HTML и строит DOM.**

Renderer не обязан ждать получения всего body.

HTML parser читает поступающий поток и строит DOM — объектное дерево документа.

Если HTML содержит синтаксические ошибки, parser применяет определённые HTML-стандартом правила восстановления и всё равно формирует дерево.

Например, исходный HTML:

```html
<main>
  <h1>Products</h1>
</main>
```

превращается в объекты DOM, с которыми затем работает JavaScript.

Одновременно preload scanner пытается заранее обнаружить ресурсы:

- stylesheets;
- scripts;
- images;
- fonts;
- preload-ссылки.

Это позволяет начать загрузку ресурса раньше, чем основной parser дойдёт до него или разблокируется после выполнения скрипта.

Preload scanner не выполняет JavaScript. Поэтому URL, который создаётся только динамическим кодом, обычно нельзя обнаружить заранее:

```js
const script = document.createElement("script");
script.src = getDynamicUrl();
```

11. **CSS загружается, разбирается и участвует в вычислении стилей.**

CSS parser строит CSSOM — объектное представление таблиц стилей и их правил.

CSS обычно не останавливает сам HTML parser: DOM может продолжать строиться, пока загружается внешняя таблица стилей.

Но подходящая для текущего устройства внешняя stylesheet обычно является render-blocking. Браузер не должен показывать документ с заведомо неполными критическими стилями, а затем сразу полностью перерисовывать его.

Например:

```html
<link rel="stylesheet" href="/styles.css">
```

обычно задерживает первый render до загрузки и разбора stylesheet.

Таблица с неподходящим media condition может не блокировать текущий render:

```html
<link
  rel="stylesheet"
  href="/print.css"
  media="print"
>
```

CSS также может задержать выполнение parser-blocking script. JavaScript способен читать вычисленные стили, поэтому обычный script может ждать ранее обнаруженные blocking stylesheets.

12. **JavaScript может блокировать или откладывать HTML parsing.**

Обычный внешний script:

```html
<script src="/app.js"></script>
```

без `defer`, `async` или `type="module"` является parser-blocking.

Когда HTML parser достигает такого элемента, он:

1. останавливает разбор документа;
2. ждёт загрузки скрипта, если он ещё не готов;
3. при необходимости ждёт ранее обнаруженные blocking stylesheets;
4. выполняет JavaScript;
5. продолжает разбор HTML.

Это требуется в том числе потому, что script может изменить документ во время парсинга:

```js
document.write(...);
```

`defer` загружает script параллельно с HTML:

```html
<script defer src="/app.js"></script>
```

Deferred scripts:

- выполняются после завершения разбора HTML;
- сохраняют порядок документа между собой;
- выполняются до `DOMContentLoaded`.

`async` также загружается параллельно:

```html
<script async src="/analytics.js"></script>
```

Но выполняется сразу после готовности файла.

Поэтому:

- порядок нескольких async scripts не гарантирован;
- async script может выполниться до или после окончания HTML parsing;
- если parser ещё работает, выполнение script временно его остановит;
- async script не обязан выполниться до `DOMContentLoaded`.

Module script:

```html
<script type="module" src="/app.js"></script>
```

по умолчанию ведёт себя подобно `defer`:

- загружается параллельно;
- загружает граф статических импортов;
- выполняется после разбора HTML;
- участвует в ожидании `DOMContentLoaded`.

Если module script получил атрибут `async`, его поведение меняется на асинхронное.

13. **Браузер вычисляет стили и формирует render tree.**

DOM описывает структуру документа, а CSSOM — CSS-правила.

Браузер сопоставляет selectors с элементами и выполняет style calculation:

- применяет каскад;
- разрешает наследование;
- вычисляет custom properties;
- получает итоговые значения CSS-свойств.

На основе DOM и вычисленных стилей формируется структура визуальных объектов, которую часто называют render tree.

Она не является простой копией DOM.

Например:

```css
.hidden {
  display: none;
}
```

Элемент остаётся в DOM, но не создаёт обычную отображаемую коробку и не участвует в layout.

Псевдоэлементы `::before` и `::after`, наоборот, могут создавать визуальные коробки, хотя отдельных HTML-узлов для них нет.

14. **Выполняются layout, paint, rasterization и composite.**

Layout рассчитывает геометрию:

- размеры;
- координаты;
- перенос строк;
- положение Flexbox- и Grid-элементов;
- расположение обычного потока и позиционированных элементов.

Paint создаёт упорядоченные команды рисования:

- текста;
- фонов;
- границ;
- теней;
- изображений;
- декоративных эффектов.

Rasterization превращает команды рисования в пиксели. Работа может разбиваться на tiles и выполняться с участием compositor threads и GPU process.

Composite собирает подготовленные слои в итоговый кадр и передаёт его для вывода на экран.

Упрощённая последовательность:

```text
style
→ layout
→ paint
→ rasterization
→ composite
```

Не каждое обновление проходит все стадии.

Например, изменение `transform` уже подготовленного слоя браузер иногда может обработать только на стадии compositing без нового layout и paint.

Это оптимизационная возможность, а не гарантия: решение о слоях и повторной растеризации принимает браузер.

15. **Появляется первый кадр и происходят события загрузки.**

Браузер может показать первые пиксели, когда у него уже достаточно DOM и CSS для построения отображаемой части страницы.

Ему необязательно ждать:

- полного получения HTML;
- всех изображений;
- всех шрифтов;
- выполнения async scripts;
- окончания всех фоновых запросов.

Момент первого paint не определяется напрямую событиями `DOMContentLoaded` или `load`.

`DOMContentLoaded` происходит после того, как:

- HTML был полностью разобран;
- deferred scripts выполнились;
- module scripts, участвующие в загрузке документа, выполнились.

Оно не обязано ждать загрузки всех изображений и async scripts.

Событие `load` происходит позже, когда документ и основные зависимые ресурсы завершили загрузку. Lazy-loaded ресурсы могут не входить в это ожидание до начала их фактической загрузки.

16. **Страница продолжает работать после первого отображения.**

После первого кадра браузер продолжает обрабатывать:

- JavaScript tasks и microtasks;
- сетевые ответы;
- пользовательский ввод;
- timers;
- анимации;
- изменения DOM и CSS;
- новые resource requests.

Эти действия могут запускать новые style calculations, layout, paint и composite.

В SSR-приложении серверный HTML и CSS могут стать видимыми до загрузки клиентского JavaScript.

Во время hydration React:

- создаёт своё клиентское представление;
- сопоставляет его с серверной разметкой;
- подключает обработчики и клиентскую логику;
- продолжает управление интерфейсом.

До hydration нативное HTML-поведение может работать. Например, обычная ссылка способна перейти по адресу, а form — отправиться стандартным способом.

Но пользовательская React-логика, состояние компонента и некоторые интерактивные сценарии ещё могут быть недоступны.

</dd>

## Дополнительные вопросы

<details>
<summary><strong>Что такое URL и какие части URL реально уходят на сервер?</strong></summary>

<dl>
<dd>
<h2></h2>

URL — адрес ресурса.

Для URL:

```text
https://example.com/products?page=2#reviews
```

обычный HTTP-запрос использует:

- scheme для выбора правил подключения;
- host и port для выбора сервера;
- path `/products`;
- query `?page=2`.

Fragment:

```text
#reviews
```

остаётся в браузере и в HTTP-запрос не отправляется.

В HTTP/1.1 path и query находятся в request target:

```http
GET /products?page=2 HTTP/1.1
Host: example.com
```

В HTTP/2 и HTTP/3 аналогичные данные представлены псевдозаголовками:

```text
:method
:scheme
:authority
:path
```

Сервер получит `/products?page=2`, но не `#reviews`.

</dd>
</dl>

<details>
<summary><strong>Всегда ли после ввода URL выполняются DNS, TCP и TLS?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Некоторые этапы можно пропустить или сократить.

Браузер может:

- восстановить страницу из `bfcache`;
- активировать prerendered-документ;
- получить ответ от Service Worker;
- использовать свежую запись HTTP cache;
- переиспользовать открытое HTTP/2- или HTTP/3-соединение;
- использовать DNS-запись из кэша;
- возобновить TLS- или QUIC-сессию.

Например, если HTTP/2-соединение с сервером уже открыто, новый запрос можно отправить по нему без нового TCP и TLS handshake.

Поэтому последовательность DNS → TCP → TLS → HTTP является полной логической моделью, но не обязательным набором новых операций для каждой навигации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем HTTP cache, Cache API и bfcache отличаются?</strong></summary>

<dl>
<dd>
<h2></h2>

HTTP cache хранит HTTP-ответы и управляется правилами заголовков:

```http
Cache-Control
ETag
Last-Modified
Expires
```

Браузер использует его автоматически для сетевых запросов.

Cache API — программное хранилище пар request/response:

```js
const cache = await caches.open("app-v1");
await cache.put(request, response);
```

Им обычно управляет Service Worker или код приложения. Cache API не обязан автоматически соблюдать HTTP cache semantics так же, как сетевой кэш.

`bfcache` хранит не отдельные ответы, а целое состояние страницы для переходов Back/Forward:

- DOM;
- JavaScript heap;
- позицию прокрутки;
- состояние выполнения.

Кратко:

```text
HTTP cache → повторное использование сетевого ответа
Cache API  → программно управляемые Response
bfcache    → восстановление целой страницы
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое DNS lookup?</strong></summary>

<dl>
<dd>
<h2></h2>

DNS lookup — получение IP-адресов по доменному имени.

Сначала могут проверяться:

- DNS-кэш браузера;
- кэш операционной системы;
- локальная конфигурация;
- кэш системного resolver.

Если записи нет, resolver обращается к DNS-сервису.

Записи имеют TTL — срок, в течение которого результат можно повторно использовать.

Один домен может вернуть:

- несколько IPv4-адресов;
- несколько IPv6-адресов;
- адреса разных edge-серверов;
- разные результаты в зависимости от региона.

Полученный IP может вести на CDN или load balancer, который уже направит запрос к подходящему серверу.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое TLS handshake?</strong></summary>

<dl>
<dd>
<h2></h2>

TLS handshake — согласование защищённого HTTPS-соединения.

Во время него:

1. Клиент сообщает поддерживаемые параметры.
2. Сервер выбирает параметры соединения.
3. Сервер предъявляет сертификат.
4. Браузер проверяет доменное имя и срок действия.
5. Проверяется цепочка до доверенного центра сертификации.
6. Стороны получают общий ключевой материал.
7. Дальнейшие данные шифруются симметричными ключами.

Также может согласовываться протокол приложения, например HTTP/2 или HTTP/1.1.

TLS защищает данные в пути от чтения и незаметного изменения.

Он не гарантирует, что:

- сам сайт не является вредоносным;
- сервер не содержит уязвимостей;
- полученный JavaScript безопасен;
- пользователь не передал данные недоверенному владельцу сайта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое HTTP request и HTTP response?</strong></summary>

<dl>
<dd>
<h2></h2>

HTTP request, или запрос, содержит:

- метод;
- адрес операции;
- заголовки;
- при необходимости body.

Например:

```http
GET /products?page=2 HTTP/1.1
Host: example.com
Accept: text/html
```

HTTP response, или ответ, содержит:

- status code;
- headers;
- body, если оно предусмотрено.

Например:

```http
HTTP/1.1 200 OK
Content-Type: text/html
Cache-Control: max-age=60
```

Body может содержать:

- HTML;
- JSON;
- изображение;
- шрифт;
- JavaScript;
- CSS;
- файл другого типа.

Для ввода URL браузер обычно отправляет `GET` без body. При отправке формы или API-запросе метод и body могут быть другими.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит при redirect?</strong></summary>

<dl>
<dd>
<h2></h2>

Сервер отвечает кодом `3xx` и заголовком `Location`:

```http
HTTP/1.1 302 Found
Location: https://example.com/new-page
```

Браузер разрешает новый URL и начинает следующую навигационную попытку.

Redirect может изменить:

- scheme;
- домен;
- port;
- path;
- query.

Каждый дополнительный переход может потребовать новый запрос, а при смене origin — DNS и новое соединение.

Слишком длинная redirect chain увеличивает задержку. Redirect loop завершается ошибкой браузера.

Для методов кроме `GET` важно различать статусы:

- `303` предписывает перейти к `GET`, кроме особого поведения для `HEAD`;
- `307` и `308` сохраняют исходные метод и body;
- `301` и `302` исторически могут преобразовать `POST` в `GET` в браузерной практике.

При обычном вводе URL исходный метод уже является `GET`, поэтому это различие чаще важно после отправки формы или другого запроса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда подключается Service Worker?</strong></summary>

<dl>
<dd>
<h2></h2>

Навигационный запрос может быть перехвачен, если:

- Service Worker уже установлен;
- он активен;
- URL входит в его scope;
- worker контролирует соответствующую страницу или навигацию.

Обработчик:

```js
self.addEventListener("fetch", (event) => {
  event.respondWith(...);
});
```

может вернуть:

- сетевой ответ;
- Response из Cache API;
- offline fallback;
- программно созданный Response.

Если Service Worker регистрируется кодом во время первой загрузки страницы, он обычно не может перехватить уже начавшуюся навигацию, которая загрузила этот документ.

После установки и активации worker начинает контролировать последующие подходящие навигации.

`clients.claim()` позволяет активному worker быстрее взять под контроль уже открытые страницы в scope, но не изменяет прошлый запрос, начавшийся до его активации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем DOM отличается от HTML?</strong></summary>

<dl>
<dd>
<h2></h2>

HTML — сериализованный текст документа:

```html
<main>
  <h1>Products</h1>
</main>
```

DOM — дерево объектов, построенное браузером после разбора HTML.

JavaScript работает с DOM:

```js
document.querySelector("h1");
```

а не напрямую с исходной строкой ответа.

DOM может отличаться от исходного HTML:

- parser исправляет часть ошибочной разметки;
- браузер добавляет обязательные элементы;
- JavaScript создаёт, удаляет и перемещает узлы;
- пользователь взаимодействует с form controls.

Изменение DOM не переписывает исходный HTML-файл на сервере.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое CSSOM?</strong></summary>

<dl>
<dd>
<h2></h2>

CSSOM — объектная модель таблиц стилей и CSS-правил.

Она содержит данные из:

- внешних stylesheets;
- элементов `<style>`;
- inline styles;
- правил, добавленных через CSSOM API.

Браузер сопоставляет selectors с DOM-элементами, применяет каскад, наследование и вычисляет итоговые значения свойств.

DOM отвечает на вопрос:

```text
Какие элементы есть в документе?
```

CSSOM помогает ответить:

```text
Какие CSS-правила могут применяться к этим элементам?
```

На основе DOM и вычисленных стилей браузер определяет визуальные коробки, участвующие в layout и paint.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое render tree?</strong></summary>

<dl>
<dd>
<h2></h2>

Render tree — упрощённое название внутренней структуры визуальных объектов, создаваемой на основе DOM и вычисленных CSS-стилей.

Она не совпадает с DOM один к одному.

Например:

```css
.hidden {
  display: none;
}
```

Элемент остаётся в DOM, но не создаёт обычную layout box.

Псевдоэлемент:

```css
.element::before {
  content: "";
}
```

может создать визуальную коробку, хотя отдельного DOM-узла нет.

Текстовые узлы могут создавать несколько line boxes, а один DOM-элемент при фрагментации способен участвовать в нескольких визуальных фрагментах.

Render tree используется как концептуальный переход от структуры документа и стилей к layout и paint. Внутренние названия и конкретные структуры различаются между browser engines.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему обычный script может блокировать загрузку страницы?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычный script без специальных атрибутов является parser-blocking:

```html
<script src="/app.js"></script>
```

Когда HTML parser достигает его, разбор документа останавливается до загрузки и выполнения JavaScript.

Это необходимо, потому что script может изменить ещё не достроенный документ:

```js
document.write(...);
```

или добавить узлы, влияющие на дальнейший parsing.

`defer` загружается параллельно и выполняется после окончания HTML parsing:

```html
<script defer src="/app.js"></script>
```

`async` загружается параллельно и выполняется сразу после готовности:

```html
<script async src="/analytics.js"></script>
```

Порядок нескольких async scripts не гарантирован.

Module scripts по умолчанию имеют поведение, похожее на `defer`:

```html
<script type="module" src="/app.js"></script>
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему CSS может задержать выполнение JavaScript?</strong></summary>

<dl>
<dd>
<h2></h2>

CSS обычно не останавливает построение DOM, но parser-blocking script может ждать ранее обнаруженную blocking stylesheet.

Например:

```html
<link rel="stylesheet" href="/styles.css">
<script src="/app.js"></script>
```

JavaScript способен запросить вычисленные стили:

```js
getComputedStyle(element).width;
```

Поэтому перед выполнением такого script браузеру нужно иметь корректные данные по предшествующим blocking stylesheets.

Получается:

```text
CSS не обязательно блокирует HTML parsing напрямую,
но может задержать parser-blocking JavaScript,
а JavaScript уже удерживает HTML parser.
```

`defer` уменьшает такую блокировку parsing, потому что выполнение откладывается до завершения разбора HTML. Но deferred script всё равно может ждать необходимые stylesheets перед выполнением.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>DOMContentLoaded</code> отличается от <code>load</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`DOMContentLoaded` происходит, когда HTML полностью разобран и scripts, которые должны выполниться до этого события, завершили работу.

К ним относятся:

- deferred scripts;
- обычные module scripts.

Событие не обязано ждать:

- все изображения;
- async scripts;
- lazy-loaded ресурсы;
- завершение всех сетевых запросов приложения.

`load` происходит позже, когда документ и основные зависимые ресурсы завершили загрузку.

Например:

```js
document.addEventListener("DOMContentLoaded", () => {
  // DOM уже построен
});

window.addEventListener("load", () => {
  // основные ресурсы документа загружены
});
```

Первый paint не привязан строго ни к одному из этих событий. Браузер может показать страницу до `DOMContentLoaded`, если уже получил достаточно HTML и CSS.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое layout, paint и composite?</strong></summary>

<dl>
<dd>
<h2></h2>

Layout рассчитывает геометрию:

- размеры;
- координаты;
- строки текста;
- положение элементов.

Paint создаёт упорядоченные команды для:

- текста;
- фонов;
- границ;
- теней;
- изображений.

Rasterization превращает эти команды в пиксели.

Composite объединяет подготовленные слои в итоговый кадр.

Браузер создаёт compositing layers не для каждого DOM-элемента, а по внутренним правилам и потребностям отображения.

Изменение `width` может потребовать:

```text
layout → paint → composite
```

Изменение `background-color` обычно не требует layout, но может потребовать:

```text
paint → composite
```

Анимация `transform` подготовленного слоя иногда выполняется через:

```text
composite
```

Но конкретный pipeline зависит от browser engine и состояния страницы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему HTML уже виден, но кнопки ещё не работают?</strong></summary>

<dl>
<dd>
<h2></h2>

При SSR сервер отправляет готовый HTML.

Браузер может:

1. разобрать HTML;
2. применить CSS;
3. показать страницу;
4. только затем загрузить и выполнить клиентский JavaScript.

В React/Next.js hydration сопоставляет клиентское React-дерево с серверной разметкой и подключает обработчики.

До hydration:

- обычная ссылка может работать нативно;
- form может отправиться стандартным способом;
- текст и изображения уже видны;
- React state и пользовательские обработчики ещё могут быть недоступны.

Если интерфейс выглядит готовым, но не реагирует, возможны причины:

- JavaScript bundle ещё загружается;
- main thread занят;
- hydration ещё не дошла до компонента;
- произошла ошибка JavaScript;
- возникло hydration mismatch;
- ресурс JavaScript не загрузился.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие процессы браузера участвуют в навигации?</strong></summary>

<dl>
<dd>
<h2></h2>

В упрощённой модели Chromium:

- **browser process** обслуживает интерфейс браузера, историю и координирует навигацию;
- **network service** выполняет DNS, соединения, TLS и HTTP;
- **renderer process** разбирает и выполняет содержимое страницы в ограниченной среде;
- **GPU process** участвует в rasterization, compositing и выводе кадров;
- вспомогательные процессы могут обслуживать extensions, audio, storage и другие подсистемы.

Процессы обмениваются IPC-сообщениями.

Site Isolation помогает размещать документы разных сайтов в разных renderer processes.

Это архитектура Chromium, а не обязательное требование веб-стандартов. Firefox, Safari и другие браузеры могут иначе распределять работу между процессами и потоками, сохраняя похожую внешнюю модель поведения веб-платформы.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что важно понимать |
| --- | --- |
| Маршрутизация SPA | History API, path, query и fragment могут менять экран без полной навигации |
| SSR/Next.js | HTML может отображаться до загрузки JavaScript, а интерактивность зависит от hydration |
| Service Worker/PWA | Навигационный ответ может прийти из Cache API или offline-стратегии |
| Производительность | DNS, соединение, redirects, CSS, scripts, fonts и изображения влияют на отображение |
| Кэширование | HTTP cache, Cache API и bfcache решают разные задачи |
| Ошибки загрузки | Ошибка DNS, TLS или соединения отличается от HTTP `404` или `500` |
| Блокировка parser | Обычный script останавливает разбор HTML |
| Render blocking | Подходящая внешняя stylesheet может задерживать первый render |
| События загрузки | `DOMContentLoaded`, `load` и первый paint обозначают разные моменты |
| Безопасность | HTTPS, HSTS, cookie, CSP и CORS влияют на загрузку и выполнение ресурсов |
