## Вопрос

<br>

 💬 **Что важно знать про Page Lifecycle, Page Visibility API, bfcache и фоновые вкладки?**

<h2></h2>

<br>
<dl>
<dd>

Жизненный цикл страницы описывает состояния между созданием документа и его удалением из памяти.

Концептуально страница может быть:

- активной и имеющей фокус;
- видимой, но не имеющей фокуса;
- скрытой;
- замороженной;
- завершающей работу;
- отброшенной браузером из памяти.

Это не одна универсальная шкала со строго одинаковыми событиями во всех браузерах.

Нужно различать три характеристики:

1. Видна ли страница — Page Visibility API.
2. Имеет ли окно фокус — `document.hasFocus()` и события `focus`/`blur`.
3. Выполняются ли задачи страницы — обычное, frozen или discarded-состояние.

Например, окно может быть видимым, но не иметь фокуса, если пользователь работает в другом окне. Скрытая страница может ещё выполнять JavaScript, а замороженная — оставаться в памяти, но не выполнять freezable tasks.

**Page Visibility API** сообщает, виден ли документ.

Основное значение доступно через:

```js
document.visibilityState
```

Обычно оно равно:

```text
visible
hidden
```

Также можно использовать:

```js
document.hidden
```

Изменение отслеживают событием:

```js
document.addEventListener("visibilitychange", () => {
  if (document.visibilityState === "hidden") {
    pauseBackgroundWork();
  } else {
    resumeBackgroundWork();
  }
});
```

Переход в `hidden` может произойти, когда пользователь:

- переключился на другую вкладку;
- свернул окно браузера;
- переключился в другое приложение;
- заблокировал экран;
- начал переход на другую страницу;
- закрыл вкладку или браузер.

`hidden` не означает, что документ уже выгружен или заморожен.

JavaScript ещё может выполняться, но браузер способен ограничить его работу.

Переход в `hidden` часто является последним достаточно надёжным сигналом, который страница успевает получить перед завершением или приостановкой, особенно на мобильных устройствах.

В этот момент обычно:

- приостанавливают визуальные обновления;
- уменьшают или останавливают polling;
- сохраняют небольшой объём состояния;
- фиксируют временную отметку;
- отправляют допустимую аналитику;
- прекращают неважную фоновую работу.

Но даже `visibilitychange` не является абсолютной гарантией. Процесс браузера или операционная система могут завершить без возможности выполнить дополнительный JavaScript.

Поэтому критичное пользовательское состояние лучше сохранять постепенно во время работы, а не только в последнем lifecycle-handler.

Например, черновик формы можно периодически или после значимых изменений сохранять локально:

```js
function saveDraft(draft) {
  localStorage.setItem("draft", JSON.stringify(draft));
}
```

Последнее lifecycle-событие должно быть дополнительной защитой, а не единственной точкой сохранения.

Скрытая страница обычно продолжает существовать в памяти.

Однако браузер может:

- остановить `requestAnimationFrame`;
- увеличить минимальную задержку timers;
- объединять вызовы timers;
- уменьшить частоту фоновых задач;
- ограничивать сетевую и вычислительную активность;
- снижать приоритет процесса.

`requestAnimationFrame` обычно не вызывается для скрытого документа, поскольку браузеру не нужно создавать визуальные кадры для невидимой страницы.

Timers:

```js
setTimeout
setInterval
```

не являются точными часами даже в активной вкладке, а в фоновой вкладке их задержка может значительно увеличиваться.

Поэтому неправильно рассчитывать время по количеству вызовов:

```js
let seconds = 0;

setInterval(() => {
  seconds += 1;
}, 1000);
```

После возвращения страницы значение может не соответствовать реальному прошедшему времени.

Для расчёта реального календарного времени сохраняют timestamp:

```js
const startedAt = Date.now();

function getElapsedTime() {
  return Date.now() - startedAt;
}
```

При возврате страницы состояние пересчитывают по текущему времени, а не пытаются выполнить все пропущенные интервалы.

Фоновый режим не означает, что нужно безусловно останавливать любую работу.

Например:

- воспроизведение аудио может быть ожидаемым поведением;
- загрузка пользовательского файла может быть важна;
- отправку уже подтверждённой операции нельзя отменять только из-за смены вкладки;
- push- и realtime-логика может иметь отдельную стратегию.

Останавливают именно ту работу, которая не имеет смысла без видимого интерфейса:

- перерисовку графика;
- декоративную анимацию;
- частый polling;
- вычисления для невидимого preview;
- обновление счётчика каждый кадр.

В состоянии **frozen**, или замороженном, документ и JavaScript heap остаются в памяти, но браузер приостанавливает выполнение freezable tasks.

Могут быть приостановлены:

- timers;
- часть callback асинхронных API;
- обработка очередей задач;
- обновления интерфейса.

При возобновлении страница продолжает работу с сохранённым состоянием.

События:

```text
freeze
resume
```

поддерживаются не одинаково во всех браузерах, поэтому основную кросс-браузерную логику обычно строят вокруг:

```text
visibilitychange
pagehide
pageshow
```

а `freeze` и `resume` используют как дополнительную оптимизацию при доступности.

Перед заморозкой полезно освободить ресурсы, которые могут мешать другим вкладкам или сохранению в bfcache:

- временные Web Locks;
- долгоживущие соединения;
- BroadcastChannel;
- ненужные IndexedDB-транзакции;
- фоновые вычисления.

Такой cleanup должен быть обратимым, потому что страница может позже возобновиться с тем же JavaScript heap.

В состоянии **discarded** браузер полностью удаляет экземпляр страницы из памяти, обычно для освобождения ресурсов.

Перед этим не гарантируется событие, которое JavaScript успеет обработать.

При возвращении к такой вкладке браузер обычно выполняет новую загрузку документа:

```text
новый DOM
новый JavaScript heap
повторная инициализация приложения
```

Если браузер поддерживает свойство:

```js
document.wasDiscarded
```

оно позволяет новому документу узнать, что предыдущий экземпляр этой вкладки был отброшен:

```js
if (document.wasDiscarded) {
  restoreUnsavedState();
  refreshCriticalData();
}
```

Поддержка свойства различается между браузерами, поэтому оно используется как дополнительный сигнал, а не как единственный механизм восстановления.

**bfcache**, или back/forward cache, решает другую задачу.

Он может сохранить живой экземпляр страницы для навигации Back/Forward:

- DOM;
- JavaScript heap;
- значения элементов формы;
- позицию прокрутки;
- внутреннее состояние приложения.

Когда пользователь возвращается кнопкой Back или Forward, браузер может восстановить этот экземпляр почти мгновенно вместо новой загрузки HTML и повторного выполнения всего JavaScript.

Это не HTTP cache.

HTTP cache хранит отдельные сетевые ответы:

```text
HTML
CSS
JavaScript
images
```

bfcache хранит состояние целой страницы.

При сохранении в bfcache выполнение JavaScript страницы приостанавливается. После восстановления оно продолжается с сохранённым heap, но внешняя реальность могла измениться:

- данные на сервере могли обновиться;
- авторизация могла истечь;
- WebSocket мог закрыться;
- срок действия токена мог закончиться;
- другая вкладка могла изменить общие данные;
- прошло значительное время.

При уходе со страницы возникает:

```js
window.addEventListener("pagehide", (event) => {
  if (event.persisted) {
    pauseForBackForwardCache();
  } else {
    prepareForTermination();
  }
});
```

Если:

```js
event.persisted === true
```

браузер сообщает, что страницу сохраняют для возможного повторного использования.

При возвращении возникает:

```js
window.addEventListener("pageshow", (event) => {
  if (event.persisted) {
    restoreAfterBackForwardCache();
  }
});
```

`pageshow` возникает не только при восстановлении из bfcache, но и после обычной загрузки.

Различие определяется через:

```js
event.persisted
```

При восстановлении из bfcache:

```text
pageshow.persisted === true
```

События:

```text
DOMContentLoaded
load
```

повторно не происходят, потому что новый документ не создавался.

Поэтому код, который должен выполняться при каждом появлении страницы, нельзя размещать только в `load`.

Удобно иметь общую функцию возобновления:

```js
async function resumePage() {
  updateElapsedTime();
  restartPollingIfNeeded();
  reconnectRealtimeIfNeeded();
  await refreshStaleData();
}

document.addEventListener("visibilitychange", () => {
  if (document.visibilityState === "visible") {
    void resumePage();
  }
});

window.addEventListener("pageshow", (event) => {
  if (event.persisted) {
    void resumePage();
  }
});
```

Функция должна быть идемпотентной: повторный вызов не должен создавать несколько timers, polling-циклов или WebSocket-соединений.

Например, перед запуском нового polling проверяют, не запущен ли он уже.

При восстановлении проверяют:

- сколько времени прошло;
- не устарели ли данные;
- актуальна ли авторизация;
- существует ли сетевое соединение;
- не изменилось ли состояние в другой вкладке;
- нужно ли повторно синхронизироваться с сервером.

Не следует выполнять logout только потому, что страница стала `hidden` или получила `pagehide`.

Пользователь мог:

- временно переключить вкладку;
- перейти назад с возможностью bfcache;
- открыть системный диалог;
- свернуть приложение.

Logout и критичные серверные операции должны иметь собственную явную бизнес-логику.

Событие `unload` не используют для важного сохранения, аналитики или cleanup:

```js
window.addEventListener("unload", handler);
```

Оно:

- может вообще не произойти;
- не подходит для асинхронной работы;
- может мешать использованию bfcache;
- способно задерживать завершение навигации;
- плохо работает при принудительном завершении приложения.

Для cleanup, совместимого с bfcache, предпочтительнее `pagehide`.

Но и `pagehide` не гарантируется во всех сценариях. Например, мобильная операционная система может завершить процесс браузера после того, как пользователь переключился в другое приложение.

Поэтому для сохранения небольшого состояния важен также переход:

```text
visibilityState → hidden
```

Для небольшой завершающей отправки можно использовать:

```js
navigator.sendBeacon("/analytics", data);
```

`sendBeacon()`:

- отправляет `POST`;
- не блокирует навигацию;
- предназначен для небольших данных;
- возвращает признак успешной постановки в очередь;
- не позволяет прочитать HTTP-ответ.

Положительный результат `sendBeacon()` не является подтверждением, что сервер успешно обработал данные.

Для запроса с большим контролем существует:

```js
fetch("/analytics", {
  method: "POST",
  body: data,
  keepalive: true,
});
```

`keepalive` позволяет запросу продолжаться после завершения страницы, но имеет ограничения по объёму и времени.

Также нельзя рассчитывать, что JavaScript страницы успеет обработать полученный response после её завершения.

Поэтому `sendBeacon()` и `keepalive` подходят для:

- телеметрии;
- небольших статистических событий;
- best-effort уведомлений.

Они не заменяют подтверждённую транзакцию для:

- оплаты;
- сохранения важного документа;
- изменения прав;
- критичной бизнес-операции.

Такая операция должна быть отправлена и подтверждена до ухода со страницы либо надёжно повторена после следующего запуска.

`beforeunload` предназначен для предупреждения о реально несохранённых изменениях:

```js
function handleBeforeUnload(event) {
  event.preventDefault();
  event.returnValue = "";
}
```

Современные браузеры показывают собственный системный текст. Страница не может надёжно задать произвольное сообщение.

Кроме того, показ предупреждения обычно требует предыдущего пользовательского взаимодействия со страницей.

Listener подключают только при появлении dirty-state:

```js
function enableUnsavedChangesWarning() {
  window.addEventListener(
    "beforeunload",
    handleBeforeUnload,
  );
}

function disableUnsavedChangesWarning() {
  window.removeEventListener(
    "beforeunload",
    handleBeforeUnload,
  );
}
```

После сохранения данных listener удаляют.

Постоянный `beforeunload`:

- ухудшает пользовательский опыт;
- создаёт ненужные предупреждения;
- может ухудшать совместимость с bfcache;
- не гарантирует сохранение данных на мобильных устройствах.

Для обычной аналитики, logout, закрытия WebSocket или очистки временного состояния `beforeunload` не нужен.

Практическая стратегия выглядит так:

```text
Во время работы
→ постепенно сохранять критичное состояние.

visibilitychange → hidden
→ остановить ненужную работу;
→ сохранить небольшой локальный state;
→ отправить best-effort аналитику.

pagehide
→ выполнить обратимый cleanup;
→ проверить persisted.

pageshow / visible / resume
→ пересчитать время;
→ проверить свежесть данных;
→ восстановить polling и соединения.

Новая загрузка после discard
→ проверить wasDiscarded;
→ восстановить локальный черновик;
→ синхронизироваться с сервером.
```

<dl>

<h2></h2>

Page Visibility API сообщает, виден ли документ пользователю.

Основное свойство:

```js
document.visibilityState
```

Обычно оно имеет значения:

```text
visible
hidden
```

document.addEventListener("visibilitychange", () => {

- переключил вкладку;

- начал уход со страницы.

Page Visibility API подходит для:

- остановки визуальных обновлений;
- уменьшения polling;
- фиксации времени ухода;
- сохранения небольшого состояния;
- восстановления данных после возврата.

<details>
<summary><strong>Чем visibility отличается от focus?</strong></summary>

<dl>
<dd>
<h2></h2>

Visibility отвечает на вопрос:

```text
Виден ли документ?
```

Focus отвечает на вопрос:

```text
Получает ли это окно активный пользовательский ввод?
```

Проверить видимость можно через:

```js
document.visibilityState
```

Проверить фокус:

```js
document.hasFocus()
```

Страница может быть видна, но не иметь фокуса.

Например, пользователь расположил рядом два окна браузера и работает во втором. Первая страница остаётся видимой, но фокус находится в другом окне.

События окна:

```js
window.addEventListener("focus", handler);
window.addEventListener("blur", handler);
```

не заменяют `visibilitychange`.

Для остановки невидимых анимаций обычно важна visibility.

Для поведения keyboard shortcuts или определения активного окна может быть важен focus.

</dd>
</dl>

<details>
<summary><strong>Чем hidden page отличается от frozen page?</strong></summary>

<dl>
<dd>
<h2></h2>

Hidden page не видна пользователю, но JavaScript ещё может выполняться.

Браузер способен:

- ограничить timers;
- остановить `requestAnimationFrame`;
- уменьшить приоритет задач;
- продолжить часть сетевой работы.

Frozen page остаётся в памяти, но freezable tasks приостанавливаются.

JavaScript heap сохраняется, однако callbacks не выполняются до возобновления.

Упрощённо:

```text
hidden
→ страница не видна, работа ограничена

frozen
→ выполнение большей части задач приостановлено
```

Браузер может перейти:

```text
visible → hidden → frozen
```

а затем:

```text
frozen → visible
```

или полностью отбросить страницу.

События `freeze` и `resume` доступны не одинаково во всех браузерах, поэтому основной код не должен зависеть только от них.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит с timers в фоновых вкладках?</strong></summary>

<dl>
<dd>
<h2></h2>

В фоновой вкладке браузер обычно ограничивает:

```js
setTimeout
setInterval
```

Он может:

- увеличивать фактическую задержку;
- объединять несколько timers;
- запускать их значительно реже;
- полностью приостановить при frozen-состоянии.

`requestAnimationFrame` обычно перестаёт вызываться, пока документ скрыт.

Поэтому такой код не измеряет точное время:

```js
let seconds = 0;

setInterval(() => {
  seconds += 1;
}, 1000);
```

Надёжнее сохранить timestamp:

```js
const startedAt = Date.now();

function getElapsedSeconds() {
  return Math.floor(
    (Date.now() - startedAt) / 1000,
  );
}
```

После возврата интерфейс пересчитывают по фактически прошедшему времени.

Не следует запускать подряд все пропущенные действия. Например, polling после десяти минут фонового режима обычно должен сделать один запрос свежих данных, а не сотни пропущенных запросов.

</dd>

<details>
<summary><strong>Как безопасно сохранять данные при уходе со страницы?</strong></summary>

<dl>
<dd>
<h2></h2>

Нельзя рассчитывать на один финальный обработчик.

Надёжная стратегия состоит из нескольких уровней.

Во время редактирования состояние сохраняют постепенно:

```js
function handleDraftChange(draft) {
  saveDraftLocally(draft);
}
```

При переходе документа в `hidden` сохраняют последнюю небольшую версию:

```js
document.addEventListener("visibilitychange", () => {
  if (document.visibilityState === "hidden") {
    saveCurrentDraft();
  }
});
```

Для best-effort аналитики используют:

```js
navigator.sendBeacon("/analytics", payload);
```

Критичная серверная операция должна быть завершена заранее и получить подтверждение.

Например, сохранение документа нельзя считать успешным только потому, что запрос был поставлен через `sendBeacon()`.

Также нельзя полагаться только на:

```text
beforeunload
pagehide
unload
```

Процесс может завершиться без выполнения JavaScript.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое bfcache?</strong></summary>

<dl>
<dd>
<h2></h2>

Back/forward cache сохраняет живой экземпляр страницы для переходов назад и вперёд.

Могут сохраняться:

- DOM;
- JavaScript heap;
- состояния компонентов;
- значения форм;
- позиция прокрутки.

При возврате браузер не обязан снова:

- загружать HTML;
- выполнять начальную загрузку JavaScript;
- создавать приложение с нуля.

Вместо этого ранее сохранённая страница размораживается.

Это не HTTP cache.

HTTP cache хранит отдельные ответы, а bfcache — целый экземпляр документа.

При восстановлении:

```text
DOMContentLoaded
load
```

повторно не запускаются.

При этом данные могли устареть, поэтому в `pageshow` проверяют свежесть критичного состояния.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как понять, что страница восстановилась из bfcache?</strong></summary>

<dl>
<dd>
<h2></h2>

Используют событие:

```js
window.addEventListener("pageshow", (event) => {
  if (event.persisted) {
    console.log("Restored from bfcache");
  }
});
```

`pageshow` возникает и при обычной загрузке.

На обычной загрузке:

```js
event.persisted === false
```

При восстановлении из bfcache:

```js
event.persisted === true
```

В обработчике можно:

- пересчитать прошедшее время;
- обновить устаревшие данные;
- проверить авторизацию;
- переподключить realtime;
- восстановить polling;
- проверить состояние другой вкладки.

Handler желательно делать идемпотентным, потому что похожая resume-логика может вызываться также после `visibilitychange`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>pagehide</code> лучше <code>unload</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`pagehide` совместим с bfcache:

```js
window.addEventListener("pagehide", (event) => {
  console.log(event.persisted);
});
```

Если:

```js
event.persisted === true
```

страницу сохраняют для возможного возврата.

`unload`:

- ненадёжен;
- может не произойти;
- способен мешать bfcache;
- не подходит для асинхронного сохранения;
- может задерживать навигацию.

Поэтому важную логику на `unload` не размещают.

Но `pagehide` тоже не гарантирован при аварийном завершении процесса или закрытии мобильного приложения через системный менеджер.

Критичное состояние сохраняют раньше, а `pagehide` используют для дополнительного обратимого cleanup.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>beforeunload</code> опасен?</strong></summary>

<dl>
<dd>
<h2></h2>

`beforeunload` может показать системное предупреждение при наличии несохранённых изменений:

```js
function handleBeforeUnload(event) {
  event.preventDefault();
  event.returnValue = "";
}
```

Но у него есть ограничения:

- браузер показывает собственный текст;
- обычно требуется предыдущее пользовательское взаимодействие;
- событие не гарантировано на мобильных устройствах;
- постоянный listener ухудшает UX;
- в некоторых браузерах он может мешать bfcache.

Обработчик подключают только при dirty-state:

```js
if (hasUnsavedChanges) {
  window.addEventListener(
    "beforeunload",
    handleBeforeUnload,
  );
}
```

После сохранения удаляют:

```js
window.removeEventListener(
  "beforeunload",
  handleBeforeUnload,
);
```

Для аналитики, logout или обычного cleanup `beforeunload` не используют.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое <code>document.wasDiscarded</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Браузер может отбросить фоновую вкладку из памяти, если системе не хватает ресурсов.

JavaScript старой страницы при этом не получает гарантированного финального события.

Когда пользователь возвращается, браузер выполняет новую загрузку документа.

Если поддерживается:

```js
document.wasDiscarded
```

новая страница может определить, что предыдущий экземпляр вкладки был discarded:

```js
if (document.wasDiscarded) {
  restoreDraft();
  refreshCriticalData();
}
```

Свойство не восстанавливает потерянный JavaScript heap.

Оно только сообщает новому документу причину предыдущего завершения.

Поэтому данные, которые должны пережить discard, заранее сохраняют во внешнем хранилище:

- сервер;
- IndexedDB;
- localStorage;
- другое устойчивое хранилище.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что проверять при возврате на вкладку?</strong></summary>

<dl>
<dd>
<h2></h2>

После возврата проверяют:

1. Сколько времени прошло.
2. Не устарели ли данные.
3. Актуальна ли авторизация.
4. Существует ли WebSocket.
5. Не изменилось ли состояние в другой вкладке.
6. Нужно ли перезапустить polling.
7. Не создаст ли повторный запуск дубликаты timers и listeners.

Пример общей функции:

```js
async function resumePage() {
  updateTimeDependentState();

  if (!isPollingRunning()) {
    startPolling();
  }

  if (!isRealtimeConnected()) {
    reconnectRealtime();
  }

  if (isDataStale()) {
    await refreshData();
  }
}
```

Её можно вызывать после:

```text
visibilitychange → visible
pageshow.persisted
resume
online
```

Функция должна быть идемпотентной.

Повторный вызов не должен создавать:

- второй `setInterval`;
- второе WebSocket-соединение;
- повторные DOM-listeners;
- несколько одинаковых запросов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как управлять polling и WebSocket в фоновой вкладке?</strong></summary>

<dl>
<dd>
<h2></h2>

Частый polling для невидимого интерфейса обычно останавливают или замедляют:

```js
document.addEventListener("visibilitychange", () => {
  if (document.visibilityState === "hidden") {
    stopPolling();
  } else {
    startPolling();
    refreshData();
  }
});
```

После возврата обычно делают один актуальный запрос, а не воспроизводят все пропущенные интервалы.

WebSocket не следует считать гарантированно живым после долгого фонового режима или bfcache.

Соединение могло закрыться из-за:

- отсутствия сети;
- server timeout;
- заморозки страницы;
- перехода устройства в sleep;
- смены IP-адреса;
- политики браузера.

После возврата проверяют:

```js
socket.readyState
```

При необходимости переподключаются с backoff и затем получают актуальное состояние с сервера.

Одного восстановления WebSocket недостаточно: за время отсутствия часть сообщений могла быть пропущена.

Поэтому realtime-приложению часто нужен отдельный запрос полной или инкрементальной синхронизации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить, почему страница не попала в bfcache?</strong></summary>

<dl>
<dd>
<h2></h2>

Сценарий проверяют через настоящую навигацию:

1. Открыть страницу.
2. Перейти на другую страницу.
3. Нажать Back.
4. Проверить `pageshow.persisted`.

Обычный reload не является проверкой bfcache.

В Chrome DevTools на вкладке Application есть раздел Back/forward cache, который запускает тест и показывает известные блокирующие причины.

Частой причиной является listener:

```js
window.addEventListener("unload", handler);
```

На eligibility также могут влиять некоторые активные API, незавершённые ресурсы и особенности документа.

Точный список различается между браузерами и изменяется со временем, поэтому ориентируются на диагностику конкретного браузера.

После исправления тест повторяют, а не предполагают, что удаление одной причины автоматически гарантировало попадание в bfcache.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что важно понимать |
| --- | --- |
| Dashboard с периодическим опросом | Останавливать или замедлять polling в скрытой вкладке |
| Таймер или обратный отсчёт | Считать время по timestamp, а не по числу вызовов interval |
| Видео или аудио | Учитывать visibility, но не останавливать ожидаемое фоновое аудио без причины |
| WebSocket | Проверять соединение и синхронизировать данные после возврата |
| Back/Forward navigation | Страница может восстановиться из bfcache без полной загрузки |
| Экран с чувствительными данными | После восстановления проверить сессию и свежесть данных |
| Несохранённая форма | Сохранять черновик постепенно и подключать `beforeunload` только при dirty-state |
| Аналитика при уходе | `sendBeacon()` или `fetch(..., { keepalive: true })` для best-effort отправки |
| Вкладка была discarded | Новый документ может проверить `document.wasDiscarded` |
| Возобновление приложения | Общая идемпотентная resume-функция без дублирования ресурсов |
