## Вопрос

Что важно знать про Page Lifecycle, Page Visibility API, bfcache и фоновые вкладки?

<details>
<summary><strong>Показать ответ</strong></summary>

Жизненный цикл страницы описывает состояния между её открытием и удалением из памяти. Страница может быть активной, видимой без фокуса, скрытой, замороженной, выгруженной при навигации или отброшенной браузером ради освобождения ресурсов. Поддержка отдельных событий различается между браузерами, поэтому код не должен рассчитывать на единственный обязательный «финальный» обработчик.

**Page Visibility API** показывает, виден ли документ. `document.visibilityState` имеет основные значения `visible` и `hidden`, а событие `visibilitychange` сообщает об их смене. Переход в `hidden` часто является последним надёжно наблюдаемым сигналом, особенно на мобильных устройствах. В этот момент сохраняют небольшой объём важного состояния, отправляют допустимую аналитику и останавливают ненужную фоновую работу.

Скрытая страница ещё не обязательно заморожена: JavaScript может продолжать выполняться, но с ограничениями. Браузер обычно останавливает `requestAnimationFrame`, снижает частоту timers и может ограничивать другую работу, чтобы экономить CPU и батарею. Поэтому `setInterval` не является точными часами. После возвращения нужно вычислять прошедшее время по текущей временной отметке, а не по числу срабатываний timer.

В состоянии **frozen**, или замороженном, браузер приостанавливает замораживаемые задачи, включая timers и обработчики некоторых асинхронных операций. Страница может позже продолжить работу, а может быть **discarded** - удалена из памяти без события, которое успеет обработать JavaScript. В Chromium при следующей полной загрузке `document.wasDiscarded` позволяет узнать, что предыдущий экземпляр вкладки был отброшен. События `freeze` и `resume` также не являются одинаково доступными во всех браузерах.

**bfcache** (back/forward cache) сохраняет целый экземпляр страницы для переходов Back/Forward: DOM, JavaScript heap, значения форм и позицию прокрутки. При возврате браузер может разморозить страницу почти мгновенно вместо новой загрузки HTML. Это не HTTP cache, который хранит отдельные сетевые ответы.

При уходе страницы событие `pagehide` получает `event.persisted === true`, если браузер планирует сохранить её для повторного использования. При восстановлении `pageshow.persisted === true` показывает возврат из bfcache. События `load` и `DOMContentLoaded` при таком возврате повторно не запускаются, поэтому свежесть авторизации, данных и соединений проверяют в `pageshow` или общей функции возобновления.

`unload` не используют для важной логики: событие ненадёжно и может лишить страницу bfcache. `pagehide` совместим с bfcache, но на мобильных тоже может не сработать, если пользователь закрыл приложение из системного менеджера. Для небольшой завершающей отправки подходит `navigator.sendBeacon()`: он ставит короткий `POST` в очередь без блокировки навигации, но не позволяет прочитать ответ. Альтернатива для более управляемого запроса - `fetch(..., { keepalive: true })` с учётом ограничений размера и времени.

`beforeunload` нужен только пока действительно есть несохранённые изменения. Обработчик может показать системное предупреждение, но браузер не разрешает произвольный текст. После сохранения формы обработчик удаляют: постоянная подписка ухудшает UX и в некоторых браузерах мешает использованию bfcache.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Что такое Page Visibility API?</summary>

API сообщает, видим ли документ: `document.visibilityState` обычно равен `visible` или `hidden`, а `visibilitychange` возникает при смене значения. `hidden` означает отсутствие видимости, но не гарантирует, что JavaScript уже заморожен. Это подходящий сигнал для остановки визуальных обновлений и сохранения небольшого состояния.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем hidden page отличается от frozen page?</summary>

Hidden page не видна, но часть JavaScript всё ещё может выполняться с ограниченной частотой. Frozen page не запускает замораживаемые задачи из своих очередей до возобновления. Браузер может перейти из hidden во frozen для экономии ресурсов или сохранения страницы в bfcache, а затем разморозить либо полностью отбросить её.

</details>

<details>
<summary><strong>Вопрос:</strong> Что происходит с timers в фоновых вкладках?</summary>

Браузер ограничивает `setTimeout` и `setInterval`, а `requestAnimationFrame` обычно перестаёт вызываться, пока документ скрыт. Точные правила зависят от браузера, нагрузки и длительности фонового режима. После возврата вычисляют фактически прошедшее время и синхронизируют состояние, а не пытаются выполнить все пропущенные интервалы.

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое bfcache?</summary>

Back/forward cache сохраняет живой экземпляр страницы для переходов назад и вперёд. При возврате восстанавливаются DOM, JavaScript heap, форма и прокрутка, поэтому страница продолжает прежнее состояние без полной загрузки документа.

Это не кэш файла и не повторное чтение HTML из HTTP cache. Поэтому `DOMContentLoaded` и `load` при восстановлении не повторяются, а данные и соединения могли устареть за время отсутствия страницы.

</details>

<details>
<summary><strong>Вопрос:</strong> Как понять, что страница восстановилась из bfcache?</summary>

Через событие `pageshow`. Если `event.persisted === true`, страница восстановлена из bfcache. На обычной первой загрузке `pageshow` тоже возникает, но `persisted` будет `false`.

Например, профиль может появиться мгновенно в старом виде, хотя сессия или права уже изменились. В обработчике восстановления проверяют время последнего обновления, состояние соединений и при необходимости повторно получают критичные данные.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем <code>pagehide</code> лучше <code>unload</code>?</summary>

`unload` ненадёжен и может блокировать bfcache. `pagehide` совместим с сохранением страницы, а `event.persisted` показывает, планируется ли её повторное использование. Однако на мобильных `pagehide` тоже не гарантирован, поэтому критичное состояние лучше сохранять раньше, в том числе при переходе документа в `hidden`.

Для короткой аналитической отправки используют `navigator.sendBeacon()`. Он не задерживает переход, но подходит только для небольшого `POST`, не возвращает тело ответа и не заменяет надёжное серверное подтверждение критичной операции.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему <code>beforeunload</code> опасен?</summary>

Он может показывать системное предупреждение и в некоторых браузерах мешать bfcache. Обработчик добавляют только после появления несохранённых изменений и удаляют после сохранения. Для аналитики, logout или обычной очистки ресурсов `beforeunload` не подходит.

</details>

<details>
<summary><strong>Вопрос:</strong> Что проверять при возврате на вкладку?</summary>

Сколько времени прошло, не устарели ли данные, жива ли сессия, сохранилось ли сетевое соединение и требуется ли повторный запрос. Временные расчёты восстанавливают по текущему времени, а не по пропущенным вызовам timer.

Для realtime-экрана проверяют состояние WebSocket, при необходимости переподключаются с постепенно увеличивающейся задержкой (backoff) и затем синхронизируют данные с сервером, потому что часть событий могла быть пропущена.

</details>

<details>
<summary><strong>Вопрос:</strong> Как проверить, почему страница не попала в bfcache?</summary>

Сценарий воспроизводят переходом на другую страницу и кнопкой Back, а не обычным reload. В Chrome DevTools раздел Back/forward cache на вкладке Application запускает тест и показывает часть блокирующих причин. Частые проблемы - обработчик `unload`, незавершённые ресурсы или API, несовместимые с заморозкой; точный список зависит от браузера и меняется со временем.

</details>

## Где это встречается во frontend

| Ситуация | Что важно понимать |
| --- | --- |
| Dashboard с периодическим опросом | Останавливать или замедлять запросы в скрытой вкладке |
| Видео или аудио | Менять поведение при переходе документа в `hidden` |
| WebSocket | Проверять соединение после возврата вкладки или восстановления сети |
| Back/Forward navigation | Страница может восстановиться из bfcache без полной загрузки |
| Экран с чувствительными данными | После восстановления проверить сессию и свежесть данных |
| Несохранённая форма | Подключать `beforeunload` только при реально изменённых данных |
