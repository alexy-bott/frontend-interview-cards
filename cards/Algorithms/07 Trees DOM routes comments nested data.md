## Вопрос

<br>

 💬 **Что такое дерево и почему деревья важны во frontend? Как работать с DOM, маршрутами, комментариями и другими вложенными данными?**

<h2></h2>

<br>
<dl>
<dd>

Дерево (tree) — иерархическая структура из узлов и связей между ними. Корень (root) — верхний узел без родителя. У узла (node) могут быть дочерние узлы (children), а узел без детей называют листом (leaf). Связь между двумя узлами называется ребром (edge), часть дерева от выбранного узла вниз — поддеревом (subtree).

Если независимых корневых узлов несколько, такая структура называется лесом (forest). При необходимости над ними можно создать один виртуальный корень и рассматривать структуру как дерево.

Глубина узла (depth) показывает количество переходов от корня до него. Если считать глубину корня равной `0`, высота дерева (height) — максимальная глубина его узлов.

Эти характеристики важны для рекурсии и памяти DFS: очень глубокое дерево может переполнить call stack, а очень широкое дерево может потребовать большую очередь для BFS.

Дерево отличается от общего графа тем, что оно связно, не содержит циклов и между любыми двумя узлами существует единственный путь. В корневом дереве у каждого узла, кроме корня, один родитель.

В графе узел может иметь несколько входящих связей, а связи могут образовывать циклы.

Во frontend деревья встречаются в разных формах. DOM представляет иерархию узлов документа: элементов, текстовых узлов и других типов. Конфигурация маршрутов (route config) описывает вложенные маршруты. Меню, категории и комментарии хранят отношения родительских и дочерних элементов.

React также строит внутреннее дерево работы, но оно не тождественно DOM: один React-компонент может вернуть несколько DOM-узлов, вернуть `null` или отрисовать содержимое через portal в другую часть DOM.

Данные дерева можно хранить вложенно или плоско.

Во вложенной форме каждый узел содержит `children`; её удобно рекурсивно отображать и передавать как готовую ветку.

В плоской форме сущности хранятся по `id`, а связь задаётся через `parentId` или отдельные списки дочерних `id`. Такая нормализованная структура удобнее для частого доступа и обновления отдельных сущностей.

Типичный полный обход дерева имеет временную сложность `O(n)`, потому что в худшем случае посещается каждый из `n` узлов.

Поиск одного узла по `id` тоже остаётся `O(n)`, если каждый раз начинать обход от корня. Индекс `Map<id, node>` требует типично `O(n)` времени и памяти при построении, но ускоряет повторный доступ по `id` до ожидаемого `O(1)`.

Для быстрого получения детей можно дополнительно построить индекс `Map<parentId, child[]>`. Индексы являются производными структурами и должны обновляться вместе с исходными данными.

При иммутабельном обновлении вложенного дерева создают новые объекты для изменённого узла и его предков до корня. Вместе с ними обычно создаются новые массивы `children` на изменённом пути. Остальные ветки переиспользуют прежние ссылки.

Такой подход называется переиспользованием структуры (structural sharing): он сохраняет неизменяемость данных без глубокого копирования всего дерева и помогает React или Redux определять изменившиеся ветки по ссылкам.

Если путь к узлу уже известен, количество новых узлов обычно связано с высотой пути `h`. Но поиск этого пути без индекса может потребовать полного обхода `O(n)`, а объём копируемых массивов зависит от количества детей у узлов на пути.

Выбор представления зависит от операций. Вложенная форма удобна для последовательной отрисовки (render) дерева.

Индексы по `id`, `parentId` и дочерним узлам полезны, если часто нужно искать узлы, строить хлебные крошки (breadcrumbs), проверять предков или обновлять отдельные элементы.

За быстрый доступ приходится платить дополнительной памятью и необходимостью синхронизировать индексы после изменений.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем дерево отличается от графа и почему это влияет на обход?</strong></summary>

<dl>
<dd>
<h2></h2>

Дерево является частным случаем графа: оно связно, не содержит циклов, а между двумя узлами существует единственный путь.

Поэтому при движении от корня по дочерним узлам корректного дерева отдельное множество `visited` обычно не требуется.

В общем графе возможны циклы и несколько путей к одной вершине. Там `visited` предотвращает бесконечный обход и повторную обработку.

Если frontend-данные называют деревом, но они содержат ссылки между ветками, циклы или повторно используют один узел как ребёнка разных родителей, их безопаснее рассматривать как граф.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда хранить дерево через <code>children</code>, а когда через <code>id</code> и <code>parentId</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Вложенная форма удобна, когда данные приходят готовой иерархией, преимущественно читаются целой веткой и рекурсивно отображаются.

Переход к детям выполняется напрямую, но поиск или обновление произвольного узла требует обхода, если отдельного индекса нет.

Плоская нормализованная форма удобна при частых обновлениях и доступе по `id`. Она уменьшает дублирование сущностей и позволяет индексировать связи.

Однако для отрисовки иерархии приходится получать детей по `parentId` или заранее строить индекс:

```ts
Map<parentId, child[]>
```

Нередко используют обе формы: нормализованные сущности как источник истины и производный список видимых узлов для отображения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как обновить узел во вложенном дереве без мутации всего дерева?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала находят путь от корня до нужного узла.

Сам узел заменяют новым объектом, затем создают новые копии его родителя, родителя родителя и так далее до корня. На каждом уровне также создают новый массив `children`, содержащий новую ссылку на изменённую ветку.

Ветки, которые не лежат на пути к изменению, сохраняют прежние ссылки.

Если путь уже известен и дерево имеет небольшое количество детей на каждом уровне, количество новых объектов связано с высотой `h`.

Однако поиск пути без индекса может потребовать `O(n)` времени. Кроме того, копирование массивов `children` зависит от ширины узлов на пути и не всегда ограничивается только `O(h)` операциями.

Полное глубокое копирование дерева было бы дороже и уничтожило бы полезное равенство ссылок неизменённых веток.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое преобразование дерева в плоский список (flatten tree) и зачем сохранять <code>depth</code> и <code>parentId</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Flatten tree, или преобразование дерева в плоский список, создаёт массив в выбранном порядке обхода.

Каждый узел можно дополнить глубиной и идентификатором родителя. Это позволяет отобразить иерархию обычным списком, вычислить отступ, сохранить связь с родителем и применять виртуализацию списка (virtualization), при которой отрисовываются только видимые строки.

Полное преобразование требует `O(n)` времени и `O(n)` памяти под результат.

Если интерфейс показывает только раскрытые ветки, в список добавляют детей только раскрытых узлов, чтобы скрытая часть дерева не участвовала в отрисовке.

Полученный список является производным представлением и должен пересчитываться или обновляться при изменении структуры и состояния раскрытых узлов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как эффективно строить breadcrumbs (хлебные крошки) или список предков узла?</strong></summary>

<dl>
<dd>
<h2></h2>

Если у каждого узла доступен `parentId`, начинают с выбранного узла и поднимаются к корню.

При индексе `Map<id, node>` путь длиной `h` строится за `O(h)`. Результат разворачивают, чтобы получить порядок от корня к текущему узлу.

Если хранится только вложенное дерево без ссылок на родителей, путь приходится искать обходом от корня, что в худшем случае требует `O(n)`.

Поэтому индекс родителей полезен, когда breadcrumbs и проверки предков выполняются часто.

При подъёме по `parentId` также нужна защита от некорректных циклических данных, если источник данных не считается полностью доверенным.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как построить дерево из плоского массива с <code>id</code> и <code>parentId</code> за <code>O(n)</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала одним проходом создают `Map<id, node>` и для каждого узла подготавливают пустой `children`.

Вторым проходом узел без `parentId` добавляют в список корней, а остальные находят родителя через `Map.get(parentId)` и добавляют в его `children`.

Каждый узел обрабатывается постоянное число раз, поэтому типичные время и дополнительная память составляют `O(n)`.

Если корень один, результат является деревом. Если корней несколько, результат представляет лес.

Важно заранее определить поведение для:

- повторяющихся `id`;
- отсутствующего родителя;
- нескольких корней;
- ссылки узла на самого себя;
- более длинных циклов.

При повторяющемся `id` обычная запись в `Map` перезапишет предыдущую, поэтому дубликаты нужно обнаруживать явно.

Без индекса поиск родителя через `find()` для каждого узла дал бы `O(n²)`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить, что данные действительно образуют корректное дерево?</strong></summary>

<dl>
<dd>
<h2></h2>

Проверяют уникальность `id`, существование каждого `parentId`, допустимое число корней и отсутствие циклов.

Отсутствующий родитель создаёт orphan node, то есть узел без доступного предка. Несколько корней образуют лес, если это разрешено контрактом данных.

Цикл означает, что структура уже является некорректным деревом и рекурсивный обход без защиты не завершится.

Циклы можно обнаружить DFS с тремя состояниями:

- вершина ещё не посещена;
- вершина находится в текущем пути;
- вершина полностью обработана.

Переход в вершину текущего пути указывает на цикл.

Проверка занимает `O(V + E)` времени. При модели, где у каждого узла не более одного `parentId`, количество рёбер линейно числу узлов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем DOM tree, React tree и accessibility tree отличаются друг от друга?</strong></summary>

<dl>
<dd>
<h2></h2>

DOM tree состоит из узлов документа, которыми управляют браузерные DOM API. Кроме элементов, в него могут входить текстовые узлы, комментарии и другие типы узлов.

React tree описывает компоненты и элементы React. Компонент может не создать отдельный DOM-узел, вернуть несколько узлов, вернуть `null` или отрисовать содержимое через portal в другую часть DOM.

Accessibility tree браузер строит для вспомогательных технологий на основе DOM, нативной семантики, ARIA, состояний и CSS.

Не каждый DOM-узел попадает в accessibility tree, а некоторые элементы получают вычисленные роли, имена и состояния.

Поэтому структура React-компонентов, итоговый DOM и доступное представление интерфейса связаны, но не совпадают.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

Преобразовать вложенное дерево в плоский список, сохранив глубину и `parentId`:

```ts
function flattenTree(
  nodes: TreeNode[],
  depth = 0,
  parentId: string | null = null,
  result: FlatNode[] = [],
) {
  for (const node of nodes) {
    const { children = [], ...data } = node;

    result.push({
      ...data,
      depth,
      parentId,
    });

    flattenTree(children, depth + 1, node.id, result);
  }

  return result;
}
```

Функция использует preorder DFS: сначала добавляет текущий узел, затем обходит его детей.

Предполагается, что входные данные являются корректным деревом или лесом без циклов.

Каждый узел добавляется один раз, поэтому время — `O(n)`.

Результат занимает `O(n)` памяти, а рекурсивный call stack — `O(h)`, где `h` обозначает максимальную глубину дерева.

При непредсказуемо большой глубине рекурсивную реализацию заменяют итеративным DFS с собственным стеком.

## Где это встречается во frontend

| Структура | Типичная операция |
| --- | --- |
| DOM | поиск и обход элементов, определение отношений между узлами |
| Конфигурация маршрутов | построение вложенной навигации и breadcrumbs |
| Комментарии | рекурсивная отрисовка, сворачивание и обновление ветки |
| Боковое меню (sidebar) | хранение раскрытых `id` и плоского списка только видимых узлов |
| Категории товаров | построение дерева или леса из плоского списка с `parentId` |
| Дерево доступности (accessibility tree) | проверка того, какую семантическую структуру получают вспомогательные технологии |
