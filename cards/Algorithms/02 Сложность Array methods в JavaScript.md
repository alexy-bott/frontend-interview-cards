## Вопрос

<br>

 💬 **Какая сложность у популярных методов массива (Array methods) в JavaScript и почему это важно во frontend?**

<h2></h2>

<br>
<dl>
<dd>

Сложность метода зависит от того, сколько элементов он должен обработать, переместить или скопировать. Если метод проходит весь массив длиной `n`, его временная сложность обычно `O(n)`. Если он обращается к известному индексу или работает с концом массива, операция обычно близка к `O(1)`.

Стандарт ECMAScript описывает поведение методов, но не закрепляет для каждого из них конкретную Big O. Поэтому оценки ниже относятся к типичным реализациям JavaScript-массивов в современных движках. Внутреннее представление разреженного массива или массива со смешанными типами может отличаться, но для собеседования обычно используют стандартную модель динамического массива.

| Операция | Типичная временная сложность | Почему |
| --- | --- | --- |
| чтение или запись по индексу | `O(1)` | индекс известен заранее |
| `at()` | `O(1)` | вычисляется один индекс, в том числе относительно конца массива |
| `push()` | амортизированно `O(1)` | работа идёт с концом массива; редкое расширение хранилища может быть дороже |
| `pop()` | `O(1)` | удаляется последний элемент без сдвига остальных |
| `shift()`, `unshift()` | `O(n)` | элементы после начала массива приходится перемещать или переиндексировать |
| `map()`, `filter()`, `forEach()`, `reduce()` | `O(n)` | метод обрабатывает каждый элемент |
| `find()`, `findLast()`, `some()`, `every()`, `includes()`, `indexOf()` | в лучшем случае `O(1)`, в худшем `O(n)` | метод может остановиться раньше, но иногда проходит весь массив |
| `slice()` | `O(k)` | копируются `k` выбранных элементов |
| `concat()` и spread `[...items]` | `O(n)` или `O(n + m)` | элементы копируются в новый массив |
| `splice()` | до `O(n)` | после вставки или удаления элементы могут сдвигаться |
| `reverse()` | `O(n)` | элементы попарно меняются местами; исходный массив изменяется |
| `toReversed()`, `with()` | `O(n)` | создаётся новый массив той же длины |
| `toSpliced()` | `O(n + k)` | копируется исходный массив и добавляются `k` новых элементов |
| `sort()` | часто `O(n log n)` | точная сложность и алгоритм зависят от JavaScript-движка |

Временная сложность не показывает расход памяти. `map()`, `filter()`, `slice()`, `concat()` и spread создают новые массивы, поэтому им нужна память под результат. `forEach()` сам по себе новый массив не создаёт. `reduce()` может работать с `O(1)` вспомогательной памятью, если аккумулятором служит число, но потребует больше памяти, если внутри строится новая коллекция.

Методы с ранней остановкой нужно оценивать для конкретного сценария. `find()` имеет `O(1)` в лучшем случае (best-case), если совпал первый элемент, и `O(n)` в худшем (worst-case), если совпадение находится в конце или отсутствует. При оценке нужно явно указывать рассматриваемый сценарий.

Последовательные методы не перемножаются автоматически. Цепочка `filter().map()` выполняет два прохода и имеет `O(n) + O(k)`, где `k` - количество элементов после фильтрации. В худшем случае `k = n`, поэтому общая временная сложность остаётся `O(n)`, но создаются промежуточный и результирующий массивы. Если внутри `map()` запускается `find()` по другой коллекции, появляется вложенный поиск `O(n * m)`.

Во frontend имеет значение не только сложность одного вызова, но и частота его выполнения. Линейный проход по небольшому массиву обычно незаметен. Тот же проход по тысячам элементов при каждом render (расчёте следующего представления компонента) или каждом введённом символе может занять main thread (основной поток браузера) и задержать обновление интерфейса.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему <code>push()</code> обычно дешевле <code>shift()</code> и что означает амортизированная сложность?</strong></summary>

<dl>
<dd>
<h2></h2>

`push()` добавляет элемент в конец массива, поэтому существующие элементы обычно не нужно перемещать. Иногда внутреннего места недостаточно и движок расширяет хранилище с копированием элементов. Отдельная такая операция может стоить `O(n)`, но она происходит редко, поэтому средняя стоимость длинной последовательности добавлений считается амортизированно `O(1)`.

`shift()` удаляет первый элемент. Оставшиеся элементы обычно приходится сдвинуть или переиндексировать, поэтому типичная стоимость зависит от длины массива и оценивается как `O(n)`. Если постоянно нужно добавлять и удалять элементы с начала, обычный массив может быть неподходящей очередью.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему у <code>find()</code>, <code>some()</code>, <code>every()</code> и <code>includes()</code> может быть разная сложность в лучшем и худшем случае?</strong></summary>

<dl>
<dd>
<h2></h2>

Эти методы завершаются, как только результат уже известен. `find()` и `includes()` останавливаются после совпадения, `some()` - после первого `true`, `every()` - после первого `false`. Если нужный результат определяется первым элементом, достаточно одной проверки и получается `O(1)`.

Если подходящий элемент находится в конце или условие не позволяет остановиться раньше, метод проверяет весь массив и получает `O(n)`. Поэтому без уточнения входных данных обычно называют worst-case `O(n)`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Цепочка из нескольких методов массива всегда имеет <code>O(n²)</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Последовательные полные проходы складываются. Например, `filter().map()` даёт `O(n) + O(k)`, что в худшем случае упрощается до `O(n)`. При этом остаётся практическая цена нескольких проходов и выделения памяти под промежуточные массивы.

Квадратичная или составная сложность появляется, когда один проход вложен в другой. Например, `users.map(user => roles.find(...))` выполняет до `m` проверок для каждого из `n` пользователей и имеет `O(n * m)`. Если обе коллекции имеют размер `n`, это частный случай `O(n²)`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как уменьшить сложность повторного <code>find()</code> внутри <code>map()</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

По коллекции, в которой постоянно ищут по `id`, можно один раз построить индекс `Map<id, entity>`. Построение индекса требует `O(m)` времени и `O(m)` дополнительной памяти. После этого `Map.get()` в типичном случае даёт доступ за `O(1)`.

Обработка `n` элементов вместо `O(n * m)` становится `O(n + m)`: один проход для индекса и один проход по основной коллекции. Индекс выгоден при множественных поисках, но для одного поиска в маленьком массиве обычный `find()` может быть проще и не требовать дополнительной памяти.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>reduce()</code> не всегда имеет только <code>O(n)</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Сам `reduce()` вызывает callback один раз для каждого элемента, но итоговая сложность включает работу внутри callback. Если на каждой итерации копировать растущий аккумулятор, стоимость копий складывается.

В выражении `items.reduce((acc, item) => [...acc, item], [])` сначала копируется 0 элементов, затем 1, 2 и так далее до `n - 1`. Сумма равна `O(n²)`. Для обычного построения массива дешевле создать один аккумулятор и добавлять в него через `push()`, если локальная мутация создаваемого результата допустима.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>toSorted()</code>, <code>toReversed()</code>, <code>toSpliced()</code> и <code>with()</code> отличаются от старых методов?</strong></summary>

<dl>
<dd>
<h2></h2>

Эти методы возвращают изменённую копию и не меняют исходный массив. `toSorted()` соответствует сортировке копии, `toReversed()` - развороту копии, `toSpliced()` - копирующему варианту `splice()`, а `with(index, value)` возвращает копию с заменённым элементом.

Они вошли в ECMAScript 2023. Каждый метод должен создать новый массив, поэтому для результата требуется память, пропорциональная его длине. Перед использованием проверяют поддержку целевых окружений или наличие polyfill, то есть кода, добавляющего отсутствующий API. TypeScript `lib` влияет только на доступность типов, а не добавляет метод во время выполнения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как стоимость callback влияет на сложность метода массива?</strong></summary>

<dl>
<dd>
<h2></h2>

Если метод вызывает callback-функцию, то есть переданную функцию обратного вызова, `n` раз, её работу тоже включают в оценку. Например, `map()` с `find()` по второй коллекции размера `m` имеет `O(n * m)`, а сортировка с линейным поиском внутри comparator (функции сравнения) может быть значительно дороже обычного `O(n log n)`.

Одна строка вызова не считается `O(1)` автоматически. Нужно раскрывать сложность всех функций, которые выполняются внутри цикла или стандартного метода.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```ts
const rows = users.map(user => ({
  ...user,
  role: roles.find(role => role.id === user.roleId),
}));
```

Пусть `n` - количество пользователей, а `m` - количество ролей. `map()` выполняется `n` раз, а каждый `find()` в худшем случае просматривает `m` ролей. Временная сложность - `O(n * m)`.

После построения `const rolesById = new Map(roles.map(role => [role.id, role]))` индекс создаётся за `O(m)`, а связывание пользователей с ролями выполняется за `O(n)`. Общая временная сложность становится `O(n + m)`, дополнительная память для индекса - `O(m)`.

## Где это встречается во frontend

| Ситуация | Что важно |
| --- | --- |
| Связывание строк таблицы со справочником | повторный `find()` внутри `map()` заменяют индексом по `id` |
| Фильтрация при вводе | `filter()` вызывается на каждый символ; учитываются размер списка и частота вызова |
| React render | повторные `map()`, `filter()` и `sort()` могут пересчитывать большой список при каждом обновлении компонента |
| Проверка выбранных элементов | множество повторных `includes()` может быть заменено на `Set.has()` |
| Иммутабельное обновление | spread, `slice()` и `map()` создают копии и требуют времени и памяти |
| Сортировка | `sort()` изменяет исходный массив; `toSorted()` возвращает новый массив |
