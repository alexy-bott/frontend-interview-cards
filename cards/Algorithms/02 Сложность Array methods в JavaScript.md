## Вопрос

<br>

 💬 **Какая сложность у популярных методов массива (Array methods) в JavaScript и почему это важно во frontend?**

<h2></h2>

<br>
<dl>
<dd>

Сложность метода зависит от того, сколько элементов он должен обработать, переместить или скопировать. Если метод проходит весь массив длиной `n`, его временная сложность обычно `O(n)`. Если он обращается к известному индексу или работает с концом массива, операция обычно близка к `O(1)`.

Стандарт ECMAScript описывает поведение методов, но не закрепляет для каждого из них конкретную Big O. Поэтому оценки ниже относятся к типичным реализациям JavaScript-массивов в современных движках. Внутреннее представление разреженного массива или массива со смешанными типами может отличаться, но для собеседования обычно используют стандартную модель динамического массива.

В таблице:

- `n` — длина исходного массива;
- `m` — длина второй независимой коллекции;
- `k` — количество копируемых, вставляемых или полученных элементов.

Для методов с callback предполагается, что один вызов callback выполняется за `O(1)`. Если внутри него есть поиск, копирование или другой проход, его стоимость также включают в общую оценку.

| Операция | Типичная временная сложность | Почему |
| --- | --- | --- |
| чтение или запись по индексу | `O(1)` | индекс известен заранее |
| `at()` | `O(1)` | вычисляется один индекс, в том числе относительно конца массива |
| `push()` | амортизированно `O(1)` | работа идёт с концом массива; редкое расширение хранилища может быть дороже |
| `pop()` | `O(1)` | удаляется последний элемент без сдвига остальных |
| `shift()`, `unshift()` | `O(n)` | элементы после начала массива приходится перемещать или переиндексировать |
| `map()`, `filter()`, `forEach()`, `reduce()` | `O(n)` при callback `O(1)` | callback вызывается не более одного раза для каждого обрабатываемого элемента |
| `find()`, `findLast()`, `some()`, `every()`, `includes()`, `indexOf()` | best-case `O(1)`, worst-case `O(n)` | метод может остановиться раньше, но иногда проходит весь массив |
| `slice()` | `O(k)` | в новый массив копируются `k` выбранных элементов |
| `concat()` | `O(n + m)` | элементы исходных массивов копируются в новый массив |
| spread `[...items]` | `O(n)` | элементы копируются в новый массив |
| spread `[...first, ...second]` | `O(n + m)` | копируются элементы обеих коллекций |
| `splice()` | до `O(n + k)` | элементы могут сдвигаться, вставляться, а удалённые значения копируются в результат |
| `reverse()` | `O(n)` | элементы попарно меняются местами; исходный массив изменяется |
| `toReversed()`, `with()` | `O(n)` | создаётся новый массив той же длины |
| `toSpliced()` | `O(n + k)` | создаётся новый массив с копированием исходных и вставляемых элементов |
| `sort()` | часто `O(n log n)` | точные алгоритм, время и вспомогательная память зависят от JavaScript-движка |
| `toSorted()` | часто `O(n log n)` | сначала создаётся новый массив, затем его элементы сортируются |

Временная сложность не показывает расход памяти.

`map()` создаёт результат длиной `n`, поэтому требует `O(n)` памяти под новый массив. `filter()` создаёт массив длиной `k`, поэтому результат занимает `O(k)`. `slice()`, `concat()`, spread, `toReversed()`, `toSorted()`, `toSpliced()` и `with()` также выделяют память под новый массив.

Это поверхностное копирование: новый массив содержит те же ссылки на вложенные объекты, а не глубокие копии самих объектов.

`forEach()` сам по себе новый массив не создаёт. `reduce()` может работать с `O(1)` вспомогательной памятью, если аккумулятором служит число, но потребует больше памяти, если внутри строится новая коллекция.

`splice()` изменяет исходный массив, но одновременно возвращает новый массив удалённых элементов, поэтому при удалении `k` элементов результат требует `O(k)` памяти.

Методы с ранней остановкой нужно оценивать для конкретного сценария. `find()` имеет `O(1)` в лучшем случае, если совпал первый проверяемый элемент, и `O(n)` в худшем, если совпадение находится в конце или отсутствует.

`findLast()` работает в обратном направлении: лучший случай возникает, если подходит последний элемент массива.

При оценке нужно явно указывать рассматриваемый сценарий.

Последовательные методы не перемножаются автоматически. Цепочка `filter().map()` выполняет два прохода и имеет `O(n) + O(k)`, где `k` — количество элементов после фильтрации. Поскольку `k ≤ n`, в худшем случае общая временная сложность упрощается до `O(n)`.

При этом создаются промежуточный и результирующий массивы, поэтому несколько линейных проходов могут отличаться по реальному времени и расходу памяти от одного прохода.

Если внутри `map()` запускается `find()` по другой коллекции, появляется вложенный поиск `O(n * m)`.

Для `sort()` и `toSorted()` нужно учитывать стоимость функции сравнения. Если comparator вызывается порядка `n log n` раз, а один его вызов выполняет линейный поиск по коллекции размера `m`, общая типичная оценка может стать `O(n log n * m)`.

ECMAScript требует стабильного результата сортировки: элементы, которые comparator считает равными, сохраняют взаимный порядок. При этом стандарт не закрепляет конкретный алгоритм сортировки и его Big O.

Во frontend имеет значение не только сложность одного вызова, но и частота его выполнения. Линейный проход по небольшому массиву обычно незаметен.

Тот же проход по тысячам элементов при каждом render — расчёте следующего представления компонента — или каждом введённом символе может занять main thread — основной поток браузера — и задержать обновление интерфейса.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему <code>push()</code> обычно дешевле <code>shift()</code> и что означает амортизированная сложность?</strong></summary>

<dl>
<dd>
<h2></h2>

`push()` добавляет элемент в конец массива, поэтому существующие элементы обычно не нужно перемещать.

Иногда внутреннего места недостаточно и движок расширяет хранилище с копированием элементов. Отдельная такая операция может стоить `O(n)`, но она происходит редко, поэтому средняя стоимость длинной последовательности добавлений считается амортизированно `O(1)`.

`shift()` удаляет первый элемент. Оставшиеся элементы обычно приходится перемещать или переиндексировать, поэтому типичная стоимость зависит от длины массива и оценивается как `O(n)`.

Если постоянно нужно добавлять и удалять элементы с начала, обычный массив может быть неподходящей реализацией очереди.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему у <code>find()</code>, <code>some()</code>, <code>every()</code> и <code>includes()</code> может быть разная сложность в лучшем и худшем случае?</strong></summary>

<dl>
<dd>
<h2></h2>

Эти методы завершаются, как только результат уже известен.

`find()` и `includes()` останавливаются после совпадения, `some()` — после первого `true`, `every()` — после первого `false`.

Если нужный результат определяется первым проверяемым элементом, достаточно одной проверки и получается `O(1)`.

Если подходящий элемент находится в конце или условие не позволяет остановиться раньше, метод проверяет весь массив и получает `O(n)`.

Поэтому без уточнения входных данных обычно называют worst-case `O(n)`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Цепочка из нескольких методов массива всегда имеет <code>O(n²)</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Последовательные полные проходы складываются.

Например, `filter().map()` даёт `O(n) + O(k)`, что в худшем случае упрощается до `O(n)`, поскольку количество отфильтрованных элементов `k` не превышает `n`.

При этом остаётся практическая цена нескольких проходов и выделения памяти под промежуточные массивы.

Квадратичная или составная сложность появляется, когда один проход выполняется внутри другого.

Например, `users.map(user => roles.find(...))` выполняет до `m` проверок для каждого из `n` пользователей и имеет `O(n * m)`. Если обе коллекции имеют размер `n`, это частный случай `O(n²)`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как уменьшить сложность повторного <code>find()</code> внутри <code>map()</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

По коллекции, в которой постоянно ищут по `id`, можно один раз построить индекс `Map<id, entity>`.

Построение индекса в типичной реализации требует `O(m)` времени и `O(m)` дополнительной памяти. После этого `Map.get()` обычно даёт доступ за `O(1)`.

Обработка `n` элементов вместо `O(n * m)` становится `O(n + m)`: один проход для построения индекса и один проход по основной коллекции.

Индекс выгоден при множественных поисках, но для одного поиска в маленьком массиве обычный `find()` может быть проще и не требовать дополнительной структуры.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>reduce()</code> не всегда имеет только <code>O(n)</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Сам `reduce()` вызывает callback не более одного раза для каждого элемента, но итоговая сложность включает работу внутри callback.

Если на каждой итерации копировать растущий аккумулятор, стоимость копий складывается.

В выражении:

```ts
items.reduce((acc, item) => [...acc, item], []);
```

сначала копируется 0 элементов, затем 1, 2 и так далее до `n - 1`. Суммарная временная сложность получается `O(n²)`.

Кроме того, на каждой итерации создаётся новый промежуточный массив, что увеличивает объём выделений памяти.

Для линейного построения массива можно создать один локальный аккумулятор и добавлять элементы через `push()`, если такая локальная мутация создаваемого результата допустима.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>toSorted()</code>, <code>toReversed()</code>, <code>toSpliced()</code> и <code>with()</code> отличаются от старых методов?</strong></summary>

<dl>
<dd>
<h2></h2>

Эти методы возвращают изменённую копию и не меняют исходный массив.

`toSorted()` соответствует сортировке копии, `toReversed()` — развороту копии, `toSpliced()` — копирующему варианту `splice()`, а `with(index, value)` возвращает копию с заменённым элементом.

Они вошли в ECMAScript 2023. Каждый метод создаёт новый массив, поэтому для результата требуется память, пропорциональная его длине.

Копирование остаётся поверхностным: ссылки на вложенные объекты сохраняются.

Перед использованием проверяют поддержку целевых окружений или наличие polyfill — кода, добавляющего отсутствующий API. TypeScript `lib` влияет только на доступность типов и не добавляет метод во время выполнения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как стоимость callback влияет на сложность метода массива?</strong></summary>

<dl>
<dd>
<h2></h2>

Если метод вызывает callback `n` раз, работу callback тоже включают в оценку.

Например, `map()` с `find()` по второй коллекции размера `m` имеет `O(n * m)`.

Для сортировки число вызовов comparator в типичной эффективной реализации имеет порядок `O(n log n)`. Если каждый comparator выполняет операцию стоимостью `C`, общую оценку можно записать как `O(n log n * C)`.

Comparator должен быть чистым, согласованным и не выполнять дорогую работу без необходимости. Часто вычисляемые значения выгоднее подготовить заранее, а не пересчитывать при каждом сравнении.

Одна строка вызова не считается `O(1)` автоматически. Нужно раскрывать сложность всех функций, выполняемых внутри прохода или стандартного метода.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```ts
const rows = users.map(user => ({
  ...user,
  role: roles.find(role => role.id === user.roleId),
}));
```

Пусть `n` — количество пользователей, а `m` — количество ролей.

`map()` выполняется `n` раз, а каждый `find()` в худшем случае просматривает `m` ролей. Временная сложность — `O(n * m)`.

После построения индекса:

```ts
const rolesById = new Map(
  roles.map(role => [role.id, role]),
);

const rows = users.map(user => ({
  ...user,
  role: rolesById.get(user.roleId),
}));
```

Индекс в типичной реализации создаётся за `O(m)`, а связывание пользователей с ролями выполняется за `O(n)`.

Общая ожидаемая временная сложность становится `O(n + m)`, дополнительная память для индекса — `O(m)`, а память под результирующий массив — `O(n)`.

ECMAScript не закрепляет конкретную внутреннюю структуру `Map`, поэтому `O(1)` для `get()` является типичной инженерной оценкой современных реализаций, а не требованием использовать конкретный алгоритм хранения.

## Где это встречается во frontend

| Ситуация | Что важно |
| --- | --- |
| Связывание строк таблицы со справочником | повторный `find()` внутри `map()` заменяют индексом по `id` |
| Фильтрация при вводе | `filter()` вызывается на каждый символ; учитываются размер списка и частота вызова |
| React render | повторные `map()`, `filter()` и `sort()` могут пересчитывать большой список при каждом обновлении компонента |
| Проверка выбранных элементов | множество повторных `includes()` может быть заменено на `Set.has()` |
| Иммутабельное обновление | spread, `slice()`, `map()` и копирующие методы требуют времени и памяти под новые массивы |
| Сортировка | `sort()` изменяет исходный массив; `toSorted()` возвращает новый массив |
