## Вопрос

<br>

 💬 **Какие типовые алгоритмические задачи встречаются во frontend и как оценивать их сложность?**

<h2></h2>

<br>
<dl>
<dd>

Во frontend алгоритмические задачи часто выглядят как обычная подготовка данных для пользовательского интерфейса (UI): удалить дубликаты, сгруппировать элементы, связать две коллекции по `id`, построить дерево, найти выбранные строки, отфильтровать и отсортировать таблицу.

Для оценки сначала определяют размеры входных данных и частоту выполнения операции. Затем считают временную сложность, вспомогательную память, память результата и стоимость взаимодействия с UI.

Полезно начинать с простого корректного решения. После этого находят повторную работу: вложенный поиск, многократный обход одной коллекции, пересоздание индекса или полную обработку данных при каждом вводе.

Оптимизация оправдана, когда размер данных и частота выполнения делают эту работу заметной.

| Задача | Прямое решение | Возможное улучшение | Сложность и цена |
| --- | --- | --- | --- |
| удалить дубликаты примитивов | `Array.from(new Set(items))` | обычно уже достаточно | типично `O(n)` времени и `O(n)` памяти; сохраняется порядок первого появления |
| удалить дубликаты объектов по `id` | пройти массив и хранить встреченные `id` в `Set` | `Map<id, item>`, если нужен последний объект для каждого `id` | типично `O(n)` времени и `O(n)` памяти |
| связать users и roles | для каждого user вызвать `roles.find()` | заранее построить `Map<roleId, role>` | от `O(n * m)` к типичному `O(n + m)`, но добавляется `O(m)` памяти |
| сгруппировать элементы | один проход с `Map` или объектом групп | дальнейший индекс обычно не нужен | типично `O(n)` времени; результат хранит `O(n)` элементов |
| проверить выбранные строки | `selectedIds.includes(id)` для каждой строки | один раз построить `Set` | от `O(n * s)` к типичному `O(n + s)` ценой `O(s)` памяти |
| построить дерево из `id` и `parentId` | для каждого узла искать родителя во всём массиве | индекс узлов по `id`, затем один проход по связям | от `O(n²)` к типичному `O(n)` с дополнительной памятью `O(n)` |
| отфильтровать и отсортировать таблицу | `filter().sort()` | не повторять без изменения данных или критерия | `O(n + k log k)`, где `k` — число элементов после фильтрации; worst-case `O(n log n)` |

Оценки доступа к `Map` и `Set` обычно считают близкими к `O(1)`, но ECMAScript не закрепляет конкретную внутреннюю структуру. Это типичная инженерная оценка современных JavaScript-движков.

Сложность одной операции не описывает всю пользовательскую стоимость. `O(n)` при загрузке 100 элементов и `O(n)` при каждом введённом символе для 100 000 элементов — разные ситуации.

Нужно учитывать, выполняется ли работа:

- один раз при загрузке;
- при каждом render — расчёте представления компонента;
- при каждом изменении input;
- во время scroll;
- для каждого элемента другой коллекции.

Например, один линейный проход требует `O(n)`. Если он выполняется для каждого из `q` изменений строки поиска, суммарная работа может достигать `O(q * n)`.

Debounce — отложенный запуск после паузы во вводе — не меняет сложность одного поиска. Каждый выполненный поиск по-прежнему может требовать `O(n)`. Однако debounce уменьшает число запусков и поэтому может уменьшить суммарную работу за пользовательский сценарий.

Виртуализация списка уменьшает количество одновременно созданных DOM-элементов и стоимость render. Но если перед виртуализацией код полностью фильтрует или сортирует исходный массив, стоимость этой подготовки данных сохраняется.

Web Worker переносит вычисление с main thread — основного потока браузера — и помогает сохранить отзывчивость интерфейса. Сам алгоритм от этого не становится асимптотически быстрее.

Кроме вычислений нужно учитывать создание Worker, отправку сообщений и передачу данных. Обычные значения копируются через алгоритм structured clone, а transferable objects позволяют передать владение некоторыми буферами без полного копирования.

Запрос к backend переносит часть работы на сервер. Сервер может использовать индексы базы данных, фильтровать, сортировать и возвращать только нужную страницу результата.

При этом добавляются сеть, состояния загрузки и ошибок, отмена устаревших запросов, пагинация и необходимость согласовать правила фильтрации и сортировки между frontend и backend.

Поэтому решение оценивают по нескольким измерениям:

- размер и форма данных;
- частота операции;
- временная сложность;
- вспомогательная память и размер результата;
- место выполнения;
- объём работы с DOM;
- сложность поддержки кода.

`Map` или `Set` могут ускорить повторные поиски, но для маленьких данных и одного прохода простой массив часто остаётся лучшим решением.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Как удалить дубликаты примитивов и объектов?</strong></summary>

<dl>
<dd>
<h2></h2>

Для примитивов можно создать `Set`, потому что он хранит только уникальные значения, а затем преобразовать его обратно в массив.

Типичные время и дополнительная память составляют `O(n)`. Порядок первого появления значений сохраняется.

Для объектов сначала определяют критерий уникальности. Два разных объекта с одинаковыми полями не считаются одинаковыми по ссылке.

Если уникальность определяется через `id`, используют:

- `Set` встреченных `id`, чтобы сохранить первый объект;
- `Map<id, object>`, чтобы сохранить последнее значение для каждого `id`.

При повторном `map.set(id, object)` значение заменяется, но позиция ключа в порядке обхода остаётся связанной с его первым добавлением.

Поэтому нужно заранее определить:

- первый или последний объект должен остаться;
- требуется ли порядок первого появления `id`;
- требуется ли порядок последнего появления;
- что делать с отсутствующим или повторяющимся `id`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как сгруппировать элементы по полю и какая будет сложность?</strong></summary>

<dl>
<dd>
<h2></h2>

Массив проходят один раз. Для каждого элемента получают ключ группы, создают группу при первом появлении ключа и добавляют элемент в соответствующий массив.

Время составляет типично `O(n)`, если добавление и доступ к группе выполняются близко к `O(1)`.

Пусть `k` — количество групп. Структура групп содержит `k` ключей и суммарно `n` ссылок на элементы, поэтому память результата составляет `O(n + k)`, что при `k ≤ n` упрощается до `O(n)`.

Если результат группировки считается выходом алгоритма, его память отделяют от вспомогательной памяти, используемой только во время вычисления.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как эффективно связать две коллекции по <code>id</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Вложенный `find()` выполняет поиск по второй коллекции для каждого элемента первой.

Для размеров `n` и `m` worst-case составляет:

```text
O(n * m)
```

Одну коллекцию преобразуют в индекс `Map<id, entity>` за типичные `O(m)` времени и `O(m)` памяти.

Затем проходят вторую коллекцию за `O(n)` и получают связанные значения через `get()`. Общая ожидаемая временная сложность становится `O(n + m)`.

Также нужно определить поведение для:

- отсутствующего связанного `id`;
- дубликатов ключей;
- изменения исходной коллекции после построения индекса.

При повторяющемся ключе новая запись в обычном `Map<id, entity>` заменит предыдущую.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как оптимизировать поиск с подсказками (autocomplete) по большому локальному списку?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала оценивают тип поиска.

Проверка подстроки по всем `n` элементам обычно требует `O(n)` на один запрос. Если сравнение каждой строки зависит от её длины, стоимость точнее связана и с общим количеством проверяемых символов.

Debounce уменьшает число запусков во время быстрого ввода, но каждый состоявшийся поиск остаётся линейным.

Дополнительно можно:

- ограничить количество отображаемых результатов;
- заранее подготовить нормализованные строки;
- не повторять поиск для неизменного запроса;
- прервать обработку после получения достаточного числа результатов;
- виртуализировать отображение найденного списка.

Виртуализация уменьшает число DOM-узлов, но не отменяет сам поиск по исходным данным.

Для очень больших наборов вычисление переносят в Web Worker или на backend. Worker оставляет основной поток свободнее, а серверный поиск уменьшает объём локальных данных.

Оба варианта добавляют асинхронность, отмену устаревших операций и обработку ошибок.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие характеристики нужно проверить перед оптимизацией алгоритма?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно определить:

- размер и форму входа;
- несколько независимых размеров, например `n` и `m`;
- ожидаемый результат;
- допустимые дубликаты;
- отсутствующие значения;
- частоту выполнения;
- worst-case по времени;
- вспомогательную память;
- объём создаваемого результата.

После этого проверяют фактическое узкое место измерениями.

Проблема может находиться не в Big O, а в дорогом comparator, большом количестве выделений памяти, сборке мусора, работе с DOM, слишком частом render или передаче больших данных между main thread и Worker.

Оптимизация должна уменьшать измеримую стоимость, не создавая непропорционально сложный код.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Меняет ли мемоизация сложность алгоритма?</strong></summary>

<dl>
<dd>
<h2></h2>

Первое вычисление сохраняет исходную сложность, например `O(n)`.

Повторное обращение с уже сохранённым ключом может стать близким к `O(1)`, если поиск записи в кэше также выполняется за ожидаемое постоянное время.

Поэтому общая эффективность зависит от:

- доли повторяющихся запросов;
- стоимости создания и сравнения ключа;
- размера кэша;
- правил инвалидирования и очистки.

`useMemo` хранит результат последнего вычисления конкретного экземпляра компонента для текущего набора зависимостей. Оно является оптимизацией, а не семантической гарантией постоянного хранения результата.

При изменении зависимости вычисление выполняется заново. Для множества разных ключей нужен отдельный ограниченный кэш, иначе ускорение может привести к неограниченному росту памяти.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда Web Worker не улучшит или даже ухудшит ситуацию?</strong></summary>

<dl>
<dd>
<h2></h2>

Worker освобождает основной поток, но его создание, обмен сообщениями и передача данных имеют стоимость.

Для короткой операции накладные расходы могут быть больше самого вычисления.

Обычные данные передаются через structured clone. Большие значения приходится сериализовать и копировать, что также требует времени и памяти.

Некоторые данные можно передавать через transferable objects. В этом случае владение буфером переходит другой стороне без полного копирования, а исходная сторона больше не может использовать переданный буфер как раньше.

Worker:

- не имеет прямого доступа к DOM;
- не делает алгоритм асимптотически быстрее;
- добавляет асинхронный обмен сообщениями;
- требует обработки ошибок и устаревших задач.

Он полезен для достаточно тяжёлой независимой CPU-работы, результат которой можно получить асинхронно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда фильтрацию и сортировку переносить на backend?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда полный набор данных велик, уже находится на сервере или пользователь получает только страницу результата.

Сервер может использовать индексы базы данных и не отправлять клиенту все записи. Frontend передаёт параметры поиска, сортировки и пагинации, а backend возвращает ограниченный результат.

Это не бесплатная оптимизация. Появляются:

- задержка сети;
- состояния загрузки и ошибок;
- отмена устаревших запросов;
- пагинация;
- кэширование;
- необходимость согласовать порядок сортировки и правила фильтрации.

Например, frontend и backend должны одинаково трактовать регистр, локаль, `null` и направление сортировки.

Для небольшого уже загруженного списка локальная обработка часто проще и быстрее.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Что оценивается |
| --- | --- |
| `Select` с уникальными вариантами | способ удаления дубликатов и порядок результата |
| Таблица с фильтрами | размер данных, частота фильтрации, сортировка и промежуточные массивы |
| Список с флажками (checkbox) | повторные проверки выбранных `id` и польза `Set` |
| Связывание DTO | индекс по `id`, отсутствующие связи и дубликаты ключей |
| Дерево маршрутов | построение дерева, поиск пути и преобразование раскрытых веток в плоский список |
| Поиск с подсказками | стоимость одного поиска, debounce, отмена запросов и место выполнения |
