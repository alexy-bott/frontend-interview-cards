## Вопрос

<br>

 💬 **Чем отличаются линейный поиск (linear search), бинарный поиск (binary search) и поиск через индекс?**

<h2></h2>

<br>
<dl>
<dd>

Линейный поиск проверяет элементы по очереди, пока не найдёт нужный или не дойдёт до конца. В JavaScript так работают `find()`, `findIndex()` и `includes()`. В лучшем случае совпадение находится сразу и поиск занимает `O(1)`, в худшем требуется проверить все `n` элементов и получается `O(n)`.

Бинарный поиск работает с отсортированными данными. Он сравнивает искомое значение с элементом в середине диапазона и отбрасывает половину, в которой значения быть не может. Поэтому количество оставшихся элементов на каждом шаге уменьшается вдвое, а временная сложность составляет `O(log n)`.

Для бинарного поиска порядок должен соответствовать условию сравнения. Если массив отсортирован по `price`, искать товар по `name` через тот же порядок нельзя.

Также нужен быстрый доступ к элементу по позиции. JavaScript-массив это позволяет. В связном списке получение элемента в середине само требует прохода, поэтому бинарный поиск теряет логарифмическое преимущество.

Индекс — дополнительная структура, которая связывает ключ с нужным значением. Например, `Map<id, user>` позволяет получать пользователя по `id`, не просматривая весь массив.

Построение индекса по `n` элементам в типичной реализации требует `O(n)` времени и `O(n)` памяти, а дальнейший `Map.get()` обычно выполняется близко к `O(1)`. Ключ индекса должен однозначно определять значение: если несколько сущностей имеют одинаковый ключ, новая запись в `Map` перезапишет предыдущую.

| Подход | Подготовка | Один поиск | Дополнительная память | Основное условие |
| --- | --- | --- | --- | --- |
| линейный поиск | не нужна | worst-case `O(n)` | `O(1)` | подходит для любых данных |
| бинарный поиск | данные должны быть отсортированы | `O(log n)` | `O(1)` для итеративной реализации | порядок сортировки соответствует поиску |
| индекс через `Map` | типично `O(n)` | типично близко к `O(1)` | `O(n)` | индекс нужно хранить и синхронизировать с данными |

Рекурсивный бинарный поиск дополнительно использует стек вызовов глубиной `O(log n)`. Итеративная реализация обходится `O(1)` вспомогательной памяти.

Если поиск выполняется один раз, линейный проход часто дешевле подготовки структуры.

Если выполнить `q` поисков по массиву, линейный подход в худшем случае стоит `O(q * n)`. Для бинарного поиска по уже отсортированным данным стоимость будет `O(q log n)`.

Если сначала требуется сортировка, добавляется её цена, обычно `O(n log n)`. Поэтому сортировать неупорядоченный массив ради одного поиска обычно невыгодно.

Индекс даёт типичную общую стоимость `O(n + q)`, но требует дополнительной памяти.

Подготовленная структура остаётся полезной, только пока соответствует исходным данным. После добавления, удаления или изменения ключа индекс нужно обновить или построить заново.

Отсортированный массив тоже имеет цену поддержки. Позицию нового элемента можно найти бинарным поиском за `O(log n)`, но вставка в JavaScript-массив обычно потребует `O(n)` из-за сдвига последующих элементов. Альтернатива — добавить данные и позднее выполнить повторную сортировку.

Во frontend выбор зависит от размера данных и частоты операций. Один `find()` в маленьком списке обычно проще индекса. Повторный поиск роли для каждой строки большой таблицы уже создаёт вложенную работу, поэтому справочник ролей выгодно один раз преобразовать в индекс по `id`.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему бинарный поиск требует отсортированных данных?</strong></summary>

<dl>
<dd>
<h2></h2>

После сравнения с серединой алгоритм должен гарантированно решить, в какой половине может находиться значение.

Такая гарантия существует только при известном порядке. Если элементы не отсортированы по тому же критерию, меньшие и большие значения могут находиться с любой стороны, поэтому отбрасывать половину нельзя.

Сортировка и поиск должны использовать совместимое сравнение. Например, массив, отсортированный по возрастанию `price`, подходит для поиска по цене, но не для бинарного поиска по `id` или `name`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Сортировка и бинарный поиск всегда лучше линейного поиска?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Если неотсортированный массив нужно проверить один раз, линейный поиск требует `O(n)`, а предварительная сортировка обычно требует `O(n log n)` плюс сам поиск `O(log n)`.

В таком сценарии сортировка дороже.

Бинарный поиск выгоден, когда данные уже отсортированы по нужному критерию или по ним выполняется много поисков.

При частых изменениях нужно учитывать стоимость поддержания порядка. Поиск позиции вставки занимает `O(log n)`, но вставка элемента в середину JavaScript-массива обычно требует `O(n)` из-за сдвига остальных элементов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда стоит построить <code>Map</code>, а когда достаточно <code>find()</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`find()` подходит для небольшого массива, редкого поиска или кода, где простота важнее подготовки дополнительной структуры. Один линейный поиск не оправдывает автоматическое создание индекса.

`Map` полезен, когда одна и та же коллекция многократно ищется по стабильному уникальному ключу: при связывании сущностей, обработке большой таблицы, проверке выбранных строк или работе нормализованного хранилища состояния.

Индекс меняет повторную стоимость `O(q * n)` на типичную `O(n + q)`, но добавляет `O(n)` памяти и обязан обновляться вместе с данными.

Если ключи повторяются, обычный `Map<key, entity>` сохранит только последнее значение. Для группировки по неуникальному ключу используют, например, `Map<key, entity[]>`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где строить и хранить индекс в React-приложении?</strong></summary>

<dl>
<dd>
<h2></h2>

Индекс строят на уровне, где доступен весь набор данных и можно контролировать его обновление: при преобразовании ответа API, в мемоизированном selector, в `useMemo` или в нормализованном store.

Это позволяет переиспользовать одну структуру для множества обращений.

Строить `new Map(items.map(...))` внутри каждой строки списка бессмысленно: каждая строка повторит полную работу.

На уровне родительского компонента необходимость мемоизации зависит от размера массива, частоты render и стоимости построения. Для маленьких данных пересоздание может быть дешевле дополнительной сложности.

`useMemo` используют как оптимизацию вычисления при стабильной ссылке на исходный массив, а не как источник истины или гарантию постоянного хранения индекса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как реализовать бинарный поиск и не ошибиться в границах?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно явно выбрать интервал поиска и сохранять его смысл на каждой итерации.

В варианте с закрытым интервалом `[left, right]` цикл продолжается, пока `left <= right`. После сравнения середина исключается: используется `left = middle + 1` или `right = middle - 1`, иначе цикл может зависнуть.

```ts
function binarySearch(items: number[], target: number) {
  let left = 0;
  let right = items.length - 1;

  while (left <= right) {
    const middle = left + Math.floor((right - left) / 2);

    if (items[middle] === target) return middle;
    if (items[middle] < target) left = middle + 1;
    else right = middle - 1;
  }

  return -1;
}
```

Инвариант цикла: если искомое значение существует, оно может находиться только внутри текущего интервала.

На пустом массиве `right` равен `-1`, цикл не запускается и функция возвращает `-1`.

Временная сложность — `O(log n)`, вспомогательная память итеративной реализации — `O(1)`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что вернёт бинарный поиск, если в массиве есть дубликаты?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычная реализация вернёт любое найденное совпадение, а не обязательно первое или последнее.

Если нужен первый элемент, равный `target`, после совпадения поиск продолжают в левой половине и запоминают найденный индекс. Для последнего совпадения продолжают поиск справа.

Более общий вариант `lower bound` ищет первую позицию, где значение не меньше `target`. Он также даёт позицию вставки, которая сохраняет сортировку.

Контракт нужно назвать явно: «найти любое совпадение», «первое совпадение» и «позиция вставки» являются разными задачами.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит с индексом после изменения исходных данных?</strong></summary>

<dl>
<dd>
<h2></h2>

Индекс является производным представлением и должен обновляться вместе с основными данными.

После добавления сущности в массив, но не в `Map`, поиск через две структуры начнёт давать разные результаты. Изменение ключа требует удалить старую запись и добавить новую.

Если индекс хранится отдельно и изменяется на месте, добавление, удаление или обновление одной записи в типичной реализации может быть близко к `O(1)`.

Если данные обновляются иммутабельно и индекс каждый раз полностью пересчитывается из нового массива, перестроение требует `O(n)` времени и `O(n)` памяти.

Согласованность упрощает единый владелец: данные сразу хранятся в нормализованной форме либо индекс каждый раз вычисляется из одного неизменяемого источника.

Две независимо изменяемые копии без общей операции обновления создают риск рассинхронизации.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

Есть массив из `n` пользователей и `q` запросов поиска по `id`.

- Повторный `users.find(...)`: worst-case `O(q * n)` по времени и `O(1)` вспомогательной памяти.
- Сначала `new Map(users.map(...))`, затем `get(id)`: типично `O(n + q)` по времени и `O(n)` дополнительной памяти.
- Сортировка по `id` и бинарный поиск: обычно `O(n log n + q log n)` по времени, если массив изначально не отсортирован.

Если массив уже отсортирован по `id`, предварительная стоимость сортировки отсутствует и `q` запросов требуют `O(q log n)`.

Для одного поиска линейный проход может быть лучшим выбором. Для большого числа запросов индекс обычно даёт наиболее дешёвый доступ, если доступна дополнительная память и индекс можно корректно обновлять.

## Где это встречается во frontend

| Ситуация | Подход |
| --- | --- |
| Один поиск элемента в небольшом dropdown (выпадающем списке) | линейный `find()` без дополнительной структуры |
| Связывание заказов с пользователями | индекс пользователей по уникальному `id` |
| Получение сущности из Redux Toolkit | нормализованный объект `entities` работает как индекс |
| Много проверок выбранных строк | `Set<id>` вместо повторного `includes()` |
| Поиск позиции во временной шкале | бинарный поиск, если точки уже отсортированы по времени |
| Поиск с подсказками (autocomplete) по локальному списку | бинарный поиск применим только при подходящем порядке; поиск по подстроке обычно требует другого подхода |
