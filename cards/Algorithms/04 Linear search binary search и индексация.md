#### Вопрос

Чем отличаются линейный поиск (linear search), бинарный поиск (binary search) и поиск через индекс?

#### Ответ

Линейный поиск проверяет элементы по очереди, пока не найдёт нужный или не дойдёт до конца. В JavaScript так работают `find()`, `findIndex()` и `includes()`. В лучшем случае совпадение находится сразу и поиск занимает `O(1)`, в худшем требуется проверить все `n` элементов и получается `O(n)`.

Бинарный поиск работает с отсортированными данными. Он сравнивает искомое значение с элементом в середине диапазона и отбрасывает половину, в которой значения быть не может. Поэтому количество оставшихся элементов на каждом шаге уменьшается вдвое, а временная сложность составляет `O(log n)`.

Для бинарного поиска порядок должен соответствовать условию сравнения. Если массив отсортирован по `price`, искать товар по `name` через тот же порядок нельзя. Также нужен быстрый доступ к элементу по позиции. JavaScript-массив это позволяет, а в связном списке получение середины само требует прохода и устраняет основное преимущество алгоритма.

Индекс - дополнительная структура, которая связывает ключ с нужным значением. Например, `Map<id, user>` позволяет получать пользователя по `id`, не просматривая весь массив. Построение индекса по `n` элементам требует `O(n)` времени и `O(n)` памяти, а дальнейший `Map.get()` в типичном случае выполняется близко к `O(1)`.

| Подход | Подготовка | Один поиск | Дополнительная память | Основное условие |
| --- | --- | --- | --- | --- |
| линейный поиск | не нужна | worst-case `O(n)` | `O(1)` | подходит для любых данных |
| бинарный поиск | данные должны быть отсортированы | `O(log n)` | `O(1)` для итеративной реализации | порядок сортировки соответствует поиску |
| индекс через `Map` | `O(n)` | типично `O(1)` | `O(n)` | индекс нужно хранить и синхронизировать с данными |

Если поиск выполняется один раз, линейный проход часто дешевле подготовки структуры. Если выполнить `q` поисков по массиву, линейный подход в худшем случае стоит `O(q * n)`. Для бинарного поиска по уже отсортированным данным стоимость будет `O(q log n)`. Если сначала требуется сортировка, добавляется её цена, обычно `O(n log n)`. Индекс даёт типичную общую стоимость `O(n + q)`, но требует дополнительной памяти.

Подготовленная структура остаётся полезной, только пока соответствует исходным данным. После добавления, удаления или изменения ключа индекс нужно обновить или построить заново. Отсортированный массив тоже имеет цену поддержки: новое значение нужно вставить в правильное место либо выполнить повторную сортировку.

Во frontend выбор зависит от размера данных и частоты операций. Один `find()` в маленьком списке обычно проще индекса. Повторный поиск роли для каждой строки большой таблицы уже создаёт вложенную работу, поэтому справочник ролей выгодно один раз преобразовать в индекс по `id`.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Почему бинарный поиск требует отсортированных данных?
>
> **Ответ:** После сравнения с серединой алгоритм должен гарантированно решить, в какой половине может находиться значение. Такая гарантия существует только при известном порядке. Если элементы не отсортированы по тому же критерию, меньшие и большие значения могут находиться с любой стороны, поэтому отбрасывать половину нельзя.
>
> Сортировка и поиск должны использовать совместимое сравнение. Например, массив, отсортированный по возрастанию `price`, подходит для поиска по цене, но не для бинарного поиска по `id` или `name`.

> [!followup]
> **Вопрос:** Сортировка и бинарный поиск всегда лучше линейного поиска?
>
> **Ответ:** Нет. Если неотсортированный массив нужно проверить один раз, линейный поиск требует `O(n)`, а предварительная сортировка обычно `O(n log n)` плюс сам поиск `O(log n)`. В таком сценарии сортировка дороже.
>
> Бинарный поиск выгоден, когда данные уже отсортированы по нужному критерию или по ним выполняется много поисков. При частых изменениях нужно также учитывать стоимость поддержания порядка, а не только сложность одного поиска.

> [!followup]
> **Вопрос:** Когда стоит построить `Map`, а когда достаточно `find()`?
>
> **Ответ:** `find()` подходит для небольшого массива, редкого поиска или кода, где простота важнее подготовки дополнительной структуры. Один линейный поиск не оправдывает автоматическое создание индекса.
>
> `Map` полезен, когда одна и та же коллекция многократно ищется по стабильному ключу: при связывании сущностей, обработке большой таблицы, проверке выбранных строк или работе нормализованного хранилища состояния (store). Индекс меняет повторную стоимость `O(q * n)` на типичную `O(n + q)`, но добавляет `O(n)` памяти и обязан обновляться вместе с данными.

> [!followup]
> **Вопрос:** Где строить и хранить индекс в React-приложении?
>
> **Ответ:** Индекс строят на уровне, где доступен весь набор данных и можно контролировать его обновление: при преобразовании ответа API, в мемоизированном selector (функции вычисления производных данных), в `useMemo` для стабильного набора или в нормализованном store. Это позволяет переиспользовать одну структуру для множества обращений.
>
> Строить `new Map(items.map(...))` внутри каждой строки списка бессмысленно: каждая строка повторит полную работу. Даже на уровне родительского компонента индекс не следует пересоздавать при каждом render (расчёте представления компонента), если исходный массив не изменился. Мемоизация здесь полезна только при стабильной ссылке на исходные данные.

> [!followup]
> **Вопрос:** Как реализовать бинарный поиск и не ошибиться в границах?
>
> **Ответ:** Нужно явно выбрать интервал поиска и сохранять его смысл на каждой итерации. В варианте с закрытым интервалом `[left, right]` цикл продолжается, пока `left <= right`. После сравнения середина исключается: используется `left = middle + 1` или `right = middle - 1`, иначе цикл может зависнуть.
>
> ```ts
> function binarySearch(items: number[], target: number) {
>   let left = 0;
>   let right = items.length - 1;
>
>   while (left <= right) {
>     const middle = left + Math.floor((right - left) / 2);
>
>     if (items[middle] === target) return middle;
>     if (items[middle] < target) left = middle + 1;
>     else right = middle - 1;
>   }
>
>   return -1;
> }
> ```
>
> Инвариант цикла: если искомое значение существует, оно может находиться только внутри текущего интервала. На пустом массиве `right` равен `-1`, цикл не запускается и функция возвращает `-1`.

> [!followup]
> **Вопрос:** Что вернёт бинарный поиск, если в массиве есть дубликаты?
>
> **Ответ:** Обычная реализация вернёт любое найденное совпадение, а не обязательно первое или последнее. Если нужен первый элемент, равный `target`, после совпадения поиск продолжают в левой половине и запоминают найденный индекс. Для последнего совпадения продолжают справа.
>
> Более общий вариант `lower bound` ищет первую позицию, где значение не меньше `target`. Он также даёт место вставки, которое сохраняет сортировку. Такой контракт нужно назвать явно: «найти любое совпадение», «первое совпадение» и «позиция вставки» являются разными задачами.

> [!followup]
> **Вопрос:** Что происходит с индексом после изменения исходных данных?
>
> **Ответ:** Индекс является производным представлением и должен обновляться вместе с основными данными. После добавления сущности в массив, но не в `Map`, поиск через две структуры начнёт давать разные результаты. Изменение ключа требует удалить старую запись и добавить новую.
>
> Эту согласованность упрощает единый владелец: данные сразу хранятся в нормализованной форме либо индекс пересчитывается из неизменяемого исходного массива. Две независимо изменяемые копии без общей операции обновления создают риск рассинхронизации.

#### Мини-задача

Есть массив из `n` пользователей и `q` запросов поиска по `id`.

- Повторный `users.find(...)`: worst-case `O(q * n)` по времени и `O(1)` вспомогательной памяти.
- Сначала `new Map(users.map(...))`, затем `get(id)`: типично `O(n + q)` по времени и `O(n)` дополнительной памяти.
- Сортировка по `id` и бинарный поиск: обычно `O(n log n + q log n)` по времени, если массив изначально не отсортирован.

Для одного поиска линейный проход может быть лучшим выбором. Для большого числа запросов индекс обычно даёт наиболее дешёвый доступ, если доступна дополнительная память и индекс можно корректно обновлять.

#### Где это встречается во frontend

> [!context]
> | Ситуация | Подход |
> | --- | --- |
> | Один поиск элемента в небольшом dropdown (выпадающем списке) | линейный `find()` без дополнительной структуры |
> | Связывание заказов с пользователями | индекс пользователей по `id` |
> | Получение сущности из Redux Toolkit | нормализованный объект `entities` работает как индекс |
> | Много проверок выбранных строк | `Set<id>` вместо повторного `includes()` |
> | Поиск позиции во временной шкале | бинарный поиск, если точки уже отсортированы по времени |
> | Поиск с подсказками (autocomplete) по локальному списку | бинарный поиск применим только при подходящем порядке; поиск по подстроке обычно требует другого подхода |
