## Вопрос

<br>

 💬 **Какие основные алгоритмы сортировки существуют? Чем они отличаются по времени, памяти и стабильности?**

<h2></h2>

<br>
<dl>
<dd>

Алгоритм сортировки упорядочивает элементы по заданному критерию. При выборе сравнивают временную сложность, дополнительную память, стабильность, изменение исходных данных и свойства входа: размер, степень предварительной упорядоченности и диапазон ключей.

Большинство универсальных алгоритмов основано на сравнении элементов. В общей модели сортировки сравнениями нижняя граница худшего случая составляет `Ω(n log n)`. Эффективные алгоритмы, такие как merge sort и heap sort, достигают верхней границы `O(n log n)`.

Алгоритмы без сравнений могут быть быстрее относительно `n`, но требуют специальных ключей, например целых чисел из ограниченного диапазона, и дополнительно зависят от размера этого диапазона.

| Алгоритм | Лучший случай | Средний случай | Худший случай | Дополнительная память | Обычно стабилен |
|---|---:|---:|---:|---:|---|
| Bubble sort, пузырьковая сортировка | `O(n)` с проверкой обменов | `O(n²)` | `O(n²)` | `O(1)` | да |
| Selection sort, сортировка выбором | `O(n²)` | `O(n²)` | `O(n²)` | `O(1)` | нет |
| Insertion sort, сортировка вставками | `O(n)` | `O(n²)` | `O(n²)` | `O(1)` | да |
| Merge sort, сортировка слиянием | `O(n log n)` | `O(n log n)` | `O(n log n)` | `O(n)` для массива | да |
| Quicksort, быстрая сортировка | `O(n log n)` | `O(n log n)` | `O(n²)` | в среднем `O(log n)`, в худшем `O(n)` для стека вызовов | нет |
| Heap sort, пирамидальная сортировка | `O(n log n)` | `O(n log n)` | `O(n log n)` | `O(1)` | нет |
| Counting sort, сортировка подсчётом | `O(n + k)` | `O(n + k)` | `O(n + k)` | `O(k)` или `O(n + k)` | может быть стабильной |

Здесь `n` — количество элементов, а `k` — размер диапазона целочисленных ключей. Таблица описывает распространённые реализации: свойства конкретной реализации могут отличаться.

Например, стабильность иногда можно добавить ценой дополнительной памяти, а неудачный выбор опорного элемента ухудшает quicksort.

Bubble sort многократно меняет местами соседние элементы. Вариант с проверкой отсутствия обменов завершится за `O(n)` на уже отсортированном массиве, но в общем случае алгоритм имеет квадратичную сложность и используется преимущественно для обучения.

Selection sort на каждом шаге находит минимум оставшейся части. Число сравнений остаётся квадратичным даже для уже отсортированного массива. Алгоритм выполняет мало обменов, но его обычная реализация нестабильна.

Insertion sort вставляет очередной элемент в отсортированную левую часть и хорошо работает на маленьких или почти отсортированных данных.

Его время можно описать как `O(n + I)`, где `I` — количество инверсий, то есть пар элементов, расположенных в неправильном порядке. Для уже отсортированного массива `I = 0`, поэтому получается `O(n)`. В худшем случае `I` имеет порядок `n²`.

Merge sort делит массив, сортирует части и сливает их. Он гарантирует `O(n log n)` и может быть стабильным, если при равенстве во время слияния первым выбирается элемент из левой части.

Для массивов merge sort обычно требует `O(n)` дополнительной памяти под слияние. Рекурсивная реализация дополнительно использует стек глубиной `O(log n)`, но общая дополнительная память всё равно остаётся `O(n)`.

Quicksort делит данные относительно pivot, или опорного элемента. При сбалансированных разбиениях он работает за `O(n log n)` и часто быстр на практике благодаря хорошей локальности доступа.

При крайне несбалансированных разбиениях quicksort может получить `O(n²)` времени и глубину стека `O(n)`. Оценка `O(log n)` памяти в среднем относится к реализации с разбиением внутри исходного массива, а не к варианту, который на каждом шаге создаёт новые массивы.

Heap sort строит heap, или двоичную кучу, из которой последовательно извлекает наибольший элемент. Он гарантирует `O(n log n)` и может сортировать массив на месте с `O(1)` дополнительной памятью, но обычно нестабилен.

Counting sort не сравнивает пары, а считает количество каждого ключа. Он эффективен, только когда диапазон `k` не слишком велик относительно `n`.

Простой вариант со счётчиками использует `O(k)` дополнительной памяти. Стабильная реализация обычно дополнительно создаёт результирующий массив и требует `O(n + k)` памяти.

`Array.prototype.sort()` не обещает использовать один из этих алгоритмов. ECMAScript задаёт наблюдаемое поведение и стабильность, но оставляет выбор реализации JavaScript-движку.

Стандарт также не закрепляет временную и дополнительную пространственную сложность `sort()`. Поэтому прикладной код не должен зависеть от конкретного внутреннего алгоритма браузера или Node.js.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Что означает стабильность сортировки?</strong></summary>

<dl>
<dd>
<h2></h2>

Стабильная сортировка сохраняет исходный взаимный порядок элементов, которые равны по критерию сравнения.

Если два пользователя имеют одинаковый статус, после стабильной сортировки по статусу они останутся в том же порядке относительно друг друга.

Стабильность важна при последовательной сортировке по нескольким полям и для предсказуемого поведения интерфейса.

Начиная с ECMAScript 2019 `Array.prototype.sort()` обязан быть стабильным: элементы, для которых comparator возвращает `0`, сохраняют прежний взаимный порядок.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что значит in-place sorting?</strong></summary>

<dl>
<dd>
<h2></h2>

In-place sorting, или сортировка на месте, переставляет элементы внутри исходной структуры и не создаёт отдельный массив размером `n`.

Обычно такой алгоритм использует `O(1)` дополнительной памяти. Иногда к in-place относят и алгоритмы с `O(log n)` памяти стека, например рекурсивный quicksort со сбалансированными разбиениями.

Это свойство не означает неизменяемость: наоборот, исходный массив обычно изменяется.

Во frontend мутация может быть неприемлема для props или state. Тогда даже in-place алгоритм запускают на копии либо используют `toSorted()`, поэтому на уровне приложения всё равно появляется `O(n)` памяти для нового массива.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему сортировки сравнением не могут в общем случае быть быстрее <code>Ω(n log n)</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Для `n` различных элементов существует `n!` возможных порядков.

Одно сравнение даёт ограниченное количество вариантов результата, поэтому дерево решений должно иметь достаточно листьев для различения всех перестановок. Его высота в худшем случае не меньше `log₂(n!)`, что имеет порядок `n log n`.

Поэтому любая общая сортировка, которая получает информацию о порядке только через сравнения, требует `Ω(n log n)` сравнений в худшем случае.

Ограничение не означает, что каждый конкретный вход нельзя отсортировать быстрее. Например, insertion sort обрабатывает уже отсортированный массив за `O(n)`.

Counting sort не ограничен этой нижней границей, потому что использует значения целочисленных ключей и размер их диапазона, а не только попарные сравнения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда insertion sort может быть хорошим выбором?</strong></summary>

<dl>
<dd>
<h2></h2>

На маленьком массиве у него простая реализация и небольшие постоянные расходы.

На почти отсортированных данных количество сдвигов определяется числом инверсий. Время можно оценить как `O(n + I)`, где `I` — количество пар элементов, расположенных в неправильном порядке.

Если нарушений мало, сложность близка к `O(n)`.

Из-за этого сложные промышленные сортировки могут использовать insertion sort для небольших фрагментов после основного разбиения.

Для большого массива в случайном или обратном порядке его `O(n²)` обычно проигрывает алгоритмам `O(n log n)`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему quicksort может получить <code>O(n²)</code> и как снизить риск?</strong></summary>

<dl>
<dd>
<h2></h2>

Если pivot каждый раз оказывается минимальным или максимальным элементом, одна часть имеет размер `n - 1`, а другая почти пуста.

Получается цепочка работы:

```text
n + (n - 1) + (n - 2) + ...
```

Её сумма имеет порядок `O(n²)`, а глубина рекурсии может достигнуть `O(n)`.

Риск уменьшают:

- случайным выбором pivot;
- выбором медианы из нескольких элементов;
- трёхчастным разбиением для большого числа дубликатов;
- переходом на другой алгоритм при плохой глубине разбиений.

Случайный pivot делает постоянно неудачные разбиения маловероятными, но теоретический худший случай классического quicksort всё равно остаётся `O(n²)`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем merge sort отличается от quicksort?</strong></summary>

<dl>
<dd>
<h2></h2>

Merge sort гарантирует `O(n log n)` и в обычной реализации стабилен, но для массива требует `O(n)` дополнительной памяти.

Quicksort с разбиением на месте обычно использует меньше дополнительной памяти и имеет хорошую локальность доступа, но его классический вариант нестабилен, а худший случай равен `O(n²)`.

Нельзя выбрать победителя только по Big O. Важны стабильность, память, форма данных и конкретная реализация.

Для связных списков merge sort особенно удобен, потому что части можно сливать изменением ссылок без копирования всех элементов во вспомогательный массив.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда counting sort полезен, а когда опасен?</strong></summary>

<dl>
<dd>
<h2></h2>

Он полезен для целочисленных ключей из небольшого известного диапазона.

Например, миллион значений от `0` до `100` можно обработать за `O(n + 101)` с небольшим массивом счётчиков.

Если значений мало, но ключи лежат между `0` и миллиардом, память `O(k)` становится неприемлемой.

Отрицательные ключи тоже можно поддержать через смещение относительно минимального значения, но размер памяти всё равно определяется всем диапазоном между минимумом и максимумом.

Для строк, произвольных объектов и чисел с большим разреженным диапазоном универсальная сортировка сравнением обычно практичнее.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выбрать алгоритм сортировки на собеседовании?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала называют требования:

- размер данных;
- стабильность;
- ограничение памяти;
- возможность мутировать вход;
- диапазон и тип ключей;
- ожидаемую степень упорядоченности;
- требования к худшему случаю.

Затем сравнивают кандидатов по времени, памяти и свойствам конкретной реализации.

Для обычного frontend-кода чаще используют стандартный `sort()` или `toSorted()` с корректным comparator.

Ручная реализация алгоритма нужна в учебной задаче, специальном формате данных или когда явно доказано, что стандартное решение не покрывает требования.

При этом нельзя утверждать, какой алгоритм находится внутри `Array.prototype.sort()`: это решение JavaScript-движка.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```text
Нужно выбрать сортировку для двух случаев:
1. Небольшой список почти отсортирован после одного локального изменения.
2. Большой массив объектов нужно стабильно отсортировать с гарантией O(n log n).
```

Для первого случая подходит insertion sort: при небольшом числе инверсий он близок к `O(n)` и имеет малые накладные расходы.

Для второго подходит стабильная реализация merge sort: она гарантирует `O(n log n)`, но для массива требует `O(n)` дополнительной памяти.

В прикладном JavaScript стандартный стабильный `toSorted()` обычно предпочтительнее ручной реализации, если нет специальных ограничений. При этом ECMAScript гарантирует стабильность результата, но не гарантирует конкретную Big O используемого движком алгоритма.

## Где это встречается во frontend

| Сценарий | Что важно |
|---|---|
| Сортировка таблицы | стабильность, comparator, `null` и локаль |
| Почти отсортированный небольшой список | преимущества insertion sort |
| Ограниченный диапазон целых ключей | возможность counting sort |
| Большие данные | `O(n log n)`, память и работа на основном потоке браузера |
| React и Redux state | сортировка копии вместо мутации входного массива |
