## Вопрос

<br>

 💬 **Что такое two pointers, sliding window и frequency map? Как распознать эти алгоритмические шаблоны?**

<h2></h2>

<br>
<dl>
<dd>

Two pointers, или два указателя, означает, что алгоритм хранит две позиции в последовательности и согласованно двигает их вместо полного перебора всех пар.

Указатели могут идти навстречу друг другу, например при поиске суммы в отсортированном массиве, или в одном направлении, например при удалении дубликатов на месте. Во втором случае один указатель часто читает элементы, а другой показывает позицию для записи результата.

Sliding window, или скользящее окно, хранит текущий непрерывный диапазон `[left, right]` и обновляет его состояние при сдвиге границ.

Вместо повторного расчёта всего диапазона алгоритм добавляет новый элемент справа и удаляет ушедший элемент слева. Окно бывает фиксированного размера или переменного размера, который изменяется до выполнения условия.

Frequency map, или частотный индекс, хранит количество появлений каждого значения.

Его реализуют через `Map<value, count>` или `Object`, если строковые ключи и JSON-форма действительно подходят. Один проход строит индекс за типичное `O(n)` времени и `O(u)` памяти, где `u` — число различных значений.

Операции `Map.get()` и `Map.set()` в современных реализациях обычно считают близкими к `O(1)`, но ECMAScript не закрепляет для них конкретную Big O.

| Шаблон | Сигнал в задаче | Типичный результат |
|---|---|---|
| Two pointers навстречу | отсортированный массив, пара значений, палиндром | `O(n)` вместо проверки всех пар `O(n²)` |
| Два указателя в одном направлении | фильтрация, сжатие или удаление дубликатов на месте | один проход и контролируемая запись результата |
| Фиксированное скользящее окно | каждый непрерывный диапазон длины `w` | `O(n)` при дешёвом обновлении состояния окна |
| Переменное скользящее окно | самый длинный или короткий непрерывный диапазон с монотонным условием | часто `O(n)`, если обе границы движутся только вперёд |
| Частотный индекс | дубликаты, частоты, анаграммы, сравнение наборов | типично `O(n)` времени и `O(u)` памяти |

Например, поиск пары с суммой `target` в отсортированном массиве начинает с крайних элементов.

Если сумма меньше `target`, левый указатель двигают вправо; если больше — правый влево. Порядок массива гарантирует, что отброшенные пары уже не дадут ответ.

Без сортировки или другого монотонного свойства такая логика некорректна. Для неотсортированных данных можно использовать частотный индекс или сначала учесть стоимость сортировки.

Для суммы каждого диапазона длины `w` первый диапазон считают за `O(w)`, а затем при каждом сдвиге вычитают ушедшее значение и добавляют новое за `O(1)`.

При `w ≤ n` общая стоимость составляет:

```text
O(w) + O(n - w) = O(n)
```

Такой переход возможен только тогда, когда состояние окна можно корректно и достаточно дёшево обновить без полного пересчёта.

Например, сумма обновляется за `O(1)`. Для максимума окна простого вычитания недостаточно: при наивном повторном поиске максимума стоимость может стать `O(n * w)`, а монотонный `Deque` позволяет сохранить `O(n)`.

Шаблон выбирают по инварианту, то есть свойству, которое остаётся истинным при движении указателей.

Сам факт наличия массива не означает, что нужны two pointers или sliding window. Нужно объяснить:

- почему отброшенная часть больше не может содержать ответ;
- почему выбранное состояние полностью описывает текущее окно;
- почему каждая позиция обрабатывается ограниченное число раз.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Когда два указателя действительно уменьшают <code>O(n²)</code> до <code>O(n)</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда после проверки пары можно доказанно отбросить целую группу вариантов.

В задаче о сумме пары это обеспечивает сортировка. Если сумма крайних элементов слишком мала, текущий левый элемент не образует нужную сумму ни с одним элементом левее текущего правого указателя. Поэтому левый указатель можно безопасно сдвинуть.

Если такого порядка, монотонности или другого инварианта нет, движение одного указателя может пропустить ответ.

Для неотсортированных данных пару с суммой обычно ищут через `Set` за типичные `O(n)` времени и `O(n)` памяти либо сортируют копию за `O(n log n)`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем фиксированное скользящее окно (fixed window) отличается от переменного (variable window)?</strong></summary>

<dl>
<dd>
<h2></h2>

Фиксированное окно имеет постоянную длину `w`. После добавления элемента справа один элемент удаляется слева.

Так считают сумму, среднее или количество событий в каждом диапазоне из `w` элементов.

Переменное окно изменяет левую границу по условию. Например, при поиске самой длинной подстроки без повторов правую границу расширяют, а левую сдвигают после найденного дубликата.

Чтобы получить `O(n)`, обе границы должны двигаться только вперёд, каждая позиция должна входить и выходить из окна ограниченное число раз, а обновление состояния окна не должно само требовать полного обхода диапазона.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему скользящее окно подходит не для любой задачи о подмассиве?</strong></summary>

<dl>
<dd>
<h2></h2>

Условие должно позволять понять, в какую сторону двигать границу, и поддерживать состояние окна после добавления или удаления элемента.

Например, для положительных чисел слишком большая сумма позволяет уменьшать окно слева: удаление положительного значения гарантированно не увеличит сумму.

При наличии отрицательных чисел уменьшение окна может как уменьшить, так и увеличить сумму. Монотонность исчезает, поэтому тот же алгоритм переменного окна становится некорректным.

Тогда могут понадобиться префиксные суммы, `Map`, монотонная очередь или другой подход.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как частотный индекс помогает проверить анаграммы?</strong></summary>

<dl>
<dd>
<h2></h2>

Для первой последовательности увеличивают счётчик каждого символа, для второй уменьшают.

Последовательности являются анаграммами, если после обработки их длины совпадают и все счётчики равны нулю.

Время составляет `O(n + m)`, память — `O(u)` для различных символов.

До подсчёта определяют правила:

- учитывается ли регистр;
- игнорируются ли пробелы и пунктуация;
- применяется ли нормализация Unicode;
- сравниваются кодовые точки или grapheme clusters.

Длину и частоты нужно сравнивать уже после выбранной нормализации и сегментации. Иначе алгоритм может быть технически линейным, но решать не тот вариант задачи.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда использовать <code>Map</code>, а когда <code>Object</code> для частот?</strong></summary>

<dl>
<dd>
<h2></h2>

`Map` прямо выражает динамический индекс, поддерживает ключи любого типа и имеет `size`.

`Object` удобен для ограниченного набора строковых ключей и простой JSON-формы, но требует проверки собственных свойств и осторожности с внешними ключами.

Для фиксированного небольшого алфавита можно использовать массив счётчиков по индексу. Например, для латинских букв это уменьшает накладные расходы, но привязывает решение к явно оговорённому набору символов.

Структуру выбирают по контракту данных, а не только по предполагаемой скорости.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое prefix sum, или префиксная сумма, и как она связана со скользящим окном?</strong></summary>

<dl>
<dd>
<h2></h2>

Prefix sum, или префиксная сумма, хранит сумму первых `i` элементов.

После подготовки массива `prefix` за `O(n)` сумма полуинтервала `[left, right)` вычисляется за `O(1)`:

```ts
const rangeSum = prefix[right] - prefix[left];
```

Скользящее окно удобно для последовательного прохода соседних диапазонов, а префиксные суммы — для множества произвольных запросов диапазона по неизменяемым данным.

Обновление одного исходного элемента делает все последующие префиксные суммы устаревшими. Для частых изменений применяют другие структуры, например дерево Фенвика или segment tree.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как JavaScript-строки влияют на задачи с указателями?</strong></summary>

<dl>
<dd>
<h2></h2>

Индекс строки обращается к кодовым единицам UTF-16, а одна Unicode code point, или кодовая точка, может занимать две такие единицы.

`Array.from(text)` и `for...of` итерируют строку по кодовым точкам, поэтому не разделяют символы за пределами базовой многоязычной плоскости на две суррогатные части.

Но пользовательский символ может состоять из нескольких кодовых точек, например из буквы и комбинируемого знака или emoji-последовательности.

Если задача относится к воспринимаемым пользователем символам, строку сегментируют через `Intl.Segmenter` с `granularity: "grapheme"`.

Единица сравнения должна быть частью постановки задачи: UTF-16 code unit, Unicode code point или grapheme cluster.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как доказать линейную сложность переменного скользящего окна с вложенным <code>while</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Внешний указатель `right` проходит последовательность один раз.

Внутренний `while` может сработать много раз на одной итерации, но указатель `left` за весь алгоритм тоже проходит не больше `n` позиций и никогда не возвращается назад.

Общее число движений обеих границ имеет порядок:

```text
n + n = 2n
```

После отбрасывания постоянного множителя получается `O(n)`, а не `O(n²)`.

Это доказательство предполагает, что работа одного сдвига границы и обновления состояния окна занимает `O(1)` или амортизированное `O(1)`.

Визуальная вложенность циклов сама по себе не определяет сложность.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда эти шаблоны не стоит применять?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда отсутствует доказуемый инвариант, данные слишком малы для усложнения или простое решение уже достаточно.

Сортировка только ради two pointers может стоить дороже одного линейного поиска, а сложное окно с неочевидной логикой легче написать с ошибкой.

Sliding window также не подходит автоматически ко всем задачам о непрерывном диапазоне: условие должно позволять безопасно расширять и сужать окно.

Сначала формулируют корректное прямое решение и ограничения, затем доказывают, какую повторную работу устраняет шаблон.

Название паттерна не заменяет доказательство корректности.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

Найти длину самой длинной подстроки без повторяющихся кодовых точек Unicode:

```ts
function longestUniqueLength(input: string) {
  const chars = Array.from(input);
  const lastIndex = new Map<string, number>();
  let left = 0;
  let best = 0;

  for (let right = 0; right < chars.length; right += 1) {
    const char = chars[right];
    const previous = lastIndex.get(char);

    if (previous !== undefined && previous >= left) {
      left = previous + 1;
    }

    lastIndex.set(char, right);
    best = Math.max(best, right - left + 1);
  }

  return best;
}
```

Правая граница движется только вперёд. Левая граница также никогда не возвращается назад, а сразу переходит за последнее вхождение повторившегося символа.

Каждая кодовая точка обрабатывается постоянное число раз, поэтому время составляет `O(n)`, где `n` — количество кодовых точек.

`Map` занимает `O(u)` памяти для `u` различных кодовых точек, а массив `chars` — `O(n)`. Поскольку `u ≤ n`, общая дополнительная память составляет `O(n)`.

Для grapheme clusters, то есть воспринимаемых пользователем символов, вместо `Array.from()` нужен `Intl.Segmenter`.

## Где это встречается во frontend

| Сценарий | Шаблон |
|---|---|
| Проверка палиндрома или пары в отсортированном списке | два указателя навстречу |
| Анализ последних `w` измерений | фиксированное скользящее окно |
| Самая длинная подстрока без повторов | переменное окно и `Map` последних позиций |
| Подсчёт тегов, статусов или ошибок | частотный индекс |
| Множество запросов суммы диапазона | префиксные суммы |
| Максимум каждого окна | Deque с монотонным порядком кандидатов |
