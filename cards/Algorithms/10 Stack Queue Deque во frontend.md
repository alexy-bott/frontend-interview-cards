## Вопрос

<br>

 💬 **Чем отличаются Stack, Queue и Deque? Как реализовать их в JavaScript и где они применяются во frontend?**

<h2></h2>

<br>
<dl>
<dd>

Stack, или стек, работает по правилу LIFO: последним добавлен, первым извлечён. Основные операции называются `push` и `pop`.

В JavaScript стек удобно реализовать массивом: `push()` и `pop()` в типичных реализациях имеют амортизированную сложность, близкую к `O(1)`. ECMAScript определяет поведение методов, но не закрепляет для них конкретную Big O.

Queue, или очередь, работает по правилу FIFO: первым добавлен, первым извлечён. Операции часто называют `enqueue` и `dequeue`.

Повторный `array.shift()` плохо подходит для большой очереди, потому что удаление начала массива обычно требует работы, зависящей от его длины. Вместо этого хранят индекс головы или используют кольцевой буфер.

Deque (double-ended queue), или двусторонняя очередь, позволяет добавлять и удалять элементы с обоих концов. При подходящей реализации все четыре операции занимают амортизированное `O(1)`.

Обычный JavaScript-массив не обеспечивает такую оценку для начала массива: `shift()` и `unshift()` обычно имеют линейную стоимость.

| Структура | Порядок | Основные операции | Типичная стоимость |
|---|---|---|---|
| Stack | LIFO | добавить и удалить с конца | амортизированно `O(1)` |
| Queue | FIFO | добавить в хвост, удалить из головы | амортизированно `O(1)` при подходящей реализации |
| Deque | с обоих концов | добавить или удалить слева и справа | амортизированно `O(1)` при кольцевом буфере |

Простую очередь на массиве можно реализовать так:

```ts
class Queue<T> {
  private items: T[] = [];
  private head = 0;

  enqueue(value: T): void {
    this.items.push(value);
  }

  dequeue(): T | undefined {
    if (this.head >= this.items.length) {
      return undefined;
    }

    const value = this.items[this.head];
    this.head += 1;

    // Очередь полностью опустела — сразу освобождаем внутренний массив.
    if (this.head === this.items.length) {
      this.items = [];
      this.head = 0;

      return value;
    }

    // Иногда удаляем уже использованный большой префикс.
    if (this.head >= 1024 && this.head * 2 >= this.items.length) {
      this.items = this.items.slice(this.head);
      this.head = 0;
    }

    return value;
  }

  get size(): number {
    return this.items.length - this.head;
  }
}
```

Индекс головы исключает сдвиг элементов при каждом извлечении.

Логически удалённые элементы остаются во внутреннем массиве и могут продолжать удерживать ссылки. Поэтому при полном опустошении массив сбрасывается, а большой использованный префикс периодически удаляется через `slice()`.

Отдельная очистка требует линейного копирования оставшейся части, но запускается только после большого числа дешёвых извлечений. Поэтому стоимость последовательности операций распределяется между ними, и `dequeue()` остаётся амортизированно близким к `O(1)`.

Stack используют для DFS, undo/redo, проверки скобок, локальной истории действий и обработки вложенной структуры.

Queue нужна для BFS, последовательной обработки поступивших задач и реализации ограничения параллелизма вместе с отдельным исполнителем.

Deque полезен для скользящего окна и других алгоритмов, в которых элементы добавляются и удаляются с разных концов.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему <code>shift()</code> делает массив плохой очередью?</strong></summary>

<dl>
<dd>
<h2></h2>

После удаления нулевого элемента оставшиеся индексы должны вести себя так, будто элементы сдвинулись к началу.

Типичная реализация выполняет работу, зависящую от длины массива, поэтому один `shift()` обычно оценивают как `O(n)`.

В BFS из `n` узлов повторный `shift()` может добавить квадратичную стоимость к обходу.

Индекс головы, кольцевой буфер или специализированная очередь дают амортизированное `O(1)` извлечение без постоянного сдвига остальных элементов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему очередь с индексом головы нужно иногда очищать?</strong></summary>

<dl>
<dd>
<h2></h2>

Увеличение `head` логически удаляет элементы, но сам массив продолжает содержать использованный префикс и ссылки на его значения.

Долгоживущая очередь может из-за этого удерживать уже ненужные объекты и постоянно увеличивать внутренний массив.

Если очередь полностью опустела, внутренний массив можно сразу сбросить.

Если она продолжает использоваться, большой обработанный префикс периодически удаляют:

```ts
items = items.slice(head);
head = 0;
```

Порог не должен запускать копирование после каждого извлечения. Очистку выполняют достаточно редко, чтобы её стоимость распределялась между большим количеством операций.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем собственный Stack отличается от call stack JavaScript?</strong></summary>

<dl>
<dd>
<h2></h2>

Собственный Stack — обычная структура данных, созданная приложением. Она хранит выбранные разработчиком значения и управляется кодом приложения.

Call stack, или стек вызовов, управляется JavaScript-движком и хранит активные вызовы функций, их контекст и место продолжения выполнения. Его конкретное устройство и размещение памяти являются деталями реализации движка.

Рекурсивный DFS использует call stack неявно.

Итеративный DFS хранит ожидающие узлы в собственном Stack и поэтому не зависит от ограничения глубины рекурсивных вызовов. При этом память для ожидающих узлов всё равно требуется.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как реализовать undo/redo через два стека?</strong></summary>

<dl>
<dd>
<h2></h2>

Stack `undo` хранит выполненные команды или предыдущие состояния.

При отмене верхний элемент извлекают, применяют обратное действие и помещают в Stack `redo`. При повторе выполняют обратный перенос.

После нового действия Stack `redo` обычно очищают: прежняя ветка истории больше не соответствует текущему состоянию.

Для больших состояний хранят команды, патчи или структурно разделяемые версии, а не полную глубокую копию всего приложения на каждом шаге.

Также обычно ограничивают максимальную глубину истории, чтобы память не росла бесконечно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Очередь задач event loop является обычным JavaScript-массивом?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Очереди event loop принадлежат среде выполнения, например браузеру, и описывают порядок допуска задач к выполнению.

JavaScript-код не получает прямой массив этих задач и не извлекает элементы через `shift()`.

Сходство состоит в FIFO-порядке внутри конкретной очереди, но у браузера есть разные task sources, очередь microtasks и отдельные правила выполнения рендеринга.

Структура Queue помогает понять базовый порядок, но не заменяет полную модель браузерного event loop.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем Queue отличается от Priority Queue?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычная Queue извлекает самый ранний добавленный элемент.

Priority Queue, или очередь с приоритетом, извлекает элемент с наивысшим или наименьшим приоритетом независимо от времени добавления.

Priority Queue часто реализуют двоичной кучей:

- просмотр главного элемента — `O(1)`;
- добавление — `O(log n)`;
- извлечение главного элемента — `O(log n)`.

Она применяется для планирования по приоритету и алгоритма Dijkstra, который ищет кратчайшие пути в графе с неотрицательными весами.

FIFO-порядок для элементов с одинаковым приоритетом не возникает автоматически. Если он нужен, вместе с приоритетом сохраняют порядковый номер добавления и используют его как дополнительный критерий.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое двоичная куча и как она работает?</strong></summary>

<dl>
<dd>
<h2></h2>

Двоичная куча (binary heap) — почти полное двоичное дерево со свойством порядка.

В min-heap значение родителя не больше значений его детей, поэтому минимум находится в корне. В max-heap в корне находится максимум.

Куча не является полностью отсортированным деревом: порядок гарантируется только между родителем и непосредственными детьми.

Кучу удобно хранить массивом. При индексации с `0` для элемента с индексом `i`:

```text
левый ребёнок  = 2 * i + 1
правый ребёнок = 2 * i + 2
родитель       = Math.floor((i - 1) / 2)
```

При добавлении новый элемент помещают в конец и поднимают через `sift up`.

После удаления корня на его место ставят последний элемент и опускают через `sift down`.

Добавление и извлечение корня занимают `O(log n)`, просмотр корня — `O(1)`, а построение кучи из готового массива снизу вверх — `O(n)`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужен Deque, а не Queue?</strong></summary>

<dl>
<dd>
<h2></h2>

Deque нужен, когда алгоритм должен работать с обоими концами структуры.

Например, монотонная очередь для максимума скользящего окна:

- удаляет слева индексы, вышедшие за границу окна;
- удаляет справа элементы, которые уже не смогут стать максимумом;
- добавляет новый индекс справа;
- читает текущий максимум слева.

Реализация через `shift()` и `unshift()` может уничтожить ожидаемую линейную сложность алгоритма.

Для больших данных используют кольцевой буфер, собственную реализацию Deque или специализированную структуру с постоянными операциями на концах.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Ограничивает ли Queue параллелизм сама по себе?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Queue только хранит порядок ожидающих задач.

Для ограничения параллелизма нужен исполнитель, который:

- хранит число активных операций;
- запускает не больше заданного лимита;
- после завершения одной операции извлекает следующую задачу;
- обрабатывает ошибки и отмену.

Также нужно определить приоритет, максимальный размер очереди и поведение при перегрузке.

Простое накопление задач без backpressure — ограничения скорости поступления или размера очереди — может привести к росту памяти и выполнению уже устаревших операций.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

Проверить правильность вложенности круглых, квадратных и фигурных скобок:

```ts
function hasBalancedBrackets(input: string) {
  const opening = new Set(["(", "[", "{"]);
  const pair = new Map([
    [")", "("],
    ["]", "["],
    ["}", "{"],
  ]);
  const stack: string[] = [];

  for (const char of input) {
    if (opening.has(char)) {
      stack.push(char);
      continue;
    }

    const expected = pair.get(char);

    if (expected && stack.pop() !== expected) {
      return false;
    }
  }

  return stack.length === 0;
}
```

Каждый символ обрабатывается один раз, а операции Stack в типичной реализации занимают амортизированное `O(1)`.

Время составляет `O(n)`, память в худшем случае — `O(n)` для последовательности открывающих скобок.

Символы, которые не являются одной из проверяемых скобок, функция игнорирует.

## Где это встречается во frontend

| Сценарий | Структура |
|---|---|
| Undo/redo редактора | два Stack с командами или состояниями |
| Обход дерева в глубину | Stack |
| Обход дерева по уровням | Queue |
| Ограничение числа одновременных запросов | Queue и исполнитель |
| Максимум в скользящем окне | монотонный Deque |
| История вложенной навигации | Stack или более сложная модель переходов поверх него |
