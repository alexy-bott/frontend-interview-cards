## Вопрос

Что такое two pointers, sliding window и frequency map? Как распознать эти алгоритмические шаблоны?

<details>
<summary><strong>Показать ответ</strong></summary>

Two pointers, или два указателя, означает, что алгоритм хранит две позиции в последовательности и согласованно двигает их вместо полного перебора всех пар. Указатели могут идти навстречу друг другу, например при поиске суммы в отсортированном массиве, или в одном направлении, например при удалении дубликатов на месте.

Sliding window, или скользящее окно, хранит текущий непрерывный диапазон `[left, right]` и обновляет его состояние при сдвиге границ. Вместо повторного расчёта всего диапазона алгоритм добавляет новый элемент справа и удаляет ушедший элемент слева. Окно бывает фиксированного размера или переменного размера, который изменяется до выполнения условия.

Frequency map, или частотный индекс, хранит количество появлений каждого значения. Его реализуют через `Map<value, count>` или `Object`, если строковые ключи и JSON-форма действительно подходят. Один проход строит индекс за `O(n)` времени и `O(k)` памяти, где `k` - число различных значений.

| Шаблон | Сигнал в задаче | Типичный результат |
|---|---|---|
| Two pointers навстречу | отсортированный массив, пара значений, палиндром | `O(n)` вместо проверки всех пар `O(n²)` |
| Два указателя в одном направлении | фильтрация или сжатие последовательности на месте | один проход и контролируемая запись результата |
| Фиксированное скользящее окно | каждый непрерывный диапазон длины `k` | `O(n)` при обновлении агрегата |
| Переменное скользящее окно | самый длинный или короткий непрерывный диапазон с условием | часто `O(n)`, если обе границы движутся только вперёд |
| Частотный индекс | дубликаты, частоты, анаграммы, сравнение наборов | `O(n)` времени и `O(k)` памяти |

Например, поиск пары с суммой `target` в отсортированном массиве начинает с крайних элементов. Если сумма меньше `target`, левый указатель двигают вправо; если больше - правый влево. Порядок массива гарантирует, что отброшенные пары уже не дадут ответ. Без сортировки такая логика некорректна; можно использовать частотный индекс или сначала учесть стоимость сортировки.

Для суммы каждого диапазона длины `k` первый диапазон считают за `O(k)`, а затем при каждом сдвиге вычитают ушедшее значение и добавляют новое. Получается `O(n)` вместо `O(n * k)`. Такой переход возможен только если состояние окна можно корректно обновить без полного пересчёта.

Шаблон выбирают по инварианту, то есть свойству, которое остаётся истинным при движении указателей. Сам факт наличия массива не означает, что нужны two pointers. Нужно объяснить, почему отброшенная часть больше не может содержать ответ и почему каждая позиция обрабатывается ограниченное число раз.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Когда два указателя действительно уменьшают <code>O(n²)</code> до <code>O(n)</code>?</summary>

Когда после проверки пары можно доказанно отбросить целую группу вариантов. В задаче о сумме пары это обеспечивает сортировка: слишком маленькая сумма означает, что текущий левый элемент не образует нужную пару ни с одним ещё меньшим правым значением.

Если такого порядка или монотонного свойства нет, движение одного указателя может пропустить ответ. Для неотсортированных данных пару с суммой обычно ищут через `Set` за `O(n)` времени и памяти либо сортируют копию за `O(n log n)`.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем фиксированное скользящее окно (fixed window) отличается от переменного (variable window)?</summary>

Фиксированное окно имеет постоянную длину. После добавления элемента справа один элемент обязательно удаляется слева. Так считают сумму, среднее или количество событий в каждом диапазоне из `k` элементов.

Переменное окно изменяет левую границу по условию. Например, при поиске самой длинной подстроки без повторов правую границу расширяют, а левую сдвигают после найденного дубликата. Чтобы получить `O(n)`, обе границы должны двигаться только вперёд и каждая позиция должна входить и выходить из окна ограниченное число раз.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему скользящее окно подходит не для любой задачи о подмассиве?</summary>

Условие должно позволять понять, в какую сторону двигать границу, и поддерживать состояние окна после добавления или удаления элемента. Например, для положительных чисел слишком большая сумма позволяет уменьшать окно слева.

При наличии отрицательных чисел уменьшение окна может как уменьшить, так и увеличить сумму. Монотонность исчезает, поэтому тот же алгоритм переменного окна становится некорректным. Тогда могут понадобиться префиксные суммы, `Map` или другой подход.

</details>

<details>
<summary><strong>Вопрос:</strong> Как частотный индекс помогает проверить анаграммы?</summary>

Для первой строки увеличивают счётчик каждого символа, для второй уменьшают. Строки являются анаграммами, если после обработки длины совпадают и все счётчики равны нулю. Время составляет `O(n + m)`, память - `O(k)` для различных символов.

До подсчёта определяют правила: учитываются ли регистр, пробелы, нормализация Unicode и пользовательские символы. Иначе алгоритм может быть технически линейным, но решать не тот вариант задачи.

</details>

<details>
<summary><strong>Вопрос:</strong> Когда использовать <code>Map</code>, а когда <code>Object</code> для частот?</summary>

`Map` прямо выражает динамический индекс, поддерживает ключи любого типа и имеет `size`. `Object` удобен для ограниченного набора строковых ключей и простой JSON-формы, но требует проверки собственных свойств и осторожности с внешними ключами.

Для фиксированного небольшого алфавита можно использовать массив счётчиков по индексу. Например, для латинских букв это уменьшает накладные расходы, но привязывает решение к явно оговорённому набору символов.

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое prefix sum, или префиксная сумма, и как она связана со скользящим окном?</summary>

Prefix sum, или префиксная сумма, хранит сумму первых `i` элементов. После подготовки массива `prefix` за `O(n)` сумма диапазона `[left, right)` вычисляется как `prefix[right] - prefix[left]` за `O(1)`.

Скользящее окно удобно для последовательного прохода соседних диапазонов, а префиксные суммы - для множества произвольных запросов диапазона по неизменяемым данным. Обновление одного исходного элемента делает все последующие префиксные суммы устаревшими, поэтому для частых изменений нужны другие структуры.

</details>

<details>
<summary><strong>Вопрос:</strong> Как JavaScript-строки влияют на задачи с указателями?</summary>

Индекс строки обращается к кодовым единицам UTF-16, а один Unicode code point, или кодовая точка, может занимать две единицы. `Array.from(text)` или `for...of` итерируют кодовые точки, поэтому правильно сохраняют символы за пределами базовой многоязычной плоскости.

Но пользовательский символ может состоять из нескольких кодовых точек, например буквы и комбинируемого знака или emoji-последовательности. Если задача относится к воспринимаемым символам, строку сегментируют через `Intl.Segmenter` с `granularity: "grapheme"`. Правило сравнения должно быть частью постановки задачи.

</details>

<details>
<summary><strong>Вопрос:</strong> Как доказать линейную сложность переменного скользящего окна с вложенным <code>while</code>?</summary>

Внешний указатель `right` проходит последовательность один раз. Внутренний `while` может сработать много раз на одной итерации, но указатель `left` за весь алгоритм тоже проходит не больше `n` позиций и никогда не возвращается назад.

Общее число движений обеих границ не превышает порядка `2n`, поэтому работа остаётся `O(n)`, а не `O(n²)`. Визуальная вложенность циклов сама по себе не определяет сложность.

</details>

<details>
<summary><strong>Вопрос:</strong> Когда эти шаблоны не стоит применять?</summary>

Когда отсутствует инвариант, данные слишком малы для усложнения или простое решение уже достаточно. Сортировка только ради two pointers может стоить дороже одного линейного поиска, а сложное окно с неочевидной логикой легче написать с ошибкой.

Сначала формулируют корректное прямое решение и ограничения, затем доказывают, какую повторную работу устраняет шаблон. Название паттерна не заменяет доказательство корректности.

</details>

## Мини-задача

Найти длину самой длинной подстроки без повторяющихся кодовых точек Unicode:

```ts
function longestUniqueLength(input: string) {
  const chars = Array.from(input);
  const lastIndex = new Map<string, number>();
  let left = 0;
  let best = 0;

  for (let right = 0; right < chars.length; right += 1) {
    const char = chars[right];
    const previous = lastIndex.get(char);

    if (previous !== undefined && previous >= left) {
      left = previous + 1;
    }

    lastIndex.set(char, right);
    best = Math.max(best, right - left + 1);
  }

  return best;
}
```

Правая и левая границы движутся только вперёд. Каждая кодовая точка обрабатывается постоянное число раз, поэтому время составляет `O(n)`, где `n` - их количество. `Map` занимает `O(k)` для всех различных символов входа, а массив `chars` - `O(n)`, поэтому общая дополнительная память равна `O(n)`. Для grapheme clusters, то есть воспринимаемых пользователем символов, вместо `Array.from()` нужен `Intl.Segmenter`.

## Где это встречается во frontend

> [!NOTE]
> | Сценарий | Шаблон |
> |---|---|
> | Проверка палиндрома или пары в отсортированном списке | два указателя навстречу |
> | Анализ последних `k` измерений | фиксированное скользящее окно |
> | Самая длинная подстрока без повторов | переменное окно и `Map` последних позиций |
> | Подсчёт тегов, статусов или ошибок | частотный индекс |
> | Множество запросов суммы диапазона | префиксные суммы |
> | Максимум каждого окна | Deque с монотонным порядком кандидатов |
