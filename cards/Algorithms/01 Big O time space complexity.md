## Вопрос

<br>

 💬 **Что такое Big O? Чем отличаются временная сложность (time complexity) и пространственная сложность (space complexity)?**

<h2></h2>

<br>
<dl>
<dd>

Big O — обозначение асимптотической верхней границы, которое показывает, как растут затраты алгоритма при увеличении входных данных. Например, оно помогает сравнить, как изменится объём работы при обработке 100, 10 000 или миллиона элементов.

Размер входных данных обычно обозначают как `n`. В зависимости от задачи это может быть количество элементов массива, строк таблицы, символов в строке или узлов дерева. Поэтому при оценке сложности важно сначала назвать, что именно означает `n`.

Если у задачи несколько независимых входов, используют несколько переменных, например `n`, `m` и `s`. Их нельзя автоматически заменять одним `n`: обход двух независимых массивов имеет сложность `O(n + m)`, а сравнение каждого элемента первого массива с каждым элементом второго — `O(n * m)`.

Временная сложность (time complexity) показывает, как растёт количество выполняемой работы. При этом считают не строки кода, а существенные операции и число их выполнений относительно размера входа.

Временная сложность не измеряет реальное время в миллисекундах: оно также зависит от устройства, JavaScript-движка, конкретных операций и входных данных.

Пространственная сложность (space complexity) показывает, как растёт расход памяти. При этом нужно уточнять, что именно считается.

Общая пространственная сложность учитывает всю память, необходимую для выполнения алгоритма. Вспомогательная память (auxiliary space) — дополнительная память, которую алгоритм использует сверх хранения входных данных. В неё входят временные массивы, `Set`, `Map` и стек рекурсивных вызовов.

В практических оценках часто считают именно вспомогательную память, поэтому используемая договорённость должна быть явной.

Например, подсчёт суммы элементов массива требует `O(n)` времени, потому что необходимо пройти по всем элементам, и `O(1)` вспомогательной памяти, потому что независимо от размера массива достаточно одной переменной с текущей суммой.

Если построить `Set`, потребуется `O(n)` дополнительной памяти. В типичных реализациях его построение занимает `O(n)` времени, а последующие проверки через `set.has()` выполняются в среднем за `O(1)` вместо линейного поиска `O(n)` через `array.includes()`.

Сложность можно классифицировать по трём разным признакам:

- по ресурсу — временная сложность и пространственная сложность;
- по характеру роста — постоянная, логарифмическая, линейная, квадратичная и другие классы;
- по рассматриваемому сценарию — best-case, average-case и worst-case.

Название класса роста показывает, как меняется объём работы при увеличении `n`. Например, при линейной сложности увеличение входа в два раза примерно удваивает работу. При квадратичной сложности увеличение входа в два раза увеличивает работу примерно в четыре раза, потому что рост зависит от `n²`.

| Обозначение | Название | Как растёт работа | Пример |
| --- | --- | --- | --- |
| `O(1)` | постоянная (constant) | не зависит от размера входа | чтение элемента массива по индексу |
| `O(log n)` | логарифмическая (logarithmic) | на каждом шаге область поиска уменьшается в несколько раз | бинарный поиск в отсортированном массиве |
| `O(n)` | линейная (linear) | растёт пропорционально количеству элементов | один проход по массиву |
| `O(n log n)` | линейно-логарифмическая (linearithmic) | растёт быстрее линейной, но медленнее квадратичной | типичная эффективная сортировка сравнением |
| `O(n²)` | квадратичная (quadratic) | для каждого из `n` элементов выполняется работа, также зависящая от `n` | сравнение каждого элемента с каждым |
| `O(2ⁿ)` | экспоненциальная (exponential) | добавление одного элемента может примерно удвоить объём работы | перебор всех подмножеств набора |
| `O(n!)` | факториальная (factorial) | перебираются все возможные перестановки элементов | полный перебор вариантов порядка |

Постоянная сложность `O(1)` не означает, что операция выполняется мгновенно. Она означает только то, что размер входа не меняет порядок роста количества работы.

Логарифмическая сложность `O(log n)` растёт медленно: если бинарный поиск делит область поиска пополам, удвоение массива добавляет примерно один шаг.

Линейная сложность `O(n)` обычно возникает при одном полном проходе по данным.

Квадратичная сложность `O(n²)` часто возникает при сравнении каждого элемента с каждым. Для 100 элементов это порядка 10 000 сравнений, а для 10 000 элементов — уже порядка 100 миллионов.

Экспоненциальная `O(2ⁿ)` и факториальная `O(n!)` сложности растут ещё быстрее, поэтому полный перебор становится непрактичным уже на сравнительно небольших входных данных.

Big O рассматривает поведение при больших входных данных. Такой подход называют асимптотическим анализом.

При оценке отбрасывают постоянные множители и менее быстро растущие части:

- `O(2n)` упрощают до `O(n)`;
- `O(n² + n)` упрощают до `O(n²)`.

Но независимые параметры сохраняют. Например, `O(n + m)` нельзя упростить до `O(n)`, если неизвестно, как `m` связано с `n`.

Строго математически Big O задаёт верхнюю границу роста. В инженерной речи его часто используют менее строго — как название наиболее точного известного порядка роста алгоритма.

Best-case, average-case и worst-case описывают разные сценарии входных данных: лучший, средний и худший. Это отдельная характеристика, а не другое название Big O.

Для каждого сценария можно указать свою сложность. Если сценарий не определён, часто оценивают worst-case, но эту договорённость лучше проговорить явно.

Big O не заменяет измерения производительности. Алгоритм с худшим порядком роста может оказаться быстрее на маленьких данных из-за меньших постоянных затрат.

Работа с DOM, расчёт layout — геометрии элементов страницы — и разбор большого JSON также могут быть дорогими, даже если алгоритм имеет линейную сложность.

Во frontend сложность особенно важна для операций, которые выполняются часто: при каждом render — расчёте следующего представления компонента, вводе символа, обработке большой таблицы или пересчёте производных данных.

Поэтому оценивают не только сложность одной операции, но и размер данных, частоту выполнения, работу на main thread — основном потоке браузера — и расход памяти.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Как определить временную сложность фрагмента кода?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала определяют размеры входных данных и обозначают их, например `n` и `m`.

Затем считают, сколько раз относительно этих размеров выполняются основные операции. Оценивают фактическую работу, а не количество строк кода.

Последовательные участки складываются:

- `O(n) + O(n)` даёт `O(2n)`, что упрощается до `O(n)`;
- `O(n) + O(m)` остаётся `O(n + m)`, если размеры независимы.

Вложенные проходы перемножаются, если внутренний проход выполняется полностью для каждой итерации внешнего: `n * n` даёт `O(n²)`.

Для условных веток обычно берут наиболее дорогую ветку, если оценивается worst-case. Вызов другой функции тоже включают в расчёт, а не считают одной операцией только потому, что он записан одной строкой.

В конце оставляют наиболее быстро растущую часть и отбрасывают постоянные множители.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли вложенные циклы означают <code>O(n²)</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Квадратичная сложность получается, когда внешний и внутренний циклы зависят от одного размера `n` и внутренний цикл выполняет примерно `n` итераций для каждой итерации внешнего.

Если циклы проходят по двум независимым коллекциям длиной `n` и `m`, сложность будет `O(n * m)`.

Если внутренний цикл каждый раз уменьшает область работы или делит её пополам, результат может быть другим.

Также два вложенных указателя не обязательно дают `O(n²)`. Если каждый указатель за всё выполнение проходит массив только один раз, общая сложность может остаться `O(n)`.

Поэтому оценивают общее количество выполнений внутренней операции, а не сам факт визуальной вложенности циклов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем отличаются best-case, average-case и worst-case и как они связаны с Big O?</strong></summary>

<dl>
<dd>
<h2></h2>

Best-case описывает наиболее удачный вход, average-case — ожидаемое поведение на типичных входах, worst-case — наиболее дорогой допустимый вход.

Например, `find()` найдёт нужный элемент за одну проверку в лучшем случае и просмотрит весь массив в худшем.

Big O и вид сценария отвечают на разные вопросы. Сценарий определяет, какие входные данные рассматриваются, а Big O описывает верхнюю границу роста затрат для выбранного сценария.

Поэтому можно отдельно оценить worst-case как `O(n)` и best-case как `O(1)`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда стоит заменить повторный поиск в массиве на <code>Set</code> или <code>Map</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Такая замена полезна, когда по одной коллекции выполняется много проверок наличия или поисков по ключу.

Линейный поиск в массиве может требовать `O(n)` на каждую проверку. Построение `Set` или `Map` обычно требует одного прохода `O(n)` и дополнительной памяти `O(n)`, после чего доступ по ключу в типичной реализации занимает в среднем `O(1)`.

Это обмен времени на память.

Для маленького массива и одной проверки построение дополнительной структуры может не окупиться из-за выделения памяти и постоянных затрат. Для большого списка и множества повторных проверок индекс обычно выгоднее.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как оценить сложность цепочки <code>filter().sort().map()</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`filter()` сначала проходит исходный массив из `n` элементов и создаёт массив из `k` подходящих элементов: `O(n)`.

Затем сортируются `k` элементов. Для типичной эффективной сортировки сравнением это `O(k log k)`, хотя стандарт JavaScript не закрепляет конкретный алгоритм и его асимптотическую сложность.

После этого `map()` проходит `k` элементов за `O(k)`.

Общая оценка — `O(n + k log k + k)`.

Если после фильтрации осталось почти `n` элементов, доминирует сортировка и выражение обычно записывают как `O(n log n)`.

Отдельно учитывается память для промежуточных и результирующих массивов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем Big O отличается от Big Omega и Big Theta?</strong></summary>

<dl>
<dd>
<h2></h2>

Big O, или `O`, задаёт асимптотическую верхнюю границу: затраты растут не быстрее указанного порядка с точностью до постоянного множителя.

Big Omega, или `Ω`, задаёт нижнюю границу.

Big Theta, или `Θ`, задаёт точный порядок роста одновременно сверху и снизу.

Один полный проход по массиву имеет `Θ(n)`: он выполняет работу, пропорциональную `n`, и сверху, и снизу.

Формально он также принадлежит `O(n²)`, но такая верхняя граница слишком грубая и почти бесполезна.

На собеседованиях словом Big O часто нестрого называют наиболее точный известный класс роста, поэтому полезно уточнить эту договорённость.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем амортизированная сложность отличается от average-case?</strong></summary>

<dl>
<dd>
<h2></h2>

Амортизированный анализ распределяет стоимость редких дорогих операций по длинной последовательности вызовов.

Например, отдельный `push()` динамического массива при расширении внутреннего хранилища может потребовать `O(n)`, но последовательность из `n` добавлений выполняется за `O(n)`, поэтому одна операция амортизированно стоит `O(1)`.

Average-case, или средний случай, усредняет стоимость по предполагаемому распределению входных данных или случайному выбору алгоритма.

Амортизированная оценка не требует считать одни входы более вероятными: она гарантирует среднюю стоимость операции внутри всей рассматриваемой последовательности.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему в <code>O(log n)</code> обычно не указывают основание логарифма?</strong></summary>

<dl>
<dd>
<h2></h2>

Логарифмы с разными постоянными основаниями отличаются постоянным множителем:

```text
log₂ n = log₁₀ n × log₂ 10
```

В Big O постоянные множители отбрасываются, поэтому `O(log₂ n)` и `O(log₁₀ n)` относятся к одному классу роста.

Основание всё ещё помогает понять алгоритм. У бинарного поиска оно связано с делением диапазона примерно пополам, а у дерева с большим числом потомков на каждом уровне будет другой коэффициент.

Асимптотический класс при постоянном коэффициенте ветвления остаётся логарифмическим.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как рекурсия влияет на пространственную сложность?</strong></summary>

<dl>
<dd>
<h2></h2>

Каждый незавершённый рекурсивный вызов обычно занимает место в стеке вызовов.

Если глубина рекурсии равна `n`, вспомогательная пространственная сложность может быть `O(n)`, даже если функция не создаёт массивы, `Set` или другие коллекции.

Например, рекурсивный обход связного списка использует `O(n)` памяти стека, а итеративный вариант с одной переменной может использовать `O(1)` вспомогательной памяти.

Для сбалансированного бинарного дерева глубина обычно составляет `O(log n)`, а для вырожденного дерева может достигать `O(n)`.

JavaScript не гарантирует оптимизацию хвостовой рекурсии во всех используемых средах, поэтому стек вызовов обычно нужно учитывать явно.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```ts
function getSelectedItems(items: Item[], selectedIds: string[]) {
  const selectedSet = new Set(selectedIds);

  return items.filter(item => selectedSet.has(item.id));
}
```

Пусть `n` — количество `items`, `s` — количество `selectedIds`, а `k` — количество элементов результата.

- Построение `Set` в типичной реализации требует `O(s)` времени и `O(s)` вспомогательной памяти.
- `filter()` проходит `items` за `O(n)`; каждая проверка `has()` в типичном случае занимает в среднем `O(1)`.
- Общая ожидаемая временная сложность — `O(n + s)`.
- Вспомогательная память без учёта результата — `O(s)`. Если считать созданный результат, добавляется `O(k)`.

ECMAScript не закрепляет конкретную внутреннюю структуру `Set`, поэтому оценка `O(1)` для `has()` является типичной инженерной оценкой реализации, а не требованием конкретного алгоритма хранения.

Вариант с `selectedIds.includes(item.id)` внутри `filter()` в худшем случае потребовал бы `O(n * s)` времени, но не создавал бы `Set`.

Это практический компромисс между временем и памятью.

## Где это встречается во frontend

| Ситуация | Как проявляется сложность |
| --- | --- |
| Проверка выбранных элементов | `includes()` для каждой строки может дать `O(n * s)`; `Set` сокращает повторные поиски ценой памяти |
| Поиск сущностей по `id` | индекс `Map<id, entity>` позволяет не выполнять `find()` по массиву при каждом обращении |
| Фильтрация и сортировка таблицы | повторный `filter().sort()` на каждом вводе может надолго занять основной поток браузера (main thread) |
| Вычисления во время React render | линейный проход становится заметным, если большой список пересчитывается при каждом обновлении компонента |
| Построение дерева | индекс по `parentId` помогает избежать повторного поиска дочерних узлов во всём массиве |
| Обработка прав доступа | `Set` удобен для множества повторных проверок, есть ли конкретное право у пользователя |
