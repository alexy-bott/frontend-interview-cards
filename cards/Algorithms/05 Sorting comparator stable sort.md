## Вопрос

<br>

 💬 **Как работает сортировка в JavaScript? Что важно знать о функции сравнения (comparator) и стабильной сортировке (stable sort)?**

<h2></h2>

<br>
<dl>
<dd>

`Array.prototype.sort()` изменяет исходный массив и возвращает ту же ссылку.

Без функции сравнения элементы преобразуются в строки и сравниваются по кодовым единицам UTF-16 (code units). Поэтому `[2, 10].sort()` даст `[10, 2]`: строка `"10"` располагается раньше строки `"2"`.

Элементы со значением `undefined` перемещаются в конец массива без вызова comparator.

Для числовой сортировки передают функцию сравнения:

```ts
items.sort((a, b) => a - b);
```

Comparator должен вернуть:

- отрицательное число, если `a` должно находиться перед `b`;
- положительное число, если `a` должно находиться после `b`;
- `0`, если элементы равны по выбранному критерию.

Важно только направление знака, а не конкретное значение `-1` или `1`.

Comparator должен задавать непротиворечивый порядок. Он должен быть чистым, возвращать одинаковый результат для одинаковых аргументов и не изменять сравниваемые данные.

Основные требования:

- сравнение элемента с самим собой должно возвращать `0`;
- если `a` располагается перед `b`, обратное сравнение должно располагать `b` после `a`;
- если `a` располагается перед `b`, а `b` перед `c`, то `a` не должно оказаться после `c`;
- элементы, равные по критерию, должны последовательно считаться равными.

Если comparator зависит от случайного значения, текущего времени или изменяемого внешнего состояния, результат может отличаться между запусками и JavaScript-движками.

Стабильная сортировка (stable sort) сохраняет исходный взаимный порядок элементов, между которыми comparator возвращает `0`.

Например, после сортировки сотрудников только по отделу сотрудники одного отдела останутся в прежнем взаимном порядке.

Начиная с ECMAScript 2019 стандарт требует стабильное поведение `Array.prototype.sort()`. Это позволяет выполнять последовательные сортировки, хотя один comparator с явными дополнительными критериями обычно понятнее и меньше зависит от истории предыдущих операций.

Стандарт JavaScript не закрепляет конкретный алгоритм сортировки, её временную сложность и расход вспомогательной памяти.

В современных движках сортировка обычно имеет порядок `O(n log n)`, но это типичная инженерная оценка, а не гарантия ECMAScript.

Comparator может вызываться много раз. Точное количество и порядок вызовов не являются публичным контрактом.

Если внутри comparator выполняется линейный поиск, разбор даты, форматирование или другой дорогой код, фактическая стоимость сортировки заметно возрастает. Значения, используемые для сравнения, выгодно подготовить заранее.

Для строк, которые видит пользователь, простого сравнения через `<` и `>` часто недостаточно: язык, регистр, диакритические знаки и числа внутри строк влияют на ожидаемый порядок.

`Intl.Collator` создаёт правило сравнения для нужной локали и может использоваться как comparator. Экземпляр collator создают один раз вне функции сравнения, а не при каждом её вызове.

Даты обычно сравнивают по числовой временной метке:

```ts
dateA.getTime() - dateB.getTime();
```

Невалидная дата возвращает `NaN`, поэтому отсутствующие и некорректные значения нужно обрабатывать отдельным предсказуемым правилом.

Если исходный массив нельзя изменять, используют `toSorted(compareFn)`, который возвращает новый массив. Метод появился в ECMAScript 2023.

В окружениях без его поддержки сначала создают копию:

```ts
[...items].sort(compareFn);
```

Это особенно важно для React и Redux state, где мутация существующего массива нарушает ожидаемую модель обновления по новой ссылке.

Однако создание копии защищает от мутации, но не устраняет стоимость самой сортировки. Большой список не следует без необходимости копировать и сортировать при каждом render.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему comparator вида <code>(a, b) =&gt; a &gt; b</code> написан неправильно?</strong></summary>

<dl>
<dd>
<h2></h2>

Такое выражение возвращает только `true` или `false`, которые преобразуются в `1` и `0`.

Оно может сообщить, что `a` должно находиться после `b`, но не возвращает отрицательное значение для обратного порядка. Например, при `a < b` comparator вернёт `0` и ошибочно объявит элементы равными.

В результате функция не задаёт антисимметричный и непротиворечивый порядок.

Для чисел используют:

```ts
(a, b) => a - b
```

Для строк можно вернуть результат `localeCompare()` или `Intl.Collator.compare`.

Для составных данных сначала сравнивают основной критерий, а при равенстве переходят к следующему.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужна stable sort и как сделать сортировку по нескольким полям?</strong></summary>

<dl>
<dd>
<h2></h2>

Stable sort сохраняет прежний порядок элементов, которые comparator считает равными, то есть возвращает для них `0`.

Это полезно, когда список уже отсортирован по имени, а затем сортируется по отделу: внутри каждого отдела прежний порядок по имени сохранится.

Более явно несколько критериев задают одним comparator:

```ts
const byDepartment = collator.compare(a.department, b.department);

if (byDepartment !== 0) {
  return byDepartment;
}

return collator.compare(a.name, b.name);
```

Сначала сравнивают главное поле. При равенстве переходят к следующему критерию.

Такой comparator не зависит от истории предыдущих сортировок и легче проверяется.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему вызов <code>sort()</code> может создать проблему в React или Redux?</strong></summary>

<dl>
<dd>
<h2></h2>

`sort()` переставляет элементы в исходном массиве.

Если этот массив пришёл через props, selector или state, компонент незаметно изменит данные, которыми может пользоваться другой код.

Ссылка на массив при этом останется прежней, что нарушает ожидаемую иммутабельность, мешает проверкам равенства по ссылке и может приводить к пропущенным или непредсказуемым обновлениям.

Безопасный вариант:

```ts
const sortedItems = items.toSorted(compareFn);
```

Или сортировка предварительной копии:

```ts
const sortedItems = [...items].sort(compareFn);
```

Однако копирование и сортировка требуют времени и памяти. Большой список не следует пересортировывать при каждом render без изменения исходных данных или критерия сортировки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как правильно сортировать строки, даты и отсутствующие значения?</strong></summary>

<dl>
<dd>
<h2></h2>

Пользовательские строки сортируют с учётом локали.

`Intl.Collator(locale, options)` позволяет настроить регистр, диакритические знаки и числовые фрагменты. Например, при `numeric: true` строка `item2` располагается раньше `item10`.

Один экземпляр collator создают заранее:

```ts
const collator = new Intl.Collator("ru", {
  sensitivity: "base",
  numeric: true,
});
```

Даты сравнивают как числовые временные метки:

```ts
dateA.getTime() - dateB.getTime();
```

Для `null`, `undefined` и невалидных дат сначала задают отдельное правило, например всегда помещать их в конец, а затем сравнивают обычные значения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Каким требованиям должна соответствовать функция сравнения?</strong></summary>

<dl>
<dd>
<h2></h2>

Comparator должен быть чистым, возвращать одинаковый результат для одинаковых аргументов и не изменять сравниваемые данные.

Основные свойства:

- рефлексивность: `compare(a, a)` возвращает `0`;
- антисимметричность: знаки `compare(a, b)` и `compare(b, a)` должны быть противоположными либо оба результата должны означать равенство;
- транзитивность: если `a` располагается перед `b`, а `b` перед `c`, то `a` должно располагаться перед `c`;
- согласованность равенства: равные по критерию значения должны последовательно давать `0`.

Если comparator зависит от случайного числа, текущего времени или изменяет элементы, движок получает противоречивые ответы при повторных сравнениях.

Порядок и количество вызовов comparator не являются публичным контрактом, поэтому побочные эффекты внутри него ненадёжны.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как сделать сортировку по убыванию и не сломать обработку <code>null</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Для чисел порядок можно развернуть через:

```ts
(a, b) => b - a
```

Для строк можно поменять аргументы:

```ts
collator.compare(b, a)
```

Или умножить результат сравнения существующих значений на `-1`.

Правило отсутствующих значений лучше обрабатывать отдельно:

```ts
function compareValues(
  a: number | null,
  b: number | null,
  direction: 1 | -1,
) {
  if (a === null && b === null) return 0;
  if (a === null) return 1;
  if (b === null) return -1;

  return (a - b) * direction;
}
```

Так `null` всегда остаётся в конце независимо от направления сортировки.

Если просто умножить весь comparator на `-1`, отсутствующие значения переместятся из конца в начало.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему дорогие значения для сортировки лучше вычислить заранее?</strong></summary>

<dl>
<dd>
<h2></h2>

Comparator вызывается многократно. В типичной сортировке количество сравнений имеет порядок `n log n`, но точное число не гарантируется стандартом.

Если внутри каждого сравнения разбирать дату, нормализовать строку или выполнять поиск в другой коллекции, эта работа повторяется для одних и тех же элементов.

Можно один раз подготовить ключи:

```ts
const preparedItems = items.map(item => ({
  value: item,
  sortKey: createSortKey(item),
}));

const sortedItems = preparedItems
  .toSorted((a, b) => compareSortKeys(a.sortKey, b.sortKey))
  .map(item => item.value);
```

Такой приём называют decorate-sort-undecorate.

Он добавляет `O(n)` памяти и отдельный проход для подготовки, но устраняет многократное дорогое вычисление одного и того же ключа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли передать в <code>sort()</code> асинхронный comparator?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. `sort()` работает синхронно и ожидает числовой результат comparator.

`async`-функция возвращает `Promise`, который не сообщает сортировке отрицательный, нулевой или положительный результат.

Асинхронные данные или ключи сначала получают отдельно:

```ts
const preparedItems = await Promise.all(
  items.map(async item => ({
    item,
    sortKey: await loadSortKey(item),
  })),
);
```

После завершения подготовки выполняют обычную синхронную сортировку по готовым значениям.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

Нужно отсортировать пользователей сначала по статусу `active`, `pending`, `blocked`, а внутри статуса — по имени с учётом локали.

```ts
const statusOrder = new Map([
  ["active", 0],
  ["pending", 1],
  ["blocked", 2],
]);

const collator = new Intl.Collator("ru", {
  sensitivity: "base",
});

const getStatusOrder = (status: string) => {
  return statusOrder.get(status) ?? Number.MAX_SAFE_INTEGER;
};

const sortedUsers = users.toSorted((a, b) => {
  const byStatus = getStatusOrder(a.status) - getStatusOrder(b.status);

  return byStatus || collator.compare(a.name, b.name);
});
```

Индекс порядка статусов подготавливается один раз.

Comparator сначала возвращает различие статусов, а при равенстве сравнивает имена.

Неизвестные статусы получают максимальный порядок и попадают в конец списка. Благодаря stable sort пользователи с одинаковым неизвестным статусом и одинаковым именем сохраняют прежний взаимный порядок.

`toSorted()` не изменяет исходный массив.

## Где это встречается во frontend

| Ситуация | Что важно |
| --- | --- |
| Таблица | comparator учитывает тип столбца, отсутствующие значения и направление сортировки |
| Локализованный список | строки сравниваются через `Intl.Collator`, а не напрямую по кодовым единицам UTF-16 |
| React или Redux state | используется `toSorted()` или копия, чтобы не мутировать исходный массив |
| Несколько критериев | при равенстве основного поля comparator переходит к дополнительному |
| Большой список | сортировка не повторяется без изменения данных или критерия; измеряется работа на основном потоке браузера (main thread) |
