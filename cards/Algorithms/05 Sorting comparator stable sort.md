## Вопрос

Как работает сортировка в JavaScript? Что важно знать о функции сравнения (comparator) и стабильной сортировке (stable sort)?

<details>
<summary><strong>Показать ответ</strong></summary>

`Array.prototype.sort()` изменяет исходный массив и возвращает ту же ссылку. Без функции сравнения элементы преобразуются в строки и сравниваются по кодовым единицам UTF-16 (code units). Поэтому `[2, 10].sort()` даст `[10, 2]`: строка `"10"` располагается раньше строки `"2"`.

Для числовой сортировки передают функцию сравнения (comparator): `items.sort((a, b) => a - b)`. Если результат отрицательный, `a` ставится перед `b`; если положительный - после `b`; если равен нулю, элементы считаются равными по выбранному критерию.

Comparator должен задавать непротиворечивый порядок. Он не должен изменять сравниваемые значения или зависеть от случайного внешнего состояния. Если `a` идёт раньше `b`, обратное сравнение должно поставить `b` после `a`. Если `a` равно `b`, а `b` равно `c` по критерию сортировки, сравнения не должны одновременно требовать несовместимого порядка. Нарушение этих правил может дать разные результаты в разных движках.

Стабильная сортировка (stable sort) сохраняет исходный взаимный порядок элементов, которые comparator считает равными. Например, после сортировки сотрудников только по отделу сотрудники одного отдела останутся в прежнем порядке. Начиная с ECMAScript 2019 стандарт требует стабильное поведение `Array.prototype.sort()`. Это позволяет выполнять последовательные сортировки, хотя один comparator с явными дополнительными критериями обычно понятнее.

Стандарт JavaScript не закрепляет конкретный алгоритм и его Big O. В современных движках сортировка обычно имеет порядок `O(n log n)`, но comparator может вызываться много раз. Если внутри него выполняется линейный поиск, форматирование или другой дорогой код, фактическая стоимость сортировки заметно возрастает. Значения, используемые для сравнения, выгодно подготовить заранее.

Для строк, которые видит пользователь, простого сравнения через `<` и `>` часто недостаточно: язык, регистр и числа внутри строк влияют на ожидаемый порядок. `Intl.Collator` создаёт правило сравнения для нужной локали и переиспользуется как comparator. Даты обычно сравнивают по числовой временной метке (timestamp), а отсутствующие значения обрабатывают отдельным правилом, чтобы их положение было предсказуемым.

Если исходный массив нельзя изменять, используют `toSorted(compareFn)`, который возвращает новый массив. Метод появился в ECMAScript 2023. В окружениях без его поддержки сначала создают копию: `[...items].sort(compareFn)`. Это особенно важно для React и Redux state, где мутация существующего массива нарушает ожидаемую модель обновления по новой ссылке.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Почему comparator вида <code>(a, b) =&gt; a &gt; b</code> написан неправильно?</summary>

Такое выражение возвращает только `true` или `false`, которые преобразуются в `1` и `0`. Оно может сказать, что `a` должно идти после `b`, но не возвращает отрицательное значение для обратного порядка. В результате comparator не задаёт симметричное и непротиворечивое сравнение.

Для чисел используют `(a, b) => a - b`. Для строк можно вернуть результат `localeCompare()` или `Intl.Collator.compare`. Для составных данных сначала сравнивают основной критерий, а при равенстве переходят к следующему.

</details>

<details>
<summary><strong>Вопрос:</strong> Зачем нужна stable sort и как сделать сортировку по нескольким полям?</summary>

Stable sort сохраняет прежний порядок элементов с одинаковым значением критерия. Это полезно, когда список уже отсортирован по имени, а затем сортируется по отделу: внутри каждого отдела порядок по имени сохранится.

Более явно несколько критериев задают одним comparator. Сначала сравнивают главное поле, например статус. Если результат не равен нулю, его возвращают. При равенстве сравнивают следующее поле, например имя. Такой comparator не зависит от истории предыдущих сортировок и легче проверяется.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему вызов <code>sort()</code> может создать проблему в React или Redux?</summary>

`sort()` переставляет элементы в исходном массиве. Если этот массив пришёл через props (входные данные компонента), из selector (функции выбора производных данных) или state (состояния), компонент незаметно изменит данные, которыми может пользоваться другой код. Ссылка на массив при этом останется прежней, что мешает проверкам равенства по ссылке и может приводить к пропущенным или непредсказуемым обновлениям.

Безопасный вариант - `toSorted(compareFn)` или сортировка предварительной копии. Однако копирование и сортировка тоже требуют времени и памяти, поэтому большой список не следует пересортировывать при каждом render (расчёте представления компонента) без изменения исходных данных или выбранного порядка.

</details>

<details>
<summary><strong>Вопрос:</strong> Как правильно сортировать строки, даты и отсутствующие значения?</summary>

Пользовательские строки сортируют с учётом локали. `Intl.Collator(locale, options)` позволяет настроить регистр и числовые фрагменты, например расположить `item2` раньше `item10` при `numeric: true`. Один экземпляр collator лучше создать заранее, а не внутри каждого вызова comparator.

Даты сравнивают как числовые значения, например `dateA.getTime() - dateB.getTime()`. Для `null` и других отсутствующих значений сначала задают отдельное правило: например, всегда помещать их в конец, а затем сравнивать обычные значения.

</details>

<details>
<summary><strong>Вопрос:</strong> Каким требованиям должна соответствовать функция сравнения?</summary>

Она должна возвращать одинаковый результат для одних и тех же аргументов, не изменять сравниваемые данные и задавать согласованный порядок. Для равных по критерию значений результат равен нулю. Знак `compare(a, b)` должен быть противоположен знаку `compare(b, a)`, а транзитивность требует: если `a` раньше `b`, а `b` раньше `c`, то `a` не может оказаться после `c`.

Если comparator зависит от случайного числа, текущего времени или меняет элементы, движок получает противоречивые ответы при повторных сравнениях. Порядок вызовов comparator не является публичным контрактом, поэтому побочные эффекты внутри него также ненадёжны.

</details>

<details>
<summary><strong>Вопрос:</strong> Как сделать сортировку по убыванию и не сломать обработку <code>null</code>?</summary>

Для чисел порядок можно развернуть через `(a, b) => b - a`, для строк - поменять аргументы `collator.compare(b, a)` или умножить результат обычного сравнения на `-1`. Но правило отсутствующих значений лучше обработать отдельно.

Если `null` должен всегда оставаться в конце, сначала проверяют `null`, а направление применяют только к двум существующим значениям. Иначе простое умножение всего результата на `-1` перенесёт отсутствующие значения из конца в начало.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему дорогие значения для сортировки лучше вычислить заранее?</summary>

Comparator вызывается многократно, обычно порядка `n log n` раз. Если внутри каждого сравнения разбирать дату, нормализовать строку или выполнять поиск в другой коллекции, эта работа повторяется для одних и тех же элементов.

Можно один раз создать элементы вида `{ value, sortKey }`, отсортировать их по готовому `sortKey`, а затем извлечь `value`. Такой приём называют decorate-sort-undecorate. Он добавляет `O(n)` памяти и подготовку ключей, но устраняет повторное дорогое вычисление.

</details>

<details>
<summary><strong>Вопрос:</strong> Можно ли передать в <code>sort()</code> асинхронный comparator?</summary>

Нет. `sort()` работает синхронно и ожидает число. `async`-функция возвращает `Promise`, который не сообщает сортировке нужный знак; результат не будет корректным контрактом сравнения.

Асинхронные данные или ключи сначала получают отдельно, например через `Promise.all()`. После завершения подготовки выполняют обычную синхронную сортировку по готовым значениям.

</details>

## Мини-задача

Нужно отсортировать пользователей сначала по статусу `active`, `pending`, `blocked`, а внутри статуса - по имени с учётом локали.

```ts
const statusOrder = new Map([
  ["active", 0],
  ["pending", 1],
  ["blocked", 2],
]);

const collator = new Intl.Collator("ru", { sensitivity: "base" });

const sortedUsers = users.toSorted((a, b) => {
  const byStatus = statusOrder.get(a.status)! - statusOrder.get(b.status)!;
  return byStatus || collator.compare(a.name, b.name);
});
```

Индекс порядка статусов подготавливается один раз. Comparator сначала возвращает различие статусов, а при равенстве сравнивает имена. `toSorted()` не изменяет исходный массив.

## Где это встречается во frontend

> [!NOTE]
> | Ситуация | Что важно |
> | --- | --- |
> | Таблица | comparator учитывает тип столбца, отсутствующие значения и направление сортировки |
> | Локализованный список | строки сравниваются через `Intl.Collator`, а не напрямую по кодовым единицам UTF-16 |
> | React или Redux state | используется `toSorted()` или копия, чтобы не мутировать исходный массив |
> | Несколько критериев | при равенстве основного поля comparator переходит к дополнительному |
> | Большой список | сортировка не повторяется без изменения данных или критерия; измеряется работа на основном потоке браузера (main thread) |
