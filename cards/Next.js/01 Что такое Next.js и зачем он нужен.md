## Вопрос

<br>

 💬 **Что такое Next.js и зачем он нужен поверх React?**

<h2></h2>

<br>
<dl>
<dd>

Next.js — React-фреймворк для создания полноценных веб-приложений.

React предоставляет модель компонентов и обновления интерфейса, а Next.js добавляет готовую структуру приложения:

- файловую маршрутизацию;
- серверный и статический рендеринг;
- загрузку и кэширование данных;
- обработчики HTTP-запросов;
- серверные mutations;
- метаданные;
- оптимизацию изображений и шрифтов;
- сборку;
- способы развёртывания.

Next.js поддерживает два маршрутизатора:

- App Router внутри каталога `app`;
- Pages Router внутри каталога `pages`.

Новые приложения обычно рассматривают App Router, построенный на React Server Components, Suspense и Server Functions.

В App Router маршруты создаются из папок и специальных файлов внутри `app`.

Компоненты по умолчанию являются React Server Components. Они выполняются в серверной среде во время сборки или обработки запроса, могут получать данные напрямую и не добавляют собственный JavaScript в клиентский bundle.

Для интерактивного интерфейса используют Client Components.

Директива:

```tsx
"use client";
```

создаёт границу клиентского модуля. Сам файл и импортируемые им модули становятся частью клиентского графа. Поэтому директиву не нужно добавлять в каждый вложенный компонент отдельно.

Client Component не означает, что компонент всегда рендерится только после загрузки JavaScript в браузере.

При первом открытии страницы Next.js может использовать его результат при создании HTML, а затем React гидратирует этот компонент — подключает к HTML состояние и обработчики событий.

Server Components не гидратируются. Они передают браузеру сериализованный RSC Payload, который React использует для согласования серверного и клиентского дерева.

Next.js позволяет сочетать разные способы формирования интерфейса:

- prerendering во время сборки для данных, известных заранее;
- формирование результата во время запроса;
- кэширование с обновлением по времени или событию;
- streaming через Suspense;
- клиентскую загрузку данных после взаимодействия;
- статическую оболочку с динамическими участками.

Это не обязательно взаимоисключающие режимы всей страницы. Разные части одного маршрута могут формироваться и доставляться по-разному.

Конкретные правила кэширования зависят от версии Next.js, используемых API и конфигурации приложения. Поэтому нельзя полагаться на универсальное утверждение вроде «все `fetch` автоматически кэшируются» или «вся страница всегда динамическая».

Next.js особенно полезен для:

- публичных индексируемых страниц;
- каталогов и интернет-магазинов;
- контентных сайтов;
- персонализированных кабинетов;
- приложений со смешанным серверным и клиентским интерфейсом;
- страниц, которым нужны данные до загрузки клиентского JavaScript.

Route Handlers позволяют создавать HTTP endpoints через стандартные Web API `Request` и `Response`.

Server Functions, используемые как Actions, позволяют вызывать серверный код из интерфейса и предназначены прежде всего для mutations — например, отправки формы или изменения данных.

Route Handlers и Server Functions могут образовывать BFF, или backend for frontend: серверный слой, адаптирующий данные и операции под потребности конкретного интерфейса.

При этом они решают разные задачи:

```text
Route Handler → HTTP endpoint
Server Function / Action → серверная операция, вызываемая приложением
```

Server Function не следует считать обычным публичным REST endpoint.

Серверный код может обращаться к базе данных, внутренним API и secret-переменным, но это не делает операцию безопасной автоматически.

В каждой Server Function и Route Handler всё равно проверяют:

- входные данные;
- authentication;
- authorization;
- допустимость операции;
- безопасный формат ответа.

Next.js также не обязан заменять основной backend. Сложная предметная логика, независимые сервисы, фоновые задачи и интеграции могут оставаться в отдельной серверной системе.

Next.js не делает приложение автоматически быстрым или безопасным.

Нужно понимать:

- границу между серверным и клиентским кодом;
- правила кэширования;
- размер клиентского bundle;
- последовательность серверных запросов;
- способ развёртывания;
- ограничения runtime;
- правила доступа к данным.

Слишком высокая граница `"use client"` может отправить в браузер лишний код. Ошибочно закэшированные персональные данные могут попасть не тому пользователю. Последовательные серверные запросы могут создать waterfall и увеличить время ответа.

Next.js может быть избыточен для небольшого SPA, где:

- не нужен серверный HTML;
- индексирование не важно;
- серверные возможности фреймворка не используются;
- достаточно статического хостинга;
- маршрутизация и server state уже решены клиентскими библиотеками.

В таком случае React с Vite, React Router и библиотекой управления server state может дать более простую сборку и развёртывание.

Выбор зависит от требований продукта, а не от предположения, что Next.js является обязательным дополнением к React.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему Next.js называют фреймворком, а React библиотекой?</strong></summary>

<dl>
<dd>
<h2></h2>

React предоставляет модель создания пользовательского интерфейса из компонентов.

Он не требует конкретной:

- файловой маршрутизации;
- структуры приложения;
- стратегии загрузки данных;
- серверной среды;
- системы кэширования;
- платформы развёртывания.

Next.js задаёт соглашения и готовые механизмы для всего приложения:

- маршруты;
- layouts;
- Server и Client Components;
- серверный и статический рендеринг;
- HTTP endpoints;
- Server Functions;
- кэширование;
- metadata;
- production build.

Поэтому Next.js сильнее определяет структуру и жизненный цикл приложения, что характерно для фреймворка.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит при первом открытии страницы App Router?</strong></summary>

<dl>
<dd>
<h2></h2>

Next.js выполняет Server Components во время сборки или обработки запроса и формирует RSC Payload — сериализованное представление серверного дерева.

На сервере RSC Payload и Client Components используются для создания начального HTML.

Браузер:

1. получает и показывает HTML;
2. использует RSC Payload для согласования Server и Client Component trees;
3. загружает JavaScript Client Components;
4. гидратирует Client Components и подключает их обработчики и состояние.

Server Components не гидратируются и не загружаются в браузер как клиентские компоненты.

При последующей навигации через Next.js Router браузер обычно получает RSC Payload для нового состояния маршрута без полной перезагрузки документа. Next.js использует его для обновления нужных сегментов и сохранения общих layouts там, где это возможно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Даёт ли Next.js SEO автоматически?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Next.js предоставляет инструменты:

- серверный и статический HTML;
- Metadata API;
- `sitemap`;
- `robots`;
- Open Graph metadata;
- управление canonical URL;
- оптимизацию загрузки ресурсов.

Но SEO зависит также от:

- качества и полноты содержимого;
- семантической HTML-разметки;
- доступности;
- скорости;
- корректных HTTP-статусов;
- внутренних ссылок;
- отсутствия дублирующихся страниц;
- возможности поискового робота получить нужный контент.

Само использование Next.js не исправляет пустую страницу, неправильные метаданные или плохую структуру документа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое BFF в Next.js?</strong></summary>

<dl>
<dd>
<h2></h2>

Backend for frontend — серверный слой, адаптирующий данные и операции под конкретный интерфейс.

Route Handler может:

- предоставить HTTP endpoint;
- объединить ответы нескольких backend API;
- скрыть server-only credentials;
- нормализовать формат ответа;
- установить cookie;
- проверить права доступа.

Server Function может обработать mutation из интерфейса:

- отправить форму;
- изменить сущность;
- выполнить серверную валидацию;
- обновить или инвалидировать кэш;
- вернуть состояние операции.

Оба варианта должны самостоятельно проверять входные данные, authentication и authorization.

BFF не должен без необходимости дублировать весь основной backend и предметную логику системы. Его задача — адаптировать серверные возможности под потребности конкретного frontend.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда Next.js может быть лишним?</strong></summary>

<dl>
<dd>
<h2></h2>

Next.js может быть избыточен, когда приложение является внутренним SPA и для него:

- не важен начальный серверный HTML;
- не требуется поисковое индексирование;
- не используются Server Components и Server Functions;
- не нужен BFF;
- предпочтителен простой статический хостинг;
- достаточно клиентской маршрутизации.

В таком случае Vite с React Router и библиотекой управления server state может дать более простую архитектуру, сборку и инфраструктуру.

При этом наличие внутреннего кабинета само по себе не запрещает Next.js. Он может быть полезен, если нужны серверная проверка доступа, streaming, общие layouts или получение данных до загрузки клиентского JavaScript.

Сложность фреймворка должна решать конкретные требования продукта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Обязательно ли размещать Next.js на Vercel?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Next.js можно развернуть как:

- Node.js-сервер;
- Docker-контейнер;
- static export;
- приложение через поддерживаемый платформенный adapter.

Node.js-сервер и Docker обычно позволяют использовать все основные серверные возможности Next.js.

Static export создаёт статические файлы и подходит только для функций, которые не требуют runtime-сервера. Возможности вроде обработки запроса на сервере должны быть либо исключены, либо заменены совместимым решением.

При самостоятельном размещении нужно проверить:

- поддержку streaming;
- хранение и синхронизацию общего кэша;
- revalidation и ISR;
- оптимизацию изображений;
- работу Server Functions;
- корректную маршрутизацию;
- graceful shutdown;
- согласованность нескольких экземпляров приложения.

Vercel предоставляет готовую интеграцию, но не является обязательной платформой для Next.js.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Требование | Возможность Next.js |
| --- | --- |
| Публичная индексируемая страница | Prerendered или request-time HTML, Metadata API |
| Персональный кабинет | Server Components, динамические данные и Client Components |
| Данные до загрузки клиентского JS | Server Components |
| HTTP endpoint рядом с UI | Route Handler |
| Отправка формы на сервер | Server Function / Action |
| Самостоятельное развёртывание | Node.js, Docker, adapter или static export |
