## Вопрос

<br>

 💬 **Чем отличаются SSR, SSG, ISR, streaming и hydration в Next.js?**

<h2></h2>

<br>
<dl>
<dd>

Эти термины описывают разные этапы.

SSR, SSG и ISR отвечают, когда сервер формирует результат маршрута и может ли он переиспользоваться.

Streaming, или потоковая передача, определяет, отправляется ли результат целиком или частями.

Hydration, или гидратация, отвечает за подключение интерактивности Client Components к сформированному HTML.

React Server Components являются отдельной компонентной моделью и могут участвовать во всех этих вариантах.

Ниже описана модель App Router в Next.js 14. В более новых версиях с Cache Components правила и API кэширования могут отличаться.

**SSR (server-side rendering), или серверный рендеринг,** означает формирование результата на сервере для конкретного запроса.

В App Router точнее говорить о динамическом рендеринге во время запроса.

Он нужен для данных, которые нельзя определить заранее:

- персонального содержимого;
- cookies;
- headers;
- параметров запроса;
- актуальных данных без серверного кэширования.

Динамически сформированный маршрут не сохраняется во внутреннем Full Route Cache.

При этом отдельные источники данных внутри него всё ещё могут использовать Data Cache или другой серверный кэш:

```text
динамический route
  ├── персональные данные без кэша
  └── общий справочник из Data Cache
```

Поэтому SSR не означает автоматически, что в приложении вообще ничего не кэшируется.

**SSG (static site generation), или статическая генерация,** означает prerendering маршрута заранее во время `next build`.

Next.js сохраняет:

- HTML;
- RSC Payload.

Они попадают в Full Route Cache и могут переиспользоваться между запросами и пользователями.

SSG подходит для:

- документации;
- статей;
- маркетинговых страниц;
- публичных данных, одинаковых для всех пользователей.

**ISR (incremental static regeneration), или инкрементальная статическая регенерация,** позволяет обновлять сохранённый статический результат после deployment без новой полной сборки приложения.

В Next.js 14 обновление может выполняться:

- по времени;
- по событию через path;
- по событию через tag.

При time-based revalidation первый запрос после истечения интервала обычно получает прежний сохранённый результат и запускает обновление в фоне.

После успешной регенерации следующие запросы получают новую версию.

Если обновление завершается ошибкой, Next.js продолжает использовать последнее успешно сохранённое значение и повторит попытку позднее.

При on-demand revalidation через:

```ts
revalidatePath()
```

или:

```ts
revalidateTag()
```

соответствующие записи помечаются для обновления. Перестроение происходит при следующем посещении затронутого пути, а не обязательно немедленно для всех возможных URL.

При вызове revalidation из Server Action Next.js также может вернуть обновлённый интерфейс в том же серверном взаимодействии.

**Streaming** означает постепенную отправку интерфейса.

Сервер может сначала передать:

- общий layout;
- навигацию;
- быстрые части страницы;
- fallback медленных участков.

Затем готовые части подставляются через Suspense без ожидания завершения всего дерева.

`loading.tsx` создаёт Suspense Boundary на уровне route segment, а ручной `<Suspense>` позволяет разделить страницу точнее.

Streaming уменьшает время до первого полезного содержимого и позволяет не блокировать всю страницу одним медленным запросом.

При этом он:

- не ускоряет сам источник данных;
- не уменьшает длительность медленной операции;
- не делает Client Component интерактивным до загрузки его JavaScript.

**Hydration**, или гидратация, подключает клиентский React к HTML, сформированному на сервере.

Next.js использует RSC Payload для согласования серверного и клиентского дерева, а JavaScript Client Components:

- подключает обработчики событий;
- активирует состояние;
- запускает эффекты;
- делает интерфейс интерактивным.

Server Components сами не гидратируются, потому что их реализация не загружается в браузер.

В Next.js 14 маршрут переходит к динамическому рендерингу, если использует request-time данные или явно отключает статическое формирование, например:

- `cookies()`;
- `headers()`;
- свойство страницы `searchParams`;
- `fetch` с `cache: "no-store"`;
- `fetch` с `next: { revalidate: 0 }`;
- `export const dynamic = "force-dynamic"`.

Статический или динамический способ формирования маршрута не следует смешивать со способом кэширования каждого источника данных.

Динамический маршрут может использовать кэшированные запросы, а статический маршрут может обновляться через ISR.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>SSR и Server Components являются одним и тем же?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

SSR описывает формирование HTML на сервере для конкретного запроса.

При SSR сервер может предварительно сформировать HTML как для Server Components, так и для Client Components.

Server Components описывают другую границу:

- их реализация выполняется только в серверной среде;
- их код не попадает в клиентский bundle;
- результат передаётся через RSC Payload;
- они сами не гидратируются.

В Next.js эти механизмы работают вместе, но решают разные задачи.

Один Server Component может участвовать:

- в статическом prerendering;
- в динамическом request-time rendering;
- в ISR;
- в streaming.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем SSG отличается от ISR?</strong></summary>

<dl>
<dd>
<h2></h2>

SSG создаёт сохранённый результат маршрута во время сборки.

Без настроенной revalidation этот результат остаётся прежним до следующего deployment или явной инвалидации.

ISR использует ту же идею сохранённого статического результата, но добавляет возможность обновлять его после deployment:

- через интервал времени;
- через `revalidatePath()`;
- через `revalidateTag()`.

В обоих случаях пользователь обычно получает уже сохранённые HTML и RSC Payload.

Главное различие — наличие политики обновления.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как работает <code>revalidate: 60</code> в Next.js 14?</strong></summary>

<dl>
<dd>
<h2></h2>

Поведение зависит от места настройки.

Для конкретного `fetch`:

```ts
fetch(url, {
  next: {
    revalidate: 60,
  },
});
```

значение разрешает хранить ответ в Data Cache и повторно проверять его не чаще заданного интервала.

На уровне route segment:

```ts
export const revalidate = 60;
```

значение задаёт revalidation для статически сформированного маршрута и является значением по умолчанию для запросов, которые не установили собственное правило.

В течение интервала используется сохранённый результат.

Первый запрос после истечения интервала обычно:

1. получает прежнее значение;
2. запускает обновление в фоне.

Если обновление успешно, кэш заменяется.

Если источник недоступен, последнее успешно сохранённое значение остаётся доступным, а Next.js повторяет обновление позднее.

Такое поведение похоже на stale-while-revalidate.

Если в одном статическом маршруте несколько запросов задают разные интервалы, на частоту обновления результата маршрута влияет наименьшее значение.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что даёт streaming пользователю?</strong></summary>

<dl>
<dd>
<h2></h2>

Пользователь раньше видит готовые части страницы, не ожидая самого медленного блока.

Например:

```text
layout и навигация → сразу
карточка пользователя → быстро
большой отчёт → позже
```

Fallback внутри Suspense показывает временное состояние только для незавершённого участка:

```tsx
<Suspense fallback={<ReportSkeleton />}>
  <SlowReport />
</Suspense>
```

Streaming улучшает воспринимаемую скорость и позволяет начать чтение или взаимодействие с уже готовыми участками.

Но он не уменьшает фактическое время выполнения `SlowReport`.

Также нужно избегать большого числа несогласованных Suspense Boundaries, иначе интерфейс будет появляться хаотичными фрагментами и создавать layout shifts.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему возникает hydration mismatch?</strong></summary>

<dl>
<dd>
<h2></h2>

Hydration mismatch возникает, когда первый render Client Component в браузере не совпадает с HTML, сформированным сервером.

Причинами могут быть:

- `Date.now()`;
- `Math.random()`;
- разные локаль или часовой пояс;
- чтение `window` или `localStorage` во время render;
- разные данные на сервере и клиенте;
- невалидная вложенность HTML;
- изменение DOM браузерным расширением до hydration.

Например, такой код может сформировать разные значения:

```tsx
export function Timestamp() {
  return <span>{Date.now()}</span>;
}
```

Первый клиентский результат должен совпадать с серверным HTML.

Значение, доступное только в браузере, обычно читают после mount:

```tsx
"use client";

import { useEffect, useState } from "react";

export function Theme() {
  const [theme, setTheme] = useState<string | null>(null);

  useEffect(() => {
    setTheme(localStorage.getItem("theme"));
  }, []);

  return <span>{theme}</span>;
}
```

Hydration mismatches нужно считать ошибками. React может восстановиться после некоторых несовпадений, но это может привести к лишнему render, потере производительности или неправильному связыванию интерфейса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли динамический route медленный?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Динамический route формируется во время запроса, но его производительность зависит от:

- времени получения данных;
- объёма серверной работы;
- сети;
- runtime;
- платформы размещения;
- используемых кэшей;
- возможности выполнять запросы параллельно;
- структуры Suspense Boundaries.

Он может использовать:

- Data Cache;
- кэш базы данных;
- CDN для отдельных ресурсов;
- параллельные запросы;
- streaming.

Статический маршрут обычно дешевле обслуживать и проще масштабировать, потому что результат уже сформирован.

Но он не подходит, если HTML должен зависеть от cookies, прав пользователя или других данных конкретного запроса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли на одной странице сочетать статические и динамические данные?</strong></summary>

<dl>
<dd>
<h2></h2>

Да, но в Next.js 14 нужно различать кэширование данных и кэширование полного результата маршрута.

Если маршрут использует некэшированный запрос или request-time API, он не сохраняется в Full Route Cache.

При этом другие `fetch` внутри него могут продолжать использовать Data Cache:

```text
динамический route
  ├── cookies пользователя
  ├── персональный запрос без кэша
  └── общий каталог из Data Cache
```

Streaming позволяет независимо показывать быстрые и медленные части такого маршрута.

Полноценная модель, при которой статическая оболочка маршрута сохраняется отдельно, а динамические участки потоково добавляются для запроса, в Next.js 14 относилась к экспериментальному Partial Prerendering, или PPR.

Поэтому фраза «на странице есть статический компонент» сама по себе не означает, что весь маршрут попадёт в Full Route Cache.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Подход |
| --- | --- |
| Документация | SSG |
| Профиль по cookies | Динамический серверный рендеринг |
| Каталог с редкими изменениями | ISR |
| Dashboard с медленными блоками | Streaming и Suspense |
| Интерактивная форма | Серверный HTML с hydration Client Component |
