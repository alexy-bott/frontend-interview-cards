## Вопрос

<br>

 💬 **Какие бывают стратегии deploy? Как связаны health checks, smoke tests и rollback?**

<h2></h2>

<br>
<dl>
<dd>

Deploy, или развёртывание, переводит окружение с одной версии на другую. Безопасная процедура знает точный артефакт, порядок переключения, критерии готовности, наблюдаемые метрики и способ восстановления. Перед выпуском образ или статический релиз получают неизменяемый идентификатор, например commit SHA и digest; tag `latest` не подходит как единственная запись версии.

Recreate, или полная замена, останавливает старую версию и затем запускает новую. Это самый простой вариант, но между остановкой и готовностью возникает недоступность. Для внутреннего стенда она может быть допустима. В production чаще используют стратегию, при которой старая версия продолжает обслуживать пользователей, пока новая не прошла проверку.

Rolling update, или постепенное обновление, по очереди заменяет экземпляры. Новый контейнер начинает получать трафик только после readiness check - проверки готовности обслуживать запросы. Стратегия требует нескольких экземпляров и совместимости старой и новой версий во время перехода. Если новый экземпляр ошибочен, rollout останавливают до замены остальных.

Blue-green держит два полных окружения: blue обслуживает трафик, green получает новый релиз и проверяется. После smoke-тестов маршрутизатор переключает трафик на green. Откат быстрый, пока blue сохранён, но удваиваются ресурсы и нужно отдельно контролировать общие базы, очереди и config.

Canary, или ограниченный выпуск, направляет небольшой процент трафика или выбранную аудиторию на новую версию. Команда сравнивает ошибки, задержку, Web Vitals и успешность критичных сценариев, затем расширяет долю. Canary полезен для обнаружения production-зависимых проблем, но требует точного определения версии пользователя и достаточного объёма метрик. Случайное смешивание версий в одной сессии может нарушить frontend, поэтому маршрутизация часто закрепляет пользователя за вариантом.

Для статической SPA стратегия выглядит иначе: процессов приложения может не быть. Файлы публикуют в новый версионированный каталог или префикс хранилища, проверяют, а затем атомарно переключают указатель или `index.html`. Старые файлы с хешем не удаляют сразу, чтобы открытые вкладки и прежний HTML могли догрузить chunks. CDN должен получить согласованную политику кэша, а не случайную массовую очистку.

Startup check отвечает, завершил ли процесс начальную загрузку. Liveness check определяет, нужно ли перезапустить зависший процесс. Readiness check решает, можно ли направлять ему трафик. Liveness не должна падать только из-за временно недоступного внешнего API, иначе все экземпляры начнут перезапускаться одновременно. Readiness может учитывать необходимые локальные ресурсы и критичную зависимость, но проверка должна быть быстрой и устойчивой.

Docker `HEALTHCHECK` даёт один общий статус контейнера. Оркестратор вроде Kubernetes разделяет startup, liveness и readiness probes и управляет трафиком и перезапуском. Сам служебный endpoint не должен возвращать секреты и дорогую диагностику. Ответ `200` означает только заранее определённую готовность, а не полную исправность пользовательского сценария.

Smoke test выполняется снаружи после deploy. Он проверяет DNS/TLS, маршрутизацию, HTML, chunks, runtime config и критичный API или действие. Rollout продолжают только при успешных probes, smoke-тестах и допустимых метриках. Автоматический откат полезен при однозначном сигнале, но шумный alert может создать колебание версий; для сложных симптомов безопаснее остановить расширение и принять решение по инструкции инцидента (`runbook`).

Rollback требует больше, чем старый frontend-артефакт. Новая версия API должна временно поддерживать старого клиента, runtime config - старые поля, а миграции данных - обратный путь или исправление следующей версией (`roll forward`). Без этой совместимости переключение образа не восстановит систему. Поэтому контрактные изменения выпускают по схеме expand and contract - «расширить, затем сузить»: сначала добавляют совместимую возможность, затем обновляют клиентов и только после переходного окна удаляют старую.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Как rolling update обеспечивает работу без простоя?</strong></summary>

<dl>
<dd>
<h2></h2>

Оркестратор запускает часть новых экземпляров, ждёт readiness и только затем удаляет часть старых. Параметры вроде `maxUnavailable` ограничивают число недоступных экземпляров, а `maxSurge` - число временно добавленных. При одном экземпляре и отсутствии дополнительной ёмкости гарантировать непрерывность невозможно.

Работа без простоя (`zero downtime`) также требует совместимого API, config и схемы данных. Работающие контейнеры не помогут, если новый frontend вызывает операцию, которую часть backend-экземпляров ещё не поддерживает.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем blue-green отличается от canary?</strong></summary>

<dl>
<dd>
<h2></h2>

Blue-green подготавливает полное параллельное окружение и обычно переключает на него весь трафик одним действием. Canary начинает с малой доли реальных пользователей и расширяется по метрикам. Blue-green даёт быстрое обратное переключение, canary уменьшает первоначальный масштаб неизвестной ошибки.

Их можно сочетать: green сначала получает canary-трафик, а затем становится основным окружением. Цена - более сложная маршрутизация и наблюдаемость.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем liveness check отличается от readiness check?</strong></summary>

<dl>
<dd>
<h2></h2>

Liveness отвечает, имеет ли смысл перезапустить экземпляр: процесс завис или не может продолжать работу. Readiness отвечает, можно ли сейчас отправлять ему пользовательский трафик. Неготовый экземпляр может оставаться запущенным и восстановиться без restart.

Если liveness зависит от общего внешнего API, его сбой перезапустит все здоровые frontend-серверы и усилит инцидент. Поэтому liveness проверяет локальную жизнеспособность, а readiness - необходимые условия обслуживания.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что должен проверять health endpoint frontend-сервера?</strong></summary>

<dl>
<dd>
<h2></h2>

Для Nginx со статической SPA достаточно подтвердить, что процесс отвечает и основной файл доступен локально. Для Next.js SSR readiness дополнительно может проверять загрузку конфигурации и возможность обработать простой server route. Проверка должна иметь короткий timeout и не выполнять тяжёлый пользовательский сценарий.

Версию release можно вернуть отдельным безопасным endpoint или header. Секреты, внутренние stack traces и полный environment в health response не публикуют.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему успешного health check недостаточно?</strong></summary>

<dl>
<dd>
<h2></h2>

Локальная probe может пройти, хотя DNS направляет не туда, CDN отдаёт старый HTML, TLS истёк или chunk отсутствует. Smoke test идёт по внешнему пользовательскому пути и проверяет интеграцию компонентов. Полный набор end-to-end тестов для каждого deploy слишком медленный и нестабильный, поэтому smoke ограничивают критичным минимумом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как атомарно выпустить статическую SPA?</strong></summary>

<dl>
<dd>
<h2></h2>

Новый набор файлов загружают в отдельный версионированный каталог, не меняя активный. Проверяют HTML и assets, затем одним переключением обновляют ссылку текущего релиза или публикуют новый `index.html` после всех chunks. Предыдущие файлы с хешем сохраняют на время, достаточное для старого HTML и открытых вкладок.

<h2></h2>
</dd>
</dl>

</details>

> Перезапись файлов на месте по одному создаёт смешанную версию. Инвалидация CDN-кэша не заменяет атомарную публикацию и может вернуть разные ответы в разных регионах.

<details>
<summary><strong>Что нужно сохранить для надёжного rollback?</strong></summary>

<dl>
<dd>
<h2></h2>

Artifact или image digest, config той версии, deployment manifest, сведения о миграциях и команду переключения. Предыдущий release должен оставаться доступным, а права и процедура - проверяться заранее. После переключения запускают тот же smoke test и наблюдают метрики, иначе факт запуска ошибочно принимается за восстановление.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выпустить frontend и backend без жёсткой синхронизации?</strong></summary>

<dl>
<dd>
<h2></h2>

Backend сначала добавляет новую операцию или поле, сохраняя старый контракт. Затем выпускается frontend, который умеет работать с переходным состоянием. После обновления активных клиентов и истечения срока старых версий backend удаляет устаревшую возможность. Для обязательного изменения API используют версионирование или capability check.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему database migration может помешать rollback frontend?</strong></summary>

<dl>
<dd>
<h2></h2>

Frontend зависит от API, а API - от схемы данных. Если migration удалила колонку или изменила смысл поля до обновления всех версий, старый backend или frontend через старый контракт перестанет работать. Безопасная миграция сначала расширяет схему, переносит данные, переключает код и только потом удаляет старое.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем feature flag отличается от canary deploy?</strong></summary>

<dl>
<dd>
<h2></h2>

Canary выбирает версию поставленного приложения или серверного экземпляра. Feature flag выбирает поведение внутри версии по пользователю, роли или условию. Flag позволяет выключить конкретную функцию без отката, но не поможет, если приложение не запускается до чтения flags или новый bundle целиком несовместим.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>По каким сигналам останавливать расширение canary?</strong></summary>

<dl>
<dd>
<h2></h2>

По заранее выбранным метрикам: рост ошибок выполнения и `ChunkLoadError`, ухудшение успешности входа или оплаты, HTTP `5xx`, задержка SSR, LCP и INP для затронутой аудитории. Сравнивают canary с контрольной версией и учитывают объём выборки. Порог и окно задают до deploy, чтобы решение не подгонялось под желаемый результат.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие механизмы GitLab защищают production deploy?</strong></summary>

<dl>
<dd>
<h2></h2>

Protected environment ограничивает исполнителей, deployment approval добавляет подтверждение, environment-scoped variables сужают доступ к credentials, а `resource_group` не даёт двум jobs менять production одновременно. Pipeline выпускает конкретный artifact и записывает deployment, поэтому предыдущую версию можно выбрать явно.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Подход |
| --- | --- |
| Один внутренний стенд | Recreate с допустимым коротким простоем |
| Несколько SSR-экземпляров | Rolling update и readiness probe |
| Быстрое переключение окружений | Blue-green |
| Проверка на реальном трафике | Canary с остановкой по метрикам |
| Статическая SPA | Версионированные assets и атомарное переключение HTML |
| Опасная отдельная функция | Feature flag как дополнительный kill switch |
