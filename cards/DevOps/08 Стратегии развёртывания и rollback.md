## Вопрос

<br>

 💬 **Какие бывают стратегии deploy? Как связаны health checks, smoke tests и rollback?**

<h2></h2>

<br>
<dl>
<dd>

Deploy, или развёртывание, переводит окружение с одной версии приложения на другую.

Безопасная процедура должна заранее определять:

- какой неизменяемый artifact выпускается;
- как новая версия получает трафик;
- какие проверки подтверждают её готовность;
- какие метрики разрешают продолжить rollout;
- как остановить распространение ошибки;
- как вернуть рабочее состояние.

Версию связывают с неизменяемым идентификатором:

```text
commit SHA
image digest
release directory
artifact checksum
```

Плавающий tag:

```text
latest
```

не подходит как единственная запись выпущенной версии, потому что позже может начать указывать на другое содержимое.

Release — это не всегда только frontend artifact.

На работоспособность также влияют:

```text
runtime config
feature flags
backend API
схема данных
CDN
Service Worker
```

Поэтому rollback одного image не обязательно восстановит систему, если остальные части уже перешли в несовместимое состояние.

Основные стратегии deploy:

```text
recreate
rolling update
blue-green
canary
атомарная публикация статической SPA
```

**Recreate**, или полная замена, сначала останавливает старую версию, а затем запускает новую:

```text
остановить old
→ запустить new
→ дождаться готовности
```

Преимущество — простота.

Недостаток — период недоступности между остановкой старой версии и готовностью новой.

Recreate подходит, когда:

- это внутренний стенд;
- короткий простой допустим;
- приложение имеет один экземпляр;
- инфраструктура не поддерживает параллельные версии;
- стоимость более сложной стратегии не оправдана.

При одном экземпляре и отсутствии дополнительной ёмкости невозможно гарантировать обновление без простоя: старый процесс нужно либо остановить, либо временно запустить второй.

**Rolling update**, или постепенное обновление, по очереди заменяет экземпляры:

```text
old old old
→
new old old
→
new new old
→
new new new
```

Новый экземпляр получает трафик только после успешной readiness probe.

Старый экземпляр удаляют после того, как новая ёмкость готова его заменить.

В Kubernetes поведение регулируют, например:

```text
maxUnavailable
maxSurge
```

`maxUnavailable` ограничивает число экземпляров, которые могут быть недоступны во время rollout.

`maxSurge` ограничивает число дополнительных экземпляров сверх обычного количества.

Например:

```text
replicas: 4
maxUnavailable: 1
maxSurge: 1
```

позволяет временно запустить пятый экземпляр и не оставлять недоступными больше одного.

Rolling update требует:

- нескольких экземпляров или дополнительной ёмкости;
- readiness probe;
- совместимости старой и новой версий;
- корректного завершения старых процессов;
- наблюдения за прогрессом rollout.

Если новые экземпляры не становятся ready, rollout должен остановиться, а не бесконечно продолжать замену.

Для этого оркестратор или pipeline использует timeout или progress deadline.

Во время rolling update старые и новые версии некоторое время работают одновременно:

```text
frontend v1
frontend v2
backend
```

Backend API и runtime config должны поддерживать обе версии на переходном интервале.

Для SSR-процесса также нужен graceful shutdown.

Упрощённый порядок:

```text
убрать экземпляр из routing
→ перестать принимать новые запросы
→ завершить уже начатые запросы
→ закрыть соединения
→ остановить процесс
```

Если процесс сразу завершить, пользовательские запросы могут оборваться посередине.

Readiness должна стать неуспешной до окончательной остановки, чтобы load balancer перестал направлять новый трафик.

**Blue-green deployment** использует два полных набора экземпляров:

```text
blue  → текущая production-версия
green → новая версия
```

Новая версия разворачивается в green, пока blue продолжает обслуживать пользователей.

На green выполняют:

- startup и readiness probes;
- smoke tests;
- проверку config;
- проверку основных метрик.

После этого routing или load balancer переключает трафик:

```text
blue → green
```

Если проблема обнаружена быстро, трафик можно вернуть на blue.

Преимущества:

- быстрое переключение;
- простая модель отката;
- полная проверка новой среды до основного трафика.

Недостатки:

- требуется дополнительная инфраструктурная ёмкость;
- нужно синхронизировать config;
- общие базы и очереди не откатываются вместе с frontend;
- обе версии должны временно работать с одной схемой данных.

Переключение лучше выполнять на уровне маршрутизатора, ingress или load balancer.

Переключение через DNS может происходить не мгновенно из-за TTL и кэшей разных resolvers.

Blue-green не означает, что нужно дублировать базу данных. Часто версии используют общее хранилище, поэтому несовместимая migration всё равно может сделать возврат на blue невозможным.

**Canary deployment**, или ограниченный выпуск, сначала направляет на новую версию небольшую долю трафика:

```text
95% → stable
5%  → canary
```

Canary может выбираться:

- случайным процентом трафика;
- списком сотрудников;
- tenant;
- регионом;
- account ID;
- feature cohort.

Затем сравнивают canary со стабильной контрольной версией.

Полезные сигналы frontend:

- runtime error rate;
- `ChunkLoadError`;
- успешность login;
- успешность оплаты или другого критичного действия;
- HTTP `5xx`;
- SSR latency;
- LCP;
- INP;
- доля неуспешных загрузок config;
- бизнес-конверсия.

Если показатели допустимы, долю расширяют:

```text
5%
→ 20%
→ 50%
→ 100%
```

Если метрики ухудшаются, расширение останавливают или возвращают трафик на stable.

Критерии остановки задают до deploy:

```text
error rate выше порога
успешность checkout ниже порога
LCP ухудшился больше допустимого
```

Иначе решение легко подогнать под желание продолжить rollout.

Нужно учитывать объём выборки.

Одна ошибка среди десяти пользователей ещё не обязательно доказывает регрессию, а ноль ошибок при слишком маленьком трафике не подтверждает безопасность версии.

Canary должен передавать в monitoring идентификатор версии:

```text
release
deployment variant
canary cohort
```

Без него нельзя надёжно сравнить новую и стабильную версии.

Для stateful-пользовательского сценария желательно закреплять пользователя за вариантом.

Иначе запросы одной сессии могут случайно попадать то в старую, то в новую версию:

```text
загрузка страницы → v1
следующий SSR-запрос → v2
следующий запрос → v1
```

Это особенно опасно, если версии используют разные:

- cookies;
- форматы session;
- URL chunks;
- runtime config;
- протоколы сообщений.

Sticky routing может основываться на cookie, account ID или другом стабильном ключе.

Canary и feature flag решают разные задачи.

Canary выбирает версию поставленного приложения:

```text
release v1
release v2
```

Feature flag выбирает поведение внутри версии:

```text
старый checkout
новый checkout
```

Их можно использовать вместе:

```text
сначала canary новой версии
→ затем постепенное включение функции
```

Feature flag является полезным kill switch, но не помогает, если:

- bundle вообще не загружается;
- приложение падает до получения flags;
- сломан startup-код;
- новая версия целиком несовместима.

Для статической SPA стратегия отличается, потому что приложение может не иметь собственных серверных процессов.

Новый release публикуют в отдельный версионированный каталог или prefix:

```text
/releases/41/
/releases/42/
```

Упрощённый порядок:

```text
1. Загрузить все файлы release 42.
2. Проверить index.html и chunks.
3. Проверить cache headers и MIME types.
4. Проверить client route.
5. Сделать release 42 активным.
```

Новый `index.html` нельзя делать доступным до публикации всех файлов, на которые он ссылается.

Опасный сценарий:

```text
новый HTML уже опубликован
→ новый chunk ещё не загружен
→ пользователь получает 404
```

Не менее опасна перезапись активного каталога по одному файлу:

```text
часть файлов старая
+
часть файлов новая
```

Это создаёт смешанную версию.

Переключение должно быть атомарным с точки зрения пользователя:

- смена symlink;
- смена release prefix;
- переключение container image;
- изменение routing;
- публикация HTML только после assets.

Инвалидация CDN-кэша не заменяет атомарную публикацию. Разные edge-регионы могут обновиться в разное время.

Файлы с content hash предыдущих версий не удаляют сразу:

```text
app.old-hash.js
settings.old-hash.js
```

Они могут понадобиться:

- старому HTML в browser cache;
- CDN;
- уже открытой вкладке;
- Service Worker;
- позднему dynamic import.

HTML обычно получает короткую политику или обязательную revalidation, а hashed assets — долгий immutable cache.

Нужно различать четыре уровня проверки:

```text
startup probe
liveness probe
readiness probe
smoke test
```

**Startup probe** отвечает:

```text
Завершил ли процесс первоначальный запуск?
```

Она полезна для приложения, которое стартует долго.

Пока startup probe не прошла, оркестратор не должен считать медленный старт обычным зависанием и применять liveness-логику слишком рано.

После успешного startup дальнейшее состояние контролируют liveness и readiness.

**Liveness probe** отвечает:

```text
Нужно ли перезапустить экземпляр?
```

Она должна обнаруживать состояние, из которого процесс сам не восстановится:

- deadlock;
- зависший event loop;
- необратимо сломанный внутренний runtime;
- процесс не может обслуживать даже локальный запрос.

Liveness не должна падать только потому, что временно недоступен общий внешний сервис:

```text
database
authentication API
сторонний provider
```

Иначе одна внешняя проблема вызовет перезапуск всех здоровых экземпляров и усилит инцидент.

**Readiness probe** отвечает:

```text
Можно ли сейчас направлять экземпляру пользовательский трафик?
```

Экземпляр может быть жив, но временно не готов:

- ещё загружает config;
- выполняет инициализацию;
- не получил обязательный локальный ресурс;
- завершает работу;
- временно потерял критичную зависимость.

Неготовый экземпляр исключают из routing, но не обязательно перезапускают.

Readiness должна быть:

- быстрой;
- предсказуемой;
- устойчивой;
- с коротким timeout;
- без тяжёлого пользовательского сценария.

Для статического Nginx frontend readiness может проверить:

```text
процесс отвечает
index.html существует
основная конфигурация загружена
```

Не нужно заставлять Nginx readiness зависеть от всех backend API: статический сервер может быть полностью исправен, даже если отдельный backend переживает инцидент.

Для Next.js SSR readiness может учитывать:

- загрузку обязательного runtime config;
- готовность server runtime;
- наличие обязательных локальных файлов;
- возможность обработать простой server route.

Служебный health endpoint не должен возвращать:

- secrets;
- полный environment;
- stack trace;
- внутреннюю диагностику инфраструктуры.

Версию release безопаснее отдавать отдельным header или диагностическим endpoint.

Dockerfile поддерживает:

```dockerfile
HEALTHCHECK
```

Он предоставляет один общий health status контейнера.

Например:

```dockerfile
HEALTHCHECK \
  --interval=30s \
  --timeout=3s \
  --retries=3 \
  CMD wget -qO- http://localhost:8080/health \
      || exit 1
```

Но Docker `HEALTHCHECK` сам по себе не разделяет startup, liveness и readiness.

Оркестратор вроде Kubernetes предоставляет отдельные probes и использует их для разных действий:

```text
startup  → разрешить переход к обычным проверкам
liveness → перезапустить
readiness → включить или исключить из трафика
```

Успешная probe не доказывает, что приложение полностью работает для пользователя.

Например:

```text
GET /health → 200
```

может выполняться, хотя:

- DNS ведёт на другой адрес;
- TLS certificate истёк;
- CDN отдаёт старый HTML;
- JavaScript chunk отсутствует;
- runtime config невалиден;
- API недоступен;
- приложение падает в браузере.

Для проверки всего пути нужен **smoke test**.

Smoke test запускается снаружи после deploy или на промежуточном этапе rollout.

Он проверяет ограниченный критичный путь:

```text
DNS
→ TLS
→ routing
→ HTML
→ JavaScript chunks
→ runtime config
→ API
→ пользовательское действие
```

Для статической SPA минимальная проверка может выглядеть так:

```text
GET /
→ 200 + text/html

GET /client-route
→ SPA HTML

GET /assets/main.hash.js
→ 200 + JavaScript Content-Type

GET /config.json
→ валидная конфигурация

критичный API
→ ожидаемый ответ
```

Для полноценного пользовательского сценария browser smoke test может:

- открыть приложение;
- дождаться bootstrap;
- выполнить вход тестовой учётной записью;
- пройти один критичный сценарий;
- проверить отсутствие критичных Console errors.

Smoke test должен быть:

- коротким;
- стабильным;
- безопасным для повторного запуска;
- достаточно быстрым для deploy;
- способным остановить rollout.

Он не заменяет полную регрессию.

Health checks и smoke tests используются совместно:

```text
startup прошёл
→ экземпляр запустился

readiness прошла
→ экземпляр может получить трафик

smoke test прошёл
→ внешний пользовательский путь работает

метрики допустимы
→ rollout можно расширять
```

Типичный rollout gate:

```text
1. Artifact имеет ожидаемый digest.
2. Startup probe успешна.
3. Readiness probe успешна.
4. Smoke test успешен.
5. Error rate не превышает порог.
6. Критичные продуктовые метрики допустимы.
7. Rollout получает разрешение на следующий шаг.
```

При ошибке:

```text
остановить rollout
→ сохранить стабильную долю трафика
→ выполнить rollback или принять решение по runbook
```

Автоматический rollback полезен при однозначном и достаточно быстром сигнале.

Например:

```text
новые экземпляры не проходят readiness
error rate резко вырос только у canary
smoke test стабильно падает
```

Но автоматизация должна учитывать:

- минимальный объём трафика;
- окно наблюдения;
- число последовательных нарушений;
- различие canary и control;
- cooldown после переключения;
- защиту от повторного запуска.

Иначе шумная метрика может вызвать flapping:

```text
v1 → v2 → v1 → v2
```

Постоянное переключение само создаёт нестабильность и усложняет диагностику.

Для сложных или медленно проявляющихся симптомов безопаснее:

```text
автоматически остановить расширение
→ уведомить ответственного
→ принять решение по runbook
```

Rollback возвращает предыдущую версию artifact:

```text
release 42
→ release 41
```

Надёжный rollback требует заранее сохранить:

- artifact или image digest;
- runtime config версии;
- deployment manifest;
- feature flags;
- сведения о migration;
- команду переключения;
- smoke test;
- необходимые права.

Rollback не должен повторно собирать старый commit во время инцидента.

Нужен уже созданный и проверенный immutable artifact.

После переключения проверяют не только статус deploy job, но и фактическое состояние:

- release ID;
- image digest;
- config version;
- активные feature flags;
- CDN-ответ;
- Service Worker;
- smoke test;
- error rate;
- пользовательские метрики.

Rollback может оказаться невозможным или бесполезным, если новая версия выполнила несовместимое изменение:

- удалила поле API;
- изменила формат session;
- удалила колонку базы;
- изменила смысл данных;
- перезаписала старые assets;
- изменила config без обратной совместимости.

В такой ситуации может потребоваться **roll forward** — новый исправляющий release, совместимый с уже изменённым состоянием.

Roll forward выбирают, когда:

- migration необратима;
- предыдущая версия больше не понимает данные;
- возврат infrastructure state слишком опасен;
- исправление новой версией надёжнее.

Для безопасных контрактных изменений используют **expand and contract**.

Упрощённый порядок:

```text
1. Backend добавляет новое поле или операцию.
2. Старый контракт продолжает работать.
3. Выпускается новый frontend.
4. Старые клиенты продолжают поддерживаться.
5. Проходит переходное окно.
6. Устаревший контракт удаляется отдельным release.
```

Для базы данных:

```text
добавить новую колонку
→ начать двойную запись или перенос данных
→ переключить чтение
→ убедиться, что старый код больше не используется
→ удалить старую колонку
```

Нельзя сначала удалить старое поле, а затем надеяться, что все frontend-вкладки мгновенно обновятся.

Пользователь может часами держать открытой старую версию SPA.

Backend должен сохранять совместимость на определённое переходное окно либо явно версионировать API.

Стратегию deploy выбирают по риску и возможностям системы:

```text
Recreate
→ простота, но возможен downtime.

Rolling
→ постепенная замена экземпляров.

Blue-green
→ отдельная полная среда и быстрое переключение.

Canary
→ ограниченный реальный трафик и расширение по метрикам.

Статическая SPA
→ версионированные assets и атомарное переключение.
```

Выбор зависит от:

- допустимого простоя;
- числа экземпляров;
- стоимости дополнительной среды;
- возможности сегментировать трафик;
- качества observability;
- обратной совместимости;
- скорости rollback;
- критичности продукта.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Как выбрать подходящую стратегию deploy?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала определяют ограничения:

- допустим ли простой;
- сколько экземпляров доступно;
- можно ли одновременно запускать две версии;
- можно ли разделить трафик;
- есть ли метрики по версиям;
- совместимы ли API и данные;
- насколько быстро нужен rollback.

Упрощённо:

```text
внутренний стенд с допустимым простоем
→ recreate

несколько одинаковых SSR-экземпляров
→ rolling update

нужно заранее проверить полную новую среду
→ blue-green

нужно проверить новую версию на малой доле production
→ canary

статическая SPA
→ атомарная публикация версионированных файлов
```

Сложная стратегия без достаточной observability может быть опаснее простой, потому что команда не сможет понять, какая версия обслуживает ошибочный запрос.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как rolling update обеспечивает работу без простоя?</strong></summary>

<dl>
<dd>
<h2></h2>

Оркестратор сначала запускает часть новых экземпляров и ждёт readiness.

Только после этого он удаляет соответствующую часть старых.

Параметры:

```text
maxUnavailable
maxSurge
```

ограничивают недоступность и временную дополнительную ёмкость.

При одном экземпляре и отсутствии surge-ёмкости гарантировать непрерывность невозможно.

Zero downtime также требует:

- совместимого API;
- совместимого config;
- совместимой схемы данных;
- graceful shutdown;
- корректного connection draining.

Даже если все контейнеры запущены, rollout не является безопасным, если старая и новая версии не могут одновременно работать с backend.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое graceful shutdown и connection draining?</strong></summary>

<dl>
<dd>
<h2></h2>

При остановке SSR-экземпляра нельзя сразу завершать процесс, если он уже обрабатывает запросы.

Безопасный порядок:

```text
readiness становится false
→ load balancer перестаёт отправлять новые запросы
→ выполняющиеся запросы завершаются
→ соединения закрываются
→ процесс останавливается
```

Connection draining даёт уже начатым запросам время завершиться.

При этом нужен максимальный timeout: зависший запрос не должен бесконечно блокировать rollout.

Для статического Nginx этот вопрос проще, но при SSR, streaming, WebSocket и долгих запросах завершение процесса нужно проектировать отдельно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем blue-green отличается от canary?</strong></summary>

<dl>
<dd>
<h2></h2>

Blue-green подготавливает полное параллельное окружение и обычно переключает на него весь основной трафик одним действием.

Canary сначала направляет новой версии небольшую долю реальных пользователей и расширяет её по метрикам.

Кратко:

```text
blue-green
→ заранее подготовить полную новую среду

canary
→ постепенно проверять новую версию на production-трафике
```

Blue-green упрощает обратное переключение.

Canary уменьшает первоначальный масштаб неизвестной ошибки.

Подходы можно сочетать: green сначала получает canary-трафик, а после проверки становится основной средой.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем liveness check отличается от readiness check?</strong></summary>

<dl>
<dd>
<h2></h2>

Liveness отвечает:

```text
Нужно ли перезапустить процесс?
```

Readiness отвечает:

```text
Можно ли сейчас направлять процессу трафик?
```

Неготовый экземпляр может оставаться живым и позже восстановить readiness без restart.

Например, при graceful shutdown readiness становится false, но процесс ещё жив и завершает начатые запросы.

Liveness не должна зависеть от общего внешнего API. Иначе сбой API вызовет массовый restart исправных frontend-серверов и усилит инцидент.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем startup probe отличается от liveness?</strong></summary>

<dl>
<dd>
<h2></h2>

Startup probe используется во время первоначального запуска:

```text
Приложение уже завершило инициализацию?
```

Она полезна для медленно стартующих процессов.

Пока startup probe не прошла, оркестратор не должен применять обычную liveness-проверку так, как будто процесс уже обязан быть готов.

После успешного startup приложение проверяется через liveness и readiness.

Увеличивать liveness timeout только ради медленного запуска хуже, потому что после старта зависший процесс также будет обнаруживаться слишком долго.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что должен проверять health endpoint frontend-сервера?</strong></summary>

<dl>
<dd>
<h2></h2>

Для Nginx со статической SPA обычно достаточно подтвердить:

- процесс отвечает;
- основной локальный файл существует;
- сервер может вернуть простой response.

Для Next.js SSR readiness дополнительно может проверять:

- загрузку обязательного config;
- готовность server runtime;
- возможность обработать простой server route.

Health endpoint должен быть:

- быстрым;
- дешёвым;
- с коротким timeout;
- без секретов;
- без полного stack trace;
- без тяжёлого пользовательского сценария.

Release ID можно вернуть отдельным безопасным endpoint или header.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему успешного health check недостаточно?</strong></summary>

<dl>
<dd>
<h2></h2>

Health check обычно выполняется рядом с процессом и проверяет ограниченное локальное условие.

Он может пройти, хотя:

- DNS указывает не туда;
- TLS certificate недействителен;
- CDN отдаёт старый HTML;
- chunk отсутствует;
- runtime config невалиден;
- браузерный JavaScript падает;
- критичный API недоступен.

Smoke test проходит по внешнему пользовательскому пути и проверяет интеграцию компонентов.

Поэтому:

```text
health check
→ готовность экземпляра

smoke test
→ работоспособность выпущенного пользовательского пути
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие проверки должны быть rollout gates?</strong></summary>

<dl>
<dd>
<h2></h2>

Перед расширением rollout обычно проверяют:

1. Выпущен ожидаемый digest.
2. Startup probe прошла.
3. Readiness стабильна.
4. Smoke test прошёл.
5. Error rate не вырос.
6. Критичный пользовательский сценарий успешен.
7. Canary не хуже контрольной версии сверх допустимого порога.

Для каждого gate заранее задают:

- порог;
- окно наблюдения;
- минимальный объём данных;
- действие при нарушении.

Действием может быть:

```text
остановить rollout
вернуть трафик
потребовать ручное решение
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда автоматический rollback может быть опасен?</strong></summary>

<dl>
<dd>
<h2></h2>

Автоматический rollback опасен, если сигнал шумный или проблема не связана с новой версией.

Например, общий backend-инцидент одновременно ухудшил метрики stable и canary.

Если система реагирует только на абсолютный error rate, она может ошибочно откатить исправный frontend.

Также возможны постоянные переключения:

```text
v1 → v2 → v1 → v2
```

Для защиты используют:

- сравнение с контрольной версией;
- minimum sample size;
- несколько последовательных нарушений;
- cooldown;
- ограничение числа автоматических попыток;
- ручное решение для неоднозначных случаев.

Часто безопаснее автоматически остановить rollout, но не выполнять rollback без подтверждения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как атомарно выпустить статическую SPA?</strong></summary>

<dl>
<dd>
<h2></h2>

Новый набор файлов сначала публикуют отдельно:

```text
/releases/42/
```

До переключения проверяют:

- `index.html`;
- наличие всех JavaScript и CSS chunks;
- MIME types;
- cache headers;
- client route fallback;
- runtime config.

Только после полной публикации новая версия становится активной.

Перезапись файлов на месте по одному создаёт смешанную версию.

Инвалидация CDN-кэша не заменяет атомарный deploy и может обновляться в разных регионах не одновременно.

Предыдущие файлы с content hash сохраняют достаточно долго для:

- старого HTML;
- открытых вкладок;
- CDN;
- Service Worker;
- поздних dynamic imports.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что нужно сохранить для надёжного rollback?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно сохранить:

- immutable artifact;
- image digest или release directory;
- runtime config;
- deployment manifest;
- feature flags;
- сведения о migrations;
- команду переключения;
- smoke test;
- release metadata.

Предыдущая версия должна оставаться доступной в registry или release storage.

Процедуру и права проверяют заранее, а не впервые во время инцидента.

После rollback запускают smoke test и наблюдают метрики. Сам факт успешного выполнения deploy job ещё не доказывает восстановление пользователей.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выпустить frontend и backend без жёсткой синхронизации?</strong></summary>

<dl>
<dd>
<h2></h2>

Используют обратную совместимость и expand-and-contract.

Порядок:

```text
backend добавляет новую возможность
→ старый контракт продолжает работать
→ выпускается новый frontend
→ проходит переходное окно
→ старый контракт удаляется отдельным release
```

Frontend при необходимости умеет работать с переходным состоянием.

Для обязательного breaking change используют:

- версионирование API;
- capability check;
- отдельный endpoint;
- длительное переходное окно.

Нельзя рассчитывать, что все открытые вкладки frontend обновятся одновременно с backend.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему database migration может помешать rollback frontend?</strong></summary>

<dl>
<dd>
<h2></h2>

Frontend зависит от API, а API — от схемы данных.

Если migration сразу:

- удалила колонку;
- переименовала поле;
- изменила смысл данных;
- преобразовала значения необратимо,

предыдущий backend или старый контракт могут перестать работать.

Безопасная migration обычно выполняется по этапам:

```text
расширить схему
→ перенести или дублировать данные
→ переключить чтение и запись
→ дождаться обновления клиентов
→ удалить старую структуру
```

Если обратный путь невозможен, вместо rollback потребуется roll forward исправляющей версией.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем feature flag отличается от canary deploy?</strong></summary>

<dl>
<dd>
<h2></h2>

Canary выбирает версию приложения:

```text
release v1
release v2
```

Feature flag выбирает поведение внутри версии:

```text
старый checkout
новый checkout
```

Flag позволяет быстро выключить отдельную функцию без возврата всего artifact.

Но он не помогает, если:

- bundle не загрузился;
- приложение падает до получения flags;
- сломан глобальный startup-код;
- новая версия целиком несовместима.

Canary и feature flags можно сочетать для уменьшения разных видов риска.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>По каким сигналам останавливать расширение canary?</strong></summary>

<dl>
<dd>
<h2></h2>

Используют заранее выбранные метрики:

- runtime errors;
- `ChunkLoadError`;
- HTTP `5xx`;
- неуспешный login;
- неуспешная оплата;
- SSR latency;
- LCP;
- INP;
- продуктовая конверсия.

Canary сравнивают с control, а не только с фиксированным абсолютным числом.

Также учитывают:

- размер выборки;
- продолжительность окна;
- браузер;
- регион;
- route;
- feature cohort.

Порог и действие задают до deploy:

```text
остановить rollout
вернуть трафик
потребовать ручное подтверждение
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие механизмы GitLab защищают production deploy?</strong></summary>

<dl>
<dd>
<h2></h2>

GitLab предоставляет:

- protected environments;
- deployment approvals;
- protected variables;
- environment-scoped variables;
- manual jobs;
- `resource_group`;
- deployment records;
- защиту от устаревших deployments.

`resource_group` сериализует jobs, меняющие одно окружение, но порядок и защита от старого pipeline должны быть настроены отдельно.

Deploy должен использовать конкретный immutable artifact и записывать release ID.

Тогда rollback выбирает известную предыдущую версию, а не случайно пересобирает старый commit.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Подход |
| --- | --- |
| Один внутренний стенд | Recreate с допустимым коротким простоем |
| Несколько SSR-экземпляров | Rolling update, readiness и graceful shutdown |
| Быстрое переключение окружений | Blue-green |
| Проверка на реальном трафике | Canary с контрольной версией и stop conditions |
| Статическая SPA | Версионированные assets и атомарное переключение HTML |
| Опасная отдельная функция | Feature flag как дополнительный kill switch |
| Долгий запуск процесса | Startup probe |
| Зависший экземпляр | Liveness probe |
| Экземпляр не должен получать трафик | Readiness probe |
| Проверка пользовательского пути | Внешний smoke test |
| Необратимая migration | Roll forward вместо простого rollback |
