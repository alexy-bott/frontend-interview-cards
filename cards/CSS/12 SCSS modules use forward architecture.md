#### Вопрос

Зачем в Sass нужны `@use` и `@forward`? Почему старый `@import` считается плохим?

#### Ответ

`@use` и `@forward` образуют модульную систему Sass. `@use` загружает Sass-файл как модуль и делает его публичные переменные, функции и mixins доступными только в текущем файле. По умолчанию обращения идут через namespace, то есть пространство имён, образованное из имени файла: после `@use "tokens"` переменная читается как `tokens.$radius`.

Sass загружает один и тот же модуль только один раз за компиляцию, даже если несколько файлов зависят от него. Это предотвращает случайное повторение сгенерированного CSS. При этом `@use` не становится транзитивным: если `button.scss` подключил `tokens`, другой файл, подключивший `button`, не получает автоматически имена из `tokens`.

`@forward` формирует публичный API модуля. Он загружает другой файл и передаёт его публичные члены потребителям текущего модуля. Так файл `styles/_index.scss` может собрать токены, mixins и функции в единую точку входа, а внутреннюю структуру папки можно менять без обновления импортов во всех компонентах. Имена, начинающиеся с `_` или `-`, Sass считает приватными и наружу не экспортирует.

Пример структуры:

```scss
// styles/_tokens.scss
$radius: 8px;

// styles/_mixins.scss
@mixin focus-ring {
  outline: 2px solid Highlight;
}

// styles/_index.scss
@forward "tokens";
@forward "mixins";

// Button.module.scss
@use "../styles" as styles;

.root {
  border-radius: styles.$radius;
}
```

В таком варианте компонент видит публичный API `styles/_index.scss` и не зависит от расположения внутренних файлов. `@forward` передаёт имена потребителю, но не делает их доступными внутри самого index-файла; если index-файл также использует эти значения, ему нужен отдельный `@use`.

Старый Sass `@import` объединяет загруженные имена в общей глобальной области. Из-за этого трудно определить источник `$primary`, порядок импортов становится частью скрытого контракта, а повторный импорт способен продублировать CSS. Начиная с Dart Sass 1.80.0 Sass-вариант `@import` помечен deprecated, то есть устаревшим и готовящимся к удалению; новый код использует `@use` и `@forward`.

Это не означает, что браузерный CSS `@import` уже удалён. Sass распознаёт некоторые импорты как обычные CSS-импорты, например URL или файл с расширением `.css`, и оставляет их в итоговом CSS. Устарела именно возможность Sass `@import` смешивать переменные, функции и правила разных SCSS-файлов в общей области.

В проекте обычно разделяют общие токены и инструменты Sass, глобальные базовые/reset-стили и локальные стили компонентов. Большая иерархия SCSS не является самоцелью: если компоненту нужны только его локальные классы и пользовательские CSS-свойства, отдельный модуль с множеством промежуточных файлов лишь усложнит навигацию.

Модули Sass и CSS Modules - разные механизмы. `@use` и `@forward` управляют видимостью Sass-переменных, функций и mixins во время компиляции. CSS Modules локализуют имена CSS-классов средствами сборщика. Их можно использовать вместе в `Component.module.scss`, но они решают разные задачи.

#### Встречные вопросы

> [!followup] Namespace
> **Вопрос:** Почему пространство имён в `@use` полезно?
>
> **Ответ:** Оно делает источник переменной или mixin явным и предотвращает конфликт одинаковых имён. `tokens.$primary` показывает, что значение пришло из модуля `tokens`, тогда как глобальный `$primary` не содержит этой информации.
>
> Если импортировать всё в глобальную область, становится трудно понять, откуда пришёл `$primary`: из токенов, темы, компонента или старого файла.

> [!followup] forward
> **Вопрос:** Когда использовать `@forward`?
>
> **Ответ:** Когда нужно создать публичную точку входа для набора модулей Sass. Например, `@forward "tokens"; @forward "mixins";`, чтобы потребители подключали один файл.
>
> Это полезно для общих стилей и дизайн-системы: внешние файлы подключают `@use "../styles"`, а внутреннюю структуру можно менять без переписывания всех подключений.

> [!followup] Import deprecated
> **Вопрос:** Почему Sass `@import` считается устаревшим?
>
> **Ответ:** Он смешивает имена подключённых файлов в общей области, может повторно вывести один и тот же CSS и создаёт зависимости от порядка импортов. `@use` ограничивает видимость имён текущим файлом и загружает модуль один раз, а `@forward` явно формирует публичную точку входа.
>
> С `@use` видно, из какого модуля пришла переменная или функция, а один и тот же модуль не загружается повторно как глобальный фрагмент кода.

> [!followup] Настройка модуля
> **Вопрос:** Как передать модулю Sass настраиваемые значения?
>
> **Ответ:** Публичную переменную модуля объявляют со значением по умолчанию через `!default`, а при первом `@use` переопределяют через `with`: `@use "theme" with ($accent: #0b57d0)`. Конфигурация применяется при первой загрузке модуля, потому что дальше этот модуль переиспользуется, а не выполняется заново для каждого файла.

> [!followup] CSS Modules
> **Вопрос:** `@use` - это CSS Modules?
>
> **Ответ:** Нет. `@use` относится к модульной системе Sass и подключает переменные, функции и mixins во время компиляции. CSS Modules - механизм сборщика, который преобразует локальные имена классов в уникальные имена вроде `Button_root__hash`.
>
> `@use` отвечает на вопрос «какие инструменты Sass доступны в этом SCSS-файле». CSS Modules отвечает на вопрос «как избежать глобальных конфликтов имён CSS-классов».

#### Где это встречается во frontend

> [!context] Практика
> | Задача | Механизм Sass |
> | --- | --- |
> | Подключить токены | `@use "tokens"` |
> | Собрать публичный API стилей | `@forward` в index-файле |
> | Избежать конфликтов имён | Пространство имён |
> | Стили дизайн-системы | Модули токенов, mixins и функций, одна публичная точка входа |
> | Миграция старого кода | Sass `@import` -> `@use`/`@forward` |
