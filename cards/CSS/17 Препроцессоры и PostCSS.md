## Вопрос

<br>

 💬 **Зачем нужны CSS-препроцессоры и постпроцессоры? Чем Sass отличается от PostCSS и Autoprefixer?**

<h2></h2>

<br>
<dl>
<dd>

CSS-препроцессор принимает язык с дополнительным синтаксисом и до запуска страницы компилирует его в обычный CSS.

Например, Sass обрабатывает:

- SCSS-переменные;
- mixins;
- функции;
- вложенность;
- условия и циклы;
- maps;
- модули `@use` и `@forward`.

Исходный SCSS:

```scss
$accent: royalblue;

@mixin interactive {
  cursor: pointer;

  &:hover {
    opacity: 0.8;
  }
}

.button {
  color: $accent;
  @include interactive;
}
```

После компиляции браузер получает обычный CSS:

```css
.button {
  color: royalblue;
  cursor: pointer;
}

.button:hover {
  opacity: 0.8;
}
```

Браузер ничего не знает о `$accent`, `@mixin` или `@include`: эти конструкции исчезли во время сборки.

PostCSS — JavaScript-инструмент для преобразования CSS.

Упрощённо его работа состоит из трёх этапов:

1. PostCSS разбирает CSS в abstract syntax tree, AST — структурное дерево правил, selectors и declarations.
2. Настроенные plugins анализируют или изменяют это дерево.
3. Из изменённого дерева генерируется итоговый CSS.

Сам PostCSS не определяет единственный набор преобразований. Его возможности зависят от подключённых plugins.

Например:

- Autoprefixer управляет vendor prefixes;
- `postcss-preset-env` преобразует поддерживаемую им часть современного CSS;
- cssnano выполняет оптимизации и минификацию;
- отдельные plugins могут сортировать, проверять или преобразовывать declarations.

PostCSS часто называют постпроцессором, потому что в типичной цепочке он получает уже скомпилированный CSS после Sass.

Но это не обязательное техническое ограничение. Место PostCSS в pipeline определяют сборщик и конфигурация проекта.

Для `.scss` типичная цепочка может выглядеть так:

1. Sass компилирует SCSS в CSS.
2. PostCSS запускает plugins над полученным CSS.
3. CSS Modules преобразуют локальные имена классов.
4. Сборщик объединяет или разделяет CSS по chunks.
5. CSS минифицируется и записывается в итоговые assets.

Точный порядок может отличаться.

Например, конкретная интеграция может выполнять CSS Modules до части PostCSS plugins, а минификацию — встроенным инструментом сборщика, а не cssnano.

Поэтому порядок не угадывают по общему названию инструмента, а проверяют в документации и конфигурации Vite, Webpack, Next.js или другого build tool.

Sass и PostCSS решают разные задачи.

Sass предоставляет конкретный язык и compile-time возможности:

```scss
$spacing: 8px;

@function spacing($step) {
  @return $spacing * $step;
}

.card {
  padding: spacing(2);
}
```

PostCSS является платформой обработки CSS. Сам по себе он не предоставляет эквивалент Sass-функций или mixins — для каждой возможности нужен соответствующий plugin.

Поэтому Sass и PostCSS могут использоваться вместе:

```text
SCSS → Sass → CSS → PostCSS plugins → итоговый CSS
```

Autoprefixer — один из plugins PostCSS.

Разработчик пишет стандартный непрификсованный CSS:

```css
.control {
  appearance: none;
  user-select: none;
}
```

Autoprefixer анализирует declarations и на основе целевых браузеров может добавить необходимые vendor prefixes:

```css
.control {
  -webkit-appearance: none;
  appearance: none;
  -webkit-user-select: none;
  user-select: none;
}
```

Конкретный результат зависит от:

- Browserslist проекта;
- данных о поддержке CSS;
- версии Autoprefixer;
- используемых свойств и значений.

Autoprefixer умеет не только добавлять нужные prefixes, но и удалять устаревшие prefixes, которые больше не соответствуют текущей конфигурации.

Разработчику обычно не следует писать префиксы вручную:

```css
.element {
  -webkit-user-select: none;
  -moz-user-select: none;
  user-select: none;
}
```

Ручной список быстро устаревает:

- можно пропустить нужный вариант;
- можно оставить ненужный prefix;
- список перестаёт соответствовать поддерживаемым браузерам;
- изменение browser support требует ручного редактирования CSS.

Лучше писать стандартное свойство:

```css
.element {
  user-select: none;
}
```

и позволить Autoprefixer сформировать результат по общему контракту поддержки.

Vendor prefix не является полноценным polyfill.

Префикс обычно предоставляет браузерную реализацию существующей или экспериментальной CSS-возможности под специальным именем:

```css
-webkit-appearance
```

Но если старый браузер вообще не умеет реализовать нужное поведение, добавление префикса само по себе эту возможность не создаст.

Нужно различать:

- **prefix** — альтернативное браузерное имя свойства или значения;
- **syntax transformation** — преобразование нового синтаксиса в более старый эквивалент;
- **polyfill** — дополнительная реализация отсутствующей возможности.

Autoprefixer прежде всего управляет prefixes. Он не является универсальным CSS-polyfill и не исправляет любой browser bug.

Browserslist задаёт список целевых браузеров проекта.

Конфигурация может находиться, например, в `.browserslistrc`:

```text
> 0.5%
last 2 versions
not dead
```

или в `package.json`:

```json
{
  "browserslist": [
    "> 0.5%",
    "last 2 versions",
    "not dead"
  ]
}
```

Browserslist отвечает на вопрос:

```text
Какие браузеры и версии должен поддерживать продукт?
```

Эту конфигурацию могут использовать:

- Autoprefixer;
- Babel;
- инструменты проверки совместимости;
- другие части build pipeline.

Общий Browserslist помогает JavaScript и CSS ориентироваться на один продуктовый контракт.

Но разные инструменты используют этот список по-разному.

Например:

- Autoprefixer решает, какие CSS-prefixes нужны;
- Babel решает, какие JavaScript-преобразования выполнить;
- инструмент анализа совместимости сообщает о неподдерживаемом API.

Одинаковая Browserslist-конфигурация не означает, что инструменты выполняют одинаковые преобразования или предоставляют одинаковые polyfills.

Autoprefixer получает данные о поддержке CSS через базу, связанную с Can I Use. В проектах она обычно поставляется через пакет `caniuse-lite`.

Устаревшие данные могут приводить к решениям на основе старой информации о браузерах. Поэтому зависимости периодически обновляют.

Но обновление `caniuse-lite` не должно незаметно заменять продуктовый контракт. Сами Browserslist queries меняют осознанно, когда команда решает добавить или прекратить поддержку определённых браузеров.

`postcss-preset-env` решает другую задачу. Он объединяет набор PostCSS plugins для части современного CSS-синтаксиса и позволяет настраивать, какие преобразования выполнять.

Например, plugin может:

- преобразовать поддерживаемую современную запись;
- добавить fallback;
- сохранить исходный современный синтаксис вместе с преобразованным;
- включить Autoprefixer как часть цепочки в зависимости от настройки.

Но `postcss-preset-env` не гарантирует полную эмуляцию любой новой CSS-возможности в любом старом браузере.

Некоторые возможности невозможно преобразовать без изменения HTML, JavaScript или самой модели layout.

В цепочке PostCSS важен порядок plugins.

Один plugin может ожидать исходный синтаксис, а другой — результат его преобразования.

Упрощённый пример:

```text
modern syntax transformation
→ prefixing
→ optimization
→ minification
```

Если сначала минифицировать или удалить данные, которые нужны следующему plugin, результат может оказаться неправильным или менее эффективным.

Также важно не дублировать одну и ту же задачу.

Например, Autoprefixer может уже запускаться:

- внутри `postcss-preset-env`;
- через конфигурацию фреймворка;
- через отдельный `postcss.config`;
- внутри готового build preset.

Если подключить его повторно без необходимости, pipeline станет сложнее понимать, хотя итоговый CSS не обязательно улучшится.

То же относится к минификации: её может выполнять cssnano, Vite, esbuild, Lightning CSS или другой инструмент сборщика.

Source maps связывают итоговый CSS с исходным SCSS или другим исходным файлом.

Без них DevTools может показывать только:

```text
assets/index-a1b2c3.css
```

вместо:

```text
src/components/Button/Button.module.scss
```

Чтобы соответствие сохранилось, source maps должна поддерживать вся цепочка:

```text
Sass
→ PostCSS
→ CSS Modules
→ bundler
→ minifier
```

Если одна стадия отбросила или неправильно объединила карту, следующая уже не сможет точно восстановить исходное расположение.

Практическая модель:

```text
Sass
Конкретный язык и compile-time генерация CSS.

PostCSS
Платформа AST-преобразований CSS через plugins.

Autoprefixer
PostCSS plugin для управления vendor prefixes.

Browserslist
Общий контракт целевых браузеров для инструментов сборки.
```

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Заменяет ли PostCSS Sass?</strong></summary>

<dl>
<dd>
<h2></h2>

Не автоматически.

Sass — конкретный язык и компилятор со встроенными возможностями:

- переменными;
- mixins;
- функциями;
- maps;
- циклами;
- условиями;
- модульной системой.

PostCSS — платформа обработки CSS, возможности которой определяются plugins.

Теоретически набор PostCSS plugins может предоставить часть похожих возможностей. Но это не означает полной совместимости с Sass или одинакового поведения.

При миграции нужно отдельно проверить:

- переменные;
- пользовательские функции;
- mixins;
- `@use` и `@forward`;
- Sass maps;
- циклы и генерацию selectors;
- вложенность;
- сторонние Sass-библиотеки.

Часть задач сегодня можно решить нативным CSS:

- custom properties;
- native nesting;
- `calc()`;
- `min()`, `max()`, `clamp()`;
- container queries;
- cascade layers.

Но это runtime- и browser-возможности, а Sass работает при сборке. Они не всегда взаимозаменяемы.

В одном проекте Sass и PostCSS часто работают последовательно:

```text
SCSS → Sass → CSS → PostCSS
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что именно делает Autoprefixer?</strong></summary>

<dl>
<dd>
<h2></h2>

Autoprefixer анализирует CSS и Browserslist проекта.

На основе данных о поддержке он может:

- добавить нужный vendor prefix;
- сохранить стандартное непрификсованное declaration;
- удалить устаревший prefix;
- вывести предупреждение для некоторых проблемных конструкций.

Разработчик пишет:

```css
.element {
  appearance: none;
  user-select: none;
}
```

А итоговый CSS зависит от целевых браузеров.

Autoprefixer не:

- исправляет любой browser bug;
- добавляет JavaScript-polyfills;
- гарантирует поддержку любой новой CSS-возможности;
- заменяет тестирование в целевых браузерах;
- выбирает продуктовый список браузеров вместо команды.

Он автоматизирует именно ту часть совместимости, которая может быть решена корректным набором vendor prefixes.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему не стоит писать vendor prefixes вручную?</strong></summary>

<dl>
<dd>
<h2></h2>

Ручной код быстро теряет связь с реальной поддержкой браузеров:

```css
.element {
  -webkit-transform: translateX(0);
  -moz-transform: translateX(0);
  -ms-transform: translateX(0);
  transform: translateX(0);
}
```

Часть этих declarations может быть не нужна, а необходимый для другого свойства prefix можно забыть.

Проблемы ручного подхода:

- CSS становится шумнее;
- разработчик должен помнить историю каждого свойства;
- старые prefixes остаются навсегда;
- изменения Browserslist не обновляют CSS автоматически;
- легко написать неправильный порядок declarations;
- разные разработчики используют разные наборы.

Предпочтительный исходный код:

```css
.element {
  transform: translateX(0);
}
```

Autoprefixer формирует необходимые варианты централизованно.

Ручной prefix оправдан только в редком случае, когда команда осознанно реализует конкретный browser workaround, который не относится к обычной работе Autoprefixer. Такой код желательно сопровождать комментарием с причиной.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем prefix отличается от преобразования синтаксиса и polyfill?</strong></summary>

<dl>
<dd>
<h2></h2>

Vendor prefix использует браузерное имя свойства или значения:

```css
-webkit-appearance: none;
appearance: none;
```

Он не меняет принцип работы возможности, а обращается к конкретной реализации браузера.

Преобразование синтаксиса переписывает современную запись в другой CSS, который выражает похожее поведение:

```text
современный CSS
→ более совместимый CSS
```

Такое преобразование возможно только тогда, когда старый синтаксис действительно способен выразить нужный результат.

Polyfill добавляет отсутствующую реализацию. Для CSS это часто сложнее, чем для отдельного JavaScript API, потому что layout и rendering выполняет сам браузер.

Некоторые новые CSS-возможности нельзя полноценно воспроизвести только генерацией других declarations.

Поэтому:

```text
Autoprefixer ≠ универсальный transpiler ≠ универсальный polyfill
```

Каждый инструмент нужно оценивать по конкретной возможности, которую он преобразует.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Для чего нужен <code>postcss-preset-env</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`postcss-preset-env` объединяет набор CSS-преобразований и позволяет использовать часть современного CSS с контролируемыми fallback-правилами.

Его поведение зависит от конфигурации:

- выбранного набора возможностей;
- целевых браузеров;
- сохранения исходного синтаксиса;
- настройки Autoprefixer;
- версий входящих plugins.

Он может позволить писать современную конструкцию, а в итоговом CSS сохранить её вместе с более совместимым вариантом.

Но plugin не гарантирует полноценную поддержку любой возможности в старом браузере.

Например, если новая модель layout не имеет эквивалента в старом CSS, простое синтаксическое преобразование не сможет полностью воспроизвести её поведение.

Поэтому перед подключением проверяют:

1. Какие именно plugins активируются.
2. Какие преобразования нужны проекту.
3. Не поддерживает ли browserslist проекта исходный синтаксис уже без преобразования.
4. Не выполняет ли ту же работу сам сборщик.
5. Не увеличивает ли результат ненужными fallback-правилами.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему Browserslist лучше настроить один раз для проекта?</strong></summary>

<dl>
<dd>
<h2></h2>

Одну конфигурацию могут читать разные инструменты:

```text
Autoprefixer
Babel
инструменты анализа совместимости
части build pipeline
```

Это создаёт общий продуктовый контракт.

Без общей конфигурации возможна ситуация:

- JavaScript компилируется для одного набора браузеров;
- CSS prefixes добавляются для другого;
- документация команды заявляет третий набор.

Browserslist не фиксирует версии npm-пакетов и не определяет, какие браузеры используют разработчики локально.

Он описывает целевую среду продукта.

При изменении queries нужно оценить:

- размер итоговых assets;
- количество преобразований;
- наличие prefixes;
- необходимость polyfills;
- поддержку используемых CSS- и JavaScript-возможностей;
- реальные данные аудитории продукта.

Один список не означает одинаковое поведение всех инструментов: каждый использует его в рамках собственной задачи.

</dd>
</dl>

<details>
<summary><strong>Нужен ли Autoprefixer, если проект поддерживает только современные браузеры?</strong></summary>

<dl>
<dd>
<h2></h2>

Это зависит от Browserslist и используемого CSS.

Для многих современных свойств prefixes уже не нужны. В таком случае Autoprefixer может почти не изменить итоговый файл.

Но централизованная обработка остаётся полезной:

- разработчики пишут стандартный CSS;
- не нужно помнить prefixes вручную;
- изменение Browserslist автоматически влияет на результат;
- устаревшие prefixes могут удаляться;
- политика browser support остаётся единой.

При этом нельзя считать Autoprefixer обязательным по привычке.

Если выбранный сборщик уже выполняет эквивалентную обработку, отдельный plugin может дублировать pipeline.

Проверяют:

- документацию build tool;
- итоговый CSS;
- конфигурацию PostCSS;
- целевые браузеры;
- реально используемые свойства.

<details>
<summary><strong>Почему порядок Sass и PostCSS имеет значение?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычные PostCSS plugins вроде Autoprefixer ожидают корректный CSS.

SCSS содержит конструкции, которых нет в CSS:

```scss
$color: red;

@mixin control {
  display: flex;
}

.button {
  color: $color;
  @include control;
}
```

Поэтому сначала Sass должен скомпилировать их:

```text
SCSS → CSS
```

После этого PostCSS получает стандартные declarations:

```css
.button {
  color: red;
  display: flex;
}
```

Если plugin не поддерживает SCSS-синтаксис, передача ему необработанного файла приведёт к ошибке parsing или неправильной обработке.

У PostCSS существуют альтернативные parsers, способные разобрать другой синтаксис, но сам факт успешного parsing не означает, что каждый plugin понимает семантику Sass-конструкций.

Поэтому типичная надёжная цепочка:

```text
Sass compilation
→ CSS transformations
→ prefixing
→ optimization
→ output
```

Точный порядок остальных стадий определяет интеграция сборщика.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему опасно дублировать PostCSS plugins и встроенные возможности сборщика?</strong></summary>

<dl>
<dd>
<h2></h2>

Современный сборщик может уже выполнять:

- CSS Modules;
- минификацию;
- преобразование части современного CSS;
- генерацию source maps;
- обработку vendor prefixes.

Дополнительно подключённые plugins могут повторять ту же работу.

Например, Autoprefixer может запускаться отдельно и одновременно входить в настроенный `postcss-preset-env`.

Возможные последствия:

- конфигурацию сложнее понимать;
- увеличивается время сборки;
- предупреждения выводятся несколько раз;
- разные стадии используют разные Browserslist-настройки;
- source maps становятся сложнее;
- итоговый CSS проходит лишние преобразования;
- обновление одного инструмента неожиданно меняет результат другого.

Перед добавлением plugin проверяют:

1. Кто уже выполняет эту задачу.
2. В какой момент pipeline она выполняется.
3. Какая конфигурация Browserslist используется.
4. Нужен ли plugin в development и production.
5. Как выглядит итоговый CSS.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем CSS source maps?</strong></summary>

<dl>
<dd>
<h2></h2>

После нескольких преобразований итоговое правило может находиться в файле:

```text
assets/index-a1b2c3.css
```

Хотя разработчик написал его в:

```text
src/components/Button/Button.module.scss
```

Source map хранит соответствие между итоговым CSS и исходным файлом.

DevTools может показать:

- исходный SCSS-файл;
- номер строки;
- исходное имя selector;
- место объявления, а не только минифицированный bundle.

Карты особенно полезны при цепочке:

```text
SCSS
→ Sass
→ PostCSS
→ CSS Modules
→ bundler
→ minifier
```

Каждая стадия должна получить предыдущую карту, обновить её и передать дальше.

Если одна стадия карту отбросила, дальнейший инструмент уже не сможет полностью восстановить связь с исходником.

Source maps облегчают отладку, но не влияют на применение CSS. Их отсутствие делает поиск причины сложнее, однако само по себе не ломает стили.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Задача | Инструмент |
| --- | --- |
| Переменные, функции и генерация при сборке | Sass |
| Компиляция SCSS в CSS | Sass compiler |
| Цепочка AST-преобразований CSS | PostCSS |
| Вендорные префиксы | Autoprefixer |
| Часть современного CSS-синтаксиса | `postcss-preset-env` |
| Единый список целевых браузеров | Browserslist |
| Данные о поддержке CSS | Can I Use / `caniuse-lite` |
| Минификация CSS | cssnano или встроенная оптимизация сборщика |
| Локальные имена классов | CSS Modules |
| Отладка исходного SCSS | Source maps |
| Проверка работы pipeline | Анализ итогового production CSS |
