## Вопрос

<br>

 💬 **Как делать адаптивный дизайн? Чем media queries отличаются от container queries?**

<h2></h2>

<br>
<dl>
<dd>

Адаптивный дизайн, или responsive design, — подход, при котором интерфейс остаётся читаемым и удобным при разных размерах доступной области, способах ввода, масштабе текста и пользовательских настройках.

Основные инструменты адаптивного интерфейса:

- гибкие Flexbox- и Grid-раскладки;
- относительные размеры и ограничения через `min-*`/`max-*`;
- media queries для условий уровня viewport и устройства;
- container queries для условий уровня компонента;
- адаптивные изображения;
- проверка длинного и реального содержимого;
- учёт пользовательских настроек доступности.

Media query, или медиазапрос, проверяет характеристики среды отображения.

Он может зависеть от размера viewport:

```css
@media (min-width: 48rem) {
  .layout {
    grid-template-columns: 16rem 1fr;
  }
}
```

Но media queries проверяют не только ширину экрана. Они также могут учитывать:

- `orientation`;
- `resolution`;
- `hover` и `pointer`;
- `prefers-reduced-motion`;
- `prefers-color-scheme`;
- `prefers-contrast`;
- тип вывода вроде `screen` или `print`.

Media query подходит для решений уровня страницы: например, появления боковой колонки, изменения общей навигации или перестройки layout приложения.

Container query, или запрос к контейнеру, проверяет размер подходящего контейнера-предка, а не всего viewport.

Это полезно для переиспользуемого компонента. Одна карточка может находиться в узкой боковой панели или в широкой основной области и менять внутреннюю раскладку в зависимости от реально выделенного ей пространства.

Сначала предка объявляют query container:

```css
.cards-region {
  container-type: inline-size;
}
```

Затем потомок может реагировать на его inline-размер:

```css
@container (min-width: 36rem) {
  .card {
    grid-template-columns: 10rem 1fr;
  }
}
```

Стилизуемый `.card` не проверяет собственную ширину напрямую. Он находит ближайшего подходящего query container среди предков.

Для устойчивой архитектуры контейнеру можно дать имя:

```css
.cards-region {
  container-name: cards;
  container-type: inline-size;
}
```

или использовать сокращение:

```css
.cards-region {
  container: cards / inline-size;
}
```

После этого запрос можно явно связать с нужным контейнером:

```css
@container cards (min-width: 36rem) {
  .card {
    grid-template-columns: 10rem 1fr;
  }
}
```

Это защищает компонент от случайного появления другого query container между ним и ожидаемым предком.

`container-type: inline-size` позволяет выполнять запросы по inline-размеру контейнера. В обычном горизонтальном режиме письма это чаще ширина.

Объявление контейнера может влиять на расчёт его размеров: браузер не должен создавать циклическую зависимость, при которой размер контейнера определяется потомком, а стили потомка одновременно зависят от размера контейнера.

Для размеров, зависящих от query container, существуют container query units:

- `cqw` — процент ширины контейнера;
- `cqh` — процент высоты;
- `cqi` — процент inline-размера;
- `cqb` — процент block-размера;
- `cqmin` — процент меньшего измерения;
- `cqmax` — процент большего измерения.

Например:

```css
.card__title {
  font-size: clamp(1rem, 4cqi, 1.5rem);
}
```

Однако для существенного изменения структуры компонента условие `@container` обычно понятнее, чем попытка решить всё только плавными единицами.

Единицы измерения выбирают по нужной зависимости.

`rem` в обычных CSS-объявлениях связан с `font-size` корневого элемента `<html>`:

```css
.card {
  padding: 1rem;
}
```

Это позволяет общей шкале размеров следовать пользовательскому масштабированию текста.

`em` для большинства свойств зависит от вычисленного размера шрифта самого элемента:

```css
.button {
  font-size: 1.25rem;
  padding: 0.5em 1em;
}
```

В этом случае padding масштабируется вместе с текстом кнопки.

Внутри самого свойства `font-size` единица `em` вычисляется от размера шрифта родителя:

```css
.child {
  font-size: 1.5em;
}
```

Поэтому при глубокой вложенности размеры в `em` могут последовательно умножаться.

Проценты вычисляются относительно величины, определённой конкретным CSS-свойством. Это не всегда просто ширина родителя.

Например:

- процентный `width` обычно зависит от ширины containing block;
- процентный `padding` в обычной раскладке исторически вычисляется от inline-размера containing block;
- процентный `transform: translate()` зависит от размера самого трансформируемого элемента.

Единицы `vw` и `vh` зависят от viewport.

На мобильных устройствах высота видимой области меняется при появлении и скрытии панелей браузера. Для более явного управления существуют:

- `svh` — высота малого viewport;
- `lvh` — высота большого viewport;
- `dvh` — текущая динамическая высота viewport.

Например:

```css
.screen {
  min-height: 100dvh;
}
```

`dvh` следует за изменениями видимой области, но из-за этого размер элемента может меняться во время появления или скрытия интерфейса браузера.

`svh` полезен, когда содержимое должно гарантированно помещаться даже при открытых панелях. `lvh` описывает максимальную доступную высоту, но часть такого элемента может временно оказаться за панелями браузера.

Функция `clamp(min, preferred, max)` ограничивает вычисляемое значение снизу и сверху:

```css
.title {
  font-size: clamp(
    1rem,
    0.8rem + 1vw,
    1.5rem
  );
}
```

Размер плавно изменяется вместе с viewport, но не становится меньше `1rem` или больше `1.5rem`.

Для текста полезно сохранять часть выражения в `rem`, а не использовать только `vw`. Это позволяет размеру лучше реагировать на пользовательское увеличение текста и не становиться слишком мелким на узком экране.

Breakpoint, или точку перелома, выбирают там, где конкретная раскладка перестаёт справляться с содержимым:

- подписи не помещаются;
- карточки становятся слишком узкими;
- элементы управления перекрываются;
- строка действий больше не помещается;
- таблица теряет читаемость;
- боковая колонка забирает слишком много места.

Набор популярных размеров телефонов и планшетов не заменяет такую проверку. Устройства меняются, а проблема layout возникает из-за доступного пространства и содержимого.

Адаптивность не сводится к ширине viewport. Нужно учитывать:

- увеличение текста и zoom;
- длинные локализованные подписи;
- экранную клавиатуру;
- safe areas устройства;
- адаптивные изображения;
- портретную и альбомную ориентацию;
- уменьшение анимации;
- разные способы ввода.

`hover` и `pointer` описывают возможности основного устройства ввода. На гибридном устройстве одновременно могут быть доступны touchscreen, мышь и перо, поэтому существуют `any-hover` и `any-pointer`.

Важное действие не должно существовать только при наведении. Hover можно использовать для дополнительной обратной связи, но основная функция должна оставаться доступной через click, touch и клавиатуру.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Что значит mobile-first CSS?</strong></summary>

<dl>
<dd>
<h2></h2>

Базовые стили пишутся для малого доступного пространства, а затем через запросы с `min-width` добавляется более сложная раскладка:

```css
.layout {
  display: block;
}

@media (min-width: 48rem) {
  .layout {
    display: grid;
    grid-template-columns: 16rem 1fr;
  }
}
```

Базовая версия работает без выполнения дополнительного условия. На широком viewport подключается улучшенная раскладка.

Это соответствует идее progressive enhancement: сначала предоставляется рабочая основа, затем добавляются улучшения для среды, способной их использовать.

Mobile-first не означает, что интерфейс проектируется только для телефона. Он должен работать при любом малом доступном пространстве, включая узкое окно desktop-браузера, split screen и встроенный WebView.

Не любой проект обязан использовать только `min-width`. Иногда компоненту понятнее локальное условие с `max-width`. Важнее последовательная система и отсутствие конфликтующих запросов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда container query лучше media query?</strong></summary>

<dl>
<dd>
<h2></h2>

Container query лучше, когда компонент должен адаптироваться к размеру своего окружения, а не всего viewport.

Например, одна карточка используется:

- в узкой боковой панели;
- в основной колонке;
- внутри модального окна;
- в адаптивной сетке карточек.

Viewport во всех случаях может быть одинаковым, но доступная ширина компонента различается.

```css
.card-region {
  container-type: inline-size;
}

@container (min-width: 32rem) {
  .card {
    display: grid;
    grid-template-columns: 8rem 1fr;
  }
}
```

Media query подходит для решений уровня страницы:

```css
@media (min-width: 64rem) {
  .page {
    grid-template-columns: 18rem 1fr;
  }
}
```

Container query подходит для внутреннего устройства переиспользуемого компонента.

Они не заменяют друг друга полностью. Media query может изменить общую структуру страницы, а container query внутри этой структуры адаптирует отдельные компоненты.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли элемент сделать container query к собственному размеру?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычный size container query проверяет подходящий контейнер-предок, а не сам стилизуемый элемент.

Такое ограничение предотвращает прямой цикл:

```text
стиль элемента зависит от его ширины →
стиль изменяет ширину →
условие запроса меняется снова
```

Обычно компонент получает специальную внешнюю оболочку:

```html
<div class="card-region">
  <article class="card">
    ...
  </article>
</div>
```

```css
.card-region {
  container-type: inline-size;
}

@container (min-width: 30rem) {
  .card {
    grid-template-columns: 10rem 1fr;
  }
}
```

Если контейнером сделать внутренний элемент, запрос всё равно применяется к его потомкам, а не к самому контейнеру.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как <code>rem</code> работает внутри media queries?</strong></summary>

<dl>
<dd>
<h2></h2>

В обычных CSS-объявлениях `rem` зависит от вычисленного `font-size` элемента `<html>`.

Но относительные единицы в условиях media queries вычисляются независимо от стилей страницы — от начального размера шрифта браузера.

Например:

```css
html {
  font-size: 20px;
}

@media (min-width: 48rem) {
  /* breakpoint не становится автоматически равен 48 × 20px */
}
```

Изменение `font-size` у `<html>` не должно использоваться как способ сдвинуть media breakpoint.

На практике `em` или `rem` в медиазапросах всё равно полезны: breakpoint может реагировать на пользовательские настройки базового размера шрифта браузера лучше, чем жёсткое значение в `px`.

Главное — не считать, что условие media query напрямую использует CSS-значение `font-size`, заданное для документа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем <code>clamp()</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`clamp()` принимает три значения:

```css
clamp(minimum, preferred, maximum)
```

Например:

```css
.title {
  font-size: clamp(
    1rem,
    0.75rem + 1.5vw,
    2rem
  );
}
```

Размер:

- не станет меньше `1rem`;
- плавно меняется через предпочтительное выражение;
- не станет больше `2rem`.

Это удобно для:

- типографики;
- отступов;
- расстояний между секциями;
- размеров декоративных элементов;
- ширины отдельных компонентов.

`clamp()` не заменяет breakpoint, если должна измениться сама структура интерфейса. Переход с одной колонки на две лучше выразить через media или container query.

Для текста не следует строить preferred-значение только на `vw`. Комбинация `rem` и viewport units лучше сохраняет связь с пользовательским масштабированием.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>em</code> отличается от <code>rem</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`rem` в обычном CSS-объявлении вычисляется от `font-size` корневого элемента `<html>`:

```css
.card {
  padding: 1rem;
}
```

Это удобно для общей шкалы размеров приложения.

`em` для большинства свойств зависит от вычисленного размера шрифта самого элемента:

```css
.button {
  font-size: 20px;
  padding: 0.5em 1em;
}
```

Здесь вертикальный padding равен `10px`, а горизонтальный — `20px`.

В свойстве `font-size` единица `em` вычисляется относительно размера шрифта родителя:

```css
.parent {
  font-size: 20px;
}

.child {
  font-size: 1.5em;
}
```

Размер `.child` станет `30px`.

После этого:

```css
.child {
  padding: 1em;
}
```

даст padding `30px`, потому что для padding используется уже собственный вычисленный `font-size` элемента.

`em` подходит, когда весь компонент должен масштабироваться вместе со своим текстом. `rem` удобнее для общей предсказуемой шкалы документа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>cqw</code>/<code>cqh</code> отличаются от <code>cqi</code>/<code>cqb</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`cqw` и `cqh` используют физические измерения query container:

- `1cqw` — один процент ширины;
- `1cqh` — один процент высоты.

`cqi` и `cqb` используют логические оси:

- `1cqi` — один процент inline-размера;
- `1cqb` — один процент block-размера.

В обычном горизонтальном режиме письма:

```text
cqi примерно соответствует cqw
cqb примерно соответствует cqh
```

Но при другом `writing-mode` inline- и block-оси могут изменить физическое направление.

Для компонентов, которые должны корректно работать в разных направлениях письма, логические `cqi` и `cqb` обычно точнее выражают намерение.

Дополнительно существуют:

- `cqmin` — процент меньшего размера контейнера;
- `cqmax` — процент большего размера контейнера.

Container units подходят для плавного масштабирования внутри компонента, но их всё равно ограничивают через `min()`, `max()` или `clamp()`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>vh</code>, <code>svh</code>, <code>lvh</code> и <code>dvh</code> отличаются?</strong></summary>

<dl>
<dd>
<h2></h2>

На мобильных устройствах размер видимой области меняется из-за адресной строки и других панелей браузера.

`svh` использует малую высоту viewport — состояние, при котором интерфейс браузера занимает больше места:

```css
.screen {
  min-height: 100svh;
}
```

Это помогает гарантировать, что содержимое помещается при открытых панелях.

`lvh` использует большую высоту viewport — состояние с максимально скрытым интерфейсом браузера:

```css
.hero {
  min-height: 100lvh;
}
```

При открытых панелях часть такой области может оказаться закрыта.

`dvh` использует текущую динамическую высоту:

```css
.dialog-layer {
  min-height: 100dvh;
}
```

Она обновляется при изменении интерфейса браузера, поэтому layout может перерасчитываться во время прокрутки.

Обычный `vh` сохраняется для совместимости, но не всегда выражает нужное поведение мобильного интерфейса явно.

Выбор зависит от задачи:

- гарантированно помещаться — `svh`;
- использовать максимальную площадь — `lvh`;
- следовать текущей видимой области — `dvh`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>pointer</code>/<code>hover</code> отличаются от <code>any-pointer</code>/<code>any-hover</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`pointer` и `hover` описывают основной способ ввода устройства.

Например:

```css
@media (hover: hover) and (pointer: fine) {
  .button:hover {
    background: var(--hover-color);
  }
}
```

Условие обычно соответствует точному указателю, способному к наведению, например мыши.

`any-pointer` и `any-hover` проверяют любой доступный способ ввода.

Гибридное устройство может иметь touchscreen как основной ввод, но при этом поддерживать подключённую мышь:

```css
@media (any-hover: hover) {
  /* хотя бы одно устройство поддерживает hover */
}
```

Нельзя делать важную функцию доступной только через `:hover`, потому что:

- touchscreen может не поддерживать настоящее наведение;
- пользователь может работать с клавиатуры;
- основное и дополнительное устройства ввода могут меняться.

Media query по способу ввода используют для улучшения интерфейса, а не для удаления базового способа взаимодействия.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему важно учитывать <code>prefers-reduced-motion</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Пользователь может попросить систему уменьшить движение из-за дискомфорта, вестибулярных нарушений или личных предпочтений.

CSS позволяет упростить анимации:

```css
@media (prefers-reduced-motion: reduce) {
  .animated {
    animation: none;
    transition-duration: 0.01ms;
  }
}
```

В первую очередь уменьшают:

- параллакс;
- большие перемещения;
- вращение и масштабирование;
- автоматическую прокрутку;
- бесконечное мерцание или пульсацию;
- фоновые декоративные анимации.

Не каждую анимацию обязательно полностью отключать. Небольшое изменение цвета или мгновенная смена состояния может сохранять полезную обратную связь без сильного движения.

JavaScript-анимации также должны проверять соответствующий media query, если CSS-правила сами их не контролируют.

## Где это встречается во frontend

| Задача | Инструмент |
| --- | --- |
| Адаптация общей раскладки страницы | Media queries |
| Компонент в разных контейнерах | Container queries |
| Плавный размер заголовка | `clamp()` с ограничениями в `rem` |
| Размер относительно компонента | `cqi`/`cqw` |
| Полноэкранная область на мобильном | `svh`, `lvh` или `dvh` по задаче |
| Удобство разных способов ввода | `pointer`, `hover`, `any-pointer`, `any-hover` |
| Уменьшить движение | `prefers-reduced-motion` |
| Учесть вырезы экрана | `env(safe-area-inset-*)` |
| Изображение под разные размеры | `srcset`, `sizes` или `<picture>` |
