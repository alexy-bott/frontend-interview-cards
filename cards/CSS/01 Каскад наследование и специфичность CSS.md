## Вопрос

<br>

 💬 **Как браузер решает, какое CSS-правило применить? Что такое каскад, наследование и специфичность?**

<h2></h2>

<br>
<dl>
<dd>

Каскад — алгоритм, по которому браузер выбирает значение CSS-свойства, когда к одному элементу подходят несколько объявлений.

Браузер не начинает со сравнения специфичности. Для каждого свойства он последовательно учитывает:

1. Применимость правила: подходит ли селектор, выполняются ли условия `@media`, `@supports` и другие ограничения.
2. Происхождение и важность объявления: browser, user или author styles, обычное объявление или `!important`.
3. Каскадный слой `@layer`.
4. Специфичность селектора.
5. Близость области `@scope`, если конфликтующие правила используют scope.
6. Порядок объявления: при равенстве предыдущих условий побеждает более позднее правило.

Происхождение, или origin, показывает, откуда пришёл стиль:

- user-agent origin — встроенные стили браузера;
- user origin — стили и настройки пользователя;
- author origin — CSS самого сайта.

Упрощённый порядок от меньшего приоритета к большему выглядит так:

1. Обычные стили браузера.
2. Обычные стили пользователя.
3. Обычные стили сайта.
4. CSS animations.
5. Важные стили сайта.
6. Важные стили пользователя.
7. Важные стили браузера.
8. CSS transitions.

На практике большинство конфликтов происходит внутри author styles приложения.

Для обычных авторских объявлений действуют следующие правила:

1. Стиль вне `@layer` приоритетнее обычных стилей внутри слоёв.
2. Среди обычных слоёв более поздний слой приоритетнее более раннего.
3. В одном слое сравнивается специфичность.
4. При одинаковой специфичности побеждает более позднее объявление.

Встроенный атрибут `style` имеет повышенный приоритет среди обычных авторских стилей:

```html
<button style="color: red">Save</button>
```

Обычный selector из таблицы стилей не переопределит такой `color` только за счёт большей специфичности. Для этого потребуется подходящее важное объявление или другой более высокий уровень каскада.

Специфичность, или specificity, — условный вес селектора. Её удобно представлять четырьмя группами:

```text
inline styles - ID - classes/attributes/pseudo-classes - elements/pseudo-elements
```

Например:

```text
#dialog             0-1-0-0
.dialog             0-0-1-0
button.dialog       0-0-1-1
.card button:hover  0-0-2-1
```

Значения сравниваются слева направо. Их не нужно складывать в одно число.

Идентификатор приоритетнее любого количества классов в следующей группе. Классы, атрибуты и псевдоклассы приоритетнее селекторов элементов и псевдоэлементов.

Универсальный селектор `*` и combinators вроде `>`, `+` и пробела специфичность не увеличивают.

Псевдокласс `:where()` всегда имеет нулевую специфичность, поэтому подходит для базовых правил, которые должно быть легко переопределить:

```css
:where(.card button) {
  color: inherit;
}
```

Наследование, или inheritance, применяется после каскада. Если элемент не получил собственного значения наследуемого свойства, браузер берёт вычисленное значение у родителя.

Обычно наследуются свойства текста:

- `color`;
- `font-family`;
- `font-size`;
- `line-height`;
- `text-align`.

Свойства раскладки обычно не наследуются:

- `margin`;
- `padding`;
- `border`;
- `width`;
- `display`.

Поэтому цвет можно задать контейнеру, а отступы дочерних элементов нужно описывать отдельно.

Если на дочернем элементе есть собственное подходящее объявление, оно участвует в каскаде и заменяет унаследованное значение независимо от специфичности правила на родителе.

Каскадные слои, или cascade layers, задают явный приоритет групп стилей:

```css
@layer reset, base, components, utilities;
```

Для обычных объявлений более поздний слой имеет больший приоритет:

```text
reset < base < components < utilities
```

Это позволяет utility-слою переопределять component-слой без увеличения специфичности.

Для объявлений с `!important` порядок слоёв разворачивается:

```text
reset > base > components > utilities
```

Важные объявления внутри слоёв также приоритетнее важных авторских объявлений вне слоёв. Такая инверсия позволяет защитить намеренно важные базовые правила от случайного переопределения более поздним CSS.

`!important` не увеличивает специфичность селектора. Он переносит объявление в отдельную, более приоритетную группу каскада. Специфичность сравнивается только между объявлениями, уже оказавшимися на одном уровне origin, importance и layer.

Конфликт стилей проверяют в DevTools: находят свойство в списке правил и смотрят, какие объявления зачёркнуты и по какой причине.

В поддерживаемом CSS полезно сохранять низкую специфичность, не строить глубокие селекторы, явно управлять слоями и использовать `!important` только для намеренно жёсткого приоритета, а не для исправления непонятного каскада.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что сильнее: <code>.card button</code> или <code>.button</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Специфичность `.card button` равна:

```text
0-0-1-1
```

Селектор содержит один класс и один тип элемента.

Специфичность `.button` равна:

```text
0-0-1-0
```

Поэтому при одинаковых origin, importance и layer селектор `.card button` приоритетнее.

Но слой сравнивается раньше специфичности. Если `.button` находится в более приоритетном cascade layer, он может победить более специфичный `.card button`.

Аналогично итог может изменить `!important`, inline style, transition или другое более высокое место в каскаде.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как рассчитывается специфичность сложного селектора?</strong></summary>

<dl>
<dd>
<h2></h2>

Специфичность считают по отдельным группам:

1. Inline styles.
2. ID-селекторы.
3. Классы, атрибуты и псевдоклассы.
4. Селекторы элементов и псевдоэлементов.

Например:

```css
#app .card[data-state="active"] button::before
```

имеет специфичность:

```text
0-1-2-2
```

Здесь есть:

- один ID — `#app`;
- один класс — `.card`;
- один атрибут — `[data-state="active"]`;
- один элемент — `button`;
- один псевдоэлемент — `::before`.

Группы сравниваются слева направо. Селектор:

```text
0-1-0-0
```

приоритетнее селектора:

```text
0-0-100-100
```

потому что наличие ID решает конфликт до сравнения следующих групп.

`!important` не является частью специфичности.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как <code>:is()</code>, <code>:not()</code>, <code>:has()</code> и <code>:where()</code> влияют на специфичность?</strong></summary>

<dl>
<dd>
<h2></h2>

Псевдоклассы `:is()`, `:not()` и `:has()` сами не добавляют отдельный вес псевдокласса. Вместо этого используется наибольшая специфичность селектора из списка аргументов.

```css
:is(.card, #dialog) button
```

В расчёте будет использована специфичность `#dialog`, даже если конкретный элемент совпал через `.card`.

То же правило применяется к `:not()` и `:has()`:

```css
button:not(#primary)
article:has(.warning)
```

`button:not(#primary)` получает вес ID из аргумента `#primary`.

Псевдокласс `:where()` является исключением. Его специфичность всегда равна нулю независимо от содержимого:

```css
:where(#app .card button) {
  color: black;
}
```

Это позволяет описать точный selector без создания тяжёлого для переопределения правила.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>!important</code> опасен?</strong></summary>

<dl>
<dd>
<h2></h2>

`!important` переносит объявление из обычной группы каскада в группу важных объявлений.

Если исправлять каждый конфликт через `!important`, следующий разработчик часто будет вынужден добавить ещё один `!important`. После этого конфликт начнут решать специфичностью, слоями и порядком уже внутри важных объявлений.

В результате причина исходного конфликта остаётся скрытой, а переопределение становится сложнее.

Сначала проверяют:

- подходит ли selector;
- порядок подключения файлов;
- cascade layer;
- специфичность;
- предусмотренный библиотекой API настройки.

`!important` может быть оправдан для узкого служебного правила, которое по контракту должно иметь жёсткий приоритет:

```css
@layer utilities {
  .is-hidden {
    display: none !important;
  }
}
```

Но его не следует использовать как основной способ управления стилями приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли что-то переопределить <code>!important</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Да. `!important` не означает абсолютный максимальный приоритет.

Важные пользовательские стили приоритетнее важных стилей сайта. Это необходимо, например, чтобы пользователь мог применять accessibility-настройки.

Важные стили user-agent origin также находятся выше важных author styles.

Активный CSS transition располагается ещё выше важных объявлений. Поэтому временно вычисляемое transition-значение может иметь приоритет над `!important`.

Внутри author origin также сравниваются cascade layers, inline styles, специфичность и порядок объявления по правилам группы важных объявлений.

`!important` гарантирует приоритет над обычными объявлениями более низкого уровня, но не отменяет остальные этапы каскада.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>color</code> наследуется, а <code>margin</code> нет?</strong></summary>

<dl>
<dd>
<h2></h2>

Каждое CSS-свойство имеет собственное правило наследования.

Текстовые свойства часто наследуются, потому что это удобно для документа:

```css
.article {
  color: #222;
  font-family: sans-serif;
}
```

Дочерние текстовые элементы автоматически получают согласованное оформление, пока не зададут собственное значение.

Свойства раскладки вроде `margin`, `padding` и `border` по умолчанию не наследуются. Иначе каждый вложенный элемент мог бы случайно получить отступы и границы всех родителей.

Наследование применяется только при отсутствии собственного cascaded value у элемента. Это не соревнование специфичности между родителем и ребёнком.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делают <code>inherit</code>, <code>initial</code>, <code>unset</code>, <code>revert</code> и <code>revert-layer</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`inherit` заставляет свойство взять вычисленное значение у родителя, даже если обычно это свойство не наследуется:

```css
.child {
  border-color: inherit;
}
```

`initial` устанавливает начальное значение свойства из CSS specification:

```css
.element {
  display: initial;
}
```

Начальное значение не обязательно совпадает со стилем браузера для конкретного HTML-элемента.

`unset` работает как `inherit` для наследуемого свойства и как `initial` для ненаследуемого:

```css
.element {
  color: unset;
  margin: unset;
}
```

`revert` отменяет значение текущего origin и позволяет получить результат более низкого origin, например встроенный стиль браузера.

`revert-layer` отменяет объявления текущего cascade layer и возвращает результат предыдущих слоёв внутри каскада.

Эти keywords управляют значением свойства, но сами объявления всё равно участвуют в обычном алгоритме каскада.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужны cascade layers?</strong></summary>

<dl>
<dd>
<h2></h2>

Cascade layers позволяют явно задать приоритет групп стилей:

```css
@layer reset, base, components, utilities;
```

Для обычных объявлений более поздние слои приоритетнее:

```text
reset < base < components < utilities
```

Поэтому utility-класс может переопределить компонент независимо от специфичности конкретных селекторов:

```css
@layer components {
  .card .title {
    color: black;
  }
}

@layer utilities {
  .text-muted {
    color: gray;
  }
}
```

Если элемент имеет оба класса, обычное объявление из `utilities` победит правило из `components`, хотя селектор компонента специфичнее.

Слои полезны, когда в проекте есть:

- reset;
- базовые правила;
- компоненты;
- utility-классы;
- стили сторонних библиотек.

Они делают взаимный приоритет этих групп частью архитектуры, а не случайным следствием порядка файлов и длинных селекторов.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Проблема | Что проверить |
| --- | --- |
| Стиль не применился | Подходит ли селектор, активен ли `media query`, затем origin/importance, слой, специфичность и порядок |
| Нужно переопределить библиотеку | Слой, порядок, официальный API переопределения, не сразу `!important` |
| Текст унаследовал цвет | Inherited `color` |
| CSS Modules не помогли | Они меняют имена классов, но не отключают каскад и специфичность |
| SCSS-вложенность стала глубокой | Выросла специфичность селектора |
| Нужно безопасно снизить вес селектора | `:where()` или упрощение селектора |
