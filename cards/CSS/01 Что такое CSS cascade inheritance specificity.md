## Вопрос

<br>

 💬 **Как браузер решает, какое CSS-правило применить? Что такое каскад, наследование и специфичность?**

<h2></h2>

<br>
<dl>
<dd>

Каскад - алгоритм, по которому браузер выбирает значение CSS-свойства, когда к одному элементу подходят несколько объявлений. Браузер не сравнивает только селекторы: сначала отбрасывает неподходящие правила, затем учитывает происхождение и важность стилей, каскадный слой, специфичность и порядок объявления.

Происхождение, или origin, показывает, откуда пришёл стиль: из таблицы стилей браузера, пользовательских настроек или кода страницы. Для обычных стилей страницы важен следующий практический порядок:

1. Объявление с `!important` имеет приоритет над обычным объявлением того же происхождения.
2. Среди обычных авторских стилей правило вне `@layer` приоритетнее правил внутри слоёв. Между слоями действует заранее заданный порядок.
3. Если предыдущие условия равны, сравнивается специфичность селекторов.
4. При одинаковой специфичности побеждает объявление, расположенное позже.

Специфичность, или specificity, - условный вес селектора. Идентификатор `#dialog` весит больше класса `.dialog`; класс, атрибут или псевдокласс - больше селектора элемента `button` или псевдоэлемента `::before`. Встроенный атрибут `style` имеет отдельный, более высокий приоритет среди обычных авторских стилей. Псевдокласс `:where()` всегда имеет нулевую специфичность, поэтому подходит для базовых правил, которые должно быть легко переопределить.

Наследование, или inheritance, работает иначе. Если элемент не получил собственное значение наследуемого свойства, браузер может взять вычисленное значение у родителя. Обычно наследуются свойства текста, например `color`, `font-family` и `line-height`; свойства раскладки `margin`, `padding`, `border` и `display` по умолчанию не наследуются. Поэтому цвет можно задать контейнеру, а отступы дочерних элементов нужно описывать отдельно.

Каскадные слои, или cascade layers, задают явный приоритет групп стилей. Например, можно объявить порядок `reset`, `base`, `components`, `utilities`, чтобы правило из более приоритетного слоя переопределяло менее приоритетный слой без наращивания специфичности. Это делает порядок стилей частью архитектуры, а не случайным следствием длинных селекторов.

Для объявлений с `!important` порядок слоёв разворачивается: важное объявление из первого слоя приоритетнее важного объявления из последующего слоя, а важные объявления внутри слоёв приоритетнее важных объявлений вне слоёв. Такая инверсия позволяет защитить намеренно важные базовые правила от случайного переопределения в более позднем слое.

Конфликт стилей проверяют в DevTools: находят свойство в списке применённых правил и смотрят, какие объявления зачёркнуты и почему. В поддерживаемом CSS полезно сохранять низкую специфичность, не строить глубокие селекторы и использовать `!important` только для намеренно жёсткого приоритета, а не для исправления непонятного каскада.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что сильнее: <code>.card button</code> или <code>.button</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`.card button` имеет класс + тип элемента, а `.button` имеет один класс. Поэтому `.card button` специфичнее. Но если используется cascade layer или `!important`, итог может измениться.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>!important</code> опасен?</strong></summary>

<dl>
<dd>
<h2></h2>

Он переводит объявление в группу важных объявлений и тем самым меняет обычный порядок каскада. Если исправлять каждый конфликт через `!important`, для следующего переопределения часто потребуется ещё один `!important`, а причина исходного конфликта останется скрытой.

Сначала проверяют селектор, порядок подключения, каскадный слой и предусмотренный библиотекой способ настройки. `!important` может быть оправдан в служебном utility-классе, то есть классе с одной узкой задачей, который по контракту всегда должен побеждать, но не как основной способ управления стилями.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>color</code> наследуется, а <code>margin</code> нет?</strong></summary>

<dl>
<dd>
<h2></h2>

CSS-свойства имеют разные правила наследования. Текстовые свойства часто наследуются, потому что это удобно для документа. Свойства раскладки вроде `margin`/`padding` не наследуются, чтобы каждый блок не получал случайные отступы от родителей.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужны cascade layers?</strong></summary>

<dl>
<dd>
<h2></h2>

Они позволяют явно задать приоритет групп стилей. Например, слой utility-классов может переопределять слой компонентов независимо от специфичности конкретного селектора, если слои объявлены в таком порядке.

Это полезно, когда в проекте есть reset-стили, базовые правила, компоненты, utility-классы и стили библиотек. Слои делают их взаимный приоритет явной частью архитектуры.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Проблема | Что проверить |
| --- | --- |
| Стиль не применился | Подходит ли селектор, активен ли `media query`, затем слой, специфичность и порядок |
| Нужно переопределить библиотеку | Слой, порядок, официальный API переопределения, не сразу `!important` |
| Текст унаследовал цвет | Inherited `color` |
| CSS Modules не помогли | Глобальные селекторы или порядок каскада |
| SCSS-вложенность стала глубокой | Выросла специфичность селектора |
| Нужно безопасно снизить вес селектора | `:where()` или упрощение селектора |
