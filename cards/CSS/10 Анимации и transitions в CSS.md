## Вопрос

<br>

 💬 **Чем отличаются CSS transitions и animations? Какие свойства лучше анимировать для производительности?**

<h2></h2>

<br>
<dl>
<dd>

CSS transition, или переход, описывает, как браузер должен перейти от старого вычисленного значения CSS-свойства к новому.

Изменение состояния может произойти из-за:

- добавления класса;
- `:hover` или `:focus`;
- изменения атрибута;
- выполнения media query;
- изменения custom property, используемой в значении;
- обновления inline style из JavaScript.

```css
.button {
  background-color: royalblue;
  transition: background-color 150ms ease;
}

.button:hover {
  background-color: navy;
}
```

Transition не описывает самостоятельный сценарий. Он запускается, когда подходящее свойство действительно меняет вычисленное значение.

Переход возможен, если браузер умеет анимировать это свойство и находить промежуточные значения между начальным и конечным состояниями. Например, цвет или длину можно интерполировать, а многие дискретные значения переключаются без плавных промежуточных состояний.

CSS animation, или ключевая анимация, связывает элемент с временным сценарием `@keyframes`:

```css
@keyframes pulse {
  0% {
    opacity: 0.5;
  }

  50% {
    opacity: 1;
  }

  100% {
    opacity: 0.5;
  }
}

.indicator {
  animation: pulse 1.5s ease-in-out infinite;
}
```

Через `@keyframes` можно задать несколько промежуточных состояний, а свойства `animation-*` управляют:

- длительностью;
- задержкой;
- timing function;
- количеством повторов;
- направлением;
- паузой;
- отображением до и после выполнения.

Animation может начаться сразу после применения `animation-name` и не требует отдельной смены между двумя состояниями, как transition.

Упрощённо формирование кадра можно представить этапами:

1. **Style** — вычисление применённых CSS-значений.
2. **Layout** — расчёт размеров и положения коробок.
3. **Paint** — отрисовка пикселей.
4. **Composite** — сборка подготовленных слоёв в итоговый кадр.

Не каждое изменение обязательно проходит все этапы. Конкретная работа зависит от свойства, размера затронутой области, структуры страницы и решений браузера.

Изменение геометрических свойств может потребовать нового layout:

- `width`;
- `height`;
- `margin`;
- `padding`;
- `top` и `left`;
- `font-size`;
- размеров Grid- и Flex-элементов.

После layout обычно требуется paint затронутой области и последующая композиция кадра.

Свойства вроде:

- `color`;
- `background`;
- `border-color`;
- `box-shadow`;

обычно не меняют геометрию, но могут потребовать нового paint.

`transform` и `opacity` браузер часто может обновлять на стадии compositing без перерасчёта геометрии соседних элементов:

```css
.panel {
  transform: translateX(100%);
  opacity: 0;
  transition:
    transform 200ms ease,
    opacity 200ms ease;
}

.panel.is-open {
  transform: translateX(0);
  opacity: 1;
}
```

`transform` меняет визуальное отображение элемента, но не его место в обычной раскладке. Соседние элементы продолжают учитывать исходную геометрию его коробки.

Поэтому движение интерфейса обычно реализуют через `translate`, `scale` или `rotate`, а появление и исчезновение — через `opacity`.

Но compositor-only выполнение не гарантируется самим CSS-кодом. Браузер решает:

- создавать ли отдельный compositing layer;
- когда его создать и удалить;
- можно ли обновить свойство без повторной растеризации;
- достаточно ли памяти для дополнительных слоёв.

Даже compositing-анимация не бесплатна:

- большие слои занимают память;
- масштабирование растрового содержимого может выглядеть размыто или потребовать новой растеризации;
- большие прозрачные области увеличивают стоимость композиции;
- фильтры и размытие могут быть дорогими;
- множество одновременно движущихся элементов создаёт нагрузку;
- JavaScript и другие long tasks могут блокировать подготовку кадров.

Поэтому правило «анимировать только `transform` и `opacity`» является хорошей отправной точкой для движения, но не заменяет профилирование.

Свойство `will-change` заранее сообщает браузеру, какое свойство скоро изменится:

```css
.panel {
  will-change: transform;
}
```

Браузер может заранее подготовить оптимизацию, например отдельный слой.

Но это подсказка, а не команда и не обязательное ускорение. Подготовленные слои расходуют память и ресурсы, поэтому постоянный `will-change` на большом количестве элементов способен ухудшить производительность.

Его используют:

- для конкретного элемента;
- при подтверждённой проблеме;
- незадолго до изменения;
- с последующим удалением, если оптимизация больше не нужна.

Проблему проверяют в DevTools Performance. Ищут:

- пропущенные кадры;
- long tasks на main thread;
- частые или длительные layout;
- большие paint areas;
- дорогие эффекты;
- чрезмерное количество compositing layers.

На экране с частотой 60 Гц новый кадр появляется примерно каждые `16.7ms`, но доступное JavaScript и rendering-время меньше, а на экранах с другой частотой бюджет отличается.

Медиазапрос `prefers-reduced-motion: reduce` сообщает, что пользователь предпочитает уменьшенное движение:

```css
@media (prefers-reduced-motion: reduce) {
  .panel {
    transition-duration: 0.01ms;
  }

  .indicator {
    animation: none;
  }
}
```

В первую очередь уменьшают:

- большие перемещения;
- параллакс;
- масштабирование;
- автоматическое движение;
- бесконечные декоративные анимации;
- интенсивное мерцание и пульсацию.

Не каждую смену состояния нужно полностью удалять. Небольшое изменение цвета или короткое затухание может сохранить понятную обратную связь без выраженного движения.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Когда transition, а когда animation?</strong></summary>

<dl>
<dd>
<h2></h2>

Transition подходит, когда есть два состояния:

```css
.button {
  opacity: 0.7;
  transition: opacity 150ms ease;
}

.button:hover {
  opacity: 1;
}
```

Типичные случаи:

- hover;
- focus;
- открытый и закрытый компонент;
- активное состояние;
- добавление или удаление класса.

Animation подходит, когда требуется временной сценарий:

```css
@keyframes loading {
  from {
    transform: rotate(0);
  }

  to {
    transform: rotate(1turn);
  }
}
```

Она удобна, когда нужны:

- несколько keyframes;
- повторение;
- направление `alternate`;
- автоматический запуск;
- пауза и продолжение;
- независимый от смены состояния сценарий.

Для обычного изменения между двумя состояниями transition обычно проще. Для циклического loader или сложной последовательности удобнее animation.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>transform: translate</code> лучше, чем <code>top</code>/<code>left</code> для движения?</strong></summary>

<dl>
<dd>
<h2></h2>

Изменение `top` и `left` влияет на положение позиционированной коробки и может потребовать layout и paint:

```css
.element {
  position: relative;
  left: 100px;
}
```

`transform` применяется после расчёта layout:

```css
.element {
  transform: translateX(100px);
}
```

Он визуально перемещает элемент, но не заставляет соседей пересчитывать место под новое положение.

Браузер часто может выполнить такую анимацию на стадии compositing, особенно если элемент уже находится в отдельном слое.

Поэтому для:

- выезжающей панели;
- drag preview;
- модального окна;
- tooltip;
- карточки при hover;

обычно выбирают `transform`.

При этом `transform` может создать stacking context и containing block для позиционированных потомков. Это нужно учитывать для `z-index`, `position: fixed` и всплывающих слоёв.

Результат всё равно проверяют профилированием: большой трансформируемый слой или дорогой paint внутри него может оставаться проблемой.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему не стоит писать <code>transition: all</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Запись:

```css
.element {
  transition: all 200ms ease;
}
```

разрешает переход для любого изменившегося анимируемого свойства.

Это может привести к неожиданным эффектам:

- начнёт анимироваться добавленное позже свойство;
- изменение размеров вызовет лишний layout;
- сложнее понять причину задержки;
- переключение состояния будет ощущаться медленным;
- отладка transition станет менее предсказуемой.

Лучше перечислять свойства явно:

```css
.element {
  transition:
    transform 200ms ease,
    opacity 200ms ease;
}
```

Так код документирует намерение и не начинает случайно анимировать новые свойства компонента.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>height: auto</code> обычно не анимируется плавно?</strong></summary>

<dl>
<dd>
<h2></h2>

Transition должен вычислить промежуточные значения между началом и концом.

Между двумя числовыми значениями это понятно:

```css
height: 0;
height: 200px;
```

Браузер может получить промежуточные `50px`, `100px` и `150px`.

`auto` не является конкретной длиной. Оно означает, что размер должен быть рассчитан из содержимого и layout:

```css
height: 0;
height: auto;
```

Поэтому обычная числовая интерполяция между `0` и `auto` не определяется так же, как между двумя длинами.

Распространённые варианты:

- анимировать известный `max-height`, учитывая его ограничения;
- измерить размер через JavaScript и временно установить конкретную длину;
- использовать Grid-подход с изменением размера дорожки;
- анимировать визуальное появление через `opacity` и `transform`, если изменение layout не обязательно.

Выбор зависит от того, должна ли окружающая раскладка плавно освобождать и занимать место.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает <code>animation-fill-mode</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`animation-fill-mode` определяет, какие значения из `@keyframes` применяются до начала и после завершения animation.

Основные значения:

- `none` — значения keyframes не сохраняются вне активной анимации;
- `forwards` — после завершения сохраняется подходящий последний keyframe;
- `backwards` — во время задержки применяется начальный keyframe;
- `both` — сочетает `forwards` и `backwards`.

```css
.element {
  animation: appear 300ms ease forwards;
}
```

`forwards` не переписывает исходные CSS-правила и не меняет DOM-состояние. Элемент только отображается с результатом animation effect.

Если постоянное конечное состояние имеет бизнес-смысл, надёжнее также выразить его классом или атрибутом:

```css
.element.is-visible {
  opacity: 1;
}
```

Тогда состояние не зависит только от сохранённого последнего кадра animation.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>will-change</code> нельзя ставить на всё?</strong></summary>

<dl>
<dd>
<h2></h2>

`will-change` сообщает браузеру, что определённое свойство скоро изменится:

```css
.element {
  will-change: transform;
}
```

Браузер может заранее:

- создать compositing layer;
- подготовить растеризацию;
- изменить внутреннюю стратегию рендеринга.

Эта подготовка требует ресурсов.

Если поставить:

```css
* {
  will-change: transform;
}
```

браузер может создать слишком много слоёв. Это увеличит расход памяти и стоимость их композиции.

Подсказку применяют только к конкретному элементу с измеренной проблемой.

Для кратковременного взаимодействия её можно добавить перед началом:

```js
element.style.willChange = "transform";
```

а после завершения убрать:

```js
element.style.willChange = "auto";
```

Добавление непосредственно в тот же момент, когда начинается анимация, может не дать браузеру времени на подготовку. Поэтому подсказку добавляют немного заранее, но не держат глобально без необходимости.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить производительность анимации?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала записывают проблемное взаимодействие в DevTools Performance.

Проверяют:

- имеются ли длинные задачи на main thread;
- выполняется ли layout на каждом кадре;
- какие области перерисовываются;
- есть ли пропущенные кадры;
- сколько элементов движется одновременно;
- создаётся ли слишком много слоёв;
- не блокирует ли кадры JavaScript.

Если анимация изменяет `width`, в записи часто будут повторяющиеся layout и paint.

Если изменяется `transform`, layout может отсутствовать, но это ещё не гарантирует хороший результат: большой слой может быть дорогим при paint или composite.

Полезно тестировать:

- на менее мощном устройстве;
- при большом количестве элементов;
- с реальным содержимым;
- во время scroll;
- одновременно с загрузкой и обработкой данных.

Оптимизируют подтверждённую причину, а не просто заменяют все свойства или добавляют `will-change`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как учесть режим reduced motion, то есть уменьшенного движения?</strong></summary>

<dl>
<dd>
<h2></h2>

Используют медиазапрос:

```css
@media (prefers-reduced-motion: reduce) {
  .animated {
    animation: none;
    transition-duration: 0.01ms;
  }
}
```

В первую очередь убирают или уменьшают:

- параллакс;
- большие выезды;
- вращение;
- масштабирование;
- бесконечное декоративное движение;
- автоматическую прокрутку;
- интенсивное мерцание и пульсацию.

Большое перемещение можно заменить коротким изменением opacity:

```css
@media (prefers-reduced-motion: reduce) {
  .panel {
    transform: none;
    transition-property: opacity;
  }
}
```

Нельзя скрывать важное состояние вместе с анимацией. Если animation показывает загрузку или успешное действие, должен сохраниться другой понятный визуальный сигнал.

JavaScript-анимации также должны учитывать настройку:

```js
const reducedMotion = window.matchMedia(
  "(prefers-reduced-motion: reduce)",
).matches;
```

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| UI | Подход |
| --- | --- |
| Наведение на кнопку | Transition конкретных свойств |
| Появление модального окна | `opacity` и `transform` |
| Выезжающая панель | `transform: translate(...)` |
| Мерцание skeleton-заглушки | `@keyframes`, учесть reduced motion |
| Пульсация индикатора прогресса | Animation без избыточной интенсивности |
| Перетаскивание | `transform`, а не `top`/`left` |
| Раскрытие динамического блока | Измеренный размер, Grid или другой осознанный способ |
| Подтверждённая проблема слоя | Точечный `will-change` |
| Проверка плавности | DevTools Performance |
