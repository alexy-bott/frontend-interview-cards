## Вопрос

<br>

 💬 **Как выбрать между Redux Toolkit, Zustand, Context и RTK Query?**

<h2></h2>

<br>
<dl>
<dd>

Сначала определяют:

```text
Что это за данные?

Кому они принадлежат?

Кто их использует?

Как они обновляются?

Как долго должны жить?
```

И только после этого выбирают инструмент.

Redux Toolkit, Zustand, Context и RTK Query не являются четырьмя полностью взаимозаменяемыми state managers.

Они решают задачи разных уровней:

```text
Context
→ доставляет значение
  через React-дерево

Zustand
→ управляет общим
  клиентским состоянием

Redux Toolkit
→ управляет клиентским состоянием
  через явные события и reducers

RTK Query
→ загружает и кеширует
  серверное состояние
  внутри Redux
```

В одном приложении они могут сочетаться.

---

## Сначала определить вид состояния

| Вид состояния | Примеры | Основной владелец |
| --- | --- | --- |
| Локальное UI state | Открыта ли модалка, активна ли вкладка | Компонент или ближайшее поддерево |
| Navigation state | Фильтр, страница, сортировка, выбранный раздел | URL или router |
| Form state | Значения полей, touched, validation errors | Форма или form library |
| Shared client state | Корзина до отправки, editor state, общий UI | Frontend application |
| Server state | Пользователи, заказы, товары, permissions | Backend |
| Dependency | Theme config, locale, API client, store instance | Provider или application boundary |
| Mutable resource | WebSocket, editor instance, media object | Service, ref или scoped owner |
| Persisted preference | Тема, плотность таблицы, раскладка | Client store + storage |

Главное правило:

```text
Инструмент выбирают
по природе данных,

а не по тому,
сколько компонентов
их используют.
```

---

## Минимальная достаточная область владения

State следует хранить как можно ближе к месту использования.

```text
Один компонент
→ useState

Несколько близких компонентов
→ поднять state к общему родителю

Глубокое поддерево
→ Context или scoped store

Несвязанные части приложения
→ внешний store

Данные backend
→ query cache

Состояние, отражённое в ссылке
→ URL
```

Глобальный store не является первым шагом после того, как state понадобился двум компонентам.

Сначала проверяют:

- можно ли поднять state;
- можно ли передать его props;
- должен ли он находиться в URL;
- принадлежит ли он форме;
- является ли он server state;
- действительно ли consumers удалены и независимы.

---

# Быстрая схема выбора

```text
Данные нужны одному компоненту?

→ useState или useReducer.

Данные должны восстанавливаться
из ссылки?

→ URL.

Это состояние сложной формы?

→ form library.

Нужно только передать dependency
вниз по React-дереву?

→ Context.

Нужно общее client state
с простыми прямыми actions
и выборочными подписками?

→ Zustand.

Нужны явные события,
reducers, middleware,
единый журнал и сложная
межмодульная координация?

→ Redux Toolkit.

Данные принадлежат backend,
нужны cache, invalidation
и повторная загрузка?

→ RTK Query
  в Redux-приложении.

Redux в проекте не нужен,
но нужен server cache?

→ TanStack Query
  или data API фреймворка.
```

---

# Сравнение инструментов

| Критерий | Context | Zustand | Redux Toolkit | RTK Query |
| --- | --- | --- | --- | --- |
| Основная задача | Доставка значения по дереву | Общее client state | Предсказуемое client state и процессы | Server state и cache |
| Где хранится state | Обычно в React state владельца | Во внешнем store | В Redux store | В API slice Redux store |
| Модель обновления | Определяет разработчик | Actions вызывают `set` | Actions → reducers | Query и mutation lifecycle |
| Выборочные подписки | Нет встроенного selector API | Да | Да, через React Redux | Да, через generated hooks |
| Сравнение подписки | Provider value через `Object.is` | Результат selector | Результат selector | Query result и выбранные поля |
| Middleware | Нет | Есть middleware Zustand | Есть Redux middleware | Использует собственный API middleware |
| Server cache | Нет | Нет | Сам по себе нет | Да |
| Invalidation | Нет | Нет | Нужно проектировать | Tags и cache utilities |
| DevTools | React DevTools | Redux DevTools через middleware | Redux DevTools | Redux DevTools |
| Event history | Нет | Ограниченная модель updates | Явная последовательность actions | Query и mutation actions |
| Provider | Обязателен | Необязателен для singleton | Обычно `<Provider>` | Использует Redux Provider |
| Несколько instances | Через разные Providers | Vanilla store + Context | Возможно, но обычно один store | Обычно один API slice на backend |
| Архитектурные ограничения | Почти отсутствуют | Небольшие | Явные правила Redux | Явная модель server cache |
| Типичная сложность | Низкая | Низкая или средняя | Средняя или высокая | Любая сложность server state |

# Локальный React state

Для локального значения обычно достаточно:

```ts
const [
  isOpen,
  setIsOpen,
] =
  useState(
    false,
  );
```

Подходит для:

- модалки одного экрана;
- локального dropdown;
- hover;
- временного input;
- состояния раскрытого блока;
- текущего шага локального компонента.

Преимущества:

- минимальная сложность;
- понятный владелец;
- автоматическое удаление вместе с компонентом;
- не нужно создавать общий API.

Не стоит переносить локальный boolean в глобальный store только потому, что store уже существует.

---

## Когда поднять state

Если два соседних компонента используют одно значение:

```text
Parent
├── Filter
└── List
```

можно хранить его в Parent:

```tsx
const [
  filter,
  setFilter,
] =
  useState(
    "",
  );
```

и передать props.

Это часто проще, чем:

- создавать Context;
- добавлять Zustand store;
- создавать Redux slice;
- синхронизировать несколько источников.

---

# URL state

URL подходит для состояния, которое должно:

- сохраняться после reload;
- передаваться ссылкой;
- поддерживать Back и Forward;
- участвовать в навигации;
- индексироваться или анализироваться;
- восстанавливаться при открытии страницы.

Примеры:

```text
?page=3

?sort=price

?status=active

?search=react
```

Не следует хранить один фильтр одновременно:

```text
в URL

в Redux

в local state
```

без отдельного смысла.

Правильный flow:

```text
URL search params
→ единственный source of truth

query arguments
→ вычисляются из URL
```

---

# Form state

Сложная форма имеет собственный жизненный цикл:

- values;
- touched;
- dirty;
- validation;
- submit status;
- field arrays;
- errors;
- reset;
- registration fields.

Такое состояние обычно принадлежит:

```text
форме
```

а не общему Redux или Zustand store.

Для большой формы используют специализированную библиотеку, например React Hook Form.

Глобальный store может хранить:

- ID редактируемой сущности;
- режим редактора;
- текущий шаг общего процесса;
- сохранённый draft с отдельным жизненным циклом.

Но техническое состояние каждого input обычно остаётся внутри формы.

---

# Context

Context позволяет Provider передать значение всем consumers ниже по React-дереву.

```tsx
const ThemeContext =
  createContext<
    ThemeContextValue |
    null
  >(
    null,
  );
```

```tsx
<ThemeContext
  value={
    themeValue
  }
>
  <App />
</ThemeContext>
```

Consumer:

```ts
const theme =
  useContext(
    ThemeContext,
  );
```

Context отвечает на вопрос:

```text
Как доставить значение
через React-дерево
без передачи props
на каждом уровне?
```

Он сам по себе не определяет:

- где создаётся state;
- какие actions допустимы;
- как выполняются side effects;
- как кешируются requests;
- как сравниваются отдельные поля;
- как ведётся журнал изменений.

---

## Для чего Context подходит

- theme;
- locale;
- feature configuration;
- API client;
- dependency injection;
- authentication interface;
- экземпляр внешнего store;
- scoped services;
- state небольшого поддерева;
- compound components.

Пример dependency:

```tsx
<ApiClientContext
  value={
    apiClient
  }
>
  <App />
</ApiClientContext>
```

В этом случае Context не управляет состоянием API client.

Он только передаёт его consumers.

---

## Обновление Context consumers

React сравнивает:

```text
previous value

и:

next value
```

через:

```text
Object.is
```

Если Provider получил новое значение, React обновляет компоненты, которые читают этот Context.

```tsx
const value = {
  theme,
  setTheme,
};
```

Если такой object создаётся при каждом render Provider:

```text
new object
→ новое context value
```

Consumers могут получить лишние updates.

Значение можно стабилизировать, если это действительно необходимо:

```ts
const value =
  useMemo(
    () => ({
      theme,
      setTheme,
    }),
    [
      theme,
    ],
  );
```

Но `useMemo` не добавляет Context выборочные подписки.

Consumer, которому нужен только `setTheme`, всё равно получает обновление Context при изменении `theme`, если оба значения находятся в одном Context object.

---

## Разделение Context

Вместо одного широкого значения:

```ts
{
  state,
  actions,
}
```

можно использовать два Context:

```text
ThemeStateContext

ThemeActionsContext
```

Или разделить независимые области:

```text
ThemeContext

LocaleContext

AuthContext
```

Это уменьшает область обновления и делает зависимости явнее.

Не следует дробить Context на десятки частей без наблюдаемой проблемы.

---

## Context вместе с `useReducer`

Для состояния небольшого поддерева можно сочетать:

```text
useReducer
+
Context
```

```tsx
const [
  state,
  dispatch,
] =
  useReducer(
    reducer,
    initialState,
  );
```

Context передаёт:

```text
state

dispatch
```

Это подходит, если:

- state принадлежит конкретному subtree;
- правила обновления умеренно сложные;
- не нужны middleware и общий server cache;
- количество consumers ограничено;
- не требуется отдельный внешний lifecycle.

Это не превращает Context в Redux.

По-прежнему отсутствуют встроенные:

- selectors;
- Redux middleware;
- Redux DevTools history;
- RTK Query cache;
- глобальная event model.

---

## Context вместе с внешним store

Context часто используют не для передачи всего меняющегося state, а для передачи store instance.

```text
Context
→ передаёт Zustand store

useStore(selector)
→ подписывается
  на конкретное поле
```

Это полезно для:

- scoped store;
- нескольких экземпляров виджета;
- dependency injection;
- SSR;
- store с initial props.

В такой архитектуре Context задаёт область владения, а выборочные подписки выполняет внешний store.

---

## Когда Context становится неудобен

- Provider передаёт большой часто меняющийся object;
- разным consumers нужны разные маленькие поля;
- Provider расположен очень высоко;
- нужно много update logic;
- нужны middleware;
- нужна история событий;
- нужны подписки вне React;
- нужно независимое существование state;
- Context начинает выполнять роль server cache.

В таких случаях внешний store может дать более подходящую модель.

---

# Zustand

Zustand — внешний store для клиентского состояния.

```ts
type UiStore = {
  sidebarOpen:
    boolean;

  toggleSidebar:
    () => void;
};

export const useUiStore =
  create<UiStore>()(
    (
      set,
    ) => ({
      sidebarOpen:
        false,

      toggleSidebar:
        () => {
          set(
            (
              state,
            ) => ({
              sidebarOpen:
                !state
                  .sidebarOpen,
            }),
          );
        },
    }),
  );
```

Component подписывается на выбранное значение:

```ts
const sidebarOpen =
  useUiStore(
    (
      state,
    ) =>
      state.sidebarOpen,
  );
```

Zustand сравнивает результат selector и обновляет component только при его изменении.

---

## Когда Zustand подходит

- общий UI state;
- настройки интерфейса;
- editor state;
- canvas state;
- выбранные entities;
- многошаговый client process;
- состояние независимого widget;
- несколько удалённых consumers;
- нужна подписка вне React;
- нужны несколько scoped store instances;
- хочется прямой API actions без Redux events.

Примеры:

```text
sidebarOpen

selectedNodeIds

editorMode

draftLayout

activeTool

openedPanels
```

---

## Сильные стороны Zustand

- небольшой API;
- мало boilerplate;
- actions рядом со state;
- выборочные subscriptions;
- store существует вне React;
- Provider необязателен для client singleton;
- легко создавать scoped stores;
- middleware для persist и DevTools;
- удобно внедрять initial state.

Zustand не заставляет описывать каждое изменение action object и reducer.

```ts
toggleSidebar();
```

вместо:

```ts
dispatch(
  sidebarToggled(),
);
```

Для прямого client state это может быть проще.

---

## Цена простоты Zustand

Zustand почти не навязывает:

- naming actions;
- разделение domains;
- event model;
- место side effects;
- правила сериализуемости;
- структуру middleware;
- нормализацию;
- границы persistence.

Без командных договорённостей store может превратиться в:

```text
один объект
со всеми данными приложения
```

Проблемы появляются, когда в нём смешиваются:

- UI flags;
- формы;
- server responses;
- WebSocket instance;
- auth tokens;
- большие persisted данные;
- несвязанные features.

---

## Когда Zustand начинает быть недостаточен

Это не определяется фиксированным количеством полей.

Признаки:

- много features реагируют на одно событие;
- трудно понять источник изменения;
- один action должен координировать несколько domains;
- side effects распределены по множеству actions;
- нужен единый журнал бизнес-событий;
- важны воспроизведение и аудит transitions;
- команда постоянно договаривается о разных update patterns;
- store actions начинают вручную имитировать Redux architecture.

В таком случае Redux Toolkit может дать более явную модель.

---

# Redux Toolkit

Redux Toolkit — официальный способ писать Redux logic.

Он строится вокруг:

```text
store

actions

reducers

middleware

selectors

DevTools
```

Главная особенность — состояние изменяется через явные события:

```text
произошёл action

→ reducers вычислили state

→ middleware могло
  выполнить side effect

→ subscribers получили update
```

---

## Когда Redux Toolkit подходит

- shared state используется во многих частях приложения;
- state часто изменяется;
- transitions имеют сложные правила;
- несколько features реагируют на общие события;
- нужна централизованная orchestration;
- важен журнал actions;
- нужно расследовать источник изменения;
- нужны listener middleware или custom middleware;
- над одним процессом работает большая команда;
- необходим единый архитектурный vocabulary.

Примеры:

- сложный checkout;
- редактор с undo/redo;
- workflow согласования;
- управление несколькими связанными domains;
- массовые операции;
- единый logout flow;
- сложная lifecycle авторизации;
- desktop-like application.

---

## Явные события

Redux action отвечает:

```text
Что произошло?
```

Например:

```text
userLoggedOut

orderSubmitted

documentPublished

selectionCleared
```

Один event могут независимо обработать:

- несколько reducers;
- listener middleware;
- analytics;
- persistence;
- monitoring.

Feature, которая отправила событие, не обязана знать обо всех reactions.

Это особенно полезно для межмодульных процессов.

---

## Redux Toolkit не выбирают только из-за размера

Большое количество файлов или компонентов не означает автоматическую необходимость Redux.

Небольшое приложение может иметь сложный business workflow.

Большое приложение может состоять из почти независимых страниц с server state и небольшим local state.

Важнее:

- сложность transitions;
- число владельцев;
- межмодульные reactions;
- требования к отладке;
- командная согласованность.

---

## Цена Redux Toolkit

- больше понятий;
- больше инфраструктуры;
- дополнительная косвенность;
- необходимость соблюдать immutability и сериализуемость;
- actions и reducers требуют общей модели;
- простой boolean может выглядеть избыточно.

Redux окупается, когда его ограничения решают реальные проблемы сопровождения.

```text
Предсказуемость
и наблюдаемость

в обмен на:

дополнительную структуру
```

---

# RTK Query

RTK Query входит в Redux Toolkit.

```text
Redux Toolkit
├── configureStore
├── createSlice
├── createAsyncThunk
├── listener middleware
└── RTK Query
```

Поэтому сравнение:

```text
Redux Toolkit
vs
RTK Query
```

не совсем корректно.

Правильнее:

```text
Обычный Redux slice
или
RTK Query cache
для конкретного вида данных?
```

---

## Для чего нужен RTK Query

RTK Query управляет server state:

- requests;
- query cache;
- loading и error status;
- объединение одинаковых queries;
- subscriptions;
- cache lifetime;
- invalidation;
- refetch;
- mutations;
- polling;
- optimistic updates;
- streaming updates.

Он отвечает на вопросы:

```text
Есть ли эти данные в cache?

Кто сейчас ими пользуется?

Когда запросить их повторно?

Какие queries устарели
после mutation?

Когда удалить
неиспользуемую запись?
```

Обычный Redux slice сам по себе этого не решает.

---

## Когда использовать RTK Query

- данные принадлежат backend;
- один результат используют несколько компонентов;
- нужны loading и error status;
- нужно объединение одинаковых запросов;
- требуется cache lifetime;
- mutation должна обновить связанные queries;
- нужен polling;
- требуется optimistic cache update;
- нужны generated hooks;
- приложение уже использует Redux Toolkit.

Примеры:

```text
users

orders

products

permissions

notifications from API

server search results
```

---

## RTK Query не заменяет client slices

RTK Query хранит отражение backend.

Обычный slice хранит client process.

Например:

```text
RTK Query:
products from backend

Redux slice:
selectedProductIds
checkoutStep
comparisonMode
```

Или:

```text
RTK Query:
document saved on server

Redux slice:
unsaved editor operations
active tool
selection
```

Они могут взаимодействовать, но имеют разных владельцев и lifecycle.

---

## Когда не копировать query data в slice

Плохо:

```text
RTK Query cache

→ useEffect

→ dispatch setUsers

→ usersSlice
```

Теперь существуют две версии:

```text
api cache

usersSlice
```

После:

- refetch;
- invalidation;
- mutation;
- polling;
- streaming update;

их придётся синхронизировать вручную.

Компоненты должны читать server data непосредственно из query cache.

---

## Когда отдельный client draft допустим

Иногда пользователь редактирует server entity локально.

```text
RTK Query data
→ подтверждённая версия backend

Form или editor draft
→ локальная незавершённая версия
```

Это не обязательно дублирование одного источника истины, потому что значения имеют разные смыслы.

Например:

```text
serverOrder
→ сохранённый заказ

orderDraft
→ несохранённые изменения
```

Важно явно определить:

- когда draft создаётся;
- когда сбрасывается;
- как реагирует на refetch;
- как обрабатывается конфликт версий;
- что происходит после успешной mutation.

---

## Если Redux в проекте не нужен

RTK Query требует Redux store и API middleware.

Если в приложении нет других причин использовать Redux, для server state естественнее может быть:

- TanStack Query;
- router data APIs;
- server-side data API фреймворка.

Не нужно подключать Redux Toolkit только для того, чтобы получить query cache, если другой data layer лучше вписывается в архитектуру.

С другой стороны, наличие Redux store не обязывает использовать RTK Query для каждого request.

Выбор зависит от:

- runtime;
- SSR-модели;
- существующего стека;
- требований cache;
- командного опыта.

# Можно ли сочетать Zustand и RTK Query

Да.

```text
Zustand
→ client state

RTK Query
→ server state
```

Пример:

```text
Zustand:
activePanel
selectedOrderId
tableDensity

RTK Query:
order
orderItems
permissions
```

Компонент:

```text
selectedOrderId из Zustand

→ argument RTK Query

→ order из server cache
```

Не нужно копировать полученный `order` обратно в Zustand.

Цена комбинации:

- в приложении появляются два внешних store;
- нужны две модели DevTools;
- нужно чётко определить владельцев;
- RTK Query всё равно требует Redux Provider и middleware.

Комбинация оправдана, если обязанности действительно разделены.

---

# Можно ли сочетать Context и Zustand

Да.

```text
Context
→ передаёт store instance

Zustand selector
→ подписывается на поле
```

Это стандартная модель для scoped store:

- один store на widget;
- один store на editor;
- store с initial props;
- store на request;
- dependency injection.

Context в этом случае не передаёт весь часто меняющийся state.

Он передаёт стабильную ссылку на внешний store.

---

# Можно ли сочетать Context и Redux

Да.

React Redux `<Provider>` сам использует Context для передачи Redux store по дереву.

Но компоненты не читают весь store object через обычный `useContext`.

Они используют:

```text
useSelector

useDispatch
```

React Redux управляет подписками и обновляет component только при изменении выбранного результата.

Это пример того, что:

```text
Context
→ transport store instance

External store
→ управляет subscriptions
```

Owner изменил state

→ Context consumers обновились
```

→ selectors пересчитались

```

```

## RTK Query

→ component
```

Можно увидеть:

- cache lifecycle.

# SSR и Server Components

## Context

Context может использоваться на server, если передаваемое значение доступно в соответствующей React-среде.

Client Context не должен считаться глобальным серверным хранилищем между запросами.

## Zustand

Store с request-specific данными создают отдельно для каждого server request или subtree.

Module-level mutable singleton на server может передать состояние между пользователями.

Первое server и client состояния должны совпадать для корректной hydration.

React Server Components не читают mutable client Zustand store через hooks.

## Redux Toolkit и RTK Query

Redux store с request-specific состоянием также создают per request.

В Next.js App Router React Server Components обычно получают данные server-oriented средствами, а Redux и RTK Query используют в Client Components.

Не следует считать global Redux store безопасным server singleton.

---

# Persistence

Persistence является отдельным требованием, а не основанием выбирать глобальный store.

Можно сохранять:

- theme;
- table density;
- layout;
- небольшие пользовательские preferences;
- незавершённый draft, если это бизнес-требование.

Не следует бездумно сохранять:

- query cache;
- loading и error flags;
- DOM nodes;
- sockets;
- functions;
- большие server responses;
- access и refresh tokens;
- чувствительные данные.

## Zustand

Использует middleware:

```text
persist
```

с `partialize`, `version`, `migrate` и hydration lifecycle.

## Redux Toolkit

Persistence подключается отдельным решением или собственной логикой.

Redux Toolkit сам по себе не сохраняет store между reload.

## RTK Query

Cache обычно восстанавливают через network и refetch rules.

Долговременное browser persistence требует отдельной стратегии актуальности и очистки пользовательских данных.

## Context

Context ничего не сохраняет самостоятельно.

# Тестируемость

## Context

Удобно подменять dependency через Provider:

```tsx
<ApiContext
  value={
    fakeApi
  }
>
  <Component />
</ApiContext>
```

## Zustand

Для тестовой изоляции полезен store factory:

```text
createStore()
→ новый instance для каждого теста
```

## Redux Toolkit

Reducer тестируется как чистая функция.

Store можно создать с test reducers, middleware и `preloadedState`.

Actions дают наблюдаемые события для integration tests.

## RTK Query

Можно тестировать:

- endpoint contract;
- generated hooks;
- invalidation;
- optimistic update;
- cache lifecycle;
- интеграцию с mock server.

Выбор инструмента не должен основываться только на утверждении, что один из них «легче тестируется».

Важнее:

- чистые границы;
- dependency injection;
- отсутствие global state между тестами;
- тестирование observable behavior.

# Командная работа

## Zustand удобен, когда

- команда согласна с простым action API;
- domains хорошо изолированы;
- нет сложной общей event model;
- правила stores документированы;
- разработчики не складывают всё в один store.

## Redux Toolkit удобен, когда

- нужен единый vocabulary events;
- features должны реагировать независимо;
- изменения расследуются через action history;
- много разработчиков меняют связанные процессы;
- нужна единая middleware architecture.

## Context удобен, когда

- dependency принадлежит одному subtree;
- update model проста;
- Context не превращён в универсальный global state.

## RTK Query удобен, когда

- команда хочет единый способ описания API;
- server state не копируется в обычные slices;
- tags и cache keys проектируются согласованно;
- query lifecycle должен быть стандартизирован.

---

# Один источник истины

Для каждого факта должен быть один основной владелец.

Плохо:

```text
filter:
local state
+
URL
+
Redux

user:
RTK Query
+
Zustand
+
Context

form:
React Hook Form
+
Redux slice
```

Проблемы:

- непонятно, какое значение актуально;
- появляются эффекты синхронизации;
- возможны циклические updates;
- reset становится сложным;
- данные расходятся после async operation.

Правильно:

```text
URL
→ владеет filter

RTK Query
→ владеет server user

Form library
→ владеет field values

Zustand или Redux
→ владеет client process
```

Остальные слои получают или вычисляют значения из владельца.

---

# Допустимое дублирование

Два похожих значения допустимы, если они имеют разный смысл.

```text
serverUser
→ подтверждённая версия backend

userDraft
→ локальные несохранённые изменения
```

```text
query.isFetching
→ network request выполняется

isSubmittingWizard
→ выполняется общий client workflow
```

```text
URL filter
→ публичное состояние навигации

temporaryInput
→ ещё не применённый текст формы
```

Нужно не запрещать любые копии, а явно описывать:

- различие смыслов;
- владельца каждого значения;
- момент синхронизации;
- reset;
- conflict policy.

# Как выбрать между Zustand и Redux Toolkit

Задать вопросы:

```text
Нужны ли явные domain events?

Несколько features должны
реагировать на одно событие?

Нужен ли общий middleware pipeline?

Нужно ли расследовать
последовательность transitions?

Есть ли сложные workflows?

Нужны ли строгие
командные ограничения?
```

Если большинство ответов:

```text
нет
```

и update logic остаётся прямой:

```text
Zustand может быть проще.
```

Если большинство ответов:

```text
да
```

то:

```text
Redux Toolkit
может лучше масштабировать
архитектуру и отладку.
```

Не следует оценивать выбор только по:

- размеру bundle;
- числу строк;
- количеству компонентов;
- популярности;
- привычке одного разработчика.

# Как выбрать между Context и Zustand

Context подходит, если:

- значение принадлежит subtree;
- consumers читают его почти целиком;
- оно редко изменяется;
- это dependency;
- не нужны subscriptions вне React;
- update model проста.

Zustand подходит, если:

- state меняется часто;
- consumers выбирают разные поля;
- нужен store вне React;
- нужны scoped store instances;
- нужен `persist`;
- нужны external subscriptions;
- Context value пришлось бы постоянно дробить.

---

# Как выбрать между RTK Query и обычным Redux slice

RTK Query:

```text
backend является
источником истины
```

Обычный slice:

```text
frontend является
источником client process
```

Пример:

```text
orders from API
→ RTK Query

selectedOrderIds
→ Redux slice

orderCreationWizard
→ Redux slice

saved order after submit
→ RTK Query cache
```

Ручной slice для server data оправдан, если:

- данные не укладываются в query cache;
- process не является обычной загрузкой ресурса;
- требуется особая event-sourced model;
- результат имеет самостоятельный client lifecycle;
- RTK Query объективно не покрывает контракт.

Это должно быть осознанным исключением.

# Алгоритм выбора

```text
1. Значение полностью локально?

Да
→ useState или useReducer.

2. Оно должно быть частью ссылки
   и навигационной истории?

Да
→ URL.

3. Это техническое state формы?

Да
→ form library.

4. Это dependency,
   которую нужно передать
   через subtree?

Да
→ Context.

5. Авторитетная версия
   находится на backend?

Да
→ query cache.

6. В проекте уже есть Redux
   и server state нужен
   в client components?

Да
→ RTK Query.

7. Нужен общий client state
   с прямыми actions
   и selectors?

Да
→ Zustand.

8. Нужны явные events,
   reducers, middleware
   и общая orchestration?

Да
→ Redux Toolkit.

9. State должно иметь
   несколько изолированных instances?

Да
→ scoped Context,
  vanilla Zustand store
  или отдельный store factory.

10. Нужна persistence?

→ Добавить её к уже
  выбранному владельцу,
  а не менять всю архитектуру.
```

# Частые ошибки

## Выбрать Redux только против prop drilling

Если state принадлежит ближайшему общему родителю, props могут быть самым прозрачным решением.

## Выбрать Context для большого изменяемого store

Все consumers Context получают новое Provider value без встроенных field selectors.

## Поместить server state в Zustand

Придётся самостоятельно реализовать cache, deduplication, freshness, invalidation и retries.

## Копировать RTK Query data в Redux slice

Создаётся второй source of truth внутри одного Redux store.

## Копировать query data в Zustand

Появляются две независимые store-системы с одним фактом.

## Поместить каждую модалку в global store

State теряет локального владельца и продолжает жить дольше нужного UI.

## Использовать один огромный Zustand store

Несвязанные domains получают общий lifecycle, persistence и reset.

## Создавать Redux slice на каждое поле

Redux используется как более многословный `useState`, а преимущества event model не задействуются.

## Сохранять всё через `persist`

В storage оказываются устаревшие server data, ошибки, loading flags и чувствительная информация.

## Выбирать инструмент только по размеру проекта

Реальная сложность определяется ownership, transitions и взаимодействием процессов.

## Дополнительные вопросы

<details>
<summary><strong>Нужно ли выбрать один state manager на весь проект?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Разные виды состояния требуют разных владельцев:

```text
модалка
→ useState

filter
→ URL

form values
→ form library

client workflow
→ Zustand или Redux Toolkit

server entities
→ query cache
```

Важно не количество инструментов само по себе, а чёткие границы и отсутствие нескольких источников истины для одного факта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Является ли RTK Query альтернативой Redux Toolkit?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

RTK Query является частью Redux Toolkit и использует Redux store и middleware.

```text
Redux Toolkit
→ общая Redux-инфраструктура

RTK Query
→ специализированный
  server-state слой
```

В одном Redux-приложении обычно используют:

```text
createSlice
→ client state

createApi
→ server state
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему Context не всегда считают полноценным state manager?</strong></summary>

<dl>
<dd>
<h2></h2>

Context доставляет значение, но не определяет модель обновления.

В нём нет встроенных:

- actions;
- reducers;
- selectors;
- middleware;
- cache;
- event history;
- persistence.

State обычно находится в `useState`, `useReducer` или внешнем store, а Context передаёт его consumers.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда Context вместе с <code>useReducer</code> достаточен?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда:

- state принадлежит одному subtree;
- transitions умеренно сложные;
- consumers не слишком многочисленны;
- не нужны middleware;
- не нужен server cache;
- не требуется общий журнал всего приложения.

Это хороший промежуточный вариант между локальным state и внешним store.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли часто меняющийся Context обновляет всё приложение?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Обновляются consumers конкретного Context, а не автоматически все компоненты приложения.

Но каждый consumer получает новое значение Context целиком.

Если Provider передаёт большой object и меняется одно его поле, все consumers этого Context могут обновиться независимо от того, какое поле они читают.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Поможет ли <code>React.memo</code> остановить update из Context?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет, если компонент сам читает изменившийся Context.

`memo` может пропустить render из-за прежних props, но consumer всё равно должен получить новое context value.

Для уменьшения области обновления:

- разделяют Context;
- стабилизируют value;
- сужают Provider;
- передают внешний store с selectors.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда выбрать Zustand вместо Redux Toolkit?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда client state обновляется прямыми понятными actions:

```text
toggleSidebar

selectNode

setTool

resetEditor
```

и не нужны:

- единая event model;
- reactions многих domains;
- общий middleware pipeline;
- детальный журнал transitions;
- строгие архитектурные ограничения.

Zustand требует меньше инфраструктуры, но команда сама отвечает за дисциплину stores.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда Redux Toolkit лучше Zustand?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда:

- один event обрабатывают несколько features;
- важна последовательность domain events;
- нужны listener middleware;
- transitions имеют сложные правила;
- нужно расследовать источник изменения;
- требуется единый подход большой команды;
- action history является частью отладки.

Redux Toolkit добавляет структуру в обмен на предсказуемость и наблюдаемость.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Означает ли большой проект, что обязательно нужен Redux?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Большой проект может состоять из независимых экранов с query cache и локальным UI state.

Небольшой проект может содержать сложный editor или workflow, для которого Redux полезен.

Решение зависит от:

- сложности transitions;
- shared ownership;
- межмодульных reactions;
- требований к отладке;
- командной модели.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Если в проекте есть Redux Toolkit, нужно ли хранить API-данные в slices?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычно нет.

Для server state официальный основной вариант — RTK Query.

Обычный slice оставляют для:

- client process;
- UI state;
- selection;
- unsaved draft;
- orchestration;
- данных, которые не являются query cache.

Ручной slice для API-данных должен решать особую задачу, которую RTK Query действительно не покрывает.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли использовать Zustand вместе с RTK Query?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

```text
Zustand
→ client state

RTK Query
→ server state
```

Например, Zustand хранит `selectedOrderId`, а RTK Query получает заказ по этому ID.

Копировать полученный заказ в Zustand не нужно.

Нужно учитывать, что RTK Query всё равно добавляет Redux store и middleware.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли использовать Context вместе с Zustand?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

Context передаёт vanilla store instance, а `useStore` подписывает component на выбранную часть.

Это полезно для:

- scoped store;
- нескольких widgets;
- store с initial props;
- dependency injection;
- SSR;
- изолированного editor.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли использовать Context вместе с Redux?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

React Redux Provider использует Context для передачи Redux store.

Компоненты читают данные через `useSelector`, поэтому подписываются на выбранные значения, а не на весь store object через обычный `useContext`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как отличить серверное состояние от клиентского?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно найти авторитетную версию.

Если данные:

- принадлежат backend;
- могут измениться другим пользователем;
- требуют загрузки и повторной синхронизации;
- имеют server ID и version;

это server state.

Если значение описывает:

- UI;
- selection;
- незавершённый локальный процесс;
- режим редактора;
- локальный draft;

это client state.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Является ли authentication client или server state?</strong></summary>

<dl>
<dd>
<h2></h2>

Authentication обычно состоит из нескольких частей:

```text
session на server
→ server state

текущий user profile
→ query data

локальный статус login process
→ client state

открыта ли login modal
→ UI state
```

Не нужно помещать весь auth flow в одно значение.

Server всегда повторно проверяет авторизацию независимо от client store.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда допустимо копировать server entity в локальный state?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда создаётся значение с отдельным смыслом:

```text
server entity
→ сохранённая версия

local draft
→ несохранённая версия
```

Например, форма редактирования может инициализироваться из query data и затем самостоятельно владеть полями.

Нужно определить reset, submit и conflict behavior.

Просто копировать query data в другой store для чтения нельзя.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда выбрать TanStack Query вместо RTK Query?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда приложению нужен client query cache, но нет других причин вводить Redux store.

RTK Query естественнее в Redux-приложении и интегрируется с Redux DevTools, actions и middleware.

TanStack Query является отдельным server-state решением и не требует Redux infrastructure.

Выбор также зависит от SSR-модели и существующих правил проекта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где хранить фильтр списка?</strong></summary>

<dl>
<dd>
<h2></h2>

Если фильтр должен:

- передаваться ссылкой;
- переживать reload;
- поддерживать Back и Forward;

его хранят в URL.

Если он временный и принадлежит одному widget, достаточно local state.

В Redux или Zustand фильтр помещают, если он является частью общего client process и URL не является его владельцем.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда состояние преждевременно сделали глобальным?</strong></summary>

<dl>
<dd>
<h2></h2>

Признаки:

- значение использует только один экран;
- после ухода со страницы state нужно сразу сбрасывать;
- consumers находятся рядом;
- появились actions только для локальной модалки;
- store содержит hover и временные inputs;
- требуется много reset logic;
- state живёт дольше своего UI.

Такое значение стоит вернуть локальному владельцу или scoped store.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какая ошибка выбора встречается чаще всего?</strong></summary>

<dl>
<dd>
<h2></h2>

Поместить в один глобальный store:

- server cache;
- form values;
- URL-фильтры;
- UI-флаги;
- mutable resources;
- persisted secrets.

После этого непонятны:

- владелец;
- lifecycle;
- freshness;
- reset;
- persistence;
- SSR behavior.

Классификация состояния должна происходить до выбора библиотеки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выбирать state manager для микрофронтендов?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала определяют границу владения.

Независимый микрофронтенд может иметь собственный scoped store.

Общие данные между микрофронтендами лучше передавать через стабильный контракт:

- props;
- URL;
- events;
- shared service;
- backend;
- явно общий store.

Не следует случайно связывать все модули одним mutable singleton только ради удобного импорта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли учитывать SSR при выборе инструмента?</strong></summary>

<dl>
<dd>
<h2></h2>

Да, особенно для внешних stores и persistence.

Нужно определить:

- создаётся ли store per request;
- совпадает ли первый server/client state;
- используются ли browser-only API;
- кто получает данные в Server Components;
- как очищаются пользовательские данные;
- нужна ли client hydration.

Но SSR не определяет инструмент самостоятельно — он добавляет требования к его lifecycle.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Задача | Подходящий инструмент |
| --- | --- |
| Открыта ли локальная модалка | `useState` |
| Связать состояние соседних компонентов | Поднять state к общему родителю |
| Сложный локальный transition | `useReducer` |
| Тема или locale | Context |
| Передать API client | Context |
| Scoped store виджета | Context + vanilla Zustand store |
| Общий UI и настройки | Zustand |
| Editor client state | Zustand или Redux Toolkit |
| Сложный клиентский процесс | Redux Toolkit |
| Общие domain events | Redux Toolkit |
| Реакции нескольких features | Redux actions + listener middleware |
| Кэш данных API в Redux-проекте | RTK Query |
| Кэш данных API без Redux | TanStack Query или framework data API |
| Фильтры, которыми делятся по ссылке | URL |
| Большая форма | React Hook Form |
| Локальный draft server entity | Form state или editor state |
| Server entity | Query cache |
| Выбранный ID server entity | Client state или URL |
| Несколько экземпляров widget | Scoped Zustand stores |
| Persistence пользовательских настроек | Zustand `persist` или отдельный persistence layer |
| SSR с request-specific store | Store factory на request |
| React Server Component | Server-oriented data fetching |
| Client refetch и invalidation | RTK Query или TanStack Query |
| WebSocket server cache | Query cache streaming update |
| Undo/redo сложного редактора | Redux Toolkit или специализированная модель |
| Dependency injection в тестах | Context или store factory |
| Небольшое приложение без shared process | Local state + Context + query library |
