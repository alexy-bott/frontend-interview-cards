#### Вопрос

В чём идея Flux и Redux? Зачем нужны store, actions и reducers?

#### Ответ

Flux описывает однонаправленный поток данных: интерфейс создаёт событие, событие проходит через слой управления состоянием, состояние обновляется, после чего интерфейс получает новое значение. Такой поток упрощает поиск причины изменения: данные не меняются произвольно из разных мест.

Redux реализует похожую идею через несколько чётких сущностей:

- **Store** хранит дерево состояния и предоставляет `getState`, `dispatch` и `subscribe`.
- **Action** является обычным объектом с обязательным полем `type`. Он описывает произошедшее событие и может переносить данные в `payload`.
- **Reducer** получает предыдущее состояние и action, затем возвращает следующее состояние.
- **Dispatch** отправляет action в Redux.
- **Subscriber** подписывается на изменения store. В React эту работу выполняет React Redux через `useSelector` и другие API.

Когда вызывается `dispatch(action)`, action сначала проходит через цепочку middleware. Middleware может выполнить побочный эффект, создать другие actions или передать исходный action дальше. Затем корневой reducer вызывает reducers соответствующих slices, Redux сохраняет новое дерево состояния и уведомляет подписчиков. React Redux повторно запускает selectors и обновляет только компоненты, у которых изменился выбранный результат.

Reducer должен быть чистой функцией. Он не отправляет HTTP-запросы, не пишет в `localStorage`, не использует случайные значения и не меняет исходное состояние. Одинаковые state и action должны давать одинаковый результат. Побочные эффекты размещают в thunk, listener middleware, RTK Query или другом middleware.

Неизменяемость состояния, или immutability, означает, что reducer не меняет прежний объект, а создаёт новое состояние с новыми ссылками только для изменённых частей. Это позволяет сравнивать значения по ссылке, воспроизводить последовательность actions и корректно работать DevTools. Redux Toolkit использует Immer, чтобы такие обновления можно было записывать короче.

Обычно приложение использует один Redux store, а состояние делит на части, или slices, по предметным областям. Это даёт единую последовательность событий и одну точку подключения DevTools. Несколько store технически возможны, но нужны редко, например для полностью изолированных виджетов.

Redux оправдан, когда состояние разделяют многие части приложения, обновления образуют сложные процессы, а предсказуемые события и централизованная отладка важнее минимального количества кода. Для локального состояния одного компонента Redux обычно избыточен. Современный Redux пишут через Redux Toolkit.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Чем однонаправленный поток данных полезен на практике?
>
> **Ответ:** У изменения есть наблюдаемый путь: UI или другой источник вызывает `dispatch`, action проходит middleware и reducers, затем подписчики получают новое состояние. При ошибке можно найти action в Redux DevTools, увидеть данные до и после него и определить reducer или middleware, участвовавший в обновлении.

> [!followup]
> **Вопрос:** Почему actions часто называют как произошедшие события?
>
> **Ответ:** Имена `cartItemAdded` или `userLoggedOut` описывают факт, на который могут независимо реагировать разные reducers и middleware. Это уменьшает связанность с конкретным исполнителем. Командные имена тоже допустимы, если action действительно выражает намерение, но название должно однозначно передавать смысл события для всей системы.

> [!followup]
> **Вопрос:** Почему reducer должен быть чистым?
>
> **Ответ:** Чистый reducer легко проверить обычным вызовом функции и можно безопасно запускать повторно. Если внутри есть запрос, таймер или запись во внешнее хранилище, результат начинает зависеть от окружения, а повторное воспроизведение actions перестаёт быть надёжным. Reducer должен только вычислять следующее состояние.

> [!followup]
> **Вопрос:** Где в Redux выполняются побочные эффекты?
>
> **Ответ:** Побочный эффект меняет что-то за пределами расчёта состояния: вызывает API, пишет в хранилище, запускает таймер или отправляет аналитику. Такие действия выполняют thunk, listener middleware, RTK Query или специализированный middleware. Результат эффекта при необходимости возвращается в store новым action.

> [!followup]
> **Вопрос:** Что происходит после `dispatch(action)`?
>
> **Ответ:** Action проходит middleware в порядке подключения. Если цепочка вызывает `next(action)`, action доходит до reducer. Redux вычисляет новое состояние, сохраняет его и уведомляет подписчиков. React Redux затем выполняет selectors подписанных компонентов и запускает повторную отрисовку только там, где выбранное значение изменилось.

> [!followup]
> **Вопрос:** Зачем Redux требует неизменяемость состояния?
>
> **Ответ:** Redux и React Redux определяют изменения главным образом по ссылкам. Если изменить старый объект на месте, ссылка останется прежней и подписчик может не заметить обновление. Создание новых ссылок для изменённых частей также позволяет хранить историю состояний, отменять и повторять изменения (undo/redo) и воспроизводить actions в DevTools.

> [!followup]
> **Вопрос:** Почему обычно используют один store?
>
> **Ответ:** Один store даёт единое дерево состояния, одну последовательность actions и одну точку подключения middleware и DevTools. Логическое разделение выполняют slices и reducers. Несколько store усложняют обмен данными и общую отладку, поэтому их оставляют для действительно независимых частей приложения.

> [!followup]
> **Вопрос:** Когда Redux не нужен?
>
> **Ответ:** Если состояние локально, обновляется простыми действиями и не требует общей событийной модели, `useState`, `useReducer` или небольшой Context будут понятнее. Redux выбирают по сложности взаимодействий и требованиям к сопровождению, а не по размеру или важности отдельного значения.

#### Где это встречается во frontend

| Сценарий | Польза Redux |
| --- | --- |
| Корзина и оформление заказа | Согласованные изменения нескольких slices |
| Сложный редактор | История событий, отмена и повтор изменений, DevTools |
| Выход пользователя | Один action очищает связанные части состояния |
| Большая команда | Единый способ описывать изменения |
