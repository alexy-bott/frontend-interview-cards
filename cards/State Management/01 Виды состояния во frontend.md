#### Вопрос

Какие виды состояния бывают во frontend и где их лучше хранить?

#### Ответ

Состояние во frontend нужно разделять по владельцу данных, источнику истины и сроку жизни. От этого зависит место хранения. Не все данные приложения должны попадать в один глобальный store.

**Локальное состояние интерфейса** принадлежит конкретному компоненту или небольшой части дерева: открыта ли модалка, какой пункт выбран, раскрыт ли выпадающий список. Обычно достаточно `useState` или `useReducer`. Если значение требуется нескольким соседним компонентам, его поднимают до ближайшего общего родителя.

**Клиентское состояние (client state)** создаёт и контролирует само приложение: выбранная тема, состояние многошагового сценария, черновик до отправки, глобальные настройки интерфейса. Если оно используется в несвязанных частях дерева или должно переживать смену экрана, подходят Context, Redux Toolkit или Zustand. Инструмент выбирают по сложности обновлений и требованиям к отладке.

**Серверное состояние (server state)** приходит с backend и остаётся его собственностью: пользователь, заказы, права доступа, товары. Эти данные могут устаревать, поэтому кроме значения нужны кэширование, повторная загрузка, устранение одинаковых запросов, обработка ошибок и синхронизация после изменений. Для этого используют RTK Query, TanStack Query или механизм загрузки данных выбранного фреймворка, а не вручную собранный slice.

**Состояние URL** хранит то, что должно восстанавливаться по ссылке: поисковый запрос, фильтры, сортировку, страницу пагинации, иногда активную вкладку. URL становится источником истины, поэтому копировать то же значение в store без необходимости не следует.

**Состояние формы (form state)** включает значения полей, ошибки, признаки `dirty` и `touched`, отправку и сброс. `dirty` показывает, что значение изменили, а `touched` означает, что пользователь уже взаимодействовал с полем. Простую форму можно держать локально. Для большой динамической формы обычно используют специализированный инструмент, например React Hook Form, потому что у формы свой жизненный цикл и правила валидации.

Производные данные не являются отдельным источником истины. Если отфильтрованный список можно получить из исходного массива и фильтра, хранить третью копию в state не нужно. Значение вычисляют во время отрисовки или через selector. Это устраняет рассинхронизацию.

Практическое правило: хранить состояние как можно ближе к месту использования, но на уровне, доступном всем его потребителям. Глобальный store нужен не потому, что данные важные, а потому, что ими совместно владеют удалённые части приложения или над ними выполняются сложные согласованные обновления.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Что такое источник истины?
>
> **Ответ:** Это место, значение из которого считается актуальным. Например, если фильтры должны восстанавливаться по ссылке, источником истины является URL. Компоненты читают фильтры из URL и изменяют его, а не поддерживают независимые копии в URL и Redux. Один источник истины уменьшает риск, что разные части интерфейса покажут разные значения.

> [!followup]
> **Вопрос:** Чем клиентское состояние отличается от серверного?
>
> **Ответ:** Клиентским состоянием владеет frontend и сам определяет правила его изменения. Серверным состоянием владеет backend, а frontend хранит только локальную копию, которая может устареть. Поэтому для серверных данных нужны правила свежести, кэш, повторные запросы и синхронизация после mutation, то есть операции изменения данных на сервере.

> [!followup]
> **Вопрос:** Когда состояние нужно хранить в URL?
>
> **Ответ:** Когда пользователь должен получить тот же экран после обновления страницы, перехода назад или открытия отправленной ссылки. Типичные примеры: строка поиска, фильтры каталога, сортировка и пагинация. Кратковременное состояние вроде открытой всплывающей подсказки (tooltip) обычно не несёт смысла в URL.

> [!followup]
> **Вопрос:** Что такое совместное размещение состояния (state colocation) и поднятие состояния (lifting state up)?
>
> **Ответ:** Совместное размещение означает хранение состояния рядом с компонентами, которые его используют. Поднятие состояния означает перенос значения к ближайшему общему родителю, если оно понадобилось нескольким дочерним компонентам. Сначала состояние размещают локально, а поднимают только при появлении общего владельца.

> [!followup]
> **Вопрос:** Почему производные данные обычно не хранят в state?
>
> **Ответ:** Две независимые копии одной информации приходится синхронизировать. Если хранить исходный список, фильтр и отдельно отфильтрованный список, изменение одного значения может не обновить другое. Надёжнее хранить исходные данные и фильтр, а результат вычислять из них. Мемоизация нужна только тогда, когда вычисление действительно дорогое или стабильная ссылка влияет на повторную отрисовку.

> [!followup]
> **Вопрос:** Когда нужен глобальный store?
>
> **Ответ:** Когда одно состояние используют удалённые части приложения, обновления образуют общий бизнес-процесс или важны централизованные события, middleware и Redux DevTools. Сам факт передачи props через два или три уровня ещё не означает, что нужен глобальный store: иногда композиция компонентов или Context решают задачу проще.

#### Где это встречается во frontend

| Данные | Подходящее место |
| --- | --- |
| Открыта ли локальная модалка | `useState` |
| Выбранные элементы сложного редактора | Redux Toolkit или Zustand |
| Список заказов из API | RTK Query или TanStack Query |
| Фильтры каталога с общей ссылкой | URL |
| Значения и ошибки большой формы | React Hook Form |
| Отфильтрованный список | Вычисление или selector |
