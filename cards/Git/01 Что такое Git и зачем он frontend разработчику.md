## Вопрос

<br>

 💬 **Что такое Git, как он хранит историю проекта и зачем нужен frontend-разработчику?**

<h2></h2>

<br>
<dl>
<dd>

Git — распределённая система контроля версий. Она сохраняет версии проекта, позволяет нескольким разработчикам независимо вести работу и затем объединять изменения.

После обычного `git clone` репозиторий с историей находится локально у разработчика, поэтому смотреть историю, создавать ветки и commits можно без подключения к GitLab или другому серверу.

Git хранит историю как граф связанных commits.

При создании commit Git сохраняет снимок данных, подготовленных в index через `git add`, а не автоматически все изменения working directory.

Основные объекты Git:

- `blob` хранит содержимое файла;
- `tree` описывает структуру каталогов и ссылки на файлы;
- `commit` ссылается на корневой tree, одного или нескольких родителей и содержит метаданные.

Commit содержит автора, создателя commit (`committer`), время, сообщение и ссылки на родительские commits.

Поэтому история имеет форму графа:

- обычный commit обычно ссылается на одного родителя;
- первый commit не имеет родителя;
- merge commit обычно ссылается на двух родителей.

Объекты Git неизменяемы. Если изменить снимок, сообщение или родителя, будет создан другой commit с другим идентификатором.

Ветка — это перемещаемая ссылка на commit. Когда разработчик создаёт новый commit в текущей ветке, ссылка ветки обычно передвигается на него.

Git не следует путать с GitHub или GitLab.

Git управляет локальным репозиторием, историей и обменом данными с удалёнными репозиториями.

GitLab и GitHub добавляют серверное хранение, управление доступом, merge requests или pull requests, code review, задачи и CI/CD.

Во frontend Git хранит не только исходный код. Через него команда согласованно изменяет:

- компоненты;
- стили;
- тесты;
- конфигурацию сборки;
- схемы API;
- `package.json`;
- lock-файл зависимостей.

История помогает понять причину изменения, проверить diff, найти регрессию, отменить ошибочное изменение и безопасно вести несколько параллельных задач.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему Git называют распределённой системой?</strong></summary>

<dl>
<dd>
<h2></h2>

После обычного `git clone` разработчик получает не только текущие файлы, но и локальную копию доступной истории и ссылок репозитория.

Большинство операций выполняется локально:

- просмотр истории;
- создание commits;
- создание и переключение веток;
- сравнение версий;
- объединение изменений.

Центральный сервер обычно используется командой как общая точка обмена и источник правил, но технически Git не требует единственного центрального репозитория.

Исключением может быть shallow clone, созданный, например, через `--depth`: он содержит только ограниченную часть истории.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что именно хранит commit?</strong></summary>

<dl>
<dd>
<h2></h2>

Commit не содержит файлы непосредственно. Он ссылается на корневой объект `tree`, который описывает снимок структуры отслеживаемых файлов.

Также commit содержит:

- ссылку на одного или нескольких родителей;
- автора изменения;
- создателя commit (`committer`);
- временные метки;
- сообщение.

Его идентификатор вычисляется из содержимого объекта. Если изменить снимок, сообщение, автора или родителя, получится другой commit с другим идентификатором.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Git хранит каждый файл целиком или только diff?</strong></summary>

<dl>
<dd>
<h2></h2>

Логическая модель Git основана на снимках состояния файлов, а не на последовательности патчей.

Если файл не изменился, новый снимок может ссылаться на уже существующий `blob`, поэтому одинаковое содержимое не нужно сохранять повторно.

При внутреннем хранении и передаче Git объединяет объекты в pack-файлы и может использовать delta compression, то есть хранить различия между похожими объектами.

Но при рассуждении о commits правильнее представлять именно связанные снимки проекта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем repository отличается от working directory?</strong></summary>

<dl>
<dd>
<h2></h2>

Working directory, или рабочая директория, содержит файлы, которые разработчик сейчас видит и редактирует.

Репозиторий содержит служебные данные Git:

- commits;
- объекты файлов и деревьев;
- ветки;
- теги;
- настройки;
- другую историю.

В обычном локальном проекте эти данные находятся в каталоге `.git` внутри working directory.

Изменение файла в рабочей директории ещё не означает, что оно сохранено в истории. Сначала нужную версию добавляют в index, а затем создают commit.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие файлы Git начинает отслеживать?</strong></summary>

<dl>
<dd>
<h2></h2>

Новый файл сначала считается untracked.

После `git add` его текущее содержимое попадает в index, и файл становится tracked и staged для следующего commit.

Если после `git add` снова изменить файл, новая версия останется в working directory и не попадёт в commit, пока её тоже не добавить в index.

`.gitignore` помогает не предлагать к добавлению подходящие неотслеживаемые файлы, но не прекращает отслеживание файла, который уже попал в index или историю.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем Git отличается от GitLab?</strong></summary>

<dl>
<dd>
<h2></h2>

Git — инструмент и модель хранения истории.

GitLab — платформа вокруг Git-репозиториев. Она:

- хранит репозитории на сервере;
- управляет пользователями и правами;
- предоставляет merge requests;
- поддерживает code review;
- настраивает protected branches;
- запускает CI/CD pipelines.

Локальные commits и ветки можно создавать без GitLab. GitLab нужен команде для обмена изменениями и организации общего процесса разработки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему commit должен быть небольшим и логически цельным?</strong></summary>

<dl>
<dd>
<h2></h2>

Такой commit проще:

- проверить;
- понять по diff;
- перенести через `cherry-pick`;
- отменить через `revert`;
- связать с причиной изменения;
- использовать при поиске регрессии.

Если в одном commit смешаны рефакторинг, новая функция и исправление бага, diff сложнее читать, а точечный `revert` может отменить лишние изменения.

Небольшой commit означает одну логическую задачу, а не обязательно минимальное количество строк.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Является ли Git резервной копией проекта?</strong></summary>

<dl>
<dd>
<h2></h2>

Локальная история защищает от части ошибок, но сама по себе не является полноценной резервной копией.

Потеря диска может уничтожить и рабочие файлы, и локальный каталог `.git`.

Для устойчивости нужен удалённый репозиторий, а для критичных проектов — отдельная политика резервного копирования серверного хранилища.

Неотслеживаемые и не добавленные в commit файлы также не защищены отправкой Git-репозитория на сервер.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Как помогает Git |
|---|---|
| Параллельная разработка | Компоненты, стили и API-интеграции меняются в отдельных ветках и объединяются через review. |
| Ошибка после релиза | По истории и diff можно найти изменение, которое вызвало регрессию, а затем исправить или отменить его. |
| Обновление зависимостей | Изменения `package.json` и lock-файла проходят через общий commit и pipeline. |
| Разбор решения | Commit и merge request сохраняют код, контекст задачи и обсуждения. |
