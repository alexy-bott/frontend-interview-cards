## Вопрос

<br>

 💬 **Что такое Git, как он хранит историю проекта и зачем нужен frontend-разработчику?**

<h2></h2>

<br>
<dl>
<dd>

Git - распределённая система контроля версий. Она сохраняет версии проекта, позволяет нескольким разработчикам независимо вести работу и затем объединять изменения. Репозиторий с историей находится локально у каждого разработчика, поэтому смотреть историю, создавать ветки и commits можно без подключения к GitLab или другому серверу.

Git хранит состояние проекта как последовательность связанных commits. Commit содержит снимок отслеживаемых файлов, автора, время, сообщение и ссылку на родительский commit. Поэтому история имеет форму графа: обычный commit ссылается на одного родителя, а merge commit обычно на двух. Ветка - это перемещаемая ссылка на последний commit некоторой линии разработки.

Git не следует путать с GitHub или GitLab. Git управляет локальным репозиторием и обменом данными с удалёнными репозиториями. GitLab и GitHub добавляют серверное хранение, управление доступом, merge requests, code review, задачи и CI/CD.

Во frontend Git хранит не только исходный код. Через него команда согласованно изменяет компоненты, стили, тесты, конфигурацию сборки, схемы API и lock-файл зависимостей. История помогает понять причину изменения, найти регрессию, проверить diff и безопасно доставить несколько параллельных задач.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему Git называют распределённой системой?</strong></summary>

<dl>
<dd>
<h2></h2>

После `git clone` разработчик получает не только текущие файлы, но и локальную копию истории и ссылок репозитория. Большинство операций выполняется локально. Центральный сервер обычно используется командой как общая точка обмена и источник правил, но технически Git не требует единственного центрального репозитория.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что именно хранит commit?</strong></summary>

<dl>
<dd>
<h2></h2>

Commit ссылается на снимок дерева файлов, содержит данные об авторе и создателе commit, время, сообщение и ссылку на одного или нескольких родителей. Его идентификатор вычисляется из содержимого этих данных. Если изменить снимок, сообщение или родителя, получится другой commit с другим идентификатором.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Git хранит каждый файл целиком или только diff?</strong></summary>

<dl>
<dd>
<h2></h2>

Логическая модель Git основана на снимках состояния файлов, а не на цепочке патчей. Неизменившиеся файлы могут ссылаться на уже сохранённые данные. При внутреннем хранении и передаче Git упаковывает информацию и может сохранять только различия между похожими данными, но пользователю удобнее рассуждать именно снимками.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем repository отличается от working directory?</strong></summary>

<dl>
<dd>
<h2></h2>

Working directory, или рабочая директория, содержит файлы, которые разработчик сейчас видит и редактирует. Репозиторий включает служебные данные Git: commits, ветки, теги и другую историю. Обычно они находятся в каталоге `.git` внутри рабочей директории.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие файлы Git начинает отслеживать?</strong></summary>

<dl>
<dd>
<h2></h2>

Новый файл сначала считается untracked. После `git add` его содержимое попадает в index, и файл становится tracked и staged для следующего commit. `.gitignore` помогает не предлагать к добавлению подходящие неотслеживаемые файлы, но не прекращает отслеживание файла, который уже попал в index или историю.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем Git отличается от GitLab?</strong></summary>

<dl>
<dd>
<h2></h2>

Git - инструмент и модель хранения истории. GitLab - платформа вокруг Git-репозиториев: она хранит их на сервере, управляет пользователями и правами, предоставляет merge requests, code review, protected branches и CI/CD pipelines.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему commit должен быть небольшим и логически цельным?</strong></summary>

<dl>
<dd>
<h2></h2>

Такой commit проще проверить, перенести, отменить и связать с причиной изменения. Если в одном commit смешаны рефакторинг, новая функция и исправление бага, diff сложнее читать, а точечный `revert` может отменить лишнее.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Является ли Git резервной копией проекта?</strong></summary>

<dl>
<dd>
<h2></h2>

Локальная история защищает от части ошибок, но сама по себе не является полноценной резервной копией. Потеря диска уничтожит и рабочие файлы, и локальный `.git`. Для устойчивости нужен удалённый репозиторий и, при необходимости, отдельная политика резервного копирования сервера.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Как помогает Git |
|---|---|
| Параллельная разработка | Компоненты, стили и API-интеграции меняются в отдельных ветках и объединяются через review. |
| Ошибка после релиза | По истории и diff можно найти изменение, которое вызвало регрессию, а затем исправить или отменить его. |
| Обновление зависимостей | Изменения `package.json` и lock-файла проходят через общий commit и pipeline. |
| Разбор решения | Commit и merge request сохраняют не только код, но и контекст задачи и обсуждения. |
