## Вопрос

<br>

 💬 **Как найти изменение, которое вызвало регрессию? Для чего нужны `git log`, `show`, `blame` и `bisect`?**

<h2></h2>

<br>
<dl>
<dd>

Регрессия - это поломка ранее работавшего поведения после изменения кода. Поиск начинают с воспроизводимого признака: конкретного теста, команды сборки или последовательности действий в интерфейсе. Затем сужают диапазон истории и проверяют commits, а не просматривают весь проект наугад.

`git log` показывает историю и помогает отфильтровать её по файлу, автору, дате, сообщению или изменённому тексту. `git show <sha>` выводит данные и diff конкретного commit. `git diff <old>..<new>` сравнивает два состояния. Эти команды подходят, если круг подозрительных изменений уже небольшой.

`git blame <file>` показывает, какой commit последним изменил каждую строку файла. Это способ найти контекст и перейти к commit, а не доказательство того, кто виноват: строка могла быть перемещена рефакторингом, а причина ошибки находиться в другом модуле или более раннем решении.

`git bisect` выполняет бинарный поиск по истории между заведомо рабочим и сломанным commit. Git выбирает commit примерно в середине диапазона, разработчик проверяет его и помечает как `good` или `bad`. После нескольких шагов остаётся первый bad commit. Если результат можно определить командой, `git bisect run` автоматизирует проверки.

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
git bisect run npm test -- --runInBand path/to/regression.test.ts
git bisect reset
```

Bisect полезен только при стабильном критерии. Flaky test, то есть тест с непредсказуемым результатом, несовместимая версия Node.js, отсутствующий lock-файл или необратимая миграция могут ошибочно пометить commit. Поэтому окружение фиксируют, а найденный commit подтверждают через `git show` и воспроизведение на соседних состояниях.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему <code>git bisect</code> называют бинарным поиском?</strong></summary>

<dl>
<dd>
<h2></h2>

На каждом шаге Git выбирает commit около середины оставшегося диапазона. Ответ `good` или `bad` отбрасывает примерно половину кандидатов. Поэтому в линейном диапазоне из тысячи commits обычно нужно около десяти проверок, а не тысяча.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означают <code>good</code> и <code>bad</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Это состояния относительно конкретного проверяемого поведения. `good` означает, что регрессии в commit ещё нет, `bad` - что она уже воспроизводится. Эти метки не оценивают качество commit целиком. Перед началом нужно убедиться, что выбранный good действительно проходит проверку, а bad стабильно падает.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает <code>git bisect run</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Для каждого выбранного commit Git запускает указанную команду. Код выхода `0` помечает состояние как good, `1-127`, кроме специального `125`, - как bad, а `125` просит пропустить непроверяемый commit. После завершения Git сообщает первый bad commit. Команда должна быть детерминированной и сама подготавливать нужное окружение.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать, если промежуточный commit не собирается по другой причине?</strong></summary>

<dl>
<dd>
<h2></h2>

Его можно отметить `git bisect skip`. Git продолжит поиск по другим кандидатам, но при нескольких пропусках иногда сможет назвать только набор возможных первых bad commits. Если старые commits требуют другой версии runtime или зависимостей, лучше восстановить воспроизводимое окружение, а не массово пропускать диапазон.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>git log -S</code> отличается от <code>git log -G</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`-S<string>` ищет commits, в которых изменилось количество вхождений конкретной строки. Это удобно для вопроса «когда добавили или удалили этот идентификатор». `-G<regex>` ищет commits, в diff которых есть строки, подходящие под регулярное выражение, и лучше работает для вариантов записи одного шаблона.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>git blame</code> может указывать не на причину ошибки?</strong></summary>

<dl>
<dd>
<h2></h2>

Blame показывает последний commit для текущего вида строки. Форматирование или перемещение кода может стать последним изменением, хотя неверное решение появилось раньше. Кроме того, ошибка может возникать из взаимодействия нескольких файлов. Найденный commit нужно открыть через `show`, прочитать сообщение и при необходимости пройти дальше по истории.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как искать историю переименованного файла?</strong></summary>

<dl>
<dd>
<h2></h2>

Для одного пути используют `git log --follow -- path/to/file`, чтобы Git попытался продолжить историю через переименование. Git распознаёт переименование по сходству содержимого, а не по отдельной записи «файл переименован», поэтому при одновременной крупной переработке связь может не определиться автоматически.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему shallow clone мешает расследованию?</strong></summary>

<dl>
<dd>
<h2></h2>

Shallow clone, или clone с ограниченной глубиной истории, не содержит старые commits за выбранной границей. Нужный good commit или родитель найденного изменения может отсутствовать, поэтому `log`, `blame` и `bisect` увидят неполный диапазон. Историю догружают через `git fetch --deepen <n>` или `git fetch --unshallow`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить найденный первый bad commit?</strong></summary>

<dl>
<dd>
<h2></h2>

Открыть его через `git show`, понять связь diff с симптомом и воспроизвести проверку на его родителе и на нём самом. Затем оценить, является ли commit непосредственной причиной или только активировал скрытую проблему окружения. Исправление должно сопровождаться тестом, который падает до него и проходит после.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```text
После одного из 300 commits форма перестала сохранять значение поля.
Есть стабильный end-to-end тест (E2E), проверяющий пользовательский сценарий целиком,
и тег известной рабочей версии. Как искать причину?
```

Ожидаемый ответ: проверить, что тест стабильно падает на текущем commit и проходит на теге рабочей версии. Запустить `git bisect`, отметить текущий commit как bad, тег как good и использовать `git bisect run` с командой этого теста. Зафиксировать версии Node.js, package manager и зависимостей. Найденный commit проверить через `git show` и повторное воспроизведение на нём и его родителе, после чего завершить `git bisect reset`.

## Где это встречается во frontend

| Ситуация | Инструмент |
|---|---|
| Известно имя удалённого prop | `git log -S'propName'` |
| Ошибка появилась между двумя релизами | `git bisect` со стабильной командой теста или сборки |
| Нужен контекст странной строки | `git blame`, затем `git show` найденного commit |
| Нужно сравнить тег production-версии с текущей веткой | `git diff <tag>..<branch>` и фильтрация `log` |
