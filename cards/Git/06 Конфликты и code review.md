## Вопрос

<br>

 💬 **Почему возникают конфликты в Git, как их правильно разрешать и что проверять на code review?**

<h2></h2>

<br>
<dl>
<dd>

Конфликт возникает, когда во время merge, rebase, cherry-pick или revert Git не может автоматически определить итоговое состояние отдельных путей.

Частый случай — две линии по-разному изменили пересекающиеся строки, но возможны и другие конфликты:

- `modify/delete`;
- переименование и изменение одного файла;
- разные переименования;
- изменение типа файла;
- бинарные данные.

Git отмечает конфликтующие пути как unmerged. В текстовый файл он может вставить conflict markers:

```text
<<<<<<<
одна версия
=======
другая версия
>>>>>>>
```

При включённом трёхстороннем отображении может также появиться секция `|||||||` с общей базовой версией.

Markers показывают участвующие фрагменты, но не определяют правильное бизнес-решение.

Разработчик должен:

1. понять назначение обеих правок;
2. собрать корректную итоговую версию;
3. удалить conflict markers;
4. проверить итоговый diff;
5. добавить разрешённый файл в index;
6. продолжить или завершить операцию.

Даже если Git объединил текст автоматически, может возникнуть semantic conflict, или смысловой конфликт.

Например, одна ветка переименовала поле API, а другая добавила использование старого имени в новом компоненте. Формального конфликта нет, проект иногда даже компилируется, но совместное поведение неверно.

Поэтому после интеграции проверяют:

- итоговый diff;
- типы;
- lint;
- тесты;
- сборку;
- затронутый пользовательский сценарий.

Если конфликт разрешался внутри merge request, значимые изменения результата нужно повторно посмотреть на code review. Conflict resolution является новым изменением и может случайно удалить часть одной из исходных реализаций.

Code review дополняет автоматические проверки.

Reviewer сначала сверяет изменение с задачей и оценивает:

- корректность поведения;
- состояния UI и ошибки;
- контракты данных;
- обратную совместимость;
- архитектурные границы;
- accessibility;
- безопасность;
- производительность;
- достаточность тестов;
- отсутствие случайных файлов, зависимостей и несвязанных изменений.

Небольшой логически цельный merge request позволяет увидеть причинно-следственные связи. В большом diff дефекты, лишние изменения и смысловые конфликты скрываются легче.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что означают conflict markers?</strong></summary>

<dl>
<dd>
<h2></h2>

Фрагмент между `<<<<<<<` и `=======` представляет одну сторону конфликта, а между `=======` и `>>>>>>>` — другую.

При трёхстороннем формате между `|||||||` и `=======` также может отображаться общая базовая версия.

Значения `ours` и `theirs` зависят от операции.

При обычном merge:

- `ours` — текущая ветка;
- `theirs` — вливаемая ветка.

При rebase:

- `ours` обычно представляет новую базу, на которую переносятся commits;
- `theirs` представляет применяемый в данный момент commit.

Поэтому во время rebase эти названия легко истолковать наоборот.

Надёжнее смотреть:

- `git status`;
- исходные commits;
- трёхсторонний diff в IDE;
- назначение обеих правок.

Выбор одной стороны целиком через `ours` или `theirs` может удалить необходимую часть другой реализации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Каков порядок разрешения merge conflict?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала выполняют:

```bash
git status
```

Затем для каждого unmerged-файла:

1. изучают обе исходные правки;
2. формируют итоговый код;
3. удаляют conflict markers;
4. запускают форматирование и релевантные проверки;
5. добавляют файл в index:

```bash
git add <file>
```

После подготовки всех файлов проверяют:

```bash
git diff --staged
git diff --check
```

`git diff --check` помогает обнаружить некоторые проблемы diff, включая оставшиеся conflict markers и ошибки пробелов.

Merge продолжают через:

```bash
git merge --continue
```

либо создают merge commit обычной командой `git commit`, если это требуется текущим состоянием операции.

Если результат не нужен, merge отменяют:

```bash
git merge --abort
```

После завершения ещё раз проверяют итоговый diff и пользовательский сценарий.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как разрешение конфликта отличается при rebase?</strong></summary>

<dl>
<dd>
<h2></h2>

Rebase заново применяет commits по одному.

После исправления текущего конфликта файлы добавляют в index:

```bash
git add <files>
```

Затем продолжают операцию:

```bash
git rebase --continue
```

Следующий применяемый commit может вызвать новый конфликт.

Rebase можно полностью отменить:

```bash
git rebase --abort
```

Текущий commit можно пропустить:

```bash
git rebase --skip
```

Но `--skip` полностью исключает его изменение из новой истории. Команду используют только после проверки, что изменение уже присутствует в базе или действительно больше не нужно.

При rebase особенно важно не полагаться механически на названия `ours` и `theirs`: `ours` обычно означает новую базу, а `theirs` — применяемый commit.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как правильно разрешать конфликт в lock-файле?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала определяют правильный итог файлов, в которых объявлены зависимости:

- `package.json`;
- workspace-конфигурация;
- другие manifest-файлы проекта.

После этого lock-файл обычно надёжнее заново сгенерировать тем же package manager и совместимой версией, а не вручную объединять его служебные блоки.

Нужно учитывать package manager проекта:

```text
npm → package-lock.json
pnpm → pnpm-lock.yaml
Yarn → yarn.lock
```

После генерации проверяют:

- diff lock-файла;
- отсутствие неожиданных обновлений пакетов;
- воспроизводимую чистую установку;
- тесты;
- production build.

Например, для npm чистую установку проверяют через:

```bash
npm ci
```

Для других package managers используют соответствующую команду проекта с запретом неявного изменения lock-файла.

Нельзя без анализа оставить только одну сторону, если обе ветки изменяли зависимости: так можно потерять пакет или восстановить устаревшее дерево.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли commit-ить generated-файлы после конфликта?</strong></summary>

<dl>
<dd>
<h2></h2>

Это зависит от правил репозитория.

Если generated-файл хранится в Git, его восстанавливают из правильных исходников штатным генератором и проверяют итоговый diff.

Ручное редактирование результата генерации создаёт расхождение с источником и может быть потеряно при следующем запуске.

Полезно повторно запустить генерацию после разрешения конфликта. Если исходники и инструменты не изменились, новый неожиданный diff появляться не должен.

Если generated-файлы не хранятся в Git, их не добавляют только ради разрешения локального конфликта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить, что конфликт разрешён правильно?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала проверяют техническое состояние:

- в `git status` нет unmerged paths;
- в файлах не осталось conflict markers;
- итоговый staged diff содержит обе необходимые правки;
- нет случайных изменений.

Затем запускают проверки, относящиеся к изменённому коду:

- typecheck;
- lint;
- тесты;
- production build;
- генерацию типов или API-клиента;
- проверку lock-файла.

После этого вручную проходят затронутый сценарий, включая необходимые состояния:

- loading;
- error;
- empty;
- success;
- граничные варианты.

Успешная сборка доказывает только часть технической корректности и не гарантирует сохранение бизнес-логики.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что в первую очередь проверять на frontend code review?</strong></summary>

<dl>
<dd>
<h2></h2>

Проверку удобно вести от наиболее важных свойств к менее важным.

Сначала:

1. соответствует ли изменение задаче;
2. корректно ли основное поведение;
3. обработаны ли необходимые состояния и ошибки;
4. соблюдён ли API-контракт;
5. нет ли регрессии или нарушения обратной совместимости.

Затем оценивают:

- читаемость;
- типы;
- архитектурные зависимости;
- accessibility;
- security;
- производительность;
- достаточность тестов;
- объём и границы изменения.

Отдельно проверяют, не попали ли в MR:

- случайные файлы;
- отладочный код;
- лишние зависимости;
- несвязанный рефакторинг;
- секреты;
- generated-файлы с необъяснимым diff.

Форматирование и повторяющиеся механические правила лучше поручить formatter, linter и pipeline, чтобы review сосредоточился на поведении и рисках.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему большой merge request сложнее проверять?</strong></summary>

<dl>
<dd>
<h2></h2>

Reviewer должен удерживать больше контекста, а связанные и случайные изменения смешиваются.

Сложнее:

- понять, какой код действительно нужен задаче;
- проследить поток данных;
- проверить все ветви поведения;
- заметить удалённую проверку или обработчик;
- отделить изменение поведения от перемещения кода;
- найти смысловой конфликт.

Большую функцию лучше делить на независимо безопасные части.

Но не следует создавать искусственные MR, которые по отдельности оставляют основную ветку в некорректном состоянии. Части должны быть технически безопасными, обратно совместимыми или скрытыми через feature flag.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать, если замечание reviewer спорное?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала определяют тип комментария:

- обязательная проблема;
- вопрос для уточнения;
- необязательное предложение;
- личное предпочтение.

Затем обсуждают:

- требования задачи;
- ограничения;
- риски;
- наблюдаемые последствия вариантов;
- принятые правила проекта.

Если решение автора сохраняется, причину полезно явно зафиксировать в обсуждении.

Если один и тот же вопрос повторяется, договорённость переносят в:

- документацию;
- lint rule;
- архитектурное соглашение;
- шаблон merge request;
- общий компонент или API.

Обсуждаются код и компромиссы решения, а не компетентность автора или reviewer.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли pipeline заменить code review?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Pipeline хорошо проверяет формализуемые свойства:

- lint;
- типы;
- автоматические тесты;
- build;
- security scans;
- форматирование;
- воспроизводимость генерации.

Он не всегда понимает:

- соответствует ли UI задаче;
- корректна ли модель данных;
- учтены ли реальные пользовательские состояния;
- не появилась ли лишняя сложность;
- насколько решение будет поддерживаемым;
- не возник ли semantic conflict.

Code review также не заменяет pipeline. Человек ненадёжно и дорого выполняет повторяющиеся механические проверки вручную.

Оба механизма дополняют друг друга.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```text
После разрешения merge conflict React-компонент собирается,
но при пустом ответе API больше ничего не показывает. Что проверять?
```

Ожидаемый ответ: сравнить обе исходные версии конфликтного участка и итоговый diff, проверить контракт API и условия перехода между `loading`, `error`, `empty` и успешным состоянием. Затем восстановить ожидаемое поведение, добавить или обновить тест на пустой ответ и вручную пройти сценарий. Успешная сборка доказывает синтаксическую и типовую корректность только в пределах настроенных проверок, но не сохранение логики.

## Где это встречается во frontend

| Ситуация | Риск |
|---|---|
| Два разработчика меняют общий компонент | Можно потерять обработчик, prop или одно из состояний UI |
| Обновление зависимостей в двух ветках | Неправильный lock-файл изменит дерево пакетов или сломает воспроизводимую установку |
| Изменение OpenAPI-схемы и формы | Автоматический merge не заметит несовместимость старого поля с новым типом |
| Большой MR с рефакторингом и функцией | Reviewer сложнее отделить изменение поведения от перемещения кода |
