## Вопрос

<br>

 💬 **Для чего нужны `cherry-pick`, `revert`, `reset`, `restore`, `stash` и `reflog`? Чем они отличаются и где можно потерять изменения?**

<h2></h2>

<br>
<dl>
<dd>

Эти команды работают с разными частями Git. Сначала нужно определить, что требуется изменить: историю commits, положение ветки, index, working tree или только временно убрать незавершённую работу.

| Команда | Что делает | Основной сценарий |
|---|---|---|
| `cherry-pick` | Применяет изменение выбранного commit и создаёт новый commit в текущей ветке | Перенести конкретное исправление без merge всей ветки |
| `revert` | Создаёт новый commit с обратным изменением | Отменить уже опубликованный commit, не переписывая историю |
| `reset` | Перемещает `HEAD` и в зависимости от режима меняет index и working tree | Пересобрать локальные commits или вернуть слои Git к выбранному состоянию |
| `restore` | Восстанавливает выбранные пути в working tree или index из указанного источника | Отбросить unstaged-правки или убрать файл из staging area |
| `stash` | Сохраняет незакоммиченные изменения во временную локальную запись и очищает рабочее состояние | Переключиться на другую задачу без промежуточного commit |
| `reflog` | Показывает локальную историю перемещений `HEAD` и других ссылок | Найти commit после ошибочного reset, rebase или удаления ветки |

`cherry-pick` вычисляет изменение выбранного commit относительно его родителя, применяет его к текущей ветке и создаёт новый commit. Новый commit имеет другого родителя и поэтому получает другой идентификатор.

`revert` не удаляет исходный commit. Он создаёт новый commit, который отменяет его изменение относительно текущего состояния проекта. Если последующие изменения пересекаются с отменяемым commit, возможен конфликт.

Главное различие между `revert` и `reset`:

- `revert` добавляет новый commit в историю;
- `reset` перемещает `HEAD` и может переписать положение текущей ветки.

Поэтому для commit, который уже получили другие разработчики, обычно используют `revert`.

В форме с указанием commit `reset` перемещает `HEAD`. Если `HEAD` указывает на ветку, эта ветка также передвигается. В состоянии detached HEAD именованная ветка не меняется.

Режимы `reset` удобно запоминать через три слоя:

| Команда | `HEAD` и текущая ветка | Index | Working tree |
|---|---:|---:|---:|
| `git reset --soft <commit>` | перемещает | сохраняет | сохраняет |
| `git reset --mixed <commit>` | перемещает | сбрасывает к commit | сохраняет |
| `git reset --hard <commit>` | перемещает | сбрасывает к commit | сбрасывает к commit |

`--mixed` используется по умолчанию.

Эта таблица относится к форме `reset` с указанием commit. В форме с путём:

```bash
git reset -- file.ts
```

команда не передвигает `HEAD` или ветку, а восстанавливает выбранную запись в index из `HEAD`. Более явный современный вариант:

```bash
git restore --staged file.ts
```

`reset --hard` и `restore` рабочего файла могут уничтожить незакоммиченные изменения отслеживаемых файлов.

Перед разрушительной операцией проверяют:

```bash
git status
git diff
git diff --staged
```

Если работа может понадобиться, сначала создают временную ветку, commit или stash.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем <code>revert</code> отличается от <code>reset</code> на практическом примере?</strong></summary>

<dl>
<dd>
<h2></h2>

Если ошибочный commit уже находится в общей `main`, команда:

```bash
git revert <sha>
```

создаст новый commit, отменяющий его изменение. Коллеги смогут получить обычное продолжение общей истории.

Команда:

```bash
git reset --hard main~1
```

передвинула бы локальную `main` назад. Для публикации такого положения потребовался бы принудительный push, а локальные истории коллег разошлись бы с remote.

`revert` также может вызвать конфликт, если более поздние commits изменили те же участки кода.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает <code>git reset --soft HEAD~1</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`HEAD` перемещается на один commit назад. Если он указывает на ветку, ветка также передвигается.

Index и working tree не меняются. Изменения отменённого commit остаются staged, поэтому их можно дополнить и создать новый commit.

Если нужно только изменить последний локальный commit, часто короче использовать:

```bash
git commit --amend
```

Обе операции переписывают локальную историю и изменяют идентификатор итогового commit.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает <code>git reset --mixed HEAD~1</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`HEAD` и текущая ветка перемещаются назад, index приводится к новому `HEAD`, а файлы в working tree сохраняются.

Изменения отменённого commit становятся unstaged.

Это стандартный режим `reset`, если флаг не указан:

```bash
git reset HEAD~1
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем опасен <code>git reset --hard</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Он приводит `HEAD`, index и working tree к выбранному commit.

Незакоммиченные изменения отслеживаемых файлов перезаписываются.

Команда не удаляет автоматически все untracked-файлы, но неотслеживаемый файл или каталог может быть удалён, если он мешает восстановить отслеживаемый путь из выбранного commit.

Commit, с которого передвинули ветку, обычно некоторое время можно найти через reflog.

Но изменения working tree, которые никогда не попадали в commit, stash или сохранённый Git-объект, Git может не восстановить.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>git restore file.ts</code> отличается от <code>git restore --staged file.ts</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Без `--staged` команда по умолчанию восстанавливает файл в working tree из index:

```bash
git restore file.ts
```

Его unstaged-изменения отбрасываются, а staged-версия остаётся в index.

С `--staged` команда восстанавливает запись в index, по умолчанию из `HEAD`:

```bash
git restore --staged file.ts
```

Файл убирается из staging area, но его изменения сохраняются в working tree.

Источник можно указать явно:

```bash
git restore --source=<commit> file.ts
```

Если одновременно передать `--staged --worktree`, команда изменит и index, и рабочий файл:

```bash
git restore \
  --source=<commit> \
  --staged \
  --worktree \
  file.ts
```

Такую операцию выполняют особенно осторожно, потому что она может перезаписать незакоммиченные данные.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужен <code>cherry-pick</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда требуется перенести один или несколько конкретных commits без интеграции всей исходной ветки.

Например, исправление из `main` переносят в поддерживаемую release branch:

```bash
git cherry-pick <sha>
```

Cherry-pick применяет изменение commit относительно его родителя и создаёт новый commit с другим родителем и идентификатором.

При конфликте после исправления выполняют:

```bash
git add <files>
git cherry-pick --continue
```

Для отмены незавершённой операции:

```bash
git cherry-pick --abort
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему нельзя постоянно синхронизировать долгоживущие ветки через <code>cherry-pick</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Cherry-pick копирует отдельные изменения, но не связывает истории так, как merge.

При множестве переносов легко:

- пропустить зависимый commit;
- применить одно логическое исправление дважды;
- получить разные варианты одного изменения;
- усложнить последующий merge;
- потерять понимание того, какие изменения уже перенесены.

Это точечный инструмент для отдельных commits, а не замена понятной стратегии интеграции веток.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что сохраняет <code>git stash</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

По умолчанию stash сохраняет staged- и unstaged-изменения отслеживаемых файлов.

Untracked-файлы добавляются через:

```bash
git stash -u
```

Ignored-файлы также включаются через:

```bash
git stash -a
```

`git stash apply` применяет выбранную запись и сохраняет её в списке.

`git stash pop` пытается применить запись и удалить её после успешного применения. Если возникают конфликты, stash обычно остаётся в списке, чтобы работу можно было восстановить повторно.

После применения проверяют:

```bash
git status
git stash list
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли считать stash надёжным долгосрочным хранилищем?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Stash находится только в конкретном локальном репозитории, не участвует в обычном push и легко забывается.

Запись также можно случайно удалить через `drop`, `clear` или успешный `pop`.

Для работы, которую важно сохранить, передать или обсудить, надёжнее создать осмысленный commit в отдельной ветке и отправить его на remote.

Stash подходит прежде всего для короткого переключения контекста.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как восстановить commit после ошибочного <code>reset --hard</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала выполняют:

```bash
git reflog
```

Затем находят прежнее положение `HEAD` и проверяют commit:

```bash
git show <sha>
```

Чтобы надёжно вернуть к нему доступ, создают recovery branch:

```bash
git branch recover-work <sha>
```

После этого commit снова достижим через именованную ссылку.

Reflog может вернуть доступ к commit, но не восстанавливает незакоммиченные изменения working tree, уничтоженные через `reset --hard`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему reflog не является удалённой резервной копией?</strong></summary>

<dl>
<dd>
<h2></h2>

Reflog ведётся отдельно в конкретном локальном репозитории и обычно не передаётся через push или fetch.

Записи имеют ограниченный срок хранения. Недостижимые объекты позднее могут быть удалены сборкой мусора Git.

Reflog помогает найти commits и другие Git-объекты после перемещения ссылок, но не гарантирует восстановление изменений, которые никогда не были сохранены в Git.

Поэтому важную работу нужно вовремя:

- фиксировать в commit;
- сохранять в именованной ветке;
- отправлять на remote.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как отменить merge commit через <code>revert</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

У merge commit несколько родителей, поэтому Git нужно указать mainline parent:

```bash
git revert -m <номер> <sha>
```

Выбранный родитель считается основной линией, которую нужно сохранить. Обычно для merge feature branch в `main` основной линией является первый родитель:

```bash
git revert -m 1 <merge-sha>
```

Но полагаться на номер без проверки нельзя.

Сначала смотрят родителей и изменение merge commit:

```bash
git show <merge-sha>
```

Ошибка в выборе родителя отменит не ту сторону объединения.

Также нужно учитывать, что последующий merge той же ветки может не вернуть уже отменённые изменения автоматически: Git помнит исходную связь histories.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Инструмент |
|---|---|
| Ошибочный commit уже попал в `main` | `revert`, чтобы сохранить общую историю |
| Срочный fix нужен в release branch | `cherry-pick` конкретного commit |
| Нужно временно переключиться на production bug | Короткоживущий `stash` или WIP-ветка |
| В staging area попал лишний файл | `restore --staged` с сохранением working tree |
| После rebase пропал доступ к commit | `reflog`, проверка через `show` и recovery branch |
