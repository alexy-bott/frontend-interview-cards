## Вопрос

<br>

 💬 **Как найти изменение, которое вызвало регрессию? Для чего нужны `git log`, `show`, `blame` и `bisect`?**

<h2></h2>

<br>
<dl>
<dd>

Регрессия — это поломка ранее работавшего поведения после изменения кода.

Поиск начинают с воспроизводимого признака:

- конкретного автоматического теста;
- команды сборки;
- стабильной ошибки;
- последовательности действий в интерфейсе.

Затем сужают диапазон истории и проверяют commits, а не просматривают весь проект наугад.

`git log` показывает историю и помогает отфильтровать её:

- по файлу;
- автору;
- дате;
- сообщению;
- изменённому тексту.

`git show <sha>` выводит метаданные и diff конкретного commit.

`git diff <old> <new>` сравнивает два состояния проекта. Запись:

```bash
git diff <old>..<new>
```

для `git diff` обычно означает то же сравнение конечных состояний. В отличие от `git log`, две точки здесь не задают множество commits диапазона.

Эти команды подходят, если круг подозрительных изменений уже небольшой.

`git blame <file>` показывает, какой commit последним изменил каждую текущую строку файла.

Это способ найти контекст и перейти к commit, а не доказательство того, кто виноват. Строка могла быть:

- отформатирована;
- перемещена;
- скопирована;
- изменена механическим рефакторингом.

Причина ошибки также может находиться в другом модуле или более раннем архитектурном решении.

`git bisect` выполняет поиск по истории между заведомо рабочим и сломанным состояниями.

Обычно выбирают:

- bad commit, на котором регрессия стабильно воспроизводится;
- good commit среди его предков, на котором проверка стабильно проходит.

Git выбирает commit, который старается разделить оставшееся множество кандидатов примерно пополам. В нелинейном графе это не обязательно хронологическая середина списка commits.

Разработчик проверяет выбранное состояние и помечает его как `good` или `bad`. После нескольких шагов Git сообщает первый bad commit относительно заданного критерия.

Если результат можно определить командой, `git bisect run` автоматизирует проверку:

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.4.0
git bisect run npm test -- --runInBand path/to/regression.test.ts
git bisect reset
```

Команда или script для `bisect run` должны:

- стабильно воспроизводить один критерий;
- возвращать правильный exit code;
- при необходимости подготавливать окружение для текущего commit;
- не зависеть от состояния предыдущего шага.

Bisect полезен только при надёжной классификации.

Flaky test, несовместимая версия Node.js, отсутствующий lock-файл, внешняя нестабильная система или необратимая миграция могут ошибочно пометить commit.

Поэтому окружение фиксируют, а найденный commit подтверждают через `git show` и повторное воспроизведение на нём и предыдущем подходящем состоянии.

В истории с merges первым bad может оказаться merge commit: иногда каждый родитель отдельно работает, а ошибка возникает только в их объединённом состоянии.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему <code>git bisect</code> называют бинарным поиском?</strong></summary>

<dl>
<dd>
<h2></h2>

На каждом шаге Git старается выбрать commit, который разделит оставшееся множество кандидатов примерно пополам.

Ответ `good` или `bad` исключает значительную часть кандидатов.

Поэтому в простой линейной истории из тысячи commits обычно потребуется около десяти проверок, а не тысяча.

В графе с ветвлениями и merge commits выбранный commit не обязательно находится в хронологической середине. Git учитывает связи предков и потомков, чтобы эффективнее уменьшить множество кандидатов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означают <code>good</code> и <code>bad</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Это состояния относительно одного конкретного проверяемого поведения.

`good` означает, что регрессия в этом commit ещё не воспроизводится.

`bad` означает, что она уже воспроизводится.

Эти метки не оценивают качество commit целиком. Один и тот же commit может быть good для одной ошибки и bad для другой.

Перед началом нужно убедиться, что:

- выбранный bad стабильно проваливает проверку;
- выбранный good стабильно её проходит;
- good относится к истории, предшествующей исследуемому bad;
- критерий одинаков на всех шагах.

Если исходные границы классифицированы неверно, результат bisect также будет неверным.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает <code>git bisect run</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Для каждого выбранного commit Git запускает указанную команду или script.

Код выхода интерпретируется так:

- `0` — good;
- `1–127`, кроме `125`, — bad;
- `125` — текущий commit нельзя проверить, его нужно пропустить.

После завершения Git сообщает первый bad commit либо несколько возможных кандидатов, если часть истории пришлось пропустить.

Проверяющая команда должна быть детерминированной.

Если разные commits требуют разных зависимостей, script может выполнять воспроизводимую установку по lock-файлу текущего состояния:

```bash
npm ci
npm test -- --runInBand path/to/regression.test.ts
```

Нужно учитывать стоимость такого запуска и очищать артефакты, которые могут переносить состояние между checkout.

Если проверка зависит от внешнего сервиса, нестабильной сети или общих тестовых данных, сначала лучше сделать её локально воспроизводимой.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать, если промежуточный commit не собирается по другой причине?</strong></summary>

<dl>
<dd>
<h2></h2>

Его можно отметить:

```bash
git bisect skip
```

При использовании `git bisect run` script должен завершиться с кодом `125`.

Git продолжит поиск по другим кандидатам, но при нескольких пропусках может не определить один точный первый bad commit и вернуть набор возможных кандидатов.

Если старые commits требуют другой версии runtime, package manager или зависимостей, лучше восстановить воспроизводимое окружение, а не массово пропускать диапазон.

Например, можно учитывать:

- `.nvmrc`;
- поле `engines`;
- версию package manager;
- lock-файл;
- Docker image;
- историческую CI-конфигурацию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>git log -S</code> отличается от <code>git log -G</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`-S<string>` ищет commits, в которых изменилось количество вхождений конкретной строки.

Например:

```bash
git log -S'legacyToken'
```

Это удобно для вопроса:

```text
В каком commit этот идентификатор появился или исчез?
```

`-G<regex>` ищет commits, в diff которых добавленные или удалённые строки соответствуют регулярному выражению:

```bash
git log -G'legacy(Token|Session)'
```

Он подходит, когда запись могла меняться или нужно искать шаблон.

`-S` и `-G` анализируют изменение diff по-разному, поэтому могут вернуть разные наборы commits.

Для просмотра найденных изменений добавляют `-p`:

```bash
git log -p -S'legacyToken'
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>git blame</code> может указывать не на причину ошибки?</strong></summary>

<dl>
<dd>
<h2></h2>

Blame показывает последний commit, изменивший текущий вид строки.

Последним изменением могло быть:

- форматирование;
- переименование переменной;
- перемещение функции;
- массовый рефакторинг;
- генерация файла.

При необходимости используют дополнительные параметры:

```bash
git blame -w file.ts
```

игнорирует изменения пробелов.

```bash
git blame -M file.ts
```

пытается обнаружить перемещение строк внутри файла.

```bash
git blame -C file.ts
```

пытается найти строки, скопированные или перемещённые между файлами.

Эти параметры уменьшают шум, но не доказывают причинность.

Найденный commit нужно открыть через `git show`, прочитать его сообщение, посмотреть соседние изменения и при необходимости пройти дальше по истории.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как искать историю переименованного файла?</strong></summary>

<dl>
<dd>
<h2></h2>

Для одного пути используют:

```bash
git log --follow -- path/to/file
```

Git попытается продолжить историю через переименование.

Git не хранит отдельный обязательный объект «файл был переименован». Переименование определяется по сходству содержимого при сравнении состояний.

Поэтому при одновременной крупной переработке файла связь может не определиться автоматически.

`--follow` также предназначен для истории одного файла и имеет ограничения при сложных перемещениях и копировании.

В таких случаях дополнительно исследуют commits до и после изменения через `git show`, поиск по содержимому и параметры обнаружения переименований.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему shallow clone мешает расследованию?</strong></summary>

<dl>
<dd>
<h2></h2>

Shallow clone, или clone с ограниченной глубиной, не содержит старые commits за установленной границей.

Из-за этого:

- нужный good commit может отсутствовать;
- `git log` покажет неполную историю;
- `git blame` может остановиться на искусственной границе;
- `git bisect` не получит полный набор кандидатов;
- родитель подозрительного commit может быть недоступен.

Историю можно догрузить частично:

```bash
git fetch --deepen <n>
```

или полностью:

```bash
git fetch --unshallow
```

После этого проверяют, что нужные tags и branches также доступны локально.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить найденный первый bad commit?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала открывают commit:

```bash
git show <sha>
```

Затем проверяют:

- соответствует ли diff наблюдаемому симптому;
- не изменилось ли окружение;
- не является ли commit только триггером более ранней проблемы;
- проходит ли тест на предыдущем состоянии;
- стабильно ли падает тест на найденном commit.

Для обычного commit сравнивают его с родителем:

```bash
git switch --detach <sha>^
```

и затем:

```bash
git switch --detach <sha>
```

Для merge commit нужно проверить оба родителя. Возможна ситуация, когда каждый родитель отдельно работает, но объединённый merge commit уже содержит регрессию.

После подтверждения исправление сопровождают тестом, который воспроизводит проблему до исправления и проходит после него.

В конце возвращаются к исходной позиции:

```bash
git bisect reset
```

</dd>
</dl>

</details>

## Мини-задача

```text
После одного из 300 commits форма перестала сохранять значение поля.
Есть стабильный end-to-end тест (E2E), проверяющий пользовательский сценарий целиком,
и тег известной рабочей версии. Как искать причину?
```

Ожидаемый ответ: проверить, что E2E-тест стабильно падает на текущем commit и проходит на теге рабочей версии. Убедиться, что тег относится к истории текущего сломанного состояния. Запустить `git bisect`, отметить текущий commit как bad, тег как good и использовать `git bisect run` со script этого теста. Зафиксировать версии Node.js, package manager и зависимостей, а при необходимости восстанавливать окружение для каждого checkout. Найденный commit проверить через `git show` и повторное воспроизведение на нём и предыдущем состоянии; если это merge commit — проверить обоих родителей. После расследования выполнить `git bisect reset`.

## Где это встречается во frontend

| Ситуация | Инструмент |
|---|---|
| Известно имя удалённого prop | `git log -S'propName'` |
| Ошибка появилась между двумя релизами | `git bisect` со стабильной командой теста или сборки |
| Нужен контекст странной строки | `git blame`, затем `git show` найденного commit |
| Нужно сравнить tag production-версии с текущей веткой | `git diff <tag> <branch>` и фильтрация `git log` |
