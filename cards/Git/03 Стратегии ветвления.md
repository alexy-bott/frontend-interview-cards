## Вопрос

<br>

 💬 **Какие стратегии ветвления используются в командах? Чем feature branches, trunk-based development и Git Flow отличаются друг от друга?**

<h2></h2>

<br>
<dl>
<dd>

Стратегия ветвления определяет, откуда разработчик начинает работу, как долго живёт ветка, как изменения интегрируются и из какой линии выпускается релиз.

Универсально лучшей стратегии нет. Выбор зависит от:

- частоты поставки;
- способа релизов;
- размера команды;
- скорости и надёжности CI;
- требований к согласованию;
- необходимости поддерживать несколько выпущенных версий.

Feature branch — отдельная ветка для задачи или части функциональности. Обычно изменение проходит merge request и code review перед интеграцией в основную линию.

Такая ветка изолирует работу и обсуждение задачи, но при долгой жизни накапливает расхождения с основной веткой. Это усложняет review, разрешение конфликтов и совместную проверку нескольких изменений.

Feature branches не обязательно противопоставляются trunk-based development. Короткие ветки, которые живут несколько часов или один-два дня и быстро интегрируются через merge request, могут быть частью trunk-based workflow.

Trunk-based development строится вокруг одной основной линии — trunk, которой обычно является `main`.

Разработчики:

- интегрируют небольшие изменения прямо в trunk;
- либо используют очень короткоживущие ветки.

Определяющий признак — частая интеграция в одну основную линию, а не полное отсутствие branches.

Trunk должен оставаться проверенным и потенциально готовым к выпуску. Для этого нужны:

- быстрый и надёжный CI;
- небольшие изменения;
- автоматические тесты;
- обратная совместимость;
- feature flags для ещё не включённой функциональности.

Feature flag, или флаг функции, отделяет deployment от release.

Deployment доставляет код в среду, а release делает возможность доступной пользователям. Поэтому незавершённый или постепенно выкатываемый код можно уже интегрировать в trunk, но оставить выключенным.

Git Flow — более формализованный workflow с несколькими типами веток:

- `main` хранит выпущенные версии;
- `develop` содержит изменения следующего релиза;
- `feature/*` создаются для разработки функций;
- `release/*` используются для стабилизации версии;
- `hotfix/*` создаются для срочных исправлений production.

Типичный путь функции в Git Flow выглядит так:

```text
feature/* → develop → release/* → main
```

После выпуска изменения из release branch также возвращают в текущую линию разработки, чтобы исправления стабилизации не потерялись.

Git Flow удобен при плановых версионных релизах и отдельном длительном этапе стабилизации, но создаёт больше merges, долгоживущих веток и процессных шагов.

Для веб-продукта с частыми небольшими deployments такой workflow часто тяжелее trunk-based development.

Классический Git Flow сам по себе не решает полную параллельную поддержку нескольких старых версий. Для этого обычно создают отдельные maintenance-ветки от соответствующих выпущенных commits или tags.

| Подход | Основная идея | Подходит, когда |
|---|---|---|
| Feature branches | Каждая задача выполняется в отдельной ветке и проходит MR | Нужны изолированный review и контролируемая интеграция |
| Trunk-based development | Маленькие изменения часто интегрируются в одну основную линию | Команда выпускает часто и имеет быстрый надёжный CI |
| Git Flow | Разработка и подготовка релиза разделены между несколькими типами веток | Есть плановые релизы и отдельный этап стабилизации |

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему feature branch должна жить недолго?</strong></summary>

<dl>
<dd>
<h2></h2>

Пока ветка существует отдельно, основная линия продолжает меняться.

Чем больше расхождение, тем сложнее:

- проверить большой diff;
- разрешить конфликты;
- проверить совместимость с другими изменениями;
- понять причину регрессии;
- безопасно интегрировать задачу.

Риск уменьшают:

- небольшие задачи;
- ранний draft MR;
- частые commits;
- регулярная синхронизация с основной веткой;
- интеграция готовых безопасных частей;
- feature flags для ещё не включённой возможности.

Короткая feature branch совместима с trunk-based development. Проблемой является не само наличие ветки, а длительная изоляция изменений.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Означает ли trunk-based development работу без branches?</strong></summary>

<dl>
<dd>
<h2></h2>

Не обязательно.

Возможны:

- небольшие commits непосредственно в trunk;
- очень короткоживущие branches;
- merge requests с быстрой проверкой и интеграцией.

Определяющий признак — частая интеграция в одну основную линию.

Если feature branch существует неделями, содержит большое изменение и редко синхронизируется с trunk, такой процесс уже противоречит основной идее trunk-based development, даже если ветка в итоге объединяется с `main`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как доставить незавершённую функцию в trunk?</strong></summary>

<dl>
<dd>
<h2></h2>

Изменение разбивают на небольшие обратно совместимые части.

Пользовательскую возможность скрывают за feature flag:

```text
код доставлен → flag выключен → пользователи функцию не видят
```

После проверки flag включают:

- для разработчиков;
- для тестовой группы;
- для части пользователей;
- для всех пользователей.

Критичные сценарии проверяют и с включённым, и с выключенным состоянием.

Feature flag должен иметь:

- понятного владельца;
- план включения;
- наблюдаемость;
- срок удаления.

Устаревшие flags удаляют, иначе они превращаются в постоянные развилки кода и увеличивают число комбинаций поведения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем release branch отличается от feature branch?</strong></summary>

<dl>
<dd>
<h2></h2>

Feature branch содержит работу над конкретным изменением или пользовательской возможностью.

Release branch фиксирует состав версии на этапе стабилизации.

В неё обычно принимают:

- исправления найденных дефектов;
- обновление версии;
- release notes;
- изменения, необходимые для выпуска.

Новые функции после начала стабилизации обычно откладывают до следующего релиза.

После выпуска результат:

- интегрируют в `main`;
- отмечают tag;
- возвращают в `develop` или другую текущую линию разработки.

Release branch нужна не каждой команде. При непрерывной поставке отдельная длительная ветка стабилизации может только задерживать интеграцию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое hotfix branch?</strong></summary>

<dl>
<dd>
<h2></h2>

Hotfix branch — ветка для срочного исправления уже выпущенной версии.

Её начинают от commit или tag той production-версии, которую нужно исправить.

После проверки исправление выпускают и переносят во все актуальные линии, где ошибка не должна появиться снова.

В классическом Git Flow hotfix обычно объединяют:

- с `main`;
- с `develop`;
- при необходимости с активной `release` branch.

Если команда поддерживает несколько старых версий, исправление отдельно переносят в соответствующие maintenance-ветки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое Git tag и зачем он нужен при релизе?</strong></summary>

<dl>
<dd>
<h2></h2>

Tag, или тег, — именованная ссылка на конкретный commit.

В отличие от ветки, опубликованный tag по соглашению не передвигают. Поэтому им удобно отмечать выпущенные версии:

```text
v2.4.0
```

Lightweight tag является простой ссылкой.

Annotated tag хранит отдельный объект с:

- автором;
- датой;
- сообщением;
- возможной криптографической подписью.

Для официальных релизов часто используют annotated tags.

Тег отправляют на remote явно:

```bash
git push origin v2.4.0
```

Либо отправляют все локальные tags:

```bash
git push origin --tags
```

Второй вариант нужно применять осознанно, потому что он отправит все отсутствующие на remote tags.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как синхронизировать feature branch с <code>main</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Можно объединить актуальную `main` с feature branch через merge:

```bash
git fetch origin
git merge origin/main
```

Merge сохраняет существующие commits и добавляет merge commit, если fast-forward невозможен.

Другой вариант — перенести собственные commits feature branch на новую `main` через rebase:

```bash
git fetch origin
git rebase origin/main
```

Rebase создаёт новые commits с другими идентификаторами и делает историю линейной.

Если feature branch уже опубликована, после rebase обычно требуется:

```bash
git push --force-with-lease
```

`--force-with-lease` безопаснее обычного `--force`, потому что проверяет, не изменилось ли ожидаемое состояние remote-ветки. Но команда всё равно переписывает опубликованную историю и должна соответствовать правилам команды.

Выбор между merge и rebase определяется workflow проекта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Защищает ли отдельная ветка от интеграционных ошибок?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Ветка отделяет изменения в истории, но не доказывает их совместимость:

- с актуальной основной веткой;
- с другими задачами;
- с конфигурацией среды;
- с production-данными;
- с новой версией API.

Для проверки нужны:

- актуальная база;
- pipeline для предполагаемого результата merge;
- автоматические тесты;
- code review;
- проверка среды, близкой к production;
- наблюдение после deployment.

Чем дольше ветка изолирована, тем меньше результаты её собственного pipeline говорят о будущем совместном состоянии системы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>По каким признакам выбирать стратегию ветвления?</strong></summary>

<dl>
<dd>
<h2></h2>

Смотрят на:

- частоту релизов;
- длительность задач;
- число поддерживаемых версий;
- требования к согласованию;
- скорость CI;
- качество автоматических тестов;
- возможность использовать feature flags;
- продолжительность стабилизации;
- возможность быстро откатить deployment.

Если изменения поставляются ежедневно, короткие branches и trunk-based workflow обычно уменьшают задержку интеграции.

Если релизы проходят длительную стабилизацию, требуют отдельного согласования или выпускаются как фиксированные версии, release branches могут быть оправданы.

Если параллельно поддерживаются старые версии, дополнительно нужны tags и maintenance-ветки для соответствующих release-линий.

Название стратегии менее важно, чем реальные свойства процесса:

- насколько быстро код интегрируется;
- как проверяется предполагаемый результат merge;
- можно ли безопасно выпустить основную ветку;
- как выполняются исправление и откат.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Возможный workflow |
|---|---|
| Небольшой SaaS с частыми deployments | Короткие feature branches, trunk-based development и feature flags |
| Корпоративный продукт с релизным циклом | Release branches и отдельный этап стабилизации |
| Срочная production-ошибка | Hotfix от выпущенного commit или tag с переносом исправления в текущую разработку |
| Большой UI-проект | Маленькие MR снижают риск конфликтов в общих компонентах и маршрутах |
