## Вопрос

<br>

 💬 **Что такое public API в FSD и зачем нужны границы импортов?**

<h2></h2>

<br>
<dl>
<dd>

Public API, или публичный интерфейс, — это контракт между slice и использующим его кодом. Он определяет, какие компоненты, функции и типы разрешено использовать снаружи, и скрывает остальные детали реализации.

Обычно public API оформляют файлом `index.ts` в корне slice:

```ts
export { EditProfileForm } from "./ui/EditProfileForm";
export { useEditProfile } from "./model/useEditProfile";
export type { EditProfileFormValues } from "./model/types";
```

Import boundaries, или границы импортов, отделяют этот публичный контракт от внутренней реализации.

Например, импорт:

```ts
import { internalStore } from "@/features/auth/model/internal-store";
```

является deep import — обращением к внутреннему файлу другого slice в обход его публичного интерфейса.

Внешний код начинает зависеть от расположения файлов и устройства хранилища. После переименования файла, переноса логики или замены store придётся изменять всех потребителей.

Вместо этого внешний модуль импортирует только из публичной точки входа:

```ts
import { AuthForm } from "@/features/auth";
```

Внутри самого slice используют прямые относительные импорты между файлами:

```ts
import { validateCredentials } from "../model/validateCredentials";
```

Внутренний код не должен импортировать собственный slice через его `index.ts`. Такой импорт может создать цикл: public API импортирует внутренний файл, а внутренний файл через public API косвенно импортирует сам себя.

Публичный интерфейс является контрактом. Изменение экспортируемого поведения может потребовать правок у потребителей, а внутренние детали можно свободно рефакторить, пока контракт сохраняется.

Поэтому `export *` из всех файлов не создаёт полезной границы. Такой barrel скрывает настоящий контракт, случайно публикует внутренние детали и усложняет понимание доступных возможностей slice.

Public API должен быть минимальным, но достаточным. Если внешнему коду регулярно нужен закрытый экспорт, нужно проверить:

- действительно ли этот объект должен стать частью контракта;
- правильно ли выбрана ответственность slice;
- не пытается ли потребитель управлять внутренним устройством чужого модуля;
- не нужно ли вынести общую логику в другой slice или нижележащий layer.

Для крупных наборов независимых модулей в `shared/ui` и `shared/lib` обычно не создают один общий public API, который экспортирует всё. Каждый компонент или библиотека может иметь отдельную точку входа:

```ts
import { Button } from "@/shared/ui/button";
import { formatPrice } from "@/shared/lib/format-price";
```

Если модули одного slice предназначены для разных сред выполнения, например отдельно для server и client, для них могут быть созданы разные публичные точки входа. Это не позволяет клиентскому bundle случайно получить серверный код.

Границы не возникают автоматически после создания `index.ts`. Deep imports могут появляться из-за ручного кода или неправильного auto-import IDE, поэтому правила дополнительно проверяют на code review и архитектурным линтером.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что такое deep import?</strong></summary>

<dl>
<dd>
<h2></h2>

Deep import — импорт из внутреннего файла другого модуля в обход его публичной точки входа.

Например:

```ts
import { privateStore } from "@/features/auth/model/private-store";
```

Такой импорт раскрывает потребителю расположение и внутреннее устройство хранилища.

Импорт через public API:

```ts
import { AuthForm } from "@/features/auth";
```

оставляет детали реализации внутри feature.

Deep import не следует путать с любым импортом между slices одного layer. Осознанный cross-import иногда может проходить через официальный public API, но обращение к внутреннему файлу другого slice всё равно нарушает его границу.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Public API — это всегда barrel file?</strong></summary>

<dl>
<dd>
<h2></h2>

Не обязательно.

Barrel file — файл, который реэкспортирует значения из нескольких файлов. Он становится public API только тогда, когда выражает осознанный внешний контракт.

Barrel с `export *` для всего slice или layer может:

- скрывать реальные зависимости;
- случайно публиковать внутренние детали;
- способствовать циклическим импортам;
- ухудшать tree shaking и работу сборщика;
- замедлять dev server в большом проекте.

В обычном slice public API чаще всего оформляют одним корневым `index.ts`.

В `shared/ui` и `shared/lib`, где находятся независимые модули, отдельную точку входа обычно создают для каждого компонента или библиотеки:

```text
shared/ui/button/index.ts
shared/ui/text-field/index.ts
shared/lib/format-price/index.ts
```

Для разных сред выполнения также могут использоваться отдельные server/client entry points.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что можно экспортировать из среза?</strong></summary>

<dl>
<dd>
<h2></h2>

Экспортируют только объекты, необходимые потребителям slice:

- основные UI-компоненты;
- публичные операции;
- hooks;
- selectors;
- константы, являющиеся частью контракта;
- связанные публичные типы.

Вспомогательные компоненты, внутреннее состояние, приватные selectors, DTO и функции реализации не экспортируют, пока у них нет самостоятельного внешнего назначения.

Публичный тип также является частью контракта. Поэтому не следует экспортировать внутреннюю структуру state или API-ответ только потому, что TypeScript позволяет это сделать.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как технически контролировать границы импортов?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала команда фиксирует допустимые направления зависимостей и публичные точки входа.

Затем правила проверяют:

- на code review;
- через ESLint `no-restricted-imports`;
- с помощью плагинов архитектурных границ;
- специализированным FSD-линтером Steiger;
- проверкой циклических зависимостей в CI.

Path aliases делают импорты понятнее:

```ts
import { EditProfileForm } from "@/features/edit-profile";
```

Но aliases сами по себе ничего не запрещают. Без правил линтера остаётся возможным deep import:

```ts
import { privateStore } from "@/features/edit-profile/model/private-store";
```

Отдельно настраивают auto-import IDE, потому что редактор может автоматически выбрать внутренний файл вместо public API.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда deep import допустим?</strong></summary>

<dl>
<dd>
<h2></h2>

Между разными slices deep import не должен использоваться. Даже допустимый cross-import обязан проходить через явно опубликованный контракт, а не через внутренние `model`, `ui`, `api` или `lib`.

Временное нарушение во время миграции должно быть явно отмечено, ограничено и позднее удалено.

Для неизбежной связи двух business entities FSD предусматривает cross-import API через нотацию `@x`.

Например, если `entities/artist` требуется минимальная часть `entities/song`, сущность `song` может открыть специальный интерфейс:

```text
entities/song/@x/artist.ts
```

Код `entities/artist` импортирует только из этой точки:

```ts
import type { Song } from "@/entities/song/@x/artist";
```

Нотацию `@x` используют только на слое `entities`, минимально и как крайнюю меру. Сначала проверяют, не разделены ли сущности слишком мелко и нельзя ли устранить зависимость другим способом.

Это не разрешение на произвольные deep imports.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что значит, что абстракция модуля протекает?</strong></summary>

<dl>
<dd>
<h2></h2>

Это ситуация, когда для использования модуля приходится знать его внутреннее устройство.

Например, потребитель самостоятельно объединяет внутренний store, промежуточный hook и DTO feature вместо вызова одной публичной операции.

Формально public API может существовать, но детали реализации уже стали неявной частью контракта. В результате внутренний рефакторинг ломает внешний код.

Другие признаки протекающей абстракции:

- потребитель знает порядок внутренних вызовов;
- снаружи изменяется state чужого slice;
- наружу экспортируется DTO конкретного backend;
- один сценарий требует набора несвязанных приватных exports;
- изменение внутренней библиотеки требует правок во многих потребителях.

Решение — пересмотреть публичный контракт или ответственность slice, а не просто добавить ещё один случайный export.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

- Из `pages/profile` импортируют `features/edit-profile` через public API.
- Внутренний UI-компонент feature не импортируется снаружи, если он не является частью её публичного контракта.
- Внутри slice используются относительные импорты, а не импорт через собственный `index.ts`.
- Рефакторинг slice безопаснее, если внешний код зависит только от его публичного интерфейса.
- Для `shared/ui/button` используется отдельная точка входа вместо одного общего barrel всего UI-kit.
- Линтер запрещает импорты из внутренних `model`, `ui`, `api` и `lib` соседних slices.
