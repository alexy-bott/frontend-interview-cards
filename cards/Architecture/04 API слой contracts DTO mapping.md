## Вопрос

<br>

 💬 **Зачем во frontend нужен отдельный API-слой? Что такое API-контракт, DTO и mapping?**

<h2></h2>

<br>
<dl>
<dd>

API-слой отделяет сетевое взаимодействие от компонентов и бизнес-логики приложения. Компонент вызывает операцию вроде `getUser(id)` или использует сгенерированный hook RTK Query, но не собирает URL, заголовки и формат ответа самостоятельно.

Обычно в API-слое находятся базовый HTTP-клиент, адрес сервера, авторизация, описание endpoints, то есть операций API, типы запросов и ответов, отмена запросов, единый формат ошибок и преобразование данных. Кэширование, повторные запросы и инвалидацию может выполнять библиотека серверного состояния, например RTK Query; дублировать эти механизмы вручную поверх неё не нужно.

**API-контракт** - соглашение между клиентом и сервером: URL и HTTP-метод, параметры, тело запроса, коды ответа, структура успешных данных и ошибок. OpenAPI описывает этот контракт в машиночитаемом виде, а Swagger UI позволяет просматривать и вызывать описанные операции. Из OpenAPI можно генерировать TypeScript-типы и клиентский код.

**DTO** (Data Transfer Object, объект передачи данных) - структура, в которой данные передаются через API. Внутренняя модель приложения может отличаться от DTO. Например, сервер возвращает `{ first_name, created_at }`, а UI работает с `{ firstName, createdAt: Date }`.

**Mapping**, или преобразование данных, переводит DTO во внутреннюю модель и обратно. Благодаря этому `snake_case`, поля, допускающие `null`, и технические значения backend не распространяются по компонентам. При изменении контракта основная правка остаётся в типах и преобразователе API-слоя.

Сгенерированный TypeScript-тип не проверяет реальный ответ во время выполнения. Сервер, proxy-сервер или старая версия API могут вернуть другую структуру. Для критичных или ненадёжных данных применяют runtime validation - проверку фактического значения во время работы программы, например библиотекой схем Zod. Проверять каждый ответ необязательно: решение зависит от доверия к API и последствий ошибочных данных.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему не стоит вызывать <code>fetch</code> прямо из любого компонента?</strong></summary>

<dl>
<dd>
<h2></h2>

Тогда компоненты начинают дублировать адрес сервера, заголовки, авторизацию, преобразование данных и обработку ошибок. Их труднее тестировать, а изменение контракта приходится исправлять во многих местах. Сам `fetch` не является проблемой: важно, чтобы сетевые правила были сосредоточены за понятным интерфейсом, а не повторялись в UI.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое API-контракт?</strong></summary>

<dl>
<dd>
<h2></h2>

API-контракт описывает, как клиент вызывает сервер и какой результат получает: URL, HTTP-метод, query-параметры или тело запроса, схему ответа, коды статуса и формат ошибки. Если контракт не зафиксирован и не синхронизирован, расхождения обнаруживаются только во время интеграции или уже во время выполнения приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем преобразовывать DTO во внутреннюю модель приложения?</strong></summary>

<dl>
<dd>
<h2></h2>

Backend может отдавать `snake_case`, поля со значением `null`, технические флаги или вложенность, неудобную интерфейсу. Mapping преобразует их в стабильную модель приложения. Например, неизвестный статус можно явно обработать в одном преобразователе, а не добавлять одинаковые проверки во все компоненты.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где хранить API-тип?</strong></summary>

<dl>
<dd>
<h2></h2>

Типы запроса и ответа хранят рядом с endpoint либо генерируют из OpenAPI. Если DTO полностью совпадает с потребностями приложения, отдельная модель не нужна. Разделять их следует тогда, когда backend-формат нестабилен, содержит транспортные детали или требует преобразования.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать, если изменился контракт backend?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала обновляют описание контракта и сгенерированные типы, затем исправляют преобразование DTO, обработку новых статусов и затронутые сценарии интерфейса. Контрактные или интеграционные тесты помогают обнаружить несовпадение раньше. Граница API-слоя уменьшает число мест, которые зависят от транспортного формата напрямую.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Гарантирует ли codegen из OpenAPI, что backend всегда вернёт правильные данные?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Codegen, то есть генерация клиентского кода, строится по описанию ожидаемого контракта, а не по фактическому ответу. На сервере может оказаться другая версия, поле может прийти как `null`, а proxy-сервер - вернуть HTML вместо JSON. В критичных местах фактические данные проверяют во время выполнения и обрабатывают несовпадение как отдельную ошибку, не позволяя ему превратиться в случайное падение UI.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

- RTK Query `createApi` описывает endpoints и cache tags.
- OpenAPI используется для генерации типов запросов и ответов.
- Поле DTO `created_at` преобразуется во внутреннее поле `createdAt`.
- Компонент получает подготовленную модель, а не сырой ответ backend.
- Ошибка API преобразуется в единый формат для форм и уведомлений.
- Runtime validation, то есть проверка данных во время выполнения, обнаруживает неожиданный ответ до падения UI на `undefined`.
