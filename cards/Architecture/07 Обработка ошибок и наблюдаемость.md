## Вопрос

<br>

 💬 **Как во frontend организовать обработку ошибок и observability?**

<h2></h2>

<br>
<dl>
<dd>

Обработка ошибок определяет, как приложение реагирует на сбой, восстанавливается после него и что видит пользователь.

Ожидаемую ошибку формы можно показать рядом с полем, недоступный ресурс — отдельным состоянием страницы, временный сетевой сбой — кнопкой повторной попытки, а падение части React-дерева — изолировать с помощью Error Boundary и резервного интерфейса.

Ошибки полезно разделять по происхождению:

- **ошибки сценария** — валидация, отсутствие доступа, ненайденный ресурс;
- **транспортные ошибки** — отсутствие сети, timeout, недоступность сервера;
- **ошибки программирования** — обращение к `undefined`, нарушение инварианта, ошибка рендеринга;
- **ошибки загрузки ресурсов** — недоступный script, stylesheet или JavaScript chunk.

**Observability**, или наблюдаемость, — способность понять внутреннее состояние и причины поведения системы по собранной телеметрии.

Основные сигналы:

- **logs**, или логи, — записи об отдельных событиях и их контексте;
- **metrics**, или метрики, — числовые показатели во времени, например доля ошибок, crash-free sessions или длительность загрузки;
- **traces**, или трассировки, — связанный путь операции через frontend, gateway и backend.

**Breadcrumbs**, или цепочка событий, являются дополнительным контекстом конкретной ошибки: последние переходы, клики, запросы и изменения значимого состояния перед сбоем.

К событию могут добавляться:

- версия release;
- environment;
- маршрут;
- тип и версия браузера;
- идентификатор запроса или trace;
- значения важных feature flags;
- допустимый идентификатор сессии или пользователя.

Контекст должен собираться осознанно. Пароли, токены, cookie, платёжные данные, содержимое полей формы и другие чувствительные значения фильтруют до отправки в monitoring.

Source maps, или карты исходного кода, позволяют сопоставить минифицированный stack trace с исходным файлом и строкой.

Source map должна соответствовать точной версии release. Обычно её загружают в сервис мониторинга отдельно и не публикуют вместе с production-статикой без необходимости.

Ошибки обрабатывают на подходящем уровне.

Ожидаемые ошибки API, валидации и прав доступа являются частью пользовательского сценария и обрабатываются рядом с ним.

Неожиданные JavaScript-ошибки, необработанные Promise rejection, ошибки загрузки chunk и проблемы hydration регистрируют в monitoring с техническим контекстом.

Крупные независимые области React-интерфейса изолируют Error Boundary, чтобы сбой одного виджета не уничтожил всю страницу.

На уровне браузера события `error` и `unhandledrejection` могут использоваться как последняя линия регистрации необработанных сбоев. Они не заменяют обработку ошибки в месте, где приложение понимает её смысл и может предложить пользователю правильное восстановление.

Monitoring должен группировать одинаковые ошибки и ограничивать объём отправки через sampling или rate limiting. Иначе один повторяющийся сбой может создать тысячи одинаковых событий и скрыть другие проблемы.

Пользователю нужен следующий безопасный шаг:

- повторить запрос;
- обновить страницу;
- вернуться назад;
- открыть другой раздел;
- сохранить или не потерять введённые данные.

Автоматически повторять следует только временные ошибки и с ограничением числа попыток. Между попытками обычно увеличивают задержку и учитывают серверный заголовок `Retry-After`, если он предоставлен.

Повтор `POST` или другой изменяющей операции без гарантии идемпотентности может создать дубликат. Для безопасного повтора backend может поддерживать idempotency key — уникальный ключ операции, по которому повторный запрос не создаёт второй результат.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что такое Error Boundary?</strong></summary>

<dl>
<dd>
<h2></h2>

Error Boundary — React-компонент, который перехватывает ошибку во время рендеринга дочернего React-дерева и вместо упавшего участка показывает резервный UI.

Он также может зарегистрировать ошибку вместе с React component stack.

Error Boundary не перехватывает:

- ошибки обработчиков событий;
- произвольные асинхронные callback;
- ошибки `setTimeout`;
- необработанные Promise rejection;
- ошибки серверного рендеринга;
- ошибки загрузки JavaScript chunk;
- ошибки в самом boundary.

Такие сбои обрабатывают в месте вызова или регистрируют другими средствами monitoring.

Boundary размещают вокруг независимых областей интерфейса. Один глобальный boundary защищает от полного белого экрана, а более локальные boundaries позволяют сохранить рабочими остальные части страницы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем expected error отличается от unexpected error?</strong></summary>

<dl>
<dd>
<h2></h2>

Expected error, или ожидаемая ошибка, предусмотрена контрактом сценария: неверный пароль, ошибка валидации, отсутствие доступа или ненайденный ресурс.

Для неё проектируют конкретное состояние интерфейса и понятный следующий шаг пользователя. Такая ошибка не обязательно означает дефект приложения.

Unexpected error — непредусмотренный сбой, например обращение к `undefined`, нарушение внутреннего инварианта или падение рендеринга.

Его регистрируют с техническим контекстом, изолируют и показывают нейтральный безопасный сценарий восстановления.

Один HTTP-статус не всегда однозначно определяет категорию. Например, `404` может быть ожидаемым результатом поиска ресурса или признаком неверно сформированного URL приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем monitoring отличается от observability?</strong></summary>

<dl>
<dd>
<h2></h2>

Monitoring, или мониторинг, следит за заранее известными показателями и условиями.

Например:

- выросла доля JavaScript-ошибок;
- снизилось число crash-free sessions;
- увеличилось время загрузки;
- после нового release появились ошибки определённого типа.

Monitoring обычно включает dashboards и alerts по заранее выбранным метрикам.

Observability, или наблюдаемость, шире: по логам, метрикам, трассировкам и связанному контексту она позволяет исследовать ранее неизвестную проблему и понять, при каких действиях, версии, флаге и backend-запросе она возникла.

Monitoring сообщает, что известный показатель ухудшился. Observability помогает исследовать, почему это произошло.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое breadcrumb в monitoring?</strong></summary>

<dl>
<dd>
<h2></h2>

Breadcrumb — краткая запись события перед ошибкой:

- переход по маршруту;
- клик по значимой кнопке;
- начало и завершение API-запроса;
- изменение feature flag;
- изменение важного состояния сценария.

Последовательность таких записей помогает понять действия, которые предшествовали сбою.

Breadcrumb не должен превращаться в запись всего поведения пользователя. Полные значения полей формы, токены, персональные данные и чувствительные payload в него не включают.

Чтобы не создавать лишний шум, сохраняют только диагностически значимые события и ограничивают длину цепочки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужны source maps в production monitoring?</strong></summary>

<dl>
<dd>
<h2></h2>

Production-сборка обычно минифицирована: имена и расположение кода изменены, поэтому stack trace указывает на малопонятные координаты в собранном файле.

Source map хранит соответствие между собранным и исходным кодом. Сервис monitoring использует её, чтобы показать исходный файл, функцию и строку ошибки.

Важно связать source map с точной версией release. Карта от другой сборки может показать неверное место ошибки.

Source maps обычно загружают непосредственно в monitoring-сервис во время CI/CD. Публично раздавать их пользователям необязательно.

Если карта содержит исходный код через `sourcesContent`, её доступ и хранение также нужно рассматривать с точки зрения безопасности.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что нельзя логировать на frontend?</strong></summary>

<dl>
<dd>
<h2></h2>

Нельзя без необходимости отправлять:

- пароли;
- access- и refresh-токены;
- cookie;
- секретные заголовки;
- платёжные данные;
- полные payload с персональными сведениями;
- содержимое полей формы;
- URL с чувствительными query-параметрами.

Данные фильтруют до отправки, а не только скрывают при отображении в dashboard.

Доступ к monitoring, срок хранения данных и возможность связать событие с конкретным человеком также ограничивают.

Идентификатор пользователя или сессии добавляют только в допустимой форме и при наличии реальной диагностической необходимости.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужны <code>error</code> и <code>unhandledrejection</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Глобальное событие `error` позволяет зарегистрировать необработанную JavaScript-ошибку, которая дошла до уровня браузера.

Событие `unhandledrejection` сообщает о Promise, для которого к моменту проверки не был установлен обработчик отклонения.

Эти события используют как последнюю линию monitoring:

```ts
window.addEventListener("error", event => {
  reportError(event.error);
});

window.addEventListener("unhandledrejection", event => {
  reportError(event.reason);
});
```

Перед отправкой значение нормализуют, потому что `throw` или Promise rejection технически могут содержать не только экземпляр `Error`.

Глобальные обработчики не знают контекст пользовательского сценария и обычно не могут правильно восстановить UI. Поэтому ожидаемые ошибки по-прежнему обрабатывают локально через `try/catch`, результат запроса или состояние библиотеки server state.

Один и тот же сбой может попасть в monitoring несколькими путями, поэтому события группируют и защищают от повторной отправки.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

- Error Boundary вокруг dashboard показывает fallback вместо белого экрана.
- API validation errors преобразуются в ошибки конкретных полей формы.
- Временный сетевой сбой предлагает повторить запрос, не очищая введённые данные.
- Chunk load error предлагает один контролируемый reload после нового deploy.
- Monitoring связывает ошибку с release version, route, feature flag и trace ID.
- `error` и `unhandledrejection` регистрируют сбои, которые не были обработаны раньше.
- Source maps загружаются в monitoring-сервис отдельно от production-статики.
- Логи и breadcrumbs очищаются от токенов и чувствительных полей.
