## Вопрос

<br>

 💬 **Зачем во frontend нужен отдельный API-слой? Что такое API-контракт, DTO и mapping?**

<h2></h2>

<br>
<dl>
<dd>

API-слой отделяет сетевое взаимодействие от компонентов и бизнес-логики приложения. Компонент вызывает операцию вроде `getUser(id)` или использует сгенерированный hook RTK Query, но не собирает URL, заголовки и формат ответа самостоятельно.

API-слой — это логическая граница, а не обязательно одна глобальная папка или отдельный слой FSD.

Например:

- общий HTTP-клиент, базовый URL и добавление токена могут находиться в `shared/api`;
- запросы пользователя — в `entities/user/api`;
- запрос отправки формы — в `features/edit-profile/api`.

Так транспортная инфраструктура переиспользуется, а предметные операции остаются рядом с отвечающим за них модулем.

Обычно за API-границей находятся:

- базовый HTTP-клиент;
- адрес сервера;
- добавление авторизационных заголовков;
- сериализация запроса и разбор ответа;
- описание endpoints, то есть операций API;
- типы запросов и ответов;
- отмена запросов;
- преобразование успешных данных и ошибок;
- runtime validation там, где она необходима.

Кэширование, дедупликацию запросов, повторные запросы, подписки и инвалидацию может выполнять библиотека серверного состояния, например RTK Query. Дублировать эти механизмы вручную поверх неё не нужно.

RTK Query позволяет выполнять mapping успешного ответа через `transformResponse`, а ошибки — через `transformErrorResponse` до того, как соответствующие данные будут предоставлены потребителям.

**API-контракт** — соглашение между клиентом и сервером. Оно может описывать:

- URL и HTTP-метод;
- path- и query-параметры;
- заголовки и авторизацию;
- формат тела запроса;
- content type;
- коды ответа;
- структуру успешных данных и ошибок;
- правила сортировки и пагинации.

OpenAPI описывает HTTP API в машиночитаемом виде. Swagger UI — один из инструментов, который отображает такое описание и позволяет интерактивно вызывать доступные операции.

Из OpenAPI можно генерировать TypeScript-типы и клиентский код.

**DTO** (Data Transfer Object, объект передачи данных) — структура, в которой данные передаются через границу API. DTO могут описывать как ответ сервера, так и отправляемый запрос.

Внутренняя модель приложения может отличаться от DTO. Например, сервер возвращает:

```ts
type UserResponseDto = {
  first_name: string;
  created_at: string;
};
```

А приложение работает с моделью:

```ts
type User = {
  firstName: string;
  createdAt: string;
};
```

**Mapping**, или преобразование данных, переводит DTO во внутреннюю модель и обратно:

```ts
function mapUserDto(dto: UserResponseDto): User {
  return {
    firstName: dto.first_name,
    createdAt: dto.created_at,
  };
}
```

Обратный mapper может преобразовать данные формы или внутреннюю модель в request DTO, который ожидает backend.

Благодаря этому `snake_case`, транспортная вложенность, поля, допускающие `null`, и технические значения backend не распространяются по компонентам.

Если меняется только транспортный формат, основную правку можно локализовать в типах и mapper. Если изменился смысл данных или поведение API, затронутые пользовательские сценарии тоже придётся пересмотреть.

Если преобразованный результат сохраняется в Redux или кэше RTK Query, его желательно оставлять сериализуемым. Например, дату можно хранить как ISO-строку или timestamp, а экземпляр `Date` создавать только там, где он действительно нужен.

Сгенерированный TypeScript-тип не проверяет реальный ответ во время выполнения. TypeScript удаляет типы при компиляции, поэтому сервер, proxy-сервер или старая версия API могут вернуть другую структуру.

Для критичных или ненадёжных данных применяют runtime validation — проверку фактического значения во время выполнения с помощью схемы.

RTK Query поддерживает проверку:

- аргументов запроса;
- сырого ответа до mapping;
- результата после mapping;
- ошибок API.

Например, сырой DTO можно проверить через `rawResponseSchema`, преобразовать через `transformResponse`, а итоговую модель при необходимости проверить через `responseSchema`.

Проверять каждый ответ необязательно. Решение зависит от доверия к API, внешнего источника данных и последствий несовпадения контракта.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему не стоит вызывать <code>fetch</code> прямо из любого компонента?</strong></summary>

<dl>
<dd>
<h2></h2>

Тогда компоненты начинают дублировать адрес сервера, заголовки, авторизацию, преобразование данных и обработку ошибок.

Их труднее тестировать, а изменение контракта приходится исправлять во многих местах. Компонент также начинает одновременно отвечать за UI и транспортные детали.

Сам `fetch` не является проблемой. Важно, чтобы правила сетевого взаимодействия были сосредоточены за понятным интерфейсом, а не повторялись в UI.

При этом необязательно создавать один глобальный файл со всеми запросами. Общий клиент можно переиспользовать, а предметные endpoints хранить рядом с соответствующими entities и features.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое API-контракт?</strong></summary>

<dl>
<dd>
<h2></h2>

API-контракт описывает, как клиент вызывает сервер и какой результат получает:

- URL и HTTP-метод;
- параметры и тело запроса;
- обязательные заголовки;
- авторизацию;
- коды статуса;
- схему успешного ответа;
- формат ошибки;
- правила пагинации, сортировки и фильтрации.

Если контракт не зафиксирован и не синхронизирован, расхождения обнаруживаются только во время интеграции или выполнения приложения.

OpenAPI позволяет хранить контракт в машиночитаемом виде, проверять его и использовать для генерации документации, типов и клиента.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем преобразовывать DTO во внутреннюю модель приложения?</strong></summary>

<dl>
<dd>
<h2></h2>

Backend может отдавать `snake_case`, поля со значением `null`, технические флаги или вложенность, неудобную интерфейсу.

Mapping преобразует их в стабильную модель приложения. Например, неизвестный статус можно явно обработать в одном mapper, а не добавлять одинаковые проверки во все компоненты.

Преобразование может выполняться в обе стороны:

- response DTO преобразуется во внутреннюю модель;
- данные приложения преобразуются в request DTO.

В RTK Query mapping успешного ответа можно выполнить через `transformResponse`.

Если результат помещается в Redux state или кэш RTK Query, следует учитывать сериализуемость. ISO-строка или числовой timestamp обычно безопаснее экземпляра `Date`.

Отдельная внутренняя модель нужна не всегда. Если DTO уже полностью соответствует потребностям приложения и не раскрывает нежелательные транспортные детали, дополнительный mapper может не принести пользы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где хранить API-тип?</strong></summary>

<dl>
<dd>
<h2></h2>

Типы запроса и ответа хранят рядом с соответствующим endpoint либо генерируют из OpenAPI.

Например:

```text
entities/user/api/get-user.ts
entities/user/api/types.ts
```

Сгенерированные DTO можно хранить отдельно от ручных внутренних моделей, чтобы обновление codegen не перезаписало прикладные типы.

Если DTO полностью совпадает с потребностями приложения, отдельная модель не нужна.

Разделять DTO и внутреннюю модель следует, когда backend-формат:

- содержит транспортные детали;
- использует другую структуру или названия;
- допускает значения, которые UI не должен обрабатывать напрямую;
- часто изменяется независимо от пользовательского сценария;
- требует преобразования перед использованием.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать, если изменился контракт backend?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала определяют характер изменения: совместимое оно или breaking change, то есть ломает существующих потребителей.

Затем:

- обновляют OpenAPI или другое описание контракта;
- обновляют сгенерированные типы и клиент;
- исправляют DTO и mapping;
- обрабатывают новые статусы и ошибки;
- проверяют затронутые пользовательские сценарии;
- запускают контрактные и интеграционные тесты.

Если изменился только транспортный формат, API-граница уменьшает число затронутых мест.

Если изменилась семантика операции, например значение статуса или обязательность пользовательского действия, одной правки mapper недостаточно — потребуется изменить соответствующий сценарий интерфейса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Гарантирует ли codegen из OpenAPI, что backend всегда вернёт правильные данные?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Codegen строится по описанию ожидаемого контракта, а не проверяет каждый фактический ответ сервера.

На сервере может оказаться другая версия, поле может прийти как `null`, а proxy-сервер — вернуть HTML вместо ожидаемого JSON.

TypeScript-типы существуют только во время разработки и удаляются из итогового JavaScript.

В критичных местах фактические данные проверяют во время выполнения и обрабатывают несовпадение как отдельную ошибку, не позволяя ему превратиться в случайное падение UI.

В актуальном RTK Query для этого можно использовать схемы endpoint, например `rawResponseSchema` или `responseSchema`. Сама схема при этом должна реально выполняться во время работы программы.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

- RTK Query `createApi` описывает endpoints и cache tags.
- OpenAPI используется для генерации типов запросов и ответов.
- Общий HTTP-клиент находится в `shared/api`, а предметный endpoint — рядом с entity или feature.
- Поле DTO `created_at` преобразуется во внутреннее поле `createdAt`.
- Компонент получает подготовленную модель, а не сырой ответ backend.
- Ошибка API преобразуется в единый формат для форм и уведомлений.
- Runtime validation обнаруживает неожиданный ответ до падения UI на `undefined`.
- ISO-строка даты хранится в кэше, а объект `Date` создаётся только при необходимости отображения или вычисления.
