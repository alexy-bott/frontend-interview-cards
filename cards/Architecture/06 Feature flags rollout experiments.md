## Вопрос

<br>

 💬 **Что такое feature flags и зачем они нужны во frontend?**

<h2></h2>

<br>
<dl>
<dd>

Feature flag, или функциональный флаг, — управляемый переключатель, который выбирает одну из веток поведения приложения.

Флаг может быть логическим (`true`/`false`) или выбирать один из нескольких вариантов и конфигураций. Его значение может зависеть от пользователя, роли, организации, окружения, региона или группы эксперимента.

Флаги разделяют **deploy** и **release**.

Deploy означает доставку кода в окружение, а release — предоставление возможности пользователям. Код можно развернуть заранее, затем включить для сотрудников, 5% аудитории и после проверки расширить доступ. Такое постепенное включение называется **rollout**.

Нужно различать два способа управления флагом:

- **build-time flag** вычисляется во время сборки и для изменения обычно требует новой сборки и deploy;
- **runtime flag** загружается или вычисляется во время работы приложения и может переключаться без новой сборки.

Значение runtime flag может вычисляться на backend, edge-сервере или во frontend. Независимо от места вычисления все части системы должны использовать согласованные правила и один контекст пользователя.

Для процентного rollout пользователь должен стабильно попадать в одну группу. Обычно сервис вычисляет вариант детерминированно из стабильного идентификатора пользователя и ключа флага.

Для анонимного пользователя может использоваться отдельный идентификатор, сохранённый, например, в cookie. После авторизации нужно заранее определить, сохранится ли прежний вариант или распределение будет пересчитано по идентификатору аккаунта.

Если выбирать ветку случайно при каждом открытии страницы, интерфейс будет переключаться между вариантами, а результаты эксперимента станут недостоверными.

Rollout и A/B-эксперимент могут использовать одинаковый механизм распределения, но решают разные задачи.

Rollout снижает технический риск выпуска: команда постепенно расширяет аудиторию и наблюдает ошибки, производительность и стабильность.

A/B-эксперимент проверяет продуктовую гипотезу. Флаг стабильно делит аудиторию на варианты, а аналитика сравнивает заранее выбранную основную метрику, например завершение оформления заказа.

Для корректного эксперимента важно фиксировать не только назначенный вариант, но и фактический показ пользователю — exposure event. Иначе в анализ могут попасть пользователи, которые были распределены в группу, но не увидели экспериментальный интерфейс.

До запуска определяют:

- основную метрику успеха;
- защитные метрики, которые не должны ухудшиться;
- целевую аудиторию;
- правила распределения;
- длительность или условия завершения.

Нельзя менять условия распределения во время эксперимента или трактовать любую выросшую метрику как успех без учёта исходной гипотезы.

Флаги бывают временными и долгоживущими.

Флаг релиза удаляют вместе со старой веткой после полного включения. Операционный флаг, или **kill switch**, сохраняют, если возможность нужно экстренно отключать.

У каждого временного флага должны быть:

- владелец;
- назначение;
- безопасное значение по умолчанию;
- ожидаемая дата удаления;
- проверка обеих веток;
- метрики или критерии завершения rollout.

Иначе условные блоки постепенно усложняют код, тесты и понимание системы.

Нужно заранее определить поведение при недоступности сервиса флагов. Приложение может использовать безопасное значение по умолчанию или последнюю успешно загруженную конфигурацию.

Frontend-флаг не является средством авторизации.

Пользователь может изменить клиентский код, подменить значение флага или отправить запрос напрямую. Поэтому доступ к данным и операциям обязан независимо проверять backend.

Флаг управляет интерфейсом, но не заменяет серверную проверку прав.

Выключенная ветка также может оставаться в загруженном JavaScript bundle. Feature flag сам по себе не скрывает код, не обеспечивает секретность и не уменьшает размер загрузки. Для этого отдельно применяют разделение bundle и условную загрузку модулей.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем deploy отличается от release?</strong></summary>

<dl>
<dd>
<h2></h2>

Deploy — доставка версии приложения в окружение.

Release — момент, когда новая возможность становится доступна целевой аудитории.

Feature flag позволяет выполнить deploy заранее, а затем управляемо выполнить release без новой сборки, если используется runtime-конфигурация флагов.

Build-time flag такого разделения полностью не даёт: для изменения его значения обычно требуется новая сборка и повторный deploy.

Развёрнутую выключенную ветку можно проверять для внутренней аудитории или отдельных тестовых пользователей до общего release.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое rollout?</strong></summary>

<dl>
<dd>
<h2></h2>

Rollout — постепенное расширение аудитории feature:

```text
сотрудники → 5% → 25% → 50% → 100%
```

На каждом этапе наблюдают:

- ошибки;
- производительность;
- нагрузку на backend;
- обращения пользователей;
- продуктовые и защитные метрики.

Распределение должно быть стабильным, чтобы один пользователь не видел разные варианты при соседних запросах.

Обычно пользователю назначают постоянный диапазон через детерминированный hash от идентификатора и ключа флага. При увеличении процента новая аудитория добавляется к уже включённой, а ранее назначенные пользователи не должны случайно менять вариант.

Rollout не обязательно является экспериментом. Его целью может быть только ограничение технического риска.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое kill switch?</strong></summary>

<dl>
<dd>
<h2></h2>

Kill switch — операционный флаг для экстренного отключения конкретного поведения без отката всего приложения.

Например, можно выключить новый checkout или тяжёлый виджет, сохранив остальные изменения текущего релиза.

Для его работы заранее предусматривают:

- безопасную альтернативную ветку;
- доступ к управлению флагом;
- быстрое распространение новой конфигурации;
- безопасное значение при недоступности сервиса;
- наблюдаемость результата переключения.

Если приложение не может получить конфигурацию флага, kill switch может не сработать. Поэтому для критичных случаев используют кэш последней конфигурации, безопасный fallback и отдельный план rollback.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем kill switch отличается от rollback?</strong></summary>

<dl>
<dd>
<h2></h2>

Rollback возвращает предыдущую версию сборки и отменяет все вошедшие в неё изменения.

Kill switch оставляет текущую версию в production, но через runtime-конфигурацию выбирает безопасную ветку одной возможности.

Он действует точечно и обычно быстрее, однако не поможет:

- при ошибке загрузки приложения;
- при синтаксической ошибке в bundle;
- в коде, который падает до получения конфигурации;
- при недоступности самого механизма флагов;
- если безопасная ветка больше не работает.

Поэтому kill switch дополняет rollback, но не заменяет его.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем флаг A/B-эксперимента отличается от обычного флага релиза?</strong></summary>

<dl>
<dd>
<h2></h2>

Флаг релиза ограничивает технический риск выкладки и постепенно доводит одну версию до всей аудитории.

Эксперимент одновременно сохраняет несколько вариантов, стабильно распределяет пользователей и связывает фактический показ варианта с заранее выбранной продуктовой метрикой.

Для эксперимента важны:

- неизменное распределение;
- регистрация exposure event;
- достаточный объём данных;
- заранее выбранная основная метрика;
- защитные метрики;
- корректное завершение анализа.

После получения результата эксперимент завершают, оставляют выбранную реализацию и удаляют остальные ветки.

Обычный rollout можно остановить из-за технических ошибок без статистического сравнения продуктовых вариантов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что нужно учитывать при флагах во frontend?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно определить безопасное значение по умолчанию и поведение до загрузки конфигурации.

При SSR сервер и браузер должны вычислить одинаковый вариант. Для этого им нужны согласованные:

- идентификатор пользователя;
- его атрибуты;
- ключ флага;
- версия конфигурации;
- правила распределения.

Иначе возможны hydration mismatch и скачок интерфейса после загрузки клиентского JavaScript.

Конфигурацию или уже вычисленные значения флагов можно передать браузеру вместе с серверным результатом, чтобы первая клиентская отрисовка использовала тот же snapshot.

Также необходимо:

- проверять обе ветки;
- собирать ошибки и метрики отдельно по вариантам;
- не использовать клиентский флаг как защиту доступа;
- учитывать состояние загрузки конфигурации;
- избегать случайного переключения варианта;
- заранее планировать удаление временного условия;
- проверять, не попадает ли выключенный код в основной bundle без необходимости.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли прятать секретную бизнес-логику за frontend flag?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Frontend-код и значения клиентских флагов доступны пользователю.

Скрытая кнопка не запрещает вручную отправить запрос, поэтому backend независимо проверяет право на операцию и доступ к данным.

Даже выключенную ветку нельзя считать секретной, если её код уже попал в загружаемую сборку. Пользователь может изучить bundle, source map, сетевые запросы и конфигурацию флагов.

Если код не должен загружаться до включения feature, его выносят в отдельный модуль и загружают условно. Но даже это является оптимизацией доставки, а не механизмом авторизации или хранения секретов.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

- Новый checkout включают только для части пользователей.
- В Next.js сервер и браузер используют один snapshot флагов, чтобы не возникло расхождения при hydration.
- Feature деплоится в production, но скрыта до согласования продукта.
- Проблемный виджет отключают через kill switch.
- A/B-тест регистрирует вариант и событие фактического показа.
- При недоступности сервиса флагов используется безопасная сохранённая конфигурация.
- После полного rollout удаляют старую ветку кода и сам временный флаг.
