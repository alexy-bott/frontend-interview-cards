## Вопрос

<br>

 💬 **Что такое shared UI и design system во frontend? Какую роль может играть Radix UI?**

<h2></h2>

<br>
<dl>
<dd>

**Shared UI** — общая библиотека интерфейсных компонентов приложения: кнопок, полей ввода, диалоговых окон, выпадающих меню и вкладок.

Такие компоненты не знают о конкретном заказе, пользователе или бизнес-сценарии. Они предоставляют стабильный внешний интерфейс, единое поведение и стили для продуктовых компонентов.

Shared UI может содержать общее UI-поведение, например управление визуальными состояниями, фокусом или размером компонента. Но он не должен принимать решения, относящиеся к предметной области: проверять права на удаление заказа, самостоятельно загружать пользователя или знать статусы конкретного бизнес-процесса.

**Design system**, или дизайн-система, шире библиотеки компонентов. В неё входят:

- правила визуального языка;
- design tokens;
- компоненты;
- шаблоны взаимодействия;
- требования доступности;
- документация;
- правила версионирования и развития системы.

**Design tokens**, или дизайн-токены, — именованные значения цветов, отступов, типографики и других параметров, например `color-text-danger`.

Они позволяют менять тему и визуальные решения системно, а не искать конкретный цвет или размер по всему CSS.

**Radix UI Primitives** — низкоуровневые React-компоненты без готового визуального оформления для сложных элементов: `Dialog`, `DropdownMenu`, `Select`, `Tooltip`, `Tabs`.

Radix реализует значительную часть общего поведения таких компонентов:

- ожидаемые WAI-ARIA-паттерны;
- управление фокусом;
- навигацию с клавиатуры;
- необходимые роли и ARIA-атрибуты;
- controlled и uncontrolled режимы там, где компонент имеет управляемое состояние;
- portal и композицию отдельных частей компонента.

Controlled-компонент получает текущее состояние и обработчик его изменения снаружи. Uncontrolled-компонент хранит состояние внутри и принимает начальное значение.

Radix не является готовой дизайн-системой. Команда сама задаёт:

- стили;
- design tokens;
- визуальные варианты;
- содержимое;
- адаптивность;
- правила композиции;
- публичный API компонентов.

Доступность тоже не появляется автоматически. Radix предоставляет корректную основу, но разработчик должен передать понятные подписи, сохранить семантику элементов и проверить итоговый сценарий с клавиатурой и программой чтения с экрана (screen reader).

Например, `Dialog.Title` и доступное описание должны соответствовать содержимому конкретного диалога, а trigger должен оставаться семантически интерактивным элементом.

Компоненты shared UI должны сохранять контракт нативных HTML-элементов.

Если `Button` рендерит `<button>`, он должен поддерживать:

- `type="button" | "submit" | "reset"`;
- `disabled`;
- обработчики событий;
- `aria-*`;
- `data-*`;
- `ref`.

Для общего `Button` безопасным значением по умолчанию обычно является `type="button"`, потому что нативный `<button>` без явно заданного `type` внутри формы может отправить её. При этом потребитель должен иметь возможность передать `type="submit"` или `type="reset"`.

Нельзя занимать prop `type` под визуальный вариант `primary`: это нарушит нативный контракт кнопки. Для внешнего вида используют отдельные props, например `variant`, `size` и `tone`.

Обёртка над Radix также не должна без необходимости раскрывать его внутреннее устройство. Продуктовый код должен зависеть от стабильного контракта shared UI, а не от того, какие именно части Radix использованы внутри.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем headless/unstyled component отличается от готового компонента?</strong></summary>

<dl>
<dd>
<h2></h2>

Headless, или unstyled component, предоставляет структуру, состояние и поведение, но не навязывает внешний вид конкретной дизайн-системы.

Готовый компонент уже содержит визуальный дизайн, стили и варианты использования определённого продукта или библиотеки.

Radix относится к unstyled primitives: он предоставляет основу поведения и доступности сложного элемента, а CSS, design tokens и визуальные варианты создаёт команда.

Unstyled не означает отсутствие DOM-структуры или поведения. Primitive может создавать элементы, управлять состоянием, фокусом и ARIA-атрибутами, оставаясь визуально неоформленным.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему dialog или select сложно писать самому?</strong></summary>

<dl>
<dd>
<h2></h2>

Модальный dialog должен:

- перевести фокус внутрь после открытия;
- удерживать клавиатурную навигацию внутри активного окна;
- закрываться по `Escape`;
- блокировать взаимодействие с фоном;
- иметь доступное имя;
- возвращать фокус на подходящий элемент после закрытия.

Select должен поддерживать навигацию с клавиатуры, выбор элемента, доступные роли и typeahead — переход к подходящему варианту по вводимым символам.

Radix Select не является обычным текстовым input или полноценным autocomplete: пользователь выбирает значение из заранее заданного списка.

Кроме того, сложным компонентам могут понадобиться:

- controlled и uncontrolled режимы;
- portal, который рендерит всплывающий слой в другом узле DOM;
- позиционирование;
- обработка прокрутки;
- взаимодействие с формой.

Пропуск одного из этих требований легко делает компонент неудобным или недоступным.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое <code>asChild</code> в Radix?</strong></summary>

<dl>
<dd>
<h2></h2>

По умолчанию primitive Radix создаёт собственный HTML-элемент.

`asChild` просит его использовать единственный дочерний React-элемент вместо своей обёртки и передать ему необходимые props, обработчики и `ref`.

Это позволяет, например, использовать существующую ссылку как trigger без дополнительного DOM-элемента:

```tsx
<Dialog.Trigger asChild>
  <a href="/settings">Открыть настройки</a>
</Dialog.Trigger>
```

Дочерний React-компонент обязан:

- передать полученные props реальному DOM-элементу;
- корректно передать `ref`;
- сохранить подходящую HTML-семантику.

Нельзя бездумно заменить кнопку на `<div>`. `asChild` меняет отрисовываемый элемент, но не добавляет ему отсутствующую нативную семантику и клавиатурное поведение.

Если trigger выполняет действие, дочерний элемент должен оставаться доступным интерактивным элементом, например `<button>` или подходящей ссылкой.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие риски есть у shared UI?</strong></summary>

<dl>
<dd>
<h2></h2>

Один «универсальный» компонент может накопить десятки props и противоречивые режимы.

Другие риски:

- бизнес-логика внутри UI-kit;
- слишком широкий публичный API;
- несогласованные design tokens;
- недоступные состояния;
- изменение общего компонента сразу ломает много экранов;
- наружу раскрываются детали используемой библиотеки;
- отсутствуют примеры для редких комбинаций props.

API и визуальные изменения общей библиотеки нужно документировать, тестировать и при необходимости версионировать.

Не следует добавлять новый prop только ради одного экрана. Сначала проверяют, является ли требование общей вариацией компонента или продуктовой особенностью, которую нужно реализовать выше.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему важно не ломать native props в wrapper-компонентах?</strong></summary>

<dl>
<dd>
<h2></h2>

Компонент-обёртка расширяет нативный элемент, но не должен скрывать его базовые возможности.

Если `Button` не передаёт `type="submit"`, форма не отправится. Если кнопка не задаёт безопасный default `type="button"`, она может отправить форму случайно.

Если `Input` теряет `name`, `disabled`, `aria-*` или `ref`, могут сломаться:

- отправка формы;
- доступное имя;
- интеграция с React Hook Form;
- автоматическое заполнение;
- программное управление фокусом.

Wrapper обычно наследует подходящие нативные props и добавляет к ним собственные визуальные параметры, не переопределяя стандартные атрибуты другим смыслом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где лучше хранить бизнес-компонент?</strong></summary>

<dl>
<dd>
<h2></h2>

Если компонент знает о пользователе, заказе, правах доступа или конкретном действии продукта, это уже не общий UI primitive.

Например, `Button` остаётся в `shared/ui`, а `DeleteOrderButton`, который проверяет права, открывает подтверждение и вызывает API, принадлежит соответствующей feature.

В `shared` оставляют переиспользуемый визуальный и поведенческий контракт без логики конкретной предметной области.

При этом feature может собирать бизнес-компонент из нескольких элементов shared UI:

```text
DeleteOrderButton
├── shared/ui/Button
├── shared/ui/ConfirmDialog
└── feature model и API
```

Так shared UI отвечает за общее поведение интерфейса, а feature — за смысл пользовательского действия.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

- Команда строит `Button`, `Dialog`, `Select` поверх Radix primitives.
- Shared UI использует общие design tokens, варианты и правила доступности.
- Feature-компонент использует `shared/ui/Dialog`, но не помещает бизнес-логику в shared.
- `asChild` используется только с компонентом, который передаёт props, `ref` и сохраняет корректную семантику.
- При SSR сервер и первый клиентский render используют одинаковое состояние открытия, а portal создаётся в подходящий момент.
- В Storybook документируются состояния, варианты, интерактивное поведение и требования доступности компонента.
