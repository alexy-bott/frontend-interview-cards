#### Вопрос

Что такое shared UI и design system во frontend? Какую роль может играть Radix UI?

#### Ответ

**Shared UI** - общая библиотека интерфейсных компонентов приложения: кнопок, полей ввода, диалоговых окон, выпадающих меню и вкладок. Такие компоненты не знают о конкретном заказе, пользователе или бизнес-сценарии. Они предоставляют стабильный внешний интерфейс, единое поведение и стили для продуктовых компонентов.

**Design system**, или дизайн-система, шире библиотеки компонентов. В неё входят правила визуального языка, design tokens, компоненты, шаблоны поведения, требования доступности и документация. **Design tokens**, или дизайн-токены, - именованные значения цветов, отступов, типографики и других параметров, например `color-text-danger`. Они позволяют менять тему системно, а не искать конкретный цвет по всему CSS.

**Radix UI Primitives** - низкоуровневые React-компоненты без готового визуального оформления для сложных элементов: `Dialog`, `DropdownMenu`, `Select`, `Tooltip`, `Tabs`. Radix реализует значительную часть поведения: управление фокусом, навигацию с клавиатуры, необходимые ARIA-атрибуты и controlled/uncontrolled API. Controlled-компонент получает состояние снаружи, а uncontrolled хранит его внутри и принимает начальное значение.

Radix не является готовой дизайн-системой. Команда сама задаёт стили, дизайн-токены, содержимое, адаптивность и правила композиции. Доступность тоже не появляется автоматически: разработчик должен передать понятные подписи, сохранить семантику элементов и проверить итоговый сценарий с клавиатурой и программой чтения с экрана (screen reader).

Компоненты shared UI должны сохранять контракт нативных HTML-элементов. Если `Button` рендерит `<button>`, он должен поддерживать `type="button" | "submit" | "reset"`, `disabled`, `aria-*` и `ref`. Нельзя занимать prop `type` под визуальный вариант `primary`: это сломает отправку формы. Для внешнего вида используют отдельные props, например `variant`, `size` и `tone`.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Чем headless/unstyled component отличается от готового компонента?
>
> **Ответ:** Headless, или unstyled component, предоставляет структуру состояния и поведения, но не навязывает внешний вид. Готовый компонент уже содержит дизайн и стили конкретной системы. Radix относится к headless primitives: он помогает с поведением и доступностью сложного элемента, а CSS и визуальные варианты создаёт команда.

> [!followup]
> **Вопрос:** Почему dialog или select сложно писать самому?
>
> **Ответ:** Диалог должен перевести фокус внутрь после открытия, удерживать клавиатурную навигацию в активном окне, закрываться по `Escape`, блокировать взаимодействие с фоном и возвращать фокус на элемент, который его открыл. Select должен поддерживать стрелки, поиск, выбор и роли доступности. Кроме того, нужны controlled/uncontrolled режимы, portal, который рендерит всплывающий слой в другом узле DOM, и обработка прокрутки. Пропуск одного из этих требований легко делает компонент неудобным или недоступным.

> [!followup]
> **Вопрос:** Что такое `asChild` в Radix?
>
> **Ответ:** По умолчанию primitive Radix создаёт свой HTML-элемент. `asChild` просит его использовать единственный дочерний элемент вместо собственной обёртки и объединить с ним обработчики и атрибуты. Это позволяет, например, сделать существующую ссылку trigger для диалога без лишнего `<button>`. Дочерний React-компонент обязан передать полученные props и `ref` до реального DOM-элемента, иначе события и управление фокусом не сработают.

> [!followup]
> **Вопрос:** Какие риски есть у shared UI?
>
> **Ответ:** Один «универсальный» компонент может накопить десятки props и противоречивые режимы. Изменение общего компонента затрагивает много экранов, поэтому его API и визуальные изменения нужно версионировать и проверять. Другие риски - бизнес-логика внутри UI-kit, несогласованные токены, недоступные состояния и отсутствие примеров для редких комбинаций props.

> [!followup]
> **Вопрос:** Почему важно не ломать native props в wrapper-компонентах?
>
> **Ответ:** Компонент-обёртка расширяет нативный элемент, но не должен скрывать его базовые возможности. Если `Button` не передаёт `type="submit"`, форма не отправится. Если `Input` теряет `name`, `disabled`, `aria-*` или `ref`, ломаются отправка формы, доступное имя, интеграция с React Hook Form и программное управление фокусом.

> [!followup]
> **Вопрос:** Где лучше хранить бизнес-компонент?
>
> **Ответ:** Если компонент знает о пользователе, заказе, правах доступа или конкретном действии продукта, это уже не общий UI primitive. Например, `Button` остаётся в `shared/ui`, а `DeleteOrderButton`, который проверяет права и вызывает API, принадлежит соответствующей фиче. В `shared` оставляют только переиспользуемый визуальный и поведенческий контракт.

#### Где это встречается во frontend

- Команда строит `Button`, `Dialog`, `Select` поверх Radix primitives.
- Shared UI использует общие дизайн-токены, варианты и правила доступности.
- Feature-компонент использует `shared/ui/Dialog`, но не кладет бизнес-логику в shared.
- При SSR проверяют, что серверная разметка совпадает с первым рендером в браузере, а всплывающий слой portal создаётся в подходящий момент.
- В Storybook документируются состояния и варианты компонента.
