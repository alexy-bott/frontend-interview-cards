## Вопрос

<br>

 💬 **Как понять, где хранить состояние во frontend: локально, в кэше server state, глобальном store или URL?**

<h2></h2>

<br>
<dl>
<dd>

Место для состояния выбирают по его владельцу, источнику истины, сроку жизни и числу потребителей.

Состояние следует хранить как можно ближе к коду, который им управляет, но достаточно высоко, чтобы все нужные потребители получали единый источник данных.

При выборе полезно проверить:

- кому принадлежит значение — компоненту, форме, frontend-приложению или backend;
- сколько независимых частей интерфейса его используют;
- должно ли оно сохраняться после перезагрузки;
- нужно ли восстанавливать его через Back/Forward;
- должен ли пользователь иметь возможность поделиться им через ссылку;
- можно ли вычислить его из уже существующих данных.

- **Локальное состояние** подходит для одного компонента или небольшого UI-сценария: открыто ли модальное окно, раскрыт ли список, какая вкладка выбрана. Если выбранная вкладка должна сохраняться в ссылке или истории браузера, её лучше перенести в URL.
- **Состояние формы** содержит введённые значения, ошибки, а также признаки изменения поля (`dirty`) и посещения поля пользователем (`touched`). Его обычно ведёт сама форма или библиотека вроде React Hook Form.
- **Server state**, или состояние серверных данных, принадлежит backend. Frontend хранит локальную копию и должен учитывать загрузку, устаревание, повторное получение и синхронизацию. Для этого подходят RTK Query или TanStack Query.
- **Глобальное клиентское состояние** нужно нескольким независимым частям интерфейса и не принадлежит серверному кэшу: например, тема, глобальная очередь уведомлений или состояние многошагового локального сценария.
- **URL state**, или состояние в адресе страницы, подходит для маршрута, поискового запроса, сортировки, фильтров и пагинации. Ссылку можно отправить другому человеку, добавить в закладки и восстановить после обновления страницы.

Параметры, с которыми загружаются серверные данные, не обязательно являются server state. Например, значение фильтра может храниться в URL, а результат запроса по этому фильтру — в кэше RTK Query.

Выбранная организация может храниться в глобальном store, если задаёт общий контекст приложения. Если она определяет текущий маршрут или открываемый ресурс, её идентификатор может быть частью URL.

Не каждое значение нужно хранить отдельно. Если `filteredItems` полностью вычисляется из `items` и `filter`, его обычно рассчитывают из исходных данных.

Дублирование производного состояния создаёт риск рассинхронизации:

```ts
const filteredItems = items.filter(item => {
  return item.name.includes(filter);
});
```

`useMemo` может уменьшить стоимость повторного вычисления, если оно действительно дорогое, но результат всё равно остаётся производным значением, а не отдельным источником истины.

Если одно значение одновременно хранится в URL, global store и локальном state, нужно выбрать один источник истины. Остальные представления должны вычисляться из него или синхронизироваться в одном явно определённом направлении.

`localStorage` и cookie отвечают за сохранение или передачу данных, но сами по себе не определяют архитектурный уровень состояния.

Например, тема может находиться в глобальном store и сохраняться между сессиями через `localStorage`. При запуске приложение читает сохранённое значение и инициализирует им активное состояние.

Секретные токены нельзя помещать в `localStorage` без оценки угроз: доступный странице JavaScript, включая внедрённый через XSS код, сможет их прочитать.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что такое server state?</strong></summary>

<dl>
<dd>
<h2></h2>

Server state — данные, источником истины для которых является backend.

Frontend хранит временную копию: запрашивает её, показывает, помечает устаревшей и синхронизирует после изменений.

Кроме самих данных приходится учитывать:

- загрузку и ошибку;
- время актуальности;
- повторный запрос;
- одинаковые параллельные запросы;
- инвалидацию кэша;
- возможное оптимистичное обновление UI до ответа сервера.

Параметры запроса при этом могут принадлежать другому виду состояния. Например, фильтр находится в URL, а полученный по нему список — в server state.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое URL state?</strong></summary>

<dl>
<dd>
<h2></h2>

URL state хранится в пути или query-параметрах адреса.

Например:

```text
/users?page=2&role=admin&sort=name
```

Такой URL описывает текущую страницу, фильтр и сортировку. Пользователь может обновить страницу, сохранить адрес в закладки или отправить ссылку без потери контекста.

Изменение URL можно записать как новую запись истории или заменить текущую. Back/Forward восстанавливают только те состояния, которые были сохранены отдельными записями истории.

Значения из URL являются внешними входными данными, поэтому их нужно разбирать, проверять и подставлять значения по умолчанию.

В URL не помещают секретные и слишком объёмные данные.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужен global store?</strong></summary>

<dl>
<dd>
<h2></h2>

Global store нужен, когда одними клиентскими данными управляют несколько независимых частей интерфейса и у них должен быть единый источник истины.

Примеры:

- тема;
- глобальная очередь уведомлений;
- состояние многошагового редактора между маршрутами;
- выбранный контекст приложения, влияющий на несколько независимых областей.

Сам факт использования данных в двух компонентах ещё не требует Redux или Zustand.

Иногда достаточно:

- поднять состояние до ближайшего общего родителя;
- передать его через props;
- использовать React Context для поддерева;
- перенести значение в URL, если оно описывает состояние страницы.

Context является способом передачи значения по дереву, но владелец и жизненный цикл состояния всё равно должны быть определены отдельно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему плохо хранить server state в обычном Redux slice?</strong></summary>

<dl>
<dd>
<h2></h2>

Технически это допустимо, но обычный slice сам по себе не предоставляет модель жизненного цикла запроса.

Команде придётся вручную реализовать:

- кэширование;
- устранение одинаковых параллельных запросов;
- повторное получение;
- инвалидацию;
- отслеживание загрузки и ошибок;
- определение устаревших данных;
- синхронизацию после мутаций.

RTK Query или TanStack Query предоставляют эти механизмы готовыми.

При этом кэш RTK Query физически находится внутри Redux store. Отличие заключается не только в месте хранения, а в модели управления серверными данными.

Обычный Redux slice остаётся оправданным, если проекту действительно нужна нестандартная модель, которую готовая библиотека не покрывает.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как понять, что state подняли слишком высоко?</strong></summary>

<dl>
<dd>
<h2></h2>

Если значение нужно только одному небольшому поддереву, но хранится глобально, становится сложнее определить его владельца и жизненный цикл.

Другие признаки:

- global store заполнен состояниями отдельных dropdown и полей ввода;
- удаление компонента требует отдельно очищать его временные данные;
- несвязанные части приложения могут изменять значение;
- для понимания локального UI приходится изучать глобальные actions и selectors;
- одноразовое состояние сохраняется дольше, чем существует использующий его сценарий.

Влияние на render зависит от устройства подписок, selectors и Context. Основная архитектурная проблема заключается в лишней связанности и неясном владельце состояния.

Такое значение лучше вернуть к ближайшему общему владельцу.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

- Фильтры таблицы кладут в URL, чтобы ссылкой можно было поделиться.
- Данные пользователя загружаются через RTK Query как server state.
- Открытие выпадающего списка хранится локально в компоненте.
- Тема хранится глобально и сохраняется между сессиями через `localStorage`.
- Черновик формы остаётся внутри формы или переносится выше, если один сценарий продолжается на нескольких маршрутах.
- Параметр страницы хранится в URL, а полученная страница данных — в серверном кэше.
