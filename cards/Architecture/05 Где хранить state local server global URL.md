#### Вопрос

Как понять, где хранить состояние во frontend: локально, в кэше server state, глобальном store или URL?

#### Ответ

Место для состояния выбирают по его владельцу, сроку жизни и числу потребителей. Состояние следует хранить как можно ближе к коду, который им управляет, но достаточно высоко, чтобы все нужные потребители получали единый источник данных.

- **Локальное состояние** подходит для одного компонента или небольшого UI-сценария: открыто ли модальное окно, какая вкладка выбрана, раскрыт ли список.
- **Состояние формы** содержит введённые значения, ошибки, а также признаки изменения поля (`dirty`) и посещения поля пользователем (`touched`). Его обычно ведёт сама форма или библиотека вроде React Hook Form.
- **Server state**, или состояние серверных данных, принадлежит backend. Frontend хранит лишь локальную копию и должен учитывать загрузку, устаревание, повторное получение и синхронизацию. Для этого подходят RTK Query или TanStack Query.
- **Глобальное клиентское состояние** нужно нескольким независимым частям интерфейса и не принадлежит серверному кэшу: например, тема, состояние многошагового локального сценария или выбранная организация, влияющая на разные области приложения.
- **URL state**, или состояние в адресе страницы, подходит для маршрута, поискового запроса, сортировки, фильтров и пагинации. Ссылку можно отправить другому человеку, добавить в закладки и восстановить кнопками Back/Forward.

Не каждое значение нужно хранить отдельно. Если `filteredItems` полностью вычисляется из `items` и `filter`, его обычно рассчитывают из исходных данных. Дублирование производного состояния создаёт риск рассинхронизации.

`localStorage` и cookie отвечают за сохранение данных между перезагрузками, но не выбирают архитектурный уровень состояния. Например, тему можно хранить в глобальном store и синхронизировать с `localStorage`. Секретные токены нельзя помещать в `localStorage` без оценки угроз: доступный странице JavaScript сможет их прочитать.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Что такое server state?
>
> **Ответ:** Server state - данные, источником истины для которых является backend. Frontend хранит временную копию: запрашивает её, показывает, помечает устаревшей и синхронизирует после изменений. Поэтому кроме самих данных приходится учитывать загрузку, ошибку, время актуальности, повторный запрос, инвалидацию кэша и возможное оптимистичное обновление UI до ответа сервера.

> [!followup]
> **Вопрос:** Что такое URL state?
>
> **Ответ:** URL state хранится в пути или query-параметрах адреса. Например, `/users?page=2&role=admin&sort=name` описывает текущую страницу, фильтр и сортировку. Браузер сохраняет такие изменения в истории, а пользователь может обновить или отправить ссылку без потери контекста. В URL не помещают секретные и слишком объёмные данные.

> [!followup]
> **Вопрос:** Когда нужен global store?
>
> **Ответ:** Когда одними клиентскими данными управляют несколько независимых частей дерева и у них должен быть единый источник истины. Примеры: тема, состояние многошагового редактора между маршрутами, глобальная очередь уведомлений. Сам факт использования данных в двух компонентах ещё не требует Redux или Zustand: иногда достаточно поднять состояние до ближайшего общего родителя или использовать React Context для передачи значения всему поддереву.

> [!followup]
> **Вопрос:** Почему плохо хранить server state в обычном Redux slice?
>
> **Ответ:** Технически можно, но обычный slice не знает жизненный цикл запроса. Команде придётся вручную реализовать кэширование, устранение одинаковых параллельных запросов, повторное получение, инвалидацию и отслеживание устаревших данных. RTK Query или TanStack Query предоставляют эту модель готовой. При этом их кэш всё равно может находиться внутри Redux store - отличие в способе управления данными, а не только в физическом месте хранения.

> [!followup]
> **Вопрос:** Как понять, что state подняли слишком высоко?
>
> **Ответ:** Если значение нужно только одному небольшому поддереву, но хранится глобально, его изменение может уведомлять лишних подписчиков и усложнять поиск владельца. Другие признаки: store заполнен временными состояниями отдельных выпадающих списков и полей ввода, а удаление компонента требует отдельно очищать его данные. Такое состояние лучше вернуть к ближайшему общему владельцу.

#### Где это встречается во frontend

- Фильтры таблицы кладут в URL, чтобы ссылкой можно было поделиться.
- Данные пользователя загружаются через RTK Query как server state.
- Открытие выпадающего списка хранится локально в компоненте.
- Тема хранится глобально и сохраняется между сессиями через `localStorage`.
- Черновик формы остаётся внутри формы или переносится выше, если один сценарий продолжается на нескольких маршрутах.
