#### Вопрос

Что такое public API в FSD и зачем нужны границы импортов?

#### Ответ

Public API, или публичный интерфейс, - это разрешённая точка доступа к срезу или сегменту FSD. Обычно её оформляют файлом `index.ts`, который экспортирует только предназначенные для внешнего использования компоненты, функции и типы.

Import boundaries, или границы импортов, отделяют этот публичный контракт от внутренней реализации. Например, импорт `features/auth/model/internal-store` является **deep import** - обращением к внутреннему файлу в обход публичного интерфейса. Внешний код начинает знать структуру среза, поэтому переименование файла или замена хранилища ломают потребителей.

Внешний модуль должен импортировать из публичной точки входа, например `features/auth`. Внутри самого среза допустимы прямые относительные импорты между его файлами: правило защищает границу среза, а не заставляет внутренний код обращаться к собственному `index.ts`.

Публичный интерфейс является контрактом: изменение экспортируемого поведения может потребовать правок у потребителей, а внутренние детали можно менять свободно. Поэтому `export *` из всех файлов не создаёт полезной границы. Если внешнему коду регулярно нужен закрытый экспорт, следует проверить, не пропущена ли часть контракта и правильно ли выбрана ответственность среза.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Что такое deep import?
>
> **Ответ:** Deep import - импорт из внутреннего файла модуля в обход его публичной точки входа. Например, `features/auth/model/private-store` раскрывает потребителю расположение и устройство хранилища. Импорт `features/auth` оставляет эти детали внутри фичи.

> [!followup]
> **Вопрос:** Public API - это всегда barrel file?
>
> **Ответ:** Не обязательно. Barrel file - файл, который реэкспортирует сущности из нескольких файлов. Он становится public API только тогда, когда выражает осознанный внешний контракт. Barrel с `export *` для всего слоя может скрывать реальные зависимости, создавать циклические импорты и случайно публиковать внутренние детали.

> [!followup]
> **Вопрос:** Что можно экспортировать из среза?
>
> **Ответ:** Только сущности, необходимые потребителям: например, основной UI-компонент, функция запуска действия, hook, selector и связанные публичные типы. Вспомогательные компоненты, внутреннее состояние и функции реализации не экспортируют, пока у них нет самостоятельного внешнего назначения.

> [!followup]
> **Вопрос:** Как технически контролировать границы импортов?
>
> **Ответ:** Сначала команда фиксирует допустимые направления зависимостей. Затем их проверяют в code review и автоматически: например, правилом ESLint `no-restricted-imports`, плагином для архитектурных границ или линтером FSD. Path aliases упрощают читаемые импорты, но сами по себе ничего не запрещают.

> [!followup]
> **Вопрос:** Когда deep import допустим?
>
> **Ответ:** В обычном коде между срезами - нет. Временное нарушение при миграции должно быть явно отмечено и удалено. Для неизбежной связи двух `entities` FSD предусматривает cross-import API: сущность экспортирует в папке `@x` минимальный интерфейс специально для другой сущности, например `entities/song/@x/artist`. Зависимость становится видимой и ограниченной, но это не разрешение на произвольные deep imports.

> [!followup]
> **Вопрос:** Что значит, что абстракция модуля протекает?
>
> **Ответ:** Это ситуация, когда для использования модуля приходится знать его внутреннее устройство. Например, потребитель сам объединяет внутренний store, промежуточный hook и DTO фичи вместо вызова одной публичной операции. Формально граница существует, но детали реализации уже стали неявной частью контракта, поэтому внутренний рефакторинг ломает внешний код.

#### Где это встречается во frontend

- Из `pages/profile` импортируют `features/edit-profile` через public API.
- UI-компонент внутри фичи не должен использоваться напрямую снаружи.
- Рефакторинг среза безопаснее, если внешний код зависит только от `index.ts`.
- Линтер запрещает импорты из внутренних `model` и `lib` соседних срезов.
