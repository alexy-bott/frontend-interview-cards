## Вопрос

<br>

 💬 **Что такое structural typing в TypeScript? Почему лишнее свойство объекта иногда вызывает ошибку, а иногда нет?**

<h2></h2>

<br>
<dl>
<dd>

TypeScript использует structural typing, или структурную типизацию: совместимость определяется формой значения, а не названием объявленного типа.

Если значение содержит все обязательные свойства с совместимыми типами, его можно использовать там, где ожидается такой контракт:

```ts
type Identifiable = { id: string };

const user = { id: "u1", name: "Ada" };
const entity: Identifiable = user; // допустимо
```

У `user` есть необходимое поле `id: string`, поэтому он совместим с `Identifiable`. Дополнительное поле `name` не мешает.

Объектный тип в TypeScript обычно описывает минимально необходимую структуру, а не точный список всех свойств, которые могут существовать у реального объекта.

Но для объектного литерала, созданного непосредственно в месте присваивания или вызова функции, TypeScript дополнительно выполняет excess property check, или проверку лишних свойств:

```ts
type User = {
  id: string;
  name: string;
};

function saveUser(user: User) {}

saveUser({ id: "u1", name: "Ada", nmae: "Typo" });
// Ошибка: свойство nmae не входит в User
```

Здесь TypeScript видит новый объектный литерал и предполагает, что незнакомое свойство `nmae` может быть опечаткой. Это дополнительная проверка литерала, а не требование точного совпадения всех объектных типов.

Если сначала сохранить значение в переменную, у неё появится собственный выведенный тип со всеми полями:

```ts
const admin = {
  id: "u1",
  name: "Ada",
  role: "admin",
};

saveUser(admin); // допустимо
```

Тип переменной `admin` содержит `id`, `name` и `role`. При передаче в `saveUser` TypeScript проверяет, что у значения есть обязательные поля типа `User`. Наличие дополнительного `role` не нарушает структурную совместимость.

Поле `role` при этом не удаляется. Функция получает исходный JavaScript-объект со всеми его свойствами. Типы влияют только на проверку кода и не преобразуют данные во время выполнения.

Структурная типизация удобна для `props`, функций и небольших контрактов: потребитель может требовать только те поля, которые действительно использует.

Обратная сторона состоит в том, что разные по смыслу сущности остаются совместимыми, если имеют одинаковую структуру. Например, обычные строковые `UserId` и `OrderId` TypeScript не различает без дополнительного брендирования.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему прямой объект с лишним полем не проходит, а переменная проходит?</strong></summary>

<dl>
<dd>
<h2></h2>

Объектный литерал, созданный непосредственно в месте вызова или присваивания, проходит дополнительную проверку лишних свойств. Неизвестный ключ в таком объекте часто означает опечатку или неверно понятый контракт.

```ts
saveUser({
  id: "u1",
  name: "Ada",
  role: "admin",
});
```

У ранее созданной переменной уже есть собственный тип:

```ts
const admin = {
  id: "u1",
  name: "Ada",
  role: "admin",
};
```

При передаче такой переменной TypeScript использует обычную структурную совместимость: проверяет наличие обязательных `id` и `name`, но не требует, чтобы набор свойств совпадал с `User` точно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Гарантирует ли excess property check отсутствие лишних полей?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Это дополнительная проверка некоторых объектных литералов на этапе компиляции, а не механизм точных объектных типов.

Она не удаляет свойства из объекта и не гарантирует, что значение во время выполнения не содержит других полей. Например, объект из переменной, API, `localStorage` или сторонней библиотеки может иметь более широкую структуру.

Если приложению нужна строго определённая форма данных, значение проверяют и преобразуют явно во время выполнения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем structural typing отличается от nominal typing?</strong></summary>

<dl>
<dd>
<h2></h2>

В структурной типизации важна форма значения. Два типа совместимы, если у значения есть необходимые свойства с подходящими типами, даже если объявления имеют разные имена.

В nominal typing, или номинальной типизации, важна принадлежность к конкретно объявленному типу. Одинаковой структуры для совместимости недостаточно.

TypeScript в основном использует структурную типизацию, что соответствует устройству объектов JavaScript.

Частичное исключение составляют классы с `private` или `protected` полями. Для совместимости такие поля должны происходить из одного объявления класса, поэтому одного совпадения их структуры недостаточно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как не перепутать <code>UserId</code> и <code>OrderId</code>, если оба представлены строкой?</strong></summary>

<dl>
<dd>
<h2></h2>

Можно использовать branded type, или брендированный тип: к базовому типу добавляется специальная метка, существующая только в системе типов.

```ts
declare const userIdBrand: unique symbol;
type UserId = string & { readonly [userIdBrand]: true };
```

После этого обычная строка, `UserId` и отдельно созданный `OrderId` перестают быть взаимозаменяемыми для TypeScript.

Бренд не изменяет строку во время выполнения и сам по себе не проверяет её формат. Значение из URL или backend сначала нужно проверить, а затем вернуть из функции создания как `UserId`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как <code>satisfies</code> помогает при создании объекта?</strong></summary>

<dl>
<dd>
<h2></h2>

Оператор `satisfies` проверяет, совместим ли объектный литерал с указанным контрактом. Он позволяет обнаружить отсутствующие обязательные свойства, несовместимые значения и неизвестные ключи.

При этом `satisfies` сохраняет более точный выведенный тип самого объекта, вместо того чтобы заменять его широкой аннотацией:

```ts
type Routes = Record<"home" | "profile", string>;

const routes = {
  home: "/",
  profile: "/profile",
} satisfies Routes;
```

Оператор работает только на этапе проверки типов. Он не удаляет лишние свойства, не преобразует объект и не проверяет внешние данные во время выполнения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему structural typing важен для функций?</strong></summary>

<dl>
<dd>
<h2></h2>

Совместимость функций тоже определяется их структурой: параметрами и результатом.

Функцию с меньшим числом параметров часто можно передать туда, где вызывающая сторона предоставляет больше аргументов. Функция обратного вызова может просто проигнорировать ненужные значения:

```ts
["Ada", "Bob"].forEach((name) => {
  console.log(name);
});
```

`forEach` также передаёт индекс и массив, но callback не обязан объявлять все эти параметры.

Более точные правила совместимости параметров и результатов зависят от variance и настройки `strictFunctionTypes`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Проверяет ли TypeScript форму JSON от backend?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. TypeScript проверяет код до его выполнения, а ответ backend появляется уже во время работы приложения.

Аннотация или type assertion могут заставить TypeScript считать значение типом `User`, но не проверят его реальные поля:

```ts
const user = (await response.json()) as User;
```

Сервер может прислать объект другой формы, и TypeScript этого не обнаружит. На границе приложения данные нужно принять как недоверенные и проверить через схему валидации, parser или корректный type guard.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```ts
type User = {
  id: string;
  name: string;
};

function printUser(user: User) {}

printUser({ id: "1", name: "Ada", role: "admin" });

const admin = { id: "1", name: "Ada", role: "admin" };
printUser(admin);
```

<details>
<summary><strong>Почему первая передача вызывает ошибку, а вторая допустима? Исчезает ли <code>role</code> во втором случае?</strong></summary>

<dl>
<dd>
<h2></h2>

Первый аргумент является объектным литералом, созданным непосредственно в месте вызова. Поэтому TypeScript выполняет excess property check и сообщает о неизвестном свойстве `role`.

Переменная `admin` уже имеет собственный тип `{ id: string; name: string; role: string }`. Этот тип структурно совместим с `User`, потому что содержит обязательные поля `id` и `name`.

Поле `role` не исчезает. Во втором случае функция получает тот же реальный объект со всеми тремя свойствами. TypeScript ограничивает доступные операции при проверке кода, но не изменяет объект во время выполнения.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Практический смысл |
| --- | --- |
| Props компонента | Компонент требует только используемую часть модели |
| Функция обратного вызова | Функция может игнорировать предложенные аргументы |
| Конфигурация | Объектный литерал проверяется на неизвестные ключи |
| DTO и доменная модель | Одинаковая форма не гарантирует одинаковый смысл |
| Идентификаторы | Branded types разделяют одинаковые примитивы |
| Данные backend | Структурный тип не заменяет проверку во время выполнения |
