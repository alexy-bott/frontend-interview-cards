#### Вопрос

Как работают абстрактные классы, `implements` и декораторы в TypeScript? Чем стандартные декораторы отличаются от старого формата?

#### Ответ

`abstract class` описывает базовый класс, экземпляр которого нельзя создавать напрямую в TypeScript-коде. Он может содержать готовую реализацию, существующую во время выполнения, и абстрактные члены (`abstract members`), которые обязан определить наследник:

```ts
abstract class ApiClient {
  constructor(protected readonly baseUrl: string) {}

  abstract getToken(): string;

  protected buildUrl(path: string): string {
    return new URL(path, this.baseUrl).toString();
  }
}
```

В JavaScript остаётся обычный класс с конструктором и готовыми методами. Модификатор `abstract` и требование реализовать метод существуют только при проверке типов. Потребитель скомпилированного JavaScript технически может вызвать `new ApiClient(...)`, если конструктор сам не проверяет `new.target`.

`implements` проверяет часть класса, относящуюся к экземпляру (`instance side`), то есть его поля и методы, относительно интерфейса или объектного типа:

```ts
interface UserRepository {
  load(id: string): Promise<User>;
}

class HttpUserRepository implements UserRepository {
  async load(id: string): Promise<User> {
    return api.loadUser(id);
  }
}
```

`implements` не копирует методы, не создаёт проверку во время выполнения и не меняет тип самого класса. Он также не выводит типы параметров реализации из интерфейса: `id` всё равно нужно аннотировать, иначе при `noImplicitAny` будет ошибка.

Статическая часть класса (`static side`), то есть конструктор и статические методы, не проверяется обычным `implements`. Для фабрики или реестра объявляют отдельную сигнатуру конструктора (`construct signature`):

```ts
type RepositoryClass = {
  new (baseUrl: string): UserRepository;
  readonly kind: string;
};
```

Декораторы (`decorators`) являются функциями, которые применяются к классу и его элементам во время выполнения. Они могут заменить метод или класс, изменить инициализацию или зарегистрировать дополнительное поведение. TypeScript проверяет их сигнатуры, но вызовы декораторов остаются в создаваемом JavaScript или обрабатываются транспилятором.

В TypeScript существуют два несовместимых режима:

1. Стандартные декораторы поддерживаются с TypeScript 5.0 без `experimentalDecorators`. Они используют объекты контекста, например `ClassMethodDecoratorContext`, и соответствуют актуальному предложению ECMAScript.
2. Декораторы старого формата (`legacy decorators`) включаются через `experimentalDecorators`. У них прежние сигнатуры с объектом назначения, именем свойства и дескриптором. `emitDecoratorMetadata` относится именно к этой экосистеме и часто используется фреймворком вместе с `reflect-metadata`.

Стандартный декоратор нельзя считать прямой заменой старого: стандартный режим не поддерживает декораторы параметров и несовместим с `emitDecoratorMetadata`. Перед миграцией проверяют требования фреймворка, версию TypeScript, настройки Babel или SWC и весь процесс тестовой сборки.

В прикладном React-коде декораторы встречаются редко. Знание нужно для Angular, старого MobX-кода, контейнеров внедрения зависимостей (DI), SDK и сборки общих пакетов. Если поведение можно выразить обычной функцией или композицией, такой код обычно легче читать и тестировать.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Чем `abstract class` отличается от интерфейса?
>
> **Ответ:** Интерфейс полностью стирается и описывает форму значений. Абстрактный класс создаёт JavaScript-класс, может хранить состояние, конструктор, защищённые члены (`protected`) и общую реализацию. Если нужен только контракт между слоями, интерфейс проще; если наследники действительно разделяют код и правила состояния, абстрактный класс может быть оправдан.

> [!followup]
> **Вопрос:** Запрещает ли `abstract` создание экземпляра во время выполнения?
>
> **Ответ:** Нет. TypeScript запрещает `new` только при проверке исходного TS-кода. После компиляции модификатор исчезает. Если защита во время выполнения является частью публичной JavaScript-библиотеки, конструктор должен проверить `new.target === ApiClient` либо API не должно предоставлять базовый класс для прямого создания.

> [!followup]
> **Вопрос:** Что делает `implements` и чего не делает?
>
> **Ответ:** Он проверяет, что экземпляр класса совместим с контрактом. Он не добавляет реализацию, не валидирует внешние объекты, не выводит автоматически типы параметров методов и не проверяет статическую часть класса. Изменение интерфейса создаст ошибку при проверке типов, но во время выполнения интерфейса не существует.

> [!followup]
> **Вопрос:** Чем TypeScript `private` отличается от JavaScript `#private`?
>
> **Ответ:** Модификатор `private` ограничивает доступ при проверке типов, но после обычной компиляции поле остаётся свойством с доступным именем. Поле `#token` является настоящим закрытым полем JavaScript и недоступно снаружи во время выполнения. Оба варианта влияют на совместимость классов, но дают разный уровень реальной защиты.

> [!followup]
> **Вопрос:** Когда выполняется декоратор?
>
> **Ответ:** При определении и инициализации декорируемого класса, а не при проверке типов. Порядок вычисления выражений и применения декораторов задаётся выбранным стандартом. Поэтому регистрация, замена метода и другие побочные эффекты происходят при загрузке модуля и могут влиять на tree shaking, то есть на удаление неиспользуемого кода, и на изоляцию тестов.

> [!followup]
> **Вопрос:** Почему стандартные декораторы и декораторы старого формата нельзя смешивать без проверки?
>
> **Ответ:** У них разные аргументы, порядок и возможности. Старый декоратор метода получает прототип, имя и дескриптор; стандартный получает значение метода и объект контекста. Библиотека, ожидающая `emitDecoratorMetadata`, не заработает автоматически в стандартном режиме. Проект должен следовать требованиям фреймворка и использовать один режим во всех транспиляторах.

> [!followup]
> **Вопрос:** Что делает стандартный декоратор метода?
>
> **Ответ:** Он получает исходную функцию и объект `context` с именем, видом элемента и другими признаками. Декоратор может вернуть заменяющую функцию с совместимой сигнатурой или выполнить регистрацию через `context.addInitializer`. Если ничего не вернуть, исходный метод остаётся без замены.

> [!followup]
> **Вопрос:** Почему декораторы могут усложнить поддержку кода?
>
> **Ответ:** Видимое объявление метода перестаёт содержать всё его поведение: декоратор может обернуть вызов, изменить дескриптор или зарегистрировать класс при импорте. Это усложняет порядок инициализации, тесты и удаление неиспользуемого кода. Польза должна оправдывать скрытую связанность, обычно на уровне фреймворка или инфраструктуры.

> [!followup]
> **Вопрос:** Проверяет ли `implements` данные, полученные из backend?
>
> **Ответ:** Нет. Он работает только с объявлением класса во время компиляции. JSON не становится экземпляром класса, не получает прототип и не проверяется интерфейсом. Внешние данные сначала проходят проверку во время выполнения и только после этого при необходимости используются для создания экземпляра.

#### Мини-задача

```ts
interface Clock {
  now(): Date;
}

abstract class BaseSession {
  constructor(protected readonly clock: Clock) {}

  abstract expiresAt(): Date;

  isExpired(): boolean {
    return this.clock.now() >= this.expiresAt();
  }
}

class UserSession extends BaseSession {
  constructor(
    clock: Clock,
    private readonly expires: Date,
  ) {
    super(clock);
  }

  expiresAt(): Date {
    return this.expires;
  }
}
```

> [!followup]
> **Вопрос:** Что здесь существует во время выполнения, а что только проверяет TypeScript?
>
> **Ответ:** Оба класса, конструкторы, поля и методы существуют в JavaScript. Интерфейс `Clock`, модификаторы типов и требование реализовать абстрактный метод стираются. Переданный объект `clock` должен иметь работающий метод `now` во время выполнения; `implements` и аннотация типа сами его не проверят.

#### Где это встречается во frontend

| Ситуация | Подход |
| --- | --- |
| Контракт адаптера или репозитория | Интерфейс и `implements` при необходимости |
| Общая реализация SDK | Абстрактный класс с осмысленным наследованием |
| Фабрика или реестр классов | Отдельный контракт конструктора и статической части |
| Функциональность React | Обычно функции и композиция |
| Angular или старый MobX | Декораторы старого формата по требованиям фреймворка |
| Новая инфраструктура | Стандартные декораторы только при реальной пользе |
