## Вопрос

<br>

 💬 **Как работают абстрактные классы, `implements` и декораторы в TypeScript? Чем стандартные декораторы отличаются от старого формата?**

<h2></h2>

<br>
<dl>
<dd>

`abstract class` описывает базовый класс, экземпляр которого нельзя создавать напрямую в TypeScript-коде. Такой класс может содержать готовые поля и методы с реализацией, а также абстрактные члены без реализации, которые обязан определить конкретный наследник:

```ts
abstract class ApiClient {
  constructor(protected readonly baseUrl: string) {}

  abstract getToken(): string;

  protected buildUrl(path: string): string {
    return new URL(path, this.baseUrl).toString();
  }
}
```

После компиляции в JavaScript остаётся обычный класс с конструктором и реализованными методами. Модификатор `abstract` и объявление абстрактного метода исчезают, поэтому запрет на создание экземпляра действует только во время проверки TypeScript-кода. Потребитель скомпилированного JavaScript технически может вызвать `new ApiClient(...)`, если класс доступен и конструктор сам не проверяет `new.target`.

`implements` проверяет, что экземпляры класса соответствуют интерфейсу или объектному типу. Проверяется экземплярная часть класса (`instance side`): его обычные поля и методы.

```ts
interface UserRepository {
  load(id: string): Promise<User>;
}

class HttpUserRepository implements UserRepository {
  async load(id: string): Promise<User> {
    return api.loadUser(id);
  }
}
```

`implements` не копирует методы из интерфейса, не добавляет runtime-проверку и не изменяет типы членов класса. Он только сообщает об ошибке, если объявленный класс несовместим с контрактом.

Типы параметров реализации также не выводятся из интерфейса автоматически: параметр `id` всё равно нужно аннотировать. Иначе при включённом `noImplicitAny` TypeScript сообщит об ошибке.

Обычный `implements` не проверяет статическую часть класса (`static side`): его конструктор, статические поля и статические методы. Для фабрики или реестра отдельно описывают тип самого конструктора:

```ts
type RepositoryClass = {
  new (baseUrl: string): UserRepository;
  readonly kind: string;
};
```

Само объявление `RepositoryClass` ничего не проверяет. Такой тип нужно использовать при присваивании класса, передаче его в фабрику или добавлении в реестр.

Декоратор — это функция, которая применяется к классу или его элементу и участвует в работе программы во время выполнения. В зависимости от вида декоратор может заменить класс или метод, настроить инициализацию поля либо зарегистрировать дополнительное поведение.

Сам декоратор вызывается во время определения класса. При этом добавленный им инициализатор может выполниться позже: например, при создании каждого экземпляра. TypeScript проверяет сигнатуру декоратора и создаёт необходимый JavaScript-код для его runtime-выполнения.

В TypeScript существуют два несовместимых режима:

1. Современные стандартные декораторы поддерживаются с TypeScript 5.0 и не требуют `experimentalDecorators`. Они получают декорируемое значение и объект контекста, например `ClassMethodDecoratorContext`, и соответствуют современному предложению декораторов ECMAScript.
2. Декораторы старого формата (`legacy decorators`) включаются через `experimentalDecorators`. Их аргументы зависят от вида декоратора. Например, legacy-декоратор метода получает объект назначения, имя метода и дескриптор свойства.

Параметр `emitDecoratorMetadata` относится к legacy-экосистеме. Он заставляет TypeScript добавлять ограниченную информацию о типах во время выполнения и обычно используется вместе с `reflect-metadata` во фреймворках и контейнерах внедрения зависимостей.

Современные декораторы не являются прямой заменой legacy-декораторов: они не поддерживают декораторы параметров и несовместимы с `emitDecoratorMetadata`. Перед миграцией нужно проверить требования фреймворка, используемых библиотек, версии TypeScript и всех инструментов сборки, например Babel или SWC.

В прикладном React-коде декораторы встречаются редко. Они чаще нужны во фреймворках, контейнерах внедрения зависимостей, SDK и инфраструктурных библиотеках. Если поведение можно выразить обычной функцией или композицией, такой код обычно легче читать и тестировать.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем <code>abstract class</code> отличается от интерфейса?</strong></summary>

<dl>
<dd>
<h2></h2>

Интерфейс существует только для проверки типов и полностью исчезает из JavaScript. Он описывает, какие поля и методы должно иметь значение, но не содержит runtime-реализацию.

Абстрактный класс превращается в JavaScript-класс. Он может содержать состояние, конструктор, защищённые члены (`protected`) и общие реализованные методы.

Если нужен только контракт между частями приложения, интерфейс обычно проще. Если наследники действительно разделяют состояние, готовую реализацию и общие правила поведения, абстрактный класс может быть оправдан.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Запрещает ли <code>abstract</code> создание экземпляра во время выполнения?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. TypeScript запрещает `new` только при проверке исходного TS-кода. После компиляции модификатор `abstract` исчезает, и JavaScript сам не знает, что класс считался абстрактным.

Если runtime-защита является частью публичной JavaScript-библиотеки, конструктор может проверить `new.target === ApiClient`. Другой вариант — не экспортировать базовый класс как доступный для прямого создания.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает <code>implements</code> и чего не делает?</strong></summary>

<dl>
<dd>
<h2></h2>

`implements` проверяет, что экземпляр класса совместим с указанным контрактом. Если в интерфейсе появится обязательный метод, TypeScript потребует добавить его в класс.

При этом `implements` не добавляет реализацию, не проверяет внешние данные во время выполнения, не выводит автоматически типы параметров методов и не проверяет статическую часть класса. После компиляции самого интерфейса и связи `implements` в JavaScript не остаётся.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>extends</code> отличается от <code>implements</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`extends` создаёт настоящее наследование: дочерний класс получает реализацию полей и методов базового класса, а между их прототипами устанавливается связь во время выполнения.

`implements` ничего не наследует и не изменяет прототипы. Он только проверяет во время компиляции, что экземпляр класса соответствует указанному интерфейсу или объектному типу.

Класс может одновременно наследоваться от одного базового класса и реализовывать несколько интерфейсов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем TypeScript <code>private</code> отличается от JavaScript <code>#private</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Модификатор TypeScript `private` ограничивает доступ во время проверки типов. После обычной компиляции поле остаётся JavaScript-свойством с доступным именем, поэтому к нему технически можно обратиться во время выполнения.

Поле `#token` является настоящим закрытым полем JavaScript. Обратиться к нему снаружи класса нельзя даже во время выполнения.

Оба варианта также влияют на совместимость типов классов, но только `#private` обеспечивает встроенную runtime-защиту.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда выполняется декоратор?</strong></summary>

<dl>
<dd>
<h2></h2>

Выражение декоратора вычисляется, а сама функция декоратора вызывается во время определения класса. Поэтому немедленная регистрация класса или замена метода обычно происходят при загрузке и выполнении модуля.

Однако не всё добавленное декоратором поведение обязательно выполняется сразу. Например, инициализатор, добавленный стандартным декоратором экземплярного метода через `context.addInitializer`, запускается при создании каждого экземпляра класса.

Из-за runtime-выполнения декораторы могут влиять на побочные эффекты модуля, изоляцию тестов и tree shaking — удаление неиспользуемого кода из итоговой сборки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему стандартные декораторы и декораторы старого формата нельзя смешивать без проверки?</strong></summary>

<dl>
<dd>
<h2></h2>

У них отличаются аргументы, правила возврата значений и доступные возможности. Например, legacy-декоратор метода получает объект назначения, имя метода и дескриптор свойства. Стандартный декоратор метода получает саму функцию и объект контекста.

Библиотека, которая ожидает декораторы параметров или данные от `emitDecoratorMetadata`, не заработает автоматически в стандартном режиме. Все инструменты, обрабатывающие код, должны использовать совместимый формат: TypeScript, Babel, SWC, тестовая сборка и сам фреймворк.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает стандартный декоратор метода?</strong></summary>

<dl>
<dd>
<h2></h2>

Стандартный декоратор метода получает исходную функцию и объект `context`. В контексте доступны имя метода, информация о том, является ли он статическим или закрытым, и функция `addInitializer`.

Декоратор может вернуть новую функцию с совместимым поведением, которая заменит исходный метод. Если он ничего не возвращает, метод остаётся прежним.

Через `context.addInitializer` можно добавить код инициализации. Для обычного экземплярного метода такой инициализатор выполняется при создании каждого экземпляра класса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему декораторы могут усложнить поддержку кода?</strong></summary>

<dl>
<dd>
<h2></h2>

Видимое объявление класса или метода перестаёт содержать всё его поведение. Стандартный декоратор может заменить метод или добавить инициализатор, а legacy-декоратор также может изменить дескриптор свойства. Кроме того, декоратор может зарегистрировать класс во внешнем реестре при выполнении модуля.

Из-за этого сложнее отследить порядок инициализации, источник изменённого поведения и побочные эффекты в тестах. Декораторы стоит использовать, когда их польза на уровне фреймворка или инфраструктуры оправдывает такую скрытую связанность.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Проверяет ли <code>implements</code> данные, полученные из backend?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. `implements` проверяет только объявление класса во время компиляции. Полученный JSON не становится экземпляром класса, не получает его методы и не проверяется интерфейсом автоматически.

Внешние данные сначала нужно проверить во время выполнения. Только после успешной проверки их можно считать значением нужного типа или использовать для создания экземпляра класса.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```ts
interface Clock {
  now(): Date;
}

abstract class BaseSession {
  constructor(protected readonly clock: Clock) {}

  abstract expiresAt(): Date;

  isExpired(): boolean {
    return this.clock.now() >= this.expiresAt();
  }
}

class UserSession extends BaseSession {
  constructor(
    clock: Clock,
    private readonly expires: Date,
  ) {
    super(clock);
  }

  expiresAt(): Date {
    return this.expires;
  }
}
```

<details>
<summary><strong>Что здесь существует во время выполнения, а что только проверяет TypeScript?</strong></summary>

<dl>
<dd>
<h2></h2>

Классы `BaseSession` и `UserSession`, их конструкторы, созданные поля и реализованные методы существуют в JavaScript во время выполнения.

Интерфейс `Clock`, аннотации типов, модификаторы `abstract`, `protected`, `private`, `readonly` и требование реализовать `expiresAt` используются TypeScript при проверке кода, а затем удаляются. Само объявление абстрактного метода `expiresAt` из `BaseSession` в JavaScript не попадает.

Переданный объект `clock` должен иметь работающий метод `now` во время выполнения. Аннотация `Clock` сама не проверяет реальный объект и не добавляет ему этот метод.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Подход |
| --- | --- |
| Контракт адаптера или репозитория | Интерфейс и `implements`, если нужна явная проверка класса |
| Общая реализация SDK | Абстрактный класс при реальном наследовании состояния и поведения |
| Фабрика или реестр классов | Отдельный контракт конструктора и статической части |
| Функциональность React | Обычно функции, хуки и композиция |
| Angular, DI или старый MobX | Режим декораторов выбирается по требованиям инструмента |
| Новая инфраструктура | Стандартные декораторы только при реальной пользе |
