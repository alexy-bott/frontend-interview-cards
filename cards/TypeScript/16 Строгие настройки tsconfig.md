## Вопрос

<br>

 💬 **За что отвечает `tsconfig.json`? Что включает `strict` и какие настройки особенно важны во frontend-проекте?**

<h2></h2>

<br>
<dl>
<dd>

`tsconfig.json` описывает TypeScript-проект: какие файлы являются его корневыми файлами, по каким правилам проверяется код, как разрешаются модули и должен ли `tsc` создавать JavaScript или только проверять типы.

```json
{
  "extends": "./tsconfig.base.json",
  "compilerOptions": {
    "strict": true,
    "noEmit": true
  },
  "include": ["src"],
  "exclude": ["dist"]
}
```

Часто используются следующие поля верхнего уровня:

- `compilerOptions` задаёт правила проверки и компиляции;
- `files` перечисляет точный список корневых файлов;
- `include` выбирает корневые файлы по путям и шаблонам;
- `exclude` исключает совпадения из результата `include`;
- `extends` наследует настройки другой конфигурации;
- `references` связывает несколько отдельных TypeScript-проектов.

`files` является точным разрешённым списком. Если указанный файл не существует, TypeScript покажет ошибку. Для проекта с большим количеством файлов обычно удобнее `include`.

`exclude` не является запретом на использование файла. Если включённый файл импортирует исключённый модуль, этот модуль всё равно попадёт в TypeScript-программу как зависимость. Поэтому через `exclude` нельзя устанавливать архитектурные границы между модулями.

`extends` позволяет вынести общие правила команды или monorepo в базовую конфигурацию. Настройки из базового файла загружаются первыми, а дочерняя конфигурация может их переопределить.

Относительные пути разрешаются от того файла конфигурации, в котором они записаны. Поля `files`, `include` и `exclude` дочерней конфигурации заменяют соответствующие значения базовой, а не объединяются с ними. Поле `references` не наследуется.

Для нескольких связанных TypeScript-проектов используют `references`, `composite` и команду `tsc -b`. Например, browser-приложение и Node-конфигурация сборщика могут иметь отдельные `tsconfig`, а не один общий набор библиотек и глобальных типов.

`strict: true` включает семейство строгих проверок. В текущий набор входят:

- `strictNullChecks`: `null` и `undefined` учитываются как отдельные типы;
- `noImplicitAny`: TypeScript сообщает о местах, где неявно получился `any`;
- `noImplicitThis`: запрещает неявный `any` у `this`;
- `strictFunctionTypes`: строже проверяет совместимость параметров функций;
- `strictBindCallApply`: проверяет аргументы `bind`, `call` и `apply` по сигнатуре функции;
- `strictPropertyInitialization`: требует инициализировать обязательные поля класса;
- `useUnknownInCatchVariables`: переменная ошибки в `catch` получает тип `unknown`;
- `strictBuiltinIteratorReturn`: строже типизирует результат встроенных итераторов;
- `alwaysStrict`: проверяет файлы по правилам strict mode JavaScript и при необходимости добавляет соответствующую директиву в результат.

Отдельную проверку из семейства `strict` можно явно отключить, даже если установлен `strict: true`. Однако такое исключение должно быть осознанным и локально объяснимым.

Набор проверок `strict` может расширяться в новых версиях TypeScript. Поэтому обновление компилятора выполняют отдельным контролируемым изменением и после него запускают полную проверку проекта.

Полезные дополнительные настройки не обязательно входят в `strict`:

```json
{
  "compilerOptions": {
    "strict": true,
    "noEmit": true,
    "isolatedModules": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitOverride": true,
    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true
  }
}
```

`noUncheckedIndexedAccess` добавляет `undefined` при чтении элемента или свойства, существование которого не доказано:

```ts
const first = items[0];
// T | undefined
```

Для tuple с известной обязательной позицией или объекта с явно объявленным обязательным свойством дополнительный `undefined` не появляется.

`exactOptionalPropertyTypes` различает отсутствующее свойство и свойство, которому явно присвоили `undefined`:

```ts
type Options = {
  theme?: "light" | "dark";
};

const options: Options = {
  theme: undefined,
};
// Ошибка с exactOptionalPropertyTypes,
// если undefined явно не входит в тип theme.
```

Это важно для `PATCH`-запросов, spread-синтаксиса, `Object.keys` и API, где «поле не передано» отличается от «поле передано со значением `undefined`».

`noImplicitOverride` требует помечать переопределяемые методы класса через `override`. `noImplicitReturns` обнаруживает функции, в которых значение возвращается не по всем ожидаемым веткам. `noFallthroughCasesInSwitch` сообщает о случайном переходе из одного `case` в следующий.

`isolatedModules` проверяет, что каждый файл можно безопасно преобразовать отдельно без анализа всей TypeScript-программы. Это особенно важно, когда JavaScript создаёт не `tsc`, а Vite или другой транспилятор, обрабатывающий файлы по отдельности.

Не существует одного обязательного набора дополнительных флагов для любого frontend-проекта. `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes` повышают точность типов, но при включении в существующем проекте могут потребовать заметной миграции.

Vite и многие другие инструменты сборки преобразуют TypeScript в JavaScript без полной проверки типов. Успешная сборка в таком случае означает, что синтаксис удалось преобразовать, но не доказывает соблюдение статических контрактов.

Поэтому отдельно запускают:

```bash
tsc --noEmit
```

Обычно для этого создают команду `typecheck` и запускают её локально и в CI. Во время разработки можно использовать режим наблюдения:

```bash
tsc --noEmit --watch
```

Сборка приложения и проверка типов решают разные задачи: сборщик создаёт исполняемые файлы и обрабатывает ресурсы, а `tsc` анализирует связи типов во всей программе.

`skipLibCheck` пропускает полную проверку файлов деклараций `.d.ts`. Их типы продолжают использоваться при проверке собственного кода, но TypeScript не анализирует полностью внутреннюю согласованность всех деклараций.

Флаг может ускорить проверку и временно обойти конфликт типов зависимостей, но способен скрыть несовместимые или дублирующиеся декларации. Сначала лучше проверить версии зависимостей и пакетов `@types`, а затем принимать `skipLibCheck` как осознанный компромисс.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему <code>strictNullChecks</code> критичен во frontend?</strong></summary>

<dl>
<dd>
<h2></h2>

Во frontend данные часто отсутствуют в определённый момент:

- ответ ещё не загружен;
- параметр URL не найден;
- `ref.current` пока равен `null`;
- поиск в массиве вернул `undefined`;
- необязательное поле отсутствует в ответе.

С выключенным `strictNullChecks` значения `null` и `undefined` совместимы почти с любым типом, поэтому код может без проверки вызвать метод у отсутствующего значения.

С включённым флагом отсутствие нужно явно проверить или выразить в модели состояния:

```ts
const user = users.find((item) => item.id === id);

if (!user) {
  return;
}

user.name.toUpperCase();
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает <code>noImplicitAny</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Он запрещает неявный `any` в местах, где TypeScript не смог вывести подходящий тип.

Например, параметр без контекста потребует явной типизации:

```ts
function print(value) {}
// Ошибка: параметр value неявно имеет тип any.
```

Явный `any` остаётся разрешённым:

```ts
function print(value: any) {}
```

Поэтому флаг не запрещает `any` полностью, а делает каждую потерю проверки типов заметным решением разработчика.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужен <code>noUncheckedIndexedAccess</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Доступ по индексу не всегда гарантирует существование значения:

```ts
const first = items[0];
const user = usersById[id];
```

Массив может быть пустым, а ключ может отсутствовать в словаре. С включённым `noUncheckedIndexedAccess` TypeScript добавляет к результату `undefined`, если существование значения не доказано.

После этого код должен проверить результат:

```ts
const first = items[0];

if (first === undefined) {
  return;
}
```

Для объекта с конечным набором обязательных ключей или tuple с известной обязательной позицией значение остаётся определённым.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что меняет <code>exactOptionalPropertyTypes</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Без этого флага optional-свойство `value?: string` обычно позволяет как полностью убрать свойство, так и явно записать в него `undefined`.

С включённым флагом optional-свойство означает: свойство отсутствует либо содержит значение указанного типа. Явный `undefined` разрешён только тогда, когда он отдельно входит в тип:

```ts
type Options = {
  value?: string | undefined;
};
```

Различие важно, потому что эти объекты ведут себя по-разному во время выполнения:

```ts
{}

// и

{ value: undefined }
```

Во втором случае ключ `value` существует и будет виден через оператор `in`, `Object.keys` и некоторые операции копирования или сериализации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем запускать <code>tsc --noEmit</code>, если Vite успешно собирает проект?</strong></summary>

<dl>
<dd>
<h2></h2>

Vite преобразует TypeScript-файлы в JavaScript, но не выполняет полную проверку типов всей программы.

Например, сборщик может успешно удалить аннотации типов и создать bundle, даже если в коде нарушена сигнатура функции или несовместимо присвоены типы.

Команда:

```bash
tsc --noEmit
```

строит TypeScript-программу, проверяет статические связи и не создаёт выходные JavaScript-файлы.

В CI обычно запускают обе команды:

- `tsc --noEmit` проверяет типы;
- команда сборки проверяет создание приложения, обработку модулей и ресурсов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что выбрать для постепенного перевода JavaScript-проекта?</strong></summary>

<dl>
<dd>
<h2></h2>

Можно разрешить JavaScript-файлы через `allowJs`, а затем постепенно включать их проверку через `checkJs` или комментарий:

```js
// @ts-check
```

Миграцию удобнее выполнять по модулям:

- новые файлы сразу писать со строгими типами;
- постепенно включать проверку существующих директорий;
- принимать внешние или неизвестные данные как `unknown`;
- оставлять временные подавления локальными;
- не отключать `strict` для всего проекта ради нескольких старых файлов.

Так новые проблемы не добавляются, а существующий код можно исправлять постепенно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>@ts-expect-error</code> лучше <code>@ts-ignore</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`@ts-expect-error` сообщает TypeScript, что на следующей строке ожидается конкретная ошибка.

Если после обновления кода или типов ошибка исчезнет, сам комментарий станет ошибкой. Благодаря этому устаревшее подавление можно обнаружить и удалить.

`@ts-ignore` всегда скрывает ошибку следующей строки и не сообщает, что подавление больше не требуется.

Временное исключение лучше оставлять с объяснением причины:

```ts
// @ts-expect-error — неверные типы библиотеки, issue #123
legacyApi(value);
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужны ссылки между TypeScript-проектами (<code>project references</code>)?</strong></summary>

<dl>
<dd>
<h2></h2>

Project references нужны в monorepo или большой кодовой базе, где отдельные приложения и пакеты имеют:

- собственные `tsconfig`;
- явные зависимости друг от друга;
- отдельную сборку;
- собственные декларации или выходные файлы.

Связанный проект указывают через `references`, а в проекте-зависимости включают `composite`.

Команда:

```bash
tsc -b
```

определяет порядок зависимостей, собирает только необходимые проекты и может переиспользовать результаты предыдущей сборки.

Для одного небольшого frontend-приложения project references обычно добавляют лишнюю сложность.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как посмотреть итоговую конфигурацию и понять, почему файл вошёл в проект?</strong></summary>

<dl>
<dd>
<h2></h2>

После нескольких уровней `extends` итоговые настройки можно вывести командой:

```bash
tsc --showConfig
```

Она показывает конфигурацию после наследования и переопределений.

Чтобы понять, какие файлы вошли в TypeScript-программу и по какой причине, используют:

```bash
tsc --explainFiles
```

Для конкретного файла конфигурации передают путь через `--project`:

```bash
tsc --project tsconfig.app.json --showConfig
```

Это помогает находить случайно подключённые тесты, глобальные декларации, Node-типы или файлы из другой части monorepo.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Задача | Настройка или команда |
| --- | --- |
| Проверить отсутствие данных | `strictNullChecks` |
| Не допустить скрытый `any` | `noImplicitAny` |
| Учесть отсутствующий элемент массива или словаря | `noUncheckedIndexedAccess` |
| Различить отсутствие поля и `undefined` | `exactOptionalPropertyTypes` |
| Безопасно использовать отдельный транспилятор | `isolatedModules` |
| Проверить типы отдельно от Vite | `tsc --noEmit` |
| Разделить пакеты monorepo | `references`, `composite`, `tsc -b` |
| Постепенно проверять JavaScript | `allowJs`, `checkJs` |
