## Вопрос

<br>

 💬 **Что такое generics в TypeScript? Когда параметр типа действительно нужен?**

<h2></h2>

<br>
<dl>
<dd>

Generics, или обобщения, позволяют писать функции, типы, интерфейсы и классы, которые работают с разными типами данных, но сохраняют связь между ними. Вместо заранее выбранного конкретного типа используется параметр типа, например `T`.

```ts
function first<T>(items: readonly T[]): T | undefined {
  return items[0];
}

const user = first([{ id: "u1", name: "Ada" }]);
// { id: string; name: string } | undefined
```

Параметр `T` связывает тип элементов массива с результатом функции. При передаче массива пользователей функция возвращает пользователя, при передаче массива строк — строку.

Если вместо `T` использовать `unknown`, информация о типе элемента потеряется и результат будет иметь тип `unknown`. Union тоже не сохранит связь с конкретным вызовом: результат останется объединением всех перечисленных вариантов.

Generic-параметр можно ограничить через `extends`. В этом контексте `extends` означает не наследование класса, а требование к допустимому типу:

```ts
function getById<T extends { id: string }>(
  items: readonly T[],
  id: string,
): T | undefined {
  return items.find((item) => item.id === id);
}
```

Ограничение гарантирует, что у каждого элемента есть строковое поле `id`, поэтому функция может безопасно его читать. При этом остальные поля конкретного `T` не теряются: функция возвращает тот же тип элемента, который получила, а не только `{ id: string }`.

Несколько параметров типов позволяют связать между собой разные части контракта:

```ts
function getProperty<T, K extends keyof T>(object: T, key: K): T[K] {
  return object[key];
}
```

Здесь `T` описывает объект, `K` может быть только одним из его ключей, а результат имеет тип свойства, выбранного через `K`. Например, при выборе числового поля результат будет числом, а при выборе строкового — строкой.

TypeScript обычно самостоятельно выводит generic-параметры из переданных аргументов. В вызове `first(users)` параметр `T` определяется из типа массива `users`, поэтому писать `first<User>(users)` обычно не нужно.

Явный аргумент типа может понадобиться, если данных для вывода недостаточно или нужно заранее зафиксировать допустимый тип. Например, для пустого состояния тип элемента часто указывают явно.

При этом возможность вручную передать аргумент типа не означает, что функция действительно проверила значение. API вида `parseJson<T>(text): T` создаёт ложную безопасность: вызывающий может указать любой `T`, хотя обычный `JSON.parse` не проверяет структуру данных.

Для внешних данных безопаснее вернуть `unknown` и проверить результат либо передать функции схему валидации, которая действительно проверит значение во время выполнения и свяжет проверку с возвращаемым типом.

Generic действительно нужен, когда параметр типа:

- связывает тип входа с типом результата;
- связывает несколько аргументов между собой;
- ограничивает один тип ключами или свойствами другого;
- позволяет сохранить конкретный тип при работе с общей структурой.

Если параметр типа встречается только в одном месте и не создаёт такой связи, generic чаще всего не нужен. Особенно подозрительна функция, в которой `T` используется только в результате и полностью выбирается вызывающим: по смыслу это может быть скрытое утверждение типа.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что означает <code>T extends SomeType</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Это ограничение generic-параметра. Конкретный тип `T` может содержать дополнительные свойства, но обязан соответствовать требованиям `SomeType`.

Например, при ограничении `T extends { id: string }` значение должно иметь строковое поле `id`, но может содержать любые дополнительные поля. Внутри функции доступно свойство `id`, а в результате сохраняется исходный конкретный тип `T`.

В данном контексте `extends` означает совместимость с ограничением, а не наследование класса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем generic отличается от union?</strong></summary>

<dl>
<dd>
<h2></h2>

Union описывает несколько возможных типов значения, но обычно не сохраняет конкретный вариант между входом и результатом.

Generic представляет один конкретный тип, который определяется отдельно для каждого вызова, и позволяет передать информацию об этом типе между частями контракта.

Например, `first<T>(items: T[])` при передаче `string[]` возвращает `string | undefined`. Если вместо generic использовать заранее составленный union, результат останется общим union даже тогда, когда конкретный тип входного массива уже известен.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда TypeScript выводит generic автоматически?</strong></summary>

<dl>
<dd>
<h2></h2>

TypeScript пытается вывести generic-параметры из переданных аргументов, ожидаемого типа и контекста функций обратного вызова.

В `first(users)` параметр `T` выводится из типа массива `users`. Поэтому явная запись `first<User>(users)` обычно только дублирует уже известную информацию.

Если входное значение не содержит достаточно информации, например передан пустой массив или `null`, TypeScript может вывести слишком узкий либо неподходящий тип. Тогда аргумент типа указывают явно или изменяют сигнатуру API так, чтобы тип можно было вывести из реальных данных.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>fetchJson&lt;T&gt;()</code> может быть небезопасным?</strong></summary>

<dl>
<dd>
<h2></h2>

Параметр `T` существует только в TypeScript и не передаётся серверу. Сам JSON также не проверяется автоматически.

Поэтому вызов `fetchJson<Admin>()` может фактически получить объект другой структуры, но TypeScript всё равно будет считать результат типом `Admin`.

Если функция не выполняет проверку данных, безопаснее вернуть `unknown`. Если ей передают схему валидации, generic можно связать с этой схемой, например `fetchWithSchema(userSchema)`: тогда возвращаемый тип основан на реально выполненной проверке.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое значение параметра типа по умолчанию (<code>generic default</code>)?</strong></summary>

<dl>
<dd>
<h2></h2>

Generic-параметру можно задать тип по умолчанию:

```ts
type ApiResult<TData, TError = Error> = {
  data?: TData;
  error?: TError;
};
```

Если `TError` не указан явно и TypeScript не вывел для него более конкретный тип, будет использован `Error`.

Параметры без значения по умолчанию должны находиться перед параметрами со значением по умолчанию. Тип по умолчанию также должен соответствовать constraint, если ограничение задано.

Generic default существует только в системе типов и не создаёт значение по умолчанию во время выполнения JavaScript.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где generics применяются в React?</strong></summary>

<dl>
<dd>
<h2></h2>

Generics применяются в таблицах, Select и Combobox, формах, хуках получения данных и компонентах, чьи `props` зависят от типа переданного значения.

Например, `Column<TRecord>` может связать ключ колонки с полями строки таблицы. Generic-компонент Select может связать тип опций со значением, которое получает `onChange`.

Для простого компонента с заранее известными `props` generic не нужен: обычный объектный тип будет понятнее.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда generic не нужен?</strong></summary>

<dl>
<dd>
<h2></h2>

Generic обычно не нужен, если параметр типа используется только один раз и не связывает несколько частей контракта.

Например, параметр `T` в такой функции не даёт полезной связи:

```ts
function logValue<T>(value: T): void {
  console.log(value);
}
```

Если функция принимает любое значение и ничего типизированного на его основе не возвращает, достаточно `unknown`:

```ts
function logValue(value: unknown): void {
  console.log(value);
}
```

Опасен и обратный случай, когда `T` встречается только в результате:

```ts
function getValue<T>(): T {
  return getExternalValue() as T;
}
```

Здесь вызывающий сам выбирает результат, хотя функция ничем не подтверждает этот тип. Такой generic фактически скрывает утверждение типа.

Generic также ухудшает код, когда параметров становится много, их связь трудно объяснить, ошибки TypeScript сложнее полезного API или реализация всё равно требует множества `as`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что дают <code>const</code> type parameters?</strong></summary>

<dl>
<dd>
<h2></h2>

Начиная с TypeScript 5.0 модификатор `const` у параметра типа просит TypeScript сохранять более узкие литеральные типы для значений, созданных непосредственно в вызове.

Без него массив строк внутри переданного объекта может быть выведен как `string[]`, а с `const` type parameter — как более точный readonly-кортеж литералов.

Модификатор влияет только на вывод типов. Он не замораживает объект во время выполнения, не делает заранее созданную изменяемую переменную `readonly` и не заменяет правильно спроектированную сигнатуру функции.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```ts
function pluck<T, K extends keyof T>(
  items: readonly T[],
  key: K,
): Array<T[K]> {
  return items.map((item) => item[key]);
}
```

<details>
<summary><strong>Как связаны <code>T</code>, <code>K</code> и результат?</strong></summary>

<dl>
<dd>
<h2></h2>

`T` описывает тип элемента массива. `K` ограничен ключами `T`, поэтому в функцию нельзя передать имя отсутствующего свойства.

`T[K]` получает тип свойства, выбранного через `K`. Поэтому для `pluck(users, "id")` результат будет массивом значений того же типа, который имеет поле `id`, а не `unknown[]`.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Связь типов |
| --- | --- |
| Таблица | Тип записи `TRecord` связан с допустимыми ключами колонок |
| Select | Тип значения связан с опциями и аргументом `onChange` |
| Хук запроса | Тип аргумента запроса связан с возвращаемыми данными |
| Форма | Имена полей связаны с моделью значений |
| Вспомогательная функция | Ключ `K` ограничен `keyof T` |
| Схема времени выполнения | Проверяющая схема связана с выведенным типом результата |
