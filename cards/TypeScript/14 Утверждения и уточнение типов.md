## Вопрос

<br>

 💬 **Чем отличаются утверждение типа (`type assertion`), `as const` и `satisfies`? Когда каждый из них безопасен?**

<h2></h2>

<br>
<dl>
<dd>

Утверждение типа (`type assertion`) записывается как `value as Type`. Оно просит TypeScript рассматривать значение как указанный тип, но не проверяет и не преобразует его во время выполнения.

```ts
const payload = JSON.parse(text) as User;
```

Если в JSON нет обязательных полей `User`, утверждение всё равно скомпилируется. Следующий код будет считать значение корректным `User`, а ошибка проявится только во время выполнения.

Поэтому `as` уместен, когда разработчик действительно знает факт, который TypeScript не способен вывести или выразить. Такая гарантия может следовать из уже выполненной проверки или из контролируемого внешнего условия. Если значение может оказаться неправильным, например пришло с backend, вместо утверждения нужна реальная проверка данных.

`as const` применяется к литеральному выражению и просит сохранить максимально узкие литеральные типы:

```ts
const statuses = ["idle", "loading", "success"] as const;
// readonly ["idle", "loading", "success"]

type Status = (typeof statuses)[number];
// "idle" | "loading" | "success"
```

У строковых, числовых и boolean-значений сохраняются конкретные литеральные типы, массив становится `readonly` tuple, а свойства объектного литерала получают `readonly`.

Это поведение существует только в системе типов. `as const` не вызывает `Object.freeze` и не запрещает изменить объект во время выполнения через другую изменяемую ссылку.

`satisfies` проверяет, совместимо ли выражение с указанным контрактом, но не заменяет собственный тип выражения этим контрактом:

```ts
type RouteName = "home" | "profile";
type Route = { path: string; auth: boolean };

const routes = {
  home: { path: "/", auth: false },
  profile: { path: "/profile", auth: true },
} satisfies Record<RouteName, Route>;
```

Для такого объектного литерала TypeScript проверит наличие всех ключей `RouteName`, неизвестные ключи и форму каждого маршрута. При этом собственными ключами `routes` останутся `"home"` и `"profile"`, а переменная не получит общий тип `Record<RouteName, Route>`.

`satisfies` не делает значение `readonly`, не преобразует его и не проверяет данные во время выполнения. Он также не гарантирует максимально узкий тип каждого свойства: выражение проходит обычный вывод типов, на который может влиять контекст целевого типа.

Если статической конфигурации нужны одновременно узкие литеральные значения, `readonly`-свойства и проверка общего контракта, используют связку:

```ts
const routes = {
  home: { path: "/", auth: false },
  profile: { path: "/profile", auth: true },
} as const satisfies Record<RouteName, Route>;
```

Сначала `as const` сохраняет литеральные значения и добавляет `readonly` к литеральной структуре. Затем `satisfies` проверяет, совместим ли полученный тип с контрактом.

Главное различие: `as` переопределяет представление значения для компилятора без проверки, `as const` сужает тип литерального выражения и добавляет `readonly`, а `satisfies` проверяет совместимость выражения с контрактом, сохраняя его собственный выведенный тип.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему <code>data as User</code> после <code>fetch</code> небезопасно?</strong></summary>

<dl>
<dd>
<h2></h2>

Утверждение типа не анализирует JSON и не проверяет его поля. Оно только заставляет TypeScript считать значение типом `User`.

Backend может вернуть `null`, объект другой формы или устаревшую версию DTO, но следующий код всё равно получит доступ ко всем полям `User`.

Безопасная граница принимает данные как `unknown`, проверяет их через type guard, parser или схему валидации и только после успешной проверки возвращает значение типа `User`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Ограничивает ли TypeScript произвольный <code>as</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Да. Обычное утверждение разрешено, когда исходный и целевой типы достаточно связаны: обычно один из них должен быть совместим с другим.

Для явно несовместимых типов TypeScript показывает ошибку и предлагает сначала перейти к `unknown`:

```ts
const user = value as unknown as User;
```

Двойное утверждение обходит почти всю защиту типов. Оно допустимо только как редкий локальный адаптер, когда несовпадение типов действительно проверено или гарантировано другим способом.

Использовать `as unknown as Type` только для того, чтобы заставить ошибочный код собраться, небезопасно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Делает ли <code>as const</code> объект глубоко неизменяемым?</strong></summary>

<dl>
<dd>
<h2></h2>

Во время выполнения — нет. `as const` не замораживает объект и не предотвращает реальные изменения.

На уровне типов вложенные объекты и массивы, созданные непосредственно внутри того же литерального выражения, также получают `readonly`-представление.

Но ранее созданная изменяемая ссылка сохраняет собственный тип:

```ts
const items = [1, 2];
const config = { items } as const;

config.items.push(3); // допустимо
```

Нельзя переназначить `config.items`, потому что само свойство `items` является `readonly`. Однако массив был создан отдельно и остаётся изменяемым.

Кроме того, даже `readonly`-представление не мешает изменить тот же объект через другую ссылку с изменяемым типом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>satisfies</code> отличается от явной аннотации переменной?</strong></summary>

<dl>
<dd>
<h2></h2>

Явная аннотация задаёт переменной указанный тип:

```ts
const routes: Record<RouteName, Route> = {
  home: { path: "/", auth: false },
  profile: { path: "/profile", auth: true },
};
```

После этого работа с переменной происходит через общий контракт `Record<RouteName, Route>`.

`satisfies` проверяет, что выражение совместимо с тем же контрактом, но оставляет переменной её собственный выведенный тип.

Поэтому он полезен для конфигураций, где одновременно нужны проверка обязательных ключей и сохранение точной структуры конкретного объекта.

При этом целевой тип `satisfies` может участвовать в контекстном выводе отдельных частей выражения, поэтому оператор не следует воспринимать как гарантию сохранения всех литералов без изменений.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем писать <code>as const satisfies</code> вместе?</strong></summary>

<dl>
<dd>
<h2></h2>

`as const` сохраняет литеральные значения и добавляет `readonly` к литеральной структуре, а `satisfies` проверяет получившийся тип по более широкому контракту.

```ts
const routes = {
  home: "/",
  profile: "/profile",
} as const satisfies Record<RouteName, string>;
```

Сначала объект получает точные значения `"/"` и `"/profile"` и `readonly`-свойства. Затем TypeScript проверяет наличие всех ключей и совместимость значений со `string`.

Связка подходит для таблиц маршрутов, имён событий, статусов, design tokens, или токенов дизайн-системы, и других статических конфигураций.

Если внутри конфигурации находятся массивы или объекты, целевой контракт должен учитывать их `readonly`-тип там, где изменяемость действительно несовместима.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает утверждение о ненулевом значении <code>!</code> (<code>non-null assertion</code>)?</strong></summary>

<dl>
<dd>
<h2></h2>

Постфиксный `!` удаляет `null` и `undefined` из типа без проверки во время выполнения:

```ts
element!.focus();
```

Если `element` фактически равен `null` или `undefined`, код завершится ошибкой. Поэтому `!` безопасен только при реальной гарантии существования значения, которую TypeScript не может вывести.

В React значение `ref.current` зависит от этапа жизненного цикла и может отсутствовать после размонтирования. Поэтому явная проверка обычно надёжнее:

```ts
if (element) {
  element.focus();
}
```

Она одновременно защищает код во время выполнения и документирует необходимое условие.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли писать утверждение типа как <code>&lt;User&gt;value</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

В `.ts` существует угловой синтаксис утверждения типа:

```ts
const user = <User>value;
```

В `.tsx` он конфликтует с синтаксисом JSX. Запись `value as User` работает и в `.ts`, и в `.tsx`, поэтому является стандартным вариантом для React-проектов.

Оба синтаксиса имеют одинаковый смысл и не выполняют проверку значения во время выполнения.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```ts
type Palette = Record<"primary" | "danger", string>;

const palette = {
  primary: "#0057b8",
  danger: "#c62828",
} as const satisfies Palette;

type ColorName = keyof typeof palette;
type ColorValue = (typeof palette)[ColorName];
```

<details>
<summary><strong>Что проверяют <code>as const</code> и <code>satisfies</code>, и какие типы получатся?</strong></summary>

<dl>
<dd>
<h2></h2>

`as const` сохраняет конкретные строковые литералы `"#0057b8"` и `"#c62828"` и делает свойства объекта `readonly`.

`satisfies` проверяет, что присутствуют оба ключа из `Palette`, отсутствуют неизвестные ключи и каждое значение совместимо со `string`.

`ColorName` получит тип:

```ts
"primary" | "danger"
```

`ColorValue` получит тип:

```ts
"#0057b8" | "#c62828"
```

Оба оператора работают только на этапе проверки TypeScript и не изменяют объект во время выполнения.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Подход |
| --- | --- |
| JSON или данные формы | Проверка во время выполнения, а не `as` |
| Статическая конфигурация | `satisfies` проверяет контракт |
| Список статусов или action types | `as const` сохраняет литералы |
| Конфигурация с точными значениями | `as const satisfies Contract` |
| Возврат tuple из хука | Явный tuple или `as const` |
| DOM-ссылка `ref` | Сужение типа предпочтительнее утверждения `!` |
