## Вопрос

<br>

 💬 **Зачем нужен TypeScript во frontend-разработке? Какие задачи он решает и от чего не защищает?**

<h2></h2>

<br>
<dl>
<dd>

TypeScript добавляет к JavaScript синтаксис типов и проверяет код до запуска программы. Редактор или компилятор `tsc` может заранее найти значение неподходящего типа, отсутствующее обязательное поле или неправильный вызов функции. В CI обычно запускают такую же проверку, чтобы код с ошибками типов не попал в сборку.

После преобразования в JavaScript типы удаляются. Браузер не выполняет TypeScript и ничего не знает об объявленных типах.

Основная польза TypeScript заключается в том, что он явно описывает связи между частями программы. Типы задают ожидаемую структуру `props`, аргументов функций, состояния, действий Redux, значений формы, ответов API и экспортов модулей. Такую ожидаемую структуру часто называют контрактом.

Когда контракт меняется, TypeScript показывает места, которые ему больше не соответствуют.

Например, если тип пользователя был таким:

```ts
type User = {
  id: string;
  name: string;
};
```

а поле `name` заменили на `fullName`, TypeScript найдёт обращения к старому полю во всём проверяемом проекте. Это делает технический рефакторинг безопаснее, но не доказывает, что новое поле правильно используется с точки зрения бизнес-логики.

TypeScript также улучшает работу редактора: даёт автодополнение, переход к определению, поиск использований, безопасное переименование и подсказки по доступным свойствам и аргументам. Особенно полезно это становится в большой кодовой базе, где разработчик не может помнить устройство всех модулей.

Типы TypeScript существуют только во время разработки. Например, запись `response.json() as User` не проверяет ответ сервера. Она лишь сообщает TypeScript, что разработчик хочет считать полученное значение типом `User`.

Данные из API, `localStorage`, URL, WebSocket, `postMessage` и стороннего JavaScript могут не соответствовать ожидаемой структуре. Поэтому их сначала считают недоверенными, проверяют во время выполнения и только после успешной проверки используют как данные нужного типа.

TypeScript не гарантирует:

- правильность бизнес-логики;
- соответствие ответа сервера объявленному типу;
- отсутствие ошибок во время выполнения;
- отсутствие сетевых ошибок и сбоев браузерных API;
- безопасность кода, если проверки обходят через `any`, `as` или отключение строгих настроек;
- соответствие устаревших деклараций типов реальному поведению библиотеки.

Использование TypeScript требует поддерживать типы, настраивать `tsconfig.json` и тратить время на проверку кода. Сложные универсальные типы также могут сделать код труднее для чтения.

TypeScript приносит больше пользы, когда включён строгий режим, внешние данные проверяются во время выполнения, а сами типы остаются понятными и не становятся сложнее описываемого кода.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем статическая типизация отличается от динамической?</strong></summary>

<dl>
<dd>
<h2></h2>

Статическая проверка анализирует код до его запуска и определяет, какие значения могут оказаться в конкретном месте программы. Динамическая проверка происходит уже во время выполнения, когда JavaScript работает с фактическим значением.

Например, TypeScript заранее запретит `user.name.toFixed()`, если `name` объявлен строкой. Но только проверка во время выполнения может подтвердить, что сервер действительно прислал строку, а не число, `null` или значение другой формы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие ошибки TypeScript обычно находит?</strong></summary>

<dl>
<dd>
<h2></h2>

TypeScript может найти:

- аргумент неподходящего типа;
- отсутствующее обязательное поле;
- ошибку в имени свойства;
- неправильный тип результата функции;
- неучтённый вариант объединения типов;
- неправильные `props` компонента;
- возможную работу с `null` или `undefined`;
- места, которые перестали соответствовать изменённому контракту.

Полнота проверки зависит от настроек проекта. Например, без `strictNullChecks` TypeScript допускает больше операций с `null` и `undefined`, поэтому часть потенциальных ошибок останется незамеченной.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему TypeScript не проверяет ответ backend автоматически?</strong></summary>

<dl>
<dd>
<h2></h2>

Ответ сервера приходит уже во время выполнения программы как обычный JSON. К этому моменту типы TypeScript удалены, поэтому они не могут проверить фактическую структуру объекта.

Объявление `UserDto` только описывает, какую структуру ожидает frontend. DTO в этом случае — это тип данных, которыми frontend и backend обмениваются между собой.

На границе приложения внешнее значение безопаснее сначала принимать как `unknown`. Затем его структуру проверяют через Zod, Valibot или собственную функцию. Такая функция может проверить свойства объекта и сообщить TypeScript, к какому типу относится значение. Её называют `type guard`.

После успешной проверки DTO при необходимости преобразуют во внутреннюю модель, удобную для приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем type assertion <code>as User</code> отличается от валидации?</strong></summary>

<dl>
<dd>
<h2></h2>

Type assertion, или утверждение типа, меняет только то, как TypeScript воспринимает значение. Оно не добавляет в JavaScript реальную проверку.

Валидация выполняется во время работы программы: она читает фактическое значение, проверяет его структуру и может отклонить неправильные данные.

`as User` допустим, когда разработчик действительно знает о значении больше, чем TypeScript может вывести самостоятельно. Но такое утверждение не должно заменять проверку данных, пришедших из внешнего источника.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли сборка TypeScript выполняет проверку типов?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Vite, Babel, SWC и esbuild могут удалить TypeScript-синтаксис и быстро преобразовать файлы в JavaScript без полной проверки типов.

Поэтому успешная сборка ещё не означает, что в проекте нет ошибок типов. Для отдельной проверки обычно запускают `tsc --noEmit`. Такая команда проверяет типы, но не создаёт JavaScript-файлы. В скриптах проекта её часто называют `typecheck`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему TypeScript не заменяет тесты?</strong></summary>

<dl>
<dd>
<h2></h2>

TypeScript проверяет соответствие значений описанным типам, но не знает, правильно ли работает бизнес-логика.

Например, функция может принимать два числа и возвращать число, поэтому с точки зрения типов всё будет корректно. Но внутри она может использовать неправильную формулу и возвращать ошибочный результат.

Тесты проверяют поведение программы на конкретных сценариях: правильность вычислений, реакции интерфейса, обработку ошибок и взаимодействие частей приложения. Поэтому TypeScript и тесты решают разные задачи и дополняют друг друга.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда TypeScript начинает мешать?</strong></summary>

<dl>
<dd>
<h2></h2>

TypeScript начинает мешать, когда команда систематически обходит его проверки через `any` и цепочки `as`, а типы перестают отражать реальные данные.

Проблемы также возникают, когда типы становятся сложнее самого поведения или разработчики создают универсальную абстракцию без реальной необходимости.

Ещё один опасный случай — когда тип обещает больше, чем проверяется во время выполнения. Например, API-функция объявлена как `Promise<User>`, хотя фактический ответ сервера нигде не проверяется.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли внедрять TypeScript постепенно?</strong></summary>

<dl>
<dd>
<h2></h2>

Да. В существующем JavaScript-проекте можно включить `allowJs`, а затем начать проверять отдельные файлы через `checkJs` или комментарий `// @ts-check`.

После этого модули постепенно переводят на `.ts` и `.tsx`. Строгие настройки также можно включать поэтапно.

Важно ограничивать временное использование `any` и не совмещать большую миграцию на TypeScript с крупным функциональным изменением. Иначе ошибки миграции и изменения поведения будет сложнее отделить друг от друга.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что даёт TypeScript |
| --- | --- |
| Компоненты | Проверяет `props`, события и результат компонента |
| API-слой | Описывает структуру DTO и преобразование проверенных данных во внутреннюю модель |
| Формы | Связывает имена полей, значения и результат отправки |
| Redux и кэш запросов | Согласует состояние, действия, селекторы и типы запросов |
| Рефакторинг | Находит места, нарушенные изменением контракта |
| Библиотечный API | Публикует декларации типов для потребителей |
| CI | Отдельная команда `typecheck` не пропускает несогласованный код |
