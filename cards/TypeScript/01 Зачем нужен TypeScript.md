## Вопрос

Зачем нужен TypeScript во frontend-разработке? Какие задачи он решает и от чего не защищает?

<details>
<summary><strong>Показать ответ</strong></summary>

TypeScript добавляет к JavaScript синтаксис типов и статическую проверку. Статическая проверка выполняется до запуска программы: редактор, `tsc` или CI анализируют код и находят несовместимые значения, отсутствующие поля и другие нарушения описанных контрактов. После компиляции типы удаляются, а браузер выполняет обычный JavaScript.

Основная польза TypeScript заключается в явных связях между частями программы. Типы описывают `props` компонентов, аргументы и результаты функций, состояние, действия Redux, значения формы, ответы API и публичные экспорты модулей. Когда контракт меняется, проверка типов показывает места, которые больше ему не соответствуют.

Например, если ответ пользователя был таким:

```ts
type User = {
  id: string;
  name: string;
};
```

а поле `name` заменили на `fullName`, TypeScript найдёт обращения к старому полю во всём проверяемом проекте. Это делает рефакторинг безопаснее, но не доказывает, что новое имя правильно отображается с точки зрения бизнеса.

TypeScript также улучшает инструменты разработки: автодополнение, переход к определению, поиск использований, безопасное переименование и подсказки по API. Эти возможности строятся на той же модели типов и особенно полезны в большой кодовой базе.

Типы не существуют во время выполнения. Запись `response.json() as User` не проверяет ответ сервера, а только просит компилятор считать значение типом `User`. Данные из API, `localStorage`, URL, WebSocket, `postMessage` и стороннего JavaScript сначала принимают как недоверенные и проверяют во время выполнения, например схемой валидации. Только после этого им присваивают доменный тип.

TypeScript не гарантирует:

- правильность бизнес-логики;
- наличие и форму внешних данных во время выполнения;
- отсутствие ошибок в коде с `any`, небезопасными утверждениями типа через `as` или отключёнными проверками;
- соответствие устаревших деклараций типов реальному поведению библиотеки;
- отсутствие исключений, сетевых ошибок и проблем браузерных API.

Цена TypeScript состоит в поддержке типов, настройке `tsconfig.json`, времени проверки и усложнении некоторых обобщённых API. Польза выше, когда включён строгий режим, внешние границы проверяются во время выполнения, а типы описывают предметную область и остаются проще кода, который они защищают.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Чем статическая типизация отличается от динамической?</summary>

Статическая проверка анализирует возможные значения до запуска программы. Динамическая проверка происходит во время выполнения, когда JavaScript уже получил конкретное значение. TypeScript может заранее запретить `user.name.toFixed()`, потому что `name` объявлен строкой, но только проверка времени выполнения способна подтвердить, что сервер действительно прислал строку.

</details>

<details>
<summary><strong>Вопрос:</strong> Какие ошибки TypeScript обычно находит?</summary>

Несовместимый аргумент, отсутствующее обязательное поле, ошибочное имя свойства, неверный результат функции, неучтённый вариант объединения типов, неправильные `props`, потенциальную работу с `null` или `undefined` и несогласованное изменение контракта. Полнота проверки зависит от настроек: без `strictNullChecks`, например, часть ошибок с отсутствующими значениями не будет обнаружена.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему TypeScript не проверяет ответ backend автоматически?</summary>

Серверный ответ появляется после компиляции и приходит как обычный JSON. TypeScript не добавляет к нему скрытую проверку и не знает, соответствует ли фактический объект объявленному `UserDto`. На границе данные принимают как `unknown`, проверяют структуру через Zod, Valibot или собственную функцию проверки типа (`type guard`), а затем преобразуют в доменную модель.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем type assertion <code>as User</code> отличается от валидации?</summary>

Type assertion, или утверждение типа, влияет только на мнение компилятора и не создаёт JavaScript-проверку. Валидация действительно читает значение во время выполнения и отклоняет неправильную форму. `as User` допустим, когда разработчик знает факт, который TypeScript не может вывести, но он не должен подменять проверку недоверенных данных.

</details>

<details>
<summary><strong>Вопрос:</strong> Всегда ли сборка TypeScript выполняет проверку типов?</summary>

Нет. Vite, Babel, SWC и esbuild могут удалить TypeScript-синтаксис и быстро собрать JavaScript без полной проверки типов. Поэтому в локальных скриптах и CI отдельно запускают `tsc --noEmit`; такую команду часто называют `typecheck`. Успешная транспиляция ещё не означает отсутствие ошибок типов.

</details>

<details>
<summary><strong>Вопрос:</strong> Когда TypeScript начинает мешать?</summary>

Когда строгие проверки систематически обходят через `any` и цепочки `as`, публичные типы становятся сложнее самого поведения либо команда тратит время на универсальную абстракцию без реального сценария. Ещё одна проблема возникает, когда типы обещают больше, чем существует во время выполнения: например, API объявлен как `Promise<User>`, хотя ответ нигде не проверяется.

</details>

<details>
<summary><strong>Вопрос:</strong> Можно ли внедрять TypeScript постепенно?</summary>

Да. В JavaScript-проекте можно сначала включить `allowJs`, проверять отдельные файлы через `checkJs` или `// @ts-check`, затем переводить модули на `.ts` и `.tsx`. Важно ограничивать временный `any`, включать строгие настройки поэтапно и не смешивать миграцию с большим функциональным изменением.

</details>

## Где это встречается во frontend

| Ситуация | Что даёт TypeScript |
| --- | --- |
| Компоненты | Проверяет `props`, события и возвращаемый JSX |
| API-слой | Описывает DTO после проверки во время выполнения и преобразование в доменную модель |
| Формы | Связывает имена полей, значения и результат отправки |
| Redux и кеш запросов | Согласует состояние, actions, или действия, селекторы и ответы endpoints |
| Рефакторинг | Находит места, нарушенные изменением контракта |
| Библиотечный API | Публикует декларации типов для потребителей |
| CI | Отдельная команда `typecheck` не пропускает несогласованный код |
