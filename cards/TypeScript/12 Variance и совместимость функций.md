# Variance и совместимость функций

## Вопрос

<br>

 💬 **Что такое вариантность (`variance`) в TypeScript? Как она влияет на совместимость функций и функций обратного вызова?**

<h2></h2>

<br>
<dl>
<dd>

Variance, или вариантность, описывает правила совместимости составных типов. Она отвечает на вопрос: если `Dog` совместим с более общим типом `Animal`, можно ли заменить тип, работающий с `Animal`, таким же типом, работающим с `Dog`, или наоборот?

```ts
type Animal = { name: string };
type Dog = Animal & { bark(): void };
```

`Dog` совместим с `Animal`, потому что содержит все его свойства. Но для функций направление безопасной замены зависит от того, где используется тип: в результате или в параметре.

Основные виды вариантности:

| Вариантность | Направление совместимости | Пример |
| --- | --- | --- |
| Covariance, ковариантность | Сохраняет направление | `() => Dog` подходит вместо `() => Animal` |
| Contravariance, контравариантность | Меняет направление на обратное | `(value: Animal) => void` подходит вместо `(value: Dog) => void` |
| Invariance, инвариантность | Замена запрещена в обе стороны | Тип одновременно принимает и возвращает `T` |
| Bivariance, бивариантность | Разрешает оба направления | Менее строгая проверка параметров некоторых методов |

Результат функции находится в выходной позиции и обычно ковариантен. Если вызывающий код ожидает получить `Animal`, функция может вернуть более конкретный `Dog`, потому что у него есть все необходимые свойства:

```ts
const createDog = (): Dog => ({
  name: "Rex",
  bark() {},
});

const createAnimal: () => Animal = createDog;
```

Для параметров функции безопасное направление обратное. Обработчик, принимающий любой `Animal`, можно использовать там, где ему будут передавать только `Dog`. Но обработчик только для `Dog` нельзя передать туда, где он может получить любое животное.

```ts
type OnValue = (value: string | number) => void;

const handleString = (value: string) => {
  console.log(value.toUpperCase());
};

const onValue: OnValue = handleString;
// Ошибка при strictFunctionTypes:
// вызывающий код имеет право передать number.
```

Тип `OnValue` обещает, что функция сможет обработать и строку, и число. `handleString` принимает только строку, поэтому не выполняет этот контракт.

Настройка `strictFunctionTypes` включает более строгую проверку параметров для отдельных function types и функций, объявленных как свойства. Она входит в общий режим `strict`.

```ts
type FunctionProperty<T> = {
  handle: (value: T) => void;
};

type Method<T> = {
  handle(value: T): void;
};
```

Свойство `handle` в первом типе проверяется контравариантно. Метод во втором типе исторически может проверяться бивариантно, то есть TypeScript способен разрешить замену параметра и в более широкую, и в более узкую сторону.

Бивариантность удобнее, но менее безопасна: метод может получить значение, с которым фактически не умеет работать. TypeScript сохраняет такое поведение для совместимости с существующими иерархиями классов, DOM-типами и библиотечным кодом.

Общее правило:

- если тип только возвращает `T`, он обычно ковариантен;
- если тип только принимает `T`, он обычно контравариантен;
- если тип и принимает, и возвращает `T`, безопасная совместимость часто требует инвариантности;
- методы и некоторые библиотечные callback-типы могут проверяться менее строго из-за бивариантности.

TypeScript обычно определяет вариантность по тому, как generic-параметр используется внутри типа. Вручную указывать вариантность в обычном frontend-коде, как правило, не требуется.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что такое covariance на примере функции?</strong></summary>

<dl>
<dd>
<h2></h2>

Ковариантность сохраняет исходное направление совместимости типов.

Поскольку `Dog` совместим с `Animal`, функция `() => Dog` совместима с `() => Animal`:

```ts
const createDog: () => Dog = getDog;
const createAnimal: () => Animal = createDog;
```

Вызывающий код ожидает получить объект со свойствами `Animal`. Функция возвращает более конкретный `Dog`, у которого все эти свойства есть, поэтому такая замена безопасна.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое contravariance у параметров функции?</strong></summary>

<dl>
<dd>
<h2></h2>

Контравариантность меняет направление совместимости на обратное.

Обработчик `(animal: Animal) => void` можно использовать там, где ему передадут только `Dog`, потому что он умеет работать с любым животным, включая собаку.

Но обработчик `(dog: Dog) => void` нельзя использовать там, где ему могут передать произвольный `Animal`. Такой обработчик может вызвать `dog.bark()`, хотя контракт `Animal` не гарантирует наличие метода `bark`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда тип становится invariant?</strong></summary>

<dl>
<dd>
<h2></h2>

Инвариантность обычно возникает, когда generic-параметр используется и на выходе, и на входе:

```ts
type Cell<T> = {
  get: () => T;
  set: (value: T) => void;
};
```

`Cell<T>` возвращает `T` через `get` и принимает `T` через `set`.

`Cell<Dog>` нельзя безопасно использовать как `Cell<Animal>`, потому что тогда через `set` в неё можно было бы записать другое животное без метода `bark`.

`Cell<Animal>` также нельзя использовать как `Cell<Dog>`, потому что `get` способен вернуть животное, которое не является собакой.

Поэтому безопасная замена такого типа обычно запрещена в обоих направлениях.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое bivariance и почему TypeScript её допускает?</strong></summary>

<dl>
<dd>
<h2></h2>

Бивариантность разрешает совместимость параметров функции в обоих направлениях: и от более общего типа к более узкому, и наоборот.

Это удобно, но потенциально небезопасно. Обработчик более узкого типа может получить значение, с которым не умеет работать.

TypeScript допускает бивариантность для методов и некоторых специально созданных библиотечных callback-типов ради совместимости с существующим JavaScript-кодом, классами и DOM API.

Поэтому даже режим `strict` не делает систему типов полностью строгой во всех ситуациях. В TypeScript есть намеренные компромиссы между безопасностью и удобством использования.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему методы и function properties могут проверяться по-разному?</strong></summary>

<dl>
<dd>
<h2></h2>

При включённом `strictFunctionTypes` функция, объявленная как свойство, проверяется строже:

```ts
type Listener<T> = {
  handle: (value: T) => void;
};
```

Её параметр проверяется контравариантно.

Метод объявляется другим синтаксисом:

```ts
type Listener<T> = {
  handle(value: T): void;
};
```

Для методов TypeScript сохраняет менее строгую бивариантную проверку параметров. Это исторический компромисс для совместимости с существующими иерархиями классов и библиотечными типами.

Если в собственном контракте callback важна строгая проверка параметра, безопаснее объявлять его свойством-функцией.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как variance проявляется в React?</strong></summary>

<dl>
<dd>
<h2></h2>

Вариантность проявляется в обработчиках событий, `onChange`, render props, generic-компонентах, подписках и reducer-функциях.

Если компонент обещает вызвать `onChange` со значением `string | number`, обработчик должен уметь принять оба варианта. Обработчик только для `string` небезопасен, потому что компонент имеет право передать число.

В generic-компонентах Table или Select вариантность влияет на совместимость функции рендера и обработчика с типом строки или выбранного значения.

Некоторые типы обработчиков React намеренно используют бивариантность, чтобы типизация событий была удобнее и сохраняла совместимость с существующим кодом. Поэтому нельзя считать, что каждый React callback всегда проверяется строго контравариантно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>readonly</code> массив безопаснее изменяемого при совместимости типов?</strong></summary>

<dl>
<dd>
<h2></h2>

`readonly Dog[]` позволяет только читать элементы. Поэтому его безопасно использовать как `readonly Animal[]`: каждый полученный `Dog` также является `Animal`.

Изменяемый массив дополнительно позволяет добавлять элементы через `push` и запись по индексу. Если обращаться с `Dog[]` как с изменяемым `Animal[]`, туда можно записать животное, которое не является собакой:

```ts
declare const dogs: Dog[];

const animals: Animal[] = dogs;
animals.push({ name: "Cat" });
```

После этого в массиве `dogs` окажется значение без метода `bark`.

TypeScript исторически разрешает некоторые подобные присваивания, хотя они потенциально небезопасны. `readonly` убирает операции записи из доступного контракта и делает ковариантное чтение безопаснее.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означают модификаторы <code>in</code> и <code>out</code> у параметров типов?</strong></summary>

<dl>
<dd>
<h2></h2>

Variance annotations позволяют явно указать ожидаемое использование generic-параметра:

- `in` — контравариантный параметр;
- `out` — ковариантный параметр;
- `in out` — инвариантный параметр.

Они могут документировать сложный библиотечный тип и ускорять некоторые сравнения рекурсивных типов.

Эти модификаторы не изменяют реальное использование параметра внутри типа и не позволяют сделать небезопасный тип безопасным. Указанная вариантность должна соответствовать структуре типа.

В обычном прикладном frontend-коде TypeScript самостоятельно определяет вариантность, поэтому `in` и `out` нужны редко.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```ts
type Animal = { name: string };
type Dog = Animal & { bark(): void };

declare function subscribe(handler: (value: Animal) => void): void;

const handleDog = (dog: Dog) => dog.bark();
subscribe(handleDog);
```

<details>
<summary><strong>Почему эта функция обратного вызова небезопасна?</strong></summary>

<dl>
<dd>
<h2></h2>

`subscribe` обещает вызывать обработчик со значением типа `Animal`. Это может быть собака, кошка или другое животное.

`handleDog` умеет работать только с `Dog` и без проверки вызывает метод `bark`. Но контракт `Animal` не гарантирует наличие этого метода.

Поэтому такой callback небезопасен. Обработчик должен принимать `Animal` и самостоятельно проверять, является ли значение собакой, либо функция `subscribe` должна гарантировать, что передаёт только `Dog`.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что проверять |
| --- | --- |
| `onChange` и DOM events | Обработчик принимает каждый обещанный вариант |
| Render props | Renderer не требует более узкие props, чем передаёт компонент |
| Шина событий (`event bus`) | Обработчик подписчика принимает весь тип события |
| Обобщённый Select или Table | Тип записи связан с обработчиком и функцией рендера |
| Store subscription | Обработчик принимает общий тип обновления |
| `readonly` коллекции | Потребитель не получает небезопасную запись |
