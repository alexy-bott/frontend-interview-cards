## Вопрос

<br>

 💬 **Какие основные типы есть в TypeScript? Как работает вывод типов (type inference)?**

<h2></h2>

<br>
<dl>
<dd>

TypeScript описывает возможные значения JavaScript-кода на этапе разработки. Он не создаёт отдельные значения или проверки в браузере: после компиляции остаются обычные строки, числа, объекты и функции JavaScript.

Основные группы типов:

| Группа | Примеры | Смысл |
| --- | --- | --- |
| Примитивы | `string`, `number`, `boolean`, `bigint`, `symbol` | Типы примитивных значений JavaScript |
| Отсутствующие значения | `null`, `undefined` | Отдельные типы при `strictNullChecks` |
| Массивы | `User[]`, `Array<User>` | Коллекция элементов одного типа |
| Кортежи | `[number, number]`, `[data, error]` | Массив с известными позициями и длиной |
| Объекты | `{ id: string; name?: string }` | Набор свойств и их типов |
| Функции | `(value: string) => number` | Параметры и результат вызова |
| Литеральные типы | `"idle"`, `200`, `true` | Одно конкретное значение |
| Композиция | `A | B`, `A & B` | Объединение вариантов или требований |
| Специальные типы | `unknown`, `any`, `never`, `void` | Неизвестность, отключение проверки, невозможность и отсутствие полезного результата |

Type inference, или вывод типов, означает, что TypeScript вычисляет тип по значению и контексту без явной аннотации:

```ts
const name = "Ada";             // "Ada"
let page = 1;                    // number
const users = [{ id: "u1" }];   // { id: string }[]

users.map((user) => user.id);    // user выведен из типа массива
```

У `const` примитивное значение часто сохраняет узкий литеральный тип, потому что переменной нельзя назначить другое значение. У `let` тип обычно расширяется: `let page = 1` получает `number`, поскольку позднее `page` может стать `2`. Свойства изменяемого объекта тоже обычно расширяются, поэтому `{ status: "idle" }` получает свойство `status: string`, если контекст или `as const` не требуют более узкого типа.

Контекст также участвует в выводе. В `button.addEventListener("click", (event) => ...)` тип `event` известен из сигнатуры метода. Это называется контекстной типизацией. Благодаря ей не нужно вручную аннотировать каждую функцию обратного вызова.

Пустая коллекция не даёт информации об элементах. Конкретный результат зависит от места и настроек компилятора: пустой массив внутри объекта или аргумента обобщённого API может быть выведен как `never[]`, а отдельная изменяемая переменная в некоторых сценариях получает расширяющийся `any[]`. Поэтому для пустого состояния доменный тип задают явно:

```ts
const [users, setUsers] = useState<User[]>([]);
const model: { users: User[] } = { users: [] };
```

Аннотация особенно полезна на публичной границе: у экспортируемой функции, структуры API, `props`, состояния библиотеки и значения, которое не содержит достаточно информации для вывода. Для простой локальной переменной повторять очевидный тип обычно не нужно.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему используют <code>string</code>, а не <code>String</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`string` описывает примитивную строку JavaScript. `String` относится к объектной обёртке, которую можно создать через `new String("text")`. Прикладной код почти всегда работает с примитивами, поэтому использует строчные `string`, `number` и `boolean`; объектные `String`, `Number` и `Boolean` создают ненужную и иногда неожиданную совместимость.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем массив отличается от tuple?</strong></summary>

<dl>
<dd>
<h2></h2>

`number[]` содержит произвольное число элементов одного типа. Tuple `[number, string]`, или кортеж, задаёт тип каждой позиции и ожидаемую структуру. Кортеж полезен для координат, пар ключ-значение и результатов хуков, но объект с именованными полями лучше читается, если позиций много или их смысл неочевиден.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>object</code>, <code>{}</code> и <code>Object</code> отличаются?</strong></summary>

<dl>
<dd>
<h2></h2>

`object` означает любое непримитивное значение, включая массив и функцию. Тип `{}` означает любое значение, кроме `null` и `undefined`, поэтому допускает строки и числа. `Object` является типом глобального объектного интерфейса и редко нужен в прикладном коде. Для конкретного объекта лучше описать его поля или использовать `Record<string, unknown>` там, где действительно нужен словарь.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что меняет <code>strictNullChecks</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

При включённой настройке `null` и `undefined` являются отдельными типами. Значение `User | undefined` нужно проверить до чтения полей. Без этой настройки отсутствующее значение считается совместимым со многими типами, поэтому ошибка проявляется только во время выполнения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое literal widening?</strong></summary>

<dl>
<dd>
<h2></h2>

Это расширение конкретного литерала до общего типа. Например, изменяемая переменная `let status = "idle"` получает `string`, потому что ей можно назначить другую строку. Если нужен закрытый набор значений, задают union-аннотацию, `as const` или `satisfies` в зависимости от задачи.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда выводу типов нельзя доверять без аннотации?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда значение не содержит достаточно контекста: пустой массив, `null` как начальное состояние, сложный `reduce`, функция с несколькими допустимыми результатами или публичный API. Аннотация должна уточнять настоящий контракт, а не просто заставлять ошибку исчезнуть через `as`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли проверить TypeScript-тип во время выполнения?</strong></summary>

<dl>
<dd>
<h2></h2>

Интерфейсы, aliases и generics удаляются при компиляции. Проверить можно только реальные признаки JavaScript: `typeof`, `Array.isArray`, `instanceof`, значение поля-дискриминатора или схему объекта. Поэтому `value is User` работает лишь тогда, когда функция действительно проверила структуру `value`.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```ts
const config = {
  mode: "dark",
};

function setMode(mode: "light" | "dark") {}

setMode(config.mode);
```

<details>
<summary><strong>Почему <code>config.mode</code> может иметь тип <code>string</code> и как сохранить литеральный тип?</strong></summary>

<dl>
<dd>
<h2></h2>

Объект остаётся изменяемым, поэтому TypeScript допускает последующее присваивание любой строки и расширяет `"dark"` до `string`. Можно использовать `as const`, чтобы сделать свойства литеральными и `readonly`, либо `satisfies` вместе с подходящим целевым типом, если нужно проверить форму без потери точного вывода.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что важно |
| --- | --- |
| `props` компонента | Явно описать публичную форму объекта |
| Пустое состояние | Передать тип элемента в `useState<User[]>([])` |
| Статусы интерфейса | Использовать литеральный union вместо свободной строки |
| Параметры URL | Сначала получить строки, затем преобразовать в доменный тип |
| Ответ API | Проверить значение во время выполнения, затем присвоить DTO |
| Обработчик события | Использовать контекстный тип, не дублировать очевидную аннотацию |
