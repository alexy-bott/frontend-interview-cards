## Вопрос

<br>

 💬 **Как TypeScript типизирует `map`, `filter`, `find`, `reduce` и `flatMap`? Когда нужен предикат типа (`type predicate`)?**

<h2></h2>

<br>
<dl>
<dd>

Тип результата метода массива зависит от исходного типа элементов, возвращаемого значения callback и выбранной перегрузки метода.

`map` вызывает функцию для каждого элемента и создаёт новый массив. TypeScript выводит тип элементов результата из значения, которое возвращает callback:

```ts
const users: User[] = getUsers();

const ids = users.map((user) => user.id);
// (User["id"])[]
```

Если callback возвращает объект другой формы, результат автоматически получает массив этого типа:

```ts
const options = users.map((user) => ({
  value: user.id,
  label: user.name,
}));
// { value: User["id"]; label: string }[]
```

`flatMap` сначала преобразует каждый элемент, а затем убирает один уровень вложенности. Он удобен, когда один входной элемент должен дать ноль, один или несколько результатов:

```ts
const validIds = rows.flatMap((row) =>
  row.user ? [row.user.id] : [],
);
```

Для строки без пользователя callback возвращает пустой массив, поэтому соответствующее значение не попадает в результат.

`filter` всегда фильтрует массив во время выполнения, но результат на уровне типов зависит от callback.

Если callback возвращает обычный `boolean`, результат обычно сохраняет исходный тип элементов:

```ts
const activeUsers = users.filter(
  (user) => user.active,
);
// User[]
```

Если исходный массив содержит объединение типов, для его сужения используется перегрузка с type predicate, или предикатом типа:

```ts
function isDefined<T>(
  value: T | null | undefined,
): value is T {
  return value !== null && value !== undefined;
}

const users = maybeUsers.filter(isDefined);
// User[]
```

Сигнатура `value is T` означает:

- если функция вернула `true`, значение имеет тип `T`;
- если функция вернула `false`, значение не относится к `T`.

Начиная с TypeScript 5.5 компилятор умеет автоматически выводить предикат для некоторых простых функций:

```ts
const users = maybeUsers.filter(
  (user) => user !== undefined,
);
// User[] в TypeScript 5.5+
```

Для автоматического вывода обычно необходимо, чтобы функция:

- не имела явно указанного возвращаемого типа;
- содержала один явный `return` без неявных путей завершения;
- не изменяла проверяемый параметр;
- возвращала логическое выражение, однозначно сужающее тип.

Например, TypeScript может вывести сужение для проверок `value !== undefined`, `value != null` или `typeof value === "string"`.

Более сложную или переиспользуемую проверку лучше объявлять отдельной функцией с явным type predicate, чтобы её контракт был понятен вызывающему коду.

`filter(Boolean)` работает во время выполнения, но часто является плохим выбором:

```ts
const values = [0, 1, null, 2].filter(Boolean);
// во время выполнения: [1, 2]
```

Он удаляет все falsy-значения:

- `false`;
- `0`;
- `""`;
- `null`;
- `undefined`;
- `NaN`.

Часть этих значений может быть допустимыми данными. Кроме того, стандартный тип функции `Boolean` не выражает точный предикат для конкретного union, поэтому TypeScript не всегда сужает результат так, как ожидает разработчик.

Если нужно удалить только `null` и `undefined`, условие лучше записать явно:

```ts
const values = items.filter(
  (item) => item !== null && item !== undefined,
);
```

`find` возвращает первый подходящий элемент или `undefined`, потому что совпадения может не существовать:

```ts
const user = users.find(
  (item) => item.id === selectedId,
);
// User | undefined
```

У `find` также есть перегрузка с type predicate. Она сужает найденный элемент, но не убирает возможность отсутствия результата:

```ts
const firstAdmin = users.find(isAdmin);
// Admin | undefined
```

`reduce` объединяет элементы массива в одно итоговое значение. Тип аккумулятора зависит от начального значения и выбранной перегрузки.

Пустой объект `{}` не содержит информации о будущих свойствах, поэтому для словаря тип часто задают явно:

```ts
const usersById = users.reduce<
  Record<string, User>
>(
  (result, user) => {
    result[user.id] = user;
    return result;
  },
  {},
);
```

Generic-параметр сообщает, что аккумулятор и итоговое значение имеют тип `Record<string, User>`.

Тип можно задать и через аннотацию начального значения:

```ts
const initial: Record<string, User> = {};

const usersById = users.reduce(
  (result, user) => {
    result[user.id] = user;
    return result;
  },
  initial,
);
```

Если `reduce` требует нескольких утверждений типов, изменяет много независимых структур или становится трудно читать, обычный цикл часто понятнее:

```ts
const usersById: Record<string, User> = {};

for (const user of users) {
  usersById[user.id] = user;
}
```

Явный type predicate является обещанием разработчика. TypeScript использует его сигнатуру, но не доказывает, что реализация действительно соответствует этому обещанию.

Например, следующий предикат некорректен:

```ts
function isSmallNumber(
  value: string | number,
): value is number {
  return (
    typeof value === "number" &&
    value < 10
  );
}
```

При результате `false` значение может быть не только строкой, но и числом больше или равным `10`. Однако объявленный предикат обещает TypeScript, что любой `number` попадает в ветку `true`.

Такую проверку нужно разделить:

```ts
if (typeof value === "number") {
  const isSmall = value < 10;
}
```

Type predicate используют только тогда, когда `true` точно подтверждает заявленный тип, а `false` действительно исключает его из исходного union.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему <code>filter(Boolean)</code> может быть ошибкой даже без TypeScript?</strong></summary>

<dl>
<dd>
<h2></h2>

`Boolean` удаляет все falsy-значения:

```ts
false
0
""
null
undefined
NaN
```

Но они могут быть законными данными.

Для массива цен `0` является допустимой ценой, `false` может быть значимым состоянием флага, а пустая строка — текущим значением поля формы.

```ts
const prices = [0, 100, null];

const result = prices.filter(Boolean);
// [100]
```

Здесь вместе с `null` случайно удаляется допустимый `0`.

Условие фильтра должно выражать конкретную цель:

```ts
const result = prices.filter(
  (price) => price !== null,
);
// [0, 100]
```

Кроме runtime-проблемы, `Boolean` не объявлен как точный type predicate для конкретного union, поэтому TypeScript не обязан удалять из результата именно те типы, которые ожидает разработчик.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда TypeScript 5.5 выводит предикат типа автоматически?</strong></summary>

<dl>
<dd>
<h2></h2>

TypeScript может вывести type predicate, если функция:

- не имеет явно указанного возвращаемого типа;
- содержит один явный `return`;
- не имеет неявных путей завершения;
- не изменяет проверяемый параметр;
- возвращает логическое выражение, связанное с сужением этого параметра.

Например:

```ts
const strings = values.filter(
  (value) => typeof value === "string",
);
```

Если `values` имеет тип `(string | number)[]`, результат получит тип `string[]`.

Также обычно выводятся проверки:

```ts
value !== undefined
value !== null
value != null
```

Автоматический предикат не выводится, если условие не даёт точного двустороннего сужения.

Например, проверка истинности числа:

```ts
const numbers = values.filter(
  (value) =>
    typeof value === "number" && value !== 0,
);
```

не означает, что ветка `false` содержит только нечисловые значения: там также может находиться число `0`.

В такой ситуации результат может сохранить более широкий тип, а условие не следует насильно оформлять как некорректный type predicate.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему неправильный предикат типа опаснее обычного <code>boolean</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычная функция с результатом `boolean` влияет на runtime-фильтрацию, но не обязательно сужает тип для последующего кода.

Type predicate является статическим обещанием:

```ts
function isUser(
  value: unknown,
): value is User {
  // реализацию TypeScript полностью не проверяет
}
```

После результата `true` TypeScript считает значение полноценным `User`.

Если функция проверила только `id`, но пообещала весь объект, последующий код сможет без ошибок компилятора читать отсутствующие поля:

```ts
user.name.toUpperCase();
```

Поэтому предикат должен проверять весь заявленный контракт либо обещать более узкое условие, которое он действительно подтверждает.

Для внешних данных сложную проверку обычно размещают в parser или runtime-схеме, а не маскируют неполную проверку широким type predicate.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему предикат должен правильно описывать и ветку <code>false</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Сигнатура:

```ts
value is User
```

означает не только «при `true` это `User`», но и «при `false` это не `User`».

Это важно в `if/else`, `filter` и функциях разделения массива.

Некорректный пример:

```ts
function isSmallNumber(
  value: string | number,
): value is number {
  return (
    typeof value === "number" &&
    value < 10
  );
}
```

Большое число вернёт `false`, хотя всё ещё имеет тип `number`.

Поэтому в ветке `else` TypeScript может ошибочно считать значение строкой, если доверится объявленному предикату.

Проверку размера лучше выполнять после отдельного сужения:

```ts
if (typeof value === "number") {
  if (value < 10) {
    // маленькое число
  }
}
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>reduce</code> с <code>{}</code> не знает будущие свойства?</strong></summary>

<dl>
<dd>
<h2></h2>

Тип аккумулятора выбирается по начальному значению и generic-параметрам вызова.

Литерал `{}` сам по себе не содержит индексной сигнатуры и не сообщает, какие свойства будут добавлены позднее:

```ts
users.reduce((result, user) => {
  result[user.id] = user;
  // Ошибка: у {} нет строковой индексной сигнатуры.

  return result;
}, {});
```

Функция `reduce` не изменяет уже выбранный тип аккумулятора на основе последующих присваиваний.

Контракт нужно задать явно:

```ts
users.reduce<Record<string, User>>(
  (result, user) => {
    result[user.id] = user;
    return result;
  },
  {},
);
```

Другие варианты:

- аннотировать начальную переменную;
- использовать обычный цикл;
- создать `Map<Id, User>`.

Утверждение:

```ts
{} as Record<string, User>
```

тоже компилируется, но generic-параметр или аннотированная переменная обычно понятнее показывают ожидаемый результат.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда <code>Map</code> лучше <code>Record</code> для результата группировки?</strong></summary>

<dl>
<dd>
<h2></h2>

`Map` удобен, когда:

- ключ имеет тип, отличный от строки или символа;
- значения добавляются динамически;
- отсутствие ключа должно быть явно видно в типе;
- нужны операции `get`, `set`, `has` и `delete`;
- объект не должен иметь свойства прототипа.

```ts
const usersById = new Map<string, User>();

for (const user of users) {
  usersById.set(user.id, user);
}

const user = usersById.get(id);
// User | undefined
```

`Record<FiniteUnion, T>` лучше, когда набор ключей конечный и каждый ключ обязателен:

```ts
type Status = "idle" | "loading";

type Labels = Record<Status, string>;
```

Так TypeScript требует оба свойства.

`Record<string, T>` описывает открытый словарь и без `noUncheckedIndexedAccess` может создавать ложное впечатление, что значение существует по любой строке:

```ts
const user = usersById[unknownId];
// User без noUncheckedIndexedAccess
```

Фактический объект содержит только добавленные ключи.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем <code>noUncheckedIndexedAccess</code>, если методы массива уже типизированы?</strong></summary>

<dl>
<dd>
<h2></h2>

Некоторые методы уже явно отражают отсутствие результата:

```ts
items.find(predicate);
// T | undefined
```

Но обычный доступ по индексу исторически возвращает `T`, хотя массив может быть пуст:

```ts
const first = items[0];
// T без noUncheckedIndexedAccess
```

С включённым флагом:

```ts
const first = items[0];
// T | undefined
```

То же правило применяется к открытым словарям:

```ts
const item = dictionary[key];
// T | undefined
```

Флаг заставляет проверить существование значения, задать значение по умолчанию или использовать тип с конечным набором обязательных ключей.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>flatMap</code> может заменить <code>map(...).filter(...)</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

При сочетании `map` и `filter` сначала может появиться промежуточный массив с отсутствующими значениями:

```ts
const ids = rows
  .map((row) => row.user?.id)
  .filter(isDefined);
```

`flatMap` позволяет вернуть массив из одного значения для сохранения и пустой массив для пропуска:

```ts
const ids = rows.flatMap((row) =>
  row.user ? [row.user.id] : [],
);
```

Итоговый массив сразу содержит только идентификаторы без промежуточного `undefined`.

`flatMap` убирает только один уровень вложенности.

Если фильтрация является отдельным важным этапом или переиспользует понятный type predicate, последовательность:

```ts
filter(isUser).map(...)
```

может читаться лучше, чем объединённый callback `flatMap`.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```ts
type Row = User | null;
declare const rows: Row[];

const users = rows.filter(
  (row): row is User => row !== null,
);

const byId = users.reduce<Record<string, User>>(
  (result, user) => {
    result[user.id] = user;
    return result;
  },
  {},
);
```

<details>
<summary><strong>Что доказывает предикат и чего не гарантирует <code>Record&lt;string, User&gt;</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Предикат:

```ts
(row): row is User => row !== null
```

обещает, что при результате `true` значение имеет тип `User`, а `null` исключается.

Поэтому `users` получает тип:

```ts
User[]
```

и callback `reduce` принимает уже только `User`.

`Record<string, User>` описывает открытый строковый словарь, но реальный объект содержит только те `id`, которые были добавлены во время прохода.

Без `noUncheckedIndexedAccess` чтение произвольного ключа статически имеет тип `User`:

```ts
const user = byId["missing"];
// User
```

Хотя во время выполнения результатом будет `undefined`.

Чтобы учитывать отсутствие значения, можно:

- включить `noUncheckedIndexedAccess`;
- проверять наличие ключа;
- использовать тип `Record<string, User | undefined>`;
- использовать `Map<string, User>`.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Подход |
| --- | --- |
| Элементы API с `null` или `undefined` | `filter(isDefined)` |
| Дискриминированное объединение | Предикат для конкретного варианта |
| Опции Select | `map` или `flatMap` с выведенным результатом |
| Нормализация по `id` | Типизированный `reduce`, цикл или `Map` |
| Поиск записи | `find` плюс обработка `undefined` |
| Чтение по индексу | `noUncheckedIndexedAccess` |
