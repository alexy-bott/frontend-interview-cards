#### Вопрос

Что изменилось в TypeScript 6 и 7? Как безопасно обновить frontend-проект до TypeScript 7?

#### Ответ

TypeScript 6.0 является переходным релизом: он меняет значения по умолчанию и предупреждает об устаревших настройках. В TypeScript 7.0 компилятор и языковая служба редактора (`language service`) переписаны с TypeScript на Go. Новая реализация использует параллельную обработку, а сама версия удаляет настройки, объявленные устаревшими в 6.0.

Для обычного frontend-кода TypeScript 7 не является новым языком с другой моделью типов. Основная совместимость строится через TypeScript 6: проект, который проходит 6.0 с `stableTypeOrdering`, без `ignoreDeprecations` и без ошибок, должен в большинстве случаев получить тот же результат проверки в 7.0.

Главное преимущество TypeScript 7 состоит в производительности. На крупных открытых проектах команда TypeScript измерила ускорение полной проверки типов примерно от 7,7 до 11,9 раза при стандартных настройках. Конкретный результат зависит от проекта. В небольшом проекте разница может быть заметнее в скорости реакции редактора и режима наблюдения за файлами (`watch mode`), чем в CI.

В TypeScript 6/7 изменились значения по умолчанию:

| Настройка | Новое значение по умолчанию | Возможный эффект |
| --- | --- | --- |
| `strict` | `true` | Старый нестрогий код получает ошибки |
| `module` | `esnext` | Нужно явно выбрать модель Node или сборщика |
| `target` | Последняя стабильная ES-версия перед `esnext` | Поддержка старой среды выполнения больше не подразумевается |
| `noUncheckedSideEffectImports` | `true` | Опечатка в импорте только ради побочного эффекта становится ошибкой |
| `rootDir` | Корень проекта | Выходные файлы могут получить лишнюю директорию `src` |
| `types` | `[]` | Глобальные имена Node, Jest или Vitest нужно перечислить явно |

Проекту лучше не зависеть от меняющихся значений по умолчанию. `strict`, `target`, `module`, `moduleResolution`, `rootDir`, `types` и `noEmit` указывают явно в собственной или расширяемой конфигурации.

Настройки, объявленные устаревшими в TypeScript 6, в TypeScript 7 больше не поддерживаются. Среди наиболее важных:

- `target: "es5"` и `downlevelIteration`;
- `moduleResolution: "node"`, `"node10"` и `"classic"`;
- `module: "amd"`, `"umd"`, `"systemjs"` и `"none"`;
- `baseUrl`;
- значения `false` для `esModuleInterop`, `allowSyntheticDefaultImports` и `alwaysStrict`.

Для frontend-приложения со сборщиком вместо старого режима разрешения модулей `node` обычно переходят на `moduleResolution: "bundler"` и `module: "preserve"` либо на ESM-режим, рекомендованный фреймворком. Для Node-программы используют согласованную пару `nodenext`. `paths` больше не требует `baseUrl`: значения делают относительными к проекту, например `"@/*": ["./src/*"]`.

Безопасная последовательность миграции:

1. Зафиксировать одну версию TypeScript в `devDependencies` и lock-файле.
2. Обновиться до TypeScript 6 и убрать предупреждения об устаревших настройках, не оставляя `ignoreDeprecations` постоянным решением.
3. Явно настроить `types`, `rootDir`, режим модулей и целевую версию JavaScript для браузеров.
4. Запустить `tsc --noEmit`, production-сборку, тесты и при наличии генерацию `.d.ts`.
5. Проверить поддержку TypeScript 7 у ESLint, плагинов фреймворка, загрузчиков webpack и инструментов, использующих Compiler API.
6. Обновиться до 7.0 и сравнить ошибки, выходные декларации и время CI.

Критическое ограничение TypeScript 7.0: первая версия на Go не предоставляет Compiler API, то есть программный интерфейс компилятора. Инструмент, который импортирует пакет `typescript`, вызывает `createProgram`, работает с абстрактным синтаксическим деревом (AST) или API языковой службы, может временно требовать TypeScript 6. Команда TypeScript предоставляет пакет совместимости `@typescript/typescript6` и допускает параллельную установку, но это переходная мера, а не причина смешивать версии без необходимости.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Почему TypeScript 7 стал значительно быстрее?
>
> **Ответ:** Компилятор и языковая служба переписаны на Go и используют многопоточную среду выполнения. Разбор файлов, проверка типов, создание выходных файлов, сборка связанных TypeScript-проектов и инфраструктура режима наблюдения получили параллельную или полностью новую реализацию. Ускорение связано с архитектурой инструмента, а не с уменьшением количества проверок пользовательского кода.

> [!followup]
> **Вопрос:** Изменяет ли TypeScript 7 JavaScript bundle приложения?
>
> **Ответ:** Сам по себе переход не добавляет библиотеку времени выполнения и не меняет модель JavaScript. Но новые значения по умолчанию и удалённые настройки могут изменить выход `tsc` или потребовать другую конфигурацию модулей. В Vite-проекте с `tsc --noEmit` итоговый bundle создаёт Vite, однако поиск типов и ошибки проекта всё равно могут измениться.

> [!followup]
> **Вопрос:** Почему после обновления исчезли `process`, `describe` или типы Node?
>
> **Ответ:** В TypeScript 6/7 значением `types` по умолчанию стал пустой массив. Нужно перечислить используемые глобальные пакеты в подходящем проекте, например `types: ["node"]` для скриптов или `types: ["vitest/globals"]` для тестов. Лучше иметь отдельные `tsconfig`, чем добавлять все глобальные имена в браузерный код.

> [!followup]
> **Вопрос:** Почему выходные файлы внезапно оказались в `dist/src`?
>
> **Ответ:** Изменилось значение `rootDir` по умолчанию: оно больше не определяется прежним способом по внутренней директории исходников. Если ожидается `src/index.ts -> dist/index.js`, нужно явно указать `rootDir: "./src"` и проверить `include`. В приложении с `noEmit` это проявится только в инструментах, которые всё же создают файлы или декларации.

> [!followup]
> **Вопрос:** Чем заменить `baseUrl`?
>
> **Ответ:** Если он использовался только для `paths`, удалить `baseUrl` и записать путь каждого псевдонима относительно `tsconfig`, например `"@/*": ["./src/*"]`. Если импорты по имени раньше искались относительно `baseUrl`, лучше перейти на явные псевдонимы, поле `imports` в `package.json` или workspace-пакеты, которые понимает среда выполнения.

> [!followup]
> **Вопрос:** Зачем сначала обновляться до TypeScript 6?
>
> **Ответ:** Он показывает предупреждения об устаревших настройках и сохраняет временный `ignoreDeprecations: "6.0"`, тогда как TypeScript 7 уже удаляет эти параметры. `stableTypeOrdering` в 6.0 помогает заранее увидеть различия в порядке типов и деклараций, хотя может заметно замедлить проверку и предназначен только для диагностики миграции.

> [!followup]
> **Вопрос:** Почему TypeScript 7.0 без Compiler API может повлиять на ESLint или webpack loader?
>
> **Ответ:** Некоторые инструменты не просто запускают `tsc`, а программно импортируют компилятор и работают с AST, модулем проверки типов (`type checker`) или языковой службой. TypeScript 7.0 пока не предоставляет этот API. Перед обновлением проверяют примечания к выпуску конкретного инструмента; при необходимости временно оставляют TypeScript 6 для API-зависимости или используют официальный вариант параллельной установки.

> [!followup]
> **Вопрос:** Нужно ли увеличивать `--checkers` и `--builders` в CI?
>
> **Ответ:** Не автоматически. Большее число рабочих процессов может ускорить большой проект, но увеличивает потребление памяти, а сочетание `checkers × builders` быстро создаёт слишком много параллельной работы. Сначала измеряют стандартный режим в реальном CI-окружении, затем фиксируют значение. Для среды с ограниченными ресурсами или отладки существует `--singleThreaded`.

> [!followup]
> **Вопрос:** Как гарантировать одинаковую версию TypeScript у команды и CI?
>
> **Ответ:** Хранить TypeScript в `devDependencies`, фиксировать граф зависимостей lock-файлом, устанавливать зависимости через `npm ci`, `pnpm install --frozen-lockfile` или эквивалент и запускать локальный исполняемый файл через скрипт `package.json`. Глобальный `tsc` не должен определять результат проекта. Версию обновляют отдельным pull request с полным набором проверок.

#### Мини-задача

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "rootDir": "./src",
    "types": ["vite/client"],
    "noUncheckedSideEffectImports": true,
    "noEmit": true,
    "paths": {
      "@/*": ["./src/*"]
    }
  },
  "include": ["src"]
}
```

> [!followup]
> **Вопрос:** Какие проблемы миграции этот конфиг устраняет и что нужно проверить отдельно?
>
> **Ответ:** Он не зависит от новых значений по умолчанию для `strict`, `target`, `module`, `rootDir` и `types`, не использует удалённый `baseUrl` и выбирает разрешение модулей для сборщика. Отдельно настраивают псевдоним пути в Vite, тестовый `tsconfig` и реальные целевые браузеры. Если JavaScript запускается напрямую в Node, режим `Bundler` нужно заменить согласованным Node-режимом.

#### Где это встречается во frontend

| Ситуация | Что проверить |
| --- | --- |
| Приложение Vite или webpack | Разрешение модулей сборщиком и поддержку загрузчиков и плагинов |
| Next.js | `tsconfig` фреймворка и поддерживаемую версию компилятора |
| Монорепозиторий | Связи проектов и память для `checkers × builders` |
| CI | Lock-файл, локальный `tsc`, проверку типов и сборку |
| ESLint, codegen или loader | Зависимость от отсутствующего в 7.0 Compiler API |
| Библиотека | `.d.ts`, стабильность порядка типов и `exports` пакета |
