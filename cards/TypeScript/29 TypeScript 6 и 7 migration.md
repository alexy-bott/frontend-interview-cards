## Вопрос

<br>

 💬 **Что изменилось в TypeScript 6 и 7? Как безопасно обновить frontend-проект до TypeScript 7?**

<h2></h2>

<br>
<dl>
<dd>

TypeScript 6.0 является переходным релизом и последней основной версией старого компилятора, написанного на TypeScript. Он меняет значения некоторых настроек по умолчанию, предупреждает об устаревших возможностях и помогает подготовить проект к TypeScript 7.

В TypeScript 7.0 компилятор и языковая служба редактора (`language service`) переписаны на Go. Новая реализация использует нативный код и параллельную обработку, а настройки и возможности, объявленные устаревшими в TypeScript 6, больше не поддерживаются.

Для обычного frontend-кода TypeScript 7 не является новым языком с другой моделью типов. Он старается сохранить поведение TypeScript 6: проект, который успешно проверяется в 6.0 с включённым `stableTypeOrdering` и без подавления устаревших настроек через `ignoreDeprecations`, в большинстве случаев должен получить тот же результат в 7.0.

Главное преимущество TypeScript 7 — производительность. На нескольких крупных открытых проектах команда TypeScript измерила ускорение полной проверки и сборки примерно от 7,7 до 11,9 раза. Это результаты конкретных проектов, а не гарантия для любого кода. В небольшом приложении разница может быть заметнее в скорости запуска редактора, диагностике и режиме наблюдения за файлами (`watch mode`), чем в CI.

В TypeScript 6 появились новые значения по умолчанию, которые TypeScript 7 также использует:

| Настройка | Новое значение по умолчанию | Возможный эффект |
| --- | --- | --- |
| `strict` | `true` | Старый нестрогий код получает ошибки |
| `module` | `esnext` | Нужно явно выбрать модель Node или сборщика |
| `target` | Последняя стабильная ES-версия перед `esnext` | Целевая версия JavaScript может изменяться при обновлении TypeScript |
| `noUncheckedSideEffectImports` | `true` | Опечатка в импорте только ради побочного эффекта становится ошибкой |
| `libReplacement` | `false` | Пользовательская замена стандартных библиотек больше не ищется автоматически |
| `stableTypeOrdering` | `true` в TypeScript 7 | Порядок вывода типов соответствует новому компилятору и не может быть отключён |
| `rootDir` | Каталог с `tsconfig.json` | Выходные файлы могут получить лишнюю директорию `src` |
| `types` | `[]` | Глобальные типы Node, Jest или Vitest нужно перечислить явно |

Проекту лучше не зависеть от меняющихся значений по умолчанию. `strict`, `target`, `module`, `moduleResolution`, `rootDir`, `types`, `noUncheckedSideEffectImports` и `noEmit` указывают явно в собственной или расширяемой конфигурации.

Настройки, объявленные устаревшими в TypeScript 6, в TypeScript 7 больше не поддерживаются. Среди наиболее важных:

- `target: "es5"` и `downlevelIteration`;
- `moduleResolution: "node"`, `"node10"` и `"classic"`;
- `module: "amd"`, `"umd"`, `"systemjs"` и `"none"`;
- `baseUrl`;
- значения `false` для `esModuleInterop`, `allowSyntheticDefaultImports` и `alwaysStrict`.

Некоторые изменения вступили в силу уже в TypeScript 6. Например, был удалён `outFile`, перестала поддерживаться директива `/// <reference no-default-lib="true"/>`, а запуск `tsc` с отдельными файлами рядом с `tsconfig.json` теперь требует явно указать `--ignoreConfig`.

Для frontend-приложения со сборщиком вместо старого режима разрешения модулей `node` обычно переходят на `moduleResolution: "bundler"` и `module: "preserve"` либо на другой ESM-режим, рекомендованный фреймворком. Для программы, запускаемой напрямую в Node.js, используют согласованную пару `nodenext`. `paths` больше не требует `baseUrl`: значения делают относительными к каталогу проекта, например `"@/*": ["./src/*"]`.

Безопасная последовательность миграции:

1. Зафиксировать одну версию TypeScript в `devDependencies` и lock-файле.
2. Обновиться до TypeScript 6 и устранить ошибки и предупреждения об устаревших настройках. `ignoreDeprecations` не оставлять постоянным решением.
3. Временно запустить TypeScript 6 со `stableTypeOrdering`, чтобы заранее увидеть различия с TypeScript 7. Не использовать эту настройку в 6.0 постоянно, потому что она может замедлять проверку.
4. Явно настроить `types`, `rootDir`, режим модулей и целевую версию JavaScript для браузеров.
5. Запустить `tsc --noEmit`, production-сборку, тесты и при наличии генерацию `.d.ts`.
6. Проверить поддержку TypeScript 7 у ESLint, плагинов фреймворка, загрузчиков webpack и инструментов, использующих Compiler API.
7. Обновиться до TypeScript 7 и сравнить диагностику, выходные декларации, работу редактора и время CI.

Критическое ограничение TypeScript 7.0: эта версия не предоставляет Compiler API, то есть программный интерфейс компилятора. Инструмент, который импортирует пакет `typescript`, вызывает `createProgram`, работает с абстрактным синтаксическим деревом (AST) или API проверки типов, может временно требовать TypeScript 6.

Для таких случаев существует пакет совместимости `@typescript/typescript6`. Он предоставляет отдельную команду `tsc6` и повторно экспортирует API TypeScript 6, поэтому TypeScript 7 можно использовать как основной `tsc`, а старую версию оставить только конкретному инструменту. Параллельная установка нужна не всем проектам и должна применяться только при реальной зависимости от Compiler API.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему TypeScript 7 стал значительно быстрее?</strong></summary>

<dl>
<dd>
<h2></h2>

Компилятор и языковая служба переписаны на Go и используют нативный код, общую память и несколько потоков выполнения. Разбор файлов, проверка типов, создание выходных файлов и сборка связанных TypeScript-проектов могут выполнять часть работы параллельно.

Ускорение связано с новой архитектурой инструмента, а не с уменьшением количества проверок пользовательского кода. Новый компилятор стремится сохранить результат проверки TypeScript 6, но выполняет ту же работу быстрее.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие изменения, кроме производительности, могут повлиять на код?</strong></summary>

<dl>
<dd>
<h2></h2>

TypeScript 6 изменил некоторые правила вывода типов в обобщённых вызовах, включая отдельные случаи с JSX, обновил DOM-типы и добавил поддержку `target` и `lib` для `es2025`. Он также добавил типы для новых стандартных API, но наличие типов не означает, что соответствующий API уже поддерживается всеми браузерами.

TypeScript 7 изменил обработку Unicode в некоторых шаблонных строковых типах: символ за пределами базовой многоязычной плоскости, например emoji, теперь воспринимается как одна кодовая точка, а не как две части UTF-16. Также были упрощены и ужесточены некоторые правила анализа JavaScript и JSDoc.

Поэтому после обновления нужно проверять не только `tsconfig`, но и новые ошибки в TypeScript-, JavaScript- и JSX-файлах.

<h2></h2>
</dl>

</details>

<details>
<summary><strong>Изменяет ли TypeScript 7 JavaScript bundle приложения?</strong></summary>

<dl>
<dd>
<h2></h2>

Сам по себе переход не добавляет библиотеку времени выполнения и не меняет модель JavaScript. Типы по-прежнему удаляются при компиляции.

Однако новые значения по умолчанию и удалённые настройки могут изменить JavaScript, создаваемый `tsc`, или потребовать другую конфигурацию модулей. В Vite-проекте с `tsc --noEmit` итоговый bundle создаёт Vite, но правила поиска типов и набор ошибок TypeScript всё равно могут измениться.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему после обновления исчезли <code>process</code>, <code>describe</code> или типы Node?</strong></summary>

<dl>
<dd>
<h2></h2>

В TypeScript 6 и 7 значением `types` по умолчанию стал пустой массив. Раньше TypeScript автоматически подключал все найденные пакеты из `node_modules/@types`, а теперь глобальные типы нужно перечислять явно.

Например, для Node-скриптов указывают `types: ["node"]`, а для тестов — `types: ["vitest/globals"]` или типы другого используемого test runner. Лучше иметь отдельные `tsconfig` для приложения, Node-скриптов и тестов, чем добавлять все глобальные имена в браузерный код.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему выходные файлы внезапно оказались в <code>dist/src</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Изменилось значение `rootDir` по умолчанию. Раньше TypeScript мог определить общую директорию исходных файлов, а теперь при наличии `tsconfig.json` корнем считается каталог, в котором находится этот файл.

Если ожидается преобразование `src/index.ts -> dist/index.js`, нужно явно указать `rootDir: "./src"` и проверить `include`. В приложении с `noEmit` это проявится только в инструментах, которые всё же создают JavaScript или декларации типов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем заменить <code>baseUrl</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Если `baseUrl` использовался только вместе с `paths`, его удаляют, а значения псевдонимов записывают относительно каталога с `tsconfig.json`, например `"@/*": ["./src/*"]`.

Если обычные импорты по имени раньше искались относительно `baseUrl`, лучше перейти на явные псевдонимы, поле `imports` в `package.json` или workspace-пакеты, которые понимают не только TypeScript, но также сборщик и среда выполнения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем сначала обновляться до TypeScript 6?</strong></summary>

<dl>
<dd>
<h2></h2>

TypeScript 6 предупреждает о настройках и возможностях, которые TypeScript 7 уже не поддерживает. Это позволяет исправлять проблемы по одной, а не одновременно разбирать ошибки конфигурации, новые значения по умолчанию и смену компилятора.

В TypeScript 6 можно временно использовать `ignoreDeprecations: "6.0"`, но для перехода на TypeScript 7 все такие предупреждения всё равно нужно устранить. Параметр `stableTypeOrdering` помогает сравнить порядок вывода типов с TypeScript 7, но предназначен только для диагностики миграции и может заметно замедлять проверку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему TypeScript 7.0 без Compiler API может повлиять на ESLint или webpack loader?</strong></summary>

<dl>
<dd>
<h2></h2>

Некоторые инструменты не просто запускают `tsc`, а программно импортируют пакет `typescript` и работают с AST, модулем проверки типов (`type checker`) или языковой службой. TypeScript 7.0 не предоставляет совместимый программный API.

Перед обновлением нужно проверить примечания к выпуску конкретного инструмента. Если инструмент ещё зависит от старого API, для него можно временно оставить TypeScript 6 через `@typescript/typescript6`, а основной проект проверять компилятором TypeScript 7.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли увеличивать <code>--checkers</code> и <code>--builders</code> в CI?</strong></summary>

<dl>
<dd>
<h2></h2>

Не автоматически. TypeScript 7 по умолчанию использует четыре процесса проверки типов, а параметр `--checkers` позволяет изменить их количество. Больше процессов может ускорить крупный проект, но также увеличивает потребление памяти.

`--builders` задаёт количество связанных TypeScript-проектов, которые могут собираться параллельно при использовании `--build`. Эти параметры перемножаются: `--checkers 4 --builders 4` может одновременно запустить до шестнадцати процессов проверки типов.

Сначала нужно измерить стандартный режим в реальном CI-окружении. Для среды с небольшим количеством CPU или памяти число процессов уменьшают. Для отладки и полностью последовательного выполнения существует `--singleThreaded`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как гарантировать одинаковую версию TypeScript у команды и CI?</strong></summary>

<dl>
<dd>
<h2></h2>

TypeScript хранят в `devDependencies`, а точный граф зависимостей фиксируют lock-файлом. В CI зависимости устанавливают через `npm ci`, `pnpm install --frozen-lockfile` или эквивалентную команду выбранного пакетного менеджера.

Проверку запускают через скрипт `package.json`, чтобы использовался локальный `tsc` из проекта, а не глобально установленная версия. Обновление TypeScript лучше выполнять отдельным pull request с проверкой типов, тестами и production-сборкой.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "rootDir": "./src",
    "types": ["vite/client"],
    "noUncheckedSideEffectImports": true,
    "noEmit": true,
    "paths": {
      "@/*": ["./src/*"]
    }
  },
  "include": ["src"]
}
```

<details>
<summary><strong>Какие проблемы миграции этот конфиг устраняет и что нужно проверить отдельно?</strong></summary>

<dl>
<dd>
<h2></h2>

Конфигурация не зависит от новых значений по умолчанию для `strict`, `target`, `module`, `rootDir`, `types` и `noUncheckedSideEffectImports`. Она не использует удалённый `baseUrl`, выбирает разрешение модулей для сборщика и запрещает `tsc` создавать JavaScript.

Отдельно нужно настроить псевдоним `@` в Vite, создать конфигурацию для тестов и Node-скриптов и проверить реальные целевые браузеры. `types: ["vite/client"]` не подключает глобальные типы Node или test runner.

`stableTypeOrdering` в TypeScript 7 всегда включён и отдельно в такой конфигурации не указывается. `libReplacement` нужно настраивать только тогда, когда проект действительно заменяет стандартные файлы библиотек TypeScript.

Если JavaScript запускается напрямую в Node.js, режим `Bundler` нужно заменить согласованным Node-режимом.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что проверить |
| --- | --- |
| Приложение Vite или webpack | Разрешение модулей сборщиком и поддержку загрузчиков и плагинов |
| Next.js | Созданный фреймворком `tsconfig` и поддержку TypeScript 7 используемой версией Next.js |
| Монорепозиторий | Связи проектов, `--builders` и доступную CI-память |
| CI | Lock-файл, локальный `tsc`, проверку типов и production-сборку |
| ESLint, codegen или loader | Зависимость от отсутствующего в TypeScript 7.0 Compiler API |
| Библиотека | Результат генерации `.d.ts`, порядок типов и `exports` пакета |
