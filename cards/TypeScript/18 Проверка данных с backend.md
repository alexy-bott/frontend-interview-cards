## Вопрос

<br>

 💬 **Как безопасно типизировать данные с backend? Зачем разделять DTO и доменную модель?**

<h2></h2>

<br>
<dl>
<dd>

Ответ backend, то есть серверной части приложения, появляется во время выполнения программы. TypeScript проверяет исходный код до запуска и не может подтвердить форму конкретного сетевого ответа.

Параметр типа у HTTP-клиента, аннотация переменной или `as User` описывают ожидания frontend-кода, но не проверяют реальные данные.

Безопасная обработка внешнего ответа состоит из нескольких этапов:

1. Выполнить запрос и отдельно обработать сетевую ошибку или отмену.
2. Проверить HTTP-статус, ожидаемый формат и наличие тела.
3. Разобрать тело ответа, учитывая возможность некорректного JSON.
4. Принять разобранное значение как `unknown` и проверить его во время выполнения.
5. Преобразовать проверенный DTO в модель приложения.
6. Представить возможные сбои явным типом ошибки, по которому UI сможет выбрать действие.

DTO (`Data Transfer Object`, объект передачи данных) описывает транспортный формат backend:

- названия полей;
- допустимость `null`;
- строки дат;
- вложенность ответа;
- служебные поля;
- особенности конкретной версии API.

Доменная модель описывает данные в форме, удобной для бизнес-логики и UI:

```ts
type UserDto = {
  id: string;
  display_name: string | null;
  created_at: string;
};

type User = {
  id: string;
  displayName: string;
  createdAt: Date;
};
```

Преобразующая функция изолирует различия между транспортным контрактом и моделью приложения:

```ts
function toUser(dto: UserDto): User {
  return {
    id: dto.id,
    displayName: dto.display_name ?? "Anonymous",
    createdAt: new Date(dto.created_at),
  };
}
```

DTO отражает то, что передаётся по сети. Доменная модель может дополнительно выражать инварианты приложения: например, `displayName` всегда является строкой, а `createdAt` — корректным объектом `Date`.

В простом API DTO и модель приложения могут совпадать. Не нужно создавать два одинаковых типа механически. Разделение полезно, когда сетевой формат отличается от формы, с которой должен работать остальной код, либо может изменяться независимо от неё.

На внешней границе непроверенное значение представляют как `unknown`. После успешного type guard, то есть функции проверки типа, или разбора по схеме оно получает тип DTO:

```ts
function isUserDto(value: unknown): value is UserDto {
  if (typeof value !== "object" || value === null) {
    return false;
  }

  const candidate = value as Record<string, unknown>;

  return (
    typeof candidate.id === "string" &&
    (typeof candidate.display_name === "string" ||
      candidate.display_name === null) &&
    typeof candidate.created_at === "string"
  );
}
```

Type predicate `value is UserDto` не проверяет данные сам по себе. TypeScript доверяет результату функции, поэтому её реализация должна действительно проверять все свойства и ограничения, на которые полагается последующий код.

После структурной проверки можно проверить семантические ограничения и создать доменную модель:

```ts
function parseUser(value: unknown): User {
  if (!isUserDto(value)) {
    throw new Error("Invalid user response");
  }

  const createdAt = new Date(value.created_at);

  if (Number.isNaN(createdAt.getTime())) {
    throw new Error("Invalid user date");
  }

  return {
    id: value.id,
    displayName: value.display_name ?? "Anonymous",
    createdAt,
  };
}
```

Проверка `typeof created_at === "string"` подтверждает только строковый тип. Она не доказывает, что строка действительно содержит корректную дату, поэтому это условие проверяется отдельно.

Ручной type guard подходит для маленькой стабильной структуры. Но в нём можно забыть поле, вложенный уровень или отдельное бизнес-ограничение.

Для больших DTO удобнее библиотека валидации по схеме, например Zod или Valibot. Многие такие библиотеки позволяют:

- проверить данные во время выполнения;
- получить структурированное описание ошибок;
- преобразовать входное значение;
- вывести TypeScript-тип из схемы и не дублировать структуру вручную.

При этом схема тоже должна правильно описывать реальный контракт. Сам факт использования библиотеки не гарантирует, что все необходимые проверки добавлены.

Проверку размещают в ближайшем общем слое после получения внешних данных и до передачи значения в состояние приложения:

- API-клиенте;
- репозитории;
- адаптере endpoint;
- `baseQuery` или `transformResponse`;
- обработчике WebSocket;
- функции чтения `localStorage`;
- parser параметров URL.

Общую транспортную оболочку можно проверять централизованно, а структуру конкретного ответа — рядом с соответствующим endpoint.

После этой границы компоненты и хранилище состояния должны получать уже проверенную модель. Иначе проверки, преобразования `snake_case`, обработка `null` и разбор дат размножатся по всему приложению.

Ошибки также полезно разделять по причинам. Сетевой сбой, HTTP-статус, некорректный JSON, неправильная форма ответа и ожидаемая бизнес-ошибка требуют разных действий.

API-слой может вернуть явный тип ошибки приложения. UI уже решает, показать ли повтор запроса, перенаправление, ошибки полей формы или общее сообщение.

OpenAPI уменьшает ручное дублирование и позволяет генерировать типы или API-клиент. Но сгенерированный тип подтверждает соответствие клиентского кода спецификации, а не реального ответа конкретного сервера.

Запущенный backend, прокси, кэш или сторонний API могут вернуть другую форму. Поэтому объём runtime-проверок выбирают с учётом доверия к источнику, критичности данных и наличия контрактных тестов.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему <code>response.json() as User</code> не решает проблему?</strong></summary>

<dl>
<dd>
<h2></h2>

`as User` не читает поля объекта и не создаёт проверку в исполняемом JavaScript. Это утверждение типа (`type assertion`): разработчик просит TypeScript считать значение типом `User`.

Backend может вернуть `null`, HTML вместо JSON, объект другой версии или данные с неправильными типами. TypeScript всё равно разрешит обращаться с результатом как с корректным пользователем.

Ошибка проявится позднее, например при рендере или вызове метода отсутствующего поля. Проверка сразу после получения ответа не позволяет неправильному значению распространиться по приложению и сохраняет место возникновения ошибки рядом с внешней границей.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>fetch</code> не отклоняет Promise при <code>404</code> или <code>500</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Для `fetch` HTTP-ответ со статусом `404` или `500` всё равно является успешно полученным ответом. Поэтому Promise обычно выполняется со значением `Response`, а не отклоняется.

Статус нужно проверить явно:

```ts
const response = await fetch("/api/user");

if (!response.ok) {
  throw new Error(`HTTP error: ${response.status}`);
}
```

Promise отклоняется при ошибке самого запроса, например отсутствии сети, невозможности установить соединение или отмене через `AbortController`.

После успешного HTTP-статуса всё ещё возможны отдельные ошибки:

- тело не является корректным JSON;
- `Content-Type` не соответствует ожиданию;
- структура JSON не соответствует DTO;
- данные структурно корректны, но нарушают бизнес-ограничения.

Поэтому проверка `response.ok` является только одним этапом обработки ответа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем валидация отличается от разбора и нормализации данных?</strong></summary>

<dl>
<dd>
<h2></h2>

Валидация проверяет, соответствует ли внешнее значение допустимому контракту. Например, является ли `id` строкой и может ли `display_name` быть `null`.

Разбор (`parsing`) преобразует одно представление в другое:

- ISO-строку в `Date`;
- строку URL-параметра в число;
- текст JSON в JavaScript-значение.

Нормализация приводит несколько допустимых вариантов к единой форме приложения:

- заменяет `null` значением по умолчанию;
- переименовывает `snake_case` в `camelCase`;
- превращает массив записей в словарь по `id`;
- удаляет неизвестные транспортные поля.

Одна библиотечная схема может выполнять несколько этих этапов, но задачи остаются разными: сначала нужно подтвердить допустимость данных, затем привести их к форме приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где именно валидировать ответ?</strong></summary>

<dl>
<dd>
<h2></h2>

Ответ проверяют в ближайшем общем слое после получения внешних данных и до передачи значения в store или UI.

Для RTK Query общую оболочку ответа можно проверять в `baseQuery`, а структуру конкретного endpoint — в `transformResponse`.

WebSocket-сообщение проверяют в обработчике протокола до отправки события подписчикам. Значение из `localStorage` проверяют сразу после `JSON.parse`, а URL-параметр — при чтении маршрута.

Компонент не должен повторно проверять DTO, переименовывать серверные поля или преобразовывать строки дат. Ему лучше получать уже проверенную модель приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли валидировать каждый ответ собственного backend?</strong></summary>

<dl>
<dd>
<h2></h2>

Глубина проверки зависит от риска, доверия к источнику и стоимости ошибки.

Строгая runtime-валидация особенно полезна для:

- платежей;
- прав доступа;
- внешних API;
- нестабильных контрактов;
- критичных настроек;
- данных, сохраняемых надолго;
- сообщений WebSocket с несколькими версиями протокола.

Для внутреннего API со сгенерированным клиентом, серверной валидацией и контрактными тестами можно проверять только критичные ответы или основные инварианты.

Но параметр типа TypeScript в любом случае не является runtime-проверкой и сам по себе не доказывает форму ответа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать с неизвестными дополнительными полями?</strong></summary>

<dl>
<dd>
<h2></h2>

Политику нужно выбрать явно. Парсер может:

- разрешить и сохранить неизвестные поля;
- разрешить, но удалить их из результата;
- считать неизвестное поле ошибкой.

Для внешнего API обычно полезно разрешать новые поля, чтобы добавление сервером необязательного свойства не ломало старый клиент. При этом передавать такие поля дальше в доменную модель необязательно.

Для конфигурации, влияющей на безопасность или поведение системы, строгий запрет неизвестных полей может быть оправдан.

Независимо от выбранной политики приложение должно проверять типы и смысл тех полей, которые оно действительно использует.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли нужно отделять DTO от доменной модели?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Если небольшой стабильный API уже возвращает данные точно в форме, необходимой приложению, два одинаковых типа только создадут лишнее дублирование.

Разделение полезно, когда между транспортом и приложением есть реальные различия:

- `snake_case` и `camelCase`;
- строки дат и объекты `Date`;
- nullable-поля и обязательные значения UI;
- серверные enum и внутренние состояния приложения;
- служебные поля ответа;
- разные версии API;
- объединение данных из нескольких endpoint.

В таком случае DTO не позволяет деталям сетевого формата распространиться по компонентам. После изменения backend обычно меняются DTO и преобразующая функция, а не каждый потребитель.

Отдельная доменная модель также снижает риск случайно отправить обратно служебное UI-поле или использовать транспортное значение без необходимого преобразования.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Достаточно ли OpenAPI для безопасности данных во время выполнения?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. OpenAPI является контрактом и источником генерации типов или клиента, но не проверяет конкретный ответ, который уже пришёл по сети.

Спецификация, сгенерированный клиент и реальный сервер могут временно разойтись. Другую форму также способны вернуть прокси, кэш, тестовый стенд или сторонняя интеграция.

Дополнительные гарантии дают:

- серверная валидация;
- контрактные тесты;
- проверка совместимости схем в CI;
- клиентская runtime-схема;
- мониторинг ошибок разбора ответа.

Объём клиентской проверки выбирают по риску, чтобы не дублировать весь контракт без практической пользы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как представить ошибки API в типах?</strong></summary>

<dl>
<dd>
<h2></h2>

Не следует сводить все ошибки к одному `Error` или строке. Полезно различать:

- отсутствие сети;
- отмену запроса;
- HTTP-ошибку;
- некорректный формат ответа;
- ошибку runtime-валидации;
- ожидаемую бизнес-ошибку;
- ошибки отдельных полей формы.

Discriminated union позволяет сохранить причину сбоя и связанные с ней данные:

```ts
type ApiError =
  | { kind: "network"; cause: unknown }
  | { kind: "aborted" }
  | { kind: "http"; status: number; body: unknown }
  | { kind: "invalid-response"; issues: string[] }
  | {
      kind: "business";
      code: string;
      fieldErrors?: Record<string, string>;
    };
```

После проверки `kind` UI получает только поля соответствующего варианта и может выбрать правильное действие без распознавания случайного текста ошибки.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```ts
type ApiError =
  | { kind: "network"; cause: unknown }
  | { kind: "aborted" }
  | { kind: "http"; status: number; body: unknown }
  | { kind: "invalid-response"; issues: string[] }
  | {
      kind: "business";
      code: string;
      fieldErrors?: Record<string, string>;
    };
```

<details>
<summary><strong>Почему такой union полезнее одного <code>message: string</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Поле `kind` сохраняет причину сбоя и сужает доступные данные конкретного варианта.

UI может:

- не показывать ошибку при осознанной отмене;
- предложить повтор при сетевом сбое;
- отдельно обработать `401` или `403`;
- показать ошибки конкретных полей формы;
- отправить нарушение серверного контракта в мониторинг.

Одна строка смешивает техническую причину, данные для обработки и текст интерфейса. В результате код начинает определять тип ошибки по содержимому сообщения, которое может измениться, локализоваться или совпасть у разных причин.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Источник | Граница проверки |
| --- | --- |
| REST API | API-клиент, репозиторий или адаптер endpoint |
| RTK Query | `baseQuery` для общей оболочки, `transformResponse` для конкретного ответа |
| WebSocket/SSE | Парсер каждого типа сообщения до передачи подписчикам |
| `localStorage` | Сразу после `JSON.parse` |
| URL и query parameters | Разбор при чтении маршрута |
| OpenAPI client | Сгенерированные типы плюс проверка рискованных ответов |
