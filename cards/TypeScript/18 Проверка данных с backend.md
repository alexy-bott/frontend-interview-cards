#### Вопрос

Как безопасно типизировать данные с backend? Зачем разделять DTO и доменную модель?

#### Ответ

Ответ backend, то есть серверной части приложения, приходит во время выполнения программы. TypeScript проверяет только исходный код и не может гарантировать форму полученного значения. Параметр типа у HTTP-клиента, аннотация переменной или `as User` описывают ожидание frontend-кода, но не проверяют сам ответ.

Безопасный путь состоит из нескольких отдельных шагов:

1. Проверить HTTP-результат: статус, `response.ok`, ожидаемый формат и наличие тела.
2. Получить неизвестное значение и проверить его во время выполнения.
3. Преобразовать транспортную форму в модель приложения.
4. Превратить сетевые, серверные и контрактные ошибки в явный тип ошибки UI.

```ts
type UserDto = {
  id: string;
  display_name: string | null;
  created_at: string;
};

type User = {
  id: string;
  displayName: string;
  createdAt: Date;
};

function toUser(dto: UserDto): User {
  return {
    id: dto.id,
    displayName: dto.display_name ?? "Anonymous",
    createdAt: new Date(dto.created_at),
  };
}
```

DTO (`Data Transfer Object`, объект передачи данных) описывает сетевой формат: названия полей, допустимость `null`, строки дат и вложенность ответа. Доменная модель описывает те же данные в форме, удобной для бизнес-логики и UI. В простом API эти типы могут совпадать, но код не должен полагаться на такое совпадение.

На границе непроверенное значение представляют как `unknown`. После успешного type guard (функции проверки типа) или разбора по схеме значение получает тип DTO:

```ts
function isUserDto(value: unknown): value is UserDto {
  if (typeof value !== "object" || value === null) {
    return false;
  }

  const candidate = value as Record<string, unknown>;

  return (
    typeof candidate.id === "string" &&
    (typeof candidate.display_name === "string" ||
      candidate.display_name === null) &&
    typeof candidate.created_at === "string"
  );
}

function parseUser(value: unknown): User {
  if (!isUserDto(value)) {
    throw new Error("Invalid user response");
  }

  const user = toUser(value);

  if (Number.isNaN(user.createdAt.getTime())) {
    throw new Error("Invalid user date");
  }

  return user;
}
```

Ручная функция проверки подходит для маленькой стабильной структуры, но в ней тоже можно ошибиться: она должна проверить каждый значимый уровень объекта. Для больших DTO удобнее библиотека валидации по схеме, например Zod или Valibot. Одна схема проверяет данные, формирует понятные ошибки и позволяет вывести TypeScript-тип без повторного описания структуры.

Проверку размещают в API-клиенте, репозитории, `baseQuery`, `transformResponse`, обработчике WebSocket или функции чтения `localStorage`. После этой границы компоненты и хранилище состояния должны получать уже проверенную модель, иначе одинаковые проверки размножатся по всему приложению.

OpenAPI уменьшает ручное дублирование и позволяет генерировать типы или API-клиент. Но сгенерированный тип доказывает только соответствие клиентского кода спецификации. Он не гарантирует, что запущенный сервер, прокси, кэш или сторонний API действительно вернул заявленную форму.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Почему `response.json() as User` не решает проблему?
>
> **Ответ:** `as User` не читает поля и не создаёт проверку в исполняемом JavaScript. Это утверждение типа (`type assertion`): разработчик просит компилятор довериться ему. Если сервер вернул `null`, HTML вместо JSON или объект другой версии, ошибка проявится позже, например при рендере `user.name`. Проверка сразу после получения ответа сохраняет место возникновения ошибки и не пропускает неподходящее значение в приложение.

> [!followup]
> **Вопрос:** Чем валидация отличается от разбора и нормализации данных?
>
> **Ответ:** Валидация проверяет, допустима ли внешняя форма данных. Разбор (`parsing`) преобразует представление, например ISO-строку в `Date` или строку URL-параметра в число. Нормализация приводит допустимые варианты к единой форме приложения, например заменяет `null` значением по умолчанию или превращает массив записей в словарь по `id`. Одна библиотечная схема может выполнять несколько шагов, но задачи у них разные.

> [!followup]
> **Вопрос:** Где именно валидировать ответ?
>
> **Ответ:** В ближайшем общем слое после получения внешних данных и до хранилища состояния или UI. Для RTK Query это может быть общий `baseQuery`, если ответы имеют одну оболочку, или `transformResponse` конкретного endpoint. WebSocket-сообщение проверяют в обработчике протокола, данные хранилища браузера сразу после `JSON.parse`, URL-параметр при чтении маршрута.

> [!followup]
> **Вопрос:** Нужно ли валидировать каждый ответ собственного backend?
>
> **Ответ:** Глубина зависит от риска, доверия и стоимости. Критичные платежи, права доступа, внешние API и нестабильные контракты проверяют строго. Для внутреннего API с контрактными тестами и сгенерированным клиентом можно проверять только ключевые границы. Но параметр типа TypeScript в любом случае не доказывает форму данных, полученных при выполнении программы.

> [!followup]
> **Вопрос:** Что делать с неизвестными дополнительными полями?
>
> **Ответ:** Политика должна быть явной. Парсер может удалить неизвестные поля, сохранить их или считать ошибкой. Для внешнего API совместимость обычно требует разрешать новые поля, но не передавать их в доменную модель. Для конфигурации, влияющей на безопасность, строгий запрет неизвестных полей может быть оправдан.

> [!followup]
> **Вопрос:** Зачем отделять DTO от доменной модели?
>
> **Ответ:** Чтобы детали сетевого формата не распространялись по компонентам: `snake_case`, поля с `null`, версии `enum`, строки дат и оболочка ответа остаются в API-слое. После изменения backend обычно меняются DTO и преобразующая его функция, а не каждый потребитель. Отдельная модель также снижает риск случайно отправить служебное UI-поле обратно в теле запроса.

> [!followup]
> **Вопрос:** Достаточно ли OpenAPI для безопасности данных во время выполнения?
>
> **Ответ:** Нет. OpenAPI является контрактом и источником генерации, а не проверкой конкретного сетевого ответа. Дополнительную гарантию дают валидация на сервере, контрактные тесты и клиентская схема, проверяющая данные при выполнении программы. Их объём выбирают по риску, чтобы не дублировать весь контракт без практической пользы.

> [!followup]
> **Вопрос:** Как представить ошибки API в типах?
>
> **Ответ:** Не сводить всё к `Error` или строке. Полезно различать отсутствие сети, HTTP-ошибку, отмену запроса, ошибку разбора ответа и ожидаемую бизнес-ошибку, например конфликт или ошибки полей формы. Дискриминированное объединение (`discriminated union`) позволяет UI выбрать повтор запроса, перенаправление, ошибки конкретных полей или общее сообщение без распознавания случайных строк.

#### Мини-задача

```ts
type ApiError =
  | { kind: "network"; cause: unknown }
  | { kind: "http"; status: number; body: unknown }
  | { kind: "invalid-response"; issues: string[] };
```

> [!followup]
> **Вопрос:** Почему такой union полезнее одного `message: string`?
>
> **Ответ:** Поле `kind` сохраняет причину сбоя и сужает доступные данные. UI может предложить повтор для сети, отдельно обработать `401` и отправить контрактную ошибку в мониторинг. Строка сообщения смешивает техническую причину с текстом интерфейса и заставляет распознавать ошибку по содержимому текста.

#### Где это встречается во frontend

| Источник | Граница проверки |
| --- | --- |
| REST API | API-клиент, репозиторий или адаптер endpoint |
| RTK Query | `baseQuery` или `transformResponse` |
| WebSocket/SSE | Парсер каждого типа сообщения |
| `localStorage` | Сразу после `JSON.parse` |
| URL и query parameters | Разбор при чтении маршрута |
| OpenAPI client | Сгенерированные типы плюс проверка рискованных ответов |
