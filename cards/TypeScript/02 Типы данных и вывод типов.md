## Вопрос

<br>

 💬 **Какие основные типы есть в TypeScript? Как работает вывод типов (type inference)?**

<h2></h2>

<br>
<dl>
<dd>

TypeScript описывает возможные значения JavaScript-кода и проверяет их на этапе разработки. Он не создаёт новые значения и не добавляет автоматические проверки в браузере: после компиляции остаются обычные строки, числа, объекты и функции JavaScript.

Основные группы типов:

| Группа | Примеры | Смысл |
| --- | --- | --- |
| Примитивы | `string`, `number`, `boolean`, `bigint`, `symbol` | Типы примитивных значений JavaScript |
| Отсутствующие значения | `null`, `undefined` | Типы отсутствующих значений; при `strictNullChecks` их нужно учитывать отдельно |
| Массивы | `User[]`, `Array<User>` | Коллекция элементов одного типа |
| Кортежи | `[number, number]`, `[data, error]` | Массив, в котором известен тип каждой позиции |
| Объекты | `{ id: string; name?: string }` | Набор свойств и их типов |
| Функции | `(value: string) => number` | Типы параметров и результата вызова |
| Литеральные типы | `"idle"`, `200`, `true` | Одно конкретное допустимое значение |
| Композиция | `A | B`, `A & B` | Один из нескольких типов или сочетание требований нескольких типов |
| Специальные типы | `unknown`, `any`, `never`, `void` | Неизвестное значение, отключение проверки, невозможное значение и отсутствие полезного результата |

Type inference, или вывод типов, означает, что TypeScript может сам определить тип без явной аннотации. Он делает это на основе уже доступной информации: начального значения, контекста использования, возвращаемых выражений и других уже известных типов:

```ts
const name = "Ada";             // "Ada"
let page = 1;                    // number
const users = [{ id: "u1" }];   // { id: string }[]

users.map((user) => user.id);    // user выведен из типа массива
```

У примитивной переменной, объявленной через `const`, TypeScript часто сохраняет узкий литеральный тип. Например, `const name = "Ada"` получает тип конкретного значения `"Ada"`, потому что переменной нельзя присвоить другую строку.

У `let` тип обычно расширяется: `let page = 1` получает тип `number`, поскольку позднее переменной можно присвоить другое число.

Свойства объекта остаются изменяемыми даже тогда, когда сам объект объявлен через `const`. Поэтому у объекта `{ status: "idle" }` свойство `status` обычно получает тип `string`, если более узкий тип не задан контекстом или через `as const`.

Контекст также участвует в выводе. В `button.addEventListener("click", (event) => ...)` TypeScript знает тип `event` из сигнатуры метода `addEventListener`. Это называется контекстной типизацией: тип определяется не только самим значением, но и местом, где оно используется. Благодаря этому не нужно вручную указывать тип каждого параметра callback-функции.

TypeScript также умеет выводить тип результата функции по её `return`. Если разные ветки возвращают разные значения, итоговый тип может стать union из этих вариантов.

Пустой массив `[]` сам по себе не содержит информации о типе будущих элементов. Поэтому его тип особенно зависит от контекста и настроек компилятора. Без подходящего контекста TypeScript может вывести тип, который окажется слишком широким или слишком узким для дальнейшего использования.

Запоминать один универсальный результат вывода для `[]` не нужно. Если массив представляет конкретное состояние или поле модели, тип элемента лучше указать явно:

```ts
const [users, setUsers] = useState<User[]>([]);
const model: { users: User[] } = { users: [] };
```

Явная аннотация особенно полезна там, где нужно закрепить ожидаемый контракт или где TypeScript не получает достаточно информации для хорошего вывода: у `props`, структур API, публичных функций, состояния библиотеки и пустых начальных значений.

Для простой локальной переменной с очевидным начальным значением повторять тип обычно не нужно. Например, запись `const count: number = 0` чаще всего не даёт дополнительной информации по сравнению с `const count = 0`.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Почему используют <code>string</code>, а не <code>String</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`string` описывает обычную примитивную строку JavaScript. `String` относится к объектной обёртке, которую можно создать через `new String("text")`.

В прикладном коде почти всегда работают с примитивами, поэтому используют строчные типы `string`, `number` и `boolean`. Объектные типы `String`, `Number` и `Boolean` нужны редко и могут приводить к значениям, которые ведут себя не так, как обычные примитивы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем массив отличается от tuple?</strong></summary>

<dl>
<dd>
<h2></h2>

`number[]` содержит произвольное количество элементов одного типа.

Tuple `[number, string]`, или кортеж, задаёт тип каждой позиции. Первый элемент должен быть числом, а второй — строкой.

Кортеж полезен для координат, пар ключ-значение и результатов хуков. Если позиций много или их назначение непонятно без пояснения, объект с именованными полями обычно читается лучше.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>object</code>, <code>{}</code> и <code>Object</code> отличаются?</strong></summary>

<dl>
<dd>
<h2></h2>

`object` означает любое непримитивное значение. К нему относятся обычные объекты, массивы и функции, но не строки, числа, `boolean`, `null` и `undefined`.

Тип `{}` означает любое значение, кроме `null` и `undefined`. Поэтому он допускает не только объекты, но также строки, числа и другие примитивы.

`Object` — глобальный объектный тип TypeScript. Он не является синонимом `object`: из-за правил JavaScript с объектными обёртками ему также совместимы многие примитивные значения. Поэтому `Object` почти никогда не выражает нужное ограничение в прикладном коде.

Если известна структура объекта, лучше явно описать его поля. Если нужен объект-словарь с неизвестными значениями, можно использовать `Record<string, unknown>`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что меняет <code>strictNullChecks</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

При включённой настройке `null` и `undefined` являются отдельными типами. Если значение имеет тип `User | undefined`, перед чтением полей нужно убедиться, что пользователь существует.

Без `strictNullChecks` отсутствующие значения считаются совместимыми со многими другими типами. Из-за этого TypeScript не показывает часть потенциальных ошибок, и они могут проявиться только во время выполнения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое literal widening?</strong></summary>

<dl>
<dd>
<h2></h2>

Literal widening — это расширение типа конкретного значения до более общего типа.

Например, переменная `let status = "idle"` получает тип `string`, а не литеральный тип `"idle"`, потому что позднее ей можно присвоить другую строку.

Если значение должно принадлежать закрытому набору вариантов, чаще используют явную union-аннотацию или `as const`. `as const` сохраняет литеральные типы и делает свойства объекта `readonly`.

Оператор `satisfies` решает немного другую задачу: он проверяет совместимость значения с указанным типом, но старается сохранить более точный выведенный тип самого выражения. Поэтому его не следует воспринимать как универсальный способ отключить literal widening.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем type inference отличается от narrowing?</strong></summary>

<dl>
<dd>
<h2></h2>

Type inference определяет тип на основе уже доступной информации, когда явная аннотация не указана. Например, из `const count = 0` TypeScript сам выводит тип значения.

Narrowing работает позже: исходный тип уже известен, но TypeScript делает его более конкретным внутри определённой ветки кода. Например, после проверки `typeof value === "string"` значение типа `string | number` внутри этой ветки сужается до `string`.

То есть inference отвечает на вопрос «какой тип вывести из контекста?», а narrowing — «какой из уже возможных вариантов остался после проверки?».

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда нужно указывать тип явно?</strong></summary>

<dl>
<dd>
<h2></h2>

Явный тип нужен, когда TypeScript не получает достаточно информации из значения или когда разработчик хочет явно закрепить ожидаемый контракт независимо от конкретного начального значения.

Частые примеры:

- пустой массив в состоянии или модели без подходящего контекста;
- `null` как начальное состояние;
- сложный `reduce`;
- функция, для которой важно явно закрепить публичный возвращаемый тип;
- `props` или публичный API;
- состояние, которое позже должно принимать несколько разных типов.

Аннотация должна описывать реальный допустимый тип значения. Не следует использовать `as` только для того, чтобы скрыть ошибку TypeScript.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли проверить TypeScript-тип во время выполнения?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет, если тип существует только в TypeScript. Интерфейсы, aliases и generics удаляются при компиляции и недоступны браузеру.

Во время выполнения можно проверять только реальные признаки JavaScript: результат `typeof`, массив через `Array.isArray`, принадлежность классу через `instanceof`, значение поля-дискриминатора или структуру объекта.

Возвращаемый тип `value is User` сам по себе ничего не проверяет. Он корректен только тогда, когда функция действительно проверила необходимые свойства значения.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```ts
const config = {
  mode: "dark",
};

function setMode(mode: "light" | "dark") {}

setMode(config.mode);
```

<details>
<summary><strong>Почему <code>config.mode</code> может иметь тип <code>string</code> и как сохранить литеральный тип?</strong></summary>

<dl>
<dd>
<h2></h2>

Объект остаётся изменяемым, поэтому TypeScript допускает последующее присваивание любой строки и расширяет `"dark"` до типа `string`.

Запись `as const` сохранит литеральный тип `"dark"`, но одновременно сделает свойства объекта `readonly`.

`satisfies` позволяет проверить объект относительно ожидаемого типа без обычной аннотации всего объекта. Например, `const config = { mode: "dark" } satisfies { mode: "light" | "dark" };` проверяет допустимость `mode`, при этом в этом случае `config.mode` сохраняет более точный тип `"dark"` и свойства не становятся `readonly`.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что важно |
| --- | --- |
| `props` компонента | Явно описать публичную форму объекта |
| Пустое состояние | Передать тип элемента в `useState<User[]>([])` |
| Статусы интерфейса | Использовать литеральный union вместо свободной строки |
| Параметры URL | Сначала получить строки, затем преобразовать в доменный тип |
| Ответ API | Проверить значение во время выполнения, затем использовать тип DTO |
| Обработчик события | Использовать контекстный тип, не дублировать очевидную аннотацию |
