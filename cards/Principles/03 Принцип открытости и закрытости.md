## Вопрос

<br>

 💬 **Что такое Open/Closed Principle? Как применять его во frontend без преждевременных абстракций?**

<h2></h2>

<br>
<dl>
<dd>

Open/Closed Principle, или OCP, предлагает проектировать модуль так, чтобы новые варианты поведения можно было добавлять через стабильный контракт, не переписывая для каждого варианта его основную логику.

Практическая формулировка:

```text
Стабильный механизм остаётся прежним.
Новый вариант подключается через предусмотренную точку расширения.
```

«Закрыт для модификации» не означает, что код полностью запрещено менять.

Изменения всё равно нужны, если:

- найден баг;
- изменился общий контракт;
- нарушена доступность или безопасность;
- прежняя абстракция оказалась неверной;
- новый сценарий не относится к предусмотренной оси расширения.

Модуль закрывают для изменений относительно конкретной вариативности.

Например, таблица может быть открыта для новых колонок, но изменение общей механики сортировки всё равно потребует изменить саму таблицу.

OCP полезен вокруг подтверждённой точки вариативности.

Например, `DataTable` знает, как:

- пройти по строкам;
- отрисовать заголовки;
- вызвать renderer ячейки;
- применить общую механику таблицы.

При этом он не знает состав бизнес-колонок каждой страницы:

```ts
type Column<Row> = {
  id: string;
  header: string;
  render: (row: Row) => React.ReactNode;
};

type DataTableProps<Row> = {
  rows: Row[];
  columns: Column<Row>[];
};
```

Новая колонка добавляется объектом `Column`, а алгоритм таблицы не меняется:

```ts
const userColumns: Column<User>[] = [
  {
    id: "name",
    header: "Имя",
    render: (user) => user.name,
  },
  {
    id: "role",
    header: "Роль",
    render: (user) => user.role,
  },
];
```

Контракт `Column` является точкой расширения.

Он должен описывать не только форму данных, но и ожидаемое поведение:

- когда вызывается `render`;
- какие данные он получает;
- что допустимо вернуть;
- как обрабатываются ошибки;
- какие требования доступности сохраняет таблица.

Другие формы OCP во frontend:

- composition, или композиция, через `children`;
- именованные области интерфейса;
- render functions;
- Strategy, или стратегия;
- Adapter, или адаптер;
- registry обработчиков;
- подключаемые реализации общего контракта.

Например, общий `Dialog` управляет:

- открытием;
- закрытием;
- focus;
- Escape;
- блокировкой фонового взаимодействия.

Предметное содержимое передаётся снаружи:

```tsx
<Dialog
  actions={<DeleteActions />}
>
  <DeleteConfirmation />
</Dialog>
```

Для добавления нового сценария `Dialog` не должен импортировать `DeleteConfirmation`, `ProfileForm` или другие бизнес-компоненты.

При расширении может измениться:

- конфигурация;
- composition root;
- registry;
- вызывающий компонент.

OCP не означает, что новый вариант всегда добавляется без изменения вообще ни одной существующей строки. Важно, чтобы не приходилось переписывать стабильный внутренний алгоритм и добавлять в него знание о каждом бизнес-сценарии.

Абстракция должна следовать за реальной вариативностью.

Если таблица используется только на одной странице, универсальная plugin-система, десятки callbacks и вложенная конфигурация нарушат:

- KISS;
- YAGNI;
- понятность публичного API.

Практический порядок:

1. реализовать первый сценарий прямо и понятно;
2. сравнить его со вторым реальным вариантом;
3. определить, что действительно остаётся стабильным;
4. выделить только существующую ось вариативности;
5. проверить, что расширение проще изменения общего механизма.

OCP не требует объединять любые похожие сценарии.

Если варианты имеют разное поведение, жизненный цикл и контракт, два явных компонента могут быть лучше одного универсального движка.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что значит «открыт для расширения»?</strong></summary>

<dl>
<dd>
<h2></h2>

Предусмотренный новый вариант добавляется снаружи через публичный контракт:

- новую Strategy;
- описание колонки;
- Adapter;
- дочерний компонент;
- render function;
- запись в registry.

Потребитель не копирует внутренний алгоритм и не добавляет условие своего бизнес-сценария внутрь общего модуля.

Например:

```text
новая колонка
→ новый объект Column

новый способ оплаты
→ новая реализация PaymentStrategy

новое содержимое Dialog
→ новый дочерний компонент
```

При этом реализация должна соблюдать весь контракт, а не только совпадать с ним по TypeScript-типам.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что значит «закрыт для модификации»?</strong></summary>

<dl>
<dd>
<h2></h2>

Стабильное ядро не требуется редактировать при каждом новом варианте, который укладывается в предусмотренный контракт.

Например, при добавлении новой колонки меняется конфигурация страницы, но не внутренний цикл рендеринга `DataTable`.

Это не абсолютная неизменяемость.

Общий модуль изменяют, если:

- исправляется ошибка;
- меняется обязательное поведение всех потребителей;
- требуется новая общая возможность;
- контракт оказался недостаточным;
- прежняя точка расширения была выбрана неверно.

OCP защищает ядро от постоянных бизнес-ветвлений, а не запрещает развивать сам модуль.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как композиция поддерживает OCP в React?</strong></summary>

<dl>
<dd>
<h2></h2>

Компонент делегирует изменяемую часть дерева вызывающему коду через:

- `children`;
- именованную область;
- render function;
- отдельный вложенный компонент.

Например, `Dialog` получает содержимое снаружи:

```tsx
<Dialog
  title="Удалить запись?"
  actions={
    <DeleteDialogActions />
  }
>
  <DeleteDialogContent />
</Dialog>
```

Базовый компонент сохраняет общую механику:

- focus management;
- backdrop;
- закрытие по Escape;
- семантику dialog.

Предметный UI расширяет его без новых специальных imports и условий внутри `Dialog`.

Композиция поддерживает OCP, когда публичные области имеют понятные ограничения. Передача десятков несвязанных slots может сделать контракт сложнее самого компонента.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как Strategy связана с OCP?</strong></summary>

<dl>
<dd>
<h2></h2>

Потребитель зависит от общего контракта алгоритма:

```ts
type PriceStrategy = (
  price: number,
) => string;
```

Каждый новый вариант добавляется отдельной реализацией:

```ts
const regularPrice: PriceStrategy =
  (price) => `${price} ₽`;

const discountedPrice: PriceStrategy =
  (price) => `${price * 0.9} ₽`;
```

Потребитель использует переданную стратегию и не знает её внутреннего алгоритма.

Место выбора связывает сценарий с реализацией:

```ts
const priceStrategies = {
  regular: regularPrice,
  discounted: discountedPrice,
};
```

Если для каждой новой Strategy приходится добавлять ветвь в большой `switch` внутри бизнес-модуля, условие лишь перенесено в другое место.

Точку выбора обычно изолируют в:

- composition root;
- factory;
- registry;
- конфигурации функционального модуля.

Strategy полезна, если алгоритмы действительно самостоятельны и имеют общий поведенческий контракт.

Для двух коротких и стабильных условий обычный `if` часто понятнее.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему boolean-флаги часто нарушают OCP?</strong></summary>

<dl>
<dd>
<h2></h2>

Каждый новый флаг может добавить ветвление во внутренний алгоритм:

```tsx
<DataTable
  isOrders
  isAdmin
  isCompact
  withActions
/>
```

Часть комбинаций может быть несовместима:

```text
isOrders + isAdmin
isCompact + withActions
isOrders + isUsers
```

Количество возможных состояний растёт, а общий компонент начинает знать бизнес-варианты потребителей.

Один независимый boolean-флаг не является нарушением сам по себе.

Например:

```tsx
<Button disabled />
```

`disabled` описывает ортогональное состояние кнопки, а не отдельный вид бизнес-компонента.

Проблема начинается, когда флаги кодируют взаимоисключающие разновидности:

```tsx
<Card
  isOrder
  isUser
  isAudit
/>
```

В таком случае обычно лучше использовать:

- отдельные компоненты;
- discriminated union;
- композицию;
- конфигурацию;
- Strategy.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли API, управляемый конфигурацией, лучше?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Конфигурация может постепенно превратиться в собственный язык:

```ts
{
  when: ...,
  then: ...,
  before: ...,
  after: ...,
  nested: ...,
  resolve: ...,
}
```

Если она начинает описывать:

- сложные условия;
- порядок выполнения;
- ветвления;
- зависимости между callbacks;
- скрытое состояние;

обычный код может быть понятнее.

Конфигурация полезна, когда описывает данные или ограниченную вариативность.

Если сценарии сильно отличаются, два явных компонента или функции лучше одного универсального движка.

OCP не требует объединять несовместимые варианты под одним API.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как OCP сочетается с YAGNI?</strong></summary>

<dl>
<dd>
<h2></h2>

OCP отвечает на уже наблюдаемую вариативность.

YAGNI не позволяет создавать точки расширения для гипотетических требований.

Практический порядок:

```text
первый сценарий
→ прямое понятное решение

второй отличающийся сценарий
→ сравнение вариантов

повторяющееся стабильное ядро
→ точка расширения
```

Не следует заранее проектировать plugin-систему на случай, если когда-нибудь появится неизвестный вариант.

Но после появления нескольких реализаций постоянное добавление условий в общий модуль тоже не нужно оправдывать YAGNI.

OCP и YAGNI работают вместе:

```text
не абстрагировать раньше времени
и не игнорировать уже существующую вариативность
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить точку расширения тестами?</strong></summary>

<dl>
<dd>
<h2></h2>

Contract tests, или тесты контракта, проверяют обязательное поведение всех реализаций.

Например, для нескольких Storage-реализаций один набор тестов проверяет:

- сохранение значения;
- чтение отсутствующего значения;
- обработку ошибок;
- удаление данных.

Особенности конкретной реализации проверяются отдельно.

Для таблицы можно разделить тесты:

```text
DataTable
→ общий рендеринг строк и колонок

Column renderers
→ форматирование и действия конкретных колонок
```

Если новый вариант требует:

- обращаться к внутренним деталям;
- отключать часть общих тестов;
- добавлять исключение в основной алгоритм;
- нарушать прежние ожидания;

точка расширения, вероятно, недостаточна или реализации не являются взаимозаменяемыми.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда общий компонент нужно изменить, а не расширять?</strong></summary>

<dl>
<dd>
<h2></h2>

Общий компонент нужно изменить, когда:

- меняется обязательное поведение всех потребителей;
- исправляется доступность;
- устраняется уязвимость;
- исправляется ошибка;
- прежний контракт оказался неверным;
- новый сценарий раскрывает фундаментальное ограничение.

Например, если все варианты `Dialog` неправильно управляют focus, это исправляют в общем компоненте, а не создают отдельный `AccessibleDialog`.

Если новая возможность нужна всем таблицам, её также следует добавить в общее ядро.

Попытка спрятать изменение обязательного поведения в отдельное расширение сохраняет ошибочную основу и создаёт несовместимые варианты.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```text
В общий DataTable для каждой новой страницы добавляют `isOrders`, `isUsers`,
`isAudit` и отдельные ветви внутри ячеек. Как изменить API?
```

Нужно отделить стабильную механику таблицы от бизнес-колонок конкретных страниц:

```ts
type Column<Row> = {
  id: string;
  header: string;
  render: (row: Row) => React.ReactNode;
};

type DataTableProps<Row> = {
  rows: Row[];
  columns: Column<Row>[];
};
```

Каждая функциональная страница создаёт собственную конфигурацию:

```ts
const orderColumns: Column<Order>[] = [
  {
    id: "number",
    header: "Заказ",
    render: (order) => order.number,
  },
  {
    id: "status",
    header: "Статус",
    render: (order) => (
      <OrderStatus status={order.status} />
    ),
  },
];
```

`DataTable` отвечает только за общий алгоритм таблицы, а `OrdersTable`, `UsersTable` и `AuditTable` остаются отдельными функциональными компонентами.

Действия конкретной страницы можно передать:

- через отдельную колонку;
- именованную область;
- render function;
- внешний компонент панели действий.

Не нужно переносить всю бизнес-логику в универсальную конфигурацию. Если страницы имеют разные модели взаимодействия, общим остаётся только действительно стабильное ядро таблицы.

## Где это встречается во frontend

| Стабильное ядро | Точка расширения |
|---|---|
| `DataTable` | Описание колонок и функции рендеринга ячеек |
| `Dialog` | `children`, именованная область действий, управляемое состояние |
| Валидация | Strategy или схема для типа формы |
| Граница API | Новый Adapter с тем же контрактом приложения |
| Постепенное включение функции | Выбор реализации через feature flag |
