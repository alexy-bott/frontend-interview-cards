## Вопрос

<br>

 💬 **Как Liskov Substitution Principle и Interface Segregation Principle применяются к React-компонентам и типам TypeScript?**

<h2></h2>

<br>
<dl>
<dd>

Liskov Substitution Principle, или LSP, требует поведенческой заменяемости.

Если потребитель работает с контрактом типа `T`, реализация подтипа `S` не должна нарушать свойства, которые потребитель вправе ожидать от `T`.

Совпадения методов, полей и TypeScript-типов недостаточно.

Поведенческий контракт включает:

- preconditions, или предусловия — что потребитель обязан выполнить до вызова;
- postconditions, или постусловия — что реализация гарантирует после успешного вызова;
- invariants, или инварианты — какие свойства должны оставаться истинными;
- семантику отсутствующих данных;
- семантику ошибок и отмены;
- побочные эффекты;
- порядок важных операций;
- поведение при повторных вызовах;
- момент, когда асинхронная операция считается завершённой.

Заменяемая реализация не должна:

- требовать более строгие предусловия;
- принимать меньше допустимых входных данных;
- ослаблять обещанные гарантии;
- добавлять неожиданные ошибки;
- менять смысл успешного результата;
- добавлять несовместимые наблюдаемые побочные эффекты.

Например, контракт хранилища обещает:

```ts
type Storage = {
  get(
    key: string,
  ): Promise<string | null>;
};
```

Значение `null` означает, что ключ отсутствует.

Одна реализация соблюдает контракт:

```ts
const memoryStorage: Storage = {
  async get(key) {
    return memory.get(key) ?? null;
  },
};
```

Другая реализация выбрасывает ошибку для отсутствующего ключа:

```ts
const remoteStorage: Storage = {
  async get(key) {
    const response = await fetch(
      `/storage/${key}`,
    );

    if (response.status === 404) {
      throw new Error(
        "Value not found",
      );
    }

    return response.text();
  },
};
```

TypeScript считает обе реализации совместимыми с типом `Storage`, потому что тип `Promise` не описывает тип и условия отклонения.

Но поведение отличается:

```text
MemoryStorage
→ отсутствие значения возвращает null

RemoteStorage
→ отсутствие значения отклоняет Promise
```

Потребитель, корректно работающий с базовым контрактом, сломается после замены реализации.

TypeScript использует structural typing, или структурную типизацию.

Совместимость определяется прежде всего формой значений:

- набором полей;
- типами параметров;
- типом результата;
- доступными методами.

Проверки типов и variance могут обнаружить часть несовместимостей сигнатур, но компилятор не знает:

- одинаково ли реализации трактуют `null`;
- какие ошибки они выбрасывают;
- когда выполняют side effect;
- поддерживают ли отмену;
- является ли операция идемпотентной;
- сохраняют ли HTML-семантику и доступность.

Поэтому поведенческий контракт:

- выражают типами настолько, насколько возможно;
- документируют;
- проверяют общими contract tests, то есть тестами контракта для всех реализаций.

Interface Segregation Principle, или ISP, говорит: потребитель не должен зависеть от части контракта, которую не использует.

Контракт проектируют под конкретную роль потребителя.

Например, компоненту аватара нужны:

```ts
type UserAvatarProps = {
  name: string;
  imageUrl?: string;
};
```

Ему не обязательно передавать полный backend DTO:

```ts
type UserDTO = {
  id: string;
  name: string;
  imageUrl?: string;
  email: string;
  address: string;
  role: string;
  paymentStatus: string;
};
```

Узкий контракт:

- уменьшает связанность;
- скрывает лишние данные;
- упрощает переиспользование;
- не заставляет компонент меняться вместе со всем DTO;
- уменьшает вероятность случайного использования неподходящих полей.

ISP не требует механически создавать отдельный интерфейс для каждого поля.

Контракт должен быть достаточно узким для роли потребителя, но оставаться цельным и понятным.

Во frontend ISP применяется к:

- props компонентов;
- типам функций;
- custom hooks;
- Context;
- selectors хранилища;
- API adapters;
- публичным интерфейсам функциональных модулей.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>LSP относится только к наследованию классов?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Исторически принцип сформулирован для подтипов, но практическая проверка полезна для любых реализаций, которые потребитель должен использовать взаимозаменяемо:

- API-клиентов;
- adapters;
- repository;
- реализаций хранилища;
- React-компонентов с общим контрактом;
- Strategy;
- mock и production-реализаций.

Например, одна и та же функция может принимать:

```ts
type UserRepository = {
  getById(
    id: string,
  ): Promise<User | null>;
};
```

и работать с:

- HTTP repository;
- in-memory repository;
- test mock.

Если потребитель должен узнавать конкретную реализацию:

```ts
if (repository instanceof RemoteRepository) {
  // Особое исключение
}
```

взаимозаменяемость, вероятно, нарушена либо общий контракт недостаточен.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему TypeScript не гарантирует LSP автоматически?</strong></summary>

<dl>
<dd>
<h2></h2>

TypeScript проверяет форму значений, а не полное поведение во время выполнения.

Две функции могут иметь одинаковый тип:

```ts
type GetUser = (
  id: string,
) => Promise<User | null>;
```

Первая возвращает `null` для отсутствующего пользователя:

```ts
const getUserFromMemory: GetUser =
  async (id) => {
    return users.get(id) ?? null;
  };
```

Вторая отклоняет Promise:

```ts
const getUserFromApi: GetUser =
  async (id) => {
    const response = await fetch(
      `/users/${id}`,
    );

    if (response.status === 404) {
      throw new Error(
        "User not found",
      );
    }

    return response.json();
  };
```

TypeScript пропустит обе реализации.

Тип `Promise<User | null>` описывает успешное значение, но не кодирует тип и условия отклонения Promise.

Компилятор также не проверит:

- количество сетевых запросов;
- порядок side effects;
- поддержку отмены;
- семантику повторного вызова;
- доступность React-компонента.

Поэтому LSP проверяется не только типами, но и контрактом поведения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что значит «не усиливать предусловия»?</strong></summary>

<dl>
<dd>
<h2></h2>

Реализация не может требовать от потребителя больше, чем обещает общий контракт.

Например:

```ts
type ImageLoader = (
  url: string,
) => Promise<Blob>;
```

Документация контракта разрешает любой корректный HTTPS URL.

Конкретная реализация не должна без отражения в типе или контракте работать только с одним доменом:

```ts
if (
  !url.startsWith(
    "https://cdn.example.com",
  )
) {
  throw new Error(
    "Unsupported host",
  );
}
```

Потребитель, который корректно передаёт другой HTTPS URL, сломается после замены.

Возможные решения:

- расширить реализацию;
- сузить общий контракт;
- выразить допустимый источник отдельным типом;
- создать другой интерфейс для ограниченного загрузчика.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что значит «не ослаблять гарантии результата»?</strong></summary>

<dl>
<dd>
<h2></h2>

Реализация должна сохранять смысл успешного результата.

Например, общий контракт обещает:

```text
Promise save() выполняется,
когда данные надёжно сохранены
```

Одна реализация записывает данные и только после этого завершает Promise.

Другая завершает Promise сразу после помещения операции во временную очередь:

```text
save()
→ задача добавлена в память
→ Promise успешно выполнен
→ процесс может завершиться
→ данные потеряны
```

Формально обе функции могут возвращать:

```ts
Promise<void>
```

Но значение успешного завершения различается.

Если очередь является частью контракта, это нужно выразить явно:

```ts
type SaveResult =
  | {
      status: "saved";
    }
  | {
      status: "queued";
    };
```

Реализация не должна молча давать более слабую гарантию, чем ожидает потребитель.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как LSP может нарушиться в дизайн-системе?</strong></summary>

<dl>
<dd>
<h2></h2>

Общий `Button` обещает поведение кнопки:

- получение focus;
- активацию клавишами Enter и Space;
- поддержку `disabled`;
- вызов `onClick`;
- отправку формы при `type="submit"`.

Вариант, который визуально похож на кнопку, но отображает:

```tsx
<div onClick={onClick}>
  Сохранить
</div>
```

не является полноценной заменой.

Он нарушает:

- HTML-семантику;
- управление с клавиатуры;
- focus;
- поведение формы;
- accessibility contract.

Для навигации лучше использовать отдельный контракт ссылки.

Если дизайн-система поддерживает polymorphic API через `as` или `asChild`, типы и документация должны явно отражать, что при смене корневого элемента может измениться поведенческий контракт.

Одинаковый внешний вид не означает взаимозаменяемое поведение.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить LSP для нескольких адаптеров?</strong></summary>

<dl>
<dd>
<h2></h2>

Для всех реализаций запускают один набор contract tests.

Например:

```ts
function storageContract(
  createStorage: () => Storage,
) {
  it("возвращает сохранённое значение", async () => {
    const storage = createStorage();

    await storage.set("theme", "dark");

    await expect(
      storage.get("theme"),
    ).resolves.toBe("dark");
  });

  it("возвращает null для отсутствующего ключа", async () => {
    const storage = createStorage();

    await expect(
      storage.get("missing"),
    ).resolves.toBeNull();
  });
}
```

Один набор запускают для:

- `MemoryStorage`;
- `LocalStorageAdapter`;
- `RemoteStorage`.

Contract tests могут проверять:

- отсутствие данных;
- граничные значения;
- ошибки, обещанные контрактом;
- отмену;
- повторные вызовы;
- порядок наблюдаемых side effects.

Они не должны закреплять внутреннюю реализацию.

Например, общий тест не должен требовать конкретное число SQL-запросов, если общий контракт этого не обещает.

У каждой реализации дополнительно остаются интеграционные тесты инфраструктурных деталей.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как ISP применяется к props?</strong></summary>

<dl>
<dd>
<h2></h2>

Props отражают роль компонента.

Например, `UserAvatar` получает:

```ts
type UserAvatarProps = {
  name: string;
  imageUrl?: string;
};
```

а не полный:

```ts
UserDTO
```

с адресом, правами доступа, email и платёжными данными.

Так компонент:

- меньше зависит от backend-модели;
- не получает чувствительные данные без необходимости;
- проще переиспользуется;
- имеет понятный публичный контракт.

Если компоненту нужно сообщить о выборе, добавляют относящийся к его роли callback:

```ts
type UserAvatarProps = {
  name: string;
  imageUrl?: string;
  onSelect?: () => void;
};
```

Не нужно передавать целый объект только для того, чтобы компонент самостоятельно выбрал несколько нужных полей.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему большое число необязательных props может быть проблемой?</strong></summary>

<dl>
<dd>
<h2></h2>

Большое число optional props часто кодирует несколько несовместимых режимов одним интерфейсом:

```ts
type ActionProps = {
  href?: string;
  onClick?: () => void;
  disabled?: boolean;
  isLink?: boolean;
};
```

Тип допускает некорректные сочетания:

- ссылка без `href`;
- `isLink: true` вместе с `onClick`, но без `href`;
- одновременно ссылка и обычная кнопка;
- `disabled` со ссылкой без определённой семантики.

Discriminated union, или дискриминируемое объединение, разделяет контракты:

```ts
type ActionProps =
  | {
      kind: "button";
      onClick: () => void;
      disabled?: boolean;
      href?: never;
    }
  | {
      kind: "link";
      href: string;
      onClick?: never;
      disabled?: never;
    };
```

Теперь каждый вариант требует только относящиеся к нему поля.

При этом не любое количество optional props является нарушением. Независимые параметры вроде `className?` или `aria-label?` могут быть нормальной частью одного цельного контракта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Достаточно ли использовать <code>Pick&lt;User, "name" | "avatarUrl"&gt;</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`Pick` сужает набор полей:

```ts
type AvatarProps = Pick<
  User,
  "name" | "avatarUrl"
>;
```

Это лучше, чем передавать весь `User`.

Но тип всё ещё зависит от:

- имени модели `User`;
- названий её полей;
- смысла этих полей;
- изменений предметной модели.

Для локального компонента функционального модуля такая связь часто допустима.

Для дизайн-системы или независимого shared-компонента собственный контракт устойчивее:

```ts
type AvatarProps = {
  name: string;
  imageUrl?: string;
};
```

Тогда вызывающий код адаптирует предметную модель:

```tsx
<Avatar
  name={user.name}
  imageUrl={user.avatarUrl}
/>
```

Выбор зависит от необходимой степени независимости компонента.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как ISP связано с selectors хранилища?</strong></summary>

<dl>
<dd>
<h2></h2>

Компонент подписывается на минимальный срез состояния, который ему нужен:

```ts
const userName = useAppSelector(
  (state) => state.user.name,
);
```

Вместо передачи всего store или большого объекта:

```ts
const userState = useAppSelector(
  (state) => state.user,
);
```

Узкий selector:

- ограничивает публичную зависимость компонента;
- скрывает внутреннюю структуру store;
- упрощает изменение остальных полей;
- может уменьшить лишние рендеры.

Снижение рендеров зависит от механизма подписки и сравнения выбранного результата.

Например, если selector каждый раз возвращает новый объект:

```ts
const value = useAppSelector(
  (state) => ({
    name: state.user.name,
  }),
);
```

компонент может обновляться чаще, если не используется подходящее сравнение.

Главная связь с ISP состоит не только в производительности, а в том, что потребитель зависит от нужной ему части контракта состояния.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем ISP отличается от SRP?</strong></summary>

<dl>
<dd>
<h2></h2>

SRP смотрит внутрь модуля:

```text
По каким причинам он меняется?
```

ISP смотрит на модуль со стороны его потребителей:

```text
От какой части публичного контракта зависит каждый клиент?
```

Модуль может иметь одну ответственность, но предоставлять слишком широкий API.

Например, store авторизации может отвечать только за authentication, но возвращать каждому компоненту:

- текущего пользователя;
- access token;
- refresh token;
- внутренние ошибки;
- методы обновления;
- административные операции.

Компоненту имени при этом нужна только строка `name`.

Следовательно:

```text
SRP
→ цельность ответственности реализации

ISP
→ соответствие интерфейса потребности клиента
```

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```text
Есть `FileStorage` с методом `get(key): Promise<string | null>`.
MemoryStorage возвращает `null`, а RemoteStorage выбрасывает 404 для отсутствующего ключа.
Можно ли прозрачно заменять реализации?
```

Прозрачно заменять реализации нельзя, пока они по-разному трактуют отсутствие значения.

Если контракт обещает:

```ts
Promise<string | null>
```

где `null` означает отсутствие ключа, Adapter удалённого хранилища должен преобразовать `404`:

```ts
async function get(
  key: string,
): Promise<string | null> {
  const response = await fetch(
    `/storage/${key}`,
  );

  if (response.status === 404) {
    return null;
  }

  if (!response.ok) {
    throw new Error(
      "Storage request failed",
    );
  }

  return response.text();
}
```

Другой вариант — изменить общий контракт и явно смоделировать результат:

```ts
type StorageResult =
  | {
      status: "found";
      value: string;
    }
  | {
      status: "not-found";
    }
  | {
      status: "error";
      error: StorageError;
    };
```

Тогда все реализации и потребители должны соблюдать новую семантику.

После выбора контракта одинаковое поведение проверяется общими contract tests.

## Где это встречается во frontend

| Принцип | Сценарий |
|---|---|
| LSP | Реализации repository в памяти и через HTTP одинаково трактуют отсутствие данных |
| LSP | Варианты `Button` сохраняют семантику, focus и управление с клавиатуры |
| ISP | Компонент формы получает `FormValues`, а не полный API DTO |
| ISP | Selector отдаёт компоненту нужное значение, а не всё глобальное состояние |
| LSP + ISP | Discriminated union задаёт отдельные контракты ссылки и действия |
