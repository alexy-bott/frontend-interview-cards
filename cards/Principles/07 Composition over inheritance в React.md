## Вопрос

<br>

 💬 **Что означает composition over inheritance? Почему в React композицию обычно предпочитают наследованию?**

<h2></h2>

<br>
<dl>
<dd>

Composition over inheritance, или «композиция вместо наследования», означает: объект или компонент получает нужные части интерфейса и поведения через небольшие явные контракты, а не наследует весь набор возможностей от цепочки базовых классов.

В React интерфейс естественно строится композицией:

- один компонент вкладывается в другой;
- JSX передаётся через props;
- поведение передаётся callback-функциями;
- React-логика объединяется в custom hooks;
- изменяемый алгоритм передаётся функцией или объектом.

Композиция решает несколько разных задач:

- **Композиция интерфейса.** `children`, именованные области и составные компоненты позволяют передать содержимое в `Card`, `Dialog` или `PageLayout`.
- **Композиция поведения.** Callback-функции передают действия, а custom hooks, то есть пользовательские React-хуки, переиспользуют связанную логику состояния и эффектов.
- **Композиция алгоритма.** Компонент получает функцию или объект с нужным поведением, например функцию сортировки или форматирования. Это применение паттерна Strategy, или стратегия.

```tsx
type PanelProps = {
  title: string;
  actions?: React.ReactNode;
  children: React.ReactNode;
};

function Panel({
  title,
  actions,
  children,
}: PanelProps) {
  return (
    <section>
      <header>
        <h2>{title}</h2>
        {actions}
      </header>

      {children}
    </section>
  );
}
```

Конкретный экран собирает `Panel` из готовых частей:

```tsx
<Panel
  title="Профиль"
  actions={<SaveButton />}
>
  <ProfileForm />
</Panel>
```

`Panel` не наследуется от специальных вариантов для профиля, настроек или заказов.

Он задаёт устойчивую структуру, а конкретное содержимое и действия получает снаружи через понятный контракт.

При наследовании потомок зависит не только от публичного API, но часто и от внутреннего устройства базового класса:

```text
BasePanel
  ↓
ProfilePanel
  ↓
AdminProfilePanel
```

Изменение базового класса может повлиять на всю иерархию.

Основные проблемы наследования для переиспользования UI:

- потомок получает поведение, которое ему может быть не нужно;
- часть контракта остаётся неявной;
- переопределённый метод может нарушить ожидания базового класса;
- независимые возможности трудно сочетать;
- глубокую иерархию сложно читать и изменять;
- изменение основания затрагивает множество потомков.

Композиция позволяет подключать только необходимые части:

```text
Panel
  + ProfileForm
  + SaveButton
  + useProfileForm
```

Каждая часть имеет собственный контракт и может заменяться независимо.

Классовый React-компонент наследуется от:

```ts
React.Component
```

Это часть классового API React, а не рекомендуемый способ переиспользовать предметную разметку между компонентами.

Классовые компоненты продолжают поддерживаться, но для нового кода React рекомендует функциональные компоненты.

React-компоненты обычно не наследуют друг от друга ради общей разметки или логики.

Представление переиспользуют через:

- вложенность;
- props;
- `children`;
- именованные области;
- составные компоненты.

Логику в функциональном коде переиспользуют через:

- custom hooks;
- обычные функции;
- callbacks;
- Strategy;
- внешние модули состояния.

Композиция не означает, что компонент должен предоставлять неограниченное количество точек расширения.

Хороший компонент открывает только понятные области вариативности. Если его API состоит из десятков slots, callbacks и зависимых друг от друга компонентов, внутренняя сложность просто перекладывается на потребителя.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что именно называют композицией в React?</strong></summary>

<dl>
<dd>
<h2></h2>

Это сборка интерфейса или поведения из нескольких частей с явными контрактами.

Например:

- `Dialog` управляет открытием и focus;
- `DialogContent` задаёт содержимое;
- бизнес-компонент передаёт текст, кнопки и обработчик подтверждения.

Простая вложенность JSX уже является композицией интерфейса:

```tsx
<Card>
  <ProductDetails />
</Card>
```

Передача callback-функции является композицией поведения:

```tsx
<Form onSubmit={saveProfile} />
```

Передача алгоритма через props является композицией Strategy:

```tsx
<ProductList
  sort={sortByPrice}
/>
```

Custom hook позволяет компоненту собрать поведение из React-логики:

```ts
const form = useProfileForm();
```

Общий признак композиции — компонент использует переданную часть через публичный контракт и не зависит от её внутренней реализации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Для чего нужен <code>children</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`children` содержит JSX, вложенный между открывающим и закрывающим тегами компонента:

```tsx
<Card>
  <ProductDetails />
</Card>
```

Благодаря этому оболочка отвечает за общую структуру или поведение, но не зависит от конкретного содержимого.

Такой контракт подходит, когда область одна и её назначение очевидно:

- содержимое карточки;
- основная область страницы;
- содержимое всплывающего окна;
- содержимое панели.

Если областей несколько, один `children` может стать недостаточно выразительным.

Тогда используют именованные props:

```tsx
<PageLayout
  header={<Header />}
  sidebar={<Sidebar />}
  footer={<Footer />}
>
  <Content />
</PageLayout>
```

или составные компоненты.

Выбор зависит от того, насколько жёстко родитель должен управлять расположением и ролью передаваемых частей.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое slot в React?</strong></summary>

<dl>
<dd>
<h2></h2>

Slot, или именованная область компонента, — это место, куда потребитель передаёт конкретную часть интерфейса.

В React нет отдельного встроенного синтаксиса slots.

Обычно их выражают props типа `ReactNode`:

```ts
type LayoutProps = {
  header: React.ReactNode;
  sidebar?: React.ReactNode;
  children: React.ReactNode;
};
```

Использование:

```tsx
<Layout
  header={<Header />}
  sidebar={<Filters />}
>
  <Catalog />
</Layout>
```

Другой вариант — составные компоненты:

```tsx
<Card>
  <Card.Header />
  <Card.Content />
  <Card.Footer />
</Card>
```

Именованные области удобнее одного `children`, когда:

- частей несколько;
- родитель располагает их в разных местах;
- у каждой части есть понятная роль;
- нужно ограничить структуру компонента.

Slot должен иметь ясный контракт. Если потребителю приходится знать скрытый порядок и внутреннюю реализацию родителя, композиция становится хрупкой.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое render prop?</strong></summary>

<dl>
<dd>
<h2></h2>

Render prop, или функция рендеринга в props, — это функция, которую компонент вызывает и передаёт ей свои данные или состояние.

Полученный JSX вставляется в интерфейс:

```tsx
type ListProps<Item> = {
  items: Item[];
  renderItem: (
    item: Item,
  ) => React.ReactNode;
};

function List<Item>({
  items,
  renderItem,
}: ListProps<Item>) {
  return (
    <ul>
      {items.map((item, index) => (
        <li key={index}>
          {renderItem(item)}
        </li>
      ))}
    </ul>
  );
}
```

Использование:

```tsx
<List
  items={users}
  renderItem={(user) => (
    <UserRow user={user} />
  )}
/>
```

Компонент `List` владеет общим алгоритмом обхода, но не знает разметку конкретного элемента.

Render prop особенно полезен, когда:

- родитель владеет состоянием;
- потребитель должен определить отображение;
- одного `children` недостаточно;
- нужно передать данные из родителя в настраиваемую область.

Для переиспользования логики состояния многие прежние render props были заменены custom hooks.

Но функции вроде `renderItem`, `renderCell` и `children(state)` по-прежнему являются удобными точками настройки интерфейса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем custom hook отличается от композиции компонентов?</strong></summary>

<dl>
<dd>
<h2></h2>

Компоненты объединяют элементы интерфейса и возвращают JSX.

Custom hook объединяет React-логику:

- состояние;
- эффекты;
- подписки;
- обработчики;
- другие hooks.

При этом hook не определяет обязательную разметку.

```ts
function useDisclosure() {
  const [
    isOpen,
    setIsOpen,
  ] = useState(false);

  return {
    isOpen,
    open: () => {
      setIsOpen(true);
    },
    close: () => {
      setIsOpen(false);
    },
  };
}
```

Компонент сам решает, как отобразить полученные данные и действия.

Hook переиспользует логику, но не делит состояние между вызовами автоматически:

```ts
const first = useDisclosure();
const second = useDisclosure();
```

`first` и `second` имеют независимое состояние.

Если нескольким компонентам нужны общие данные, состояние должно иметь общего владельца:

- родительский компонент;
- Context;
- внешний store;
- внешний источник с подпиской.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое Higher-Order Component и где здесь композиция?</strong></summary>

<dl>
<dd>
<h2></h2>

Higher-Order Component, или HOC, — это функция, которая принимает компонент и возвращает новый компонент с дополнительным поведением или props:

```tsx
const EnhancedComponent =
  withPermissions(Component);
```

HOC не изменяет исходный компонент, а оборачивает его, поэтому является формой композиции.

Он часто встречается в библиотеках и существующем коде:

```ts
connect()
memo()
withRouter()
```

Множество вложенных HOC может усложнить:

- дерево компонентов;
- отображаемые имена;
- типизацию;
- происхождение props;
- порядок выполнения обёрток.

Поэтому в современном функциональном коде внутреннюю React-логику часто удобнее переиспользовать через custom hooks.

Но hooks не полностью заменяют HOC.

HOC остаётся полезен, когда нужно:

- принять произвольный компонент снаружи;
- встроиться в API библиотеки;
- обернуть компонент без изменения его исходного кода;
- предоставить единое поведение набору компонентов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как композиция связана с headless UI?</strong></summary>

<dl>
<dd>
<h2></h2>

Headless-компонент предоставляет состояние, поведение и правила доступности, но не навязывает законченный внешний вид.

Потребитель собирает интерфейс из primitives и применяет стили своей дизайн-системы.

Например, headless Dialog может управлять:

- открытием;
- focus trap;
- закрытием по Escape;
- возвратом focus;
- ARIA-связями.

Проект определяет:

- визуальную разметку;
- размеры;
- цвета;
- иконки;
- анимации;
- содержимое.

Некоторые библиотеки позволяют заменить корневой элемент через композицию, например с помощью API наподобие `asChild`.

После такого изменения нужно проверить итоговые:

- HTML-семантику;
- focus;
- keyboard interaction;
- ARIA-атрибуты;
- поддержку `disabled`;
- forwarding props и `ref`.

Headless API помогает с доступностью, но неправильная композиция может нарушить предоставленный контракт.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда композиция становится неудобной?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда для простого сценария потребителю приходится:

- собирать слишком много вложенных компонентов;
- соблюдать скрытый порядок;
- передавать одни данные через длинную цепочку;
- вручную связывать множество Context;
- знать внутреннее устройство библиотеки;
- повторять одинаковую настройку во всех местах.

Например:

```tsx
<Component.Root>
  <Component.Provider>
    <Component.Trigger>
      <Component.TriggerContent>
        {/* ... */}
      </Component.TriggerContent>
    </Component.Trigger>
  </Component.Provider>
</Component.Root>
```

Такой API может переложить внутреннюю сложность на потребителя.

Помогают:

- разумные значения по умолчанию;
- более крупные готовые компоненты поверх primitives;
- presets;
- понятные именованные области;
- явные ограничения структуры;
- специализированные компоненты для частых сценариев.

Композиция полезна, пока её части проще понимать и сочетать, чем один монолитный компонент.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>cloneElement</code> не является универсальным способом композиции?</strong></summary>

<dl>
<dd>
<h2></h2>

`cloneElement` создаёт новый React-элемент на основе переданного и добавляет или заменяет его props.

Например, родитель может неявно передать ребёнку обработчик:

```tsx
cloneElement(child, {
  onClick: handleClick,
});
```

Недостатки такого подхода:

- потребитель не всегда понимает, какие props будут заменены;
- компонент зависит от непосредственной формы дочернего элемента;
- существующий обработчик можно случайно перезаписать;
- ref и типы усложняются;
- промежуточная обёртка может сломать ожидания.

Более явные варианты:

- render prop;
- Context;
- custom hook;
- обычные props;
- составные компоненты с документированным контрактом.

`cloneElement` допустим в ограниченном API, если тип дочернего элемента контролируется, а правила объединения props понятны и задокументированы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Композиция устраняет prop drilling?</strong></summary>

<dl>
<dd>
<h2></h2>

Иногда.

Передача готового элемента через `children` позволяет промежуточному layout-компоненту не знать данные содержимого.

Вместо:

```tsx
<Layout
  user={user}
/>
```

можно передать готовую часть:

```tsx
<Layout
  sidebar={
    <UserSidebar user={user} />
  }
/>
```

Теперь `Layout` не зависит от `User`.

Но если одни данные нужны многим удалённым компонентам, prop drilling может сохраниться или переместиться в другое место.

Тогда рассматривают:

- Context;
- внешний store;
- подъём состояния;
- перенос чтения данных ближе к потребителю.

Выбор зависит от:

- частоты обновлений;
- области использования;
- владельца состояния;
- необходимости общего доступа.

Композиция уменьшает лишние зависимости промежуточных компонентов, но не является универсальной заменой управлению состоянием.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Наследование во frontend всегда запрещено?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Наследование уместно, когда:

- отношение подтипа действительно устойчиво;
- базовый класс специально спроектирован для расширения;
- поведенческий контракт понятен;
- API платформы или библиотеки требует наследования.

Например, собственная ошибка может расширять стандартный класс:

```ts
class ValidationError extends Error {
  constructor(
    public readonly fields:
      Record<string, string>,
  ) {
    super(
      "Validation failed",
    );

    this.name =
      "ValidationError";
  }
}
```

Наследование также встречается в API framework, специально предоставляющем базовый класс как точку расширения.

Но наследование React-компонентов ради общей разметки, состояния или обработчиков обычно уступает:

- композиции;
- custom hooks;
- обычным функциям;
- Strategy.

Важно проверять:

- поведенческую заменяемость;
- глубину связи с базовым классом;
- стабильность иерархии;
- возможность сочетать независимые возможности.

Само наличие `extends` не является ошибкой, но для переиспользования React UI обычно есть более явные способы.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Задача | Вариант композиции |
|---|---|
| Общая рамка страницы | `children` или именованные области layout-компонента |
| Настраиваемая строка таблицы | `renderCell` или описание колонок |
| Повторно используемая логика формы | Custom hook без жёсткой разметки |
| Выбор сортировки или форматирования | Функция Strategy передаётся через props |
| Доступный компонент без заданного дизайна | Headless primitives объединяются с компонентами дизайн-системы |
