## Вопрос

<br>

 💬 **Что такое Single Responsibility Principle? Как определить ответственность компонента, React-хука или модуля во frontend?**

<h2></h2>

<br>
<dl>
<dd>

Single Responsibility Principle, или SRP, говорит: модуль должен отвечать перед одним владельцем связанных требований, которого также называют actor, и иметь одну основную причину изменения.

Практическая формулировка:

```text
Код, который меняется по одной причине, держат вместе.
Код, который меняется по независимым причинам, разделяют.
```

Ответственность — не отдельное техническое действие.

Например, отправка формы может включать:

- чтение полей;
- проверку данных;
- вызов mutation;
- обработку результата;
- обновление состояния интерфейса.

Если все эти действия относятся к одному пользовательскому сценарию и обычно меняются вместе, они могут оставаться в одном модуле.

Разделение требуется, когда внутри одного модуля сталкиваются независимые источники требований.

Например:

```text
поля и поведение формы
→ меняются из-за требований продукта

формат DTO и HTTP-запрос
→ меняются из-за backend-контракта

формат события аналитики
→ меняется из-за системы аналитики
```

Если один React-компонент напрямую реализует все три области, независимые изменения начинают конфликтовать в одном месте.

SRP не требует, чтобы React-компонент только отображал JSX.

Компонент страницы может:

- загрузить данные;
- управлять состоянием сценария;
- обработать действия пользователя;
- собрать интерфейс из дочерних компонентов.

Это может быть одной ответственностью, если компонент координирует один цельный сценарий и зависит от понятных высокоуровневых операций.

Проблема возникает, когда компонент дополнительно знает:

- внутренний формат HTTP-запроса;
- структуру backend DTO;
- устройство SDK аналитики;
- правила нескольких независимых бизнес-сценариев;
- детали хранения токенов;
- внутреннее устройство несвязанных виджетов.

Например, допустимая координация:

```tsx
export function ProfilePage() {
  const profileQuery = useProfileQuery();
  const updateProfile = useUpdateProfile();

  return (
    <ProfileForm
      profile={profileQuery.data}
      onSubmit={updateProfile}
    />
  );
}
```

Компонент управляет сценарием профиля, но не знает:

- URL backend;
- формат transport response;
- способ обновления токена;
- формат события аналитики.

Размер файла является только сигналом, а не доказательством нарушения.

Большой компонент может декларативно описывать один сложный экран.

Небольшой hook может нарушать SRP, если одновременно управляет:

- авторизацией;
- формой;
- навигацией;
- аналитикой;
- уведомлениями;
- несколькими несвязанными запросами.

Более точные признаки смешанных ответственностей:

- модуль меняется в задачах разных предметных областей;
- внутри используется словарь нескольких несвязанных сценариев;
- imports приходят из независимых инфраструктурных модулей;
- тест одной функции требует настройки множества несвязанных зависимостей;
- изменение одного требования регулярно ломает другую часть модуля;
- публичный контракт содержит данные и callbacks для разных потребителей.

Разделение полезно, если после него каждая часть:

- получает понятное предметное имя;
- скрывает собственные детали;
- имеет небольшой контракт;
- может изменяться локально;
- уменьшает объём знаний исходного модуля.

Механическое увеличение числа файлов SRP не улучшает.

Если извлечённые функции всегда вызываются вместе, передают друг другу десятки аргументов и меняются в каждой задаче одновременно, вероятно, одна ответственность была искусственно раздроблена.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что значит «одна причина для изменения»?</strong></summary>

<dl>
<dd>
<h2></h2>

Это один связный источник требований или один владелец решений.

Например:

```text
Price
→ меняется из-за правил отображения цены

priceApi
→ меняется из-за контракта обмена с backend

priceAnalytics
→ меняется из-за требований аналитики
```

При этом не каждое отдельное требование требует нового файла.

Если изменения относятся к одной цели и обычно приходят вместе, их разумно держать рядом.

Например, форматирование валюты, отображение скидки и зачёркнутой старой цены могут быть одной ответственностью компонента цены.

SRP разделяет независимые причины изменения, а не каждую строку или операцию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Компонент на тысячу строк обязательно нарушает SRP?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Большой размер требует проверки, но не доказывает нарушение.

Компонент может декларативно описывать один сложный экран с большим количеством связанной разметки.

И наоборот, короткий hook может нарушать SRP:

```ts
function usePageLogic() {
  // authentication
  // form state
  // navigation
  // analytics
  // notifications
}
```

Критериями являются:

- причины изменения;
- смысловая связность;
- зависимости;
- публичный контракт;
- возможность локально изменить поведение.

Количество строк, функций и файлов является только косвенным сигналом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли компонент сам загружать данные и соблюдать SRP?</strong></summary>

<dl>
<dd>
<h2></h2>

Да, если загрузка относится к его цельному сценарию и инфраструктурные детали скрыты за понятной операцией.

Например, компонент маршрута может вызвать:

```ts
useProfileQuery()
```

и передать данные форме.

Это не обязательно нарушает SRP, потому что компонент координирует сценарий страницы профиля.

Граница начинает размываться, если UI самостоятельно:

- собирает URL;
- устанавливает transport headers;
- обновляет access token;
- преобразует backend DTO;
- разбирает внутренние коды backend;
- выполняет retry;
- управляет SDK аналитики.

Тогда ответственность API-границы и инфраструктуры протекает в компонент.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли нужно разделять container и presentational component?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Container component связывает данные и действия, а presentational component получает готовые props и отвечает за отображение.

Такое разделение полезно, когда:

- представление используется с разными источниками данных;
- визуальная часть меняется независимо от сценария;
- логика имеет отдельные тесты;
- компонент становится удобнее использовать в Storybook;
- зависимости мешают читать основную разметку.

Для небольшого сценария разделение может только увеличить число файлов, props и переходов по коду.

SRP требует разделять независимые причины изменения, а не обязательно создавать container для каждого компонента.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли custom hook стать God Object, то есть объектом со слишком большим числом обязанностей?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

Перенос всей логики компонента в:

```ts
usePageLogic()
```

изменяет расположение кода, но не обязательно его границы.

Hook по-прежнему нарушает SRP, если одновременно:

- загружает несвязанные данные;
- управляет несколькими формами;
- проверяет права;
- выполняет навигацию;
- показывает уведомления;
- отправляет аналитику;
- возвращает большой набор несвязанных значений и callbacks.

Большой возвращаемый объект часто показывает скрытый публичный контракт:

```ts
return {
  profile,
  orders,
  form,
  permissions,
  modal,
  notifications,
  analytics,
};
```

Custom hook должен объединять связанную React-логику, а не становиться контейнером для всего кода страницы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выбрать, что именно извлекать?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно искать самостоятельную ответственность, а не просто длинный фрагмент.

Обычно извлекают:

- преобразование DTO — на API-границу;
- повторяемое предметное правило — в чистую функцию;
- самостоятельную часть интерфейса — в компонент;
- связанную React-логику — в custom hook;
- работу с внешним SDK — в adapter или facade;
- независимый пользовательский сценарий — в отдельный функциональный модуль.

Полезный вопрос:

```text
Что перестанет знать исходный модуль после извлечения?
```

Если ответ — «ничего», новая функция, вероятно, только переносит строки.

Хорошая граница скрывает решение или нестабильную деталь, а не просто создаёт новый файл.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как история Git помогает увидеть нарушение SRP?</strong></summary>

<dl>
<dd>
<h2></h2>

История Git показывает реальные причины изменения лучше предполагаемой архитектуры.

Если один файл регулярно меняется в задачах разных областей:

- аналитика;
- backend;
- дизайн-система;
- авторизация;
- бизнес-правила;

в нём могут быть смешаны ответственности.

Это также может вызывать постоянные конфликты между независимыми командами.

Обратный сигнал — несколько файлов почти всегда меняются вместе по одной причине.

Возможно, они образуют один смысловой модуль, который был искусственно раздроблен.

Git-история является сигналом для анализа, а не автоматическим доказательством. Совместные изменения могут быть вызваны общей миграцией, переименованием или массовым форматированием.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как SRP влияет на тесты?</strong></summary>

<dl>
<dd>
<h2></h2>

У цельного модуля меньше несвязанных dependencies.

Поэтому подготовка теста обычно короче, а проверки относятся к одной области поведения.

Например, если для проверки форматирования цены нужно подменить:

- router;
- authentication;
- API;
- аналитику;
- storage;

границы, вероятно, смешаны.

После правильного разделения чистое правило можно проверить отдельно, а интеграционный тест компонента оставить для пользовательского сценария.

При этом не нужно тестировать каждую извлечённую функцию только потому, что она находится в отдельном файле.

Разделение должно улучшать дизайн и тестируемость, а не увеличивать количество формальных unit-тестов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда разделение по SRP ухудшает код?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда ответственность ещё не ясна и код дробят по техническим операциям:

```text
getData()
mapData()
validateData()
submitData()
showMessage()
```

Появляются:

- одноразовые wrappers;
- десятки параметров;
- большое число переходов между файлами;
- интерфейсы без реальных альтернатив;
- модули, которые всегда меняются вместе;
- циклические зависимости.

Такое разделение снижает cohesion, то есть смысловую цельность модуля, и увеличивает coupling между искусственно разделёнными частями.

Хорошая граница позволяет понять сценарий на более высоком уровне.

Плохая граница заставляет собирать исходный алгоритм по множеству маленьких файлов.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```text
ProfilePage загружает DTO, преобразует его в поля формы, отображает форму,
отправляет запрос обновления и напрямую вызывает SDK аналитики. Что разделять первым?
```

Сначала нужно выделить части, которые меняются независимо от сценария страницы.

API-граница может скрыть:

- загрузку DTO;
- преобразование DTO в модель frontend;
- преобразование формы в payload;
- transport errors.

Например:

```text
profileApi или profileAdapter
```

Facade аналитики может принимать предметное событие:

```ts
profileAnalytics.profileUpdated();
```

и скрывать конкретный SDK и его формат.

Форма может отвечать за:

- поля;
- локальное состояние;
- отображение ошибок;
- правила UI-валидации своего сценария.

`ProfilePage` при этом может продолжать:

- запускать загрузку;
- передавать данные форме;
- координировать отправку;
- связывать результат сценария.

Саму координацию не нужно немедленно выносить, пока она остаётся одной ответственностью страницы профиля.

Порядок разделения определяется реальными причинами изменения. Обычно первыми выделяют наиболее нестабильные внешние границы, но не создают отдельный слой для каждой технической операции.

## Где это встречается во frontend

| Причина изменения | Возможный владелец |
|---|---|
| Изменился backend DTO | API Adapter или функция преобразования |
| Изменилась разметка формы | Компонент формы |
| Изменилось правило сценария | Модель функционального модуля или пользовательский сценарий (use case) |
| Изменилась отправка аналитики | Facade аналитики |
| Изменился общий базовый элемент интерфейса | Компонент дизайн-системы |
