## Вопрос

<br>

 💬 **Что такое SOLID? Как эти принципы применяются во frontend, где основная часть кода написана функциями и React-компонентами, а не классами?**

<h2></h2>

<br>
<dl>
<dd>

SOLID — пять принципов проектирования ответственностей, точек расширения, поведенческих контрактов и зависимостей.

Они появились в объектно-ориентированном контексте, но не зависят от использования классов. Принципы применимы к:

- функциям;
- React-компонентам;
- хукам;
- модулям;
- сервисам;
- слоям приложения;
- границам API.

Их общая цель — локализовать изменения и не заставлять независимые части системы меняться вместе.

| Принцип | Основная мысль | Пример во frontend |
|---|---|---|
| SRP, Single Responsibility Principle, принцип единственной ответственности | Модуль отвечает перед одним владельцем требований и имеет одну основную причину изменения | Преобразование данных API не смешано с отображением формы и отправкой аналитики |
| OCP, Open/Closed Principle, принцип открытости и закрытости | Поддерживаемые варианты добавляются через стабильную точку расширения без постоянного изменения общего механизма | `DataTable` принимает описание колонок, а не содержит условия для каждой страницы приложения |
| LSP, Liskov Substitution Principle, принцип подстановки Лисков | Любая реализация контракта сохраняет его поведенческие ожидания | Любая реализация `Storage` одинаково трактует отсутствие значения, ошибки и сохранение данных |
| ISP, Interface Segregation Principle, принцип разделения интерфейсов | Потребитель зависит только от необходимой ему части контракта | Компонент имени получает `name`, а не весь `UserDTO` |
| DIP, Dependency Inversion Principle, принцип инверсии зависимостей | Высокоуровневое правило зависит от собственного контракта, а инфраструктура адаптируется к нему | Сценарий обновления профиля вызывает `updateProfile`, а не собирает `fetch` и HTTP headers самостоятельно |

**SRP** не означает, что модуль должен содержать только одну функцию или выполнять одно техническое действие.

Например, сценарий отправки формы может:

- проверить данные;
- вызвать mutation;
- обработать ожидаемый результат;
- обновить состояние интерфейса.

Если всё это относится к одному цельному пользовательскому сценарию и меняется по одной причине, разделение не обязательно.

Проблема появляется, когда один модуль одновременно меняется из-за независимых требований:

- backend-контракта;
- визуального дизайна;
- аналитики;
- правил авторизации;
- формата хранения данных.

**OCP** не означает, что любой код нужно заранее превращать в универсальный framework.

Точку расширения выделяют, когда уже появилась реальная вариативность:

```text
несколько способов форматирования
→ функция formatter

несколько вариантов отображения ячейки
→ render function

несколько способов оплаты
→ набор стратегий
```

Если нового варианта ещё нет и его появление не ожидается, прямой код обычно проще.

**LSP** требует не только совпадения типов, но и сохранения поведения.

TypeScript может считать две реализации совместимыми структурно, однако одна из них способна нарушить ожидания потребителя:

- выбросить новую ошибку;
- отказаться принимать допустимое значение;
- вернуть значение в другой семантике;
- перестать поддерживать keyboard interaction;
- изменить побочный эффект операции.

Поэтому type compatibility не гарантирует LSP автоматически.

**ISP** означает, что контракт проектируется под задачу потребителя.

Компоненту аватара обычно достаточно:

```ts
type AvatarProps = {
  name: string;
  imageUrl?: string;
};
```

Ему не нужен полный объект:

```ts
type UserDTO = {
  id: string;
  name: string;
  imageUrl?: string;
  email: string;
  role: string;
  createdAt: string;
};
```

Так компонент меньше зависит от backend-модели и реже меняется вместе с ней.

**DIP** означает, что высокоуровневый сценарий не должен знать детали транспорта или конкретной библиотеки.

Например, сценарий зависит от операции:

```ts
type UpdateProfile = (
  data: ProfileInput,
) => Promise<Profile>;
```

а конкретная реализация может использовать:

- `fetch`;
- GraphQL client;
- SDK;
- mock для теста.

Контракт определяется потребностью сценария, а инфраструктура адаптируется к нему.

SOLID не требует:

- писать классы;
- создавать интерфейс для каждой функции;
- использовать DI-контейнер;
- делить каждый компонент на container и presentation;
- раскладывать простую форму по десяти слоям.

Strategy, или стратегия, может быть набором функций.

Dependency injection, или передача зависимости, может быть обычным аргументом функции.

SRP может выражаться границей функционального модуля.

DIP может реализовываться импортом adapter в composition root, то есть в точке сборки приложения.

SOLID не является автоматической проверкой качества.

Между расширяемостью и простотой есть компромисс. Дополнительная абстракция полезна, когда она изолирует:

- реальную нестабильную деталь;
- несколько существующих реализаций;
- внешний сервис;
- сложный изменяемый контракт.

Если второй вариант существует только в воображении, прямой код обычно дешевле и понятнее.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Нужно ли знать SOLID frontend-разработчику без опыта с ООП?</strong></summary>

<dl>
<dd>
<h2></h2>

Да, на уровне проектирования модулей и зависимостей.

React-компонент имеет:

- ответственность;
- публичный контракт props;
- зависимости;
- ожидаемое поведение.

React-хук может зависеть от API, storage или другого модуля.

Функциональный сценарий взаимодействует с backend и состоянием приложения.

Наследование классов не требуется, чтобы обсуждать:

- причины изменения;
- заменяемость реализаций;
- размер контрактов;
- направление зависимостей;
- точки расширения.

Важно понимать смысл принципов, а не воспроизводить объектно-ориентированные шаблоны в функциональном коде.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как SRP проявляется в React?</strong></summary>

<dl>
<dd>
<h2></h2>

Код, который меняется из-за независимых требований, разделяется по понятным границам.

Например:

- компонент отвечает за отображение формы;
- adapter преобразует backend DTO в модель интерфейса;
- модуль аналитики отправляет событие;
- функция авторизации проверяет право на операцию.

Это не означает, что React-компонент обязан только отображать JSX.

Загрузка данных, обработка состояния и отображение могут оставаться рядом, если относятся к одному цельному сценарию и обычно меняются вместе.

Разделение на container и presentation components также не является обязательным правилом SRP. Оно полезно только тогда, когда действительно разделяет разные причины изменения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как OCP проявляется в UI-компоненте?</strong></summary>

<dl>
<dd>
<h2></h2>

Стабильный компонент предоставляет ограниченные точки расширения для реально существующих вариантов:

- `children`;
- именованные области;
- render functions;
- описание колонок;
- formatter;
- strategy;
- композицию компонентов.

Например, таблица принимает описание колонок:

```ts
type Column<T> = {
  key: keyof T;
  title: string;
  render?: (item: T) => React.ReactNode;
};
```

Новая страница добавляет конфигурацию снаружи, а не новое условие внутри общей таблицы:

```ts
if (page === "users") {
  // ...
}

if (page === "orders") {
  // ...
}
```

При этом OCP не требует запрещать любые изменения общего компонента.

Если изменился сам контракт таблицы или найден дефект, компонент нужно изменить.

Принцип предлагает отделять ожидаемые варианты использования от постоянного редактирования стабильного механизма.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как LSP связан с React-компонентами?</strong></summary>

<dl>
<dd>
<h2></h2>

Если несколько компонентов используются через один контракт, они должны сохранять его поведенческие ожидания.

Например, варианты общего `Button` должны поддерживать ожидаемые свойства:

- keyboard activation;
- focus;
- `disabled`;
- обработку `onClick`;
- отправку формы при `type="submit"`.

Вариант не должен незаметно отрисовывать нефокусируемый `div`, если потребитель ожидает поведение нативной кнопки.

Одинаковые TypeScript props сами по себе не гарантируют LSP.

Компоненты могут быть совместимы по типам, но отличаться по:

- доступности;
- обработке ошибок;
- побочным эффектам;
- порядку вызовов callback;
- поведению в loading-состоянии.

LSP проверяет полный поведенческий контракт, а не только форму объекта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как ISP применяется к props и типам TypeScript?</strong></summary>

<dl>
<dd>
<h2></h2>

Компоненту передают минимальную модель, необходимую для его задачи.

Вместо полного `UserDTO`:

```tsx
<UserAvatar user={user} />
```

компонент может получить:

```tsx
<UserAvatar
  name={user.name}
  imageUrl={user.imageUrl}
/>
```

Так он не зависит от:

- структуры backend DTO;
- роли пользователя;
- email;
- служебных полей;
- изменений, не связанных с аватаром.

Можно использовать `Pick`, но это не всегда лучший публичный контракт:

```ts
type AvatarProps = Pick<
  UserDTO,
  "name" | "imageUrl"
>;
```

Такой тип всё ещё связан с backend-моделью.

Независимый контракт компонента часто устойчивее:

```ts
type AvatarProps = {
  name: string;
  imageUrl?: string;
};
```

Взаимоисключающие варианты props выражают через discriminated union, или дискриминируемое объединение, чтобы потребитель не зависел от полей, которые не относятся к выбранному варианту.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означает DIP во frontend?</strong></summary>

<dl>
<dd>
<h2></h2>

Высокоуровневый сценарий определяет, какая операция ему нужна.

Например:

```ts
type SaveProfile = (
  profile: ProfileInput,
) => Promise<Profile>;
```

Конкретная инфраструктура адаптируется к этому контракту:

```ts
const saveProfileViaApi: SaveProfile =
  async (profile) => {
    const response = await fetch(
      "/api/profile",
      {
        method: "PUT",
        body: JSON.stringify(profile),
      },
    );

    return response.json();
  };
```

Сценарий не обязан знать:

- URL;
- HTTP-метод;
- headers;
- используемый SDK;
- формат backend DTO.

Реализацию можно передать:

- аргументом функции;
- через props;
- через Context;
- через factory;
- связать в composition root.

DIP определяет направление зависимости, а не требует DI-контейнер.

Важно, чтобы контракт принадлежал потребности высокоуровневого сценария, а не был просто копией API конкретной библиотеки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли соблюдать один принцип и нарушать другой?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

Универсальный `Table` может быть открыт для расширения через десятки callback-функций, но одновременно нарушать ISP огромным контрактом и KISS сложным API.

Модуль может соблюдать SRP, но напрямую зависеть от конкретного HTTP-клиента и усложнять замену инфраструктуры.

Узкий интерфейс может соблюдать ISP, но его реализации способны нарушать LSP разным поведением.

Принципы являются разными углами проверки.

Решение оценивают целиком:

- насколько оно понятно;
- какие изменения локализует;
- какие зависимости создаёт;
- насколько предсказуем его контракт;
- оправдана ли сложность реальными требованиями.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда применение SOLID превращается в overengineering, то есть чрезмерное усложнение?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда интерфейсы, фабрики, adapters и слои создаются до появления:

- разных реализаций;
- независимых причин изменения;
- нестабильной внешней зависимости;
- необходимости тестовой подмены;
- понятной точки расширения.

Вместо прямого вызова появляется длинная цепочка:

```text
component
→ hook
→ service
→ use case
→ repository interface
→ repository implementation
→ HTTP client
```

но изменение одного поля backend всё равно требует исправить каждый слой.

Такая архитектура не локализует изменение, а только добавляет переходы и новые имена.

Абстракция полезна, если потребитель действительно перестаёт знать нестабильную деталь.

Если слой только переименовывает следующий вызов и не защищает собственный контракт, его ценность сомнительна.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить применение SOLID при проверке кода (code review)?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала определить ожидаемые сценарии изменения:

- что изменится при новом поле backend;
- что изменится при новом варианте UI;
- что потребуется для замены storage или HTTP-клиента;
- какие требования принадлежат разным командам или владельцам.

Затем проверить:

- не смешаны ли независимые причины изменения;
- не знает ли UI структуру backend DTO без необходимости;
- есть ли стабильная точка расширения для уже существующих вариантов;
- сохраняют ли реализации одинаковое поведение;
- не требует ли потребитель лишние поля и методы;
- зависит ли бизнес-правило от инфраструктурной детали;
- уменьшает ли новая абстракция связанность;
- оправдана ли её стоимость реальными требованиями.

Цель review — не найти формальное нарушение каждой буквы SOLID, а понять, насколько безопасно и локально будет меняться код.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Область | Как помогают принципы |
|---|---|
| Дизайн-система | Компоненты имеют предсказуемое поведение и ограниченные точки расширения |
| Слой API | DTO и ошибки не протекают в UI; функциональный модуль зависит от собственного контракта |
| Формы | Схемы данных моделируют реальные варианты без несовместимых необязательных props |
| Управление состоянием | Store разделён по цельным областям, selectors возвращают потребителю нужный срез |
| Тестирование | Подменяется узкая внешняя граница, а не вся внутренняя реализация |
