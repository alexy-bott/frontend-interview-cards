## Вопрос

<br>

 💬 **Что означают DRY, KISS и YAGNI? Как применять эти принципы во frontend без крайностей?**

<h2></h2>

<br>
<dl>
<dd>

DRY, KISS и YAGNI — практические принципы, которые помогают управлять сложностью кода. Это не абсолютные запреты, а эвристики для выбора между несколькими решениями.

- **DRY, Don't Repeat Yourself:** у каждого знания, правила или решения должен быть один авторитетный источник. Принцип направлен не против одинаковых строк кода, а против нескольких независимых копий одного смысла.
- **KISS, Keep It Simple:** среди корректных решений, удовлетворяющих известным требованиям, выбирают наиболее простое для понимания и изменения. Простое не означает короткое, примитивное или неполное.
- **YAGNI, You Aren't Gonna Need It:** не следует заранее реализовывать возможности, которые пока не нужны. Предполагаемую потребность можно зафиксировать как идею, но не нужно оплачивать её сложностью текущего кода.

Например, одинаковая JSX-разметка двух карточек ещё не обязательно нарушает DRY. Карточки могут относиться к разным предметным областям и со временем развиваться по-разному.

Но формула скидки, правило доступа или преобразование ответа API не должны иметь несколько независимых реализаций. После изменения требования такие копии могут начать давать разные результаты.

```text
Повторяются строки
→ возможно, это допустимое сходство

Повторяется одно правило
→ вероятно, нужен единый источник истины
```

KISS оценивает не количество строк и файлов, а сложность понимания, проверки и изменения.

Один компонент с тридцатью флагами может быть короче нескольких специализированных компонентов, но допустимые сочетания его props сложнее понять и протестировать.

Разделение интерфейса, поведения и работы с API иногда делает решение проще, хотя кода становится больше.

YAGNI ограничивает преждевременное обобщение.

Не нужно:

- строить plugin system для двух вариантов формы;
- переносить локальное состояние dropdown в глобальное хранилище «на будущее»;
- создавать несколько Adapter без реальных альтернативных реализаций;
- поддерживать параметры, которые пока никто не использует.

При этом YAGNI не запрещает:

- давать модулям понятные границы;
- скрывать нестабильную внешнюю систему;
- писать код, который можно безопасно изменить;
- учитывать уже согласованные требования.

Безопасность, доступность, обработку ошибок и поддержку согласованных браузеров нельзя считать гипотетическими возможностями.

Эти принципы могут предлагать разные решения.

DRY может предложить вынести общее правило, а KISS и YAGNI — оставить похожий код раздельным, пока общее поведение не стало устойчивым.

Решение принимают по смыслу и причинам изменения, а не по количеству повторившихся строк.

Практический порядок:

```text
появилось сходство
→ проверить, повторяется ли одно знание
→ сравнить причины изменения
→ сформулировать понятный контракт
→ только затем выделять абстракцию
```

Иногда используют Rule of Three, или правило трёх: после нескольких реальных повторений общая форма обычно становится понятнее.

Это лишь эвристика, а не обязательный порог. Критичное бизнес-правило может потребовать одного источника уже при первом появлении, а три визуально похожих блока могут оставаться независимыми.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем повторение кода отличается от повторения знания?</strong></summary>

<dl>
<dd>
<h2></h2>

Повторение кода означает, что фрагменты текста программы похожи.

Повторение знания означает, что одно правило или решение независимо записано в нескольких местах.

Второе опаснее: копии могут начать давать разные результаты после изменения требования.

Например, похожая разметка `ProductCard` и `ArticleCard` может быть случайным совпадением.

А две функции, каждая из которых по-своему определяет, доступна ли пользователю оплата, дублируют бизнес-правило.

Такое правило должно иметь:

- один авторитетный источник;
- либо единый контракт, который все реализации обязаны соблюдать.

DRY относится прежде всего к знаниям и решениям, а не к визуальному совпадению строк.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда похожий код лучше не объединять?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда сходство поверхностное, а причины изменения разные.

Если два компонента принадлежат разным сценариям и их требования меняют разные части продукта, общая абстракция свяжет независимый код.

Признаки неудачного объединения:

- общий компонент постоянно получает флаги только для одного потребителя;
- внутри появляется всё больше условных ветвей;
- изменение одного сценария требует проверять остальные;
- название общей абстракции перестаёт объяснять её назначение;
- потребители используют только небольшую и разную часть её API.

В таком случае небольшое повторение разметки обычно дешевле зависимости между независимыми сценариями.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нарушает ли DRY одинаковая валидация на frontend и backend?</strong></summary>

<dl>
<dd>
<h2></h2>

Не обязательно.

Backend обязан проверять недоверенные данные и остаётся источником истины для бизнес-ограничений.

Frontend может повторить часть проверок, чтобы сразу подсветить ошибку пользователю, но не может заменить серверную валидацию.

```text
Frontend validation
→ быстрый UX

Backend validation
→ защита доверенной границы
```

Одна и та же проверка выполняется в двух средах по разным причинам.

DRY нарушается скорее тогда, когда само бизнес-правило независимо описано в нескольких местах и может разойтись.

Расхождение уменьшают через общее описание контракта:

- JSON Schema;
- OpenAPI;
- общую библиотеку схем;
- кодогенерацию;
- единый предметный тип ошибки.

Даже при общем описании проверки выполняются и на frontend, и на backend, потому что у них разные задачи и границы доверия.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли общий helper улучшает DRY?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Helper, или вспомогательная функция, полезен, когда у операции есть устойчивый смысл и понятное имя.

Например:

```ts
formatCurrency()
```

может скрывать единое правило форматирования денег.

Функция:

```ts
processData()
```

которая объединяет несвязанные преобразования только ради устранения похожих строк, скрывает зависимости и ухудшает читаемость.

Большой файл `utils` часто размывает границы:

- в нём смешиваются правила разных предметных областей;
- функции получают слишком общие имена;
- изменение общего helper затрагивает неожиданных потребителей;
- становится непонятно, кто владеет правилом.

Полезнее размещать функцию рядом с модулем или предметным знанием, которому она принадлежит.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>KISS означает писать всё в одном компоненте?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Один файл может быть сложнее набора небольших модулей, если в нём смешаны:

- загрузка данных;
- правила доступа;
- управление формой;
- аналитика;
- представление.

Разделение оправдано, когда каждая часть получает ясную ответственность и понятный контракт.

Лишние слои тоже нарушают KISS.

Если React-хук, service и repository только передают одни и те же аргументы в `fetch`, не добавляя собственного смысла, разработчику приходится проходить больше уровней без выигрыша.

```text
component
→ hook
→ service
→ repository
→ http client
→ fetch
```

Названия слоёв сами по себе не делают решение простым.

Нужен минимальный набор границ, который действительно скрывает сложность или нестабильную деталь.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем простое решение отличается от быстрого временного решения?</strong></summary>

<dl>
<dd>
<h2></h2>

Простое решение корректно покрывает требования и явно обрабатывает важные состояния.

Временное решение часто скрывает долг:

- не обрабатывает ошибку;
- допускает невозможные состояния;
- смешивает независимые ответственности;
- зависит от случайной структуры данных;
- не учитывает согласованные ограничения.

KISS не требует минимального числа строк.

Например, явная модель состояний:

```ts
type RequestState =
  | {
      status: "idle";
    }
  | {
      status: "loading";
    }
  | {
      status: "success";
      data: Data;
    }
  | {
      status: "error";
      error: Error;
    };
```

может быть проще для сопровождения, чем набор независимых boolean-флагов:

```ts
isLoading
isSuccess
isError
hasData
```

Дискриминируемое объединение занимает больше строк, но исключает противоречивые сочетания состояний.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как YAGNI сочетается с проектированием архитектуры?</strong></summary>

<dl>
<dd>
<h2></h2>

Архитектура должна поддерживать известные сценарии и оставлять понятные места для изменений, но не реализовывать все воображаемые варианты.

Например, можно отделить работу с API от отображения, если это уже разные ответственности.

Но не нужно создавать систему адаптеров для пяти предполагаемых способов обмена данными без второй реальной реализации и причины её появления.

Полезно откладывать легко обратимые решения:

- локальное имя helper;
- расположение небольшой функции;
- способ реализации внутреннего компонента.

Дорогие и трудно обратимые решения требуют большего анализа:

- публичный API библиотеки;
- формат данных;
- границы между командами;
- схема авторизации;
- выбор платформы;
- архитектура хранения данных.

YAGNI не означает, что любые предварительные решения запрещены. Оно предлагает не реализовывать дополнительную функциональность без подтверждённой потребности.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Оправдывает ли YAGNI отказ от оптимизации производительности?</strong></summary>

<dl>
<dd>
<h2></h2>

YAGNI предостерегает от оптимизации по предположению, но не от исправления измеренной проблемы.

Обычно порядок такой:

1. определить пользовательский симптом;
2. измерить его профилировщиком или метриками;
3. найти реальную причину;
4. применить минимальное исправление;
5. повторно измерить результат.

Некоторые ограничения известны заранее.

Например, не следует без необходимости:

- загружать многомегабайтный JavaScript на первом экране;
- выводить десятки тысяч DOM-узлов;
- отправлять один запрос для каждого элемента списка;
- выполнять тяжёлые вычисления при каждом render.

Это не преждевременная оптимизация, а соблюдение известных требований и ограничений платформы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда уже пора выделять абстракцию?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда:

- повторяется одно и то же знание;
- стала понятна причина его изменения;
- копии уже начали расходиться;
- изменение приходится синхронно вносить в несколько мест;
- общее поведение можно назвать предметным термином;
- контракт формулируется без исключений для каждого потребителя.

Полезная абстракция отвечает на вопрос:

```text
Какое знание теперь имеет один источник истины?
```

Количество повторений само по себе не является строгим критерием.

Rule of Three может служить сигналом: после нескольких реальных повторений обычно легче увидеть устойчивую общую часть.

Но критичное правило доступа можно централизовать при первом появлении, а три визуально похожих компонента лучше оставить независимыми, если они меняются по разным причинам.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как распознать переобобщённый компонент?</strong></summary>

<dl>
<dd>
<h2></h2>

Его props кодируют множество несвязанных режимов:

```text
isCompact
isAdmin
asLink
withActions
legacyMode
isOrder
isUser
```

Признаки проблемы:

- часть комбинаций бессмысленна;
- некоторые props работают только вместе;
- изменение одного режима ломает другой;
- внутри много ветвлений;
- название компонента больше не описывает единый контракт;
- разные потребители используют несовместимые части API.

Обычно помогает разделить компоненты по реальным сценариям и вынести только подтверждённую общую основу.

Для допустимых взаимоисключающих вариантов можно использовать:

- композицию;
- отдельные компоненты;
- Strategy;
- discriminated union.

Дискриминируемое объединение позволяет типу явно определить допустимые сочетания props вместо набора независимых optional-полей.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Принцип | Практическое решение |
|---|---|
| DRY | Единая функция форматирует деньги по согласованным правилам |
| DRY | Контракт API генерируется из OpenAPI вместо ручного повторения DTO |
| KISS | Явные состояния запроса используются вместо набора противоречивых флагов |
| KISS | Компонент делится по ответственностям, если это упрощает путь изменения |
| YAGNI | Локальное состояние не переносится в глобальное хранилище без потребителей |
| YAGNI | Система подключаемых расширений не создаётся до появления реальной потребности |
