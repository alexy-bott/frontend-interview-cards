## Вопрос

<br>

 💬 **Что такое coupling и cohesion? Как связанность и цельность модулей влияют на frontend-архитектуру?**

<h2></h2>

<br>
<dl>
<dd>

Coupling, или связанность, показывает, насколько один модуль зависит от другого, какие его детали должен знать и насколько изменение одной стороны влияет на другую.

При оценке связанности важны:

- сила зависимости;
- её направление;
- явность;
- устойчивость используемого контракта;
- радиус изменений при модификации модуля.

Cohesion, или цельность модуля, показывает, насколько тесно код внутри модуля работает на одну понятную задачу или область поведения.

Обычно стремятся к:

```text
высокой cohesion
+
контролируемой coupling
```

Полностью независимые модули не взаимодействовали бы и не могли составить приложение.

Поэтому задача не в том, чтобы устранить все зависимости, а в том, чтобы заменить случайную связанность с изменчивыми деталями на явную зависимость от небольшого устойчивого контракта.

Например, модуль редактирования профиля является цельным, если его:

- компоненты;
- состояние;
- правила формы;
- запрос сохранения;

обслуживают один пользовательский сценарий.

Он сильно связан с соседним модулем, если:

- импортирует его внутренние файлы;
- напрямую изменяет его store;
- зависит от точной структуры его backend DTO;
- должен знать скрытый порядок его внутренних операций.

Связанность проявляется не только в `import`.

Основные примеры:

- **Связанность с внутренним устройством.** Потребитель делает deep import, то есть импортирует файл в обход публичного API модуля.
- **Связанность по структуре данных.** Компонент получает весь `UserDTO`, хотя использует только имя и аватар, и начинает зависеть от серверной модели.
- **Управляющая связанность.** Потребитель передаёт флаги, определяющие внутренний алгоритм другого модуля: `isAdmin`, `useLegacyFlow`, `skipValidation`.
- **Временная связанность.** Методы необходимо вызвать в неочевидном порядке, например сначала `initialize()`, затем `load()`.
- **Связанность через общее состояние.** Независимые модули читают и изменяют один глобальный объект, поэтому их поведение начинает влиять друг на друга.
- **Неявная событийная связанность.** Модули взаимодействуют через события, но зависят от имени события, структуры payload и момента его отправки.

Граф imports показывает только часть зависимостей.

Runtime-связанность также может возникать через:

- React Context;
- глобальный store;
- event bus;
- browser storage;
- глобальные переменные;
- URL;
- cookies;
- порядок вызовов.

Высокая цельность не означает «всё в одном файле».

Внутри функционального модуля могут быть отдельные сегменты:

```text
ui
model
api
lib
```

Если все они совместно обслуживают одну предметную задачу, модуль может оставаться цельным.

Например:

```text
features/edit-profile/
  ui/
  model/
  api/
```

может объединять форму, состояние и операцию сохранения профиля.

Низкая цельность возникает, когда код сгруппирован только по техническому признаку, но не имеет общей предметной задачи.

Например:

```text
utils.ts
```

может одновременно содержать:

- форматирование денег;
- проверку прав;
- работу с датами;
- преобразование заказов;
- обработку URL.

Такие функции имеют разные причины изменения и разных владельцев требований.

Cohesion связана с SRP, но не полностью совпадает с ним.

SRP спрашивает:

```text
По каким причинам меняется модуль?
```

Cohesion спрашивает:

```text
Насколько тесно его внутренние части работают на одну задачу?
```

Границы модулей локализуют изменения.

Для этого используют:

- public API;
- направленные правила импортов;
- узкие props;
- adapters между DTO и моделями приложения;
- selectors и публичные actions;
- явного владельца состояния;
- предметные операции вместо доступа к внутренним данным.

Хорошая граница позволяет потребителю знать:

```text
что модуль предоставляет
```

но не требует знать:

```text
как модуль это реализует
```

Например:

```ts
import {
  updateProfile,
} from "@/features/edit-profile";
```

безопаснее, чем зависимость от внутреннего файла:

```ts
import {
  updateProfileReducer,
} from "@/features/edit-profile/model/store/updateProfileSlice";
```

Полностью убрать зависимости нельзя и не нужно.

Явная зависимость от стабильного публичного контракта является нормальной частью архитектуры.

Проблемой становится зависимость от:

- внутренней структуры;
- нестабильного DTO;
- глобального изменяемого состояния;
- скрытого порядка операций;
- большого количества необязательных режимов.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что такое tight coupling?</strong></summary>

<dl>
<dd>
<h2></h2>

Tight coupling, или сильная связанность, возникает, когда потребитель зависит от внутренних или нестабильных деталей другого модуля.

Например, разные функциональные модули напрямую:

- читают структуру чужого store;
- импортируют reducers из внутренних файлов;
- изменяют чужие данные;
- знают внутренние HTTP status codes;
- зависят от конкретного SDK.

Сильная связанность видна по широкому радиусу изменений:

```text
небольшое изменение детали
→ требует менять много несвязанных потребителей
```

Другие признаки:

- модуль трудно протестировать отдельно;
- его нельзя использовать без запуска большой части приложения;
- рефакторинг внутренней структуры становится опасным;
- потребители содержат условия для конкретных реализаций.

Не любая зависимость является tight coupling.

Зависимость от небольшого стабильного public API может быть сильной по смыслу, но безопасной по устройству.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означает high cohesion?</strong></summary>

<dl>
<dd>
<h2></h2>

High cohesion, или высокая цельность, означает, что содержимое модуля объединено одной задачей и изменяется по связанным причинам.

Например:

```text
features/edit-profile
```

может содержать:

- форму редактирования;
- состояние отправки;
- правила валидации;
- mutation сохранения;
- преобразование данных формы.

Это части одного пользовательского действия.

Файл или папка не становятся цельными только из-за общего технического типа содержимого.

Например:

```text
hooks/
```

может содержать React-хуки из несвязанных предметных областей:

- авторизации;
- корзины;
- аналитики;
- редактора профиля.

Технически все файлы являются hooks, но смысловой цельности у каталога почти нет.

Высокая cohesion помогает:

- быстрее находить код сценария;
- локализовать изменения;
- уменьшать количество внешних зависимостей;
- формировать понятный public API.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как импорты помогают найти нарушение границ?</strong></summary>

<dl>
<dd>
<h2></h2>

Подозрительными могут быть:

- циклические зависимости;
- импорты внутренних путей в обход public API;
- зависимость нижнего архитектурного слоя от верхнего;
- прямые imports между независимыми функциональными модулями;
- массовые imports из общего barrel-файла.

Они показывают, что потребитель знает расположение или внутреннее устройство чужого модуля.

Например:

```ts
import {
  cartReducer,
} from "@/features/cart/model/store";
```

раскрывает внутреннюю структуру `cart`.

Предпочтительнее публичная операция:

```ts
import {
  clearCart,
} from "@/features/cart";
```

Не каждый deep import плох.

Внутри одного модуля прямые относительные imports могут быть нормальными:

```ts
features/cart/model
→ features/cart/lib
```

Важна пересекаемая архитектурная граница.

Правило должно защищать внешний контракт модуля, а не запрещать любые относительные пути.

В FSD также учитывают направление слоёв и независимость slices. Если прямой импорт между features запрещён, их координацию размещают в более высоком слое или пересматривают владельца сценария.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое public API модуля?</strong></summary>

<dl>
<dd>
<h2></h2>

Public API, или публичный интерфейс модуля, — это явно разрешённый набор:

- компонентов;
- функций;
- типов;
- selectors;
- actions;
- предметных операций.

Остальные файлы считаются внутренней реализацией и могут меняться без массового обновления проекта.

В TypeScript-проекте публичный API часто выражают через:

```text
index.ts
```

Например:

```ts
export {
  CartButton,
} from "./ui/CartButton";

export {
  selectCartTotal,
  clearCart,
} from "./model";
```

Но `index.ts` является только техническим entry point.

Он не создаёт хорошую границу автоматически.

Если из него экспортировать всё содержимое папки:

```ts
export * from "./model/store";
export * from "./api";
export * from "./lib";
```

внутренние детали фактически становятся публичными.

Хороший public API должен быть:

- ограниченным;
- понятным;
- устойчивым;
- сформулированным на языке потребителя.

Границу дополнительно защищают:

- ESLint import rules;
- package exports;
- соглашения проекта;
- архитектурные тесты.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему передача всего DTO усиливает связанность?</strong></summary>

<dl>
<dd>
<h2></h2>

DTO, Data Transfer Object, или объект передачи данных, отражает контракт обмена с backend.

Например:

```ts
type UserResponseDTO = {
  user_id: string;
  profile_data: {
    full_name: string;
    avatar_url: string | null;
  };
  permissions: string[];
};
```

Если UI-компонент принимает весь DTO, он начинает зависеть от:

- названий серверных полей;
- вложенности ответа;
- формата permissions;
- транспортной модели.

Даже если компонент использует только имя и аватар, изменение backend-контракта может потребовать менять его props.

Adapter может преобразовать DTO:

```ts
type UserAvatarModel = {
  name: string;
  imageUrl?: string;
};
```

Компонент получает узкий контракт:

```tsx
<UserAvatar
  name={user.name}
  imageUrl={user.imageUrl}
/>
```

Это не означает, что нужно создавать копию каждого типа.

Отдельная модель особенно полезна там, где:

- серверная и пользовательская модели различаются;
- DTO нестабилен;
- UI использует вычисленные данные;
- компонент является независимым shared-элементом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое временная связанность и как её уменьшить?</strong></summary>

<dl>
<dd>
<h2></h2>

Временная связанность означает, что корректность зависит от скрытого порядка операций.

Например:

```ts
client.setToken(token);
await client.initialize();
await client.loadUser();
```

Если `loadUser()` вызвать раньше, модуль ломается, но API не показывает это ограничение.

Временную связанность уменьшают несколькими способами.

Передают обязательные данные при создании:

```ts
const client =
  createAuthorizedClient(token);
```

Объединяют неделимые шаги:

```ts
await authenticateAndLoadUser(
  credentials,
);
```

Явно моделируют состояния:

```ts
type ClientState =
  | {
      status: "anonymous";
    }
  | {
      status: "authorized";
      client: AuthorizedClient;
    };
```

Главная цель — сделать невозможный порядок операций трудным или невозможным для выражения через публичный API.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему глобальный store может усиливать связанность?</strong></summary>

<dl>
<dd>
<h2></h2>

Глобальный store делает данные технически доступными всему приложению.

Само наличие общего хранилища не является проблемой.

Связанность усиливается, когда компонент:

- читает внутреннюю структуру чужого slice;
- напрямую изменяет не принадлежащие ему данные;
- зависит от большого объекта состояния;
- использует store как неявный канал общения между модулями.

Например:

```ts
state.cart.internal.items
```

связывает потребителя со структурой реализации `cart`.

Публичный selector скрывает её:

```ts
selectCartItems
```

Публичное action или предметная операция скрывает способ изменения:

```ts
removeCartItem()
clearCart()
```

Selectors и actions уменьшают структурную связанность, но не устраняют смысловую зависимость.

Если `checkout` использует данные корзины, он всё равно зависит от контракта `cart`. Важно, чтобы эта зависимость была явной и ограниченной.

В глобальном store стоит держать состояние, которое:

- действительно разделяется удалёнными частями приложения;
- должно переживать жизненный цикл отдельных компонентов;
- имеет понятного владельца.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>События всегда уменьшают связанность между модулями?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Событие убирает прямой вызов отправителя к конкретному получателю, но создаёт другие зависимости:

- от имени события;
- от структуры payload;
- от момента отправки;
- от гарантии доставки;
- от порядка обработчиков;
- от списка скрытых подписчиков.

Например:

```ts
eventBus.emit(
  "order_completed",
  order,
);
```

Отправитель может не знать получателей, но вся система должна одинаково понимать контракт `order_completed`.

Если событие не задокументировано и не типизировано, поток выполнения становится трудно проследить.

События полезны, когда отправитель действительно не должен знать получателей:

- аналитика;
- журналирование;
- независимые реакции на завершённый факт;
- интеграционные события.

Для обязательной операции с ожидаемым результатом явный вызов обычно понятнее:

```ts
await reserveStock(order);
```

чем событие, успешность обработки которого отправитель не может определить.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему папка <code>shared</code> может увеличить связанность?</strong></summary>

<dl>
<dd>
<h2></h2>

В `shared` легко вынести код до понимания его владельца.

В результате общий helper начинает импортировать модели разных функциональных модулей:

```text
shared/utils
  → cart
  → orders
  → profile
```

Теперь изменение общей функции затрагивает большую часть проекта, а нижний общий слой зависит от предметных областей.

В `shared` обычно подходят:

- UI primitives;
- инфраструктурные клиенты;
- независимые утилиты;
- базовые типы без предметной логики;
- общие конфигурационные инструменты.

Предметное правило следует оставлять у владельца:

```text
правило расчёта корзины
→ cart

правило доступности оплаты
→ checkout или payment

преобразование заказа
→ order
```

Даже если правилом пользуются несколько внутренних компонентов модуля, это не делает его глобально общим.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли связанность быть полезной?</strong></summary>

<dl>
<dd>
<h2></h2>

Да.

Модули должны взаимодействовать, поэтому нулевая связанность невозможна.

Функциональный модуль нормально зависит от:

- стабильного компонента дизайн-системы;
- явно определённого API-контракта;
- публичного selector;
- предметной операции другого владельца;
- стандартного browser API.

Нужно оценивать:

- направление зависимости;
- размер контракта;
- его устойчивость;
- явность;
- необходимость взаимодействия.

Явная зависимость:

```ts
import {
  formatCurrency,
} from "@/shared/lib/currency";
```

безопаснее, чем косвенная зависимость от глобальной переменной:

```ts
window.appCurrency
```

Цель — не отсутствие связей, а управляемые связи через подходящие границы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как понять, что граница модуля выбрана неудачно?</strong></summary>

<dl>
<dd>
<h2></h2>

Практический сигнал дают реальные изменения.

Если файлы почти всегда меняются вместе, но находятся по разные стороны границы, связанные части могли быть разделены искусственно.

Если один модуль постоянно меняется по несвязанным причинам, внутри него могли смешаться разные ответственности.

Дополнительные признаки:

- циклические imports;
- постоянно растущий public API;
- регулярные deep imports в обход границы;
- большое число исключений в правилах зависимостей;
- преобразование одних и тех же данных туда и обратно;
- десятки мелких вызовов между двумя модулями;
- необходимость знать внутренний порядок операций;
- частые изменения двух модулей в одной задаче.

Большое число мелких вызовов может указывать на разговорчивую границу:

```text
module A
→ getName()
→ getPrice()
→ getStatus()
→ getOwner()
→ updateStatus()
```

Возможно, потребителю нужна одна более цельная операция или модель данных.

История Git, import graph и частые конфликты дают сигналы, но окончательное решение принимают по предметному смыслу и владельцу данных.

</dl>

</details>

## Мини-задача

```text
Feature `checkout` импортирует `features/cart/model/store`, напрямую меняет массив товаров
и передаёт полный `OrderResponseDTO` в компонент итоговой суммы.
Какие виды связанности здесь возникают и как изменить границы?
```

Возникают несколько видов связанности.

Прямой импорт:

```text
features/cart/model/store
```

связывает `checkout` с внутренней структурой `cart` и обходит public API.

Прямое изменение массива создаёт связанность через общее изменяемое состояние и нарушает владение данными.

Передача полного `OrderResponseDTO` связывает UI с транспортным контрактом backend.

`cart` должен предоставить публичные операции и selectors, например:

```ts
selectCartItems
removeCartItem
clearCart
```

или более предметную операцию:

```ts
createCheckoutDraft()
```

Компонент итоговой суммы должен получать подходящую модель:

```ts
type OrderSummaryProps = {
  subtotal: number;
  discount: number;
  total: number;
  currency: string;
};
```

Преобразование `OrderResponseDTO` выполняют на API-границе или в модуле, владеющем моделью заказа.

Если архитектура запрещает прямую зависимость `checkout` от `cart` как двух features одного слоя, их координацию можно разместить:

- в widget;
- в page;
- в app-level сценарии;
- в отдельном более высокоуровневом процессе.

Не нужно переносить правила корзины в `shared`.

Владельцем данных и операций корзины остаётся `cart`, а `checkout` или координирующий слой зависит только от его публичного контракта.

## Где это встречается во frontend

| Ситуация | Улучшение границы |
|---|---|
| Функциональный модуль импортирует внутренний reducer соседнего модуля | Публичная операция или пересмотр владельца сценария |
| UI зависит от вложенной структуры ответа backend | Adapter и локальная модель представления |
| Компонент получает всё глобальное состояние | Selector возвращает минимально нужные данные |
| Общий компонент управляется множеством флагов | Разделение сценариев или композиция вариантов |
| Методы требуют скрытого порядка вызовов | Явная операция, factory или модель состояний |
| Модули обмениваются десятками мелких вызовов | Более цельный контракт или пересмотр границы |
