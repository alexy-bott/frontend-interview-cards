## Вопрос

<br>

 💬 **Чем GraphQL отличается от REST? Когда GraphQL полезен frontend-команде и какую сложность он добавляет?**

<h2></h2>

<br>
<dl>
<dd>

REST и GraphQL решают похожие задачи, но находятся на разных уровнях.

REST является архитектурным стилем, в котором HTTP API обычно строится вокруг ресурсов: URL идентифицирует ресурс, метод выражает намерение, HTTP-статус сообщает результат, а кеширование использует стандартную семантику HTTP.

GraphQL является языком запросов, системой типов и набором правил выполнения операций над типизированной schema, то есть схемой доступных данных и действий. Клиент может запрашивать только поля и операции, которые сервер явно открыл в schema.

GraphQL не является обязательной заменой REST. Например, GraphQL gateway или BFF может собирать данные из REST API, gRPC и баз данных, а загрузку файлов приложение продолжит выполнять через отдельный HTTP endpoint.

В GraphQL клиент описывает точный набор нужных полей:

```graphql
query UserPage($id: ID!) {
  user(id: $id) {
    id
    name
    avatarUrl
    orders(first: 5) {
      nodes {
        id
        status
      }
    }
  }
}
```

Форма `data` в ответе соответствует форме selection set, то есть выбранных полей операции. Если клиент не запросил поле, сервер не должен включать его в результат этой операции.

Schema определяет:

- типы объектов;
- поля и их аргументы;
- скалярные значения;
- `enum`;
- интерфейсы и объединения;
- входные типы;
- nullable- и non-null-поля;
- корневые операции.

Основные типы операций:

- `query` предназначен для чтения данных;
- `mutation` предназначен для изменения состояния;
- `subscription` описывает длительный поток результатов.

В одной `mutation` корневые поля выполняются последовательно. Это позволяет предсказуемо выполнить несколько корневых изменений в указанном порядке.

Однако `mutation` сама по себе не гарантирует:

- транзакцию базы данных;
- откат всех предыдущих изменений при ошибке;
- идемпотентность;
- защиту от повторной отправки;
- выполнение операции ровно один раз.

Эти свойства определяет серверный контракт конкретного поля.

Запросы и mutations часто отправляют на один HTTP endpoint:

```text
/graphql
```

Это распространённое соглашение, а не главное свойство GraphQL. У сервиса может быть несколько GraphQL endpoints или другой транспорт.

Ядро GraphQL не требует HTTP и не определяет cookie, TLS, CORS или конкретные HTTP-статусы. Для query и mutation обычно используют HTTP, а subscription часто передают через WebSocket или SSE.

Поэтому при работе с GraphQL никуда не исчезают:

- аутентификация;
- авторизация;
- CORS;
- сетевые ошибки;
- отмена запроса;
- timeout;
- повторные попытки;
- мониторинг;
- защита от CSRF при cookie-аутентификации.

GraphQL уменьшает overfetching, то есть получение лишних полей, когда REST endpoint возвращает больше данных, чем нужно конкретному экрану.

Он также уменьшает underfetching, то есть нехватку данных одного ответа, когда frontend вынужден последовательно получать пользователя, его заказы, права и связанные сущности.

Клиент может запросить связанную форму данных одной GraphQL-операцией, а сервер решает, из каких источников её собрать.

Это не означает, что GraphQL полностью устраняет overfetching и underfetching.

GraphQL уменьшает лишние данные на границе между клиентом и GraphQL-сервером. Внутри backend сервер всё ещё может:

- получить из базы больше колонок, чем требуется;
- вызвать несколько внутренних сервисов;
- повторно загрузить одну сущность;
- выполнить дорогую агрегацию;
- обратиться к источнику, который не поддерживает выбор отдельных полей.

Одна GraphQL-операция также не означает один запрос к базе данных или одному микросервису.

Значение поля обычно получает resolver, то есть серверная функция вычисления поля. Resolver получает родительское значение, аргументы, контекст запроса и информацию об операции.

Например, resolver поля `User.orders` может загрузить заказы конкретного пользователя.

Наивная реализация списка создаёт проблему N+1:

```text
1 запрос пользователей
+
N запросов заказов для каждого пользователя
```

Сервер уменьшает проблему через:

- пакетную загрузку;
- join или оптимизированный запрос;
- кеш в пределах текущего GraphQL-запроса;
- DataLoader-подобный механизм;
- предварительную загрузку связанных данных.

Кеш пакетной загрузки обычно ограничивают одним запросом пользователя. Общий кеш между запросами требует отдельного контроля прав, актуальности и tenant, иначе один пользователь может получить данные другого.

Авторизация не должна существовать только во frontend или только в одном корневом resolver.

Сервер проверяет право:

- выполнить операцию;
- получить конкретный объект;
- прочитать отдельное поле;
- изменить конкретную сущность;
- подписаться на конкретный поток.

Скрытие поля или кнопки во frontend улучшает UX, но не защищает GraphQL operation от прямого вызова.

GraphQL различает request errors и execution errors.

Request error возникает до выполнения полей, например если:

- GraphQL-документ содержит синтаксическую ошибку;
- запрошено несуществующее поле;
- операция не прошла validation;
- не указано, какую из нескольких операций выполнить;
- variables не соответствуют объявленным типам.

В таком случае выполнение не начинается, `data` отсутствует, а ответ содержит `errors`.

Execution error возникает во время выполнения конкретного поля. Например:

- resolver выбросил исключение;
- внутренний сервис недоступен;
- пользователь не имеет доступа к полю;
- resolver вернул `null` для non-null-типа;
- результат нельзя привести к типу schema.

В таком случае GraphQL пытается продолжить выполнение соседних полей и может вернуть частичный результат:

```json
{
  "data": {
    "user": {
      "id": "42",
      "name": "Alex",
      "avatarUrl": null
    }
  },
  "errors": [
    {
      "message": "Avatar service is unavailable",
      "path": ["user", "avatarUrl"]
    }
  ]
}
```

Основные поля ошибки:

- `message` — описание для разработчика;
- `locations` — позиции связанных элементов GraphQL-документа;
- `path` — путь до поля результата, на котором возникла ошибка;
- `extensions` — дополнительные данные конкретной реализации.

GraphQL не стандартизирует универсальное значение `extensions.code`. API может определить собственные стабильные коды:

```json
{
  "message": "Access denied",
  "path": ["user", "email"],
  "extensions": {
    "code": "FORBIDDEN"
  }
}
```

Frontend не должен принимать программные решения через разбор строки `message`. Он использует согласованный код, тип результата или другое стабильное поле контракта.

Ожидаемые бизнес-результаты, например ошибки заполнения формы, часто удобнее моделировать как обычные данные schema:

```graphql
type UpdateUserPayload {
  user: User
  fieldErrors: [FieldError!]!
}
```

или через union:

```graphql
union UpdateUserResult =
    UpdateUserSuccess
  | ValidationError
  | PermissionError
```

Тогда codegen создаёт явный тип результата, а frontend обрабатывает ожидаемое состояние через `__typename`.

Top-level `errors` чаще оставляют для ошибок выполнения, инфраструктуры или других исключительных ситуаций. Конкретная граница является частью соглашений проекта.

Если nullable-поле завершилось ошибкой, его значение заменяется на `null`, а соседние поля могут остаться в `data`.

Если ошибка возникла в non-null поле, которое не допускает `null`, она распространяется вверх до ближайшего родительского поля, где `null` разрешён.

Например:

```graphql
type User {
  profile: Profile!
}
```

Если `profile` не может быть вычислен, GraphQL не может вернуть:

```json
{
  "profile": null
}
```

при обещании `Profile!`. Поэтому `null` распространяется на родителя `User` или ещё выше, если родитель тоже non-null.

Избыточное использование non-null может превратить локальную ошибку одного поля в потерю крупной части результата. Слишком большое количество nullable-полей, наоборот, заставляет frontend повсюду обрабатывать отсутствие значений. Nullability является важной частью API-дизайна, а не только синтаксисом schema.

GraphQL core specification не устанавливает HTTP-статусы. Их определяет HTTP-транспорт и контракт сервера.

На август 2026 года GraphQL over HTTP остаётся prerelease working draft. Он вводит специальный media type ответа:

```http
application/graphql-response+json
```

Клиенту рекомендуется сообщать его поддержку:

```http
Accept: application/graphql-response+json, application/json;q=0.9
```

Текущий draft рекомендует:

- `200` для успешного ответа с `data` без `errors`;
- подходящий `4xx` для синтаксических, validation- и других request errors;
- подходящий `5xx`, если сервер не способен обработать запрос;
- нестандартный `294 Partial Success` для ответа, содержащего одновременно `data` и `errors`.

Рекомендация `294` относится к текущему draft и может измениться до окончательной публикации. Она также ещё не поддерживается всеми серверами, клиентами, proxy и инструментами.

Многие существующие GraphQL API используют `application/json` и возвращают `200` при execution errors, включая ответ с частичными `data` и `errors`.

Поэтому frontend должен проверять:

1. Получен ли HTTP-ответ.
2. Какой у него `Content-Type`.
3. Какой HTTP-статус определяет контракт сервера.
4. Присутствует ли `data`.
5. Присутствует ли непустой массив `errors`.
6. Можно ли использовать частичные данные.

Нельзя считать, что `response.ok === true` означает отсутствие GraphQL-ошибок.

Клиентский кеш GraphQL часто нормализует сущности. Он хранит сущность один раз, а результаты разных операций содержат ссылки на эту запись.

Распространённый ключ выглядит как сочетание:

```text
__typename + id
```

Например:

```text
User:42
```

`__typename` является стандартным GraphQL meta-field, но поле `id` и конкретный алгоритм нормализации не являются обязательной частью GraphQL Specification. Schema должна предоставить устойчивую идентичность, а клиентская библиотека — знать, какие поля образуют cache key.

Если сущность не имеет стандартного `id`, библиотеке задают собственные key fields или отключают нормализацию для этого типа.

Нормализованный кеш помогает обновить одну сущность во всех местах, где на неё ссылаются. Например, mutation возвращает обновлённый объект:

```graphql
mutation RenameUser($id: ID!, $name: String!) {
  renameUser(id: $id, name: $name) {
    id
    name
  }
}
```

Если клиент распознает тот же `User:42`, он может обновить его поля автоматически.

Однако нормализация не всегда понимает, как изменить структуру коллекции. После создания или удаления сущности может понадобиться:

- добавить ссылку в конкретный список;
- удалить её из списка;
- настроить merge pagination;
- инвалидировать операцию;
- повторно выполнить query.

Пагинация, разные фильтры и нестандартные идентификаторы требуют явных cache policies.

Нормализованный кеш является возможностью GraphQL-клиента, а не обязательным свойством GraphQL API. Можно использовать GraphQL через обычный `fetch`, RTK Query или TanStack Query без нормализации сущностей.

HTTP-кеширование GraphQL тоже возможно, но часто сложнее, чем у ресурсного REST API.

Query можно передавать через `GET`, если параметры операции помещаются в URL. Тогда браузер, CDN и proxy могут использовать обычный HTTP-кеш с учётом URL и response headers.

Mutation через `GET` выполнять нельзя: `GET` предназначен для безопасных операций чтения.

Большие GraphQL-документы могут не помещаться в URL. Persisted documents позволяют передавать короткий идентификатор или хеш вместо полного текста, что упрощает использование `GET` и CDN.

Кеш всё равно должен учитывать:

- variables;
- пользователя и область доступа;
- заголовок `Authorization`;
- cookie;
- локаль;
- правила `Cache-Control`;
- `Vary`;
- возможность наличия персональных данных.

Один endpoint `/graphql` не запрещает HTTP-кеширование, но требует более явного проектирования cache key и политики безопасности.

GraphQL schema хорошо подходит для codegen, то есть генерации кода.

Обычно генератор использует:

1. Schema сервера.
2. GraphQL-документы конкретных операций.
3. Fragments, используемые этими операциями.

Из них он создаёт:

- тип variables;
- тип конкретного результата;
- функцию или hook запроса;
- типы fragments;
- вспомогательные данные для клиента.

Тип результата должен соответствовать selection set конкретной операции.

Например, общий тип schema может содержать:

```graphql
type User {
  id: ID!
  name: String!
  email: String!
  avatarUrl: String
}
```

Но операция запрашивает только:

```graphql
user {
  id
  name
}
```

Значит, generated result type должен содержать только `id` и `name`. Использовать общий тип всех полей `User` для любого запроса неправильно: незапрошенные поля в ответе отсутствуют.

CI может проверить GraphQL-документы относительно актуальной schema и обнаружить:

- несуществующее поле;
- неправильный аргумент;
- несовместимый тип variable;
- удалённое значение `enum`;
- неверный fragment;
- изменение nullability.

Но generated TypeScript-типы не выполняют runtime validation. Они удаляются при компиляции и не проверяют реальные байты ответа.

Если frontend работает с ненадёжным GraphQL-сервером, разными версиями окружений или критичными данными, на границе может понадобиться runtime validation либо защитное преобразование.

GraphQL schema обычно развивается без создания новой версии всего API.

Новые возможности можно добавлять через:

- новые типы;
- новые поля;
- новые необязательные аргументы;
- новые mutations.

Старые клиенты не запрашивают новые поля, поэтому такие добавления обычно не ломают их.

Несовместимыми могут быть:

- удаление или переименование поля;
- изменение типа поля;
- превращение output-поля из non-null в nullable;
- добавление обязательного аргумента без значения по умолчанию;
- удаление значения `enum`;
- изменение смысла существующего поля;
- изменение поведения ошибки;
- изменение идентичности сущности.

Добавление нового значения `enum` в ответ расширяет schema, но может сломать frontend с исчерпывающим `switch`, который не предусматривает неизвестный вариант.

Устаревающее поле помечают через `@deprecated` с причиной и заменой:

```graphql
type User {
  fullName: String!
  name: String @deprecated(reason: "Use fullName")
}
```

Само добавление `@deprecated` не мигрирует клиентов. Перед удалением поля нужно:

1. Обновить frontend-операции.
2. Перегенерировать типы.
3. Развернуть новые клиенты.
4. Отследить использование старого поля.
5. Учесть старые мобильные и другие долгоживущие клиенты.
6. Только затем удалить поле.

GraphQL упрощает постепенную эволюцию schema, но не отменяет breaking changes и governance, то есть управление владельцами, ревью и жизненным циклом полей.

Без ограничений клиент может отправить очень дорогую операцию:

- слишком глубокое дерево;
- большое количество aliases;
- повторяющиеся fragments;
- множество элементов в списках;
- большое количество resolver-вызовов;
- запрос нескольких дорогих ветвей одновременно.

Одного ограничения глубины недостаточно. Сервер применяет сочетание мер:

- максимальный размер документа;
- ограничение глубины;
- анализ стоимости;
- обязательную пагинацию списков;
- максимальный `first` или `limit`;
- timeout;
- rate limiting;
- ограничение параллельных операций;
- server-side кеш;
- мониторинг дорогих полей.

Persisted document хранит GraphQL-операцию на сервере под идентификатором, обычно хешем. Клиент может передавать только этот идентификатор.

Это уменьшает размер запроса и позволяет серверу заранее анализировать известные операции.

Если сервер принимает только заранее зарегистрированные и проверенные документы, получается allowlist, который также называют trusted documents.

Automatic Persisted Queries работают иначе: если хеш неизвестен, клиент может отправить полный текст, чтобы сервер зарегистрировал его автоматически. Поэтому APQ уменьшает трафик, но сам по себе не запрещает произвольные операции.

Хеш не делает запрос безопасным автоматически. Сервер всё равно проверяет:

- доступ пользователя;
- variables;
- ограничения стоимости;
- срок действия документа;
- соответствие текущей schema.

Subscriptions описывают GraphQL-поток результатов, но GraphQL core specification не назначает обязательный сетевой транспорт.

На практике subscriptions передают через WebSocket или SSE по отдельному community-протоколу. Клиент и сервер должны поддерживать один и тот же транспортный протокол.

После разрыва остаются обычные realtime-задачи:

- reconnect;
- повторная аутентификация;
- восстановление subscriptions;
- пропущенные события;
- дубли;
- гонка начального query и новых событий;
- обновление нормализованного кеша.

GraphQL subscription не гарантирует replay или доставку exactly once. Для редких обновлений polling или повторный query могут быть проще.

REST часто практичнее, когда:

- данные естественно представлены небольшими ресурсами;
- важна стандартная HTTP-семантика;
- нужен простой CDN-кеш;
- API в основном состоит из обычного CRUD;
- требуется загрузка и раздача файлов;
- инфраструктура и команда небольшие;
- публичным клиентам удобны независимые endpoints.

GraphQL полезен, когда:

- экран собирает много связанных данных;
- web, mobile и административный интерфейс требуют разные наборы полей;
- frontend-команды часто ждут изменения специализированных REST endpoints;
- важны operation-level codegen и schema tooling;
- несколько источников нужно скрыть за одной клиентской границей;
- организация готова управлять schema, стоимостью запросов и клиентским кешем.

Выбор не обязан быть глобальным. Приложение может использовать REST для файлов и простых ресурсов, GraphQL для сложных экранов, а WebSocket или SSE для событий.

Главный критерий — не количество endpoints, а общая стоимость контракта: разработка, производительность, безопасность, кеширование, наблюдаемость и дальнейшее развитие API.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что такое GraphQL schema?</strong></summary>

<dl>
<dd>
<h2></h2>

Это типизированный контракт GraphQL API.

Schema описывает:

- типы объектов;
- поля и их аргументы;
- input types;
- `enum`;
- interfaces и unions;
- nullability;
- корневые `query`, `mutation` и `subscription`.

Клиентская операция сначала проверяется относительно schema. Если она запрашивает несуществующее поле или передаёт несовместимый аргумент, выполнение не начинается.

Schema описывает доступную форму API, но сама по себе не доказывает правильность бизнес-логики, производительность resolver или наличие права пользователя на конкретный объект.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое resolver?</strong></summary>

<dl>
<dd>
<h2></h2>

Resolver — серверная функция, которая получает значение GraphQL-поля.

Обычно ей доступны:

- родительский объект;
- аргументы поля;
- контекст запроса;
- информация о выполняемой операции.

Например, resolver `User.orders` загружает заказы пользователя.

Не для каждого простого поля обязательно писать отдельную функцию: GraphQL-реализация может взять одноимённое значение из родительского объекта автоматически.

Общие правила авторизации, пакетной загрузки и доступа к данным лучше размещать в переиспользуемом серверном слое, а не независимо дублировать во множестве resolvers.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Является ли GraphQL заменой REST?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. GraphQL и REST можно использовать как альтернативы или совместно.

GraphQL BFF может собирать данные из нескольких REST API. При этом загрузка файлов, webhooks, публичные кешируемые ресурсы и простые CRUD-операции могут остаться обычными HTTP endpoints.

GraphQL полезен как единая типизированная граница для сложных клиентских данных. REST часто проще там, где хорошо работает ресурсная модель и стандартная HTTP-семантика.

Выбор делают для конкретной системы и сценария, а не по принципу «новая технология должна полностью заменить старую».

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое overfetching и underfetching?</strong></summary>

<dl>
<dd>
<h2></h2>

Overfetching означает, что клиент получает больше полей, чем требуется текущему интерфейсу.

Underfetching означает, что одного ответа недостаточно и клиенту приходится выполнять дополнительные запросы за связанными данными.

GraphQL позволяет клиенту описать нужную форму результата и уменьшает обе проблемы на границе frontend и GraphQL API.

Но сервер всё равно должен получить эту форму эффективно. Один GraphQL-запрос может породить множество обращений к базе данных или внутренним сервисам.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое проблема N+1?</strong></summary>

<dl>
<dd>
<h2></h2>

Один запрос списка порождает отдельную загрузку для каждого элемента.

Например:

```text
1 запрос пользователей
100 запросов заказов каждого пользователя
```

Это происходит, если resolver `User.orders` независимо обращается к источнику для каждого пользователя.

DataLoader-подобный механизм собирает идентификаторы и выполняет одну пакетную загрузку:

```text
SELECT * FROM orders WHERE user_id IN (...)
```

Его кеш обычно ограничивают текущим GraphQL-запросом, чтобы не смешивать данные разных пользователей и не возвращать устаревшее состояние.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли GraphQL вернуть одновременно <code>data</code> и <code>errors</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Да. Execution error отдельного nullable-поля позволяет вернуть остальные данные.

`errors[].path` показывает, какое поле результата завершилось ошибкой.

Если ошибка возникла в non-null поле, `null` распространяется вверх до ближайшего nullable-родителя. Поэтому ошибка одного вложенного поля может обнулить более крупный объект или даже весь `data`.

Клиент должен определить политику:

- показать доступные данные;
- показать локальную ошибку блока;
- признать весь экран неуспешным;
- повторить только нужную операцию.

Одного общего флага `isError` для сложного GraphQL-ответа может быть недостаточно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему GraphQL может вернуть HTTP <code>200</code>, хотя в <code>errors</code> есть ошибки?</strong></summary>

<dl>
<dd>
<h2></h2>

GraphQL core specification не определяет HTTP-статусы. Исторически многие серверы с `Content-Type: application/json` возвращают `200`, если GraphQL-операция дошла до выполнения, даже когда отдельные поля завершились ошибкой.

Текущий prerelease GraphQL-over-HTTP draft вводит `application/graphql-response+json` и рекомендует нестандартный статус `294 Partial Success` для ответа, содержащего одновременно `data` и `errors`.

Поскольку draft ещё может измениться, а реализации отличаются, клиент следует контракту конкретного API и проверяет одновременно:

- HTTP-статус;
- `Content-Type`;
- `data`;
- `errors`.

Нельзя считать `response.ok === true` доказательством отсутствия GraphQL-ошибок.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Гарантирует ли <code>mutation</code> транзакцию и идемпотентность?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

GraphQL гарантирует последовательное выполнение корневых полей одной mutation-операции, но не определяет транзакции базы данных, rollback и идемпотентность.

Например, первая mutation может успешно создать заказ, а вторая завершиться ошибкой. Будет ли первый результат отменён, зависит от серверной реализации.

Повторная отправка mutation также может выполнить действие второй раз. Для платежей и создания заказов нужны отдельные идентификаторы операции, idempotency key или серверная дедупликация.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Является ли нормализованный кеш частью GraphQL?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. GraphQL определяет операции, schema и формат результата, но не обязательный клиентский кеш.

Apollo Client, Relay и другие библиотеки могут нормализовать сущности по устойчивому ключу, например:

```text
User:42
```

Для этого schema должна предоставить идентичность объекта, а клиент — знать правила формирования ключа.

Можно использовать GraphQL через обычный `fetch`, RTK Query или TanStack Query и кешировать результаты целых операций без нормализации сущностей.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как кешировать GraphQL на клиенте?</strong></summary>

<dl>
<dd>
<h2></h2>

Распространённый GraphQL-клиент нормализует объекты по `__typename` и устойчивому идентификатору, а результаты операций хранят ссылки на них.

После mutation кеш может обновиться через:

- возвращённую изменённую сущность;
- ручное изменение списка;
- cache policy;
- invalidation;
- повторный query.

Нормализация хорошо обновляет поля известной сущности, но не всегда понимает, в какие фильтрованные списки её нужно добавить или из каких удалить.

Пагинация также требует правил объединения страниц, cursor и аргументов поля.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли кешировать GraphQL через обычный HTTP-кеш?</strong></summary>

<dl>
<dd>
<h2></h2>

Да, особенно query-операции, отправленные через `GET`.

URL тогда содержит GraphQL-документ или идентификатор persisted document и variables, а сервер возвращает обычные `Cache-Control`, `ETag` и другие HTTP-заголовки.

Persisted documents уменьшают URL и делают cache key стабильнее.

Mutation через `GET` выполнять нельзя.

При кешировании нужно учитывать авторизацию, персональные данные, `Vary`, размер URL и то, что разные variables создают разные результаты.

Один endpoint `/graphql` усложняет HTTP-кеширование, но не запрещает его.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое persisted query?</strong></summary>

<dl>
<dd>
<h2></h2>

Это GraphQL-операция, текст которой сохранён на сервере под идентификатором, обычно хешем. Клиент передаёт идентификатор вместо полного документа.

Это уменьшает размер запроса и может упростить CDN-кеширование.

Если сервер принимает только заранее зарегистрированные и проверенные операции, получается allowlist, который также называют trusted documents.

Automatic Persisted Queries могут регистрировать неизвестную операцию во время выполнения. Поэтому APQ уменьшают трафик, но сами по себе не ограничивают клиента заранее одобренным списком.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда REST будет проще и лучше?</strong></summary>

<dl>
<dd>
<h2></h2>

REST часто проще, когда данные естественно представлены небольшими ресурсами, важны стандартные HTTP-методы и статусы, CDN-кеширование, загрузка файлов и минимальная инфраструктура.

GraphQL не стоит добавлять только ради одного сложного endpoint или генерации TypeScript-типов, если schema, resolvers, безопасность и кеш создают больше работы, чем решают.

GraphQL оправдан, когда несколько клиентов требуют разные связанные представления данных и команда готова поддерживать полноценную GraphQL-платформу.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что даёт GraphQL |
| --- | --- |
| Сложный профиль | Связанные данные одной операцией |
| Web, мобильное и административное приложение | Разные наборы полей поверх общей schema |
| TypeScript | Генерация типов конкретных операций |
| Частичная ошибка | `data` вместе с `errors` и `path` |
| Общие сущности на экранах | Нормализованный кеш клиентской библиотеки |
| Обновления в реальном времени | Subscription плюс конкретный транспорт |
| Контроль нагрузки | Trusted documents и ограничение стоимости |
