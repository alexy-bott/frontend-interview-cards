## Вопрос

<br>

 💬 **Чем GraphQL отличается от REST? Когда GraphQL полезен frontend-команде и какую сложность он добавляет?**

<h2></h2>

<br>
<dl>
<dd>

REST обычно строит HTTP API вокруг ресурсов: URL идентифицирует ресурс, метод выражает намерение, HTTP-статус сообщает результат, а кеширование использует стандартную семантику HTTP. GraphQL является языком запросов и средой выполнения вокруг типизированной schema, то есть схемы доступных данных и операций.

В GraphQL клиент описывает точный набор нужных полей:

```graphql
query UserPage($id: ID!) {
  user(id: $id) {
    id
    name
    avatarUrl
    orders(first: 5) {
      nodes {
        id
        status
      }
    }
  }
}
```

Schema определяет типы объектов, их поля и аргументы, перечисления (`enum`), входные типы и корневые операции:

- `query` читает данные;
- `mutation` изменяет состояние;
- `subscription` описывает поток событий.

Запросы часто отправляют на один HTTP endpoint `/graphql`, но это распространённое соглашение, а не главное свойство GraphQL. Протокол передачи, аутентификация, cookie, TLS, CORS и сетевые ошибки никуда не исчезают.

GraphQL уменьшает overfetching, то есть получение лишних полей, когда REST endpoint возвращает больше данных, чем нужно экрану. Он также уменьшает underfetching, то есть нехватку данных одного ответа, когда для экрана приходится последовательно загружать пользователя, заказы и права. Клиент запрашивает связанную форму данных одной GraphQL-операцией, а сервер решает, из каких сервисов её собрать.

Это не означает, что GraphQL автоматически ускоряет сервер. Каждое поле обслуживает resolver, то есть функция получения значения. Наивная загрузка списка пользователей и заказов каждого пользователя может создать проблему N+1: один запрос за списком и ещё N запросов за связанными данными. Сервер решает её пакетной загрузкой, кешем в пределах запроса и DataLoader-подобным механизмом.

Типичный ответ GraphQL содержит `data` и при необходимости `errors`. Если nullable-поле, то есть поле, допускающее `null`, завершилось ошибкой, клиент может получить остальные данные и ошибку с `path` до проблемного поля. Если ошибка возникла в non-null поле, которое не допускает `null`, обнуление распространяется вверх до ближайшего родительского поля, где `null` разрешён. Поэтому интерфейс должен решить, можно ли показать успешные блоки и отдельно состояние ошибки, а не сводить весь экран к одному логическому флагу `isError`.

Клиентский кеш GraphQL часто нормализует сущности по паре `__typename` и `id`: хранит каждую сущность один раз, а результаты запросов ссылаются на неё. Тогда один и тот же `User` в разных запросах представлен одной записью. Но обновление кеша после mutation всё равно требует стратегии: вернуть изменённую сущность, обновить конкретные поля, признать запрос устаревшим или повторить его. Пагинация и нестандартные идентификаторы требуют явных правил слияния.

GraphQL schema хорошо подходит для codegen, то есть генерации кода. Из неё и документов операций генерируют TypeScript-типы и hooks, а CI проверяет, что запрос обращается к существующим полям. Это надёжнее одного общего типа `User`, потому что тип результата соответствует конкретному набору запрошенных полей. Реальный ответ всё равно остаётся внешними данными, а разные версии клиента и сервера требуют совместимого развития схемы: старые поля обычно сначала помечают `@deprecated`, затем удаляют только после миграции клиентов.

Без ограничений клиент может отправить очень глубокий или дорогой запрос. Сервер ограничивает глубину и вычислительную стоимость операции, её размер и время выполнения, а также проверяет доступ к полям. Дополнительно применяют persisted queries, то есть сохранённые запросы. При строгом allowlist-режиме сервер заранее связывает хеш с разрешённым текстом операции и принимает только зарегистрированные запросы. В режиме Automatic Persisted Queries клиент при необходимости сначала регистрирует новый хеш, поэтому такой режим сам по себе не является списком разрешённых операций.

Subscriptions описывают GraphQL-события, но не создают надёжный канал сами по себе. Доставка обычно работает поверх WebSocket или SSE, поэтому остаются переподключение, аутентификация, повтор пропущенных событий и синхронизация кеша.

REST часто проще для обычного CRUD, файлов, публичных API, CDN/HTTP-кеширования и небольшой команды. GraphQL оправдан, когда экраны собирают сильно связанные данные, несколько клиентов требуют разные формы ответа, схема имеет владельцев, а команда готова поддерживать resolvers, генерацию кода, ограничения стоимости запросов и клиентский кеш.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что такое GraphQL schema?</strong></summary>

<dl>
<dd>
<h2></h2>

Это типизированный контракт API: типы объектов, их поля и аргументы, входные значения, `enum` и доступные `query`, `mutation`, `subscription`. Клиентские операции проверяются относительно схемы, а серверные resolvers реализуют получение значений.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое resolver?</strong></summary>

<dl>
<dd>
<h2></h2>

Это серверная функция, которая вычисляет значение поля. Resolver получает родительский объект, аргументы, контекст текущего запроса и информацию об операции. Например, `User.orders` загружает заказы пользователя. Общие правила авторизации и пакетной загрузки нельзя бездумно дублировать в сотнях resolvers.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое overfetching и underfetching?</strong></summary>

<dl>
<dd>
<h2></h2>

Overfetching означает получение лишних полей, а underfetching необходимость дополнительных запросов для полного экрана. GraphQL позволяет клиенту описать нужную форму данных, но сервер всё равно должен получить её эффективно и ограничить слишком дорогие операции.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое проблема N+1?</strong></summary>

<dl>
<dd>
<h2></h2>

Один запрос списка порождает отдельный запрос для каждого элемента, например один запрос пользователей и сто запросов их заказов. Resolver каждого `User.orders` работает независимо. DataLoader группирует ключи в одну пакетную загрузку и кеширует результат в пределах текущего GraphQL-запроса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли GraphQL вернуть одновременно <code>data</code> и <code>errors</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Да. Ошибка поля, допускающего `null`, позволяет вернуть остальные данные, а `errors[].path` показывает проблемное место. Клиентская политика определяет, показывать ли частичные данные. Ошибка поля, которое не допускает `null`, обнуляет родительские поля вверх по дереву до ближайшей границы, где `null` разрешён.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему GraphQL может вернуть HTTP <code>200</code>, хотя в <code>errors</code> есть ошибки?</strong></summary>

<dl>
<dd>
<h2></h2>

HTTP-статус сообщает, был ли GraphQL-запрос принят и обработан на уровне транспорта, а `errors` описывает ошибки выполнения полей. Поэтому корректно выполненная операция с частичными данными часто приходит с `200`. Ошибки разбора запроса или неподдерживаемый метод могут иметь другой HTTP-статус. Клиент должен проверять и транспортный результат, и содержимое GraphQL-ответа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как кешировать GraphQL на клиенте?</strong></summary>

<dl>
<dd>
<h2></h2>

Распространённый клиент нормализует объекты по `__typename` и `id`, а результат запроса хранит ссылки на них. После mutation кеш обновляют возвращёнными сущностями, явной функцией или повторным запросом. HTTP-кеш применить сложнее, потому что разные операции часто идут на один URL через `POST`, хотя сохранённые запросы и `GET` для чтения могут помочь.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое persisted query?</strong></summary>

<dl>
<dd>
<h2></h2>

Это GraphQL-операция, текст которой сохранён на сервере под хешем. Клиент передаёт идентификатор вместо полного текста. Это уменьшает размер запроса. Если сервер принимает только заранее зарегистрированные хеши, получается allowlist, то есть список разрешённых операций. Automatic Persisted Queries могут регистрироваться динамически и сами по себе такой защиты не дают.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда REST будет проще и лучше?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда данные естественно представлены небольшими ресурсами, важны стандартное HTTP-кеширование, загрузка файлов, простая диагностика и минимальная инфраструктура. GraphQL не стоит добавлять только ради одного endpoint или генерации типов, если его схема, resolvers и кеш создают больше работы, чем решают.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что даёт GraphQL |
| --- | --- |
| Сложный профиль | Связанные данные одной операцией |
| Web, мобильное и административное приложение | Разные наборы полей поверх общей схемы |
| TypeScript | Генерация типов конкретных запросов |
| Частичная ошибка | `data` вместе с `errors` и `path` |
| Общие сущности на экранах | Нормализованный кеш |
| Обновления в реальном времени | Subscription плюс конкретный транспорт |
| Контроль нагрузки | Сохранённые запросы и ограничение стоимости |
