## Вопрос

<br>

 💬 **Что такое REST API? Какие ограничения REST и свойства ресурсной модели важны для frontend-разработчика?**

<h2></h2>

<br>
<dl>
<dd>

REST (Representational State Transfer) — это архитектурный стиль для распределённых гипермедийных систем. В HTTP API его идеи обычно выражаются через ресурсы с устойчивыми URI, стандартную семантику HTTP-методов, передачу представлений ресурсов, кеширование и независимую обработку запросов.

REST не является протоколом или форматом данных. API может передавать JSON, HTML, изображения или другое представление ресурса. При этом не любой JSON API поверх HTTP автоматически является REST API: для этого недостаточно использовать URL и методы `GET` или `POST`.

Ресурс — это идентифицируемое понятие предметной области. Им может быть пользователь, коллекция заказов, документ, отчёт, процесс экспорта или результат вычисления. Ресурс не обязан напрямую соответствовать таблице базы данных.

Например:

- `/users` идентифицирует коллекцию пользователей;
- `/users/42` — конкретного пользователя;
- `/orders/123/items` — позиции конкретного заказа;
- `/exports/17` — процесс или результат экспорта.

Представление ресурса — это данные, которые сервер передаёт клиенту. Например, пользователь `/users/42` может быть представлен в JSON, HTML или другом формате. Ресурс и его представление — не одно и то же: изменение структуры JSON не обязательно означает появление нового ресурса.

HTTP-метод сообщает желаемую семантику операции над целевым ресурсом:

| Запрос | Смысл |
| --- | --- |
| `GET /users/42` | Получить представление пользователя |
| `POST /users` | Передать данные коллекции на обработку; часто создать нового пользователя |
| `PUT /users/42` | Создать или полностью заменить состояние ресурса по известному URI |
| `PATCH /users/42` | Частично изменить состояние пользователя |
| `DELETE /users/42` | Удалить ресурс по указанному URI |

Классическая модель REST содержит несколько ограничений:

1. **Client-server, разделение клиента и сервера.** Клиент и сервер имеют разные зоны ответственности и могут развиваться независимо, пока сохраняется общий интерфейс.
2. **Stateless, отсутствие состояния сессии на сервере.** Каждый запрос содержит всю информацию, необходимую для его понимания и обработки.
3. **Cacheable, кешируемость.** Ответ должен явно или неявно сообщать, можно ли сохранить его и повторно использовать для эквивалентных запросов.
4. **Uniform interface, единый интерфейс.** Компоненты взаимодействуют через общий набор правил работы с ресурсами и представлениями.
5. **Layered system, слоистая система.** Между клиентом и конечным сервером могут находиться CDN, reverse proxy, API gateway и другие посредники.
6. **Code on demand, код по требованию.** Сервер может расширять клиент, передавая ему исполняемый код. Это единственное необязательное ограничение REST.

Uniform interface является центральным ограничением REST и состоит из четырёх частей:

1. Ресурсы идентифицируются через URI.
2. Ресурсами управляют через передаваемые представления.
3. Сообщения являются самодостаточными: их смысл определяется методом, URI, заголовками, media type и содержимым.
4. Клиент изменяет состояние приложения через доступные гипермедийные переходы, то есть ссылки и действия из полученных представлений.

Последний пункт называют HATEOAS — Hypermedia as the Engine of Application State.

Stateless не означает, что сервер вообще не хранит состояние. Сервер хранит пользователей, заказы, права доступа и другие состояния ресурсов. Ограничение относится к состоянию диалога между запросами.

Каждый запрос должен быть понятен сам по себе. Например, он может содержать токен доступа или cookie с необходимыми учётными данными. Однако если cookie содержит только идентификатор серверной сессии, а для обработки запроса серверу требуется восстановить скрытый контекст предыдущих действий, это нарушает stateless-ограничение в строгом смысле REST.

Серверные сессии широко используются в практических HTTP API. Поэтому важно различать строгий архитектурный стиль REST и распространённые REST-like API, которые используют только часть его ограничений.

URI обычно называют существительными, а действие выражают HTTP-методом: `GET /users/42` понятнее, чем `POST /getUser`.

Однако не каждая доменная операция естественно сводится к простому CRUD. Отмену заказа можно представить созданием отдельного ресурса:

```text
POST /orders/123/cancellations
```

Такой запрос создаёт запрос или факт отмены. Другой вариант — изменить состояние заказа через `PATCH`, если это соответствует контракту API.

Главное — чтобы модель была последовательной. Адрес вроде `POST /cancelOrder` является RPC-вызовом команды. Он тоже может быть допустимым решением, но сам по себе не следует ресурсной модели REST.

REST API должен согласованно использовать семантику HTTP:

- выбирать метод по смыслу операции;
- возвращать подходящие статус-коды;
- передавать корректный media type;
- задавать правила кеширования;
- поддерживать условные запросы, когда они нужны;
- учитывать safe- и idempotent-свойства методов;
- возвращать предсказуемые представления ошибок.

Например, идемпотентную операцию можно безопаснее повторить после сетевого сбоя, потому что несколько одинаковых запросов должны иметь тот же желаемый эффект, что и один запрос. При этом конкретные HTTP-ответы могут различаться: повторный `DELETE` способен вернуть другой статус, хотя удалённый ресурс по-прежнему отсутствует.

Если все операции отправляются через `POST`, а любые результаты возвращаются с `200`, клиент, браузер, кеш и промежуточные серверы не могут использовать стандартную семантику HTTP. Frontend также сложнее определить, можно ли повторить запрос и к какому классу относится ошибка.

Для frontend API-контракт определяет:

- состояния загрузки и ошибки;
- возможность отмены и повторения запроса;
- форму данных для интерфейса;
- обновление или инвалидацию кеша;
- оптимистичное обновление;
- пагинацию и фильтрацию;
- обработку валидационных ошибок;
- конфликты конкурентного изменения;
- параметры ключа запроса, или query key.

Поэтому качество REST API оценивают не только по форме URL. Важны предсказуемость всей ресурсной модели, семантика HTTP и стабильность представлений, которые получает клиент.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Любой ли JSON API поверх HTTP является REST API?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. JSON является только форматом представления данных, а HTTP — протоколом передачи сообщений.

API может использовать JSON и HTTP, но при этом строиться как RPC: например, отправлять все команды через `POST /executeAction`, хранить скрытое состояние сессии и не использовать кеширование или гипермедийные переходы.

Такой интерфейс может быть рабочим, но точнее называть его HTTP API или REST-like API. REST определяется совокупностью архитектурных ограничений, а не расширением файла, формой JSON или наличием нескольких URL.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем ресурс отличается от его представления?</strong></summary>

<dl>
<dd>
<h2></h2>

Ресурс является идентифицируемым понятием, например пользователем с URI `/users/42`.

Представление — это текущее описание ресурса в сообщении: JSON, HTML, изображение или другой формат. Один ресурс может иметь несколько представлений для разных media type, языков или клиентов.

Изменение полей JSON не обязательно создаёт новый ресурс. И наоборот, два разных URI могут идентифицировать разные ресурсы, даже если в конкретный момент их представления выглядят одинаково.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означает stateless в REST?</strong></summary>

<dl>
<dd>
<h2></h2>

Каждый запрос должен содержать контекст, достаточный для его понимания и обработки: URI ресурса, данные операции, заголовки и сведения для аутентификации.

Сервер не должен зависеть от скрытого состояния диалога, сохранённого после предыдущего запроса. Это позволяет обработать следующий запрос на другом серверном узле и упрощает восстановление после сбоев.

Состояние самих ресурсов в базе данных под запрет не попадает. Ограничение относится именно к session state между клиентскими запросами.

Cookie также не нарушает REST автоматически. Важно, какие данные она передаёт: самодостаточные учётные данные совместимы со stateless, а идентификатор обязательной серверной сессии создаёт зависимость от сохранённого контекста.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>REST и CRUD являются одним и тем же?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. CRUD описывает четыре базовые операции над данными: создание, чтение, изменение и удаление.

REST является более широкой архитектурной моделью. Она включает stateless-взаимодействие, единый интерфейс, кеширование, слои, ресурсы, представления и гипермедийные переходы.

CRUD удобно отображается на HTTP-методы, но поиск, экспорт, отмена заказа или длительная задача требуют отдельного моделирования. Их можно представить ресурсами, например `/exports/17` или `/orders/123/cancellations`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем REST отличается от RPC?</strong></summary>

<dl>
<dd>
<h2></h2>

REST строит интерфейс вокруг ресурсов и общей семантики представлений, URI и HTTP-методов.

RPC строит интерфейс вокруг вызова операций:

```text
cancelOrder
calculatePrice
sendInvoice
```

RPC не является неправильным подходом. Для командной предметной области он может быть проще и понятнее.

Проблема возникает, когда RPC-интерфейс называют REST API, но при этом ожидают от него свойства стандартной HTTP-семантики: безопасное повторение, кеширование, единообразные методы и работу посредников.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое HATEOAS?</strong></summary>

<dl>
<dd>
<h2></h2>

HATEOAS расшифровывается как Hypermedia as the Engine of Application State. Это означает, что представление ресурса содержит ссылки или описания доступных переходов из его текущего состояния.

Например, ответ с заказом может содержать ссылку или действие `cancel`, только пока отмена разрешена. После отправки заказа такой переход может исчезнуть, а вместо него появится ссылка на отслеживание доставки.

В строгом REST гипермедиа является частью uniform interface. Многие JSON API не реализуют HATEOAS полностью и требуют, чтобы клиент заранее знал все URL и переходы. Такие API обычно называют REST на практике, хотя точнее считать их REST-like HTTP API.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как версионировать REST API?</strong></summary>

<dl>
<dd>
<h2></h2>

Версию часто помещают в путь:

```text
/api/v1/users
```

Другой вариант — выбирать версию представления через заголовок `Accept` и специальный media type.

Однако версия URL не заменяет политику совместимости. Добавление необязательного поля обычно является совместимым изменением, а удаление поля, изменение его типа или смысла статуса может сломать клиент.

По возможности API развивают через совместимые добавления, период устаревания и контролируемое удаление старого контракта. OpenAPI, журнал изменений и контрактные тесты помогают обнаружить несовместимое изменение до развёртывания.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда вложенный URL вроде <code>/users/42/orders/7</code> оправдан?</strong></summary>

<dl>
<dd>
<h2></h2>

Вложенный URI полезен, когда дочерний ресурс имеет смысл только в контексте родителя или родитель определяет область доступа.

Например, `/orders/7/items/3` может ясно показывать, к какому заказу относится позиция.

Слишком глубокая вложенность связывает модели и усложняет маршруты. Если заказ имеет собственную устойчивую идентичность, обычно достаточно `/orders/7`, а пользователя можно получить из представления заказа или передать как фильтр коллекции:

```text
GET /orders?userId=42
```

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что определяет контракт API |
| --- | --- |
| Загрузка карточки | URI ресурса, `GET`, кеширование и `404` |
| Создание сущности | `POST`, `201`, `Location` и новое представление |
| Редактирование формы | `PUT` или `PATCH`, валидация и конфликт версии |
| Повтор запроса | Идемпотентность метода и ключ идемпотентности |
| Обновление серверных данных | Инвалидация ключа запроса или изменение кеша |
| Миграция API | Совместимость версии и OpenAPI-контракт |
