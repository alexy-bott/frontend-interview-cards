#### Вопрос

Что такое REST API? Какие ограничения REST и свойства ресурсной модели важны для frontend-разработчика?

#### Ответ

REST (Representational State Transfer, «передача состояния через представление») является архитектурным стилем для распределённых систем. В HTTP API он обычно выражается через ресурсы с устойчивыми URL, стандартную семантику HTTP-методов, представления ресурсов, кеширование и независимые запросы. REST не является форматом данных: API может передавать JSON, HTML, изображения или другое представление одного ресурса.

Ресурсом называют сущность или коллекцию, которую API идентифицирует адресом. Например, `/users` обозначает коллекцию пользователей, `/users/42` конкретного пользователя, а `/orders/123/items` позиции заказа. Представление ресурса является данными, которые сервер отправляет клиенту, например JSON с полями пользователя. Один ресурс может иметь несколько представлений.

Метод сообщает, что клиент хочет сделать с ресурсом:

| Запрос | Смысл |
| --- | --- |
| `GET /users/42` | Получить представление пользователя |
| `POST /users` | Создать пользователя в коллекции |
| `PUT /users/42` | Заменить состояние пользователя по известному URL |
| `PATCH /users/42` | Частично изменить пользователя |
| `DELETE /users/42` | Удалить пользователя |

Классическая модель REST содержит несколько ограничений:

1. **Client-server, разделение клиента и сервера.** Клиент отвечает за интерфейс, сервер за данные и правила предметной области.
2. **Stateless, отсутствие скрытого состояния диалога.** Каждый запрос содержит сведения, необходимые для его обработки; сервер не должен зависеть от контекста предыдущего запроса.
3. **Cacheable, кешируемость.** Ответ явно сообщает, разрешено ли его кешировать и на каких условиях.
4. **Uniform interface, единый интерфейс.** Ресурсы идентифицируются единообразно, изменяются через представления, сообщения самодостаточны, а доступные переходы могут описываться ссылками.
5. **Layered system, слоистая система.** Между клиентом и сервером могут находиться CDN, reverse proxy (обратный прокси), gateway (API-шлюз) и другие слои, о которых клиенту не обязательно знать.
6. **Code on demand, код по требованию.** Сервер может передавать исполняемый код, но это необязательное ограничение.

Stateless не означает, что сервер не хранит данные. Он хранит состояние ресурсов в базе, а также может проверять токен или cookie сессии. Ограничение относится к обработке последовательности запросов: второй запрос не должен быть понятен только потому, что сервер помнит скрытый шаг первого. Серверные сессии распространены на практике, хотя в строгом смысле добавляют состояние взаимодействия.

URL обычно называют существительными, а действие выражают методом: `GET /users/42` понятнее, чем `POST /getUser`. Однако не каждая операция сводится к CRUD. Для отмены заказа или подтверждения платежа допустима явная команда, например `POST /orders/123/cancellation` или `POST /payments/123/confirmation`. Такой адрес показывает создаваемый результат операции лучше, чем произвольный глагол.

REST API должен использовать семантику HTTP согласованно: корректные методы и статусы, заголовки кеширования, единый формат ошибок, условные запросы и идемпотентность. Если любой запрос отправляется через `POST`, а результат всегда возвращается с `200`, клиент теряет возможность безопасно повторять запросы, использовать стандартный кеш и различать классы ошибок.

Для frontend API-контракт определяет поведение интерфейса: состояние загрузки, форму ошибки, повтор запроса, обновление кеша, оптимистичное обновление, пагинацию и параметры ключа запроса (query key). Поэтому качество REST API оценивают не только по URL, но и по предсказуемости полного контракта.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Чем ресурс отличается от его представления?
>
> **Ответ:** Ресурс является идентифицируемой сущностью, например пользователь с URL `/users/42`. Представление является текущим описанием этого ресурса в сообщении: JSON, HTML или изображение. Изменение набора полей JSON не обязательно создаёт новый ресурс, а один ресурс может иметь разные представления для разных форматов или языков.

> [!followup]
> **Вопрос:** Что означает stateless в REST?
>
> **Ответ:** Каждый запрос должен содержать контекст, достаточный для его обработки: адрес ресурса, данные операции и сведения для аутентификации. Сервер не должен требовать скрытой последовательности вроде «сначала вызови A, тогда тот же узел запомнит состояние для B». Это упрощает балансировку нагрузки и повтор запроса. Состояние ресурсов в базе под запрет не попадает.

> [!followup]
> **Вопрос:** REST и CRUD являются одним и тем же?
>
> **Ответ:** Нет. CRUD описывает четыре операции над данными: создание, чтение, изменение и удаление. REST задаёт более широкую архитектурную модель, включая stateless-взаимодействие, единый интерфейс, кеширование и слои. CRUD удобно отображается на HTTP-методы, но доменные команды, поиск или запуск экспорта требуют отдельного моделирования.

> [!followup]
> **Вопрос:** Чем REST отличается от RPC?
>
> **Ответ:** REST строит интерфейс вокруг ресурсов и общей семантики HTTP, а RPC вокруг вызова операций, например `cancelOrder` или `calculatePrice`. RPC не является плохим подходом: для командной предметной области он может быть яснее. Проблема возникает, когда API внешне называется REST, но игнорирует методы, статусы и остальные свойства HTTP, из-за чего контракт становится непредсказуемым.

> [!followup]
> **Вопрос:** Что такое HATEOAS?
>
> **Ответ:** Hypermedia as the Engine of Application State означает, что ответ содержит ссылки или действия, доступные из текущего состояния. Например, заказ может содержать ссылку `cancel`, только пока отмена разрешена. Клиенту не нужно конструировать все переходы самостоятельно. Многие JSON API используют эту идею частично и всё равно называют себя REST API.

> [!followup]
> **Вопрос:** Как версионировать REST API?
>
> **Ответ:** Версию часто помещают в путь (`/api/v1`) или выбирают через заголовок и media type, то есть тип представления. Важнее самой формы политика совместимости: добавление необязательного поля обычно совместимо, а удаление поля, изменение типа или смысла статуса является несовместимым изменением. OpenAPI, журнал изменений и контрактные тесты помогают обнаружить проблему до развёртывания.

> [!followup]
> **Вопрос:** Когда вложенный URL вроде `/users/42/orders/7` оправдан?
>
> **Ответ:** Он полезен, если заказ рассматривается в контексте конкретного пользователя или родитель задаёт область доступа. Слишком глубокая вложенность связывает модели и усложняет URL. Если у заказа есть собственная устойчивая идентичность, часто достаточно `/orders/7`, а пользователя передают фильтром или получают из самого заказа.

#### Где это встречается во frontend

| Ситуация | Что определяет контракт API |
| --- | --- |
| Загрузка карточки | URL ресурса, `GET`, кеширование и `404` |
| Создание сущности | `POST`, `201`, `Location` и новое представление |
| Редактирование формы | `PUT` или `PATCH`, валидация и конфликт версии |
| Повтор запроса | Идемпотентность метода и ключ идемпотентности |
| Обновление серверных данных | Инвалидация ключа запроса или изменение кеша |
| Миграция API | Совместимость версии и OpenAPI-контракт |
