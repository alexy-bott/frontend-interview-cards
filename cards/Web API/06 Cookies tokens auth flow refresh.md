#### Вопрос

Как во frontend устроены серверные сессии, access token и обновление токенов? Какие риски нужно учитывать?

#### Ответ

Authentication, или аутентификация, подтверждает личность пользователя. Authorization, или авторизация, определяет его права. Frontend участвует в обоих процессах, но окончательное решение всегда принимает сервер: скрытая кнопка не защищает endpoint, то есть адрес операции API, от прямого запроса.

В браузерных приложениях часто используют одну из следующих схем или их сочетание:

| Схема | Как подтверждается запрос |
| --- | --- |
| Серверная сессия | Браузер автоматически отправляет cookie со случайным идентификатором, а данные сессии хранятся на сервере |
| Bearer access token, или токен доступа | Клиент добавляет `Authorization: Bearer <token>`; сервер проверяет непрозрачный токен или JWT |
| BFF (Backend for Frontend) | Браузер работает с HttpOnly cookie сессии, а отдельный серверный слой для frontend хранит или получает токены для вызова внутренних API |

Cookie с идентификатором сессии или refresh token, то есть токен обновления, обычно защищают атрибутами:

- `HttpOnly` запрещает чтение через `document.cookie`;
- `Secure` разрешает отправку только по HTTPS, кроме специальных правил localhost;
- `SameSite` ограничивает отправку в межсайтовом контексте;
- `Path` и `Domain` ограничивают область cookie;
- короткий срок жизни уменьшает время использования украденного значения.

`HttpOnly` снижает риск кражи токена при XSS, но не устраняет сам XSS: вредоносный скрипт всё ещё может отправлять запросы от имени пользователя из открытой страницы. Поскольку cookie прикладывается браузером автоматически, для изменяющих запросов также нужна CSRF-защита. `SameSite=Lax` или `Strict` помогает, но выбор зависит от сценария входа, внешних переходов и встраивания приложения.

Bearer token клиент добавляет к запросу сам. Access token обычно делают короткоживущим и хранят в памяти приложения либо на стороне BFF. Если токен лежит в `localStorage`, любой JavaScript, выполнившийся в том же origin, то есть источнике, из-за XSS или скомпрометированной зависимости, может его прочитать и вынести. Конкретная схема хранения зависит от архитектуры, но refresh token требует более строгой защиты, чем краткоживущий access token.

JWT является форматом токена, а не способом хранения. Его payload, то есть полезная нагрузка, обычно закодирован, но не зашифрован, поэтому клиент и злоумышленник могут прочитать поля. Подпись позволяет проверить целостность и издателя, если сервер корректно проверяет алгоритм, ключ, `iss`, `aud`, срок действия и другие claims, то есть утверждения о пользователе и токене. Нельзя помещать в JWT секретные данные только потому, что строка выглядит непонятно.

Типичный процесс обновления токенов выглядит так:

1. API возвращает `401`, потому что access token истёк или недействителен.
2. Клиент запускает один запрос обновления токена.
3. Остальные запросы, получившие `401` одновременно, ждут тот же Promise, а не запускают собственное обновление.
4. После успеха access token обновляется, ожидающие запросы повторяются один раз.
5. После неудачи клиент очищает состояние аутентификации и кеш чувствительных серверных данных, затем переводит пользователя на страницу входа.

Такой single-flight, то есть один общий запрос обновления для всех ожидающих запросов, предотвращает гонки. Повтор должен иметь защиту от цикла: `401` endpoint обновления или повторного исходного запроса не запускает новое обновление бесконечно. `403` обычно не является поводом обновлять токен, потому что проблема связана с правами, а не сроком действия.

Refresh token является долгоживущей учётной информацией с высоким уровнем доступа. Сервер может применять rotation, то есть ротацию: при каждом успешном обновлении выдавать новый refresh token, делать предыдущий недействительным и сохранять связь между ними. Повторное использование старого токена указывает на возможную кражу и позволяет отозвать активную цепочку. Также нужны срок неактивности, отзыв при выходе из системы или смене пароля и привязка к клиенту согласно выбранному протоколу.

При аутентификации через cookie между разными origin клиент использует `credentials: "include"`, сервер возвращает конкретный `Access-Control-Allow-Origin` и `Access-Control-Allow-Credentials: true`, а cookie должна пройти правила `SameSite` и `Secure`. Cross-origin и cross-site не одно и то же: разные поддомены имеют разные origin, но могут относиться к одному сайту. CORS и `SameSite` проверяют разные границы.

Выход из системы не должен ограничиваться очисткой состояния React. Сервер завершает сессию или отзывает refresh token, frontend очищает чувствительные кеши, закрывает WebSocket и удаляет доступные токены. Иначе кнопка выхода изменит только внешний вид страницы, а действующая сессия останется пригодной для повторного использования.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Что даёт `HttpOnly`?
>
> **Ответ:** JavaScript не может прочитать такую cookie через `document.cookie`, поэтому атакующему сложнее вынести идентификатор сессии и использовать его с другого устройства. Однако XSS-код внутри страницы может отправлять запросы, к которым браузер приложит cookie автоматически. Поэтому `HttpOnly` является одним защитным слоем, а не полной защитой от XSS.

> [!followup]
> **Вопрос:** Что делает `SameSite`?
>
> **Ответ:** Атрибут определяет, когда cookie можно отправлять в межсайтовом контексте. `Strict` наиболее ограничительный. `Lax` допускает часть безопасных переходов верхнего уровня. `None` разрешает межсайтовую отправку и требует `Secure`. Выбор должен соответствовать сценарию входа, использованию `iframe` и необходимости запросов между сайтами.

> [!followup]
> **Вопрос:** Чем session cookie отличается от JWT?
>
> **Ответ:** Cookie серверной сессии обычно содержит случайный идентификатор, по которому сервер находит состояние сессии. JWT может сам нести подписанные claims и проверяться без чтения общей сессии. Cookie является механизмом хранения и отправки, а JWT форматом токена, поэтому JWT тоже можно передавать в cookie. Эти понятия не являются взаимоисключающими.

> [!followup]
> **Вопрос:** Почему нельзя запускать refresh на каждый `401`?
>
> **Ответ:** Несколько параллельных запросов создадут несколько обновлений и гонку токенов. При rotation один запрос может сделать токен другого уже недействительным. Клиент хранит один Promise refresh-операции, остальные запросы ожидают его результат, а затем повторяются с новой учётной информацией.

> [!followup]
> **Вопрос:** Всегда ли `401` означает logout?
>
> **Ответ:** Нет. Для истёкшего access token сначала допустим один refresh. Logout нужен, если refresh отсутствует, истёк, отозван или завершился ошибкой. API полезно различать причины стабильным кодом, но клиент не должен бесконечно повторять недействительную сессию.

> [!followup]
> **Вопрос:** Что такое refresh token rotation?
>
> **Ответ:** Сервер выдаёт новый refresh token при каждом использовании и делает старый недействительным. Если старое значение появляется повторно, сервер предполагает replay, то есть повторное использование украденного токена, и отзывает связанную активную цепочку. Ротация требует атомарной серверной реализации и аккуратной обработки параллельных запросов.

> [!followup]
> **Вопрос:** Где безопаснее хранить access token?
>
> **Ответ:** Универсального ответа без архитектуры нет. Память вкладки уменьшает время и область кражи, но требует способа восстановить сессию. HttpOnly cookie скрывает значение от JavaScript, но требует CSRF-защиты. BFF может вообще не отдавать токен браузеру. `localStorage` прост, но доступен любому коду в origin, поэтому долгоживущие токены там особенно опасны.

> [!followup]
> **Вопрос:** Что должен сделать frontend при logout?
>
> **Ответ:** Вызвать серверное завершение сессии или отзыв refresh token, очистить access token и данные пользователя, сбросить кеш чувствительных серверных данных, остановить фоновые запросы и закрыть соединения реального времени. Очистку выполняют и после окончательной ошибки обновления токена.

#### Где это встречается во frontend

| Ситуация | Поведение клиента |
| --- | --- |
| Access token истёк | Один запрос обновления и однократный повтор исходного запроса |
| Несколько запросов получили `401` | Один общий refresh и очередь ожидания |
| Refresh завершился ошибкой | Очистить состояние и перейти к экрану входа |
| Cookie между разными origin | `credentials`, CORS и атрибуты cookie |
| Сервер вернул `403` | Показать отсутствие прав без refresh |
| Выход из системы | Отозвать серверную сессию, очистить кеши и соединения |
| Интерфейс проверяет право | Улучшить UX, сохранив серверную проверку каждого запроса |
