## Вопрос

<br>

 💬 **Чем отличаются polling, long polling, Server-Sent Events и WebSocket? Как выбрать способ доставки обновлений в реальном времени?**

<h2></h2>

<br>
<dl>
<dd>

Эти подходы решают похожую задачу разными способами: доставляют frontend новые данные после первой загрузки страницы. Выбор зависит от направления обмена, допустимой задержки, частоты событий, необходимости бинарных данных, авторизации, восстановления после разрыва и возможностей инфраструктуры.

Термин realtime, то есть работа в реальном времени, здесь обычно означает небольшую ожидаемую задержку. Ни один из транспортов не гарантирует строгое время доставки или актуальность данных сам по себе.

| Подход | Направление | Соединение | Подходит для |
| --- | --- | --- | --- |
| Polling, периодический опрос | Клиент периодически запрашивает сервер | Последовательность коротких HTTP-запросов | Редкие обновления и простая инфраструктура |
| Long polling, долгий опрос | Клиент запрашивает, сервер задерживает ответ до события | Последовательность долгих HTTP-запросов | Быстрая доставка серверных событий без постоянного потока |
| SSE | Сервер отправляет клиенту текстовые события | Долгий HTTP-поток с автоматическим reconnect | Прогресс, уведомления, логи и ленты |
| WebSocket | Обе стороны отправляют текстовые или бинарные сообщения | Постоянное WebSocket-соединение | Чат, присутствие пользователей и совместное редактирование |

При обычном polling клиент через заданный интервал вызывает HTTP endpoint:

```text
запрос → ответ → ожидание → новый запрос
```

Реализация проста и использует обычные HTTP-методы, статусы, кеширование, аутентификацию и балансировку. Такой подход хорошо подходит, если обновления происходят редко, а задержка в несколько секунд приемлема.

Цена polling состоит в лишних запросах, когда данные не изменились, и задержке до следующего интервала. Чем меньше интервал, тем быстрее обновляется интерфейс, но тем выше нагрузка на клиент, сервер и сеть.

Polling-запросы не должны бесконтрольно перекрываться. Если запрос выполняется дольше интервала, новый `setInterval` может запустить второй запрос до завершения первого.

Безопаснее:

1. Дождаться завершения текущего запроса.
2. Учесть его результат.
3. Запланировать следующую проверку.

Другой вариант — отменять предыдущий запрос через `AbortController`, если новый результат полностью заменяет старый.

Если сервер поддерживает `ETag` или `Last-Modified`, polling может использовать условные запросы. При отсутствии изменений сервер возвращает `304 Not Modified` без повторной передачи полного представления.

Интервал polling можно:

- увеличивать после временных ошибок;
- уменьшать во время активной операции;
- останавливать после завершения задачи;
- изменять при скрытии вкладки;
- учитывать подсказку `Retry-After`.

Интервал обычного обновления и retry-задержка после ошибки являются разными настройками. Не следует продолжать частый polling во время перегрузки сервера.

Long polling отправляет запрос, который сервер оставляет открытым до одного из событий:

- появились новые данные;
- истёк серверный timeout;
- соединение было закрыто;
- произошла ошибка.

После ответа клиент сразу открывает следующий запрос:

```text
долгий запрос → событие или timeout → ответ → новый долгий запрос
```

Задержка обычно ниже, чем у периодического polling, потому что сервер может ответить сразу после появления события.

При этом long polling не является постоянным потоком. Каждый ответ завершает HTTP-запрос, после чего создаётся новый. Между ответом и следующим запросом теоретически существует промежуток, поэтому контракту может понадобиться `eventId`, cursor или версия, чтобы не потерять события.

Штатный timeout long polling не обязательно означает ошибку. Сервер может вернуть пустой результат, чтобы соединение не оставалось открытым дольше ограничений proxy или load balancer. Клиент после такого ответа открывает следующий запрос без сообщения пользователю.

После сетевой или серверной ошибки новый запрос запускают с ограниченным backoff, а не в мгновенном бесконечном цикле.

SSE (Server-Sent Events) является односторонним потоком событий от сервера к клиенту. Браузер открывает соединение через `EventSource`, а сервер отвечает:

```http
Content-Type: text/event-stream
```

Поток SSE всегда является текстом в UTF-8. Каждое событие состоит из строк с полями и завершается пустой строкой:

```text
id: 1842
event: order-updated
data: {"orderId":"42","status":"paid"}

```

Основные поля:

- `event` задаёт имя события;
- `data` содержит его данные;
- `id` обновляет последний идентификатор события;
- `retry` задаёт рекомендуемую задержку перед переподключением в миллисекундах.

Если `event` отсутствует, браузер создаёт обычное событие `message`. Именованное событие слушают через `addEventListener`.

Несколько последовательных строк `data` объединяются через перевод строки. Событие передаётся обработчику только после пустой строки, поэтому сервер должен правильно завершать каждый блок и немедленно сбрасывать его в сеть.

```ts
const source = new EventSource("/api/events");

source.addEventListener("order-updated", (event) => {
  const message = JSON.parse(event.data);
  handleOrderUpdate(message);
});
```

`EventSource` имеет состояния:

- `CONNECTING`;
- `OPEN`;
- `CLOSED`.

При временном разрыве браузер обычно автоматически пытается восстановить соединение. Событие `error` не всегда означает окончательное завершение: объект может перейти обратно в `CONNECTING` и начать reconnect.

Для окончательного закрытия со стороны клиента вызывают:

```ts
source.close();
```

После этого `readyState` становится `CLOSED`, и автоматическое переподключение прекращается.

Сервер также может ответить статусом:

```http
204 No Content
```

Такой ответ сообщает `EventSource`, что повторно подключаться больше не нужно.

Если сервер передавал поле `id`, браузер сохраняет последний идентификатор. При восстановлении соединения он может отправить:

```http
Last-Event-ID: 1842
```

Сам заголовок не восстанавливает события. Сервер должен:

1. Хранить журнал либо уметь восстановить события после указанного идентификатора.
2. Проверить область доступа пользователя.
3. Отдать пропущенные события в правильном порядке.
4. Сообщить, если история уже недоступна.

Если replay невозможен, клиент заново получает актуальный снимок данных по HTTP.

Нативный `EventSource` не позволяет задавать произвольный набор request headers, например вручную добавить Bearer-токен в `Authorization`.

Для аутентификации обычно используют:

- cookie;
- короткоживущий подписанный URL;
- отдельный одноразовый ticket;
- потоковый `fetch` вместо нативного `EventSource`.

Для cross-origin SSE с автоматически отправляемыми credentials используют:

```ts
const source = new EventSource("https://api.example.com/events", {
  withCredentials: true,
});
```

Сервер при этом должен правильно настроить CORS, вернуть конкретный разрешённый origin и `Access-Control-Allow-Credentials: true`. Cookie также должна соответствовать `SameSite`, `Secure`, `Domain` и политике браузера.

Долгоживущий токен в URL опасен, потому что адрес может попасть в логи, историю диагностики и мониторинг. Если URL-токен всё же используется, он должен быть короткоживущим, узким по назначению и по возможности одноразовым.

SSE передаёт только текст. JSON является обычной строкой внутри `data`. Бинарные данные можно закодировать, например в Base64, но это увеличивает размер и обычно означает, что для задачи лучше подходит другой транспорт или отдельная HTTP-загрузка.

У SSE есть ограничение количества одновременных соединений. При HTTP/1.x браузеры обычно разрешают только небольшое число соединений к одному домену, и несколько вкладок могут быстро исчерпать лимит. При HTTP/2 SSE использует параллельные HTTP-потоки, количество которых согласуется между клиентом и сервером.

Поэтому приложение не должно без необходимости открывать отдельный `EventSource` для каждого виджета. Обычно создают одно соединение и распределяют именованные события внутри приложения.

Прокси, CDN, серверный framework или сжатие могут буферизовать SSE-ответ. Тогда события будут приходить пачкой, хотя сервер генерирует их по одному.

Для корректной работы проверяют:

- отключено ли нежелательное буферизование;
- выполняется ли flush после события;
- не удерживает ли данные компрессор;
- не закрывает ли proxy тихое соединение;
- передаёт ли CDN поток без накопления.

Периодический комментарий SSE начинается с `:` и не создаёт событие в JavaScript:

```text
: heartbeat

```

Он помогает поддерживать активность соединения через промежуточную инфраструктуру.

WebSocket предоставляет двусторонние текстовые и бинарные сообщения по одному постоянному соединению. Он лучше подходит, когда клиент часто отправляет данные в тот же realtime-канал:

```text
клиент ⇄ сервер
```

В отличие от SSE, классический браузерный WebSocket не имеет встроенного автоматического reconnect. Приложение самостоятельно определяет:

- формат сообщений;
- аутентификацию;
- подписки;
- подтверждения;
- heartbeat;
- reconnect с backoff;
- восстановление пропущенных событий;
- дедупликацию;
- обработку кодов закрытия.

WebSocket позволяет передавать `Blob`, `ArrayBuffer` и другие бинарные данные. Но его гибкость увеличивает объём прикладного протокола и инфраструктуры.

У классического браузерного WebSocket также нет автоматического backpressure для входящих сообщений. Если сервер отправляет быстрее, чем JavaScript обрабатывает поток, растут очередь, память и нагрузка на главный поток. Частоту ограничивают на сервере, события агрегируют, а интерфейс обновляют пакетами.

Ни один из четырёх подходов сам по себе не гарантирует доставку события ровно один раз или согласованность всего состояния.

При polling клиент получает отдельные снимки и может не увидеть кратковременное промежуточное состояние.

При long polling, SSE и WebSocket событие может:

- потеряться во время разрыва;
- прийти повторно после reconnect;
- устареть до обработки;
- относиться к более старой версии сущности.

Для важных данных используют:

- `eventId`;
- sequence number;
- версию сущности;
- cursor;
- серверный replay;
- идемпотентный обработчик;
- повторный HTTP-снимок.

Начальный снимок и восстановление состояния удобно выполнять через обычный HTTP API, а realtime-транспорт использовать для последующих изменений.

Инфраструктура также влияет на выбор:

- polling создаёт большое количество отдельных запросов;
- long polling удерживает много ожидающих запросов;
- SSE удерживает долгие HTTP-потоки;
- WebSocket удерживает постоянные соединения и требует поддержки upgrade или Extended CONNECT;
- proxy и load balancer имеют тайм-ауты;
- CDN может не поддерживать нужный режим или буферизовать ответ;
- серверу нужно ограничивать число соединений и частоту сообщений.

Проверять транспорт нужно в окружении, близком к production, а не только на localhost.

Использовать WebSocket только потому, что он воспринимается как наиболее realtime-технология, не обязательно.

Практический выбор:

- **Polling** — обновления редкие, задержка допустима, важна простота.
- **Long polling** — нужна быстрая доставка серверных событий, но SSE или WebSocket недоступны.
- **SSE** — основной поток идёт от сервера к клиенту, данные текстовые, удобен автоматический reconnect.
- **WebSocket** — нужен частый двусторонний обмен, бинарные сообщения или сложный интерактивный протокол.

При уничтожении владельца транспорта нужно освободить ресурсы:

- остановить polling-таймер;
- отменить активный HTTP-запрос;
- вызвать `EventSource.close()`;
- закрыть WebSocket;
- остановить heartbeat и reconnect-таймеры;
- удалить обработчики.

Иначе приложение продолжит выполнять запросы, откроет дубли соединений или применит события к уже неактуальному экрану.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Что такое <code>EventSource</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Это браузерный API для SSE. Он открывает HTTP endpoint с `Content-Type: text/event-stream`, разбирает блоки событий и автоматически пытается восстановить соединение после временного разрыва.

Клиент слушает общее событие `message` или именованные события через `addEventListener`.

У объекта есть состояния `CONNECTING`, `OPEN` и `CLOSED`. Для окончательного закрытия соединения и остановки автоматического reconnect вызывают `close()`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем long polling отличается от обычного polling?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычный polling получает ответ сразу, затем ждёт заданный интервал перед следующим запросом.

Long polling оставляет запрос открытым до появления события или серверного timeout. Поэтому новое значение может прийти почти сразу после его появления.

После каждого ответа long polling всё равно создаёт новый HTTP-запрос. Это не постоянный поток, поэтому контракту может понадобиться идентификатор последнего события или cursor для защиты от пропусков между запросами.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда SSE лучше WebSocket?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда данные почти всегда идут от сервера к клиенту, события текстовые, а действия клиента можно отправлять обычным HTTP.

SSE использует HTTP-инфраструктуру, имеет стандартный формат событий, автоматический reconnect и поддержку `Last-Event-ID`.

Для прогресса задачи, серверных логов, уведомлений и обновляемой ленты этого часто достаточно. WebSocket нужен, если клиент тоже часто отправляет realtime-сообщения или требуется бинарный обмен.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как передать <code>Authorization</code> в нативный <code>EventSource</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Нативный конструктор `EventSource` не позволяет задать произвольный заголовок `Authorization`.

Часто используют HttpOnly cookie. Для cross-origin-соединения создают `EventSource` с `withCredentials: true` и правильно настраивают CORS.

Другой вариант — короткоживущий подписанный URL или одноразовый ticket. Долгоживущий токен в URL использовать опасно из-за логов и утечек адреса.

Альтернативой является потоковый `fetch`, где можно добавить заголовки, но разбор SSE, reconnect и `Last-Event-ID` тогда реализует приложение или библиотека.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Гарантирует ли <code>Last-Event-ID</code>, что события не потеряются?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Браузер только запоминает последний полученный `id` и сообщает его серверу при переподключении.

Сервер должен хранить журнал, понимать этот идентификатор и вернуть события после него.

Если история уже удалена или идентификатор не относится к текущему пользователю и выборке, сервер должен предложить клиенту заново получить актуальный снимок данных.

Также клиенту может понадобиться дедупликация, если последнее событие было обработано, но сервер повторил его после восстановления.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как остановить автоматический reconnect SSE?</strong></summary>

<dl>
<dd>
<h2></h2>

Клиент вызывает:

```ts
source.close();
```

После этого `EventSource` переходит в состояние `CLOSED` и больше не пытается подключиться.

Сервер может вернуть `204 No Content`. Для `EventSource` это означает, что соединение не нужно восстанавливать.

Обычный разрыв или временная сетевая ошибка, наоборот, обычно приводят к автоматическому reconnect после установленной задержки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему количество SSE-соединений может быть ограничено?</strong></summary>

<dl>
<dd>
<h2></h2>

При HTTP/1.x браузер ограничивает количество одновременных соединений к одному домену. Несколько вкладок и несколько `EventSource` на каждой странице могут быстро исчерпать этот лимит.

При HTTP/2 одно сетевое соединение может содержать несколько параллельных потоков, а их максимальное количество согласуется между клиентом и сервером.

Поэтому обычно открывают одно SSE-соединение на приложение и передают через него несколько типов именованных событий.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли передавать бинарные данные через SSE?</strong></summary>

<dl>
<dd>
<h2></h2>

SSE передаёт текст в UTF-8. Нативной передачи бинарного сообщения, как в WebSocket, у него нет.

Бинарные байты можно предварительно закодировать в Base64 или другой текстовый формат, но это увеличивает размер данных и нагрузку на кодирование.

Для крупных файлов используют обычную HTTP-загрузку, а для частого двустороннего бинарного потока чаще выбирают WebSocket или другой подходящий транспорт.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему SSE-события приходят пачкой, а не сразу?</strong></summary>

<dl>
<dd>
<h2></h2>

Чаще всего сервер, framework, компрессор, reverse proxy или CDN накапливает часть ответа перед отправкой.

Нужно проверить:

- завершается ли событие пустой строкой;
- выполняется ли flush;
- отключено ли нежелательное буферизование;
- не задерживает ли данные сжатие;
- поддерживает ли proxy потоковую передачу;
- не действует ли слишком большой внутренний буфер.

Периодический комментарий-heartbeat помогает поддерживать активность соединения, но сам по себе не исправляет буферизацию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда polling является нормальным выбором?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда обновления редкие, задержка в несколько секунд допустима, а простота важнее постоянного соединения.

Например:

- статус генерации отчёта;
- редкое обновление административной таблицы;
- проверка завершения фоновой задачи;
- запасной вариант при недоступности другого транспорта.

Интервал адаптируют к активности, не допускают перекрывающихся запросов, останавливают после завершения задачи и увеличивают после ошибок.

Для уменьшения трафика можно использовать условные запросы с `ETag` или `Last-Modified`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какой транспорт гарантирует доставку события ровно один раз?</strong></summary>

<dl>
<dd>
<h2></h2>

Ни один из перечисленных транспортов не предоставляет прикладную гарантию exactly once автоматически.

После разрыва событие может потеряться или прийти повторно. Клиент также может получить событие, обработать его и потерять соединение до подтверждения.

Для важных событий используют:

- уникальный `eventId`;
- sequence number;
- acknowledgement;
- журнал и replay;
- дедупликацию;
- идемпотентный обработчик;
- повторный снимок состояния по HTTP.

Гарантии доставки являются свойством полного прикладного протокола, а не только выбранного сетевого транспорта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие вопросы задать перед выбором транспорта?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно определить:

1. В какую сторону передаются данные.
2. Как часто появляются события.
3. Какая задержка допустима.
4. Нужны ли бинарные сообщения.
5. Сколько клиентов и вкладок будут подключены одновременно.
6. Как работает аутентификация.
7. Поддерживают ли proxy, CDN и load balancer долгие соединения.
8. Как восстанавливаются пропущенные события.
9. Требуется ли точная последовательность или снимок данных.
10. Как клиент освобождает соединение и обрабатывает ошибки.

Ответы на эти вопросы важнее предпочтения конкретной библиотеки или технологии.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Задача | Подход |
| --- | --- |
| Статус задачи раз в десять секунд | Polling |
| Прогресс генерации отчёта | SSE |
| Поток серверных логов | SSE |
| Уведомления | SSE или WebSocket |
| Чат и присутствие пользователей | WebSocket |
| Совместный редактор | WebSocket и отдельная модель конфликтов |
| Восстановление после разрыва | Replay по id или новый HTTP-снимок |
| Простой запасной вариант | Polling |
