## Вопрос

<br>

 💬 **Как во frontend устроены серверные сессии, access token и обновление токенов? Какие риски нужно учитывать?**

<h2></h2>

<br>
<dl>
<dd>

Authentication, или аутентификация, подтверждает личность пользователя. Authorization, или авторизация, определяет его права.

Frontend участвует в обоих процессах: показывает форму входа, хранит состояние пользователя, добавляет учётные данные к запросам и скрывает недоступные действия. Но окончательное решение всегда принимает сервер. Скрытая кнопка не защищает endpoint, то есть адрес операции API, от прямого запроса.

В браузерных приложениях часто используют одну из следующих схем или их сочетание:

| Схема | Как подтверждается запрос |
| --- | --- |
| Серверная сессия | Браузер автоматически отправляет cookie со случайным идентификатором, а состояние сессии хранится на сервере |
| Bearer access token, или токен доступа | Клиент добавляет `Authorization: Bearer <token>`; сервер проверяет непрозрачный токен или JWT |
| BFF (Backend for Frontend) | Браузер работает с HttpOnly cookie сессии, а отдельный серверный слой хранит токены и вызывает защищённые API |

При серверной сессии cookie обычно содержит не данные пользователя, а случайный непрозрачный идентификатор. По нему сервер находит сессию, пользователя, права и срок действия в собственном хранилище.

После успешного входа и любого значимого повышения привилегий сервер должен выдать новый идентификатор сессии, а старый сделать недействительным. Это защищает от session fixation, когда злоумышленник заранее навязывает пользователю известный session ID, а затем пытается использовать его после входа.

Для сессии обычно задают несколько независимых ограничений:

- idle timeout — завершение после периода бездействия;
- absolute timeout — максимальный срок сессии независимо от активности;
- отзыв при logout, смене пароля или другом событии безопасности;
- срок хранения cookie в браузере.

Срок cookie и срок серверной сессии — не одно и то же. Удаление или истечение cookie убирает идентификатор из браузера, но сервер всё равно должен самостоятельно проверять срок действия и отзывать сессию. И наоборот, сервер может завершить сессию раньше, чем исчезнет cookie.

Cookie с идентификатором сессии или refresh token, то есть токен обновления, обычно защищают атрибутами:

- `HttpOnly` запрещает чтение через `document.cookie`;
- `Secure` разрешает отправку только по HTTPS, кроме специальных правил localhost;
- `SameSite` ограничивает отправку в межсайтовом контексте;
- `Path` ограничивает URL-пути, для которых браузер отправляет cookie;
- `Domain` определяет доступность для текущего хоста и его поддоменов;
- `Max-Age` или `Expires` определяет срок хранения постоянной cookie в браузере.

Для чувствительной cookie обычно не задают `Domain`. Тогда она становится host-only и не отправляется поддоменам.

`Path` уменьшает область отправки cookie, но не является надёжной границей безопасности между приложениями на одном origin. JavaScript одного origin может взаимодействовать с другими путями этого origin.

Для cookie, которая должна принадлежать только текущему хосту, можно использовать префикс `__Host-`. Такая cookie должна иметь `Secure`, `Path=/` и не должна содержать `Domain`:

```http
Set-Cookie: __Host-session=<value>; Path=/; Secure; HttpOnly; SameSite=Lax
```

`HttpOnly` снижает риск кражи значения при XSS, но не устраняет сам XSS. Вредоносный скрипт не сможет прочитать cookie, однако всё ещё сможет отправлять запросы из открытой страницы, и браузер автоматически приложит к ним cookie.

Поскольку cookie отправляется автоматически, изменяющие запросы требуют CSRF-защиты. `SameSite=Lax` или `Strict` является важным защитным слоем, но конкретная схема также может использовать CSRF token, проверку `Origin`, обязательный собственный заголовок или другую серверную защиту.

Bearer access token клиент добавляет к запросу самостоятельно:

```http
Authorization: Bearer <token>
```

Bearer означает, что обладание значением обычно достаточно для использования токена. Поэтому утечка позволяет злоумышленнику выполнять запросы от имени владельца до истечения или отзыва токена.

Access token обычно делают короткоживущим. В browser-only приложении его можно хранить в памяти JavaScript, чтобы он не сохранялся между перезагрузками и не лежал длительно в постоянном хранилище.

Хранение в памяти уменьшает срок и область сохранения токена, но не защищает от вредоносного JavaScript, который уже выполняется в странице. Такой код может прочитать текущий токен или отправить запросы от имени приложения.

Если access token хранится в `localStorage`, любой JavaScript, выполняющийся в том же origin из-за XSS, уязвимой зависимости или расширения с соответствующим доступом, может прочитать и вынести его. `localStorage` также сохраняется между перезагрузками и доступен вкладкам одного origin.

Refresh token является более долгоживущей учётной информацией и требует более строгой защиты. Его часто хранят в HttpOnly cookie либо полностью оставляют на стороне BFF.

При BFF браузер не получает access и refresh tokens. Он отправляет BFF защищённую cookie сессии, BFF находит серверные токены, добавляет access token к запросу внутреннего API и возвращает браузеру результат.

BFF уменьшает риск извлечения токенов из браузера, но не делает заражённую страницу безопасной. XSS-код всё ещё может выполнять разрешённые запросы через BFF от имени пользователя, поэтому остаются важны защита от XSS, CSRF и строгий список направлений, куда BFF может проксировать запросы.

JWT является форматом токена, а не способом хранения или отправки. JWT может быть access token, ID token или другим типом сообщения.

Обычный подписанный JWT обеспечивает контроль целостности, но не конфиденциальность. Его header и payload закодированы в URL-safe-форме и могут быть прочитаны без секретного ключа. Для сокрытия содержимого требуется зашифрованный JWT, то есть JWE.

Поэтому в payload подписанного JWT нельзя помещать пароли, приватные ключи и другие данные, которые пользователь или злоумышленник не должен видеть.

Сервер или другая проверяющая сторона должны:

- разрешать только ожидаемые алгоритмы;
- проверять подпись или другую криптографическую защиту;
- проверять `iss`, то есть издателя;
- проверять `aud`, то есть получателя токена;
- учитывать `exp`, `nbf` и другие временные ограничения;
- проверять тип и назначение токена;
- не доверять claims только потому, что они присутствуют в payload.

Frontend может декодировать JWT, чтобы показать несекретную информацию или приблизительно определить срок окончания. Но результат декодирования нельзя использовать как доказательство прав: подпись и актуальность разрешений проверяет сервер.

Типичный процесс обновления токенов выглядит так:

1. API сообщает, что access token истёк или больше не действителен.
2. Клиент запускает один запрос обновления токена.
3. Остальные запросы с той же причиной ошибки ожидают тот же Promise, а не запускают собственное обновление.
4. После успеха новая учётная информация сохраняется, а ожидающие запросы повторяются один раз.
5. После неудачи клиент завершает локальную сессию, очищает чувствительные данные и переводит пользователя к повторному входу.

Refresh не следует запускать при любом `401` без разбора контракта. `401` также может означать неправильный токен, отозванную сессию, неподходящую схему аутентификации или ошибку самого endpoint обновления.

API полезно возвращать стабильный машинный код, позволяющий отличить истёкший access token от окончательно недействительной сессии. Сам запрос refresh и уже повторённый исходный запрос не должны снова запускать бесконечный цикл обновления.

`403` обычно не является поводом обновлять токен. Он означает, что сервер понял запрос, но текущему пользователю или клиенту не разрешено действие. Повтор с теми же правами проблему не исправит.

Single-flight, то есть один общий запрос обновления для всех ожидающих запросов, предотвращает гонки внутри одного JavaScript-контекста.

Однако несколько вкладок имеют отдельную память и могут одновременно начать refresh. Для координации можно использовать BFF, `BroadcastChannel`, `SharedWorker` или другой механизм обмена состоянием. Независимо от frontend-координации сервер должен атомарно обрабатывать использование refresh token.

Refresh token rotation означает, что при успешном обновлении сервер:

1. Выдаёт новый access token.
2. Выдаёт новый refresh token.
3. Делает использованный refresh token недействительным.
4. Сохраняет связь между токенами одной цепочки.

Если уже использованный refresh token появляется снова, это может означать replay, то есть повторное использование украденного значения. Сервер не всегда способен определить, кто отправил старый токен — пользователь или злоумышленник, — поэтому отзывает активный refresh token или всю связанную авторизацию и требует нового входа.

Для публичных OAuth-клиентов сервер авторизации должен защищать refresh token от повторного использования через rotation либо sender-constrained-токены, криптографически привязанные к экземпляру клиента.

Ротация не должна превращать refresh token в бессрочную учётную информацию. Сервер задаёт общий максимальный срок жизни либо срок неактивности, а также может отзывать токены при logout, смене пароля или другом событии безопасности.

При аутентификации через cookie между разными origin клиент использует `credentials: "include"`, сервер возвращает конкретный `Access-Control-Allow-Origin` и `Access-Control-Allow-Credentials: true`, а cookie должна пройти правила `SameSite`, `Secure`, `Domain` и политики браузера.

Cross-origin и cross-site не одно и то же. Разные поддомены имеют разные origin, но могут относиться к одному site. CORS и `SameSite` проверяют разные границы.

Выход из системы не должен ограничиваться очисткой состояния React.

Сервер должен завершить сессию или отозвать refresh token. Если используется HttpOnly cookie, JavaScript не может удалить её напрямую: сервер возвращает `Set-Cookie` с тем же именем, `Path` и `Domain`, но с `Max-Age=0` или прошедшим `Expires`.

Frontend после logout:

- очищает access token, если он доступен JavaScript;
- удаляет данные текущего пользователя;
- сбрасывает кеш чувствительных серверных данных;
- отменяет фоновые запросы;
- закрывает WebSocket, SSE и другие длительные соединения;
- переводит приложение в неаутентифицированное состояние.

Уже выданный автономный access token может оставаться действительным до окончания `exp`, даже если refresh token отозван. Для немедленного прекращения доступа нужна серверная проверка сессии, интроспекция, denylist или другой механизм отзыва. Поэтому access token обычно имеет ограниченный срок жизни.

Длительные соединения также не должны полагаться только на состояние frontend. Сервер должен учитывать завершение сессии и прекращать обслуживание соединения, когда доступ пользователя отозван.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Что даёт <code>HttpOnly</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

JavaScript не может прочитать такую cookie через `document.cookie`, поэтому атакующему сложнее вынести идентификатор сессии или refresh token и использовать его с другого устройства.

Однако XSS-код внутри страницы всё ещё может отправлять запросы, к которым браузер автоматически приложит cookie.

Поэтому `HttpOnly` защищает значение от прямого чтения, но не устраняет XSS и не заменяет CSRF-защиту.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает <code>SameSite</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Атрибут определяет, когда cookie разрешено отправлять в межсайтовом контексте.

`Strict` является наиболее ограничительным и отправляет cookie только в same-site-контексте.

`Lax` дополнительно допускает некоторые безопасные переходы верхнего уровня, например обычное открытие ссылки.

`None` разрешает межсайтовую отправку и требует `Secure`.

`SameSite` является защитным слоем против CSRF, но не всегда единственным достаточным механизмом. Выбор зависит от внешнего входа, поддоменов, `iframe`, платёжных переходов и других сценариев приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем session cookie отличается от JWT?</strong></summary>

<dl>
<dd>
<h2></h2>

Cookie серверной сессии обычно содержит случайный идентификатор, по которому сервер находит состояние сессии.

JWT является форматом токена, который может содержать подписанные или зашифрованные claims. Его можно передавать в заголовке `Authorization`, cookie или другим способом.

Cookie — это механизм хранения и автоматической отправки данных браузером. JWT — формат сообщения. Поэтому JWT можно хранить в cookie, а session ID можно передавать не только через cookie.

Также выражение session cookie иногда означает cookie без `Max-Age` и `Expires`, которая хранится только в рамках браузерной сессии. Это отдельное значение термина и не гарантирует, что серверная сессия завершится одновременно с закрытием браузера.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем время жизни cookie отличается от времени жизни сессии?</strong></summary>

<dl>
<dd>
<h2></h2>

`Max-Age` и `Expires` определяют, как долго браузер хранит cookie. Они не заставляют сервер автоматически удалить связанную сессию.

Сервер отдельно применяет idle timeout, absolute timeout и правила отзыва. Даже если браузер продолжает отправлять cookie, сервер должен отклонить истёкший или отозванный session ID.

Если cookie исчезла раньше, браузер перестанет отправлять идентификатор, но серверная запись может оставаться в хранилище до очистки. Поэтому жизненный цикл контролируют на обеих сторонах, а главным источником решения о действительности является сервер.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем менять идентификатор сессии после входа?</strong></summary>

<dl>
<dd>
<h2></h2>

До входа пользователь может иметь анонимную сессию. Если после успешной аутентификации сохранить тот же идентификатор, злоумышленник, заранее узнавший или установивший его, сможет попытаться использовать уже авторизованную сессию.

Сервер после входа создаёт новый случайный session ID, переносит необходимые данные и делает старый идентификатор недействительным.

Идентификатор также меняют после повышения привилегий, смены пароля и других важных изменений уровня доступа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему нельзя запускать refresh на каждый <code>401</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`401` не всегда означает только истечение access token. Причиной может быть отозванная сессия, неправильная схема аутентификации, повреждённый токен или ошибка самого refresh endpoint.

Несколько параллельных запросов также могут создать несколько обновлений и гонку токенов. При rotation один запрос способен сделать токен другого уже недействительным.

Клиент запускает refresh только для предусмотренной контрактом причины, хранит один Promise операции и повторяет исходный запрос не более одного раза.

Refresh endpoint, запрос входа и уже повторённый запрос не должны снова запускать обновление.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать с refresh в нескольких вкладках?</strong></summary>

<dl>
<dd>
<h2></h2>

Один Promise refresh-операции доступен только внутри текущего JavaScript-контекста. Другая вкладка имеет собственную память и может одновременно использовать тот же refresh token.

Для координации можно применять `BroadcastChannel`, `SharedWorker`, серверный BFF или другой общий механизм.

Но frontend-координация не является границей безопасности. Сервер должен атомарно обрабатывать rotation, не допускать двойное успешное использование одного токена и корректно реагировать на повтор старого значения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли <code>401</code> означает logout?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Если access token истёк, а refresh token ещё действителен, допустим один запрос обновления и однократный повтор исходной операции.

Logout нужен, если refresh token отсутствует, истёк, отозван, повторно использован либо обновление завершилось окончательной ошибкой.

API полезно различать причины стабильным машинным кодом, но клиент не должен бесконечно пытаться восстановить недействительную сессию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое refresh token rotation?</strong></summary>

<dl>
<dd>
<h2></h2>

Сервер выдаёт новый refresh token при каждом успешном использовании и делает старый недействительным.

При этом сервер сохраняет связь между токенами одной авторизации. Если старое значение появляется повторно, это указывает на возможный replay украденного токена.

Поскольку сервер может не знать, какая сторона является злоумышленником, он отзывает активный токен или всю связанную цепочку и требует новой аутентификации.

Ротация требует атомарной серверной реализации, ограниченного общего срока жизни и аккуратной обработки параллельных запросов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где безопаснее хранить access token?</strong></summary>

<dl>
<dd>
<h2></h2>

Универсального ответа без архитектуры нет.

Память вкладки не сохраняет токен надолго, но вредоносный JavaScript текущей страницы всё равно может его прочитать.

`localStorage` прост и переживает перезагрузку, но доступен всему JavaScript текущего origin, поэтому утечка через XSS может сохранять доступ и после закрытия страницы.

HttpOnly cookie скрывает значение от JavaScript, но браузер отправляет её автоматически, поэтому требуется CSRF-защита.

BFF может вообще не отдавать access и refresh tokens браузеру. Это уменьшает риск их извлечения, хотя вредоносный код всё ещё может выполнять разрешённые запросы через активную cookie-сессию пользователя.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что должен сделать frontend при logout?</strong></summary>

<dl>
<dd>
<h2></h2>

Frontend вызывает серверный endpoint завершения сессии или отзыва refresh token.

Если используется HttpOnly cookie, очистить её должен сервер через `Set-Cookie` с теми же областью и именем, но с `Max-Age=0` или прошедшим `Expires`.

Затем frontend:

- очищает доступный ему access token;
- удаляет состояние пользователя;
- сбрасывает кеш чувствительных данных;
- отменяет фоновые запросы;
- закрывает realtime-соединения;
- переводит приложение в неаутентифицированное состояние.

Уже выданный автономный access token может оставаться действительным до истечения срока, если система не поддерживает его немедленный отзыв. Поэтому logout и короткий срок access token решают связанные, но разные задачи.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Поведение клиента |
| --- | --- |
| Access token истёк | Один запрос обновления и однократный повтор исходного запроса |
| Несколько запросов получили `401` | Один общий refresh и очередь ожидания |
| Refresh завершился ошибкой | Очистить состояние и перейти к экрану входа |
| Cookie между разными origin | `credentials`, CORS и атрибуты cookie |
| Сервер вернул `403` | Показать отсутствие прав без refresh |
| Выход из системы | Отозвать серверную сессию, очистить кеши и соединения |
| Интерфейс проверяет право | Улучшить UX, сохранив серверную проверку каждого запроса |
