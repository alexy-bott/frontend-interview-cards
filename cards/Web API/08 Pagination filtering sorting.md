## Вопрос

<br>

 💬 **Как устроены пагинация, фильтрация и сортировка в API? Чем offset pagination отличается от cursor pagination?**

<h2></h2>

<br>
<dl>
<dd>

Pagination, или пагинация, делит большую коллекцию на части. Без неё ответ становится медленным, тяжёлым для сети и неудобным для кеширования. API должен заранее определить формат параметров, стабильный порядок элементов и метаданные, по которым клиент понимает, как получить следующую часть.

Основные модели:

| Модель | Пример | Сильная сторона | Ограничение |
| --- | --- | --- | --- |
| Offset/limit, смещение и размер | `?offset=40&limit=20` | Просто перейти к известной позиции | Вставки и удаления дают пропуски или дубли; большое смещение может быть дорогим |
| Page/pageSize, номер и размер страницы | `?page=3&pageSize=20` | Удобно показать номера страниц | Обычно является вариантом offset с теми же ограничениями |
| Cursor, курсор | `?after=eyJpZCI6...&limit=20` | Устойчивее для изменяющейся ленты и последовательной загрузки | Сложнее перейти на произвольную страницу и получить точное общее количество |

При offset pagination, или пагинации по смещению, сервер пропускает заданное число записей. Если между запросами в начало списка добавился новый элемент, запись с границы может повториться на следующей странице. Если элемент удалился, другая запись может быть пропущена. Для небольшой административной таблицы это часто приемлемо, а для активно меняющейся ленты лучше cursor pagination.

При cursor pagination, или пагинации по курсору, сервер возвращает непрозрачное значение, обозначающее позицию в выбранной сортировке. Например, при порядке `createdAt DESC, id DESC` курсор может кодировать оба значения последнего элемента. `id` служит tie-breaker, то есть дополнительным уникальным критерием для записей с одинаковым временем. Без стабильной сортировки один и тот же набор данных может каждый раз разбиваться на страницы по-разному.

```json
{
  "items": [{ "id": "42", "createdAt": "2026-07-27T10:00:00Z" }],
  "pageInfo": {
    "hasNextPage": true,
    "nextCursor": "eyJjcmVhdGVkQXQiOiIuLi4iLCJpZCI6IjQyIn0"
  }
}
```

Клиент не должен разбирать или самостоятельно изменять курсор: его формат принадлежит серверу и может поменяться. Для обратной навигации контракт отдельно предоставляет `before`/`previousCursor` или другой симметричный механизм. Если нужен переход на страницу 37 и точное число страниц, offset-модель может быть практичнее.

Фильтрацию и сортировку обычно передают через query-параметры, то есть параметры строки запроса, например `?status=active&sort=-createdAt,name`. Сервер обязан разрешать только известные поля и операции, а также ограничивать `limit`. Frontend должен знать, как кодируются массивы, диапазоны, пустые значения и направление сортировки, иначе одинаковый фильтр будет представлен разными URL.

Все параметры, влияющие на ответ, входят в ключ кеша: фильтры, сортировка, страница, курсор, область доступных пользователю данных и иногда локаль. Если использовать один ключ `users` для разных фильтров, библиотека управления серверным состоянием может показать данные другой выборки. Параметры полезно канонизировать, то есть приводить к одному представлению: сортировать неупорядоченные массивы и не отправлять значения по умолчанию двумя разными способами.

Когда фильтр или сортировка меняется, текущую страницу обычно сбрасывают в начало. Старый запрос отменяют либо не позволяют ему заменить данные нового запроса. Для строки поиска применяют debounce, то есть небольшую задержку перед запросом, чтобы не отправлять его после каждого нажатия клавиши.

Состояние таблицы хранят в URL, если пользователь должен обновить страницу, поделиться ссылкой или пользоваться кнопками браузера «назад» и «вперёд» без потери фильтров. Локальное состояние подходит для временного интерфейсного параметра, который не определяет содержимое страницы. Преобразование между URL и объектом фильтров должно быть двусторонним и типобезопасным.

При бесконечной прокрутке клиент добавляет новые элементы к существующим, проверяет `hasNextPage`, не запрашивает один курсор дважды и удаляет дубли записей по `id`. После изменения данных, восстановления соединения или долгой паузы может понадобиться повторный запрос: курсор гарантирует продолжение по контракту, но не делает однажды загруженный снимок данных актуальным навсегда.

Точное общее количество записей (`total`) бывает дорогим на больших или распределённых данных. Для бесконечной ленты достаточно `hasNextPage` и `nextCursor`. Для таблицы с номерами страниц общее количество может требоваться интерфейсу, но API вправе возвращать приближённое значение или считать его отдельным запросом. Это должно быть явно отражено в контракте.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем cursor pagination лучше offset?</strong></summary>

<dl>
<dd>
<h2></h2>

Она продолжает выборку после конкретной позиции в стабильной сортировке, поэтому вставка новых элементов перед уже просмотренными меньше влияет на следующую страницу. Кроме того, серверу часто не нужно пропускать большое число строк. Цена заключается в отсутствии простого перехода к произвольному номеру страницы и более сложном контракте.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему курсор должен опираться на уникальный порядок?</strong></summary>

<dl>
<dd>
<h2></h2>

Поле `createdAt` может совпадать у нескольких записей. Если курсор хранит только его, сервер не знает, какие элементы с тем же временем уже были отданы. Пара `createdAt` и `id` создаёт однозначный порядок и не позволяет записи потеряться на границе.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли использовать <code>id</code> как cursor?</strong></summary>

<dl>
<dd>
<h2></h2>

Да, если сортировка действительно определяется монотонным `id` и контракту не нужны другие критерии. При сортировке по рейтингу, дате или нескольким полям одного `id` недостаточно. Чаще сервер выдаёт непрозрачный cursor, чтобы клиент не зависел от внутреннего устройства индекса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему query key должен включать фильтры и сортировку?</strong></summary>

<dl>
<dd>
<h2></h2>

Потому что `status=active` и `status=blocked` являются разными результатами одной операции API. Если ключ одинаковый, кеш смешает выборки или покажет предыдущие данные как актуальные. В RTK Query эту роль выполняют аргументы endpoint и их сериализация, в TanStack Query явный `queryKey`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда фильтры нужно хранить в URL?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда они определяют восстанавливаемое состояние страницы: каталог, поиск, административную таблицу. URL позволяет открыть ту же выборку после перезагрузки, поделиться ссылкой и использовать историю браузера. Состояние открытого выпадающего списка или временный черновик обычно остаётся локальным.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему при смене фильтра нужно сбрасывать страницу?</strong></summary>

<dl>
<dd>
<h2></h2>

Третья страница нового узкого фильтра может не существовать, и пользователь увидит пустой список, хотя на первой странице есть данные. Новый набор параметров обычно начинает отдельную последовательность пагинации с `page=1` или без cursor.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему API иногда не возвращает <code>total</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Точный подсчёт может потребовать дорогого полного прохода по большой выборке или координации нескольких хранилищ. Для кнопки «загрузить ещё» достаточно знать наличие следующей страницы. Если продукту нужен total, стоимость подсчёта и допустимая точность становятся частью API-контракта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как избежать дублей в infinite scroll?</strong></summary>

<dl>
<dd>
<h2></h2>

Использовать стабильную сортировку и курсор от сервера, не запускать повторно одну и ту же страницу, а при объединении удалять дубли сущностей по устойчивому `id`. После изменения списка нужно понимать политику библиотеки: обновить запись в кеше, признать последовательность устаревшей или загрузить актуальный снимок заново.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Подход |
| --- | --- |
| Административная таблица | `page`/`pageSize`, общее количество и состояние в URL |
| Бесконечная лента | Cursor, `hasNextPage` и дедупликация |
| Каталог товаров | Фильтры и сортировка в параметрах URL |
| Автодополнение | Debounce, отмена и защита от устаревшего ответа |
| RTK Query | Все параметры входят в аргумент endpoint |
| TanStack Query | Все параметры входят в `queryKey` |
| Изменение фильтра | Сброс страницы и отдельный кеш результата |
