## Вопрос

<br>

 💬 **Как работает Fetch API? Что нужно учитывать при обработке ответа, отмене запроса, заголовках и `credentials`?**

<h2></h2>

<br>
<dl>
<dd>

Fetch API является браузерным интерфейсом для сетевых запросов и доступен в контексте страницы и Web Worker. `fetch(url, options)` возвращает Promise с объектом `Response`.

Promise обычно выполняется после получения статуса и заголовков ответа. В этот момент тело может быть загружено ещё не полностью и продолжать поступать как поток данных. Чтение тела выполняется отдельным асинхронным действием.

`fetch` не считает `404` или `500` ошибкой самого сетевого запроса. Доступный HTTP-ответ получен, поэтому Promise выполняется, а `response.ok` имеет значение `false`.

Отклонение Promise происходит, когда Fetch API не может предоставить JavaScript доступный ответ: например, из-за сетевой ошибки, некорректного URL, блокировки CORS или отмены запроса. При CORS-сбое сервер мог получить запрос и даже вернуть ответ, но браузер не передаст его JavaScript-коду, поэтому реальный HTTP-статус обычно будет недоступен.

```ts
async function getUser(id: string, signal: AbortSignal) {
  const response = await fetch(`/api/users/${id}`, {
    headers: { Accept: "application/json" },
    credentials: "same-origin",
    signal,
  });

  if (!response.ok) {
    throw await toApiError(response);
  }

  if (response.status === 204) {
    return undefined;
  }

  return response.json();
}
```

Тело `Response` можно прочитать через `json()`, `text()`, `blob()`, `arrayBuffer()`, `formData()` или поток `body`.

Обычно тело читают только один раз. После начала чтения `bodyUsed` становится `true`, а повторная попытка получить содержимое того же ответа завершается ошибкой.

Если один ответ действительно нужно передать двум независимым обработчикам, его заранее клонируют через `response.clone()`. Клон нужно создать до чтения тела. Две ветви потока читаются независимо, поэтому медленный потребитель может привести к дополнительному буферизованию данных в памяти.

`response.json()` не проверяет, объявил ли сервер `Content-Type: application/json`. Метод читает тело и пытается разобрать его как JSON. Если тело пустое или содержит другой формат, Promise метода отклоняется с ошибкой разбора.

Заголовки `Content-Type` и `Accept` решают разные задачи:

- `Content-Type` описывает формат тела, которое отправляет клиент или сервер;
- `Accept` сообщает серверу, какие форматы ответа предпочитает клиент.

`Accept: application/json` не гарантирует, что сервер действительно вернёт JSON. API-слой всё равно должен учитывать статус, `Content-Type` ответа и контракт endpoint.

Для отправки JSON объект сериализуют через `JSON.stringify` и задают соответствующий тип тела:

```ts
await fetch("/api/users", {
  method: "POST",
  headers: {
    Accept: "application/json",
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    name: "Alex",
  }),
});
```

Для `FormData` заголовок `Content-Type` вручную обычно не устанавливают. Браузер сам формирует `multipart/form-data` и добавляет уникальный `boundary`, то есть разделитель частей тела.

JavaScript не может произвольно управлять всеми HTTP-заголовками. Некоторые заголовки, например `Host`, `Content-Length` и `Cookie`, устанавливает сам браузер, и Fetch API не разрешает задавать их из скрипта.

При cross-origin-запросе JavaScript также видит не все заголовки ответа. CORS автоматически открывает только ограниченный набор. Для доступа к дополнительному заголовку, например `X-Request-Id`, сервер должен перечислить его в `Access-Control-Expose-Headers`.

`AbortController` позволяет сообщить Fetch API, что запрос или дальнейшее чтение ответа больше не нужны:

```ts
const controller = new AbortController();

fetch("/api/search?q=react", { signal: controller.signal });
controller.abort();
```

Вызов `abort()` переводит сигнал в отменённое состояние. Связанный `fetch` или операция чтения тела отклоняется с причиной отмены. При обычном вызове `controller.abort()` это обычно `DOMException` с именем `AbortError`.

Один `AbortSignal` можно передать нескольким связанным запросам и отменить их вместе. После отмены сигнал нельзя вернуть в начальное состояние или повторно использовать для нового независимого запроса: для этого создают новый `AbortController`.

Отмена полезна при смене страницы, новом запросе автодополнения и очистке эффекта React. Она может остановить дальнейшую передачу или чтение данных на клиенте и сократить ненужную работу.

При этом отмена сама по себе не гарантирует, что устаревшие данные никогда не попадут в интерфейс. Запрос мог завершиться до вызова `abort()`, а другой источник данных может вообще не поддерживать сигнал. Поэтому код дополнительно проверяет актуальность параметров или идентификатор попытки.

Отмена на клиенте также не гарантирует откат операции на сервере. Сервер мог уже получить запрос, изменить данные или запустить фоновую задачу. Поэтому операции изменения всё равно требуют корректной идемпотентности, транзакций или ключа идемпотентности.

У `fetch` нет отдельного параметра `timeout`. Ограничение времени реализуют через `AbortSignal.timeout(ms)` в поддерживаемых окружениях:

```ts
await fetch("/api/report", {
  signal: AbortSignal.timeout(10_000),
});
```

При истечении времени операция обычно отклоняется с `DOMException`, имя которой равно `TimeoutError`. Обычная ручная отмена через `AbortController` приводит к `AbortError`, поэтому эти случаи можно по-разному отображать в интерфейсе.

Чтобы объединить отмену по жизненному циклу компонента и таймаут, используют `AbortSignal.any()`:

```ts
const controller = new AbortController();

const signal = AbortSignal.any([
  controller.signal,
  AbortSignal.timeout(10_000),
]);

await fetch("/api/report", { signal });
```

Истечение времени означает только то, что клиент прекратил ждать или читать ответ. Это не доказывает, что сервер остановил выполнение операции.

Параметр `credentials` управляет автоматическими учётными данными браузера и тем, будет ли браузер учитывать `Set-Cookie` из ответа. К таким данным относятся cookies, клиентские TLS-сертификаты и данные встроенной HTTP-аутентификации.

| Значение | Поведение |
| --- | --- |
| `omit` | Не отправлять автоматические учётные данные и не учитывать их из ответа |
| `same-origin` | Использовать учётные данные только для запросов к тому же origin; значение по умолчанию |
| `include` | Разрешить использование учётных данных и при cross-origin-запросе |

Явно добавленный приложением заголовок вроде `Authorization: Bearer ...` нужно контролировать отдельно через `headers`. Не следует использовать `credentials` как способ добавить или удалить такой токен. При cross-origin-запросе `Authorization` обычно приводит к CORS preflight и должен быть разрешён сервером.

`credentials: "include"` само по себе не гарантирует отправку cookie. Cookie должна подходить по `Domain`, `Path`, `Secure`, `SameSite` и другим правилам браузера. Дополнительно могут действовать ограничения на third-party cookies.

Для credentialed cross-origin-запроса сервер должен вернуть:

- `Access-Control-Allow-Credentials: true`;
- `Access-Control-Allow-Origin` с конкретным origin клиента.

При таком запросе значение `Access-Control-Allow-Origin: *` недопустимо. Предварительный CORS-запрос `OPTIONS` при этом отправляется без credentials, а уже основной запрос может содержать их после успешной проверки.

Заголовок `Set-Cookie` недоступен JavaScript через `response.headers`. Браузер обрабатывает его самостоятельно, если это разрешают `credentials`, CORS и политика cookies.

Режим `no-cors` не исправляет ошибку CORS. Он сильно ограничивает методы и заголовки запроса, а JavaScript получает opaque response, то есть непрозрачный ответ:

- `status` равен `0`;
- `ok` равен `false`;
- содержательные заголовки недоступны;
- тело нельзя прочитать.

Такой режим используется в отдельных сценариях загрузки ресурсов и Service Worker, но не подходит для чтения JSON API.

В приложении Fetch API обычно закрывает общий API-слой. Он задаёт базовый URL, условно добавляет нужные заголовки и авторизацию, безопасно разбирает успешные ответы и ошибки, связывает отмену с жизненным циклом запроса и ограничивает повторные попытки.

Обёртка не должна безусловно устанавливать `Content-Type: application/json` для всех запросов: у `GET` обычно нет тела, а для `FormData` тип формирует браузер.

API-слой также должен сохранять различия между `401`, `403`, `422`, отменой, таймаутом, сетевой ошибкой и ошибкой контракта, а не превращать их в одну строку «что-то пошло не так».

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что означает <code>response.ok</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Это логическое значение, равное `true` для HTTP-статусов от `200` до `299`.

Оно не проверяет формат тела, схему JSON или бизнес-результат внутри ответа. Сервер может вернуть `200` с неожиданной структурой, повреждённым JSON или внутренним полем ошибки.

Для `404` или `500` объект `Response` существует, но `ok` равен `false`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему тело ответа читается отдельным вызовом?</strong></summary>

<dl>
<dd>
<h2></h2>

Статус и заголовки могут прийти раньше полного тела, а само тело может быть большим или поступать постепенно.

`response.json()` сначала асинхронно читает поток целиком и только затем разбирает полученную строку как JSON. `response.text()`, `blob()` и другие методы работают по тому же принципу.

Для потокового интерфейса можно читать `response.body` по частям и обновлять UI по мере поступления данных.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что произойдёт после <code>controller.abort()</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Сигнал получает состояние `aborted`, а связанная незавершённая операция отклоняется с причиной отмены. При вызове `controller.abort()` без собственной причины это обычно `DOMException` с именем `AbortError`.

Отмена может прервать не только ожидание первоначального `Response`, но и чтение его тела.

Обработчик должен отличать ожидаемую отмену от сетевой ошибки, чтобы не показывать лишнее уведомление пользователю.

Один сигнал можно передать нескольким связанным запросам и отменить их вместе. Повторно вернуть отменённый сигнал в активное состояние нельзя.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Отменяет ли <code>AbortController</code> операцию на сервере?</strong></summary>

<dl>
<dd>
<h2></h2>

Не гарантированно. Браузер прекращает ожидание и по возможности останавливает дальнейшую передачу или чтение данных.

Однако сервер мог уже получить тело, записать заказ, провести операцию или запустить фоновую задачу. Закрытие соединения также не обязывает сервер выполнять откат.

Для изменения данных нужны серверная дедупликация, транзакции, проверка версии и идемпотентность. `AbortController` решает прежде всего клиентский жизненный цикл запроса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему для <code>FormData</code> не ставят <code>Content-Type</code> вручную?</strong></summary>

<dl>
<dd>
<h2></h2>

Браузер формирует multipart-тело из нескольких частей и создаёт уникальный разделитель.

Затем он добавляет разделитель в заголовок:

```http
Content-Type: multipart/form-data; boundary=...
```

Если вручную указать только `multipart/form-data`, значение `boundary` может отсутствовать или не совпасть с телом. Сервер тогда не сможет правильно разделить поля и файлы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли устанавливать и читать любые HTTP-заголовки?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Часть request headers управляется браузером и недоступна скрипту. Например, JavaScript не может напрямую установить `Host`, `Content-Length` или `Cookie`.

При `mode: "no-cors"` список разрешённых методов и заголовков ограничивается ещё сильнее.

Для cross-origin-ответа JavaScript по умолчанию видит только CORS-safelisted response headers. Чтобы открыть дополнительный заголовок, например `X-Request-Id`, сервер должен вернуть:

```http
Access-Control-Expose-Headers: X-Request-Id
```

`Set-Cookie` является специальным запрещённым для чтения response header. Браузер может сохранить cookie, но JavaScript не получит её значение через `response.headers`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>credentials: "same-origin"</code> отличается от <code>"include"</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`same-origin` является значением по умолчанию и использует автоматические учётные данные только при полном совпадении схемы, хоста и порта.

`include` разрешает использовать их и для cross-origin-запроса. После этого всё равно применяются CORS, атрибуты cookie и ограничения браузера на third-party cookies.

Для credentialed CORS-запроса сервер должен вернуть конкретный разрешённый origin и `Access-Control-Allow-Credentials: true`.

Явно добавленный приложением Bearer-токен в `Authorization` управляется через `headers`, а не используется как причина автоматически выбирать `include`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>mode: "no-cors"</code> не решает ошибку CORS?</strong></summary>

<dl>
<dd>
<h2></h2>

Режим разрешает отправить только ограниченный запрос, но скрывает ответ от JavaScript.

У opaque response значение `status` равно `0`, `ok` равно `false`, заголовки недоступны, а тело нельзя прочитать. Поэтому приложение не сможет получить JSON или определить реальный HTTP-статус.

Такой режим подходит отдельным сценариям загрузки ресурсов и Service Worker, но не обычному API. Разрешение доступа настраивают на сервере или reverse proxy, то есть обратном прокси.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как не показать устаревший результат поиска?</strong></summary>

<dl>
<dd>
<h2></h2>

Предыдущий запрос отменяют при изменении строки поиска, но одной отмены недостаточно.

Запрос мог завершиться до вызова `abort()`, а некоторые источники данных могут не поддерживать `AbortSignal`. Поэтому ответ дополнительно связывают с текущим параметром, query key или идентификатором попытки.

Интерфейс применяет данные только в том случае, если они всё ещё относятся к актуальному запросу. Библиотеки серверного состояния обычно выполняют такую проверку на уровне ключа запроса и состояния подписки.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что учесть |
| --- | --- |
| API вернул `422` | Проверить `ok`, разобрать Problem Details и ошибки полей |
| Автодополнение | Отменить предыдущий запрос и проверить актуальность результата |
| Загрузка файла | Использовать `FormData`, не задавать `boundary` вручную |
| Аутентификация через cookie между origin | `credentials: "include"`, CORS и атрибуты cookie |
| Эффект React | Отмена в функции очистки и отсутствие лишней ошибки в интерфейсе |
| Долгий запрос | Ограничение времени через `AbortSignal` и понятное состояние интерфейса |
| Потоковый ответ | Читать `response.body`, не вызывать `json()` заранее |
