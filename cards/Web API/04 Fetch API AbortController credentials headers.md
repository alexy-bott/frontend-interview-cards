#### Вопрос

Как работает Fetch API? Что нужно учитывать при обработке ответа, отмене запроса, заголовках и `credentials`?

#### Ответ

Fetch API является браузерным интерфейсом для сетевых запросов. `fetch(url, options)` возвращает Promise с объектом `Response`. Promise выполняется после получения статуса и заголовков, но тело ответа читается отдельно и может продолжать поступать как поток данных.

`fetch` не считает `404` или `500` ошибкой самого сетевого запроса. Ответ получен, поэтому Promise выполняется, а `response.ok` имеет значение `false`. Отклонение Promise происходит, если запрос нельзя завершить на уровне Fetch: например, из-за сетевой ошибки, блокировки CORS или отмены.

```ts
async function getUser(id: string, signal: AbortSignal) {
  const response = await fetch(`/api/users/${id}`, {
    headers: { Accept: "application/json" },
    credentials: "same-origin",
    signal,
  });

  if (!response.ok) {
    throw await toApiError(response);
  }

  if (response.status === 204) {
    return undefined;
  }

  return response.json();
}
```

Тело `Response` можно прочитать через `json()`, `text()`, `blob()`, `arrayBuffer()` или поток `body`. Обычно его читают один раз: после этого `bodyUsed` становится `true`. Если один ответ нужен двум обработчикам, его заранее клонируют через `response.clone()`, учитывая дополнительное буферизование данных.

Заголовки `Content-Type` и `Accept` решают разные задачи. `Content-Type` описывает формат отправляемого тела, а `Accept` сообщает, какие форматы ответа клиент готов принять. Для JSON тело сериализуют через `JSON.stringify` и указывают `Content-Type: application/json`. Для `FormData` заголовок `Content-Type` вручную обычно не ставят: браузер сам добавляет `multipart/form-data` с уникальным `boundary`, то есть разделителем частей.

`AbortController` позволяет сообщить Fetch API, что результат больше не нужен:

```ts
const controller = new AbortController();

fetch("/api/search?q=react", { signal: controller.signal });
controller.abort();
```

Отмена полезна при смене страницы, новом запросе автодополнения и очистке эффекта React. Она освобождает клиентские ресурсы и не позволяет устаревшему ответу обновить интерфейс. Однако отмена на клиенте не гарантирует откат операции на сервере: сервер мог уже получить запрос и продолжить обработку. Поэтому опасные операции всё равно требуют идемпотентности или ключа идемпотентности.

У `fetch` нет отдельного параметра `timeout`. Ограничение времени реализуют через `AbortSignal.timeout(ms)` в поддерживаемых окружениях либо через `AbortController` и таймер. Истечение времени означает, что клиент перестал ждать ответ, а не что сервер отменил работу.

Параметр `credentials` управляет учётными данными: отправкой cookies, клиентских TLS-сертификатов и HTTP-аутентификации, а также тем, будет ли браузер учитывать `Set-Cookie` из ответа:

| Значение | Поведение |
| --- | --- |
| `omit` | Не использовать учётные данные |
| `same-origin` | Использовать только для запросов к тому же origin; значение по умолчанию |
| `include` | Использовать и для запроса к другому origin при выполнении правил CORS и cookie |

`credentials: "include"` само по себе не гарантирует отправку cookie. Cookie должна подходить по `Domain`, `Path`, `Secure`, `SameSite` и политике браузера, а сервер обязан вернуть совместимые CORS-заголовки. Режим `no-cors` не исправляет CORS: JavaScript получает opaque response, то есть непрозрачный ответ без доступных статуса, заголовков и тела.

В приложении Fetch API обычно закрывает общий API-слой. Он задаёт базовый URL, добавляет авторизацию, безопасно разбирает успешные ответы и ошибки, связывает отмену с жизненным циклом запроса и ограничивает повторные попытки. При этом обёртка должна сохранять важные различия между `401`, `403`, `422`, отменой и сетевой ошибкой, а не превращать их в одну строку «что-то пошло не так».

#### Встречные вопросы

> [!followup]
> **Вопрос:** Что означает `response.ok`?
>
> **Ответ:** Это логическое значение, равное `true` для статусов от `200` до `299`. Оно не проверяет схему JSON и не гарантирует, что бизнес-операция успешна по внутренним правилам API. Для `404` или `500` объект `Response` существует, но `ok` равен `false`.

> [!followup]
> **Вопрос:** Почему тело ответа читается отдельным вызовом?
>
> **Ответ:** Заголовки могут прийти раньше полного тела, а само тело может быть большим или потоковым. `response.json()` сначала читает поток целиком, затем разбирает JSON. Для потокового интерфейса можно работать с `response.body` по частям и обновлять UI по мере поступления данных.

> [!followup]
> **Вопрос:** Что произойдёт после `controller.abort()`?
>
> **Ответ:** Сигнал становится отменённым, а связанный `fetch` отклоняет Promise с причиной отмены. Обработчик должен отличать ожидаемую отмену от ошибки, чтобы не показывать лишнее всплывающее уведомление. Один сигнал можно передать нескольким связанным запросам и отменить их вместе.

> [!followup]
> **Вопрос:** Отменяет ли `AbortController` операцию на сервере?
>
> **Ответ:** Не гарантированно. Браузер прекращает ожидание и по возможности закрывает передачу, но сервер мог уже принять данные, записать заказ или запустить задачу. Для изменения данных нужны серверная дедупликация, транзакции и идемпотентность; AbortController решает прежде всего клиентский жизненный цикл.

> [!followup]
> **Вопрос:** Почему для `FormData` не ставят `Content-Type` вручную?
>
> **Ответ:** Браузер формирует multipart-тело из нескольких частей и добавляет к `Content-Type` параметр `boundary`, совпадающий с разделителями внутри тела. При ручном значении `multipart/form-data` этот параметр легко потерять, и сервер не сможет разделить поля и файлы.

> [!followup]
> **Вопрос:** Чем `credentials: "same-origin"` отличается от `"include"`?
>
> **Ответ:** `same-origin` является значением по умолчанию и использует учётные данные только при совпадении origin. `include` разрешает их и для запроса к другому origin, но затем применяются CORS, атрибуты cookie и ограничения браузера. Для публичного API без cookie обычно оставляют значение по умолчанию или используют `omit` осознанно.

> [!followup]
> **Вопрос:** Почему `mode: "no-cors"` не решает ошибку CORS?
>
> **Ответ:** Режим разрешает отправить ограниченный запрос, но скрывает ответ от JavaScript. У opaque response, то есть непрозрачного ответа, недоступны содержательные статус, заголовки и тело. Такой режим подходит отдельным загрузкам ресурсов, но не чтению JSON API. Разрешение доступа настраивают на сервере или reverse proxy, то есть обратном прокси.

> [!followup]
> **Вопрос:** Как не показать устаревший результат поиска?
>
> **Ответ:** Предыдущий запрос отменяют при изменении строки и дополнительно связывают ответ с текущим параметром или идентификатором попытки. Это важно, потому что отмена может произойти поздно, а некоторые источники данных не поддерживают её полностью. Библиотеки серверного состояния обычно делают такую проверку на уровне ключа запроса (query key).

#### Где это встречается во frontend

| Ситуация | Что учесть |
| --- | --- |
| API вернул `422` | Проверить `ok`, разобрать Problem Details и ошибки полей |
| Автодополнение | Отменить предыдущий запрос и проверить актуальность результата |
| Загрузка файла | Использовать `FormData`, не задавать `boundary` вручную |
| Аутентификация через cookie между origin | `credentials: "include"`, CORS и атрибуты cookie |
| Эффект React | Отмена в функции очистки и отсутствие лишней ошибки в интерфейсе |
| Долгий запрос | Ограничение времени через `AbortSignal` и понятное состояние интерфейса |
| Потоковый ответ | Читать `response.body`, не вызывать `json()` заранее |
