## Вопрос

Что такое WebSocket? Как устроены подключение, обмен сообщениями, авторизация и восстановление после разрыва?

<details>
<summary><strong>Показать ответ</strong></summary>

WebSocket является протоколом и браузерным API для постоянного двустороннего соединения между клиентом и сервером. После установки соединения обе стороны могут отправлять сообщения без нового HTTP-запроса для каждого события. Это подходит для чатов, совместного редактирования, presence, то есть отображения присутствия пользователей, торговых данных и интерактивных обновлений с малой задержкой.

В браузере соединение создают через `new WebSocket(url, protocols)`. Его жизненный цикл отражают состояния `CONNECTING`, `OPEN`, `CLOSING`, `CLOSED` и события `open`, `message`, `error`, `close`:

```ts
const socket = new WebSocket("wss://api.example.com/realtime");

socket.addEventListener("open", () => {
  socket.send(JSON.stringify({ type: "subscribe", channel: "orders" }));
});

socket.addEventListener("message", (event) => {
  const message = JSON.parse(event.data);
  handleMessage(message);
});
```

В распространённом случае подключение начинается с opening handshake, то есть начального HTTP/1.1-рукопожатия. Клиент отправляет заголовки `Upgrade: websocket` и `Connection: Upgrade`, а сервер подтверждает переход статусом `101 Switching Protocols`. Затем соединение передаёт WebSocket frames, то есть кадры протокола. Браузер скрывает формирование рукопожатия и сборку кадров за объектом `WebSocket`.

`ws://` является незашифрованным соединением, а `wss://` использует TLS. Страница, открытая по HTTPS, должна подключаться через `wss`, иначе браузер обычно заблокирует mixed content, то есть смешивание защищённого и незащищённого содержимого. TLS защищает канал, но не заменяет аутентификацию, авторизацию сообщений и проверку входных данных.

WebSocket сохраняет порядок сообщений внутри одного соединения, потому что обычно работает поверх TCP. Но приложение не должно считать поток полным навсегда. После переподключения часть событий могла быть пропущена, сервер мог повторить последнее событие, а сообщения из нескольких источников могут отражать разные версии данных. Для важных обновлений используют `eventId`, номер версии или sequence number, то есть порядковый номер события, идемпотентные обработчики и удаление дублей.

Восстановление состоит не только в повторном `new WebSocket`. Обычно клиент:

1. Отличает намеренное закрытие от сетевого сбоя.
2. Повторяет подключение с exponential backoff и jitter: постепенно увеличивает задержку и добавляет случайный разброс, чтобы множество клиентов не подключались одновременно.
3. Учитывает `online`/`offline`, скрытие вкладки и максимальное число частых попыток.
4. Повторно проходит аутентификацию и восстанавливает подписки.
5. Передаёт последний `eventId` для replay, то есть повторной выдачи пропущенных событий, либо заново запрашивает актуальный снимок данных по HTTP.
6. Только после синхронизации применяет новые события.

Авторизация зависит от сервера. Браузерный конструктор `WebSocket` не позволяет произвольно задать заголовок `Authorization`. Частые варианты: HttpOnly cookie в начальном рукопожатии, короткоживущий одноразовый токен в URL, согласованный subprotocol, то есть подпротокол приложения, или первое сообщение аутентификации после открытия. Токен в параметре URL может попасть в логи прокси и мониторинга, поэтому долгоживущие секреты так передавать нельзя.

CORS не управляет WebSocket так же, как `fetch`. Браузер отправляет заголовок `Origin`, и сервер должен проверить его, особенно при аутентификации через cookie. Иначе вредоносный сайт может открыть WebSocket от имени вошедшего пользователя. После подключения сервер проверяет право на каждый канал и тип сообщения, а не доверяет однажды открытому соединению.

Для обнаружения разорванного, но формально не закрытого соединения используют heartbeat, то есть периодическую проверку связи. В протоколе есть служебные кадры Ping/Pong, однако браузерный JavaScript не может отправлять их напрямую: этим управляют браузер и сервер. Если приложению нужен собственный контроль, стороны обмениваются обычными сообщениями `ping`/`pong` или сервер периодически присылает ожидаемое событие и закрывает неактивные соединения.

У классического браузерного `WebSocket` нет автоматического backpressure, то есть механизма замедления отправителя, для входящих сообщений. Если сервер отправляет быстрее, чем интерфейс обрабатывает, растут очередь, память и нагрузка на главный поток. Помогают серверное ограничение частоты, агрегация, выборочное сохранение событий, пакетная обработка и уменьшение частоты рендера. Для исходящих данных проверяют `socket.bufferedAmount`: большое значение показывает, что данные накапливаются до отправки.

WebSocket обычно дополняет HTTP, а не заменяет его. Начальный снимок данных и обычные CRUD-операции удобно выполнять через REST/RTK Query, а WebSocket использовать для последующих событий. После разрыва повторный HTTP-запрос возвращает клиент к согласованному состоянию, даже если сервер не умеет повторно выдавать пропущенные события.

При выходе из системы, смене пользователя или размонтировании владельца соединения нужно удалить обработчики, остановить таймеры, отменить запланированное переподключение и закрыть WebSocket с подходящим кодом закрытия. Иначе старое соединение продолжит получать данные и создавать дубли подписок.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Что происходит во время WebSocket handshake, то есть начального рукопожатия?</summary>

В HTTP/1.1 клиент отправляет запрос с предложением перейти на WebSocket, ключом проверки и при необходимости списком подпротоколов. Сервер проверяет URL, origin и аутентификацию, затем отвечает `101 Switching Protocols` с вычисленным `Sec-WebSocket-Accept`. После этого по соединению передаются кадры WebSocket, а не обычные HTTP-запросы и ответы.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему не использовать WebSocket для всего API?</summary>

HTTP уже предоставляет методы, статусы, кеширование, условные запросы, стандартную диагностику и OpenAPI-инструменты. Поверх WebSocket пришлось бы самостоятельно определить идентификаторы запросов, ответы, ошибки, тайм-ауты, повторы, версии схемы и права на каждое сообщение. Для обычного CRUD это часто сложнее без практической выгоды.

</details>

<details>
<summary><strong>Вопрос:</strong> Как авторизовать WebSocket в браузере?</summary>

Можно использовать cookie, короткоживущий одноразовый токен, подпротокол или первое сообщение аутентификации. Выбор согласуют с серверной командой и настройкой прокси. Сервер проверяет `Origin`, срок и область действия учётной информации, а затем права на подписки. Долгоживущий токен в URL опасен из-за логов и утечек адреса.

</details>

<details>
<summary><strong>Вопрос:</strong> Применяется ли CORS к WebSocket?</summary>

Не как к Fetch API: WebSocket handshake не использует обычную CORS preflight-модель и `Access-Control-Allow-Origin`. Браузер всё же отправляет `Origin`. Сервер обязан проверить его сам, особенно если cookie прикладывается автоматически, иначе возможен Cross-Site WebSocket Hijacking.

</details>

<details>
<summary><strong>Вопрос:</strong> Как правильно делать reconnect?</summary>

Использовать увеличивающуюся задержку со случайным разбросом, ограничить частые попытки, не переподключаться после намеренного выхода и учитывать состояние сети. После открытия нужно заново пройти аутентификацию, восстановить подписки и синхронизировать данные: запросить пропущенные события или заново загрузить актуальное состояние.

</details>

<details>
<summary><strong>Вопрос:</strong> Гарантирован ли порядок сообщений?</summary>

Внутри одного соединения кадры доставляются по порядку. Но после reconnect, между несколькими каналами или источниками и при повторной доставке бизнес-события могут быть пропущены, продублированы или устареть. Поэтому данные снабжают идентификаторами и версиями, а обработчики делают идемпотентными.

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое backpressure?</summary>

Это способность получателя замедлить отправителя, когда он не успевает обрабатывать поток. Классический браузерный WebSocket не регулирует входящий поток автоматически. Приложение ограничивает частоту на сервере, объединяет события и следит, чтобы обработка не перегружала память и главный поток.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем протокольные Ping/Pong отличаются от heartbeat приложения?</summary>

Ping и Pong являются служебными кадрами WebSocket. Браузер отвечает на них внутри реализации, не передавая управление JavaScript. Heartbeat приложения является обычным сообщением согласованного формата и нужен, если frontend должен сам проверять доступность соединения, измерять задержку или соблюдать собственный тайм-аут.

</details>

## Где это встречается во frontend

| Сценарий | Что учесть |
| --- | --- |
| Чат | Идентификаторы, подтверждение отправки, порядок и пропущенные сообщения |
| Уведомления | Начальный HTTP-снимок, события и удаление дублей |
| Обновляемый dashboard | Агрегация, backpressure и ограничение рендера |
| Совместное редактирование | Версии, конфликты и присутствие пользователей |
| Кеш RTK Query | `onCacheEntryAdded`, обновление данных и повторный запрос |
| Истечение сессии | Повторная аутентификация или закрытие соединения |
| Выход из системы | Закрытие WebSocket и отмена переподключения |
