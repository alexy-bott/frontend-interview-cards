## Вопрос

<br>

 💬 **Что такое WebSocket? Как устроены подключение, обмен сообщениями, авторизация и восстановление после разрыва?**

<h2></h2>

<br>
<dl>
<dd>

WebSocket — протокол постоянного двустороннего обмена сообщениями между клиентом и сервером. Браузерный интерфейс `WebSocket` позволяет открыть такое соединение и работать с ним из JavaScript.

После установки соединения обе стороны могут независимо отправлять сообщения без нового HTTP-запроса для каждого события. Это подходит для чатов, совместного редактирования, presence, то есть отображения присутствия пользователей, торговых данных и интерактивных обновлений с малой задержкой.

WebSocket предоставляет транспорт сообщений, но не готовую модель запросов и ответов. Приложение самостоятельно определяет типы сообщений, формат ошибок, подтверждения, версии схемы, подписки и правила повторной доставки.

В браузере соединение создают через `new WebSocket(url, protocols)`. Его жизненный цикл отражают состояния `CONNECTING`, `OPEN`, `CLOSING`, `CLOSED` и события `open`, `message`, `error`, `close`:

```ts
const socket = new WebSocket("wss://api.example.com/realtime");

socket.addEventListener("open", () => {
  socket.send(JSON.stringify({ type: "subscribe", channel: "orders" }));
});

socket.addEventListener("message", (event) => {
  const message = JSON.parse(event.data);
  handleMessage(message);
});
```

Сообщение можно отправлять только после перехода соединения в состояние `OPEN`.

Если вызвать `send()` в состоянии `CONNECTING`, браузер выбросит ошибку. В состояниях `CLOSING` и `CLOSED` отправляемые данные будут отброшены. Поэтому общий транспорт проверяет `readyState` и явно определяет, что делать с сообщением: поставить его в прикладную очередь, отклонить операцию или дождаться нового соединения.

В классическом случае подключение начинается с opening handshake, то есть начального рукопожатия через HTTP/1.1. Клиент отправляет заголовки `Upgrade: websocket` и `Connection: Upgrade`, а сервер подтверждает переход статусом `101 Switching Protocols`.

WebSocket также может устанавливаться поверх HTTP/2 и HTTP/3 через механизм Extended CONNECT, если его поддерживают браузер, сервер и промежуточная инфраструктура. Браузерный объект `WebSocket` скрывает конкретный способ установки соединения.

После рукопожатия стороны обмениваются WebSocket frames, то есть кадрами протокола. Браузер самостоятельно формирует и собирает кадры, а JavaScript обычно работает с целыми текстовыми или бинарными сообщениями.

`ws://` обозначает незашифрованное соединение, а `wss://` использует TLS. Страница, открытая по HTTPS, должна подключаться через `wss`, иначе браузер обычно блокирует mixed content, то есть смешивание защищённого и незащищённого содержимого.

TLS обеспечивает конфиденциальность и целостность канала, а также проверку сервера по сертификату. Он не заменяет аутентификацию пользователя, авторизацию действий и проверку данных сообщений.

Текстовое сообщение приходит в `event.data` как строка. Для бинарных сообщений результат зависит от `socket.binaryType`: браузер может вернуть `Blob` или `ArrayBuffer`.

Прикладной протокол обычно определяет конверт сообщения с полями вроде:

- `type` — тип события или команды;
- `version` — версия схемы сообщения;
- `id` или `eventId` — идентификатор события;
- `requestId` — связь команды с ответом;
- `channel` — подписка или логический поток;
- `payload` — полезные данные;
- `error` — стабильный машинный формат ошибки.

Полученное сообщение является внешними данными. Недостаточно выполнить `JSON.parse`: нужно обработать ошибку разбора, проверить тип сообщения, обязательные поля, допустимые значения и размер данных.

Неизвестный тип или новую версию сообщения нельзя безусловно передавать в бизнес-логику. В зависимости от контракта клиент игнорирует совместимое неизвестное событие, сообщает об ошибке протокола или закрывает соединение.

Сервер также проверяет каждое клиентское сообщение, ограничивает размер и частоту, повторно выполняет авторизацию конкретного действия и не доверяет данным только потому, что соединение уже открыто.

WebSocket сохраняет порядок сообщений внутри одного соединения. Если клиент получил сообщения `A`, `B` и `C` через одну последовательность WebSocket, они не должны самопроизвольно поменяться местами.

Но порядок внутри соединения не означает гарантию exactly-once, то есть доставки каждого бизнес-события ровно один раз.

После разрыва:

- часть событий могла не дойти до клиента;
- последнее событие могло быть обработано, но подтверждение потерялось;
- сервер может повторно отправить уже полученное событие;
- запись может измениться в другом источнике;
- разные каналы могут относиться к разным версиям данных.

Для важных обновлений используют `eventId`, sequence number, то есть порядковый номер, или версию сущности. Обработчики делают идемпотентными и удаляют повторы по устойчивому идентификатору.

Если клиент отправляет команды, для них отдельно определяют подтверждение:

```text
client command → server acknowledgement
```

Отсутствие подтверждения не доказывает, что сервер не выполнил команду. Для платежей, создания заказов и других критичных операций нужна серверная идемпотентность, а не только повторная отправка сообщения после reconnect.

Восстановление состоит не только в повторном вызове `new WebSocket`. Обычно клиент:

1. Отличает намеренное закрытие от неожиданного разрыва.
2. Анализирует событие `close`, его `code`, `reason` и `wasClean`.
3. Решает, разрешено ли переподключение для этой причины.
4. Использует exponential backoff и jitter: постепенно увеличивает задержку и добавляет случайный разброс.
5. Повторно проходит аутентификацию.
6. Восстанавливает подписки.
7. Передаёт последний подтверждённый `eventId` для replay или запрашивает актуальный снимок по HTTP.
8. Согласует снимок с новыми событиями.
9. Сбрасывает счётчик задержки только после достаточно стабильной работы соединения.

Событие `error` обычно не содержит подробной причины сбоя, а после неудачной попытки подключения или ошибки возникает событие `close`. Поэтому переподключение обычно планируют в одном месте — в обработчике `close`, чтобы не создать два параллельных reconnect-таймера.

Состояния браузера `online` и `offline` можно использовать как подсказки, но они не доказывают доступность конкретного WebSocket-сервера. Значение `online` может означать только наличие некоторого сетевого подключения.

Не следует бесконечно переподключаться после любой причины закрытия. Например:

- нормальное закрытие при logout не требует reconnect;
- ошибка политики или авторизации требует сначала изменить учётные данные или права;
- временный сетевой сбой обычно допускает повтор;
- отсутствие поддержки протокола не исправится частыми попытками.

После открытия нового соединения сначала восстанавливают аутентификацию и подписки, а затем считают клиент синхронизированным.

Если сервер поддерживает replay, клиент передаёт последний подтверждённый идентификатор. Сервер возвращает пропущенные события, после чего продолжает обычный поток.

Если replay отсутствует или период хранения событий закончился, клиент заново получает актуальный снимок по HTTP. Новые события, пришедшие во время загрузки снимка, нужно либо временно буферизовать, либо согласовать по версии, чтобы старый HTTP-ответ не затёр более свежие данные.

Авторизация WebSocket зависит от серверного контракта. Браузерный конструктор `WebSocket` не позволяет произвольно установить заголовок `Authorization`.

Основные варианты:

- HttpOnly cookie, которую браузер автоматически отправляет при рукопожатии;
- короткоживущий одноразовый токен в URL;
- первое сообщение аутентификации после открытия;
- серверный BFF или получение отдельного одноразового WebSocket ticket.

Токен в URL может попасть в access logs, историю диагностики, мониторинг или конфигурацию прокси. Поэтому туда нельзя помещать долгоживущий access или refresh token. Если применяется URL-токен, он должен быть короткоживущим, одноразовым, ограниченным конкретным назначением и скрытым из логов.

Если аутентификация выполняется первым сообщением, соединение уже установлено до проверки пользователя. Сервер до завершения аутентификации должен:

- запрещать остальные типы сообщений;
- устанавливать короткий тайм-аут;
- ограничивать объём данных;
- закрывать соединение после ошибки;
- не создавать подписки и не выдавать защищённые данные.

`Sec-WebSocket-Protocol` предназначен прежде всего для согласования прикладного подпротокола, например версии формата сообщений. Некоторые системы используют его для передачи учётной информации из-за ограничений браузерного API, но это нестандартное соглашение приложения, а не полноценный аналог заголовка `Authorization`.

Подпротокол может быть виден промежуточной инфраструктуре и должен соответствовать синтаксису заголовка. Долгоживущий секрет не следует передавать таким способом без отдельного анализа угроз.

CORS не управляет WebSocket так же, как `fetch`: обычная модель preflight и `Access-Control-Allow-Origin` здесь не используется.

Браузер всё же отправляет при рукопожатии заголовок `Origin`. Сервер должен проверять его по точному allowlist, особенно если аутентификация основана на автоматически отправляемой cookie.

Без проверки `Origin` вредоносный сайт может попытаться открыть WebSocket к приложению от имени уже вошедшего пользователя. Такой сценарий называют Cross-Site WebSocket Hijacking.

`Origin` не является самостоятельной аутентификацией. Небраузерный клиент может сформировать произвольное значение, поэтому сервер всё равно проверяет сессию или токен.

После подключения сервер не должен считать пользователя авторизованным для любых действий. Право проверяют для каждого канала, команды и ресурса:

```text
открытое соединение ≠ разрешение на все сообщения
```

Долгоживущее соединение может пережить окончание сессии, отзыв токена, смену роли или logout. Сервер должен учитывать такие события и закрывать либо ограничивать активные соединения. Frontend после обновления учётной информации при необходимости открывает новое соединение и заново восстанавливает подписки.

Для обнаружения разорванного, но формально не закрытого соединения используют heartbeat, то есть периодическую проверку связи.

В протоколе WebSocket есть служебные кадры Ping и Pong. Браузерный JavaScript не может отправлять их напрямую: браузер обрабатывает такие кадры внутри реализации и автоматически отвечает Pong на серверный Ping.

Сервер может использовать протокольный Ping/Pong, чтобы обнаруживать неактивные соединения и не держать их бесконечно после сетевого разрыва.

Если frontend должен самостоятельно отслеживать задержку или время последнего ответа, прикладной протокол вводит обычные сообщения, например:

```text
{ "type": "heartbeat" }
{ "type": "heartbeat_ack" }
```

Это не протокольные кадры Ping/Pong, а обычные текстовые или бинарные сообщения приложения.

Heartbeat также помогает не потерять соединение из-за idle timeout на proxy, load balancer или gateway. Интервал должен быть согласован с инфраструктурой и не создавать избыточную нагрузку на тысячи соединений.

У классического браузерного `WebSocket` нет автоматического backpressure, то есть механизма замедления сервера, когда JavaScript не успевает обрабатывать входящие сообщения.

Если сервер отправляет быстрее, чем приложение обрабатывает данные:

- растёт потребление памяти;
- очередь событий увеличивается;
- главный поток перегружается;
- интерфейс перестаёт отвечать.

Проблему решают на уровне системы:

- ограничивают частоту на сервере;
- объединяют несколько обновлений;
- передают только последнее состояние;
- вводят подписки только на нужные данные;
- обрабатывают сообщения пакетами;
- уменьшают частоту рендера;
- закрывают соединение при превышении лимита.

Для исходящих данных свойство `socket.bufferedAmount` показывает число байтов, поставленных в очередь через `send()`, но ещё не переданных в сеть.

Большое значение означает, что клиент отправляет быстрее, чем данные уходят. Приложение задаёт собственный порог и решает, что делать: временно не отправлять, объединить некритичные обновления, отбросить устаревшее событие или закрыть перегруженное соединение.

`bufferedAmount` является показателем очереди, но не полноценным механизмом backpressure и не подтверждает, что сервер уже получил сообщение.

WebSocket обычно дополняет HTTP, а не заменяет его.

Начальный снимок данных и обычные CRUD-операции удобно выполнять через REST, RTK Query или другой HTTP API. WebSocket используется для последующих событий и быстрых изменений.

После разрыва повторный HTTP-запрос позволяет вернуть клиент к согласованному состоянию, даже если сервер не хранит историю событий для replay.

При выходе из системы, смене пользователя или уничтожении владельца соединения нужно:

- отметить закрытие как намеренное;
- отменить запланированный reconnect;
- остановить heartbeat и остальные таймеры;
- удалить обработчики;
- очистить очередь исходящих сообщений;
- закрыть WebSocket подходящим кодом;
- очистить связанные подписки и чувствительные данные.

Иначе старое соединение продолжит получать данные, а новый экземпляр создаст дубли обработчиков и подписок.

Открытый WebSocket также может помешать браузеру сохранить страницу в back/forward cache. Для обычного перехода со страницы соединение можно закрыть в `pagehide`, а при восстановлении страницы через `pageshow` открыть заново и синхронизировать состояние.

## Дополнительные вопросы

<details>
<summary><strong>Что происходит во время WebSocket handshake, то есть начального рукопожатия?</strong></summary>

<dl>
<dd>
<h2></h2>

В классическом варианте через HTTP/1.1 клиент отправляет запрос с предложением перейти на WebSocket, случайным ключом проверки и при необходимости списком подпротоколов.

Сервер проверяет URL, `Origin`, аутентификацию и поддерживаемые подпротоколы, затем отвечает `101 Switching Protocols` с вычисленным `Sec-WebSocket-Accept`.

После этого по соединению передаются кадры WebSocket, а не последовательность обычных HTTP-запросов и ответов.

При работе поверх HTTP/2 или HTTP/3 соединение может устанавливаться через Extended CONNECT без классической пары `Upgrade` и `101`. Для браузерного JavaScript это различие обычно незаметно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему не использовать WebSocket для всего API?</strong></summary>

<dl>
<dd>
<h2></h2>

HTTP уже предоставляет методы, статусы, кеширование, условные запросы, стандартную диагностику, прокси и OpenAPI-инструменты.

Поверх WebSocket пришлось бы самостоятельно определить:

- идентификаторы запросов и ответов;
- формат ошибок;
- тайм-ауты;
- отмену;
- идемпотентность;
- повторы;
- версии схемы;
- авторизацию каждого сообщения;
- восстановление после reconnect.

Для обычного CRUD это часто сложнее без практической выгоды. WebSocket полезнее там, где сервер должен быстро и регулярно отправлять события клиенту либо обе стороны активно обмениваются сообщениями.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как авторизовать WebSocket в браузере?</strong></summary>

<dl>
<dd>
<h2></h2>

Браузерный конструктор не позволяет произвольно установить `Authorization`.

Можно использовать:

- HttpOnly cookie в рукопожатии;
- короткоживущий одноразовый WebSocket ticket в URL;
- первое сообщение аутентификации;
- BFF, который управляет учётными данными на серверной стороне.

Сервер проверяет `Origin`, срок и назначение учётной информации, а затем отдельно проверяет права на каждую подписку и команду.

Долгоживущий токен в URL опасен из-за логов и утечек адреса. Если аутентификация выполняется первым сообщением, до её завершения сервер не должен принимать остальные действия или отправлять защищённые данные.

`Sec-WebSocket-Protocol` предназначен для выбора прикладного протокола. Передача токена через него является специальным соглашением конкретной системы и требует отдельного анализа безопасности.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Применяется ли CORS к WebSocket?</strong></summary>

<dl>
<dd>
<h2></h2>

Не так, как к Fetch API. WebSocket handshake не использует обычную CORS preflight-модель и заголовок `Access-Control-Allow-Origin`.

Браузер всё же отправляет `Origin`. Сервер обязан проверить его по allowlist, особенно если cookie прикладывается автоматически.

Иначе вредоносный сайт может открыть аутентифицированное соединение от имени пользователя. Такой сценарий называют Cross-Site WebSocket Hijacking.

`Origin` не заменяет аутентификацию, потому что небраузерный клиент может указать произвольное значение.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как правильно делать reconnect?</strong></summary>

<dl>
<dd>
<h2></h2>

Reconnect обычно запускают из одного обработчика `close`, а не одновременно из `error` и `close`.

Нужно:

1. Отличить намеренное закрытие от сбоя.
2. Проверить код и причину закрытия.
3. Использовать exponential backoff с jitter.
4. Ограничить частоту и число быстрых попыток.
5. Повторно пройти аутентификацию.
6. Восстановить подписки.
7. Запросить replay либо актуальный HTTP-снимок.
8. Согласовать снимок с новыми событиями.

После logout, ошибки политики или окончательно недействительной сессии автоматический reconnect прекращают. Счётчик backoff сбрасывают после стабильной работы, а не сразу после кратковременного события `open`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как использовать коды закрытия WebSocket?</strong></summary>

<dl>
<dd>
<h2></h2>

Событие `close` содержит:

- `code` — код закрытия;
- `reason` — дополнительную причину от сервера;
- `wasClean` — завершился ли closing handshake корректно.

Например:

- `1000` означает нормальное завершение;
- `1006` наблюдается клиентом при ненормальном разрыве и не передаётся как обычный close frame;
- `1008` обычно означает нарушение политики;
- `1011` означает неожиданную серверную ошибку;
- диапазон `4000–4999` можно использовать для приватных кодов приложения.

Политику reconnect нельзя строить только на `wasClean`: нормальное техническое закрытие может требовать нового подключения, а корректно переданная ошибка авторизации — наоборот, запрещать его.

Поле `reason` не считается безопасным пользовательским сообщением. Его используют для диагностики или машинной логики только по заранее согласованному контракту.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Гарантирован ли порядок сообщений?</strong></summary>

<dl>
<dd>
<h2></h2>

Внутри одного WebSocket-соединения сообщения доставляются приложению в порядке протокола.

Но это не гарантирует целостность всей истории после reconnect. Бизнес-события могут быть пропущены, повторены или уже устареть к моменту обработки.

Между несколькими соединениями, каналами или backend-источниками также нет общего порядка без отдельного sequence number или версии.

Поэтому сообщения снабжают идентификаторами и версиями, а обработчики делают идемпотентными.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Гарантирует ли WebSocket доставку exactly once?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. WebSocket передаёт упорядоченный поток сообщений в рамках текущего соединения, но не предоставляет прикладную гарантию доставки ровно один раз.

Соединение может разорваться в момент, когда сервер уже обработал сообщение, но клиент ещё не получил подтверждение. После reconnect клиент не знает, нужно ли повторять операцию.

Для важных команд используют:

- уникальный идентификатор операции;
- acknowledgement от сервера;
- серверную дедупликацию;
- идемпотентный обработчик;
- журнал событий или replay.

Подтверждение получения также не всегда означает завершение бизнес-операции. Протокол должен различать «сообщение принято» и «операция успешно выполнена».

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое backpressure?</strong></summary>

<dl>
<dd>
<h2></h2>

Backpressure — способность получателя замедлить отправителя, когда он не успевает обрабатывать поток.

Классический браузерный `WebSocket` не регулирует входящий поток автоматически. Если сообщений слишком много, растут очередь, память и нагрузка на главный поток.

Сервер ограничивает частоту, объединяет обновления и задаёт лимиты. Клиент обрабатывает события пакетами и уменьшает количество рендеров.

Для исходящих данных `bufferedAmount` показывает объём очереди до отправки. Это полезный сигнал перегрузки, но не подтверждение доставки и не полноценный механизм обратного давления.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем протокольные Ping/Pong отличаются от heartbeat приложения?</strong></summary>

<dl>
<dd>
<h2></h2>

Ping и Pong являются служебными кадрами WebSocket. Сервер может отправить Ping, а браузер отвечает Pong внутри реализации, не передавая этот обмен JavaScript-коду.

Браузерный JavaScript не может самостоятельно создать протокольный Ping frame.

Heartbeat приложения является обычным сообщением согласованного формата. Он нужен, если frontend должен сам отслеживать время последнего ответа, измерять задержку или отображать состояние соединения.

Прикладной heartbeat не следует отправлять слишком часто: тысячи активных клиентов могут создать значительную дополнительную нагрузку.

<h2></h2>
</dd>
</dl>

</details>
