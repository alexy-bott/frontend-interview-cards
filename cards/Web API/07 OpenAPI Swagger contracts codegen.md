## Вопрос

<br>

 💬 **Что такое OpenAPI и Swagger? Как frontend-команда использует контракт, генерацию кода и проверку совместимости?**

<h2></h2>

<br>
<dl>
<dd>

OpenAPI Specification является независимым от языка стандартом описания HTTP API. Документ в JSON или YAML перечисляет доступные операции, параметры, тела запросов, ответы, HTTP-статусы, схемы данных, способы аутентификации и примеры.

По такому документу человек или инструмент может понять интерфейс API без чтения серверного кода и ручного исследования сетевых запросов.

OpenAPI описывает контракт, но не является самим API. Реальный сервер может соответствовать документу, отставать от него или вести себя иначе.

Swagger и OpenAPI не являются полными синонимами.

OpenAPI называется сама спецификация, а Swagger — семейство инструментов вокруг неё:

- Swagger UI отображает интерактивную документацию;
- Swagger Editor помогает редактировать и проверять документ;
- Swagger Codegen генерирует клиентский и серверный код.

В разговоре страницу Swagger UI часто называют просто «Swagger», хотя её источником является OpenAPI-документ.

Основные элементы OpenAPI-документа:

| Элемент | Что описывает |
| --- | --- |
| `openapi` | Версию OpenAPI Specification, по которой нужно интерпретировать документ |
| `info` | Название, версию и общую информацию об API |
| `servers` | Базовые URL доступных окружений API |
| `paths` | URL и операции над ними |
| `parameters` | Параметры пути, query, заголовков и cookie на уровне пути или операции |
| `requestBody` | Тело запроса и поддерживаемые media type |
| `responses` | Статусы, заголовки и схемы ответов |
| `components.schemas` | Переиспользуемые схемы данных |
| `components.securitySchemes` | Cookie, bearer token, OAuth и другие схемы аутентификации |
| `security` | Требования аутентификации для всего API или отдельной операции |
| `operationId` | Уникальное стабильное имя операции для инструментов и codegen |

Переиспользуемые параметры также можно хранить в `components.parameters`, а затем подключать через `$ref`.

Поле `operationId` не является обязательным, но при наличии должно быть уникальным среди всех операций API. Генераторы часто используют его для имён TypeScript-функций, hooks и endpoints.

Поэтому переименование `operationId` может сломать frontend на уровне сгенерированного API-клиента, даже если HTTP-метод и URL остались прежними.

На август 2026 года последней опубликованной версией является OpenAPI 3.2.0. В проектах по-прежнему распространены версии 3.0 и 3.1.

Перед выбором синтаксиса нужно проверить поддержку версии во всей цепочке:

- Swagger UI;
- редакторе;
- генераторе клиента;
- gateway, то есть API-шлюзе;
- линтере;
- валидаторе;
- mock-сервере;
- инструменте сравнения контрактов.

Нельзя рассчитывать на возможность новой версии, если один из обязательных инструментов молча её игнорирует или интерпретирует иначе.

Особенно заметно различаются схемы OpenAPI 3.0 и 3.1+. В OpenAPI 3.1 и 3.2 Schema Object основан на JSON Schema Draft 2020-12. Например, допустимость `null` можно описывать как объединение типов:

```yaml
type:
  - string
  - "null"
```

В OpenAPI 3.0 для этого обычно использовалось:

```yaml
type: string
nullable: true
```

Генератор должен поддерживать именно ту версию схемы, которая указана в документе.

Контракт можно вести двумя способами:

- **Contract-first, или сначала контракт.** Сначала проектируют OpenAPI, затем по нему реализуют сервер и клиент.
- **Code-first, или сначала код.** Серверные типы, маршруты или аннотации используются для генерации OpenAPI из реализации.

Contract-first удобен для предварительного согласования и параллельной работы frontend и backend. Frontend может генерировать типы и использовать mock-сервер ещё до готовности реального API.

Code-first уменьшает ручное дублирование, но документ может содержать только те ограничения, которые серверный генератор умеет вывести из кода. Например, бизнес-условие или точный формат ошибки всё равно приходится описывать явно.

В обоих подходах опубликованный OpenAPI-документ должен соответствовать реально развёрнутой версии API. Важно определить один источник истины и не изменять независимо серверные типы, YAML-файл и сгенерированный клиент.

Для frontend из OpenAPI можно генерировать:

- TypeScript-типы запросов и ответов;
- функции API-клиента;
- endpoints и hooks RTK Query;
- mock-обработчики;
- документацию;
- часть runtime-схем валидации.

Конкретные возможности зависят от выбранного генератора и поддерживаемой им версии OpenAPI.

RTK Query предоставляет пакет `@rtk-query/codegen-openapi`, который генерирует endpoints из OpenAPI-схемы. При этом его документация относит codegen к ранним возможностям, поэтому особенно важно фиксировать версию пакета и проверять получившийся код.

Сгенерированный код является производным артефактом. В него не следует вручную добавлять бизнес-логику, сложные преобразования или настройки, которые исчезнут при следующей генерации.

Такие изменения размещают поверх генерации:

- в обёртке API-слоя;
- в mapper-функциях;
- через настройки генератора;
- через `endpointOverrides`;
- через `enhanceEndpoints` для тегов и поведения кеша RTK Query.

Codegen, то есть генерация кода, уменьшает ручное копирование DTO и позволяет обнаружить часть несовместимых изменений во время typecheck или сборки.

Генерация должна быть воспроизводимой:

1. Используется конкретная версия OpenAPI-документа.
2. Версия генератора фиксируется в зависимостях и lock-файле.
3. Конфигурация генератора хранится в репозитории.
4. Одна и та же команда выполняется локально и в CI.
5. Сгенерированный результат проходит форматирование, typecheck и тесты.

Результат либо коммитят и проверяют в diff, то есть списке изменений, либо генерируют в CI перед остальными проверками.

Если код коммитится, CI может повторить генерацию и проверить, что рабочее дерево осталось неизменным. Это обнаруживает ситуацию, когда контракт обновили, а производный клиент забыли перегенерировать.

DTO (Data Transfer Object), или объект передачи данных, описывает форму данных на границе API. DTO оптимизирован для передачи и сериализации, но не обязан совпадать с моделью интерфейса.

Например, сервер может вернуть:

- дату строкой;
- денежную сумму в минимальных единицах;
- поле с возможным `null`;
- технический статус;
- имена в формате `snake_case`.

Модель интерфейса может использовать:

- объект `Date` или заранее отформатированную строку;
- сумму в удобном представлении;
- явное состояние отсутствия;
- пользовательский статус;
- имена в формате проекта.

Преобразование DTO в модель приложения держат в API-слое или отдельном mapper, а не повторяют в компонентах.

Обязательность поля и возможность значения `null` — разные свойства.

Если поле не входит в `required`, оно может отсутствовать:

```ts
type UserDto = {
  middleName?: string;
};
```

Если схема разрешает `null`, поле может присутствовать со значением `null`:

```ts
type UserDto = {
  middleName: string | null;
};
```

Поле может одновременно быть необязательным и nullable:

```ts
type UserDto = {
  middleName?: string | null;
};
```

Эти состояния имеют разную семантику и не должны случайно объединяться генератором или ручным TypeScript-типом.

Аннотации `readOnly` и `writeOnly` помогают разделить направления данных. Например, серверный `id` может присутствовать только в ответе, а пароль — только в запросе. Однако конкретное поведение generated types зависит от инструмента, поэтому результат нужно проверить на реальном примере.

Сгенерированный TypeScript-тип существует только во время разработки и удаляется при компиляции. Он не проверяет JSON, который фактически пришёл по сети.

Выражение:

```ts
const user = (await response.json()) as UserDto;
```

не выполняет валидацию. Оно только сообщает TypeScript, что разработчик считает объект соответствующим `UserDto`.

Ответ может прийти:

- от старой версии сервера;
- из другого окружения;
- от proxy;
- от mock-сервера;
- из кеша;
- от внешнего сервиса;
- с нарушением заявленного контракта.

Для критичной или недоверенной границы используют runtime validation, то есть проверку данных во время выполнения, либо защитное преобразование с понятной ошибкой контракта.

Валидировать каждый ответ необязательно: это добавляет код и вычисления. Решение зависит от происхождения данных, критичности операции и надёжности server-side-проверок.

Contract drift, или расхождение контракта, означает, что OpenAPI, сгенерированный frontend-клиент и реальное поведение API описывают разные версии интерфейса.

Например:

- схема обещает обязательное поле, а сервер перестал его возвращать;
- сервер уже требует новый параметр, а опубликованный OpenAPI этого не показывает;
- frontend сгенерирован из development-контракта, а работает с более старым production API;
- mock-сервер возвращает данные, невозможные по реальному контракту.

Расхождение уменьшают несколькими независимыми проверками:

1. OpenAPI-документ проверяют линтером и валидатором.
2. CI сравнивает новую спецификацию с базовой версией.
3. Frontend генерирует клиент из той версии, которая будет развёрнута.
4. Сгенерированный клиент проходит typecheck и тесты.
5. Серверные тесты проверяют запросы и ответы по контракту.
6. Интеграционные или контрактные тесты вызывают реальный API.
7. Развёрнутая версия публикует доступный идентификатор или документ контракта.

Проверка самого OpenAPI-файла доказывает только корректность документа. Она не доказывает, что сервер возвращает описанные статусы и данные.

Swagger UI также отображает документ, а не проверяет каждый ответ реального сервера. Возможность выполнить запрос через кнопку `Try it out` полезна для ручной диагностики, но не заменяет автоматические проверки соответствия.

При поиске breaking changes важно учитывать направление передачи данных.

Для запроса обычно несовместимы:

- добавление нового обязательного параметра;
- запрет ранее допустимого значения;
- сужение типа;
- удаление принимаемого значения `enum`;
- изменение media type;
- изменение способа аутентификации.

Для ответа обычно несовместимы:

- удаление поля, на которое рассчитывает клиент;
- изменение типа поля;
- превращение обязательного поля в необязательное;
- разрешение `null`, если клиент его не обрабатывает;
- изменение структуры ошибки;
- удаление ожидаемого HTTP-статуса.

Добавление необязательного поля в ответ обычно совместимо для клиента, который игнорирует неизвестные данные. Но строгий runtime-валидатор с запретом дополнительных полей может посчитать такой ответ ошибочным.

Добавление нового значения `enum` в ответ формально расширяет контракт сервера, но может сломать frontend с исчерпывающим `switch`. Поэтому автоматический анализ спецификации не отменяет понимание того, как тип используется в приложении.

Изменение `operationId` может не затронуть сетевой контракт, но изменить имена generated functions и hooks. Для frontend это тоже является несовместимым изменением на уровне исходного кода.

OpenAPI описывает форму сообщений и значительную часть протокола, но не доказывает бизнес-семантику.

Спецификация может обещать `200` и правильный набор полей, а сервер при этом:

- вернуть устаревшие данные;
- неправильно рассчитать сумму;
- не проверить права;
- выполнить операцию дважды;
- нарушить порядок событий.

Поэтому OpenAPI, codegen и contract tests дополняют обычные тесты, авторизацию и production-мониторинг, а не заменяют их.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Чем OpenAPI отличается от Swagger?</strong></summary>

<dl>
<dd>
<h2></h2>

OpenAPI является спецификацией машиночитаемого контракта HTTP API.

Swagger является названием семейства инструментов вокруг OpenAPI. Например, Swagger UI визуализирует документ, Swagger Editor помогает его редактировать, а Swagger Codegen генерирует код.

Поэтому файл является OpenAPI-документом, а открытая в браузере интерактивная страница обычно является Swagger UI.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое DTO?</strong></summary>

<dl>
<dd>
<h2></h2>

DTO — это форма данных, передаваемая через границу системы. Она оптимизирована для контракта и сериализации, а не обязательно для интерфейса.

Например, `UserDto` может содержать дату строкой, сумму в копейках и поле `middleName: string | null`.

Frontend может преобразовать его в собственную модель, чтобы один раз обработать даты, единицы измерения, `null`, технические статусы и несовпадающие имена полей.

Такое преобразование выполняют на границе API, чтобы компоненты работали с удобной и стабильной моделью приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужен <code>operationId</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`operationId` задаёт уникальное имя операции внутри OpenAPI-документа.

Генератор может использовать его для создания:

- имени клиентской функции;
- RTK Query endpoint;
- React hook;
- имени метода SDK;
- ссылки между операциями.

Если `operationId` указан, он должен быть уникальным среди всех операций API.

Его переименование может изменить публичный интерфейс generated client, даже если URL и HTTP-метод не изменились. Поэтому `operationId` рассматривают как стабильную часть контракта для codegen.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем обязательное поле отличается от nullable-поля?</strong></summary>

<dl>
<dd>
<h2></h2>

Обязательность определяет, должно ли поле присутствовать в объекте. Nullable определяет, разрешено ли передать значение `null`.

Это разные случаи:

```ts
type Example = {
  requiredValue: string;
  nullableValue: string | null;
  optionalValue?: string;
  optionalNullableValue?: string | null;
};
```

В OpenAPI 3.0 допустимость `null` обычно описывается через `nullable: true`. В OpenAPI 3.1 и 3.2 используется синтаксис JSON Schema, например объединение `string` и `null`.

Неправильное описание этих свойств приводит к неверным generated types и ошибкам при обработке ответа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что можно генерировать из OpenAPI?</strong></summary>

<dl>
<dd>
<h2></h2>

Из OpenAPI можно генерировать:

- типы запросов и ответов;
- функции API-клиента;
- endpoints и hooks RTK Query;
- клиентские SDK;
- mock-обработчики;
- документацию;
- серверные заготовки;
- часть runtime-схем валидации.

Возможности и качество результата зависят от генератора и поддерживаемой версии OpenAPI.

Сгенерированный код проверяют как производную зависимость: фиксируют версию генератора, изучают diff и не добавляют внутрь файла ручную бизнес-логику, которая исчезнет при следующем запуске.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему сгенерированных TypeScript-типов недостаточно?</strong></summary>

<dl>
<dd>
<h2></h2>

TypeScript-типы удаляются при компиляции и не проверяют данные, пришедшие по сети.

Выражение `response.json() as UserDto` только заставляет TypeScript доверять указанному типу. Оно не проверяет наличие полей, значения `enum`, формат даты или допустимость `null`.

Если нарушение контракта может привести к повреждению данных, ошибке оплаты или падению важного интерфейса, ответ проверяют во время выполнения до передачи в остальное приложение.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое contract drift?</strong></summary>

<dl>
<dd>
<h2></h2>

Contract drift — это расхождение между опубликованной схемой, сгенерированным клиентом и реальным API.

Например, поле указано обязательным, но сервер перестал его возвращать. Другой вариант: development-контракт уже изменился, а production-сервер ещё работает по предыдущей версии.

Причинами бывают ручное обновление документации, разные версии окружений, устаревшие mocks и генерация клиента из непредназначенной для релиза схемы.

Проблему уменьшают сравнением спецификаций, серверной проверкой сообщений, контрактными тестами и генерацией frontend-клиента из версионированного артефакта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Гарантирует ли Swagger UI соответствие реального API контракту?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Swagger UI визуализирует переданный ему OpenAPI-документ.

Если документ устарел, страница покажет устаревший контракт. Возможность успешно выполнить несколько запросов через `Try it out` также не доказывает соответствие всех статусов, схем и граничных случаев.

Соответствие проверяют автоматическими server-side, интеграционными или контрактными тестами, которые сравнивают реальные запросы и ответы со спецификацией.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие изменения OpenAPI могут сломать frontend?</strong></summary>

<dl>
<dd>
<h2></h2>

Frontend могут сломать:

- удаление или переименование используемого поля;
- изменение типа;
- добавление обязательного параметра запроса;
- разрешение неожиданного `null`;
- изменение HTTP-статуса или media type;
- изменение формата ошибки;
- удаление значения `enum`;
- добавление значения `enum` в ответ для клиента с исчерпывающим `switch`;
- переименование `operationId`.

Совместимость зависит от направления данных. Расширение допустимых входных данных сервера обычно безопасно для старого клиента, а расширение вариантов ответа может потребовать изменений в frontend.

Автоматический diff помогает найти подозрительные изменения, но окончательное решение требует понимания реального использования контракта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что лучше: contract-first или code-first?</strong></summary>

<dl>
<dd>
<h2></h2>

Выбор зависит от процесса.

Contract-first полезен, когда frontend и backend должны начать работу параллельно и заранее согласовать публичный API. По контракту можно создать mock-сервер и generated client до готовности backend.

Code-first удобен, когда серверные маршруты и типы являются надёжным источником истины, а генератор точно отражает особенности используемого framework.

Критерий качества у подходов один: OpenAPI должен обновляться вместе с реализацией и соответствовать развёрнутому серверу.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли коммитить сгенерированный клиент?</strong></summary>

<dl>
<dd>
<h2></h2>

Оба подхода допустимы.

Коммит generated client:

- позволяет использовать проект без локального запуска генератора;
- делает изменение публичного клиентского API видимым в pull request;
- упрощает публикацию пакета;
- создаёт большой производный diff.

Генерация только в CI:

- уменьшает шум в репозитории;
- требует доступного версионированного контракта;
- требует запуска генератора до typecheck и тестов;
- усложняет просмотр изменения generated API до выполнения pipeline.

В обоих случаях локально и в CI должны использоваться одинаковые версии контракта, генератора и конфигурации.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Задача | Как помогает OpenAPI |
| --- | --- |
| Типизировать API | Генерация типов запросов и ответов |
| Создать API-клиент | Генерация функций или endpoints RTK Query |
| Обработать форму | Схема `422` и ошибки отдельных полей |
| Разрабатывать без готового сервера | Mock-сервер по контракту |
| Обнаружить несовместимое изменение | Сравнение спецификаций в CI |
| Защитить границу приложения | Проверка внешнего ответа во время выполнения |
| Развести DTO и модель интерфейса | Преобразование в API-слое |
