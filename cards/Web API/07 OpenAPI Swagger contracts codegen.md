## Вопрос

Что такое OpenAPI и Swagger? Как frontend-команда использует контракт, генерацию кода и проверку совместимости?

<details>
<summary><strong>Показать ответ</strong></summary>

OpenAPI Specification является независимым от языка стандартом описания HTTP API. Документ в JSON или YAML перечисляет пути, методы, параметры, тело запроса, ответы, HTTP-статусы, схемы данных, способы аутентификации и примеры. По нему человек или инструмент может понять возможности API без чтения серверного кода.

Swagger и OpenAPI не являются полными синонимами. OpenAPI называется сама спецификация, а Swagger является семейством инструментов: Swagger UI показывает интерактивную документацию, Swagger Editor редактирует документ, Swagger Codegen генерирует код. В разговоре страницу документации часто называют «Swagger».

Основные части OpenAPI-документа:

| Раздел | Что описывает |
| --- | --- |
| `paths` | URL и операции над ними |
| `parameters` | Параметры пути, строки запроса, заголовков и cookie |
| `requestBody` | Тело запроса и его формат данных (`media type`) |
| `responses` | Статусы, заголовки и схемы ответов |
| `components.schemas` | Переиспользуемые модели данных |
| `securitySchemes` | Cookie, bearer token, OAuth и другие схемы аутентификации |
| `operationId` | Стабильное имя операции для инструментов и генерации кода |

На июль 2026 года последней опубликованной версией является OpenAPI 3.2.0. В проектах по-прежнему распространены 3.0 и 3.1, поэтому перед выбором синтаксиса нужно проверить поддержку версии в Swagger UI, генераторе клиента, gateway, то есть API-шлюзе, и валидаторах. Нельзя использовать возможность новой версии, если остальная цепочка её молча игнорирует.

Контракт можно вести двумя способами:

- **Contract-first, или сначала контракт.** Сначала проектируют OpenAPI, затем по нему реализуют сервер и клиент.
- **Code-first, или сначала код.** Серверные аннотации или типы генерируют OpenAPI из реализации.

Contract-first удобен для параллельной разработки и предварительного согласования. Code-first уменьшает ручное дублирование, но документация может описывать только то, что генератор смог вывести из кода. В обоих случаях опубликованный документ должен соответствовать реально развёрнутой версии API.

Для frontend из OpenAPI генерируют TypeScript-типы, функции API-клиента, endpoints RTK Query, обработчики mock-сервера и иногда схемы валидации. Codegen, то есть генерация кода, уменьшает ручное копирование DTO и обнаруживает несовместимые изменения на этапе сборки. Генератор должен запускаться воспроизводимо, его версия фиксируется, а результат либо коммитится и проверяется в diff, то есть списке изменений, либо создаётся в CI до проверки типов.

DTO (Data Transfer Object), или объект передачи данных, описывает форму данных на границе API. DTO не обязан быть моделью интерфейса. Например, сервер может вернуть дату строкой, денежную сумму в минимальных единицах и nullable-поля, то есть поля, допускающие `null`. Модель интерфейса при этом будет содержать `Date`, отформатированную сумму и явное состояние отсутствия. Такое преобразование держат в API-слое, а не размазывают по компонентам.

Сгенерированный TypeScript-тип существует только во время разработки и не проверяет реальный JSON. Ответ может прийти от старой версии сервера, прокси, mock-сервера или внешнего сервиса. Для критичной границы используют runtime validation, то есть проверку данных во время выполнения, либо защитное преобразование с понятной ошибкой контракта.

Contract drift, или расхождение контракта, означает рассинхронизацию спецификации и поведения сервера. Его уменьшают следующими проверками:

1. Сервер проверяет запросы и ответы по схеме или генерирует схему из единого источника.
2. CI сравнивает OpenAPI с базовой версией и отмечает несовместимые изменения (`breaking changes`).
3. Frontend генерирует клиент из той версии контракта, которая будет развёрнута.
4. Контрактные тесты проверяют реальные примеры взаимодействия.
5. Изменения `enum`, обязательности, допустимости `null`, формата и ошибок проходят отдельное ревью.

OpenAPI описывает форму и протокол, но не доказывает бизнес-семантику. Спецификация может обещать `200` и правильные поля, а сервер вернуть устаревшие данные или неверно проверить права доступа. Поэтому генерация кода дополняет тесты и мониторинг, а не заменяет их.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Чем OpenAPI отличается от Swagger?</summary>

OpenAPI является спецификацией формата контракта. Swagger является названием набора инструментов вокруг неё. Swagger UI отображает OpenAPI, но сама интерактивная страница не является источником семантики отдельно от документа.

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое DTO?</summary>

Это форма данных, передаваемая через границу системы. Она оптимизирована для контракта и сериализации, а не обязательно для интерфейса. Frontend может преобразовать `UserDto` в собственную модель, чтобы один раз обработать даты, поля с `null`, единицы измерения и несовпадающие имена.

</details>

<details>
<summary><strong>Вопрос:</strong> Что можно генерировать из OpenAPI?</summary>

Типы запросов и ответов, функции клиента, endpoints RTK Query, обработчики mock-сервера, документацию и часть схем валидации. Возможности зависят от генератора и версии OpenAPI. Сгенерированный код проверяют как любую зависимость: фиксируют версию, смотрят список изменений и не помещают в него бизнес-логику вручную.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему сгенерированных TypeScript-типов недостаточно?</summary>

Типы удаляются при компиляции и не проверяют байты, пришедшие по сети. Выражение `response.json() as UserDto` только обещает компилятору форму объекта. Если нарушение контракта опасно, данные валидируют во время выполнения до передачи в остальное приложение.

</details>

<details>
<summary><strong>Вопрос:</strong> Что такое contract drift?</summary>

Это расхождение между опубликованной схемой, сгенерированными типами и реальным API. Например, поле указано обязательным, но сервер перестал его возвращать. Причиной бывает ручное обновление документации, разные версии окружений или mock-сервер, который не следует контракту.

</details>

<details>
<summary><strong>Вопрос:</strong> Какие изменения OpenAPI могут сломать frontend?</summary>

Удаление или переименование поля, изменение типа, добавление нового обязательного параметра, удаление значения `enum`, запрет `null`, изменение HTTP-статуса или формата данных. Даже добавление значения `enum` может сломать клиент с исчерпывающим `switch`, поэтому автоматический анализ совместимости не отменяет понимание того, как контракт используется в коде.

</details>

<details>
<summary><strong>Вопрос:</strong> Что лучше: contract-first или code-first?</summary>

Выбор зависит от процесса. Contract-first полезен, когда команды должны начать параллельно и заранее согласовать публичный API. Code-first удобен, когда серверные типы являются надёжным источником и генерация точно отражает используемый framework. Критерий качества один: документ должен обновляться вместе с кодом и соответствовать развёрнутому серверу.

</details>

<details>
<summary><strong>Вопрос:</strong> Нужно ли коммитить сгенерированный клиент?</summary>

Оба подхода допустимы. Коммит упрощает использование без локального генератора и делает изменения видимыми в pull request, но создаёт большой производный список изменений. Генерация в CI уменьшает шум, но требует доступного и версионированного контракта. Нельзя допускать, чтобы локально и в CI использовались разные версии генератора.

</details>

## Где это встречается во frontend

| Задача | Как помогает OpenAPI |
| --- | --- |
| Типизировать API | Генерация типов запросов и ответов |
| Создать API-клиент | Генерация функций или endpoints RTK Query |
| Обработать форму | Схема `422` и ошибки отдельных полей |
| Разрабатывать без готового сервера | Mock-сервер по контракту |
| Обнаружить несовместимое изменение | Сравнение спецификаций в CI |
| Защитить границу приложения | Проверка внешнего ответа во время выполнения |
| Развести DTO и модель интерфейса | Преобразование в API-слое |
