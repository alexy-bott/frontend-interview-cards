## Вопрос

Чем отличаются основные HTTP-методы? Что означают свойства safe, idempotent и cacheable?

<details>
<summary><strong>Показать ответ</strong></summary>

HTTP-метод задаёт стандартный смысл запроса. Сервер может реализовать любой адрес API как угодно, но нарушение семантики метода ломает ожидания браузеров, кешей, промежуточных серверов и клиентов.

| Метод | Назначение | Safe, безопасный | Idempotent, идемпотентный | Типичное кеширование |
| --- | --- | --- | --- | --- |
| `GET` | Получить представление ресурса | Да | Да | Часто |
| `HEAD` | Получить заголовки ответа без тела | Да | Да | Как у `GET` |
| `OPTIONS` | Узнать возможности сервера или выполнить предварительную проверку CORS (preflight) | Да | Да | Редко, preflight кешируется отдельно |
| `POST` | Передать данные ресурсу, создать подчинённый ресурс или запустить операцию | Нет | Обычно нет | Возможно при явных правилах, но редко |
| `PUT` | Создать или полностью заменить ресурс по известному URL | Нет | Да | Обычно нет |
| `PATCH` | Частично изменить ресурс | Нет | Не гарантируется | Обычно нет |
| `DELETE` | Удалить связь с ресурсом | Нет | Да | Нет |

Safe, или безопасный, метод не просит изменить состояние ресурса. `GET`, `HEAD` и `OPTIONS` являются безопасными. Сервер всё равно может записать лог, обновить метрику или начислить стоимость запроса, но клиент не должен ожидать бизнес-изменения. Поэтому удаление через `GET /delete-user/42` опасно: ссылку может открыть поисковый робот, механизм предварительной загрузки или кеширующий компонент.

Idempotent, или идемпотентный, метод при нескольких одинаковых запросах должен иметь тот же предполагаемый итоговый эффект, что и при одном. Повторный `PUT` с одним телом оставляет ресурс в одном состоянии, а повторный `DELETE` оставляет ресурс удалённым. Ответы при этом могут различаться: первый `DELETE` вернёт `204`, второй `404`, но итоговое состояние одинаково.

`POST` обычно не идемпотентен: два запроса могут создать два заказа или два платежа. Для критичной операции клиент передаёт idempotency key, то есть уникальный ключ попытки. Сервер хранит результат по ключу и при повторе того же запроса возвращает прежний результат вместо создания новой операции. Ключ работает только при серверной поддержке; блокировка кнопки в интерфейсе не защищает от повтора сетью или другим клиентом.

`PUT` и `PATCH` различаются не размером тела, а семантикой. `PUT /users/42` передаёт полное желаемое представление ресурса и может затереть пропущенные поля согласно контракту. `PATCH` передаёт набор частичных изменений, например JSON Merge Patch или JSON Patch. Операция `replace` может быть идемпотентной, а команда «увеличить счётчик на один» нет, поэтому сам метод `PATCH` не считается идемпотентным.

Cacheable, или кешируемый, означает, что ответ разрешено сохранять и повторно использовать по правилам HTTP-кеша. На практике чаще всего кешируют `GET` и `HEAD`. Ответ на `POST` также может быть кешируемым при явной информации о свежести, но такая схема поддерживается не всеми кешами и встречается редко. Одного имени метода недостаточно: важны `Cache-Control`, валидаторы `ETag`/`Last-Modified`, заголовок `Vary`, наличие авторизации и правила конкретного кеша.

Свойства метода влияют на повторные попытки (`retry`). Клиент может осторожно повторить идемпотентный запрос после сетевого сбоя, но должен учитывать причину ошибки, лимиты и задержку. Неидемпотентный `POST` нельзя автоматически повторять без idempotency key, то есть уникального ключа одной бизнес-операции, или другого способа устранить дубли.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Чем <code>PUT</code> отличается от <code>PATCH</code>?</summary>

`PUT` передаёт полное желаемое состояние ресурса по известному URL. `PATCH` описывает частичное изменение. Если API принимает неполный объект через `PUT` и сохраняет остальные поля, это допустимая реализация только при явно описанном контракте, но она расходится с обычным ожиданием замены и может запутать клиентов.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему <code>DELETE</code> идемпотентен, если второй ответ может быть <code>404</code>?</summary>

Идемпотентность относится к предполагаемому эффекту на сервере, а не к побитовому равенству ответов. После первого и второго запроса ресурс отсутствует. Статус может измениться, потому что второй запрос наблюдает уже изменённое состояние.

</details>

<details>
<summary><strong>Вопрос:</strong> Может ли <code>PATCH</code> быть идемпотентным?</summary>

Конкретный PATCH-запрос может быть идемпотентным. Установка `status = "done"` повторяется безопасно, а операция `increment views by 1` каждый раз меняет результат. HTTP не гарантирует идемпотентность `PATCH`, поэтому клиент не должен предполагать её без контракта API.

</details>

<details>
<summary><strong>Вопрос:</strong> Как работает idempotency key для <code>POST</code>?</summary>

Клиент создаёт уникальный ключ для одной бизнес-попытки и отправляет его с запросом. Сервер связывает ключ, параметры и результат операции. Повтор с тем же ключом и теми же данными получает прежний результат, а повтор с другим телом должен быть отклонён. Сервер также определяет область ключа и срок его хранения.

</details>

<details>
<summary><strong>Вопрос:</strong> Можно ли передавать тело в <code>GET</code>?</summary>

HTTP не определяет общепринятую семантику тела `GET`, а некоторые реализации и посредники его игнорируют или отклоняют. Браузерный Fetch API не разрешает тело у `GET` и `HEAD`. Параметры чтения обычно передают в URL, а сложный поиск иногда моделируют отдельным `POST`-адресом API.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему нельзя автоматически повторять любой запрос после <code>503</code>?</summary>

Сервер мог выполнить операцию, а ответ потерялся. Повтор неидемпотентного `POST` тогда создаст дубль. Нужно учитывать семантику метода, idempotency key, `Retry-After`, число попыток и exponential backoff, то есть постепенное увеличение задержки между попытками.

</details>

<details>
<summary><strong>Вопрос:</strong> Означает ли safe, что запрос не имеет никаких побочных эффектов?</summary>

Нет. Логи, метрики, кеширование и учёт стоимости самого запроса допустимы. Safe означает, что клиент не просил изменить состояние целевого ресурса и не должен отвечать за такое изменение. Действие вроде отправки письма или удаления записи нельзя прятать в `GET`.

</details>

## Где это встречается во frontend

| Сценарий | Что учитывать |
| --- | --- |
| Повтор загрузки списка | `GET` идемпотентен, но число попыток ограничивают |
| Создание платежа | `POST` и ключ идемпотентности |
| Сохранение всей формы | Контракт полного `PUT` |
| Изменение одного поля | `PATCH` и семантика операции |
| Удаление записи | Повторный `DELETE` может вернуть другой статус |
| Предварительная загрузка ссылки | `GET` не должен выполнять опасное действие |
| Кеш запроса | Метод, `Cache-Control`, `Vary` и валидаторы |
