## Вопрос

<br>

 💬 **Какие HTTP-статусы важно знать frontend-разработчику? Как построить обработку ошибок API?**

<h2></h2>

<br>
<dl>
<dd>

HTTP-статус сообщает общий результат запроса на уровне протокола. Класс `2xx` означает успешную обработку, `3xx` — перенаправление или работу с кешированным представлением, `4xx` — невозможность выполнить запрос в текущем виде, а `5xx` — ошибку сервера или промежуточной инфраструктуры.

Статус не заменяет тело ошибки. Код статуса сообщает общую семантику браузеру, кешам, прокси и клиентским библиотекам, а тело передаёт детали, необходимые конкретному приложению.

На frontend чаще всего встречаются следующие статусы:

| Статус | Смысл и типичная реакция |
| --- | --- |
| `200 OK` | Операция выполнена, тело зависит от метода и контракта |
| `201 Created` | Ресурс создан; ответ обычно содержит его представление или заголовок `Location` |
| `202 Accepted` | Запрос принят, но обработка ещё не завершена и может завершиться неуспешно |
| `204 No Content` | Операция выполнена, дополнительного тела ответа нет |
| `304 Not Modified` | Условный `GET` или `HEAD` подтвердил актуальность кешированного представления |
| `400 Bad Request` | Сервер считает запрос некорректным и не может обработать его в текущем виде |
| `401 Unauthorized` | Нет действительных данных аутентификации |
| `403 Forbidden` | Сервер понял запрос, но отказывается выполнять его |
| `404 Not Found` | Ресурс не найден либо сервер не раскрывает его существование |
| `405 Method Not Allowed` | Ресурс существует, но не поддерживает использованный HTTP-метод |
| `409 Conflict` | Операция конфликтует с текущим состоянием ресурса |
| `412 Precondition Failed` | Не выполнено условие `If-Match` или другого условного запроса |
| `413 Content Too Large` | Тело запроса превышает допустимый сервером размер |
| `415 Unsupported Media Type` | Сервер не поддерживает присланный `Content-Type` |
| `422 Unprocessable Content` | Тип и синтаксис данных понятны, но содержащиеся инструкции невозможно выполнить |
| `429 Too Many Requests` | Превышен лимит запросов; нужно учитывать `Retry-After`, если он передан |
| `500 Internal Server Error` | Непредвиденная ошибка серверного приложения |
| `502 Bad Gateway` | Прокси или API-шлюз получил некорректный ответ от следующего сервиса |
| `503 Service Unavailable` | Сервис временно недоступен, перегружен или находится на обслуживании |
| `504 Gateway Timeout` | Шлюз не дождался ответа следующего сервиса |

`202 Accepted` не означает, что экспорт, платёж или другая долгая операция уже выполнена. Запрос только принят на обработку и в итоге может завершиться успешно, завершиться ошибкой или вообще не быть выполнен.

Хороший контракт возвращает идентификатор или URL ресурса операции и способ узнать её состояние: периодический опрос, Server-Sent Events, WebSocket или другой realtime-канал.

`204 No Content` не содержит тела ответа. Заголовки при этом могут присутствовать, например новый `ETag`. Безусловный вызов `response.json()` для такого ответа завершится ошибкой разбора пустого содержимого.

`304 Not Modified` относится к условному `GET` или `HEAD` и не содержит обычного представления ресурса. Как правило, браузерный HTTP-кеш сам объединяет метаданные ответа `304` с ранее сохранённым телом, поэтому прикладной код получает уже восстановленный результат.

`401` и `403` требуют разного поведения.

`401` означает, что запрос не содержит действительных данных аутентификации. Такой ответ должен сопровождаться заголовком `WWW-Authenticate` с описанием применимой схемы аутентификации.

Если используемый контракт поддерживает refresh token, клиент может один раз обновить access token и повторить исходный запрос. Если обновление не удалось, пользователя переводят к повторному входу. Несколько одновременных `401` не должны запускать множество параллельных refresh-запросов.

`403` означает, что сервер понял запрос, но отказывается его выполнять. Повтор с теми же данными и теми же правами обычно бессмысленен. Интерфейс показывает отсутствие доступа или объясняет, какое условие нужно выполнить.

Сервер всё равно проверяет права при каждом запросе. Скрытая или заблокированная кнопка в интерфейсе не является механизмом авторизации.

`404` может означать как реальное отсутствие ресурса, так и отказ сервера раскрывать его существование. Поэтому frontend не всегда способен по одному статусу отличить «такого ресурса нет» от «у пользователя нет права знать о нём».

`405 Method Not Allowed` означает, что целевой ресурс известен, но не поддерживает использованный метод. Например, endpoint принимает `GET`, но получил `POST`. Сервер должен передать заголовок `Allow` со списком поддерживаемых методов.

`413 Content Too Large` особенно важен при загрузке файлов. Frontend может проверить размер заранее для удобства пользователя, но окончательное ограничение всё равно применяет сервер.

`409 Conflict` подходит для конфликта с текущим состоянием ресурса или бизнес-правилом. Например, выбранный слот уже забронирован, имя занято или переход заказа в новое состояние больше не разрешён.

Для optimistic concurrency, то есть защиты от перезаписи более новой версии, сервер может вернуть `ETag`, а клиент — передать его в `If-Match`. Если версия изменилась, условие становится ложным и сервер возвращает `412 Precondition Failed`. Тогда интерфейс предлагает загрузить свежие данные, повторить редактирование или вручную разрешить конфликт.

`415 Unsupported Media Type` относится к формату тела запроса. Например, endpoint ожидает JSON, а клиент отправил данные с неподдерживаемым `Content-Type`.

`422 Unprocessable Content` означает, что сервер понимает тип и синтаксис тела, но не может выполнить содержащиеся в нём инструкции. В API этот статус часто используют для семантической или бизнес-валидации формы.

Граница между `400` и `422` является частью контракта API. Важно не выбрать единственно возможную классификацию, а применять выбранное правило последовательно во всех endpoint.

У ответа об ошибке должен быть стабильный машинный формат. Стандарт Problem Details использует media type `application/problem+json` и основные поля:

- `type` — URI, идентифицирующий класс проблемы;
- `title` — краткое стабильное название класса проблемы;
- `status` — вспомогательная копия HTTP-статуса;
- `detail` — человекочитаемое описание конкретного случая;
- `instance` — URI, идентифицирующий конкретное возникновение проблемы.

API может добавлять собственные поля, например `errors` для ошибок формы и `requestId` для поиска события в логах.

```json
{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Данные не прошли проверку",
  "status": 422,
  "errors": [
    { "field": "email", "code": "already_exists" }
  ],
  "requestId": "req-8f1c"
}
```

Клиент принимает программные решения по реальному HTTP-статусу, стабильному `type` или отдельному машинному коду расширения. Поле `detail` предназначено для человека и не должно разбираться строковыми условиями.

Поле `status` внутри Problem Details является вспомогательным. Сервер должен согласовать его с реальным HTTP-статусом, но общие HTTP-механизмы и клиентский API-слой в первую очередь ориентируются на статус самого ответа.

В клиентском API-слое полезно различать четыре группы сбоев:

1. **Сетевая ошибка или недоступный ответ.** JavaScript не получил доступный HTTP-ответ из-за сети, DNS, TLS, некорректного URL или блокировки CORS.
2. **Отмена.** Запрос отменён через `AbortController` и обычно не требует сообщения об ошибке пользователю.
3. **HTTP-ошибка.** Ответ получен, но его статус находится вне диапазона `2xx`.
4. **Ошибка разбора или контракта.** Статус мог быть успешным, но тело пустое, повреждено, имеет неожиданный `Content-Type` или не соответствует ожидаемой схеме.

При CORS-ошибке сервер мог сформировать HTTP-ответ, но браузер не предоставляет его JavaScript-коду. Поэтому frontend обычно не видит реальный статус и получает такую же категорию ошибки, как при некоторых сетевых сбоях.

Fetch API не отклоняет Promise только из-за `404`, `422` или `500`. Если браузер получил доступный HTTP-ответ, Promise выполняется со значением `Response`.

Нужно проверить `response.ok`, которое равно `true` только для статусов `200–299`, затем безопасно разобрать тело с учётом статуса и `Content-Type`.

Нельзя предполагать, что любой успешный или ошибочный ответ обязательно содержит JSON. Ответ может быть пустым, содержать `application/problem+json`, обычный JSON, текст или HTML от reverse proxy.

После разбора API-слой преобразует результат в единый тип приложения. Компоненты не должны самостоятельно в разных местах проверять `status`, разбирать случайный JSON и определять вид ошибки по строке сообщения.

Автоматические повторные попытки обычно рассматривают для временных сетевых сбоев, `429`, `502`, `503` и `504`. При этом учитывают:

- safe- и idempotent-свойства метода;
- наличие idempotency key;
- возможность повторно отправить тело запроса;
- заголовок `Retry-After`;
- ограничение числа попыток;
- exponential backoff и случайный разброс задержки.

Сетевая ошибка не доказывает, что сервер не выполнил операцию: запрос мог дойти до сервера, а ответ — потеряться. Поэтому неидемпотентный `POST` нельзя автоматически повторять без серверной защиты от дублей.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем <code>401</code> отличается от <code>403</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`401` означает, что запрос не содержит действительных данных аутентификации. Ответ должен сопровождаться `WWW-Authenticate`, описывающим применимую схему аутентификации.

В API с access token клиент может один раз попытаться обновить токен и повторить запрос. Если обновление не удалось, требуется повторный вход.

`403` означает, что сервер понял запрос, но отказывается его выполнять. Повтор с теми же правами обычно ничего не изменит, поэтому интерфейс показывает отсутствие доступа.

Сервер может вернуть `404` вместо `403`, если не хочет раскрывать существование защищённого ресурса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>400</code> отличается от <code>422</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`400` является общим статусом некорректного запроса. Его можно использовать, когда сломан JSON, отсутствует обязательная часть запроса или нарушен общий контракт endpoint.

`422` означает, что сервер понимает тип и синтаксис тела, но не может выполнить содержащиеся в нём инструкции. Например, email уже занят или дата окончания находится раньше даты начала.

Конкретная граница является частью контракта API. Важно применять выбранное правило последовательно и возвращать frontend стабильные машинные коды ошибок.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда использовать <code>409</code>, а когда <code>412</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`409` описывает конфликт операции с текущим состоянием ресурса или бизнес-правилом. Например, слот уже забронирован или заказ больше нельзя отменить.

`412` означает, что не выполнилось условие, которое клиент явно передал в HTTP-заголовке: например, `If-Match` содержит устаревший `ETag`.

Для контроля конкурентного редактирования через HTTP-предусловия точнее использовать `412`. Для конфликтов без такого условия подходит `409`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что важно помнить про <code>204 No Content</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

У ответа нет тела, поэтому нельзя безусловно вызывать `response.json()`.

Заголовки при этом могут содержать полезные метаданные, например новый `ETag`.

API-слой должен заранее определить результат такого ответа: вернуть `undefined`, использовать данные исходного запроса или после изменения заново получить ресурс.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>fetch</code> не попал в <code>catch</code> при <code>500</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Запрос получил доступный HTTP-ответ, поэтому Promise выполнился со значением `Response`. Для `500` у него будет `response.ok === false`.

`catch` срабатывает при ошибках другого уровня: например, сетевом сбое, некорректной схеме URL, блокировке CORS, отмене запроса или ошибке разбора тела, если она произошла внутри `try`.

Поэтому после `fetch` нужно отдельно проверить `response.ok` или `response.status` и преобразовать неуспешный ответ в ошибку приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как безопасно разобрать тело ответа с ошибкой?</strong></summary>

<dl>
<dd>
<h2></h2>

Нельзя безусловно вызывать `response.json()`: ответ может быть пустым, содержать обычный текст или HTML от прокси.

Сначала учитывают статус и заголовок `Content-Type`. JSON обычно ожидают для `application/json`, `application/problem+json` и других media type с суффиксом `+json`.

Тело `Response` читается только один раз. API-слой может сначала получить текст, проверить, пуст ли он, и затем попытаться разобрать JSON, если формат это предполагает.

Если объявленный JSON повреждён или структура не соответствует контракту, это отдельная ошибка разбора или контракта. Пользователю показывают безопасное общее сообщение, а технические детали и `requestId` отправляют в мониторинг.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое Problem Details?</strong></summary>

<dl>
<dd>
<h2></h2>

Это стандарт RFC 9457 для машинно читаемого описания ошибок HTTP API. JSON-представление использует media type `application/problem+json`.

`type` является основным идентификатором класса проблемы. `title` кратко называет этот класс, `detail` описывает конкретный случай, `instance` идентифицирует возникновение проблемы, а `status` вспомогательно повторяет HTTP-статус.

Проект может добавлять собственные поля, например список ошибок валидации. Клиент должен игнорировать неизвестные расширения, чтобы формат мог развиваться без поломки старых версий приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему нельзя показывать пользователю любое сообщение сервера?</strong></summary>

<dl>
<dd>
<h2></h2>

Сообщение может содержать стек вызовов, имя таблицы, внутренний путь, SQL-запрос или другую чувствительную информацию.

Сервер должен возвращать безопасное описание и стабильный машинный код. Frontend может локализовать пользовательский текст по коду, а `requestId` показать для обращения в поддержку.

Неизвестную серверную ошибку лучше преобразовать в нейтральное сообщение, а исходные технические данные отправить в защищённую систему мониторинга.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие ошибки можно повторять автоматически?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычно рассматривают временные сетевые ошибки, `429`, `502`, `503` и `504`, если конкретную операцию безопасно повторить.

Нужно учитывать идемпотентность метода, наличие idempotency key, возможность повторно отправить то же тело, `Retry-After`, ограничение числа попыток, exponential backoff и случайный разброс задержки.

`400`, `403`, `404` и ошибки валидации без изменения запроса повтором обычно не исправляются.

Сетевой сбой не означает, что сервер точно не выполнил запрос. Поэтому неидемпотентные операции нельзя автоматически повторять без защиты от дублей.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Реакция интерфейса |
| --- | --- |
| `202` после запуска экспорта | Показать прогресс и получать состояние задачи |
| `401` | Один refresh, затем вход при неудаче |
| `403` | Показать отсутствие доступа |
| `404` | Экран «не найдено» или пустое состояние по контракту |
| `412` | Обновить данные и разрешить конфликт версии |
| `422` | Сопоставить ошибки с полями формы |
| `429` | Уважать `Retry-After` и ограничить повтор |
| `503` | Показать временную недоступность и предложить повтор |
