## Вопрос

<br>

 💬 **Какие HTTP-статусы важно знать frontend-разработчику? Как построить обработку ошибок API?**

<h2></h2>

<br>
<dl>
<dd>

HTTP-статус сообщает общий результат запроса на уровне протокола. Класс `2xx` означает успешную обработку, `3xx` перенаправление или работу кеша, `4xx` проблему с запросом или доступом клиента, а `5xx` ошибку сервера либо промежуточной инфраструктуры. Статус не заменяет тело ошибки: код помогает общим HTTP-инструментам, а тело передаёт детали для приложения.

На frontend чаще всего встречаются следующие статусы:

| Статус | Смысл и типичная реакция |
| --- | --- |
| `200 OK` | Операция выполнена, тело зависит от метода |
| `201 Created` | Ресурс создан; ответ может содержать представление и `Location` |
| `202 Accepted` | Задача принята, но ещё не завершена; нужен статус операции, периодический опрос или realtime-канал |
| `204 No Content` | Операция выполнена без тела ответа |
| `304 Not Modified` | Кешированное представление всё ещё актуально; браузер объединяет его с кешем |
| `400 Bad Request` | Запрос нельзя обработать из-за синтаксиса или общего нарушения контракта |
| `401 Unauthorized` | Нет действительных данных аутентификации; часто нужно обновить сессию или войти заново |
| `403 Forbidden` | Запрос распознан, но действие запрещено политикой доступа |
| `404 Not Found` | Ресурс не найден или сервер не раскрывает его существование |
| `409 Conflict` | Операция конфликтует с текущим состоянием ресурса |
| `412 Precondition Failed` | Не выполнено условие `If-Match` или другого условного запроса |
| `415 Unsupported Media Type` | Сервер не поддерживает присланный `Content-Type` |
| `422 Unprocessable Content` | Формат понятен, но данные не проходят семантическую или бизнес-валидацию |
| `429 Too Many Requests` | Превышен лимит; нужно учитывать `Retry-After` |
| `500 Internal Server Error` | Непредвиденная ошибка приложения на сервере |
| `502 Bad Gateway` | Прокси или API-шлюз получил некорректный ответ от следующего сервиса |
| `503 Service Unavailable` | Сервис временно недоступен или перегружен |
| `504 Gateway Timeout` | Шлюз не дождался ответа следующего сервиса |

`202` не означает, что экспорт, платёж или другая долгая задача уже выполнена. Хороший контракт возвращает идентификатор операции и способ узнать её состояние. `204` не содержит тела, поэтому безусловный `response.json()` завершится ошибкой. `304` обычно обрабатывает HTTP-кеш браузера, а не прикладной код.

`401` и `403` требуют разного поведения. При `401` клиент может один раз обновить access token, то есть токен доступа, и повторить исходный запрос. При `403` повтор с теми же правами бессмысленен: нужно показать отсутствие доступа. Сервер всё равно проверяет права на каждый запрос, даже если интерфейс скрывает запрещённую кнопку.

`409` подходит для конфликта с текущим состоянием, например повторного бронирования уже занятого слота. Для optimistic concurrency, то есть защиты от перезаписи более новой версии, сервер может вернуть `ETag`, клиент отправить `If-Match`, а несовпадение привести к `412`. Тогда интерфейс предлагает загрузить свежие данные или вручную разрешить конфликт.

У ответа об ошибке должен быть стабильный машинный формат. Стандарт Problem Details использует тип данных `application/problem+json` и поля `type`, `title`, `status`, `detail`, `instance`. API может добавить `errors` для полей формы и `requestId` для поиска события в логах. Клиент принимает решение по стабильному `type` или коду ошибки, а не разбирает человекочитаемый `detail` строковыми условиями.

```json
{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Данные не прошли проверку",
  "status": 422,
  "errors": [
    { "field": "email", "code": "already_exists" }
  ],
  "requestId": "req-8f1c"
}
```

В клиентском API-слое полезно различать четыре группы сбоев:

1. **Сетевая ошибка (network error).** Ответ не получен из-за сети, DNS, TLS или блокировки CORS.
2. **Отмена (abort).** Запрос отменён и часто не требует сообщения пользователю.
3. **HTTP-ошибка.** Ответ получен с неуспешным статусом.
4. **Ошибка разбора или контракта.** Статус мог быть успешным, но тело повреждено или не соответствует ожидаемой схеме.

Fetch API не отклоняет Promise только из-за `404` или `500`: это полученный HTTP-ответ. Нужно проверить `response.ok`, безопасно разобрать тело с учётом `Content-Type` и преобразовать ошибку в единый тип приложения. Автоматические повторные попытки обычно оставляют для временных сетевых ошибок, `429`, `502`, `503` и `504`, учитывая идемпотентность операции и `Retry-After`.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем <code>401</code> отличается от <code>403</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`401` означает отсутствие подходящих данных аутентификации и по стандартной схеме сопровождается `WWW-Authenticate`. На практике это может быть истёкший токен доступа. Для `401` можно один раз обновить токен или попросить пользователя войти, а при `403` обычно показывают запрет без бессмысленного повтора.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>400</code> отличается от <code>422</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`400` используют, когда запрос в целом некорректен: сломан JSON, отсутствует обязательная часть протокола или нарушен общий контракт. `422` означает, что тип данных и синтаксис понятны, но инструкции невозможно выполнить, например поле имеет недопустимое значение. Конкретная граница является частью контракта API и должна применяться последовательно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда использовать <code>409</code>, а когда <code>412</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`409` описывает общий конфликт с текущим состоянием ресурса или бизнес-правилом. `412` относится к явно переданному условию HTTP, например `If-Match` с устаревшим ETag. Для контроля конкурентного редактирования `412` точнее, а `409` подходит для конфликтов без такого условия.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что важно помнить про <code>204 No Content</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

У ответа нет тела. Нельзя безусловно вызывать `response.json()`. API-слой должен проверить статус или наличие содержимого и вернуть `undefined`, заранее известный результат либо обновить состояние по данным исходного запроса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>fetch</code> не попал в <code>catch</code> при <code>500</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Запрос успешно дошёл до сервера и получил корректный HTTP-ответ, поэтому Promise выполнился со значением `Response`. У него `response.ok === false`. `catch` срабатывает, когда ответ нельзя получить, запрос отменён или Fetch API завершился ошибкой другого уровня.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое Problem Details?</strong></summary>

<dl>
<dd>
<h2></h2>

Это стандарт RFC 9457 для машинно читаемого описания ошибок HTTP API. Поле `type` идентифицирует класс проблемы, `title` кратко его называет, `detail` объясняет конкретный случай, `instance` идентифицирует случай, а `status` дублирует HTTP-статус для удобства. Проект может добавлять собственные поля, например список ошибок валидации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему нельзя показывать пользователю любое сообщение сервера?</strong></summary>

<dl>
<dd>
<h2></h2>

Оно может содержать стек вызовов, имя таблицы, внутренний идентификатор или другую чувствительную информацию. Сервер должен возвращать безопасный текст и стабильный код. Frontend может локализовать сообщение по коду, а `requestId` показать пользователю для обращения в поддержку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие ошибки можно повторять автоматически?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычно временные сетевые ошибки, `429`, `502`, `503` и `504`, если операция безопасна для повтора. Число попыток ограничивают, задержку постепенно увеличивают и добавляют случайный разброс, а также учитывают `Retry-After`. `400`, `403`, `404` и ошибки валидации повтором без изменения запроса не исправляются.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Реакция интерфейса |
| --- | --- |
| `202` после запуска экспорта | Показать прогресс и получать состояние задачи |
| `401` | Один refresh, затем вход при неудаче |
| `403` | Показать отсутствие доступа |
| `404` | Экран «не найдено» или пустое состояние по контракту |
| `412` | Обновить данные и разрешить конфликт версии |
| `422` | Сопоставить ошибки с полями формы |
| `429` | Уважать `Retry-After` и ограничить повтор |
| `503` | Показать временную недоступность и предложить повтор |
