## Вопрос

<br>

 💬 **Что такое WebRTC? Как устанавливается соединение и чем WebRTC отличается от WebSocket?**

<h2></h2>

<br>
<dl>
<dd>

WebRTC является набором браузерных API и сетевых протоколов для передачи аудио, видео и произвольных данных с малой задержкой. Его используют для звонков, видеоконференций, демонстрации экрана и RTCDataChannel, то есть канала данных между конечными точками.

WebRTC старается подобрать подходящий сетевой маршрут, но соединение не обязательно будет прямым. Трафик может идти между двумя клиентами, через TURN-сервер или через медиасервер вроде SFU.

Основные браузерные API:

| API | Назначение |
| --- | --- |
| `navigator.mediaDevices.getUserMedia()` | Получить tracks камеры и микрофона после разрешения пользователя |
| `navigator.mediaDevices.getDisplayMedia()` | Получить track демонстрации экрана, окна или вкладки |
| `RTCPeerConnection` | Согласовать медиапараметры, найти сетевой маршрут и передавать tracks |
| `RTCDataChannel` | Передавать произвольные текстовые или бинарные данные |
| `RTCPeerConnection.getStats()` | Получить метрики соединения: битрейт, потерю пакетов, jitter и время прохождения сигнала туда и обратно |

`MediaStream` является набором media tracks, то есть отдельных аудио- или видеодорожек. `MediaStreamTrack` представляет один источник, например микрофон, камеру или демонстрацию экрана.

Track можно временно выключить:

```ts
videoTrack.enabled = false;
```

При этом объект track остаётся пригодным для повторного включения. Для видео удалённой стороне обычно передаются чёрные кадры, а для аудио — тишина.

Вызов:

```ts
videoTrack.stop();
```

окончательно переводит track в состояние `ended` и освобождает связанный источник, когда он больше нигде не используется. Возобновить тот же track после `stop()` нельзя: нужно снова получить источник через `getUserMedia()` или `getDisplayMedia()`.

Доступ к камере и микрофону требует secure context, то есть защищённого контекста, обычно HTTPS или localhost, а также разрешения пользователя.

Встроенный `iframe` дополнительно должен получить разрешение через Permissions Policy и атрибут `allow`, если доступ к устройствам не предоставлен ему политикой страницы.

Пользователь может отклонить запрос камеры или вообще не ответить на него, поэтому Promise `getUserMedia()` не следует считать гарантированно быстро завершающимся.

Для демонстрации экрана действуют более строгие правила. Вызов `getDisplayMedia()` должен происходить после действия пользователя, например нажатия кнопки. Разрешение на демонстрацию нельзя сохранить навсегда: браузер запрашивает выбор экрана, окна или вкладки при каждом новом запуске.

WebRTC не определяет signaling, то есть способ доставки служебных сообщений для установки и изменения соединения.

Приложение самостоятельно использует WebSocket, HTTP, SSE или другой серверный канал, чтобы участники обменялись:

- offer и answer;
- ICE candidates;
- командами входа и выхода из звонка;
- данными об участниках;
- запросами на повторное согласование;
- сообщениями о завершении сессии.

Signaling-сервер обычно не обязан понимать всю внутреннюю структуру SDP. Но он должен аутентифицировать пользователя, проверять доступ к комнате, ограничивать размер сообщений и отправлять данные только разрешённому участнику.

Signaling-сообщения нужно связывать с конкретным звонком и текущим циклом согласования. Например, используют `callId`, идентификатор участника и номер generation. Иначе запоздавший ICE candidate или answer от предыдущего соединения может попасть в уже созданный новый `RTCPeerConnection`.

Offer и answer являются описаниями совместимых параметров соединения.

Они содержат SDP, то есть текстовое описание:

- медиасекций аудио, видео и data channel;
- поддерживаемых кодеков;
- направлений передачи;
- RTP-параметров;
- ICE-данных;
- параметров защищённого транспорта.

SDP не содержит сами аудио- и видеоданные. Он описывает, как стороны собираются их передавать.

Один участник создаёт offer и устанавливает его как локальное описание:

```ts
const offer = await peerConnection.createOffer();

await peerConnection.setLocalDescription(offer);
```

Затем offer передаётся другому участнику через signaling.

Вторая сторона устанавливает его как удалённое описание:

```ts
await peerConnection.setRemoteDescription(offer);
```

После этого она создаёт answer, устанавливает его как локальное описание и возвращает первой стороне.

В современном коде можно вызвать `setLocalDescription()` без аргумента. Браузер сам создаст подходящий offer или answer в зависимости от текущего `signalingState`.

При добавлении или удалении согласуемых tracks и transceivers возникает событие `negotiationneeded`. Приложение создаёт и отправляет новое локальное описание.

Если обе стороны одновременно создают offer, возникает offer collision, или glare. Чтобы не получить гонку состояний, рекомендуется perfect negotiation pattern.

В этом шаблоне стороны получают роли:

- polite peer может отказаться от собственного конфликтующего offer и принять входящий;
- impolite peer игнорирует конфликтующий входящий offer.

Роли polite и impolite относятся только к разрешению конфликтов negotiation и не означают постоянные роли звонящего и отвечающего.

ICE (Interactive Connectivity Establishment) собирает возможные сетевые маршруты и проверяет пары candidates двух конечных точек.

Основные типы ICE candidate:

| Тип candidate | Откуда берётся |
| --- | --- |
| Host | Адрес локального сетевого интерфейса |
| Server-reflexive (`srflx`) | Публичный адрес, который STUN-сервер увидел за NAT |
| Peer-reflexive (`prflx`) | Адрес, обнаруженный во время ICE-проверок, а не полученный заранее через signaling |
| Relay | Адрес TURN-сервера, который пересылает трафик |

Host candidate представляет непосредственный сетевой интерфейс устройства, хотя браузер может скрывать реальный локальный IP с учётом политики приватности.

STUN помогает определить внешний адрес клиента за NAT и попытаться построить прямой маршрут. Сам STUN обычно не пересылает постоянный медиатрафик.

TURN создаёт relay candidate и пересылает трафик между участниками, если прямой маршрут недоступен из-за firewall, NAT, корпоративной сети или других ограничений.

TURN повышает надёжность подключения, но:

- добавляет промежуточный сетевой узел;
- увеличивает задержку;
- потребляет серверный трафик;
- требует масштабирования пропускной способности;
- увеличивает стоимость инфраструктуры.

Production-система звонков обычно должна иметь рабочий TURN, а не рассчитывать только на STUN. Иначе звонки будут успешно работать в домашней сети разработчика, но не подключаться у части пользователей в корпоративных и мобильных сетях.

Учётные данные TURN не следует бессрочно хранить во frontend-коде. Обычно backend выдаёт короткоживущие credentials авторизованному пользователю.

При trickle ICE candidates передаются по мере обнаружения:

```ts
peerConnection.addEventListener("icecandidate", (event) => {
  signaling.send({
    callId,
    candidate: event.candidate,
  });
});
```

Удалённая сторона добавляет полученный candidate:

```ts
await peerConnection.addIceCandidate(candidate);
```

Это позволяет начать connectivity checks, не дожидаясь завершения полного сбора candidates, и обычно сокращает время подключения.

Приложение должно учитывать порядок signaling-сообщений. Candidate нельзя добавлять до установки соответствующего `remoteDescription`. Его временно сохраняют либо signaling-протокол гарантирует правильную последовательность.

ICE проверяет не отдельный candidate, а пары локального и удалённого candidates. В итоге выбирается рабочая candidate pair, по которой передаются данные.

Для наблюдения за соединением используются несколько независимых состояний:

| Свойство | Что показывает |
| --- | --- |
| `signalingState` | Состояние offer/answer negotiation |
| `iceGatheringState` | Процесс сбора локальных ICE candidates |
| `iceConnectionState` | Состояние ICE-проверок и выбранного маршрута |
| `connectionState` | Обобщённое состояние ICE и защищённых транспортов |

Например, `connectionState === "connected"` означает, что соединение установлено, а `"failed"` — что один из необходимых транспортов больше не может работать.

Состояние `iceConnectionState === "disconnected"` не всегда означает окончательный разрыв. Оно может появиться при кратком сетевом сбое, переходе между сетями или временной потере пакетов и затем самостоятельно вернуться в `connected`.

При кратком `disconnected` обычно дают соединению время восстановиться и дополнительно проверяют `getStats()`. Немедленное пересоздание всего звонка может создать лишние гонки и оборвать соединение, которое могло восстановиться само.

При устойчивом состоянии `failed` выполняют ICE restart:

```ts
peerConnection.restartIce();
```

После этого новое negotiation создаёт свежие ICE credentials и собирает новые candidates. Offer и candidates снова передаются через signaling.

ICE restart меняет сетевой маршрут, но не обязан заново запрашивать камеру или пересоздавать все media tracks.

Типичный жизненный цикл на frontend:

1. Авторизовать пользователя и присоединить его к комнате через signaling.
2. Получить разрешение и tracks камеры или микрофона.
3. Создать `RTCPeerConnection` с адресами STUN- и TURN-серверов.
4. Добавить локальные tracks и обработчики удалённых tracks.
5. Настроить передачу ICE candidates через signaling.
6. Обменяться offer и answer.
7. Добавлять удалённые candidates через `addIceCandidate()`.
8. Наблюдать состояния соединения и качество через `getStats()`.
9. При смене устройства заменить track или выполнить renegotiation.
10. При смене сети при необходимости выполнить ICE restart.
11. При завершении остановить tracks, закрыть каналы и соединение, удалить обработчики и подписку signaling.

Удалённые media tracks приходят через событие `track`:

```ts
peerConnection.addEventListener("track", (event) => {
  remoteVideo.srcObject = event.streams[0];
});
```

В зависимости от способа добавления tracks массив `event.streams` может быть пустым. Тогда приложение может самостоятельно создать `MediaStream` и добавить в него `event.track`.

Переключение камеры часто можно выполнить без полного negotiation:

```ts
const sender = peerConnection
  .getSenders()
  .find((item) => item.track?.kind === "video");

await sender?.replaceTrack(newVideoTrack);
```

`replaceTrack()` обычно не требует нового offer/answer, если новый track совместим с уже согласованными параметрами: например, имеет тот же вид media и не требует неподдерживаемого кодека.

Добавление новой медиасекции, изменение направления transceiver или удаление согласованного sender может потребовать renegotiation.

`RTCDataChannel` передаёт произвольные данные внутри `RTCPeerConnection`. Его используют, например, для:

- сообщений чата;
- состояния курсора;
- игровых команд;
- метаданных звонка;
- небольших файлов;
- P2P-синхронизации.

По умолчанию data channel является надёжным и упорядоченным:

```ts
const channel = peerConnection.createDataChannel("chat");
```

Но при создании можно изменить свойства доставки:

```ts
const channel = peerConnection.createDataChannel("position", {
  ordered: false,
  maxRetransmits: 0,
});
```

Такой канал не ждёт бесконечной повторной доставки устаревшей позиции. Это полезно для данных, где свежее значение важнее гарантированной доставки старого.

Можно ограничить либо число повторов через `maxRetransmits`, либо время повторной доставки через `maxPacketLifeTime`. Эти параметры задаются при создании канала и не меняются во время его работы.

Даже надёжный `RTCDataChannel` не предоставляет бизнес-гарантию exactly once. После разрыва приложение может не знать, успела ли удалённая сторона обработать сообщение. Для важных команд всё равно используют идентификаторы, acknowledgement, дедупликацию и идемпотентные обработчики.

У `RTCDataChannel` есть исходящая очередь. Свойство:

```ts
channel.bufferedAmount
```

показывает количество байтов, ожидающих отправки.

Для больших объёмов данных задают `bufferedAmountLowThreshold` и продолжают отправку после события `bufferedamountlow`. Иначе приложение может быстрее заполнять память, чем сеть передаёт сообщения.

Очень большие сообщения могут увеличивать задержку остальных каналов и превышать согласованный лимит. Поэтому файлы делят на части, ограничивают размер сообщения и реализуют контроль потока.

WebRTC обязательно шифрует передаваемые media и data channels между конечными точками конкретного `RTCPeerConnection`.

Это защищает данные в сети, но не решает все вопросы безопасности:

- signaling-сообщения также должны передаваться по защищённому каналу;
- сервер должен авторизовать вход в комнату;
- TURN credentials должны иметь ограниченный срок;
- входящие SDP и candidates относятся к недоверенным данным;
- пользователю нельзя разрешать подписаться на чужой звонок по угадываемому ID;
- backend должен отзывать доступ при logout или исключении из комнаты.

При прямом соединении конечными точками защищённого транспорта являются два участника.

При использовании SFU обычно создаются отдельные защищённые соединения:

```text
клиент A ⇄ SFU
клиент B ⇄ SFU
```

SFU принимает потоки и пересылает выбранные участникам. Он может не выполнять полное декодирование и повторное кодирование media, но обычно остаётся конечной точкой транспортного шифрования и имеет доступ к закодированным медиаданным.

Если требуется, чтобы даже SFU не мог прочитать содержимое media, поверх обычного WebRTC применяют отдельное end-to-end encryption. Например, приложение шифрует encoded frames до передачи SFU и расшифровывает только на клиенте получателя.

Такое E2EE требует отдельного управления ключами, поддержки браузеров, ротации ключей при изменении состава комнаты и продуманной обработки записи звонка и серверных функций.

Для группового звонка полная P2P mesh-топология быстро становится дорогой.

При `N` участниках каждый клиент должен отправлять свой поток остальным участникам. Растут:

- исходящий трафик;
- число кодирований;
- нагрузка на CPU;
- количество соединений;
- сложность адаптации качества.

Поэтому групповые звонки часто используют SFU (Selective Forwarding Unit). Клиент отправляет ограниченное количество потоков SFU, а сервер пересылает подходящие версии другим участникам.

Для адаптации под разные размеры видео и качество сети клиент может отправлять несколько пространственных или качественных слоёв через simulcast или scalable video coding. SFU выбирает подходящий слой для конкретного получателя.

Качество соединения анализируют через `getStats()`. В зависимости от типа отчёта можно получить:

- отправленный и полученный битрейт;
- количество потерянных пакетов;
- jitter;
- round-trip time;
- число декодированных и потерянных кадров;
- доступный исходящий битрейт;
- текущую candidate pair;
- тип маршрута: host, `srflx` или relay;
- используемый кодек.

Отдельную метрику нельзя интерпретировать изолированно. Например, низкий битрейт может быть результатом плохой сети, ограничения отправителя, адаптации браузера или отсутствия движения в кадре.

Frontend обычно преобразует метрики в понятные состояния:

- подключение;
- соединение установлено;
- плохая сеть;
- звук или видео временно восстанавливаются;
- соединение потеряно;
- используется relay;
- устройство недоступно.

WebSocket и WebRTC решают разные задачи.

WebSocket предоставляет постоянный упорядоченный канал сообщений между браузером и сервером. Он работает поверх надёжного байтового транспорта и подходит для чатов, уведомлений, команд и серверных событий.

WebRTC предназначен прежде всего для realtime-media и соединений между WebRTC endpoints. Он:

- согласовывает аудио- и видеокодеки;
- адаптируется к состоянию сети;
- использует ICE для прохождения NAT;
- может выбрать прямой маршрут или TURN;
- передаёт media tracks;
- предоставляет настраиваемый `RTCDataChannel`.

WebSocket не умеет самостоятельно получать камеру, согласовывать медиакодеки и строить маршрут между участниками. Теоретически видео можно отправлять сообщениями WebSocket, но пришлось бы самостоятельно решать кодирование, синхронизацию, адаптацию качества, congestion control и обработку потерь.

WebRTC часто использует WebSocket только для signaling:

```text
WebSocket: offer, answer, candidates и команды комнаты
WebRTC: аудио, видео и data channel
```

После установки WebRTC-соединения signaling-канал всё равно может оставаться открытым для новых negotiations, добавления участников и завершения звонка.

При завершении звонка нужно:

- остановить локальные camera, microphone и display tracks;
- закрыть `RTCDataChannel`;
- закрыть `RTCPeerConnection`;
- отменить таймеры статистики и восстановления;
- удалить обработчики;
- очистить `srcObject` у media elements;
- отписаться от signaling;
- уведомить сервер о выходе из комнаты;
- не применять запоздавшие signaling-сообщения.

Для демонстрации экрана отдельно обрабатывают событие `ended`: пользователь может завершить показ через системный интерфейс браузера, не нажимая кнопку приложения.

## Дополнительные вопросы

<details>
<summary><strong>Что такое signaling?</strong></summary>

<dl>
<dd>
<h2></h2>

Это прикладной канал, через который участники передают offer, answer, ICE candidates и команды звонка.

WebRTC определяет структуру SDP и ICE-данных, но не способ их доставки. Приложение может использовать WebSocket, HTTP или другой транспорт.

Signaling-сервер обычно:

- аутентифицирует пользователя;
- проверяет доступ к комнате;
- определяет получателя сообщения;
- ограничивает размер и частоту сообщений;
- связывает сообщение с конкретным звонком;
- не допускает передачу данных постороннему участнику.

Запоздавшие сообщения старого звонка нельзя применять к новому `RTCPeerConnection`, поэтому в контракт добавляют `callId`, идентификатор участника и generation.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое offer, answer и SDP?</strong></summary>

<dl>
<dd>
<h2></h2>

Offer предлагает параметры соединения, answer сообщает совместимый ответ, а SDP описывает медиасекции, кодеки, направления передачи и транспортные параметры.

SDP не содержит само видео или аудио. Он сообщает, какие потоки стороны готовы передавать и как установить защищённые транспорты.

Приложение обычно не редактирует SDP вручную. Оно передаёт результат `localDescription` через signaling и устанавливает входящий документ через `setRemoteDescription()`.

Одновременно начатые offer могут создать glare. Для обработки таких гонок используют perfect negotiation pattern.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое ICE candidate?</strong></summary>

<dl>
<dd>
<h2></h2>

Это возможный сетевой адрес и способ установить транспортное соединение.

Candidate может представлять:

- локальный интерфейс;
- внешний адрес, обнаруженный через STUN;
- адрес, обнаруженный во время ICE-проверок;
- маршрут через TURN.

Каждая сторона собирает локальные candidates и передаёт их другой через signaling. ICE формирует пары локальных и удалённых candidates, проверяет доступность и выбирает рабочую пару.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем STUN отличается от TURN?</strong></summary>

<dl>
<dd>
<h2></h2>

STUN помогает клиенту определить внешний адрес за NAT и попытаться построить прямой маршрут. После этого медиатрафик обычно не проходит через STUN-сервер.

TURN предоставляет relay: принимает трафик одного участника и пересылает другому, если прямой путь невозможен.

TURN расходует серверную пропускную способность и увеличивает стоимость, но значительно повышает вероятность успешного соединения.

Поэтому production-система звонков обычно использует и STUN, и TURN. Наличие только STUN означает, что часть пользователей за сложным NAT или корпоративным firewall не сможет подключиться.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли WebRTC является P2P?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Соединение между двумя участниками может быть прямым, проходить через TURN relay или завершаться на медиасервере.

В групповых звонках часто используется SFU: каждый клиент создаёт WebRTC-соединение с сервером, а сервер пересылает подходящие потоки другим участникам.

WebRTC определяет API и совместимые realtime-протоколы, но не гарантирует отсутствие серверов на пути.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое renegotiation и когда она нужна?</strong></summary>

<dl>
<dd>
<h2></h2>

Renegotiation — повторный обмен offer и answer после изменения параметров соединения.

Она может потребоваться при:

- добавлении новой медиасекции;
- удалении sender;
- изменении направления transceiver;
- добавлении демонстрации экрана;
- ICE restart.

Простое переключение камеры часто выполняется через `RTCRtpSender.replaceTrack()` без renegotiation.

Если обе стороны одновременно создадут offer, возникает glare. Perfect negotiation назначает polite- и impolite-роли и определяет, какая сторона уступает при конфликте.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>track.enabled = false</code> отличается от <code>track.stop()</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`track.enabled = false` временно выключает выход track. Объект остаётся активным, и его можно снова включить:

```ts
track.enabled = true;
```

Это подходит для кнопок mute и camera off.

`track.stop()` окончательно завершает track. Его `readyState` становится `ended`, и повторно запустить тот же объект нельзя.

После `stop()` для возобновления передачи нужно получить новый track и передать его через `replaceTrack()` либо выполнить renegotiation.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Насколько надёжен <code>RTCDataChannel</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

По умолчанию `RTCDataChannel` передаёт сообщения надёжно и по порядку.

При создании можно выбрать частично надёжный режим:

```ts
peerConnection.createDataChannel("position", {
  ordered: false,
  maxRetransmits: 0,
});
```

Он подходит для быстро устаревающих данных, например позиции курсора или игрового состояния.

Даже надёжный канал не гарантирует выполнение бизнес-операции ровно один раз. При разрыве может быть неизвестно, обработал ли получатель последнее сообщение. Для важных команд нужны идентификаторы, подтверждения и дедупликация.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Является ли WebRTC-шифрование сквозным при использовании SFU?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычный WebRTC шифрует транспорт между конечными точками каждого `RTCPeerConnection`.

При SFU это обычно два разных защищённых участка:

```text
отправитель ⇄ SFU
SFU ⇄ получатель
```

SFU остаётся конечной точкой транспортного шифрования и обычно может получить доступ к закодированным медиаданным, даже если не выполняет полное декодирование видео.

Чтобы SFU только пересылал зашифрованное содержимое, добавляют отдельное end-to-end encryption поверх WebRTC. Оно требует клиентского шифрования encoded frames и отдельного управления ключами.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как диагностировать плохое качество звонка?</strong></summary>

<dl>
<dd>
<h2></h2>

Проверяют `getStats()`:

- потерю пакетов;
- jitter;
- round-trip time;
- битрейт;
- доступный исходящий битрейт;
- выбранную ICE candidate pair;
- тип маршрута;
- число потерянных и декодированных кадров.

Затем метрики связывают с `iceConnectionState`, `connectionState`, типом маршрута и возможностями устройства.

Например, relay через TURN может увеличить задержку, а высокая потеря пакетов — привести к снижению качества браузером.

Одного общего события `error` для такой диагностики недостаточно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать при смене сети или переходе Wi-Fi в мобильную сеть?</strong></summary>

<dl>
<dd>
<h2></h2>

Рабочая ICE candidate pair может стать недоступной.

Клиент наблюдает `iceConnectionState` и `connectionState`. Краткое состояние `disconnected` не обязательно требует немедленного вмешательства: соединение может восстановиться самостоятельно.

Если ICE переходит в устойчивое состояние `failed`, выполняют `restartIce()` и отправляют новое локальное описание через signaling.

После ICE restart стороны обмениваются новыми candidates. Media tracks при этом обычно можно сохранить, не запрашивая устройства заново.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что нужно очистить после звонка?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно:

- остановить локальные camera, microphone и display tracks;
- закрыть `RTCDataChannel`;
- закрыть `RTCPeerConnection`;
- отменить таймеры статистики и восстановления;
- удалить обработчики;
- очистить `srcObject` у media elements;
- отписаться от signaling;
- уведомить сервер о выходе из комнаты;
- игнорировать запоздавшие сообщения завершённого звонка.

Для демонстрации экрана также обрабатывают событие `ended`, потому что пользователь может прекратить показ через интерфейс браузера.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что важно |
| --- | --- |
| Видеозвонок | Разрешения, tracks, offer/answer и ICE |
| Демонстрация экрана | Пользовательское действие, `getDisplayMedia`, замена track и `ended` |
| Корпоративная сеть | Запасной маршрут через TURN и диагностика candidate pair |
| Групповой звонок | SFU вместо полной mesh-топологии |
| Смена камеры | `replaceTrack()` или renegotiation |
| Плохая сеть | `getStats()`, адаптация качества и понятное состояние интерфейса |
| Смена сети | Ожидание при `disconnected` и ICE restart при устойчивом сбое |
| Завершение звонка | Остановка устройств и полная очистка ресурсов |
