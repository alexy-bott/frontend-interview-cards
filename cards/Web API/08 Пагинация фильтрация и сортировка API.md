## Вопрос

<br>

 💬 **Как устроены пагинация, фильтрация и сортировка в API? Чем offset pagination отличается от cursor pagination?**

<h2></h2>

<br>
<dl>
<dd>

Pagination, или пагинация, делит большую коллекцию на части. Без ограничения размера ответ может стать медленным, тяжёлым для сети и неудобным для интерфейса и кеширования.

Контракт пагинации должен заранее определить:

- параметры запроса;
- размер страницы по умолчанию и максимальный `limit`;
- порядок элементов;
- формат ответа;
- способ получить следующую и предыдущую часть;
- поведение при некорректном или устаревшем курсоре;
- необходимость и точность общего количества записей.

Основные модели:

| Модель | Пример | Сильная сторона | Ограничение |
| --- | --- | --- | --- |
| Offset/limit, смещение и размер | `?offset=40&limit=20` | Просто перейти к известной позиции | Изменения коллекции дают пропуски или дубли; большое смещение может быть дорогим |
| Page/pageSize, номер и размер страницы | `?page=3&pageSize=20` | Удобно показать номера страниц | Обычно является вариантом offset с теми же ограничениями |
| Cursor, курсор продолжения | `?after=eyJpZCI6...&limit=20` | Клиент не зависит от внутреннего способа поиска следующей части | Нельзя предполагать формат или свойства курсора; переход к произвольной странице сложнее |
| Keyset/seek, поиск после последнего ключа | `?after=<opaque-cursor>` | Эффективное последовательное чтение по индексу и меньшая чувствительность к вставкам перед текущей позицией | Требует стабильной сортировки и не даёт простого перехода к номеру страницы |

Для любой модели пагинации нужен предсказуемый порядок. Без явной сортировки база данных не обязана возвращать записи в одном и том же порядке, поэтому страницы могут пересекаться или пропускать элементы даже при неизменившихся данных.

Порядок должен быть не только стабильным, но и уникальным. Например:

```text
createdAt DESC, id DESC
```

Если несколько записей имеют одинаковый `createdAt`, уникальный `id` используется как tie-breaker, то есть дополнительный критерий разрешения равенства.

При offset pagination сервер пропускает заданное число записей и затем возвращает страницу:

```text
offset=40
limit=20
```

Если между запросами в начало списка добавился новый элемент, запись с границы может повториться на следующей странице. Если элемент перед текущей позицией удалился, другая запись может быть пропущена.

Большое значение `offset` также может быть дорогим: серверу нередко всё равно приходится найти или вычислить пропускаемые строки, прежде чем вернуть нужную часть.

Для небольшой административной таблицы с переходом по номерам страниц это часто приемлемо. Для большой или активно меняющейся ленты обычно удобнее последовательная cursor pagination.

Cursor pagination описывает контракт API: сервер возвращает непрозрачное значение, которое клиент передаёт обратно для получения следующей части.

Само наличие cursor не гарантирует конкретную реализацию. Внутри курсора сервер может закодировать:

- offset;
- идентификатор последней записи;
- значения полей сортировки;
- идентификатор снимка данных;
- внутренний указатель хранилища.

Поэтому cursor pagination и keyset pagination не являются полными синонимами.

Keyset pagination, также называемая seek pagination, продолжает выборку после значений последнего элемента в стабильной сортировке. Например, при порядке:

```text
createdAt DESC, id DESC
```

следующая страница концептуально выбирается по условию:

```sql
WHERE
  created_at < :createdAt
  OR (created_at = :createdAt AND id < :id)
ORDER BY created_at DESC, id DESC
LIMIT :limit
```

Курсор может непрозрачно кодировать `createdAt` и `id`, чтобы клиент не зависел от структуры базы данных и правил сравнения.

Пример ответа:

```json
{
  "items": [
    {
      "id": "42",
      "createdAt": "2026-07-27T10:00:00Z"
    }
  ],
  "pageInfo": {
    "hasNextPage": true,
    "nextCursor": "eyJjcmVhdGVkQXQiOiIuLi4iLCJpZCI6IjQyIn0"
  }
}
```

Клиент не должен декодировать, изменять или самостоятельно создавать курсор. Его формат принадлежит серверу и может измениться без изменения публичного контракта.

Курсор также относится к конкретной выборке. Он может зависеть от:

- фильтров;
- сортировки;
- направления движения;
- размера страницы;
- пользователя или tenant;
- версии или снимка данных.

После изменения фильтра или сортировки старый курсор использовать нельзя. Новая комбинация параметров начинает новую последовательность с первой страницы.

Сервер должен валидировать курсор и не доверять содержащимся в нём данным только потому, что они были закодированы через Base64. При необходимости курсор подписывают или связывают с серверным состоянием, чтобы клиент не мог незаметно изменить область выборки.

Для обратной навигации контракт отдельно предоставляет `before`, `previousCursor`, `hasPreviousPage` или готовую ссылку на предыдущую страницу.

API также может возвращать полностью сформированные ссылки:

```json
{
  "items": [],
  "links": {
    "next": "/users?status=active&after=abc&limit=20",
    "prev": null
  }
}
```

Готовая ссылка уменьшает дублирование логики: клиент следует ей, не собирая заново фильтры, сортировку и cursor.

Если интерфейсу нужен переход сразу на страницу 37 и точное количество страниц, offset-модель часто практичнее. Cursor-модель в первую очередь подходит для последовательной навигации: «загрузить ещё», infinite scroll, следующая и предыдущая часть.

Cursor и keyset уменьшают некоторые проблемы offset, но не создают неизменяемый снимок данных автоматически.

Например, запись может:

- измениться так, что переместится по полю сортировки;
- быть удалена между запросами;
- появиться внутри уже просмотренного диапазона;
- перестать соответствовать фильтру.

Из-за этого дубли или пропуски всё ещё возможны в зависимости от семантики API. Если продукту нужен строго согласованный снимок, контракт должен отдельно предоставить snapshot ID, версию выборки, время `asOf` или другой механизм фиксации набора данных.

Фильтрацию и сортировку обычно передают через query-параметры:

```text
?status=active&sort=-createdAt,name
```

Контракт должен определить:

- разрешённые поля;
- доступные операторы;
- синтаксис направления сортировки;
- кодирование массивов;
- кодирование диапазонов;
- различие отсутствующего, пустого и `null`-значения;
- регистр и правила поиска;
- сочетание нескольких фильтров;
- максимальный `limit`.

Сервер должен использовать allowlist разрешённых полей и операций. Нельзя напрямую подставлять произвольные названия полей или выражения пользователя в SQL, поисковый запрос или внутренний API.

Frontend должен сериализовать одинаковое состояние одинаковым способом. Например, массив можно передавать как:

```text
?status=active&status=blocked
```

или:

```text
?status=active,blocked
```

Оба варианта допустимы, но клиент и сервер должны заранее выбрать один контракт.

Параметры полезно канонизировать, то есть приводить к единому представлению:

- не отправлять значение по умолчанию то как отсутствующее, то как явное;
- единообразно представлять пустые значения;
- удалять параметры, не влияющие на запрос;
- сортировать только те массивы, порядок которых по контракту не имеет значения.

Если порядок значений влияет на результат, сортировать такой массив при канонизации нельзя.

Все переменные, влияющие на получаемый набор данных, должны участвовать в ключе прикладного кеша:

- фильтры;
- сортировка;
- страница или cursor;
- размер страницы;
- поисковая строка;
- локаль;
- tenant или другая область данных.

Например:

```ts
["users", { status, sort, page, pageSize }]
```

Если использовать один ключ `users` для разных фильтров, кеш может показать данные другой выборки.

Токены, cookie и другие секреты нельзя помещать в query key или URL. Но кеш должен учитывать смену auth-контекста: после logout, смены пользователя или tenant чувствительные данные предыдущего контекста очищают либо хранят в изолированной области.

В RTK Query аргумент endpoint сериализуется во внутренний `queryCacheKey`. Поэтому все параметры, которые изменяют запрос, должны присутствовать в аргументе endpoint.

В TanStack Query все изменяющиеся зависимости функции запроса включают в `queryKey`. Объект ключа должен быть сериализуемым и однозначно описывать данные.

Когда фильтр или сортировка меняется, текущую страницу обычно сбрасывают в начало:

- `page=1`;
- `offset=0`;
- cursor удаляется.

Третья страница старой выборки не является третьей страницей новой. Если сохранить прежнее положение, пользователь может получить пустой результат или начать просмотр с середины нового списка.

Предыдущий запрос при смене параметров отменяют через `AbortController` либо не позволяют его позднему ответу заменить данные более нового запроса.

Для строки поиска применяют debounce, то есть небольшую задержку перед отправкой запроса. Отмена и debounce решают разные задачи:

- debounce уменьшает количество запросов;
- отмена прекращает работу с уже неактуальным запросом;
- проверка query key или идентификатора попытки не позволяет применить устаревший результат.

Состояние таблицы хранят в URL, если пользователь должен:

- обновить страницу без потери выборки;
- поделиться ссылкой;
- добавить страницу в закладки;
- использовать кнопки браузера «назад» и «вперёд».

Локальное состояние подходит для временного параметра интерфейса, который не определяет содержимое страницы: например, открытого меню или черновика ещё не применённого фильтра.

Преобразование между URL и объектом фильтров должно быть двусторонним:

```text
URL → валидированный объект → запрос API
объект → канонический URL
```

Значения из URL являются внешними строковыми данными. Их нужно разобрать, ограничить разрешёнными вариантами и подставить значения по умолчанию.

При infinite scroll клиент:

1. Хранит уже загруженные страницы.
2. Проверяет `hasNextPage` или наличие `nextCursor`.
3. Не запускает повторно загрузку одной и той же следующей страницы.
4. Не смешивает страницы разных фильтров и сортировок.
5. Учитывает параллельные вызовы «загрузить ещё».
6. При необходимости защитно удаляет дубли по устойчивому `id`.

Дедупликация по `id` полезна как защитная мера, но не должна скрывать ошибку серверного контракта. Если API постоянно возвращает пересекающиеся страницы, нужно исправить порядок, cursor или условия выборки.

После изменения данных, восстановления соединения или долгой паузы последовательность страниц может устареть. В зависимости от продукта клиент:

- обновляет одну запись в кеше;
- инвалидирует всю выборку;
- повторно загружает первую страницу;
- последовательно обновляет все сохранённые страницы;
- начинает новую последовательность с новым snapshot.

Точное общее количество записей `total` может быть дорогим для сложной выборки, большого хранилища или распределённой системы.

Для infinite scroll часто достаточно:

```json
{
  "hasNextPage": true,
  "nextCursor": "..."
}
```

Для таблицы с номерами страниц может потребоваться:

```json
{
  "total": 1284,
  "page": 3,
  "pageSize": 20
}
```

Контракт должен уточнить, является ли `total`:

- точным;
- приближённым;
- актуальным на момент запроса;
- полученным отдельным запросом;
- вообще недоступным.

Frontend не должен вычислять общее количество как `page.length * numberOfPages`: последняя страница может быть неполной, а коллекция — измениться между запросами.

</dd>
</dl>

## Дополнительные вопросы

<details>
<summary><strong>Чем cursor pagination лучше offset?</strong></summary>

<dl>
<dd>
<h2></h2>

Cursor позволяет серверу скрыть способ продолжения выборки и изменить внутреннюю реализацию без изменения клиентского контракта.

Если курсор реализован через keyset pagination, сервер продолжает чтение после конкретного значения сортировки. Вставка новых элементов перед уже просмотренной позицией тогда меньше влияет на следующую страницу, а серверу не нужно пропускать большое количество строк.

Но cursor может кодировать обычный offset. Само наличие непрозрачной строки не гарантирует производительность или устойчивость.

Цена cursor-модели — более сложный контракт, отсутствие простого перехода к произвольному номеру страницы и необходимость отдельно реализовать обратную навигацию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Cursor pagination и keyset pagination — одно и то же?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет.

Cursor pagination — это интерфейс API: клиент получает непрозрачный маркер и передаёт его для продолжения выборки.

Keyset pagination — это серверная стратегия: следующая часть выбирается сравнением значений полей сортировки с последней полученной записью.

Cursor может содержать ключи keyset pagination, но может также кодировать offset, snapshot ID или внутренний указатель.

Поэтому преимущества keyset нельзя автоматически приписывать любому endpoint с параметром `cursor`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему курсор должен опираться на уникальный порядок?</strong></summary>

<dl>
<dd>
<h2></h2>

Поле `createdAt` может совпадать у нескольких записей. Если курсор хранит только его, сервер не знает, какие элементы с тем же временем уже были отданы.

Пара `createdAt` и `id` создаёт однозначный порядок:

```text
createdAt DESC, id DESC
```

Сервер продолжает выборку после обоих значений. Это уменьшает риск потери или повторения записи на границе страниц.

Уникальный порядок нужен и для offset pagination: без него база данных не обязана возвращать одинаковую последовательность строк.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли использовать <code>id</code> как cursor?</strong></summary>

<dl>
<dd>
<h2></h2>

Да, если порядок действительно определяется одним уникальным и подходящим `id`.

Например, это может работать для монотонно возрастающего идентификатора при сортировке только по нему.

Если список сортируется по рейтингу, дате, цене или нескольким полям, одного `id` недостаточно. Он может использоваться как дополнительный tie-breaker, но курсор должен учитывать и основной критерий сортировки.

Чаще сервер выдаёт непрозрачный cursor, чтобы клиент не зависел от типа идентификатора, индекса и внутренней реализации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Гарантирует ли cursor отсутствие дублей и пропусков?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет, если контракт отдельно не обещает работу с зафиксированным снимком данных.

Keyset cursor хорошо обрабатывает многие вставки перед текущей позицией, но запись может изменить поле сортировки, исчезнуть или перестать соответствовать фильтру.

Для строго согласованного обхода сервер должен предоставить snapshot ID, версию, время `asOf` или другой способ зафиксировать набор данных.

Frontend может удалять случайные дубли по `id`, но это защитная мера, а не доказательство корректности пагинации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему query key должен включать фильтры и сортировку?</strong></summary>

<dl>
<dd>
<h2></h2>

Потому что `status=active` и `status=blocked` являются разными результатами API.

Если ключ одинаковый, кеш может смешать выборки или показать предыдущие данные как актуальные.

В RTK Query эту роль выполняют аргументы endpoint и их сериализация. В TanStack Query все изменяющиеся параметры включают в `queryKey`.

Секретные токены в ключ не помещают. При смене пользователя или tenant кеш очищают либо изолируют другим способом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда фильтры нужно хранить в URL?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда они определяют восстанавливаемое состояние страницы: каталог, поиск, отчёт или административную таблицу.

URL позволяет:

- открыть ту же выборку после перезагрузки;
- поделиться ссылкой;
- использовать историю браузера;
- сохранить страницу в закладках.

Состояние открытого выпадающего списка, фокуса или неприменённого черновика обычно остаётся локальным.

Параметры из URL нужно валидировать и преобразовывать в типизированный объект, а объект — обратно в единообразный URL.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему при смене фильтра нужно сбрасывать страницу?</strong></summary>

<dl>
<dd>
<h2></h2>

Третья страница нового узкого фильтра может не существовать, хотя на первой странице есть данные.

Кроме того, cursor относится к конкретному сочетанию фильтров и сортировки. После их изменения прежняя позиция больше не имеет определённого смысла.

Новый набор параметров начинает отдельную последовательность с `page=1`, `offset=0` или без cursor.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему API иногда не возвращает <code>total</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Точный подсчёт может потребовать полного прохода по сложной выборке, обращения к нескольким хранилищам или дополнительной синхронизации.

Для кнопки «загрузить ещё» достаточно знать наличие следующей страницы.

Если продукту нужен `total`, его стоимость, точность и момент актуальности становятся частью API-контракта. Сервер может возвращать точное значение, оценку либо предоставлять отдельный endpoint подсчёта.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как избежать дублей в infinite scroll?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно использовать стабильную уникальную сортировку и корректный cursor от сервера, не запускать параллельно повторную загрузку одной страницы и не смешивать выборки с разными параметрами.

При объединении страниц можно защитно удалять дубли по устойчивому `id`.

После изменения списка нужно выбрать явную политику:

- обновить отдельную запись;
- инвалидировать последовательность;
- повторно загрузить сохранённые страницы;
- начать загрузку сначала.

Постоянные дубли нельзя исправлять только frontend-дедупликацией: нужно проверить серверную сортировку и условия продолжения выборки.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Подход |
| --- | --- |
| Административная таблица | `page`/`pageSize`, общее количество и состояние в URL |
| Бесконечная лента | Cursor, `hasNextPage` и дедупликация |
| Каталог товаров | Фильтры и сортировка в параметрах URL |
| Автодополнение | Debounce, отмена и защита от устаревшего ответа |
| RTK Query | Все параметры входят в аргумент endpoint |
| TanStack Query | Все параметры входят в `queryKey` |
| Изменение фильтра | Сброс страницы и отдельный кеш результата |
