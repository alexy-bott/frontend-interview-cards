## Вопрос

<br>

 💬 **Как JavaScript хранит числа? Почему `0.1 + 0.2 !== 0.3`, что такое безопасное целое число (safe integer) и когда нужен `BigInt`?**

<h2></h2>

<br>
<dl>
<dd>

Тип `number` хранит числа в 64-битном двоичном формате IEEE 754 binary64 с двойной точностью. Один тип представляет целые и дробные значения, `Infinity`, `-Infinity`, `NaN` и `-0`.

Формат имеет ограниченную двоичную точность. Многие конечные десятичные дроби нельзя представить конечным количеством двоичных разрядов, поэтому JavaScript сохраняет ближайшее доступное значение.

```js
0.1 + 0.2; // 0.30000000000000004
```

Значения `0.1`, `0.2` и `0.3` представлены внутри `number` приближённо. После сложения приближённых значений результат снова округляется до ближайшего представимого числа. Получившееся значение немного отличается от представления литерала `0.3`.

Это не случайная ошибка JavaScript, а следствие арифметики с плавающей точкой.

Для сравнения результатов вычислений иногда используют допустимую погрешность. Она зависит от масштаба чисел и требований задачи. `Number.EPSILON` показывает точность около числа `1` и не является универсальным порогом для любых вычислений.

Безопасными целыми называют значения от `Number.MIN_SAFE_INTEGER` до `Number.MAX_SAFE_INTEGER`:

```text
-(2 ** 53 - 1) ... 2 ** 53 - 1
```

В этом диапазоне каждое целое число представляется точно и однозначно.

За его пределами некоторые отдельные целые всё ещё могут быть представлены точно, но тип `number` больше не гарантирует различие всех соседних математических значений:

```js
Number.MAX_SAFE_INTEGER + 1 === Number.MAX_SAFE_INTEGER + 2; // true
```

Для проверки используют:

```js
Number.isSafeInteger(value);
```

`BigInt` представляет целые числа произвольной точности в пределах доступной памяти:

```js
const id = 9007199254740993n;
```

`BigInt`:

- не хранит дробные значения;
- не смешивается с `number` в обычной арифметике;
- не поддерживается стандартной JSON-сериализацией без явного преобразования;
- не работает с большинством методов объекта `Math`.

Большие идентификаторы API часто передают строкой. Это позволяет JSON-парсеру, frontend, backend и базе данных сохранить все цифры без округления. Кроме того, идентификатор обычно не является числом, над которым нужно выполнять арифметику.

Для денег часто хранят целое количество минимальных единиц, например копейки. Это устраняет ошибки двоичного представления десятичных дробей, но всё равно требует контроля безопасного диапазона и явного правила округления при процентах, налогах и конвертации валют.

Если нужны точные десятичные вычисления с большими значениями, используют подходящую библиотеку десятичной арифметики.

Метод `toFixed` только округляет и форматирует уже вычисленное значение. Он не делает предыдущие операции точными.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что такое <code>NaN</code> и как его проверять?</strong></summary>

<dl>
<dd>
<h2></h2>

`NaN` — специальное значение типа `number`, которое обозначает некорректный числовой результат:

```js
Number("text"); // NaN
0 / 0; // NaN
```

```js
typeof NaN; // "number"
```

`NaN` не равно самому себе:

```js
NaN === NaN; // false
```

Для проверки используют `Number.isNaN`:

```js
Number.isNaN(value);
```

Он возвращает `true` только для самого значения `NaN` без предварительного приведения типа.

Глобальный `isNaN` сначала преобразует аргумент в число:

```js
isNaN("text"); // true
```

Такой результат может скрыть, что исходное значение было строкой, а не числом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>Number.isFinite</code> отличается от глобального <code>isFinite</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`Number.isFinite` возвращает `true` только для конечного значения типа `number`:

```js
Number.isFinite(10); // true
Number.isFinite(Infinity); // false
Number.isFinite("10"); // false
```

Глобальный `isFinite` сначала приводит аргумент к числу:

```js
isFinite(""); // true
```

Пустая строка преобразуется в `0`, поэтому результат равен `true`.

При проверке внешних данных обычно сначала проверяют тип, а затем используют строгий метод `Number.isFinite`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>Number.MAX_VALUE</code> отличается от <code>Number.MAX_SAFE_INTEGER</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`Number.MAX_VALUE` — крупнейшее конечное значение типа `number`, примерно:

```text
1.8 × 10^308
```

Оно описывает максимальную величину, после которой результат превращается в `Infinity`.

`Number.MAX_SAFE_INTEGER` намного меньше:

```js
2 ** 53 - 1;
```

Это граница диапазона, внутри которого каждое целое представляется точно и различается с соседними целыми.

Тип `number` может хранить значения значительно больше `MAX_SAFE_INTEGER`, но уже не гарантирует точность каждого целого.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое <code>-0</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

IEEE 754 содержит положительный и отрицательный ноль.

При обычном строгом сравнении они равны:

```js
0 === -0; // true
```

Метод `Object.is` позволяет различить их:

```js
Object.is(0, -0); // false
```

Знак также виден при делении:

```js
1 / 0; // Infinity
1 / -0; // -Infinity
```

В большинстве прикладных задач знак нуля не важен, но он может иметь значение в математике, графиках и отображении направленных величин.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как сравнивать дробные результаты с погрешностью?</strong></summary>

<dl>
<dd>
<h2></h2>

Вместо точного равенства сравнивают абсолютную разницу с допустимым порогом:

```js
Math.abs(a - b) <= tolerance;
```

Для чисел разного масштаба часто учитывают и относительную погрешность:

```js
const nearlyEqual = (a, b, tolerance = 1e-10) =>
  Math.abs(a - b) <= tolerance * Math.max(1, Math.abs(a), Math.abs(b));
```

`Math.max(1, ...)` сохраняет абсолютную составляющую сравнения для чисел около нуля и относительную — для больших значений.

Конкретный порог зависит от задачи. Для координат, графиков, физических расчётов и финансов действуют разные требования.

Если нужны точные десятичные значения, сравнение с погрешностью не заменяет десятичную арифметику.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что именно означает <code>Number.EPSILON</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`Number.EPSILON` — разница между числом `1` и следующим представимым значением типа `number`:

```js
Number.EPSILON; // примерно 2.22e-16
```

Это характеристика точности около единицы, а не максимальная ошибка любого вычисления.

Чем больше абсолютное значение числа, тем больше расстояние между соседними представимыми значениями. Поэтому такая проверка подходит не всегда:

```js
Math.abs(a - b) < Number.EPSILON;
```

Для значений большого масштаба она может оказаться слишком строгой, а для конкретной бизнес-задачи — не соответствовать требованиям.

Порог выбирают с учётом масштаба, количества операций и допустимой ошибки предметной области.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>Number</code>, <code>parseInt</code> и <code>parseFloat</code> разбирают строку?</strong></summary>

<dl>
<dd>
<h2></h2>

`Number` пытается преобразовать всю строку:

```js
Number("42"); // 42
Number("42px"); // NaN
```

`parseInt` читает целую числовую часть с начала строки и останавливается на первом неподходящем символе:

```js
parseInt("42px", 10); // 42
```

Второй аргумент задаёт основание системы счисления. Для обычного десятичного ввода явно передают `10`.

`parseFloat` похожим образом читает дробную часть:

```js
parseFloat("3.14rem"); // 3.14
```

Частичный разбор полезен, когда формат действительно разрешает единицу измерения после числа.

При проверке пользовательского поля он может скрыть ошибочный ввод: строка `"42abc"` будет частично принята вместо отклонения целиком.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему побитовые операторы дают неожиданные результаты для больших чисел?</strong></summary>

<dl>
<dd>
<h2></h2>

Большинство побитовых операций над `number` сначала преобразуют значение в 32-битное целое со знаком.

Старшие разряды отбрасываются:

```js
2 ** 40 | 0; // значение уже не равно 2 ** 40
```

Операция `>>>` возвращает 32-битное целое без знака, но её операнды тоже ограничиваются 32 разрядами.

Поэтому побитовые операторы нельзя использовать как универсальный быстрый способ округления идентификаторов, денежных значений или временных меток.

У `BigInt` есть отдельные побитовые операции произвольной точности, но оператор беззнакового сдвига `>>>` для него не поддерживается.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что важно знать про арифметику BigInt?</strong></summary>

<dl>
<dd>
<h2></h2>

В обычной арифметической операции оба операнда должны быть значениями `BigInt`:

```js
1n + 1; // TypeError
1n + 1n; // 2n
```

Операндом называют значение, над которым выполняется операция.

Деление `BigInt` отбрасывает дробную часть в направлении нуля:

```js
5n / 2n; // 2n
-5n / 2n; // -2n
```

Методы объекта `Math` не принимают `BigInt`.

При преобразовании большого `number` в `BigInt` потерянная точность не восстанавливается:

```js
const value = 9007199254740993;
BigInt(value); // исходные цифры уже могли быть округлены
```

Для точного большого значения используют строку или литерал:

```js
BigInt("9007199254740993");
9007199254740993n;
```

Преобразование `BigInt` в `number` также может потерять точность:

```js
Number(9007199254740993n);
```

Его выполняют только после проверки, что значение помещается в требуемый безопасный диапазон.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему большое целое число из JSON может потерять точность ещё до TypeScript-проверки?</strong></summary>

<dl>
<dd>
<h2></h2>

JSON не имеет отдельного типа `BigInt`. Числовой литерал из JSON разбирается в JavaScript как `number`.

Если значение находится за диапазоном безопасных целых, округление может произойти уже внутри `JSON.parse`:

```js
const data = JSON.parse('{"id": 9007199254740993}');
```

К моменту TypeScript-проверки исходные цифры уже потеряны. Type guard или schema validator не смогут восстановить первоначальное значение.

Большой идентификатор следует передавать строкой:

```json
{
  "id": "9007199254740993"
}
```

Другой вариант требует специального формата и согласованного парсера на обеих сторонах API.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как <code>BigInt</code> работает с JSON?</strong></summary>

<dl>
<dd>
<h2></h2>

Стандартный `JSON.stringify` не умеет сериализовать `BigInt` напрямую:

```js
JSON.stringify({
  id: 9007199254740993n,
}); // TypeError
```

Обычно значение явно преобразуют в строку:

```js
JSON.stringify({
  id: String(9007199254740993n),
});
```

При чтении приложение должно знать, какие строковые поля следует преобразовать обратно:

```js
const id = BigInt(data.id);
```

Нельзя автоматически превращать каждую строку с цифрами в `BigInt`: строка может быть телефонным номером, кодом, индексом или обычным идентификатором, который должен остаться строкой.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Подходит ли <code>toFixed(2)</code> для финансовой логики?</strong></summary>

<dl>
<dd>
<h2></h2>

`toFixed` форматирует `number` и возвращает строку:

```js
const text = value.toFixed(2);
```

Он округляет уже сохранённое двоичное значение и не исправляет ошибки предыдущих вычислений.

Для отображения конечного результата `toFixed` может быть приемлем, если его правило округления соответствует требованиям продукта.

Для последовательных денежных операций обычно используют:

- целое количество минимальных единиц;
- десятичную арифметику;
- явное правило округления на определённом этапе.

Даже при хранении копеек нужно учитывать деление, проценты, налоги, конвертацию валют и возможный выход за диапазон безопасных целых.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как форматировать число для пользователя?</strong></summary>

<dl>
<dd>
<h2></h2>

Для локализованного отображения используют `Intl.NumberFormat`:

```js
const formatter = new Intl.NumberFormat("ru-RU", {
  style: "currency",
  currency: "RUB",
});

formatter.format(1234.5);
```

Локаль определяет разделители, порядок символов, формат валюты и другие региональные правила.

Полученная строка предназначена только для отображения. Её не используют для последующих вычислений или передачи в API.

Приложение хранит исходное числовое значение отдельно и форматирует его на границе пользовательского интерфейса.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```js
const id = Number.MAX_SAFE_INTEGER + 1;

console.log(id === id + 1);
console.log(Number.isSafeInteger(id));
console.log(5n / 2n);
```

<details>
<summary><strong>Что будет выведено?</strong></summary>

<dl>
<dd>
<h2></h2>

Будет выведено:

```text
true
false
2n
```

`id` равен первому целому за `Number.MAX_SAFE_INTEGER`.

При вычислении `id + 1` математическое значение увеличивается, но ближайшее представимое значение типа `number` остаётся тем же. Поэтому строгое сравнение возвращает `true`.

`Number.isSafeInteger(id)` возвращает `false`, потому что значение находится за гарантированным диапазоном безопасных целых.

Деление `BigInt` не создаёт дробную часть:

```js
5n / 2n; // 2n
```

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Представление | Что учитывать |
| --- | --- | --- |
| Цена | Минимальные единицы или десятичное число | Явное правило округления |
| Большой идентификатор сервера | Строка | JSON-число может потерять точность |
| Координаты и графики | `number` | Погрешность зависит от задачи |
| Форматирование в интерфейсе | `Intl.NumberFormat` | Не использовать строку для расчётов |
| Временная метка в миллисекундах | `number` в безопасном диапазоне | Не применять 32-битные побитовые операции |
| Криптографическое большое целое | `BigInt` или байты по протоколу | Не смешивать с `number` |
