# 53 Number BigInt и точность вычислений

#### Вопрос

Как JavaScript хранит числа? Почему `0.1 + 0.2 !== 0.3`, что такое безопасное целое число (safe integer) и когда нужен `BigInt`?

#### Ответ

Тип `number` хранит числа в 64-битном двоичном формате IEEE 754 binary64 с двойной точностью. Один формат представляет целые, дробные значения, `Infinity`, `-Infinity`, `NaN` и `-0`. У него ограниченная двоичная точность: многие десятичные дроби нельзя записать конечным количеством двоичных разрядов, поэтому сохраняется ближайшее представимое значение.

```js
0.1 + 0.2; // 0.30000000000000004
```

Это не случайная ошибка JavaScript, а следствие представления чисел с плавающей точкой. Для сравнения результатов вычислений иногда используют допустимую погрешность. Её значение зависит от масштаба чисел и требований задачи: `Number.EPSILON` не является универсальным порогом для любых вычислений.

Формат binary64 точно представляет целые только от `Number.MIN_SAFE_INTEGER` до `Number.MAX_SAFE_INTEGER`, то есть от `-(2 ** 53 - 1)` до `2 ** 53 - 1`. Этот диапазон называют диапазоном безопасных целых чисел. За его пределами разные математические целые могут округлиться к одному значению типа `number`.

```js
Number.MAX_SAFE_INTEGER + 1 === Number.MAX_SAFE_INTEGER + 2; // true
```

`BigInt` представляет целые числа произвольного размера: `9007199254740993n`. Он не хранит дроби, не смешивается с `number` в обычной арифметике и не поддерживается стандартным JSON без преобразования. Большие идентификаторы в API часто передают строкой: так клиент, сервер, JSON-парсер и база данных сохраняют значение без округления.

Для денег обычно хранят целое количество минимальных единиц, например копейки, если валюта и диапазон это позволяют, либо используют библиотеку десятичной арифметики. Метод `toFixed` только округляет число при форматировании и не делает предыдущие вычисления точными.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Что такое `NaN` и как его проверять?
>
> **Ответ:** `NaN` является специальным значением типа `number`, которое обозначает некорректный результат числовой операции, например `Number("text")`. Оно не равно самому себе. `Number.isNaN(value)` проверяет значение без приведения типа. Глобальный `isNaN` сначала приводит аргумент к числу, поэтому `isNaN("text")` вернёт `true` и может скрыть, что исходное значение было строкой.

> [!followup]
> **Вопрос:** Чем `Number.isFinite` отличается от глобального `isFinite`?
>
> **Ответ:** `Number.isFinite` возвращает `true` только для конечного значения типа `number`. Глобальный `isFinite` сначала приводит значение к числу: `isFinite("")` вернёт `true`, потому что пустая строка превращается в `0`. Для проверки внешних данных обычно нужен строгий метод и предварительный контроль типа.

> [!followup]
> **Вопрос:** Чем `Number.MAX_VALUE` отличается от `Number.MAX_SAFE_INTEGER`?
>
> **Ответ:** `MAX_VALUE` является крупнейшим конечным значением типа `number`, примерно `1.8e308`. `MAX_SAFE_INTEGER` намного меньше и обозначает границу точного представления каждого целого. Тип `number` может хранить величину больше этой границы, но уже не различает все соседние целые значения.

> [!followup]
> **Вопрос:** Что такое `-0`?
>
> **Ответ:** IEEE 754 хранит положительный и отрицательный ноль. `0 === -0` возвращает `true`, но `Object.is(0, -0)` возвращает `false`, а `1 / -0` даёт `-Infinity`. Обычно знак нуля не важен, но появляется в математике, графиках и форматировании направленных величин.

> [!followup]
> **Вопрос:** Как сравнивать дробные результаты с погрешностью?
>
> **Ответ:** Проверять абсолютную или относительную разницу по требованиям задачи:
>
> ```js
> const nearlyEqual = (a, b, tolerance = 1e-10) =>
>   Math.abs(a - b) <= tolerance * Math.max(1, Math.abs(a), Math.abs(b));
> ```
>
> Порог для координат, финансов и научных данных различается. Если по требованиям нужны точные десятичные значения, сравнение с погрешностью не заменяет десятичную арифметику.

> [!followup]
> **Вопрос:** Чем `Number`, `parseInt` и `parseFloat` разбирают строку?
>
> **Ответ:** `Number("42px")` вернёт `NaN`, потому что ожидает преобразование всей строки. `parseInt("42px", 10)` и `parseFloat("3.14rem")` читают допустимую числовую часть в начале строки и останавливаются на первом неподходящем символе. Второй аргумент `parseInt` задаёт основание системы счисления, например `10` для десятичной. Частичный разбор полезен только тогда, когда единица измерения разрешена форматом данных; при проверке поля формы он может скрыть ошибочный ввод.

> [!followup]
> **Вопрос:** Почему побитовые операторы дают неожиданные результаты для больших чисел?
>
> **Ответ:** Обычные побитовые операции преобразуют `number` в 32-битное целое со знаком. Исключение `>>>`: результат этой операции является 32-битным целым без знака. Старшие разряды отбрасываются, поэтому побитовые операции нельзя использовать как быстрый способ округления больших идентификаторов или временных меток.

> [!followup]
> **Вопрос:** Что важно знать про арифметику BigInt?
>
> **Ответ:** Все операнды арифметической операции должны быть значениями `BigInt`: `1n + 1` вызывает `TypeError`. Операндом называют значение, над которым выполняется операция. Деление целых отбрасывает дробную часть: `5n / 2n === 2n`. Методы `Math` не принимают `BigInt`. Явное преобразование через `Number(bigint)` может потерять точность, поэтому его выполняют только после проверки диапазона.

> [!followup]
> **Вопрос:** Почему большое целое число из JSON может потерять точность ещё до TypeScript-проверки?
>
> **Ответ:** Число из JSON разбирается как JavaScript `number`. Значение за диапазоном безопасных целых округляется уже во время `JSON.parse`, и последующая проверка не восстановит исходные цифры. API должен передавать такой идентификатор строкой либо использовать специальный формат и согласованный с ним парсер.

> [!followup]
> **Вопрос:** Подходит ли `toFixed(2)` для финансовой логики?
>
> **Ответ:** `toFixed` форматирует `number` в строку и округляет уже сохранённое двоичное значение. Для отображения конечного результата это может быть приемлемо, если соответствует правилам продукта. Для последовательных денежных операций используют целое количество минимальных единиц либо десятичную арифметику и явно задают правило округления.

> [!followup]
> **Вопрос:** Как форматировать число для пользователя?
>
> **Ответ:** Через `Intl.NumberFormat`, указав локаль, валюту и число отображаемых разрядов. Локаль определяет языковые и региональные правила форматирования. Полученная строка не подходит для вычислений и передачи в API: приложение хранит исходное числовое значение, а форматирует его на границе пользовательского интерфейса.

#### Мини-задача

```js
const id = Number.MAX_SAFE_INTEGER + 1;

console.log(id === id + 1);
console.log(Number.isSafeInteger(id));
console.log(5n / 2n);
```

> [!followup]
> **Вопрос:** Что будет выведено?
>
> **Ответ:** `true`, `false` и `2n`. Значение типа `number` уже находится за диапазоном безопасных целых и не различает следующее целое. `Number.isSafeInteger` обнаруживает это, а деление `BigInt` возвращает целую часть без дроби.

#### Где это встречается во frontend

| Ситуация | Представление | Что учитывать |
| --- | --- | --- |
| Цена | Минимальные единицы или десятичное число | Явное правило округления |
| Большой идентификатор сервера | Строка | JSON-число может потерять точность |
| Координаты и графики | `number` | Погрешность зависит от задачи |
| Форматирование в интерфейсе | `Intl.NumberFormat` | Не использовать строку для расчётов |
| Временная метка в миллисекундах | `number` в безопасном диапазоне | Не применять 32-битные побитовые операции |
| Криптографическое большое целое | `BigInt` или байты по протоколу | Не смешивать с `number` |
