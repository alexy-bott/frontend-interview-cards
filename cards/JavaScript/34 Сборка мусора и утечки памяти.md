## Вопрос

<br>

 💬 **Как JavaScript освобождает память? Из-за чего возникают memory leaks во frontend и как их искать?**

<h2></h2>

<br>
<dl>
<dd>

Garbage collector, или сборщик мусора, освобождает память объектов, которые стали недостижимыми.

Объект считается достижимым, если до него существует цепочка сильных ссылок от roots — исходных точек живой программы. К ним относятся глобальные объекты, активные контексты выполнения и объекты, которые браузер продолжает использовать через свои внутренние механизмы.

Упрощённое правило:

- пока до объекта существует путь сильных ссылок, он остаётся в памяти;
- когда все такие пути исчезают, объект может быть освобождён сборщиком мусора.

Например, если `window` хранит listener, listener через замыкание ссылается на большой массив, массив остаётся достижимым. Если все внешние ссылки на группу объектов исчезли, сборщик может освободить её, даже когда объекты внутри группы циклически ссылаются друг на друга.

Современная сборка мусора основана на достижимости, а не только на подсчёте ссылок.

Конкретный JavaScript-движок может применять mark-and-sweep, разделение объектов по поколениям, incremental и concurrent phases. Это внутренние оптимизации. Код не знает точный момент запуска GC, не может потребовать немедленного освобождения памяти и не должен связывать бизнес-логику со сборкой мусора.

Memory leak во frontend означает, что данные остаются достижимыми для GC, хотя приложению они уже не нужны.

Типичные источники:

- listener на долгоживущем `window`, `document` или store не удалён;
- interval, observer, WebSocket или subscription продолжает работать после уничтожения владельца;
- cache растёт без ограничения и политики удаления;
- callback незавершённой async-операции удерживает крупные данные через замыкание;
- DOM node удалён из документа, но остаётся в массиве, map, ref или callback;
- повторный mount создаёт новые ресурсы без cleanup.

```js
function mountDashboard(root, rows) {
  function onResize() {
    renderChart(root, rows);
  }

  window.addEventListener("resize", onResize);

  return () => {
    window.removeEventListener("resize", onResize);
  };
}
```

Без возвращённого cleanup объект `window` продолжает хранить `onResize`, а замыкание функции удерживает `root` и `rows` даже после удаления dashboard.

Cleanup нужен не только для освобождения памяти. Он также прекращает нежелательные callbacks, запросы, таймеры и обновления уже удалённой части интерфейса.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Является ли циклическая ссылка утечкой?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет, если вся группа объектов недостижима от roots.

Например, два локальных объекта могут ссылаться друг на друга и всё равно быть собраны после завершения функции, если внешних ссылок на них не осталось.

Цикл становится проблемой только тогда, когда долгоживущая внешняя ссылка удерживает хотя бы один объект из этой группы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое detached DOM node?</strong></summary>

<dl>
<dd>
<h2></h2>

Это DOM-узел, который больше не находится в активном дереве документа, но остаётся достижимым из JavaScript.

Например, удалённая панель может продолжать храниться в глобальном массиве, ref или замыкании listener на `window`. Вместе с узлом могут удерживаться его потомки, обработчики и связанные данные.

Сам вызов `element.remove()` не гарантирует освобождение памяти. Узел может быть собран только после исчезновения всех сильных путей ссылок на него.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Освобождает ли присваивание <code>null</code> память?</strong></summary>

<dl>
<dd>
<h2></h2>

Не напрямую. Присваивание `null` только удаляет одну конкретную ссылку на объект.

Если это была последняя сильная ссылка, объект становится недостижимым и позже может быть освобождён сборщиком мусора. Если объект всё ещё хранится в listener, timer, коллекции или другом замыкании, присваивание одной переменной значения `null` ничего не освободит.

Поэтому важно находить и удалять реальный удерживающий путь, а не механически присваивать всем переменным `null`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли listener на DOM-элементе вызывает утечку после удаления элемента?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Если удалённый элемент, его listener и замкнутые данные образуют полностью недостижимую группу, GC может собрать их вместе.

Опасен listener на долгоживущем target, например `window` или `document`, потому что target продолжает удерживать callback и его замыкание. Другой частый случай — внешняя коллекция, которая продолжает хранить удалённый элемент.

Cleanup всё равно важен: он прекращает ненужное поведение и делает lifecycle ресурса предсказуемым.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как closure может удерживать лишнюю память?</strong></summary>

<dl>
<dd>
<h2></h2>

Живая функция сохраняет доступ к используемым значениям внешнего лексического окружения.

Если callback хранится в timer, subscription, listener или cache, связанные с ним данные могут жить столько же, сколько сама функция.

Проблема не в замыкании как механизме, а в слишком долгой жизни callback или в том, что он удерживает крупный объект вместо минимально необходимых данных. JavaScript-движок может оптимизировать окружение, но полагаться на такую оптимизацию вместо правильного lifecycle нельзя.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как <code>WeakMap</code> помогает с памятью?</strong></summary>

<dl>
<dd>
<h2></h2>

Ключ `WeakMap` не мешает сборщику мусора удалить объект, если других достижимых ссылок на него не осталось.

Это подходит для metadata или memoization, жизненный цикл которых должен совпадать с жизненным циклом объекта-ключа.

`WeakMap` не закрывает WebSocket, не удаляет listener с `window` и не ограничивает cache по строковым ключам. Поэтому он не заменяет явный cleanup внешних ресурсов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли использовать <code>WeakRef</code> и <code>FinalizationRegistry</code> для обязательной очистки?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Сборщик мусора может запуститься значительно позже или не запуститься до завершения работы среды. Callback `FinalizationRegistry` также не имеет гарантированного времени выполнения.

Эти API подходят для редких оптимизаций кеша и дополнительной диагностики.

Обязательные действия — закрытие соединения, освобождение lock, отписка и сохранение данных — должны выполняться явно и не зависеть от GC.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему бесконечный cache является утечкой, даже если данные ещё достижимы намеренно?</strong></summary>

<dl>
<dd>
<h2></h2>

Для сборщика мусора все записи cache являются живыми, потому что коллекция продолжает на них ссылаться.

Но с точки зрения приложения старые записи могут быть уже бесполезны, а объём занятой памяти продолжает расти. GC не может самостоятельно определить продуктовую ценность данных.

Поэтому cache нужна явная политика очистки: LRU, TTL, ограничение размера, очистка по route или user либо слабые object keys там, где это соответствует задаче.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как искать memory leak в DevTools?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала определяют повторяемый сценарий, после которого приложение должно вернуться примерно к исходному состоянию: например, несколько раз открыть и закрыть один экран.

Затем сценарий повторяют несколько раз и сравнивают heap snapshots или allocation timeline после принудительного GC в DevTools.

Для объектов, количество или retained size которых продолжает расти, изучают retaining path — цепочку сильных ссылок от объекта до root.

Detached DOM nodes, повторяющиеся listeners и closures являются подсказками. Исправлять нужно конкретный удерживающий путь: удалить listener, остановить timer, завершить subscription или очистить коллекцию.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как отличить leak от нормального роста памяти?</strong></summary>

<dl>
<dd>
<h2></h2>

JIT-компиляция, внутренние кеши, изображения и отложенный запуск GC могут временно увеличивать объём памяти.

Утечка подтверждается повторяемым сценарием: после нескольких одинаковых циклов и принудительной сборки число экземпляров или retained size продолжает расти и не выходит на стабильный уровень.

Один снимок памяти редко позволяет сделать надёжный вывод. Важно сравнивать несколько одинаковых циклов и искать конкретный удерживающий путь.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что очищать в React effect?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно очищать всё, что effect подключил к внешней системе и что продолжает жить самостоятельно:

- DOM listeners;
- timers;
- observers;
- store subscriptions;
- WebSocket и другие socket handlers;
- listeners `MediaQueryList`;
- асинхронные операции, если они поддерживают отмену.

Cleanup должен быть симметричен setup и безопасно выдерживать повторный цикл setup → cleanup → setup в Strict Mode development.

Обычные локальные объекты и вычисления вручную очищать не нужно: после исчезновения ссылок ими займётся сборщик мусора.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Удерживающий путь | Cleanup или ограничение |
| --- | --- | --- |
| Listener на `window` | `window → callback → closure` | `removeEventListener` или AbortSignal |
| Polling | Timer registry → callback | `clearTimeout`/`clearInterval` |
| WebSocket | Connection → handlers/state | Unsubscribe и `close` по ownership |
| Removed UI | Collection/ref → detached node | Удалить внешнюю ссылку |
| Cache | Global cache → entries | LRU, TTL, лимит или WeakMap |
| React effect | Повторный setup → ресурсы | Симметричный cleanup |
