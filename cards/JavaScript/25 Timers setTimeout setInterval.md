## Вопрос

<br>

 💬 **Как работают `setTimeout` и `setInterval`? Почему указанная задержка не гарантирует точное время выполнения?**

<h2></h2>

<br>
<dl>
<dd>

Таймеры являются API среды выполнения, а не частью самого языка JavaScript.

`setTimeout(callback, delay)` регистрирует однократный таймер. Значение `delay` указывает минимальное время, которое должно пройти до того, как callback сможет быть запланирован для выполнения.

```js
const timerId = setTimeout(() => {
  console.log("later");
}, 1000);

clearTimeout(timerId);
```

Даже после окончания задержки callback не выполняется немедленно. Сначала должна завершиться текущая task, освободиться main thread и выполниться накопившаяся очередь microtasks. Только после этого event loop может выбрать task таймера.

Поэтому задержка является нижней границей, а не точным расписанием. Если main thread занят длинным синхронным кодом, очередь microtasks долго не заканчивается или браузер ограничивает фоновую вкладку, callback запустится позже.

`setInterval(callback, delay)` планирует повторные вызовы callback примерно через указанные интервалы.

На одном main thread два синхронных callback интервала не выполняются одновременно. Но если callback работает долго, следующий вызов может произойти почти сразу после его завершения, а фактическое расписание начнёт отклоняться от ожидаемого. Такое отклонение называют timer drift.

Если callback интервала является `async`-функцией, `setInterval` не ожидает возвращённый Promise. Callback синхронно запускает асинхронную операцию и завершается, после чего следующий интервал может запустить ещё одну операцию до завершения предыдущей.

Для отмены используют идентификатор, возвращённый `setTimeout` или `setInterval`. `clearTimeout` и `clearInterval` предотвращают ещё не начавшийся вызов соответствующего таймера.

Если callback уже начал выполняться, очистка таймера не может остановить его текущий запуск.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему <code>setTimeout(callback, 0)</code> не выполняется сразу?</strong></summary>

<dl>
<dd>
<h2></h2>

`setTimeout(callback, 0)` всё равно создаёт отдельную task.

Сначала полностью выполняется текущий JavaScript-код. После завершения текущей task среда очищает очередь microtasks, например callbacks Promise. Только затем event loop может перейти к task таймера.

Поэтому `0` означает отсутствие дополнительной запрошенной задержки, а не синхронный вызов callback.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Существует ли минимальная задержка таймера?</strong></summary>

<dl>
<dd>
<h2></h2>

Да. Браузер может увеличить слишком маленькую задержку.

По HTML Standard при глубокой цепочке вложенных таймеров задержка меньше `4` миллисекунд ограничивается значением около `4` миллисекунд.

Более сильные ограничения применяются к фоновым вкладкам, неактивным страницам и энергосберегающим режимам. В таких условиях callback может вызываться значительно реже запрошенного интервала.

Поэтому таймеры нельзя использовать как высокоточные часы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое timer drift?</strong></summary>

<dl>
<dd>
<h2></h2>

Timer drift — это разница между ожидаемым и фактическим временем запусков таймера.

Она появляется из-за занятости main thread, продолжительности callback, очереди других задач и ограничений браузера. Если при каждом вызове просто уменьшать счётчик на единицу, задержки будут постепенно накапливать ошибку.

Для обратного отсчёта лучше хранить конечный момент времени и при каждом callback заново вычислять остаток:

```js
const remaining = deadline - Date.now();
```

Тогда поздний запуск одного callback не изменит само значение конечного времени.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда recursive <code>setTimeout</code> лучше <code>setInterval</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Recursive `setTimeout` подходит, когда следующую итерацию нужно запланировать только после завершения предыдущей.

Это особенно полезно для polling. Сначала код ожидает ответ сервера, обрабатывает результат или ошибку и только затем создаёт следующий таймер.

`setInterval` не ожидает завершения асинхронного callback и может запустить несколько запросов одновременно.

```js
let stopped = false;

async function poll() {
  try {
    await loadStatus();
  } finally {
    if (!stopped) setTimeout(poll, 1000);
  }
}
```

В этом примере пауза перед следующим вызовом начинается после завершения `loadStatus`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как сделать polling устойчивым?</strong></summary>

<dl>
<dd>
<h2></h2>

Следующую итерацию запускают только после завершения предыдущей, чтобы запросы не накладывались друг на друга.

Также обычно предусматривают:

- отмену текущего запроса через `AbortController`;
- остановку polling при размонтировании компонента или уходе со страницы;
- обработку offline-состояния;
- ограничение повторов после ошибок;
- backoff — постепенное увеличение паузы после неудачных запросов.

В фоновой вкладке браузер может значительно замедлить таймеры. Поэтому текущее серверное состояние и время нельзя определять только по количеству локальных вызовов таймера.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему для анимации лучше <code>requestAnimationFrame</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`requestAnimationFrame` вызывает callback перед подготовкой следующего кадра и синхронизируется с частотой обновления экрана.

Браузер передаёт callback временную метку кадра и может приостановить анимацию на скрытой вкладке.

`setInterval` не знает, когда браузер будет отрисовывать кадр. Из-за этого изменение DOM может происходить между кадрами, выполнять лишнюю работу или создавать заметные рывки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит с <code>this</code>, если передать метод прямо в таймер?</strong></summary>

<dl>
<dd>
<h2></h2>

При передаче `object.method` таймер получает только функцию. Последующий вызов больше не содержит объекта слева от точки, поэтому метод теряет ожидаемое значение `this`.

Нельзя рассчитывать, что внутри callback `this` останется исходным объектом.

Обычно передают стрелочную обёртку:

```js
setTimeout(() => object.method(), 1000);
```

Либо заранее создают связанную функцию:

```js
setTimeout(object.method.bind(object), 1000);
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему timers нужно очищать в React effect?</strong></summary>

<dl>
<dd>
<h2></h2>

Effect может выполниться повторно при изменении зависимостей, а компонент может размонтироваться до запуска таймера.

Без cleanup предыдущий таймер продолжит существовать. Это может создать несколько одинаковых интервалов, запустить устаревший сценарий или выполнить callback с данными старого рендера.

Cleanup отменяет таймер, созданный конкретным запуском effect:

```js
useEffect(() => {
  const timerId = setInterval(update, 1000);

  return () => clearInterval(timerId);
}, []);
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли таймер удерживать память?</strong></summary>

<dl>
<dd>
<h2></h2>

Пока таймер зарегистрирован, среда должна хранить ссылку на его callback. Callback через замыкание может удерживать другие объекты, данные компонента или DOM-узлы.

Однократный timeout после выполнения обычно перестаёт удерживаться системой таймеров, если на него и связанные данные больше нет других ссылок.

Бесконечный interval или постоянно создаваемый recursive timeout нужно явно остановить вместе с жизненным циклом владельца.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему нельзя передавать строку вместо callback?</strong></summary>

<dl>
<dd>
<h2></h2>

Запись `setTimeout("code", delay)` заставляет среду компилировать и выполнять строку подобно `eval`.

Такой код выполняется в глобальном контексте, хуже анализируется инструментами, усложняет отладку и может создать риск выполнения внедрённого кода.

В таймер следует передавать функцию:

```js
setTimeout(run, delay);
```

Дополнительные данные можно передать через замыкание или аргументы таймера.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```js
const startedAt = Date.now();

setTimeout(() => {
  console.log(Date.now() - startedAt >= 50);
}, 50);

const end = Date.now() + 100;
while (Date.now() < end) {
  // Main thread занят синхронной работой.
}
```

<details>
<summary><strong>Что будет выведено и примерно когда выполнится callback?</strong></summary>

<dl>
<dd>
<h2></h2>

Будет выведено `true`.

Таймер станет готов к выполнению не раньше чем через `50` миллисекунд. Но в этот момент main thread всё ещё занят синхронным циклом, который выполняется примерно `100` миллисекунд.

Callback сможет запуститься только после завершения цикла, освобождения текущего call stack и обработки microtasks.

Поэтому он выполнится примерно через `100` миллисекунд или позже, но не ровно через `50` миллисекунд.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Подход | Что учитывать |
| --- | --- | --- |
| Debounce | Переносимый `setTimeout` | Отменять предыдущий запуск |
| Polling API | Recursive timeout | Не накладывать запросы и поддержать отмену |
| Обратный отсчёт | Расчёт от deadline | Не считать время по количеству ticks |
| React effect | Cleanup timer | Не оставлять старые callbacks |
| Анимация | `requestAnimationFrame` | Синхронизация с кадром |
| Фоновая вкладка | Page Visibility и серверное время | Таймеры могут сильно ограничиваться |
