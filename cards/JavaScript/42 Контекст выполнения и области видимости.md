## Вопрос

<br>

 💬 **Что такое контекст выполнения, лексическое окружение и цепочка областей видимости?**

<h2></h2>

<br>
<dl>
<dd>

Контекст выполнения (`execution context`) описывает состояние, необходимое движку для выполнения текущего кода: связанные окружения, сведения о вызове и позицию, с которой должно продолжаться выполнение.

Отдельные контексты создаются для глобального кода, модулей, вызовов функций и некоторых других механизмов языка. Активные контексты образуют стек вызовов (`call stack`).

```js
function outer() {
  function inner() {
    return 1;
  }

  return inner();
}

outer();
```

При вызове `outer` её контекст помещается поверх глобального. При вызове `inner` поверх него появляется следующий контекст. После возврата контексты функций снимаются со стека в обратном порядке.

Лексическое окружение (`lexical environment`) является структурой спецификации, через которую имена связываются с переменными, функциями и другими объявлениями. Оно состоит из записи окружения с привязками и ссылки на внешнее окружение.

Когда код обращается к идентификатору, движок ищет его привязку в текущем окружении. Если её нет, поиск продолжается во внешнем окружении и далее до конца цепочки. Это называют scope chain, или цепочкой областей видимости:

```js
const value = "global";

function outer() {
  const value = "outer";

  return function inner() {
    return value;
  };
}

outer()(); // "outer"
```

Scope chain не является отдельным массивом переменных. Она образуется ссылками каждого окружения на внешнее окружение.

JavaScript использует лексическую область видимости: внешнее окружение функции определяется местом её создания в исходном коде. Место последующего вызова не меняет эту цепочку.

Область видимости и лексическое окружение связаны, но не тождественны. Scope описывает статическое правило: в какой части исходного кода доступно имя. Lexical environment содержит конкретные привязки, существующие во время выполнения этой области.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что происходит с объявлениями до выполнения инструкций функции?</strong></summary>

<dl>
<dd>
<h2></h2>

При создании контекста движок подготавливает окружения и привязки объявлений. `var` инициализируется значением `undefined`, function declaration получает объект функции, а `let`, `const` и `class` остаются неинициализированными до выполнения соответствующего объявления.

После подготовки привязок инструкции выполняются по порядку.

Деление на «фазу создания» и «фазу выполнения» является полезной учебной моделью. Точные шаги спецификации зависят от вида кода, но эта модель объясняет hoisting и TDZ без ошибочной идеи, что объявления физически перемещаются в начало файла или функции.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем контекст выполнения отличается от лексического окружения?</strong></summary>

<dl>
<dd>
<h2></h2>

Контекст выполнения представляет активное выполнение кода: текущую функцию или модуль, связанные окружения, сведения о вызове и состояние продолжения.

Лексическое окружение отвечает за хранение привязок имён и связь с внешней областью.

Один контекст выполнения может последовательно использовать несколько лексических окружений, например при входе во вложенные блоки.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Создаёт ли каждый блок новый контекст выполнения?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Обычный блок `{}` не создаёт отдельный execution context.

Если внутри блока есть объявления `let`, `const`, `class` или другие блочные привязки, для него может быть создано новое лексическое окружение. При этом код продолжает выполняться в том же контексте функции, скрипта или модуля.

Новый контекст выполнения обычно появляется при вызове функции, а не при входе в каждый блок.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит с окружением после выхода функции со стека?</strong></summary>

<dl>
<dd>
<h2></h2>

Если окружение больше недостижимо, оно может быть освобождено сборщиком мусора.

Если созданная внутри функция использует внешние привязки, её внутренний слот `[[Environment]]` сохраняет ссылку на соответствующее окружение.

Контекст завершённого вызова уже не находится в call stack, но нужные функции данные остаются достижимыми через замыкание.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем lexical scope отличается от dynamic scope?</strong></summary>

<dl>
<dd>
<h2></h2>

При lexical scope функция ищет внешние имена относительно места своего объявления в исходном коде.

При dynamic scope поиск зависел бы от цепочки функций, которые вызвали её во время выполнения. JavaScript использует lexical scope.

Поэтому передача callback в таймер, Promise или обработчик события не меняет доступные ему внешние переменные.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит при затенении переменной?</strong></summary>

<dl>
<dd>
<h2></h2>

Внутреннее окружение создаёт привязку с тем же именем, и поиск останавливается на ней. Внешнее значение не изменяется, но становится недоступно по этому имени внутри текущей области.

Если внутренняя привязка находится в TDZ, движок не продолжает поиск во внешнем окружении. Обращение завершается ошибкой `ReferenceError`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем окружение ES-модуля отличается от глобального скрипта?</strong></summary>

<dl>
<dd>
<h2></h2>

Верхнеуровневые объявления ES-модуля находятся в модульном окружении, не становятся свойствами `window` и доступны другим модулям только через `export` и `import`.

Импорты являются живыми привязками: потребитель видит актуальное экспортируемое значение после его инициализации.

Глобальное окружение браузерного classic script сочетает объектную часть для некоторых `var` и function declarations с отдельной декларативной частью для `let`, `const` и `class`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Где хранится <code>this</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`this` не является обычным идентификатором и не ищется по scope chain как локальная переменная.

Обычная функция создаёт собственную `this`-привязку. Её значение определяется формой вызова функции.

Стрелочная функция собственной `this`-привязки не создаёт. При обращении к `this` она использует привязку внешнего окружения.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```js
const value = "global";

function createReader() {
  const value = "created";

  return function read() {
    return value;
  };
}

function run(callback) {
  const value = "called";
  return callback();
}

console.log(run(createReader()));
```

<details>
<summary><strong>Почему будет выведено <code>"created"</code>, а не <code>"called"</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Функция `read` создана внутри `createReader`, поэтому её ссылка на внешнее окружение ведёт к окружению с привязкой `value = "created"`.

Вызов функции из `run` создаёт новый контекст в call stack, но не меняет лексическую цепочку `read`. Локальная переменная `value` из `run` не входит в её scope chain.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что объясняет модель |
| --- | --- |
| Замыкание | Окружение может жить дольше вызова, который его создал |
| React callback | Функция принадлежит окружению конкретного рендера |
| Hoisting и TDZ | Привязка создаётся до выполнения, но не всегда инициализирована |
| ES-модули | Верхнеуровневые имена имеют модульную область |
| Debugger | Панели Call Stack и Scope показывают разные части модели |
| `this` | Определяется вызовом, а не обычным поиском имени |
