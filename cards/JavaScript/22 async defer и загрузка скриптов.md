## Вопрос

<br>

 💬 **Чем отличаются обычный `<script>`, `defer`, `async` и `type="module"`?**

<h2></h2>

<br>
<dl>
<dd>

Атрибуты определяют, загружается ли скрипт параллельно с разбором HTML, когда он выполнится и сохраняется ли порядок между несколькими файлами.

| Подключение | Загрузка | Выполнение | Порядок |
| --- | --- | --- | --- |
| `<script src>` | Останавливает HTML parser до загрузки | До продолжения разбора HTML | Порядок документа |
| `<script defer src>` | Параллельно с разбором HTML | После разбора, до `DOMContentLoaded` | Порядок документа |
| `<script async src>` | Параллельно с разбором HTML | Когда файл готов и main thread свободен | Не гарантирован |
| `<script type="module" src>` | Граф загружается параллельно | После разбора HTML по умолчанию | Зависимость выполняется раньше импортирующего модуля |

HTML parser, или парсер HTML, читает разметку и строит DOM. Обычный classic script без `async`, `defer` и `type="module"` является parser-blocking.

Когда парсер встречает внешний такой скрипт, он останавливается, ждёт загрузку файла и его выполнение, а только затем продолжает читать HTML. Это необходимо, потому что скрипт может вызвать `document.write` или изменить уже построенную часть документа.

`defer` относится к внешним classic scripts. Файлы загружаются параллельно с разбором HTML, но выполняются только после его завершения. Несколько deferred scripts выполняются в порядке расположения элементов `<script>` в документе.

Событие `DOMContentLoaded` ждёт загрузки и выполнения deferred scripts. Для inline classic script атрибут `defer` не действует.

`async` используют для внешнего независимого скрипта. Файл загружается параллельно с разбором HTML и выполняется, когда загрузка завершена и main thread освободился.

Если HTML в этот момент ещё разбирается, выполнение `async`-скрипта приостанавливает парсер. При этом скрипт не может прервать другой уже выполняющийся JavaScript: текущая задача сначала завершится.

Порядок между несколькими `async`-скриптами не гарантирован. Более поздний небольшой файл может загрузиться и выполниться раньше предыдущего большого файла. `DOMContentLoaded` может произойти как до, так и после выполнения такого скрипта.

`type="module"` включает ESM. Module script имеет собственную область видимости, автоматически выполняется в strict mode и может использовать `import` и `export`.

Внешний модуль загружает не только свой файл, но и граф импортируемых зависимостей. Зависимости выполняются до импортирующего их модуля.

Обычные module scripts имеют отложенное поведение по умолчанию, в том числе inline module scripts: они выполняются после завершения разбора HTML. Поэтому атрибут `defer` для модуля не нужен и не меняет его поведение.

Для загрузки module scripts с другого origin применяется CORS. Если добавить `async` к внешнему module script, его граф выполнится сразу после готовности и не будет ждать обычную очередь отложенных скриптов.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что именно блокирует обычный script?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычный parser-inserted script блокирует продолжение разбора HTML с того места, где браузер встретил элемент `<script>`.

Для внешнего файла парсер ждёт его загрузку, подготовку и выполнение. Inline script не требует сетевой загрузки, но также выполняется до того, как браузер продолжит разбирать следующую разметку.

Долгое выполнение занимает main thread, поэтому может задерживать не только парсинг, но и отрисовку, обработку пользовательских событий и выполнение других задач JavaScript.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему основной bundle обычно подключают как module script или с <code>defer</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Браузер обнаруживает файл в `<head>` и может сразу начать его загрузку, одновременно продолжая строить DOM.

Код выполняется после завершения разбора документа, поэтому к этому моменту элементы HTML уже созданы. При этом загрузка скрипта не создаёт сетевую паузу внутри работы HTML parser.

Module script дополнительно предоставляет стандартную систему ESM, отдельную область видимости и граф зависимостей.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Для чего подходит <code>async</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`async` подходит для независимого кода, которому не нужен определённый порядок относительно других скриптов и готовность DOM в конкретный момент.

Типичные примеры — автономная аналитика, реклама или внешний виджет. Если один `async`-скрипт зависит от другого, результат становится непредсказуемым, потому что первым выполнится файл, который раньше загрузится.

Даже независимый third-party script может занять main thread, ухудшить производительность и получить доступ к странице. `async` управляет загрузкой и моментом выполнения, но не решает вопросы производительности, безопасности и доверия.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что будет, если одновременно указать <code>async</code> и <code>defer</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

У внешнего classic script в современных браузерах при одновременном наличии `async` и `defer` используется поведение `async`: файл выполняется после готовности и не сохраняет порядок deferred scripts.

Исторически `defer` добавляли как fallback для старых браузеров без поддержки `async`. В современном коде одновременное указание атрибутов обычно только скрывает выбранную семантику.

Для module script атрибут `defer` не влияет на поведение. Наличие `async` переводит внешний модуль из стандартного отложенного режима в выполнение после готовности его графа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Гарантирует ли <code>defer</code>, что DOM полностью готов?</strong></summary>

<dl>
<dd>
<h2></h2>

К моменту выполнения deferred script HTML уже разобран и элементы разметки созданы. `document.readyState` находится в состоянии `interactive`.

Для поиска и изменения элементов DOM этого обычно достаточно. Однако изображения, шрифты и другие внешние ресурсы ещё могут загружаться, а размеры элементов — изменяться после их загрузки.

Если логика зависит от конкретного ресурса или его размеров, нужно ждать загрузку этого ресурса либо использовать подходящий механизм наблюдения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как <code>DOMContentLoaded</code> связан со скриптами?</strong></summary>

<dl>
<dd>
<h2></h2>

Событие `DOMContentLoaded` происходит после завершения разбора HTML и выполнения deferred classic scripts и обычных module scripts.

`Async`-скрипт не является обязательным условием для этого события. В зависимости от скорости загрузки он может выполниться как до, так и после `DOMContentLoaded`.

Событие `window.load` происходит позже и ждёт загрузку зависимых ресурсов страницы, включая скрипты, изображения и стили.

Если код добавляет listener динамически и может запуститься после `DOMContentLoaded`, сначала проверяют `document.readyState`, чтобы не ждать событие, которое уже произошло.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем module script отличается от <code>defer</code> classic script?</strong></summary>

<dl>
<dd>
<h2></h2>

Deferred classic scripts разделяют глобальную область видимости и выполняются в порядке элементов `<script>` в документе.

Module script имеет собственную область видимости, автоматически использует strict mode и поддерживает зависимости через `import` и `export`. Его верхнеуровневые переменные не становятся свойствами глобального объекта.

Один модуль по одному и тому же разрешённому URL выполняется один раз, даже если импортируется из нескольких мест. Для загрузки модуля с другого origin требуется корректная CORS-настройка.

Порядок внутри module graph определяется связями импортов: зависимости должны быть подготовлены и выполнены до импортирующего их модуля.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как ведут себя скрипты, добавленные через JavaScript?</strong></summary>

<dl>
<dd>
<h2></h2>

Внешний classic script, созданный через `document.createElement("script")`, по умолчанию загружается и выполняется как `async`.

Если нескольким динамически добавленным classic scripts нужен порядок, свойство `async` устанавливают в `false` до вставки элементов в документ. Тогда такие скрипты выполняются в порядке их добавления после загрузки.

Для модулей чаще используют `import()`. Он асинхронно загружает модуль и возвращает `Promise`, через который можно явно обработать успешную загрузку или ошибку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужен <code>modulepreload</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`<link rel="modulepreload" href="...">` позволяет браузеру заранее начать загрузку и подготовку модуля, не выполняя его немедленно.

Браузер также может заранее обнаружить и загрузить зависимости этого модуля. Это сокращает задержку, если важный module script или его импорт обнаруживается поздно.

Избыточный preload конкурирует за сеть с другими критическими ресурсами, поэтому `modulepreload` добавляют для действительно важных модулей и проверяют результат измерениями.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему script в конце <code>body</code> не всегда равен <code>defer</code> в <code>head</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Оба варианта позволяют выполнить код после разбора большей части или всей разметки.

Но script в конце `body` браузер может обнаружить только после того, как парсер дойдёт до конца документа. Поэтому загрузка файла может начаться позже.

`defer` в `head` позволяет раньше обнаружить и начать загружать файл, одновременно продолжая строить DOM. Выполнение при этом всё равно откладывается до завершения парсинга.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Сценарий | Выбор | Причина |
| --- | --- | --- |
| Точка входа современного приложения | `type="module"` | ESM и deferred-поведение |
| Legacy bundle с зависимостями | `defer` | Порядок документа и готовый DOM |
| Независимая аналитика | `async` | Выполнение сразу после готовности файла |
| Поздняя функциональность | `import()` | Загрузка по пользовательскому сценарию |
| Важный поздно обнаруживаемый модуль | `modulepreload` после измерений | Более ранняя загрузка графа |
| Third-party script | Минимально необходимый `async` или отложенная загрузка | Он всё равно выполняется на main thread и имеет доступ к странице |
