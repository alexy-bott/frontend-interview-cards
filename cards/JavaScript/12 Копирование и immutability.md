## Вопрос

<br>

 💬 **Чем отличаются поверхностное и глубокое копирование? Почему неизменяемые обновления важны во frontend?**

<h2></h2>

<br>
<dl>
<dd>

Присваивание объекта другой переменной не создаёт копию. Обе переменные получают одну и ту же ссылку и обращаются к одному объекту:

```js
const original = { name: "Ada" };
const alias = original;

alias.name = "Grace";
console.log(original.name); // "Grace"
```

Поверхностная копия (`shallow copy`) создаёт новый внешний объект или массив, но сохраняет ссылки на вложенные объекты. Её можно получить через spread-синтаксис, `Object.assign`, `Array.from`, `slice` и другие подходящие методы:

```js
const state = {
  user: { name: "Ada" },
  page: 1,
};

const copy = { ...state };

copy !== state;           // true
copy.user === state.user; // true
```

Объект `copy` является новым, но его свойство `user` указывает на тот же вложенный объект, что и `state.user`.

Глубокая копия (`deep copy`) создаёт новый граф данных, в котором вложенные изменяемые объекты также копируются. Универсального способа клонировать любое значение JavaScript нет: функции, DOM-узлы, экземпляры классов, Proxy и платформенные объекты имеют разное поведение и не всегда могут быть корректно скопированы.

Для поддерживаемых типов данных платформа предоставляет `structuredClone`:

```js
const cloned = structuredClone({
  createdAt: new Date(),
  tags: new Set(["js"]),
});
```

Алгоритм поддерживает циклические ссылки и многие встроенные типы, включая `Date`, `Map`, `Set`, `ArrayBuffer` и типизированные массивы. Он не клонирует функции и DOM-узлы. У объекта пользовательского класса не сохраняются прототип, методы и поведение полноценного экземпляра класса.

Неизменяемое обновление (`immutable update`) означает, что существующая версия данных не изменяется. Новые объекты создаются только на пути к изменённому значению:

```js
const nextState = {
  ...state,
  user: {
    ...state.user,
    name: "Grace",
  },
};
```

Корневой объект и изменённый `user` получили новые ссылки, а остальные неизменённые ветки можно переиспользовать. Такой подход называется структурным разделением (`structural sharing`): новая и старая версии данных совместно используют неизменённые части.

Это дешевле полного глубокого копирования и позволяет механизмам, основанным на сравнении ссылок, быстро определить, какие данные изменились. Такой подход важен для React, Redux, мемоизированных компонентов и селекторов.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему object spread не делает глубокую копию?</strong></summary>

<dl>
<dd>
<h2></h2>

Object spread перебирает собственные перечисляемые свойства источника и записывает их значения в новый объект.

Если значение свойства является примитивом, копируется сам примитив. Если значением является объект или массив, копируется ссылка на него. Spread не проходит рекурсивно по всей вложенной структуре.

Поэтому при обновлении `state.user.name` новые объекты нужны для `state` и `state.user`, но остальные неизменённые ветки можно оставить прежними.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда использовать <code>structuredClone</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`structuredClone` используют, когда действительно нужна независимая копия всего поддерживаемого графа данных. Например, для отдельного редактируемого черновика, копирования `Map`, `Set`, `Date`, циклической структуры или бинарного буфера.

Перед использованием нужно учитывать объём данных, потому что глубокое копирование требует времени и дополнительной памяти.

Для обычного обновления React state глубокое копирование всего дерева чаще не нужно. Оно создаёт новые ссылки даже для неизменённых веток, увеличивает объём работы и мешает полезной мемоизации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что означает transfer в <code>structuredClone</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Некоторые данные, например `ArrayBuffer`, можно не копировать, а передать новому объекту через список `transfer`.

После передачи новый объект получает доступ к содержимому буфера, а исходный буфер отсоединяется и больше не содержит доступных байтов. Это позволяет не копировать большой объём бинарных данных, например при передаче в Worker.

После такой операции исходный код не должен продолжать использовать переданный буфер.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>JSON.parse(JSON.stringify(value))</code> не является универсальным deep clone?</strong></summary>

<dl>
<dd>
<h2></h2>

JSON поддерживает только ограниченный набор данных.

При такой сериализации:

- `Date` превращается в строку;
- `undefined`, функции и символьные свойства теряются;
- `NaN`, `Infinity` и `-Infinity` превращаются в `null`;
- `Map` и `Set` не сохраняют свою структуру;
- `BigInt` и циклические ссылки вызывают ошибку.

Такой способ допустим только тогда, когда данные заранее гарантированно соответствуют формату JSON и преобразование в JSON является ожидаемым поведением.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему мутация state мешает React и мемоизации?</strong></summary>

<dl>
<dd>
<h2></h2>

Многие механизмы во frontend определяют изменение данных с помощью сравнения ссылок.

Если объект состояния изменить напрямую и снова передать ту же ссылку, React может посчитать значение прежним. `React.memo`, селекторы и другие механизмы мемоизации также не получают новую ссылку, по которой можно заметить изменение.

Мутация дополнительно изменяет предыдущую версию данных задним числом. Из-за этого становится сложнее сравнивать состояния, отменять изменения и искать причину ошибки.

Новая ссылка на каждом изменённом уровне делает обновление заметным. Но создавать новые объекты для всех веток без причины тоже не нужно: это вызывает лишние рендеры и пересчёты. Поэтому используют точечное неизменяемое обновление, а не полный deep clone.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему в Redux Toolkit разрешена запись <code>state.user.name = ...</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Внутри case reducer Redux Toolkit передаёт не исходное состояние, а специальный Proxy-черновик библиотеки Immer.

Записи в этот черновик фиксируются как набор изменений. После выполнения reducer Immer создаёт новое состояние только для изменённых веток и переиспользует неизменённые части. Исходное Redux-состояние при этом не изменяется.

Такой синтаксис выглядит как мутация, но выполняется внутри управляемого механизма Immer. За его пределами обычная запись в объект остаётся обычной мутацией JavaScript.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Означает ли immutability использование <code>Object.freeze</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Immutability — это подход к обновлению данных: существующий объект не изменяют, а создают новую версию с нужными изменениями.

`Object.freeze` является дополнительным ограничением во время выполнения. Он запрещает добавлять и удалять свойства объекта, а также изменять значения его обычных собственных свойств.

Заморозка действует только на сам объект. Вложенные объекты остаются изменяемыми, пока их не заморозили отдельно.

В строгом режиме попытка нарушить эти ограничения обычно выбрасывает `TypeError`, а в нестрогом режиме запись может молча не сработать. Для immutable update использовать `Object.freeze` необязательно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Всегда ли новый объект означает изменение данных?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Запись `{ ...user }` создаёт новый объект и новую ссылку, даже если все значения остались прежними.

Для сравнения по ссылке это считается изменением идентичности объекта, хотя его бизнес-данные могут полностью совпадать. Такая новая ссылка может вызвать лишний рендер или повторный расчёт.

Поэтому новые объекты создают для действительно изменённых веток, а ссылки на неизменённые данные стараются сохранять.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```js
const state = {
  user: {
    name: "Ada",
    address: { city: "Moscow" },
  },
  theme: "dark",
};

const next = {
  ...state,
  user: {
    ...state.user,
    name: "Grace",
  },
};

console.log(next === state);
console.log(next.user === state.user);
console.log(next.user.address === state.user.address);
console.log(next.theme === state.theme);
```

<details>
<summary><strong>Какие сравнения будут истинными и почему?</strong></summary>

<dl>
<dd>
<h2></h2>

Первые два сравнения вернут `false`.

Для корневого объекта `next` и вложенного объекта `next.user` были созданы новые объекты, потому что путь к изменённому свойству `name` должен получить новые ссылки.

`next.user.address === state.user.address` вернёт `true`, потому что объект `address` не изменялся и его ссылка была переиспользована.

`next.theme === state.theme` также вернёт `true`. `theme` содержит примитивную строку, а примитивы сравниваются по значению.

Это пример структурного разделения: новые объекты создаются только на изменённом пути, а остальные данные переиспользуются.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Подход |
| --- | --- |
| React state | Создавать новые объекты только на изменённом пути и не мутировать предыдущее состояние |
| Redux Toolkit | Immer преобразует изменения Proxy-черновика в immutable update |
| Мемоизированный селектор | Стабильные ссылки позволяют сохранить результат в кэше |
| Редактор черновика | Иногда оправдан независимый `structuredClone` |
| Web Worker | Используется клонирование или transfer поддерживаемых данных |
| API-кэш | Общий объект ответа нельзя случайно мутировать для всех потребителей |
