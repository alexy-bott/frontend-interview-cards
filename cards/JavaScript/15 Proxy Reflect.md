## Вопрос

<br>

 💬 **Как работают `Proxy` и `Reflect`? Какие ограничения прокси важны во frontend?**

<h2></h2>

<br>
<dl>
<dd>

`Proxy` создаёт отдельный объект-обёртку вокруг целевого объекта (`target`). Операции, выполненные через Proxy, можно перехватывать: чтение свойства, запись, проверку через `in`, удаление, вызов функции и другие действия.

Второй аргумент `handler` содержит ловушки (`traps`) для нужных операций: `get` вызывается при чтении свойства, `set` при записи, `has` при использовании оператора `in`, а `deleteProperty` при удалении.

```js
const user = { name: "Ada" };

const proxy = new Proxy(user, {
  get(target, property, receiver) {
    console.log("read", property);
    return Reflect.get(target, property, receiver);
  },

  set(target, property, value, receiver) {
    console.log("write", property, value);
    return Reflect.set(target, property, value, receiver);
  },
});
```

Если для операции нет соответствующей ловушки, JavaScript выполняет обычную операцию с `target`.

`Reflect` — это набор методов для стандартных операций с объектами: `Reflect.get`, `Reflect.set`, `Reflect.has`, `Reflect.deleteProperty`, `Reflect.ownKeys`, `Reflect.construct` и другие.

Внутри ловушки соответствующий метод `Reflect` удобно использовать, чтобы выполнить обычную операцию после дополнительной логики. Например, ловушка может сначала записать действие в лог, а затем передать чтение или запись объекту `target`. Использовать `Reflect` необязательно, но он обычно точнее передаёт стандартное поведение операции.

Аргумент `receiver` — это фактический объект, с которого началось чтение или присваивание. Обычно им является сам Proxy, но при наследовании это может быть другой объект. `receiver` важен для getters и setters, потому что определяет значение их `this`.

Поэтому `Reflect.get(target, property, receiver)` лучше сохраняет обычное поведение свойства, чем прямое чтение `target[property]`.

Proxy не копирует целевой объект и имеет другую идентичность:

```js
proxy !== user; // true
```

При этом операция через Proxy может изменить сам `target`, если ловушка делегирует её целевому объекту. Но операция, выполненная напрямую с `target`, обходит Proxy и не вызывает его ловушки.

Перехват внешнего объекта также не делает его вложенные объекты прокси автоматически. Если получить вложенный объект и изменить его напрямую, ловушки внешнего Proxy не сработают. Реактивные библиотеки отдельно оборачивают вложенные значения и самостоятельно управляют зависимостями.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему ловушка <code>set</code> должна вернуть <code>boolean</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Результат ловушки сообщает JavaScript, удалось ли выполнить присваивание. `true` означает успех, а `false` — отказ от записи.

`Reflect.set` уже возвращает подходящее логическое значение, поэтому его результат обычно возвращают из ловушки:

```js
return Reflect.set(target, property, value, receiver);
```

Если ловушка вернёт `false`, присваивание в строгом режиме завершится `TypeError`. В нестрогом режиме неуспешная запись обычно просто не изменит значение.

Возврат `true` не позволяет обойти обязательные правила объекта. Если ловушка сообщит об успехе, но нарушит ограничения свойства, движок всё равно может выбросить `TypeError`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое инварианты Proxy?</strong></summary>

<dl>
<dd>
<h2></h2>

Инварианты — это основные гарантии объектной модели, которые Proxy не может нарушить даже с помощью собственных ловушек.

Например, Proxy не может сообщить, что успешно изменил собственное свойство, которое одновременно является неизменяемым (`writable: false`) и неудаляемым (`configurable: false`). Ловушка `ownKeys` также не может скрыть некоторые неудаляемые свойства объекта.

Сначала выполняется код ловушки, а затем движок проверяет, не противоречит ли результат реальному состоянию `target`. При нарушении возникает `TypeError`.

Таким образом, Proxy может изменять наблюдаемое поведение объекта, но не может отменять фундаментальные ограничения его свойств.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как Proxy используют для реактивности?</strong></summary>

<dl>
<dd>
<h2></h2>

Ловушка `get` может запоминать, какое вычисление прочитало определённое свойство. Ловушка `set` может сообщать этим вычислениям, что значение изменилось и результат нужно пересчитать.

Сам Proxy предоставляет только точки перехвата. Он не хранит зависимости, не объединяет несколько обновлений и не решает, какие части интерфейса нужно обновить.

Граф зависимостей, пакетирование обновлений, обработку вложенных объектов и защиту от повторных вычислений реализует реактивная библиотека.

React по умолчанию использует другую модель. Обновление React запускается через state API или внешнюю подписку. Обычная мутация объекта через Proxy сама по себе не является сигналом для рендера React.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Перехватывает ли Proxy операции, выполненные напрямую с <code>target</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Ловушки вызываются только для операций, выполненных через объект Proxy.

Если изменить целевой объект напрямую, Proxy не узнает об этом:

```js
target.name = "Grace";
```

При последующем чтении через Proxy новое значение будет видно, потому что Proxy работает с тем же `target`. Но ловушка `set` во время прямой записи не вызывалась.

Поэтому для логирования, проверки или реактивности важно, чтобы код работал через Proxy, а исходный `target` не передавался наружу отдельно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему методы <code>Map</code>, <code>Set</code> и private fields могут не работать через простой Proxy?</strong></summary>

<dl>
<dd>
<h2></h2>

Некоторые встроенные объекты хранят внутреннее состояние не в обычных свойствах, а в скрытых структурах движка, которые называют внутренними слотами.

Например, метод `Map.prototype.get` ожидает, что его `this` является настоящим экземпляром `Map`. При вызове `proxyMap.get(key)` значением `this` становится Proxy, у которого внутренних данных `Map` нет. В результате возникает ошибка несовместимого получателя.

Похожая проблема возникает с приватными полями класса. Доступ к `this.#value` разрешён только объекту, который действительно был создан этим классом. Proxy является отдельным объектом и такую проверку может не пройти.

Обёртка может возвращать методы, заранее связанные с `target`, но это создаёт новые функции и не является универсальным решением для всех встроенных объектов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли использовать Proxy как проверку данных API?</strong></summary>

<dl>
<dd>
<h2></h2>

Proxy может проверять будущие записи, запрещать определённые значения или логировать обращения к данным. Но он не доказывает, что исходный ответ API уже соответствует ожидаемой структуре.

Если неправильное значение обнаруживается только при позднем чтении свойства, ошибка возникает далеко от места получения данных и становится сложнее для отладки.

Внешние данные лучше один раз проверить на границе приложения и преобразовать в понятную внутреннюю модель. Proxy после этого можно использовать как дополнительный механизм, но не как замену валидации ответа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает <code>Proxy.revocable</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`Proxy.revocable` создаёт Proxy, доступ к которому можно позднее отключить. Метод возвращает объект `{ proxy, revoke }`.

После вызова `revoke()` операции с этим Proxy начинают выбрасывать `TypeError`:

```js
const { proxy, revoke } = Proxy.revocable(target, handler);

revoke();
```

Это полезно, когда доступ к объекту должен действовать только ограниченное время: например, пока активен плагин, экран или внешняя сессия.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие практические недостатки есть у Proxy?</strong></summary>

<dl>
<dd>
<h2></h2>

Proxy добавляет скрытое поведение: обычное чтение или присваивание может запускать пользовательский код. Из-за этого сложнее читать код, ставить точки останова и понимать стек ошибок.

Proxy и `target` являются разными объектами. Они будут разными ключами в `Map`, разными элементами в `Set` и не будут равны через `===`.

Некоторые встроенные объекты и приватные поля требуют дополнительной обработки из-за проверки значения `this`. Частые вызовы ловушек также могут мешать оптимизациям JavaScript-движка и добавлять накладные расходы.

Proxy нельзя напрямую клонировать через `structuredClone`. Перед клонированием обычно извлекают или создают обычный объект с нужными данными.

Полноценный полифил для Proxy создать нельзя, потому что он перехватывает сами операции языка, например чтение через точку и оператор `in`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем методы <code>Reflect</code> отличаются от похожих операторов?</strong></summary>

<dl>
<dd>
<h2></h2>

Методы `Reflect` предоставляют стандартные объектные операции в виде обычных функций с единообразным способом вызова.

Например, `Reflect.has(object, key)` соответствует выражению `key in object` и также учитывает цепочку прототипов. `Reflect.deleteProperty(object, key)` соответствует оператору `delete`, но возвращает явный результат `true` или `false`.

`Reflect.set` также возвращает `boolean`, показывающий успешность записи. `Reflect.construct` позволяет вызвать конструктор и при необходимости отдельно указать значение `newTarget`.

Это делает методы `Reflect` удобными внутри ловушек Proxy, где результат операции часто нужно вернуть вызывающему коду.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```js
"use strict";

const account = { balance: 100 };

const guarded = new Proxy(account, {
  set(target, property, value, receiver) {
    if (property === "balance" && value < 0) {
      return false;
    }

    return Reflect.set(target, property, value, receiver);
  },
});

guarded.balance = 50;

try {
  guarded.balance = -1;
} catch (error) {
  console.log(error.name);
}

console.log(account.balance);
```

<details>
<summary><strong>Что будет выведено и почему target содержит <code>50</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Будут выведены `"TypeError"` и `50`.

Запись `guarded.balance = 50` проходит через ловушку `set`. Значение допустимо, поэтому ловушка вызывает `Reflect.set`, который записывает `50` в исходный объект `account`.

При попытке записать `-1` ловушка возвращает `false` и не вызывает `Reflect.set`. Поскольку код выполняется в строгом режиме, неуспешное присваивание превращается в `TypeError`.

Ошибка перехватывается через `try/catch`, а последнее успешное значение `50` остаётся в `target`.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что учитывать |
| --- | --- |
| Реактивная библиотека | Ловушки только дают сигналы, граф зависимостей строит библиотека |
| Валидация записи | `set` должен соблюдать инварианты и вернуть `boolean` |
| SDK-обёртка | Proxy имеет другую идентичность и может ломать внутренние слоты |
| Отладочный инструмент | Доступ к свойству может логироваться или измеряться |
| Временный API | `Proxy.revocable` прекращает доступ |
| React state | Сам Proxy не инициирует React-обновление |
