## Вопрос

<br>

 💬 **Как работают ES modules? Что происходит при `import` и `export`?**

<h2></h2>

<br>
<dl>
<dd>

ES modules, или ESM, — стандартная модульная система JavaScript. Каждый модуль имеет собственную область видимости, явно экспортирует доступные значения и импортирует необходимые зависимости.

Код модуля автоматически выполняется в строгом режиме, а `this` на верхнем уровне равно `undefined`.

```js
// counter.js
export let count = 0;

export function increment() {
  count += 1;
}

// app.js
import { count, increment } from "./counter.js";

increment();
console.log(count); // 1
```

Статические `import` и `export` обрабатываются ещё до выполнения тела модуля и должны находиться на его верхнем уровне. Благодаря этому среда заранее понимает, от каких файлов зависит модуль и какие значения между ними связаны.

Упрощённо работа происходит в несколько этапов:

1. Среда находит и загружает все зависимости.
2. Проверяет модули и связывает импорты с соответствующими экспортами.
3. Выполняет тела модулей с учётом их зависимостей.

Так формируется граф модулей — набор связанных файлов, начиная с точки входа приложения.

Импорт является live binding, то есть живой связью с экспортированной переменной, а не копией её значения. Если модуль изменит экспортированную переменную, импортирующий код при следующем чтении увидит новое значение.

Саму импортированную переменную переназначить нельзя:

```js
import { count } from "./counter.js";

count = 10; // TypeError
```

При этом импортированный объект остаётся обычным изменяемым объектом. Можно изменить его свойство, если сам объект не защищён от изменений.

Один и тот же модуль по одному и тому же разрешённому адресу обычно загружается и выполняется один раз. Все последующие импорты используют тот же экземпляр модуля и его текущее состояние.

Разные адреса могут считаться разными модулями. Например, URL с отличающимися query-параметрами может привести к отдельной загрузке и отдельному состоянию.

Динамический `import(specifier)` вызывается во время выполнения и возвращает `Promise`. Результатом Promise становится объект, содержащий экспорты загруженного модуля:

```js
const { openEditor } = await import("./editor.js");
openEditor();
```

Этот объект отражает актуальные экспортируемые значения, но его свойства нельзя использовать как обычные изменяемые поля.

Сборщики используют динамический импорт как границу для code splitting: код можно вынести в отдельный chunk и загрузить только тогда, когда он действительно понадобится. Для этого путь к модулю обычно должен быть понятен сборщику во время сборки.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Что значит «статический import»?</strong></summary>

<dl>
<dd>
<h2></h2>

Статический import записывается на верхнем уровне модуля:

```js
import { value } from "./module.js";
```

Его положение и строка пути известны ещё до выполнения программы. Поэтому такой import нельзя поместить внутрь `if`, цикла или функции.

Благодаря этому среда или сборщик могут заранее построить граф зависимостей, проверить наличие импортируемых named exports и проанализировать, какие части кода используются.

Для загрузки модуля по условию или в ответ на действие пользователя применяют динамический `import()`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему импорт нельзя переназначить, но импортированный объект можно изменить?</strong></summary>

<dl>
<dd>
<h2></h2>

Импортированное имя доступно только для чтения. Оно связано с экспортом другого модуля, поэтому импортирующий модуль не может заменить эту связь:

```js
import { config } from "./config.js";

config = otherConfig; // ошибка
```

Если `config` является объектом, его свойства всё ещё можно изменять:

```js
config.theme = "dark";
```

В этом случае изменяется сам объект, а импортированное имя продолжает указывать на него.

Поэтому `import` и `const` защищают переменную от переназначения, но не делают объект неизменяемым. Изменение экспортированного объекта также будет видно другим модулям, которые используют ту же ссылку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем named export отличается от default export?</strong></summary>

<dl>
<dd>
<h2></h2>

Named export имеет определённое имя в интерфейсе модуля:

```js
export const Button = {};
```

При импорте это имя указывают в фигурных скобках:

```js
import { Button } from "./button.js";
```

Named exports обычно проще искать по проекту, автоматически переименовывать и анализировать инструментами сборки.

Default export может быть только один на модуль и импортируется без фигурных скобок. Локальное имя при импорте можно выбрать самостоятельно:

```js
export default function Button() {}

import AppButton from "./button.js";
```

Запись `export default expression` сохраняет результат вычисленного выражения. Если default export должен оставаться живой связью с изменяемой переменной, её можно экспортировать отдельно:

```js
let value = 1;

export { value as default };
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как выполняется граф модулей?</strong></summary>

<dl>
<dd>
<h2></h2>

Упрощённо работа делится на три этапа.

Сначала среда разрешает пути импортов, загружает файлы и разбирает их синтаксис. На этом этапе тело модулей ещё не выполняется.

Затем импорты связываются с соответствующими экспортами. Именно здесь создаются живые связи между модулями и проверяется, существуют ли запрошенные named exports.

После связывания выполняется код модулей. Зависимости должны быть подготовлены раньше использующих их модулей, но циклические зависимости и top-level `await` могут делать порядок выполнения сложнее.

Разделение связывания и выполнения объясняет, почему импорт можно создать до выполнения экспортирующего модуля, но читать значение разрешено только после его инициализации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Выполняется ли модуль повторно при нескольких импортах?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычно нет. После первой загрузки и выполнения модуль сохраняется в системе модулей текущей среды.

Если несколько файлов импортируют один модуль по одному и тому же разрешённому адресу, они получают доступ к одному экземпляру его экспортов и общему внутреннему состоянию.

Например, если модуль хранит счётчик, его изменение через один импорт будет видно через другой.

Модуль может выполниться повторно, если среда разрешит путь как другой адрес. Например, URL с разными query-параметрами могут считаться разными модулями:

```js
import "./config.js?mode=dev";
import "./config.js?mode=prod";
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит при циклической зависимости?</strong></summary>

<dl>
<dd>
<h2></h2>

Циклическая зависимость возникает, когда модуль `A` импортирует `B`, а `B` напрямую или через другие файлы снова импортирует `A`.

ESM может построить и связать такой граф, потому что импорты являются живыми связями, а не готовыми копиями значений.

Проблема возникает во время выполнения. Если один модуль попытается прочитать экспортированную `let`, `const` или `class` другого модуля до выполнения её объявления, возникнет `ReferenceError` из-за TDZ.

Даже если цикл не вызывает ошибку, код становится зависимым от порядка инициализации модулей. Часто это означает, что общую часть логики стоит вынести в отдельный модуль.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как браузер разрешает пути модулей?</strong></summary>

<dl>
<dd>
<h2></h2>

Браузер напрямую понимает URL-подобные пути:

```js
import "./module.js";
import "/assets/module.js";
import "https://example.com/module.js";
```

Bare specifier без относительного пути, например `react`, браузер сам по себе обычно разрешить не может:

```js
import React from "react";
```

Для такого импорта нужен import map или преобразование сборщиком.

При прямой работе браузерного ESM обычно требует точный путь к файлу, включая расширение. Модуль с другого origin загружается с учётом правил CORS.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как <code>import()</code> связан с code splitting?</strong></summary>

<dl>
<dd>
<h2></h2>

Статические импорты входят в основной граф точки входа приложения. Динамический `import()` создаёт асинхронную границу, которую сборщик может вынести в отдельный файл — chunk.

Такой chunk загружается при первом выполнении соответствующего `import()`:

```js
const module = await import("./editor.js");
```

Это может уменьшить объём JavaScript, загружаемого при первом открытии страницы.

При этом появляется дополнительный сетевой запрос, а интерфейсу нужны состояния загрузки и ошибки. Поэтому разделять код стоит по реальным пользовательским сценариям, а не выносить каждый небольшой модуль в отдельный chunk.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему статический ESM помогает tree shaking?</strong></summary>

<dl>
<dd>
<h2></h2>

Статические импорты и экспорты известны до выполнения программы. Благодаря этому сборщик может определить, какие экспорты действительно используются приложением, а какие можно удалить из production-сборки.

Однако удалить модуль можно не всегда. Если при импорте он выполняет побочное действие — изменяет глобальное состояние, регистрирует обработчик или подключает стили, — сборщик должен сохранить такой код.

Tree shaking выполняется инструментом сборки. Само использование синтаксиса `import` и `export` не гарантирует, что неиспользуемый код обязательно будет удалён.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем ESM отличается от CommonJS?</strong></summary>

<dl>
<dd>
<h2></h2>

ESM использует `import` и `export`. Его зависимости можно определить до выполнения кода, а импорты являются живыми связями с экспортами.

CommonJS использует `require()` и `module.exports`. Вызов `require()` выполняется во время работы программы и может находиться внутри условия или функции.

CommonJS исторически использует синхронную загрузку модулей, поэтому получил широкое распространение в Node.js. ESM является стандартом JavaScript и напрямую поддерживается современными браузерами и Node.js.

Совместное использование двух систем может требовать дополнительного преобразования. Например, default export CommonJS-модуля в ESM иногда имеет неожиданную форму, а динамическая структура `require()` может мешать tree shaking.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делает top-level <code>await</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Top-level `await` позволяет ожидать Promise непосредственно в теле ES-модуля, без дополнительной `async`-функции:

```js
const config = await loadConfig();
```

Выполнение такого модуля приостанавливается до завершения Promise. Модули, которые зависят от его результата, также должны дождаться окончания инициализации.

Это удобно, когда данные обязательны для запуска модуля. Но медленная операция или ошибка могут задержать выполнение всей зависимой ветви графа.

Независимые ветви графа, которым этот модуль не нужен, могут продолжать выполнение.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```js
// state.js
export let status = "idle";
export const setStatus = (next) => {
  status = next;
};

// app.js
import { status, setStatus } from "./state.js";

console.log(status);
setStatus("ready");
console.log(status);
```

<details>
<summary><strong>Что будет выведено и почему это не копирование значения?</strong></summary>

<dl>
<dd>
<h2></h2>

Будут выведены `"idle"` и `"ready"`.

При импорте `status` не копируется в отдельную локальную переменную. Импортированное имя связано с переменной `status`, которая находится в модуле `state.js`.

Первое чтение возвращает её начальное значение `"idle"`. Затем функция `setStatus` изменяет эту же переменную внутри экспортирующего модуля.

При втором чтении импортированная связь получает уже актуальное значение `"ready"`.

При этом выполнить `status = "other"` внутри `app.js` нельзя, потому что импортированное имя доступно только для чтения.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Механизм | Что учитывать |
| --- | --- | --- |
| Обычный импорт приложения | Статический `import` | Зависимость входит в основной граф |
| Ленивая страница или редактор | `import()` | Нужны состояния загрузки и ошибки chunk |
| Tree shaking | Named exports и анализ графа | Побочные эффекты ограничивают удаление |
| Browser ESM | URL или import map | Для другого origin нужен CORS |
| Циклические зависимости | Live bindings и TDZ | Не читать экспорт до инициализации |
| SSR и пакеты | ESM/CommonJS interop | Проверять формат пакета и exports map |
