#### Вопрос

Как JavaScript представляет дату и время? Как корректно работать с часовыми поясами и форматированием через `Intl`?

#### Ответ

Объект `Date` представляет конкретный момент времени числом миллисекунд, прошедших с `1970-01-01T00:00:00Z`. Такое число называют timestamp, или временной меткой. Сам `Date` не хранит часовой пояс: локальные методы используют пояс среды, где выполняется код, а UTC-методы интерпретируют ту же временную метку во всемирном координированном времени.

```js
const date = new Date("2026-01-01T00:00:00.000Z");

date.getTime();      // 1767225600000
date.toISOString();  // "2026-01-01T00:00:00.000Z"
```

В приложении нужно различать три типа данных:

| Смысл | Пример | Что передавать |
| --- | --- | --- |
| Точный момент | Время создания заказа | ISO-строка с `Z` или смещением, либо timestamp |
| Календарная дата без времени | День рождения | Строка `YYYY-MM-DD`, не превращённая без необходимости в момент |
| Местное время в заданном регионе | Встреча в 10:00 по Москве | Локальные дата и время вместе с идентификатором часового пояса |

Смещение вроде `+03:00` описывает разницу с UTC в конкретный момент, но не все правила региона. Идентификатор `Europe/Moscow` или `America/New_York` обозначает часовой пояс с его историческими и будущими правилами, включая переходы на летнее время там, где они есть.

Для обмена точным моментом обычно используют строку ISO 8601 с `Z` или явным смещением. `Z` означает UTC. Строка без часового пояса неоднозначна на уровне бизнес-контракта, даже если JavaScript умеет её разобрать.

`Intl` является встроенным API интернационализации. Он форматирует даты, числа, валюты, относительное время, списки и формы множественного числа с учётом locale, то есть языковых и региональных настроек. Форматирование следует отделять от хранения: данные сохраняются в согласованном машинном формате, а пользователю показываются через `Intl`.

```js
const formatter = new Intl.DateTimeFormat("ru-RU", {
  dateStyle: "long",
  timeStyle: "short",
  timeZone: "Europe/Moscow",
});

formatter.format(new Date("2026-01-01T00:00:00.000Z"));
```

#### Встречные вопросы

> [!followup]
> **Вопрос:** Хранит ли `Date` часовой пояс?
>
> **Ответ:** Нет. Внутри хранится только временная метка. `getHours()` и похожие методы используют локальный пояс текущей среды, а `getUTCHours()` интерпретирует тот же момент в UTC. Идентификатор исходного региона, например `Europe/Berlin`, после создания `Date` не сохраняется.

> [!followup]
> **Вопрос:** Чем временная метка отличается от строки ISO?
>
> **Ответ:** Временная метка является числом миллисекунд и однозначно задаёт момент. ISO-строка может задавать тот же момент в читаемой форме, если содержит `Z` или смещение. Строки `2026-01-01T00:00:00Z` и `2026-01-01T03:00:00+03:00` обозначают один момент и дают одинаковый `getTime()`.

> [!followup]
> **Вопрос:** В чём ловушка разбора строки без часового пояса?
>
> **Ответ:** По правилам JavaScript дата без времени, например `"2026-01-01"`, интерпретируется как полночь UTC. Дата со временем, но без смещения, например `"2026-01-01T00:00:00"`, интерпретируется как локальное время среды. Это исторически закреплённое различие легко приводит к сдвигу даты.
>
> Нестандартные строки вроде `"01/02/2026"` могут разбираться по-разному в разных движках. Для API следует использовать согласованный формат, а не полагаться на эвристику `Date.parse`.

> [!followup]
> **Вопрос:** Почему `"2026-01-01"` может отобразиться как предыдущий день?
>
> **Ответ:** Строка создаёт момент `2026-01-01T00:00:00Z`. В часовом поясе западнее UTC этот момент ещё относится к вечеру 31 декабря. Проблема возникает из-за того, что календарную дату без времени ошибочно преобразовали в глобальный момент. Для дня рождения или даты отчёта часто правильнее хранить исходную строку `YYYY-MM-DD`.

> [!followup]
> **Вопрос:** Почему прибавление 24 часов не всегда означает следующий местный день в то же время?
>
> **Ответ:** В регионах с переходом на летнее и зимнее время календарный день может длиться 23 или 25 часов. Прибавление `24 * 60 * 60 * 1000` изменяет точный момент на 24 часа, а не выполняет календарную операцию «следующий день». Для календарной логики нужно учитывать правила требуемого часового пояса и использовать подходящую библиотеку или `Temporal` там, где он доступен в целевой среде.

> [!followup]
> **Вопрос:** Как проверить, что объект `Date` корректен?
>
> **Ответ:** Некорректный `Date` всё ещё является объектом `Date`, но его временная метка равна `NaN`. Проверка выглядит как `!Number.isNaN(date.getTime())`. Метод `toISOString()` для некорректной даты выбросит `RangeError`, поэтому входные данные проверяют до форматирования.

> [!followup]
> **Вопрос:** Зачем передавать `timeZone` в `Intl.DateTimeFormat`?
>
> **Ответ:** Без этой настройки форматтер использует часовой пояс среды. На компьютере разработчика, сервере SSR и устройстве пользователя результат может различаться. Явный `timeZone` нужен, когда интерфейс должен показывать время в бизнес-регионе или выбранном пользователем поясе. Когда требуется локальное время самого пользователя, пояс можно не задавать, но это решение должно быть осознанным.

> [!followup]
> **Вопрос:** Что ещё умеет `Intl` кроме форматирования дат?
>
> **Ответ:** `Intl.NumberFormat` форматирует числа, проценты и валюты; `Intl.RelativeTimeFormat` формирует выражения вроде «2 дня назад»; `Intl.PluralRules` выбирает грамматическую форму; `Intl.ListFormat` форматирует перечисления; `Intl.Collator` сравнивает и сортирует строки по правилам языка. `Intl` не переводит произвольный текст интерфейса, для него всё равно нужен словарь локализации.

> [!followup]
> **Вопрос:** Нужно ли создавать новый formatter для каждого значения списка?
>
> **Ответ:** Нет. Создание форматтера требует разбора locale и настроек. Для таблицы разумно создать один `Intl.DateTimeFormat` или `Intl.NumberFormat` и переиспользовать его для всех строк, например через модульный кеш или мемоизацию по набору настроек.

#### Где это встречается во frontend

| Ситуация | Модель данных | Что учитывать |
| --- | --- | --- |
| Время создания записи | Момент | Передавать `Z` или смещение |
| День рождения | Календарная дата | Не сдвигать через часовой пояс |
| Расписание события | Местное время и регион | Смещение может измениться из-за правил пояса |
| SSR и hydration | Один момент, две среды | Явно согласовать locale и `timeZone` |
| Таблица цен | Число и код валюты | Форматировать через `Intl.NumberFormat` |
| Поле `datetime-local` | Локальные дата и время | Значение не содержит часовой пояс |
