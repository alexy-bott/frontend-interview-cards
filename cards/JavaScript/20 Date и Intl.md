## Вопрос

<br>

 💬 **Как JavaScript представляет дату и время? Как корректно работать с часовыми поясами и форматированием через `Intl`?**

<h2></h2>

<br>
<dl>
<dd>

Объект `Date` представляет конкретный момент времени. Внутри он хранит число миллисекунд, прошедших с `1970-01-01T00:00:00Z`. Такое число называют timestamp, или временной меткой.

Сам объект `Date` не хранит часовой пояс. Локальные методы, например `getHours()`, показывают сохранённый момент в часовом поясе текущей среды. UTC-методы, например `getUTCHours()`, показывают тот же момент в UTC.

```js
const date = new Date("2026-01-01T00:00:00.000Z");

date.getTime();      // 1767225600000
date.toISOString();  // "2026-01-01T00:00:00.000Z"
```

Важно разделять сам момент времени, его отображение пользователю и бизнес-смысл значения.

В приложении обычно встречаются три разные модели:

| Смысл | Пример | Что передавать |
| --- | --- | --- |
| Точный момент | Время создания заказа | ISO-строка с `Z` или смещением либо timestamp |
| Календарная дата без времени | День рождения | Строка `YYYY-MM-DD`, не превращённая без необходимости в момент |
| Местное время в заданном регионе | Встреча в 10:00 по Москве | Локальные дата и время вместе с идентификатором часового пояса |

Смещение вроде `+03:00` показывает разницу с UTC только для конкретного момента. Оно не содержит исторические и будущие правила региона.

Идентификатор `Europe/Moscow` или `America/New_York` обозначает региональный часовой пояс. Он позволяет учитывать изменение смещения во времени, включая переходы на летнее и зимнее время в тех регионах, где они применяются.

Для обмена точным моментом обычно используют строку ISO 8601 с `Z` или явным смещением:

```text
2026-01-01T00:00:00Z
2026-01-01T03:00:00+03:00
```

Обе строки задают точный момент. `Z` означает UTC.

Строка с датой и временем, но без часового пояса, например `2026-01-01T10:00:00`, не задаёт глобальный момент явно. JavaScript интерпретирует её как локальное время среды, но для API такой формат может быть неоднозначным: сервер и клиент могут находиться в разных часовых поясах.

`Intl` — это встроенный API интернационализации. Он форматирует даты, числа, валюты, относительное время, списки и другие значения с учётом locale — языковых и региональных настроек.

`Intl.DateTimeFormat` не изменяет сохранённый момент и не добавляет часовой пояс в объект `Date`. Он только отображает этот момент в выбранном формате и часовом поясе.

Форматирование следует отделять от хранения: данные сохраняют и передают в согласованном машинном формате, а пользователю показывают через `Intl`.

```js
const formatter = new Intl.DateTimeFormat("ru-RU", {
  dateStyle: "long",
  timeStyle: "short",
  timeZone: "Europe/Moscow",
});

formatter.format(new Date("2026-01-01T00:00:00.000Z"));
```

В этом примере строка задаёт точный момент в UTC, а `Intl.DateTimeFormat` отображает его по-русски во времени Москвы.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Хранит ли <code>Date</code> часовой пояс?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Внутри `Date` хранится только временная метка, представляющая конкретный момент.

Методы `getHours()`, `getDate()` и другие локальные методы отображают этот момент в часовом поясе среды, где выполняется код. Методы `getUTCHours()`, `getUTCDate()` и другие UTC-методы используют UTC.

Идентификатор исходного региона, например `Europe/Berlin`, после создания объекта `Date` не сохраняется. Если он нужен для бизнес-логики, его необходимо хранить отдельно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем временная метка отличается от строки ISO?</strong></summary>

<dl>
<dd>
<h2></h2>

Временная метка — это число миллисекунд от начала эпохи Unix. Она однозначно задаёт конкретный момент.

ISO-строка является текстовым представлением. Она тоже однозначно задаёт момент, если содержит `Z` или явное смещение.

Строки `2026-01-01T00:00:00Z` и `2026-01-01T03:00:00+03:00` обозначают один момент, поэтому созданные из них объекты `Date` имеют одинаковый результат `getTime()`.

Строковый формат удобнее для передачи через JSON и чтения человеком, а timestamp удобен для числового сравнения и вычисления разницы между моментами.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>В чём ловушка разбора строки без часового пояса?</strong></summary>

<dl>
<dd>
<h2></h2>

JavaScript по-разному интерпретирует два похожих формата.

Дата без времени:

```text
2026-01-01
```

интерпретируется как полночь UTC.

Дата со временем, но без `Z` или смещения:

```text
2026-01-01T00:00:00
```

интерпретируется как локальное время среды.

Из-за этого добавление или удаление части со временем может изменить смысл значения. Кроме того, один и тот же код на сервере и устройстве пользователя может создать разные моменты из строки с локальным временем.

Нестандартные строки вроде `"01/02/2026"` могут разбираться по-разному в разных средах. Для API следует использовать заранее согласованный формат, а не полагаться на эвристику `Date.parse`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>"2026-01-01"</code> может отобразиться как предыдущий день?</strong></summary>

<dl>
<dd>
<h2></h2>

Строка `"2026-01-01"` создаёт момент `2026-01-01T00:00:00Z`.

В часовом поясе западнее UTC в этот момент всё ещё может быть вечер 31 декабря. Например, при форматировании в таком поясе календарная дата сдвинется на предыдущий день.

Проблема возникает из-за того, что календарную дату без времени превратили в глобальный момент. Для дня рождения, даты отчёта или срока действия часто правильнее хранить исходную строку `YYYY-MM-DD` и не преобразовывать её в `Date` без необходимости.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему прибавление 24 часов не всегда означает следующий местный день в то же время?</strong></summary>

<dl>
<dd>
<h2></h2>

Прибавление `24 * 60 * 60 * 1000` сдвигает точный момент ровно на 24 часа.

Но в регионах с переходом на летнее или зимнее время местный календарный день может длиться 23 или 25 часов. Поэтому после прибавления 24 часов местное время может отличаться от исходного на один час.

Операции «добавить 24 часа» и «перейти на следующий календарный день в том же регионе» имеют разный смысл.

Для календарных операций нужно учитывать правила требуемого часового пояса. Можно использовать подходящую библиотеку или `Temporal`, предварительно проверив поддержку API в целевой среде либо подключив полифил.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверить, что объект <code>Date</code> корректен?</strong></summary>

<dl>
<dd>
<h2></h2>

Некорректный `Date` всё равно является объектом класса `Date`, но его временная метка равна `NaN`.

Проверка выглядит так:

```js
const isValidDate = !Number.isNaN(date.getTime());
```

Одной проверки `date instanceof Date` недостаточно: она подтверждает тип объекта, но не корректность хранящегося значения.

Метод `toISOString()` для некорректной даты выбрасывает `RangeError`, поэтому внешние данные нужно проверять до сериализации и форматирования.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем передавать <code>timeZone</code> в <code>Intl.DateTimeFormat</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Без параметра `timeZone` форматтер использует часовой пояс текущей среды.

На сервере SSR, компьютере разработчика и устройстве пользователя могут быть настроены разные часовые пояса. Поэтому один момент может отображаться разными датами и временем.

Явный `timeZone` нужен, когда интерфейс должен показывать время:

- в конкретном бизнес-регионе;
- в часовом поясе события;
- в поясе, выбранном пользователем;
- одинаково на сервере и клиенте.

Если требуется локальное время текущего пользователя, `timeZone` можно не задавать. Но тогда различие результатов между пользователями является ожидаемым поведением.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему сервер и клиент могут по-разному отформатировать одну дату?</strong></summary>

<dl>
<dd>
<h2></h2>

Если `locale` и `timeZone` не заданы явно, `Intl.DateTimeFormat` использует настройки текущей среды.

SSR может выполняться на сервере с одним часовым поясом и locale, а hydration — в браузере пользователя с другими настройками. В результате один момент может получить разный текст, например другую дату, порядок частей или формат времени.

Если форматированный текст участвует в серверном HTML, нужно согласовать `locale` и `timeZone` между сервером и клиентом либо выполнять зависимое от пользовательской среды форматирование только после загрузки интерфейса.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что ещё умеет <code>Intl</code> кроме форматирования дат?</strong></summary>

<dl>
<dd>
<h2></h2>

`Intl.NumberFormat` форматирует числа, проценты и валюты.

`Intl.RelativeTimeFormat` создаёт выражения вроде «2 дня назад», а `Intl.PluralRules` помогает выбрать грамматическую форму в зависимости от числа.

`Intl.ListFormat` форматирует перечисления, а `Intl.Collator` сравнивает и сортирует строки по правилам выбранного языка.

`Intl` не переводит произвольный текст интерфейса и не хранит словарь переводов. Для локализации подписей, сообщений и другого текста всё равно нужна отдельная система переводов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли создавать новый formatter для каждого значения списка?</strong></summary>

<dl>
<dd>
<h2></h2>

При форматировании большого списка обычно нет необходимости создавать новый экземпляр `Intl.DateTimeFormat` или `Intl.NumberFormat` для каждой строки.

Если locale и настройки одинаковы, один formatter можно создать заранее и переиспользовать:

```js
const formatter = new Intl.DateTimeFormat("ru-RU", {
  dateStyle: "medium",
  timeZone: "Europe/Moscow",
});

const labels = dates.map((date) => formatter.format(date));
```

Если настройки меняются, formatter можно кешировать по комбинации locale, `timeZone` и других параметров. Для нескольких единичных значений специальная оптимизация обычно не требуется.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Модель данных | Что учитывать |
| --- | --- | --- |
| Время создания записи | Момент | Передавать `Z` или смещение |
| День рождения | Календарная дата | Не сдвигать через часовой пояс |
| Расписание события | Местное время и регион | Хранить локальные компоненты вместе с идентификатором пояса |
| SSR и hydration | Один момент, две среды | Явно согласовать locale и `timeZone` |
| Таблица цен | Число и код валюты | Форматировать через `Intl.NumberFormat` |
| Поле `datetime-local` | Локальные дата и время | Значение не содержит часовой пояс |
