## Вопрос

<br>

 💬 **Как JavaScript хранит строки? Чем отличаются кодовая единица, кодовая точка и графемный кластер, и почему это важно при работе с Unicode?**

<h2></h2>

<br>
<dl>
<dd>

На уровне модели языка строка JavaScript является неизменяемой последовательностью 16-битных кодовых единиц UTF-16. Конкретный движок может оптимизировать внутреннее хранение, но поведение `length`, индексов и строковых методов определяется этой моделью.

Неизменяемость означает, что методы строки не меняют исходное значение, а возвращают новое. Свойство `length`, доступ по индексу и многие методы, включая `slice`, считают именно кодовые единицы, а не обязательно знаки, видимые пользователю.

Unicode назначает числовые значения буквам, эмодзи, комбинируемым знакам и другим элементам текста. Такое значение называют кодовой точкой.

В UTF-16 одна кодовая точка занимает одну кодовую единицу либо пару кодовых единиц, которую называют суррогатной парой. Поэтому кодовая точка за пределами основной многоязычной плоскости может иметь `length === 2`:

```js
"A".length;  // 1
"😀".length; // 2
```

Даже одна кодовая точка не всегда совпадает с одним знаком, который воспринимает пользователь. Буква и комбинируемый диакритический знак, эмодзи и модификатор цвета кожи или несколько эмодзи, соединённых через ZWJ, могут образовать один графемный кластер.

```js
const value = "👍🏽";

value.length;      // 4 кодовые единицы UTF-16
[...value].length; // 2 кодовые точки
```

Итератор строки, который используют `for...of`, оператор spread и `Array.from`, проходит по кодовым точкам и не разделяет корректную суррогатную пару. Но он всё ещё может разделить один графемный кластер на несколько частей.

Для подсчёта, выделения или ограничения видимых пользователю знаков используют `Intl.Segmenter` с `granularity: "grapheme"`.

Строка JavaScript и байты сетевого сообщения являются разными представлениями данных. `TextEncoder` кодирует строку в байты UTF-8, а `TextDecoder` преобразует байты обратно в строку.

При потоковом чтении декодер должен сохранять неполную последовательность байтов между частями, потому что байты одной кодовой точки UTF-8 могут оказаться в разных chunks.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему <code>"😀".length</code> возвращает <code>2</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Кодовая точка этого эмодзи находится за пределами диапазона, который помещается в одну 16-битную кодовую единицу UTF-16.

JavaScript представляет её как суррогатную пару из двух кодовых единиц. `length` считает именно эти единицы, поэтому возвращает `2`, хотя пользователь видит один знак.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>charCodeAt</code> отличается от <code>codePointAt</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`charCodeAt(index)` возвращает числовое значение одной кодовой единицы UTF-16. Для эмодзи он вернёт только одну половину суррогатной пары.

`codePointAt(index)` распознаёт корректную суррогатную пару, если вызван на её первой кодовой единице, и возвращает полную кодовую точку.

Обратное преобразование кодовой точки выполняет `String.fromCodePoint`. Метод `String.fromCharCode` работает с отдельными кодовыми единицами UTF-16.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как посчитать длину строки так, как её видит пользователь?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала нужно определить, что продукт считает одним знаком. Для пользовательского текста обычно нужны графемные кластеры.

Их можно получить через `Intl.Segmenter`:

```js
const segmenter = new Intl.Segmenter("ru", {
  granularity: "grapheme",
});

const length = [...segmenter.segment("👍🏽")].length; // 1
```

Поддержку `Intl.Segmenter` проверяют для целевых браузеров. В старых средах понадобится совместимая библиотека сегментации Unicode.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>split("").reverse().join("")</code> может повредить строку?</strong></summary>

<dl>
<dd>
<h2></h2>

`split("")` делит строку по кодовым единицам UTF-16 и может разнести половины суррогатной пары.

Оператор spread сохраняет кодовые точки, но всё ещё разделяет составные эмодзи и буквы с комбинируемыми знаками.

Если операция должна учитывать видимые пользователю знаки, строку сначала сегментируют на графемные кластеры, а затем изменяют порядок сегментов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем UTF-8 отличается от UTF-16 в контексте JavaScript?</strong></summary>

<dl>
<dd>
<h2></h2>

Оба формата кодируют данные Unicode, но используют разные последовательности единиц.

На уровне модели JavaScript строка состоит из 16-битных кодовых единиц UTF-16. В современных веб-протоколах и файлах текст обычно передаётся в UTF-8, где кодовая точка занимает от одного до четырёх байтов.

Поэтому `string.length` не показывает размер строки в байтах. Размер UTF-8 можно получить так:

```js
const bytes = new TextEncoder().encode(value).byteLength;
```

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужна нормализация Unicode?</strong></summary>

<dl>
<dd>
<h2></h2>

Один видимый знак иногда можно представить разными последовательностями кодовых точек. Например, буква с диакритическим знаком может быть одной кодовой точкой или сочетанием базовой буквы и отдельного комбинируемого знака.

Внешне строки могут выглядеть одинаково, но строгое сравнение вернёт `false`. Метод `normalize("NFC")` приводит канонически эквивалентные последовательности к согласованной форме.

Выбранную форму нужно применять на определённой границе данных, а не нормализовать случайно в разных частях приложения.

Нормализация не делает одинаковыми все визуально похожие символы. Например, латинская и кириллическая буквы могут выглядеть похоже, но оставаться разными кодовыми точками.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему строки нельзя корректно сортировать обычным <code>sort()</code> для любого языка?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычная сортировка строк сравнивает последовательности кодовых единиц и не учитывает алфавитные правила языка, регистр и диакритические знаки так, как ожидает пользователь.

Для пользовательской сортировки применяют `Intl.Collator` или `localeCompare` с нужной локалью и настройками.

Если сравнений много, обычно создают один экземпляр `Intl.Collator` и переиспользуют его метод `compare`.

Точное сравнение по кодовым единицам по-прежнему подходит для технических ключей и протокольных значений.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Может ли изменение регистра поменять длину строки?</strong></summary>

<dl>
<dd>
<h2></h2>

Да. Преобразование регистра определяется правилами Unicode и иногда заменяет одну кодовую точку несколькими либо зависит от выбранной локали.

Поэтому нельзя рассчитывать позиции или ограничения длины, предполагая, что `toUpperCase()` и `toLowerCase()` сохраняют количество кодовых единиц, точек или графем.

Для языковых правил используют `toLocaleUpperCase` и `toLocaleLowerCase` с нужной локалью.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как флаги <code>u</code> и <code>v</code> влияют на регулярное выражение?</strong></summary>

<dl>
<dd>
<h2></h2>

Флаги `u` и `v` включают Unicode-aware режим регулярного выражения. В нём многие операции, включая точку и квантификаторы, учитывают полные кодовые точки вместо отдельных половин корректной суррогатной пары.

Флаг `v` дополнительно расширяет возможности наборов символов и операций над ними.

Однако ни `u`, ни `v` не превращают точку `.` в операцию над графемными кластерами. Составной эмодзи по-прежнему может состоять из нескольких кодовых точек.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как безопасно обрезать пользовательскую строку до заданного количества знаков?</strong></summary>

<dl>
<dd>
<h2></h2>

Если ограничение относится к видимым знакам, строку сегментируют через `Intl.Segmenter`, берут нужное число графемных кластеров и соединяют их обратно.

Если ограничение задано сервером в байтах, сначала нужно согласовать кодировку и проверять размер закодированного значения.

Обрезка через `slice(0, n)` решает только задачу ограничения по кодовым единицам UTF-16 и может разделить суррогатную пару или графемный кластер.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```js
const value = "👍🏽";
const segmenter = new Intl.Segmenter("ru", {
  granularity: "grapheme",
});

console.log(value.length);
console.log([...value].length);
console.log([...segmenter.segment(value)].length);
```

<details>
<summary><strong>Что будет выведено и почему?</strong></summary>

<dl>
<dd>
<h2></h2>

Будут выведены `4`, `2` и `1`.

Строка состоит из четырёх кодовых единиц UTF-16, двух кодовых точек и одного графемного кластера, который пользователь воспринимает как один эмодзи.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что считать или преобразовывать | Основной риск |
| --- | --- | --- |
| Ограничение длины имени | Графемные кластеры | `length` завышает число видимых знаков |
| Обрезка текста | Графемные кластеры | Разрыв эмодзи или комбинируемого знака |
| Сортировка списка | `Intl.Collator` | Непривычный для языка порядок |
| Поиск и сравнение | Согласованная нормализация | Внешне одинаковые строки могут отличаться |
| Получение сетевых данных | UTF-8 и `TextDecoder` | Символ может разделиться между частями потока |
| Ограничение размера запроса | Байты выбранной кодировки | `length` не равен размеру сообщения |
