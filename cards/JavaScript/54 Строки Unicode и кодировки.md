## Вопрос

Как JavaScript хранит строки? Чем отличаются кодовая единица, кодовая точка и графемный кластер, и почему это важно при работе с Unicode?

<details>
<summary><strong>Показать ответ</strong></summary>

Строка в JavaScript является неизменяемой последовательностью 16-битных кодовых единиц UTF-16. Неизменяемость означает, что методы строки не меняют исходное значение, а возвращают новое. Свойство `length`, доступ по индексу и многие методы, включая `slice`, считают именно кодовые единицы, а не обязательно символы, видимые пользователю.

Unicode является стандартом, который назначает символам числовые значения. Такое значение называют кодовой точкой. В UTF-16 одна кодовая точка занимает одну кодовую единицу либо пару кодовых единиц, которую называют суррогатной парой. Поэтому один символ за пределами основной многоязычной плоскости может иметь `length === 2`:

```js
"A".length;  // 1
"😀".length; // 2
```

Даже кодовая точка не всегда совпадает с одним знаком, который воспринимает пользователь. Например, базовый эмодзи, модификатор цвета кожи и соединитель могут вместе образовать один графемный кластер, то есть один визуально воспринимаемый знак.

```js
const value = "👍🏽";

value.length;      // 4 кодовые единицы UTF-16
[...value].length; // 2 кодовые точки
```

Итератор строки, который используют `for...of`, оператор spread и `Array.from`, проходит по кодовым точкам и не разрывает суррогатную пару. Но он всё ещё может разделить один графемный кластер на несколько частей. Для подсчёта, выделения или ограничения видимых пользователю знаков используют `Intl.Segmenter` с `granularity: "grapheme"`.

Строка JavaScript и байты сетевого сообщения являются разными представлениями данных. `TextEncoder` кодирует строку в байты UTF-8, а `TextDecoder` преобразует байты обратно в строку. При потоковом чтении декодер должен сохранять неполную последовательность байтов между частями, потому что один UTF-8-символ может быть разделён границей сетевых данных.

</details>

## Встречные вопросы

<details>
<summary><strong>Вопрос:</strong> Почему <code>"😀".length</code> возвращает <code>2</code>?</summary>

Кодовая точка этого эмодзи находится за пределами диапазона, который помещается в одну 16-битную кодовую единицу UTF-16. JavaScript хранит её как суррогатную пару из двух кодовых единиц. `length` считает эти единицы, поэтому возвращает `2`, хотя пользователь видит один знак.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем <code>charCodeAt</code> отличается от <code>codePointAt</code>?</summary>

`charCodeAt(index)` возвращает числовое значение одной кодовой единицы UTF-16. Для эмодзи он вернёт только одну половину суррогатной пары. `codePointAt(index)` распознаёт корректную пару, если вызван на её первом элементе, и возвращает полную кодовую точку. Обратное преобразование выполняет `String.fromCodePoint`.

</details>

<details>
<summary><strong>Вопрос:</strong> Как посчитать длину строки так, как её видит пользователь?</summary>

Нужно определить, что именно продукт считает одним знаком. Для поля с пользовательским текстом обычно нужны графемные кластеры. Их можно получить через `Intl.Segmenter`:

```js
const segmenter = new Intl.Segmenter("ru", {
  granularity: "grapheme",
});

const length = [...segmenter.segment("👍🏽")].length; // 1
```

Поддержку `Intl.Segmenter` проверяют для целевых браузеров. В старых средах понадобится совместимая библиотека.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему <code>split("").reverse().join("")</code> может повредить строку?</summary>

`split("")` делит строку по кодовым единицам и может разнести половины суррогатной пары. Оператор spread сохраняет кодовые точки, но всё ещё разделяет составные эмодзи и буквы с комбинируемыми знаками. Если операция должна учитывать видимые знаки, строку сначала сегментируют на графемные кластеры.

</details>

<details>
<summary><strong>Вопрос:</strong> Чем UTF-8 отличается от UTF-16 в контексте JavaScript?</summary>

Оба формата кодируют символы Unicode, но используют разные последовательности единиц. JavaScript представляет строки кодовыми единицами UTF-16. HTML, JSON и сетевые протоколы обычно передают текст в UTF-8, где кодовая точка занимает от одного до четырёх байтов. Поэтому `string.length` не показывает размер строки в байтах. Размер UTF-8 можно получить через `new TextEncoder().encode(value).byteLength`.

</details>

<details>
<summary><strong>Вопрос:</strong> Зачем нужна нормализация Unicode?</summary>

Один видимый знак иногда можно представить разными последовательностями кодовых точек. Например, буква с диакритическим знаком может быть одной кодовой точкой или сочетанием базовой буквы и отдельного знака. Внешне строки выглядят одинаково, но строгое сравнение может вернуть `false`. Метод `normalize("NFC")` приводит их к согласованной форме. Выбранную форму нужно применять на одинаковой границе данных, а не нормализовать случайно в разных частях приложения.

</details>

<details>
<summary><strong>Вопрос:</strong> Почему строки нельзя корректно сортировать обычным <code>sort()</code> для любого языка?</summary>

Обычная сортировка сравнивает строки по значениям кодовых единиц и не учитывает алфавитные правила языка, регистр и диакритические знаки так, как ожидает пользователь. Для пользовательской сортировки применяют `Intl.Collator` или `localeCompare` с нужной локалью и настройками. Точное двоичное сравнение всё равно подходит для технических ключей и протокольных значений.

</details>

<details>
<summary><strong>Вопрос:</strong> Может ли изменение регистра поменять длину строки?</summary>

Да. Преобразование регистра определяется правилами Unicode и иногда заменяет один знак несколькими или зависит от локали. Поэтому нельзя заранее выделять память или вычислять позицию по предположению, что `toUpperCase()` и `toLowerCase()` сохраняют длину. Для языковых правил используют методы `toLocaleUpperCase` и `toLocaleLowerCase` с нужной локалью.

</details>

<details>
<summary><strong>Вопрос:</strong> Как флаги <code>u</code> и <code>v</code> влияют на регулярное выражение?</summary>

Они включают режим обработки Unicode, в котором движок интерпретирует суррогатные пары как кодовые точки и корректнее обрабатывает Unicode-экранирование. Флаг `v` дополнительно расширяет возможности наборов символов. Однако ни один из этих флагов сам по себе не превращает точку `.` в операцию над графемными кластерами: составной эмодзи всё ещё может состоять из нескольких кодовых точек.

</details>

<details>
<summary><strong>Вопрос:</strong> Как безопасно обрезать пользовательскую строку до заданного количества знаков?</summary>

Если ограничение относится к видимым знакам, строку делят через `Intl.Segmenter`, берут нужное число графемных кластеров и соединяют обратно. Если ограничение задано сервером в байтах, сначала нужно согласовать кодировку и проверять размер закодированного значения. Обрезка через `slice(0, n)` решает только задачу ограничения по кодовым единицам UTF-16.

</details>

## Мини-задача

```js
const value = "👍🏽";
const segmenter = new Intl.Segmenter("ru", {
  granularity: "grapheme",
});

console.log(value.length);
console.log([...value].length);
console.log([...segmenter.segment(value)].length);
```

<details>
<summary><strong>Вопрос:</strong> Что будет выведено и почему?</summary>

Будут выведены `4`, `2` и `1`. Строка состоит из четырёх кодовых единиц UTF-16, двух кодовых точек и одного графемного кластера, который пользователь воспринимает как один эмодзи.

</details>

## Где это встречается во frontend

| Ситуация | Что считать или преобразовывать | Основной риск |
| --- | --- | --- |
| Ограничение длины имени | Графемные кластеры | `length` завышает число видимых знаков |
| Обрезка текста | Графемные кластеры | Разрыв эмодзи или комбинируемого знака |
| Сортировка списка | `Intl.Collator` | Непривычный для языка порядок |
| Поиск и сравнение | Согласованная нормализация | Внешне одинаковые строки могут отличаться |
| Получение сетевых данных | UTF-8 и `TextDecoder` | Символ может разделиться между частями потока |
| Ограничение размера запроса | Байты выбранной кодировки | `length` не равен размеру сообщения |
