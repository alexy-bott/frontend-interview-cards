## Вопрос

<br>

 💬 **Как связаны `FormData`, `Blob`, `File`, object URL и `FileReader`? Как безопасно отправлять и читать файлы?**

<h2></h2>

<br>
<dl>
<dd>

`Blob` представляет неизменяемую последовательность bytes с `size` и необязательным MIME type. Его можно создать из строк, `ArrayBuffer`, typed arrays и других blobs, получить часть через `slice` и прочитать через Promise-методы `text()`, `arrayBuffer()` или поток `stream()`.

`File` наследует `Blob`, поэтому поддерживает те же способы чтения, но дополнительно хранит файловые метаданные: `name`, `lastModified` и иногда относительный путь. Обычно `File` приходит из `<input type="file">`, drag-and-drop или File System API. Имя и `type` контролируются клиентской средой и не являются доказательством фактического содержимого.

`FormData` хранит упорядоченный набор полей. Значением может быть строка, `Blob` или `File`. Другие значения при добавлении приводятся к строке. `FormData` используется как request body для `multipart/form-data`, когда вместе отправляются обычные поля и бинарные файлы.

```js
const formData = new FormData();
formData.set("title", "Avatar");
formData.append("files", firstFile);
formData.append("files", secondFile);

await fetch("/api/upload", {
  method: "POST",
  body: formData,
});
```

При отправке `FormData` через `fetch` не нужно вручную устанавливать `Content-Type`. Браузер добавляет `multipart/form-data` вместе с уникальным `boundary`, то есть разделителем частей. Если самостоятельно задать header без соответствующего boundary, сервер не сможет корректно разобрать body.

`new FormData(form)` собирает successful controls: элементы с `name`, которые не disabled и подходят по текущему состоянию. Unchecked checkbox и radio не попадают в результат. Кнопка отправки включается только тогда, когда она передана как submitter или участвует в реальной отправке формы. Несколько controls с одним `name` сохраняют несколько значений, которые можно получить через `getAll`.

`FileReader` является event-based API чтения `Blob` как text, `ArrayBuffer` или data URL. Для нового Promise-кода методы `Blob` обычно проще. `FileReader` остаётся полезен для `readAsDataURL`, progress events чтения, явного выбора encoding через `readAsText` и совместимости со старым кодом.

Object URL, созданный через `URL.createObjectURL(blob)`, позволяет временно использовать `Blob` или `File` как адрес ресурса, например для preview. После завершения использования URL нужно освободить через `URL.revokeObjectURL`.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем <code>append</code> отличается от <code>set</code> у FormData?</strong></summary>

<dl>
<dd>
<h2></h2>

`append(name, value)` добавляет ещё одно значение и сохраняет предыдущие записи с таким именем.

`set(name, value)` удаляет все существующие значения этого имени и оставляет одно новое.

Для нескольких файлов одного поля используют `append`, а для одиночного редактируемого значения чаще подходит `set`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Какие элементы формы не попадут в <code>new FormData(form)</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

В результат не попадут controls без `name`, disabled controls, unchecked checkbox и radio, а также кнопки, которые не являются выбранным submitter.

Значение file input представлено объектом `File`.

Если важно включить конкретную submit button с её `name` и `value`, её можно передать вторым аргументом в `new FormData(form, submitter)`. В обработчике отправки доступ к ней также можно получить через `SubmitEvent.submitter`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда отправлять JSON, а когда FormData?</strong></summary>

<dl>
<dd>
<h2></h2>

JSON удобен для структурированных текстовых данных и явного API contract.

`FormData` используют для multipart-запросов, особенно когда вместе с полями передаются `File` или `Blob`.

Вложенный объект внутри `FormData` не сериализуется автоматически. Обычный объект будет приведён к строке `"[object Object]"`, поэтому его явно преобразуют в JSON-строку или раскладывают по согласованной с сервером схеме.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как показать preview изображения?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно создать `URL.createObjectURL(file)` и назначить полученный URL элементу `img`, `video` или ссылке.

Object URL удерживает связанный ресурс до вызова `URL.revokeObjectURL(url)` или завершения документа.

Предыдущий URL освобождают после завершения его использования: например, при замене файла, unmount компонента или после загрузки ресурса, если URL больше не понадобится. Отзывать URL сразу после присваивания нельзя — потребитель может не успеть прочитать ресурс.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем object URL отличается от data URL?</strong></summary>

<dl>
<dd>
<h2></h2>

Object URL является короткой внутренней ссылкой браузера на `Blob` и не содержит его bytes непосредственно в строке.

Data URL содержит данные внутри самой строки. При использовании base64 объём обычно увеличивается примерно на треть, а длинная строка занимает дополнительную память.

Для preview большого файла object URL обычно эффективнее. Data URL нужен, когда данные действительно должны быть встроены в текстовый формат, например HTML или JSON.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли доверять <code>file.type</code>, extension и атрибуту <code>accept</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. `accept` является только подсказкой для file picker.

`file.type` может быть неточным, подменённым или вообще пустым. Расширение и имя файла также контролируются клиентом.

Client validation улучшает UX, но сервер должен повторно проверить размер, фактический формат, допустимое расширение, правила хранения и security policy. Пользовательский файл нельзя без проверки отдавать как активный HTML или другой исполняемый контент.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как показать upload progress с <code>fetch</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Обычный `fetch` не предоставляет простой стабильный progress event загрузки request body во всех целевых браузерах.

Если upload progress обязателен, используют `XMLHttpRequest.upload`, поддерживаемую библиотеку или контролируемую chunk/resumable upload схему.

Download progress можно рассчитывать, читая `response.body` как stream. Для точного процента также нужен достоверный общий размер ответа.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как обрабатывать большой файл?</strong></summary>

<dl>
<dd>
<h2></h2>

Не следует без необходимости читать весь файл в строку, преобразовывать его в base64 или хранить содержимое в React state.

Используют `Blob.stream()`, чтение по chunks, Worker для CPU-heavy parsing, incremental upload или серверную обработку.

Само использование stream не гарантирует низкое потребление памяти. Parser и остальная цепочка обработки тоже должны поддерживать incremental processing, иначе данные всё равно будут полностью собраны в одном из этапов.

Также нужно учитывать отмену, progress, лимиты памяти и partial failure.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли программно установить путь file input?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Браузер не позволяет странице выбрать произвольный локальный файл без действия пользователя.

Значение file input можно очистить, но нельзя назначить ему путь к файлу на компьютере пользователя.

В React file input обычно остаётся uncontrolled, а выбранный `FileList` читают из события или через ref.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит с File при structured clone?</strong></summary>

<dl>
<dd>
<h2></h2>

`Blob` и `File` поддерживаются structured clone и могут передаваться в Worker без преобразования в JSON.

Получение объекта в Worker не делает дальнейшую обработку бесплатной: Worker всё равно должен прочитать и разобрать его содержимое.

После чтения данных в `ArrayBuffer` его можно передать через transfer list, если нужно переместить владение буфером без копирования.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как скачать созданный на клиенте файл?</strong></summary>

<dl>
<dd>
<h2></h2>

Нужно создать `Blob`, object URL и ссылку `<a download>`, запустить ожидаемый пользовательский сценарий, затем удалить временную ссылку и вызвать `URL.revokeObjectURL`.

Значение атрибута `download` является подсказкой для имени файла и может быть изменено браузером.

Для очень больших экспортов лучше использовать серверную генерацию или streaming-подход, чтобы не собирать весь файл в памяти страницы.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```js
const formData = new FormData();

formData.append("tag", "js");
formData.append("tag", "react");
formData.set("tag", "web");

console.log(formData.getAll("tag"));
```

<details>
<summary><strong>Что будет выведено?</strong></summary>

<dl>
<dd>
<h2></h2>

`["web"]`. Два вызова `append` создали повторяющиеся значения, после чего `set` заменил все записи с именем `tag` одним новым значением.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | API | Главный нюанс |
| --- | --- | --- |
| Multipart upload | FormData | Не задавать boundary вручную |
| Несколько файлов | `append` | Сервер должен ожидать повторяющийся key |
| Preview | Object URL | Revoke при замене или cleanup |
| Маленький текстовый файл | `blob.text()` | Обработать encoding и размер |
| Большой import | Stream и Worker | Не буферизовать всё без необходимости |
| File validation | Client и server | MIME/extension не являются доказательством |
