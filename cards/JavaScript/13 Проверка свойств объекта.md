## Вопрос

<br>

 💬 **Как проверить наличие свойства в объекте? Чем отличаются `in`, `Object.hasOwn`, `hasOwnProperty` и optional chaining?**

<h2></h2>

<br>
<dl>
<dd>

Способ проверки зависит от того, что именно нужно узнать: существует ли свойство с учётом цепочки прототипов, принадлежит ли оно самому объекту или какое значение вернётся при чтении.

Оператор `in` проверяет наличие собственного или унаследованного свойства. Значение свойства при этом не важно: оно может быть равно даже `undefined`.

```js
const user = Object.create({ role: "user" });
user.name = "Ada";

"name" in user; // true
"role" in user; // true
```

`Object.hasOwn(object, key)` проверяет только собственные свойства объекта и не учитывает его прототипы:

```js
Object.hasOwn(user, "name"); // true
Object.hasOwn(user, "role"); // false
```

Метод `object.hasOwnProperty(key)` отвечает на тот же вопрос, но вызывать его напрямую ненадёжно. Объект может содержать собственное свойство с именем `hasOwnProperty` или вообще не иметь прототипа. В старом коде используют `Object.prototype.hasOwnProperty.call(object, key)`, а в современном — `Object.hasOwn`.

Проверка `object[key] !== undefined` проверяет полученное значение, а не наличие свойства. Свойство может существовать и при этом содержать `undefined`:

```js
const patch = { name: undefined };

Object.hasOwn(patch, "name"); // true
patch.name !== undefined;     // false
```

Optional chaining `object?.profile?.name` также не проверяет наличие или принадлежность свойства. Он безопасно читает значение и возвращает `undefined`, если слева встречается `null` или `undefined`.

По результату такого чтения нельзя определить, отсутствует ли свойство или существует со значением `undefined`.

Оператор `in` требует, чтобы справа находился объект. Проверка свойства у `null`, `undefined` или другого примитива через `in` вызовет `TypeError`.

`Object.hasOwn` выбрасывает ошибку для `null` и `undefined`. Остальные примитивы он внутренне преобразует в объекты, но при проверке внешних данных всё равно сначала нужно убедиться, что значение имеет ожидаемую объектную структуру.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Когда использовать <code>in</code>, а когда <code>Object.hasOwn</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`in` используют, когда нужно учитывать всю цепочку прототипов. Например, так можно проверить наличие метода у экземпляра независимо от того, находится метод в самом объекте или в прототипе.

`Object.hasOwn` используют, когда важны только явно записанные свойства самого объекта. Это типично для словарей данных, конфигураций, DTO и PATCH-объектов, где унаследованные свойства не должны считаться входными данными.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Вызывает ли оператор <code>in</code> getter свойства?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Оператор `in` проверяет существование ключа, но не читает его значение, поэтому обычный getter не вызывается.

Проверка `object.key !== undefined` выполняет чтение свойства. Она может вызвать getter или ловушку `get` у Proxy.

Если сам объект является Proxy, оператор `in` может вызвать его ловушку `has`. Поэтому поведение проверки может быть определено пользовательским кодом Proxy.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>Object.keys</code>, <code>for...in</code> и <code>Reflect.ownKeys</code> отличаются?</strong></summary>

<dl>
<dd>
<h2></h2>

`Object.keys` возвращает собственные перечисляемые свойства со строковыми ключами. Унаследованные, неперечисляемые и символьные свойства в результат не попадают.

`for...in` перебирает перечисляемые строковые свойства самого объекта и его прототипов. Поэтому внутри такого цикла часто используют `Object.hasOwn`, если нужны только собственные данные.

`Reflect.ownKeys` возвращает все собственные ключи объекта: строковые и символьные, перечисляемые и неперечисляемые. Унаследованные свойства он не возвращает.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>Object.hasOwn</code> важен для PATCH-запроса?</strong></summary>

<dl>
<dd>
<h2></h2>

В PATCH-объекте сам факт наличия ключа может иметь отдельный смысл. Например, отсутствующий ключ может означать «не изменять поле», а переданный ключ со значением `null` — «очистить поле».

Конкретное значение зависит от контракта API, но проверка truthy/falsy не позволяет различить отсутствие ключа, `null`, `false`, `0` и пустую строку.

`Object.hasOwn(patch, "name")` проверяет именно то, было ли поле явно передано в объекте.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверка собственных свойств связана с prototype pollution?</strong></summary>

<dl>
<dd>
<h2></h2>

Prototype pollution может возникнуть, когда внешний ключ без проверки используется для глубокого присваивания или слияния объектов. Опасные пути вроде `__proto__`, `constructor.prototype` могут изменить общий прототип, после чего неожиданные свойства появятся у других объектов.

`Object.hasOwn` помогает не принимать унаследованные свойства за пользовательские данные, но одной этой проверки недостаточно.

На границе приложения используют список разрешённых ключей, отдельно запрещают опасные пути, не выполняют бесконтрольное глубокое слияние внешних объектов и обновляют библиотеки, работающие с такими операциями. Для словарей также можно использовать `Map` или `Object.create(null)`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда optional chaining скрывает ошибку контракта?</strong></summary>

<dl>
<dd>
<h2></h2>

Optional chaining может скрыть ошибку, если поле должно обязательно присутствовать.

Например, `response?.user?.name` вернёт `undefined` и при допустимом отсутствии `user`, и при неправильной структуре ответа API. В результате проблема может проявиться позже в интерфейсе и дальше от места её возникновения.

Для действительно необязательных веток `?.` уместен. Обязательные внешние данные сначала проверяют и при нарушении ожидаемой структуры создают явную ошибку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли использовать переменную как ключ в <code>in</code> и <code>Object.hasOwn</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Да. Оба механизма принимают строковый или символьный ключ.

Числовой ключ будет преобразован в строку. Например, число `0` станет строковым ключом `"0"`. Значение типа `symbol` останется символьным ключом.

Сам факт поддержки динамического ключа не делает его безопасным. Если ключ получен извне, нужно отдельно проверить, разрешён ли он правилами приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как безопасно применить оператор <code>in</code> к значению неизвестного типа?</strong></summary>

<dl>
<dd>
<h2></h2>

Сначала нужно убедиться, что значение не равно `null` и является объектом или функцией. Только после этого его можно использовать справа от `in`.

Проверки только `typeof value === "object"` недостаточно, потому что `typeof null` также возвращает `"object"`.

Если проверяются внешние данные, одной проверки типа обычно мало: дополнительно проверяют ожидаемые собственные свойства и типы их значений.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```js
const base = { inherited: 1 };
const value = Object.create(base);

Object.defineProperty(value, "hidden", {
  value: undefined,
  enumerable: false,
});

value.visible = 2;

console.log("inherited" in value);
console.log(Object.hasOwn(value, "inherited"));
console.log(Object.hasOwn(value, "hidden"));
console.log(Object.keys(value));
console.log(Reflect.ownKeys(value));
```

<details>
<summary><strong>Что покажут проверки и перечисление ключей?</strong></summary>

<dl>
<dd>
<h2></h2>

Будут выведены `true`, `false`, `true`, `["visible"]` и `["hidden", "visible"]`.

Свойство `inherited` существует в прототипе `base`, поэтому оператор `in` его находит. Но оно не принадлежит самому объекту `value`, поэтому `Object.hasOwn` возвращает `false`.

Свойство `hidden` является собственным, поэтому `Object.hasOwn` возвращает `true`, даже несмотря на значение `undefined` и флаг `enumerable: false`.

`Object.keys` возвращает только собственное перечисляемое свойство `visible`. `Reflect.ownKeys` возвращает все собственные ключи, поэтому включает и неперечисляемое свойство `hidden`.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Подход |
| --- | --- |
| PATCH-объект | `Object.hasOwn` отличает отсутствие ключа от явно переданного поля |
| Экземпляр класса | `in` учитывает методы и свойства из прототипов |
| Внешний словарь | Проверка типа объекта, собственных ключей и списка разрешённых полей |
| `for...in` | `Object.hasOwn` отфильтровывает унаследованные свойства |
| Необязательная ветка | `?.` безопасно читает значение, но не доказывает наличие свойства |
| Proxy | Оператор `in` может вызвать ловушку `has` |
