## Вопрос

<br>

 💬 **Как проверить наличие свойства в объекте? Чем отличаются `in`, `Object.hasOwn`, `hasOwnProperty` и optional chaining?**

<h2></h2>

<br>
<dl>
<dd>

Способ проверки выбирают по вопросу, на который должен ответить код: существует ли свойство в цепочке прототипов, принадлежит ли оно самому объекту или какое значение получится при чтении.

Оператор `in` проверяет собственные и унаследованные свойства:

```js
const user = Object.create({ role: "user" });
user.name = "Ada";

"name" in user; // true
"role" in user; // true
```

`Object.hasOwn(object, key)` проверяет только собственное свойство:

```js
Object.hasOwn(user, "name"); // true
Object.hasOwn(user, "role"); // false
```

Метод `object.hasOwnProperty(key)` решает ту же задачу, но полагаться на него напрямую опасно. Объект может переопределить это имя или иметь прототип `null`. Для старой среды используют `Object.prototype.hasOwnProperty.call(object, key)`, для современной предпочтителен `Object.hasOwn`.

Проверка `object[key] !== undefined` отвечает на другой вопрос. Свойство может существовать и хранить `undefined`:

```js
const patch = { name: undefined };

Object.hasOwn(patch, "name"); // true
patch.name !== undefined;     // false
```

Optional chaining `object?.profile?.name` не проверяет принадлежность свойства. Он безопасно читает значение и возвращает `undefined`, если слева встретились `null` или `undefined`. По результату нельзя отличить отсутствующее свойство от существующего со значением `undefined`.

Перед любой проверкой внешнее значение должно быть объектом и не быть `null`: `in` и `Object.hasOwn` выбрасывают ошибку на неподходящем правом операнде.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Когда использовать <code>in</code>, а когда <code>Object.hasOwn</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`in` нужен, когда контракт включает наследование: например, проверить наличие метода у экземпляра независимо от того, лежит он в самом объекте или прототипе. `Object.hasOwn` нужен для словаря данных, DTO, PATCH-объекта или конфигурации, где учитываются только явно переданные ключи.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Вызывает ли оператор <code>in</code> getter свойства?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Он проверяет существование ключа в объекте и цепочке прототипов, но не читает значение. Выражение `object.key !== undefined` выполняет обычный доступ и может вызвать getter, Proxy-ловушку или другое пользовательское поведение.

У Proxy оператор `in` может быть перехвачен ловушкой `has`, поэтому для произвольного Proxy даже проверка наличия не обязательно является простой операцией.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>Object.keys</code>, <code>for...in</code> и <code>Reflect.ownKeys</code> отличаются?</strong></summary>

<dl>
<dd>
<h2></h2>

`Object.keys` возвращает собственные перечисляемые строковые ключи. `for...in` обходит перечисляемые строковые ключи самого объекта и его прототипов, поэтому внутри такого цикла часто нужна `Object.hasOwn`. `Reflect.ownKeys` возвращает все собственные строковые и символьные ключи, включая неперечисляемые.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>Object.hasOwn</code> важен для PATCH-запроса?</strong></summary>

<dl>
<dd>
<h2></h2>

Отсутствующий ключ может означать «не менять поле», а присутствующий ключ со значением `null` «очистить». Проверка значения по truthy/falsy или только на `undefined` стирает эту разницу. `Object.hasOwn(patch, "name")` фиксирует сам факт передачи поля.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как проверка собственных свойств связана с prototype pollution?</strong></summary>

<dl>
<dd>
<h2></h2>

Если код рассматривает унаследованные ключи как пользовательские данные или без фильтра выполняет глубокую запись по внешнему пути, злоумышленник может повлиять на общий прототип. После этого значения появятся у несвязанных объектов.

На границе ограничивают допустимые ключи, используют `Object.hasOwn`, не доверяют `__proto__`/`constructor`/`prototype`, обновляют библиотеки слияния и для словарей рассматривают `Map` или `Object.create(null)`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Когда optional chaining скрывает ошибку контракта?</strong></summary>

<dl>
<dd>
<h2></h2>

Когда поле является обязательным. Цепочка `response?.user?.name` превращает неправильный ответ API в `undefined`, и ошибка проявляется позже в UI. Для действительно необязательной ветки `?.` уместен; обязательный внешний контракт сначала проверяют и при нарушении создают явную ошибку.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли использовать переменную как ключ в <code>in</code> и <code>Object.hasOwn</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Да. Оба механизма принимают property key: строку или `symbol`. Число будет преобразовано в строку. Для произвольного пользовательского ключа этого недостаточно для безопасности: нужно отдельно проверить, разрешён ли такой ключ бизнес-контрактом.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```js
const base = { inherited: 1 };
const value = Object.create(base);

Object.defineProperty(value, "hidden", {
  value: undefined,
  enumerable: false,
});

value.visible = 2;

console.log("inherited" in value);
console.log(Object.hasOwn(value, "inherited"));
console.log(Object.hasOwn(value, "hidden"));
console.log(Object.keys(value));
console.log(Reflect.ownKeys(value));
```

<details>
<summary><strong>Что покажут проверки и перечисление ключей?</strong></summary>

<dl>
<dd>
<h2></h2>

`in` вернёт `true` для унаследованного ключа, а `Object.hasOwn` для него вернёт `false`. Собственное неперечисляемое `hidden` существует, поэтому следующая проверка даст `true`. `Object.keys` вернёт только `["visible"]`, а `Reflect.ownKeys` вернёт `["hidden", "visible"]`.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Подход |
| --- | --- |
| PATCH-объект | `Object.hasOwn` отличает отсутствие ключа |
| Экземпляр класса | `in` учитывает методы прототипа |
| Внешний словарь | Проверка типа объекта, допустимых и собственных ключей |
| `for...in` | Фильтрация унаследованных свойств |
| Необязательная ветка | `?.` безопасно читает, но не доказывает наличие |
| Proxy | Проверка может вызвать ловушку `has` |
