## Вопрос

<br>

 💬 **Как работают `JSON.stringify` и `JSON.parse`? Какие данные нельзя без потерь представить в JSON?**

<h2></h2>

<br>
<dl>
<dd>

JSON — это текстовый формат для передачи и хранения данных. Он поддерживает объекты, массивы, строки, числа, `true`, `false` и `null`. Ключи объектов в JSON всегда являются строками.

В JSON нет отдельных типов для `undefined`, функций, `Symbol`, `BigInt`, дат, `Map`, `Set`, экземпляров классов и циклических ссылок. Поэтому такие значения либо преобразуются, либо пропускаются, либо приводят к ошибке.

`JSON.stringify(value)` выполняет сериализацию: преобразует JavaScript-значение в строку JSON. `JSON.parse(text)` выполняет обратную операцию: разбирает строку и создаёт из неё JavaScript-значение.

```js
const json = JSON.stringify({ id: 1, active: true });
const data = JSON.parse(json);

console.log(json); // '{"id":1,"active":true}'
console.log(data); // { id: 1, active: true }
```

При сериализации обычного объекта учитываются его собственные перечисляемые свойства со строковыми ключами. Перечисляемыми называют свойства, которые участвуют в стандартном обходе объекта. Унаследованные, неперечисляемые и символьные свойства в JSON не попадают.

Некоторые JavaScript-значения преобразуются по-разному в зависимости от того, находятся они в объекте или массиве:

| Значение | В свойстве объекта | В элементе массива |
| --- | --- | --- |
| `undefined`, функция, `Symbol` | Свойство пропускается | Записывается `null` |
| `NaN`, `Infinity`, `-Infinity` | Записывается `null` | Записывается `null` |
| `BigInt` | `TypeError` без явного преобразования | `TypeError` без явного преобразования |
| `Date` | Обычно ISO-строка через `toJSON` | Обычно ISO-строка через `toJSON` |
| `Map`, `Set` | Обычно `{}` без специального преобразования | Обычно `{}` без специального преобразования |

В объекте неподдерживаемое свойство можно пропустить целиком. В массиве позицию нельзя просто удалить без изменения индексов, поэтому неподдерживаемое значение записывается как `null`.

Если верхнеуровневое значение равно `undefined`, является функцией или символом, `JSON.stringify` возвращает JavaScript-значение `undefined`, а не строку. При обнаружении циклической ссылки метод выбрасывает `TypeError`.

Перед сериализацией объект может определить собственный метод `toJSON`, который возвращает значение для записи. Например, `Date` обычно преобразуется в ISO-строку именно через `toJSON`.

`JSON.parse` восстанавливает только типы, существующие в JSON. Дата останется строкой, экземпляр класса станет обычным объектом, а методы и исходный прототип не восстановятся.

Если переданная строка не соответствует синтаксису JSON, `JSON.parse` выбрасывает `SyntaxError`.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем JSON отличается от литерала объекта JavaScript?</strong></summary>

<dl>
<dd>
<h2></h2>

JSON — это текст в формате с ограниченным набором правил. Имена свойств и строки должны быть записаны в двойных кавычках. Комментарии, завершающие запятые, `undefined`, функции, методы, spread и вычисляемые выражения запрещены.

Литерал объекта является частью JavaScript-кода и поддерживает возможности языка:

```js
const user = {
  id: 1,
  getName() {},
  ["user" + "Name"]: "Ada",
};
```

Внешне JSON и объектный литерал могут выглядеть похоже, но JSON является данными в виде строки, а объектный литерал создаёт объект при выполнении JavaScript-кода.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем отличаются отсутствующее поле, <code>undefined</code> и <code>null</code> при отправке API?</strong></summary>

<dl>
<dd>
<h2></h2>

Отсутствующее поле вообще не передаётся в объекте. Поле со значением `undefined` существует в JavaScript, но при обычной сериализации объекта также исчезает из JSON. Поэтому после передачи сервер не сможет отличить эти два случая.

`null` сохраняется в JSON и передаётся явно.

Например, в `PATCH`-запросе отсутствие поля может означать «не изменять значение», а `null` — «очистить значение». Точный смысл каждого варианта должен быть описан в контракте API.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит с <code>Date</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Перед сериализацией `JSON.stringify` вызывает у объекта метод `toJSON`. У корректного экземпляра `Date` этот метод возвращает ISO-строку в UTC:

```js
JSON.stringify({
  createdAt: new Date("2026-01-01T00:00:00.000Z"),
});
```

После `JSON.parse` получится обычная строка, потому что в JSON нет отдельного типа даты.

Если приложению нужен объект `Date`, его необходимо восстановить явно:

```js
const createdAt = new Date(data.createdAt);
```

После преобразования следует проверить, что строка действительно представляла корректную дату.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Для чего нужны <code>replacer</code> и <code>reviver</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Второй аргумент `JSON.stringify` называется `replacer`. Он позволяет выбрать свойства для сериализации или преобразовать значения перед их записью.

Второй аргумент `JSON.parse` называется `reviver`. Он вызывается для разобранных значений и позволяет преобразовать их перед возвратом итогового результата.

```js
const json = JSON.stringify({ id: 1, secret: "x" }, ["id"]);

const data = JSON.parse(
  '{"createdAt":"2026-01-01T00:00:00.000Z"}',
  (key, value) => (key === "createdAt" ? new Date(value) : value),
);
```

В первом примере в JSON попадёт только поле `id`. Во втором поле `createdAt` будет преобразовано из строки в объект `Date`.

Автоматически превращать любую похожую строку в дату опасно. Структура данных должна точно определять, какие поля имеют тип даты.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли делать deep copy через <code>JSON.parse(JSON.stringify(value))</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Такой способ допустим только для заранее известной структуры, которая полностью совместима с JSON.

Он теряет `undefined`, функции, символы, специальные числовые значения и прототипы. `Date` превращается в строку, `Map` и `Set` — в обычные пустые объекты, а `BigInt` и циклические ссылки приводят к ошибке.

Кроме того, данные дважды полностью обходятся: сначала для создания строки, затем для её разбора.

Для копирования поддерживаемых JavaScript-типов обычно лучше использовать `structuredClone`. Он поддерживает циклические ссылки, `Date`, `Map` и `Set`, но также не способен клонировать любые значения, например функции.

При обновлении состояния приложения обычно не копируют всё дерево целиком, а создают новые объекты только для изменившихся ветвей.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как обработать циклическую ссылку?</strong></summary>

<dl>
<dd>
<h2></h2>

JSON представляет данные как вложенное дерево. Циклическая структура не имеет конечной точки вложенности, поэтому `JSON.stringify` не может записать её напрямую.

Сначала нужно определить, как представить такую связь в JSON. Для API обычно вместо обратной ссылки передают идентификатор другого объекта:

```js
{
  "userId": 1,
  "managerId": 2
}
```

Для отладочного вывода можно использовать `replacer`, который запоминает уже посещённые объекты и заменяет повторную ссылку специальной строкой.

При этом нельзя бездумно удалять все повторяющиеся объекты: несколько свойств могут ссылаться на один объект, не образуя цикла, и эта связь может быть важна для данных.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Достаточно ли успешного <code>JSON.parse</code>, чтобы доверять ответу API?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Успешный `JSON.parse` подтверждает только то, что строка имеет корректный синтаксис JSON.

Он не проверяет:

- наличие обязательных полей;
- типы значений;
- допустимые диапазоны;
- бизнес-правила;
- соответствие ожидаемой версии API.

Внешние данные нужно проверить на границе приложения, а затем преобразовать во внутреннюю модель.

Типы TypeScript существуют только во время разработки и не проверяют данные, которые реально пришли от сервера во время выполнения программы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли всегда оборачивать <code>JSON.parse</code> в <code>try...catch</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`JSON.parse` выбрасывает `SyntaxError`, если строка содержит некорректный JSON.

Если источник строки может быть повреждён или недостоверен и ошибка должна обрабатываться в текущем месте, используют `try...catch`. Это типично для данных из `localStorage`, пользовательского ввода или неизвестного внешнего формата.

```js
try {
  const data = JSON.parse(value);
} catch (error) {
  // Обработать некорректные данные
}
```

Метод `Response.json()` также завершает свой Promise с ошибкой, если тело ответа невозможно разобрать как JSON. В этом случае ошибку обрабатывают через `try...catch` вокруг `await` или через обработку отклонённого Promise.

Если строка гарантированно создаётся и контролируется текущей программой, отдельный `try...catch` на каждом вызове может быть не нужен.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```js
const value = {
  missing: undefined,
  invalidNumber: NaN,
  list: [undefined, Symbol("id")],
  createdAt: new Date("2026-01-01T00:00:00.000Z"),
};

const json = JSON.stringify(value);
const parsed = JSON.parse(json);

console.log(json);
console.log(typeof parsed.createdAt);
```

<details>
<summary><strong>Какие данные окажутся в строке и какой тип будет у <code>createdAt</code> после парсинга?</strong></summary>

<dl>
<dd>
<h2></h2>

Поле `missing` не попадёт в строку, потому что его значение равно `undefined`. Поле `invalidNumber` будет записано как `null`.

Элементы массива `undefined` и `Symbol("id")` будут заменены на `null`, поэтому `list` станет `[null, null]`.

Объект `Date` через `toJSON` преобразуется в ISO-строку. Итоговое значение будет соответствовать следующей структуре:

```json
{
  "invalidNumber": null,
  "list": [null, null],
  "createdAt": "2026-01-01T00:00:00.000Z"
}
```

После `JSON.parse` поле `createdAt` останется строкой, поэтому оператор `typeof` вернёт `"string"`.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Что учитывать |
| --- | --- |
| REST API | Успешный parse не заменяет проверку контракта |
| `localStorage` | Хранилище содержит строки, а данные могут устареть или повредиться |
| Черновик формы | Отсутствие поля, пустая строка и `null` могут иметь разный смысл |
| Даты | После parse дата остаётся строкой |
| `Map`, `Set`, `BigInt` | Нужен согласованный формат преобразования |
| Глубокая копия | JSON не сохраняет полную модель типов JavaScript |
