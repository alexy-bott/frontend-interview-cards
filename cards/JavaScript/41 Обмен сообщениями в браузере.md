## Вопрос

<br>

 💬 **Как безопасно обмениваться сообщениями между window, iframe, popup, вкладками и workers?**

<h2></h2>

<br>
<dl>
<dd>

`window.postMessage` позволяет отправить данные другому окну, на которое у кода есть ссылка:

- iframe доступен через `iframe.contentWindow`;
- popup — через результат `window.open`;
- открывшее окно — через `window.opener`.

Отправитель указывает ожидаемый `targetOrigin`, а получатель проверяет `event.origin`, `event.source` и структуру `event.data`.

```js
authWindow.postMessage(
  { type: "AUTH_REQUEST", requestId },
  "https://auth.example.com",
);

window.addEventListener("message", (event) => {
  if (event.origin !== "https://auth.example.com") return;
  if (event.source !== authWindow) return;
  if (!isAuthResponse(event.data)) return;

  completeAuth(event.data);
});
```

`targetOrigin` ограничивает доставку точным origin получателя — сочетанием protocol, host и port. Если окно к моменту доставки находится на другом origin, браузер не передаст ему сообщение.

Значение `"*"` разрешает доставку независимо от origin. Оно опасно для секретных данных: iframe или popup может быть перенаправлен на чужой сайт, который затем получит сообщение.

Получатель всё равно должен выполнить собственные проверки:

- `event.origin` подтверждает origin отправителя в момент отправки;
- `event.source` подтверждает конкретное окно, из которого пришло сообщение;
- `event.data` проверяется по прикладному протоколу.

Ссылка `event.source` указывает на browsing context, а не навсегда на одну страницу. После отправки сообщения это окно может перейти на другой origin, поэтому старую ссылку нельзя считать постоянным доказательством текущего содержимого окна.

`postMessage` работает асинхронно: он не вызывает listener прямо внутри текущего call stack. Сообщение ставится на последующую обработку, а отправляющий код продолжает выполнение.

Payload передаётся по алгоритму structured clone. Можно передавать обычные объекты, массивы, `Map`, `Set`, `Date`, `ArrayBuffer` и другие поддерживаемые значения.

Функции и DOM-узлы клонировать нельзя. У экземпляров пользовательских классов не следует рассчитывать на сохранение методов и исходного прототипа: протокол сообщений должен состоять из обычных данных.

Transfer list позволяет не копировать некоторые ресурсы, а передать их владение:

```js
targetWindow.postMessage(
  { buffer },
  "https://example.com",
  [buffer],
);
```

После передачи `ArrayBuffer` становится detached у отправителя и доступен получателю. Подобным образом можно передавать `MessagePort` и другие transferable-объекты.

`BroadcastChannel(name)` создаёт именованный канал между подходящими документами и workers одного origin и одной storage partition.

```js
const channel = new BroadcastChannel("app");

channel.postMessage({
  type: "LOGOUT",
});
```

Сообщение получают другие активные объекты `BroadcastChannel` с тем же именем. Объект, который вызвал `postMessage`, собственное сообщение не получает.

Канал не хранит историю. Вкладка, открытая позднее, не увидит старые сообщения. Поэтому `BroadcastChannel` подходит для живых сигналов между вкладками, но не является постоянным хранилищем или надёжной очередью.

Обмен с Worker использует похожие методы `postMessage` и события `message`. Проверка `origin` обычно не требуется, потому что связь уже задана конкретным объектом `Worker` или `MessagePort`.

При этом прикладной формат сообщения всё равно следует проверять, особенно если Worker, iframe или интеграционный код контролируются не полностью текущим приложением.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему нужно проверять и <code>event.origin</code>, и <code>event.source</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`event.origin` показывает origin страницы, которая отправила сообщение:

```text
scheme + host + port
```

`event.source` указывает на конкретное окно, iframe или popup, от которого сообщение пришло.

На одном доверенном origin может находиться несколько страниц или frames с разными ролями. Проверка только origin позволила бы любому из них попытаться отправить сообщение ожидаемого формата.

Для popup-сценария сравнение с сохранённой ссылкой подтверждает, что ответ пришёл именно из открытого приложением окна:

```js
if (event.source !== authWindow) return;
```

При этом `source` представляет browsing context. Окно может позднее перейти на другой сайт, поэтому для каждого сообщения всё равно проверяют актуальный `event.origin`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли доверять <code>event.data</code> после проверки origin?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. Проверка origin подтверждает источник сообщения, но не корректность данных.

Даже доверенный отправитель может:

- использовать старую версию протокола;
- содержать ошибку;
- быть скомпрометирован через XSS;
- прислать сообщение в неподходящем состоянии операции.

Payload проверяют во время выполнения:

- допустимый `type`;
- версию протокола;
- `requestId`;
- наличие обязательных полей;
- типы и допустимые значения.

TypeScript discriminated union помогает работать с уже проверенным сообщением внутри проекта, но не проверяет данные, поступившие во время выполнения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как спроектировать messaging protocol?</strong></summary>

<dl>
<dd>
<h2></h2>

У сообщений используют небольшой общий envelope:

```js
{
  type: "AUTH_RESPONSE",
  version: 1,
  requestId: "request-42",
  payload: {
    code: "..."
  }
}
```

Для каждого `type` определяют отдельную структуру `payload` и проверяют её во время выполнения.

Для request-response протокола обычно:

- создают уникальный `requestId`;
- хранят ожидающие запросы по этому идентификатору;
- принимают только один подходящий ответ;
- ограничивают время ожидания;
- удаляют запись после ответа, ошибки или timeout.

Нельзя без проверки превращать значение `type` в имя вызываемого метода или передавать код для выполнения. Входное сообщение должно выбирать только действие из заранее заданного allowlist.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что делать с iframe, у которого sandboxed origin равен <code>null</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Sandboxed iframe без разрешения `allow-same-origin` может получить opaque origin. В событии он отображается строкой:

```js
event.origin === "null"
```

Значению `"null"` нельзя доверять как уникальному origin: разные непрозрачные контексты могут иметь такое же представление.

Для отправки сообщения некоторым документам с opaque origin приходится использовать `targetOrigin: "*"`, потому что указать их точный origin невозможно.

В таком случае безопасность строят на дополнительных проверках:

- точном сравнении `event.source`;
- минимальном наборе разрешённых сообщений;
- одноразовом секрете или capability, переданном через безопасный handshake;
- проверке состояния текущей операции;
- отказе от передачи лишних секретных данных.

По возможности архитектуру строят с обычным origin, который можно проверить напрямую.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Связан ли <code>postMessage</code> с CORS?</strong></summary>

<dl>
<dd>
<h2></h2>

Напрямую нет.

CORS управляет тем, может ли JavaScript прочитать cross-origin сетевой ответ через `fetch` или XHR.

`postMessage` — отдельный канал обмена между уже существующими окнами и frames. Его безопасность основана на:

- точном `targetOrigin`;
- проверке `event.origin`;
- проверке `event.source`;
- валидации `event.data`.

Успешная настройка CORS не означает, что сообщения от этого origin можно принимать без проверки. И наоборот, безопасный `postMessage` не предоставляет доступ к закрытым сетевым ответам.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Выполняется ли <code>postMessage</code> синхронно и можно ли полагаться на порядок сообщений?</strong></summary>

<dl>
<dd>
<h2></h2>

`postMessage` не вызывает обработчик синхронно. Отправляющий код сначала завершает текущий call stack, а событие `message` обрабатывается позднее.

```js
target.postMessage("message", origin);
console.log("after postMessage");
```

Строка `"after postMessage"` будет выполнена до listener получателя.

Последовательные сообщения одного канала должны обрабатываться как протокол, но нельзя предполагать единый глобальный порядок для сообщений от разных окон, workers или независимых каналов.

Если порядок важен, в сообщение добавляют `sequence`, `version` или `requestId`, а получатель проверяет ожидаемое состояние.

`postMessage` также не предоставляет подтверждение доставки. Для надёжного request-response сценария получатель должен отправить отдельный ответ или acknowledgement.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем <code>MessageChannel</code> отличается от прямого <code>window.postMessage</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`MessageChannel` создаёт два связанных объекта `MessagePort`:

```js
const channel = new MessageChannel();

channel.port1.onmessage = (event) => {
  console.log(event.data);
};

channel.port2.postMessage("hello");
```

Один port можно передать iframe, popup или Worker через transfer list. После этого участники общаются по выделенному каналу.

В отличие от глобального `window`-события `message`, listener получает только сообщения этого port. Это упрощает изоляцию протокола, handshake и RPC.

Если listener регистрируется через `addEventListener("message", ...)`, port обычно нужно запустить через `port.start()`. Присваивание `port.onmessage` запускает его автоматически.

Когда канал больше не нужен, port закрывают через `port.close()`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем BroadcastChannel отличается от <code>storage</code> event?</strong></summary>

<dl>
<dd>
<h2></h2>

`BroadcastChannel` предназначен непосредственно для обмена сообщениями. Он передаёт structured-clone значения и не требует записывать данные на диск.

`storage` event является следствием изменения `localStorage`. Он передаёт строковые `oldValue` и `newValue` и не возникает в документе, который сам выполнил запись.

Для явного современного протокола между вкладками `BroadcastChannel` обычно понятнее:

```js
channel.postMessage({
  type: "CACHE_INVALIDATED",
  version: 2,
});
```

`storage` event можно использовать как fallback в среде без подходящей поддержки или когда изменение `localStorage` само является источником события.

Ни один вариант не превращает сообщения в транзакционную очередь.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему две страницы одного origin иногда не видят один BroadcastChannel?</strong></summary>

<dl>
<dd>
<h2></h2>

Современные браузеры могут разделять хранилища и коммуникационные механизмы не только по origin, но и по top-level site.

Например, iframe с origin `https://b.example`, открытый внутри `https://a.example`, может находиться в другой storage partition, чем отдельная top-level вкладка `https://b.example`.

Несмотря на одинаковый origin iframe и вкладки, они могут не получить доступ к одному каналу.

Поэтому нельзя использовать предположение «одинаковый origin всегда гарантирует общий BroadcastChannel» для обхода ограничений third-party privacy.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Подходит ли BroadcastChannel для надёжной очереди событий?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. BroadcastChannel не предоставляет:

- постоянное хранение;
- историю и повторную доставку;
- acknowledgement;
- доставку закрытой или ещё не открытой вкладке;
- гарантированное восстановление после сбоя.

Он подходит для живой координации:

- сообщения о logout;
- синхронизации темы;
- уведомления об изменении кеша;
- предложения перечитать актуальное состояние;
- координации активных вкладок.

Важные данные хранят на сервере или в IndexedDB. BroadcastChannel только сообщает другим вкладкам, что источник истины изменился и его следует перечитать.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как избежать конфликтов между вкладками?</strong></summary>

<dl>
<dd>
<h2></h2>

Сообщение не делает изменение состояния атомарным. Несколько вкладок могут одновременно прочитать старое значение и записать разные результаты.

Для выбора одной активной вкладки используют:

- lease с ограниченным сроком действия;
- Web Locks API;
- серверную координацию.

К обновлениям состояния добавляют `version`, timestamp или другой механизм разрешения конфликтов.

Правило «последнее сообщение победило» подходит не для всех данных. При одновременной работе оно может без предупреждения потерять изменения одной из вкладок.

Для критических операций итоговый порядок и конфликт должен разрешать сервер или транзакционное хранилище.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как обрабатывать lifecycle?</strong></summary>

<dl>
<dd>
<h2></h2>

При завершении сценария нужно освободить связанные ресурсы:

- удалить `window` listener через `removeEventListener`;
- закрыть `BroadcastChannel`;
- закрыть `MessagePort`;
- очистить timeout ожидающих запросов;
- удалить pending requests;
- игнорировать поздние ответы завершённой операции.

Для popup дополнительно проверяют, не было ли окно закрыто до получения ответа, и завершают ожидающий Promise с понятной ошибкой.

В React ресурс создают и уничтожают в одном effect либо передают общий lifecycle отдельному сервису с явным владельцем.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое <code>messageerror</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Событие `messageerror` возникает, когда получатель не смог десериализовать переданное сообщение.

Это отличается от прикладной ошибки в структуре `event.data`. При прикладной ошибке structured clone уже завершился успешно, но данные не соответствуют протоколу приложения.

`messageerror` поддерживают, в частности, `MessagePort`, `BroadcastChannel` и Worker:

```js
channel.addEventListener("messageerror", (event) => {
  console.error("Не удалось прочитать сообщение", event);
});
```

Такую ошибку полезно отправить в диагностику. Исправлять нужно несовместимый тип данных, transfer list или контекст передачи.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```js
function onMessage(event) {
  if (event.origin !== "https://pay.example.com") return;
  if (event.source !== paymentFrame.contentWindow) return;
  if (event.data?.type !== "PAYMENT_DONE") return;
  if (typeof event.data.orderId !== "string") return;

  completeOrder(event.data.orderId);
}

window.addEventListener("message", onMessage);
```

<details>
<summary><strong>Какие четыре независимые проверки здесь выполнены?</strong></summary>

<dl>
<dd>
<h2></h2>

Выполнены четыре отдельные проверки:

1. `event.origin` подтверждает origin отправителя.
2. `event.source` подтверждает конкретный iframe.
3. `event.data.type` ограничивает список допустимых команд.
4. Тип `orderId` проверяется во время выполнения.

В реальном платёжном сценарии также следует проверить:

- соответствие `orderId` текущему заказу;
- `requestId` или другой correlation id;
- текущее состояние операции;
- отсутствие уже обработанного ответа.

После успешного завершения listener нужно удалить, чтобы позднее или повторное сообщение не запустило действие ещё раз.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Канал | Обязательная защита |
| --- | --- | --- |
| Payment iframe | Window postMessage | Origin, source, schema, correlation id |
| OAuth popup | Window postMessage | Origin, popup reference, OAuth state |
| Worker RPC | Worker/MessagePort | Message ids, error и cancellation protocol |
| Cross-tab logout | BroadcastChannel | Сервер остаётся источником auth state |
| Cross-tab cache invalidation | BroadcastChannel | Version и повторное чтение данных |
| Legacy cross-tab fallback | Storage event | Строковая schema и races |
