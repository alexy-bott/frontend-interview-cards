#### Вопрос

Что такое контекст выполнения, лексическое окружение и цепочка областей видимости?

#### Ответ

Контекст выполнения (`execution context`) описывает состояние, необходимое движку для выполнения текущего кода. Отдельные контексты создаются для глобального кода, модулей, вызовов функций и некоторых других механизмов языка. Активные контексты образуют стек вызовов (`call stack`).

```js
function outer() {
  function inner() {
    return 1;
  }

  return inner();
}

outer();
```

При вызове `outer` её контекст помещается поверх глобального, при вызове `inner` появляется следующий. После возврата контексты функций снимаются со стека в обратном порядке.

Лексическое окружение (`lexical environment`) является структурой спецификации, через которую код связывает имена с переменными, функциями и другими объявлениями. Оно состоит из записи окружения и ссылки на внешнее окружение.

Когда код читает идентификатор, движок ищет привязку в текущем окружении. Если её нет, поиск продолжается во внешнем окружении и далее до конца цепочки. Это называют scope chain, или цепочкой областей видимости:

```js
const value = "global";

function outer() {
  const value = "outer";

  return function inner() {
    return value;
  };
}

outer()(); // "outer"
```

JavaScript использует лексическую область видимости: внешнее окружение функции определяется местом её создания в исходном коде. Место последующего вызова не меняет эту цепочку.

Область видимости и лексическое окружение связаны, но не тождественны. Scope описывает статический участок исходного кода, где доступно имя. Lexical environment является моделью привязок, существующих во время выполнения конкретного входа в эту область.

#### Встречные вопросы

> [!followup]
> **Вопрос:** Что происходит с объявлениями до выполнения инструкций функции?
>
> **Ответ:** При создании контекста движок подготавливает окружения и привязки объявлений. `var` получает `undefined`, function declaration получает функцию, а `let`, `const` и `class` остаются неинициализированными до своих строк. Затем инструкции выполняются по порядку.
>
> Деление на «фазу создания» и «фазу выполнения» является полезной учебной моделью. Точные шаги спецификации зависят от вида кода, но эта модель корректно объясняет hoisting и TDZ без идеи физического перемещения строк.

> [!followup]
> **Вопрос:** Чем контекст выполнения отличается от лексического окружения?
>
> **Ответ:** Контекст представляет активное выполнение: текущую функцию или модуль, положение продолжения, связанные окружения и сведения о вызове. Лексическое окружение отвечает именно за разрешение имён и связь с внешней областью. Один контекст может использовать несколько окружений, например при входе во вложенные блоки.

> [!followup]
> **Вопрос:** Что происходит с окружением после выхода функции со стека?
>
> **Ответ:** Если на окружение больше ничего не ссылается, оно может быть освобождено сборщиком мусора. Если возвращённая функция использует внешние привязки, её внутренний `[Environment](<./42 Execution context lexical environment scope chain.md>)` сохраняет доступ к нужному окружению. Контекст вызова уже не находится на стеке, но захваченные данные остаются достижимыми через замыкание.

> [!followup]
> **Вопрос:** Чем lexical scope отличается от dynamic scope?
>
> **Ответ:** При lexical scope функция ищет имена относительно места объявления. При dynamic scope поиск зависел бы от того, какие функции вызвали её во время выполнения. JavaScript использует первый вариант.
>
> Поэтому передача callback в таймер, Promise или обработчик события не меняет доступные ему внешние переменные.

> [!followup]
> **Вопрос:** Что происходит при затенении переменной?
>
> **Ответ:** Внутреннее окружение создаёт привязку с тем же именем, и поиск останавливается на ней. Внешнее значение не изменяется, но временно недоступно по этому имени. Если внутренняя привязка находится в TDZ, поиск не продолжится наружу: обращение завершится `ReferenceError`.

> [!followup]
> **Вопрос:** Чем окружение ES-модуля отличается от глобального скрипта?
>
> **Ответ:** Верхнеуровневые объявления модуля находятся в модульном окружении, не становятся свойствами `window` и доступны другим модулям только через `export` и `import`. Импорты являются живыми привязками: потребитель видит изменение экспортируемого значения после его инициализации.
>
> Глобальное окружение браузерного скрипта сочетает объектную часть для некоторых `var` и function declarations с отдельной декларативной частью для `let`, `const` и `class`.

> [!followup]
> **Вопрос:** Где хранится `this`?
>
> **Ответ:** `this` относится к контексту вызова и записи окружения функции, но не ищется как обычная переменная по scope chain. Обычная функция получает собственную привязку `this` согласно форме вызова. Стрелочная функция собственной привязки не создаёт и использует `this` внешнего окружения.

#### Мини-задача

```js
const value = "global";

function createReader() {
  const value = "created";

  return function read() {
    return value;
  };
}

function run(callback) {
  const value = "called";
  return callback();
}

console.log(run(createReader()));
```

> [!followup]
> **Вопрос:** Почему будет выведено `"created"`, а не `"called"`?
>
> **Ответ:** Функция `read` создана внутри `createReader`, поэтому её внешнее окружение содержит привязку `value = "created"`. Вызов из `run` добавляет новый контекст в call stack, но не меняет лексическую цепочку функции. Локальная переменная `run` для неё не видна.

#### Где это встречается во frontend

| Ситуация | Что объясняет модель |
| --- | --- |
| Замыкание | Окружение может жить дольше вызова, который его создал |
| React callback | Функция принадлежит окружению конкретного рендера |
| Hoisting и TDZ | Привязка создаётся до выполнения, но не всегда инициализирована |
| ES-модули | Верхнеуровневые имена имеют модульную область |
| Debugger | Панели Call Stack и Scope показывают разные части модели |
| `this` | Определяется вызовом, а не обычным поиском имени |
