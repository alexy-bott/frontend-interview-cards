## Вопрос

<br>

 💬 **Как работают регулярные выражения в JavaScript? Какие ошибки при их использовании особенно важны во frontend?**

<h2></h2>

<br>
<dl>
<dd>

Регулярное выражение, или `RegExp`, описывает шаблон поиска в строке. Его используют для поиска совпадений, извлечения частей текста, замены и проверки простого формата. Оно состоит из шаблона и флагов, которые меняют режим сопоставления.

```js
const orderPattern = /^ORD-(\d+)$/;
const match = orderPattern.exec("ORD-42");

console.log(match?.[1]); // "42"
```

Символы `^` и `$` привязывают шаблон к началу и концу строки. Скобки `(...)` создают capturing group, или захватывающую группу: совпавшая часть доступна отдельно. `\d+` означает одну или больше цифр.

Основные флаги:

| Флаг | Назначение |
| --- | --- |
| `i` | Сравнение без учёта регистра |
| `g` | Глобальный поиск с сохранением следующей позиции в `lastIndex` |
| `m` | `^` и `$` работают для каждой строки многострочного текста |
| `s` | Точка `.` также совпадает с переводом строки |
| `u` | Unicode-aware режим и корректная обработка Unicode code points |
| `y` | Поиск начинается строго с позиции `lastIndex` |
| `d` | Результат содержит индексы совпавших диапазонов |

`RegExp` подходит для ограниченного текстового шаблона. Он не заменяет парсер HTML, JSON или языка программирования и не доказывает бизнес-корректность значения. Например, регулярное выражение может проверить общую форму email, но факт существования адреса подтверждается другим способом.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Чем отличаются <code>test</code>, <code>exec</code>, <code>match</code> и <code>matchAll</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`regexp.test(text)` отвечает только `true` или `false`.

`regexp.exec(text)` возвращает одно совпадение вместе с группами, индексом и исходной строкой.

`text.match(regexp)` без флага `g` похож на `exec`, а с `g` возвращает массив полных совпадений без подробной информации о группах.

`text.matchAll(regexp)` возвращает iterator со всеми совпадениями, группами и индексами и требует глобальный флаг `g`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему повторный <code>test</code> с флагом <code>g</code> может менять результат?</strong></summary>

<dl>
<dd>
<h2></h2>

`RegExp` с флагом `g` или `y` хранит следующую позицию поиска в свойстве `lastIndex`.

Успешный `test` сдвигает `lastIndex`, а неуспешный поиск сбрасывает его в `0`. Поэтому один экземпляр с `g` или `y` является stateful, то есть сохраняет состояние между вызовами.

```js
const pattern = /a/g;

pattern.test("a"); // true, lastIndex === 1
pattern.test("a"); // false, поиск начался с позиции 1
```

Если нужно выполнить независимую проверку, не используют `g` либо перед проверкой явно сбрасывают `lastIndex`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем нужны <code>^</code> и <code>$</code> при валидации?</strong></summary>

<dl>
<dd>
<h2></h2>

Без границ шаблон может найти допустимый фрагмент внутри недопустимой строки.

`/\d+/` успешно совпадёт с `"abc123xyz"`, а `/^\d+$/` требует, чтобы строка соответствовала шаблону целиком.

При флаге `m` символы `^` и `$` также относятся к началу и концу каждой строки многострочного текста, поэтому такой режим при валидации нужно использовать осознанно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое захватывающие и незахватывающие группы?</strong></summary>

<dl>
<dd>
<h2></h2>

Группа `(...)` объединяет часть шаблона и сохраняет совпавший фрагмент в результате.

Группа `(?:...)` только объединяет выражение и не добавляет отдельный элемент в результат.

Именованная группа `(?<year>\d{4})` доступна как `match.groups.year`, что делает извлечение данных из сложного шаблона понятнее.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем литерал RegExp отличается от <code>new RegExp()</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Литерал `/\d+/` удобен, когда шаблон известен во время написания кода.

Конструктор `new RegExp(pattern, flags)` нужен, когда шаблон формируется динамически. Поскольку его шаблон передаётся обычной JavaScript-строкой, обратную косую черту приходится экранировать дважды:

```js
const literal = /\d+/;
const dynamic = new RegExp("\\d+");
```

Обе записи создают шаблон `\d+`. Запись `new RegExp("\d+")` некорректна для этой цели, потому что строковый литерал сначала обрабатывается самим JavaScript.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как безопасно вставить пользовательскую строку в динамический <code>RegExp</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Если строка должна означать буквальный текст, её специальные символы нужно экранировать через `RegExp.escape(value)`.

Иначе ввод вроде `.` или `.*` изменит смысл шаблона:

```js
const pattern = new RegExp(RegExp.escape(userInput), "i");
```

`RegExp.escape` доступен в современных браузерах. Для старых целевых сред нужна проверенная совместимая реализация или отказ от динамического регулярного выражения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое catastrophic backtracking и ReDoS?</strong></summary>

<dl>
<dd>
<h2></h2>

Некоторые шаблоны с неоднозначными вложенными повторениями заставляют движок проверять очень большое количество вариантов на почти подходящей строке.

Время выполнения может вырасти настолько, что main thread зависнет. Атака через специально подготовленный ввод называется ReDoS — отказом в обслуживании из-за регулярного выражения.

Следует избегать конструкций вроде вложенных квантификаторов `(a+)+`, ограничивать длину внешнего ввода, тестировать длинные неуспешные строки и выбирать простой последовательный разбор, если формат слишком сложный.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему регулярное выражение не всегда подходит для проверки email?</strong></summary>

<dl>
<dd>
<h2></h2>

Полный стандарт email сложен, а чрезмерно строгий шаблон может отклонить допустимые адреса.

Во frontend обычно достаточно базовой проверки формы и нативного `type="email"`, чтобы помочь пользователю заметить ошибку.

Сервер всё равно повторяет проверку, а существование и принадлежность адреса подтверждаются письмом или другим процессом верификации.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что меняет Unicode-режим?</strong></summary>

<dl>
<dd>
<h2></h2>

С флагом `u` шаблон учитывает Unicode code points, а не только отдельные 16-битные code units UTF-16.

Это важно для символов вне базовой многоязычной плоскости, которые занимают в строке две code units.

Для классов символов разных языков можно использовать Unicode property escapes:

```js
/\p{Letter}+/u
```

Property escapes требуют Unicode-режима `u` или `v`.

<h2></h2>
</dd>
</dl>

</details>

## Мини-задача

```js
const pattern = /^(?<name>[a-z]+)-(?<id>\d+)$/i;
const match = pattern.exec("Order-42");

console.log(match?.groups);
console.log(pattern.test("bad-42-extra"));
```

<details>
<summary><strong>Что будет выведено?</strong></summary>

<dl>
<dd>
<h2></h2>

Первая строка выведет объект с `name: "Order"` и `id: "42"`. Значения групп являются строками.

Вторая строка выведет `false`, потому что `^` и `$` требуют совпадения всей строки, а суффикс `-extra` не входит в шаблон.

У шаблона нет флагов `g` и `y`, поэтому предыдущий вызов `exec` не влияет на последующий вызов `test`.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Применение | Ограничение |
| --- | --- | --- |
| Поиск по тексту | Выделение и извлечение совпадений | Экранировать буквальный пользовательский ввод |
| Простая проверка формата | Код заказа, маска, slug | Бизнес-правила проверяются отдельно |
| Замена текста | `replace`, `replaceAll` с группами | Учитывать специальные последовательности замены |
| Разбор URL и JSON | Не использовать `RegExp` как основной парсер | Есть `URL` и `JSON.parse` |
| Обработка длинного ввода | Проверять худший случай | Не блокировать main thread сложным backtracking |
