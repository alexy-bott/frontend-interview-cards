## Вопрос

<br>

 💬 **Чем отличаются `localStorage`, `sessionStorage` и `IndexedDB`? Как выбрать браузерное хранилище?**

<h2></h2>

<br>
<dl>
<dd>

`localStorage` и `sessionStorage` относятся к Web Storage API. Они хранят пары строковых ключей и значений и предоставляют синхронные методы `getItem`, `setItem`, `removeItem` и `clear`.

Синхронность означает, что чтение, запись и удаление выполняются на main thread и блокируют текущий JavaScript-код до завершения операции. Это может задерживать интерфейс при больших значениях, частых обращениях, регулярной JSON-сериализации или на медленном устройстве.

`localStorage` используется документами одного origin и сохраняется между перезапусками браузера, пока данные не удалит приложение, пользователь или политика хранения браузера.

`sessionStorage` изолирован по origin и вкладке. Он сохраняется при перезагрузке страницы, но обычно удаляется после закрытия соответствующей вкладки или окна.

Новая вкладка, открытая с доступным `opener`, может первоначально получить копию `sessionStorage` исходной вкладки. После создания вкладки эти хранилища независимы: последующие изменения между ними автоматически не синхронизируются.

Web Storage хранит только строки. Объекты обычно преобразуют через JSON, но при чтении нужно учитывать повреждённую запись, изменение схемы и ограничения самого JSON:

```js
const key = "settings:v2";
localStorage.setItem(key, JSON.stringify({ theme: "dark" }));

let settings;
try {
  settings = JSON.parse(localStorage.getItem(key) ?? "null");
} catch {
  localStorage.removeItem(key);
  settings = null;
}
```

`IndexedDB` — асинхронная транзакционная база данных браузера. Она предназначена для большого количества структурированных записей и операций, которые не должны синхронно блокировать main thread.

IndexedDB хранит значения по алгоритму structured clone. Он поддерживает, например, объекты, массивы, `Date`, `Blob`, `ArrayBuffer`, `Map` и `Set`. При этом функции, DOM-узлы и некоторые специальные объекты сохранить нельзя, а пользовательские методы и прототипы классов не следует считать частью сохраняемой модели.

Данные размещаются в object stores — хранилищах записей. Записи имеют ключи, indexes позволяют искать по дополнительным полям, а transactions объединяют связанные операции чтения или записи в атомарную группу.

IndexedDB подходит для offline-данных, больших прикладных кешей, файлов, истории операций и очередей синхронизации.

Выбор зависит не только от размера данных, но и от времени жизни и модели доступа:

| Требование | Подходящий API |
| --- | --- |
| Небольшая настройка между сессиями | `localStorage` |
| Временное состояние только вкладки | `sessionStorage` |
| Много структурированных записей и запросы по index | `IndexedDB` |
| HTTP Request/Response для offline | Cache API |
| Cookie-сессия, отправляемая серверу | Cookie, не storage API |

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему нельзя считать объём storage фиксированным?</strong></summary>

<dl>
<dd>
<h2></h2>

Доступный объём зависит от браузера, устройства, свободного места, origin, режима приватности и политики пользователя.

При нехватке места запись может выбросить `QuotaExceededError`. Доступ к Web Storage также может быть запрещён настройками браузера или политикой документа, что способно привести к `SecurityError`.

Кроме того, браузер или пользователь может очистить сохранённые данные. Поэтому приложение должно обрабатывать отказ при чтении и записи и не хранить единственную копию критически важных данных только в браузере.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как версионировать данные в <code>localStorage</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Версию можно включить в имя ключа:

```js
const key = "settings:v2";
```

Другой вариант — хранить объект с отдельным полем версии.

После чтения нужно проверить структуру данных и при необходимости выполнить явную миграцию. Запись могла быть создана старой версией приложения, повреждена, изменена вручную или содержать неожиданную структуру.

Если версия несовместима и безопасной миграции нет, обычно лучше удалить кешированную запись и применить значение по умолчанию, чем без проверки считать её актуальным TypeScript-типом.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как работает событие <code>storage</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Изменение `localStorage` вызывает событие `storage` в других документах того же origin, использующих соответствующее хранилище.

Документ, который сам выполнил запись, это событие не получает.

Событие содержит:

- `key` — изменённый ключ;
- `oldValue` — предыдущее значение;
- `newValue` — новое значение;
- `url` — адрес документа, выполнившего изменение;
- `storageArea` — изменённое хранилище.

Это удобно для простых сигналов между вкладками, например синхронизации темы или выхода из аккаунта.

При этом `storage` event не создаёт транзакцию между вкладками. Если несколько вкладок одновременно выполняют последовательность read-modify-write, одно изменение может перезаписать другое.

Для более явного обмена сообщениями между вкладками можно использовать `BroadcastChannel`.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Можно ли хранить access token в <code>localStorage</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

Любой JavaScript-код, выполняющийся в текущем origin, может прочитать `localStorage`. Поэтому при XSS-уязвимости злоумышленник может получить сохранённый access token и передать его за пределы приложения.

HttpOnly cookie недоступна JavaScript и снижает риск прямой кражи токена. Но браузер автоматически отправляет такую cookie с подходящими запросами, поэтому архитектура должна учитывать CSRF, атрибуты `SameSite`, `Secure` и другие серверные меры защиты.

HttpOnly также не устраняет XSS полностью: вредоносный код может выполнять разрешённые действия от имени пользователя, даже не читая значение cookie.

Выбор способа хранения токенов делают вместе с backend с учётом модели угроз, срока жизни токенов и механизма обновления. Само хранилище не исправляет XSS-уязвимость приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему <code>localStorage</code> нельзя использовать как реактивный state store?</strong></summary>

<dl>
<dd>
<h2></h2>

Web Storage является синхронным строковым хранилищем, а не системой управления состоянием.

Частые чтения, записи и JSON-преобразования выполняются на main thread и могут замедлять интерфейс. Текущая вкладка также не получает `storage` event после собственной записи.

Кроме того, Web Storage не предоставляет транзакции для последовательности операций. Одновременные изменения из разных вкладок могут перезаписать друг друга.

Актуальное состояние обычно держат в памяти приложения, где оно участвует в реактивных обновлениях. `localStorage` используют как отдельный слой сохранения: записывают данные с контролируемой частотой, проверяют их схему и восстанавливают при запуске.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Из чего состоит IndexedDB?</strong></summary>

<dl>
<dd>
<h2></h2>

База IndexedDB имеет имя и числовую версию.

Object store хранит записи. Каждая запись имеет ключ, который может передаваться отдельно или извлекаться из поля объекта через `keyPath`.

Index создаёт дополнительный путь поиска по значениям определённого поля, не меняя основной ключ записи.

Transaction определяет группу связанных операций и режим доступа: только чтение или чтение с записью. Успешная транзакция фиксирует изменения целиком, а при ошибке может быть отменена.

Request представляет отдельную операцию IndexedDB и сообщает о результате через события. Cursor позволяет последовательно обходить записи или диапазон ключей.

Нативный API основан на событиях. На практике часто используют Promise-обёртку вроде `idb`, но она не отменяет правила версий, транзакций и обновления схемы.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Почему нельзя ожидать сетевой запрос внутри активной IndexedDB transaction?</strong></summary>

<dl>
<dd>
<h2></h2>

IndexedDB-транзакция рассчитана на короткую последовательность связанных операций с базой.

Она может автоматически завершиться, когда управление вернулось event loop и у транзакции больше нет ожидающих IndexedDB requests.

Если внутри транзакции выполнить:

```js
await fetch(url);
```

сетевая операция продолжится позже, а транзакция к этому моменту может уже перейти в неактивное состояние. Последующая попытка записи тогда способна привести к `TransactionInactiveError`.

Поэтому сетевые данные сначала получают вне write transaction. После этого открывают короткую транзакцию и выполняют внутри неё только необходимые операции IndexedDB.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что происходит при изменении схемы IndexedDB?</strong></summary>

<dl>
<dd>
<h2></h2>

Для изменения схемы базу открывают с увеличенной версией:

```js
indexedDB.open("app", 2);
```

Во время события `upgradeneeded` выполняется versionchange transaction. В ней создают, удаляют или изменяют object stores и indexes, а также при необходимости мигрируют данные.

Если база уже открыта в другой вкладке, старое соединение может заблокировать обновление. Старые вкладки получают событие `versionchange` и должны закрыть соединение.

Новый запрос открытия может получить состояние `blocked`. Интерфейс должен уметь сообщить пользователю, что для обновления базы нужно закрыть или перезагрузить другие вкладки приложения.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Гарантирует ли IndexedDB постоянное хранение?</strong></summary>

<dl>
<dd>
<h2></h2>

Нет. IndexedDB использует дисковую квоту origin и по умолчанию может относиться к хранилищу, которое браузер способен очистить при нехватке места или по решению пользователя.

Метод `navigator.storage.persist()` позволяет запросить persistent storage, которое браузер будет реже удалять автоматически. Но решение о предоставлении такого режима принимает сам браузер.

Для действительно важных данных источником восстановления должен оставаться сервер, экспорт пользователя или другой независимый механизм. IndexedDB не следует считать гарантированной единственной копией.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем IndexedDB отличается от Cache API?</strong></summary>

<dl>
<dd>
<h2></h2>

IndexedDB хранит прикладные записи и предоставляет ключи, indexes и transactions. Она подходит, например, для сообщений, черновиков, сущностей приложения и очередей синхронизации.

Cache API хранит пары HTTP `Request` и `Response`. Его часто использует Service Worker для offline-стратегий и кеширования сетевых ресурсов.

Эти API могут применяться вместе. Например, сами HTTP-ответы хранятся в Cache API, а метаданные, состояние синхронизации и информация о сроке актуальности — в IndexedDB.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что учитывать при SSR?</strong></summary>

<dl>
<dd>
<h2></h2>

На сервере нет объектов `window`, `localStorage`, `sessionStorage` и IndexedDB. Обращаться к ним можно только после выполнения кода в браузере.

Если сервер отрендерил интерфейс с одной темой или состоянием авторизации, а первый клиентский render сразу прочитал другое значение из storage, HTML и результат React могут не совпасть. Это приводит к визуальному переключению или hydration mismatch.

Начальное значение можно передать через серверную разметку или cookie, применить небольшой ранний безопасный script до отображения страницы либо прочитать storage после hydration и отдельно обновить интерфейс.

Конкретный подход зависит от того, должно ли сохранённое значение влиять на самый первый отображаемый кадр.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

| Ситуация | Хранилище | Что учитывать |
| --- | --- | --- |
| Theme и locale | `localStorage` | Версия, SSR и отсутствие доступа |
| Черновик текущей вкладки | `sessionStorage` | Вкладки изолированы |
| Offline records | IndexedDB | Schema upgrade и короткие transactions |
| Cross-tab logout | `storage` event или BroadcastChannel | Источник события сам его не получает |
| HTTP offline cache | Cache API | Политика обновления и размер |
| Sensitive auth | Архитектурное решение | XSS/CSRF, не только удобство API |
