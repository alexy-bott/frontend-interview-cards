## Вопрос

<br>

 💬 **Что важно учитывать для доступности в React-приложении и при использовании Radix UI?**

<h2></h2>

<br>
<dl>
<dd>

React не меняет правила доступности браузера. JSX должен в итоге создать правильные HTML-элементы, доступные имена, состояния и клавиатурное поведение. Компонентная абстракция полезна только тогда, когда сохраняет этот DOM-контракт.

Компонент поля должен передать на реальный `<input>` `id`, `name`, `type`, `autocomplete`, `aria-describedby`, `aria-invalid`, обработчики и `ref`. Нельзя оставить эти атрибуты на внешнем `div`: вспомогательные технологии и библиотека форм должны взаимодействовать именно с контролом.

Для уникальной связи подписи и поля при SSR используют `useId()`: React создаёт идентификатор, согласованный между серверным HTML и hydration — подключением React к серверной разметке. Один результат `useId()` можно использовать как префикс для `id` поля, подсказки и ошибки.

`useId()` предназначен для accessibility-связей и других идентификаторов внутри компонента. Его не используют как `key` элементов списка: ключ должен происходить из данных.

`ref` нужен библиотеке форм, Radix и собственному коду для фокуса, измерения DOM или восстановления фокуса.

В React 18 функциональный компонент получает внешний `ref` через `forwardRef`. В React 19 `ref` можно принимать как prop и передавать DOM-элементу напрямую; `forwardRef` больше не нужен для новых компонентов. Если библиотека или дизайн-система поддерживает обе версии React, её публичный контракт выбирают с учётом этой совместимости.

Portal меняет положение узла в DOM, но сохраняет его в React-дереве. Это удобно для dialog, menu, popover и tooltip, однако доступность определяется итоговой DOM-структурой и поведением.

Для модального dialog нужно управлять начальным и возвращаемым фокусом, удерживать фокус внутри и делать фон недоступным для взаимодействия. Tooltip, menu и немодальный popover не должны автоматически делать остальную страницу `inert`: их фокус и клавиатурное управление зависят от конкретного паттерна.

Radix UI предоставляет headless primitives — неоформленные базовые компоненты — с ролями, состояниями и значительной частью клавиатурного поведения. Приложение всё равно отвечает за содержимое, понятные подписи, правильную композицию, видимый фокус и проверку полного сценария.

Например, `Dialog.Title` задаёт доступное имя Radix Dialog, а `Dialog.Description` при необходимости добавляет описание. Библиотека не может самостоятельно придумать подходящий заголовок и текст для конкретного окна.

При `asChild` Radix не создаёт свой стандартный DOM-элемент, а объединяет необходимые props, обработчики и `ref` с переданным дочерним элементом.

Если используется пользовательский компонент, он обязан передать все полученные props и `ref` на настоящий DOM-узел и сохранить правильную семантику. `Dialog.Trigger asChild` с нефокусируемым `div` всё равно останется ошибкой: `asChild` не превращает неподходящий элемент в доступную кнопку.

</dd>
</dl>
<br>


## Дополнительные вопросы

<details>
<summary><strong>Почему пользовательские компоненты могут ломать подписи полей?</strong></summary>

<dl>
<dd>
<h2></h2>

Если компонент поля ввода не передаёт `id`, `aria-describedby`, `aria-invalid`, обработчики или `ref` на реальный DOM-контрол, внешний `label` и библиотека форм могут потерять с ним связь.

Распространённая ошибка — применить полученные атрибуты к внешнему `div`, а не к вложенному `<input>`.

Визуально поле останется на странице, но его доступное имя, описание, состояние ошибки или программная фокусировка могут работать неправильно.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Что такое прокидывание <code>ref</code> и зачем оно нужно для доступности?</strong></summary>

<dl>
<dd>
<h2></h2>

Это передача ссылки на настоящий DOM-элемент через компонент-обёртку.

Библиотека форм использует её, чтобы сфокусировать ошибочное поле, а Radix — чтобы измерить trigger или вернуть на него фокус после закрытия слоя.

В React 18 для этого обычно нужен `forwardRef`. В React 19 функциональный компонент может принять `ref` как prop и передать его DOM-элементу.

`ref` применяют для императивных действий вроде фокуса и измерения, а не как замену props и state.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Зачем <code>useId</code> и можно ли использовать случайный id?</strong></summary>

<dl>
<dd>
<h2></h2>

`useId()` создаёт уникальный идентификатор для связей `label`/`input`, `aria-describedby` и `aria-labelledby`, в том числе при SSR и hydration.

`Math.random()` во время рендера может дать разные значения на сервере и клиенте, а один жёстко заданный `id` конфликтует при нескольких экземплярах компонента.

Один идентификатор можно использовать как префикс:

```jsx
const id = useId();

<input
  id={`${id}-input`}
  aria-describedby={`${id}-hint ${id}-error`}
/>
```

`useId()` не используют для создания `key` в списке. Ключ должен быть связан с идентификатором данных и сохраняться при изменении порядка элементов.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Чем опасен <code>asChild</code>?</strong></summary>

<dl>
<dd>
<h2></h2>

`asChild` заменяет стандартный DOM-элемент Radix переданным дочерним элементом и объединяет с ним необходимые props.

Если дочерний пользовательский компонент не передаёт все props на DOM, теряются обработчики, состояния и ARIA-атрибуты. Если он не принимает и не передаёт `ref`, могут сломаться измерение и управление фокусом.

Разработчик также отвечает за семантику замены: trigger действия обычно должен остаться кнопкой, а элемент перехода по URL — ссылкой.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Нужно ли тестировать Radix-компоненты?</strong></summary>

<dl>
<dd>
<h2></h2>

Да. Библиотека тестирует собственный примитив, но не знает, какой элемент передан в `asChild`, есть ли у Dialog понятный заголовок, виден ли фокус после пользовательских стилей и не изменили ли обработчики стандартное поведение.

Проверяют итоговую композицию: клавиатуру, доступные имена, открытое и закрытое состояния, формы, SSR/hydration, Portal, начальный фокус и его возврат.

Для Radix Dialog отдельно проверяют наличие `Dialog.Title`. `Dialog.Description` добавляют, когда окну действительно нужно дополнительное описание.

<h2></h2>
</dd>
</dl>

</details>

<details>
<summary><strong>Как доступность связана с дизайн-системой?</strong></summary>

<dl>
<dd>
<h2></h2>

Если библиотека компонентов правильно реализует `Button`, `Input`, `Dialog`, `Tooltip` и `Select`, продуктовые команды реже повторяют одни и те же ошибки.

Дизайн-система фиксирует семантику, доступные имена, клавиатурные паттерны, состояния, стили фокуса и требования к тестированию, а затем переиспользует их в разных функциях продукта.

При этом она не должна скрывать важные нативные props. Пользователь компонента должен иметь возможность передать `id`, `name`, ARIA-атрибуты, обработчики и `ref` на правильный DOM-элемент.

<h2></h2>
</dd>
</dl>

</details>

## Где это встречается во frontend

- Обёртка поля ввода прокидывает `id`, `aria-describedby`, ошибку и `ref` на настоящий `<input>`.
- Radix Dialog получает заголовок, при необходимости описание и корректную кнопку закрытия.
- Компонент Button сохраняет семантику настоящего `button`.
- При смене маршрута пользователь получает понятный новый контекст.
- Стили `focus-visible` проверяются во всех вариантах компонента.
- Компонент с `asChild` распространяет props и передаёт `ref`.
