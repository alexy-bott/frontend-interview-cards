Имена файлов в этой таблице являются каноническими для данного комплекта. Внутренние ссылки между правилами должны использовать эти имена.

Этот документ задаёт не новый уровень правил, а порядок применения уже существующих уровней.

Уровни 1–4 описывают требования к состоянию карточки.

Уровень 5 описывает осмысленное изменение содержания и структуры текущего состояния.

Служебные элементы репозитория, управляемые автоматически, обновляются внешним штатным механизмом репозитория и затем снова проверяются уровнями 1–4.

Главный цикл:

```text
текущее состояние
↓
1 → 2 → 3 → 4
↓
все PASS?
├── нет
│   ↓
│   5
│   ↓
│   новая текущая версия
│   ↓
│   служебное обновление репозитория, если требуется
│   ↓
│   1 → 2 → 3 → 4
│
└── да
    ↓
    остались блокирующие локальные NOT CHECKED?
    ├── да → полный статус готовности недоступен до фактической проверки
    └── нет
        ↓
        кандидат на готовность Vn
        ↓
        fresh review: новый независимый проход 1 → 2 → 3 → 4 для той же Vn
        ├── FAIL
        │   ↓
        │   5
        │   ↓
        │   новая версия → полный основной цикл → новый fresh reviewer
        ├── независимая проверка NOT CHECKED
        │   ↓
        │   полный статус готовности недоступен
        └── INDEPENDENT PASS(Vn)
            ↓
            финальная проверка
            ↓
            есть подозрение на регрессию?
            ├── да → повторить соответствующий уровень 1–4
            └── нет
                ↓
                репозиторные проверки, если доступны
                ↓
                полный статус определяется по результатам проверки
```

Шестой уровень не вводится.

Повторная проверка выполняется теми же уровнями 1–4.

Independent fresh review является gate процесса, а не новым уровнем правил.

## Обозначения процесса

Слова `BUILD`, `VALIDATE`, `ANALYZE` и `EDIT` в схемах этого документа обозначают роль уровня в конкретном проходе.

Обозначения вида `[Уровень N: ...]`, встречающиеся в структурных спецификациях, являются маркерами содержательных позиций. Они описывают границу ответственности между уровнями и никогда не являются операцией замены реального содержимого.

В режиме проверки (`VALIDATE` / `ANALYZE`) существующие данные сохраняются на месте: проверяющий уровень только оценивает требования своей ответственности и не подставляет вместо данных маркеры спецификации.

Для уровня 3 режимы `BUILD` и `VALIDATE` являются явно закреплёнными правилами самого уровня.

Для уровней 1–2 эти слова в схемах не создают новых самостоятельных подуровней: при первичном создании их правила используются для формирования структуры, а при последующих проходах — только для проверки текущего состояния.

### Общий контракт проверки уровней 1–4

Каждый проверяющий уровень возвращает либо:

```text
PASS
```

либо один или несколько результатов:

```text
FAIL
Уровень: [1–4]
Правило: [конкретное нарушенное правило]
Место: [блок, элемент или позиция]
Причина: [что именно не соответствует правилу]
```

Если отдельную под-проверку нельзя выполнить из-за отсутствия достоверных входных данных, основной контракт `PASS/FAIL` уровня не меняется. Дополнительно указывается:

```text
[Под-проверка]: NOT CHECKED
Причина: [каких достоверных данных не хватает]
```

Локальный `NOT CHECKED`:

- относится только к конкретной под-проверке;
- не является подтверждением соответствия этого требования;
- не является нарушением сам по себе;
- не отменяет остальные доступные проверки;
- не равен `REPO NOT CHECKED`.

Локальная под-проверка может быть **блокирующей для полного статуса готовности**, если соответствующее правило прямо так её определяет. Блокирующий `NOT CHECKED` не превращается в `FAIL`: доступные требования уровня по-прежнему получают обычный `PASS/FAIL`, но карточку нельзя объявить `готово`, пока под-проверка не выполнена фактически.

В текущем комплекте блокирующей является проверка актуальности существенных изменяемых технических утверждений, определённая уровнем 4. Ошибка в таких утверждениях может изменить понимание темы или практическое решение читателя, поэтому отсутствие проверки нельзя компенсировать корректной структурой или качеством остальных фрагментов.

Уровень 5 получает этот список нарушений. Дополнительно он может получить `REPO FAIL`, если репозиторное нарушение требует изменения содержимого карточки.

Проверяющие уровни и репозиторные проверки не описывают готовую правку вместо уровня 5.

### Результат independent fresh review

Если новый независимый проход уровней 1–4 не выявил нарушений и не оставил блокирующих локальных `NOT CHECKED`, дополнительно фиксируется процессный статус:

```text
INDEPENDENT PASS
Версия: [идентификатор или другое достоверное подтверждение проверенной версии Vn]
```

Если независимую проверку нельзя фактически выполнить в отдельном свежем контексте, фиксируется:

```text
Независимая проверка: NOT CHECKED
Причина: отдельный свежий контекст недоступен или независимость проверки нельзя подтвердить
Влияние: блокирует статус готово
```

`INDEPENDENT PASS` и `Независимая проверка: NOT CHECKED` являются статусами процесса, а не результатами шестого уровня.

Нарушения, обнаруженные fresh reviewer, возвращаются по обычному доказательному формату `FAIL` соответствующего уровня 1–4. Отдельный статус `INDEPENDENT FAIL` не вводится.

Fresh reviewer только диагностирует текущее состояние. Он не редактирует карточку или другие файлы, не применяет уровень 5 и не описывает готовую правку вместо него.

## 1. Два начальных сценария

### Создание новой карточки

При создании новой карточки:

```text
уровень 1
→ формирует внешний каркас

уровень 2
→ формирует внутренние структурные блоки

уровень 3 BUILD
→ собирает и распределяет содержательный черновик

уровни 1 → 2 → 3 VALIDATE → 4
→ проверяют сформированное текущее состояние
```

Первичный `BUILD` уровня 3 выполняется один раз для появления содержательного черновика.

После этого уровень 3 больше не пересоздаёт содержание.

### Проверка уже существующей карточки

Если на входе уже есть заполненная карточка, её содержимое сразу считается текущим состоянием.

В этом случае уровни 1–4 применяются как проверка:

```text
1 VALIDATE
→ 2 VALIDATE
→ 3 VALIDATE
→ 4 ANALYZE
```

Существующая карточка не пересобирается уровнями 1–3 перед анализом.

### Базовая версия для финального сравнения

Для существующей карточки базовой версией считается файл, полученный на входе до первого применения уровня 5.

Для новой карточки базовой версией считается первый полный вариант `V1`, полученный после первичного `BUILD` уровня 3 и формирования структуры уровнями 1–2.

Базовая версия используется только для обнаружения возможной регрессии. Она не является эталоном формулировок и не должна автоматически восстанавливаться поверх улучшенной текущей версии.

---

## 2. Первичная проверка текущего состояния

Перед редактированием текущая версия проверяется последовательно.

### Уровень 1

Проверяет внешний каркас:

- формат файла;
- H1;
- верхнюю навигацию;
- расположение внутренней области;
- `Связанные темы`;
- `Источники`;
- разделитель;
- нижнюю навигацию.

На этапе проверки уровень 1 ничего не изменяет.

### Уровень 2

Проверяет:

- наличие нужных внутренних блоков;
- их порядок;
- нормативную Markdown/HTML-разметку;
- структуру дополнительных вопросов;
- структуру стандартизированных динамических блоков.

На этапе проверки уровень 2 ничего не изменяет.

### Уровень 3

Используется только в режиме `VALIDATE`.

Проверяет:

- тему и её содержательное соответствие;
- главный вопрос;
- наличие необходимых смысловых частей;
- распределение материала;
- дополнительные вопросы;
- данные динамических блоков;
- связанные темы;
- источники как конкретные данные раздела.

Он не создаёт новый черновик и не возвращает старое состояние.

### Уровень 4

Анализирует качество:

- техническую корректность;
- полноту;
- понятность;
- перегруженность;
- избыточность.

Он не вносит изменения.

## 3. Решение после проверки

Если хотя бы один уровень возвращает `FAIL`, все обнаруженные нарушения передаются уровню 5.

Если уровни 1–4 одновременно возвращают `PASS` и не осталось блокирующих локальных под-проверок со статусом `NOT CHECKED`, текущая версия `Vn` становится **кандидатом на готовность**, но процесс ещё не завершён.

Кандидат — это конкретная версия, для которой:

- основной цикл уровней 1–4 дал полный `PASS`;
- отсутствуют блокирующие локальные `NOT CHECKED`;
- применимые служебные обновления, способные изменить карточку, уже выполнены;
- после последнего изменения выполнен полный основной цикл.

Для каждого кандидата один раз запускается independent fresh review той же неизменённой версии:

```text
1–4 PASS для Vn
→ блокирующие локальные NOT CHECKED отсутствуют
→ кандидат на готовность Vn
→ fresh review той же Vn
```

Fresh reviewer:

- работает в отдельной сессии, отдельном агенте или другом реально свежем контексте;
- получает одну карточку и тот же канонический комплект правил с `00-workflow.md` как точкой входа;
- не получает вердикт, аргументы, отчёт, подсказки о проблемах или защиту решения основного прохода;
- не использует основной проход как доказательство соответствия;
- самостоятельно проверяет применимые актуальные первичные источники там, где этого требует уровень 4;
- применяет уровни 1–4 только диагностически и проверяет одну карточку за раз;
- завершает назначенный fresh review после результатов уровней 1–4 и не запускает из него ещё один independent fresh review;
- не выполняет отдельные репозиторные проверки: они остаются последующим этапом после independent fresh review и финального сравнения.

Передача пути, фактического содержимого кандидата, канонических правил и необходимого контекста репозитория не нарушает независимость. Передача вывода основного прохода нарушает её, потому что создаёт риск якорения на прежнем решении.

Если уровни 1–4 дали `PASS`, но остался блокирующий `NOT CHECKED`, доступная часть проверки завершена, однако версия не становится кандидатом на полный статус готовности. Нужно получить достоверные данные и выполнить эту под-проверку; изменение карточки уровнем 5 требуется только тогда, когда фактическая проверка подтвердит нарушение.

Перед статусом `готово` обязательны `INDEPENDENT PASS` той же версии, финальная проверка на регрессии и применимые репозиторные проверки.

Если independent fresh review нельзя выполнить и зафиксирован `Независимая проверка: NOT CHECKED`, кандидат не получает статус `готово`. Фактический fresh review должен быть выполнен позднее для той же неизменённой версии либо для новой версии после полного основного цикла. Сам `NOT CHECKED` не считается выполненным запуском review.

Уровень 5 получает именно текущую версию и конкретные нарушения.

## 4. Применение уровня 5

Уровень 5:

- исправляет выявленные структурные нарушения;
- исправляет нарушения состава и распределения содержания;
- исправляет проблемы качества;
- сохраняет уже корректные части, если их изменение не требуется;
- создаёт новую текущую версию.

После уровня 5 нельзя считать работу завершённой без новой проверки.

Если нарушение найдено fresh reviewer, он завершает работу после диагностики. Конкретный `FAIL` передаётся уровню 5 в основном рабочем процессе.

---

## 5. Обязательная повторная проверка после уровня 5

После любого применения уровня 5 заново выполняется полный проход:

```text
1 → 2 → 3 → 4
```

Это обязательное правило.

Нельзя проверять только тот уровень, нарушение которого исправлялось.

Если уровень 5 применён после `FAIL` независимого reviewer, порядок продолжается так:

```text
fresh review Vn → FAIL уровня 1–4
→ reviewer завершает диагностику
→ уровень 5 изменяет карточку
→ Vn+1
→ полный основной цикл 1 → 2 → 3 → 4
→ при PASS новый кандидат Vn+1
→ новый fresh reviewer
```

Нельзя:

- исправлять карточку внутри fresh review;
- продолжать тот же fresh-контекст после уровня 5 до положительного результата;
- проверять только уровень, на котором fresh reviewer нашёл нарушение;
- переносить основной или независимый `PASS` с `Vn` на `Vn+1`.

Новый fresh reviewer не получает прежний независимый `FAIL`, выполненную правку или её обоснование.

Причина: правка одного аспекта может создать регрессию в другом.

Примеры:

```text
исправление уровня 4
→ случайно ломает HTML
→ обнаруживает уровень 2
```

```text
перенос материала ради понятности
→ случайно удаляет необходимую смысловую часть
→ обнаруживает уровень 3
```

```text
структурная правка
→ случайно повреждает путь навигации
→ обнаруживает уровень 1
```

---

## 6. Повторная проверка не является повторной генерацией

После уровня 5 уровни 1–4 работают только как проверяющие.

Они не должны перестраивать карточку самостоятельно.

Особенно важно для уровня 3:

```text
первичное создание:
уровень 3 BUILD

после любой правки:
уровень 3 VALIDATE
```

Повторный уровень 3 не имеет права:

- заново генерировать основной ответ;
- возвращать старые дополнительные вопросы;
- восстанавливать первоначальный порядок материала только потому, что он был в черновике;
- перезаписывать улучшенные формулировки более ранними;
- считать первоначальный черновик нормативной версией.

---

## 7. Принцип текущей версии

В каждый момент существует одна текущая версия.

Схема:

```text
V1
↓ проверка
уровень 5
↓
V2 — новая текущая версия
↓ проверка
уровень 5
↓
V3 — новая текущая версия
```

После появления `V2` именно она является объектом следующей проверки.

`V1` становится исторической версией.

Для independent gate версия означает точное фактическое содержимое карточки, включая нормативный Markdown/HTML-каркас и служебные элементы уровня 1. Конкретный технический идентификатор не навязывается: отсутствие изменений можно подтвердить снимком содержимого, blob/hash или эквивалентным точным сравнением.

Основной `PASS` и последующий `INDEPENDENT PASS` должны относиться к одной и той же неизменённой версии `Vn`.

Любое изменение карточки после одного из подтверждений:

- создаёт новую текущую версию;
- аннулирует основной и независимый `PASS` прежней версии;
- требует полного основного цикла для новой версии;
- после нового основного `PASS` требует нового fresh review в новом независимом контексте.

Исторические `PASS` разных версий нельзя объединять для получения статуса `готово`.

Историческая версия может использоваться:

- для сравнения;
- для обнаружения случайно утраченного полезного смысла;
- для объяснения, что именно изменилось.

Она не используется как шаблон автоматического восстановления.

---

## 8. Защита улучшений

Повторная проверка не должна отменять изменение только потому, что оно отличается от первоначального черновика.

Изменение отменяется или перерабатывается только если текущая версия нарушает конкретное правило уровней 1–4.

Сохранение полезного улучшения не сохраняет подтверждения прежней версии: если содержимое изменилось, новая версия заново доказывает соответствие основным и независимым проходами.

Пример:

```text
V1:
частный случай находится в основном ответе

уровень 4:
подача перегружена

уровень 5:
частный случай перенесён в дополнительный вопрос

V2:
уровень 3 проверяет содержательную допустимость нового положения

если положение допустимо:
PASS

нельзя:
вернуть частный случай обратно только потому,
что так было в V1
```

---

## 9. Защита от регрессий

Каждая новая версия должна повторно доказать соответствие всем уровням состояния.

Условие появления кандидата на independent fresh review:

```text
Уровень 1 → PASS
Уровень 2 → PASS
Уровень 3 → PASS
Уровень 4 → PASS
Блокирующие локальные под-проверки → выполнены
```

Этот результат делает версию кандидатом на готовность. Финальный статус определяется только после independent fresh review, финальной и репозиторной проверки.

Кандидат проходит один fresh review. Он не запускается после каждой промежуточной правки до полного основного `PASS` и не повторяется для той же неизменённой версии после уже полученного `INDEPENDENT PASS` без нового основания.

Условие перехода кандидата к финальному сравнению:

```text
основной PASS(Vn)
→ последующий INDEPENDENT PASS(Vn)
```

Это два последовательных подтверждения одной версии, а не два любых `PASS` в истории карточки.

Если новый `FAIL` появился после правки, это регрессия текущей версии.

Она снова исправляется уровнем 5 и затем снова проходит полный цикл.

## 10. Репозиторные проверки

Репозиторные проверки не являются шестым уровнем и не подменяют уровни 1–5. Они проверяют инварианты, которые невозможно подтвердить по одной карточке.

Репозиторный этап начинается после `INDEPENDENT PASS(Vn)` и финального сравнения той же неизменённой версии. Он остаётся отдельным от fresh review: независимый reviewer применяет уровни 1–4 к одной карточке, а `REPO PASS` подтверждает инварианты репозитория.

К ним относятся:

- наличие хотя бы одной входящей тематической ссылки на каждую карточку из другой карточки;
- существование целей ссылок там, где это требует проверки файлов репозитория;
- согласованность автоматически генерируемой навигации и страниц разделов.

Результат репозиторной проверки оформляется отдельно от уровней 1–4:

```text
REPO PASS
```

или:

```text
REPO FAIL
Правило: [нарушенный инвариант репозитория]
Объект: [карточка, ссылка, навигационный файл или другой объект]
Причина: [что именно не соответствует правилу]
```

Если `REPO FAIL` требует изменения содержимого одной или нескольких карточек, нарушение передаётся уровню 5 для этих карточек, после чего каждая изменённая карточка снова проходит полный основной цикл уровней 1–4 и новый independent fresh review.

Если `REPO FAIL` относится к автоматически управляемой служебной навигации, исправление выполняется внешним штатным механизмом репозитория, а не вручную уровнем 5.

### Служебная навигация

Навигацию между карточками и другие служебные элементы, которые управляются репозиторием автоматически, не редактируют вручную в рамках правил карточки.

Если после изменения карточки такие элементы требуют актуализации, это выполняется внешним штатным механизмом репозитория.

Конкретные команды, имена скриптов и технический способ такой актуализации не относятся к правилам карточки и в этом документе не задаются.

После внешнего служебного обновления изменённая карточка снова проходит полный основной цикл уровней 1–4 и новый independent fresh review.

Перед финальным завершением, если доступен репозиторий, состояние служебных элементов проверяется штатным механизмом репозитория. Такая проверка не заменяет уровни 1–4.

Если на входе дана только отдельная карточка без доступа к репозиторию, репозиторные проверки нельзя объявлять `PASS` без фактической проверки.

В этом случае итог разделяется на два статуса:

```text
LOCAL PASS
→ основной проход всех доступных локальных проверок уровней 1–4 не выявил нарушений

INDEPENDENT PASS
Версия: [идентификатор или другое достоверное подтверждение проверенной версии Vn]
→ указывается отдельно только после фактически выполненного fresh review той же версии

[локальная под-проверка]: NOT CHECKED
→ указывается отдельно, если конкретное локальное требование нельзя было проверить без достоверных входных данных

Независимая проверка: NOT CHECKED
→ указывается вместо INDEPENDENT PASS, если отдельный свежий контекст недоступен или независимость нельзя подтвердить

REPO NOT CHECKED
→ репозиторные инварианты не проверялись из-за отсутствия доступа
```

`LOCAL PASS` не означает, что локальные под-проверки со статусом `NOT CHECKED` были успешно пройдены. Если такие под-проверки есть, они должны быть явно перечислены рядом с итоговым локальным статусом.

`LOCAL PASS` также не означает, что independent fresh review выполнен. Его результат всегда указывается отдельно; `Независимая проверка: NOT CHECKED` блокирует полный статус готовности так же, как отсутствие `INDEPENDENT PASS`.

`LOCAL PASS` не равен полному статусу готовности карточки внутри репозитория. Полный `REPO PASS` можно заявлять только после фактической репозиторной проверки.

## 11. Конфликт правил и защита от бесконечного цикла

Если одно нарушение невозможно исправить без неизбежного нарушения другого действующего правила, нельзя бесконечно переключаться между двумя вариантами.

Нужно зафиксировать конфликт правил:

```text
правило A требует X
правило B запрещает X
```

и остановить автоматический цикл до изменения или уточнения самих правил.

Уровень 5 не должен самовольно выбирать, какое из конфликтующих правил игнорировать.

### Отсутствие прогресса

Цикл также прекращается, если новая итерация фактически не меняет состояние или снова воспроизводит то же нарушение, а нового обоснованного способа исправления нет.

В таком случае фиксируется:

```text
UNRESOLVED
Правило: [нарушение, которое остаётся]
Причина: повторная правка не устраняет нарушение или возвращает систему в уже проверенное состояние
```

Это не считается `PASS`. Процесс требует уточнения правил или другого способа исправления, а не бесконечного повторения одного и того же цикла.

Если новые независимые проверки повторно находят одно и то же доказательное нарушение, а уровень 5 не создаёт содержательно нового состояния или возвращает карточку к уже проверенной версии, применяется тот же статус `UNRESOLVED`. Само расхождение между основным и независимым reviewer не является основанием для правки: основанием остаётся конкретное нарушенное правило уровня 1–4.

## 12. Финальная проверка текущей версии

Финальное сравнение начинается только после того, как основной цикл и последующий independent fresh review дали `PASS` для одной и той же неизменённой версии `Vn`.

После этого перед завершением сравниваются исходная версия и последняя текущая версия.

Если правка является крупной по правилам уровня 5, в финальном сравнении проверяется временная карта смысла:

| Исходный аспект | Действие | Итоговое место или основание удаления |
|---|---|---|
| [самостоятельный аспект исходной версии] | [сохранён / переписан / перенесён / объединён / удалён] | [конкретный блок текущей версии или подтверждённый `FAIL`] |

Карта используется только для контроля изменения и не добавляется в карточку.

Сравнение используется только для обнаружения случайных регрессий:

- не потерян ли полезный смысл;
- не исчезла ли необходимая деталь;
- не сломаны ли ссылки и пути;
- не повреждена ли навигация;
- не нарушены ли Markdown/HTML и вложенность;
- не изменена ли стилистика повторяющихся блоков без необходимости;
- не ухудшилось ли содержание ради локальной правки.

Исходная версия не считается эталоном формулировок и не восстанавливается автоматически.

Финальное сравнение не создаёт `FAIL` самостоятельно.

Если сравнение обнаруживает возможную регрессию, оно фиксирует **подозрение** и повторно запускает соответствующую проверку:

```text
подозрение на структуру
→ уровень 1 или 2

подозрение на потерю/неверное распределение содержания
→ уровень 3

подозрение на ухудшение качества
→ уровень 4

подозрение на репозиторный инвариант
→ репозиторная проверка
```

Только соответствующий уровень или репозиторная проверка может подтвердить новый `FAIL` / `REPO FAIL`.

Если отличие является улучшением и повторная проверка не подтверждает нарушение, откат не выполняется.

Если повторная проверка не требует изменения карточки и подтверждает `PASS`, основной и независимый `PASS(Vn)` сохраняются. Если подтверждённое нарушение приводит к редактированию, появляется новая версия, оба подтверждения `Vn` аннулируются и процесс возвращается к полному основному циклу.

### Условие завершения

Полный `PASS` уровней 1–4 является обязательным условием, но сам по себе даёт только кандидата на готовность и не завершает процесс.

Полный статус `готово` для карточки внутри репозитория допустим, когда одновременно выполнены условия:

- основной цикл уровней 1–4 дал `PASS` для версии `Vn`;
- не осталось блокирующих локальных под-проверок со статусом `NOT CHECKED`;
- последующий independent fresh review дал `INDEPENDENT PASS` для той же версии `Vn`;
- между основным и независимым подтверждениями, финальным сравнением и завершением карточка не изменялась;
- финальное сравнение не привело к подтверждённому новому `FAIL`;
- репозиторные проверки дали `REPO PASS`;
- применимые внешние проверки служебных элементов выполнены успешно.

Формула полного статуса:

```text
готово для Vn
=
основной PASS(Vn)
+ последующий INDEPENDENT PASS(Vn)
+ отсутствие блокирующих NOT CHECKED
+ финальная проверка
+ REPO PASS
```

Это два последовательных положительных подтверждения одной финальной версии, а не два любых `PASS` в истории карточки.

Если репозиторий недоступен, результат ограничивается `LOCAL PASS`, отдельным статусом independent fresh review и `REPO NOT CHECKED`; полный статус `готово` не заявляется.

Если вместе с `LOCAL PASS` остаются локальные `NOT CHECKED`, они обязательно сохраняются в итоговом статусе до появления достоверных данных. Непроверенная локальная под-проверка не должна молча превращаться в подтверждённый `PASS`. Если под-проверка является блокирующей, полный статус `готово` запрещён независимо от доступности и результата репозиторных проверок.

Последним действием процесса является проверка, а не редактирование. Последняя неизменённая версия должна иметь основной `PASS`, последующий `INDEPENDENT PASS` и `REPO PASS`; одного последнего основного прохода недостаточно.

Правильный финал:

```text
уровень 5
↓
новая текущая версия
↓
служебное обновление репозитория, если требуется
↓
основной цикл: 1 PASS → 2 PASS → 3 PASS → 4 PASS
↓
блокирующие локальные под-проверки выполнены
↓
кандидат на готовность Vn
↓
fresh review Vn в новом независимом контексте
↓
INDEPENDENT PASS(Vn)
↓
финальное сравнение
↓
при подозрении → повтор соответствующей проверки
↓
репозиторные проверки
↓
REPO PASS
↓
готово
```

Неправильный финал:

```text
уровень 5
↓
готово
```

Также неправильно:

```text
1–4 PASS
↓
финальное сравнение
↓
REPO PASS
↓
готово
```

В этой ветке отсутствует обязательный independent fresh review той же версии.

## 13. Формат результата ревью

Если выполняется ревью готовой карточки, после завершения цикла результат должен состоять из четырёх частей.

### 1. Оценка исходной текущей версии

Кратко указываются существенные проблемы, обнаруженные первоначальной проверкой.

Не требуется перечислять всё, что уже было правильно.

### 2. Что изменено

Перечисляются существенные изменения:

- где была проблема;
- что изменено;
- зачем это было необходимо.

Для `Дополнительных вопросов` отдельно указываются существенные добавления, удаления, объединения, разделения и перестановки.

Если изменён кодовый пример, это указывается отдельно.

### 3. Итоговая проверка

Показываются:

- состояние после последнего полного основного прохода уровней 1–4;
- идентификатор версии `Vn` или эквивалентное достоверное подтверждение неизменности;
- отдельный `INDEPENDENT PASS(Vn)`, доказательные `FAIL` fresh reviewer либо `Независимая проверка: NOT CHECKED`;
- сохранившиеся локальные под-проверки со статусом `NOT CHECKED`.

Итоговая положительная оценка допустима только после основного и независимого проходов одной версии, а не сразу после уровня 5 или одного полного прохода уровней 1–4.

### 4. Представление результата

Форма четвёртой части зависит от того, где находится карточка.

#### Репозиторный файл

Для карточки, доступной как файл текущего репозитория, указываются:

- путь к карточке;
- существенный diff, а не повтор всего файла;
- карта смыслового контроля, если правка была крупной;
- результаты основного прохода уровней 1–4;
- версию и отдельный статус independent fresh review;
- отдельный статус `REPO PASS` / `REPO FAIL`.

#### Отдельная переданная карточка

Если на вход передан текст карточки без доступа к её репозиторию:

- возвращается весь итоговый Markdown в одном обычном code block, а не в edit/writing-блоке;
- указываются `LOCAL PASS`, отдельный результат independent fresh review и `REPO NOT CHECKED`;
- сохраняются все локальные под-проверки со статусом `NOT CHECKED`.

В обоих сценариях не добавляются технические атрибуты или служебные элементы, которых нет в нормативной структуре.

## Краткая схема

```text
НОВАЯ КАРТОЧКА
1 BUILD
→ 2 BUILD
→ 3 BUILD
→ 1 VALIDATE
→ 2 VALIDATE
→ 3 VALIDATE
→ 4 ANALYZE

СУЩЕСТВУЮЩАЯ КАРТОЧКА
1 VALIDATE
→ 2 VALIDATE
→ 3 VALIDATE
→ 4 ANALYZE

ЕСЛИ ЕСТЬ FAIL
→ 5 EDIT
→ новая текущая версия
→ внешнее служебное обновление репозитория, если применимо
→ 1 VALIDATE
→ 2 VALIDATE
→ 3 VALIDATE
→ 4 ANALYZE

КОГДА 1–4 ДАЛИ PASS ДЛЯ Vn
→ проверить блокирующие локальные NOT CHECKED
→ если они остались: полный статус готовности недоступен
→ если их нет: кандидат на готовность Vn
→ fresh review Vn в новом независимом контексте
→ если FAIL: 5 EDIT → новая версия → полный основной цикл → новый fresh reviewer
→ если независимая проверка NOT CHECKED: полный статус готовности недоступен
→ если INDEPENDENT PASS(Vn): финальное сравнение
→ при подозрении повторить соответствующую проверку 1–4 / репозиторную проверку
→ если репозиторий доступен: получить REPO PASS и проверить служебные элементы
→ готово

ЕСЛИ РЕПОЗИТОРИЙ НЕДОСТУПЕН
→ LOCAL PASS
→ отдельно указать INDEPENDENT PASS или Независимая проверка: NOT CHECKED
→ REPO NOT CHECKED
→ полный статус готовности внутри репозитория не заявляется
```
